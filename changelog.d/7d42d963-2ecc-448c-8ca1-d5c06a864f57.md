### Fixed

- **A restarted Compose worker can continue a run from its verified saved pin instead of stopping at retained recovery (#3644).**
  The retained predecessor stays held (counting toward `custody_hold_limit`) until the owner's guarded discard of the new attempt then the predecessor, and merging closes only server custody holds (and discards their non-ready captures), never the predecessor's worker-side bytes; a worker started by an older build has no boundary record, so its predecessor is never restored. Rolling back to any build before the restore-enabling release after a restore is unsupported (rc.3 to rc.5 lack the restore code too; the compatibility proof executed the v0.87.0-rc.2 sources): rc.2 can write a reservation and a `preservation_failed` blocker into the predecessor's journal and delete its legacy HOME and provision directories once terminal, while keeping the new attempt's clone and the predecessor's clone bytes, owed refs and pins. If rc.2 reclaimed the predecessor, rolling forward recognises it, but when rc.2's ledger compaction dropped the evidence the roll-forward refuses and the bytes stay (fence tracked by #3981, open); the supported exit is the guarded discard of the new attempt, then the predecessor. Hosted workers, and predecessors started by an older build, refuse; on the normal running path with active-run snapshots such a claim no longer fails with `preservation_failed` but uses up its requeue allowance and usually holds at `worker_requeue_exhausted`, counting toward `custody_hold_limit` (workers without active-run snapshots keep `preservation_failed`). While a retained predecessor is undiscarded, the bare-wide census refuses other independent restores on the same repository (`census_foreign_active`). Crash safety covers process crashes only.
