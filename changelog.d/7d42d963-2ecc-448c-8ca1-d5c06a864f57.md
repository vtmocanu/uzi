### Fixed

- **A restarted Compose worker can continue a run from its verified saved pin instead of stopping at retained recovery (#3644).**
  Restore applies to eligible attempt-path predecessors on Compose, normally Docker-wired, or an unwired key already in the supported persisted attempt mode; a fresh unwired (no-DinD) key keeps canonical paths and is the canonical unsupported class. The retained predecessor stays held (counting toward `custody_hold_limit`) until the owner's guarded discard of the new attempt then the predecessor, and merging closes only server custody holds (and discards their non-ready captures), never the predecessor's worker-side bytes. Canonical, hosted and no-boundary-record (started by an older build) predecessors are refused before any source effect and, when the api advertises `recovery_cause_retained_recovery_adoption_failed`, parked for the owner at `recovery_wait` / `retained_recovery_adoption_failed` with no predecessor byte changed (here the cause means the release does not support the predecessor: no adoption, no persisted blocker, no proven quiescence); Resume holds again and adds a claim and a hold, and an owner-held hosted run blocks its worker's image roll until cancelled or discarded. Without that capability, and for every other refusal, the claim stops nonterminally with server charging: on the running path charged requeues up to `RUN_MAX_REQUEUES` then `worker_requeue_exhausted` when custody is uncertain, on the claimed path uncharged generations up to the run's own hold-admission bound or the server-only `retained_continuation_unwitnessed` park, and a custody-blocked queued run on a live worker may stay queued even at the cap; each accepted generation opens a custody hold counting toward `custody_hold_limit`. Without active-run snapshots, first refusals with no restore entry keep `preservation_failed`; existing restore entries remain blocked (#3999). A restored run reads the default-branch tip from the bare without fetching, so an unpinned restored claim no longer falls into the repo-agent source hold when the bare has `origin/<default>`, and a `--require-base` restore whose planned base differs from the pin holds for attestation instead of failing `base_diverged`. The restore uses the single ordinary pin record of the dead generation (several refuse `pin_ambiguous`, none `no_eligible_pin`); choosing among several records is not implemented. Rolling back to any build before the restore-enabling release after a restore is unsupported (rc.3 to rc.5 lack the restore code too; the compatibility proof executed the v0.87.0-rc.2 sources): rc.2 can write a reservation and a `preservation_failed` blocker into the predecessor's journal and delete its legacy HOME and provision directories once terminal, while keeping the new attempt's clone and the predecessor's clone bytes, owed refs and pins. If rc.2 reclaimed the predecessor, rolling forward recognises it, but when rc.2's ledger compaction dropped the evidence the roll-forward refuses and the bytes stay (fence tracked by #3981, open); the supported exit is the guarded discard of the new attempt, then the predecessor. While a retained predecessor is undiscarded, the bare-wide census refuses other independent restores on the same repository (`census_foreign_active`). Crash safety covers process and container crashes and injected faults only; later live successor journal rewrites are unsynced.
