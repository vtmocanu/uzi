# uzi-release

Cut a uzi release, watch it publish, verify it, then summarize. This repo is hosted on **GitHub**: use `gh` (which infers the repo from the checkout, so a fork under any owner works unedited; never `glab`/`tea`). CI is **GitHub Actions** (`.github/workflows/`), images and the Helm chart publish to **GHCR** on a `v*` tag.

**Boundary.** Reviewing and merging PRs, one or the whole open set, Renovate included, is the `uzi-lander` skill (`references/batch.md` for the set, `references/renovate.md` for dependency PRs). This skill starts once what should ship is on `main`.

Do NOT bake step details that live in the repo into your head. Read the source of truth each run: `.github/workflows/release.yml` (and `ci.yml`, `kind-smoke.yml`, `brew.yml`), `.claude/agents/release.md` (the mechanics reference), the destructive-ops rules in `CLAUDE.md`, and `deploy/README.md` for deploy (still GitLab-worded in places, not the authority for publish mechanics).

> **Note on the deploy layer.** Cluster/deploy verification needs cluster access you may not have; if so, say so plainly rather than guessing.

## 0. Guardrails first
- NEVER `docker compose -p uzi down -v` and never glob `uzi-` containers (see `CLAUDE.md` "Destructive operations"). This skill touches git, `gh`, and (if you have deploy access) `kubectl` only.
- Work on `main` in the repo root worktree; `release-cut.sh` makes its own throwaway worktree for a promote. Never check the root worktree out onto another branch.
- The release commit goes direct to `main` under the admin role's ruleset bypass (`uzi-lander` `references/merge-mechanics.md` has the ruleset). If a push is refused, read the refusal and stop rather than forcing.

## 1. Preconditions: nothing wanted left unmerged, `main` green
- **Nothing wanted in this release is still open.** `gh pr list --state open`, `uzi run list` for in-flight runs. Anything the user wants in the release gets landed first with `uzi-lander` (the whole set: its `references/batch.md`), then come back. Say which open PRs you are leaving out. When unsure what the user wants in, ask.
- **Exact `main` tip green.** Fetch and fast-forward `main`. Watch all existing tip workflows to green with `.agents/skills/uzi-lander/scripts/watch-run-ci.sh --sha "$(git rev-parse origin/main)" --branch main` in the background; require successful `ci.yml` and `kind-smoke.yml` push runs on that exact SHA. Run `python3 -I scripts/release-ci-coverage.py tip HEAD --wait 0` for the shared policy. A missing, queued, running, failed or cancelled run blocks the cut. Wait for the exact tip's ci.yml + KinD success BEFORE release-cut: pushing the release commit supersedes main CI and cancels a running parent, destroying inheritance evidence. `release-cut.sh` repeats this precondition for verbs that write main. For `--promote-only`, validate candidate coverage instead; the current main tip need not be green. Candidate validation accepts at most one strictly metadata hop to green main-push CI and smoke: the stable commit is the publish gate's first hop, so it reaches only one past the candidate (#2719). Do not substitute evidence from an older commit.
- **A Codex runtime bump in the release.** When the range since the previous tag changes `agent/codex/codex-package.lock`, confirm its PR recorded the adoption read and CI coverage that `.agents/skills/uzi-lander/references/renovate.md` (*Agent runtimes*) requires; if not, do that read before cutting.

## 2. Cut the release inline with the deterministic scripts — do NOT dispatch a subagent
Once step 1 holds (nothing wanted left unmerged, `main` green on the tip), cut the release **inline as the lead**, driving three bundled scripts. Do NOT dispatch the `release` subagent for this: a background subagent spawns a watch and then idles, so every wait becomes a manual re-ping (the "agent keeps dying" ping-pong), while the steps that actually need judgment — flake-vs-defect, whether to rerun, authoring the CHANGELOG — are the lead's regardless. `.claude/agents/release.md` stays the MECHANICS reference (what each step proves, the signing traps, deploy verify), but the driver is the lead + scripts, not that agent.

**What the lead decides first** (from what merged since the previous stable tag):

- **The version `X.Y.Z`.** Patch (`0.46.0` → `0.46.1`) for a maintenance/deps/tooling batch with no user-facing feature or behavior change; minor (`0.46.0` → `0.47.0`) when a product feature ships. Patch tags are in this repo's history (`v0.42.1`, `v0.38.1`), so a small batch does not force a minor. Model B: chart `version` == `appVersion` == the tag.
- **RC-first (PRD #1265): which verb.** A release is cut as a CANDIDATE `vX.Y.Z-rc.1` by default and PROMOTED to stable later, from the candidate's own commit, in lockstep with the next candidate. When an RC is already in flight for a lower base, `release-cut.sh` REFUSES with the facts (which RC, since when, whether pending legacy notes plus fragments are empty) and exits 3. That refusal is the lead's cue to ask the user which of four: **promote** the in-flight RC and cut the next candidate (`--promote`, the usual answer once a candidate has been dogfooded), **promote it alone** (`release-cut B --promote-only`, when `main` carries work the user does not want in a candidate yet), cut **another candidate** for the same base (`release-cut B`, when the candidate was not good enough; it assembles legacy `[Unreleased]` plus pending fragments into the open `## [B]` section per canonical category and refuses, CHANGELOG untouched, on text outside a subsection, a non-Keep-a-Changelog subsection name, a duplicate subsection in the result, or a line lost, invented or moved; repeated legacy categories are grouped during assembly), or **abandon** it (`--skip-promote`). `--stable` (the old one-step model) is only for a docs-only release and is refused while an RC is in flight.
  - **RC dogfood install (PRD #1378):** `brew install vtmocanu/tap/uzi-cli-rc` builds the newest candidate from source; it `conflicts_with` the stable `uzi-cli` by design (one active `uzi`), so uninstall stable first if present. Switch back with `brew uninstall uzi-cli-rc && brew install uzi-cli`. Stable users on `uzi-cli` never see a candidate.
  - **Stale in-flight RC, and the stable must contain current `main` (not the old candidate).** When the in-flight RC is many merges behind `main` and you want the stable to ship everything on `main`: you cannot `--stable` (refused while an RC is in flight), and a plain `--promote` tags the OLD rc commit, so neither gives you the tip. The route is rc-at-tip, **PUBLISH it**, then promote: (1) review pending fragments against the oracle's shipping identities (`release-cut` requires committed regular mode-100644 fragments and a clean tracked tree, so an input it refuses at preflight still needs a committed fragment); (2) `release-cut.sh B` cuts `vB-rc.(N+1)` at the tip; if verification rejects missing citations, apply "Non-promote cut, oracle refuses missing citations" below; push `main`; tag immediately once the metadata-only release diff is reviewed; (3) tag that RC and **PUSH it** (`git tag -a vB-rc.(N+1) HEAD`, then `! git push origin vB-rc.(N+1)`), and wait for it to publish (`release-watch.sh` then `release-verify.sh`). Do NOT keep it local-only: the rc cut's `worker-tag-autobump` has already pinned `workers.image.tag` to that RC, so an unpushed tag would leave the stable chart pointing at an `agent-*` image `release.yml` never built (`--promote` REFUSES an in-flight RC that is not on origin). The redundant RC publish is the price of the invariant. (4) `release-cut.sh <B+1> --promote` sees zero delta since the new RC and takes the **promote-only** branch: it tags `vB` from the tip and cuts NO next candidate. Before promotion, require green candidate coverage, directly or through at most one strictly classified metadata hop. Push `vB`, watch, verify. **Wart:** promote-only after an on-main RC cut leaves `main`'s `Chart.yaml` at `B-rc.(N+1)` (behind the stable). Harmless (nothing publishes off `main` until the next tag; ArgoCD tracks the newest published chart = `vB`), and the next feature cut clears it.
  - **The stable must be the candidate exactly, and `main` has moved on.** `release-cut.sh B --promote-only` (B = the in-flight base, not a next version): it tags `vB` from the RC commit and stops. No next candidate, no commit on `main`, no `main` push; work merged after the RC is not in `vB` and ships with the next plain `release-cut <next>`, whose coverage window starts at `vB`. It keeps `--promote`'s published-RC refusal and takes no `--changelog-file`/`--no-commit`/`--prev-tag`. Push `vB` only, watch, verify once. Same wart as above, plus `main`'s `## [B]` date stays at the RC-cut date until the next cut of a new base syncs it from the `vB` tag. Prefer `--promote` when the next candidate is wanted anyway: a plain `--promote` with shipping work on `main` and no pending legacy notes or fragments refuses before promotion creates a stable tag.
- **Review pending notes: legacy `[Unreleased]` plus `changelog.d/` fragments.** Ordinary PRs create a new lowercase UUID-v4 fragment before a PR exists, initially citing the relevant issue; [fragment guidance](../../../changelog.d/README.md) defines the grammar and exemptions. Keep existing legacy bullets until the next cut; direct additions remain accepted during migration. The cutter groups Added, Changed, Deprecated, Removed, Fixed, Security; within each category it preserves legacy order then appends fragments in C filename order. It consumes exactly the incorporated paths in the release commit. No shared index. A manual drafted `## [X.Y.Z] - <date>` via `--changelog-file` remains available with no pending fragments; pending fragments cause refusal before mutation. Use **no em dashes** (user preference for user-facing content). The section is keyed by the STABLE base `X.Y.Z` even for a candidate (PRD #1265 D3). The oracle `scripts/assert-changelog-covers-release.sh` still requires shipping commit identity in that assembled section; fragment touches are not an exemption. Its shipping paths and exemptions live in `scripts/lib/shipping-paths.sh` and the oracle; keep `Changelog: none` with a reason and docs-typed exemptions. `release-cut.sh` cites dependency bumps spared at PR time (`scripts/lib/dependency-bump.sh`) in a fresh `Routine dependency updates` bullet per cut under `### Changed`. Shipped RC bullet blocks stay frozen byte-for-byte; append new blocks for amendments (`check:changelog-rc-bullets`). Enumerate shipping identities with `git log --first-parent --oneline <prev-stable-tag>..HEAD`. Omit `--changelog-file` for normal assembly. See [ADR-2957](../../../adr/2957-changelog-fragments.md) for classifier and recovery boundaries.
- **Non-promote cut, oracle refuses missing citations: fix the staged section instead of committing fragment edits.** A separate commit moves `main`'s tip and costs a full main CI + KinD wait (the pre-cut check needs the exact tip green; fragment edits never inherit). After `VERIFY FAILED`, the edits stay staged on the already-green tip: add each printed `#PR` or short SHA to a newly assembled, unshipped bullet in `## [B]` of `CHANGELOG.md`, else append a new bullet; never touch a shipped RC block. Then `bash scripts/changelog-links.sh && git add CHANGELOG.md && git commit -m "chore(release): <tag>"`, and require all three to pass before pushing: `bash scripts/assert-changelog-covers-release.sh HEAD <prev-stable> B`, `bash scripts/changelog-links.sh --check`, `bash scripts/changelog-section.sh check-rc-bullets <tag>`. Then continue at step 2. Not for `--promote`: a verify failure there deletes the provisional stable tag (`promote_guard`), which a manual commit does not recreate; re-run instead.

**The three scripts** (`.agents/skills/uzi-release/scripts/`), in order:

1. **`release-cut.sh <X.Y.Z> [--promote|--promote-only|--skip-promote|--stable] [--changelog-file FILE]`** — the whole prep, deterministic. It reads the LOCAL `main` and refuses one that is behind `origin/main`: fast-forward first. To rehearse a verb you have not run live, clone the repo to a scratch dir, `git remote set-url origin <the GitHub URL>`, `git checkout -B main <commit>`, and cut there: every tag stays in the clone. A `<commit>` behind the live `origin/main` trips the behind refusal, so to rehearse a past state point `origin` at a scratch `git clone --bare` of that state instead. It DERIVES the coverage base (the previous stable tag) itself, so there is no `<prev-tag>` positional (`--prev-tag TAG` overrides for a repair). Default cuts `vX.Y.Z-rc.1` (assembles pending legacy notes + fragments), the next `rc.(N+1)` for the in-flight base (appends pending blocks to the open section, guarded), or refuses (exit 3, with the facts) when a lower RC is in flight. `--promote` creates the stable `vB` tag LOCALLY from a throwaway `release/B` worktree at the RC commit (metadata-only edits, a diff allowlist checked BEFORE any tag exists, worktree+branch removed after), then cuts the next `vX.Y.Z-rc.1` on main. `--promote-only` runs that promote half alone and exits: `X.Y.Z` = the in-flight base, nothing is committed on `main`, main's pending fragments remain for the next cut, and the rest of this step does not apply (review `git show vB`, push the tag, go to script 3). Every other verb bumps `Chart.yaml`, runs `worker-tag-autobump.sh` (rolls the fleet IFF the agent runtime surface changed — the pin may legitimately STAY at a PUBLISHED RC tag inside a stable chart, D11, do not hand-normalize it; an unpublished pin is refused by the release guards), `changelog-links.sh`, commits `chore(release): <tag>` on main, and verifies with the oracle + `changelog-links --check`. Preflight refusals preserve inputs. Preparation failure or interruption can leave assembled notes and incorporated fragment deletions staged, or a completed local commit; verify failures soften the release commit and keep edits staged. Inspect HEAD, worktree and index before acting. Use the printed starting SHA and exact owned paths to finish preparation or deliberately restore it; after a completed commit, deliberate undo first soft-resets to that SHA, then restores those paths. Inspect any provisional stable tag separately. There is no automatic destructive rollback. Linkification still maintains links and a new-base cut reconciles the previous stable heading date; the pending renderer's preservation guarantee does not cover that maintenance. It does NOT push and does NOT tag the RC. Review `git show HEAD`, then `git push origin main`.
2. Review the release diff, push `main`, then tag the candidate immediately with `git tag -a vX.Y.Z-rc.1 -m vX.Y.Z-rc.1 HEAD` (use the exact tag printed by release-cut), and push it under the user's existing authorization or hand them `! git push origin vX.Y.Z-rc.1`. Do not wait for the release commit's own full CI. `release.yml` enforces successful main-push CI and smoke on the tagged SHA or through at most two strict metadata hops; a known failure on the tagged SHA blocks publication. It validates the tagged chart and bundled changelog, and requires the real tagged KinD smoke before chart publication. Full main CI still runs on the release commit. Never use a skip-ci marker, which suppresses tag workflows too. **Promote push order: stable tag, main, candidate tag.** A promote-only cut pushes just the stable tag; candidate coverage is required but current-main coverage is not.
3. **`release-watch.sh <tag>`**, **in the BACKGROUND** — it watches `release.yml` AND `brew.yml` for every tag (PRD #1378: an RC publishes the opt-in `uzi-cli-rc` formula, a stable publishes `uzi-cli`). It AUTO-RERUNS a transient publish failure (any non-gate job) up to `--max-reruns` (default 2); gate failures (`assert-*`/`prep`) are NOT auto-rerun. For a KinD flake causing red `assert-tag-smoke`, first run `gh run rerun <kind-run> --failed` on the failed tag KinD run and wait for success, then run `gh run rerun <release-run> --failed` on release.yml. Then **`release-verify.sh <tag>`** proves the publish: five image tags + chart on GHCR, the cosign "Pushing signature to:" lines, and the channel — a stable Release is marked latest; an RC Release is flagged pre-release with `releases/latest` unchanged (the previous stable). On a promote, run verify TWICE: once for the stable tag, once for the new RC. After a stable, also confirm what verify does not: `gh release list` shows `vB` as Latest with no `vB-rc.*` entry left (`release.yml` prunes them), the deployment's chart revision reaches `B` (it lags a reconcile or two even after a hard refresh; re-check before calling it stuck), and an unchanged worker pin rolled no workers.

**Manual hotfix compatibility.** An off-main stable patch has no main-push CI. Follow `deploy/README.md`'s Hotfix procedure: run affected local gates and `check:release-metadata`, then annotate the patch tag with the exact standalone line `CI-Coverage: hotfix-uncovered`. The exception requires the immediately previous stable patch on the first-parent chain and rejects a tag targeting main. In general, a failed main-push run on the tagged SHA or any visited coverage-chain commit vetoes publication. Report **UNVERIFIED hotfix, no full CI evidence**; tagged metadata, worker-image checks and real tagged smoke still apply. Never present the exception as CI-covered.

**Use the lander's verified asynchronous completion route for every watcher, never a foreground blocking `gh run watch`.** A foreground blocking watch pins the turn and has host-specific time limits. Native Claude/OpenCode background callbacks, or a consenting native-capable observer, must provide actual STARTED and exit evidence; background execution alone is not coverage. Codex's bounded observer is receipt-only until idle-wake validation permits its wake flag.

**A tag push needs the user's go-ahead.** It publishes unattended, so without an explicit in-session authorization the harness classifier blocks `git push origin v*` (`Blocked by classifier`, from a subagent and the lead alike); with one, the lead pushes the tag itself. That is a harness permission-mode block, distinct from the `protect-release-tags` ruleset (which would instead come back as a git/remote rejection). If blocked, the annotated tag already exists locally (shared across worktrees via `.git`), so hand the user one command: `! git push origin vX.Y.Z`. The admin role then bypasses the ruleset's creation restriction (`remote: Bypassed rule violations … [new tag]`). Do NOT route around it with `gh api` to create the ref — that defeats the same intent.

**Present the step-3 summary once the tag is pushed** — the publish runs unattended in the background (`release-watch.sh`) while you report what shipped, and you fold the verified tags (or a block) into the summary when `release-verify.sh` confirms.

## 3. Final summary (always end with this)
Report to the user, concisely:
- **One line up top**: version X.Y.Z and its status — cut / CI-green / tag pushed / **published to GHCR (images + chart)** / blocked on `<what>` (e.g. the tag push awaiting the user's `! git push`); CI coverage proven at publish (or explicitly UNVERIFIED for an annotated hotfix exception); deploy state (or "deploy verification needs cluster access I don't have"). Since the publish runs in the background (step 2's `release-watch.sh`), the summary may go out while it is still publishing — say so, and update once `release-verify.sh` confirms.
- **What shipped, by issue/PR**: one table over the release's CHANGELOG section (every shipping merge since the previous stable tag, as the oracle enforces): PR | issue | what it delivered in 1-2 sentences.
- **Behavior changes to flag**: anything that changes existing behavior, plus post-deploy caveats.
- **Left out**: open PRs deliberately not in this release, and why.
- **Follow-ups**: release-mechanics gaps this cut surfaced; offer to file issues.
