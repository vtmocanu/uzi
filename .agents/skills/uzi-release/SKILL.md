# uzi-release

Drive uzi's open pull requests through review, merge, release, and deploy verification, then summarize. This repo is hosted on **GitHub**: use `gh` (which infers the repo from the checkout, so a fork under any owner works unedited; never `glab`/`tea`). CI is **GitHub Actions** (`.github/workflows/`), images and the Helm chart publish to **GHCR** on a `v*` tag.

Do NOT bake step details that live in the repo into your head. Read the source of truth each run: `deploy/README.md` (release + deploy runbook), the workflow files under `.github/workflows/` (`ci.yml`, `release.yml`, `kind-smoke.yml`, `e2e.yml`, `brew.yml`), the destructive-ops rules in `CLAUDE.md`, and `.claude/rules/*.md` for the component you touch.

> **Note on the deploy layer.** `deploy/README.md` still describes the previous GitLab/ArgoCD-on-Harbor deploy path and is mid-migration to GitHub/GHCR; treat its deploy specifics as in-flux and verify against the maintainer rather than this skill. The release itself (tag → GHCR publish) is fully on GitHub and is what this skill drives end to end. Cluster/deploy verification needs cluster access you may not have; if so, say so plainly rather than guessing.

## 0. Guardrails first
- NEVER `docker compose -p uzi down -v` and never glob `uzi-` containers (see `CLAUDE.md` "Destructive operations"). This skill touches git, `gh`, and (if you have deploy access) `kubectl` only.
- Work on `main` in the repo root worktree; make a sibling worktree for any branch integration (`git worktree add ../uzi-issue-NNN -B agent/issue-NNN origin/agent/issue-NNN`). Never check the root worktree out onto another branch.
- `main` is guarded by a **ruleset** (`protect-main`), not classic branch protection — so `gh api repos/OWNER/REPO/branches/main/protection` 404s even though rules are enforced; read the live rules with `gh api repos/OWNER/REPO/rules/branches/main`. As of 2026-08-20 it enforces three things that matter here: strict **required status checks** (branch must be up to date), **1 approving review from a non-author** (`required_approving_review_count: 1`, `require_last_push_approval: true`, `dismiss_stale_reviews_on_push: true`), and no force-push/deletion. The **admin RepositoryRole bypasses the entire ruleset** (`bypass_actors` = role id 5, `bypass_mode: always`), which is how the owner lands a release and merges renovate PRs. The approval rule has a sharp consequence for a solo-owner renovate batch — see step 3. If a push or merge is refused, read the refusal and stop rather than forcing.

## 1. Survey the open PRs
```sh
gh pr list --state open
```
For each PR pull metadata, the changed-file list, the closing issue/PRD, and its check status:
```sh
gh pr view <n> --json number,title,headRefName,mergeable,mergeStateStatus,files \
  --jq '"branch=\(.headRefName)  \(.mergeable)/\(.mergeStateStatus)\n" + ([.files[]|"  \(.path)"]|join("\n"))'
gh pr diff <n>            # full diff for review
```

**Worker-toolchain bump PRs come from a workflow, not renovate.** The devbox-pinned worker toolchain (`agent/devbox-global`: go, gcc, python3, chromium, semgrep, helm, …) is NOT renovate-covered, so a weekly `.github/workflows/devbox-update.yml` job re-resolves it against the latest nixpkgs and opens a `chore(deps): refresh devbox worker toolchain` PR (branch `chore/devbox-toolchain-update`). Review it like a renovate PR, with three specifics: it **tracks `nixpkgs-unstable`, so it can carry MAJOR tool bumps** — read the lock delta; this is intended (workers should get current, patched tools). The check that actually validates it is **`build-agent` (base + jvm)**, which builds the worker image and runs the toolchain guard — the other `ci.yml` jobs are code tests unaffected by a toolchain lock. And because the workflow opens the PR with `GITHUB_TOKEN`, **the PR may not auto-trigger its own CI** (GitHub's recursion guard, even with "Actions can create PRs" on); push an empty commit with your own token to run it, or rely on the scheduled run's own base-image build plus post-merge `main` CI.
Branches are fetched by `gh` on demand; `git fetch origin <branch>` if a review agent needs whole files locally. `mergeStateStatus=BEHIND` means the branch is out of date with `main` (the ruleset requires up-to-date AND a non-author approval before a normal merge — see step 3); `CONFLICTING` means a real conflict.

**Get every open PR to green CI before you review or merge anything — start with the red ones.** A failing check is the highest-priority signal in the survey: triage and fix the red PRs FIRST, then work the green batch. Two reasons this is first, not last: (a) a red PR is often red for a **repo-wide** reason — a new CVE tripping a `vulncheck` gate, a stale base, a toolchain-currency failure — that also reddens `main` and every sibling PR, so diagnosing one red can unblock the whole batch in a single `main` bump (see "Triage a red check" below); and (b) a PR red for a **real defect** cannot merge until the fix is pushed and its checks re-run green anyway, so surfacing that early beats reviewing green PRs only to stall at the merge on a red one. Classify each open PR up front — green / red-repo-wide / red-defect / stale-base — resolve the reds (fix on `main` for a repo-wide cause, push a fix to the branch for a defect, `gh pr update-branch` for a stale base), and only then spend review cycles (step 2) on the batch. Review still gates merge (step 2); this is about work order, not skipping review.

**Phase order within the green batch: our PRs first, routine renovate last.** Once the reds are cleared, merge OUR feature/fix PRs (the ones that name this release) before the routine renovate minor/patch batch. Renovate **auto-rebases its own PRs** when `main` moves, so landing ours first keeps the renovate batch fresh for free — whereas merging renovate first re-stales our PRs against the new deps. It also **isolates dependency breakage** (a clean bisect: features settled, then deps) and **confines the lockfile-stacking conflicts** (step 3) to one end-phase instead of tangling them with our PRs' own `go.mod`/`package.json` edits. **The one carve-out is the reds-first rule above:** a dependency/renovate PR that is the FIX for a repo-wide red (a new CVE tripping `vulncheck`, a toolchain-currency failure) unblocks every other PR and jumps to the front. The two rules do not conflict — reds-first is about *unblocking*, renovate-last is about the routine green batch. (Renovate MAJORs needing code changes are already deferred to their own issue below, so "renovate last" means the minor/patch batch.)

**Detect migration collisions now.** Two PRs adding the same `NNNNN_*.sql` under `api/internal/store/migrations/` will both land as distinct files (git sees no conflict) and brick strict-goose boot. Find the live head (`ls api/internal/store/migrations/ | sort | tail -1`) and note which PRs add migrations at or below it. They get renumbered at merge (step 3). Note: PRs that only edit sqlc-generated query files (`*.sql.go`, `queries/*.sql`) add **no** migration and pose no collision risk — check for a genuinely new file under `migrations/`.

**Check in-flight uzi runs before you start.** `uzi run list` (if the `uzi` CLI is on PATH). uzi's auto-CI-fix opens a `ci_fix` run for a failed pipeline (often parked at the plan-approval gate, `awaiting_approval`) and can auto-open a PR mid-release. Read a run's plan first (`uzi run get <id>`, `uzi run logs <id>`) so you don't re-diagnose what it already found; `uzi run reject <id> -m "<why>"` any whose fix you supersede.

**Also surface report-only runs whose issue could now be closed — not every delivery is a PR.** A run can finish `completed` with `report_only=true` and **no MR/PR** (the `report_only` boolean and `report_md` are first-class fields on the run DTO). These come from two places: an `issue`/`prompt` run that investigated, validated, or fixed-in-place and had nothing to open an MR for; and the **time-driven schedules** (`uzi schedule list --json` — e.g. weekly test pass, docs-hygiene, bug-hunt, feature-bingo) which are *designed* to finish report-only on an empty week. Their backing issue often sits open with the answer already delivered in the report, so a release is the natural moment to sweep them. Enumerate the candidates:

```sh
uzi schedule list --json | jq -r '.[]|"\(.id[0:8])  \(.status)  next=\(.next_fire_at // "-")  \((.title // .prompt // "-")[0:60])"'
uzi run list --json | jq -r '
  [ .[] | select(.status=="completed" and .report_only==true and .issue_iid!=null and .mr_iid==null) ]
  | sort_by(.finished_at) | reverse
  | .[0:30][] | "run=\(.id[0:8])  #\(.issue_iid)  judge=\(.judge_verdict // "-")  \(.issue_title[0:70])"'
```

Then, per distinct still-open issue, decide before recommending a close: **report-only ≠ resolved.** Many report-only runs are "surveyed, found nothing" (an empty-week schedule fire) or a partial investigation, and closing their issue would be wrong. Read the run's conclusion (`uzi run get <id> --field report_md`, and `judge_verdict`) and confirm the issue is still open (`gh issue view <n> --json state,title -q '.state'`). Present the ones that genuinely look done as a **close-candidate list for the user to confirm** — do NOT auto-close: closing an issue is a mutating, owner's-call action (the permission classifier may block it, like `--admin`), so close only the ones the user green-lights (`gh issue close <n> --comment "<what the run delivered; run <id>>"`), then report them in step 6.

**Renovate files a SEPARATE PR for a major bump — when both a minor/patch PR and a major PR exist for the same dependency, prefer the major if it's safe.** `renovate.json` extends `config:recommended`, so `separateMajorMinor` is on: a package at `1.2` with `1.3` and `2.0` available gets both an "Update X to v1.3" PR and an "Update X to v2.0" PR. Landing the major supersedes the minor (renovate auto-closes the minor once the major merges, or close it yourself), so you do one merge and land on the version you'd reach anyway. **A major is a breaking change by definition, so vet it before preferring it:** read the breaking-changes / first entries of the release notes — the renovate "Release Notes" section in the major PR body (`gh pr view <n> --json body -q .body`), or the upstream CHANGELOG between the current and target versions — for anything that touches how uzi uses the package. If nothing breaking affects uzi and its checks are green, take the major and drop the minor. If adopting the major needs real code changes, do NOT force it into the release: merge the safe minor/patch now and file the major as its own `dependencies`/`enhancement` issue for a dedicated PR (`gh issue create`), reporting it in the step 6 follow-ups. An `@anthropic-ai/claude-agent-sdk` major additionally gets the adoption review the SDK-bump note below calls for.

**A minor/patch bump is not automatically a drop-in; CI is the arbiter, and two classes redden a green-looking bump.** (a) A **tool/analyzer** bump (knip, oxlint, a linter) can be stricter and surface a pre-existing backlog the zero-tolerance gate (`deadcode:web`, `lint:*`) rejects, so it needs a triage/ignore pass, not a merge; land the safe siblings and defer it. (b) A **k8s node-image** bump (`kindest/node`) can outrun the SHA-pinned runner action (`helm/kind-action`) that ships `kind`: a newer node (observed at v1.37.0) rejects the obsolete `kubeadm.k8s.io/v1beta3` config the pinned `kind` still emits (`Create KinD cluster` fails with `uses an old API spec: "kubeadm.k8s.io/v1beta3"`), so the action must be bumped in tandem. Before touching any renovate PR, **diff its target against `origin/main`** (`git show origin/main:<file>`): another merge may already satisfy it, a redundant PR renovate will auto-close.

**When a PR bumps `@anthropic-ai/claude-agent-sdk`, read the SDK changelog for adoption opportunities — this is not just a lockfile bump.** That package is uzi's agent-runtime core (the `agent/` worker builds on it, incl. the `PreToolUse` guardrail hooks and `settingSources`), so a new version can ship capabilities uzi should adopt or refactor onto, not merely a patched dependency. Read the release notes: renovate usually embeds an upstream "Release Notes" section in the PR body (`gh pr view <n> --json body -q .body`); if that's thin, go to the source changelog (`anthropics/claude-agent-sdk-typescript` `CHANGELOG.md`, or `npm view @anthropic-ai/claude-agent-sdk`). **Read EVERY intermediate version's notes, not just the target's** — a bump `0.3.235 → 0.3.238` spans `0.3.236` and `0.3.237` too, and an adoptable change (or a guardrail-relevant fix) can land in any of them. Renovate embeds a section per intermediate version in the PR body by default, so they are already there to read; if you fell back to the source changelog, read the whole span between the current and target versions, not only the top entry. Scan for new hooks, tool-runner/permission APIs, session/streaming features, or options uzi could use — and cross-check against the four guardrail layers and the run lifecycle in `ARCHITECTURE.md` for anything that lets uzi simplify or harden them. Merging the bump does NOT implement any of that; it only makes the new SDK available. When you spot something uzi could benefit from, **propose it to the user and offer to file an `enhancement` issue** (`gh issue create`), keeping the improvement issue separate from the dep-bump PR — never implement it inside the release. Report what you found (or "nothing actionable in this bump") in the step 6 follow-ups.

**Triage a red check: is it the PR's fault?** Often it is NOT. The `vulncheck:{api,controller,web}` steps (inside the `lint-*`/`validate-web` jobs — govulncheck on *called* Go stdlib/dep CVEs, npm audit for web) re-evaluate against the LIVE advisory DB, so a branch green when cut goes red when a new CVE lands, with no code change, and `main` fails the same way. Read the failing job's log (step 4). If it's repo-wide (new CVE, toolchain currency), the fix is a dependency bump, not a PR change: land it on `main` directly (`chore(deps): ...`, e.g. re-pin the toolchain digest and bump the lockfile), then `git merge origin/main` into each PR branch (or `gh pr update-branch <n>`) so their checks re-run green.

**A renovate PR whose CI fails because the new version needs a code change — do NOT push the fix onto the renovate branch. Make your OWN branch that both bumps the dep and carries the fix, and let renovate auto-close its PR.** Renovate rebases/force-pushes its own branches, so a commit you add there can be clobbered; and you cannot admin-merge it cleanly under the solo-owner self-approval block anyway. The flow:
  1. **Diagnose against BOTH versions before writing a line of fix** — reproduce in a throwaway worktree (`git worktree add <tmp> origin/<renovate-branch>`, or off `main` with the version `go get`/`npm install`-ed in), and run the *same* thing on the current and target versions. A failure under the new version is not automatically a regression: it can be a stricter check, a changed-but-equivalent behavior, or (as with go-chi/chi v5.3.2, PR #1148) a tool now *reporting* something that was always true. Establish which — serve the real endpoint / run the real path on both versions — so the fix matches the actual change and you can state the production impact (often "none").
  2. **One branch off `main`** (`fix/<dep>-<version>` or `chore/<dep>-<version>`), bump the dependency yourself (`go get <mod>@<v> && go mod tidy`, or `npm install <pkg>@<v>`), apply the code fix, run the component gate (`task gate:<component>`), push, open a PR. Keep it scoped: the dep bump + only the change the bump forces. **Title it honestly** — a dep bump is a dep bump, so `fix(deps): …` / `chore(deps): …` is the correct semantic-commit type even though the substance is the code fix. Do NOT contort the title to a non-deps type just to dodge CodeRabbit (see next step); gaming the convention is a smell, and there is a clean override.
  3. **Drive it to merge yourself: poll CI and CodeRabbit, fix what you judge needs fixing, then admin-merge when you judge it ready.** Watch the branch's CI to green (step 4's job-level polling) and get CodeRabbit's review. **CodeRabbit AUTO-SKIPS a `*(deps)` title** — `.coderabbit.yaml`'s `auto_review.ignore_title_keywords` lists `chore(deps)` / `fix(deps)` / `build(deps)` (belt-and-braces beside `ignore_usernames: renovate[bot]`), so an honestly-titled dep PR shows `CodeRabbit  pass  Review skipped: ignored keyword in the PR title` and never reviews on its own. **Force it with a comment: `gh pr comment <n> --body "@coderabbitai review"`** — an explicit review command overrides the auto-skip regardless of title (verified: the check flips to `Review in progress` on a `fix(deps)`-titled PR). Then wait for it to land (step 2's `Review completed`). Assess every finding against the actual change, fix the ones you consider worth fixing with follow-up commits to the branch (re-running the component gate before each push), and skip the ones that are noise or deliberate — the same review discipline as step 2. When CI is green and you judge the PR ready, admin-merge it (step 3's `--admin` path, since the solo-owner self-approval block applies here too). Do not wait to be told to merge each step; the standing authorization for a user-initiated fix is to carry it to a merged, green PR, surfacing only genuine blockers (an `--admin` classifier block the user must clear, or a finding you want a decision on).
  4. **Renovate auto-closes its own PR** on its next run once the dependency is at the target version on `main` (it detects the update is satisfied). You do not close it by hand. To not wait for the scheduled run, you can trigger renovate immediately — **load the `/renovate` skill for how to fire a run**; this skill does not duplicate that mechanism.

## 2. Review each PR (gate: no objections)
This is a **third** pass, not a first — each uzi run already ran its own internal reviewer + auditor + fact-checker wave over its commits, and **CodeRabbit reviews ordinary PRs automatically** the moment it opens — so the default is to **wait for CodeRabbit and assess its findings**, and escalate only where an independent deep look earns its keep. Do NOT auto-spawn a per-PR `reviewer` agent and do NOT auto-run `/code-review`; that would be a redundant fourth pass over code two waves already read, and the standing preference here is not to spin up review agents by default (2026-08-24). It is the **same review discipline the day-driver applies**: an overnight batch merged here and an MR merged mid-day by the `uzi-lander` skill are the same artifact, so they get the same gate, not a heavier one. The review, merge and CI-watch mechanics (scripts and runbooks) have ONE home, `.agents/skills/uzi-lander/`; this skill calls them, it does not restate them.

**Routine Renovate exception.** The `*(deps)` title and `renovate[bot]` ignores are intentional: inspect the diff, release notes and CI, but do not request CodeRabbit or substitute a local review solely because it skipped. If a Renovate diff warrants CodeRabbit, explain why and get the user's approval before posting `@coderabbitai review`.

**Default per non-Renovate PR: wait for CodeRabbit, then assess.** CodeRabbit posts asynchronously (a few minutes after the PR opens), so wait for its review to **land** (`gh pr checks <n>` shows `CodeRabbit  pass  Review completed`; the review body reads `Actionable comments posted: N`) before assessing — `0` is a clean PR. **The tally lives in `pulls/<n>/reviews`, NOT `issues/<n>/comments`** (the issue-comment stream carries only the walkthrough/summary and the rate-limit/trigger notices, with no tally), and an **absent** review is not clean — so gate on `.agents/skills/uzi-lander/scripts/pr-findings.sh OWNER/REPO <n>`, which reads the right endpoint (and Greptile's check-run on the head), and **exits 3 if any named PR was not reviewed on its head**, rather than hand-rolling a grep over issue comments that reads a reviewed-with-findings PR as a false "clean" (that is how a Major finding rode into `main` unseen, 2026-09-07 PR #1175). **If instead it shows `CodeRabbit … Review rate limited`, CodeRabbit did NOT review and does not self-retry** (distinct from the `*(deps)`-title auto-skip in step 1) — re-trigger it with `gh pr comment <n> --body "@coderabbitai review"` (the same force command), then wait for `Review completed`. To learn WHEN capacity returns, comment `@coderabbitai rate limit` (alias `@coderabbitai reviews remaining?`) — it replies with the reset window ("More reviews will be available in N minutes"); `@coderabbitai ratelimits` (one word) and a plain-English question both get the useless "I cannot view the quota" non-answer, so use the exact two-word `rate limit`. Refill is adaptive to the org's last-7-day review volume, so the wait varies; `.agents/skills/uzi-lander/scripts/cr-rate-limit.sh OWNER/REPO <n> --ask --wait` reads the reset (asking only when nothing on the PR states it) and waits it out, then re-run `@coderabbitai review` ONCE. **If CodeRabbit never appears at all** (no review and no `CodeRabbit` check even after a re-trigger — down, not rate-limited), fall back to `/code-review` on the PR, the same as the `uzi-lander` skill's CR-absent fallback: **at `low` by default, `medium` only for an important PR** (security / auth / credential, subtle state / concurrency, or a large diff — the escalation criteria in the next paragraph); never higher, and never when a CR review already landed (user preference, 2026-09-01). Pull its inline findings (`gh api repos/OWNER/REPO/pulls/<n>/comments --paginate --jq '.[]|select(.user.login|test("coderabbit";"i"))|"### \(.path):\(.line)\n\(.body)"'`), **verify each against current code** (a finding may be on inherited/base-realigned code, deliberate documented behavior, or mock-only — label it), and pair it with the milestone check yourself (item 1 below — CodeRabbit won't read the PRD). When findings exist across the batch, follow the **batch-triage flow** (assess ALL, present once, collect every decision, then execute unattended) — that flow and the per-finding options (fix-locally / rework-on-demand / skip / send-to-uzi, with their tradeoffs) are the `uzi-lander` skill's findings step and its `references/coderabbit-triage.md`; read them there rather than re-deriving, so the two skills can't drift. **Escalate to a bespoke `reviewer` agent** (parallel, one per PR that needs it) ONLY on request or for a diff that is **security / auth / credential**-touching, **subtle state / concurrency** logic, a **test-only diff whose risk is the vacuous-assertion trap** (name the invariant, e.g. demand `IsAdmin==true` over the zero value), or simply **large** — briefed with the approved plan's invariants **verbatim** and pinned to the immutable PR-head SHA in an isolated `git worktree add --detach` (the shared `main` tree moves under a reviewer).

**Skip CodeRabbit on demand.** Put `[skip-cr]` anywhere in a PR title and CR does not auto-review it (`.coderabbit.yaml` `ignore_title_keywords`, alongside the `*(deps)` keywords); for a PR already open, or to skip one review only, post `@coderabbitai ignore`. For non-Renovate PRs, `[skip-cr]` skips the BOT, not the review gate: `pr-findings.sh` then reports the PR as not reviewed (exit 3), which is the cue to run the local review fallback (a `reviewer` agent, or `/code-review` at `low`) before merging, not to merge unreviewed. Reach for it only when the bot adds nothing (a mechanical or generated diff).

Each review ends with a one-line verdict `MERGE` / `MERGE-WITH-NOTES` / `OBJECT`, answering concisely:
1. **Milestones.** Read the PRD (`git show origin/agent/issue-N:prds/done/<file>.md` or the merged file); enumerate milestones and mark each IMPLEMENTED / PARTIAL / SKIPPED with backing files. Flag any in-scope milestone with no code. A milestone deliberately *reframed* and documented is not "skipped" — say which it is. (This is the per-PRD form of the plan↔diff scope match — always yours, whichever reviewer runs.)
2. **Correctness.** Red flags that block merge (read code, do not re-run tests). If a check is red for a reason unrelated to the diff (step-1 triage: a vuln-gate CVE, a known flake, a path-skipped build showing as non-success), tell the reviewer so explicitly and have them review the code only.
3. **Migration** (if it adds one): is it standalone/safe to renumber filename-only, or does it depend on ordering?

One deterministic check stays yours regardless of which reviewer runs: the **`.github/workflows` grep** on the changed-file list (`gh pr diff <n> --name-only`).

Do not merge anything until every verdict is MERGE or MERGE-WITH-NOTES. Surface any OBJECT to the user.

## 3. Merge orchestration
**Merge in the phase order from step 1** — our feature/fix PRs first, the routine renovate minor/patch batch last (the one exception being a dep PR that fixes a repo-wide red, which goes first to unblock everything).

**Probe cross-PR conflicts first** when several PRs touch a shared, hand-edited file (ARCHITECTURE.md, a shared handler). Two PRs editing *different regions* of the same big file three-way-merge cleanly; only overlapping hunks conflict. A throwaway worktree settles it without pushing: `git worktree add -b probe/batch <tmp> origin/main`, then `git merge --no-ff origin/agent/issue-N` for each in your intended order, recording which merge clean and which conflict; `git merge --abort` between probes; remove the worktree after.

**Merge method.** Merge commits (`gh pr merge <n> --merge`) keep both the PR number (`Merge pull request #<pr>`) and the source branch (`agent/issue-<M>`) in the merge subject, which is what lets the CHANGELOG cite the **issue** number and still satisfy the changelog oracle (step 5). Squash puts only the PR number in the subject. Add `--delete-branch`. There is no GitLab-style full-SHA requirement here.

- **Clean, up-to-date PRs**: `gh pr merge <n> --merge --delete-branch`.
- **`BEHIND` PRs (ruleset requires up-to-date AND a non-author approval; no merge queue)**: a normal `gh pr merge --merge` is refused (`the base branch policy prohibits the merge`) until BOTH the branch is up to date AND the PR carries 1 approving review from someone other than its author. Two ways forward, and which is even *possible* depends on who authored the PR:
  1. **Update the branch, get it approved, then merge** — `gh pr update-branch <n>` (or `git merge origin/main` on the branch and push), a reviewer approves, then `gh pr merge <n> --merge`. This is the no-bypass path, but it is **sequential** (each merge advances `main`, re-staling the rest, so a batch costs one CI cycle per PR) **and it needs a second account to approve.** 🔴 **It is IMPOSSIBLE for renovate PRs when renovate authors as the repo owner** (verified 2026-08-20: the renovate PRs showed `author = vtmocanu`, the same account `gh` was authenticated as; GitHub forbids self-approval, and `require_last_push_approval` + `dismiss_stale_reviews_on_push` mean even a granted approval is dismissed by the update-branch push). So for a solo-owner renovate batch the approval requirement can never be satisfied and this path cannot complete — `--admin` is the only option, and you should reach for it directly rather than update-branching first.
  2. **`--admin`** — `gh pr merge <n> --merge --admin --delete-branch` bypasses the up-to-date AND approval requirements (the admin role bypasses the ruleset) and merges immediately (`.agents/skills/uzi-lander/scripts/merge.sh OWNER/REPO <n> --method merge --expect-head <sha>` is the guarded form: it re-checks the head, the rework lane and the required checks, then confirms `MERGED`). Use it ONLY when you have reviewed the PR (verdict MERGE), its checks are green, and you have **confirmed no conflict and no migration collision** (a probe merge or a different-region check). `ci.yml` re-runs on the resulting `main` push as the safety net. `--admin` is a privileged action: an agent session's permission classifier commonly blocks it (and `gh pr review --approve` too) — it is genuinely the owner's call, so if blocked, ask the user to run it or to add a `Bash(gh pr merge:*)` permission rule rather than forcing.
     - **Renovate lockfile-stacking note.** Back-to-back `--admin` merges of PRs that share a generated lockfile (`api/go.mod`+`api/go.sum`, `agent/package-lock.json`) will 3-way-conflict once one lands — each is clean against the *current* `main` individually, but merging one makes the rest conflict. GitHub refuses the conflicting one with `Pull Request has merge conflicts`; resolve it locally (in a sibling worktree: **`git fetch origin main` first**, so a stale local `origin/main` does not silently omit a just-merged sibling's bump, then `git merge origin/main`, take the union of the version bumps, then regenerate — `go mod tidy` for go.mod/go.sum, `npm install --package-lock-only` in the package dir for a lockfile — and `go build ./...` to confirm), push, and `--admin` merge. CI runs `npm ci` (not `npm install` + a diff check), so regenerating a lockfile under a newer local npm is safe as long as it stays internally consistent with `package.json`. Also expect a **transient stale** `Pull Request has merge conflicts` right after you push a resolution (GitHub's async mergeability lag) — re-check `mergeable`/`mergeStateStatus` after a few seconds and retry the merge; a genuine conflict persists, the stale one clears.
- **Conflicting / migration-colliding PRs**: integrate locally in a sibling worktree.
  1. `git merge origin/main`; resolve conflicts (semantic merge, keep both intents).
  2. Renumber any colliding migration to the next free number above the live head: `git mv .../00120_x.sql .../00122_x.sql` (goose reads the version from the filename; grep confirms no code cites the number).
  3. Regenerate sqlc with the PINNED version, not the PATH one (find the pin in `Taskfile.yml` / `api/sqlc.yaml`). CI enforces zero drift via `git diff --exit-code`; a wrong local sqlc version reddens it. Zero diff after regen means git's auto-merge of the generated files was already canonical.
  4. `go build ./...` + `go vet` + the touched package's unit tests; `task gate:web` for web changes. NOTE local Node: `.nvmrc` pins the CI version; a newer local Node can fail unrelated tests (jsdom localStorage) that pass on CI — reproduce any failure on clean `main` before blaming the merge.
  5. Push the branch, let its checks go green (step 4), then merge.

After all merges, `git checkout main && git pull --ff-only origin main` and confirm migrations are distinct (`ls api/internal/store/migrations/ | sort | tail`).

## 4. Watch CI at JOB level (~2-min cadence) — act on a failed job immediately, do NOT wait for the whole run
This step is the skill's own CI watch: after the step-3 merges, and again after the release commit lands, watch **`main`'s `ci.yml`** (and the `kind-smoke.yml` it triggers) to green. **The tag's own runs — `release.yml` and `brew.yml` — are NOT this step; they are step 5 (the lead drives them via `release-watch.sh`), with the mechanics documented in `.claude/agents/release.md`. They publish UNATTENDED (the old `release`-environment approval gate was removed 2026-08-20 — access control is now the `protect-release-tags` tag ruleset, so there is nothing to approve).** Poll the run's **jobs** every ~2 min and surface any failed one the moment a tick sees it. A job is a terminal unit: once it is `failure`, the rest of the run still going tells you nothing new about it, and waiting for the whole run to conclude just wastes minutes. **Beware a stale first-tick read:** `gh run view --json jobs` can briefly report `in_progress` jobs with a non-null (often `failure`/`cancelled`) conclusion right after a run starts, so a poller's first tick may print bogus `FAILED` lines that clear on the next tick — re-query live before believing a failure, and confirm the final state at run end.
```sh
# ALL runs for the ref you pushed (main OR the tag) — iterate every one, don't pick just one
gh run list --branch <ref> --limit 10 \
  --json databaseId,workflowName,headSha,status,conclusion \
  --jq '.[]|"\(.workflowName)  \(.headSha[0:7])  \(.status)/\(.conclusion // "-")  run=\(.databaseId)"'
# failed jobs in a run (ignore SKIPPED path-filtered build jobs — a docs-only change skips image builds)
gh run view <run-id> --json jobs \
  --jq '.jobs[]|select(.conclusion!=null and .conclusion!="success" and .conclusion!="skipped" and .conclusion!="neutral")|"FAILED \(.name)"'
```
Run it as a background command that loops on a **120s** sleep, prints failed-job lines each tick, and **exits the moment any job fails** — do NOT wait for the whole run to reach `completed`, because a long job (e.g. `test-api-store-it`, several minutes) keeps the run `in_progress` long after a fast job (e.g. `validate-api`) has already gone red, so a whole-run `status` wait learns of the failure late (measured cutting v0.68.0: a `validate-api` provisioning flake stayed masked behind a still-running `store-it` because the poller keyed on whole-run `status`). On a clean run it exits once every job is terminal and none failed. Do not block a foreground turn on it. Read a failed job's log right then: `gh run view --job <job-id> --log-failed` (or open the job `web_url`). **`--log`/`--log-failed` returns 0 bytes while the run is still in progress** (the `/logs` zip is empty then too), so to name the failing step without waiting for the whole run, read the step conclusions from the API: `gh api repos/OWNER/REPO/actions/jobs/<job-id> --jq '.steps[]|select(.conclusion=="failure")|.name'`, then reproduce that step locally. If it's a real defect, fix and re-push; if it's a flake/infra failure, **rerun just the failed jobs** without touching the branch: `gh run rerun <run-id> --failed` (or `gh run rerun --job <job-id>`). `ci.yml`'s `concurrency` cancels older `main` runs when a newer commit lands, so a `cancelled` older run is expected, not a failure.

**The pollers live in `.agents/skills/uzi-lander/scripts/` (one poller family for every skill; `uzi-lander` owns them).** Run each in the background:

- **A PR, or a WHOLE MERGE BATCH (the common step-1/step-3 shape, e.g. the reds re-running CI after a repo-wide-red fix landed on `main`): `watch-prs-ci.sh <PR> [<PR>...]`**, keyed on `gh pr checks` (every CI job as its own row; a single PR is a batch of one). It polls every named PR each tick, **exits `1` the moment any PR has a confirmed failing job** (printing which PR + its jobs; re-querying once to shake off the stale-first-tick read above; a batch cannot merge on a red member), `0` only when they are ALL terminal and none failed, `2` on timeout, `3` on a gh error. Flags `--interval` / `--max-ticks` / `--wait-cr`. CI only: for merge-READINESS (CI + CodeRabbit/Greptile on the head + mr_rework) use `watch-pr.sh OWNER/REPO <PR>` (exit codes in `uzi-lander`'s SKILL.md). Prefer the scripts over a hand-rolled multi-PR poll loop — that is exactly where a fragile loop gets written under time pressure (zsh word-splitting/arithmetic, or a gawk-only 3-arg `match` that BSD awk on macOS rejects).
- **A branch/run rather than a PR — `main`'s `ci.yml` after the step-3 merges or the release commit: `watch-run-ci.sh <run-id>`** (or `--branch main [--workflow ci.yml]`, which re-resolves the latest run each tick so a run minted by a concurrent push is picked up; or `--sha <sha>` for every run of one commit, the post-merge form). Keyed on `gh run view --json jobs`: it **exits `1` the moment a job is `completed` with a failing conclusion** (confirmed by one immediate re-query), `2` on timeout, `0` when every job is terminal and none failed — `build-*` jobs `skipped` by the path filter count as green; in `--sha` mode `4` means the commit's runs were cancelled by concurrency (superseded, not red). **Use it here instead of polling the whole-run `status`**, which is exactly the late-detection bug the paragraph above warns about.

All of them parse with `awk -F'\t'` on purpose: this host's `grep` is ugrep, whose POSIX modes mishandle negated classes and brace intervals (repo `CLAUDE.md`), so job-state parsing must not go through a grep pattern. **They are a starting point — keep improving them** (in `uzi-lander`) as the CI surface changes; each script header documents its exit codes.

**The tag's `release.yml`/`brew.yml` runs are step 5 (the lead, via `release-watch.sh`), not this step.** They publish unattended (no approval gate — see `.claude/agents/release.md` for the mechanics). This step only needs to get `main`'s `ci.yml` green.

**A note on SKIPPED checks.** `ci.yml` has a `changes` job that path-filters the image `build-*` jobs, so a PR that doesn't touch a component shows those builds as SKIPPED. `gh pr checks` renders those as skipped/neutral, not failing — do not read them as red.

**Real failure vs flake.** A timing/resource-sensitive test failing under CI CPU contention is a flake, not a defect — confirm it (assertion is timing-based, failing test unrelated to the diff, same job passed on another run off the same base), then **rerun the single job** instead of re-pushing. File the flake as a `bug` issue. Shared runners can also hit transient infra failures (disk pressure, a registry hiccup) on a SUBSET of runners, so some jobs pass while others fail on the same run — that is the rerun-not-repush case par excellence; keep polling until the run is terminal, because jobs still `in_progress` when you first looked can fail later.

## 5. Cut the release inline with the deterministic scripts — do NOT dispatch a subagent
Once **every PR is merged** and **`main`'s `ci.yml` is green** on the tip (steps 3-4), cut the release **inline as the lead**, driving three bundled scripts. Do NOT dispatch the `release` subagent for this: a background subagent spawns a watch and then idles, so every wait becomes a manual re-ping (the "agent keeps dying" ping-pong), while the steps that actually need judgment — flake-vs-defect, whether to rerun, authoring the CHANGELOG — are the lead's regardless. `.claude/agents/release.md` stays the MECHANICS reference (what each step proves, the signing traps, deploy verify), but the driver is the lead + scripts, not that agent. *(Changed 2026-09-01 at the maintainer's direction, retiring the dispatch-a-release-agent flow; the scripts are the executable form of what that agent did.)*

**What the lead decides first** (it has the review context):

- **The version `X.Y.Z`.** Patch (`0.46.0` → `0.46.1`) for a maintenance/deps/tooling batch with no user-facing feature or behavior change; minor (`0.46.0` → `0.47.0`) when a product feature ships. Patch tags are in this repo's history (`v0.42.1`, `v0.38.1`), so a small batch does not force a minor. Model B: chart `version` == `appVersion` == the tag.
- **RC-first (PRD #1265): which verb.** A release is cut as a CANDIDATE `vX.Y.Z-rc.1` by default and PROMOTED to stable later, from the candidate's own commit, in lockstep with the next candidate. When an RC is already in flight for a lower base, `release-cut.sh` REFUSES with the facts (which RC, since when, whether `[Unreleased]` is empty) and exits 3. That refusal is the lead's cue to ask the user which of four: **promote** the in-flight RC and cut the next candidate (`--promote`, the usual answer once a candidate has been dogfooded), **promote it alone** (`release-cut B --promote-only`, when `main` carries work the user does not want in a candidate yet), cut **another candidate** for the same base (`release-cut B`, when the candidate was not good enough; needs an empty `[Unreleased]`, so write re-spin notes into the open `## [B]` section first), or **abandon** it (`--skip-promote`). `--stable` (the old one-step model) is only for a docs-only release and is refused while an RC is in flight.
  - **RC dogfood install (PRD #1378):** `brew install vtmocanu/tap/uzi-cli-rc` builds the newest candidate from source; it `conflicts_with` the stable `uzi-cli` by design (one active `uzi`), so uninstall stable first if present. Switch back with `brew uninstall uzi-cli-rc && brew install uzi-cli`. Stable users on `uzi-cli` never see a candidate.
  - **Stale in-flight RC, and the stable must contain current `main` (not the old candidate).** When the in-flight RC is many merges behind `main` and you want the stable to ship everything on `main`: you cannot `--stable` (refused while an RC is in flight), and a plain `--promote` tags the OLD rc commit, so neither gives you the tip. The route is rc-at-tip, **PUBLISH it**, then promote: (1) author the oracle-flagged shipping merges into the open `## [B]` section and COMMIT them first (the oracle reads the changelog at the committed ref, and `release-cut` refuses a dirty tree); (2) `release-cut.sh B` cuts `vB-rc.(N+1)` at the tip; push `main` and wait for `ci.yml` green; (3) tag that RC and **PUSH it** (`git tag -a vB-rc.(N+1) HEAD`, then `! git push origin vB-rc.(N+1)`), and wait for it to publish (`release-watch.sh` then `release-verify.sh`). Do NOT keep it local-only: the rc cut's `worker-tag-autobump` has already pinned `workers.image.tag` to that RC, so an unpushed tag would leave the stable chart pointing at an `agent-*` image `release.yml` never built (that is exactly the 0.83.0-rc.7 incident, 2026-09-19, and `--promote` now REFUSES an in-flight RC that is not on origin). The redundant RC publish is the price of the invariant. (4) `release-cut.sh <B+1> --promote` sees zero delta since the new RC and takes the **promote-only** branch: it tags `vB` from the tip and cuts NO next candidate. Push `vB`, watch, verify. **Wart:** promote-only after an on-main RC cut leaves `main`'s `Chart.yaml` at `B-rc.(N+1)` (behind the stable). Harmless (nothing publishes off `main` until the next tag; ArgoCD tracks the newest published chart = `vB`), and the next feature cut clears it.
  - **The stable must be the candidate exactly, and `main` has moved on.** `release-cut.sh B --promote-only` (B = the in-flight base, not a next version): it tags `vB` from the RC commit and stops. No next candidate, no commit on `main`, no `main` push; work merged after the RC is not in `vB` and ships with the next plain `release-cut <next>`, whose coverage window starts at `vB`. It keeps `--promote`'s published-RC refusal and takes no `--changelog-file`/`--no-commit`/`--prev-tag`. Push `vB` only, watch, verify once. Same wart as above, plus `main`'s `## [B]` date stays at the RC-cut date (the tag's copy carries the promotion date). Prefer `--promote` when the next candidate is wanted anyway: a plain `--promote` with shipping work on `main` and an empty `[Unreleased]` fails the RC half and rolls the stable tag back.
- **A draft `## [X.Y.Z] - <date>` CHANGELOG section** (write it to a file for `release-cut.sh --changelog-file`), folded from `[Unreleased]` (keep an empty `[Unreleased]` on top), Keep-a-Changelog subsections (`### Added`/`### Changed`/`### Fixed`), **no em dashes** (user preference for user-facing content). The section is keyed by the STABLE base `X.Y.Z` even for a candidate (it is opened at `rc.1` and reused by every later `rc.N` and the promotion, PRD #1265 D3). **Every shipping merge since the previous STABLE `v*` tag MUST be cited** by issue/PR number or short SHA — the oracle `scripts/assert-changelog-covers-release.sh` enforces it (shipping = `api/**`, `agent/src/**`, `controller/**`, `web/src/**`, `deploy/chart/**`, `docs/**`, excluding tests; `docs(...)`-typed, `chore(release):`, and non-shipping-only merges are exempt). Enumerate them with `git log --first-parent --oneline <prev-stable-tag>..HEAD`. (If `[Unreleased]` already carries the entries, omit `--changelog-file` and `release-cut.sh` folds it in.)

**The three scripts** (`.agents/skills/uzi-release/scripts/`), in order:

1. **`release-cut.sh <X.Y.Z> [--promote|--promote-only|--skip-promote|--stable] [--changelog-file FILE]`** — the whole prep, deterministic. It DERIVES the coverage base (the previous stable tag) itself, so there is no `<prev-tag>` positional (`--prev-tag TAG` overrides for a repair). Default cuts `vX.Y.Z-rc.1` (folds `[Unreleased]`), the next `rc.(N+1)` for the in-flight base (needs an empty `[Unreleased]`), or refuses (exit 3, with the facts) when a lower RC is in flight. `--promote` creates the stable `vB` tag LOCALLY from a throwaway `release/B` worktree at the RC commit (metadata-only edits, a diff allowlist checked BEFORE any tag exists, worktree+branch removed after), then cuts the next `vX.Y.Z-rc.1` on main. `--promote-only` runs that promote half alone and exits (`X.Y.Z` = the in-flight base; `main` untouched, so nothing below applies to it). Either way it bumps `Chart.yaml`, runs `worker-tag-autobump.sh` (rolls the fleet IFF the agent runtime surface changed — the pin may legitimately STAY at a PUBLISHED RC tag inside a stable chart, D11, do not hand-normalize it; an unpublished pin is refused by the release guards), `changelog-links.sh`, commits `chore(release): <tag>` on main, and verifies with the oracle + `changelog-links --check`. On a verify failure it undoes the commit (`reset --soft`, edits kept staged) and exits 1. It does NOT push and does NOT tag the RC. Review `git show HEAD`, then `git push origin main`.
2. Watch **`main`'s `ci.yml`** on the release commit to green with **`.agents/skills/uzi-lander/scripts/watch-run-ci.sh --branch main --workflow ci.yml`**, **in the BACKGROUND**. release.yml does NOT re-run the full gate, so the tagged commit must already be green. Then tag the candidate `git tag -a vX.Y.Z-rc.1 -m vX.Y.Z-rc.1 HEAD` (release-cut prints the exact tag), and hand the user **`! git push origin vX.Y.Z-rc.1`** (the classifier blocks the tag push from the lead too — see below). **On a `--promote` cut the PUSH ORDER is: the STABLE tag `vB` FIRST, then `main`, then the RC tag** — the RC's changelog gate computes its coverage base from the tags it can see and needs `vB` on the remote first; release-cut prints the three lines in that order. **On a `--promote-only` cut there is one push, the stable tag `vB`**: `main` did not move, so there is no `ci.yml` run to wait for (the RC commit's was already green when the RC was tagged).
3. **`release-watch.sh <tag>`**, **in the BACKGROUND** — it watches `release.yml` AND `brew.yml` for every tag (PRD #1378: an RC publishes the opt-in `uzi-cli-rc` formula, a stable publishes `uzi-cli`). It AUTO-RERUNS a transient publish failure (any non-gate job) up to `--max-reruns` (default 2); gate failures (`assert-version`/`assert-changelog`/`prep`) are NOT rerun. Then **`release-verify.sh <tag>`** proves the publish: five image tags + chart on GHCR, the cosign "Pushing signature to:" lines, and the channel — a stable Release is marked latest; an RC Release is flagged pre-release with `releases/latest` unchanged (the previous stable). On a promote, run verify TWICE: once for the stable tag, once for the new RC.

**Run every watcher in the BACKGROUND, never a foreground blocking `gh run watch`.** A foreground blocking watch pins the turn for the 5-10 min CI/publish window and locks the user out of the session the whole time; that background-vs-foreground split is the one real reason watches must not block the lead. Use a `run_in_background` command (or a background waiter) and react to its completion notification.

**The tag push is blocked by the harness classifier — for the lead too.** Verified: `git push origin v*` returns `Blocked by classifier` from both a subagent and the lead session. That is a harness permission-mode block, distinct from the `protect-release-tags` ruleset (which would instead come back as a git/remote rejection). The annotated tag already exists locally (shared across worktrees via `.git`), so the fix is one command handed to the user: `! git push origin vX.Y.Z`. The admin role then bypasses the ruleset's creation restriction (`remote: Bypassed rule violations … [new tag]`). Do NOT route around it with `gh api` to create the ref — that defeats the same intent.

**Present the step-6 summary once the tag is pushed** — the publish runs unattended in the background (`release-watch.sh`) while you report what shipped, and you fold the verified tags (or a block) into the summary when `release-verify.sh` confirms.

## 6. Final summary (always end with this)
Report to the user, concisely:
- **One line up top**: version X.Y.Z and its status — cut / CI-green / tag pushed / **published to GHCR (images + chart)** / blocked on `<what>` (e.g. the tag push awaiting the user's `! git push`); CI green on the tagged commit; deploy state (or "deploy verification needs cluster access I don't have"). Since the publish runs in the background (step 5's `release-watch.sh`), the summary may go out while it is still publishing — say so, and update once `release-verify.sh` confirms.
- **What shipped, by issue/PR**: one table covering every PR **merged** (PR | issue | what it delivered in 1-2 sentences | review verdict) **and** every issue **closed** from a report-only run (issue | run id | what the run delivered | why it's closeable). Include PRs closed-not-merged (e.g. superseded) with the reason. The point is a single overview of what this release resolved and a terse description of each delivery.
- **Milestone check**: state plainly that nothing was silently skipped, and call out any milestone reframed/deferred with documentation rather than dropped.
- **Behavior changes to flag**: anything that changes existing behavior (surface it even though it shipped), plus post-deploy caveats.
- **Report-only / schedule sweep**: the close-candidate issues you surfaced in step 1 — which you closed (with the user's go-ahead), and which you left open and why (found-nothing survey, partial investigation, still-live). Never list one as closed unless it actually is.
- **Follow-ups**: adjacent-scope gaps the reviews surfaced; SDK-bump adoption opportunities (step 1); any renovate **major** deferred to its own issue because adopting it needed code changes (step 1); offer to file issues.
- **Merge mechanics handled**: migration renumbers, conflict resolutions, sqlc regen, any `--admin` merges — one line.
