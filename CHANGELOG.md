# Changelog

Notable changes to uzi, loosely following [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
Versions are release git tags (`deploy/chart/Chart.yaml`'s `version`/`appVersion`, Model B) — this
file is not bumped per-commit; `[Unreleased]` collects everything since the last tag. Under the
release-candidate train (PRD #1265) a `## [X.Y.Z]` section is opened by folding `[Unreleased]` at
the FIRST candidate cut for that version (`vX.Y.Z-rc.1`); later candidates of the same version append
to that open section, and promotion to stable only refreshes its date. So a section keyed by the
stable `X.Y.Z` may describe a version that is still a candidate; the git tag carries the `-rc.N`.

Format each bullet as a bold title on its own physical line, then the description directly on the
next physical line (NO blank line between them), the description on ONE physical line (no
mid-description newlines) indented two spaces so it stays inside the list item: a release's notes are
this file's `## [X.Y.Z]` section verbatim (`scripts/changelog-section.sh body`), and GitHub renders
single newlines in a release body as hard `<br>` breaks, so the title and its description render on
consecutive lines with nothing between them, while a hard-wrapped description would show as short,
ragged lines and a blank line after the title would open a gap. Keeping the description on one
physical line lets GitHub reflow it to the reader's width. Blank lines between bullets and `###`
subsection headers are unaffected. (Title-line-then-description established 2026-08-22, applied
back across earlier sections too; one-physical-line-per-bullet was the interim rule from 2026-08-21
through `[0.52.0]`.)

## [0.86.0] - 2026-10-06

### Changed

- **Ephemeral Docker preference on the Workers page ([#2278](https://github.com/vtmocanu/uzi/issues/2278)).**
  Persistent and ephemeral workers have separate sections. Instances offering the Docker tier show a saved Docker-capable checkbox beside auto-provision, usable even while auto-provision is off; writes share a pending lock and show local errors without changing confirmed preferences. Help text covers saturation, warm leases and the ephemeral cap, and qualifies Docker by the admin's repository allowlist. For eligible repositories, plain warm workers step aside so Docker-capable capacity can be provisioned immediately when no worker can claim the run; busy persistent workers retain the saturation debounce.

  When a dispatch assigns a valid export slot, the auditor (v15), fact-checker (v12), reviewer (v20) and tester (v18) reuse its path for sequential throwaway exports, allowing path-keyed build caches to reuse unchanged packages.

- **New hosted workers default to the large preset ([#2240](https://github.com/vtmocanu/uzi/issues/2240)).**
  Ephemeral provisioning defaults and falls back to L, and the persistent provision form preselects L. Existing workers keep their sizes; new workers reserve more CPU and memory capacity.

- **The agent gate distinguishes Linux-only contracts on macOS ([#1912](https://github.com/vtmocanu/uzi/issues/1912)).**
  Linux process-proof and descriptor-pinned filesystem cases report named skips on other platforms; portable cases retain coverage. The scratch guard normalizes slash spelling, while timing checks use controlled clocks, CPU budgets, and readiness or completion events.

- **Agent gates report quota and concurrency diagnostics ([#2240](https://github.com/vtmocanu/uzi/issues/2240)).**
  Gates print Node/libuv versions, detected parallelism, readable CPU quota, selected test-file concurrency and unit/M4 durations. A two-CPU default runs two unit files at a time; caller overrides and the procfs-denied serial cap keep precedence, and one-CPU workers keep Node's default.

- **Hosted worker sizes `l` and `m` get more memory: `l` 14Gi request / 20Gi limit, `m` 8Gi request / 12Gi limit ([#2127](https://github.com/vtmocanu/uzi/issues/2127)).**
  Workers running whole-program Go analyzer gates were OOMKilled at the old limits; the chart's worker LimitRange ceilings and memory quotas rise to match (CPU and disk are unchanged), at the cost of fewer `l` workers per node.

- **Codex subscription runs can wait out a usage window and resume automatically ([#2360](https://github.com/vtmocanu/uzi/issues/2360)).**
  The existing default-on usage-limit preference now covers recognized Codex window failures using structured evidence from the failed turn, with the latest exhausted-window reset or bounded fallback; Settings and per-run controls use shared Usage limits wording. Resume keeps the same Codex account and restores captured work, with approval reused when recovered; Docker workers retain the existing fresh-thread lineage break. Missing or unaccepted evidence and non-window limits fail as typed `rate_limited` without a reset promise; `rateLimitExceeded` and `sessionBudgetExceeded` are unchanged ([#2361](https://github.com/vtmocanu/uzi/pull/2361) tracks the former). Capture and publish can fail, so latest-work durability is conditional; each park can hold an issue lock and a run-bound hosted worker/PVC for up to the default 8 days, while fallback retries can exhaust the wait budget before a weekly reset.

- **Higher default resource requests for the api and the CNPG database.**
  The chart now requests 100m CPU / 320Mi for the api (was 50m / 128Mi) and 512Mi per CNPG instance (was 256Mi), matching what a live install actually uses, which reduces their eviction risk under node memory pressure. Limits are unchanged; override `api.resources` or `postgres.cluster.resources` to size differently.

- **Codex runs provision JavaScript dependencies before implementation ([#1743](https://github.com/vtmocanu/uzi/issues/1743)).**
  Dependency installation overlaps planning, reports installed and failed projects before the first implementation turn, and settles before capture, credential reconciliation and teardown across provider epochs.

- **Ephemeral workers default to M, with chart-configurable sizing ([#2412](https://github.com/vtmocanu/uzi/issues/2412)).**
  New ephemeral workers reserve 8Gi instead of 14Gi by default; operators can select S, M or L through `workers.ephemeralDefaultSize`. M now matches the earlier L preset: 1/4 CPU, 8Gi/12Gi memory and 25Gi persistent data; ephemeral data retains its separate 20Gi default. Persistent provisioning still preselects L; existing workers keep their stored size and existing M workers receive the CPU changes on their next controller roll, while existing 10Gi data PVCs stay at that size until reprovisioned. Upgrade note: an `UZI_EPHEMERAL_DEFAULT_SIZE` set under `api.config` or `api.secretEnv` now fails the render; move it to `workers.ephemeralDefaultSize`.

- **MR review rework now reads only comments from people with repository access and allowlisted review bots ([#2347](https://github.com/vtmocanu/uzi/issues/2347)).**
  Review comments from authors without repository access, or whose access can't be verified in time, are withheld from the rework's snapshot and prompt (the agent sees only a fixed count note) and never trigger a rework. An admin allowlists bots such as CodeRabbit or Greptile in the new admin-only `mr_review_trusted_bots` setting (`<base_url>#<forge_user_id>` entries, matched by forge instance and numeric id; edit it in the Admin Settings "Trusted review bots" card, list it read-only with `uzi admin review-bots`); allowlisting only permits ingestion, and a trusted bot's summary comment never triggers. Reply and resolve are allowed only on threads with an eligible comment in the run's snapshot, so a wholly withheld thread is refused (403); resolving a mixed thread also resolves the outsider's replies in it. Comments that could not be verified are retried on later ticks and fire once their author checks out, and an on-demand rework answers a distinct 409 when that is the only reason it has nothing to do. Authors waiting for a check sit in a per-MR FIFO queue, so an outsider flood does not suppress an eligible finding unless the pending set (one entry per unverified author, accumulated across fires; near the cap, when superseding could not be guaranteed to fit, an author's older id is kept so an author may briefly hold two entries rather than risk losing both) exceeds 10,000 entries, but it can delay it; the delay is bounded only under stated conditions (see the MR review rework doc), a departure from the issue's zero-delay criterion that the maintainer accepted on 2026-10-07. **Upgrade note:** after upgrading, CodeRabbit, Greptile and other non-collaborator review bots stop triggering reworks and stop reaching the prompt until an admin allowlists them, and `mr_rework` runs already in flight replay no review comments and cannot reply or resolve; one that had already started (it has a session or a stored plan) fails at its next claim instead, so start a fresh Rework now from its source run. See [MR review rework](docs/mr-review-watcher.md#the-trust-model).

- **A run requeued because its worker went stale is held for that worker's return, and the wait is explained ([#2705](https://github.com/vtmocanu/uzi/issues/2705)).**
  `WORKER_STALE_REQUEUE_GRACE` (default `10m`, `0` disables) keeps such a run pinned to its previous worker while that worker's row exists, so a worker killed and restarted resumes its own run from local recovery state instead of a peer starting cold; `WORKER_AFFINITY_CEILING` still releases it and a deleted worker row falls open at once. - **A completed run's guarded recovery archive can expire early once the published branch provably contains it ([#2625](https://github.com/vtmocanu/uzi/issues/2625)).**
  With worker and API support for `recovery_archive_redundancy_v1`, the worker asks the API from its receipt and covering-final-ACK cleanup, after releasing the journal lock, under one 30-second deadline that never gates cleanup. The API proves through the forge, against the live head of the published branch, that every root, the captured head (for parked WIP, a same-tree witness commit plus every parent of the captured head, using only the receipt's final head) and every recorded prerequisite are ancestors, bound to the exact released, completed, identity-stamped hold, generation, coverage digest and source commit. It then expires the capture as `published_redundant`, records the proof and deletes its payload, so ready-payload and instance byte quotas recover, and (with #2744) the expired capture no longer counts toward the per-owner capture limit. Any missing, mismatched or inconclusive proof keeps the normal retention, and a forge-evidence refusal is not retried for an hour. Accepted risk: after early expiry, later deletion or force-rewrite of the published branch is not protected by uzi, the same post-publication risk #2598 accepts for custody release. Discard and failed-run handling are unchanged.

- **An opt-in Code cross-check now adds the other model family's findings to the merge request, without ever blocking it ([#2170](https://github.com/vtmocanu/uzi/issues/2170)).**
  Turn it on in Settings → Run defaults (`PUT /api/me/cross-check` with `{"code": bool}`; it needs usable Claude and Codex credentials and warns when no online worker advertises `cross_check_code_v1`). Each issue, prompt, self-improve, CI fix, MR rework and task run takes the setting at creation, auto-approved or human-gated, and an interactive task is checked once at finalisation. When the lead finishes, the worker snapshots the committed head in a local-only ref (`refs/uzi-cross-check/<lead-run-id>`, never pushed) and a read-only child on the opposite family (Claude lead to Codex, Codex lead to Claude) checks it on the lead's own worker, strictly pinned there, in the cross-check lane; `CODE_CROSS_CHECK_TIMEOUT` (default 30m, at most 2h) bounds it and the wait is excluded from the lead's wall budget. With findings the lead gets one repair turn and reports addressed or declined with a reason per finding through `report_cross_check_dispositions` (a finding with none shows as not reported); there is no second check. - **A stale or fenced run stop no longer deletes the stopped clone's unfetched commits and dirty files ([#1786](https://github.com/vtmocanu/uzi/issues/1786)).**
  When a worker learned its claim was stale (`stale_claim`) or was fenced by an input receipt, ordinary teardown deleted the clone even when it held commits never fetched back or uncommitted and untracked files. The worker now stops that generation's own processes, makes no further report, publish or tracking write through the stopped claim, and keeps the exact clone (ledger `reclaimed` for attempt clones, a stopped-source marker for canonical clones) until an operator inspects and discards it. A clone is not covered, and is kept, when it holds a populated submodule (including under `ignore=all`), when the final process proof had to kill a writer, or when the stopped-source proof's Docker teardown failed; an operator discard on a Docker-wired worker is refused unless the Docker teardown reported `docker_unconfirmed`. A stopped exit keeps its clone even when the worker's coverage check finds it clean and anchored (the verdict is a snapshot that cannot see a writer that writes and exits after it, so it is logged as a diagnostic only); the cost is that every stale or fenced stop keeps its clone until an operator discards it, even one the worker's bare repository already holds, and attempt-ledger `reclaimed` entries stay until discard. Gitignored files are not covered by any capture and commits reachable only from the reflog (for example after `git reset --hard`) are not counted. A later claim of the issue (a newer generation of the same run, or a different run) starts on a fresh path on every worker and leaves the kept clone untouched. On a worker with no Docker host, a canonical clone kept by a stop persists that issue's attempt mode, writes the stopped-source marker and clears the plain journal, so later runs no longer fail with `worker_residue_blocked`; the cost is that the issue stays in attempt mode on that worker, so later claims start a fresh model session and the work carries over through the tracking ref and checkpoints, and this now applies to every stopped canonical clone, including one stopped while planning and clean at its seed base; stopped markers count toward the per-run cap of 64, past which the clone stays under its plain journal. Real writer exclusion through retirement, which would let a covered stopped clone be released again, is not shipped. A source whose detachment cannot be completed safely is still kept, and the later run is refused with `worker_residue_blocked` only where marker evidence names the path or the run (malformed or overflowing evidence, or a bound journal whose digest no longer matches) or the fresh seed finds unattributed processes in the key's footprint; if writing the attempt mode or marker fails the clone stays under its plain journal and routes as before (a journal that already names another source keeps its own routing, and the kept clone is then not listed), a malformed attempt-mode value or a failed write during discovery fails the run closed with the "corrupt journal or unsafe local recovery storage" reason, and a latched residue quarantine keeps the journal until the container restarts. The recovery-park and terminal-disk exits follow the same coverage rule, decided once at the recovery handler's exit rather than at the capture: a remembered or degraded capture result no longer counts. Exits that stop this generation (a stopped confirm, another generation, a stale park report) record the stopped source as above and keep the clone even when covered; park exits (`recovery_wait`, a live non-terminal status, shutdown) and terminal exits still release a clone proven covered at the handler's exit and otherwise keep the clone and its journal with no marker, so a resume on the same worker recaptures bytes written after the capture and a later run's terminal-orphan handling applies as before. Such a canonical clone is now listed by inspect and discardable by explicit operator confirmation only on positive evidence that its run is terminal: the worker reads the run's status through its existing ownership probe and the status must be `completed`, `failed` or `cancelled`, with no open hold, local record or live flight (a released or never-opened hold does not prove the run is no longer parked). An unreadable probe (404, error, timeout, malformed body) refuses with `run_state_unknown` and any other status with `run_state_not_terminal`; the probe is scoped to the claiming worker, so a leftover whose run moved off this worker reads 404 and its bytes are retained: while no open hold of this worker on the run covers it the channel refuses it (an open hold still gives `owner_hold_discard`, the owner's hold discard, even when the lifecycle is unknown), and its only automatic reclaim is a later run of that branch's terminal-orphan handling on this worker, which moves the clone to `<dataDir>/runner-quarantine/` (retained, never deleted automatically; the retention sweep never touches `runner-quarantine/`) and frees the canonical path, while a protected source or an attempt clone is kept in place; cross-worker reclaim needs a lifecycle read that is not worker-scoped and is an open follow-up, not shipped. The `uzi-watcher` `backup-runs.sh` now finds a detached kept canonical clone through its `uzi-stopped.<runId>.entry` marker, and for an active or failed run captures every attributed source on every running worker pod (journal or protected-descriptor sources, the marker canonical, and attempt clones whose last ledger entry for the run is `live` or `reclaimed`; an unreadable one counts only on that evidence or a journal naming it): the primary stays `<stem>.tgz` and each other source becomes a separately verified `<stem>.source-N.tgz` (members prefixed `<stem>.source-N.`); completed and cancelled runs capture protected-descriptor or marker sources and attempt clones whose last ledger entry for the run is `live` or `reclaimed` (the plain journal is ignored; a terminal status does not prove a predecessor's unique work is preserved), and a same-stem directory without `.git` is skipped only when it is positively empty. When an attributed source is listed but unreadable, a capture is not verified, or a probe of the search failed (a kubectl listing or exec, an unreadable bare repository), including when the run fell back to the bare tracking ref, the run logs `FAIL <run> (<label>): incomplete coverage: <k> of <m> attributed sources captured (<reasons>)` where `<m>` counts the sources found plus attributed unreadable ones, and the script exits 1 without advancing `latest`, replacing the earlier warning-only behaviour; any archive that did verify is kept. When nothing is captured at all (no readable clone and no owned tracking ref), a failed search instead logs `FAIL <run> (<label>) status=<st>: status saved, but the source search was inconclusive (<reasons>); retry` (still exit 1, `latest` not advanced), where a kubectl listing or exec failure, an errored probe, an unreadable `.git` and an attributed source listed but unreadable each name their pod or namespace in the reason, and capture failures name the source path. The cost is that every backup cycle now execs into every Running pod in `UZI_WORKER_NS` for each bound run, and one pod that cannot be exec'd into fails every bound run's cycle until it is fixed (the FAIL line names it and verified artifacts are kept); do not drop its namespace from `UZI_WORKER_NS` (which lists namespaces, so excluding a pod means excluding its namespace) unless you have verified that namespace holds no source a tracked run needs, since excluding it hides those sources from the search and the backup could read green without their work. An owner-authorized cancel of a non-credential run keeps its normal cleanup; a credential-deferred captured cancel is revalidated at cleanup, and a retained result keeps the clone. Park timing, report order and retries are unchanged. Retention is local: a pod replacement still loses an emptyDir clone.

- **Checkpoint publishes can recover from an HTTP 5xx within the same logical operation ([#296](https://github.com/vtmocanu/uzi/issues/296)).**

Any supplied caller deadline or abort signal is shared across attempts; each HTTP request retains its own client timeout. Some callers supply no outer signal, so the first request's timeout does not bound the total operation; the outer checkpoint gate (default 20m) still limits logical operations. Each replay uses a fresh producer for the fixed original source, candidate and floor, rechecks ownership, scratch/floor safety and remediation, and explicitly cancels and settles the abandoned producer first.
