### agent (Node 22 + tsx, Claude Agent SDK worker)

```sh
task gate:agent                            # lint + deadcode + typecheck + test
task lint:agent                            # the lint slot alone (oxlint; NOT ratcheted)
task deadcode:agent                        # the dead-code slot alone (knip) — exports tier is `warn`, see below
task test:agent                            # node --test via tsx
task typecheck:agent
cd agent && node --import tsx --test --test-timeout=120000 test/worker.test.ts   # single file — no target
```

**Carry `--test-timeout=120000` on the single-file form anyway.** `agent/package.json`'s `test` script is `node --import tsx --test --test-timeout=120000 test/*.test.ts`. The flag works: a 3-second test body run under `--test-timeout=1000` is cancelled with `test timed out after 1000ms`. A single-file recipe that silently differs from the gate is the same class as the reporting traps above: it can return a different verdict than the thing it is standing in for.

> **🔴 THIS PARAGRAPH SAID THE CAP WAS `30000` AND THAT "no test in the suite depends on it today" BECAUSE "every body in this suite finishes in under a second". BOTH CLAIMS WERE FALSE, AND THE SECOND IS THE INTERESTING ONE: WHAT `--test-timeout` GOVERNS DIFFERS BY NODE MAJOR, SO THE LOCAL GATE AND THE CI GATE WERE NOT MEASURING THE SAME THING.** Corrected 2026-08-03 after `test:agent` went **fail, fail, pass on three retries of one unchanged commit** (pipeline 20258, `duration_ms: 30003`, `location: runner.test.ts:1:1`).
>
> | | isolation | the capped test is | `runner.test.ts` |
> |---|---|---|---|
> | local, node **v26.4.0** | files share a process | each top-level **suite** | 7 suites summing to **~96s** — passed under a 30s cap, worst single suite 24.5s |
> | CI, **node:22-alpine** | child process per file | the **file** | **~25-30s** — CI is faster than the laptop, so it sat right on the line |
>
> So a file taking 96s locally passed a 30s cap while the same file failed it in CI, and **no local run could ever have caught this** — which is a live counter-example to the root `CLAUDE.md`'s "local and CI cannot drift apart" claim about the Taskfile gates. The divergence is not in the Taskfile; it is in the node major underneath it.
>
> Three things worth carrying past this instance. **A per-test cap silently becomes a per-file cap when isolation changes**, so the safe reading of any `--test-timeout` is "the tightest thing it might bind" — check which node the *slowest* environment runs. **The tally lies in this exact case**: a file killed by the cap is reported `cancelled`, not `fail`, so the summary reads `fail 0` on a red job, and the TAP plan shrinks (`1..207` → `1..202`) with the **file** named in place of its remaining suites — the same `node --test` tally trap documented below, arriving one level up. And **the only control that settles it is re-running one unchanged commit**: a code diff that cannot explain a failure invites inventing a mechanism, and a same-SHA retry costs one pipeline and answers it outright.
>
> `test/judge-runner.test.ts:167` unrefs a 60s timer; that unref is load-bearing for **wall time** (454ms vs 60263ms measured), not for the cap, since an idle timer holding the event loop open is not body duration. `agent/test/fake-api.ts:94` records the *other* way this file has hit the cap — a leaked listening handle on musl, every subtest passing. Two different causes, one symptom, so read the durations before assuming which one you have.
>
> **`runner.test.ts` no longer exists — it was split into seven `runner-*.test.ts` files on 2026-08-03** (same day, after the cap was raised), sharing `test/runner-harness.ts`. Everything above is the record of why the cap moved and stays accurate about the tree it was measured on; the file name is a past-tense identifier, not a live path. The split is what actually removed the knife-edge — the raised cap only bought margin — and it cut the whole agent suite from **112s to 46s** wall locally, because those seven suites had been running serially inside one file and now run as seven parallel files. **The general lesson is about the UNIT, not the number: node's per-file cap makes a large test file a serialization point that no timeout value fixes.** If a file approaches the cap again, split it before raising 120000.

**`cd agent && npm ci` — AND `npm install` — BREAKS THE MACHINE'S `agent-browser` FOR EVERY OTHER SESSION, and deleting the worktree afterwards is what makes it permanent.** `agent/package.json` pins `agent-browser` (`0.32.3`) as a dependency, and that npm package's `postinstall` **rewrites `/opt/homebrew/bin/agent-browser`** to point inside whatever `node_modules` just installed it — clobbering the brew formula's symlink (`0.31.1` here, a different version). Install into a throwaway worktree, remove the worktree, and the CLI is off `PATH` host-wide with a dangling link. Observed twice on 2026-07-27, hours apart, from ordinary validator gate runs — this is not someone being careless, it is the documented gate step doing it.

**`npm install` was added to that first sentence on 2026-08-02 (PRD #103 M3), measured rather than inferred.** This entry named only `npm ci`, so anyone adding a devDependency — which is `npm install <pkg>`, not `npm ci` — read it as not applying to them. It applies. Adding oxlint with `npm install --save-dev --save-exact oxlint@1.76.0` in `agent/` rewrote the symlink to `…/prd-103-m3-m6/agent/node_modules/agent-browser/bin/agent-browser-darwin-arm64`, verified with `ls -l` before and after. **And npm 11.17 makes it look as though it did not**: it prints `npm warn allow-scripts 3 packages have install scripts not yet covered by allowScripts:` naming `agent-browser@0.32.3` first, which reads as *"these were skipped"*. It is advisory — the postinstall ran anyway. So the warning is worse than silence here, because it says the word you were hoping for. The `brew unlink` + `brew link --overwrite` repair below worked exactly as documented (`0 symlinks removed`, then `1 symlinks created`); confirm the target is back under `/opt/homebrew/Cellar`, since `agent-browser --version` answers happily either way and differs only in the version it prints.

**`web/` is not exposed, and this is a build-graph fact rather than a measurement** — stated that way on purpose, because the same session ran `npm install` in `web/` first and did **not** read the symlink in between, so nobody observed that half. What is checkable: `agent-browser` appears in `agent/package.json` and in **neither** `web/package.json` nor `web/package-lock.json`, so there is no **`agent-browser`** postinstall in that tree to run. (That qualifier is load-bearing and the first version omitted it: `web/package-lock.json` carries **4** packages with `"hasInstallScript": true` — `esbuild` ×3 and `fsevents` — so `npm install` there runs four postinstalls. None of them is this one. A paragraph about not overclaiming had a false general statement wrapped around a true specific one.) If you want the observation, read `ls -l /opt/homebrew/bin/agent-browser` on both sides of the command.

**THE SAFE FORM IS `npm install --ignore-scripts …`, AND THE STANDING "SYMLINK INSTEAD OF INSTALLING" ADVICE CANNOT HELP YOU HERE.** That advice exists for a throwaway worktree that needs the deps; it is useless to anyone *adding* a devDependency, because writing `package.json` and the lockfile is the entire point. `--ignore-scripts` is already settled for this repo with its own measurements (`agent/src/js-deps.ts`, PRD #121), including that **a repo `.npmrc` with `ignore-scripts=false` does NOT override the CLI flag**. So: `npm install --ignore-scripts --save-dev --save-exact <pkg>@<version>`. The honest cost is that it skips *every* package's install scripts, not just this one, so a package needing a genuine native build stays unbuilt — recover that by reinstalling the single package or by the symlink route, both of which are cheaper than the host-wide repair above.

**Do not remove the failure by remembering to avoid `npm ci` — remove it by not installing at all.** A validator that needs the deps in a throwaway worktree can **symlink `node_modules` from the long-lived worktree** instead of installing: no install step, so no `postinstall`, so no clobber — and it is faster than `npm ci` besides. That is the change that ends the recurrence; everything below is triage.

**The tell is SILENT, which is why nobody catches it in time.** A clobbered link still resolves while the throwaway worktree exists, so `agent-browser --version` answers happily — with the npm version (`0.32.3`), not brew's (`0.31.1`), which is the only visible difference. Anyone asking "is `agent-browser` fine?" gets yes. The check that discriminates is `ls -l /opt/homebrew/bin/agent-browser`: read whether the target is under `/opt/homebrew/Cellar` or under somebody's `node_modules`. The breakage becomes host-wide `command not found` the moment that worktree is deleted, which is typically minutes later and by a different session.

**Repairing it takes a specific sequence, and the two obvious commands each fail on their own** (measured 2026-07-27, three repairs in one afternoon): `brew link --overwrite` alone answers *"Already linked"* and refuses, because brew's bookkeeping still thinks it owns the link. `brew unlink && brew link` then removes **0 symlinks** — brew no longer recognises the npm-written link as its own — and the plain `link` refuses because a file is in the way. What works is **`brew unlink agent-browser` followed by `brew link --overwrite agent-browser`**: the unlink clears the bookkeeping, the `--overwrite` replaces the foreign symlink. And the repair does not *hold* — the next `npm ci` in `agent/` undoes it. If you only need to drive a browser, call the Cellar binary directly and skip the whole cycle: `/opt/homebrew/Cellar/agent-browser/<version>/libexec/bin/agent-browser`, which no npm postinstall touches.

**`node --test` prints `ℹ fail 0` while tests are failing, when they fail by TIMEOUT.** Measured twice independently (PRD #121): three tests timed out at 15s, surfaced under `✖ failing tests:`, and were not counted in the `fail` tally; `$?` was 1 throughout, so the exit code is the field that told the truth and the tally is the one that lied. This is the **mirror image** of the `PASS=0` trap in `.claude/rules/go.md`: there, a tally shaped for the wrong invocation (no `-v`) reads zero from a **healthy** run; here, the right invocation reads zero from a **broken** run — same lesson, opposite direction. Read the exit code and the named failing tests, never a bare tally.
