## What M4 ships

1. **`deadcode` per Go module** — `golang.org/x/tools/cmd/deadcode -test ./...`, invoked via a **pinned `go run`**, matching the `sqlc@v1.30.0` precedent in `validate:api` and the `golangci-lint@v2.12.2` precedent M3 just set. Never a preinstalled global binary; git-manager's dependence on one is a trap the PRD explicitly declines to copy.
2. **A committed `deadcode` wrapper** — run, sort, diff against `.deadcode-baseline`, fail on additions. **Writing it is the milestone, not a flag to pass.** `deadcode` has no ratchet of any kind: plain report output, no baseline file, nothing upstream.
3. **`knip` for `web/` and `agent/`** — unused exports, files and dependencies, as a devDependency installed by the existing `npm ci`, with a `knip.json` per package.
4. **Taskfile targets** — `deadcode:api`, `deadcode:controller`, `knip:web`, `knip:agent` (name them as you see fit, but say why), wired into `gate:*`.
5. **CI wiring** — following M3's shape, which is settled: Go gets `lint`-stage jobs, npm folds into `validate:web` / `validate:agent`.
6. **Docs** — the `dead code` slot in **both** copies (`.claude/agent-team.md` and `.claude/agents/tester.md`), `CLAUDE.md` §Commands, `docs/dev-conventions.md`, `CHANGELOG.md`.

## The ratchet, per Decision 4 — different mechanism per tool, again

- **`deadcode`: nothing exists.** No baseline file, no diff mode, no severity tiers. The wrapper is the ratchet. ~20 lines, committed, with `.deadcode-baseline` alongside it.
- **`knip`: severity staging.** `rules: { exports: "warn", files: "error", … }` per issue type, promoted to `error` as each reaches zero, with `--max-issues` as a regression budget meanwhile.

**🔴 Success Criterion 2 names knip's staging as its ONE exception and you must not silently close it.** Its exact words: unused TS exports *"reach this bar last"*, because **warn-severity issues do not count toward knip's error total**, so a new unused export gates nothing until that type is burned down and promoted. `--max-issues` is a fixed budget, not a ratchet — fix one old finding, add one new, still under budget. If gate-on-new is wanted for exports before the burn-down finishes, knip needs the **same diff-wrapper you are writing for `deadcode`**. Decide, and say which.

## Calibration (Success Criteria 2 and 8) — read this before choosing a probe

**The first run must be checked against a symbol known to be dead**, so "no findings" is distinguishable from "tool not wired up".

**🔴 DO NOT use PRD #99's legacy `"Task"` switch case** in `web/src/components/RunEvent.tsx` (the two `case "Task":` arms). It is a **dead branch inside a live function**, and neither `deadcode` (unreachable *functions*) nor `knip` (unused *exports/files/deps*) can see it. Using it would produce a clean "no findings" from a working tool and read as a wiring failure.

That limit is real and belongs in the docs: **dead branches stay the reviewer's job.** Say so in the slot text rather than letting the slot imply coverage it does not have.

Use an unexported Go function with no callers, and an unused TS export. **Apply M3's four-property bar to every arm** — non-zero exit, the finding's **identity in the output** (the symbol name, not just a count), a sane path, and green on restore verified with `git status`. `task` exits 201 on any failure; test for non-zero, never a number.

## Inherited hazards from M3 — all measured, none hypothetical

- **Caches lie across sibling worktrees, in both directions.** golangci-lint's host-global cache made a *ratcheted* run falsely green and the *unfiltered* recording targets falsely loud. **Check before trusting a green: does `deadcode` cache? does `knip`?** Do not assume either is cache-free. And clean **after** deleting a throwaway worktree, not only before an arm — cached paths outlive the tree.
- **A new devDependency breaks every existing checkout's gate.** `knip` lands in both `package.json`s, so `gate:web` / `gate:agent` fail with `command not found` until contributors reinstall. **This owes a `CHANGELOG.md` line and a `docs/dev-conventions.md` line.** And the safe form for adding it is `npm install --ignore-scripts --save-dev --save-exact` — settled for npm in `agent/src/js-deps.ts` (PRD #121), including that a repo `.npmrc` cannot override the CLI flag. **Never a bare `npm install` in `agent/`**: it clobbers `/opt/homebrew/bin/agent-browser` host-wide, and npm's `allow-scripts` warning reads as "these were skipped" while the postinstall runs anyway.
- **Any new CI job goes into `.gate_needs` AND `.publish_needs`.** They enumerate by name; a job in neither lets a `v*` tag publish over its failure. **Check completeness by resolved `stage` through `extends`, never by job-name shape** — a name-based filter is exactly what hid `test:api-store-it` for months. Lists are currently 12 and 14, differing only by the two `publish:assert-*` entries; preserve that two-element delta, it is the readable invariant.
- **npm targets DELEGATE to a `package.json` script.** `Taskfile.yml`'s header: a target that reimplements the command drops its flags silently. Never a bare `npx knip` — it fetches from the network when the dep is missing, which a gate may not do.
- **No `sources:`/`generates:`/`status:`, no `dotenv:`, no `includes:`, no dynamic root `vars:`, no unquoted variable spliced into a `cmds:` line.**
- **A count is a lossy projection.** Any tool figure you record carries its date, its tool version and its exact invocation — and check for truncation flags before believing a total. golangci-lint's defaults silently capped a figure at 50 and cost three agents a wrong number.

## Open design points — settle these in the design wave, BEFORE any code

1. **Does the `deadcode` wrapper live in `scripts/` as a shell script, or inline in the Taskfile?** M2's `fmt-check:api` is inline with a guard; a 20-line diff-and-compare probably is not. ## R2 — KEEP THE WRAPPER, AS `scripts/deadcode-gate.sh`. IT IS ~15 LINES AND IT IS NOT OPTIONAL

**The wrapper survives the empty baseline because it is not the baseline that needs it — it is the exit code.**

**🔴 `deadcode` EXITS 0 WHETHER IT FINDS 0, 1 OR 3 DEAD FUNCTIONS. rc=1 ONLY ON A LOAD ERROR, AND THEN STDOUT IS 0 BYTES.** Measured. So on a module that does not compile, the naive wrapper captures an empty finding set, diffs it against the baseline as removals-only, and **"fail on additions" passes green**:

```
naive: run | sort > cur; comm -13 baseline cur; fail if additions
  on a tree holding 'func broken( {'   ->  RC=0, 0 findings captured
rc-first form, same three trees:          broken 2 | clean 0 | new dead func 1
```

That is M2's `test -z "$(...)"` hole through a different door — **an empty result set indistinguishable from a clean one.** The wrapper reads **rc before output**, and uses **2/0/1** matching `fmt-check:api`'s convention: 2 = instrument broken, 1 = findings, 0 = clean.

**Script, not inline, and the argument is M5's:** M5 adds `shellcheck` over `git ls-files '*.sh'`, so **a script gets linted and an inline Taskfile recipe gets nothing** — yamllint checks YAML, not embedded shell. Precedent: `scripts/assert-chart-render.sh`, invoked from `helm_chart`.

**Do not generalise the script to take a pluggable producer for M5.** shellcheck's identity is file+code+message and needs its own normalisation; M5's fallback is conditional on an unmeasured day-one count. **Copy the discipline, not the file.**

## R3 — POSITION-FREE IDENTITY, SORTED ON BOTH SIDES, `LC_ALL=C`

Default output is `path:line:col: unreachable func: Name`. **One inserted comment line above a baselined symbol moved `skillhook.go:75:24` → `:76:24`** — every unrelated edit becomes a spurious addition *and* removal. It also violates Decision 11.

Use the supported template form for the **baseline key**, while the live run still prints positions for the human:
`deadcode -test -f='{{range .Funcs}}{{printf "%s\t%s\n" $.Path .Name}}{{end}}' ./...`

**And the ordering subtlety, which is not what you would assume:** output is **stable across runs** (three runs × three shapes, byte-identical, including a 7475-line shape) but it is **deterministic, not lexicographic** — packages by import path, functions by (file, *line number*). So `sort` is **not idempotent on tool output**: sort **both** sides, and `LC_ALL=C` is part of the file's contract.

cd api && deadcode -test ./internal/...  86

**Only `main` packages are call-graph roots**, so dropping `cmd/server` and `cmd/uzi` from the pattern orphans everything they reach. The wrapper takes the **module root** and nothing else, and that must be stated where someone would otherwise "scope it to just our code".

## Standing hazards for anyone working in this tree

- **`golangci-lint` takes a HOST-GLOBAL lock and a host-global result cache**, and this repo is a bare clone with many sibling worktrees running agents concurrently by design. `parallel golangci-lint is running` with `exit status 3` means another worktree holds it: **re-run, do not report a red gate.** The status cannot distinguish it from a real finding, because `go run` prints the 3 as text and then exits 1 itself. The message text is the only discriminator.
- **The result cache replays other worktrees' findings and lies in BOTH directions.** A `../` in a finding's path is an invalid run, not a finding. Clean the cache **after** deleting a throwaway worktree, not only before an arm.
- **Never `npm ci` in `agent/`.** Its `agent-browser` postinstall rewrites the host's `/opt/homebrew/bin/agent-browser` symlink into whatever `node_modules` it just installed, breaking the CLI host-wide for every other session the moment your worktree is deleted. ## Deliberately NOT in this MR — proposed as their own issues

Both are the auditor's ungraded items: real mechanisms, no demonstrable attack at this SHA, and both pre-existing patterns this MR extends rather than introduces. Folding them in would grow an MR that is already three milestones deep.

## W12 — the LINE-selection half of the grep trap, for `CLAUDE.md`

**`git grep <literal> | grep <post-filter>` drops exactly the lines whose wording differs from the one you had in mind.** The tester's sweep failed this way twice, and the second failure is the one worth recording, because it happened **inside the command written to diagnose the first**:

- Sweep 1, post-filter `grep -iE 'deadcode|dead code|finding|prints'`: `.claude/agents/tester.md:319` and `docs/dev-conventions.md:192` **were in the file list and did match `44`**, then the filter dropped them — their lines carry none of those four words. One of three in-list hits survived.
- Sweep 2, post-filter `grep -viE '…|[0-9]{3,}|…'`, intended to strip noise: **`[0-9]{3,}` matches `2026` inside `2026-08-02` and `103` inside the PRD's own path**, so it silently removed **all five** live sites, including the two already known. It returned a tidy 11-line result set containing none of the answers and no indication anything was missing.

**Why this is strictly nastier than the file-selection half `CLAUDE.md` already documents** (the ignored-but-tracked entry, with `git grep` as the fix): file selection fails **uniformly** — a whole file is in or out — whereas a content post-filter fails **selectively**, dropping precisely the lines phrased differently from your mental template. That is the same wording-drift property that made `.claude/agents/coder.md` defeat a literal grep during M3.

**The rule, and it is the tester's own sentence: a sweep for a claim that appears in five phrasings cannot be post-filtered on any one of them.** Anchor on the invariant token, take the whole file set, and read the hits — the filtering is the reader's job, not the pipeline's. Add this to `CLAUDE.md`'s grep section, adjacent to the ignored-but-tracked entry, since the two are halves of one failure.
