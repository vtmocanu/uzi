## Non-negotiable traps (all three are silent-green shapes)

- **🔴 `oxlint src test` EXITS 0 WHILE REPORTING FINDINGS.** `correctness` defaults to `warning` severity and warnings do not set the exit code. A target without `-D correctness` (or `--deny-warnings`) is a lint job that can never fail. This is the whole reason the calibration below must assert a **nonzero exit**, not merely that output appeared.
- **🔴 The oxlint `react` plugin is OFF BY DEFAULT**, and **`rules-of-hooks` is `pedantic`, not `correctness`.** A config that enables the plugin and stops there still never runs the rule this milestone exists for. Both must be in the shipped config; neither is discoverable from a clean run.
- **🔴 Do not gate with `test -z "$(cmd)"`.** M2 proved that shape fails OPEN when the tool exits nonzero and writes to stderr. Where a target must inspect output, use the assignment-plus-explicit-`|| exit N` form already shipped in `Taskfile.yml`'s `fmt-check:api` — read that recipe, do not restate one. Where the tool sets its own exit code correctly (golangci-lint always; oxlint **only** with `-D correctness`), let the exit code do the work and say so in a comment.

## R1 — EXTEND THE EXISTING `validate:*` JOBS. DO NOT OPEN NEW `lint`-STAGE JOBS.

`.gate_needs` and `.publish_needs` enumerate gate jobs **by name** (lead-verified at `06404d51`: nine names in the first, eleven in the second). `*gate_needs` is consumed by the kaniko build template and `e2e:kind-smoke`; `*publish_needs` by the publish-image template and `publish:chart`. **A new lint job absent from both means a `v*` tag pushes every image and the OCI chart to Harbor while the lint job is failing.** The pipeline reddens afterwards; the artifacts are already out.

This is not inference. `validate:api`'s own script comment already records it as the reason M2 did not open a new job: *"No new job, because `.gate_needs` and `.publish_needs` enumerate jobs BY NAME. A new lint-stage job absent from both produces this repo's signature failure shape: a red job nothing `needs:`, with the images and chart publishing anyway."*

**The PRD contradicts itself here and the contradiction is resolved in favour of the later, more specific statement.** Decision 3 prescribes new jobs (`lint:api`, `lint:controller`, …). M1's own Files section prescribes the opposite for web: *"at M1 that is `task check-docs:web` + `task typecheck:web` for `validate:web` … **M3 adds `task lint:web` to the first**"*. M1's wins. Extending removes the failure mode instead of mitigating it, adds no `.task_setup` fetch and no new `cache:` cycle, and follows M2's precedent.

**Record the deviation from Decision 3 in the PRD as part of this milestone** — a spec that disagrees with the shipped code is the failure this PRD spends its length on.

**Consequence M5 inherits, and it is not optional:** M5's checks are repo-wide (`shellcheck`, `yamllint`, `gitleaks`, `govulncheck`), so they genuinely cannot fold into a per-toolchain `validate:*` job and M5 **will** open lint-stage jobs. Adding them to **both** anchor lists is M5's definition of done, and the two lists become a second single-hot-line contention that the PRD's Parallelization section does not list (it names only `stages:` and the two `package.json`s). Note this in the PRD too.

## R2 — RATCHET IN `.golangci.yml`, REF IS `origin/main`, WITH A PRE-FLIGHT ASSERTION

```yaml
issues:
  new-from-merge-base: origin/main
  whole-files: true
```

- **Config, not a command-line flag.** Lead-verified, golangci-lint 2.12.2, 2026-08-02: `config verify` exits **0** on those keys and **3** on a bogus sibling key, naming it (`additional properties 'no-such-key' not allowed`) — so the positive control fires and the green means something. One recipe, byte-identical locally and in CI, Success Criterion 1's symmetry exact, and no variable spliced into a `cmds:` line.
- **`origin/main`, never bare `main`.** A bare `main` resolves in this bare-clone-with-worktrees layout and does **not** resolve in GitLab's detached-HEAD checkout, where no local branch exists. That is a check that works on your machine and degrades in CI — precisely the divergence SC1 exists to prevent.
- **🔴 THE FAILURE MODE IS FAIL-OPEN-INTO-NOISE, AND IT IS WHY THE PRE-FLIGHT IS MANDATORY.** Measured by the auditor: an unresolvable ref does not skip the ratchet and does not error — golangci-lint logs a single `level=warning msg="[runner] Can't process results by diff processor…"` and reports the **entire unfiltered finding set**. The first MR then reddens with the whole pre-existing debt and the only explanation is one warning line buried in a `prefixed` log.

  So `lint:api` and `lint:controller` open with a **literal** pre-flight, in the Taskfile so local and CI both get it:
  `git rev-parse --verify -q 'origin/main^{commit}' >/dev/null || { echo "lint: origin/main is unresolvable — the ratchet would silently report the whole backlog; fetch it (GIT_DEPTH=0) before linting"; exit 2; }`
  Literal ref, no splice. **`exit 2` not `exit 1`**, matching `fmt-check:api`'s convention: 2 = the instrument is broken, 1 = there are findings. `task`'s own rc is 201 for both, so the distinction has to live in the recipe.
- **CI needs `GIT_DEPTH: "0"` AND the ref actually fetched.** Depth alone is not sufficient and the repo already knows it: `publish:assert-changelog` is the only job setting `GIT_DEPTH: 0` today, it also sets `GIT_STRATEGY: clone`, **and it still runs an explicit `git fetch`**. Whether `origin/main` exists after a fetch is a property of the runner's refspec, not of `.gitlab-ci.yml` — so this is settled by running a pipeline, not by reading config. The pre-flight is what makes a wrong guess loud.
- **Rejected — `CI_MERGE_REQUEST_DIFF_BASE_SHA`.** It sidesteps the ref question and the auditor is right that it is available on `merge_request_event` pipelines. It is also **CI-only**, so it forces either a banned Go-template splice or a shell env reference that is empty locally and then **silently lints everything**. That trades a loud CI problem for a silent local one, in the milestone about silent-green gates.

## R3 — INVOKE golangci-lint VIA PINNED `go run`, INSIDE THE ALREADY-PINNED `golang:1.26`. VERIFY BEFORE COMMITTING.

The official `golangci/golangci-lint` image is a **third image family** and the auditor measured why it is the wrong choice: it ships Go **1.26.2** with **`GOTOOLCHAIN=auto`**, while both `go.mod` files require **1.26.4** — so `go: downloading go1.26.4` happens on every lint run. The pinned `golang:1.26` this pipeline already uses is 1.26.4 with **`GOTOOLCHAIN=local`**, so no existing job fetches a toolchain and switching is disabled outright. Adopting that image would make lint the first job whose effective Go toolchain is fetched rather than pinned.

**Preferred:** `go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.12.2 run …`, exactly matching the `sqlc@v1.30.0` precedent already living in `validate:api`. Sumdb-verified, version pinned identically local and CI (which also kills the unpinned-local-binary divergence), no new image, no `.task_setup` change.

**Do NOT use `go get -tool`.** That writes golangci-lint's whole dependency tree into `api/go.mod`, and this repo keeps that file deliberately clean — the separate `controller` module exists precisely so `k8s.io/client-go` stays out of it. A module-versioned `go run pkg@version` builds in its own context and does not touch `go.mod`; confirm that is still true when you run it.

**MEASURE IT BEFORE COMMITTING.** Real risks: upstream discourages `go install` of golangci-lint, cold-`GOCACHE` build time, and version-info embedding. If it proves unworkable, fall back to the digest-pinned image **with `GOTOOLCHAIN: local` set explicitly in the job's `variables:`** so a version mismatch fails loudly instead of fetching — and say in the MR which route you took and what the measurement was. The auditor derived the digest two independent ways (Docker Hub tags API and the registry `docker-content-digest` header, agreeing); derive it yourself rather than copying, and note the image runs as uid 0, has apk but no curl (so `.task_setup`'s apk branch fires), and needs no `entrypoint: [""]` override.

## C7 — THE RESULT CACHE PRODUCES A SILENT GREEN ON THE RATCHET ACROSS TWO WORKTREES

Not in Amendment 1 and directly relevant to this repo's bare-clone-with-siblings layout. golangci-lint's result cache is **host-global** (`~/Library/Caches/golangci-lint`), shared across every sibling worktree exactly like the Go build cache `CLAUDE.md` documents. Reproduced deterministically:

```
cache clean; cwd=<dirA>/api  golangci-lint run ./...                   EXIT=1  (warms cache)
            cwd=<dirB>/api  golangci-lint run --new-from-merge-base…   EXIT=0  "0 issues."  <- WRONG
cache clean; cwd=<dirB>/api  golangci-lint run --new-from-merge-base…   EXIT=1  api/new.go:6:11 (errcheck)
```

dirB genuinely contains a new finding. The cached result replays dirA's absolute paths, so the diff processor cannot match a path outside the repo against `git diff` output and drops everything. **The unfiltered run stays red with wrong paths; the ratcheted run goes green. The ratchet is the half that lies.**

Two worktrees at the same SHA is the normal state of a fresh `git new-wt`, and it is **exactly the configuration of the M3 calibration when the tester runs it from its own worktree.** So, binding on the calibration:

- **Run `golangci-lint cache clean` before each calibration arm.**
- **Assert the finding's path is repo-root-relative (`api/...`). A path containing `../` is an invalid run, not a finding.**

Residual stated honestly by the architect: reproduced in a two-module scratch replica, not in the uzi tree, and the exposed configuration is two checkouts whose *package under test* is byte-identical. The mitigation is cheap; take it regardless.

## C13 — golangci-lint DELIVERY: MEASURE BEFORE CHOOSING

Amendment 1's R3 preferred pinned `go run`. The architect prefers a sha256-pinned tarball into the already-pinned `golang:1.26`. **Both agree on the part that matters — do NOT adopt the `golangci/golangci-lint` image**, because it ships Go 1.26.2 with `GOTOOLCHAIN=auto` against both modules' `go 1.26.4`, making lint the first job in this pipeline whose effective toolchain is fetched rather than pinned, and because `.go_job` already supplies the `GOPATH`/`GOCACHE`/`go mod download`/`cache:` that golangci-lint needs to type-check.

The remaining choice is delivery, and it is a measurable trade:
- **`go run …@v2.12.2`** pins the version identically local and CI, which kills the unpinned-local-binary divergence outright and matches the `sqlc@v1.30.0` precedent already inside `validate:api`. Cost: a cold-cache build of a large dependency tree.
- **sha256-pinned tarball** is fast and is a reviewed, shipped shape here (`.task_setup`, `e2e:kind-smoke`). Cost: it is a CI-only mechanism, so the local binary stays unpinned and local/CI can disagree about what a finding is — and arm64 needs a second checksum literal.

**Measure the cold and warm `go run` cost on this tree and choose on the number, then record it in the MR.** If the tarball wins, the target must additionally assert the expected version so local drift is loud. Do **not** use `go get -tool`: it writes golangci-lint's whole dependency tree into `api/go.mod`, and this repo keeps that file deliberately clean — the separate `controller` module exists precisely so `k8s.io/client-go` stays out of it.
