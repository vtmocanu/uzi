## Non-negotiable traps (all three are silent-green shapes)

- **🔴 `oxlint src test` EXITS 0 WHILE REPORTING FINDINGS.** `correctness` defaults to `warning` severity and warnings do not set the exit code. A target without `-D correctness` (or `--deny-warnings`) is a lint job that can never fail. This is the whole reason the calibration below must assert a **nonzero exit**, not merely that output appeared.
- **🔴 The oxlint `react` plugin is OFF BY DEFAULT**, and **`rules-of-hooks` is `pedantic`, not `correctness`.** A config that enables the plugin and stops there still never runs the rule this milestone exists for. Both must be in the shipped config; neither is discoverable from a clean run.
- **🔴 Do not gate with `test -z "$(cmd)"`.** M2 proved that shape fails OPEN when the tool exits nonzero and writes to stderr. Where a target must inspect output, use the assignment-plus-explicit-`|| exit N` form already shipped in `Taskfile.yml`'s `fmt-check:api` — read that recipe, do not restate one. Where the tool sets its own exit code correctly (golangci-lint always; oxlint **only** with `-D correctness`), let the exit code do the work and say so in a comment.

## Taskfile constraints (from `Taskfile.yml`'s own header — read it)

No `sources:` / `generates:` / `status:` on any target. No `dotenv:`. No `includes:`. No dynamic root `vars:`. Never splice a variable unquoted into a `cmds:` line. Serial, not concurrent. Every load-bearing flag gets an inline comment naming why it is there.

## Scope ruling — correctness-only

Type-aware linting (`oxlint-tsgolint`) is **its own issue**, not M3. The PRD's reason is behavioural, not budgetary: 119 of web's type-aware findings are `onClick={asyncHandler}`, and wrapping a promise-returning handler changes what happens to a **rejection**. That is 119 chances to change error behaviour under cover of a lint fix. Do not let it ride in.

The React Compiler rule family is likewise excluded — this repo is on React 18.3.1 and does not run the compiler.

## Calibration (Success Criteria 2 and 8) — the acceptance bar

Two mutations, each proving its own gate is live, **each asserting a nonzero exit**, both recorded in the MR description with the exact command and its output:

1. Add an unchecked error return in a scratch Go file → `errcheck` fires through `task lint:api` → **nonzero exit** → remove it → green.
2. Add a violating hook call in a scratch web file → `rules-of-hooks` fires through `task lint:web` → **nonzero exit** → remove it → green.

`CLAUDE.md`'s rule applies verbatim: *a control that produces no output is not a control.* A first run reporting nothing is indistinguishable from a linter that is not wired up. Restore with a `cp`-based backup, **never `git checkout --`** (it reverts to HEAD and silently wipes uncommitted work).

Do the same for `lint:controller` and `lint:agent` if it is cheap; if you skip either, say which and why in the report rather than leaving it implied.

## Open design points — SETTLE THESE IN THE DESIGN WAVE, BEFORE ANY CODE

1. **Where does the `--new-from-merge-base=main --whole-files` ratchet live — the Taskfile target, or the CI job only?** Success Criterion 1 says `task gate` reproduces every toolchain check CI runs *and CI runs no toolchain check `task gate` does not*. Putting the ratchet only in CI breaks that symmetry; putting it in the shared target means a contributor on `main` lints nothing. Both readings are defensible. Pick one, state the cost, and write the reason beside the target.
2. **One root `.golangci.yml` or one per module?** golangci-lint v2 walks up from the working directory for config, so a single root file may cover both modules given the `dir:` each target uses — **verify by running it, do not reason about it.** Per-linter test-file exclusions differ between the modules in principle; check whether they do in fact.
3. **Does the ratchet need `GIT_DEPTH: "0"` alone, or also an explicit `git fetch origin main`?** The PRD says merge-base needs the *ref*, not merely the depth, and MR pipelines do not fetch `origin/main` by default. Establish which, by reading the CI config rather than assuming.
4. **`goconst` on a repo of this size** — git-manager's own CLAUDE.md records 136 goconst warnings accumulating unnoticed. Confirm it is worth enabling here given the ratchet, or justify leaving it off with a one-line note in the config (that file's convention: every *disabled* linter carries a justification).
