## Lead's scouting measurement — the one the milestone was told to branch on

The PRD opens M5 with *"First step is a measurement, and the milestone branches on it"*, and Open Question 4 asks whether `e2e/run-e2e.sh` survives severity staging or wants splitting first.

**Measured by the lead 2026-08-03, shellcheck 0.11.0, at `3ca30153`, over `git ls-files '*.sh'` (14 files):**

```
git ls-files '*.sh' | xargs shellcheck -f json1 -S style
EXIT=1     error 0     warning 4     info 9     style 2
```

**`--severity=error` returns ZERO.** So the PRD's contingency — *"if day-one error-severity findings are non-zero, severity staging alone cannot deliver a gating job, and the fallback is the same diff-wrapper M4 writes for deadcode"* — **does not fire**, and Success Criterion 2's shellcheck half can be met by severity staging with no wrapper. Open Question 4's answer is that `run-e2e.sh` survives comfortably: it carries 1 of the 4 warnings and 8 of the 11 info/style.

The four warnings, in full, because the whole tail is small enough to print:

```
e2e/run-e2e.sh:3704            SC1010  Use semicolon or linefeed before 'done'
agent/templates/entrypoint.sh:208,225,228  SC3067  In POSIX sh, test -O is undefined
```

**Three of the four are on the production-reaching script**, and SC3067 is a portability claim about a real shell, not a style nit. Whether it is a live bug depends on what interpreter that file actually runs under in the shipped image. **That is a question for the design wave to answer from the code, not one this brief answers.**

Two constraints on how much this measurement is worth:

- **It is a LOCAL shellcheck 0.11.0 reading.** CI will pin some version, and a different version reports differently. The design must say which version it pins and where the pin lives; the count must be re-derived under the pinned version before any severity threshold is chosen.
- **A count is not a control.** Nothing here says the gate this milestone builds is live. That is the tester's work and it must not be designed from this section.

## Hard constraints inherited from M1–M4

Not optional, and each has already cost this PRD a round:

- **`.gate_needs` and `.publish_needs` enumerate jobs BY NAME** (carry-forward item 2). Every lint-stage job M5 opens must be added to both. A job missing from `.publish_needs` means a `v*` tag publishes every image and the OCI chart to Harbor while that job is failing. **M5 inherits this in full** — its checks are repo-wide and cannot fold into a per-toolchain `validate:*` job. Verify by parsing, never by grepping.
- **The `lint` stage already exists and already has jobs** (`lint:api`, `lint:controller` from M3). M5 appends; it does not create the stage.
- **The CI job provides the tool, never devbox** (Decision 7). Options in preference order: a pinned `go run pkg@vX.Y.Z` inside the already-pinned `golang:1.26` (M3's precedent, and how `govulncheck` should arrive), a digest-pinned official image, an npm devDependency installed by the existing `npm ci`, or a version- and sha256-pinned `before_script` fetch.
- **A new devDependency silently breaks every existing checkout's gate** (carry-forward item 12), and in `agent/` the required remedy collides with the documented `agent-browser` host-wide clobber. If M5 adds one, the safe form is `npm install --ignore-scripts --save-dev --save-exact <pkg>@<version>`, and it owes a `docs/dev-conventions.md` line.
- **Taskfile bans**: no `sources:`/`generates:`/`status:` on any gate target, no `dotenv:`, no `includes:`, no dynamic root `vars:`, and never an unquoted variable spliced into a `cmds:` line. npm targets **delegate** to a `package.json` script rather than reimplementing the command.
- **Recipes live in `Taskfile.yml` and nowhere else** (Decision 9). `CLAUDE.md`, the `.claude/agent-team.md` paste-block and the `.claude/agents/*` tails name **targets**.
- **Give a new job its own `cache:` prefix** if it builds something the jobs sharing that key do not (carry-forward item 6).
- **The three fail modes** (carry-forward item 3) — fail-open, fail-loud-but-misleading, silent no-op — each need a different fix. Every check M5 adds should be classified against them before it ships. `exit 2` = instrument broken, `exit 1` = there are findings; `task`'s own rc is 201 for both, so the distinction lives in the recipe.
