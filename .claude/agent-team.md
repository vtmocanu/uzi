# Agent team workflow for uzi

Generated by the `agent-team` skill; roster adapted from an internal team.

> **How to add to this file.** Its growth rate is the thing most likely to make
> it useless, and every rule that lives only here is unenforced on teammates by
> construction: they cold-start and never read it, so `roles.yaml` and the role
> tails are what reach them (`grep` the role files and you find one passing
> citation of this manifest). Three rules, about where text goes, not about
> writing less:
>
> 1. **Lead each section with its OPERATIVE sentence; evidence below it.** A
>    reader who stops after one line still has the rule.
> 2. **A rule that has failed TWICE migrates; it does not grow.** Move its
>    operative sentence into the role body of whoever must keep it (the
>    skills-repo `roles.yaml`, which reaches every repo) and leave the evidence
>    here with a pointer. A third paragraph in a file nobody must read cannot fix
>    a rule already in it.
> 3. **This file is the ARCHIVE; the role tails are the OPERATIVE copy.** Check
>    the pointer's target actually holds the thing before moving anything.

## Orchestrator workflow

You (the team lead) NEVER do implementation, review, or audit work yourself. You
coordinate the team via Agent (name + subagent_type) + SendMessage + the Task*
tools. Default flow:

0. **Non-trivial task** (new component, cross-cutting change, new or changed
   contract): dispatch architect BEFORE the coder and fold its design into the
   coder's prompt; skip it for small fixes. Dispatch it too whenever a PRD is
   written or reviewed. Open design questions go to the user, not to the coder as
   guesses. An unsatisfiable acceptance criterion is one such question: escalate a
   crisp go/no-go BEFORE authoring a multi-milestone plan.
1. **Coder** with full task context. It runs the component gates it touched
   (`task gate:api` / `gate:controller` / `gate:web` / `gate:agent`, or `task
   gate` for all four, plus `./e2e/run-e2e.sh` + `./scripts/smoke.sh` for
   stack-level changes) before reporting done. One coder per file-disjoint unit.
2. **Reviewer + auditor IN PARALLEL** on that unit's diff + report, pinned to
   commit SHAs. Add fact-checker in the same wave when the change touches
   claim-bearing artifacts (README, plan, specs, "we beat X" claims); REFUTED
   claims are blocking. Add architect when the change moved boundaries. Where
   there is more than one unit, add an integrated pass over the combined diff
   after the last unit lands.
3. **Tester** on the scenario surface when behavior changed.
4. **Resolve** blocking findings (route them back to coder via SendMessage).
5. **Spec-keeper**, once findings are resolved, with the change summary plus a
   user-vs-AI provenance split (only the lead has seen the conversation).
   `specs/ai.md` applies directly; `specs/human.md` edits go to the user first.

## Context handoff (CRITICAL)

Every teammate cold-starts with no memory of prior conversation or other
teammates' outputs. Whatever you write in the spawn `prompt:` is the entire
context they have, plus the body of `.claude/agents/<role>.md`.

Therefore every spawn prompt MUST include:
- File paths the teammate should read (the spec, the files being modified,
  CLAUDE.md/CONTRIBUTING.md when authoring rules matter)
- A summary of any prior teammate's findings when chaining workers
- The exact error message when retrying after a failure
- If context is long, write it to `.claude/agent-team-tasks/<slug>.md` and
  reference that path in the prompt instead of pasting inline

## Re-derive the claim at the moment you assert it (CRITICAL)

**Re-derive a claim from the code at the moment you assert it, however sure you
are.** Having verified something once is not knowing it: you verified a *past*
state and you assert in the present. This applies to every role, including the
lead.

**A comment is an assertion, so it deserves the same mutation as a test.**
Freeze the field, drop the line, move the path, and watch the assertion fail.
If nothing fails, the comment describes a mechanism that is not there.

**A test's FAILURE MESSAGE is an assertion too, and it is the one nobody
mutates.** A message that names a cause the check never measured is worse than a
vacuous test: a vacuous test merely fails to help, while a lying message actively
routes the next reader into the wrong subsystem. Ask of every diagnostic: could
this string be printed by a condition other than the one it names? (2026-07-21: an
e2e guard failed with "the worker claimed nothing (204)" when the actual cause was
a wrong jq path into a 200 response — `[ -n "$x" ]` cannot tell "no response" from
"wrong path", both give the empty string. It cost the lead an hour aimed at queue
contention. Fix: split the status check from the extraction so the two modes
produce two different messages.) Corollary for shell harnesses: `fail` called
inside `$( )` exits only the subshell and writes to stdout, which the substitution
*captures* — the run aborts under `set -e` with the diagnosis swallowed and nothing
printed at all. Set a global and return instead of printing.

Corollaries, each earned:
- **The code is usually right; the story is what rots.** Every instance below had
  correct logic and a wrong description. Nobody was careless: each claim was true
  when written and stopped being true, or was never re-derived from the code.
- **Presence is not efficacy.** "The attribute is there" and "it reaches anyone"
  are different claims. Two validators can both be right and appear to conflict
  because they asked different questions: find the two questions before picking a
  winner.
- **The experiment that justifies a choice usually also bounds it.** Record both
  halves, not the flattering one.
- **It hides in the artifacts with no gate.** Comments get read in review, tests
  get run, commit messages get diffed. A "still open" list, a checkpoint, a
  handoff note is prose nobody executes, and it decides where the next person
  spends their time. Re-derive those too.
- **The check can be as blind as the claim: a verification that cannot fail is not
  evidence.** A distinct failure from a wrong measurement, and worse, because
  re-running a blind instrument re-runs the blindness — "just double-check it" is
  the instinct this class defeats. `grep … | head -N` cannot show a summary line
  past N (→ a fabricated count); a page-width probe cannot show a truncated label
  (→ a "no regression" that regressed); `pgrep -f <name>` matches its own command
  line (→ a phantom process, or a deadlock); a stale git ref cannot show remote
  drift; a green CI *summary* cannot show that the phase you needed never ran.
  Defense: ask *what result could this instrument not produce?* — if the answer is
  "the one that would prove me wrong," it is not evidence. Prefer an instrument
  that holds an **identity** over one that holds a **pattern**: `kill -0 <pid>`
  over `pgrep -f`, `getElementById` over `querySelector`, `toBe(el)` over
  `textContent.toMatch`, `git grep <sha>` over a working-tree grep, a
  named-assertion count over an exit code. Naming the class buys no immunity — on
  the PRD that surfaced it the author hit it five times, once *during the shutdown
  check seconds after committing the note that says the author isn't immune*, each
  caught only because an identity-based check dissented from the blind one.
- **A constraint stated in a form cheaper to satisfy than to mean is an invitation
  to satisfy it.** "No horizontal scroll" was met while the lane label rendered
  zero characters; the intent was "the layout is not worse." A correct constraint
  measured with a blind instrument and a blind constraint measured well fail
  identically silently — they are two different questions. The writer of a
  dispatch owes the *intent* alongside the measurable proxy, and the receiver owes
  one question asked **before** the work, of the instruction itself: *what would
  make this true but still bad?* It is the only check in this section that
  prevents the work rather than catching it after.
- **A hostile fixture that cannot reach the sink it targets passes vacuously.** A
  payload clamped, trimmed, or flattened before it reaches the code under test
  proves nothing: a 63-rune XSS string cut at a 48-rune clamp, leading tabs eaten
  by `TrimSpace` before the column they were meant to break, a benign label making
  a sanitize-mutation a no-op. Caught only when the test fails for the *wrong*
  reason and someone asks why. Run a **positive control** — confirm the un-fixed
  code actually fails your check first — or "0 failures" is the blind-instrument
  result above wearing a green hat.
- **A number you did not see is a claim, not a measurement.** A figure read off a
  truncated window (`| head`), or a tally inherited across a handoff and
  incremented but never re-derived, is not evidence even when every digit in it is
  real — build the list first and let the count fall out of it, never the reverse.
  On one run both a coder's mutation count and the lead's running "claims caught"
  tally failed this way; the honest report is the corrections themselves, each
  recorded where it does work, not a total.

Validated 2026-07-16 on a PRD where **nine claims fell over**, each believed by
someone competent and each disproved in seconds once someone ran it: a PRD
decision asserting a quota was atomic (measured: 8 of 8 concurrent provisions
passed a quota of 2); a design claiming one test caught a misplaced lock (it
stays green, because a misplaced lock still blocks); a design claiming only a
browser could prove a UI gate escapable (a page-level test does it); three code
comments naming mechanisms the code did not have; a test-count baseline carried
from memory; a handoff note that outlived the fix that killed it and was
reported open twice; and a browser pass that "verified" a `title` reaching no
screen-reader user. The coder that made four of them diagnosed the root: *"I
trusted any claim I had personally verified once, and stopped re-checking it,
because having checked it felt like knowing it."*

**Lead's share of this:** relay findings as claims to check, not facts to apply.
When you forward a teammate's finding, say what was measured and what was
inferred. Verify a load-bearing claim yourself before acting on it, and say
plainly when you did not.

### Uzi-local corollaries and traps

- **Audit the support under conclusions you AGREE with.** Unchecked claims
  accumulate not under contested conclusions (those get argued and checked) but
  under sound ones, in corroborating detail nobody reads adversarially because the
  point is already accepted. When a claim goes into a document, ask which clause does
  the work and which is *support*, then re-derive the support or delete it: evidence
  attached to a conclusion that stands without it is evidence nobody will check.
- **Correctness is not reachability**, a different axis from presence: asserting an
  attribute's exact value is strictly stronger than asserting its presence and still
  satisfiable while the information reaches nobody (a `title`-only detail passes a
  jsdom test on its exact string that no keyboard, touch, or screen-reader user can
  reach). jsdom verifies an attribute is correct, never that anyone can reach it.
- **A check passes because the case you chose is one where broken and correct
  AGREE** — every instrument reports green for the right reasons, yet the *input* was
  one both implementations handle identically (an all-current version fixture
  certifies a classifier that never normalizes; a `v`-prefixed semver probe cannot
  discover that the `v`-prefix assumption is the bug). Ask of the INPUT, not the
  instrument: is there a version of this code that is wrong and would still pass on
  the case I picked? If yes, pick another case.
- **A directory-wide `gofmt -w` sweeps foreign pre-existing drift into your commit,
  under your message** — run `gofmt -l ./api` on your own tree first and scope `-w` to
  your own files by name. `fmt-check` detects drift, not a sweep (a swept tree is
  gofmt-clean, so the gate is green by construction).
- **A fixture whose rows DELIBERATELY share coordinate strings pins a join for free,
  and "tidying" it to distinct values silently deletes that coverage** — the pin
  comes from the row-count guards (`rows != 2`), so dropping a join half lets other
  rows attach and the guard fires. Cite the MECHANISM (a cross-tenant attach), never
  the tally.
- **Three verification traps live elsewhere, dropped here to a pointer:** plain `$?`
  after a pipe reads the last command not yours, `${PIPESTATUS[0]}` expands to nothing
  in zsh, and zsh does not word-split an unquoted variable in a mutation loop
  (`.claude/rules/go.md`, `.claude/rules/stack.md`); and a green Go suite can mean
  nothing ran, the `PASS=0` family (`.claude/rules/go.md`). The unifying rule: a
  verification step needs its own positive control, same as a live-DB run or a
  mutation. The two React-specific traps (a vacuous `activeElement.textContent` focus
  assertion; colliding `role="status"` regions) now live in `.claude/rules/web.md`.

## A claim about what would happen if you removed it is not readable from the code

**A counterfactual — *if X were absent, Y would happen* — needs an EXECUTED
counterfactual, not a reading.** Remove the guard and watch the test redden;
delete the line and watch the build fail; gut the fixture and confirm the gate
goes red. If actually removing it is too expensive, then you do not know: say "I
did not check" rather than asserting. This is the generalization of "a failed
grep is not evidence the text is absent" past greps, and on the branch that
earned it every agent including the lead asserted a counterfactual from reading,
and reading could not have caught any of them.

- **A null result is an observation of your INSTRUMENT, not of the world:** a grep
  that finds nothing tells you about your pattern, a green test about your fixture, an
  empty precedent search about your search. Before believing a zero, run the pattern
  against a string you KNOW is present, because the pattern you choose encodes what
  you expect, so an uncalibrated search confirms your expectation rather than testing
  it.
- **The rule covers WHEN a mechanism fires, not just whether:** "this is an `init()`,
  so it runs at boot" is a counterfactual, and Go loads the package during `go test`
  too, so it runs there in every importing package; the inverse is a check in an
  earlier-sorting file's `init()` panicking on a healthy tree. Each costs one build.
- **Two corollaries:** a *negative* test case must sit in a fixture containing a
  *positive* match, or its green is satisfiable by a mechanism that never fires; and
  an *absence* assertion needs a guard that the thing still exists under that name.
- **A retraction propagates only as far as the people holding copies, so chase the
  copies** — and that does not mean paste the same correction, since a copy carrying a
  *different*, narrower claim the retraction did not touch correctly changes nothing.
  **Read the commits that landed under you, not just the diff of the file you are
  about to touch:** a "what landed since my commit" read is cheap and owed on a moving
  tree, and is what catches a stale claim copied into shipped files.

Keep if you keep only one: the sharpest instance was written by the author who had
catalogued this exact class two revisions earlier, and caught only on a re-derivation
they volunteered. Fluency in the rule buys no immunity from it.

## Citing and dispatching across a moving tree (CRITICAL)

Several agents commit against one worktree, so **the tree a claim was read from
may already be gone by the time the claim is acted on.**

- **0. Name the tip in the dispatch, and add: "take the live tip if it has moved
  past this, and say so rather than guessing."** The dispatcher's half is the
  cheaper fix, and it was a branch's dominant failure mode: most lead-vs-validator
  disagreements resolved to "both correct for the SHA each read." **Verify the
  artifact immediately before SENDING, not before COMPOSING**, since the gap is not
  zero on a long dispatch, which is exactly when it matters. **On a RE-SEND, name the
  tip you verified against and what you saw**, because a cold-started agent cannot
  tell a re-dispatch from new scope and a named tip settles it with one `git
  rev-parse`. Two lead-side failures that are not stale reads: asserting a completed
  action from having *instructed* it, and reading a grep's absence as "elsewhere"
  when the absence WAS the defect.
- **0b. When a live-tree measurement disagrees with a pinned one, the first
  hypothesis is MID-EDIT, not defect.** Eliminating one cause does not leave only
  one: enumerate three (this SHA, elsewhere, mid-edit) and test the cheapest
  first. For an EARLY tree the disposition is *re-probe*, never escalate, and it
  costs one rerun.
- **1. An instruction to change a file is a CLAIM about its current contents, and
  it EXPIRES.** Read the file before acting on any dispatch that quotes it, names a
  line number, or says a fix "did not land": open it at HEAD and report the
  refutation rather than complying. The instructor reads a tree the recipient is
  actively changing, so the instructor's read is the one that goes stale and the
  recipient is the only one positioned to notice. Fluency in a rule is not
  exemption from it; the instructor is the one who cannot see their own instance.
- **1b. A measurement's shelf life is set by what it measured.** A claim about a
  *comment* expires on the next commit that touches it (one expired within a single
  commit); a claim about a *query's behaviour* expires when the query, fixture,
  assertions, or ENVIRONMENT change (the migrations that apply before yours, the
  Postgres version, the sqlc version). `git diff <sha>..HEAD -- <paths>` can only
  FALSIFY a measurement, never confirm one, and a green suite does not close it
  (passing proves the tests pass, not that they would fail if the code were wrong).
  A measurement is bound to a WORKING TREE as well as a SHA, so a persisted `cd`
  silently rebinds it to another tree with no change in the output; a tree with
  `MERGE_HEAD` set is neither state, so cite file lists and mechanisms from it and
  re-derive counts on the committed merge.
- **A TRUNCATED VIEW is not the output.** `| head -N` / `| tail -N` produce output
  that stops at your limit, indistinguishable from output that ended. Count with
  `rg -c`, `wc -l`, or `--stat`'s own summary and reconcile it against the rows you
  can see; the disproof is usually on screen (`--stat` says six while three rows
  show).
- **1b-i. Dating a number is not bounding it.** State which part is durable and
  which is incidental, and bind the incidental half to a SHA, not a date: a date
  names when someone typed, a SHA names the tree the number describes. When you fix
  an instance, grep for the DEFECT (`RUN=`, `PASS=`, a bare tally), not for the
  string you changed, or you leave the copy phrased differently.
- **1b-ii. Duplicate the CLAIM, never the COUNT.** A duplicated claim is a
  cross-check that fires when reality moves (a guard silently went missing and was
  caught only because three artifacts carried three different guard counts); a
  duplicated count is N things to drift. Resolve a count disagreement by deleting
  the tally and citing the mechanism, never by picking a winner, which removes the
  only instrument that detected the defect. When you add a guard, ask "what did I
  just make unreachable, and what claims that reachability?"
- **1c. "Verbatim" binds the claim, not the examples.** A claim generalises; an
  example is a measurement with a shelf life. Ship the claim verbatim; restate the
  examples as dated history (*"as of <date>, before X landed, …"*), which cannot
  expire.
- **A summary is checkable for SHAPE; only the artifact is checkable for FACTS.**
  Both are real capabilities and neither substitutes for the other: a validator
  can predict a draft's structural defect sight unseen and still find a wrong
  number in it ninety seconds after reading the actual words.
- **2. A line number is meaningless without a SHA** — cite the assertion by name or
  message, not by line. This rule has migrated to `roles.yaml` and the architect /
  researcher / reviewer tails, which reach teammates; it stays here as archive.
- **3. Before dispatching a recommendation, name the other recommendations
  touching the same file or fixture, and say whether they compose.** Collisions are
  two locally correct instructions written against different files at different
  times and never read against each other; the agent merging sources into one work
  list is the likeliest producer and the least likely to notice.
- **4. Compile a fold before you prescribe it.** `sqlc generate` + `go vet` settles
  it in under a minute with no container and no database, so the check costs less
  than the correction (see `.claude/rules/go.md`, sqlc types by expression).

## Two negative results from instruments that share an assumption are ONE negative result

**A search that comes back empty is evidence only if it could have come back
full.** Running a second search and getting empty again feels like corroboration
and usually is not: if both are shaped by the same guess about naming, they fail
together, and their agreement measures the guess rather than the code.

Measured 2026-07-27, and it nearly shipped a false security invariant. A field was
ruled safe on the premise that one query was the only one listing a table:

- the first grep searched for a substring the counterexample's name **does not
  contain** (the two names share no common substring, though they name the same
  concept), so it was structurally incapable of returning it — and its short
  output was read as an enumeration;
- the second searched a directory the relevant page does not live in, for a type
  name that differs from the one actually imported.

Two empty results, each shaped by a different naming guess, treated as agreement.
The premise was false: an admin route rendered every user's row, so the "safe"
field was the only cross-principal sink in the batch. It was caught because the
agent asked to *write the claim into a comment* checked it first — the last cheap
moment before a false invariant becomes code carrying two names.

**Enumerate from the schema object, not from a name you already know**: every
query touching the table, not every query whose name matches a string you have
already seen. The same reduction covers the sibling failures — a grep over
already-inventoried field names, a fixture built to demonstrate one state and read
as a search for its opposite, an assertion over one channel read as whole-component
coverage. **All four search a space defined by what you already found.**

**Corollary for the lead:** relaying a teammate's verified-sounding premise is not
verification. When a claim is about to be *written down* as an invariant — in a
comment, a spec, a doc — re-derive it yourself, however well-sourced. That is the
moment it stops being a finding and starts being something the next reader trusts
without checking.

## An instrument that cannot produce the disconfirming answer is not evidence

**Before believing a result, ask what answer the instrument could NOT have
returned.** If that answer is the one that would have proved you wrong, the run
measured your setup, not the code. Nine incidents, each a different tool failing a
different way, the shape underneath one:

| the instrument | what it could not return |
|---|---|
| `grep -F` with a `\|` alternation | anything, ever: `-F` makes the pipe a literal, so the pattern matched a string nobody wrote |
| `git show $c:path` under zsh | the file: the `:a` history modifier ate the path, read as a missing file |
| `comm` over two path lists | any overlap: one side carried a `./` prefix, so two identical sets compared disjoint |
| `cut -d=` under zsh | a whole field: word-splitting truncated the value being compared |
| file mtimes, to prove a run happened | the distinction between reading and idling, the entire question |
| a mutation that failed to compile | a red for the stated reason; vitest printed `Tests no tests`, read as "unguarded" |
| a mutation reddening on `SQLSTATE 42P18` | a red for the stated reason: Postgres rejected the *parameter typing*, not the predicate |
| a direction inversion that made the action a no-op | a red at all: the assertion never ran, so green meant "nothing happened" |
| a test that aborts before its own assertions | the disconfirming answer: a `t.Fatalf` on a status identical in both configs fired first |

**For mutation testing specifically: a mutation is verified by the tests going red
FOR THE REASON THE MUTATION NAMES.** Read the failure text, never the count.
`.claude/rules/go.md`'s "compile the mutation before you believe it" is necessary
and not sufficient: it eliminates only the non-compiling row. Put the checks that
can only fail in one configuration BEFORE any check that fails identically in both,
so the discriminating assertion actually runs.

Two shapes a green looks most trustworthy in: **an interrupted long run** (a zero
exit and an absent-FAIL grep are both satisfiable by a run that stopped early;
the tell is the phase count, or reaching the terminal teardown phase), and **a
silently-dropped Tailwind arbitrary variant** (a mistyped variant is discarded at
build with no error, leaving a green class-token test asserting a class with no CSS
behind it; only reading the built stylesheet can tell "shipped" from "typo'd").

## A right measurement with the wrong gesture attached to it

**A number can be correct and still be about something else, and that is harder to
catch than a wrong number, because the number reproduces, so checking it confirms
the wrong claim.** A drag-drop finding arrived as measurement plus explanation and
swapped two adjacent rows of one table: the `[30,10] -> [10,30]` measurement was
exactly right about the *lane-whitespace* gesture and was attached to the
*self-drop* gesture, which is a no-op. Editing the doc as instructed would have
replaced two true rows with one false one.

When a finding arrives as measurement + explanation, the measurement reproducing
does not confirm the explanation: vary the thing the explanation names (here, the
gesture) and check that the number moves with it. And when told to correct a doc,
read the doc first: this one was already right, and the instruction to change it
was the error.

## A rule nobody is keeping is a different failure from a rule that is wrong

**And it needs the opposite fix.** Most entries in this file are stated mechanisms
that were not the operative ones, and the remedy is to re-derive and rewrite. This
one is the mirror: a *correct* rule that nobody was running. Three concurrent
writers shared one worktree while the context doc said "exactly one teammate writes
at a time"; nothing was lost, but it held by luck, because a single `git add -A`
from any of them would have swept the others' in-flight work into one commit.

Writing the rule more clearly would not have helped; it was already clear. What was
missing is the relaxation being visible at the moment it was taken. So if you
deliberately relax a rule here:

1. the relaxed constraint must be **provably** satisfied, not merely expected (file
   sets provably disjoint);
2. every participant must be **told explicitly** what replaces it (stage by path,
   never `-A`, never `-a`, never a directory);
3. **say so in the doc, at the time** — the next reader gets the doc, not your
   outbox.

When you find a rule being violated, establish which kind it is before fixing it:
weakening a correct rule to match what people were doing is the failure that looks
most like tidying up.

## TYPECHECK the mutated tree before reading the test result

**A mutation that does not compile produces a run that says nothing, and "nothing"
is one glance from the finding you were hoping for.** Measured 2026-07-27, on the
last round of a long batch: a replacement string carried literal backslashes into
the mutation script, the mutant was a syntax error, the runner failed to *collect*
the file, and the run printed `Tests  no tests`.

The dangerous reading was right there — *"the mutation applied and no test went
red"* reads as *"this site is unguarded"*, which would have been a false
**Blocking** finding against a correct fix.

**It is the inverse of the silent no-op mutation** (a fold that matches nothing,
runs green, and understates). Both look like "the tests did not say what I
expected", and only the compiler separates them:

- run the typechecker (`npx tsc --noEmit`, or the language's equivalent) **between
  mutate and run**; `.claude/rules/go.md` states the same for the Go/sqlc case;
- keep the pre-assert that the pattern was present and the post-assert that it is
  gone;
- add a post-assert that no stray escape reached the source, since the escaping bug
  is what produced the syntax error in the first place;
- **read the collection line, not just the tally** — "no tests" and "1 failed" are
  both "not the green I expected", and only one of them is a result.

**Read every red's arrival time and line number, not just the count.** A red at the
runner's timeout is a lookup failing, not an assertion firing: two render tests
reddened at a 5-second `findByText` timeout, so their real assertions had never
executed. After anchoring the awaits on something the mutation cannot move, the
same reds arrived at named lines in 2-4ms.

## Mutate at the CALL SITE, not in the shared helper

**Folding a mutation into a shared function proves the function is live. It does
not prove every caller routes through it** — and those are the two different
claims a control is usually asked to settle.

Measured 2026-07-27. A helper had two call sites; the control replaced its body
with the identity and two cases reddened, which read as proof the behaviour was
load-bearing. Both reddened cases exercised **the same call site**. The other arm
had no assertion at all, so a fix applied to only one of the two would have passed
that control unchanged — which is what happened, and it was caught by an audit
reading a comment rather than by any test.

**The discriminating instrument is per-call-site:** fold each site separately and
require **each** to red on its own, on disjoint sets. As the tester who found it
put it: *"mutating the shared helper is the composition-point mistake one level
down — the same shape as the finding itself, which is presumably why neither of us
saw it from inside."* A control written from inside an abstraction inherits that
abstraction's blind spot.

## An assertion defines its CHANNEL

**"Nothing in this component carries X" and "nothing in this component's TEXT
carries X" are different claims, and the test that means the second reads like the
first.** A whole-subtree text assertion cannot see attribute values, a form
control's `value`, or the document title. The component is in scope; the channel is
not, and the assertion's own wording papers over the gap.

Measured 2026-07-27: nine tests asserting over rendered text all passed while
**four** untrusted values reached tooltip and accessible-name attributes
unstripped, across three rounds of review. Every one was found by a sweep or a
mutation control; **none by a test.** The demonstration is one line — revert the
attribute fix and only the new case reds, while the existing text-channel case for
the *same field* stays green.

Three habits follow:

- **Fix at the composition point, not the render sites.** One descriptor feeding
  five renderers gets one fix where it is composed. But state the coverage
  honestly: in that batch the comment claimed all five were covered when only two
  consumed that descriptor.
- **A test that renders the wrong component passes forever.** One test rendered a
  component that does not render the field under test. It was green and worthless,
  and only its own control caught it. **Files in that batch needed a component
  extracted to make the claim assertable at all** — if the value is not reachable
  by a test, that is a finding about the code's shape, not a licence to assert
  something adjacent.
- **A guarded render can make an assertion VACUOUS rather than weak.** Where the
  markup renders behind a truthiness guard and the fixture leaves the field empty,
  the subtree never mounts and a "no bad characters present" assertion passes over
  nothing. Require a **positive** assertion that the value is on screen. The two
  mechanisms differ: one branch did not mount at all, while a sibling mounted with
  a partial string, so only the positive assertion caught the second.

Pairs with the per-fact sweep below, and with `vitest` not typechecking: run the
typecheck alongside and narrow a type rather than casting, since a cast hides the
regression the type would have caught.

## A value reconstructed at a layer that does not own it

**The derived path always works on the happy path, which is why it survives
review: it is not a bug on the day it is written, it is a SHAPE.** The tell is a
value reconstructed somewhere that does not own it while the authoritative source
sits one layer away. Stated as "prefer authoritative sources" the rule is unusable;
stated as "which component OWNS this value, and am I reading it from that one?" it
is checkable in seconds.

Two checks, both cheap:

1. **Which component owns this value?** Ask it about the *write*, not the read: the
   owner is whoever last set it, and if that write happens after your read, the
   value cannot exist yet (the sharpest form: the derived value is not stale, it is
   unobtainable, because the run has not chosen yet).
2. **If the authoritative field were wrong, would any test notice?** A test can
   only fail on a field something reads. On a field nobody consumes yet, "no test
   fails" is the *precondition* for the bug, not evidence against it: the green is
   CAUSED by the gap it is read as ruling out. The only way to learn anything is to
   make something read the field.

**The moment a previously-ignored field becomes load-bearing, audit every fake of
that endpoint IN THE SAME COMMIT.** Leniency that was free while the field was
unread (a fake answering `{}` where the real handler answers `{"run":{…}}`) becomes
a lie at exactly that commit, and it agrees with the new code rather than
contradicting it.

Sits with **TYPECHECK the mutated tree**, **Mutate at the CALL SITE**, and **An
assertion defines its CHANNEL** as one family: a green or red that measures the
instrument instead of the code, here because the instrument was never pointed at
the value. The worked instances are recorded as Decisions in
`adr/0035-run-limit-retry.md` and the PRD Decision Logs; read those for the "why"
on the specific fields rather than re-narrating them here.

## Sweep per FACT after the last behavioural commit

**A batch's own findings falsify claims in code it never touched, and nothing
per-commit or per-file catches that, because the stale claim is not in the diff.**
After the last behavioural commit — before the final review wave, not after it —
grep for every *fact* the batch established and find every place that asserts
otherwise.

Validated 2026-07-27 on a batch that shipped six code defects and ten prose ones.
Every prose defect was a true statement a neighbouring commit falsified, and none
had an executable control. The code was right every time. They cost four review
rounds and were found by four different agents.

Three things make the sweep work:

- **Sweep for the CLAIM, not the wording.** A grep for the phrase misses a sentence
  asserting the same thing in different words; one file carried the superseded
  measurement table without ever using the searched phrase.
- **The correction must state the mechanism, not just delete the false clause.** A
  comment that is no longer false but no longer explains anything leaves the next
  reader to re-derive it and get it wrong.
- **A CITATION is an assertion too, and `git log -S` is its control.** "Commit X
  fixed this" is checkable and almost never checked.

  **But the plain `-S` form is FAIL-OPEN on a merge-introduced line**, which makes
  it the wrong instrument inside the rule that teaches distrust of fail-open
  instruments: git omits merge diffs by default, so a line produced by a conflict
  resolution returns nothing, which reads as "refuted". Three commands, not one,
  and disagreement between them IS the finding:

  ```
  git log --oneline -s -S '<string>' -- <path>                             # non-merge introductions
  git log --oneline -s --diff-merges=first-parent -S '<string>' -- <path>  # + merge resolutions
  git log --oneline -s --first-parent --diff-merges=first-parent -S '<string>' -- <path>   # when did MAIN get it
  ```

  Three teeth: `--oneline` and `-s` are both required, or `--diff-merges` floods
  the output with full commit headers and nobody runs it twice; keep the path
  filter, or the query also matches docs that merely *quote* the string; and `-S`
  counts occurrences, so a MOVE that leaves the string behind (in an explanatory
  comment) is invisible, so read the chain, not the head.

**Corollary for the lead:** when you dispatch a fix that names N sites, verify all
N landed. The one that got missed was missed because the lead checked the site it
had argued about and not the four it had listed in the same message.

## Quality gates

Paste this block into every tester, reviewer and auditor dispatch: teammates
cold-start and never read this file, so a slot you do not paste is a slot they
cannot run. The slots name **targets, not recipes** (every recipe lives in root
`Taskfile.yml`; `task --list` enumerates them): a stale pasted *command* still
runs, prints `ok`, and reports green, while a stale *target* dies loudly. Once a
`none (gap)` slot has been raised, the lead appends a `noted` marker; roles report
a gap only when its line carries no marker.

- **format**: `task fmt-check` (gofmt over both Go modules; the per-module
  `fmt-check:api` / `fmt-check:controller` run first inside each component gate, so
  a component gate already covers this slot for its component).
- **lint**: `task lint` (composite: the four components plus repo-wide
  `lint:shell` / `lint:yaml` / `lint:formula`, which hang off `gate:repo` and are in
  no `gate:<component>`). The Go half is ratcheted in `.golangci.yml`, not on the
  command line, so Task's echo cannot show it: read that file. `lint:api:all` /
  `lint:controller:all` print the unfiltered backlog and gate nothing. See
  CLAUDE.md "Lint ratchet" for the caps, the `origin/main` pre-flight, and the
  host-global lock.
- **typecheck**: `task typecheck:web`, `task typecheck:agent` (the Go typecheck is
  `vet` + `build` inside the Go component gates).
- **test**: `task test:api`, `task test:controller`, `task test:web`,
  `task test:agent`, `task check-docs:web`.
- **dead code**: `task deadcode` (Go = `deadcode -test ./...` per module against a
  committed empty baseline, gating at zero; npm = knip). A green means different

  by golangci-lint `unused` earlier in the gate). See CLAUDE.md "Dead code".

- **security scan**: `task scan:secrets` (gitleaks, inside `gate:repo`, inside
  `task gate`, so it is the tester's slot). Canary-wrapped: read the "canaries
  DETECTED" line, not just rc=0, since `.gitleaks.toml` auto-discovers and a
  contributor can disarm the scanner in the same commit that adds a secret. Each

- **long-running**: `task gate` (the whole gate, from a cold checkout it exceeds the

**Reading a gate result.** `task` exits 201 on any failure, never the underlying
command's code, so test for non-zero, never for a number. Output is prefixed per
task and components run serially, so a failing component's named test is readable
while the run is still going. The composite verdict is the exit code: the
per-component forms (`--- FAIL` for Go, the summary line for vitest, `ℹ fail` plus
the exit code for `node --test`) tell you WHICH component and test failed, never
pass/fail on their own, because a component whose runner never ran contributes
nothing to another's pattern. See CLAUDE.md "Reading a gate result".

**The four load-bearing flags** (`-count=1` and `-race` on the Go test targets,
`-p 1` on `./e2e/run-store-it.sh`, `--test-timeout=120000` in `agent/package.json`)

## The pattern worth inheriting, above any individual finding

**Every substantive correction is someone applying a rule to OTHERS that its own
author had stated and not applied to themselves.** Not carelessness: the
rule-holder is simply not the person best placed to notice their own instance.
Across one branch it was four for four roles, with the lead accounting for half the
instances, which is the opposite of what seniority predicts. Holding a rule and
applying it to yourself are separate skills, so position in the loop is not
protection. The fix is never "be more careful": it is a mechanism that does not
depend on the author noticing.

- **A true local fact that ends the search is not a finished one.** "There is no
  custom timeout configured in the file or a vitest config" was correct and *was*
  the root cause of five intermittent failures across four PRDs, and it did not ask
  what it implied beyond the file.
- **Apply the rule to the CLASS, not the instance.** Before shipping a fix, name
  the other instances of the same claim, usually with one grep. But **CLASSIFY each
  hit before you touch it**: a grep cannot tell a CURRENT CLAIM (fix it) from a
  HISTORICAL RECORD (leave it, because rewriting it manufactures a false history),
  and the more mechanical the sweep, the more reliably it corrupts the second kind.
  **Sweep on the UNIQUE token, not the ambiguous one**: a bare migration number, an
  id, or a version identifies whatever each writer meant on the day, so a blind
  `sed` over it rewrites true statements in other PRDs' records.
- **The unifying diagnosis: all of these substitute a PROXY for the PROPERTY** — an
  assertion count for isolation, a blanking fold for a discriminating one, a comment
  for the behaviour, agreement for verification, a passing commit for a measured
  property. The property is always *would this fail if the code were wrong in the way
  it is actually likely to be wrong*, and no proxy answers it.
- **Why two validators, and do not rely on care:** neither miss was catchable by the
  person holding the rule, so the second validator does the part the first
  structurally cannot, not redundant work. The mechanisms are what worked: an
  assert-it-applied check, a positive control on every run, folds chosen to look like
  data, fixtures with distinct values per row, and a deferred-instruction backstop
  that fails the build for the instruction nobody has written yet.

### A mutation result is meaningless four different ways, and only one is the edit

`.claude/rules/go.md` says to assert a mutation actually applied. That covers one
of four failure modes:

1. **The edit did not apply.** A replacement string that does not match the file is
   a no-op that scores as SURVIVED (a five-values-on-one-line enum defeats a
   one-per-line pattern).
2. **The system did not observe it.** The file diffed, but a version-keyed cache (a
   goose migration runner reusing one Postgres container, a package installer) never
   re-applied it: the file changed and the system under test did not.
3. **The suite did not run.** The harness never exported `UZI_TEST_DATABASE_URL`, so
   every `*LiveDB` test skipped, `go test` exited 0, and that scored as survival:
   the positive-control failure, occurring inside the tool built to run the controls.
4. **The build failed.** A mutation that changes sqlc's inferred nullability scores
   RED purely because a build failure also exits non-zero.

**The asymmetry is the point:** a *reddening* mutation proves itself, a *surviving*
one proves nothing until all four are ruled out. Require a `--- PASS`/`--- FAIL`
line for the named test before believing any result.

### A source-text control is satisfied by disabled code

A guard asserting a string is **present** in a file's raw text passes when the code
it names is commented out, moved below a section marker, or otherwise
present-but-inert: a `toContain` over `RunView` source stays green with the JSX
wrapped in `{/* … */}`; a `strings.Contains(migration, backfill)` coupling stays
green with the statement commented out or moved below `-- +goose Down`. Stripping
comments closes one member, not the class: `{false && <… />}` is disabled code that
is not a comment at all. The honest ceiling of any source-text presence guard is
"the text is present", never "it runs"; name the residual as known.

**The inverse is correct and must not be "fixed".** An *absence* assertion over
comment-stripped source is right to ignore commented-out code, because it genuinely
is not a second implementation. Presence and absence assertions have opposite
relationships to comments; grouping all three as one class sends someone to "fix"
the one already correct.

## Standing rules — each exists because something went wrong once

Live-DB mechanics (positive control, `-p 1`, compile-the-mutation) live in
`.claude/rules/go.md`; these are the general ones.

- **Make your own processes attributable** by prefixing a long-running probe's echo
  with your role name (`echo "=== [reviewer] … ==="`): `pgrep` output is the only
  unshared view of your process, every other channel (shell snapshot, cwd, log path)
  is shared and manufactures a confident *wrong* match. Pairs with CLAUDE.md
  "Destructive operations" #3 (attribute by log path, leave what you cannot).
- **Stage and commit by explicit path** — never `git add -A` / `git add .` /
  `commit -a`, and use `git commit -- <path>` because a bare `git commit` takes the
  whole index including another agent's interval staging. This has migrated to
  `.claude/agents/coder.md`, which reaches teammates. Recovery from a swept commit:
  `git reset --soft HEAD~1` then `git commit -- <path>`. One writer at a time and
  stage-by-path are one rule; both remove the failure mode rather than relying on
  noticing.
- **A delivered task description carries neither its currency nor its completion** —
  a `TaskUpdate` wakes the idle agent, which reads the text as a live assignment, so
  check the task's STATUS before acting. Put a SHA or milestone in the description for
  currency; only a status check catches already-executed. Do task-list bookkeeping
  BEFORE the dispatch.
- **An execution oracle is not a coverage oracle:** Postgres `log_statement='all'`
  shows a query RAN, never that anything WATCHED (blind between "pinned" and
  "executed but unasserted"; a caller swallowing the error hides even a failure). It
  lies three ways in different directions, so guard each: a `docker logs X 2>&1 > f`
  redirect loses stderr and under-counts to zero (verify the CAPTURE holds a
  statement you know ran); a partial index's predicate is textually identical to its
  query, so anchor on `-- name: <QueryName> :`, never the WHERE clause, or the DDL
  over-counts; and a failing statement echoes on a `STATEMENT:` line, so exclude
  those. Settle two disagreeing tallies by asking the PROPERTY, not the total.
- **`go list ./...` can return silence instead of an error, inconsistently in one
  session** — for package counts use `go test ./...` output, where `ok` ran tests and
  `no test files` merely exists, and a zero-failures claim gets the first denominator
  only.
- **A lost working directory produces a clean green for code it never ran** —
  absolute `cd` on *every* command, verify the tree in the *same* command that
  produces the measurement, and require every result to name the test you looked for.
  A run that cannot name your test is not your run, however green.
- **The verification tooling is where this team fails, not the reading**, and each
  broken instrument prints output indistinguishable from success. Remedies by
  mechanism: a mutation by LINE NUMBER landing on a comment → address by content and
  assert the changed-line count; a `head`-truncated census → count with `rg -c` /
  `--stat` and reconcile against the rows shown; a broken pipeline that mutated
  nothing → a content hash plus a re-grep, since `git diff --numstat` is itself blind
  to an unstaged new file; a presence check → assert identity/behaviour. Ask what each
  step would print if it were broken.
- **A measurement expires relative to the SHA it was TAKEN AT**, not to whatever
  later landmark is convenient: a diff cited as evidence it still holds must START at
  that SHA, not at a merge, release, or "current main".
- **A mutation can go red for the WRONG REASON and no gate sees it** — record a fold
  by the assertion MESSAGE, not RED/GREEN, because a fold reddening at a `Fatalf`
  about the fixture certifies nothing. Ask of every diagnostic whether its string
  could be printed by another condition. (A repro that self-cleans cannot reproduce.)
- **Bound every enumeration where you write it**, not after a validator finds it.
- **Assert the mutation actually applied**, not just that the test ran: an edit whose
  pattern misses gofmt's spacing matches nothing and the "verified" result is
  unmutated code.
- **A mutation can apply textually and be semantically INERT** — the edit lands, the
  file differs, the build passes, the behaviour is unchanged. A mutation reddening
  nothing has two explanations (weak test, inert edit), told apart only by reading
  what the mutated expression now evaluates to.
- **A projection pin is isolated only if it reddens under a fold to a value the
  fixture ALREADY contains** — blanking or a novel constant proves nothing; the
  discriminating fold looks like DATA. The fixture comes first: read-back and
  pairwise-different assertions are both inert while every row carries the same value.
- **Restore by COPY-ASIDE, never `git checkout`** — a git restore silently does
  nothing for an untracked or new file (once left an `OR true` authz bypass alive
  past a cleanup step).
- **Scope live-DB assertions to the fixture, never the whole table** — the LiveDB
  packages share one database and fixtures accumulate.
- **Read a file back after writing it through a shell heredoc** — that path corrupts
  silently.
- **No amends after a SHA is dispatched for review.** Fixes land as follow-up commits.
- **State an invariant where it is ENFORCED, not derived from a decision made
  elsewhere.** Tell: if removing an unrelated predicate elsewhere would make this code
  unsafe, the predicate belongs here.
- **A printed instruction is an untested claim** — run the command, do exactly what
  its output told the user, and assert the outcome (nothing else typechecks it).
- **A comment justifying a choice on ONE axis crowds out what else that choice
  decides**, and is nastier than a wrong comment because it is complete-looking: ask
  what OTHER property the operator or type decides, not just whether the stated reason
  is sound.
- **Apply the screen PER CLAIM, not per comment block** — a verified sentence next to
  an unverified one reads as one argument and the guard drops; the credibility is
  borrowed from the neighbour.
- **Screen every test with two questions:** what production change would make this
  fail (if "nothing, only the test file or stdlib", it is decoration), and would this
  line EXECUTE in the failing case (an assertion behind an earlier `waitFor`/`Fatalf`
  is documentation). Apply it hardest to tests whose NAMES make strong claims.
- **Do not run a live-DB suite while another agent runs one, but do NOT record a
  reason** — two confident explanations have already been wrong; keep the sequencing,
  "we do not know" is the honest inheritance.
- **"Did I run something that would fail if this were false?"** — ask before writing a
  claim down. Every claim mutation-tested has held; every claim reasoned to has needed
  correcting.
