# ADR-836: Upstream release-check — a scheduled, api-only egress path that derives "update available" offline

**Status**: Accepted (PRD #836, M1–M6 landed)
**Date**: 2026-08-30
**Deciders**: Vlad + agent team (architect, coders, review waves — scope/feasibility + milestones/testability screened the PRD before first commit)
**PRD**: [prds/done/836-update-available-signal.md](../prds/done/836-update-available-signal.md) (GitHub issue [vtmocanu/uzi#836](https://github.com/vtmocanu/uzi/issues/836)) — the PRD carries the milestones, the baked-in facts, and the full Decision Log (D1–D8); this ADR carries the durable design shape and the two rationale points a future reader most needs and will not re-derive from the diff: why this egress path bypasses the SSRF allowlists, and why the semver compare is guarded.

## Decision (summary)

A deployed instance now answers "is there a newer uzi release than the one I'm running?" without any client ever touching GitHub. The **api** — the only component that makes this release-check request (its own egress; the agent worker's outbound reach is the separate tiered egress of ADR-0285) — polls `GET https://api.github.com/repos/vtmocanu/uzi/releases/latest` on a schedule (default 6h), persists the remote facts to `app_settings`, and derives `update_available` / `far_behind` / `security` at **read time** with zero egress. `web` and the CLI render only from server booleans; neither hits GitHub (no CORS; nginx proxies only `/api/*`).

This mirrors the agent-source update-check's **poll → persist → derive** core (`api/internal/agentsource/update.go`), but deliberately takes only that core: it schedules via a dedicated interval **Runner** (not a `poller.Engine` detector, not a `schedsvc` job) and seeds create-only from env (like `seed.SlackSettings`), because agent-source's own scheduling and admin-only-no-seed halves are the wrong precedent here. New code lives in `api/internal/releasecheck/` (`client.go` fetch, `check.go` poll/persist, `derive.go` read-time booleans, `runner.go` scheduler). The whole feature is gated by two admin-runtime toggles, default on.

## Context

A uzi instance already knows and serves its **own** version (`GET /api/version` → `apitypes.BuildInfoDTO`, `api/internal/apitypes/buildinfo.go`; rendered by `web/src/components/BuildInfoPopover.tsx`), but nothing told the operator the instance had fallen **behind** upstream. So self-hosted instances silently aged out of security and feature fixes; the operator learned they were behind only by hand-checking GitHub. No upstream-release check existed anywhere in the product.

Two adjacent mechanisms existed and neither targeted upstream releases: CLI-vs-server skew (`api/internal/uzicli/versioncheck.go`, client-side) and the agent-source update check (`api/internal/agentsource/update.go`, which polls a configured template git source). The second is the structural template for this feature's core, not its schedule or seeding.

The api is the only correct home: it holds the decrypted secrets and is the only component that reaches the open web for this check (the agent worker's outbound reach is governed separately by ADR-0285's egress tiers), and `web`/CLI cannot reach GitHub directly. That single fact drives most of what follows.

## The decisions

### D1 — A new outbound-egress path, api-only, poll→persist→derive

The api fetches `releases/latest` (fields `tag_name`, `name`, `body`, `published_at`, `html_url`), persists them to `app_settings` via the settings KV, and derives the booleans on read. The read-time derivation (`releasecheck.UpdateAvailable` / `FarBehind` / `Security` in `derive.go`) is pure and touches nothing but computes-from-persisted-facts; it never derives at write time and never mutates anything but the settings KV. Every render surface (pip, popover, admin card, banner, CLI) reads the server boolean — the version math lives server-side in exactly one place. Rejected: a client-side compare in the SPA — it would put the semver trap (D3) in every browser and re-open the fail-open.

### D2 — Schedule via a dedicated interval Runner, seed create-only from env; NOT a poller/schedsvc job

Scheduling mirrors `agentsource.NewRunner(...).Start(ctx)` (`api/internal/agentsource/reconcile.go`) — a panic-recovered goroutine that sleeps `KeyReleaseCheckInterval` per tick and calls `CheckForUpdate`, wired next to the agent-source runner in `api/cmd/server/main.go` (`releasecheck.NewReconciler` / `NewRunner`). It is deliberately **not** a `poller.Engine` detector (those are post-forge-sync hooks) and **not** a `schedsvc` job (user-facing scheduled runs) — this is instance-global infrastructure polling, not per-repo reconciliation and not a run.

Seeding, in contrast, follows `seed.SlackSettings` (`api/internal/seed/slack.go`), not agent-source (which is admin-only and never env-seeded). `seed.ReleaseCheckSettings` (`api/internal/seed/release_check.go`) writes only **absent** keys at boot, so helm/compose sets the initial default via env (`UZI_RELEASE_CHECK_*`) while an admin's later runtime "off" survives every reboot. Two precedents, split on purpose — the reason this is worth recording is that "reuse agent-source" is the obvious-but-partly-wrong instinct.

### D3 — The semver fail-open trap, and its guard

The server serves the version **bare** (`0.14.0`, because the Dockerfile stamps `-X main.version=${UZI_VERSION#v}`); the GitHub `tag_name` is **`v`-prefixed** (`v0.14.0`). `golang.org/x/mod/semver` requires a leading `v` and **treats every invalid version as equal** — `Compare` returns `0`, `IsValid` is false. So a naive `Compare(served, tag)` fails **silently open**: it reports "up to date" for a pair that is genuinely behind. The guard (`releasecheck.semverNewer`, `derive.go`, mirroring `agentsource.semverNewer`) re-prefixes **both** operands with `v` and `IsValid`-guards **both** before comparing; an unparseable version is "unknown", never "behind". The discriminating unit fixture is a genuinely-behind pair (e.g. `0.11.0` vs `0.11.7`) — an all-current fixture is a **false control**, because `Compare("v0.11.7","v0.11.7")=0` is the correct answer even from the broken compare. This trap is also catalogued in root `CLAUDE.md` and `.claude/rules/go.md`.

### D4 — Two runtime toggles, default on, master gate fails CLOSED

- `release_check_enabled` (`KeyReleaseCheckEnabled`) — the master / air-gap gate. Off → the api never calls github.com. Without it an offline install would log poll errors hourly with no way to silence them.
- `release_check_banner_enabled` (`KeyReleaseCheckBannerEnabled`) — governs only the intrusive escalation banner; the pip and admin card do not depend on it.

Both default `true`, are admin-editable at runtime (no redeploy), and are env/helm-seeded create-only (D2) — the judge-style admin-gate shape, not the deploy-time `workers.enabled` shape. The load-bearing invariant: the master gate is read **inside** `CheckForUpdate` (`check.go`), and an **errored** settings read fails **closed** — it returns status `disabled` with no HTTP call and nothing persisted. An air-gapped instance whose settings read transiently errors must never leak egress on the strength of an unread toggle; "unknown enable state" degrades to "off", not "on".

### D5 — Security detection is a CHANGELOG-discipline heuristic, and its caveat is explicit

`security = true` when the persisted release `body` contains a `### Security` heading (`releasecheck.Security`, tolerant of trailing text like `### Security fixes`). This needs no severity field and no extra API call because uzi controls the release body: `.github/workflows/release.yml` generates each GitHub Release `body` from the matching `CHANGELOG.md` section **verbatim** (`scripts/changelog-section.sh body "$VERSION"`), and the CHANGELOG uses Keep-a-Changelog `### Security` subsections. **Caveat (the ADR's explicit residual):** a security fix shipped **without** a `### Security` heading reads as routine. This is accepted — the signal is a nudge, not a guarantee, and it depends on release-note discipline. Recording it here is the whole point: a future reader debugging "why did a security release not flag" should find the answer is release-note discipline, not a code bug.

### D6 — Why this egress bypasses the SSRF allowlists (the load-bearing point)

`FORGE_ALLOWED_BASE_URLS` and `AGENT_SOURCE_ALLOWED_BASE_URLS` (`config.AgentSourceBaseURLAllowed`, `api/internal/config/config.go`) exist to guard **user-supplied** base URLs — a user can point a forge/agent-source connection at an attacker-chosen host, so those inputs must be allowlisted against SSRF. This check hits a **compile-time-constant** URL: `defaultBaseURL + releasePath` = `https://api.github.com/repos/vtmocanu/uzi/releases/latest` (`api/internal/releasecheck/client.go`, no user input in the path). The user-URL SSRF threat therefore does not apply, and there is nothing to allowlist — `api.github.com` would not match the default `https://github.com` forge entry anyway. It carries **no user PAT** on the unauthenticated path (an optional instance-global `UZI_RELEASE_CHECK_TOKEN` only raises the rate ceiling, and is scrubbed from errors via `scrubToken`). It uses a **dedicated guarded HTTP client** (`newHTTPClient` in `client.go`: hard `Timeout` of 15s, `CheckRedirect` refuses all redirects so a 3xx cannot replay a request cross-origin, bounded body), **not** the per-user forge driver `newGitHub` (`api/internal/forge/github.go`) — that client is built per-user with a PAT, the wrong trust context for an instance-global unauthenticated check. `timeoutClient()` (`api/internal/forge/forge.go`) is the minimal in-repo shape the guarded client follows.

### D7 — DTO exposure: three optional fields public, body + snooze admin-only

`apitypes.BuildInfoDTO` gains three optional, omitted-when-unknown top-level fields — `latest` (object `{version, name, published_at, notes_url, security}`), `update_available *bool`, `far_behind *bool`. They are **`*bool`, not bare `bool`**: a bare `bool` with `omitempty` also omits `false`, collapsing "checked & up to date" into "never checked"; the pointer keeps nil / false / true as three distinct states — the same "unknown beats wrong" rule the DTO's existing `*int` fields use. The public surface is gated by `TestVersionEndpointCarriesNothingPrivate` (`api/internal/handler/version_test.go`): exactly three new top-level allowlist entries with reasons. Note the test walks only **top-level** struct tags and does **not** recurse into the `latest` object, so `latest`'s inner fields are public-by-construction and unaudited by that test — an implementer must not assume coverage it lacks. The release `body` (raw markdown notes) and the per-tag snooze state are **admin-only** — they are never serialized onto the unauthenticated `/api/version`, and are reached only through the admin-only handlers (`POST /api/admin/release-check`, `.../snooze`, mounted in the `RequireAdmin` group in `handler.go`, mirroring `handler.PostAgentSourceUpdateCheck` in `api/internal/handler/agent_source.go`). `handler.Version` now reads the read-through `settings.Cache` (no per-request DB hit); the token key is never serialized into the DTO.

### D8 — Deployment consequence: allow `api.github.com`, and this is NOT the worker egress tier

The api's runtime egress must reach `api.github.com`. A k8s NetworkPolicy or egress proxy that already allows `github.com` for forge traffic must **also** allow `api.github.com` (a distinct host). This is a deployment concern, not code — noted in the chart docs (`deploy/chart/values.yaml` wires `UZI_RELEASE_CHECK_*`); the `disabled` / `error` status degrades gracefully if egress is blocked, which is exactly what the master toggle and the error status are for. Crucially this does **not** involve the worker egress tier of [ADR-285](0285-worker-egress-tier-trust-model.md) — that governs the agent **worker** container's outbound reach, a different component with a different trust model. This egress is the api's own, from a host that already holds every secret.

## Consequences

- **The api has a new, permanent outbound dependency on `api.github.com`**, active by default. It is bounded (one poll per 6h, guarded client, fail-closed master gate) and disable-able at runtime, but any future egress-policy or NetworkPolicy change on the api must keep `api.github.com` reachable or accept a permanent `error`/`disabled` status. This is separate from and must not be conflated with the worker egress tiers (ADR-285).
- **The version math is server-side in one place** (`api/internal/releasecheck/derive.go`). Every surface — the sidebar pip, the popover row, the admin Updates card (`web/src/pages/AdminSettings.tsx`), the escalation banner, and the CLI `uzi version` line — renders from the server booleans exposed on `BuildInfo` (`web/src/lib/api.ts`); none does a client-side compare. A future surface that re-derives in the browser re-opens D3's fail-open.
- **`/api/version` is now settings-dependent** (reads `h.settings`) where it was previously pure build-stamps. It stays unauthenticated and unrated; the read-through `settings.Cache` keeps it DB-free per request, and `TestVersionEndpointCarriesNothingPrivate` remains the gate forcing any future top-level field to be a deliberate, reasoned addition — with the recorded blind spot that it does not recurse into `latest`.
- **The security signal is only as good as CHANGELOG discipline** (D5): a security release without a `### Security` heading reads as routine. Accepted as a nudge, documented here so it is diagnosed as discipline, not a bug.
- **`far_behind` is a v1 heuristic** (`FarBehind`: majorGap ≥ 1 OR minorGap ≥ threshold OR published ≥ 30 days old), server-computed for the same reason the pip is. An exact "N releases behind" via a releases-LIST call is a future refinement, not v1 — and would add a second egress call, so it is a deliberate non-goal here.
