# ADR-2396: Proactive worker memory guard

**Status**: Accepted (guard core, Codex adapter, owner-only memory holds and the Claude adapter, D8; memory-authority claim gate added by the 2026-10-21 amendment, issue #3142; the broader dispatch-only-to-capable-workers gate remains deferred; working-set metric and optional PSI added by the 2026-10-24 amendment, issue #3384; cooperative memory source settlement added by the 2026-10-30 amendment, issue #3638)
**Date**: 2026-10-15
**Issue**: [vtmocanu/uzi#2396](https://github.com/vtmocanu/uzi/issues/2396)

## Context

Concurrent run, chat and checker work shares a worker cgroup. An actual OOM can kill the worker before preservation finishes. The guard offers bounded proactive mitigation through existing worker-owned process handles and recovery custody. It creates no new process authority, concurrency policy or OOM-prevention guarantee. No PRD exists for this unit; this ADR records the approved contract.

## Decision

### D1: Explicit opt-in and measured sizing

The guard is off by default. Enabling it requires six explicit positive numeric settings: reserve bytes, sample interval, hysteresis bytes, rearm dwell, response budget and maximum interventions. [Configuration](../docs/configuration.md#worker-memory-guard) records names, ceilings and deployment wiring. The reserve sizing input remains literally `max(1Gi, 10-15% of memory.max)`. It is not a default or production recommendation. Small fixture measurements do not establish hosted reserve settings; production sizing remains uncalibrated.

### D2: Total cgroup pressure, bounded observation and quiet rearm (superseded in part by the 2026-10-24 amendment below)

[The reader](../agent/src/worker-memory-reader.ts) supplies cgroup-v2 `memory.current`, finite `memory.max`, `memory.stat` and memory PSI. [The policy](../agent/src/worker-memory-guard.ts) uses total current usage without subtracting file memory. For limit L, high threshold H = L - reserve and quiet threshold Q = H - hysteresis must satisfy `0 < Q < H < L`. Unavailable, stale, replayed or incompatible samples inhibit intervention and cannot repair quiet dwell.

Usage at or above H can trigger intervention. The early path requires fresh consecutive evidence: increasing full-PSI total, growth in anon/shmem/slab_unreclaimable/unevictable, and total-usage growth projected over the response budget to reach H. These signals do not attribute cgroup usage to a command. Rearm requires confirmed drain, a resolved outcome and fresh consecutive samples below Q for the configured dwell; a single low sample cannot clear uncertainty. One worker-wide monitor serializes intervention while configured concurrency remains unchanged.

### D3: Worker-owned enrollment and exact target identity

[The Codex adapter](../agent/src/codex/memory-command.ts) enrolls broker-minted model shell callbacks through their already registered supervisor handles. It binds the supervisor and original primary PID/start ticks, run, worker registration nonce, claim generation, memory episode, flight/lifecycle context and tool/attempt/command identity. Enrollment requires complete supervisor evidence. Transient stale initial observations can start retries within `min(1000 ms, enrollment deadline / 4)`, with each read bounded by half the enrollment deadline and the full wait bounded by that deadline. Other unavailable evidence, or persistent stale evidence after that window, skips enrollment while ordinary execution and registered-root cleanup continue. Revoked admission, cancellation and complete-evidence identity mismatches remain refusals. [Selection](../agent/src/worker-memory-commands.ts) rejects stale, incomplete, overlapping or protected process evidence; approximate tree RSS ranks eligible commands, descending, with deterministic supervisor PID/start-time and entry-identity ties. RSS is a ranking estimate, not cgroup attribution or proof of freed memory.

Fresh exact-tree evidence and current phase/registration authority are rechecked before cancellation. Cancellation uses the selected registered handle; selection does not authorize a PID-pattern fallback or a different target. Provider and credential processes, worker/internal probes, boundary/checkpoint/capture operations and checker authority are excluded. The Claude adapter is recorded in D8. The API's checker lifecycle fences do not establish a delivered checker adapter.

### D4: Durable episode allowance and exact reservation replay

[API admission](../api/internal/workersvc/memory.go) locks the worker, applicable parent and run before reservation. [Persistence](../api/internal/store/queries/memory.sql) freezes the episode policy and charges admitted interventions; policy maximum and spent allowance survive ordinary redispatch and new claims within the episode. A worker-generated intervention UUID binds exactly to owner, run, worker, registration nonce, claim generation, episode and policy. Exact replay does not charge again; a conflicting identity or policy is refused. Denials are ledger entries too. Historical replay can report the original result without authorizing a new signal.

The monitor marks cancellation as `unknown` before entering the cancellation seam; confirmed disposal of an invoked cancellation can establish `confirmed_drained`. Attempts stopped before that seam can report `no_signal`. The first persisted outcome is immutable. An uncertain cancellation or no-signal outcome does not refund a reservation. Outcome ACKs are non-authorizing and do not settle source custody. Transport retry is bounded and is not exactly-once delivery.

### D5: Captured settlement survives authority retirement

[Client registration](../agent/src/client.ts) captures memory authority from a valid register response advertising `worker_memory_pressure_v1`. Heartbeat feature growth does not create an incarnation. Feature shrink revokes authority before further reservation or signalling. Registration rotation, lifecycle retirement and shutdown invalidate cancellation authority.

Retirement does not transfer or erase the original flight's obligations. [Monitor finish](../agent/src/worker-memory-guard.ts) retains captured feedback and preservation intent before resolving the original tool result, even after authority retires. [Runner reconciliation](../agent/src/runner.ts) owns the bounded capture/park attempt and retained source. A bounded sink wait does not prove an abort-ignoring producer stopped; an unconfirmed capture or park ACK does not establish release or latest-work durability.

### D6: Bounded retry and owner-held recovery

Confirmed drain, resolved outcome and fresh quiet dwell permit subsequent command admission within the remaining episode allowance. Exhaustion, uncertain drainage or unconfirmed outcome reporting invokes preservation and attempts `recovery_wait` / `worker_memory_pressure`, with no automatic retry timestamp. An accepted hold requires owner Resume or terminal Cancel. Resume queues a fresh memory episode under existing run-budget, custody, claim and parent/checker lifecycle fences; it does not erase unknown drain evidence. Credential/account changes, approval, follow-up, pause and budget extension do not release the hold. An extension can supply budget for a later Resume.

Command admission feedback (#3436) distinguishes retirement, exhaustion, phase holds and pressure holds. Only pressure waits inside a model shell call, bounded by its original deadline, run cancellation and one configured rearm dwell plus sample/response margin. Waiting holds no guard lock and changes no admission predicate, latch or allowance. Before a delayed launch, both adapters revalidate the original captured flight, phase revision, cancellation and command authority. A phase change invalidates the pending call even if running resumes before it wakes. Phase-held, retired and exhausted calls do not wait; the configured dwell is a recovery condition, never an ETA.

Failed or uncertain capture retains local source, possibly its only copy, without an archive or latest-work guarantee. Available historical archives remain exportable independently of attention and do not authorize custody release. Migration [00342](../api/internal/store/migrations/00342_worker_memory_interventions.sql) retains discarded/released precedence, then classifies an OPEN hold at `recovery_wait` for either `worker_requeue_exhausted` or `worker_memory_pressure` as `needs_action` after failed latest capture, otherwise `source_only`, before available unguarded archives or capture progress. Other decisions remain unchanged. This approved extension amends [ADR-2445](2445-custody-admission-accounting.md) and [ADR-1742's 2026-10-08 amendment](1742-finalize-resume-allowance.md#amendment-2026-10-08--2445-exhaustion-attention).

The later #3495 amendment in [ADR-1197](1197-transient-recovery-park.md) adds
`retained_recovery_exhausted` to that conservative custody protection for its
whole wait, including timed parks. This changes neither memory holds' owner-only
Resume policy nor the proof required to release custody after a park ends.
The #3527 amendment there also protects `retained_recovery_adoption_failed`
throughout its owner-held wait, before archive readiness or capture progress.

### D7: Rollout, disable and command deadlines

Supported API-first rollout: deploy the API advertising `worker_memory_pressure_v1`, then enable workers. [Worker startup](../agent/src/worker.ts) refuses an enabled guard against an older API or invalid register incarnation with `UnsupportedMemoryAPI`. Supported worker-first rollout: deploy with the guard disabled until the API is ready, then enable through fresh registration/restart. A heartbeat advertisement alone cannot upgrade a disabled or revoked registration into memory authority.

Operational disable turns off the worker flag and restarts/rolls workers, retaining persisted episodes, holds and source custody. Migration 00342 Down is destructive: it marks memory-held runs failed with `worker_lost`, clears the cause, drops intervention history and episode columns, and restores the exhaustion-only classifier. It is not an operational disable path and supplies no source-release proof.

[Codex command execution](../agent/src/codex/codex-executor.ts) retains the ordinary finite 60-minute bound, or fixed 120-minute bound for broker-authorized root-lead `long_running: true`. Memory feedback does not extend a deadline, disable abort/output-cap handling or grant ordinary cleanup authority. Ordinary disposal and periodic adopted-child reaping stream identity-validated direct children under the existing deadlines, independently of memory-observation limits. Diagnostic PID lists retain at most 256 entries and mark omitted details with `evidenceTruncated: true`; only ECHILD plus a fresh complete empty enumeration confirms drainage. If pressure feedback wins first, foreground execution still waits for ordinary exit/abort/cap/deadline and owns registered-root cleanup. After the required disposal, output-drain and prepared-outcome joins, matching pressure feedback returns `worker_memory_pressure`, including for `long_running: true` when the effective deadline becomes ready during those joins; it is not relabelled `command_deadline`. Without matching pressure feedback, abort takes precedence over a simultaneous deadline, and deadline errors report the effective wall bound. Owner cancellation, pause-now, turn abort and run wall retain their run-lifecycle priority; pressure is no exemption.

Legacy snapshots remain a separate best-effort reporting lane: sorted, sanitized rows, a bound of 200 unique descendants, skipped unreadable or vanished rows, and an empty comm when unavailable. Snapshot rows grant no intervention or cleanup authority. The strict memory observer keeps its independent identity, consistency, thread, byte and deadline checks. As before the guard, snapshot collection reads thread child files synchronously without aggregate thread or byte caps; a thread-heavy reporting walk can delay the next control operation. Ordinary cleanup does not use that walk.

Disposal preserves the actual primary terminal wait status and emits its existing `child_exit` evidence exactly once, including when the drain consumes that status before ordinary readiness. Adopted-child statuses cannot stand in for the primary. Reporting a primary exit grants no drainage authority: unconfirmed disposal, identity validation, deadlines, fresh-empty enumeration and ECHILD requirements remain independent. Calibration cleanup binds a distinct abort signal to each owned broker callback while retaining the shared registry and context; aborting one tree cannot stop its sibling. Selected pressure settlement still joins genuine primary exit and matching pressure feedback before measurement acceptance.

Provider exits received while the launcher's exact owned disposal request remains unanswered are provisional terminal evidence. They do not reject that pending disposal or grant cleanup authority. Only the existing matched drained response, ECHILD proof, zero supervisor exit, closed streams and original deadline can confirm cleanup. If disposal remains unconfirmed after the provider exit, the provider is failed and its tree retained. Unsolicited, duplicate, malformed or out-of-window provider exits remain failures.

When memory preservation yields to a current owner `now` or `milestone` pause, the existing pause handler may run only after the original operation, feedback, closing and sink receipts truly settle within the original memory deadline. Accepted parking, cancellation, shutdown, claim fencing, registration changes, credential switching or known ownership loss prevent that handoff. An ownership refusal observed by the original operation stays latched; a later pause cannot revive it. Source and session custody stay latched; unconfirmed original work authorizes no competing park. The existing bounded batcher close remains owned. Disk and wall modes retain their existing retained-stop behavior and need separate race proof.

### D8: Claude adapter

Issue #2471. A guard-bound flight is one where the memory runtime exists and `bindWorkerMemory` in [the runner](../agent/src/runner.ts) bound it. That method no longer requires a Codex claim; it returns early without a memory runtime, and its refusal message is harness-neutral: "Worker memory enrollment requires the full worker claim and registration". Chat, job, judge, isolated, review, summary and cross-check runners are unchanged.

On a guard-bound Claude `RunRunner` flight, [the harness options](../agent/src/claude-harness.ts) map the SDK `toolAliases` entry `Bash` to `mcp__uzi_cmd__bash` and add native `Bash` and `Monitor` to `disallowedTools`. The worker-owned in-process MCP server `uzi_cmd` ([server](../agent/src/claude-command/server.ts), `alwaysLoad`) exposes the tool `bash`. Its server timeout is 3660000 ms, the 3600000 ms command maximum plus 60000 ms of transport headroom only; it is not a command deadline. [Grant shaping](../agent/src/claude-command/grants.ts) replaces explicit plain `Bash` grants with the MCP tool. A role whose shell grants are all scoped `Bash(...)` is unavailable on that run: it is listed in prompts and denied by the Agent guard. Inherit-all roles stay inherit-all. With the guard disabled, options, prompts and roster are unchanged.

[The command lane](../agent/src/claude-command/lane.ts) attributes a call by the SDK `toolUseId` matched against a PreToolUse hook record, and refuses visibly when none matches. `run_in_background` is refused visibly. The shared `screenBashCommand` screens in the PreToolUse hook (`ClaudeCommandLane.hook`, registered in [the SDK executor](../agent/src/sdk-executor.ts) for both the `Bash` and `mcp__uzi_cmd__bash` matchers), which also records the `toolUseId`, and the handler screens again independently. Admission refusal uses the `worker_memory_pressure` code. At most 8 commands per run may be live; the 9th is refused visibly. Every call starts at the repository root. The foreground deadline defaults to 120000 ms with a 3600000 ms maximum; at the deadline the command and every descendant are stopped and drained. There is no background mode, no `long_running` tier and no automatic extension. Inline output is capped at 30000 characters (a head and tail preview, [bounded-output](../agent/src/claude-command/bounded-output.ts)) with redaction. A best-effort spill file `.uzi/scratch/uzi-cmd/<commandId>.log` is written by the runner-uid [wrapper](../agent/src/claude-command/wrapper.ts), capped at 64 MiB and truncated beyond it; it is bounded, not a promise of full output, and the worker never opens it. Native `TaskStop` is unchanged.

`launchRunnerCommandRoot` in [the launcher](../agent/src/codex/launcher.ts) runs the existing immutable supervisor at the runner uid (`setpriv` to `RUNNER_UID` under the uid split, the worker's own uid in single-uid mode), with stdin closed and an explicit environment: the CLI environment minus provider credential variables and minus the worker token, API URL and spawn mark ([env](../agent/src/claude-command/env.ts)). This is parity with native `Bash` at the same uid, not isolation. The supervisor root is recorded per attempt (`SdkExecutor.recordedRootPids`), not worker-wide; own-run safety relies on lane joins at every turn end and at run end. Unconfirmed disposal fails closed: an exact SIGKILL of the unreaped supervisor child, the lane poisoned and the turn aborted.

[Enrollment](../agent/src/claude-command/enroll.ts) uses the source `claude-model-command`; [selection](../agent/src/worker-memory-commands.ts) accepts exactly `codex-model-command` and `claude-model-command`, with worker-minted metadata only. An uncertain read-only observation leaves the command running unenrolled but still deadline-bounded. A `stale` first observation (the tree still forming) is re-sampled for at most min(1 s, a quarter of the enrollment budget; about 1 s with the default 10 s budget). On pressure the selected call receives the structured `worker_memory_pressure` result as its tool error, plus the existing feed event.

Loss of memory authority mid-turn (invalidation) aborts the turn through a typed trip carrier that preserves `RetainedRecoveryStop`. Pause-now and credential-switch keep their first-wins precedence. Renewal, non-running reports and preservation retires do not abort. `stale_claim` behaves as for Codex: new commands are denied and live ones stay deadline-bounded. The mid-life triggers are the API ceasing to advertise `worker_memory_pressure_v1` (feature shrink, which includes the worker's `clearFeatures()` after a rejected heartbeat) and worker shutdown. The operator action is to restart the worker, because registration runs once at startup. Until then the API withholds guard-bound run-lane claims from that worker (see the 2026-10-21 amendment) so they stay `queued` rather than failing in `bindWorkerMemory` ("Worker memory enrollment requires the full worker claim and registration"). A claim already in flight when authority is lost can still fail closed in `bindWorkerMemory` under the existing authority rules, and is reported as a run failure. The aborted turn continues through the existing recovery/requeue policy.

[Startup preflight](../agent/src/claude-command/preflight.ts), called in [worker startup](../agent/src/worker.ts) only when the memory guard is enabled, launches the supervisor with an inert child and requires `started`, one observe and clean drained disposal within 15 s. On failure the worker logs "memory guard launcher preflight FAILED — refusing to register" with a reason (for a supervisor profile refusal, `profile:<field>`) and refuses to start. The blast radius is wider than Claude: guard-enabled Codex-only workers are refused too, and single-uid workers whose bounding set or NoNewPrivs fails the profile refuse to start while the guard is enabled (the e2e single-uid phase exercises ok, `profile:noNewPrivs` and `profile:capBnd`).

Option A limits, as delivered: foreground commands only; roles whose shell grants are all scoped `Bash(...)` are unavailable on a guard-bound run; `Monitor` is unavailable; there is no working-directory persistence between calls; and there is no `TaskStop` alias for guarded commands.

Deferred follow-up (owner decision D-2): the broader eligibility/capability gate, so the API dispatches Claude guard-bound work only to workers that can run it, is not built. What exists is the narrower memory-authority claim gate recorded in the 2026-10-21 amendment below. An enabled guard whose preflight fails still refuses worker startup rather than being filtered at dispatch.

Off-CI evidence, recorded in [the M0 record](../agent/test/fixtures/claude-command-m0-long-call.md) (SDK 0.3.292, CLI 2.1.292, server timeout 3660000 ms): in-process MCP calls of 11 minutes and 60.1 minutes completed and reached the model. This proves transport duration only; the handler was inert, so it says nothing about descendant drain. M4 calibration measured a Node 24 many-mismatch `deepStrictEqual` on 200000 pairs OOM-killed at both 1 GiB and 2 GiB private cgroups, while equivalent and bounded-diagnostic controls peaked near 120 MB. Run as a guarded command through the real Claude lane, launcher, reader and monitor (high-water mark at half the limit, 250 ms sampling; measurement parameters), the same workload was stopped before any OOM kill at both sizes: about 110-210 ms from the crossing sample to confirmed drain across two local runs, with the exact `worker_memory_pressure` tool result and confirmed cleanup. That local run synthesized absent PSI as zeros (recorded as `psiSynthesized`; the 2026-10-24 amendment replaced that field with `psiAvailable`); that CI runners provide real PSI is an expectation, to be confirmed by the `psiAvailable` field of the CI calibration report. That synthesized-PSI local run does not establish production behaviour on a PSI-less host. It is measurement only and sets no threshold (`e2e/worker-uid/calibration-claude-guard.mts`; the diagnostic spreads its result).

## Delivery boundary and limitations

Delivered scope is guard core, Codex enrollment, owner-only memory holds and the Claude adapter (D8). The memory-authority claim gate (2026-10-21 amendment, [#3142](https://github.com/vtmocanu/uzi/issues/3142)) is built; the broader D-2 eligibility/capability gate is not. M5 acceptance requires both bound 1 GiB/2 GiB CI reports plus the full validation gates; production thresholds remain unproven. Separately accounted Docker-in-Docker memory is outside the worker cgroup. Sudden allocation bursts, stalled sampling and node pressure can still kill or evict the worker. Capture itself costs memory and can fail; loss of retained worker storage can lose uncaptured work. Actual worker death continues through the existing recovery/requeue policy.

Measured, in local runs only: the M4 calibration figures in the off-CI evidence above (the OOM kill of the plain workload and the guarded-lane stop with its confirmed drain), taken with PSI synthesized where the host had none. Source inspection only, not runtime validation: the rest of this ADR, including the Claude adapter (D8) behavior and the CI-runner PSI expectation. Earlier validation records remain historical evidence and are not proof of execution for this documentation unit.

## Amendment 2026-10-21: memory-authority claim gate (issue #3142)

**Decision.** A worker that lost memory authority mid-life (see D5/D7 and the mid-life triggers above) no longer claims run-lane work that would fail in `bindWorkerMemory`. The gate is a claim-time check on memory authority only. It is not the broader D-2 gate: a worker that fails the launcher preflight still refuses to start, and nothing here routes work to workers by Claude capability.

- **Protocol.** New feature/capability `worker_memory_authority_claim_v1`. A guard-enabled worker registers it together with `worker_memory_pressure_v1`. When the API advertises it, the worker sends `memory_authority` (`held` or `lost`) on each ordinary run-lane claim, computed at send time ([client](../agent/src/client.ts), `claimRunLane`). Guard-disabled workers never register it and are unchanged.
- **Claim-request field, not heartbeat state.** The API judges the member per claim inside the claim transaction ([claim query](../api/internal/store/queries/runtime.sql), [judgment](../api/internal/workersvc/memory_authority_tracker.go) `memoryAuthorityLost`). A heartbeat-carried flag could lag the claim and, per D5/D7, a heartbeat advert never restores authority, so reading the request avoids a stale-state window and needs no API-side persistence for the gate itself.
- **Absent from a capable worker is lost.** Any present value other than `held` is lost. An absent member is lost when the worker's registered protocol capabilities contain both capabilities. This covers the strict-decode rollback, where `clearFeatures()` drops the negotiated feature set and the worker stops sending the member.
- **Exempt kinds.** When lost, the worker claims only kinds that never reach the memory runtime: judge, job, cross-check runs, review runs (`review_target_run_id`) and isolated-fetch runs (`egress_profile_id`). Every other run-lane kind (issue, `ci_fix`, `self_improve`, prompt, task, `mr_rework`, and any new kind) is withheld and stays `queued`. Chat and the cross-check lane are unaffected.
- **Rollout.** Old API with a new worker: no advert, so no member, and today's behaviour. New API with an old worker: the old image lacks the capability and is never gated; its claims still fail in `bindWorkerMemory` until restart. During a rolling API deploy an old replica rejects a claim body carrying the member (400; the worker retries on its next poll), and an old replica's heartbeat advert can briefly make a still-authorized worker omit the member and be withheld (it idles only).
- **Visibility and the restart window.** The gate has no restart window: it reads only the claim request and persisted capabilities. Visibility is an in-process API tracker that resets on API restart and is re-observed on the worker's next run-lane claim poll; an entry clears on a `held` claim, re-registration, worker delete, or 24 hours without a gated claim. Surfaces: `memory_authority_lost_at` on the worker DTO (API clock, first gated claim since the worker's last registration or API start), a CLI status suffix, a TUI row, a web badge and the owner health check `fleet.memory_authority`; see [Worker setup](../docs/worker-setup.md#lost-memory-authority).
- **Recovery.** Only a worker restart (fresh registration) restores authority. A heartbeat advert never restores it. There is no self-restart and no retry policy.
- **Known limits.** Next to the restart action:
  - Resume affinity: runs the lost worker aborts and requeues stay pinned to it while its heartbeat is fresh (up to `WORKER_AFFINITY_CEILING`, default 2h) and wait queued until the worker restarts or the ceiling lapses.
  - The ephemeral provisioner and the capacity/queued-reason counts still count the lost worker as able to take guard-bound runs. This is not time-bounded: it persists until that worker restarts. The gate prevents failing admissions; it does not promise automatic rerouting.
  - Spread delay: a busy healthy worker may defer a run to the idle lost worker for up to `WORKER_SPREAD_GRACE` (3x the poll interval).
  - In-flight race: a claim already in flight when loss happens still fails closed in `bindWorkerMemory`.
  - Triggers: an API downgrade below the version advertising `worker_memory_pressure_v1`, and restarting the API with `UZI_ACTIVE_SNAPSHOT_DISABLED` (heartbeat 400, stripped retry, `clearFeatures()`).

## Amendment 2026-10-24: working-set metric and optional PSI (issue #3384)

**Decision.** This supersedes two parts of D2: the pressure metric "total current usage without subtracting file memory" and the requirement that cgroup memory PSI be present. D2's text is left as written. The change alters enabled-guard behaviour on PSI-capable and PSI-less hosts alike; a disabled guard is unchanged.

- **Working set.** Pressure is `max(0, memory.current - inactive_file)`, an estimate of memory the cgroup cannot cheaply give back. It is compared with the hard threshold `H = limit - reserve` and drives the early projection and the below-`Q` quiet dwell. `memory.stat` must carry `inactive_file` in addition to the existing four fields, else the sample is unavailable. Feedback's `observed_total_bytes` stays the raw `memory.current`, so it can exceed the working set that triggered.
- **PSI is optional.** A `memory.pressure` read failing with exactly `ENOENT` or `ENOTSUP` yields an explicit PSI-absent marker (reason absent or unsupported), never zeros. Any other read error (`EACCES`, `EIO` and so on), or malformed or oversized PSI, keeps the whole sample unavailable and inhibits intervention.
- **Behaviour change.** (a) PSI-capable hosts: the hard check, the early projection and the quiet dwell now subtract `inactive_file`, so a large file cache makes the guard intervene later and rearm sooner. (b) PSI-less hosts: previously an enabled guard never intervened, because every sample was unavailable; it is now hard-only on valid core accounting.
- **Two paths.** The hard path (working set at or above `H`) fires with or without PSI. Early intervention additionally needs real PSI in two consecutive samples, an increasing full-PSI total, growth in `anon`, `shmem`, `slab_unreclaimable` or `unevictable`, and a working-set projection reaching `H` within the response budget. Without PSI only the hard path can fire; rearm still needs confirmed drain, a resolved outcome and a fresh low dwell. Reserve, hysteresis, sample, rearm and budget settings, defaults, default-off and disabled behaviour are unchanged.
- **Logs.** One `warn` ("worker memory guard: cgroup memory PSI unavailable; early intervention disabled, hard intervention continues on valid core accounting", field `reason`) on initial absence or loss; one `info` ("worker memory guard: cgroup memory PSI restored; early intervention resumes after consecutive PSI samples") on restoration. Repeats are silent and unavailable samples do not log.
- **Calibration.** The Node diagnostic guarded leg no longer synthesizes zero PSI; its report field `psiSynthesized` is replaced by `psiAvailable` (`e2e/worker-uid/calibration-claude-guard.mts`, which the diagnostic spreads into its report).
- **Known limits.** The working set is an estimate, not guaranteed non-reclaimable memory and not an OOM predictor. Inactive file pages can be dirty, under writeback or slow to reclaim, so the subtraction can underestimate pressure; dirty/writeback validation is deferred. Allocation bursts, stalled sampling, slow reclaim, node pressure and Docker-in-Docker memory remain outside. Production thresholds remain unmeasured.

## Amendment 2026-10-30: cooperative memory source settlement (issue #3638)

**Decision.** A memory park used to leave the parked flight's source use `active` under its worker incarnation, because the memory hold is never cleared and teardown required it to be absent before ending source use. A fresh incarnation that claimed the resumed run was then refused ("source is active under another worker incarnation") and the run failed. This amendment lets the producing flight end its own source use on positive evidence, so a fresh worker continues after Resume, and holds the run for its owner when that evidence is missing but the journal records the park; where an unsettled park's record could not be written, a different worker process fails the run as before and the same worker process stops the claim without failing until the requeue cap (see Residuals). It adds no server, status, cause or blocker: the owner hold reuses the existing `recovery_wait` / `worker_memory_pressure` park. Consuming the settlement as authority is the companion issue #3639, not built here.

### Positive-settlement contract, as built

- **Witness bound to the hold origin.** Both hold writers capture an `origin` (executor, executor incarnation, `flightId`, attempt id, claim generation) synchronously, before any async work. The park witness is written only after the server's accepted-park binding is checked and the observed-empty result is confirmed, and never on a throw. Teardown treats the hold as settled (`memoryHoldSettled`) only for that witness, the same executor and flight, a settled operation, no ownership rejection and `flight.parked`. The hold itself stays as the owner-policy and custody record. A failed or swallowed preservation leaves no witness, so the slot stays active as before.
- **Confirmed durable source end.** The authority's `endSourceUse` reports `endedSlots`, filled only when the slot transition to `ineligible` was saved (the existing tmp, fsync, rename, directory fsync, readback and head write). Kept, dropped, queued, timed-out, pending-footprint and failed-head-write outcomes add nothing.
- **Sink retirement.** `endFlightSourceUse` retires the flight's admission sink on entry. Every guarded admission (`bindSource`, each `#admit` hook operation except `discard`, non-destructive mint) refuses with `SourceUseHeldRefusal` from a retired sink before any effect, so an old callback cannot re-admit after teardown or after a successor's admission. An admission that already passed its last in-lock check when the sink was retired still completes; teardown therefore takes the authority lock once as a barrier (no drain) before it snapshots the flight's paths, which can add up to the source-use end wait to teardown. If the barrier times out, an admission still running is either before its lease (the end keeps its key and never queues or ends it) or after it (ended only if the end gets the lock after the admission finished, otherwise queued); either way a key without an end receipt blocks the settlement, so no settlement covers an incomplete set.
- **Same-process per-key ownership.** A key is recorded as owned by a sink (with its epoch) only after an admission in that sink succeeds. An admission from another sink, or from outside any sink, is refused while the owner has no confirmed end. Ownership is released only on a positively confirmed end: an `endedSlots` entry, a queued end the drain later applies as ended, a publication that moved the slot out of `active`, an operator discard's own end, or a re-check showing the slot is no longer `active` under the recorded incarnation and epoch. A refused admission or a dropped end records or leaves no owner, so nothing wedges. Kept, timed-out, unjoined and lost queued ends stay owned, and a later same-process flight is refused.
- **A refused flight never ends another flight's key.** `endFlightSourceUse` ends and publishes only keys its own sink owns, and a refused retained-source discard passes `skipFlightOwned` so it skips keys a live flight owns.

### The `memoryPark` v1 record

A strict-parsed field of the recovery journal (`RecoveryJournalEntry.memoryPark`, [git.ts](../agent/src/git.ts)), emitted immediately before `completionSourceFence`:

```
{ version: 1,
  binding: { runId, claimGeneration, workerId, registerNonce, memoryEpisode },
  ack: "confirmed" | "sent_unconfirmed" | "not_sent",
  origin: { flightId, attemptId|null, executorIncarnation|null, authorityIncarnation, sourceEpoch },
  settlement?: {                       // only when ack === "confirmed"
    version: 1, confirmed: boolean,
    sources: [{ path, authorityKey, attemptId|null, epoch, seq }],    // 1..16, sorted, unique
    evidence: { parkAck, interventionIds, processJoin: "executor"|"codex_disposal",
      commands: "confirmed"|"not_required", steering: "joined", auxiliaries: "joined"|"none",
      feedback: "drained", sinkReceipts: "joined", parkReap: "complete"|"not_applicable" } } }
```

- `ack` is `confirmed` iff a park witness exists, `sent_unconfirmed` iff a park body was actually sent (a latch set immediately before the report), else `not_sent`. `origin.sourceEpoch` is the epoch of the parked flight's own slot for its clone path; the producer writes no record when it cannot be determined.
- `settlement` is written only when every source path the flight used has an `endedSlots` entry and nothing was published, dropped or kept. An incomplete set, or more than 16 paths, writes no settlement (it logs) and is never truncated. `interventionIds` holds the triggering intervention for a pressure hold (captured synchronously from the pressure result when the hold is written) and is empty for an exhausted-allowance hold.
- **Metadata only.** It is not a completion certificate, a publication fence or a custody release.
- **Two-phase durability under one lock.** `GitCache.recordMemoryPark` runs each phase's write, config fsync, directory fsync and readback under one hold of the bare lock (the lock `installCompletionSourceFence` takes). Phase 1 writes `settlement.confirmed: false`. Only after it fully succeeds does phase 2 rewrite with `confirmed: true`. A phase-1 failure never qualifies; a phase-2 failure makes a best-effort compare-and-swap revert to `confirmed: false` and reports `unconfirmed`. A strictly greater `claimGeneration` replaces a record; within one generation only an identical replay or an upgrade (`not_sent`, `sent_unconfirmed`, `confirmed`, then adding a settlement) is allowed, and a settled record is never replaced by an unsettled one.
- **Reader-side confirmation.** `GitCache.readConfirmedMemoryPark` holds the same bare lock across read, config fsync, directory fsync and readback, and returns the record only when every step succeeds and both reads are canonically equal to the expected record. The recovering worker uses it, with the read-only `verifyEndedSlots` check of the authority, only on a continuation whose record carries a settlement (not on the re-park path), to log `predecessor cooperative settlement verified` or `unverified`. Neither authorizes anything.
- **Not independent of the journal.** The reader's expected record is the journal itself. A phase-2 failure whose revert also fails (or a Linux fsync error that loses dirty pages) can leave a readable `confirmed: true` that the reader re-confirms. An authoritative consumer (#3639) must bind `expected` to an independent server reference and treat a phase-2 or fsync failure as disqualifying.

### Rollback and older-parser behaviour

A worker built before this change parses the journal with a strict allowlist and rejects the unknown `memoryPark` key, so it treats the whole journal as invalid. Attach, recover and discard then fail closed for that source until a supporting worker handles it. This is an accepted operational consequence: roll back only after memory-parked runs are resolved, or accept owner-held retention. It reaches further than the completion-fence precedent (ADR-1783's 2026-10-27 amendment), which only a completing journal triggers; a journal carrying `memoryPark` can belong to any memory-parked run. Nothing strips the field to make a rollback succeed.

### Rule for future journal fields

A new recovery-journal field must be versioned and strict-parsed (exact keys, bounded values); added to the parser allowlist, the rebuilt return, the fixed JSON order and the watcher backup validator (`backup-runs.sh`); never stripped for a rollback; written durably, with an explicit confirmation phase when a consumer relies on it; one field per producer purpose; and not backed by a second proof registry. The restart follow-up (#3644) builds on this rule.

### Owner-hold semantics (D4)

When a retained continuation meets a predecessor whose source use was never positively ended but whose journal proves a memory park of this run, the claimant re-parks for the owner instead of failing. `memoryReparkOwner` is read-only and runs after the custody latches, before the recovery-stage renewal and before any recovery charge. It authorizes only this re-park, never source use, capture or settlement. All four must hold:

1. `classifySourceAdmission` returns `foreign_active` or `held_unended`. It takes the authority lock without the pre-callback drain and reads the slot only through the read-only inspection, so it repairs nothing; any uncertainty (a slot ahead of its head, a lock timeout, an unreadable slot) classifies as `other`.
2. The active-key journal carries a `memoryPark` of this run from an earlier claim generation, and the episodes agree (E is the record's, C the claim's): `confirmed` needs C = E + 1; `sent_unconfirmed` needs C = E (the server never applied the park) or C = E + 1 (it applied it, every ACK was lost, and the owner Resumed); `not_sent` needs C = E.
3. The slot's owner incarnation and epoch equal the record's `origin.authorityIncarnation` and `origin.sourceEpoch`. This excludes a post-Resume successor that minted its own epoch and crashed, and any unrelated writer.
4. Worker memory is bound for the flight and `worker_memory_pressure_v1` is negotiated.

Otherwise the existing flow is unchanged, including the `preservation_failed` mapping. `parkMemoryContinuationRefused` then reports `recovery_wait` / `worker_memory_pressure` at the claim's own episode (only an owner Resume increments it), through the existing park body. Nothing is written before the ACK: no capture, admission, recovery-episode charge, model turn or publication, and it sets no `memory.hold`. At most two park report calls (each call may retry transient HTTP failures) and no terminal report are made per claim. An exact accepted binding (a 409 replay counts) marks the flight parked and stops the claim nonterminally. A credential switch is handed to the retained switch protocol. Every other outcome (a stale claim or checker-parent change, a wall-parked response, pause, cancel, claim fence, the deadline, a transport failure, a crash between report and ACK) stops nonterminally with custody retained and nothing marked `failed`; the teardown producer then records the attempt as `sent_unconfirmed`, or `confirmed` for an accepted one, preserving the slot owner and epoch.

**Until #3639, Resume of an unsettled continuation re-parks immediately**, using one episode per Resume. Cancel or an operator discard of the retained source is the exit until #3639 lands. A worker restart does not release it: the slot stays active under the old incarnation (the crashed-active boundary is unchanged), so the claim classifies as `foreign_active` and Resume keeps re-parking while the record exists, or fails as before without one.

### Ordering with the restart follow-up (#3644)

Today D4's owner-held re-park takes precedence over a later pin-based restore. This is an ordering rule, not a ban: #3644 may build on it, and its pin restore applies only where D4 is ineligible.

### Discovery and disposition

- **One discovery surface.** D4 reads `memoryPark` only from the active journal key, through `discoverRetainedRecovery`. The protected descriptor (`uzi-retained.<runId>.journal`) preserves the record byte-identically but nothing consumes it; continuation from a descriptor is a separate follow-up.
- **Stopped-marker rule.** A stopped marker (`uzi-stopped.<runId>.entry`) never carries `memoryPark`. Its absence, or the absence of a record anywhere, is never settlement, source-use, publication, Resume eligibility or custody-release authority.
- **Per-site disposition.** Every writer keeps the retirement and rollback behaviour it had; `writeRecovery` still never reads the prior journal.

| Site | Disposition |
|---|---|
| `recordMemoryPark` (phase 1, phase 2, single write, phase-2 revert) | writer of the field |
| `markRecoveryCapture`, `installCompletionSourceFence`, `recoveryClockCurrent`, `reserveRecoveryIteration`, `recordRecoveryCapture`, `blockRecoveryEpisode`, `prepareRecoverySuccessor` (intermediate write), `completeRecoveryEpisode`, `releaseAttemptInPlace` (spread branch) | carry (spread of the parsed journal) |
| `retireRunnerCloneImpl` retained rollback (raw restore, ledger-repair spread, interrupted rollback) | carry |
| `prepareRecoverySuccessor` adopt successor (fresh object) | fresh object; same-run predecessor replacement: the predecessor's record retires with its journal, reached only after predecessor admission succeeds |
| `retireRunnerCloneImpl` `anchored` (fresh object) | fresh object; same-run replacement of the completed successor's journal, terminal-run path only, so a memory park is never involved |
| `detachTerminalRetained` | preserve in the protected descriptor, not consumed |
| `releaseAttemptInPlace` clear branch, `healBoundStoppedJournal`, `retainStoppedAttempt`, `markStoppedCanonical`, `completionSourceAlreadyRetired`, `clearRetiredCompletionJournal`, `retireRunnerCloneImpl` journal clear and completion `finishMetadata` clear | active-key clear (not source disposal) |
| `discardRetainedRecoveryUnderLock`, `discardRetainedSource`, certified retirement with a matching `expectedFence` | retained-source disposal, unchanged |

`reclaimTerminalOrphan` branch by branch (behaviour unchanged): the refusal branches (classification failure, malformed identity, nonterminal owner, repo/branch/path mismatch, path-probe error, `terminalRetainedSnapshot` error, quiescence error or block) throw with journal, ledger and path untouched; `retained` is `detachTerminalRetained`; the attempt shape is `releaseAttemptInPlace(..., "reclaimed")` (fence refusal first, then carry or clear); the canonical shape is `retireRunnerClone(..., { discard: false })` (rollback carries, a successful move clears the active key); a retirement error is a refusal. `refuseFenceDrop` in `releaseAttemptInPlace` still runs first, and `memoryPark` never clears a journal or bypasses it. The restart follow-up (#3644) must keep the adopt-successor payload, `memoryPark` included, byte-identical.

### Material change from the approved plan

The canonical clone path `issue-N` is shared across runs of the same issue, so the same-process ownership refusal reaches a same-issue re-claim, not only a same-run one. When such a claim meets another flight's unconfirmed end in `phaseClone` or reseed (and in retained recovery without memory provenance), it stops nonterminal: `RetainedRecoveryStop`, custody retained, no `failed` report. It is bounded by the server requeue cap, which ends in a `worker_requeue_exhausted` owner hold or `failed` according to the exhaustion evidence. `keepGuardedInventoryOpen` on that path may pin re-dispatch to the worker until the cap.

### Residuals and not shipped

- Docker and other unregistered writers are unchanged (#3404, ADR-1783).
- A crash after the park ACK and before teardown writes no record, so today's terminal path remains. This is the crashed-active boundary of [ADR-1783](1783-run-quiescence-and-attempt-clone-paths.md#amendment-2026-10-27--3404-durable-completion-source-authority-executor-lifetime-seal-and-restart-retirement); the hard-kill companion owns it.
- The re-park of an unsettled park (a confirmed source end leaves the slot ineligible, so that run continues normally) needs a `memoryPark` record in the active journal. The record can be missing for an unknown authority incarnation or source epoch, a stopped or protected source, a write failure, or a timeout whose write did not land (a write already holding the bare lock may still land, and Resume then re-parks). On a different worker process (for example after a restart, slot foreign-active) the run then fails as `preservation_failed`, as before. On the same worker process (the earlier flight's source end unconfirmed) the claim stops without failing ("held by an earlier flight's unended source use") and retries until the requeue cap, then ends in `worker_requeue_exhausted` or `failed` per the existing exhaustion rule; this is new with #3638, not "as before".
- A successor without the memory guard or `worker_memory_pressure_v1` behaves as before. Descriptor-only sources are not continued.
- The `sent` latch is set before `reportState`, so it can over-claim `sent_unconfirmed` if the call throws before sending; that only widens eligibility of the owner-held re-park.
- A refused retained-source discard can still end an unowned active lease, and a quiescence-proven discard ends a key whose owner sink is live. This is accepted ("live owner").
- Receipt consumption and server delivery (#3639), generic terminal reconciliation (#2494, #3031) and the restart follow-up (#3644) are not built. No hosted or compose acceptance of a memory park followed by a pod roll is claimed; it remains a human step.
