# ADR-238: GitHub — the third forge driver

**Status**: Accepted (PRD #238, milestones M1–M9 landed; M10 go-live pending)
**Date**: 2026-08-08
**Deciders**: Vlad + agent team (architect, coders, review waves — architect, fact-checker, reviewer, auditor)
**PRD**: [prds/done/238-github-forge-support.md](../prds/done/238-github-forge-support.md) (GitLab issue [vtmocanu/uzi#238](https://github.com/vtmocanu/uzi/issues/238)) — the PRD carries the milestones, the full evidence base, and the decision log; this ADR carries the durable design shape and its rationale, for a reader rebuilding from specs who should not have to reread it.

## Decision (summary)

A `github` driver behind the existing `Forge` interface, at **full parity** with GitLab and Forgejo (board sync, runs, pull-request creation and watching, privilege guardrails, the GitHub Actions CI-fix loop), built on `github.com/google/go-github/v90`, classic-PAT auth, **github.com only**. The Go call sites did not change — `ForgeForConnection`/`ForgeForToken` already thread `forge.Type` through every one, and (unlike Forgejo's ADR-0065) the `Forge` interface method set itself did not change either, so no test fake needed touching. The driver landed cleanly on the seams ADR-0065 built and predicted a third driver would need: a driver file, its per-forge scope set, a `forgeNoun`/`pipelinestatus` vocabulary entry, and a `forge_types` advert.

**Everything ships dark.** Milestones M1–M9 are committed but `handler/forge.go` still advertises and accepts only `gitlab`/`forgejo` — the `github` connect-form option is unreachable until the go-live milestone (M10) flips the advert and validation. This ADR records the design as-built; it does not claim GitHub connections are live.

## Context

uzi's specs long read "GitLab first, others later." GitLab was joined by a second driver, Forgejo (ADR-0065), which proved the abstraction and closed the three layers that were not actually behind it (a second worker client, web URL-by-string-surgery, and merge-permission modelling). GitHub — the largest forge, and the one most prospective users already host on — was never blocked by a false doc the way Forgejo was; it simply had not been built. This PRD is the direct test of ADR-0065's own prediction that a third driver would be "a driver file, its per-forge scope set, a `forgeNoun`/`pipelinestatus` vocabulary entry, and a `forge_types` advert" and nothing more.

## The decisions

### Third driver, same shape, method set unchanged

`api/internal/forge/github.go` and its per-seam `github_*.go` files (auth, issues, labels, access, mr, graphql, pipelines) implement the full `Forge` interface behind `forge.New`'s existing switch; `forge.TypeGitHub` is a third `const`, alongside `TypeGitLab`/`TypeForgejo`. Unlike ADR-0065's Forgejo driver, this one added no new interface method — the closest thing to a structural change is one additive field (`BranchProtection.ProtectionUnverified bool`, below), which the five existing test fakes zero-value safely. The GitHub-specific per-forge arms landed in the same four seams ADR-0065 predicted: `privcheck.requiredScopesFor`, the `pipelinestatus`/`pipelineBadge` status fold, `forgeNoun`/`forgePlatform` (plus its Go and CLI twins), and `agent/src/forge.ts`'s `GitHubClient`. The third driver landing cleanly on those seams, with no interface break, is itself evidence the current shape scales — see "Still no registry" below.

### Classic PAT, github.com only

The bot authenticates with a GitHub **classic** personal access token (`Authorization: Bearer <token>`); the connection base URL is `https://github.com`, the driver targets `https://api.github.com`. `VerifyToken` **refuses a `github_pat_`-prefixed (fine-grained) token up front**, rather than saving it on a warning: a fine-grained token cannot be introspected for its scopes (no `X-OAuth-Scopes` header, and a documented buggy expiry header — go-github issue #3708), so accepting it would silently defeat the over-privilege guard for exactly the token type whose breadth uzi cannot see. This is a deliberately different disposition from GitLab's introspection-unsupported *warning* path, whose coarse shape is at least known. github.com only (no GHES) for v1 — the test harness still points its client at an `httptest` host via go-github's base-URL override, which is ordinary test plumbing, not GHES support.

### The `repo`-scope requirement and the `workflow`-scope boundary

`privcheck.requiredScopesFor(github)` is exactly `{repo}` — the single classic scope covering private-repo contents write, issues, pull requests, and Actions read. GitHub's classic scopes are coarse by design (there is no way to narrow `repo` the way Forgejo's three fine scopes do); this is an accepted, documented weakening of least-privilege relative to GitLab/Forgejo, not something uzi can improve without a future fine-grained-PAT follow-up.

**A `git push` touching any file under `.github/workflows/` requires the `workflow` scope**, which a `{repo}`-only token does not carry. Three options were on the table: permit `workflow` as an allowed extra, require it outright, or forbid it and document the consequence. **Resolved by the user: forbid-and-document.** The required set stays exactly `{repo}`; the driver refuses a `workflow`-scoped token at connect as over-privilege (the same set-equality check that already rejects `{repo, delete_repo}`), and an agent whose change touches `.github/workflows/*` fails at push time with GitHub's error surfaced verbatim, PAT-redacted. This is a deliberate **CI-integrity boundary**: the bot token that pushes agent branches structurally cannot also rewrite the CI that guards `main`. The cost is real and stated plainly, not hidden — a user who needs agents to edit workflow files cannot use GitHub with uzi today; that is out of scope here, not solved.

### Branch protection: the accepted limitation, and why it is the crux

This is the one place GitHub is genuinely harder than Forgejo, and the single most important thing for a future reviewer to pressure-test against a real repo.

On Forgejo, `GET /repos/{o}/{r}/branches/{branch}` returns `user_can_push`/`user_can_merge` computed for the calling bot by the same code path the pre-receive hook enforces — a direct, authoritative answer at write role. **GitHub has no such bot-scoped flag at write role.** `GET .../branches/{branch}/protection` (which would give the full detail) requires `Administration: read` — effectively admin — so a write-role bot gets 403, same wall ADR-0065 hit on Forgejo's admin-gated route. The only reader-gated signal is `GET .../rules/branches/{branch}` (rulesets, go-github `ListRulesForBranch`, `Metadata:read`), and it has two hard limits:

1. **Legacy branch protection is invisible at write role.** GitHub's classic branch-protection rules and the newer rulesets are independent systems; a classically-protected repo exposes nothing through the rulesets endpoint beyond the bare `protected` bool.
2. **Whether the rulesets endpoint reflects the calling bot's own bypass ability, as opposed to merely listing rules that exist, could not be verified** — the implementation environment carried no GitHub credentials to run the live probe (create a repo, add a ruleset, read as a write bot, observe). This is recorded honestly as an unexecuted spike, not asserted as confirmed.

**`DefaultBranchProtection` (`api/internal/forge/github_access.go`) is built fail-safe to both possible outcomes of that unresolved question.** It never reports a fabricated `WriteRoleCanPush`/`WriteRoleCanMerge = true` on a branch it knows is protected: an unprotected branch reports both `true` (the honest worst case — see `BranchProtection`'s own zero-value convention); a protected branch with a readable, enforced, covering ruleset reports both `false` (authoritative either way the spike would have resolved); and a protected branch with **no** readable ruleset — the legacy-protection case — reports both `false` **and** sets the new additive field `ProtectionUnverified = true`, so "undetermined" is never conflated with a verified "safe". The driver never calls the admin-gated `/protection` route at all, the same discipline ADR-0065 established for Forgejo's `branch_protections/`.

**`ProtectionUnverified` is additive and does not change the `Forge` interface's method set** — the five test fakes zero-value it to `false` (verified/safe default), so nothing else broke. `privcheck`'s shared `evaluateRepo` gained one warning branch: `Protected && ProtectionUnverified` appends a warning rather than a Violation, because the existing evaluator's error channels could only produce a Warning or an early-return that skipped the Protected check entirely — genuinely unable to express "report Protected:true truthfully AND flag the degradation" without this field.

**This is the accepted limitation this ADR exists to record.** On a legacy-branch-protected GitHub repo, uzi's *detection* of whether the write-role bot can push or merge to `main` is undetermined, and surfaces as a `ProtectionUnverified` warning, never a Violation and never a false "safe". **[PRD #66](../prds/done/66-guardrail-enforcement.md) (guardrail enforcement) must treat `ProtectionUnverified` as fail-closed** — its `Protected`-first predicate, as currently specified, reads `Protected:true, all-Can:false` as *allow*, which on this case is exactly wrong. **Until #66 is taught to fail-closed on `ProtectionUnverified`, the primary directive on a legacy-protected GitHub repo rests on guardrail layers 2–4** (the worker holds no push credential to anything but the agent's own branch, the SDK deny-hook, and the process-isolation layer), **not on #66's detection**. `docs/github-bot-setup.md` states this to the operator up front and recommends a ruleset over classic protection precisely because a ruleset gives uzi an authoritative answer.

*(**Corrected 2026-08-13**: PRD #66 landed and satisfies this requirement — it folds `ProtectionUnverified` into a `protection_unreadable` **BLOCK** finding (fail-closed), so a legacy-protected GitHub repo the bot might reach is now **refused** at enable/run/claim, and the admin per-repo override never waives `protection_unreadable`. The primary directive on such a repo no longer rests on layers 2–4 alone.)*

### Actions status fold

GitHub Actions reports status across two sequential fields (`status`, then `conclusion` once `status == completed`), which the driver collapses into uzi's single verbatim status string. `pipelinestatus.IsFailed` — the CI-fix loop's *trigger* — is deliberately **narrower** than "every terminal non-success": it adds `failure`, `timed_out`, `startup_failure`, but excludes `cancelled` (a human cancelled it) and `action_required` (a human must approve a gate — attention, not a code failure). Folding those into the fix trigger would launch an unwanted fix run on every cancelled or approval-pending build. `pipelineBadge`'s tone table is broader (adds `queued`/`in_progress`/`requested` as running, `action_required` as its own `attention` tone, `stale`/`neutral` as neutral) because the badge answers a different question ("is this red?") than the fix trigger does. The one genuine cross-forge string collision, GitHub's run-level `waiting` (blocked on a deployment gate, i.e. attention) versus Forgejo's `waiting` (in-flight, i.e. running), is resolved by keeping the shared map's `waiting → running`: the tone stays a nuance either way, and no run is mis-triggered by it.

### Still no registry

ADR-0065 deferred the plugin/registry question to "the third driver." This is the third driver, and the judgement is: **still a hand-written `switch` in `forge.New`.** Three `case` arms and three vocabulary-map entries remain legible at a glance; a registry (registration order, init-time coupling, a plugin interface) would add indirection for no behavioural gain and would make the "every forge is exactly these N seams" audit *harder* by hiding the arms rather than showing them. If anything, this driver landing without reopening any of ADR-0065's seams is evidence the current shape scales fine as-is.

### Interface-level transport invariants, inherited and extended

`agent/src/forge.ts` gained a `GitHubClient extends HttpForgeClient` beside `GitLabClient`/`ForgejoClient`. The one shared-base change: GitHub signals "PR already exists" with **422**, not the 409 GitLab/Forgejo use, so the base's duplicate-detection widened to a **driver-declared status set** (`{409}` for GitLab/Forgejo, `{409, 422}` for GitHub) rather than a blanket 409‖422 widen — a blanket widen would have made a GitLab/Forgejo 422 for an unrelated reason newly (and wrongly) route into find-existing. The three transport guards ADR-0065 established as interface-level invariants, not per-driver details, carry forward unchanged: refuse a non-https base URL before sending the PAT, `redirect:"error"` so a 3xx cannot replay the PAT cross-origin, and duplicate-status → fetch-existing with fall-through to the real error when nothing is found.

**GitHub adds one Go-side transport surface neither existing driver has: the Actions job-log redirect.** `Actions.GetWorkflowJobLogs` returns a redirect URL to a short-lived, unauthenticated blob host — a genuinely new hop, fetched by the driver itself rather than the SDK. The driver's fetch of that URL: attaches no `Authorization` header (the pre-signed URL needs none, and must not receive the bot's PAT), refuses to follow any further redirect (`CheckRedirect` → `http.ErrUseLastResponse`), and never logs the raw redirect URL (it carries its own short-lived token in the query string, which the PAT-only redactor cannot scrub). This closes an SSRF + PAT-leak surface a hostile forge could otherwise use to redirect uzi to an internal address or replay the token cross-origin.

## Consequences

- **`gitlab.go`/`forgejo.go` are no longer the only drivers.** A fourth forge would repeat this PRD's shape almost exactly: a driver file, its scope-set arm, a vocabulary entry, an advert change — evidence for, not against, staying with the hand-written switch.
- **The branch-protection guarantee is now honestly forge-dependent in its detectability, not just its default.** GitLab is safe by platform default; Forgejo is user-supplied but bot-scoped-detectable; GitHub is user-supplied **and**, on legacy protection, undetectable at write role. `docs/github-bot-setup.md` states this to the operator; #66 inherits an explicit, named obligation (fail-closed on `ProtectionUnverified`) rather than a silent gap.
- **Least-privilege on GitHub is coarser by platform, not by choice.** `{repo}` is the finest classic scope available; uzi cannot narrow it further without a fine-grained-PAT follow-up, which is out of scope here and recorded as a future option, not a plan.
- **CI-tamper resistance is a first-class, deliberate side effect of D7a**, not merely a limitation: the bot token that can push agent branches cannot also edit the workflows that gate `main`.
- **Everything in this ADR is dark until M10.** `handler/forge.go` does not yet advertise or accept `github`; no GitHub connection can be created through the product today. This ADR records the design that M10's flip will make live, not a live system.
