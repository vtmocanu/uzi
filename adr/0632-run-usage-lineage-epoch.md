# ADR-632: A defaulted `lineage_epoch` marker fixes the broken-resume undercount by SUMming independent legs while still MAX-collapsing within-lineage snapshots

**Status**: Accepted (implemented, issue #632)
**Date**: 2026-08-29
**Deciders**: lead (design + integration), coder (implementation), reviewer + auditor + tester (independent validation passes, findings addressed).
**Issue**: [vtmocanu/uzi#632](https://github.com/vtmocanu/uzi/issues/632) — supersedes #332, the design tracker. #332's "ADR (Option B)" is a pinned GitHub issue comment, **not** a committed file; there is deliberately no `adr/0332`. The PRD [`prds/done/632-run-usage-lineage-epoch.md`](../prds/done/632-run-usage-lineage-epoch.md) is the design of record; this ADR restates the load-bearing shipped contract so a future reader needs no external fetch.
**Numbering**: `0632` is an **issue** number, like `0195` and `0106`. `0035`, `0042`, `0065` and `0238` are PRD numbers. See ADR-106's numbering note. Per convention ADRs are `adr/NNNN-slug.md` numbered by the originating **tracking item**, not an ADR sequence.

## Decision (summary)

`run_usage` is the per-run token/cost ledger (PRD #40). Each delivered result frame's cumulative `modelUsage` is folded into a row keyed `(run_id, session_id, model)` and merged with `GREATEST`; the `run_usage_totals` view then rolls up MAX-per-`(run_id, model)`-across-session-rows → SUM-across-models. MAX-across-sessions is correct **only** while every session row belongs to one unbroken accumulator lineage. When a worker restart **fails to resume** (SDK transcript not resolvable on this worker → a fresh SDK session starts from 0 under a new `session_id`), the view's MAX silently masks the smaller leg — a run undercounts by up to a full leg (measured live 2026-08-23, run `0a0ea841`: ledger `$64.74` vs. `$321.66` summed across the two legs' result frames).

We adopt **Option B**: a defaulted per-leg `lineage_epoch` marker.

- **Schema (migration `00175_run_usage_lineage_epoch.sql`).** Two columns, both `integer NOT NULL DEFAULT 0`: `runs.lineage_epoch` (the per-run counter) and `run_usage.lineage_epoch` (the stamped snapshot). Existing rows default to 0.
- **Bump (query `BumpRunLineageEpoch`, `runtime.sql`; call site `appendMessages`, `service.go`).** The API increments `runs.lineage_epoch` **once per newly-inserted `resume_lineage_break` status event** (#334, emitted at `agent/src/runner.ts`). No new endpoint, no new worker signal — Option B reuses the existing #334 emission. `UPDATE runs SET lineage_epoch = lineage_epoch + 1`.
- **Stamp (`foldRunUsage`, `service.go`).** The fold stamps the run's current `LineageEpoch` onto each `UpsertRunUsage` (`LineageEpoch: run.LineageEpoch`).
- **Pin-to-first-insert (`UpsertRunUsage`, `runtime.sql`).** `lineage_epoch` is in the INSERT column list but **omitted from the `ON CONFLICT DO UPDATE SET`** clause. The conflict key stays `(run_id, session_id, model)` and every token/cost column still merges with `GREATEST` — both unchanged.
- **View (migration `00176_run_usage_totals_epoch.sql`).** A view cannot be `ALTER`ed, so this DROP + CREATE replaces 00063's rollup. The inner grouping is now `(run_id, model, lineage_epoch)` with `MAX`; the outer stays `SUM` per `run_id` across the per-`(model, epoch)` maxima. Output columns are byte-identical in name and type, so every dependent read query (`GetRunUsageTotal`, `ListRunsForUser`, `SelfUsage`, the admin usage queries, `judge.sql`'s LEFT JOIN) compiles unchanged.

Historical result: every existing row is epoch 0, so a single-lineage run has one epoch group per model, the inner grouping collapses to `(run_id, model)`, and the output is value-identical to 00063 — **zero historical restatement**. Historical broken-lineage runs keep their (undercounted) numbers, forward-only and honest, since the marker was never recorded for them.

## Why it works — the load-bearing precondition

`session_id` is the **row-splitter**; the epoch only prevents over-counting **within** a lineage. The fix works only because a dropped-resume fresh leg lands in a *separate* `run_usage` row from leg 1, and that separation comes from `session_id`, not from the epoch (the conflict key does not include `lineage_epoch`). If two legs ever shared a `session_id`, `GREATEST` would collapse them at the row level before the view ran, and the epoch stamp would be inert.

They get distinct `session_id`s via a structural chain (verified at HEAD; re-derive before relying on it): the break is emitted before a fresh `executor.run()`; `onSessionId` fires `reportState({session_id: B})` only `if (!state.reportedSessionId)`, and `state`/`reportedSessionId` are created once per `run()` and never reset, so a fresh `run()` reports the fresh id B; `SetRunRunning` writes `session_id = COALESCE(narg, session_id)`, which **overwrites** to B. So break ⟹ fresh `run()` ⟹ `onSessionId(B)` re-latch ⟹ COALESCE overwrite ⟹ leg 2 under a distinct `session_id` row. M5's live-DB merge test asserts the two legs actually persist under distinct `session_id`s (not merely distinct epochs), so a future change to the `reportedSessionId`-once latch or the COALESCE cannot silently break the fix with every epoch-only test still green.

**Why the epoch and not just "SUM across session rows".** Given the two legs are already distinct rows, a plain SUM would seem to suffice. It does not: PRD #40 Decision 3 verdict-b lets `session_id` evolve turn-to-turn *within* one unbroken lineage while carrying the cumulative forward, so two rows can be snapshots of ONE accumulator. A plain SUM across session rows would double-count those within-lineage snapshots — the exact multiply the current MAX exists to prevent. The epoch is what distinguishes "reset to 0" (new epoch → SUM across) from "carried forward" (same epoch → MAX within): `session_id` splits rows, the epoch groups them correctly.

## Idempotency and epoch visibility

- **Bump only for `inserted`, never `msgs`.** The insert loop tracks genuinely-new `(run_id, seq)` rows in `inserted` (rows > 0). The epoch bump scans `inserted`, so an at-least-once re-delivery of a break (seq-deduped, rows == 0 ⇒ absent from `inserted`) never double-bumps. This is the opposite of `foldRunUsage`, which deliberately runs over **all** `msgs` so the idempotent `GREATEST` merge re-converges on re-delivery.
- **The bump loop sits right after the insert loop**, ahead of both the high-water-mark update and the `insertErr`/`UpdateRunLastSeq` returns. The message inserts are not transactional (each commits on its own), so once a break's row is committed it is owed its bump; bumping at the earliest point where `inserted` is complete means a later `return` (an unstorable message co-batched after the break, or an `UpdateRunLastSeq` failure) cannot lose the bump to seq-dedup on the worker's retry. The `inserted` gate makes the bump **at-most-once** regardless of position: it never double-bumps a re-delivered break, and it is exactly-once *when the bump statement succeeds* — but a bump-statement failure after the break row has already committed is NOT recovered on retry (the committed break is seq-deduped out of `inserted`), see the irreducible lost-bump bullet below. One consequence of the position: a bump failure now returns before `UpdateRunLastSeq`, so `last_seq` is not advanced on that path. The `last_seq` half **is** self-healing — the retry recomputes `maxStored` and advances it then — but the bump itself is not; that residual is the lost-bump window, not a self-healed one.
- **Per-frame epoch within a batch.** `foldRunUsage` stamps each result frame with the epoch in force *when that frame was emitted*: the run's committed epoch at batch start (`run.LineageEpoch`, fetched fresh in `appendMessages` and never mutated) plus the number of `resume_lineage_break` events preceding that frame in **seq order** within the same batch. This matters when a batch interleaves legs — `[result A, break, result B]` — where A belongs to the old leg and B to the fresh one: a single batch-final epoch applied to every frame would stamp A with B's epoch, and because `UpsertRunUsage` pins `lineage_epoch` on first insert, a later re-fold could not repair it and the totals view would `MAX`-collapse the two legs. In the normal cross-batch case there are no breaks in the batch carrying the result frames, so every frame gets the committed epoch unchanged. Counting breaks from `msgs` (not `inserted`) is safe under at-least-once re-delivery: a seq-deduped replay's recomputed epoch is never written, precisely because the epoch is pinned.
- **The irreducible lost-bump window** is the `BumpRunLineageEpoch` statement itself failing — which no reordering can close without a shared transaction. `run_usage` is advisory telemetry, not billing, so the impact is advisory-only. The bump returns its error raw (500), never through `classifyStoreError`, because it writes only the run id and a server-computed +1 (no worker-controlled value), so a failure is a genuine server error to retry, not a poisoned batch.

## Alternatives considered and rejected

**A. Additive-delta ledger** (immutable per-frame delta events, SUM rollup). Rejected: it still needs *this same* lineage marker to know which frames belong to which leg, plus a fragile delta/reorder idempotency story (reordered or re-delivered deltas must not double-apply), plus a retroactive restatement of past totals it cannot cleanly decompose from the stored cumulative snapshots. Option B is the smaller change that reuses the existing `GREATEST` idempotency wholesale.

**B (rejected sub-option). "SUM across session rows, drop the epoch."** Double-counts within-lineage snapshots, because verdict-b lets `session_id` evolve within one lineage and carry the cumulative forward — two rows can be snapshots of one accumulator. The epoch is exactly what tells a reset-to-0 leg (SUM) apart from a carried-forward snapshot (MAX). See "Why it works" above.

## What this does not cover

**The web client-side fold (`web/src/lib/runUsage.ts`, ADR-195) is epoch-unaware and remains so — this is the honest, prominent limitation of #632.** That module reduces `modelUsage` per model against a running high-water max over the message stream, which carries **no `session_id` and no `lineage_epoch`**. For a broken-lineage run it therefore still MAX-masks leg 2, exactly as the old server view did. So #632 **introduces a NEW client/server divergence on broken-lineage runs**: the server total via `GetRunUsageTotal` now SUMs the legs, while the client-derived run-page strip still shows the masked MAX. This breaks ADR-195's "cannot diverge by mechanism" invariant **for that case** — which held before #632 only because both sides undercounted identically. Single-lineage runs (all epoch 0, the vast majority) are unaffected and still agree exactly.

This is a known limitation left to a maintainer follow-up. A feasible fix exists: the client already sees the `resume_lineage_break` event in the same stream and could reset its per-model high-water baseline there (so leg 2 accumulates from 0 into a summed total rather than being masked), plus a broken-lineage contract fixture and a comment correction in `runUsage.ts`. The cross-language contract tests (`api/internal/workersvc/run_usage_contract_test.go` and `web/src/lib/runUsageContract.test.ts`) pin client/server agreement for **single-lineage fixtures only**; they do not assert agreement on a broken-lineage run, and must not be read as covering it.

The PRD's own out-of-scope items, restated:

- **Validating the non-dropped-resume reseed assumption** (PRD #40 Decision 3 verdict-b, PROVISIONAL). Option B trusts that a *non-dropped* resume reseeds the CLI accumulator so those rows are one lineage (same epoch). Confirming this needs a live two-phase-across-requeue run with a real Anthropic session (open egress + a live cluster) — not something an offline sweep worker can perform. The dropped-resume path this ADR implements and tests is safe regardless; the reseed validation is a separate maintainer live-run follow-up.
- **Reducing the frequency of lineage breaks** is #628's job and is orthogonal — Option B makes the ledger correct *when* a break happens, whatever the rate.
- **Recovering a never-completed turn's cost** is permanently unrecoverable: cost exists only at result-frame boundaries in the CLI's process-global accumulator, with no mid-query cost signal. Not attempted — this captures whole legs, not sub-turn tails.
- **Marking #332's Option B "implemented"** is a forge write to another issue, outside an offline worker's branch diff — a maintainer follow-up alongside the reseed-validation live run.
