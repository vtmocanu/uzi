# ADR-65: Forgejo — the second forge driver

**Status**: Accepted (PRD #65 merged)
**Date**: 2026-07-17
**Deciders**: Vlad + agent team (architect, coders, three review waves — design + security audit + fact-check — over two revision rounds)
**PRD**: [prds/done/65-forgejo-support.md](../prds/done/65-forgejo-support.md) (GitLab issue [vtmocanu/uzi#65](https://github.com/vtmocanu/uzi/issues/65)) — the PRD carries the milestones, the full evidence base, and the decision log; this ADR carries the durable design shape and its rationale, for a reader rebuilding from specs who should not have to reread 900 lines.

## Decision (summary)

A `forgejo` driver behind the existing `Forge` interface, at **full parity** with GitLab (board sync, runs, MR/PR creation and watching, privilege guardrails, the CI-fix loop), gated to **Forgejo ≥ 16.0.0** and built on `code.gitea.io/sdk/gitea`. The Go call sites did not change — `ForgeForConnection` already threaded `forge.Type` through every one. The real work was the driver plus the **three layers the abstraction never actually reached**: the worker's own un-abstracted forge client, the web's URL-by-string-surgery, and merge-permission modelling. Merge-permission is now detected and **reported** on both forges; turning that into a run **refusal** is deliberately split to [PRD #66](../prds/done/66-guardrail-enforcement.md), because refusing is a GitLab-behaviour change with no Forgejo content.

The abstraction held where it claimed to (callers, schema, REST surface) and was honestly extended where it did not. Nothing in #65 refuses anything that ran before it; every milestone but the go-live lands dark.

## Context

uzi always claimed a forge-generic design with "GitLab first, Forgejo later" (`specs/human.md`). The `Forge` interface existed, the `forge_type` column existed, and `gitlab.go` was the only driver. Forgejo was deferred on a **recorded blocker that was false**: `specs/ai.md` claimed "Forgejo has no atomic add+remove label call, so single-column enforcement is best-effort there." Forgejo has `PUT /repos/{o}/{r}/issues/{index}/labels`, whose handler runs its diff inside a DB transaction — single-column enforcement is **atomic** on Forgejo, by a different mechanism than GitLab. A wrong doc argued against feasible work for months; correcting it (via spec-keeper) is why this PRD ran now, and it is the archetype of the methodological failure catalogued at the end of this ADR.

Three truths the specs did not record, all real work:

1. **The worker held a second, un-abstracted GitLab client.** `agent/src/gitlab.ts` hardcoded `/api/v4/...` and `PRIVATE-TOKEN`; the forge abstraction was Go-side only. The worker opens the MR itself and could not know which forge it was talking to.
2. **The web reconstructed forge URLs by string surgery** (`/-/merge_requests/N`) because the DB stored `mr_iid` but not the MR web URL the driver already received and discarded.
3. **uzi checked merge permission on neither forge.** `BranchProtection` modelled push only. On GitLab that is safe by platform default; on Forgejo it is not.

## The decisions

### Parity and vocabulary

- **D1 — Full parity or the forge is not supported.** A Forgejo user gets the same product: same board, same guardrails, same CI-fix loop, no "GitLab-only" asterisks. The interface audit found no method Forgejo cannot satisfy. Board-only was rejected — a half-driver is a support-burden trap that the neutral interface does not require.
- **D2 — `MergeRequest`/`IID`/`mr_iid` stay internal; only user copy is per-forge** (a Forgejo card says "Pull Request", a GitLab card "Merge Request"). Forgejo's PR `index` *is* GitLab's `iid` — a per-project sequential number — so the domain type is already structurally neutral; only its name was GitLab-flavoured, and a name is not a contract. The architect recommended against per-forge copy (a mixed-forge board mixes vocabulary) and was **overruled by the user**; the objection is recorded, not dropped. Consequence owned by the web: `forge_type` reaches the web per card/run, mapped at a **single site** (`web/src/lib/forgeNoun.ts`, one Go twin in `slacksvc/notifier.go`); shared/forge-less chrome names both ("merge/pull request") or restructures past the noun, never defaulting to one forge's word. Rejected: renaming to a neutral third term across Go + DB + API + UI — a live data migration and a REST-surface change for zero behavioural gain.

### The version floor and its gate

- **D4 — Forgejo ≥ 16.0.0, refuse below it, no degradation path.** The CI-**fix** loop needs `GET .../actions/jobs/{job_id}/logs`, which first ships in v16.0.0 (released 2026-07-16). `LatestPipeline` would work on 15.x; only `ListPipelineJobs`/`JobLogTail` do not. The architect recommended a 15.x floor with a `404 → ErrCIUnsupported` degraded mode; the **user overruled** to a hard floor, trading every pre-2026-07-16 instance for a guarantee (D1 becomes real, not per-instance) and no degradation branch to write, test, or explain. The gate lives in `VerifyToken` (so the user sees the version in the error, which `CreateConnection` surfaces verbatim), and is re-checked on the privilege sweep.
- **D4a — The gate is strict semver ≥ `v16.0.0` (`golang.org/x/mod/semver`): prerelease refused, build metadata ignored, unparseable refused.** `16.0.0-dev-N` is a **~4-month range, not a version** — the `v16.0.0-dev` tag (2026-03-26) lacks the gating route, while a later `16.0.0-dev-N` build has it, and both report `16.0.0-dev-N`; the class is not even orderable (semver compares the dev suffix lexically). So refusing a `-dev` build — including codeberg.org's live one — is **correct**, not a false negative. Grammar derived from Forgejo's Makefile and 293 tags (modern majors are only `vN.N.N` and `vN.0.0-dev`; no `-rc`), not from live samples. The gate is a **feature gate, never a security control** (`/api/v1/version` is public, unauthenticated, self-reported), so failing-closed on an unparseable version buys no security and costs none — it is purely a failure-mode choice, and one clear error at connect beats a bare 404 mid-run.

### The client library

- **D5 — `code.gitea.io/sdk/gitea`, not `codeberg.org/mvdkleijn/forgejo-sdk`.** forgejo-sdk was 13 months stale, had no issue timeline, and only Actions *secrets* (no runs/jobs/logs). gitea-sdk has both, including `GetRepoActionJobLogs`; Forgejo still ships the `+gitea-1.22.0` compatibility suffix precisely for this. **Narrowed at implementation:** the "gitea-sdk has an issue timeline" rationale held for existence, not usability — the SDK types a timeline entry's label as `[]*Label`, but Forgejo serializes the label-event label as a **single object**, so `ListIssueLabelEvents` **hand-parses** that one endpoint rather than using the SDK's typed timeline (`forgejo.go`; pinned by `TestForgejoListIssueLabelEventsMapping`, which also pins the undocumented `body=="1"` add / `body==""` remove convention so an upstream change fails loudly). Two more SDK warts handled: client-scoped `context` (construct a client per call over a shared `*http.Client`, `SetGiteaVersion("")` to skip the version round-trip) and a client-side basic-auth gate on `ListAccessTokens` (so `TokenInfo` is hand-rolled — the server route only needs `reqSelfOrAdmin`).

### Guardrails — the largest cluster, and the one the security audit reshaped

- **D6 — Every PRD #5 check maps to Forgejo or the connection is refused.** The original mapping was **unsafe**: three rows read `GET .../branch_protections/{name}`, whose route group is `reqAdmin()` — a bot at exactly `write` (which the role check *requires*) gets 403 on every one, which `privcheck` converts to a *warning*, silently degrading the protected-branch guardrail forever. The security audit caught it. The corrected mapping reads `GET /repos/{o}/{r}/branches/{branch}` (reader-gated, so a `write` bot can call it), which returns `protected` / `user_can_push` / `user_can_merge` **computed for the calling bot by the same code path the pre-receive hook enforces** — a *direct authoritative answer* to "can this bot push/merge to `main`", better than GitLab's inference from access-level lists.
- **D6a / D6a-1 — Detect that the bot can merge; enforce in #66.** On a default Forgejo a `write` bot can merge its own PR into protected `main` (`EnableMergeWhitelist` defaults false → merge falls back to write permission). GitLab's default forbids it — but `merge_access_levels` is configurable, and safe-by-default is not safe — so `BranchProtection` gains `WriteRoleCanMerge` + `BotCanMerge` on **both** drivers. #65 **reports** the finding as a per-repo **Violation** (the same tier as its push sibling — a bot that can merge to `main` breaks the primary directive exactly as one that can push does; committed first as a Warning, reconsidered and inverted); the run **refusal** is #66, split out because blocking a mergeable-`main` repo is a GitLab-behaviour change that should not ride, as a footnote, in a Forgejo PRD.
- **D6b — Per-forge required token-scope set, "exactly" kept.** Forgejo has no `api` scope. GitLab requires exactly `{api}`; Forgejo exactly `{write:repository, write:issue, read:user}` — verified sufficient *and* minimal (Actions live inside the repo scope; git push needs `write:repository`; introspection needs `read:user`). Two wire traps handled: Forgejo re-emits scopes in a canonical order (compare as an unordered **set**, never a string) and collapses a full `write:*` run to the literal `all` (reject that string, do not try to expand it).
- **D6c — Unprotected default branch: warn, don't block; document loudly.** Forgejo creates repos with zero protection, so PRD #5's warn-not-block policy meets a forge where unprotected `main` is the *default*. Kept warn-not-block (blocking is #66); the weight #65 carries is the doc — `docs/forgejo-bot-setup.md` **leads** with "protect `main` and enable the merge whitelist — uzi will not do it for you." Honest posture: on a default Forgejo, guardrail layer 1 is user-supplied; layers 2–4 (worker holds the PAT, deny-hook, `settingSources: []`) hold regardless.
- **D6e — DROPPED: `unprotected_file_patterns` has no write-role source.** The check was specced against a field that lives *only* on the admin-gated `BranchProtection` object — the exact endpoint D6 abandoned. Verified live on a released 16.0.0: `GET /branches/{branch}` does not carry the field and `user_can_push` does not reflect the per-file override, while both `branch_protections` reads 403 a `write` bot. So it is unimplementable at write role and becomes a **documented manual-audit gap**, like the team-whitelist gap D6 already documents. Escalating the bot to admin to read it is strictly worse (it grants `DELETE` on the rule too).
- **D7 — `ProjectRole` returns a `Role` enum, not a raw `int`.** Forgejo has no numeric access levels (`none|read|write|admin|owner`); mapping `write → 30` would be a driver lying to satisfy a GitLab-shaped contract. The enum is **not contained in `api/`** — the role is persisted as JSONB and typed `number` in the web, so the REST field changes `number → string` (M8's web side) and existing rows fail to unmarshal until the next sweep re-stamps them (accepted; the sweep interval is documented, and the silently-ignored unmarshal error is now logged). `member` needs a Forgejo-specific derivation from the permission payload, not a 404 (a bot removed from a *public* repo still gets 200 `permission:read`).

### Source-of-truth plumbing

- **D8 — Persist `runs.mr_web_url`; stop guessing forge URL grammar.** The driver already received the MR web URL and discarded it, which was the sole reason `web/src/lib/forgeUrls.ts` reconstructed `/-/merge_requests/N` by string surgery. The worker now persists it at MR creation; the web renders it directly, guarded by `isHttpsUrl` (twinned as `isHTTPSURL` in `notifier.go` for the Slack path). No backfill — old rows fall back to the GitLab-only reconstruction. Restores "the forge is the source of truth": uzi should not guess a URL the forge already told it.
- **D9 — A minimal TS forge seam in the worker, not a port of the Go interface.** `agent/src/gitlab.ts → agent/src/forge.ts` with a small `ForgeClient` (`GitLabClient` / `ForgejoClient`); only `createMr` is genuinely per-forge. `ClaimRepo` gains an additive, optional `forge_type` (absent → gitlab, so an old worker against a new api still works). Three transport guards are **interface requirements**, not per-implementation details: refuse a non-https base URL before sending the PAT, `redirect:"error"` so a 3xx cannot replay the PAT cross-origin, and 409-on-duplicate → fetch the existing MR (Forgejo's 409 also covers other conflicts, so the fetch-existing fallback tolerates finding no open PR). The SDK deny-hook and `git.ts` needed **no** change — both are URL-derived and forge-agnostic by construction; all four guardrail layers are untouched.

### Validation strategy

- **D10 — M9's live target is a pinned ephemeral `forgejo/forgejo:16.0.0` container, not an upgraded self-hosted instance.** The released image exists on both registries, boots in ~4s on sqlite, and reports `16.0.0+gitea-1.22.0` — a release, so it passes the D4a gate where codeberg.org's dev build does not. R3's lost-update probe and the D6/D6a-1/D6b/D7 branch-protection and scope facts were each executed against it — the first time any ran against a released 16.0.0. codeberg.org was rejected as a target on three independent grounds, any one sufficient: it is volunteer-run production infrastructure the `[live]` criteria would *write to* (decisive on its own), the gate refuses it, and it is a moving dev build.
- **D10a — CI-fix live coverage is fixtures-only; the real-runner check is deferred, not done.** The e2e lane (Variant A) proves `ListPipelineJobs`/`JobLogTail` + the loop against `forge-fake`'s canned `text/plain` logs; a real `forgejo-runner` emitting real logs is **unverified** — the user has no runner environment. Recorded as an open residual, **not claimed as done** — acceptable because the log route is verified on a release and `JobLogTail` does near-zero forge-specific parsing (SDK call + tail-truncate).

### Connect UX

- **D11 — Connect requires an explicit forge-type picker, not auto-detection.** The web connect form only ever consumed `allowed_base_urls`, never `forge_types`, so even after the go-live flip the UI sent no `forge_type` and every product-created connection would be GitLab — the headline `[live]` connect criterion was unreachable through the product. `CreateConnection` selects the driver *before* `VerifyToken` can reach the instance, so `forge_type` must be known up front, and `ForgeConfig` already advertised `forge_types` for exactly a picker. Auto-detection (probe `/api/v1` vs `/api/v4`) was rejected: it would put forge-discrimination logic *outside* the `forge` package in a driver-less handler pre-probe — the leak the abstraction exists to prevent — to solve a non-problem (the user knows their forge). The picker lands dark (hidden while `forge_types=[gitlab]`); the go-live flip advertises + accepts `forgejo` and neutralizes the connect lead-in copy, at the single user-visible moment.
- **D11a — Base-URL and forge-type are picked independently (accepted limitation).** `allowed_base_urls` is a flat list not associated with forge types, so a mismatched pair fails at `VerifyToken` (the safety net, not a silent miswrite). Associating URLs with forge types is a `ForgeConfig` contract change, out of scope here.

## The methodological story — recorded because it is the point

This PRD's durable value is not the driver; it is the discipline it was forced to learn. **A single live instance proves what that version does; a grep proves what a string matches; neither proves absence.** A dozen-plus claims, each believed by someone competent, fell over under "re-derive it at the moment you assert it" — several stamped "verified" by their own author:

- The **architect** called the CI job-log API a hard blocker from a complete swagger scan of a live **15.0.4** instance — the routes existed in **v16.0.0**, released the day before.
- The **PRD author** wrote "v15.0.4 has zero `actions/runs` routes" from a grep for a path string that cannot match Forgejo's nested route groups — v15.0.4 *does* serve `actions/runs`; the conclusion held, the evidence was false.
- The **security audit** found D6's original guardrail table read an admin-gated endpoint a `write` bot 403s on — the whole protected-branch check would have degraded to a warning forever (D6).
- The GitLab default-branch-protection default was quoted wrong ("No one can merge" — the manual-protection default) and stamped verified; the real default is "Fully protected" (D6a-1).
- codeberg.org's version was stale in the PRD within a day (`15.0.0-209` → `16.0.0-dev-626`); re-measuring it surfaced the **D4a semver trap** (a naive `≥16.0.0` refuses the very instance that has every route it requires).
- "gitea-sdk has an issue timeline" was true for existence, false for usability — the `[]*Label` vs single-object break forced the hand-parse (D5).
- The lost-update window (D3) was read from source and **never executed** — running it on the released container closed the architect's own recorded riskiest assumption.
- The CI-fix loop keyed its start gate, failed-job snapshot, and fix verdict on GitLab's `"failed"`; Forgejo Actions spells failure `"failure"`, so a Forgejo Fix-CI could never start — a Forgejo **e2e** caught all three, and `internal/pipelinestatus` (with `TestMirrorsWebPipelineBadge`) exists to fold both vocabularies so no consumer silently mis-reads the forge it was not written against.
- D6e was **unimplementable** as specced (no write-role source), caught before it shipped.
- D2's "forge_type to the web is a DTO field, not a query change" held for board cards and was **wrong for runs** (three new joins + a helper).
- The connect-UI gap (D11) was found investigating deferred copy — the product could not create a Forgejo connection at all until it was fixed.

The lesson is written into the code, not just here: freeze the assertion and prove it fails. `TestMirrorsWebPipelineBadge` pins the Go↔web status correspondence; `TestForgejoListIssueLabelEventsMapping` pins the undocumented label convention; the version gate is table-driven against every real version string including codeberg's live one. A future reader who trusts a comment over the source is repeating exactly the failure this ADR records.

## Consequences

- **`gitlab.go` is no longer the only driver.** Any future forge is a fourth thing: a driver file, its per-forge scope set (D6b), a `forgeNoun`/`pipelinestatus` vocabulary entry, and a `forge_types` advert. There is deliberately **no plugin/registry mechanism** — two drivers is not a pattern, and the third is the moment to reconsider, not now.
- **The `Forge` interface is the source of truth for forge knowledge**, and #65 proved the three places that were not behind it (worker, web, pipeline classification) and pulled them in. The one accepted cross-language duplicate is the noun/status twin (Go ↔ TS); the status half is test-pinned (`TestMirrorsWebPipelineBadge`), the noun half is guarded by review + adjacent comments (D2).
- **Merge-permission is modelled but not enforced** *(at the time of this ADR; **Corrected 2026-08-13** — [PRD #66](../prds/done/66-guardrail-enforcement.md) landed and now enforces it)*. #66 consumes `BotCanPush`/`BotCanMerge` through a shared `Protected`-first predicate — never a raw struct read, or the R12 inversion (unevaluated `false` read as "safe" on an unprotected branch) reopens.
- **`docs/forgejo-bot-setup.md` carries a hard operator obligation** GitLab's defaults hid: protect `main`, enable the merge whitelist. Until #66, that is guidance uzi reports but does not enforce *(**Corrected 2026-08-13**: #66 landed — uzi now refuses to enable/run/claim on a repo whose `main` the bot can reach, live and fail-closed)*.
- **The self-hosted validation instance upgrade is optional**, wanted for dogfooding but gating nothing (D10); the real-`forgejo-runner` CI-fix check is an open, honestly-recorded residual (D10a).
