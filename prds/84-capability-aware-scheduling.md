# PRD #84: Capability-aware run scheduling & plan-gate — match runs to workers that can run them

**GitLab Issue**: [#84](https://gitlab.example.com/vtmocanu/uzi/-/issues/84)
**Status**: Draft (created 2026-07-18)
**Priority**: Medium
**Depends on**: PRD #4 (run state machine + claim protocol — `queued → claimed → running → awaiting_approval → running`, and the `FOR UPDATE SKIP LOCKED` claim this PRD adds a predicate to); PRD #18 (worker templates + the declared/reported self-report this PRD promotes from observability to a scheduling input, and the devbox tool tiers whose "provisionable" set the gate must subtract); PRD #41 (plan-revision gate — the approval surface this PRD extends).
**Related**: PRD #83 (docker-capable worker) is this PRD's **first consumer** and depends on M1–M4 — docker is the first capability that cannot be runtime-provisioned, which is what forces this mechanism to exist. PRD #58 (hosted k8s workers) provides the "provision a docker worker" remediation the gate offers — *persistent* provisioning today; the *ephemeral* auto-provision path (Decision 9) needs #58's deferred spawn-on-demand + teardown. PRD #79 (open) tracks that ephemeral-worker cost/GC question. PRD #42 (concurrency) — the sweeper must not time out a run that is *waiting for an eligible worker* as if it were a stale claim.

## Problem

A run is claimed by whatever worker grabs it first (`FOR UPDATE SKIP LOCKED`, with an affinity grace for resumes). A worker's template is **observability-only** today — PRD #18 self-reports it and badges declared-vs-reported drift, but nothing routes on it. So if a run needs a toolchain or capability the claiming worker lacks, it fails **mid-run** with `command not found`, after burning a claim and part of a token budget, with a confusing failure the user cannot pre-empt.

This has been survivable for one specific reason: missing **CLI tools** are auto-provisioned per run (devbox tier-1/2, PRD #18), so "tool not found" is largely self-healing. That masks the absence of any real matching.

**PRD #83 breaks the mask.** Docker is the first capability that **cannot** be runtime-provisioned — it needs a sidecar/daemon, not a nix package (PRD #83 Decision 1). A docker-needing run that lands on a `base` worker is **dead on arrival**: nothing can install a daemon into it at run time. So the system must know, *before committing the run to a worker*, that it needs a docker-capable one — and must do something better than crash if none exists. (`jvm` has had the same latent gap since PRD #18; it is simply rarely hit. This PRD fixes the general case and retrofits `jvm`.)

How does the user — or the planner — know a run needs a docker worker, and what happens when the available worker can't satisfy it?

## Inspiration check

| Aspect | Kubernetes scheduler | CI runners (GitHub/GitLab) | uzi today | uzi (this PRD) |
|---|---|---|---|---|
| Match work to capable executor | `nodeSelector` / taints+tolerations / `runtimeClass` | `runs-on:` labels / runner tags | None — any worker claims any run; template is a badge | Capability set per worker + `required ⊆ caps` predicate on the claim |
| "No capable executor" | Pod stays `Pending`, surfaced with a reason | Job queues on a label with no runner; surfaced as pending | Silent — run is claimed and fails mid-flight | Pre-claim "no eligible worker" state + remediation, or blocked at the plan gate |
| Who declares the need | Author sets selectors/tolerations on the pod | Author sets `runs-on` | Nobody | Static per-repo hint **and** plan-time inference by the lead (both) |

The pattern is settled prior art: **capability-as-selector scheduling with a pending/surfaced state when nothing matches.** uzi already has the two hard parts — workers self-report (PRD #18) and runs already **stop for human approval** (`awaiting_approval`). This PRD wires those together rather than inventing a scheduler.

## Solution Overview

Three layers — **Declare → Match → Gate.**

1. **Declare (both sources — user decision 2026-07-18):**
   - **Static per-repo hint** (`required_capabilities: [docker, …]`) in repo settings, next to PRD #18's tool profile / tier-2 toggle; optionally an issue label (`uzi:needs-docker`). Known **before claim**, so the scheduler can route without waiting for a plan to run.
   - **Plan-time inference** by the lead: the planning step scans the clone and emits the run's **full requirement set** — non-provisionable `required_capabilities` (docker…), the provisionable **`required_tools`** toolchain (go, python, node…, inferred mainly from language manifests — `go.mod`, `package.json`, `pyproject.toml`, `Cargo.toml`, `pom.xml` — and build/test/CI scripts), plus an estimated **size class** (mem/CPU/disk) — alongside the agents it already proposes. This is a **pre-run readiness check** (Decision 11): make sure everything for a successful run is present or auto-provisionable *before* committing the run. The planner emits *requirements*, not a worker pick (Decision 8). **Authoritative and escalation-only** — it can add a requirement the hint missed, never remove a hinted one.
   - Effective requirement = hint ∪ plan-inferred.

2. **Match (capability-based claim):** every worker advertises a **capability set** derived from its reported template (via a server-side template→capabilities map) plus provisioned-tool tags. The claim query gains a predicate: a run's **non-provisionable** required capabilities must be a subset of the claiming worker's capabilities. A `base` worker will not claim a `docker` run. Affinity/resume grace is unchanged.

3. **Gate (stop only when genuinely unsatisfiable):** `unmet = required − (worker_caps ∪ provisionable)`; a missing CLI tool tier-1/2 can install is **not** unmet (provisioned, not gated). The gate also flags a **size** shortfall (the plan's estimate exceeds the worker's mem/CPU), not only missing capabilities. When `unmet` or a size shortfall is non-empty, the gate offers a **remediation spectrum** (Decision 9): switch to an eligible worker you have · provision a *persistent* one (today, #58) · auto-provision an *ephemeral* one for this run (deferred). It surfaces at two moments:
   - **Pre-claim** (static hint already makes it unsatisfiable, no eligible worker online): the run parks in a **"no eligible worker"** state — not a silent hang or a mid-run crash — with the remediation CTA, consuming no claim. You provision (or start) a worker; the run then claims it. *Planning never runs on the wrong worker* (Path 1, Decision 9).
   - **At the plan-approval gate** (need discovered by inference on a worker that can plan but not execute): approval is **blocked** with the reason + remediation; on remediation the run is **requeued and re-claimed** by a capable worker, which resumes from the approved plan — existing claim + durable-plan mechanics, no cross-worker session transfer (Path 2, Decision 9).

## Design Decisions

1. **Capability matching is *scheduling*, and is distinct from *provisioning*.** The load-bearing split: **provisionable** needs (nix CLI tools, PRD #18 tiers) are satisfied by installing them per-run and must never gate; **non-provisionable** needs (docker, and today `jvm` unless in the template, later gpu) can only be satisfied by landing on the right worker, so they are matched at claim time and gated when unmet. The requirement's *type* picks the path. Getting this split right is what makes docker usable without regressing #18's provisioning UX.

2. **Two declaration sources: the hint pre-routes, the plan escalates** (user, 2026-07-18: "both"). The static repo hint is known before a plan exists, so the scheduler can route a statically-hinted run to the right worker with zero plan latency; plan-time inference is authoritative and catches needs the hint missed. They compose as a union, and inference is **escalation-only** so a heuristic can never silently *drop* a requirement the user explicitly declared.

3. **Reuse the existing plan-approval gate; add exactly one new pre-claim state — do not invent a scheduler.** uzi already halts at `awaiting_approval`; capability satisfaction is surfaced there for the inference path. The only genuinely new state is a pre-claim **"no eligible worker"** for the case where the hint makes a run unsatisfiable *before* any plan runs — otherwise such a run would either hang in `queued` forever (no worker will ever claim it) or, worse, be claimed and crash. That state is surfaced with remediation, not a silent queue.

4. **Capabilities are a bounded, declared vocabulary — not free-form strings.** A small server-owned enum (`docker`, `jvm`, `gpu`, …), each mapped to (a) the templates that provide it and (b) optionally a provisionable-tool tag. Templates declare what they provide; the map is code-reviewed, so matching is deterministic and the UI/CLI can render a fixed set. No repo-supplied arbitrary capability names (they would be unmatchable and a spoofing surface).

5. **Never over-gate.** A requirement that tier-1/2 provisioning can satisfy must not block approval or claiming — that would regress the PRD #18 experience where "install my repo's tools" just works. The gate subtracts the provisionable set first; only the residue stops a run. (This is Decision 1 restated as a hard rule for the gate implementation and its tests.)

6. **The hint is a contract; inference is a heuristic.** The static hint is the user's explicit, always-honored declaration. Plan-time inference (scan for compose/Dockerfile/testcontainers/`docker` in scripts) has false negatives by nature; it may only **add** requirements. A repo the scan misses still has the hint as the reliable path, and a missed inference degrades to today's clear mid-run failure — never to a wrong *removal* of a requirement.

7. **Matching is best-effort scheduling + a clear failure, not a security boundary.** A worker self-reports its capabilities; the join token stays the sole trust anchor (PRD #18 Decision 5). A worker that falsely claims `docker` and lacks it simply fails the run — identical to today's drift, not an escalation. So this PRD adds no trust surface; it improves routing and UX. (Guardrails and the uid split remain the security layers.)

8. **The planner emits *requirements*, not a worker choice — and requirements include size, not just boolean capabilities.** The lead outputs `required_capabilities` + an estimated **size class** (mem/CPU/disk); it never picks, and never needs to know, your worker inventory. The server resolves those needs → *an eligible worker you have* or *a worker type + size to provision* (via the template→capabilities map + #58's S/M/L presets). This keeps the planner simple and inventory-agnostic, and lets the gate flag "too small for this plan," not only "missing docker." "Suggest a worker you don't have yet" is therefore the normal unmet case — resolved by the remediation spectrum (Decision 9), not a special path.

9. **Remediation is a spectrum, and unmet dispatch reuses existing claim machinery — no cross-worker session handoff.** When nothing you have satisfies a run, the gate offers, in ascending cost: **(a)** route/switch to an eligible worker you already have; **(b)** one-click provision a *persistent* hosted worker (works today on #58's static provisioning); **(c)** auto-provision an *ephemeral* worker for just this run (deferred — depends on #58's spawn-on-demand + teardown, its explicit non-goals, and #79's ephemeral-cost/GC question). Two dispatch paths, both built on mechanics uzi already has (any worker claims a queued run; the approved plan is durable in `run_messages`), **not** live worktree/PAT/SDK-session transfer:
   - **Path 1 — hint-first (provision before planning).** The static hint makes the need known pre-claim, so an unsatisfiable run parks in "no eligible worker"; you provision; the capable worker then claims, plans, and executes. Cleanest — planning never lands on the wrong worker.
   - **Path 2 — plan-time discovery.** A worker that can plan claims and plans; the plan escalates to a capability/size it lacks; the gate blocks; on remediation the run is **requeued and re-claimed** by a capable worker that **resumes from the approved plan** (re-cloning as it would anyway). Whether execution can resume from the plan text alone is the one thing to validate — see Risks.

10. **Considered and deferred: an always-on "control" worker + splitting one run across workers.** An always-on small worker for the light lane (plan/judge/chat) with heavy execution handed to a different worker mid-run was weighed and set aside: a *shared* control worker would hold many users' Anthropic tokens + forge PATs, breaking the per-user creds boundary the whole worker model protects; a *per-user* one just reintroduces the "keep a worker up" friction #58 reduces; and splitting a single run's plan and execute phases across workers needs live worktree/PAT/SDK-session transfer + claim reassignment — real new machinery for a laptop-first tool. #84's pre-claim state (Path 1) and requeue (Path 2) deliver the same user outcome without it. Note: `judge` and `chat` are *already* separate light run kinds (`RunKind`, `agent/src/protocol.ts:45`), so a small worker can naturally serve that lane today; only making *plan* its own claimable run would need the handoff above — a possible future PRD, not this one.

11. **The plan is a pre-run readiness check over the *whole toolchain*, not just non-provisionable capabilities.** The inference pass infers the run's full requirement set — the non-provisionable **capabilities** (docker…) *and* the **toolchain** (`required_tools`: go, python, node, rust, jvm… + specific CLIs), primarily from language manifests (`go.mod`, `package.json`, `pyproject.toml`/`requirements.txt`, `Cargo.toml`, `pom.xml`/`build.gradle`) and build/test/CI scripts — then **classifies each need before the run**:
    - **present** (base + template + already-provisioned) → ready;
    - **provisionable + allowlisted** (nix/devbox tier) → auto-provisioned, shown as "will install," never a nag (Decision 5);
    - **provisionable but not allowlisted** (admin policy forbids) → flagged/blocked: "repo needs `X`, not permitted — ask an admin";
    - **non-provisionable capability** (docker) → hard-gated (Decisions 1/3);
    - **unknown / unsatisfiable** → blocked.
    This is the user's north star — *"make sure we have everything for a successful run"* — surfaced at the plan gate: auto-resolve what we can, flag/gate only what we can't, so the common mid-run "command not found" is caught pre-run. It moves uzi's existing `JudgeSignal.missing_tools` scan from a post-hoc judge signal to a pre-run preflight. **Scope, honestly:** detect the *primary* toolchain from manifests (high-signal, low false-positive); do **not** try to enumerate every transitive CLI a test might shell out to — that long tail stays backstopped by the mid-run failure + the judge `missing_tools` post-scan. The preflight raises the floor; it does not promise a guaranteed-green run (see Risks).

## Technical Design

### 1. Capability vocabulary + worker advertisement
- A server-owned capability enum + a `template → capabilities` map (e.g. `base → {}`, `jvm → {jvm}`, `docker → {docker}`), plus provisioned-tool tags where relevant. Code-reviewed, tested.
- Register payload (extends PRD #18's `template` self-report): the worker advertises its capability set (derived from template + any baked/provisioned tools) **and its size/resource envelope** (mem/CPU/disk, from the #42/#58 preset it runs). Stored per worker; surfaced on the workers/admin pages next to the drift badge.
- **Reuse the existing tool-gap primitive:** the judge claim already carries `JudgeSignal.missing_tools` — a "command-not-found pre-scan" (`agent/src/protocol.ts:297`). The inference pass (§4) builds on that primitive rather than inventing a second tool-detection path.

### 2. Run requirement model + static hint
- `runs.required_capabilities` (non-provisionable) **and `runs.required_tools`** (provisionable toolchain) — array/JSONB or small join tables. Populated at enqueue from the repo hint (and issue label if present); updated by plan inference (§4), union-merged.
- Repo settings: `repo.required_capabilities` static hint, living beside the #18 tool profile + tier-2 toggle. (The tool profile already carries the provisionable toolchain per PRD #18; inference cross-checks it and flags gaps — §4.) Optional issue-label parsing (`uzi:needs-<cap>`).

### 3. Capability-aware claim
- Extend the claim query (`workersvc` / the `FOR UPDATE SKIP LOCKED` selection): a run is claimable by a worker only if `required_capabilities − provisionable ⊆ worker_capabilities`. `provisionable` is computed from the same allowlist/tier config #18 uses. Affinity/resume grace and all other claim semantics unchanged.
- The sweeper (PRD #42) must distinguish a run **waiting for an eligible worker** from a **stale claim** — the former is not a timeout/requeue candidate on the claim-heartbeat path.

### 4. Plan-time inference + the gate
- The lead's plan step (`agent/src` planning path) gains a bounded **readiness-inference** pass over the clone: it infers `required_capabilities` + `required_tools` (from language manifests + build/test/CI scripts) **+ an estimated size class**, cross-checks against present + provisionable, and **classifies each need** — present / will-provision / needs-admin / capability-gate / unsatisfiable (Decision 11) — emitting the set + classification in the plan payload/schema. This moves the existing `JudgeSignal.missing_tools` command-not-found scan *earlier*, from a post-hoc judge signal to a pre-run preflight (Decision 8 — requirements, not a worker pick).
- The plan-approval gate (PRD #41 surface) computes `unmet` (+ any size shortfall) and, when non-empty, **blocks approval** with the reason + the remediation spectrum (Decision 9: switch existing / provision persistent [#58] / auto-provision ephemeral [deferred]). The plan schema and the approval DTO carry the capability list, estimated size, and per-worker satisfaction.
- On gate remediation (Path 2), the run is **requeued** so a capable worker re-claims it and resumes from the approved plan (durable in `run_messages`); no live session transfer between workers.
- New pre-claim **"no eligible worker"** run state for statically-known unsatisfiable runs (Path 1); surfaced in web + CLI with the same remediation. Documented in the run state machine (`specs/ai.md` §36/§lifecycle).

### 5. Surfacing (web + CLI)
- Plan approval shows a **pre-run readiness summary**: every inferred need (capabilities, toolchain, size) with its status — ✓ ready · will-install (provisioned) · needs-admin (not allowlisted) · provision-a-worker (non-provisionable) — plus per-worker satisfaction; the block state renders the remediation spectrum. Auto-resolvable needs never nag; only the genuinely unsatisfiable block.
- **Worker suggestion + select-time flag:** wherever the user picks or is assigned a worker, the UI suggests the fitting one and flags a mismatch inline — "this worker has no `docker`" / "too small: plan estimates ~4 GiB, this worker is 2 GiB" — *before* the run commits. This is the gate's check surfaced earlier, at selection time.
- Workers page shows each worker's capabilities **and size**. A run blocked on capability/size shows *why* + how to fix.
- `api/cmd/uzi` (PRD #64 CLI): the same requirement/satisfaction/block info exposed (list/inspect a run's required caps + size; the blocked state + remediation hint) — the CLI is a second consumer of the same API (CLAUDE.md CLI-parity rule).

### 6. Docs + specs
- `specs/ai.md`: capability model, the provisionable-vs-not split, the claim predicate, the new run state, plan `required_capabilities`. `ARCHITECTURE.md`: scheduling paragraph (workers advertise capabilities; runs carry requirements; the gate).
- Docs: repo-settings capability hint; what the plan gate's "needs a docker worker" block means and how to resolve it.
- `specs/human.md` is user-stated — not edited without approval.

## Risks & Open Questions

- **Readiness inference is a floor, not a guarantee.** Primary-toolchain detection from language manifests is high-signal; the long tail of tools a test shells out to is **not** exhaustively pre-flighted (that would be brittle and give false confidence). Those stay backstopped by the existing mid-run failure + the judge's `missing_tools` post-scan. The preflight catches the common, high-signal gaps pre-run; it must not be sold as "guaranteed green."
- **Inference false negatives.** A repo that needs docker in a way the scan misses won't be gated. Mitigated by the static-hint contract (Decision 6) and the fact that a missed inference degrades to today's clear mid-run failure, not a wrong result. Tune the scan heuristics; document them.
- **Provisionable-vs-not classification drift.** The gate's correctness depends on an accurate "provisionable" set; it must track PRD #18's tiers/allowlist as they evolve. A capability wrongly marked provisionable would let a run be claimed by a worker that then fails; wrongly marked non-provisionable would over-gate. Single source of truth + tests.
- **New run state × sweeper/timeouts.** "No eligible worker" must not be timed out like a stale claim (PRD #42), but also must not wedge forever — decide a policy (indefinite with a surfaced age, or a long soft cap with notification). **Open.**
- **★ Can execution resume from the approved plan alone? (the key fork.)** Path 2 (plan-time discovery → requeue → a capable worker resumes) assumes the implement phase can start from the plan text (durable in `run_messages`) + a fresh clone, without the planning session's in-memory working state. If it can, Path 2 is nearly free. If implement needs the planning session's context, then Path 1 (static-hint → provision-before-plan) becomes the recommended default and Path 2 degrades to *re-plan on the capable worker* (still correct — just re-does the cheap planning step). **Settle this early: it decides whether the static hint is a convenience or the primary path.**
- **Auto-ephemeral remediation depends on #58's deferred work.** Remediation (c) — spin a temporary worker for one run and tear it down — is not buildable until #58 grows spawn-on-demand + teardown (its non-goals today; #79's cost/GC question). #84 designs the gate to *support* it as a mode; it lights up when #58 does.
- **Size estimation quality.** The plan's size estimate is a heuristic; a low estimate under-provisions (OOM mid-run → #42's shared-cgroup requeue), a high one wastes capacity. Start coarse (S/M/L bands tied to #58 presets), refine from observed run stats later. Never *hard-block* on size (unlike a missing capability) — flag and let the user proceed, since size is a soft failure and capability is a hard one.
- **Where inference runs (resolved).** If a run is statically unsatisfiable it never plans (Path 1 pre-claim state); if it's statically satisfiable but the plan escalates, the gate catches it and requeues (Path 2). Both paths covered by tests.
- **Open: issue-label declaration** — ship in M2 or defer? Recommendation: repo-settings hint in M2, label parsing deferred unless cheap.
