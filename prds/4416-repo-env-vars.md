# PRD #4416: Per-repo secrets and variables for runs

**Status**: M1 shipped; M2 implemented (pending landing); M3 and M4 pending
**Priority**: Normal

## Problem

A run executes repo code on the worker: builds, unit tests, integration and end-to-end tests, code generators, migrations. That code reads configuration and secrets from the environment, the way it does in the repo's own CI pipeline, where CI variables supply them: API keys for third-party services and their sandboxes, database and broker URLs, licence keys, tokens for private package indexes, artifact-repository and container-registry credentials, cloud credentials, feature flags, and plain settings such as a region or a base URL.

uzi gives a run none of them. Stored secrets are limited to three kinds (`anthropic_token`, `openai_api_key`, `codex_auth`, `api/internal/store/migrations/00198_codex_secret_kinds.sql`), the Claude and Codex command environments are built from scratch (`agent/src/sdk-env.ts`, `buildCommandEnv` in `agent/src/codex/codex-executor.ts`), and a user has no place to put a value a repo needs.

A run that lacks a value skips the tests that need it, swaps the dependency for a stand-in and tests something CI does not test, or guesses. One real run of a JVM service did all three:

- The build reads its private artifact-repository URL, user and password from the environment. None was set. The agent looked for the URL in the repo, found only an outdated hostname in a code comment, probed it, got a DNS failure and concluded the repository was unreachable. The correct URL existed only as a CI variable.
- The integration and end-to-end suites start containers from a private registry. The registry was reachable, and every private pull was refused for missing credentials.
- The run fell back to public dependencies and reported both suites as blocked, so the change it produced was never tested the way CI tests it.

Two things follow. A missing non-secret value (a URL) blocks a run as surely as a missing password, and the agent will guess when it has none. And nothing short of the values themselves fixes it: the pipeline file tells the agent which names are needed, not their values.

## Outcome

A user defines named variables on one of their repos. Every run on that repo that executes shell commands gets them as environment variables, the way a CI job gets CI variables. Each variable is either a secret or a plain value. uzi does not interpret them: what a variable is for is between the user and the repo's code.

Acceptance examples:

1. A user opens a repo's settings and adds `PAYMENTS_SANDBOX_URL` as a plain value and `PAYMENTS_SANDBOX_KEY` as a secret, each with a description. The list shows every name, description and update time. Plain values are shown and can be read back. Secret values are never shown again, in the web UI, the CLI or any API response.
2. A new run on that repo runs the integration tests. The test code reads both variables from the environment and calls the sandbox, with no step by the agent. This holds on the Claude harness and on the Codex harness, in every command of the run, whichever agent issues it.
3. The lead's prompt lists each variable's name and description, and the value of each plain variable, so the agent knows what is set and does not guess. Secret values never appear in a prompt.
4. Any tool that takes its settings from the environment works unchanged. A package manager installs from a private index with a token variable. A build tool resolves private dependencies from `ARTIFACT_REPO_URL`, `ARTIFACT_REPO_USER` and `ARTIFACT_REPO_PASSWORD`. A database migration runs against `DATABASE_URL`.
5. A tool that logs in once and keeps the result on disk is driven by the agent or a repo script. For a container registry: `echo "$REGISTRY_PASSWORD" | docker login "$REGISTRY_HOST" -u "$REGISTRY_USER" --password-stdin` runs once, and later commands in the same run, including an image build with a private base image and a test suite that starts containers through a library reading the Docker client configuration, pull private images without logging in again. This holds on Claude from M2 and on Codex from M3; before M3 a Codex run logs in and pulls in one command. A run resumed on a worker that no longer has the login is told to log in again.
6. A command prints a secret's value. The run message, the worker log and any memory, review reply or finding the agent writes show the redaction marker instead. A plain value such as a hostname is not redacted, so output stays readable.
7. The agent writes a secret's value into a tracked file. The next checkpoint or the final push is held by the existing secret-remediation hold, the hold names the variable, and nothing containing the value reaches the forge. A plain value that already appears in tracked files (a hostname in a build file) holds nothing.
8. A user tries to save `ANTHROPIC_BASE_URL`, `NODE_OPTIONS`, `GITHUB_TOKEN` or `PATH`. The save is refused with a field error naming the rule.
9. A user marks a 5-character value as secret. The save is refused: a secret must be at least 8 characters so it can be masked. The same value saves as a plain value. A plain value that is a URL carrying a user and password is refused.
10. The user's vault is locked. Their runs on that repo wait exactly as they do today and continue after unlock; none fails because of a variable.
11. `uzi repo env list <repo>` prints names, kinds, descriptions, update times and plain values. The CLI has no command that writes a variable.
12. A worker that does not implement the feature never claims a run whose repo has variables. Run health names the reason while no capable worker is connected.
13. The run page lists the names injected into that run. The repo row shows how many variables the repo has.
14. A user edits a variable's description without re-entering its value, replaces a value, and deletes a variable. A run already claimed keeps the set it was given; the next claim of any run gets the current set.

## Out of scope

- **Hiding secret values from the agent.** The agent chooses the commands and edits the code those commands run, so it can read any value given to them. The UI and docs say so. Keeping a credential out of the run entirely needs a credential-holding proxy (the direction of `prds/50-llm-egress-proxy.md` and the fetcher of `adr/1906-isolated-fetch-lane.md`); that is a separate PRD.
- **Typed credentials and tool setup.** uzi delivers variables and knows nothing about what they are for. It does not log in to anything or write a tool's configuration file. The agent does that, guided by the variable descriptions, the repo's pipeline file or repo instructions, or the repo's own scripts do. Typed entries the worker acts on (a registry login, a package-index configuration) are a possible follow-up.
- **Network reachability.** A variable holding a URL does not make its host reachable from the worker.
- **Making container test libraries work against the worker's Docker daemon.** The daemon is a separate sidecar; a library that expects mapped ports on localhost may need its own setting (for example a host override). That is repo configuration, and a variable can carry it.
- Per-run variables. Planned as a follow-up; the wire field and worker merge here are written so a second source can be added.
- Variables shared between users. Repos, secrets and runs are per user today and stay so.
- CLI or product-API writes. Secret writes are cookie-only today (`api/internal/handler/routes_me.go`) and this keeps that rule.
- File-type variables.
- Variables in worker-spawned checks and the dependency install (`buildCheckEnv` in `agent/src/sdk-env.ts`), and in lanes without a shell (judge, task review, summary, cross-check, chat, jobs, isolated research).
- Forge credentials as variables (`GH_TOKEN`, `GITLAB_TOKEN` and similar). They would bypass the guardrail that only the worker holds a forge credential.

## Design: what changes and what stays

What changes:

- The agent command environment carries user-supplied values, some of them secrets. This amends two recorded invariants, by an ADR in M2: the Codex command environment being credential-free, and the SDK environment holding exactly one secret (`adr/0319-env-read-diagnostic-allowlist.md`).
- A second vault-sealed table exists beside `user_secrets`.
- The Docker client configuration directory becomes per run on both harnesses (M3). It is the one tool the worker has to help, because the worker owns `DOCKER_CONFIG` and a user variable cannot set it.

What stays:

- No reveal endpoint for secrets, no admin read path to another user's values.
- Worker-set environment keys always win. A user variable can never replace or remove one.
- A locked vault delays work and never fails it.
- Guardrails are unchanged. Bare environment enumeration, non-allowlisted environment reads and `/proc` reads stay denied; the existing diagnostic reads (`printenv PATH` and the rest of `adr/0319-env-read-diagnostic-allowlist.md`) remain allowed. This feature does not rely on any of them as a boundary.

Residuals, accepted and to be recorded in the ADR:

- The agent can read secret values and docker-tier egress is open (`adr/0285-worker-egress-tier-trust-model.md`). Users should store read-only, narrowly scoped credentials.
- Concurrent runs on one worker share a runner uid and one DinD daemon (`adr/0091-runner-cross-run-persistence-residual.md`, `docs/proc-hardening.md`). A run on one repo can reach another repo's variables and pulled images. A worker serves one user, so nothing crosses users. The Anthropic token has the same exposure today.
- Redaction is exact-match with an 8-character floor (`agent/src/redact.ts`). It covers the forms listed under Worker and no other encoding. It is a net, not a boundary.
- Values reach the model provider: the agent reads them and tool results carry them. Native Claude and Codex transcripts persisted on the worker hold them unredacted, as they hold anything else the agent reads.
- Login state a tool writes to disk holds the credential for as long as the directory lives. On Claude that is the run home, until the run ends. On Codex the command home is recreated per command, so before M3 a login and the command that uses it must run in one command (`docker login … && docker pull …`); from M3 the run's Docker configuration directory keeps the login, including while the run is parked. Either directory follows the run home's custody: it is removed with the run home, kept where the run home is retained (resume-preserving paths, a retained-home marker), and kept with a warning when removal is refused or fails. While it exists, a concurrent run on the same worker can read it, per the shared-uid residual above.
- Values passed to an image build as build arguments stay in that image's history in the shared DinD daemon. That is how such builds behave everywhere; the user doc says so.

## Modules and seams

### Store and vault (`api`)

- New table `run_env_vars` (additive goose migration), one row per version of a variable: `id`, `var_id`, `user_id` (`ON DELETE CASCADE`), `repo_id` (nullable, `ON DELETE CASCADE`), `name`, `secret` (bool), `description`, `ciphertext`, `sealed_with` (`master_aad` or `dek`), `value_bytes` (the plaintext length), `rev`, `retired_at` (nullable), `disabled_at` (nullable), `pending_delete_at` (nullable), `created_at`, `updated_at`. `var_id` is a UUID minted when a variable is created and never reused, so a delete then re-create is a different variable; `rev` counts up per `var_id`, and `(var_id, rev)` is unique. Every save that changes the value or the secret flag writes a new version with the next `rev`. A row with a repo belongs to that repo; a row without one is the user-level scope that M4 uses. M1 to M3 write and read repo rows only. A row is live when neither `retired_at` nor `pending_delete_at` is set; a disabled row is still live. Two partial unique indexes over live rows: `(user_id, repo_id, name)` where `repo_id` is set, and `(user_id, name)` where it is not.
- Retired versions. A new version and a secret-to-plain change retire the previous secret version instead of dropping it when any run holds a delivery receipt for it (see Claim). A retired version stays sealed, is never injected or shown, and is delivered to those runs for redaction and scanning only. It is kept until every such run is terminal and has no open custody hold, terminal preservation, salvage or held-ref publication pending; only then does the sweeper delete it. A plain version is never retired.
- Every value, plain or secret, is sealed through the existing vault seam, so there is one storage path. The `secret` flag decides what may be read back, redacted and scanned. The AAD binds a domain tag, the user id, a scope tag (repo or user) with the repo id when there is one, the secret flag and the length-prefixed name. A ciphertext cannot be moved between names, repos or scopes, and a secret cannot be relabelled plain without its value being supplied again.
- Edits: a save without a value changes only the description, in place. A save with a value writes a new version with the next `rev`. Secret to plain requires a value in the same save and writes a new version. Plain to secret writes a new version sealed from the stored value and needs an unlocked vault. There is no rename; delete and create, which mints a new `var_id`.
- The table joins every explicit vault enumeration, or its rows become undecryptable: the material totals, the lock and reseal batches used when the vault is enabled or disabled (`api/internal/store/queries/vault_material.sql`, `api/internal/vault/lifecycle.go`), the budgets of `adr/3507-optional-credential-vault.md`, and the account-reset delete (`api/internal/store/queries/account_reset_links.sql`). Writes take the same users-row fence as other secret writes.
- Value rules: valid UTF-8 without NUL (a process environment cannot carry it); at most 65536 bytes; a plain value may be empty and must not be a URL with userinfo; a secret is at least 8 characters as `MIN_SECRET_LEN` in `agent/src/redact.ts` counts them, so every secret can be masked and scanned. Plain values are never masked or scanned, whatever their length.
- Limits: name `^[A-Z_][A-Z0-9_]{0,127}$`; description at most 1024 bytes of UTF-8; at most 50 variables and 262144 value bytes per scope, counting live rows (enabled and disabled) and rows pending deletion, which the panel shows as "N of 50, D disabled, P pending deletion"; at most 200 retired versions and 2097152 retired value bytes per user. Live and retired rows count toward the vault's owner-wide material totals (`maxMaterialRows`, `maxMaterialBytes` in `api/internal/vault/conversion.go`). A rotation or a secret-to-plain change that would exceed any of these is refused in the same transaction with 409 `env_history_full`, naming the runs whose receipts keep the retired versions; the panel then offers Disable and Delete, which are never refused for budget reasons (see Disable and Delete). A save of a secret is also refused with 409 `env_forms_budget` when it would raise the repo's secret value bytes (every secret row of the repo and the user scope in any state; plain values excluded) above 116,959, so a claim stays under the 40,000,000-unit form cap; a save that does not raise the count (or leaves it at or below the cap), and Disable, Enable and Delete, are never refused for budget reasons. Every boundary is tested at the limit and one past it.
- Disable and Delete. Both are never refused for history-budget reasons, take the same owner, cookie, CSRF and users-row fence as any write, and change nothing about custody or unpublished work. Neither revokes the credential: the owner revokes it at the provider, and the panel and the user doc say so.
  - Disable is metadata-only on the live version: it sets `disabled_at`, writes no new version and needs no history or vault capacity. The variable keeps its name and its slot in the per-scope limit, so it cannot be re-created under that name while disabled; it can be enabled again (metadata-only, clears `disabled_at`) or have its value replaced (a normal save, which writes a new version, retires the old one within the history budget, and keeps the variable disabled until enabled). It is not injected or listed in any prompt from the next claim on. In M4, disabling a repo variable suppresses that name for the repo's runs; the user-scope value of the same name is not injected in its place.
  - Delete of a variable no run holds a receipt for drops it at once. Delete of a secret some run holds a receipt for sets `pending_delete_at` instead, answers 202 with state `pending_deletion`, and the panel shows it as "Pending deletion, kept to mask N runs", never as deleted. The row leaves the live set, so its name is free at once and can be re-created as a new `var_id`; it moves no data and still counts toward the per-scope limit, so retained material stays inside existing bounds. The sweeper deletes it under the same rule as retired versions.
  - Disabled and pending-deletion versions are delivered in `run_env_redact` to runs holding a receipt for them, so historical protection stays.

### Name rules (shared fixture)

- The rules protect the worker's own invariants and guardrails: its credentials, its Docker endpoint, its git authority, the provider configuration and the directories it manages. They do not protect the build from its owner. The user who sets a variable owns the repo and the run, and can already change what the build does by editing it.
- One JSON fixture under `fixtures/` lists denied names and prefixes and is pinned by tests on the api and the worker, like `fixtures/claims/claim-response-limit.json`. It contains at least the union of the two protected-key sets (`PROTECTED_ENV_KEYS` in `agent/src/sdk-env.ts`, `COMMAND_ENV_PROTECTED_KEYS` in `agent/src/codex/codex-executor.ts`), every key either builder sets after its fold, and every worker-owned harness control.
- Harness controls versus application configuration. A harness control is a setting the harness process itself reads to decide how it runs: provider and endpoint selection, timeouts, token limits, feature switches. Those are denied. A setting a command the agent runs reads is application configuration and is allowed. On Claude the SDK environment is also the Claude CLI's own environment, so the fixture lists the controls outside the denied prefixes that the pinned `@anthropic-ai/claude-agent-sdk` review classified (for example `API_TIMEOUT_MS`, `MAX_THINKING_TOKENS`, `MAX_MCP_OUTPUT_TOKENS` and the `DISABLE_` prefix). The list is only as complete as the review behind it: the #4611 audit found controls read since 0.3.319 that the first review had missed (see the Decision Log). On Codex the per-command environment is separate from the worker-owned app-server environment, which never receives user variables, so only names that leak into the app-server count. Where a harness also reads a name that is application configuration, the fixture records the overlap and its decision. The invariant is that user variables cannot change the provider or the authentication the worker selects. Every provider selector the pinned SDK reads (`CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY`, `CLAUDE_CODE_USE_ANTHROPIC_AWS`, `CLAUDE_CODE_USE_ANTHROPIC_GOOGLE_CLOUD`, `CLAUDE_CODE_USE_MANTLE`, `CLAUDE_CODE_USE_GATEWAY`) is denied by the `CLAUDE_` prefix (and `_CLAUDE_CODE_ASSUME_FIRST_PARTY_BASE_URL`, whose leading underscore escapes the prefix, by name), and the pinned-version review must cover every selector a new version adds. Under that invariant cloud credentials (`AWS_*`, `GOOGLE_*`) are allowed as application configuration. On Claude they also enter the CLI's own environment, where they have no effect while no selector is set. A test sets every allowed name the pinned SDK also reads and pins that the run still uses the worker-selected provider and credential.
- Fixture review. The fixture records the harness versions it was derived from, and a test fails when either pin changes without a matching fixture update. The update procedure is part of every harness bump: list the environment settings the new version reads, classify each new name as a harness control or application configuration, record overlaps with their decision, then update the recorded version in the same PR. The recorded version is never advanced only to make CI pass.
- Denied names: `HOME`, `PATH`, `TMPDIR`, `LANG`, `SHELL`, `ENV`, `IFS`, `PS4`, `PROMPT_COMMAND`, `SHELLOPTS`, `BASHOPTS`; `DOCKER_HOST`, `DOCKER_CONFIG`, `DOCKER_CONTEXT`, `DOCKER_TLS_VERIFY`, `DOCKER_CERT_PATH`, `BUILDKIT_HOST`; `GOMAXPROCS`, `GOFLAGS`, `GOTMPDIR`, `GOMODCACHE`, `GOCACHE`, `GOPROXY`, `GOSUMDB`, `GOENV`, `GOTOOLCHAIN`; `NPM_CONFIG_CACHE`; `NODE_OPTIONS`, `NODE_PATH`, `NODE_EXTRA_CA_CERTS`, `NODE_TLS_REJECT_UNAUTHORIZED`; `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `JDK_JAVA_OPTIONS`; `CURL_HOME`, `NETRC`, `WGETRC`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`, `RUBYOPT`; the browser discovery keys and run-attempt markers; the SDK 0.3.325 audit names (#4611) `NODE_INSPECTOR_IPC`, `VSCODE_INSPECTOR_OPTIONS`, `TEMP`, `TMP`, `SYSTEMDRIVE`, `API_FORCE_IDLE_TIMEOUT`, `ENABLE_TOOL_SEARCH`, `SLASH_COMMAND_TOOL_CHAR_BUDGET`, `AUTOMODE_DECISION_LOG`, `NODE_USE_SYSTEM_CA`, `ENABLE_BETA_TRACING_DETAILED`, `ENABLE_ENHANCED_TELEMETRY_BETA`, `BETA_TRACING_ENDPOINT`, `_CLAUDE_CODE_ASSUME_FIRST_PARTY_BASE_URL`; and any name ending in `_PROXY`.
- Denied prefixes: `UZI_`, `CLAUDE_`, `ANTHROPIC_`, `CODEX_`, `OPENAI_`, `MCP_`, `DISABLE_`; `GH_`, `GITHUB_`, `GITLAB_`, `GLAB_`; `GIT_`, `SSH_`; `LD_`, `DYLD_`, `BASH_`, `XDG_`, `SSL_CERT_`, `PYTHON`, `PERL5`, `NIX_`, `DEVBOX_`. The list grew during M2 (for example `BUN_`, `LC_`, `OTEL_EXPORTER_OTLP_`, `GCE_METADATA_`, `AWS_ENDPOINT_URL_BEDROCK`, and the exact names `AWS_ENDPOINT_URL`, `AWS_ENDPOINT_URL_STS`, `AWS_ENDPOINT_URL_SSO` and `AWS_ENDPOINT_URL_SSO_OIDC`); `fixtures/run-env/name-rules.json` is the authoritative list.
- Everything else is allowed: application names of any kind (`DATABASE_URL`, `STRIPE_API_KEY`, `SENTRY_DSN`), cloud credentials (`AWS_*`, `AZURE_*`, `GOOGLE_*`, except the endpoint settings the fixture denies, such as `AWS_ENDPOINT_URL`, `AWS_ENDPOINT_URL_STS`, `AWS_ENDPOINT_URL_SSO`, `AWS_ENDPOINT_URL_SSO_OIDC`, `AWS_ENDPOINT_URL_BEDROCK*` and `AWS_EC2_METADATA_SERVICE_ENDPOINT`; other per-service names such as `AWS_ENDPOINT_URL_S3` stay allowed), package-index tokens (`NPM_TOKEN`, `PIP_*`, `NPM_CONFIG_*` other than the cache), and build-tool configuration such as `GRADLE_OPTS`, `MAVEN_OPTS`, `ORG_GRADLE_PROJECT_*`, `COMPOSE_*`, `TESTCONTAINERS_*` and `DOCKER_AUTH_CONFIG`.

### API (`api/internal/handler`)

- `GET /api/repos/{id}/env`: list with metadata and plain values, plus the variable count on the repo DTO. Accepts the session cookie and the CLI token. This is the first list a CLI token can read values from; they are values the user declared not secret.
- `PUT /api/repos/{id}/env/{name}` (value optional on an existing variable), `POST /api/repos/{id}/env/{name}/disable`, `POST /api/repos/{id}/env/{name}/enable` and `DELETE /api/repos/{id}/env/{name}` (200 when dropped, 202 with `pending_deletion` when kept for masking): cookie and CSRF only, owner only, behind the same repo preflight as the tool profile (`api/internal/handler/tool_profiles.go`). A locked vault answers 409 `vault_locked`, as secret saves do; the list then shows names and metadata with plain values withheld.

### Claim (`api/internal/workersvc`)

- Run kinds. `run_env` is delivered to the lead kinds of `fixtures/run-kinds/registry.json` that execute repo code: `issue`, `prompt`, `self_improve`, `ci_fix`, `mr_rework`, and `task` runs whose `review_target_run_id` is null. Task-review runs (`task` with `review_target_run_id` set), `chat`, `judge`, `job` and `cross_check` never receive it, and the claim gate does not apply to them.
- `ClaimSecrets` gains `run_env` (`omitempty`): for each live, enabled variable, `var_id`, scope, rev, name, value, the secret flag and description. A second list, `run_env_redact`, carries every secret version this run holds a receipt for that is not in the effective injection set, whatever the reason (retired, disabled, pending deletion, or a live version shadowed by a same-named variable of the other scope), deduplicated by `(var_id, rev)` across all receipt generations, for redaction and scanning only, each carrying only `var_id`, rev, scope, name and value (no description); the worker never sets them in an environment or a prompt.
- Claim size. The whole serialized `run_env` and `run_env_redact`, with every metadata field at its limit and worst-case JSON escaping (every byte escaped as `\u00XX`), stays below a quarter of `claim_response_max_bytes` in `fixtures/claims/claim-response-limit.json` and the cap applied in `api/internal/workersvc/claim_size.go`. A test serializes the actual claim DTOs at that worst case and checks the encoded size, so variables alone cannot make a claim hit `errClaimTooLarge`.
- Snapshot. `assembleClaim` reads the effective injection set: the enabled, live versions across the scopes in effect after precedence and suppression, as a list of `(var_id, rev)`, plus the `(var_id, rev)` list of the redact-only versions. `finishRunClaimTx` (`api/internal/workersvc/claim_recovery.go`) then takes the owner's users-row fence that variable writes take, recomputes both lists and checks `run_env_v1` against it. If either list changed (a Disable, Enable, Delete, rotation or create in between), or the set is non-empty and the worker lacks the capability, the claim settles through the existing transient path (like `errCustomModelCapabilityMissing`): the run returns to queued and is retried, and nothing is delivered. Otherwise the same transaction appends one receipt per delivered secret version to `run_env_receipts(run_id, var_id, rev, scope, claim_generation)`, an append-only table that is never pruned while the run's retired versions are kept. Receipts carry no values and no hashes. A change committed after that transaction reaches the run at its next claim.
- An open failure caused by a locked vault maps to the existing requeue path, never to a failed run. A receipted retired version that cannot be opened, or is missing, is not delivered silently: the claim parks the run with a visible reason, and the run neither resumes nor publishes until the owner acts.
- New worker protocol capability `run_env_v1`. `ClaimRun` requires it when the run is of a receiving kind and its repo has live variables or the run holds receipts, using the existing `EXISTS` gate pattern in `api/internal/store/queries/runtime.sql`. The same condition is mirrored in fleet-aware placement and in run health, so an unplaceable run says why.
- The claim response sets `Cache-Control: no-store`.

### Worker (`agent`)

- Variables are an explicit optional input of `buildSdkEnv` and `buildCommandEnv`, passed only by the receiving run lanes (`agent/src/sdk-executor.ts` and the Codex run executor). Chat, cross-check, the isolated executor, the advice harness and the job runner (`agent/src/chat-executor.ts`, `agent/src/claude-cross-check.ts`, `agent/src/isolated-executor.ts`, `agent/src/claude-advice-harness.ts`, `agent/src/job-runner.ts`) never pass it, and a test pins that each of them builds an environment with no user variable. Variables are merged at the lowest precedence: a key already present is kept, then worker-set keys are applied as today. The worker re-checks every name against the fixture and drops a violation with a run event.
- Variables are set on every command, so a tool that reads the environment needs nothing else on either harness. A tool that logs in and stores the result under the home directory keeps it on Claude, where the run home lasts for the run, and loses it on Codex, where the command home is recreated per command; there the login is repeated or the tool is pointed at variables. The user doc says so.
- Docker client configuration (M3). The Docker CLI cannot take a login from the environment and the worker owns `DOCKER_CONFIG`, so the worker gives each run one directory named `.docker` and points `DOCKER_CONFIG` at it. A login made by one command is then read by the Docker CLI, image builds and container test libraries in later commands.
  - Claude: the run home is already per run and kept across commands (`agent/src/main.ts`); the directory is `.docker` under it.
  - Codex: the command home is recreated for every command (`commandEffectSpec` in `agent/src/codex/codex-executor.ts`), and the run's shared cache is optional and rotated, so neither can hold it. The command sandbox gets a dedicated per-run grant for this directory, independent of the cache, and `DOCKER_CONFIG` is set per command in `commandEffectSpec`. It applies with and without the uid split.
  - Lifecycle follows the run home's custody and cleanup rules (`agent/src/runner.ts`, `agent/src/retained-homes.ts`): the directory is kept wherever the run home is retained, including resume-preserving paths, and removed only when the run home is. A refused or failed removal keeps it, with the same warning the run home gets, and that retention is a recorded residual; preservation is not weakened to delete it. The name `.docker` keeps `config.json` inside the existing credential denylist for terminal snapshots (`agent/src/git.ts`).
  - M3 starts by proving on Codex, on a uid-split worker, that a login in one command is visible to an image pull and an image build in the next. If the sandbox cannot be granted the directory, M3 stops and the PRD is revised; M2 does not depend on it.
- Registered forms. One helper derives, for each secret in `run_env` and `run_env_redact`: the value; its JSON-escaped form when that differs (`agent/src/log.ts` scrubs after `JSON.stringify`, so a value holding a quote, backslash or newline is otherwise missed); and the three base64 alignments of the value, each trimmed to the characters that do not depend on neighbouring bytes, so the secret is caught inside any base64 stream, including the `user:password` entry a registry login stores and an HTTP Basic header. Plain values are never registered. The run's secret set in `agent/src/runner.ts` is built from every claim, so a worker restart rebuilds it from the next claim with nothing persisted.
- Outbound sinks. Every path that carries repo or agent text off the worker either passes the run's redactor, or the exact-value scan, or both:
  - Redacted: run messages, the worker log, the Codex stream, saved memories, review-thread replies, findings, PR/MR title and body including the description fallback fields (`agent/src/pr-description-publisher.ts`), issues the agent files, questions and answers, persisted plan and cross-check inputs, and judge-visible output, the plan-turn changed-file list (`plan_changed_files`), capability-inference evidence paths and a proposal's `repo_path` and `repo_id`. Park and recovery reports carry only fixed values (recovery causes, `semantic_park`, wall and iteration park bodies, `limit_wait` fields, fixed failure codes) and need no redaction; judge and task-review runs never receive run variables (`LeadLane` in `api/internal/leadcfg/leadcfg.go`, `RunEnvDelivered` in `api/internal/workersvc/run_env_claim.go`).
  - Scanned, and held on a hit: checkpoint publish, salvage-ref publish, final push, recovery-capture archives uploaded to the API, and the terminal preservation pack behind `refs/uzi-terminal/<run-id>` (`api/internal/workersvc/terminal_preservation.go`). These paths run after a run is terminal too, which is why retired versions outlive terminal status. When historical protection for a run is unavailable (a receipted version is missing or cannot be opened), every later scanned publish of that run is refused, not sent unscanned.
  - Redacted and scanned: `preserved_patch`. The raw patch is withheld whole when the claim is over the form budget, when a whole-value form occurs in it (`raw_value`), when a registered line form occurs (`line_form`), when the run holds any multi-line secret, live or retained, of any length (`multi_line_secret`), or, for a run whose secrets are all single-line, when a git-quoted header path decodes to a secret form, it cannot be parsed (binary, combined diff, a line-count mismatch, or a stray line such as a non-header line between a file header and its first hunk) or a whole-value form occurs in a rebuilt per-hunk pre- or post-image; the image and parse checks apply when the run has any secret variable, retired versions included. Otherwise it is scrubbed with the run's registered secrets (now including these) before its gitleaks scan. Accepted limitation (owner decision B4, 2026-11-22): a line fragment shorter than 8 characters, or a value that appears only re-encoded, is not masked in run output (see the ADR's Residuals).
  - Allowed exposure, not protected: the model provider and the worker's local filesystem, listed under residuals.
- Exact-value scan. Before each scanned publish, every commit in the outgoing range is searched for the registered forms, not only the final tree, and the verdict is bound to the exact commit or archive digest that is then published. A hit uses the existing secret-remediation hold and names the variable, so a user who chose a common word as a secret sees why. The scan fails closed: on timeout, an unresolved range, truncated input or a scanner error the publish is withheld, unlike the gitleaks path in `agent/src/secret-scan-guard.ts`, which fails open to forge push protection that cannot know these values. A withheld recovery path (salvage ref, recovery capture, terminal pack) keeps the work recoverable: the source stays on the worker under the existing custody hold, which on an ephemeral worker keeps that worker's storage, and the owner sees the hold with its reason. gitleaks stays as it is.
- Prompt. The environment-facts block of `agent/src/prompt.ts` (Claude and Codex call sites) and the append every subagent gets list names, descriptions and plain values, fenced and sanitised like other user-supplied text, and state that the listed variables are already set in the command environment. From M3, a resumed run is also told that a registry login may not have survived and to log in again if a pull is refused.
- A test pins that no outbox, recovery journal or hibernation record serialises `run_env`.

## Testing decisions

- Store: both partial unique indexes, limits, the edit rules, cascade on repo and user delete.
- Vault: enable, disable and account reset with live and retired versions present; every row opens afterwards or is gone, and the material totals include retired rows. A ciphertext swapped between two names, two repos, or a secret and a plain row, fails to open.
- Name rules: the shared fixture drives table tests on both sides; a name allowed by one side and denied by the other fails the build.
- Value rules: NUL refused, empty plain value accepted, a 7-character secret refused and an 8-character one accepted, size and count limits at the boundary and one past it.
- Claim: gate on and off per run kind, a task-review run never receiving variables, an old worker never claims a gated run, locked vault requeues, names and revs recorded, `no-store` header present. Races through the claim hooks: a repo's first variable added between admission and finish for a worker without the capability returns the run to queued with nothing delivered; a rotation and a delete between assembly and finish do the same; a change after finish reaches only the next claim. A Disable, an Enable and a Delete each landing between assembly and finish return the run to queued; in M4, disabling a repo variable suppresses the user-scope value of the same name. In M4, a user-scope secret delivered to a run and then shadowed by a new repo variable of the same name arrives in `run_env_redact` at the next claim.
- Versions and receipts: several rotations followed by repeated re-claims deliver every earlier version in `run_env_redact` and only the latest in the environment; a delete then re-create during assembly is a different `var_id` and requeues the claim; secret-to-plain and plain-to-secret each advance `rev` and retire the secret side; receipts accumulate across claims and are never replaced.
- Retention: a retired version survives the run's terminal status while a custody hold, terminal preservation, salvage or held-ref publication is pending; terminal, then sweep, then worker restart, then recovery or publication is either still protected or refused; a receipted version that cannot be opened parks the run and refuses its scanned publishes.
- History budget: a rotation at the retired-version and retired-byte limits, and at the vault material limits, is refused with `env_history_full` and changes nothing. With the budget full and an open custody hold on a receipted run, Disable and Delete still succeed: Delete answers `pending_deletion`, the name can be re-created at once as a new `var_id`, a disabled name cannot, both count toward the per-scope limit, the next claim injects nothing for that variable, the receipted run still receives the value in `run_env_redact`, and the held work is untouched. The worst-case envelope test and the `(var_id, rev)` deduplication across repeated claims run here too.
- Lanes: chat, cross-check, the isolated executor, the advice harness and the job runner build environments with no user variable even when the repo has variables; a variable named after a pinned harness setting is refused by both sides.
- Worker: precedence (a user `PATH` smuggled past the api is dropped). Redaction through each redacted sink of a secret, its JSON-escaped form, each base64 alignment and a written registry login entry; no redaction of a plain value. Restart, then rotate or delete, then resume, then an attempted publish of a commit holding the old value: held. Exact-value scan holding a hit in a middle commit of the range, in a recovery archive and in `preserved_patch`; withholding on timeout, an unresolved range, truncated input and a scanner error; refusing a publish whose candidate differs from the scanned one; holding nothing for a plain value present in the tree.
- E2E for M2, compose, both harnesses, dummy values: a run's test command reads a plain URL variable and a secret, calls a local HTTP stub that requires the secret, and passes; the secret printed by a command is redacted in the run messages.
- E2E for M3, compose, both harnesses, with a local registry stub that requires authentication: a run logs in with a secret, and later commands pull an image and build one from a private base image through the Docker client configuration.
- The two E2E scenarios run at landing, not in a run (see Landing obligations).
- Fixtures that look like credentials are assembled at runtime and `task scan:secrets` runs in every milestone gate.

## Decision Log

- **Plain variables, agent-readable.** Reviewed alternatives: command-only injection, a worker-run fixed command, running the tests in the forge's CI, and short-lived tokens. None hides a value from an agent that authors the commands and the code. Only a credential-holding proxy does, at a much larger cost, and only for pull credentials. Chosen: ship plain variables with an honest label; treat the proxy as its own PRD.
- **A secret flag per variable.** Treating every value as a secret would redact registry hosts out of every log line and hold every push from a repo whose build files name that host. It would also hide the URL the agent most needs to see.
- **One sealed storage path for both kinds.** Simpler than two tables or a plaintext column; the cost is that plain values are unavailable while the vault is locked, when runs do not start anyway.
- **Generic variables, not typed credentials.** A store of registry or artifact-repository logins would cover one class of need and leave API keys, database URLs and every other value a repo reads without a home. Named variables cover all of them the way CI variables do, and the typed cases reduce to variables plus a command.
- **uzi does not log in or configure tools.** A worker-written login or configuration file is deferred until variables prove insufficient.
- **A Docker configuration directory per run, as its own milestone.** It is the only tool-specific piece. Without it a login on Codex does not survive to the next command: authentication still works when login and use share one command, but a test suite that pulls in later commands cannot authenticate, and no variable can fix that because the worker owns `DOCKER_CONFIG`. It is split from M2 so generic injection does not wait on the Codex sandbox proof. It follows the run home's custody and cleanup, so it is kept while a run is parked or its home is retained; clearing it separately would need a call on every park path and could weaken preservation, and the credential it holds is already readable by the run.
- **Plain values readable by a CLI token.** The secrets list is readable by a CLI token because it never carries a value. This list carries values the user declared not secret; a URL with embedded credentials is refused as plain to keep that true.
- **The name rules guard the worker, not the build.** Build-tool options that can load code stay allowed, because the user who sets them owns the repo and can do the same by editing the build.
- **No `master_aad` column; `sealed_with` stands in.** The seal discriminator is the `sealed_with` column (`master_aad` or `dek`), the same one `user_secrets` carries minus the nil-AAD legacy `master`. `value_bytes` records the plaintext length so the per-scope and retired-history byte limits need no decryption.
- **No audit table.** No other secret has one, and nothing would read it.
- **Per user per repo, then per user.** Matches repos, the tool profile and the vault. The user-level scope is in the schema from M1 so M4 needs no migration of existing rows. Sharing between users would need an authorization model uzi does not have.
- **Web-only writes.** Keeps the existing cookie-only rule for secret writes.
- **Lowest-precedence merge plus a denylist.** The existing provisioning fold is a three-key allowlist and cannot carry user names; precedence protects every worker-set key structurally, the denylist covers names the worker never sets.
- **Hard claim gate.** A soft gate would let an old worker run the job without the variables and fail in a confusing way.
- **Snapshot checked at finish, not assembled at finish.** Assembly stays outside the claim transaction as it is today; the finish transaction re-reads the `(var_id, rev)` list under the owner fence and requeues on a mismatch. Retrying a rare race is cheaper than moving vault opens into the claim transaction.
- **Retired secrets kept server-side while a run needs them.** The worker persists nothing about `run_env`, so a restarted or different worker can protect an old value only if the claim carries it. Keeping every receipted version until the run's custody and publication obligations end does that; refusing to resume or publish is the fallback when one cannot be opened.
- **Version identity is `(var_id, rev)`, receipts are append-only.** A name and rev alone cannot tell scopes apart or a re-created variable from the old one, and a latest-only record would drop a version a resumed run still has to scrub.
- **A bounded history, refused at the edge, with a disable that is never refused.** Retired versions sit outside the live limits, so they get their own per-user budget inside the vault's totals; refusing a rotation is visible and recoverable, unlike a claim that turns terminal for being too large. A compromised value must always be cut off, so Disable is metadata-only and consumes no budget; cancelling a run does not reliably end its custody, so pointing the owner at runs is not an exit on its own.
- **Harness controls denied, application configuration allowed.** A blanket deny of everything a harness reads would forbid ordinary cloud credentials that builds and tests need. The harness is protected by denying its own controls and the provider switches that would make it read application names.
- **Variables are an explicit input, not a global merge.** The environment builders are shared with lanes that must not see the variables; passing them only from the receiving run lanes makes exclusion structural.
- **Exact-value scan fails closed.** gitleaks can fail open because forge push protection backs it; nothing outside the worker knows these values, so an untrustworthy scan withholds.
- **Base64 alignments instead of fixed pairs.** Three trimmed alignments catch a secret inside any base64 stream, including a `user:password` entry, without knowing which other value it is paired with.
- **Cross-repo exposure on a shared worker accepted.** Same exposure as the Anthropic token today; recorded as a residual rather than requiring uid-split or ephemeral workers.
- **M2 delivery record (2026-11-21).** The ADR is `adr/4416-run-env-vars.md`. The compose E2E scenarios for M2 are authored and run at landing; the hosted owner acceptance is not done, so this delivery stays `non_closing`.
- **Receipts are plain and secret.** The run page names what a claim injected, so every delivered version gets a receipt. Retention, retire and pending-delete decisions and the finish gate read the secret receipts only, so a plain receipt never keeps a version.
- **A finalize hit fails the run `push_secret_blocked`.** The PRD had the secret-remediation hold take it. The existing typed finalize outcome is used instead, with no push and no preserved patch; checkpoint hits still latch into the remediation state. The exact-value scan runs on every forge and fails closed, where the finalize gitleaks scan was GitHub-only and fail-open.
- **The salvage ref is an API copy of the checkpoint.** The PRD listed a worker-side salvage-ref publish to scan. There is none; scanning the checkpoint covers the copy. Park, shutdown, pause and overlay checkpoints were not gitleaks-scanned and recovery bundle uploads were unscanned; both now pass the exact-value scan, at the single `publishCheckpoint` call and the recovery coordinator.
- **One lead-lane function.** The lane is `leadcfg.LeadLane`, mirrored in SQL by `fn_run_env_lane` and pinned by a LiveDB test, so run kinds, review targets and egress-profile-bound runs cannot drift between claim, gate, placement and health.
- **A variable identity table.** `run_env_var_ids` binds a `var_id` to one owner, repo, scope and name while anything references it, enforced by a trigger, so a receipt can never be satisfied by another variable's row.
- **AAD version 2.** New seals bind owner, `var_id` and `rev` as well as scope, repo, secret flag and name, selected per row by `aad_version`. Residual: version-1 rows sealed before M2 can be swapped with a ciphertext of the same owner, repo, name, scope and secret flag (in practice another version of the same variable), and a database writer can downgrade `aad_version`; both close when the row is rewritten.
- **Cross-check children mask the lead's secret versions.** A child never receives `run_env` and writes no receipts, but its checker reads the lead's code and output, so its claim carries the lead's secret versions as `run_env_redact`. Without `run_env_v1` or an openable version it ends `checker_unavailable`, which forces a human gate. Residuals: retention does not consider a child's dependence on its lead's versions (the child fails closed), and placement does not steer a child to a `run_env_v1` worker, so a rolling deploy can force a human gate.
- **A maintenance redact route without a generation bound.** A worker that last held the run, or took an open custody hold on it, reads the run's whole receipted secret history after its claim, so held, terminal and recovery publishes can still be scanned. Read-only and same-user only, so accepted.
- **An unreadable receipted version parks the run.** Hold reason `run_env_history_unavailable`: Resume retries once the history is restored, Cancel is terminal.
- **Secret forms cover the common encodings (2026-11-22).** Registered forms include JSON with escaped slashes, HTML-safe `\u00XX`, percent-encoded and base64url alignments, variants without a trailing line break and LF-normalized, and per-line forms of a multi-line value for redaction only. Scan needles for a multi-line value add diff-shaped forms rather than single lines, because a public line would hit unrelated files. Superseded for the preserved patch by the 2026-11-22 entry "Preserved patch is judged on rebuilt hunk images".
- **Prompts list only injected variables (2026-11-22).** A name dropped as protected or already set by the tool profile is not listed, so the agent is never told a variable is set when it is not.
- **Redact route needle fallback uses a durable per-run marker (2026-11-22).** An absent route (a 404 with no code) resolves to no needles only when no marker exists. The worker writes the marker durably before any variable reaches an executor and a failed write stops the run from starting. The marker proves only that this worker never received variables for the run: adopted work, or work claimed by a build from before the marker existed (not released), has none.
- **Name rules extended (2026-11-22).** Denied: `NODE`, `NODE_NO_WARNINGS`, `NODE_SKIP_PLATFORM_CHECK`, `NODE_PENDING_PIPE_INSTANCES`, `UV_USE_IO_URING`, `AWS_EC2_METADATA_SERVICE_ENDPOINT` and the prefixes `OTEL_EXPORTER_OTLP_`, `GCE_METADATA_`, `AWS_ENDPOINT_URL_BEDROCK` (no trailing underscore, so it also covers `AWS_ENDPOINT_URL_BEDROCK_AGENT*`). The first two prefixes moved from allowed application settings to denied network wiring because the harness reads them. No released worker has run-variable delivery, so none injects them. Enable keeps the full name rule; disable and delete check only the name's shape, so a variable a later rule denies can still be removed.
- **The redact route serves plaintext only while it can still be needed (2026-11-22).** Open while the requested run is not terminal or a publication is in flight (an open custody hold, a capture preparing or uploading, a held publication prepared, invoked or of unknown outcome, a terminal preservation bound or publishing); a cross-check child only while it is not terminal and its check row is open before its deadline, or a publication is in flight. Otherwise 409 `run_env_redact_closed` and the worker withholds. The route's 404 carries `run_env_run_not_found`.
- **A variable identity is kept only while referenced (2026-11-22).** The sweeper deletes an identity once no row and no receipt references it, after which the id may be issued again; var_ids are random UUIDs.
- **Forms are computed once per claim and capped (2026-11-22).** `runEnvClaimForms` builds the redaction forms, scan needles and line forms once; `RUN_ENV_FORM_CHARS_MAX` (40,000,000 UTF-16 units of distinct forms) caps them. An over-budget claim fails before any work with a failure reason starting `run_env_forms_over_budget` (no value) and publishes nothing; lanes with no live flight (held, terminal, bundle publication) withhold with `forms_over_budget`. Over budget only the raw values (and their trimmed and LF variants) are registered for redaction, with no needles or line forms. Rejected: a partial set of encoded forms when over budget, because the encoded forms left out would go unmasked in streamed output. The cap no longer leaves a gap for full stores: see "Form budget is enforced at write time".
- **Line forms need substance (2026-11-22).** A line of a multi-line secret is registered alone (redaction and the patch line check, never a scan needle) only when it is at least 8 characters, has a letter or digit, has at least 2 distinct non-space characters, and is neither PEM armor nor a public line (`Proc-Type` lines; the service-account JSON members `type`, `auth_uri`, `token_uri`, `auth_provider_x509_cert_url`, `universe_domain`). This replaces "every line of 8 characters or more except PEM armor" (superseded by "Line forms need a qualifying token (2026-11-22)"). Superseded by "Every line of a multi-line secret is a line form (2026-11-22)".
- **Preserved patch is judged on rebuilt hunk images (2026-11-22).** The patch is withheld when the claim is over budget, a whole-value form occurs in the raw patch or in a rebuilt per-hunk pre- or post-image (also LF-normalized), a registered line form occurs, or the patch cannot be parsed (binary, combined diff, a line-count mismatch, or a stray line such as a non-header line between a file header and its first hunk); the image, line-form and parse checks apply when the run has any secret variable, retired versions included, so such a run loses its patch when the diff touches a binary file. Remaining gaps: a secret whose lines hold no qualifying token (single-case letters (with any `+=_-`) alone or with one digit, tokens shorter than 8 characters or with fewer than 5 distinct characters, a secret in a URL's host, formatted codes such as `8462-9137`, non-ASCII text, a secret that is the line's leading key), split across files or by elided context between hunks, and a value that appears only re-encoded. Rejected: withholding every mixed hunk, in favour of detection plus fail-closed parsing. Superseded by "The preserved patch is withheld for any multi-line secret (2026-11-22)": the split-across-files and elided-context gaps are closed and the rejection of withholding is reversed for runs holding a multi-line secret; the rebuilt-image and parse checks stay for runs whose secrets are all single-line.
- **`AWS_ENDPOINT_URL` is denied by exact name (2026-11-22).** `network_wiring`: the global override also routes Bedrock traffic; `AWS_ENDPOINT_URL_STS` and the other non-Bedrock per-service names stay allowed (superseded by the entry below). Names are checked on write only, so a stored variable whose name a later rule denies is dropped at injection by a worker that has the rule, with a run event naming the rule. Rejected: allowing it with a recorded invariant, for the same reason the `AWS_ENDPOINT_URL_BEDROCK` prefix is denied.
- **STS, SSO and SSO OIDC endpoint overrides are denied by exact name (2026-11-22).** `AWS_ENDPOINT_URL_STS`, `AWS_ENDPOINT_URL_SSO` and `AWS_ENDPOINT_URL_SSO_OIDC` are `network_wiring`. Owner decision: they override the endpoints of the AWS credential exchange (STS, IAM Identity Center and SSO OIDC) that the Bedrock harness's AWS SDK credential chain can use, so they are denied for consistency with `AWS_ENDPOINT_URL`. The other per-service names (for example `AWS_ENDPOINT_URL_S3`) stay allowed. Rejected: an `AWS_ENDPOINT_URL_` prefix, which would also deny S3 and other per-service names builds need.
- **Form budget is enforced at write time (2026-11-22).** A variable save is refused with 409 `env_forms_budget` when it would raise the repo's counted secret value bytes above 116,959 (`FormCharsMax` 40,000,000 divided by 342 form units per byte, a conservative analytic bound that counts the logger's JSON-escaped copy of every redaction form, control-character worst case, in `api/internal/runenv/form_budget.go`, shared with the agent through `fixtures/run-env/form-budget.json`). Counted: every secret row of the repo and the user scope in any state (live, disabled, pending deletion, retired); plain values do not. A save is refused only when it raises the count and leaves it above the cap, so a repo already above it can shrink but not grow; Delete, Disable and Enable are never refused for budget reasons. Disabling frees no budget; deleting a secret a run still holds frees it once the held version is released and the sweeper removes it. Rejected: sizing the cap to the store limits, which needs about 450M units.

- **Line forms need a qualifying token (2026-11-22).** A line of a multi-line secret (not PEM armor) is registered alone (redaction and the patch line check, never a scan needle) only when its value part holds a token. Tokens are maximal runs of `A-Z a-z 0-9 + = _ -` (`/` separates). - **Redaction is bounded by a step-counted work guard (2026-11-22).** Owner decision B3: fixed. A step counter, not a wall clock (a deadline cannot interrupt synchronous matching), charges each literal comparison in the matcher (`agent/src/redact.ts`): budget `REDACTION_WORK_BUDGET` = 2^26 units, bound budget + 1 + the longest literal per redacted string, one shared budget per payload walk (`redactPayloadWithin`).
