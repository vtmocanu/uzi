# PRD #1390: Api outage recovery: boot grace, heartbeat re-adoption, claim dedupe

- **Issue**: #1390
- **Priority**: High
- **Surfaces**: api (`api/internal/sweeper`, `api/internal/workersvc`, `api/internal/handler/worker_protocol.go`, one goose migration, the claim, heartbeat and stale-sweep queries in `api/internal/store/queries`), an additive change to the worker protocol on both ends (`agent/src/protocol.ts`, `agent/src/client.ts`, `agent/src/worker.ts`, `agent/src/runner.ts`), one e2e phase, docs. No web change: the board already renders every status this restores.
- **Guardrail**: nothing here touches `.github/workflows/**` (`.claude/rules/prds.md`). The e2e phase is exercised locally through `./e2e/run-e2e.sh`; the nightly `e2e.yml` picks it up without edits.
- **Landing order**: **after PRD #1247's M5 merges.** This PRD's fences read `runs.claim_released_at`, which #1247 adds (its migration `00230`); the run is dispatched only once that column is on `main`.
- **Scope**: the **run lane** (issue, ci_fix, self_improve, prompt, task, mr_rework, judge, review). The chat lane is out (D10): its claim query carries no generation, so it cannot join an exact-generation contract; it keeps the boot grace and today's behaviour otherwise, and is named as a follow-up.
- **Siblings, out of scope here**: #1391 (worker side of the same incident; shares the snapshot contract below) and #1392 (forge unreachable at clone). #1349 M8 (lead-owned hosted acceptance) stays with its owner; this PRD is what makes its "queued work resumes without database intervention" criterion true.

## Problem

On 2026-09-15 the api was unreachable for about 50 minutes while two issue runs kept executing on their hosted worker. Nothing on the worker had failed, yet the api's picture of those runs went wrong the moment it came back, and stayed wrong for hours:

1. **The boot sweep declared every worker dead.** `sweeper.Engine.Boot` runs a full `Sweep` immediately at api start; every worker's `last_heartbeat_at` was older than `WORKER_HEARTBEAT_STALE` (45 s) because the api had been gone, so `MarkStaleWorkersOffline` + `RequeueRunsOfStaleWorkers` flipped both live runs to `queued`, charged each a `requeue_count`, and kept `worker_id` for affinity. With `RUN_MAX_REQUEUES` defaulting to 1, that single outage consumed each run's whole re-queue budget: the next stale event fails them outright ("worker lost; exceeded re-queue budget").
2. **Nothing could put them back.** Ownership on every worker endpoint is `worker_id` only, and `SetRunRunning` / `SetRunCompleted` accept a `queued` row, so the still-executing attempt kept working and would have self-corrected at its next `running` state report. But a lead inside one long subagent turn sends no such report for hours; the board showed `queued`, the health detector read the silence as `stalled`, and three sessions spent the afternoon on a run that was alive.
3. **The same worker double-claimed its own live run.** `ClaimRun` returns a `queued` run to its affinity worker, and the worker's claim loop tracks in-flight promises, not run ids, so as soon as a slot freed it claimed the run it was already executing. `runner.execute` serialised the two attempts through `executionTails`, so attempt 2 sat parked holding a slot and a gen+1 custody hold; five minutes later `SweepClaimedNeverStarted` reset the row to `queued` again, inviting a third claim and a third hold. This is the hold accumulation #1349 describes, produced from a healthy worker.

The live fix was a hand-written `UPDATE runs SET status='running'`, which is exactly the database intervention #1349 M8 says an owner must never need.

## Solution

Three api-side changes on top of one shared worker snapshot.

**The snapshot.** The worker reports the run-lane attempts it is executing as `{snapshot_epoch, active: [{run_id, claim_generation, phase, terminal_pending}]}`. `snapshot_epoch` is a worker-process-monotonic counter incremented every time a snapshot is built, shared by the heartbeat and claim loops so the api can order snapshots captured independently; `phase` is the status the attempt is in from the worker's point of view (`running`, `awaiting_approval`, `awaiting_input`, `awaiting_followup`); `terminal_pending` is true while the attempt's outcome is journaled but not yet accepted by the api (#1391). The snapshot rides every heartbeat **and every run-lane claim request**, stamped with the `register_nonce` the api issued at register; the api stores the latest one per worker by **atomic full replacement**, discarding any snapshot whose nonce is not the current one or whose epoch is not greater than the stored one, and an invalid snapshot is ignored (the previous valid one stays), never treated as empty. Judge and review attempts are listed (they hold slots), always with phase `running`.

1. **Boot grace.** At api start the three stale-worker passes (`MarkStaleWorkersOffline`, `FailRunsOfStaleWorkersOverCap`, `RequeueRunsOfStaleWorkers`) are skipped until `SWEEPER_BOOT_GRACE` (default 60 s: the stale window plus one heartbeat interval; `0` means today's immediate behaviour) has elapsed since the listener became ready, not since the process started. Every other pass runs at boot as today.
2. **Re-adoption via heartbeat, to the exact phase, fenced.** On every heartbeat that carries a snapshot: a `queued` run owned by this worker whose listed generation equals `runs.claim_generation` and whose `claim_released_at IS NULL` is restored to its listed phase, the interval it spent `queued` banked into `budget_paused_seconds` when that phase is `awaiting_approval` or `awaiting_input`, its stale-requeue charge refunded only when the same generation was charged by the stale-worker requeue, and its custody hold untouched. A run-lane `running` run (`kind <> 'chat'`) owned by this worker, absent from the snapshot (or listed with another generation), not under a terminal-pending lease, with the current generation, `claim_released_at IS NULL`, and `status_since` older than the stale window plus one interval, is requeued through the existing requeue path. The stale-worker fail and requeue passes, and register's own orphan fail and requeue of the worker's previous runs, honour the same lease: a run under an unexpired terminal-pending lease for its current generation is neither failed nor requeued by any of them.
3. **Claim dedupe, global and pre-claim.** `ClaimRun` never returns a run whose current generation any **fresh** snapshot lists as active (freshness is the snapshot's own `reported_at`, not the worker's heartbeat), never one under a terminal-pending lease, and never one the claimant's own request snapshot lists; the check runs inside the claim transaction, which first locks the runs its own snapshot lists (so a sibling's concurrent `FOR UPDATE SKIP LOCKED` claim skips them), then replaces the snapshot, then selects a candidate, before the generation increments and before the `hold` CTE opens custody. The worker's claim loop keeps a run-id set as a loud assertion only.

### User journey

- **Owner, api outage of any length**: cards flicker to nothing and come back as they were, `running` or waiting at the plan gate, within one heartbeat of the api returning; no `stalled`, no requeue budget spent, no extra custody holds, no "Review held work" prompt for work that was never at risk.
- **Owner, worker really dies**: unchanged. Its runs requeue after the stale window; only the owning worker's own snapshot can prove an execution gone while that worker lives.
- **Owner, a live worker silently loses one execution**: the run is requeued within the stale window plus two intervals of the loss (worst case: the fence elapses just after a heartbeat) instead of at its wall-clock timeout.
- **Operator**: `uzi worker list` / `uzi admin workers` show what each worker says it is running and in which phase, so a split view is visible instead of inferred from pod logs.
- **Old worker image** (no snapshot): today's behaviour plus the boot grace. The hosted fleet gains re-adoption once the worker pin moves, which the release-time autobump does because `agent/src` changes.

## Resolved facts (baked in for an offline worker)

The e2e agent's claim loop polls every 500 ms; the e2e compose agent defaults to `max_concurrent_runs` 1 (`e2e/docker-compose.e2e.yml:246-256`).
2. **Boot path.** `api/cmd/server/main.go:655-726` builds the engine with six extra passes and calls `sweep.Boot(ctx)`; the engine and its ticker start **before** `ListenAndServe` (`main.go:740-748, 1157-1208`), so a process-start anchor ages while workers still cannot connect. `runOnce` runs the extra passes first, then `Service.Sweep` (`workersvc/sweep.go:20-129`): stale-workers-offline, claimed-never-started, running-timeout, completion-budget stamp, fail-over-cap, requeue, chat idle, proposals, promotions, detectors. Fail-over-cap runs before requeue (`sweep.go:83-103`) and reads the worker's staleness through an unlocked subquery (`runtime.sql:2804-2826`).
3. **What the stale sweep converts.** `RequeueRunsOfStaleWorkers` (`runtime.sql:2828-2853`) covers `claimed, running, awaiting_approval, awaiting_input, awaiting_followup`, has no kind exclusion, keeps `worker_id`, increments `requeue_count`, banks the park interval into `budget_paused_seconds` for the approval/input states, resets `status_since` and health. `SweepClaimedNeverStarted` (`runtime.sql:2512-2529`) also writes `queued` but does **not** increment `requeue_count`. So a `queued` row alone does not say whether it was charged, nor which state it came from. `SetRunRunning` on an already-running row preserves `status_since`.
4. **Held states keep their attempt alive**, and their content survives the requeue. A worker parked at a plan gate or a question keeps its `execute` promise live (`worker.ts:184-198`, `runner.ts:632-659`); the plan candidates, open question, completion question and follow-up identity columns are not touched by the requeue (its `SET` list is status, timing, health, budget and codex-cap columns only), so restoring the status is enough to restore the gate.
5. **Ownership and status guards.** `GetRunOwnedByWorker` is `id = @id AND worker_id = @worker_id` with no status predicate (`runtime.sql:617-619`); `SetRunRunning` admits `queued` and `claimed`; `SetRunCompleted` admits anything non-terminal. #1247 adds the fences this PRD must honour.
6. **#1247's fence.** On `origin/agent/issue-1247`: migration `00230` adds `runs.claim_released_at` (set by the credential-switch release, cleared only by `ClaimRun` while it increments `claim_generation`, `runtime.sql:878-888` there), and a row-locked state-write fence (`workersvc/service.go:2438-2501` there). Its PRD (line 91) requires every worker-driven write that touches a run row, heartbeat writes included, to carry `claim_generation` and be predicated on `claim_generation = @gen AND claim_released_at IS NULL`; its M5 adds `resume_phase` on the claim (PRD lines 88-94).
7. **Heartbeat and claim wire.** Heartbeat body `{version, stats?}` decoded by `httpx.DecodeJSON` with `DisallowUnknownFields` (`worker_protocol.go:319-353`, `httpx/respond.go:91-103`), so an unknown field is a 400. The register response is `{worker_id}` (`protocol.ts:334-339`); register is one-shot per worker process (`worker.ts:61-72`) and re-declares a fresh start (`workersvc/service.go:1490-1528`). The heartbeat loop and the claim loop are independent (`worker.ts:61-72, 155-169, 200-248`): a claim can be sent before the first post-outage heartbeat lands, and a delayed older heartbeat can arrive after a newer claim.
8. **Claim.** `ClaimRun`'s affinity clause admits `r.worker_id = @worker_id` unconditionally and falls open to any sibling at the affinity ceiling even with a live owner (`runtime.sql:665-877`); the statement increments `claim_generation` and its `hold` CTE opens a custody hold when the claimant is recovery-capable and the kind is one of the six publishing kinds (`runtime.sql:843-877`), judge never. `ClaimChatRun` (`chat.sql:71-104`) neither increments nor returns a generation and `ChatClaimResponse` carries none (`protocol.ts:1176-1194`). The worker's `claimLoop` keeps `Set<Promise>` (`worker.ts:200-241`); `runner.execute` serialises same-run claims through `executionTails` (`runner.ts:632-654`).
9. **Custody.** #1349 D3/D4 (`prds/1349-recovery-custody-hardening.md:85-119`): one hold per generation, minted at claim, settled by the worker at its graceful boundary; the stale-worker requeue mutates no hold.
10. **Ephemeral reap.** `ReapEphemeralWorkers` is busy-guarded (`hosted_workers.sql:193-234`); the boot grace does not need to gate it.
11. **e2e.** Phase registry in `e2e/run-e2e.sh:263-278`; compose services `forge-fake`, `web`, `db`, `api`, `agent`; phase 15 restarts the worker under a live run (lines 20-48), phase 34 restarts the api but not under a live run (lines 108-115); phase number 27 is taken (`27-mr-close-watcher.sh`). The stub executor already has hold-style sentinels (`executor.ts:1166-1169, 1247-1272`). A compose-driving phase needs a docker-tier worker when a uzi run executes it.
12. **Docs.** `docs/configuration.md:233` documents `RUN_MAX_REQUEUES=0` as "fail on the first stale event"; D9 changes that to two windows, so the sentence and its embedded mirror move with M5.

## Success criteria

- **SC1**: an api restart of any duration under live run-lane runs leaves every run in the status it had within one worker heartbeat of the api returning, `requeue_count` unchanged, park time correctly banked, no new custody hold (M1+M2, proven by M4 and M6).
- **SC2**: a live worker that silently loses an execution has that run requeued within the stale window plus two heartbeat intervals of the loss (fence plus one heartbeat), instead of at its wall-clock timeout (M2b).
- **SC3**: no worker ever holds two live attempts of one run and no sibling claims a run a fresh snapshot lists; `executionTails` never sees a second claim in any test or in M6 (M3).
- **SC4**: an old worker image (no snapshot) behaves exactly as today plus the boot grace; an old or rolled-back api never loses a heartbeat to the field (D7).
- **SC5**: a run released by #1247's credential switch is never revived by a stale worker's heartbeat; a `terminal_pending` attempt (#1391) is never requeued or re-claimed while its lease holds, and follows the ordinary stale path once it expires (D11).
- **SC6**: `task gate:api`, `task gate:agent`, `task check:migration-additive`, `task check-docs:web` green; the e2e phase green locally.

## Contract with #1391

The snapshot entry is the shared wire contract: `{run_id, claim_generation, phase, terminal_pending}` under a worker-monotonic `snapshot_epoch`. #1391 keeps an attempt listed with `terminal_pending: true` from the moment its outcome is journaled until the api accepts it; #1390 never requeues or re-claims such an entry while its server-side lease (`TERMINAL_PENDING_LEASE`, refreshed on every snapshot that still lists it) is unexpired, so `ClaimRun` never advances the generation under a pending replay and the replayed completion still matches #1247's fence. A worker that dies with a pending outcome has one lease of time for its boot drain to land it; after that the run is recoverable through the ordinary stale path. Pending entries do not hold worker slots; the worker lists at most `WORKER_OUTBOX_MAX_PENDING` of them and sets `pending_overflow` when it has more, which closes every run it owns to every claimant until it can list them all; #1391 replays the rest under that closure. Whichever PRD lands first adds the register `protocol_features` mechanism; the other adds its value.

## Decision Log

- **D1 — Boot grace is a listener-anchored delay, one knob, `0` is today.** One heartbeat window after the api can actually be reached covers the only case that matters (the api was gone, so every worker looks stale); anchoring at process start would let the grace expire while workers still cannot connect (fact 2). A worker that does not heartbeat within it is genuinely dead and is swept on the first post-grace tick. A live partition with the api up is the reconciliation's job (D2, D9), not the grace's.
- **D2 — Refund only with provenance.** `RUN_MAX_REQUEUES` exists to stop a run that keeps killing its worker from being re-run forever. A re-adopted run was never re-run, but `queued` alone does not say whether this transition was charged (fact 3). `stale_requeue_generation` records the generation the stale-worker requeue charged; the refund applies only when it equals the generation being restored; the restore and every claim clear it, so a legitimate earlier loss is never refunded.
- **D3 — The snapshot is a full-replacement table under a worker epoch, keyed by (worker, run), carrying generation, phase and lease, and it rides the claim request too.** `ClaimRun` must read it in SQL (D8) across all workers by run, an api restart must not forget it, operators should see it, and the claim can beat the first heartbeat (fact 7), so the claim request carries the same snapshot and the statement binds it. Full replacement is what removes ended attempts; the epoch is what stops a delayed older heartbeat from resurrecting them; freshness is the snapshot's own `reported_at`, since a worker whose snapshots fail validation must not keep stale rows protected by its liveness; an invalid snapshot is ignored rather than applied as empty, because an empty snapshot would drop every lease; the register nonce, persisted on the worker row, is what makes the epoch trustworthy across a worker restart and an api restart alike; and only entries for runs the authenticated worker owns are ever persisted or locked, so a buggy or compromised worker cannot suppress a sibling's claims.
- **D4 — Both directions are fenced on generation and `claim_released_at`; the missing path is fenced on `status_since` with margin.** Generation plus the unreleased fence is #1247's rule for every worker-driven write (fact 6); it also stops a stale generation from masking an absent newer one. The missing-run fence is the stale window plus one heartbeat interval, which is the 30 s HTTP timeout plus the 15 s cadence with margin; "within one heartbeat" is therefore the *re-adoption* promise, not the missing-run one (SC2).
- **D5 — Restore to the exact phase, bank the queued interval, never blanket `running`.** The stale sweep converts held states too (fact 3) and the worker keeps their attempts alive (fact 4). Restoring `running` would hide a gate the worker is still waiting on. The phase comes from the worker, which is the only party that knows it; the held-state content columns survive the requeue, so restoring the status is enough for the gate, and banking the queued interval keeps the wall-clock budget honest, as the requeue did for the park interval before it. This is the heartbeat-side twin of #1247's `resume_phase` (fact 6).
- **D6 — Re-adoption leaves custody alone; the missing path uses the existing requeue.** #1349 mints one hold per generation at claim and settles it at the worker's graceful boundary (fact 9); a re-adopted run has the same generation and the same live hold. A missing run is a hard loss and follows today's requeue exactly.
- **D7 — The snapshot is negotiated at register and degrades on a 400.** A heartbeat that 400s is a lost heartbeat, worse than the bug (fact 7). Register is one-shot per worker process, so an api rolled back under a running worker would 400 every heartbeat forever; the worker therefore retries a 400'd heartbeat once without the field and disables it until its next process start, which is also its next register.
- **D8 — Server-side, global, pre-claim dedupe is the mechanism; the worker set is an assertion.** A claimant-only check after the claim is too late: the claim has already advanced the generation and opened a hold (fact 8), and a sibling at the affinity ceiling is a different claimant. The exclusion must read every fresh snapshot and the request's own, inside the claim transaction, before either side effect, and the transaction must lock its own listed runs first, because a sibling's statement started before the replacement commits cannot see it.
- **D9 — Over-cap failure waits for a second stale window and serialises with the heartbeat.** With `RUN_MAX_REQUEUES = 1` a run that was requeued once and then hits a partition of 46 s would be terminated before any heartbeat could re-adopt it; terminal cannot be undone. Two consecutive windows before the over-cap fail (the requeue itself still fires after one) is the smallest change that leaves a live worker time to return, and the `FOR UPDATE` on the worker row closes the race where a heartbeat commits between the staleness read and the terminal write (fact 2). A worker that is really gone is failed 45 s later than today; `docs/configuration.md` moves with it (fact 12).
- **D10 — Chat is out, named as a follow-up.** The chat claim carries no generation and returns none (fact 8), so chat cannot join an exact-generation contract without first giving it one; doing that here would widen the PRD into the chat protocol. Chat keeps the boot grace and today's behaviour; a follow-up issue adds a generation to `ClaimChatRun`, returns it on the chat claim, and then admits chat to the snapshot.
- **D11 — `terminal_pending` is a server-side lease, not a liveness shadow.** #1391's guarantee is about an outcome that exists on the worker's disk, which outlives the worker's heartbeat; protecting it only while the heartbeat is fresh would let a dead worker's pending completion be overtaken by a re-claim and then rejected by #1247's fence when it finally replays. The lease (`TERMINAL_PENDING_LEASE`, default 1 h, refreshed by every snapshot that still lists the entry) bounds how long a run can be held by a worker that never comes back. Every path that could move the run out from under the pending replay honours it: the missing-run requeue, both stale-worker passes, register's orphan fail and requeue, the running-timeout sweep, the persist-failure auto-stop, the claimed-never-started reset, and the claim; register preserves the leased rows themselves. The lease expiry is the single backstop, so a worker that never returns still frees its runs.

## Risks

- **A worker that lists a run it is not really executing** (a stuck promise) is re-adopted and never requeued by absence. Mitigation: the running-timeout and completion-budget sweeps still apply, and the worker watchdog ends the attempt; the run cannot outlive its budget. #1391 owns the worker-side liveness of an attempt.
- **Snapshot write volume**: one replace per heartbeat per worker, bounded by the entry cap; the table is small (tens of rows), probed by `(run_id, claim_generation)`.
- **Fleet skew**: hosted workers stay on the pinned image until the release autobump; until then only M1 is live. Documented in M5; M6 verifies after the roll.
- **Landing after #1247** means this PRD's queries are written against the fenced `SetRunRunning` and the `claim_released_at` column as they exist on `main` then; the run must read them there, not from this document.
- **M4 needs a docker-tier worker**; the lead dispatches accordingly or runs the phase locally.
- **Chat lane** keeps today's requeue-and-wait behaviour until the follow-up lands (D10).
