# PRD #1184: Admin "All users" scope on the Judge page

**Issue:** [#1184](https://github.com/vtmocanu/uzi/issues/1184)
**Status:** Ready for planning; no implementation yet. **Held until PRD #1183 merges** (this PRD renders through the shared triage row #1183 introduces; sending both to uzi the same night collides on `web/src/pages/judge/GroupRow.tsx` and `Judge.tsx`).
**Execution:** Commit and push for later; the maintainer queues it for the `Planned` sweep after #1183 lands. Api + web + CLI + docs, one additive migration, no workflow files.
**Mock:** `prds/mockups/1183-triage-row-mock.html`, section 4 "Judge page, signed in as an admin" (markers 10 to 13). The mock is the accepted design for the scope switch, the attribution-hidden row, the category default and the "Done by an admin" chip.

Judge recommendations are the best signal for improving uzi itself, but the backlog is owner-scoped: `GET /me/judge/recommendations` never consults `IsAdmin` (`api/internal/handler/judge_recommendations.go:15-40`), so an admin can only read other users' recommendations one run at a time through the run page (owner-or-admin via `GetRunForViewer`, `api/internal/workersvc/service.go:3765`, reached from `GetReviewForTarget` at `judge_read.go:75`), with the owner's name on every one. This PRD adds an admin-only aggregate: every user's recommendations deduped by `(category, target)`, attribution hidden (no owner, no run id, title or link; a distinct-user count instead), instance-level categories on by default, plus two actions on the aggregate: file an issue from the newest occurrence, and mark a coordinate done across every user with a new `admin` provenance so each owner's row reads "Done by an admin". No Dismiss: dismissing someone else's recommendation is their judgment. The scope switch is remembered per browser; the nav badge stays the caller's own count.

Use current `main` and a new working branch, never write to `main`. Do not touch `.github/workflows/**`.

## Design

**Two questions with opposite answers, and why.** Decision 8 shows attribution when an admin files; this PRD hides it in the list. Filing publishes a user's worker text to a forge, so the reader must see whose text they are about to publish: the draft card keeps its provenance line. The aggregate is a triage view over patterns, where the person is noise and, on a small team, a temptation; it shows how widespread a recommendation is, never whose it is. Attribution is hidden at four layers (§379's template): the SQL projection omits `run_title`, `rr.id`, `rv.target_run_id`, `f.filed_issue_iid` and `f.filed_issue_url`; the Go grouper counts distinct `user_id`s and drops them; the admin DTOs have no field for any of them; a wire test asserts the tag set **and** a live-DB test seeds an owner email, a run title and a personal-namespace filed URL and asserts none of the three strings appears anywhere in the serialized admin response (the tag test cannot see a leak that rides a permitted field's value). The one deliberate exception is the draft card: the draft renderer (`review_issue_draft.go:115-132`) names the producing run, its repo and the requesting user by design (Decision 8), because filing publishes text. Rationale text can still name a repo or a file, so the docs say "aggregated across users", never "anonymous", and every user who opts into the judge is told an admin sees the aggregate.

**Routes (all new, all under `/api/admin/judge`, the owner handlers byte-identical).**

| route | group | purpose |
|---|---|---|
| `GET /admin/judge/recommendations?bucket=&category=` | read (`RequireUser` + `RequireAdminRO`, `routes_admin.go:31-33`) | the aggregate backlog; **no `?run`** (an anchor names a run) |
| `GET /admin/judge/stats`, `GET /admin/judge/category-stats` | read | the strip and the chip counts, all users |
| `GET /admin/judge/recommendations/issue-draft?category=&target=` | read | the #68 draft for the coordinate's **newest open occurrence** across users, with provenance |
| `POST /admin/judge/recommendations/issue` | write (`RequireAuth` + `RequireAdmin`, `forgeLimiter.PerUserMiddleware`) | files it through the existing `FileIssue` path (caller-owns-repo, sanitizer, `uzi` label) |
| `PUT /admin/judge/recommendations/disposition` | write | `{items: [{category, target}], status: "done"}` only; `dismissed` and `scope: all` are `400` |
| `DELETE /admin/judge/recommendations/disposition` | write | the admin Undo: same items, deletes only rows with `set_via = 'admin'` |

Reads are CLI-reachable with a `uza_` token; writes are cookie-only, by decision (§379's split). A separate route rather than `?all=1` on the owner route keeps `judge_recommendations.go:21`'s "IsAdmin is never consulted" true, and the four comments that lean on it.

**Queries (new, no user predicate anywhere; never a nullable `user_id` sentinel on the owner queries).** `ListJudgeRecommendationRowsAll` (the `:10` spine minus `:72` and minus the anchor block, projecting `rv.user_id` for counting, `rv.updated_at AS judged_at`, verdict, bucket inputs, `set_via`, filed columns; **not** `run_title`, `rec_id`, `run_id`), `ListJudgeTriageRowsAll` (the `:75` stats spine minus `:95`), `ListRecommendationsForCoordsAll` (the fan-out resolve minus `:121`, plus `rv.user_id`), `UpsertAdminDispositionsForResolvedCoords` (`status = 'done'`, `set_via = 'admin'`, `set_by_user_id = @admin_user_id`, `rationale_hash` stamped, **`ON CONFLICT DO NOTHING`** so a human verdict is never overwritten), `DeleteAdminDispositionsForCoords` (`WHERE set_via = 'admin'`), and `NewestOpenOccurrenceForCoord` (the first todo member of the coordinate under the backlog's full four-key order `rv.updated_at DESC, rv.created_at DESC, rv.id DESC, rr.created_at ASC, rr.id ASC` from `judge_recommendations.sql:110`, so a tie is deterministic). The draft and the file are two requests and each resolves independently: **the file resolves at file time**, and if a newer occurrence appeared between the two, the link lands on that one. Making them identical would need an occurrence id on the wire, which is the attribution this design hides; the draft's provenance line is therefore "whose text the draft was rendered from", and the docs say so. Migration draft `00203_admin_disposition_provenance.sql`: drop and re-add `recommendation_dispositions_set_via_check` as `IN ('issue_close', 'denied_cli', 'admin')`, following `00128`'s pattern and recording the same Down hazard. `set_by_user_id` is **set** to the admin (accountability in the row), unlike the two system values; the user-facing chip never names the admin.

## Success criteria

1. An admin can switch `/judge` to All users and see every user's recommendations grouped by coordinate with a user count, and the choice is remembered in that browser; a non-admin sees no switch and the owner endpoints behave exactly as before.
2. No response from the admin read or the admin disposition carries an owner, a run id, a run title, a review id, a recommendation id or a filed-issue iid or URL, asserted by a wire test on the tag set and a live-DB test on seeded values; the draft card is the one surface that names the producing run and user, by design.
3. An admin Mark done settles every owner's open member of the coordinate in one statement, never overwrites a human verdict, and each owner sees "Done by an admin" with a working Undo.
4. A `uza_` token can read the aggregate and structurally cannot write; a `uzc_` token gets `403` on the read.
5. The nav badge and the Mine tab count are unchanged under All users.

## Risks

- **The relaxed predicate leaks into the owner path** by a future refactor merging the two queries with a nullable `user_id`. Mitigation: separate queries with no user parameter at all, the ADR, and a test asserting the owner query's SQL text still contains `rv.user_id = @user_id`.
- **Rationale text identifies a person.** Not fixable at this layer; mitigated by wording ("aggregated across users") and the docs sentence users read when opting in.
- **Admin done on a recommendation the owner disagrees with.** The owner keeps Undo, and the chip says who set it.
- **Migration numbering**: draft `00203` collides with any parallel PRD; renumber on the landing rebase.
