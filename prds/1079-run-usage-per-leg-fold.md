## Problem

`run_usage` is the per-run token/cost ledger (PRD #40). Each delivered result frame's `modelUsage` is folded into a row keyed `(run_id, session_id, model)` and merged with `GREATEST` (`UpsertRunUsage`, `api/internal/store/queries/runtime.sql:2202-2229`); the `run_usage_totals` view (`00177_run_usage_totals_epoch.sql`) takes MAX per `(run_id, model, lineage_epoch)` then SUMs across epochs and models. Every rollup surface reads that view: `GetRunUsageTotal` (`runtime.sql:2240`), `ListRunsForUser` (`:475`), `SelfUsage` (`:2250`), `AdminUsageTotals` (`:2277`), `AdminUsagePerUser` (`:2306`), the judge join (`judge.sql:187`). The run page derives the same numbers client-side in `web/src/lib/runUsage.ts` (`deriveRunUsage`, `:557`) with a per-model running high-water mark and clamped deltas, which telescopes to the same MAX.

**Both folds assume the SDK result frame reports a CUMULATIVE total over the resumed session.** `runtime.sql:2204-2205` says so ("CUMULATIVE-across-resume (M1's Decision 3 verdict b)"), `00062_run_usage.sql:9-19` bakes it into the schema, `runUsage.ts:8-10` repeats it. ADR-632 recorded the assumption as **PROVISIONAL** and never validated (`adr/0632…:52`): *"Option B trusts that a non-dropped resume reseeds the CLI accumulator so those rows are one lineage (same epoch). Confirming this needs a live two-phase-across-requeue run…"*

**It is false.** The Agent SDK's own cost-tracking page states: *"When using sessions, the cost reported is limited to the individual query call rather than the entire session"* and *"Because the SDK does not maintain a session-level total, developers are responsible for manually accumulating these values."* (https://code.claude.com/docs/en/agent-sdk/cost-tracking — resolved locally on 2026-09-03 and restated here because a uzi worker has no open-web egress.) The worker starts one `query()` per turn (planning, then each implement iteration), each resumed on the previous session id, so **each result frame is one leg and reports only that leg**. All legs share `runs.session_id` (the worker reports it once per claim; `SetRunRunning` COALESCEs it), so they collapse into ONE `(run_id, session_id, model)` row and `GREATEST` keeps only the largest leg.

**Measured, live (2026-09-03).** Sum of `payload.total_cost_usd` over the `status`/`event:"result"` frames of each run, against the stored `usage.cost_usd`:

| run | legs | stored | true (sum of legs) | ratio |
|---|---|---|---|---|
| `02854d5e` #1064 | plan + 3 | $77.19 | $153.58 (6.33 / 44.12 / 75.03 / 28.10) | 2.0x |
| `d8648b31` #966 | 7 | $43.02 | $153.95 | 3.6x |
| `55977a4f` #1030 | 7 | $26.70 | $100.63 | 3.8x |
| `011433d0` #991 | 6 | $49.31 | $68.51 | 1.4x |

For `02854d5e` the stored value is max-per-model across frames **to the cent**: opus 75.029070 (leg 3) + haiku 0.010111 (leg 1) + sonnet 2.146358 (leg 4) = 77.185539; `output_tokens` 514572 = 488268 (leg-3 opus) + 26292 (leg-4 sonnet) + 12 (leg-1 haiku). No `resume_lineage_break` was emitted, so all frames sat in epoch 0. Two independent confirmations that frames are per-leg, not cumulative: **leg 4 is smaller than leg 3 in every column** (opus input 438 < 1285, output 158427 < 488268, cache_read 25620187 < 96109126, cache_creation 1285948 < 2223283, cost 25.955935 < 75.029070) while the lead's `context.used` kept growing across that same transition (165188 → 246422), and per-leg cost tracks per-leg tool-call volume (480 / 700 / 270 subagent tool calls against $44 / $75 / $28). Across the seven runs whose transcripts were read, `init` frames and `result` frames were 1:1 (4/4, 7/7, 6/6, 7/7, 7/7, 4/4, 6/6).

`00062_run_usage.sql:15-19` anticipated this exact outcome — *"if a live run ever firms the verdict as per-invocation deltas instead, the fold flips to plain latest-wins and rollups to SUM"* — but that hedge is incomplete: with a stable `session_id` the rows still collapse at the key before any rollup rule runs. The key has to carry the leg.

`run_usage` is advisory telemetry, not billing. The cost of the bug is every cost-based decision made on it: which runs are expensive, whether a model-routing change paid off, the `uzi admin usage` lifetime total (currently $6,327.74 across 932 runs, an under-count by an unknown factor).

## Solution

**A leg is one SDK process, and the persisted `init` frame marks it.** `mapResult`'s sibling in `agent/src/sdk-messages.ts:262-268` already persists the SDK's `system/init` message as a `status` frame with `payload.event = "init"` at the start of **every** `query()` call (resumed or not), and it precedes that call's result frame in seq order. So:

1. **Server (`api/`)** — a result frame's leg index is **derived from the run's persisted history at fold time**: `lineage_epoch = COUNT(init frames of this run with seq < frame.seq)`, read from `run_messages` after the batch's inserts have committed. It is a pure function of `(run_id, seq)`, so a re-delivered frame recomputes the same value and lands in the same row whatever else has happened since (D1). Add `lineage_epoch` to the `run_usage` primary key and to `UpsertRunUsage`'s conflict target; keep `GREATEST` within a key (re-delivery of the same frame stays idempotent; a multi-turn `query()` that emitted several cumulative result frames inside one process still MAX-collapses correctly). **Retire the counter**: `runs.lineage_epoch`, `BumpRunLineageEpoch` and the `resume_lineage_break` bump loop go away (D4); the #334 `resume_lineage_break` event stays persisted as a diagnostic. Leave the `run_usage_totals` view **unchanged**: `00177` already computes MAX within `(run_id, model, lineage_epoch)` then SUM across epochs and models, which is exactly the per-leg rule once every leg has its own epoch (D3).
2. **Client (`web/`)** — `deriveRunUsage` resets its per-model high-water marks at **every** `init` frame (outside the existing one-shot `model === null` latch at `runUsage.ts:618`), so each phase row reports its own leg's figures exactly (the documented "post-reset phase reads 0" price disappears) and the run total is the SUM of legs. Both folds count the same persisted `init` frames, so they agree by mechanism (D6), pinned by a shared fixture both halves read (ADR-195).
3. **Backfill** — every result frame of every still-existing run is still in `run_messages` (nothing prunes that table; the only deletion is the `runs` → `run_messages` `ON DELETE CASCADE` on repo removal, and a run without a `runs` row is never selected for refold), so a boot-time one-shot re-folds every **pre-migration** terminal non-chat run through the **same** fold function with its full `status`/`error` history, replacing the collapsed rows. An explicit `runs.usage_refolded` marker, **defaulting to `true` for rows created after the migration and set to `false` for every row that exists at migration time**, scopes it to history and makes it converge (D5).
4. **Record** — an ADR (ADR-1079, file adr/1079-run-usage-per-leg-fold.md once M4 creates it, numbered by this issue per the ADR convention) stating the per-leg invariant and marking ADR-632 superseded; docs, CHANGELOG, `specs/ai.md`. <!-- check-docs:ignore-path: adr/1079-run-usage-per-leg-fold.md is a forward reference created by this PRD's M4; remove this marker once the file exists -->

Nothing changes in `agent/` (the worker already emits everything needed) and nothing touches `.github/workflows/**`.

### The fold rule, stated once

For a run, after a batch's `run_messages` inserts have committed, for each delivered frame with `payload.event == "result"` and a non-empty `modelUsage`:

```
epoch(frame) = COUNT(*) FROM run_messages
               WHERE run_id = frame.run_id AND kind = 'status'
                 AND seq < frame.seq AND payload->>'event' = 'init'
for each model m in frame.modelUsage:
    upsert run_usage(run_id, session_id, m, epoch(frame)) with GREATEST per column
run total = SUM over (model, epoch) rows of MAX within the row   -- run_usage_totals, unchanged
```

`session_id` stays in the key (zero churn; it still splits rows for the cross-worker dropped-resume case ADR-632 documents, where a fresh process also emits a fresh `init`, so the two designs agree). A result frame with no `init` before it in the run's history (only conceivable for a pre-init-mapping worker; none of the seven read runs) lands in epoch 0 exactly as today. The same function serves the incremental path (one batch's frames) and the refold (the whole history), so there is one implementation, not two (D5).

## Decision Log

- **D1 — The leg index is position-absolute: a count of persisted `init` frames before the result frame, computed at fold time from `run_messages`.** The first draft kept ADR-632's mutable `runs.lineage_epoch` counter, bumped on each newly inserted `init`. The architect pass showed that breaks once the epoch is in the primary key: a re-delivered batch whose co-batched `init` is seq-deduped is stamped with the *current* counter and lands in a *different* row (worked on the fixture: replaying leg 2 after leg 4 raises opus@4 from $25.96 to $44.12). A pure function of `(run_id, seq)` recomputes the same value on every delivery, so idempotency holds by construction, the refold and the incremental path are the same computation, and the lost-bump failure class ADR-632 documents cannot exist. Cost: one indexed count per result frame (one per iteration).
- **D2 — The epoch goes into the primary key; `session_id` stays in it.** The row must split per leg because all legs share `runs.session_id`; adding the epoch to the existing PK is the smallest change (existing rows are trivially unique on the new key, no data rewrite; `run_id` stays leading so the rollup index survives). Dropping `session_id` would be churn and would remove the cross-worker split ADR-632 documents.
- **D3 — The view is not rewritten.** `00177` already does MAX within `(run_id, model, lineage_epoch)` then SUM across; once every leg has its own epoch that IS the per-leg rule.
- **D4 — The counter and both bump triggers are retired.** With D1 there is nothing to bump: `runs.lineage_epoch`, `BumpRunLineageEpoch` and the `resume_lineage_break` bump loop are deleted. The #334 event stays persisted as the dropped-resume diagnostic; a break is always followed by a fresh `init`, which D1 counts.
- **D5 — The backfill is a Go boot one-shot with an explicit marker that defaults to `true` for new rows, not a SQL data migration and not an admin verb.** The migration runner embeds SQL only, so a SQL rewrite of `run_usage` from `run_messages` would be a second implementation of the fold (jsonb parsing, quantization, truncation, clamps) that ADR-195's rule says must then be fixture-pinned against the first; reusing the fold keeps one implementation. Admin write verbs are web-only by convention. `usage_refolded DEFAULT true` plus a one-time `UPDATE … SET false` for existing rows makes the job a true one-off over history: a post-migration run is born refolded and is never touched by the ticker, so the incremental fold stays the only writer for live runs.
- **D6 — Client phases become exact per-leg figures, and parity holds because both folds count the same persisted `init` frames.** Resetting the marks at every `init` makes each phase row its own leg's numbers and removes the "post-reset phase reads 0" caveat. Within a leg the running-MAX delta identity is kept so the client and server agree on the multi-result-per-process shape too. The one shape where they could differ, a server epoch collision from a lost bump, no longer exists under D1.
- **D7 — Applied migrations are not edited.** `00062`'s and `00177`'s header comments state the old assumption and will read as stale; the correction lives in `00187`'s header, the rewritten query comments (sqlc-regenerated), ADR-1079 and the ADR-632 status line.
- **D8 — Migration number `00187` is a draft**, assigned at the landing rebase above the live head (`00186` belongs to #1064's open PR).
- **D9 — The new fixture's rollup is authored, the frames are recorded.** The 84b6a933 pair's "recorded, never authored" rule exists because a golden derived from an implementation locks in its blind spots. Here the shipped server's output IS the defect (77.185539), so it cannot be the golden; the frames are verbatim from the dev-cluster run and the expected rows come from an independent jq reduction (a third implementation, documented in the file's `note`). Both production folds must reproduce it.
- **D10 — Only terminal, pre-migration runs are refolded.** A pre-migration run still in flight at upgrade keeps its earlier frames collapsed in its epoch-0 row until it finishes and the ticker picks it up; a post-migration run is never refolded (D5).

## Risks

- **Refold on a large history.** 932 runs today; only `status`/`error` frames are loaded per run (a few dozen each). Batched with a log line per batch; a failure marks nothing and retries on the next tick/boot.
- **Multi-pod api.** Two replicas could both start the one-shot; the per-run transaction is idempotent and the marker makes the second pass a no-op.
- **A frame with no preceding `init`.** Lands in epoch 0 exactly as today. Only a pre-init-mapping worker could produce it; none of the seven read runs did.
- **An `init` frame that fails to insert** (an unstorable status message) would leave its leg counted with the previous one (an under-count for that run, never an over-count). The `init` payload is `{event, model}`, so this is theoretical; note it in the ADR.
- **Downgrade.** `Down` collapses rows to MAX per old key before restoring the old PK (M1 spells it out) and therefore restores the under-counted totals; goose down is rarely exercised, so the migration test that runs `Down` then `Up` must cover a run with several epochs.
- **The web bundle's phase table now shows real per-leg numbers** that no longer telescope to the old total; anyone comparing a run page screenshot from before the fix will see larger totals. That is the fix.

- Any worker (`agent/`) change, any CLI verb, any new DTO field.
