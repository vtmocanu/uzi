# PRD #747: Ephemeral workers should also burst on saturation, not just capability gaps

**Issue**: [#747](https://github.com/vtmocanu/uzi/issues/747)
**Status**: Draft
**Priority**: Medium
**Depends on**: PRD #529 (ephemeral auto-provisioner — shipped), PRD #422 (worker roll/drain semantics), PRD #216 (queued-run reason resolver)

## Problem

The ephemeral auto-provisioner shipped in PRD #529 spins a run-bound throwaway hosted worker only when a queued run needs a **capability no online worker has**. Its trigger query, `ListUnplaceableQueuedRunsForEphemeral` (`api/internal/store/queries/runtime.sql:2696-2760`), requires `cardinality(r.required_capabilities) > 0` (`:2744`) and a `NOT EXISTS` clause that checks **capabilities only** — it does not look at `max_concurrent_runs` or active-run counts (`:2745-2752`).

Consequence: a queued run that a worker *could* claim, but can't right now because every capability-matching online worker is already at its `max_concurrent_runs` cap, is considered **placeable** and is excluded from the trigger. It just waits — for as long as the fleet stays saturated. Nothing escalates capacity. The system only surfaces this as a display reason ("fleet saturated") via `CountOnlineWorkersWithFreeSlotForUser` (`runtime.sql:2643-2663`); it does not act on it.

Observed live (2026-08-28, hosted fleet on meta-dev-02): a user with 2 base workers, each `max_concurrent_runs=2` (4 slots), all 4 occupied, with a 5th run sitting `queued`. No worker spun up. This is working as designed today — but on the hosted k8s path (the primary runtime per the repo's conventions) elastic burst under load is exactly what hosted capacity is for.

## Solution overview

Add a **sibling trigger path** for saturation. Provision a run-bound ephemeral worker for a queued run that is:

1. capability-**placeable** (some online, non-draining, non-ephemeral worker's effective caps satisfy it), AND
2. slot-**blocked** (every such capable worker is at its `max_concurrent_runs` cap — i.e. `CountOnlineWorkersWithFreeSlot-among-capable-workers = 0`), AND
3. has been queued **longer than a debounce interval** (so transient claim-cycle queueing doesn't provision, and we don't pay pod cold-start when a running slot would free sooner).

Everything else is reused from PRD #529: the 1:1 `ephemeral_run_id` bind, the per-user cap (`UZI_EPHEMERAL_MAX_PER_USER`, default 2), the instance kill-switch (`ephemeral_workers_enabled`) + per-user opt-in (`users.ephemeral_workers_enabled`), the advisory-locked `provisionOne`, and the `ReapPass` idle-reaper (`ProvisionDeadline`, `UZI_EPHEMERAL_PROVISION_DEADLINE`, default 10m).

### Why a debounce, and why it equals cold-start (design rationale, resolved)

A **capability gap** is permanent: nothing in the fleet can ever serve the run, so PRD #529 provisions immediately — waiting is pointless. **Saturation is transient**: a running slot frees when any of the busy runs settles. So the two paths must behave differently:

- Provisioning on *raw* saturation would spawn a pod for every run that queues for even one claim cycle under load — saturation is the *normal* state of a busy fleet, so this would churn constantly.
- An ephemeral worker is **not free or instant**: it provisions a PVC, pulls the image, and bare-clones the repo (these are heavy workers — DinD, 20Gi PVC). If a running slot frees in ~90s but a fresh worker takes ~2min to be claim-ready, bursting spends money to go *slower*.

Therefore the saturation path gates on **"queued longer than roughly the worker cold-start time"** — a new knob `UZI_EPHEMERAL_SATURATION_DELAY` (Go `time.Duration`, default **90s**), threaded as a query `interval` param (not read off a private provisioner clock). Below the interval the run waits; a freeing slot claims it and no pod is provisioned. Past the interval, the backlog is real and bursting is worth it. **The 90s default ships as-is + env-overridable; empirically validating it against meta-dev-02 worker-pod boot logs is a maintainer follow-up** — an offline worker in a clean clone has no access to prod pod logs, so that step must not block M2. Note `parseDuration` rejects 0 (`config.go`, `d > 0` guard), so `UZI_EPHEMERAL_SATURATION_DELAY=0` in prod silently falls back to 90s (a safety, not a bug — prevents accidental churn); tests set 0 via the `EphemeralConfig` struct, never env.

### Reaping (partly handled — the timing is the open question, not the mechanism)

The `EphemeralConfig.ProvisionDeadline` **field** doc (`api/internal/hostedsvc/ephemeral.go:42-48`) describes reaping orphan shape **(c) idle-stolen**: "online past the deadline but its bound run is being served by a sibling", and the mechanism is already shipped and tested — `store/ephemeral_reap_livedb_test.go`'s `(c) idle-stolen` subtest proves exactly the saturation race (a base worker claims the bound run, `ReapEphemeralWorkers` GCs the now-idle ephemeral; SQL at `hosted_workers.sql:171-176`).

**But the shared deadline is 10m, and the saturation race resolves in seconds**, so a burst worker whose run is stolen by a freed base slot holds a fully-provisioned, paid pod (DinD, 20Gi PVC, image pull, bare-clone) idle for **up to 10m** before GC. The mechanism is right; the *grace* may be wrong for this path. So this is **not** verify-only — see M3, which owns the decision (keep the 10m grace and accept the waste, or add a shorter idle-grace on the idle-stolen arm). A shorter grace collides head-on with the deliberate note at `ephemeral.go:46-47` ("There is deliberately no separate idle-grace knob: one deadline keeps the config surface to the approved set"), so it is a conscious tradeoff to make, not a bug to fix silently.

## Scope / non-goals

- **In scope**: the api-side trigger query, provisioner wiring, one config knob, reaper verification, tests, docs.
- **Out of scope**: any change to `.github/workflows/**` (the uzi worker PAT lacks `workflow` scope — a workflow-file touch in the branch diff is an atomic push rejection that loses the whole branch; see `.claude/rules/prds.md`). This feature needs no CI-workflow change; if one is later wanted (e.g. a new job), it is a **separate maintainer/local-only issue**, kept out of both this PRD's implementation and its validation.
- **Out of scope**: controller changes. The controller already materializes a Deployment (replicas 1) + PVCs + Secret from any desired-worker row (`controller/internal/kube/materializer.go` `reconcileWorker`), with **zero** `ephemeral` branching, so a new ephemeral row from the saturation path materializes exactly as PRD #529's rows do — no controller change.
- **Out of scope**: raising `hosted_worker_quota` or `WORKER_MAX_CONCURRENT_RUNS` — those are the steady-state-capacity alternatives, deliberately not this feature (this is spiky-load burst).

## Key design decisions (resolve during implementation)

1. **Separate query vs. extend the existing one.** Recommendation: **add a new sibling query** `ListSaturationQueuedRunsForEphemeral` rather than adding an `OR` branch to `ListUnplaceableQueuedRunsForEphemeral`. The existing query's predicates and its ~40-line explanatory comment are precise and load-bearing; the debounce and the "capable-but-full" predicate apply only to the saturation path. Keeping them separate leaves the capability-gap path byte-untouched and lets `ProvisionPass` union the two result sets (dedup by run id — a run cannot be both, but guard anyway).

2. **Runs with zero required capabilities.** The saturation path must handle a **plain** run (`cardinality(r.required_capabilities) = 0`) — the observed case is a bare issue run. So the new query must *not* carry the `cardinality > 0` guard; "capable worker exists" for a zero-cap run means simply "an online non-draining non-ephemeral worker exists".

3. **The "capable but full" predicate.** Reuse the effective-caps fold (`fn_effective_worker_caps` / the inline `capabilities || docker` expression at `runtime.sql:2751`) to find capability-matching workers, then require that **none** of them has a free slot, using the same free-slot definition as `CountOnlineWorkersWithFreeSlotForUser` (`runtime.sql:2659-2663`: `max_concurrent_runs IS NULL OR active_run_count < max_concurrent_runs`, active = status in claimed/running/awaiting_approval/awaiting_input/awaiting_followup, kind <> 'chat'). A capable worker with a NULL cap has unbounded room → the run is not slot-blocked → excluded (correct: a NULL-cap worker will claim it).

4. **Debounce column: `runs.status_since`.** Gate on time-in-queued using **`runs.status_since`** (migration `00163_run_status_since.sql`), which is stamped only by statements that assign `status` and is set to `now()` by **every** requeue path (`RequeueRunsOfStaleWorkers`, `RequeueWorkerRuns`, `RequeueClaimedRunToQueued`, and the roll path — all in `runtime.sql`). This is strictly better than `created_at` (unchanged on requeue → a run requeued after a roll would falsely read as "long-queued") and than `updated_at` (drifts on unrelated writes, per `00163`'s own header). It is already the queued-age clock the health path uses (`workersvc/health.go:243`, `olderThan(now, r.StatusSince, th.queued)`), so this path and the display path share one notion of "how long queued".

5. **Opt-in surface: reuse vs. new sub-toggle.** Recommendation for the smallest correct surface: **reuse** the existing `ephemeral_workers_enabled` instance kill-switch + `users.ephemeral_workers_enabled` per-user opt-in (no migration). Note the cost tradeoff in the decision log: a user who opted into capability-gap ephemeral also gets saturation burst. If the team wants them independently controllable, that is a **follow-up** (a new column + migration + web toggle, mirroring PRD #649's UI), not this PRD — flagged so it is a conscious choice, not an accident.

6. **Per-user cap composition.** The saturation path shares the same `UZI_EPHEMERAL_MAX_PER_USER` cap and the same authoritative advisory-locked `CountEphemeralHostedWorkersForUser` check in `provisionOne`. So base quota (default 2) + ephemeral cap (default 2) = a user can burst to at most 4 concurrent workers. Confirm this composition is intended; do not add a second cap.

7. **Relation to the health-threshold display gating.** The "fleet saturated" *display reason* (`reasonAllWorkersBusy`) fires only when `health_enabled = true` **and** the run is past the *queued health threshold* (`workersvc/health.go:243`). The new trigger gates on its own `UZI_EPHEMERAL_SATURATION_DELAY`, **independent of `health_enabled` and the health threshold** — so a burst can happen with health disabled (no UI reason shown), and if `SaturationDelay ≠ queued threshold` the UI can say "saturated" with no burst yet, or burst with no UI reason. This is acceptable (burst is a capacity action, not a UI state), but must be **stated**: the burst path is intentionally independent of `health_enabled`, and both clocks read `status_since` so they measure the same "how long queued" even when their thresholds differ. Document the intended relation; do not couple burst to `health_enabled`.

8. **Union dedup before the batch LIMIT.** `ProvisionPass` must combine the capability-gap and saturation candidate sets, **dedup by run id, then apply the `ephemeralProvisionBatch` (50/tick) LIMIT** — so the combined set cannot bypass the per-tick bound. A run cannot legitimately be in both sets, but guard anyway.

## Success criteria

1. Under a saturated, capability-matching fleet with an opted-in user, a run queued past `UZI_EPHEMERAL_SATURATION_DELAY` provisions exactly one run-bound ephemeral worker, and that worker claims and serves the run.
2. A run queued *under* the debounce interval, or with any capable worker holding a free slot, provisions **nothing** — verified by a live-DB test, not by inspection.
3. The capability-gap path (PRD #529) is byte-for-byte unchanged and its tests still pass.
4. A burst worker whose bound run is claimed by a freed base worker is reaped, not left idle.
5. Per-user and instance gating fully control the new path; the per-user ephemeral cap bounds it; no path over-provisions past the advisory-locked authoritative cap.
6. `task gate:api` green; no `.github/workflows/**` changes in the branch diff.

## Risks & mitigations

- **Cost / churn** if the debounce is too short → routine pod provisioning. *Mitigation*: default 90s ≈ cold-start; the debounce is the whole point of the rationale above; env-overridable, with `parseDuration`'s `>0` guard falling 0 back to 90s so it can't be accidentally disabled.
- **Up-to-10m wasted pod per lost race.** The debounce lowers the *probability* of the base-worker-steals-the-run race but does not remove it, and the shared reaper grace is 10m while a base slot frees in seconds — so a lost-race burst pod (DinD, 20Gi PVC, image pull, bare-clone) can sit fully provisioned and idle for up to 10m before GC. *Mitigation*: M3 owns the keep-10m-vs-shorter-grace decision; whichever is chosen, the cost is stated, not silent.
- **Requeued-run debounce error** if `created_at` were used for a run requeued after a roll. *Mitigation*: Decision 4 — use `status_since`, which every requeue path re-stamps.
- **Thundering herd across users** under broad saturation. *Mitigation*: bounded by `ephemeralProvisionBatch` (50/tick) + per-user `UZI_EPHEMERAL_MAX_PER_USER` + the advisory-locked authoritative `CountEphemeralHostedWorkersForUser` cap; M2's union must dedup-by-run-id **then** apply the 50/tick LIMIT (Decision 8) so the combined set cannot bypass the per-tick bound.
- **Debounce vs. health-threshold display divergence** — the "fleet saturated" UI reason is gated on `health_enabled` + the queued health threshold, while burst is gated on `SaturationDelay` alone. *Mitigation*: Decision 7 — accepted as intentional (burst is a capacity action, not a UI state); both clocks read `status_since`; documented in M6.
- **Interaction with fleet-aware claim deferral** (`ClaimRun` peer-deferral, `runtime.sql:652-660`) — an ephemeral worker is run-bound (a valid deferral target only for its own run), so it does not participate in peer spread; confirm the bound worker claims its own run without being deferred to a (full) peer.
- **Offline-worker constraint**: this PRD is fully internal-codebase; no open-web dependency. A uzi worker can clone the repo and verify every anchor, schema column, and query locally. The one step needing prod access — empirically tuning the 90s default against meta-dev-02 boot logs — is a **maintainer follow-up**, not a milestone (see the Solution rationale); it does not block M2. Migration numbers (if a follow-up adds a column) are assigned at merge time (`.claude/rules/go.md`).
