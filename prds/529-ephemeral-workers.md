# PRD #529: Auto-provision ephemeral workers on unmet capability

**Status**: Planned (queued for the `Planned` uzi sweep)
**Priority**: Medium (the issue is explicitly "not near-term"; see Risks)
**Depends on / relates to**: PRD #84 (capability-aware scheduling — closed, designed the gate to support this as a mode), PRD #58 (hosted k8s workers — closed, shipped *static* provisioning only and left spawn-on-demand + teardown as explicit non-goals), PRD #422 (worker roll/drain), issue #79 (ephemeral-worker cost / nix-store GC — the cost tradeoff, resolved in-body below), issue #91 / [ADR-91](../adr/0091-runner-cross-run-persistence-residual.md) (the runner cross-run/cross-repo executable-persistence residual this feature structurally closes — a run-bound worker has its own fresh `-nix`/`-data` PVCs, so there is no shared `/nix` or provisioning HOME to plant into).

## Problem

When a run needs a capability no online worker has (today the vocabulary is `{docker, jvm}` — `api/internal/capability/capability.go`), PRD #84 blocks it and offers a remediation spectrum (Decision 9): **(a)** switch to an eligible worker you already have, **(b)** provision a *persistent* hosted worker (shipped, PRD #58), **(c)** auto-provision an *ephemeral* worker for just this run, then tear it down (deferred — this PRD).

Only (a) and (b) exist. So a user whose run needs `docker` (or `jvm`) must keep a persistent capable worker running, paying for idle capacity between the rare runs that need it. Option (c) removes that: the capable worker appears exactly when a run needs it and disappears when the run finishes.

**Scope note on size:** the trigger is **capability-unmet only** for v1 (a run whose `required_capabilities` no online worker satisfies). Size-based unplaceability ("the plan is too big for any online worker") is **not** a v1 trigger — the detector `CountOnlineWorkersSatisfyingCaps` (`runtime.sql:2522-2536`) tests capabilities only, and `runs.size_class` is not populated until *after* a plan runs (see below). Size-aware provisioning rides with Path 2 and is deferred.

## What already exists (verified against the tree 2026-08-22)

This feature is **almost entirely api-side**. A two-agent codebase survey plus a two-reviewer critique found the controller needs **zero changes**, and every provisioning primitive already exists.

**Controller is a pure desired-state reconciler (no change needed to create or tear down):**
- The `workers` table IS the desired-state store; a hosted worker is a `workers` row with `kind='hosted'` (migration `api/internal/store/migrations/00066_hosted_workers.sql:24-26`, constraint `ck_workers_hosted_metadata:34-37`). There is **no** separate "desired worker" table.
- The controller polls the full fleet every 10s (`GET /api/controller/poll` → `PollResponse{Workers []DesiredWorker}`, `api/internal/hostedsvc/protocol.go:40-95`), sourced by `ListHostedWorkersForController` (`api/internal/store/queries/hosted_workers.sql:6-45`) = every `kind='hosted'` row. It selects **named** columns, so adding `ephemeral*` columns does not perturb the wire DTO.
- Presence in the poll ⇒ the controller creates Deployment + PVCs + Secret (`controller/internal/kube/materializer.go:484-652`). **Absence** of a previously-stamped worker ⇒ `teardown` deletes the Deployment + Secret + all PVCs (`controller/internal/kube/materializer.go:709-725`, Pass 3 at `:466-479`). So **dropping a `workers` row is the entire teardown primitive** — no ownerRef, no TTL, no controller code to add. Token/secret cleanup is automatic: `hosted_worker_tokens.worker_id` is `ON DELETE CASCADE` (`00066:89`) and the Secret is deleted by name (`materializer.go:716`).
- `Busy` (holds ≥1 non-terminal run) is already computed api-side in `ListHostedWorkersForController` (`hosted_workers.sql:31-33`, predicate `status NOT IN ('completed','failed','cancelled')`) and surfaced on `DesiredWorker.Busy`.

**⚠️ Teardown is UNCONDITIONAL — Pass-3 has no busy guard.** The cordon/drain safety lives only in the Pass-2 drift/roll path (`materializer.go:606-629`); `teardown` itself does an unconditional `Deployments().Delete` (`:709-725`). So "safe reap" is entirely the api's responsibility: the api must not drop an ephemeral row while its pod still holds a non-terminal run, or the pod is SIGTERMed mid-flight (spurious interruption + requeue + a second cold-start). This drives Decisions 2 and 4.

**Provisioning primitives already exist:**
- `CreateHostedWorker` (`hosted_workers.sql:78-98`) is **deliberately UNGUARDED** — "the quota decision belongs to the caller" (its own comment) — so an internal auto-provisioner can call it under a different quota policy. Paired with `hostedsvc.SealJoinToken` in one transaction (`api/internal/handler/hosted_workers.go:219-283` is the persistent-path template to mirror, including its `pg_advisory_xact_lock` at `:232`).
- Capability → template mapping is a code constant: `templateCaps` (`capability.go:75`, `{"base":{}, "jvm":{jvm}}`); `docker` maps to the `docker_enabled` / `DesiredWorker.Docker` dimension, not a template. `capability.Unmet(...)` (pure, offline) computes the exact unmet set.
- The run's **capability** need is available pre-claim: `runs.required_capabilities text[]` (migration `00142:8`) is copied from the repo hint at enqueue (`CreateRun`, `runtime.sql:373-374`). **The size need is NOT available pre-claim:** `runs.size_class` (migration `00145:14-19`) is the plan-time, worker-reported bucket, written only on the `awaiting_approval` report — so at the Path-1 trigger (an unplaceable run that has never been claimed or planned) it is the empty-string default. v1 therefore provisions at a **default size** (Decision 3); `size_class` is not a usable input on this path. (There is no `runs` column named `n`; that is a Go local for a worker *count*.)

**The trigger condition already exists:** the pre-claim "no online worker can satisfy this" detector `queuedReason` (`api/internal/workersvc/health.go:504-536`) calls `CountOnlineWorkersSatisfyingCaps` (`runtime.sql:2522-2536`, same effective-caps fold as `fn_worker_can_claim`, excludes draining workers) and returns `reasonNoEligibleWorker` when the count is 0 **and** `len(RequiredCapabilities) > 0` (`health.go:526`). Today it produces a *display reason*; this PRD turns the same condition into an *action*.

**The gaps this PRD fills:** no `ephemeral` marker or owning-run FK on `workers`; no auto-provision loop; a **claim restriction** so an ephemeral worker only runs the run it was made for; a **busy-guarded** run-completion → teardown; concurrency-safe cap + one-per-run; and orphan/failure GC.

## Solution overview

A background control loop in the api finds **unplaceable queued runs** (0 online workers satisfy their capabilities, `required_capabilities` non-empty) belonging to users who opted into ephemeral auto-provisioning, and, under a concurrency-safe per-user cap, provisions **one run-bound ephemeral hosted worker** per such run. The worker boots, registers, and — restricted by construction — claims **only** its bound run, executes, and on the run's terminal transition the api **deletes the worker row once the pod is idle** (busy-guarded). The controller reaps the pod with no controller change. An orphan/failure reaper is the correctness backstop for every teardown the primary path misses.

**Scope decision — pre-claim trigger only (Path 1).** PRD #84 Decision 9 defines two dispatch paths. This PRD implements **Path 1** (pre-claim: a queued run nothing online can satisfy). **Path 2** (a run that planned on a capable-to-plan worker and hit the approve-time capability `409` from `capabilityGate`, `service.go:5099-5111`) requires the *automatic requeue-to-a-capable-worker* machinery that PRD #84 M4 **explicitly deferred**, and is where `size_class` first becomes known — so both size-aware provisioning and the Path-2 trigger are follow-ons, noted in Risks, not in this scope.

**Flag-off, opt-in, capped — by design** (see the cost tradeoff under Risks). Nothing auto-spawns unless a user turns it on, and never more than a small cap of concurrent ephemeral workers per user.

## Design decisions

1. **The `workers` row is the desired-state unit; ephemerality is two columns on it, not a new table.** `ephemeral bool NOT NULL DEFAULT false` + `ephemeral_run_id uuid REFERENCES runs(id) ON DELETE SET NULL` (nullable; the run this worker exists to serve — `SET NULL` so a future hard-delete of a run can never be blocked by this FK). This keeps the controller's poll/reconcile/teardown untouched — an ephemeral worker is an ordinary hosted row the api creates and deletes on its own schedule.

2. **Teardown is "drop the row", triggered by the owning run reaching terminal AND busy-guarded.** Because Pass-3 teardown is unconditional (see the ⚠️ above), the api deletes the ephemeral row only when the run is terminal **and** `CountWorkerNonTerminalRuns(worker) = 0` (`runtime.sql:286-295`) — the *same* guard the persistent `DeleteWorkerForUser` path uses (`runtime.sql:283-295`), genuinely reused rather than substituted with a weaker single-run check. With Decision 4 the worker can only ever hold its bound run, so this guard is defense-in-depth; it exists so no logic slip can SIGTERM a running pod.

3. **Resolve `{template, docker}` from the run's stored capabilities; size is the default preset for v1.** `template` from `capability.Unmet` ∩ template-derived caps (`jvm` → `jvm`, else `base`); `docker` = `docker ∈ required_capabilities`; `size` = a configured **default (`m`, matching the preset default)** because `size_class` is empty on the pre-claim path (see above). A pure `resolveEphemeralSpec(run) → (template string, docker bool)` function, unit-tested with no DB. Size-from-`size_class` is deferred to Path 2, where it is populated.

4. **An ephemeral worker claims ONLY its bound run — this replaces affinity steering, which is vacuous here.** `ClaimRun` (`runtime.sql:536-648`) and `fn_worker_can_claim` (migration `00142:34-51`) gain a clause: a worker with `ephemeral = true` may claim a run only when `r.id = worker.ephemeral_run_id`. This is the correctness fix for the mid-run-kill hazard — the worker can never take foreign work, so it never holds a non-owning run when its bound run terminates. Soft affinity (`worker_id` + `updated_at` bump) is **rejected** as the steering mechanism: an ephemeral worker cannot claim anything until it has cold-started (PVC bind + ~2.6GiB seed-nix copy + boot + register, minutes), which far outlasts `WorkerAffinityGrace`, so the affinity window never overlaps the worker's online life — and bumping `updated_at` would also un-bypass the fleet-spread clause (`runtime.sql:603-605`). The bound run is **not** hard-pinned to the ephemeral worker: a genuinely-eligible sibling that appears during cold-start may claim it first, leaving the ephemeral worker idle for the reaper (Decision 6, cost-only, self-correcting).

5. **A dedicated background loop, flagged off, capped per user, concurrency-safe.** A new pass (wired beside `hostedsvc.ExpirePendingTokens` at `api/cmd/server/main.go:540`) selects unplaceable queued runs and provisions one worker each, when the feature is enabled for that user and the user is under the concurrent-ephemeral cap. Concurrency safety is **not** left to READ COMMITTED (the TOCTOU `CountHostedWorkersForUser:51-68` documents): a partial **`UNIQUE (ephemeral_run_id) WHERE ephemeral`** index makes double-provision-per-run impossible regardless of api replica count (precedent: `uq_runs_one_active_per_issue`, `00020:63`), and a per-user `pg_advisory_xact_lock` around the cap check closes the cap TOCTOU (precedent: `provisionHostedWorker:232`). The whole provision — lock → cap check → `CreateHostedWorker` (ephemeral, run-bound) → `SealJoinToken` — is one transaction mirroring the persistent path.

6. **Orphan / provision-failure GC is the correctness backstop, and it DELETES the row.** A reaper pass (same loop) deletes an ephemeral worker (row → controller reaps) when: **(a)** its `ephemeral_run_id` run is terminal or absent — this is the comprehensive periodic sweep that backstops M4 (whose named terminal-writers are an incomplete set; the full terminal set includes `MarkRunFailedByID`/`FailRunAutoStop`/`RejectRunServerSide`/`SweepRunningTimeout`, `runtime.sql:1445-1446`); **(b)** it never reached `status='online'` within a provision deadline; **(c)** it has sat idle with no owned non-terminal run past a short grace (the sibling-stole-the-run case from Decision 4). The reaper DELETEs — the pending-token-expiry query (`ExpirePendingHostedWorkerTokens`, `hosted_workers.sql:177-206`) only NULLs a token and deliberately leaves the row alive, so it is the *deadline-knob analogy*, not the reaper itself.

7. **Cost is accepted, documented, and defended by the flag-off default — not solved here (issue #79).** Every ephemeral worker pays a fixed, **size-independent** cold-start: a flat 20Gi `-nix` PVC plus a `-data` PVC (5/10/20Gi by size) provisioned and bound, a `seed-nix` init container copying the baked ~2.6GiB nix closure into the PVC (`render.go:898-922`), then pod boot + register before the run can claim. **Each ephemeral worker's PVCs are its own** (named by worker id, `render.go:558-565`), so nothing is shared across runs — the isolation property [ADR-91](../adr/0091-runner-cross-run-persistence-residual.md) and M8 rely on. Whether ephemeral-per-run beats a small warm pool is a genuine product tradeoff, not a fact to look up; v1 resolves it by shipping **off by default, opt-in, capped**, and defers the warm-pool alternative to an issue-#79 follow-on. The cost facts above are all in-repo/measured, so the PRD stays internet-independent.

## Technical design

### 1. Schema + model (M1)
- Migration: `workers.ephemeral bool NOT NULL DEFAULT false`, `workers.ephemeral_run_id uuid REFERENCES runs(id) ON DELETE SET NULL`, and a partial **`UNIQUE (ephemeral_run_id) WHERE ephemeral`** index. `sqlc generate` locally; regenerate `hosted_workers.sql.go` / `models.go`.
- `resolveEphemeralSpec(run) → (template string, docker bool, err)` in `api/internal/capability` (or a small new file), pure, unit-tested (`go test`), reusing `capability.Unmet` + `templateCaps`. Size is the configured default, not derived here.

### 2. Auto-provisioner + trigger loop (M2)
- New store query: unplaceable queued runs = queued runs whose owner opted in, with non-empty `required_capabilities` no online worker satisfies (`CountOnlineWorkersSatisfyingCaps == 0`), and **no** existing ephemeral worker (enforced by the unique index, checked for skip). Live-DB tested.
- `CreateEphemeralHostedWorker`: a `CreateHostedWorker` variant setting `ephemeral=true`, `ephemeral_run_id`, and the resolved template/size/docker, run inside a tx with `SealJoinToken` and a per-user `pg_advisory_xact_lock` for the cap — mirroring `provisionHostedWorker` (`hosted_workers.go:219-283`) but with the **concurrent-ephemeral cap** in place of the standing per-user quota.
- Loop wired at `cmd/server/main.go` beside `ExpirePendingTokens`.

### 3. Ephemeral claim restriction (M3)
- Extend `ClaimRun` / `fn_worker_can_claim` (migration + `runtime.sql`) with the Decision-4 clause: an `ephemeral` worker matches only `r.id = worker.ephemeral_run_id`. Regenerate sqlc. Live-DB tested: an ephemeral docker worker offered two eligible docker runs claims only its bound one.

### 4. Busy-guarded teardown (M4)
- On the common terminal writers, if the run has a bound ephemeral worker AND `CountWorkerNonTerminalRuns(worker) = 0`, delete that `workers` row (a new idempotent `DeleteEphemeralWorkerForRun`). The controller reaps within one poll. M5(a) is the backstop for terminal writers not on this list.

### 5. Orphan / failure GC (M5)
- Reaper pass (same loop) implementing Decision 6 (a)/(b)/(c), each a DELETE. Reuse the token-expiry *deadline* value for the never-booted case; the reaper itself deletes the row.

### 6. Config + chart + surfacing (M6, M7)
- Per-user opt-in following the `judge_enabled`/`judge_model` precedent (admin default + per-user override, `api/internal/settings/settings.go:66,76,174-176`) — **not** the global `KeyCapabilityAwareScheduling` (`settings.go:111`, which is app-wide). Plus `UZI_EPHEMERAL_MAX_PER_USER` (cap), `UZI_EPHEMERAL_PROVISION_DEADLINE`, and the default size. Rendered in `deploy/chart/templates/api-deployment.yaml` / `values.yaml` (api-side; **no controller change, no `.github/workflows` touch**).
- CLI parity (`api/cmd/uzi`): `uzi worker list` marks ephemeral workers; the queued-run reason surfaces "auto-provisioning a worker". Docs: `specs/ai.md`, `ARCHITECTURE.md` (worker section), a user-facing scheduling doc.

## Risks & open questions

- **Is ephemeral worth it vs. a warm pool? (issue #79, unresolved by design.)** The cold-start cost (Decision 7) is real and size-independent. v1 ships off-by-default/opt-in/capped and defers the warm-pool comparison. **Recommendation:** M1–M8 deliver the *mechanism*; gate any default-on rollout on real cold-start timings measured after landing. Honest consequence: with the flag off, v1 may see little production use until #79 measures cold-start.
- **Path 2 (approve-time `409`) and size-aware provisioning are out of scope.** Both need PRD #84's deferred auto-requeue machinery, and Path 2 is where `size_class` is first known. Filed as a follow-on. Path 1 (pre-claim, capability-unmet) is the common case.
- **Single-replica concurrency dependency, now closed at the schema level.** The advisory lock + partial UNIQUE index (Decision 5) make provisioning correct regardless of `api.replicaCount` — but note the wider codebase still assumes `replicaCount: 1` (`values.yaml`, double-sweep caveat); this PRD does not rely on that assumption for its own correctness, and should not silently reintroduce a dependency on it.
- **The bound run is not hard-pinned.** A genuinely-eligible sibling that appears during cold-start may claim the run first; the now-idle ephemeral worker is reaped by M5(c). Cost-only, self-correcting, disclosed. Hard pinning is deliberately not added.
- **Provision latency is inherent** (provision → PVC bind → seed-nix copy → boot → register → claim). The queued run waits, surfaced via its existing health reason; no new status. The provision deadline (M5b) bounds a stuck provision.
- **Cap vs. the standing per-user quota.** Ephemeral workers are counted by a *separate* concurrent-ephemeral cap, not the persistent `CountHostedWorkersForUser` quota, so an opted-in user is not blocked by a full standing quota. Confirm this policy at review.

Neither implementation nor validation may create or edit a workflow file (the worker PAT lacks `workflow` scope; a single touch loses the whole branch). The controller module needs no change at all.

- **2026-08-22 (authoring).** Two-agent codebase survey established that teardown needs **zero controller changes** (dropping a `workers` row is the whole primitive, `materializer.go:709-725`) and that every provisioning primitive already exists. Scoped to **Path 1 (pre-claim)** because Path 2 needs PRD #84's deferred auto-requeue. Chose **two columns on `workers`** over a new table to keep the controller untouched. Resolved issue #79's cost question **in-body** as flag-off/opt-in/capped with the warm-pool alternative deferred.
- **2026-08-22 (two-reviewer critique, folded in).** Corrected five load-bearing flaws found against the code: (1) `size_class` is empty pre-claim (populated only post-plan), so v1 provisions at a **default size** and size-aware provisioning is deferred to Path 2 — the trigger is capability-unmet only. (2) Pass-3 teardown is **unconditional** (no busy guard), and an ephemeral worker was not bound to a single run, so teardown could SIGTERM a mid-run pod — fixed by an **ephemeral claim restriction** (worker claims only its bound run) plus a **busy-guarded** delete reusing `CountWorkerNonTerminalRuns`. (3) Soft affinity gives no real steering (cold-start outlasts `WorkerAffinityGrace`) and was **replaced** by the claim restriction. (4) The provision path had a **TOCTOU** on both the per-run one-shot and the cap — closed with a partial **UNIQUE index** and a per-user **advisory lock**. (5) The orphan reaper is the **correctness backstop** and DELETEs the row; `ExpirePendingHostedWorkerTokens` only NULLs a token and was mis-cited as the reaper. Also: `ephemeral_run_id ON DELETE SET NULL`; per-user opt-in follows the `judge_enabled` precedent, not the global `KeyCapabilityAwareScheduling`.
- **2026-08-22 (ADR-91 linkage, from @uzi-d2).** Issue #91's runner cross-run/cross-repo executable-persistence residual is recorded in [ADR-91](../adr/0091-runner-cross-run-persistence-residual.md) and structurally closed by this feature: a run-bound ephemeral worker has its own fresh `-nix`/`-data` PVCs (Decision 7), so there is no shared `/nix` or provisioning HOME to plant into. M8 verifies the property and closes #91. Caveat carried from the ADR: an issue-#79 shared-nix-store optimization would partially reopen the `/nix` half and must re-check the residual.
