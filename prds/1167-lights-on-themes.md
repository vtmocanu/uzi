# PRD #1167: Lights on — light themes, system-follow appearance mode, typeface setting

**Issue:** [#1167](https://github.com/vtmocanu/uzi/issues/1167)
**Status:** Implemented (all milestones landed); in review as PR #1203.
**Execution:** Queued for the nightly `Planned` sweep (auto-approve on, MR rework on). Web + api + docs, no workflow files.
**Mock:** `prds/mockups/1167-lights-on-themes-mock.html` (open locally; keys `1`/`2`/`3` switch proposal, `O`/`B`/`R`/`S`/`C` switch screen, `T` toggles the typeface, `N` the notes drawer). The mock is the accepted design for the three light themes, the Appearance settings card and the "Lights on / Lights off" vocabulary.

uzi is a dark factory and ships dark-only: Ember and Mission control. Daytime and bright-room use has no light option, and the appearance picker is one explicit theme id with no way to follow the operating system or to hold a preferred theme per polarity. This PRD adds three light themes that each keep the dark factory somewhere on screen, gives every theme a polarity, replaces the single picker with a mode (System / Lights on / Lights off) plus one theme per polarity and admin instance defaults, and adds a per-user typeface setting (System or IBM Plex, bundled, no external font fetch).

Use current `main` and a new working branch, never write to `main`. Do not touch `.github/workflows/**`.

## The three light themes

All three share one light token set (verified below) and differ only in **where the dark goes**. The dark values are today's ember values, so a machine surface looks exactly as it does now.

| id | name | where the dark goes | mechanism |
|---|---|---|---|
| `dawn` | Dawn | Console surfaces only: activity feed, code blocks, tool output, CLI token boxes. Sidebar and all chrome light. | the `console` scope (M3) |
| `hall` | Hall | Dawn, plus the sidebar (and the mobile top bar) stays the ember dark frame pixel for pixel: brand tile, active item, badges, rate-limit meters. | the `frame` scope on AppShell's sidebar (M4) |
| `shadow` | Shadow | Dawn, plus dark travels with live machine work: a board card, an in-flight row and the run header whose run is `claimed` or `running`. Anything waiting on a human (`awaiting_approval`, review requested) gets a rust left rail and tint. Everything at rest is light. | `data-live` / `data-attention` attributes on IssueCard, run rows and the RunView header (M4) |

Hall is the recommended instance default for the light slot. Shadow is the boldest; its mixed polarity is capped to the two machine-working statuses, and `awaiting_approval` is deliberately light so the human's decision surface never sits inside a dark card.

`index.css` stores every colour as a space-separated channel triple, never hex (`web/src/index.css:23-27`; `tailwind.config.js:6` wraps them as `rgb(var(--x) / <alpha-value>)`), so a pasted `--bg: #F2F4F7` is an invalid declaration and a silently unstyled theme. The contrast oracle parses the triple form and resolves `var()` aliases (`--ring: var(--brand)`, the `--syn-*` and `--queue-*` slots). The 10% pill tint and 40% border pattern (`bg-warn/10 border-warn/40 text-warn`) ships unchanged: every status tone is ≥ 4.5:1 as text on its own tint. Ember's bright orange `#FB923C` is 2.0:1 on white and cannot be text or a UI edge on light ground, which is why the brand splits: rust on light surfaces, ember inside dark scopes (8.3:1 on the live ember surface `#0F121A`).

**Why one token cannot serve both the page and the code panes on light.** Today `bg-ink` is both the body ground (`web/src/index.css:170`, `web/src/pages/Board.tsx:1099`) and the surface of thirteen opaque code/log/console sites (`web/src/index.css:295` `.docs-prose pre`; `web/src/components/RunEvent.tsx:289` and `:677` `NEUTRAL_BODY`; `AgentTemplateEditor.tsx:306`, `:431`; `CliTokens.tsx:155`; `WorkerUpgradeBadge.tsx:419` (note box); `web/src/pages/AgentDetail.tsx:333`; `WorkersSettings.tsx:959`; `Skills.tsx:463`; `adminSettings/UpdatesSettingsCard.tsx:249`; `adminSettings/AgentSourceSettingsCard.tsx:171`), plus one **progress-bar track** at `WorkerUpgradeBadge.tsx:438` that is not a console at all: on light it would become the page ground and vanish against a white card, so it is a plain token fix to `bg-raised`. Under dark, "darker than the card" is right for all of them. Under light the page wants to be lighter than the card and a code pane wants to stay dark. The fix is a **scope, not a token rename**: a `console` class that remaps the palette variables (`--bg`, `--surface`, `--raised`, `--edge`, `--edge-strong`, `--fg`, `--muted`, `--faint`, `--brand`, `--brand-hover`, `--on-brand`, the four status tones, `--plan`, `--ring`) to the dark set and sets `color-scheme: dark`, so every nested `bg-ink` / `text-muted` / `border-edge` utility keeps working unchanged. On ember and mission the console scope maps to the theme's own values (a visual no-op). **The run transcript is a console too:** the `ActivityFeed` root scroll container takes the `console` class so the whole live activity pane (prose events included) is dark on light themes, as in the mock; the chat transcript (`ChatMessages`) is a human conversation and stays light, with only its tool/code blocks scoped. The `bg-ink/40`, `/50`, `/60` overlay washes (`ScheduleModal.tsx:1115`, `:1140`, `:1258`; `ActivityFeed.tsx:930`, `:1037`; `AdminBlockedRepos.tsx:263`; `Repos.tsx:1785`; `runView/JudgePanel.tsx:1043`; `ChatMessages.tsx:61`; `judge/LabelFilter.tsx:89`) read as much shallower insets on light (ground to card is about 8 of 255 per channel, so `bg-ink/60` is nearly invisible): M3's mock-mode check decides per site whether a wash switches to `bg-raised`; inside a `console` scope they are unaffected. `RunEvent.test.tsx:736` asserts the literal `"border-edge bg-ink"` and will need the `console` class appended.

**Syntax tokens.** `--syn-*` and `--tool-rail` alias palette tokens (`index.css:71-77`). Inside the console scope they resolve to the dark palette automatically; the light theme blocks must still define them (a theme block is a complete set).

## Data model and wire contract

- **Registry gains polarity.** `theme.Theme{ID, Label, Polarity}` with `Polarity ∈ {light, dark}`; `ember`, `mission` dark; `dawn`, `hall`, `shadow` light. `Validate(id)` stays; add `ValidateFor(polarity, id)` and `Polarity(id)`. Web mirror: `THEMES` becomes a typed list with `polarity`, `THEME_LABELS` stays, plus `LIGHT_THEMES` / `DARK_THEMES` derived, and `POLARITIES`.
- **Mode vocabulary.** Wire and storage values are `system`, `light`, `dark`. UI labels are **System**, **Lights on**, **Lights off**; the picker headings are **Lights on theme** and **Lights off theme**. Polarity stays `light`/`dark` in code and docs.
- **Per-user state (migration draft `00198_user_appearance.sql`, additive):** `users.appearance_mode text NULL`, `users.light_theme text NULL`, `users.dark_theme text NULL`, `users.typeface text NULL`; NULL means "use the instance default". Backfill in the same migration: `UPDATE users SET dark_theme = theme, appearance_mode = 'dark' WHERE theme IS NOT NULL` so nobody's screen changes on upgrade (an explicit override today is a dark theme; the only way to keep it winning is to pin the mode to dark). `users.theme` stays in place and is no longer read; dropping it is a later migration (the `lineage_epoch` precedent, #1087).
- **Instance defaults (app_settings keys, no migration):** `default_appearance_mode` (compiled fallback **`dark`**, not `system`: a user who never picked a theme has `users.theme = NULL`, gets no backfill, and would otherwise paint `hall` on a light OS the morning after the upgrade), `default_light_theme` (fallback `hall`), `default_dark_theme` (fallback: the legacy `default_theme` value if set, else `ember`), `default_typeface` (fallback `system`). `default_theme` keeps validating and keeps feeding the dark slot so an admin who never touches the new keys sees no change. System mode is therefore opt-in: per user in Settings, or instance-wide when the admin sets `default_appearance_mode = system`.
- **Resolution (Go `theme.ResolveAppearance`, mirrored in `web/src/lib/theme.ts`):** each of mode, light, dark, typeface resolves independently: valid user value, else valid instance value, else the compiled fallback. Server output: `appearance: {mode, light_theme, dark_theme, typeface}` plus the sources for the Settings UI (`overrides` with the raw nullable user values, `defaults` with the instance values). The polarity actually painted is decided on the client: `mode = system` reads `matchMedia("(prefers-color-scheme: dark)")`, otherwise the mode is the polarity; `data-theme` = the slot for that polarity, `data-font` = the typeface.
- **Session `me()` keeps `theme`, `theme_override`, `default_theme` for one release** (decode fidelity for the CLI, `apitypes/user_settings.go:15`): `theme` = the dark slot when mode is `dark` or `system`, the light slot when `light`; `default_theme` = the resolved instance dark default. Mark them deprecated in the DTO comments.
- **`PUT /api/me/settings`** accepts `appearance_mode`, `light_theme`, `dark_theme`, `typeface` as tri-state `json.RawMessage` fields (absent / null / value, the existing `theme` pattern at `handler/user_settings.go:103`). Validation: mode ∈ {system, light, dark}; `light_theme` must be a light theme, `dark_theme` a dark theme, else `400` naming the field and the offending id; typeface ∈ {system, plex}. The legacy `theme` field stays accepted and maps to the slot of its polarity **and** sets `appearance_mode` to that polarity, so an old client keeps its old behaviour.
- **`PUT /admin/settings`** accepts the four default keys with the same validation; polarity mismatch is a `400`. No `changed`-driven resync, as today.
- **Pre-paint cache** `uzi.appearance` (JSON `{mode, light, dark, typeface}`) replaces `uzi.theme`; `theme-preinit.js` parses it defensively, validates ids against a literal polarity map, evaluates the media query for `system`, and stamps `data-theme` and `data-font` before first paint. A stale `uzi.theme` value is read once as a dark slot and then ignored. **With no cache at all** (first visit, cleared storage) the script no longer leaves `data-theme` unset (which renders ember): it reads the media query and stamps the compiled fallback for that polarity (`hall` when the OS is light, `ember` when dark), so a system-mode user never sees a wrong-polarity flash; the session response corrects the exact theme once `me()` resolves.
- **Live switching.** With `mode = system`, `applyAppearance` subscribes to the media query's `change` event and restamps; the subscription is torn down when the mode changes. Explicit modes ignore the OS.
- **Typeface.** `html[data-font="plex"]` swaps `--font-sans` / `--font-mono`. The `--font-*` tokens move **out** of the theme blocks into a typeface layer (`:root { system stack }` then `:root[data-font="plex"] { Plex stack }` placed after every theme block), so typeface and theme are orthogonal and no theme block can silently override the choice. Mission's extra `"Liberation Mono"` fallback moves into the shared mono stack.
- **CLI.** `PUT /api/me/settings` is cookie-only (`RequireAuth`), so the CLI cannot write appearance today and this PRD does not open that route. The CLI decodes the new fields (fidelity only) and `uzi me settings --json`, if such a read exists by then, prints them; no new write command. Recorded in the decision log.

## Success criteria

1. A user can pick System / Lights on / Lights off, one light theme and one dark theme, and a typeface; the choice applies immediately, survives reload without a flash, and follows the OS when System is chosen.
2. Nobody's screen changes on upgrade: an existing user with an explicit `theme` override sees exactly what they saw before (backfilled dark slot, mode `dark`); a user with no override on an instance whose admin set only `default_theme` still gets that dark theme, because the compiled mode fallback is `dark`; System mode applies only where a user or the admin chose it.
3. Every text token on every theme clears WCAG 2.2 AA on every surface it is used on, enforced by a test, not a review.
4. Machine output (logs, code, commands, the run transcript) is dark on every theme; on Hall the `frame` scope resolves to ember's token triples (asserted by test); on Shadow only `claimed`/`running` surfaces are dark and `awaiting_approval` is light with a rust rail.
5. No external font request ever; no CSP change; users on System download no font files.
6. Ember and mission render unchanged: their token blocks match the checked-in snapshot apart from the `--font-*` lines.

## Risks

- **Mixed polarity on Shadow** can read as noise on a dense board. Mitigated by the status cap, identical card geometry, and no glow; if a review finds it still noisy, Shadow ships behind the same picker but is not an instance default.
- **Five literal id lists** drift. The contrast oracle covers CSS; a Go test iterating the registry against the web `THEMES` file (read from disk, as `TestEmbeddedDocsMatchSource` reads `docs/`) covers the two registries; the pre-paint script's polarity map is covered by its jsdom test.
- **Font layer ordering**: a theme block defined after the typeface layer would win. The typeface layer is last in `index.css` and a parse-level test asserts that ordering (M6).
- **Migration numbering**: draft `00198` collides with any parallel PRD; renumber on the landing rebase (strict goose, no `allow-missing`).
