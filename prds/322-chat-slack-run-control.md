# PRD #322: Cancel and steer runs from Chat and Slack

**Issue**: [#322](https://gitlab.example.com/vtmocanu/uzi/-/issues/322)
**Priority**: Medium (a run-control gap, not a broken run: both chat surfaces can start a run but neither can stop or steer one)
**Status**: Planned
**Anchor**: all code references below are against `main` @ `e438b44d`.
**Offline-ready**: this PRD is self-contained for a restricted-egress worker (e.g. the `Night-Shift` sweep). Every contract cited is an in-repo `file:line`; the only third-party surface touched is `github.com/slack-go/slack v0.27.0` (`api/go.mod:21`), already in the module cache. No open-web lookup is required to implement any milestone.

## Problem

The two "chat" surfaces — the in-app **Chat with uzi** page and the **Slack** integration — can *start* a run on an issue, but only through a human-gated card: the chat agent's `start_run` tool emits a `run_request` card, and the user's click performs the write (`agent/src/uzi-tools.ts:164-190`; web `web/src/components/RunRequestCard.tsx`; Slack `api/internal/slacksvc/chatactions.go:274-287`). There is **no equivalent for cancelling a live run and no equivalent for steering one** (sending a follow-up instruction to a run that is mid-flight). A user who notices a run going the wrong way from chat or Slack has to leave the surface and go to the web run view (`web/src/pages/RunView.tsx`) or the CLI (`uzi run cancel` / `uzi run follow-up`) to intervene.

Both interventions already exist server-side and are owner-only; they are simply not wired to the chat surfaces:

- **Cancel** and **follow-up** are two `kind`s of the single generic steering endpoint `POST /api/runs/{id}/inputs` → `Handler.CreateRunInput` (`api/internal/handler/workers.go:998`) → `workersvc.SubmitInput` (`api/internal/workersvc/service.go:4207`). The accepted-kind whitelist `runInputKinds = {follow_up, approve_plan, reject_plan, cancel, revise_plan, answer}` lives in the handler at `api/internal/handler/workers.go:101-105` (checked at `:1014`), mirroring the DB CHECK.
- The web run view already drives both: cancel via `submit("cancel")` (`RunView.tsx:702,832,1111`) and steer via `SteerQueueCard` → `submit("follow_up", text)` (`RunView.tsx:904-911`). The CLI already drives both: `uzi run cancel <id>` (`api/cmd/uzi/run.go:466-477`) and `uzi run follow-up <id> -m <msg>` (`run.go:479-496`).

So the gap is exactly the chat-surface wiring, on both web-chat and Slack.

## Current state (what exists, what is missing)

**Chat agent toolset is five read/propose tools, none of which can cancel or steer** (`agent/src/uzi-tools.ts:41-53`): `list_runs`, `get_run`, `get_run_messages`, `propose_issue`, `start_run`. `start_run` is the only run-affecting one and it is human-gated (emits a card; the comment at `:165-170` states it "does NOT start anything"). `docs/chat.md:26-49` enumerates the toolset and the guardrail.

**In-app Chat card pipeline** (the template to mirror):
- Agent emits `{ kind: "run_request", payload: { repo_path, issue_iid, title } }` (`uzi-tools.ts:181-184`), no server round-trip.
- Web renders the discriminated union in `web/src/components/ChatMessages.tsx` (`text` `:121-131`, `proposal` `:133-142`, `run_request` `:144-153`); `RunRequestCard.tsx` calls `api.startRunFromChat(...)` (`web/src/lib/api.ts:2890-2894`) → `POST /chats/run-requests`.
- Server handler `StartChatRun` (`api/internal/handler/chat.go:191-216`) re-validates the **untrusted** card value server-side (`:202-209`) and calls `h.wsvc.StartRunForUserByPath(...)` (`:210`); route mounted at `handler.go:1176`.

**Slack card pipeline** (the second template to mirror):
- Frame dispatch: `chatpost.go` routes emitted frames by kind (allowlist `:66`, `run_request` → `postRunRequestCard` `:156-158,229-247`).
- Card builder `runRequestCardBlocks` (`chatactions.go:536-567`) with a Start button (`ActionChatRunStart`, `:554`), a confirm dialog (`:557-562`), and Dismiss.
- Action router `HandleBlockAction` (`chatactions.go:136-198`) dispatches `slack_chat_run_start` → `startRun` → `svc.StartRunFromCard` (`:274-287`); the card value is untrusted and re-resolved against the presser's own repos (`:510-534`). Interface method + adapter in `api/cmd/server/main.go:1017-1023`.
- Slack **does** already capture free-text thread replies for other intents (request-changes, answer, chat follow-up) via `api/internal/slacksvc/replier.go` and `question.go` — this is the offline-safe mechanism to reuse for steer text (see Solution). Slack has **no** modal / `view_submission` machinery today (verified: no `ModalViewRequest`/`OpenView`/`view_submission` under `api/internal/slacksvc/`).

**What is missing, precisely:**
1. No chat agent tool proposes a cancel or a steer (the toolset is the five above).
2. No `cancel_request` / `steer_request` card kind on either surface.
3. No `POST /chats/cancel-requests` / `POST /chats/steer-requests` confirm handler.
4. No Slack cancel button, no Slack steer capture, and no `slacksvc` seam calling `SubmitInput` with `cancel`/`follow_up` for an issue run. (The existing `slack_chat_end` button cancels the **chat conversation's own** run via `EndChat` → `SubmitInput(...,"cancel",...)` `api/internal/workersvc/chat.go:346-353`; it does not target an issue run.)
5. **CLI: nothing missing** — `uzi run cancel` / `uzi run follow-up` (`run.go:466-496`) and the TUI steer bar (`tui_steer.go`) already cover both, through the same `SubmitInput` path. This satisfies the repo convention "new uzi functionality ⇒ check whether `api/cmd/uzi/` needs a matching CLI change" (root `CLAUDE.md`) with a no-op-plus-confirmation, recorded in M6.

## Solution (Decision)

**Add two human-gated card tools to the chat agent — `cancel_run` and `steer_run` — and render/confirm them on both surfaces, each funnelling to the existing owner-only `SubmitInput` endpoint** (`cancel` and `follow_up` respectively). The chat agent may only *propose* the action as a card; the human's click (web) or button-press + confirm (Slack) performs the write. This preserves the primary guardrail exactly as `start_run` does today: a run's activity feed (read via `get_run_messages`, which surfaces agent output derived from untrusted repo/issue content) can contain an injected "cancel run X" or "tell run X to …" instruction, and the agent must be structurally unable to act on it without a human click.

Concretely, mirroring the `start_run` pipeline end to end:

**Cancel** (`kind: "cancel"`, no free text):
- Agent tool `cancel_run(run_id: string)` → emits `{ kind: "cancel_request", payload: { run_id } }`, no write. The tool may call the existing `get_run` read first to put the target's issue title / status in the card copy, but performs no mutation.
- Web: `cancel_request` union branch in `ChatMessages.tsx` → new `CancelRequestCard.tsx` (mirror `RunRequestCard.tsx`, single danger button + confirm) → `api.cancelRunFromChat(runId)` → `POST /chats/cancel-requests`.
- Server: `CancelChatRun` handler (mirror `StartChatRun` `chat.go:191-216`), body `{ run_id }`, validate non-empty, call `h.wsvc.SubmitInput(r.Context(), user.ID, runID, "cancel", "", nil)`. Route at `handler.go:1176` neighbourhood.
- Slack: `ActionChatRunCancel = "slack_chat_run_cancel"`, a `cancelRequestCardBlocks` builder (mirror `runRequestCardBlocks` `:536-567`, danger button + confirm dialog), frame kind `"cancel_request"` in the `chatpost.go` allowlist (`:66`) and dispatch (`:156`), router branch in `HandleBlockAction`, and a new `svc.CancelRunFromCard(ctx, userID, runID)` seam + adapter in `main.go` that calls `SubmitInput(...,"cancel",...)`.

**Steer / follow-up** (`kind: "follow_up"`, carries free text):
- Agent tool `steer_run(run_id: string, message: string)` → emits `{ kind: "steer_request", payload: { run_id, message } }`, no write.
- Web: `steer_request` branch → new `SteerRequestCard.tsx` with an **editable** textarea prefilled with the agent's proposed `message` (the human confirms/edits the actual instruction before it is sent) → `api.steerRunFromChat(runId, message)` → `POST /chats/steer-requests` → `SubmitInput(...,"follow_up", message)`.
- Slack: `ActionChatRunSteer = "slack_chat_run_steer"` button posts a prompt; the user's **in-thread reply** carries the steer text. **No Slack modal** — `view_submission` handling does not exist in `slacksvc` and introducing it is out of scope. Note this is **not** a straight reuse of `replier.go`: that path resolves the target run from the thread anchor and intercepts chat-thread replies as chat turns, so cross-run steer-from-chat needs a new pending-steer registry and a new interception branch (fully specified in M4, which is the highest-risk milestone and independently deferrable). The Slack-cancel path (M2) has no such complication — it is a pure button carrying the untrusted `run_id` in the card value, like `start_run`.

**Target-kind guard for steer:** `SubmitInput` rejects `follow_up` on a **chat** run with `ErrChatInputNotAllowed` → 409 (guard at `service.go:4221-4222`; error defined `api/internal/workersvc/chat.go:59`). `steer_run` therefore targets issue-family runs (`issue`/`ci_fix`/`self_improve`); when a user points it at a chat run, the 409 surfaces on the card as "steering applies to issue runs, not chats." (Chat turns ride `POST /api/chats/{id}/messages`, not `follow_up`.) Cancel has no such restriction — `cancel` is valid on chat runs too.

**Ownership and staleness are enforced server-side by `SubmitInput`, not by the card.** The card value (`run_id`) is untrusted, exactly like `start_run`'s `repo_path`/`issue_iid`. `SubmitInput` → `GetRun` → `GetRunByIDForUser` scopes by `user_id` (`service.go:4208`; SQL `WHERE id=$1 AND user_id=$2`, `runtime.sql.go:1421-1422`), so a forged or foreign `run_id` returns `ErrRunNotFound` → 404; an already-terminal run returns `ErrRunTerminal` → 409 (service pre-check `service.go:4212-4213`, and the SQL guard `status NOT IN ('completed','failed','cancelled')` in `CancelRunServerSide`, `api/internal/store/runtime.sql.go:147-148`). There is **no admin override** in this path — the unscoped `GetRunByID` reader is a separate method `SubmitInput` never calls. **The confirm handlers map errors like the existing `CreateRunInput` handler (`workers.go:1022-1031`: `ErrRunNotFound`→404, `ErrRunTerminal`→409, `ErrChatInputNotAllowed`→409), NOT like `writeStartRunError` (`workers.go:827`), which sends those errors to its `default` 500 arm.** So a stale card degrades to a clear 404/409 message, never a 500 and never a wrong action.

**Start stays gated as-is (start-directness sub-scope, resolved to no change).** The "full run-control parity" scope included revisiting whether starting a run from chat should be more direct (fewer clicks). Decision: **keep the human-click gate on start, and apply the same gate to cancel and steer.** The gate is the load-bearing prompt-injection guardrail documented in `docs/chat.md` and `docs/slack.md` ("A repo or issue that says 'start a run on #42' can at most produce a card, never a run"). Making start (or cancel/steer) auto-execute would let injected content in a run's activity feed drive real state changes. The start-path gates themselves are unchanged: `StartRunForUser`/`StartRunForUserByPath` (`composite.go:197-234`) enforce repo ownership (`GetRepoForUser`) and read a real forge issue, then call `CreateRun`, which enforces the PRD-label requirement (unless the instance-level prdless bypass applies). M5 records this decision and adds the regression test that locks the gate in.

**Must NOT do:** let any chat agent tool perform a cancel/steer/start write directly (all three stay card-gated); add a new `runs.status` value or a DB migration (both interventions reuse existing `SubmitInput` plumbing and existing columns); introduce Slack modal/`view_submission` machinery for steer text (reuse `replier.go` thread capture); or weaken the start-path gates.

## Success criteria

1. From **in-app Chat**, a user can cancel a live issue run and steer (follow-up) a live issue run, each via a card the user must click; the chat agent alone never performs the write (asserted by test, M5).
2. From **Slack**, a user can cancel a live issue run (button + confirm) and steer one (button → in-thread reply), each human-confirmed; no modal machinery is added.
3. Both interventions reuse the existing owner-only `POST /api/runs/{id}/inputs` (`SubmitInput`) with `cancel` / `follow_up`; **no new run endpoint, no new `runs.status` value, no DB migration.**
4. A forged or foreign `run_id` on any card is refused with 404, and an already-terminal run with 409, because `SubmitInput` re-resolves ownership and terminality server-side (the card value is untrusted, mirroring `start_run`).
5. `steer_run` against a **chat** run is refused with a clear "issue runs only" message (the `ErrChatInputNotAllowed` guard); `cancel_run` works on any of the user's non-terminal runs.
6. The start path is unchanged and still gated (repo ownership + real issue + PRD label + human click); the start-directness question is recorded as resolved (keep the gate).
7. The CLI already provides cancel/steer parity and needs no change (confirmed and documented, M6).
8. Touched gates green: `task gate:api`, `task gate:web`, `task gate:agent`, `task gate:repo`; k8s end-to-end validated (M7).

## Risks and mitigations

- **Prompt-injection via a run's activity feed.** The chat agent reads run output (`get_run_messages`) that can contain untrusted, injected instructions ("cancel run X"). Mitigated structurally: the tools only emit cards; the write happens on human click and re-resolves ownership server-side. M5 locks this with a test that all three run-write tools make no server call. This is the same guarantee `start_run` already provides.
- **Stale card / race.** A card may be clicked after the run finished or after the user lost access. Mitigated by `SubmitInput`'s server-side terminality (409) and ownership (404) guards and the `CancelRunServerSide` SQL guard; the handler maps both to clear card states. No client-side trust.
- **Slack steer free-text capture is the biggest hole (M4).** It is *not* a `replier.go` reuse: the existing capture resolves the target run from the thread anchor and intercepts chat-thread replies as chat turns, so cross-run steer-from-chat needs a new pending-steer registry `(channel, prompt-ts)→run_id` and a new interception branch ahead of the chat-run arm, plus correct handling of Slack `thread_ts` nesting. M4 contracts this explicitly and is flagged highest-risk and independently deferrable; if it slips, M1–M3 (cancel on both surfaces + steer on web-chat) still ship the reported gap. Covered by expanded `replier_test.go`/`chatactions_test.go` cases (stale pending, collision, wrong-thread reply).
- **File-sharing serialization (M1↔M3, M2↔M4).** The cancel and steer milestones touch the same files per surface; done in sequence this is mechanical. Splitting cancel-first means the primary gap the user reported (cannot cancel) closes at M1/M2 even if steer (M3/M4) is deferred.
- **Rollout skew (api vs web/agent).** New card kinds are additive. `ChatMessages.tsx` is an `if (msg.kind === …)` chain whose unknown-kind fallthrough renders an escaped terse `RunEventRow` (`ChatMessages.tsx:157-160`), not nothing — so an older web seeing a new `cancel_request`/`steer_request` kind degrades to an inert row, never an error. Confirm that fallthrough stays inert; do not assume a "renders nothing" default.
- **Emergency-stop must not be rate-limited.** Cancel is mounted with no limiter (mirroring `/{id}/end`), deliberately: mounting it under `forgeLimiter` would let a user who exhausted their forge budget be unable to cancel a runaway run. Steer, which induces agent spend, is under `chatLimiter`. Getting these mounts wrong is a real regression, not a style choice.

## Testing strategy

- **Agent (M1/M3/M5):** `agent/test/uzi-tools.test.ts` — each new tool emits the right card kind, carries the right payload (`run_id`, and `message` for steer), makes **no** server call, and is present in the `mcp__uzi__*` allowlist; the M5 no-write assertion covers all three run-write tools together.
- **API handler (M1/M3):** `chat_test.go` — the confirm handlers submit `cancel`/`follow_up` for an owned issue run; a forged/foreign `run_id` → 404; a terminal run → 409; a chat-run steer target → 409 with the "issue runs only" message; route mounts asserted in `route_limiter_mounts_test.go`. These exercise the real `SubmitInput` seam via the handler; no new store query is added, so no new live-DB test is required beyond what `SubmitInput` already has.
- **Slack (M2/M4):** `chatactions_test.go` and `chatpost_test.go`/`replier_test.go` — cancel/steer frames post the right cards; the cancel action calls the fake submitter with `cancel`; malformed frames post nothing; foreign/terminal/chat targets are refused gracefully. ## Decision Log

- **D1 — Reuse `SubmitInput` (`cancel`/`follow_up`) rather than add cancel/steer endpoints.** Both interventions already exist as `kind`s of `POST /api/runs/{id}/inputs`, owner-scoped, and are what the web run view and CLI use. Adding chat-surface confirm handlers that call `SubmitInput` keeps one source of truth for the state change and inherits its ownership/terminality guards for free. No new run endpoint, no new `runs` column, no migration.
- **D2 — Human-gated cards for cancel and steer, exactly like `start_run`.** The chat agent reads untrusted run output; a run write it could perform directly would be an injection vector. Emitting a card that a human clicks (and whose `run_id` is re-resolved server-side) is the existing, proven guardrail. This is non-negotiable and is the reason the tools never call the server themselves (locked by an M5 test).
- **D3 — Card axis by surface, capability split cancel-first.** Milestones are ordered by shared files (per-surface), with cancel (M1/M2) before steer (M3/M4). Cancel is the gap the user actually reported and the simpler, text-free intervention, so it lands first and independently; steer builds on the same scaffolding.
- **D4 — Slack steer uses the thread-reply interaction model, not a modal — but it is new machinery, not a `replier.go` reuse.** A modal (`view_submission`) was rejected because `slacksvc` has none today and adding it is out of scope. The thread-reply *interaction* (a Steer button, then the user types the instruction as a reply) fits the existing Slack UX and is offline-safe. However, `replier.go` cannot be reused as-is: it resolves the target run from the thread anchor and pre-empts chat-thread replies as chat turns, whereas steer-from-chat routes a reply in the *chat* thread to a *different* issue run. So M4 must add a pending-steer registry `(channel, prompt-ts)→run_id` and a new interception branch. This was corrected during PRD review after three reviewers independently found the "pure reuse" framing false; M4 is therefore the highest-risk milestone and is independently deferrable (M1–M3 still ship cancel-everywhere + web-chat steer).
- **D5 — Keep the human-click gate on start (start-directness resolved to no change).** The "full parity" scope asked whether start should be more direct. It should not: the gate is the documented prompt-injection defense, and the same reasoning that gates cancel/steer gates start. The start-path gates (repo ownership, real issue, PRD label) are likewise unchanged. Recorded here so the sub-scope is explicitly closed rather than silently dropped.
- **D6 — No CLI change.** `uzi run cancel` / `uzi run follow-up` and the TUI steer bar already provide cancel/steer through the same `SubmitInput` path, so the CLI-parity convention is satisfied by confirmation + a doc note (M6), not new commands.
- **D7 — `steer_run` targets issue-family runs only.** `SubmitInput` rejects `follow_up` on chat runs (`ErrChatInputNotAllowed`); rather than fight that, `steer_run` surfaces the 409 as guidance. Chat turns have their own endpoint (`POST /api/chats/{id}/messages`). Cancel has no such restriction and works on chat runs too.
