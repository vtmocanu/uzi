## Problem

Users who have an approved Responses-compatible endpoint and its own credential cannot use it with the Codex engine. The production adapter fixes the provider to OpenAI and accepts only vendor API-key/subscription authentication. Treating a gateway key as an OpenAI vendor key, or changing a base URL independently of the bound credential, could disclose a secret or charge the wrong account.

PRD #4320 supplies engine-neutral provider management and selection plus the Claude implementation; #4505 activated it with key redaction and upload scans. PRD #4321 supplies the offline runtime evidence for the Codex adapter. This PRD delivers one outcome: an approved user-owned Responses provider runs the Codex issue/task run lane end to end. Codex judge and plan/code cross-check on a provider source are the follow-up PRD; until it lands they refuse.

Current-main anchors (symbols, not lines; re-read at implementation):

- `agent/src/codex/config.ts`: `buildCodexProductionConfigToml` (vendor production builder, built-in `openai`); `buildCodexLoopbackTestConfigToml` (managed-login loopback characterization); the separate custom env-key builder is not the accepted path. The provider arm adds its own production builder (not the test-gated loopback builder) and deliberately updates the `CODEX_PRODUCTION_PROVIDER` "never from a claim" comment and the no-endpoint-override tests for that arm.
- `agent/src/codex/launcher.ts` `buildReplacedEnv` (sets `CODEX_EXEC_SERVER_URL=none`, stays on `useAppServerAuth`); `agent/src/codex/appserver-auth.ts` login via `account/login/start` (not `handleRefresh`).
- `agent/src/codex/codex-executor.ts` credential bridge (`releaseCodex`/`refreshCodex`, `buildRunLaneReconcile`) and `codexOperationAuthorityIdentity` / `acquireCodexOperationScope` admission.

- `prds/done/1106-codex-harness-phase1.md` anticipates a distinct compatible-endpoint auth profile; this PRD implements it through #4320's shared provider object, not a third harness.

## Outcome

A user can create, test and select a user-owned provider with engine `codex` and protocol `openai_responses` through the web and CLI surfaces from PRD #4320, and Codex issue/task runs then use only that provider's credential and model mapping, with the same execution boundary as existing Codex runs.

Acceptance examples:

1. The operator approves an exact base URL. A user saves a Responses provider and its own key, sees separate authentication/protocol and tool-use probe results, selects it as their Codex source, and starts a Codex issue run. The run starts at its frozen binding and completes through worker-owned callbacks. The pinned runtime may follow redirects and forward request content or headers as characterized by PRD #4321; this is an accepted risk, not destination confinement. Vendor credentials are absent from that claim and launch.
2. With `users.codex_provider_id` set, explicit `--harness codex` uses that source. Explicit `--harness claude` uses `claude_provider_id` when set, otherwise today's Claude vendor ladder. `default_harness` still selects the engine for implicit requests. A broken or revoked selected Responses source returns the typed provider refusal even when a vendor credential or another engine is usable; it never silently spends an OpenAI subscription, OpenAI vendor key or another provider key.
3. A provider changes while a run is queued or parked. The run keeps its bound provider revision and key `enablement_rev`, or receives the core's explicit revoked/unavailable/stale outcome on its next actual claim. A held claim keeps its authority until it ends; cancellation is the immediate stop (PRD #4320 D9). Resume, retries and cold resume never adopt a new destination or credential. Native-vendor runs keep their behavior.

## Out of scope

Chat-Completions-only endpoints, arbitrary provider plugins/config snippets, subscription OAuth forwarded to third parties, new harnesses, per-run/schedule provider selectors, per-role provider mixing, admin-shared providers (Codex-engine shared providers follow #4324), provider budgets/reserve, runtime upgrades and PRD #50 proxy composition. Codex judge and plan/code cross-check on a provider source (follow-up PRD). Codex provider runs on the isolated lane (PRD #4322 M3 is Claude-only). Jobs and chat sessions are Claude-only at the reviewed baseline (`jobs.go` pins Claude, `job_claim.go` refuses Codex jobs, chat uses the Claude `ChatExecutor`); this PRD enables neither a Codex job executor nor Codex chat, and preserves their behavior and #4322's Claude-provider work. A chat tool that starts an ordinary Codex run is an ordinary run, in scope as such. No implementation or validation edits under `.github/workflows/`.

## Testing decisions

- Source lifecycle mirrors A1: deleting a provider still selected returns `provider_in_use_as_source`; retirement keeps the source set and new requests return `provider_source_unusable`; never auto-null on delete, retirement or grant change. The resolver checks ownership/access and engine as well as the FK.
- Automatic selection mirrors A1 in both directions: a set Codex source makes the path ineligible for `automaticHarnessEligible` and `evaluateCreationOverflow`, including overflow into and out of the provider; unknown provider usage never enters weekly-reading comparisons. Test with a usable alternate-engine vendor credential and with a usable Codex pool.
- One test asserts the vendor Codex readers (pool, reserve, meter `codex_rate_limits.sql` `unmetered`, `codexSwitchTargetUsable`, default-clear) never see `openai_compatible_key`; kind-predicate readers already exclude an unknown kind.
- Capability: legacy and A1-only workers at claim, placement, wake, demand and reap; neither claims or strands a Codex provider run.
- Delivery: zero `releaseCodex`/`refreshCodex` calls and zero vendor operation admission, by instrumenting the release/dispatch seams, not log search; `/codex/release` and `/codex/refresh` refuse provider runs.
- Gateway limits reuse A1's `limit_wait` / `provider_gateway_limit`, resume delays 1, 5 and 15 minutes, then owner Resume only; retry count persists across claims. Test the timer/owner-resume sequence with controlled timers, the unchanged binding after reclaim, and the E2E reason literal.
- Fences: rotation and disable/enable between creation and claim give `provider_binding_stale`; an unusable selected provider with a usable vendor credential on each engine refuses with no fallback spend. Structured refusal versus free-text gateway error. Switch refusal provider-to-vendor and vendor-to-provider, including a source change between selection and apply.
- Interim refusals: Codex judge skip; plan and code cross-check refusals in both engine directions with the existing stage outcomes.
- Offline runtime evidence runs in CI without a workflow edit: the production-composition rows ship as clauses in the Codex conformance path run by `task test:codex-m4` (registry under `e2e/codex-m4/`, executed by `test-agent-shard` shard 1) or as agent unit tests, not only in the standalone `test:codex-provider-spike`.
