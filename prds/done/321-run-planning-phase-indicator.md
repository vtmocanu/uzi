# PRD #321: Distinguish a run's planning phase from its running phase

**Issue**: [#321](https://gitlab.example.com/vtmocanu/uzi/-/issues/321)
**Priority**: Medium (a correctness-of-communication gap, not a broken run: every surface reports "running" for two visibly different things)
**Status**: Planned
**Anchor**: all code references below are against `main` @ `b0b659b6`.

## Problem

When a run is started from the board or the CLI, the agent's **first turn is planning** — it drafts a plan and touches no code. Today that phase carries `runs.status = 'running'` and renders the exact same pulsing sky/cyan **"running"** badge as a run that was approved minutes ago and is now on its second implement⇄review iteration. A user looking at the board (or `uzi run list`) cannot tell "still thinking about it" from "actively writing code."

The state machine is `queued → claimed → running → awaiting_approval → running → completed|failed|cancelled` (`api/internal/store/migrations/00020_workers_runs.sql:26-37`): `status` is `running` on **both** sides of the approval gate, so the badge is identical on both sides. The only status-level marker between the two phases is the transient `awaiting_approval` gate itself, which a fast/autopilot run may never visibly sit in.

This is purely a display/communication gap. Nothing is functionally broken; the run behaves correctly. But "running" is doing double duty for two states a user genuinely wants to tell apart — one is waiting on the agent to propose work, the other is the agent doing the work.

## Current state (root cause of the ambiguity)

There is **no phase / plan-approved column** on `runs` and **no field on `RunDTO`** that says "past the gate." Phase is only inferable from side channels:

- `runs.plan_md` (`00020:45`, "captured plan awaiting approval"), `runs.iteration_count` (`00020:46`, the implement⇄review counter), `runs.plan_source` (`agent`|`seeded`, PRD #209), and the milestone columns (PRD #122).
- `PlanApproved` exists **only** on the worker `ClaimPayload` (`api/internal/workersvc/claim.go:64-71`, derived at claim time in `service.go:1805`); it is never persisted and never reaches a read DTO. There is no `approved_at`, no `phase`, no `plan_approved` on the run row or DTO.

The web badge taxonomy has one entry for `running` and renders it the same everywhere by design (`web/src/lib/runBadge.ts:289-293`, `web/src/components/ui.tsx:322-345`, "one status renders one color everywhere," asserted by a test in `runBadge.test.ts`). The CLI collapses `running` into a single green `crewWorking` lane (`api/cmd/uzi/tui_render.go:124-127`, `tui_lanes.go:226`). Neither has any notion of a planning sub-phase.

## The derivation (verified)

A run is in its **planning** phase when, and only when:

```
is_planning = kind NOT IN ('chat','judge')
              AND status == 'running'
              AND iteration_count == 0
              AND (plan_md IS NULL OR btrim(plan_md) == '')
```

The `kind` guard is load-bearing, not decoration: a `chat` run (inserted with no `plan_md`/`iteration_count`, `chat.sql`, and whose `ChatRunner` only ever reports `status:"running"`, `agent/src/chat-runner.ts:200,240`) and a `judge` run (`judge.sql`) sit at `running, iter 0, plan_md NULL` for their **entire life** — the three-field rule alone reports `is_planning: true` on them forever. That is only accidentally harmless today (`ListRunsForUser` filters `kind NOT IN ('chat','judge')` at `runtime.sql:398`, the board is issue-scoped, and `Chat.tsx:61` renders the raw status, not an effective one), but `GetRun → runToDTO` would still ship a semantically-wrong `is_planning: true` on any chat/judge run fetched by id. The guard makes the predicate correct rather than correct-by-list-filter. Use the same `kind NOT IN ('chat','judge')` set `ListRunsForUser` already uses, so `issue`, `ci_fix`, and `self_improve` (all of which genuinely have a planning turn) are planning-capable and only the two non-planning kinds are excluded.

Among the three planning inputs, no single field is sufficient; the pair `iteration_count == 0` **and** `plan_md` empty is what makes it robust. Verified against the code at the anchor SHA:

- **`iteration_count` is 0-indexed and counts only the implement loop.** The planning turn (`drivePlanningTurn`, `agent/src/sdk-executor.ts:1559-1600`) sends no iteration report, so `iteration_count` stays **0** through planning. The implement loop does `iteration++` before its first turn and reports `reportIteration(1)` (`agent/src/sdk-executor.ts:1166,1180-1186`; `agent/src/runner.ts:769-773`), so the **first implement iteration is `1`, not `0`**. Persistence is monotonic: `SetRunRunning` does `iteration_count = GREATEST(iteration_count, @iteration_count)` (`api/internal/store/queries/runtime.sql:746`), so once it reaches 1 it never regresses on resume.
- **`plan_md` is NULL during a normal planning turn.** It has exactly two writers: `CreateRun`'s INSERT (`runtime.sql:343-344`, seeded runs only) and `SetRunAwaitingApproval` (`runtime.sql:856`, written when the plan is submitted to the gate). So during the initial planning turn `plan_md` is NULL, becomes populated at the gate, and is **retained** through implementing (nothing clears it).

### Why each field alone fails, and why the pair is robust

| Scenario | status | iteration_count | plan_md | derived | note |
|---|---|---|---|---|---|
| Normal planning turn | running | 0 | NULL | **planning** | |
| Normal implementing (post-approval) | running | ≥1 (transient 0) | populated | **implementing** | `plan_md` populated excludes the transient-0 window |
| Re-planning after `revise` | *awaiting_approval* | 0 | prior version | n/a | not `running` — never classified (see below) |
| Seeded implementing | running | 0 → ≥1 | populated from creation | **implementing** | `plan_md` populated excludes the iter-0 startup window |
| Autopilot planning turn | running | 0 | NULL | **planning** | |
| Autopilot implementing | running | ≥1 | NULL | **implementing** | `iteration_count ≥ 1` excludes it |
| `chat` / `judge` run | running | 0 | NULL | **implementing** (not planning) | excluded by the `kind` guard — these never plan |

- `iteration_count == 0` **alone** misclassifies a **seeded** run's startup (it enters the implement loop with the counter still 0 for one turn) as planning. The `plan_md`-populated term fixes it: a seeded run has `plan_md` set from creation (`service.go:3750-3751,3886-3887`, `plan_source='seeded'`), and is pre-approved (`service.go:1805` third disjunct), skipping the planning turn and the gate (`sdk-executor.ts:847-861`).
- `plan_md` empty **alone** misclassifies **autopilot implementing** as planning, because an autopilot run **never persists `plan_md`** — it never reports `awaiting_approval` (the only non-seeded writer of `plan_md`), emitting the plan only to the feed batcher (`agent/src/runner.ts:1831`) and resolving the gate with an immediate approve verdict (`runner.ts:1836-1880`). So `plan_md` stays NULL in both autopilot phases; only `iteration_count` (0 vs ≥1) separates them.
- **Revise / "request changes" never surfaces as a `running` run to classify.** On `revise_plan` the run stays at `awaiting_approval` and re-plans there — `SetRunRunning`'s guard refuses `awaiting_approval → running` without a consumed `approve_plan` (`runtime.sql:823-827`), and the worker's revise loop runs another `drivePlanningTurn` at that status (`sdk-executor.ts:1006-1019`). `plan_md` is retained-then-overwritten there, never nulled. **Reject** is terminal (`PlanRejectedError`, `sdk-executor.ts:1021-1022`; run ends `failed`/`cancelled` with `stop_kind='plan_rejected'`), so it is never `running` either.

### One known transient (accepted)

An **autopilot** run, in the one turn between auto-approving and its first `reportIteration(1)`, has `iteration_count == 0` **and** `plan_md == NULL`, so it reads as **planning** for a few seconds until the first implement report lands. This self-corrects within one turn and is the genuine planning→implementing boundary moment. Accepted as a cosmetic transient, not worth a heavier signal (documented in the Decision Log). A normal (non-autopilot) run does not have this window, because its `plan_md` is already populated at the gate before implementing begins.

## Solution (Decision)

**Compute the phase once, server-side, and expose it as a single boolean on the run read model.** The rule needs three fields (`status`, `iteration_count`, `plan_md`); of the read surfaces only `RunDTO` carries all three, while the board's `LatestRun` projection (`web/src/lib/api.ts:431-463`) is deliberately narrow and its Go query does not even select them. Deriving client-side would therefore mean (a) widening `LatestRun` with raw fields anyway and (b) re-implementing the rule in TypeScript **and** again in Go for the CLI — three copies that can drift, in a codebase whose whole badge design is "one taxonomy, asserted by a test." Instead:

1. **One shared Go helper** `isPlanningPhase(kind, status string, iterationCount int32, planMd pgtype.Text) bool` implementing the four-condition rule above (the `kind` term excludes `chat`/`judge`), in the `handler` package next to `runToDTO` (`api/internal/handler/workers.go:305`).
2. **Expose `is_planning bool`** on `apitypes.RunDTO` (`api/internal/apitypes/run.go:24`, near `IterationCount int32` `:47` and `PlanMd *string` `:123`) and on the board's `latestRunDTO`. `runToDTO` and `mapLatestRun` (`board.go:146`) both call the one helper. **No DB migration** — the three inputs are existing columns.
3. **No new `runs.status` value and no change to the enum.** `status` stays honest (`running`); `is_planning` is a derived display predicate meaningful only while `status == 'running'`. Everything that keys on `status` is unaffected.

**The planning phase gets its own badge treatment (mock Option A — a dedicated tone).** Add a `plan` tone (indigo, distinct from violet `queued` and cyan `running`) and render a **"planning"** label with a pulsing dot. Concretely the web treats `is_planning` as an *effective status* `"planning"` that flows through the existing taxonomy tables, so no render site special-cases it beyond one table entry and one switch arm.

**Scope: light up planning on every surface that renders run status, in one change** — board card, run-detail `StatusPill`, runs-list rows, and the CLI TUI. Doing all four together is what the single server-computed field buys us; splitting them would reintroduce the drift the field exists to prevent. This also satisfies the repo convention "new uzi functionality ⇒ check whether `api/cmd/uzi/` needs a matching CLI change" (root `CLAUDE.md`) in the same MR.

**Must NOT do:** add a `runs` column or a new `status` enum value for this (the derivation is exact and free from existing columns); duplicate the rule in SQL or TypeScript when the Go helper is the single source; or change what `status` means to any existing consumer.

## Success criteria

1. An **issue/ci_fix/self_improve** run whose `status` is `running` with `iteration_count == 0` and empty `plan_md` reports `is_planning: true` on `GET`/list run reads and on the board card projection; every other running run reports `false`.
2. A **seeded** run, an **autopilot implementing** run, and a **`chat`/`judge`** run all report `is_planning: false` (the three cases a naive rule gets wrong: single-field rules miss the first two, a kind-less rule misses the third).
3. The board card, run-detail `StatusPill`, and runs-list rows render a distinct pulsing "planning" badge (the new `plan` tone) for a planning run, and the unchanged cyan "running" badge once it is implementing.
4. The CLI TUI / `uzi run list` visibly distinguishes a planning run from an implementing one.
5. `status` semantics are unchanged for every existing consumer (no new enum value, no migration); a pre-feature api pod omitting `is_planning` renders exactly as today (absent ⇒ not planning).
6. The board↔pill tone-agreement test still passes with `planning` in the taxonomy, and the mock board (`VITE_UZI_MOCK=1`) shows the planning badge.
7. Touched gates green: `task gate:api`, `task gate:web` (and CLI exercised).

## Risks and mitigations

- **Threading two columns through `mapLatestRun`'s long positional signature × 4 call sites (`board.go`).** Real but mechanical; mitigated by adding the two params once and calling the shared helper, and by the M1 handler tests that assert the board projection's `is_planning`. Consider a small struct or computing the boolean in the projection query if the positional list becomes unwieldy — but keep the rule in the one Go helper, not duplicated in SQL.
- **The autopilot first-implement-turn transient** (shows "planning" for ~one turn before `reportIteration(1)`). Accepted and documented; self-corrects. If it ever reads as a bug, the fix is a stronger "implementing has begun" signal, not a change to the rule.
- **Rollout skew (api newer than web, or vice-versa).** Mitigated by making `is_planning` optional on the web interfaces and truthy-guarded, exactly as `plan_source` handles the same skew (`api.ts:1252`): absent reads as not-planning, so a mixed deploy degrades to today's behavior rather than erroring.
- **Taxonomy drift between the board badge and the pill.** Mitigated by the existing agreement test (extended in M3) — the same guardrail that keeps every other status one color everywhere.

## Testing strategy

- **Go (M1):** table-driven unit test of `isPlanningPhase` over the seven-row scenario matrix. The discriminating cases are seeded-startup and autopilot-implementing (which a single-field rule gets wrong) AND a `chat`/`judge` row (which a kind-less rule gets wrong) — the test must include all three and fail a naive `iteration_count==0`-only, `plan_md-empty`-only, or kind-agnostic implementation. Handler tests that a running+iter0+empty-plan issue run serializes `is_planning: true` through `runToDTO` and the board projection, and a chat run serializes `false`.
- **Web (M3):** `runBadge.test.ts` — the planning badge (tone `plan`, pulse, label "planning") and the unchanged running badge; the extended `RUN_STATUS_TONES` board↔pill agreement; `StatusPill` planning rendering. All are pure/DOM tests, no live stack. A `VITE_UZI_MOCK=1` browser pass confirms rendering only (mock data cannot exhibit real phase transitions — see `.claude/rules/web.md` on mock limits); it is a rendering check, not a data check.
- **CLI (M4):** exercise `uzi run list` / the TUI against a planning run (or a fixture) and confirm the distinct treatment; covered structurally by `task gate:api`.
- No new live-DB test is required: the derivation reads existing columns and adds no query or transition. The store's run lifecycle is already covered; this PRD changes only what a read DTO *reports*.

## Decision Log

- **D1 — Server-computed single boolean over client-side derivation.** The rule needs three fields; only `RunDTO` carries all three, `LatestRun` is deliberately narrow, and the CLI is a third consumer in Go. Computing once server-side and exposing `is_planning` keeps the rule in one place and all four surfaces consistent (the repo's "one taxonomy, asserted by a test" ethos). Client-side derivation would widen `LatestRun` anyway and fork the rule into TS and Go. Trade: one extra DTO field and threading two columns through the board mapper; accepted.
- **D2 — Derived predicate, not a new `status` value or column.** `status` stays the honest state-machine enum; `is_planning` is display-only and meaningful only while running. Rejected alternatives: a new `planning` status (breaks the state machine and every consumer that keys on `status`, and the DB CHECK) and a `runs.phase` column (a migration for something exactly derivable from existing columns).
- **D3 — `iteration_count == 0 AND plan_md empty AND kind not chat/judge`, all terms required.** Verified that no smaller rule is correct: `iteration_count`-only misclassifies seeded startup, `plan_md`-only misclassifies autopilot implementing (autopilot never persists `plan_md`), and any rule without the `kind` guard misclassifies `chat`/`judge` runs (running+iter0+null-plan for life) as planning forever. The conjunction is the minimal robust rule. Revise/reject never present as a `running` run, so the rule needs no `awaiting_approval` handling. The `kind` set matches `ListRunsForUser`'s existing `NOT IN ('chat','judge')` filter, so `self_improve` (which genuinely plans) is correctly planning-capable.
- **D4 — Boolean `is_planning` over a `phase` enum.** A boolean matches the existing derived-flag pattern (`report_only`, `auto_approve`) and is meaningful only alongside `status == 'running'`. A `run_phase: "planning" | "implementing" | null` enum was considered (more self-describing) but adds a type for no consumer that needs the third value; revisit only if a future surface needs to name "implementing" explicitly.
- **D5 — Mock Option A (dedicated `plan` tone) over a qualifier label or a stepper.** A distinct indigo tone reads at board scale (the primary surface) where a "running · planning" qualifier (Option B) is easy to miss and a two-step pip (Option C) needs card real estate the badge does not have. The mock artifact presented all three; A was chosen for legibility at a glance.
- **D6 — Autopilot first-turn transient accepted.** Documented above; self-corrects within one turn. Not worth a heavier "implementing has begun" signal. Note this is most visible for **`self_improve`** runs (auto-approve, `plan_md` NULL for life, `selfimprove.sql`): unlike autopilot issue runs, they stay in the runs list, so their one-turn planning→implementing boundary is user-visible on the list, not just abstract. Still cosmetic.
- **D7 — Refinements found during implementation.** Four corrections to the plan above, each discovered while building M1–M4:
  - **CLI renders planning on the run-status colour axis, not the crew-lane ladder — supersedes the M4 sketch.** The original M4 text proposed a `crewPlanning` value on the `crewState` enum. Building it surfaced that the crew-lane ladder (`crewStateFor`, its `ActivityFeed.tsx` web twin, `laneDot`, `worstLaneState`) is a per-agent *activity* axis, and a planning agent legitimately sits on it as "working" — it's actively drafting, not idle. Adding a `crewPlanning` lane would have forked that axis from its `ActivityFeed.tsx` counterpart and broken the documented `tui_lanes.go`↔`ActivityFeed.tsx` parity for no gain. Planning instead rides the existing **run-status colour axis** (PRD #325 M2's `p.statuses`/`statusColor`/`chip` seam) as an indigo chip with a hollow `○` spine glyph (NO_COLOR-safe), and surfaces on `uzi admin runs` and the board's `/` filter for free from that seam.
  - **The board projection computes `has_plan_md` in SQL, not `plan_md` itself.** `ListLatestRunsForRepo`/`GetLatestRunForIssue` select a `has_plan_md BOOLEAN` and never put raw `plan_md` on the shared board card — its contract comment forbids carrying `plan_md`/secrets onto that card. Consequently the shared Go helper `isPlanningPhase` takes a plain `bool` (`planMdPresent`), not `pgtype.Text` as first sketched in the Solution section above; the board and the run DTO both resolve to that same boolean before calling the helper.
  - **`has_plan_md`'s SQL trims the same whitespace class as `runToDTO`.** The SQL uses `btrim(plan_md, E' \t\n\r\f\v')` (ASCII whitespace) so it agrees exactly with `runToDTO`'s Go-side `strings.TrimSpace` — one consistent "empty" rule across the run read and the board card, rather than two trim rules that could disagree on an edge case like a plan that's all tabs.
  - **The ember `--plan` token is indigo-400, not indigo-600.** `129 140 248` (indigo-400) replaces the indigo-600 first drafted in M2 — a web-ux browser finding that indigo-600's `text-plan` fell short of WCAG AA on ember's near-black card (only ~3:1), where indigo-400 clears it at ~6.3:1. Mission's `--plan` already used indigo-400 and needed no change.
