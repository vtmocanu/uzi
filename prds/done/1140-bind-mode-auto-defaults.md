# PRD #1140: Anthropic bind mode defaults to `auto` for every new worker and for the judge lane

> Anchors verified against main at 3ca8b70 on 2026-09-05 (the commit that merged PR #1138 / PRD #1136). Everything a milestone relies on is stated here as a fact with its file anchor; no milestone needs the open web.

**GitHub Issue**: [#1140](https://github.com/vtmocanu/uzi/issues/1140)
**Status**: Draft (created 2026-09-05)
**Priority**: Medium
**Related**: issue #804 (ephemeral workers default to `auto` when the pool is non-empty; a sole token is born pool-eligible: `specs/ai.md` §594, migration `00182`), PRD #111 (`prds/done/111-auto-select-anthropic-token.md`, the three-valued worker bind mode and the ranker), PRD #754 (`specs/ai.md` §581: the auto lane never spends an un-pooled token; `pool_wait`), PRD #104 (`prds/done/104-*`: mint-time worker binding and the per-user judge binding, D1/D8/D11), PRD #529 (ephemeral workers), PRD #983 (`runkind` registry).

## Problem

uzi has one good default and applies it in one place. Since #804 an **ephemeral** (burst) hosted worker is born with `anthropic_bind_mode = auto` when its owner has at least one pooled token, else `default` (`api/internal/hostedsvc/ephemeral.go:263-270`, via `UserHasAutoEligibleAnthropicToken`, `api/internal/store/queries/user_secrets.sql:362`). Every other create path still lands on the owner's default token:

| create path | mode today | anchor |
|---|---|---|
| external worker, join-token mint (`POST /api/workers`) | `default`; `pinned` only when the request names a token label; never `auto` | `api/internal/workersvc/service.go:3060-3093` (`CreateWorker`), `api/internal/store/queries/runtime.sql:3-26` |
| hosted worker, provision (`POST /api/workers/hosted`) | the INSERT does not name `anthropic_bind_mode`, so the row takes the column default `'default'` | `api/internal/handler/hosted_workers.go:255-266`, `api/internal/store/queries/hosted_workers.sql:206-227`, migration `00088:38` |
| ephemeral hosted worker | `auto` iff the owner has ≥1 pooled token, else `default` | `api/internal/hostedsvc/ephemeral.go:263-283` |

And the **judge lane** has no auto mode at all. Which credential a user's retrospectives spend is a per-user pointer, `users.judge_anthropic_secret_id` (migration `00079`): NULL means the default token, a value means that one token. `assembleJudgeClaim` resolves it statically (`api/internal/workersvc/judge.go:1048-1094`, `judgeSecretID` then `openAnthropic`, recorded with reason `judge`), and `self_improve` runs, which ride the ordinary run lane, follow the same pointer first, before any worker bind mode is consulted (`api/internal/workersvc/secretchoice.go:301-311`). So a user who opted three tokens into the pool still has every retrospective and every self-improvement run bill one fixed account.

Two facts make the flip safe now, and they are why this PRD is a defaults change rather than a new feature:

1. **"Pool empty" is a deliberate state, not the common one.** Since #804 a user's first or only `anthropic_token` is inserted `auto_eligible = true` (both write paths, `specs/ai.md` §594) and `00182` backfilled existing sole-token users. So a single-token user has a non-empty pool whose only member *is* their default token, and a multi-token user has at least their first token pooled unless they un-pooled it by hand. The `UserHasAutoEligibleAnthropicToken` guard therefore falls to `default` only for a user with zero anthropic tokens (nothing can run anyway) or one who explicitly emptied the pool.
2. **The auto lane's semantics are settled and documented** (#754, `ARCHITECTURE.md:468-485`, `docs/anthropic-token.md:97-180`): pick by headroom; floor onto the best pooled token when nothing is measurable (`pool_stale`); hold in `pool_wait` only when the pool is genuinely empty, resumable by pooling a token or `uzi run resume-now`. Nothing here changes those semantics for the run lane.

The cost of the status quo is toil and a silent spend concentration: a pooled-up user re-points every new worker by hand (`uzi worker set-token <id> --auto`, or the Workers page picker), and cannot spread retrospectives at all.

## Solution

**M1, workers**: one rule for every worker create path, derived at create time exactly as #804 does it:

```
label named in the request          → pinned   (+ anthropic_secret_id)
else owner has ≥1 pooled token      → auto
else                                → default
```

Applied to `workersvc.CreateWorker` (external mint) and to the hosted provision handler, whose INSERT starts naming `anthropic_bind_mode` explicitly. The ephemeral provisioner already does this; its `UserHasAutoEligibleAnthropicToken` read is the shared primitive.

**M2, judge lane**: a three-valued `users.judge_anthropic_bind_mode` (`default` / `pinned` / `auto`) mirroring `workers.anthropic_bind_mode` (00088), column default `auto`, backfilled to `pinned` where `judge_anthropic_secret_id IS NOT NULL`. `judgeSecretID` grows into a judge-lane choice: `pinned` reads the pointer, `default` reads nothing, `auto` runs the same `autoChoice` ranker the run lane uses. Judge runs and `self_improve` runs both go through it, as today. The "Token the judge spends" picker gains an "Auto-select from the pool" option; the API and CLI contracts carry the mode.

The two lanes agree on everything except what `auto` does on a **genuinely empty pool**, and that difference is D4 below.

## Decisions

- **D1. Create-time derivation, not claim-time, for workers.** A worker's bind mode is a stored, user-visible tri-state that the owner can read (`uzi worker list` TOKEN column, the Workers page picker) and set. Deriving it once at create and storing it keeps "what will this worker spend" answerable from the row, which is what #804 chose and what `TestCreateWorkerWritesTheBindMode` (`api/internal/workersvc/bind_mode_test.go:240`) already pins for the pinned case. A later change to the pool does not retroactively re-mode existing workers; the Workers page already warns on an `auto` worker whose pool went empty (`web/src/pages/WorkersSettings.tsx:738-760`).
- **D2. New rows only; no backfill of existing `default` workers.** A worker sitting on `default` beside a non-empty pool may be deliberate (a reserved account for one worker), and the whole point of PRD #111 D2 is that auto never helps itself to a credential the user reserved. The flip is a *default* for rows that do not exist yet. Existing workers are re-pointed by the owner, as today.
- **D3. The hosted INSERT names the column, always.** `runtime.sql:10-21` records exactly the regression this avoids: PRD #111 M3 made the mode decide whether the id is read at all, and an INSERT that set the id but let the mode take its SQL default produced a worker carrying a real binding that resolved the owner's default. `CreateHostedWorker` has no id to mis-pair today, but the moment M1 makes the mode a create-time decision, an INSERT that omits it would silently ship `default` for every hosted worker, green at every gate. So the mode is a required parameter of the query, derived by the handler and written in the same statement, as `CreateWorker` and `CreateEphemeralHostedWorker` do.
- **D4. Judge-lane `auto` on an empty pool spends the default token, recorded `pool_empty`; the run lane keeps holding in `pool_wait`.** This is the one deliberate asymmetry, and it exists because the two lanes hold different things. A run-lane hold exists so an `auto` *worker* never spends a token the user reserved from it, and the held run keeps its issue and worker affinity for a resume the user is waiting on. A judge run holds no issue, no branch and nobody's attention; a retrospective parked in `pool_wait` for a user who emptied the pool would silently pile up (every finished run enqueues one) with no surface that shows the backlog, and the judge's own contract is "spends **your own** token" (`docs/judge.md:12-13`), the default being the one credential a user with any token always has. `self_improve` follows the judge's resolution exactly, including this fallback, for the reason `secretchoice.go:284-296` gives: it is uzi reviewing itself and follows the judge's credential, not a worker's. `autoselect.ReasonPoolEmpty` already exists in the closed vocabulary (`api/internal/autoselect/select.go:45-51`, kept "for PRE-#754 historical rows where the default genuinely was spent"); the judge lane revives it for a row where the default genuinely was spent, so migration `00089`'s CHECK and every renderer are unchanged. The alternative, holding judge runs in `pool_wait` too, is mechanically free: `assembleClaim` forks to `assembleJudgeClaim` (`api/internal/workersvc/claim_assembly.go:33`) and `ClaimRun` wraps that whole call in `recoverClaimAssembly` (`service.go:1417-1419`; the function itself is at `service.go:1438`, and its `errAutoPoolEmpty` arm at `1445-1459` maps to the hold) and is the reason this is a decision, not an accident; if the maintainer prefers the hold, M2 flips one branch and D4 is rewritten, nothing else moves.
- **D5. Judge mode default `auto` for existing users too, because it changes nobody's spend for the worse.** Unlike a worker row (D2), the judge pointer is resolved at claim time, so the column default reaches existing users. With D4 in force: a user with a pinned judge token is backfilled to `pinned` (unchanged); a sole-token user's pool is their default token (unchanged credential, reason becomes `auto` instead of `default`); a multi-token user with a pooled set gets the spread they opted those tokens into; a user who emptied the pool spends the default (unchanged). Backfilling to `default` instead would make the feature reach nobody who did not find the new picker option.
- **D6. Mode and pointer are written in one statement, and `pinned` with a NULL pointer resolves as `default`.** The same two rules 00088 states for workers (one statement and same-migration backfill at `00088:15-18`; no coupling CHECK and `pinned`-with-NULL-resolves-`default` at `00088:21-36`), for the same reason: `00079`'s FK is `ON DELETE SET NULL (judge_anthropic_secret_id)`, so a legal token delete nulls the pointer and leaves the mode, and a coupling CHECK would reject the delete. The API reports the *effective* mode (`effectiveBindMode`, `api/internal/handler/workers.go:33-58`, reused or mirrored) so no client re-derives the rule.
- **D7. Reuse the ranker; add no second one.** `autoChoice` (`secretchoice.go:392-427`) is called from the judge lane with the same run and the same exclude, so `claimExclude` (a just-parked dead credential) applies to a judge run exactly as it does to an issue run. `ARCHITECTURE.md:462-467` states that the ranker runs in one place; after M2 it still does, `autoChoice`, with two callers.
- **D8. No new CLI verb.** Setting the judge token is web-only today (there is no `uzi judge …` command; PRD #104 D8 kept credential-choosing writes reachable from a CLI token only where they hand back no credential, and the judge picker was never ported). M2 exposes the mode on `GET /api/auth/me` (`uzi whoami --json`) because it rides `UserDTO`, and leaves a `uzi judge set-token` verb to a follow-up issue if the maintainer wants it. The CLI skill text is still corrected (M5).
- **D9. Chat runs are untouched.** The chat lane calls the opener directly with no override and always resolves the owner's default (`ARCHITECTURE.md:452-453`; `uzi worker set-token --help` says the same). Out of scope, stated so nobody reads M1 as covering it.

## Success criteria

1. `POST /api/workers` with no `anthropic_token`, by a user with a pooled token, returns `anthropic_bind_mode: "auto"`; with an emptied pool, `"default"`; with a label, `"pinned"` regardless of the pool. Same for `POST /api/workers/hosted` minus the label case.
2. A judge run for a user in `auto` with two measured pooled tokens records the higher-headroom token with reason `auto` and a headroom; with an empty pool, the default token with reason `pool_empty`, and the run completes rather than holding.
3. A `self_improve` fire on the same user shows the same resolution on its run record.
4. A user with a judge token set before the migration reads `judge_anthropic_bind_mode: "pinned"` and keeps spending that token; a user without reads `"auto"`.
5. The pre-M2 body `PUT /api/me/judge {"enabled": true}` leaves the binding untouched; `{"enabled": true, "anthropic_token": null}` sets `default`, not `auto`.
6. The Run defaults page offers "Auto-select from the pool" for the judge with one or more tokens, and the Workers page renders a freshly minted worker's derived mode without a page reload.
7. `task gate` is green on the branch; the store-it sweep names the new `*LiveDB` tests with zero skips.
8. Post-merge on the dev cluster (maintainer, after the next release): provision a hosted worker and `uzi worker list --json | jq '.[-1].anthropic_bind_mode'` reads `auto`; `uzi whoami --json | jq .judge_anthropic_bind_mode` reads `auto`; the next judge run's `uzi run get <id> --json | jq '{anthropic_select_reason, anthropic_secret_label}'` reads a pooled token with reason `auto`.

## Risks

- **A user relying on the judge spending their default while holding a pooled multi-token set** now sees retrospectives spread. That is the feature, and D5 explains why it reaches them; the picker makes `default` one click away. Called out in the `docs/judge.md` paragraph.
- **A hosted worker created by an older web bundle** sends the same body as today (no token field), so it gets the derived mode; nothing in the request shape changes.
- **`gate:web` red between M2 and M3** on the API contract test: expected, the two ship in one branch; the milestone order keeps the red window inside the run.
- **The judge `auto` fallback (D4) recording `pool_empty` on new rows** re-purposes a reason the code comments call historical. The comment on `ReasonPoolEmpty` (`select.go:47-53`) is updated to say the judge lane still produces it, so a later reader does not "clean it up".
- **Migration numbering**: `00197` is a draft; renumber above the live head on the landing rebase. `gate:repo`'s `check:migration-numbering` catches a duplicate; a number below an applied head is caught by nothing local and refuses boot (root `CLAUDE.md`, Conventions).
