## Problem

A `task` run — created by `uzi handoff` (kind `task`, PRD #400; `uzi run create` makes *issue* runs, not tasks) — is **one-shot**. Its implement loop runs autonomous turns until the agent calls `signal_done`, then the run finalizes (pushes `uzi/task/<id>`, optionally opens an MR) and goes **terminal** (`completed`). To change anything you must either edit locally or spin up a **fresh** task, which starts cold and loses the agent's accumulated session context.

There is no way to keep a task **alive** so you can iterate with it conversationally — send a new request, have the *same* agent session act on it with full prior context, and repeat — and then explicitly tell it you are done so it winds down cleanly. Today the only ways to influence a live task are `run follow-up` (which the loop consumes only while it is still running, before `signal_done`, and never idles waiting for) and `run cancel` (a hard, mid-turn abort).

## Solution

Add an **opt-in interactive mode** for task runs. When a task is created interactive:

- On `signal_done`, instead of finalizing to `completed`, the run **checkpoint-pushes its branch** and **parks** in a new non-terminal status `awaiting_followup`, held in-process by the worker so the **SDK session, clone, and branch stay alive**.
- `uzi run follow-up <id>` **wakes** the parked run: the follow-up is delivered, the **same agent session resumes with full context** (session-id resume, no history replay), takes turns until the next `signal_done`, checkpoint-pushes, then parks again.
- An **idle timeout** (worker-side) auto-winds-down a forgotten interactive task: finalize (push, optional MR) → `completed`. A **server sweep backstop** covers a *dead* worker — but for a git-backed task it **requeues for worker finalize**, it does not itself flip the run to `completed` (a DB write cannot push the branch).
- A new **`uzi run stop <id>`** verb tells the run to **wind down gracefully**: finalize (push / optional MR) → `completed` with a distinct stop reason. Separate from `cancel` (hard abort).

This is largely **wiring three existing subsystems onto the task lane** — the `awaiting_input` in-process park (recovery + resume already proven), chat's idle-timeout + explicit-end lifecycle, and the `session_id`-resume that `limit_wait`/`ContinueChat` use — **plus two pieces of genuinely new work the reviews surfaced**: a correct blocking follow-up waiter on the task-lane steering channel (the drop-on-idle race, Decision 4), and a task-aware idle/recovery path that never abandons unpushed commits (Decision 6).

## Background — current state (resolved facts; re-locate symbols by name at HEAD)

### Run status is a text CHECK, not an enum — but THREE CHECK domains must widen, not one

`runs.status` is `text NOT NULL DEFAULT 'queued'` with a named CHECK `runs_status_check` (`store/migrations/00020_workers_runs.sql`), widened in place to add `limit_wait` (`00091_run_limit_wait.sql`) and `awaiting_input` (`00092_run_awaiting_input.sql` — `ALTER TABLE runs DROP CONSTRAINT IF EXISTS runs_status_check;` then re-add all values). Adding `awaiting_followup` follows that precedent (down narrows back, removing the value — see the data-dependency note in Risks). **Two further CHECK constraints are in play and were missed in the first draft:**

- **`stop_kind` has its own CHECK**, currently `('cancelled','plan_rejected','auto_stopped')` (`00050_run_stop_kind.sql`, widened by `00082_run_stop_kind_auto.sql`). Writing the new `run stop` reason `'stopped'` (Decision 5) **violates this CHECK** unless it is widened. Several later migrations (`00126`/`00137`/`00139`) build derived `fail_origin`/recovery expressions enumerating these literals — check them when adding a value.
- **`run_user_inputs.kind` has a CHECK** `run_user_inputs_kind_check`, currently `('follow_up','approve_plan','reject_plan','cancel','revise_plan','answer')` (`00092`). If `run stop` is a new input kind (Decision 5 — it is), this CHECK must gain `'stop'`.

**All four schema changes (status CHECK, `interactive` column, `stop_kind` CHECK, inputs-`kind` CHECK) land in the single M1 migration** so M4 never reopens a "done" migration file.

The **terminal set** literal is `terminalStatuses = {completed, failed, cancelled}` at `workersvc/service.go` (definition ~`:86`; consumed at `autostop.go`, `chat.go`, `findings.go`, `summaries.go`). `awaiting_followup` must be kept **out** of it. The worker `home-reclaim.ts` uses `TERMINAL_RUN_STATUSES = {completed,failed,cancelled}` checked **negatively** (~`:82`), so a new non-terminal value needs **no behavioral change there** — only its stale "NINE values" comment (~`:61`) is bumped.

### The SQL active-run predicate family is the real recovery + concurrency surface (first draft missed it)

`awaiting_input` is a deliberate member of `status IN ('claimed','running','awaiting_approval','awaiting_input')`, which recurs ~15× across `store/queries/runtime.sql` (+ generated `runtime.sql.go`). Whether `awaiting_followup` is **added to** or **excluded from** each is a correctness decision, not display:

- **Worker-death recovery — TWO distinct paths, both SQL-gated.** Register-time: `RequeueWorkerRuns` + `FailWorkerRunsOverCap`. Periodic stale-heartbeat sweep: `RequeueRunsOfStaleWorkers` + `FailRunsOfStaleWorkersOverCap`. All four filter that IN-list. The `Register` doc (`service.go`, the Register func + its comment) states `awaiting_input` must be in **both** because a fast-restarting worker is never "stale," so the heartbeat sweep never sees it. **Miss the SQL and a parked task whose worker dies becomes a zombie** (`awaiting_followup` forever) — the Go `Register` branch never runs because the SQL that feeds recovery filtered it out first.
- **Load-balancing + concurrency accounting.** `ClaimRun` peer-spread math, `ListWorkersByUser` `active_runs`/`busy`, `CountOnlineWorkersWithFreeSlotForUser` all use the IN-list. A parked task holds an in-process slot (Decision 3) but, if excluded, reads as **not active** → the fleet schedules new runs onto a worker that is actually full (they stall until the spread cutoff), and the UI under-reports load. So `awaiting_followup` should be **added** to the active set for these.
- **Autostop backstop.** `FailRunAutoStop` (`runtime.sql`) excludes `limit_wait` and `awaiting_input` so a park cannot be auto-**failed**; its comment states this SQL clause is the required defense-in-depth for the day the Go guard (`autostop.go`, bails at `run.Status != "running"`) is relaxed. Add `AND status <> 'awaiting_followup'` for the same reason.
- **Wake guard.** `SetRunRunning` (the `awaiting_input`→`running` resume) admits the transition; `limit_wait` carries an explicit `status <> 'limit_wait'` exclusion so a delayed/duplicate `running` report cannot un-park a run under a defunct worker. `awaiting_followup` needs an equivalent guard (Decision 7) so only the in-process worker on the current claim can wake it.

The worker→server state report validates the status string at `handler/worker_protocol.go` (`"state must be one of running, awaiting_approval, awaiting_input, limit_wait, completed, failed"`) — the new value must be added or the worker cannot report the park.

### The wall clock only touches `running`; the park has no server clock except the idle backstop

`SweepRunningTimeout` (`runtime.sql`) fires `WHERE status = 'running' AND started_at < now - COALESCE(budget_wall_seconds, RUN_TIMEOUT) AND kind NOT IN ('chat','judge')` (default `RUN_TIMEOUT` 2h). Scoped to `running`, so `awaiting_followup` is wall-clock-exempt — **which means the idle timeout (M5) is the only clock on the park, not "hardening."** This makes M5 safety-critical (see MVP note).

### Session persistence resumes real context; the commit-loss window is what widens

Session resume is real-context (`resumeId = ctx.sessionId`, `sdk-executor.ts`), with a fresh-session fallback when the transcript is not on the re-claiming worker (`runner.ts`, `sessionTranscriptResolvable` → sets `sessionId = undefined`, warns) — **no history replay**. The bigger interactive-mode hazard is **git, not context**: a one-shot task pushes on `signal_done`, so unpushed commits live locally only briefly. An interactive task that pushes **only at wind-down** would keep a whole multi-turn session's commits on the worker volume for hours; a worker death then loses commits to PVC-only recovery. **Decision 4 therefore checkpoint-pushes at every park** (the `ctx.checkpoint` / pushbroker seam from PRD #122), so the branch tip is always on the remote and dead-worker recovery is a requeue, not a loss.

### The precedents to generalize

- **`awaiting_input` park:** `Runner.askUser` (`agent/src/runner.ts`) reports `awaiting_input`, blocks in-process on `steering.awaitAnswer(questionId)`, resumes on the same session; `Register` re-queues on worker death; timeout (`QUESTION_TIMEOUT_SECONDS`, 24h) **fails** the run. Interactive-task reuses the structure but waits for the next **follow-up** and **completes** (not fails) on idle.
- **Chat idle lifecycle:** `ChatSteering.awaitFollowUp(idleMs)` (`agent/src/steering.ts`) parks between turns; idle bounded by `WORKER_CHAT_IDLE_TIMEOUT` (60m) and server `SweepIdleChatRuns` (70m) — but that server sweep is a bare `UPDATE runs SET status='completed'`, **clean only because chat has NO git collaborator** (Decision 6 is why a task cannot reuse it as-is). Explicit end: `EndChat` rides the cancel path; `ContinueChat` resumes a finished chat into a new run.
- **`SteeringChannel` ≠ `ChatSteering`.** The task-lane channel (`SteeringChannel`, `agent/src/steering.ts`) has an `awaitAnswer` waiter and a **non-blocking** `pullFollowUp()` dequeue — it owns **no idle clock and no follow-up waiter**. `ChatSteering`'s class doc calls its idle-clock-ownership + "route THEN service in the same iteration, single outstanding park" the *load-bearing fix for the drop-on-idle race*. Adding a blocking `awaitFollowUp(idleMs)` to the task lane must replicate that discipline — **genuine concurrency code, not wiring** (Decision 4).

### The task run lane, `--review`/`--then-fix`, and what is NOT affected

A `task` run is a `RunRunner` run dispatched at `worker.ts` (`this.runner.execute(claim)`); the implement loop breaks on `if (turn.done) break;` (`sdk-executor.ts`, the `signal_done` path). `max-iterations` throws `REASON_MAX_ITERATIONS` **before** that break, so an interactive task can still **fail** and never park (SC1 is "on a clean `signal_done`", not "on any exit"). `--review`/`--then-fix` (`api/cmd/uzi/handoff.go`; `--then-fix` implies `--review`) fire **server-side on the committed `completed` transition** (`workersvc/service.go` `maybeEnqueueTaskReview`/`maybeEnqueueThenFix`, gated `status=="completed" && kind=="task"`), auto-creating a **separate** review/fix run — so M4 stop and M5 worker-idle report `completed` and get review **for free**; the mental model "worker runs the review at wind-down" is wrong (Decision 8).

**Verified non-interactions (no change needed; stated so the worker does not chase them):**
- **Judge:** `judgeEligibleKinds = {issue, ci_fix}` (`workersvc/judge_enqueue.go`) — `task` is never judged, so an interactive task is not judged at wind-down.
- **Active-run/issue dedup:** tasks are created from inline context with a per-run branch `uzi/task/<id>` and no `issue_iid` (`workersvc/task.go`), so the issue-dedup / branch-collision predicates never apply to `awaiting_followup`.

## Design decisions

1. **New non-terminal status `awaiting_followup`.** A distinct, user-visible status is a feature (the user wants to see a task is alive and awaiting them). Reusing `awaiting_input` is wrong (means "answer this question", fails on timeout); staying `running` (chat's choice, exempt by `kind`) mislabels an idle task and needs a non-kind discriminator anyway.

2. **Opt-in `runs.interactive boolean NOT NULL DEFAULT false`, threaded to the worker on the claim.** Default one-shot preserves today's behavior and resource profile exactly. Set by `uzi handoff --interactive`; carried create DTO → `runs` row → `ClaimResponse` (`agent/src/protocol.ts`). Non-interactive tasks touch no new code path. *(Corrected 2026-08-21: `--interactive` shipped on `uzi handoff` only — task runs are created by handoff, not by `uzi run create` (which makes issue runs), so there is no `run create --interactive`.)*

3. **In-process hold for v1 (like `awaiting_input`); release-and-reclaim is a scoped follow-up.** The park holds the worker slot + clone + HOME, reusing `awaiting_input`'s proven recovery + same-session resume. The `limit_wait`-style release-and-reclaim (free the slot between requests, re-claim with affinity + `session_id`) is better for long idles and removes the slot-exhaustion exposure when several interactive tasks park at once — but it is deferred. Note the delta is smaller than "larger" implies (in-process hold already needs Register-requeue + affinity + `session_id`), and the short worker idle timeout (M5, 30m) plus the concurrency-accounting fix (M2) bound the slot cost until then.

4. **Park at `signal_done`; checkpoint-push; wake on follow-up; implement the waiter correctly.** In the `RunRunner` implement path, when `interactive` and the loop would break on `turn.done`: (a) **checkpoint-push** `uzi/task/<id>` via the `ctx.checkpoint` seam (bounds commit loss, Background); (b) report `awaiting_followup`; (c) block in-process on a **new blocking follow-up waiter** on the task-lane `SteeringChannel`, built to `ChatSteering`'s route-then-service / single-outstanding-park / **drain-after-arm** discipline so a follow-up landing between "decide to break" and "arm the waiter" is not dropped; (d) on follow-up report `running` (guarded, Decision 7), fold via `pullFollowUp`, loop. The park sits **outside** `driveTurn` so the idle watchdog cannot trip it.

5. **`run stop` = new input kind `"stop"` on `/inputs`, graceful and owner-scoped.** Riding `SubmitInput` inherits `GetRun(ctx, userID, runID)` ownership + CSRF automatically (match `EndChat`'s authz; do **not** hand-roll a weaker check on a dedicated route). It signals the parked (or running) worker to stop waiting and **finalize normally** — push, open MR iff `open_mr`, and (via the server `completed` transition) trigger the diff-review iff requested — then report `completed` with `stop_kind = "stopped"` (distinct from cancel's `"cancelled"`). On a still-**running** run, stop means "finish the current turn, then wind down" — queued on the same FIFO as follow-ups but **serviced ahead of buffered follow-ups** so it is not starved. `cancel` stays the hard mid-turn abort.

6. **Idle timeout completes via the WORKER; the server backstop REQUEUES, it does not complete.** Worker-side `WORKER_TASK_IDLE_TIMEOUT` (new, default 30m — shorter than chat's 60m because a task pins a git clone) fires the same graceful finalize as `run stop` (push then `completed`) — this is the path that satisfies "preserve committed work." The **server backstop** for a *dead* worker is **not** a chat-style `UPDATE→completed` (a DB write cannot push the branch, would skip the review hook, and would race a slow-but-alive worker into `ErrRunTerminal` with work lost). Instead, a stale `awaiting_followup` task is **requeued for a worker to finalize** (reusing the stale-worker requeue path, M2) — or failed-with-recovery if unclaimable — never silently `completed`. Because Decision 4 checkpoint-pushes at each park, a requeue-and-finalize loses no commits.

7. **Guard the wake.** `SetRunRunning` must only un-park `awaiting_followup` for the in-process worker on the current claim (mirror `limit_wait`'s `status <>` exclusion / an ownership guard), so a delayed or duplicate pre-park `running` report cannot spuriously un-park an idle task and re-arm the wall clock.

8. **`--review`/`--mr` compose via the server `completed` transition; `--interactive --then-fix` is a usage error (v1).** The diff-review fires once, server-side, when the run finally reports `completed` (stop or worker-idle) — no worker-side review logic to add, and it must **not** fire on each intermediate park. Spawned review/fix runs never inherit `interactive`. `--then-fix` chains a separate fix run whose interaction with a still-iterating interactive parent is ambiguous, so `--interactive --then-fix` is rejected at the CLI for v1 rather than guessed.

9. **`awaiting_followup` is actionable for `run wait` and gate-free.** Task runs have no plan gate; interactivity is purely post-`signal_done`. A bare `uzi run wait <id>` stops on `awaiting_followup` (join `awaiting_approval`/`awaiting_input`/terminals in the default stop set; add to `allRunStatuses` so `--until awaiting_followup` validates).

## Success criteria

1. `uzi handoff --interactive` creates a task that, on a **clean** `signal_done`, checkpoint-pushes its branch and enters `awaiting_followup` (not `completed`), holding its SDK session. (A max-iterations failure still fails, never parks. Interactive mode is a handoff-only opt-in — there is no `run create --interactive`.)
2. `uzi run follow-up <id>` on a parked run resumes the **same** session with full context (session-id resume, not fresh), the agent acts, and the run parks again on the next `signal_done` — including when the follow-up races the park boundary (no lost wakeup).
3. `uzi run stop <id>` winds a parked-or-running interactive run down gracefully — branch pushed, MR iff `open_mr`, diff-review iff requested (via the server `completed` transition) — landing `completed` with `stop_kind="stopped"`; `cancel` remains a hard abort; `--interactive --then-fix` is a usage error.
4. An interactive task idle past `WORKER_TASK_IDLE_TIMEOUT` finalizes and **completes** with work pushed. A task whose **worker died** while parked is **requeued and finalized** by the server backstop (never flipped to `completed` with unpushed work), and — because of checkpoint-push — loses no commits.
5. A **non-interactive** task run is behaviorally identical to today (byte-identical prompts/finalize; additive-absent tests prove it).
6. A parked interactive task is correctly classified everywhere it must be: counted as **active** in worker load/scheduling; **recoverable** via both the Register and stale-heartbeat requeue paths; **not** auto-failable by the autostop backstop; and rendered as a labeled, actionable status in CLI, TUI (glyph twin), web (badge + usable steer input), and Slack — never `unknown` and never silently dropped from a band/lane/predicate. A bare `uzi run wait` stops on it.
7. `task gate:api`, `task gate:agent`, `task gate:web` pass; new behavior covered by non-vacuous tests proven via call-site mutation (the SQL recovery/concurrency/autostop assertions especially); no `.github/workflows/**` touched; `main` untouched; delivered on a branch + PR.

## Risks & mitigations

- **Highest single risk (was the first draft's biggest hole): the server idle sweep abandoning a git-backed task.** A chat-style `UPDATE→completed` cannot push the branch, skips the review hook, and races a live worker. Mitigation: Decision 6 — the server backstop **requeues for worker finalize**; only the alive worker completes-and-pushes; M5's test asserts the **work outcome**, not the status label (so it cannot codify the bug).
- **Missing a SQL status-set predicate → zombie parked run or fleet mis-scheduling.** Mitigation: M2 owns the full `runtime.sql` IN-list as correctness, both recovery paths named (Register **and** stale-heartbeat), each proven by a predicate mutation.
- **Drop-on-idle / lost-wakeup race** on the new task-lane waiter. Mitigation: Decision 4 replicates `ChatSteering`'s route-then-service + drain-after-arm; M3 tests the park-boundary race explicitly.
- **Commit loss across a long interactive session.** Mitigation: checkpoint-push at every park (Decision 4), so the remote always has the tip.
- **MVP fallback leaking worker slots.** Mitigation: MVP is M1+M2+M3+**M5** (idle backstop), and M2 fixes concurrency accounting so parked tasks count against load.
- **Two extra CHECK domains (`stop_kind`, inputs-`kind`) missed → runtime constraint violation.** Mitigation: M1 folds all four schema changes into one migration.
- **Wake un-parked by a stale duplicate `running` report.** Mitigation: Decision 7 guard on `SetRunRunning`.
- **Data-dependent down migration.** Narrowing any CHECK back down fails if a row holds the new value (the hazard `00074`/`00082` document); accepted pattern — the down is best-effort and documented, not run against live data with such rows.
- **Vacuous tests** on silent-omission surfaces. Mitigation: call-site/predicate mutation mandated for the SQL recovery/concurrency assertions and the web classification predicates, not just M3/M5.
