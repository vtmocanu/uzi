## Problem

On a marginal / high-latency connection the board floods the user with:

```
could not refresh: reading response from uzi: context deadline exceeded
```

Two design facts turn a merely-slow link into a self-inflicted cascade:

1. **No in-flight guard on the 2s poll.** `boardTickMsg` (`tui.go:463-475`) issues a fresh `fetchRunsCmd` every 2s regardless of whether the previous poll has returned. Because bubbletea runs each `Cmd` in its own goroutine (verified: `tea.go:729-741`), a link where one `ListRuns` takes longer than 2s accumulates **overlapping concurrent requests** that compete for the same scarce bandwidth, making every one slower — until they hit the cap. The detail-view meta poll (`refreshRunMetaCmd`, same tick) has the identical hazard.
2. **The only bound is a flat 30s timeout meant for one-shot CLI calls.** `fetchRunsCmd` uses the long-lived `m.ctx` (`tui.go:324`), so a poll is capped only by the shared `http.Client.Timeout` of 30s (`client.go:523`). 30s is far too long for a 2s-cadence poll: a stalled poll blocks its goroutine for a full 30s (during which ~14 more ticks pile behind it), and because that timeout also covers the body read, the failure surfaces at `client.go:636` as the `context deadline exceeded` above.

Additionally, on repeated failure the board retries at the **full 2s cadence** with no backoff, hammering an already-struggling link.

What already works and must be preserved: on error, `apply` (`tui_board.go:50-58`) keeps the last-good `runs` and only sets `b.err`, so the board still shows the previous run list under the error banner — the data is not wiped.

This is genuinely triggered by a poor connection, but the polling design amplifies a survivable slow link into an error flood. Fixing the design makes the TUI usable on a marginal connection instead of self-congesting.

## Solution

Three focused, independently-testable hardening changes to the board (and detail-meta) poll loop. No change to the shared HTTP client, no new render surface required.

1. **In-flight guard.** Add an in-flight marker so a *periodic* tick never starts a new board poll while one is still pending; the pending poll's reply clears the marker. The same guard covers the detail-view meta poll with its own marker. **User-initiated** fetches (`keyRefresh` / `keyAdmin`) are never blocked — they may set the marker (so the next tick doesn't stack on them) but are always allowed to run.
2. **Per-poll request timeout.** `fetchRunsCmd` (and `refreshRunMetaCmd`) derive a short-lived `context.WithTimeout(m.ctx, boardPollTimeout)` (a package var, default on the order of 10s, so a test can shrink it), cancelled when the closure returns. This is **separate from** the 30s shared client timeout, which stays as-is for one-shot CLI calls and the stream handshake (`client.go:523` is not touched). Consequence: a stalled poll fails within `boardPollTimeout` instead of 30s, which also means the in-flight marker self-heals within that bound (a wedged poll cannot keep the guard latched for 30s).
3. **Error backoff on the reschedule.** Track a consecutive-error streak on `boardState`; the tick reschedule interval grows from `boardPollInterval` on each consecutive failure up to a cap (e.g. 2s → 4s → 8s → … capped ~30s) and **resets to `boardPollInterval` on the first success**. Implemented as a pure `boardTickInterval(errStreak)` helper feeding `tickCmd`, so the interval is unit-assertable without inspecting an opaque `tea.Tick`.

Interaction to state explicitly: the guard (1) prevents pile-up, the per-poll timeout (2) bounds each attempt and unlatches the guard, and backoff (3) spaces out attempts once the link is confirmed bad — together they convert the cascade into at most one bounded, backing-off request at a time.

## Success criteria

1. On a slow link, at most **one** periodic board poll is in flight at a time (proven by test: two back-to-back ticks with no reply → one `ListRuns`), and the same holds for the detail-view meta poll.
2. A stalled poll fails within `boardPollTimeout` (~10s), not 30s, and the in-flight marker clears afterward so polling resumes rather than wedging.
3. After consecutive failures the poll interval backs off and caps; the first success resets it to the 2s base.
4. The last-good run list still renders under the error banner on a failed poll (no regression to `apply`'s error path).
5. A manual `r` refresh always issues a fetch, even while a periodic poll is in flight.
6. `task gate` green across components; no rendered-frame regression; no `.github/workflows/**` touched.

## Decision Log

- **D1 — guard the periodic poll only; never the user's `r`/`a`.** A user pressing refresh on a slow link is expressing intent and expects an attempt; the pile-up hazard is the automatic 2s cadence, not the occasional keypress. User-initiated fetches may set the in-flight marker (so the next tick doesn't stack on them) but are themselves always allowed.
- **D2 — the in-flight marker must clear on EVERY reply, and the two polls have opposite shapes.** The board case and the detail-meta case early-return in different places, so the clear goes in a different spot for each:
  - **Board (`boardRunsMsg`, `tui.go:489`)**: the message case calls `apply` unconditionally, and `apply` itself early-returns on an admin/own-runs mismatch (`tui_board.go:47`). Put the board clear **in the message case, not behind `apply`'s early return**, so a mid-flight admin toggle cannot latch the guard.
  - **Detail-meta (`detailMetaMsg`, `tui.go:553-559`)**: this case early-returns on `msg.runID != m.detail.runID || msg.err != nil` (:554) **before** `applyMeta`. Clearing at the `applyMeta` happy path would leave the marker set on the `err` branch — precisely the flaky-connection case — wedging the detail-meta poll forever. Put the detail clear at the **top of the case, above the guard**. The runID-mismatch branch self-heals (drill-in resets detail state), but the `err` branch does not, so the top-of-case clear is mandatory.

  This asymmetry is the single non-obvious correctness point in the PRD and the reason M1's tests assert a `detailMetaMsg` with `err != nil` re-enables the next detail fetch.
- **D3 — per-poll timeout is separate from the shared 30s client timeout.** `client.go:523`'s 30s is correct for one-shot CLI calls and the stream handshake; shortening it there would harm unrelated commands. A per-request `context.WithTimeout` on the board closures scopes the shorter bound to exactly the high-frequency poll. A package var (not const) so tests shrink it deterministically instead of sleeping, matching the existing `boardPollInterval` / `rateLimitPollInterval` var convention (`tui.go:33,39`).
- **D4 — backoff via a pure interval helper, not by reading `tea.Tick`.** `tea.Tick` returns an opaque `Cmd`; asserting the reschedule interval means asserting a value, so the streak→duration mapping is a pure function the test calls directly. Reset-on-success (not a slow decay) so the board snaps back to live 2s cadence the instant the link recovers.
- **D5 — do not widen scope to the 60s/5m strip & skew fetches.** `fetchRateLimitsCmd` / `fetchSettingsCmd` / `fetchBuildInfoCmd` run at 60s / 5m (`tui.go:39,45`) and swallow their errors (never block the board), so pile-up is not a realistic hazard there and the 30s cap is proportionate. Keeping scope on the 2s board + detail-meta polls keeps the change small and reviewable. Revisit only if evidence shows otherwise.
- **D6 — TUI-only; no CLI or DTO surface.** The board is a `tuiModel` view; no non-TUI `api/cmd/uzi` command consumes this loop, and no wire type changes, so there is no CLI-parity or `fixtures/api-contract` work. Recorded so a reviewer does not go looking for it.

## Risks & mitigations

- **Guard latches and freezes a poll surface** (the real hazard, and the review's HIGH finding). The detail-meta case is the dangerous one: it early-returns on `err` (`tui.go:554`), so a clear placed after `applyMeta` would wedge the detail poll on exactly a flaky link. Mitigated by D2's per-case placement (board clear in the message case; detail clear at the top of the case, above the guard), by the per-poll timeout (M2) guaranteeing a reply within ~10s so no marker stays set on a wedged request, and by explicit tests: an admin-toggle-mid-flight sequence for the board and a `detailMetaMsg{err}` sequence for the detail poll, each proving the next tick fetches again.
- **Backoff makes the board feel stale after recovery.** Mitigated by reset-on-success (D4): one good poll returns the cadence to 2s immediately; the user also always has `r`.
- **Per-poll timeout too aggressive on a normal-but-not-fast link**, causing false failures. Mitigated by defaulting to ~10s (5× the poll interval, well above a healthy round-trip) and making it a var; tune from the product's own behavior, not a guess.
- **Rendered-frame regression from touching `tui_*.go`.** The change is behavioral and the visible error line is intentionally unchanged, so the worker's guard is M4's deterministic `View()→string` seam test (no devbox env needed); the uxlab PNG pass + `tui-ux` agent review are a maintainer post-merge confirmation, not a worker milestone.
- **Test that only checks "not two requests" passes vacuously.** Mitigated by requiring a positive-count assertion against a real fake-client call counter (M1), per the repo's vacuous-negative-assertion and `PASS=0` guidance.
