## A standing caveat on every measurement in this document

Dated **2026-07-25**, against `main` unless stated. Three classes of claim appear below and they are **not** equally reliable:

- **Repo facts** (call graphs, wire structs, migrations, committed manifests) — checkable by anyone with the tree.
- **Deployed facts** (what image tag dev-cluster runs, what the controller binary contains) — inferred from `main` unless a tag is named. `main` is ahead of the deployed tag.
- **Live facts** (DB rows, `/nix` contents, actual NetworkPolicy) — knowable only by looking, and **a migration is not a substitute for looking.** This PRD got that wrong once already (see the correction under §"The two tiers"), so every remaining instance is labelled inline.

## Problem

### 1. The per-run manifest carries no lock, so every run resolves against github

`provisionTools` (`agent/src/provision.ts:169-185`) synthesizes the run's manifest as **`{packages}` and nothing else** — no `devbox.lock` — then runs `devbox install`:

```
const manifest = JSON.stringify({ packages: input.packages }, null, 2) + "\n";
await fs.writeFile(path.join(input.runDir, "devbox.json"), manifest, "utf8");
...
await run("devbox", ["install"], { cwd: input.runDir, env });
```

An unlocked `devbox install` resolves the floating `nixpkgs-unstable` flake ref, which needs `api.github.com` (branch → commit metadata) and `codeload.github.com` (the nixpkgs source). It also consults devbox's own search service — **`search.devbox.sh`**, not the `search.jetify.com` that issue #82 named; `searchAPIEndpoint`, `internal/searcher/client.go:21` in the pinned **0.17.5** (`base/Dockerfile:108`), overridable only via `DEVBOX_SEARCH_HOST`.

The worker FQDN allowlist on dev-cluster is three entries (`deploy/values/dev-cluster.yaml:234-246`): `gitlab.example.com`, `*.anthropic.com`, `cache.nixos.org`. Antrea default-denies the rest. Verified from inside a worker pod during #78: `cache.nixos.org` CONNECT ok (120ms); `github.com` and `api.github.com` both TIMEOUT.

> **MEASURED LIVE 2026-07-25, and the answer is that WORKER TIER changes it — a distinction this PRD did not draw.** The two worker namespaces carry different egress:
>
> | | `uzi-workers` (standard) | `uzi-workers-docker` |
> |---|---|---|
> | egress rules | DNS + api `:8443` + web `:8080` only; external governed by the `uzi-worker-egress` ANNP | DNS + api `:8443` + **broad `0.0.0.0/0` except internal CIDRs** |
> | github reachable? | **no** | **YES** — `api.github.com` 200, `codeload.github.com` 301, `search.devbox.sh` 404 |
>
> So **§1's premise holds for standard-tier workers** — which is where #78 ran and what this PRD is about — but **provisioning would simply work on a docker-tier worker**, because that tier has broad internet egress by design (PRD #83).
>
> *(Recorded because the operator got this wrong first: an egress probe was run against the only worker that happened to be up, which was docker-tier, and the 200s were briefly read as falsifying §1 outright. Generalising from one pod across a tier boundary is the same error class as reading the allowlist off a seed migration. **M0 must state which tier every measurement came from.**)*
>
> Two consequences for scope: **(a)** M0(b)'s tier-2 reproduction must run on a **standard-tier** worker, or it will pass for the wrong reason; **(b)** a docker-tier worker combines broad internet egress with the §6 denylist bypass and `sandbox = false` (measured live, same day) — that combination is worth an explicit look in M1b rather than being left implied.

### 2. The allowlist and the image seed are different sets — and both columns below are approximations

| set | source | contents |
|---|---|---|
| tier-1 allowlist | `00046_tool_profiles.sql:38-40` | kubectl, terraform, jq, yq, ripgrep, fd, **go**, nodejs, **python3** |
| image `/nix` seed | `agent/devbox-global/devbox.json` | **go**, gcc, **python3**, pip, chromium, fontconfig, dejavu_fonts, openssl.bin |

**Left column is a FLOOR.** `00046` is the *initial* seed and its own comment says nothing re-seeds it (`:36-37`); admins add rows through `web/src/pages/ToolAllowlist.tsx` at any time, and at least one has — **ruby**, version policy `any` (see the correction below). So the live allowlist is a strict superset of these nine.

**Right column is a property of the DEPLOYED TAG, not of `main`.** It happens to be accurate today by luck, not construction: nothing after **v0.11.4** (2026-07-24) touches `agent/devbox-global/`, and `main` is one commit ahead. The check is `git log <deployed-tag>..main -- agent/devbox-global/`.

**So: at least eight allowlisted packages are unseeded** — kubectl, terraform, jq, yq, ripgrep, fd, nodejs, **plus ruby** — and the true count is whatever M0(a) measures. An admin can allowlist a package (`tool_allowlist.go:105-146`) and an owner can save a profile containing it (`tool_profiles.go:75-109`, which validates against the allowlist plus a count cap at `:99-102`, and nothing that can see the seed); the run then fails at 0 iterations on a hosted worker. Nothing in the write path can see the seed, so **the failure is discoverable only by running**.

### 3. A reseed wipes runtime-provisioned packages, and they cannot come back

From `controller/internal/kube/render.go:529-531`:

> *"A reseed WIPES the store, so any store paths per-run provisioning realized at runtime vanish"*

The version-aware seed (PRD #92 M2) reseeds whenever the image's toolchain-identity marker changes (`/etc/uzi-toolchain-profile`, a store hash — `render.go:518-536`). So **any** release touching `agent/devbox-global/devbox.json` wipes every runtime-realized package fleet-wide, and they cannot be re-realized with github blocked. The openssl and chromium promotions were themselves marker-changing rolls: the mechanism that delivers the workaround is the mechanism that detonates it.

> **Hypothesis, not measured:** that jq/yq/fd/ripgrep work on a given worker *because* an earlier run fetched them while github was reachable. Equally consistent with "nobody ever requested them, so they were never fetched." This is the premise for "the warm volume is a trap", so it deserves the one command that settles it: `ls /nix/store | grep -E 'ripgrep|jq'` in a live pod.

### 4. The workaround is now a habit, and it has run three times

`047b83d7` declared `openssl` tier-2 in this repo's `devbox.json`; `14336e0f` promoted it into the baked toolchain **because tier-2 could not provision it**; `devbox.json:32-34` records the promotion. Before that PRD #83 M1 baked go/python3/pip (**gcc is not #83's** — it landed separately in `b0f3c351`, 2026-07-19, citing no PRD) and PRD #87 baked chromium+fonts. Baking broadly-useful tools is correct and should continue — but it is being used as a *bug workaround*, one package at a time, with an image roll each time and no error telling anyone that is what is happening.

### 5. The failure is a hang, then a generic error

`provision.ts:184` throws `tool provisioning failed (devbox install): <err>`. Nothing distinguishes "bad package name" from "host not egress-allowed". The run burns to a generic timeout, and the judge read it as transient and recommended retry (#81) — a whole extra run.

### 6. Tier-2 bypasses the credential-CLI denylist — and this PRD's fix un-masks it

**This section exists because of the adversarial review. The first draft did not know this problem was here.**

`toolprofile.denylist` (`toolprofile.go:66-72`) bars 18 credential-bearing CLIs — glab, gh, hub, tea, awscli, awscli2, aws-sam-cli, azure-cli, google-cloud-sdk, gcloud, kubelogin, oci-cli, doctl, flyctl, heroku, vault, op, bw — with an explicit rationale (`:61-65`): *"a logged-in glab/gh/aws/az/gcloud reachable by the agent's Bash tool would bypass the 'worker holds the PAT, agent doesn't' boundary. This turns Decision 6 from advisory prose into enforced policy."*

It is enforced at both tier-1 write points and at claim. It is enforced at **neither tier-2 point**. Every refutation route was tried and failed: API claim assembly copies `RepoDevboxOptIn` as a bare bool and never sees a package (`service.go:927`); `PatchRepo` flips a boolean (`forge.go:589-635`); the worker goes straight from `mergeToolPackages` to `provision()` (`provision-run.ts:66-72`); `provisionTools` serialises the list verbatim (`provision.ts:176`); `buildSdkEnv` filters env *keys*, not packages (`sdk-env.ts:68-103`). There is no compensating control: `guardrails.ts` denies commands and paths — `git push`, remote mutation, force ops, git-config, `/proc`, `env`/`printenv`, `/run/secrets/*` — but **never CLI identity**; zero of the 18 names appear in `agent/src/`.

**This makes a shipped security comment false.** `provision.ts:21-22` states *"The admin allowlist still bounds WHICH packages install (their build hooks run in this scrubbed env)"* — the stated mitigation for the accepted single-uid residual documented at `:17-24`. Under `repo_devbox_opt_in` it does not bound them. **Fixed in this PRD's commit.**

**Exploitability — stated precisely, because the honest answer is not "yes".** Credential *pickup* looks closed in both postures: the agent subprocess env is a full replacement carrying no `GITLAB_TOKEN`/`AWS_*`/`VAULT_TOKEN`/`KUBECONFIG` (`sdk-env.ts:74-102`), `HOME` is a fresh per-run dir so `~/.aws/credentials` and `~/.config/glab-cli/` do not exist (`main.ts:88`), and the forge PAT rides `http.extraHeader` through env-scoped git config in the *worker's* process only, never landing in the clone's `.git/config` (`git.ts:442,524-544`). A freshly nix-installed `glab` has nothing to log in *with*.

What diverges is **build-hook reach**, and k8s — the primary runtime — is the exposed side:

| | compose / A1 split | k8s (#58) |
|---|---|---|
| provisioning uid | cap-less `runner` (`runner-uid.ts:88-91`) | the **worker's own uid** (`render.go:819-821`, `:733-734`) |
| join token | 0400 worker-owned | **0440 root:fsGroup, deliberately group-readable by 10001** (`render.go:718,727-733`) at a fixed path |
| what stops a build hook | the uid boundary | **nothing** — it runs inside `devbox install`, before the SDK, so the Bash `PreToolUse` hook never sees it |

**UNVERIFIABLE, not proven-exploitable.** `PKG_RE` drops flake refs and paths (`repo-tools.ts:20`), so a payload must be an *existing* nixpkgs derivation, and none reads `/run/secrets/`. No exploit was constructed and none is asserted. **The single check that settles it: `nix show-config | grep sandbox` in a live worker pod.** `Dockerfile:100` sets `NIX_REMOTE=""` (single-user nix), and single-user nix as a non-root uid typically cannot sandbox; if it cannot, this flips from "no known payload" to "any payload".

**Why it belongs in this PRD.** The egress block is currently masking all of it — nothing builds at run time on dev-cluster because resolution is blocked. **Fixing provisioning removes that accidental mitigation.** Shipping M2–M4 without M1b would make a currently-unreachable path reachable.

## Why this is the current state (in code)

Nothing here is an oversight. PRD #18 M3/M4 built provisioning when the worker was a compose container with unrestricted egress; resolution-at-run-time is correct for that. PRD #58 locked worker egress to three FQDNs on k8s — correctly. PRD #92 made the seed version-aware — correctly. The defect lives in the *seam*: no milestone owned "the set a run may install" against "the set the image can supply."

## The two tiers are two different problems

**Tier-1** — `repo_tool_profiles`, bounded by the admin `tool_allowlist`, re-validated at claim time (`service.go:938-970`). Finite and admin-controlled, so a seed can cover it.

**Tier-2** — the cloned repo's own `devbox.json`, merged in `provision-run.ts:54-64` when `repo_devbox_opt_in` is set (**measured live: `true` for `vtmocanu/uzi`**). Bounded by **shape only**: `PKG_RE`, a 128-char cap, a 64-package cap (`repo-tools.ts:20-22,84`). An **unbounded set of arbitrary nixpkgs attrs**, which no image seed can ever be a superset of.

> **A doc said otherwise, and it was corrected in this PRD's first commit** — the repo's own `devbox.json` claimed tier-2 packages must be "on the admin tool_allowlist". False, in two halves:
>
> **(a) The Go call graph**, exhaustively. `Resolve` has exactly two callers: `tool_profiles.go:107` (profile write) and `service.go:963` (claim). `Denied` has one (`tool_allowlist.go:129`) plus one internal read inside `Allowed` (`toolprofile.go:119`). **`Allowed` has zero external callers.** The two remaining `toolprofile` call sites, `tool_allowlist.go:71,123`, are `WellFormedVersion`/`WellFormed` — **shape checks, not rule checks**. All tier-1. `provision.ts:57` documents its own input as "the resolved TIER-1 package list (already allowlist-validated server-side)".
>
> **(b) The wire contract**, which is what actually closes it. A Go call graph proves the *api* never validates tier-2; it cannot prove the *worker* doesn't, because the worker is TypeScript and no Go call graph reaches it. The proof there is structural: `ClaimConfig` (`workersvc/claim.go:160-183`) carries exactly `ToolPackages []string` and `RepoDevboxOptIn bool` — **no rules, allowlist, or denylist field** — and its TS mirror carries the same two and nothing else (`protocol.ts:244,248`). The worker is **never sent a rule set**, so it structurally cannot apply one. No rule set exists anywhere in `agent/src/`.
>
> *(Half (b) came from the review, which noted the original argument was entirely Go-side and then asserted a property of a TypeScript path — true, but not shown. The enumeration in (a) was also wrong in that pass: it cited `tool_allowlist.go:123` as a `Denied` caller when it is `WellFormed`, and omitted `:71`. An argument staked on exhaustiveness has to be exhaustive.)*
>
> *(And the FIRST version of this correction was wrong too: it cited `ruby@3.3` as unlisted-yet-provisioning. Ruby **is** on the live allowlist, version `any`, noted "Homebrew formula ruby -c lint (tier-2 repo devbox); PRD #89 follow-up" — caught by the owner from the admin UI. `00046` is the initial seed; admins add rows at runtime. **Do not infer live-DB state from a seed migration.** The conclusion survived; the proof did not — which is the failure mode that gets past review, because the headline reads as confirmed.)*

**Testable prediction, unrun.** ruby is allowlisted (`any`) but **not** in the image seed, and github is unreachable — so a hosted run against this repo with `repo_devbox_opt_in` on should fail provisioning `ruby@3.3` today. That is §2's gap in live form, on the repo we develop in, produced by an admin doing exactly what the UI invites. **M0(a) must dump `repo_tool_profiles` as well as `tool_allowlist`**: if ruby is also in this repo's tier-1 profile it arrives via tier-1, and the spike would be exercising the wrong tier while believing it tested tier-2.

> **⚠ The failure mechanism is PACKAGE-SHAPE-DEPENDENT, so do not read a different host as a falsified premise.** From the pinned devbox 0.17.5 source (`internal/lock/lockfile.go:76-105`):
> - **Bare name** (`jq`, `kubectl` — every `00046` entry as seeded): `IsLegacyPackage` resolves **locally, no searcher call**; then `Stdenv()` resolves `nixpkgs-unstable` with an **empty `Rev`** (the synthesized manifest has no `nixpkgs` field), so `lockFlake` does not short-circuit (`resolve.go:214-227`) → `nix flake metadata` → **`api.github.com`**. §1's mechanism is exactly right *for this shape*.
> - **`name@version`** (tier-2's `ruby@3.3`; any version-pinned tier-1 entry): `FetchResolvedPackage` hits **`search.devbox.sh` FIRST** (`resolve.go:51-70`, or `resolveV2` at `:103` — `RESOLVE_V2` defaults ON, `featureflag/resolvev2.go:4`).
>
> So M0(b) will reproduce **a** failure, but at a **different host** than §1 predicts, because `ruby@3.3` is the versioned shape. **Treating that as "premise wrong, stop and rework" would self-abort on a correct result.** The prediction under test is *that provisioning fails*, not *which host it names*. M1's classifier must cover all three hosts; the good news is `execGet` returns a transport error **carrying the URL** (`internal/searcher/client.go:97-114`), so the host is always nameable. SC4's negative control must therefore use a **versioned** bad name — a 404 maps to `ErrNotFound`, a blocked connect does not.

## Solution Overview

1. **Fail fast and say why** (M1) — classify the egress failure. Independent of every design question; ship first.
2. **Close the denylist bypass** (M1b) — apply `Denied()` to tier-2. **Unconditional** (Decision 3-A): independent of everything below, breaks no legitimate repo, and **must not lag M2–M4** (§6).
3. **Make the seed a superset of the live allowlist** (M2).
4. **Gate the allowlist to the seed** (M3) — drift becomes an admin-time error instead of a run-time hang.
5. **Bound tier-2** (M4) — Decision 3-B, whose branch is determined by M0(c).

**Egress stays at three FQDNs.** Re-adding github (#82 option 3) was tried and reverted (`prds/69-judge-mode-and-per-user-model.md:42`).

## Design Decisions

**Decision 1 — Seed-superset for tier-1, not a lockfile.** The lockfile route needs no image roll per package but rests on an unverified premise (Decision 2). Seeding is *proven* — it is how go/python3/chromium/openssl already work, and it is the Dockerfile's stated rule (`base/Dockerfile:125-146`). M3 converts the per-package image-roll cost from a silent run failure into an admin-time error.

**Decision 2 — The lockfile route is a spike, not a plan; and there is a cheaper option next to it.** A committed lock removes the `api.github.com` metadata call for certain. It does **not** obviously remove the source fetch: every entry in the existing lock resolves to `github:NixOS/nixpkgs/20535e48…#<attr>` (`devbox.lock:8-15`) — a **flake ref, not a store path** — so nix must still evaluate nixpkgs.

**The blocker is not "no eval cache in the image" — it is a different `HOME` at run time.** The build-time `devbox global install` (`Dockerfile:146`) *does* populate `/home/worker/.cache/nix`. But `main.ts:88,124` pass `provisionHomeDir = <dataDir>/agent-home` and `buildProvisionEnv` (`provision.ts:114-122`) sets `HOME` to that, so the baked cache is never consulted. Same conclusion, far more actionable: M0(c) should test the variant that copies the build-time nix cache into the data-volume HOME (or points `XDG_CACHE_HOME` at it).

**Cheaper option the first draft missed, and it is one line.** Adding `"nixpkgs": {"commit": "20535e48…"}` to the *synthesized* manifest makes `Devbox.Stdenv()` (`internal/devbox/devbox.go:210-214`) read it via `cfg.NixPkgsCommitHash()` (`internal/devconfig/configfile/file.go:103-108`) and set `Ref.Rev`, which short-circuits `lockFlake` (`resolve.go:225-227`) — **removing the `api.github.com` call with no lockfile and no image roll.** Not a complete fix (the source fetch remains), but strictly cheaper than the lockfile route for the same partial win. M0(c) must evaluate it alongside.

**Decision 3 — SPLIT IN TWO. The security half ships unconditionally; the scope half is decided by M0(c)'s result, not by preference.** *(Owner-ratified 2026-07-25. The first draft deferred the whole thing; review reversed it to recommend-adopt; this is the settled form.)*

**3-A — `Denied()` on tier-2 (M1b). Unconditional. Not gated on anything in this decision.** It closes the §6 bypass, breaks no legitimate repo, and is **fail-closed when stale** (a stale denylist can only lack a newly-added entry, which the tier-1 path still catches at the next claim — unlike a stale *allowlist*, which is fail-open). Above all it is a **prerequisite of this PRD's own fix**: M2–M4 remove the egress block currently masking the bypass, so shipping them ahead of M1b would make a presently-unreachable path reachable. **There is no ordering in which deferring 3-A is correct.**

**3-B — full allowlist-bounding of tier-2 (M4). Decided by M0(c), and the branches are pre-committed here so the result is not re-litigated later:**

| M0(c) — does a committed lock make `devbox install` offline-capable? | ruling on 3-B |
|---|---|
| **RED** (it does not, incl. the Decision 2 variants) | **Adopt the narrowing.** It becomes the *only* route to a tier-2 that works on the primary runtime, and M0(d) will have shown the casualty set empty. |
| **GREEN** (it does) | **Do not narrow.** Tier-2 keeps its full range and works on k8s via the lock; 3-A already holds the security half. |
| **Ambiguous** (green locally, red in-cluster) | Treat as RED, per the Risks entry. |

**Why 3-B is not simply "adopt".** The genuine tension, which the recommend-adopt framing glossed: if the lock works, tier-2 could function *unbounded* on k8s, and narrowing would have removed capability for nothing. M0(c) costs an afternoon and converts the choice from a preference into a result. **If a ruling is needed before M0(c) runs, adopt** — the ledger today is an unenforced security control plus a tier-2 that cannot work on the primary runtime, weighed against a capability that is already broken there.

**A distinction to keep hold of, because it is easy to lose.** `Allowed()` passing `ruby@3.3` does **not** mean ruby provisions. The allowlist governs **permission**; the seed governs **availability**. Ruby is permitted and unavailable — precisely the gap M3's gate exists to surface. So 3-B is not itself a fix for anything: **M2 and M3 are the fix**, and 3-B only decides whether tier-2 gets to benefit from them.

**The residual under 3-B-adopt, stated honestly.** M0(d) inventories the fleet in about ten minutes (one SQL query plus one `glab api` call per opted-in repo — no clone, no run). That collapses the unknown to *no repo's **default branch** declares an unlisted tier-2 package today*. It does **not** collapse to "nothing can ever break": the worker reads `devbox.json` from the **run's worktree** (`provision-run.ts:55` → `extractRepoDevboxPackages(ctx.worktreePath)`), the agent's branch, not the default branch. Someone can add a package on a feature branch tomorrow — which surfaces as Decision 3a's named "not on the allowlist, ask an admin" notice rather than a silent hang. That is the whole residual; it is not an un-inventoried fleet.

**Decision 3a — Rejected tier-2 packages are DROPPED with notice, not run-failing.** Tier-1 rejection fails the claim (`errToolPackagesRejected`) because a profile is explicit user intent. Tier-2 is incidental repo metadata; failing a run because some repo's `devbox.json` names an unlisted package would be hostile. Drop each, naming it and the reason, on the existing status surface (`provision-run.ts:61` already emits "merged N package(s)").

**Decision 4 — `nodejs`: REWORKED, because the gate can never fire for it.** *(The first draft said "gate it, don't seed it" — impossible.)* `nodejs` is **already in the `00046` seed**, and `00046:36-37` says nothing re-seeds it. M3 gates `CreateToolAllowlistEntry`, an HTTP write path the seeded row never passes through. So on every deployment nodejs stays allowlisted, `SetRepoToolProfile` accepts it, `resolveTooling` accepts it, and the run dies at 0 iterations. Three options: **(a)** a migration deleting the row, **(b)** M2 seeds nodejs (a second, unrelated Node beside the image's `node:22-alpine`; the closure cost is **unmeasured** — an earlier draft asserted ~150MB with no source, which this PRD has no business doing while demanding measurements elsewhere), **(c)** move the gate to `SetRepoToolProfile` and/or `resolveTooling`.

**Take (c), and note what it costs.** It is the only option that makes SC1 literally true and the only one covering a hand-inserted row — and **it is incompatible with the "warn-not-block on existing rows" mitigation** in Risks, which would grandfather the exact row the gate exists to reject. Both cannot be carried; (c) wins and the mitigation is rewritten as a **reporting migration** that names offenders without refusing boot.

**Decision 5 — The api learns the seed via a generated copy + a golden.** `go:embed` cannot leave the **package** directory — verified empirically, `pattern ../../outside/data.json: invalid pattern syntax`, and that holds even *within* one module, so the operative rule is the package-dir one rather than the module boundary (`api/` being its own module, `api/go.mod`, merely removes the last workaround; there is no `go.mod` above `agent/`, and `go:embed` does not follow symlinks). Either way it cannot reach `agent/devbox-global/devbox.json`. Ship a generated copy under `api/internal/` plus a golden — the "three copies, cannot drift silently" trade PRD #58 made for preset labels. Skew between a rolled api and an un-rolled worker image is bounded by Model B (chart `version` == `appVersion`).

**Decision 6 — Ship the rule set to the worker in `ClaimConfig`; do not mirror the resolver. Ship the DENYLIST unconditionally; ship the allowlist only if Decision 3 is adopted.** M1b/M4 need the worker to apply rules to a package list that only exists after clone. `ClaimConfig` **already carries server-side policy for exactly this reason** — `SkillMaxBytes`/`SkillsMaxPerRun` are delivered so the worker "enforces the same limits (no hardcoded drift)" (`claim.go:168-174`) — and it already carries variable-size collections (`Agents`, `Skills`, `SkillsDropped`, `claim.go:915-917`), so a rules map is not a novel shape. No extra DB read either: `loadToolRules` already runs on every claim (`service.go:959-962,976-982`), and the denylist is a compile-time Go constant (`toolprofile.go:66-72`), pure serialization.

**Staleness is why the two halves are scoped differently.** `SkillMaxBytes` is a *ceiling*, so a stale copy is still a ceiling — fail-safe. Membership is not: a stale **allowlist** could permit something an admin removed a minute ago (**fail-open**), whereas a stale **denylist** can only be missing a newly-added entry, which the tier-1 path still catches at the next claim (**fail-closed**). That asymmetry is the argument for M1b shipping `Denied()` alone and leaving allowlist delivery to M4.

**Why not mirror the resolver into TypeScript:** the two copies would sit across both a module *and* a language boundary — precisely the situation Decision 5 concedes needs a generated copy plus a golden. So mirroring does not cost "a parity test"; it costs Decision 5's trade paid a second time. `ClaimConfig` removes the copy entirely.

**Wiring caveat:** the E2E stub executor runs the same `provisionRunTools` path (`executor.ts:351`), so the e2e claim fixture must carry the denylist or the stub path silently diverges from production and the e2e stops covering the check.

**Decision 6a — Batch toolchain additions: the RESEED is the cost unit, not the package.** Any edit to `agent/devbox-global/devbox.json` changes the toolchain store hash, hence `/etc/uzi-toolchain-profile`, hence triggers the version-aware reseed **fleet-wide** — which per §3 wipes every runtime-realized store path and clears the shared devbox/nix state under `/data`. So a 1 MB utility costs exactly as much to ship as a 648 MB browser closure. **Never spend a standalone roll on a small addition; ride an existing one.**

**Rider on M2 — add `file` to the global toolchain.** Surfaced 2026-07-25 during PRD #87's M7 gate run: a `web-ux` agent hit `exit 127`, `/bin/bash: line 1: file: command not found` while trying to identify a screenshot it had just captured. `file` is the right shape for the baked toolchain — tiny, broadly useful to any agent inspecting an artifact, not repo-specific — the same argument that promoted `openssl` out of tier-2 (`devbox.json:32-34`). It is **not** an allowlist candidate: the allowlist bounds what a tier-1 profile may `devbox install`, whereas this wants to be on every run's PATH unconditionally.

> **Live illustration of Decision 6a, from the same day.** The worker that ran the M7 gate provisioned tier-2 `ruby@3.3` cleanly *because its `/nix` was warm* (2 ruby store paths). Shipping `file` on its own would reseed, wipe those paths, and force a re-fetch — free on the docker tier (github reachable) and **fatal on a standard-tier worker**, which is §3's thesis reproduced in one package. That is the concrete reason to batch rather than a tidiness preference.

**Decision 7 — Seed growth is measured and `nixSize` re-validated.** `nixSize` is a flat 20Gi (`preset/preset.go:146` — *deployed-fact caveat: that is `main`'s value, and the controller binary in-cluster may lag*). jq/yq/fd/ripgrep are negligible; kubectl, terraform and any nodejs decision are the weight. M2 records image-size, build-delta and reseed-delta as PRD #87 M2 does.

## Success Criteria

1. A hosted worker with a **cold** `/nix` provisions **every entry in the live allowlist as dumped at M0(a)** — not "the 9 seeded names" — with egress still at three FQDNs.
2. An admin adding an unseeded package gets a 400 naming it and the image-roll requirement, **verified against a live api through a BROWSER, not the CLI** — `/api/tool-allowlist` sits under `mw.RequireAuth` (`handler/handler.go:523-524`), cookie-only, and a CLI bearer token is rejected (`{"error":"authentication required"}`, confirmed); and a *pre-existing* unseeded row (seeded or hand-inserted) is rejected at profile-save or claim, not silently accepted.
3. Two distinct tests, because one cannot cover both: **(i)** the Decision-5 golden asserting generated-copy == manifest; **(ii)** a test asserting migration-seeded allowlist names ⊆ seed manifest — **RED on 7 of 9 today**, and the thing that would have surfaced Decision 4's defect. Runtime-added rows are covered by the **gate**, not by any test, and no golden can change that.
4. A blocked-egress provisioning failure produces a classified, host-naming error within seconds. Positive control: it names the host, and a bad-package-name failure does **not** produce it.
5. A toolchain-changing image roll no longer strands packages — reseed, then a run using every live allowlist entry, green.
6. A tier-2 `devbox.json` declaring a denylisted CLI has it dropped with a named notice, on compose **and** k8s. **This criterion holds regardless of how 3-B resolves** — it is 3-A's, and 3-A is unconditional.
7. `nixSize` re-validated (or bumped) against the measured seed, numbers in the Decision Log.

## Risks & Mitigations

- **The seed grows as the allowlist grows.** Real; the gate makes it visible rather than preventing it. If it becomes painful, that is the concrete cost for the lockfile route to beat.
- **M3 breaks a deployment whose live allowlist already exceeds the seed.** It does — that is the point, and per Decision 4 it cannot be softened into warn-not-block without grandfathering the row the gate exists to reject. **Mitigate with a reporting migration** that names offenders at deploy time so the admin fixes them deliberately. Do not let the gate refuse to boot an instance whose data predates it.
- **M0(c) comes back ambiguous** (green locally, red in-cluster). Treat as red; M4's fallback is the design.
- **§6 gets deprioritised because no exploit was demonstrated.** The specific hazard: M2–M4 remove the egress block that currently masks it. **M1b is Phase 1 for that reason** and must not slip behind the milestones that un-mask it.
- **These measurements go stale.** Dated 2026-07-25; the standing caveat at the top says which class each belongs to. M0 re-checks the load-bearing ones before M2 spends anything.
