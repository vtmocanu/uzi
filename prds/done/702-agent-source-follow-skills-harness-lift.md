## Problem

Two independent gaps, one in each direction of the agent-source seam #602 built.

**A — consumption UX is bare.** #602 shipped the plumbing (configure a URL + ref, sync, stage, approve, apply) but the *source folder* is a hardcoded constant `sourceAgentsDir = ".claude/agents"` (`api/internal/agentsource/git.go:31`, single use at `readRoleFiles` → `tree.Tree(sourceAgentsDir)`, `git.go:417`). An admin cannot point uzi at a `product-agents/` subfolder, there is no one-click way to follow uzi's canonical roster (`github.com/vtmocanu/skills`) at its latest tag, and nothing tells an admin when that source has published a newer version — they would have to know to re-type a ref and hit "Sync now".

**B — worker-runtime context is baked into role bodies.** The instruction "the worker pre-installs this repo's JS deps in the background, so do not run `npm ci` / `npm install`" lives inside the builtin `coder` role *body* (`api/internal/agenttmpl/builtins/coder.md:18-22`). That couples prompt content to harness behavior and reaches only the roles whose body carries the line. The lead channel already carries a *generic, harness-level* version (`depsProvisionPlanNote()` / `depsProvisionImplementNote()` in `agent/src/prompt.ts`), but the **subagent** channel does not — so the coder (a subagent that does the implementation) depends on its body text for a fact that is really a property of the worker.

## Solution Overview

**Group A — sync-consumption UX (extends #602):**

1. **Configurable source folder.** A new `agent_source_folder` setting (default `.claude/agents`, so existing installs are unchanged) threaded through config → validation → `CloneOptions` → `readRoleFiles` → the read DTO → the web card → the CLI `get`. SSRF-neutral: it selects a subtree of an *already-allowlisted, already-cloned* repo and adds no new egress.
2. **Preset button.** One click in the admin card fills the source URL (`https://github.com/vtmocanu/skills`), the folder (`product-agents/`), and the **latest tag resolved at click time** (never a hardcoded version), via a lightweight backend ls-remote. The admin still reviews and Saves.
3. **"Update available" badge.** A lightweight `git ls-remote`-equivalent (reusing go-git's ref advertisement, **no full clone**) surfaces whether the source has a newer resolvable ref than what is running; a "bump pin" button writes the new ref. Applying still flows through the existing sync → approve → apply gate — the badge never applies anything.

**Group B — harness lift + builtin strip (agent runtime):**

4. **Harness lift.** Add a generic, repo-neutral worker-runtime dependency note to the **subagent** system-prompt channel (a shared constant appended in `agent/src/agents.ts` `toDefinition`, mirroring `FINDINGS_NUDGE_APPEND`), so every subagent — including `coder` — carries it regardless of body. The lead channel is already covered.
5. **Strip the builtin body.** Remove the worker-runtime lines from `coder.md`. **Harness-first** (M5 before M6): land and verify the harness carries the note and roll the worker fleet *before* stripping.
6. **Optional dev-roster cleanup.** Once the harness covers it, the conditionally-worded worker note in this repo's own `.claude/agents/coder.md:242-245` is redundant and removable — the only file under `.claude/agents/` this PRD touches.

Explicitly **not** in this PRD: any change to `vtmocanu/skills`; replacing the `go:embed` builtins (they stay the shipped default + offline/boot fallback, #602 D1); pre-filling the source URL by default (#602 D2 stands — the preset is an explicit click); exact "ahead by N commits" for a branch-pinned source (Decision 6); any `.github/workflows/**` change (Scope Guard).

## Design Decisions

1. **Reuse #602's approve-before-apply + provenance machinery verbatim.** The folder, preset, and badge only change *what source is configured* and *how the admin discovers a new version*; the staging → approve → apply pipeline, the `origin`-aware upsert, and the source-aware drift badge are untouched. This PRD adds no new way for a role change to reach a run without an admin approving it. The `go:embed` builtins remain the offline/boot fallback.

2. **The source folder is a repo-relative subpath, validated + normalized, needing no migration.** The `agent_source_*` config keys are admin-writable, synthesized from `Defaults` with **no seeded DB row** (`settings.go:398-406`, verified), so `agent_source_folder` is added to `Defaults` and needs **no goose migration**. Validation: a clean repo-relative path — reject a leading `/`, any `..` segment, and any scheme/host; **normalize a trailing slash** (`product-agents/` → `product-agents`) before it reaches `tree.Tree`. Default `.claude/agents` (the existing const proves a nested two-segment path already resolves via `tree.Tree`). Empty/unset resolves to the default so existing installs are byte-for-byte unchanged. It selects a subtree of the already-cloned, already-allowlisted repo — no new network reach, outside the SSRF surface.

3. **`git ls-remote` reuses go-git's ref advertisement — no `git` binary, no full clone, and it is the ONE new egress surface.** `FetchRoleFiles` already performs a single ref-advertisement round trip (`session.AdvertisedReferencesContext`, `git.go:168`) *before* any pack fetch (`fetchCommit`, `git.go:179`); the advertised `*packp.AdvRefs` carries every tag as an individual `refs/tags/<name>` entry in `References` (iterate the map for keys prefixed `refs/tags/` — there is no literal wildcard key), with annotated peels in `Peeled`. `resolveWant` (`git.go:378-384`) already resolves tags purely from the advertisement, proving a tag-list-only helper that stops after the advertisement (skipping `fetchCommit`) is feasible. go-git is pure Go (`go-git/v5`; `git.go` has no `os/exec`), so this works in distroless. This is the only *new* outbound-egress path in the PRD, behind the same SSRF allowlist + cookie-only admin gate as `sync` (Decision 5).

4. **Semver comparison follows the in-repo re-prefix + `IsValid` pattern, guarding BOTH operands.** `golang.org/x/mod/semver` treats every non-`v`-prefixed or malformed version as equal (`Compare` returns 0), failing *silently and open*. The precedent is `api/internal/forge/forgejo.go:173-184` (re-prefix with `v`, then `IsValid`-guard) — note it guards its *one* untrusted operand against a *trusted compile-time constant*; this feature compares **two untrusted tags**, so it must re-prefix and `IsValid`-guard **both** and skip any operand that fails (the correct, safer generalization of that pattern). "Latest tag" = the newest `IsValid` semver tag among the advertised `refs/tags/*`. Discriminating fixture for any test: `v1.10.0` must sort above `v1.2.0` (a lexical compare gets this wrong).

5. **The ls-remote seam has two callers with different credential sources; egress stays behind cookie-only admin, off the GET, off the read-only CLI token.** One helper, two entry points:
   - **Preset resolve** (M3): resolves the latest tag for a *typed, unsaved* URL. No saved credential exists for an unsaved URL, so this call is **anonymous** — it only works against a **public** source (the canonical `github.com/vtmocanu/skills` is public). SSRF-rechecked against `AGENT_SOURCE_ALLOWED_BASE_URLS`.
   - **Update check** (M4): ls-remotes the *configured, saved* source using its sealed `secretbox` credential; persists **remote facts** (see below).
   Both run in the cookie-only admin group (`RequireAuth` + `RequireAdmin`, the same gate as `sync` — verified at `handler.go:1075-1076`), never on `GET /admin/agent-source` (reads group, reachable by a read-only `uza_` token) and never on the CLI `status` path. The GET/`status` must perform **no** egress: assert (call-counting fake, count 0) that the ls-remote helper is not invoked on GET.

6. **Persist only REMOTE facts; DERIVE "update available" at read time so the badge self-clears.** The update check persists `agent_source_latest_ref`, `agent_source_remote_tip_sha`, `agent_source_update_checked_at` (engine settings, the pattern the last-sync/last-applied keys already use) — **not** a boolean. `GET`/`status` derive update-available from those stored remote facts + the **live** config (current `ref` / `agent_source_last_applied_sha`), so a pin bump or an apply clears the badge with no new egress. "Newer" is defined per ref type, and the branch-pinned case is a boolean (a shallow ls-remote yields only tips, not history):
   - **tag-pinned**: the newest `IsValid` semver tag on the source is strictly greater than the pinned tag.
   - **branch-pinned** (or empty = default branch): the advertised branch tip hash differs from `agent_source_last_applied_sha` — i.e. "the source moved past what is running." Exact "ahead by N commits" is **out of scope** (needs a fetch + history walk). The badge copy and docs say **"moved"**, not "N behind." Because a newer tip may already be **staged-awaiting-approval**, the badge copy distinguishes "source moved past what's running" from "a change is staged awaiting approval" (the latter is #602's existing staged state).
   - **SHA-pinned** (40-hex): no update signal (an immutable pin is intentionally frozen); no badge.

7. **The harness note reaches the SUBAGENT channel; the lead channel is already covered.** `agent/src/agents.ts` `toDefinition` composes every subagent's system prompt as `${t.prompt_body}\n\n${FINDINGS_NUDGE_APPEND}` (`agents.ts:156`) — appending a shared constant to every role regardless of body is the established precedent (it exists "so shared-library repo agents get it WITHOUT editing their files"), called for both roster paths (`agents.ts:248` own/builtin, `:302` repo). The generic worker-runtime note is added the same way, unconditionally. The lead's user-turn prompts already carry `depsProvisionPlanNote()` (defined `prompt.ts:618`, injected in `buildPlanPrompt` at `prompt.ts:803`) and `depsProvisionImplementNote()` (`prompt.ts:652`), so **only the subagent channel is the gap**. The note is generic (names no specific repo) **and carries the full actionable guidance the stripped body lines held, so the M6 strip drops nothing** — including the missing-module clause. Target wording: *"The worker installs the worked repo's JS dependencies in the background as the run starts (discovered by lockfile), and waits for that to finish before implementation. Do not run your own `npm ci` / `npm install`: `npm ci` deletes `node_modules` before reinstalling, and either command races that background install. If a targeted test fails on a missing module, report it rather than installing."* This matches what `agent/src/js-deps.ts` + `sdk-executor.ts` actually do and is a clause-for-clause superset of `coder.md:18-22`.

8. **Harness-first is defense-in-depth over an already-present backstop, and the ordering is one-directional (not atomic).** The hard implement-phase race — a subagent running its own `npm ci` while the background install is mid-flight — is **already prevented** by `joinDepsInstall` (`agent/src/sdk-executor.ts`, start ~:605, join-before-implement ~:1359, ~:1959), which is image-baked and prompt-independent and lives in any recent worker image. So a worker in the roll window does **not** hard-race the install; what it loses without the note is the coder's **discretionary** guidance to *report a missing module rather than self-install*. That makes the ordering honest defense-in-depth. The sequencing constraint is still real and one-directional: the strip changes a builtin body → api DB seed at api boot (**app tier**); the harness note is a constant in the **agent worker image**; PRD #422 rolls those on different cadences. So **M5 (harness) must land on the worker image and the fleet must roll onto it before M6 (strip) lands on the api tier** — "atomically with" is impossible under #422 decoupling and is not claimed. Roll caveat: a busy worker is **cordoned** and finishes its in-flight run on the *old* image (up to the 24h drain deadline), so "the fleet is on M5" can lag; the residual cordoned-straggler window is soft (covered by `joinDepsInstall`), and the roll-time confirmation should account for draining stragglers, not just idle workers. Post-ordering there is no gap in either direction (new-M5 worker + old-api body = a redundant note; new worker + stripped api = the harness note only).

9. **The dev-roster note is a separate, dev-only cleanup and is the only `.claude/agents/` touch.** `.claude/agents/coder.md` is this repo's dev-team roster, decoupled from the product (root `CLAUDE.md`: "product changes must never touch it") and never seeded into a worker. Its worker note (`:242-245`) is conditionally worded ("**When a uzi worker runs this repo**…"), so laptop dev is already unaffected. Removing it once the harness covers it is legitimate but is *not* part of the product strip — it is an optional final milestone (M7) touching only that note. Droppable/splittable to a maintainer-local issue with no effect on M1-M6.

10. **The strip needs NO version bump and MUST NOT touch `library/manifest.json`.** `agent_templates` has no version column; `RefreshPristineBuiltin` re-applies a builtin body by a **content guard** (`IS DISTINCT FROM` on description/model/tools/prompt_body, `agent_templates.sql.go`), so the stripped body reaches pristine installs on the next api boot **regardless of the `version:` frontmatter**. The `version:` integer is consumed **only** by `TestBuiltinLibraryDrift` (`library_test.go`), which requires the stamp to *exactly equal* `library/manifest.json` (errors on both `<` and `>`); `coder.md` is `version: 9` and the manifest says `9`. So: **keep `version: 9`, edit no manifest** — the strip is a uzi-local removal, not an upstream port, and the drift test stays green (9 == 9). Bumping to 10 without a matching manifest edit reddens the gate, and refreshing the manifest correctly would need the post-backport upstream SHA from `github.com/vtmocanu/skills` — an egress fact the offline worker cannot obtain. No test asserts the note text anywhere (`git grep -F 'races that background install'` under `api/` returns only `coder.md`), so removing it breaks no presence test. The strip reaches only **pristine** `coder` rows; an `admin`/`synced`-origin `coder` row keeps the old line until Reset — harmless (redundant with the M5 harness note), not incomplete coverage.

## Threat Model delta (relative to ADR-0602)

ADR-0602 / `prds/done/602:82` state "the fetch is the only egress and it targets the pinned ref." This PRD **supersedes** that: it adds one new egress path (Decision 3/5) and a genuinely new trust property — egress to an **unsaved, browser-supplied URL** (the preset resolves a *typed* URL before Save). That stale line in `prds/done/602:82` and the equivalent ADR-0602 wording are corrected in M2 (the milestone that makes them false). Controls, all reusing #602's machinery:
- **SSRF**: the URL is re-checked against `AGENT_SOURCE_ALLOWED_BASE_URLS` (`Config.AgentSourceBaseURLAllowed`) at the endpoint; https-only; the guarded transport (redirect allowlist re-check + cumulative wire budget) from `git.go` is reused. A ref advertisement is tiny.
- **Capability gating**: cookie-only admin (`RequireAuth` + `RequireAdmin`), same gate as `sync`; a read-only `uza_` CLI token cannot trigger it (Decision 5).
- **DoS**: the check is admin-triggered (not on every GET), single operation, 60s-bounded by the existing `cloneTimeout`.
- **Credential hygiene**: the preset resolve is anonymous (public source only); the update check uses the sealed configured credential; every error is PAT-scrubbed via the existing `scrubber` (`git.go:466`).
- **No new apply path**: the badge/preset only *configure* and *discover*; nothing reaches a run without the existing approve-before-apply gate. Blast radius, pinning, and the "no guardrail weakened" posture from ADR-0602 are otherwise unchanged.
- Group B adds a source of *prompt text* to the harness (not tools/credentials); the deny-hook, `settingSources: []`, and the worker-holds-the-PAT invariants are untouched.
