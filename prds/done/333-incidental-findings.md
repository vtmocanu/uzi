# PRD #333 — Incidental Findings: agents surface off-task bugs for one-click filing

- **Issue**: https://gitlab.example.com/vtmocanu/uzi/-/issues/333
- **Mock**: interactive UI mock (run-stream card, inbox ping, review-and-file editor, per-repo Findings backlog) built during PRD authoring — https://claude.ai/code/artifact/6a1d59ec-d754-4583-b4e3-1a71fc52c300
- **Status**: Implemented (all eight milestones landed on `agent/issue-333`, 2026-08-16)
- **Priority**: Medium

## Problem

While a worker implements a PRD, it routinely notices a bug that is **outside the task at hand** — a leaked ticker in a sweeper it read on the way to the code it was changing, a retry that can never succeed, a boot check with a hole. Today the worker has nowhere to put that. Its choices are all bad: smuggle an unrelated fix into the task's MR (widens the diff, muddies review, risks `main`-adjacent scope creep), mention it in prose the user never reads, or drop it. The observation is lost, and the user is never told.

Locally, Claude Code handles this by *asking* — "want me to file these as issues?". uzi runs are headless: nobody is watching the stream, so an interactive prompt is the wrong shape. We need the headless equivalent: the worker flags the finding without stopping its task, and the user is told **asynchronously** and files it (or dismisses it) on their own schedule, with the same guardrail every other forge write in uzi already honours — **the human gates every filing; the worker never writes to the forge.**

## Goals

- A worker mid-run can flag an off-task bug **without blocking or ending its turn** — it records the finding and keeps working.
- The user is told through the surfaces they already watch: a card in the run stream (if watching) and an **inbox + Slack** notification (if not).
- A finding becomes a real forge issue only on an explicit user action (file), on the user's own forge connection, with labels assembled server-side — never by the worker, never automatically.
- Findings **dedupe across runs** on a stable `(repo, location)` coordinate and collect into a **per-repo Findings backlog** the user triages (file / dismiss-with-reason), the way the judge backlog is triaged today.
- Repos are differentiated everywhere a finding is shown: the backlog groups and filters by repo, and each finding carries its repo, because the coordinate is repo-scoped by construction.
- All agent-authored text (title, description, location) is treated as untrusted and rendered inert, matching the existing proposal/judge sanitisation discipline.
- The feature is available on autonomous run lanes (issue / ci_fix / prompt / self_improve), **not** gated to a single kind.

## Non-goals

- **Auto-filing.** v1 is propose-then-file, matching every existing forge write. An opt-in "auto-file with an `agent-found` label, notify after" is a deliberate later extension (D9), not v1.
- **Findings on chat runs.** The in-app chat agent already has `propose_issue` (`agent/src/uzi-tools.ts`) for user-directed issue drafting. This feature is for *autonomous, off-task* discovery. (D2 explains why they are separate mechanisms rather than one.)
- **The judge producing findings.** The judge is retrospective and grades *the agent's own performance/config* (`improve_agent`, `adjust_template`, `improve_uzi`). Findings are mid-run and about *the user's code*. They reuse the judge's *backlog data-model shape*, not its producer.
- **AI / semantic dedup.** Dedup is a deterministic coordinate match, not a meaning match. A content hash (D3) only decides whether a *materially different* finding re-surfaces on a resolved coordinate; it is not fuzzy matching.
- **Cross-user or global findings.** A finding belongs to the run's owner and their repo, exactly like a proposal or a judge recommendation.
- **Overloading `issue_proposals`.** Considered and rejected — see D1.

## Context and current facts (verified against the tree, 2026-08-16)

All facts below are codebase-internal, confirmed by reading the tree and independently re-verified by three PRD reviewers; nothing here needs the open web (this PRD is handed to an offline worker with no web egress — see *Offline-worker readiness*).

### Forge issue creation (the filing primitive)
- `Forge.CreateIssue(ctx, projectID int64, title, description string, labels []string) (Issue, error)` — `api/internal/forge/forge.go:385`. Only title/description/label-names are settable. Implemented by all three drivers: `gitlab.go:327`, `github.go:345`, `forgejo.go:405`. **Forgejo takes label IDs, not names**, so its driver resolves names against the repo catalogue and errors on an unknown name — a marker label must be ensured to exist first (`Forge.EnsureLabels`, `forge.go:371`) before `CreateIssue` on a Forgejo repo.
- The filing precedent this PRD copies: `handler/review_issue_file.go` files a forge issue from a judge recommendation — labels assembled from server settings only (`:128-133`, **never from the request body**), `CreateIssue` at `:161`. `workersvc/composite.go` `ConfirmProposalForUser` (`:115`) is the **claim-first two-phase forge write**: `ClaimProposalForConfirm` (pending→confirming, `:120`), `CreateIssue` on the user's connection (`:150`), settle + stamp iid, revert on any post-claim failure. **Surface-agnostic**, called from web (`handler/chat.go:237`) and Slack (`slacksvc/chatactions.go:295`).
- **The sanitisers are generic and pure, but `issuedraft.Render` is NOT reusable.** `SanitizeTitle` (`issuedraft.go:320`), `SanitizeFiledBody` (`:311`), `FenceBlock`, `SafeInlineCode`, `ScrubSecretShapes` are field-level, feature-neutral and are the security-load-bearing pieces. `issuedraft.Render` (`:118`) itself is **judge-hardcoded** — headings like `## What the judge found`, `CategoryLabel()` over judge enums, an `Input` struct of judge fields (`Verdict`, `JudgeModel`, `ReviewDate`). Findings must build their **own** deterministic template that *calls the sanitisers*, not reuse `Render` (D4).

### The judge backlog family (the dedup / disposition / filed-issue precedent this PRD mirrors)
- `review_recommendations` (migration `00059_run_reviews.sql`) are per-run evidence, **deleted-and-reinserted per re-judge**; disposition and filed-issue links are therefore keyed on a **stable coordinate** `(review_id, category, target)`, not the churning row id:
  - `recommendation_dispositions` (`00073`): `status` `done|dismissed`, `dismiss_reason` `wont_do|not_an_issue`, a **`rationale_hash`** driving a "changed since you resolved" stale flag, CHECK `((status='dismissed') = (dismiss_reason IS NOT NULL))`.
  - `recommendation_filed_issues` (`00071`): same coordinate, a transient `filing_since` claim marker.
- **The judge's cross-run rollup is at READ time** (`Handler.JudgeRecommendations`, `handler/judge_recommendations.go:41`), deduping `(category, target)` across the caller's reviews, bucketed `todo|filed|done|dismissed|all`, highest-wins ranking, `?category=`/`?run=` filters. CLI `uzi review backlog`. Findings differ deliberately: they push dedup **into the storage coordinate** (D7).

## Design decisions (Decision Log)

**D1 — Findings get their own two-table store, modeled on the judge backlog, NOT on `issue_proposals` and NOT a single table.** The mock's first framing ("reuse the `issue_proposals` spine") is right for the *filing card* but wrong for the *v1 cross-run backlog*: `issue_proposals` is **per-run** (found by `run_id`, no coordinate, no backlog query, reconstructed from one run's stream). The v1 requirement — dedupe a bug seen in N runs into one row, triage it once, survive re-discovery — is exactly the judge's shape. So:
- `findings` — **per-run evidence** (one row per report; two runs finding the same bug write two rows; analogue of `review_recommendations`).
- `finding_dispositions` — the **coordinate-keyed lifecycle** (one per `(user_id, repo_id, location)`), collapsing the judge's two side-tables into one linear lifecycle: `status ∈ {open, filing, filed, dismissed}`, `filed_issue_iid`, `filing_since` claim marker, `dismiss_reason ∈ {wont_do, not_an_issue}`, **`content_hash`** (D3), `resolved_at`.

A **single** coordinate-keyed table (upsert latest title/desc, inline status) was also considered and rejected: it would lose the "seen in N runs" occurrence count that the backlog UX and R2 depend on, and the incremental cost of the evidence table is one migration. Overloading `issue_proposals` is rejected because it would bolt this same coordinate+disposition structure onto a table that also serves chat.

**D2 — Capture is a plain MCP tool on the run lane; the card-emit and id-return are new plumbing.** A finding must produce a persisted row **and** a stream card **and** return an ack while the agent keeps working — the `propose_issue` plain-tool shape, not the `report_progress` fire-and-forget signal shape. Concretely, this is **not** a copy of any single precedent: `forge-tools.ts` is the right *run-scoped, token-less* structure but emits nothing, and `propose_issue`'s emit lives in the chat executor. So M2 threads `ctx.emit` (or a batcher wrapper) into the new tool's deps, and `WorkerClient.reportFinding` **returns the created finding's id** (the `createProposal` analogue returns the proposal) so the emitted card carries an `{id}` its buttons can act on. The tool is non-turn-ending by construction (a plain tool never parks) and is registered on **all** autonomous lanes — deliberately not behind the `isIssueRun` gate that wraps `report_progress`.

**D3 — Coordinate is `(user_id, repo_id, location)` with a canonical `location`, plus a `content_hash` to re-surface materially-different findings.** `repo_id` in the coordinate is the whole answer to "how do we differentiate repos" — structural, and every read groups/filters by it. `location` is agent-supplied but **canonicalised server-side to a fixed form**: repo-root-relative path, forward slashes, leading `./` dropped, lowercased, whitespace-stripped, length-capped, plus at most one normalised symbol token (`file.go#sweepLoop`). Line numbers are excluded by the tool contract (they drift and would defeat dedup). Because the coordinate has no content discriminator, two *different* bugs at the same `file#symbol` would otherwise collide, and D6 suppression would permanently hide the second: so `finding_dispositions` carries a `content_hash` (sha256 of the normalised title+description, the judge's `rationale_hash` idea reinstated). A report whose coordinate is already `filed`/`dismissed` but whose `content_hash` **differs materially** re-opens the coordinate (new `open`, re-notify); an identical-hash report on a resolved coordinate is suppressed (D6). **Open for reviewer**: whether a missing symbol matches a present one (default: path+symbol are distinct coordinates; a symbol-less report matches only other symbol-less reports for that path).

**D4 — Findings get their own deterministic issue template that CALLS the sanitisers; the file endpoint resolves text from the stored row, never from the card payload.** Not `issuedraft.Render` (judge-hardcoded). The finding template routes each untrusted field through the matching sanitiser: title → `SanitizeTitle`; description → `FenceBlock` then `SanitizeFiledBody`; `location` → `SafeInlineCode`; and appends a provenance footer ("Found by run #N while working PRD #M"). The file endpoint (`POST /api/findings/{id}/issue`) resolves the title/description from the **stored, already-sanitised finding row by `{id}`** — agent-authored text never rides in through the request body. If the user edited the draft, only their edited title/description are accepted and are re-run through the same sanitiser passes; labels follow D5.

**D5 — Labels are server-assembled with one mandatory marker; user edits are additive and sanitised.** Filed labels = a server-mandated marker (`agent-found`, config-overridable) **∪** the user's sanitised, capped selection. The marker is `EnsureLabels`-ed first (Forgejo needs it to pre-exist). This gives the mock's editable-labels UX without a client-trusted trigger label (the `review_issue_file.go` rule).

**D6 — Notification is inbox+Slack via a new coalescing path, per-run, with resolved-coordinate suppression.** Kind `incidental_finding`; payload `{run_id, repo_id, repo_path, count, finding_ids}`. **Coalescing is new plumbing** (Context): M1 adds a find-unread-`(user_id, run_id, kind)` query and an update-payload query; M3 adds a `notifysvc` entry point that, for a run's *first* finding, inserts the inbox row and fires **one** Slack DM (`.Slack` populated: `Title "Run #N flagged M findings"`, `Link` to the run, `Emoji "🐛"`), and for *subsequent* findings on the same run updates the existing unread row's `count` **without re-firing Slack**. Suppression: a report whose coordinate is already `filed`/`dismissed` **and** whose `content_hash` matches records the evidence row but does **not** notify and does **not** re-enter the `to-file` bucket (so a dismissed bug stays gone across runs); a materially-different hash re-opens (D3). The suppression check is a benign read-then-notify: a report racing a concurrent file/dismiss of the same coordinate may emit one harmless extra ping — acceptable, not a correctness break (the `UNIQUE(user_id, repo_id, location)` + `ON CONFLICT DO NOTHING` makes the `open` insert itself atomic).

**D7 — The backlog read is disposition-driven and dedup lives in the storage coordinate (a deliberate divergence from the judge's read-time rollup).** `GET /api/findings` reads `FROM finding_dispositions LEFT JOIN findings` (not findings-driven), so a `filed`/`dismissed` coordinate survives even if its evidence rows are later cascaded away with a deleted run; it computes `seen_in_runs` from the joined evidence, buckets `to_file|filed|dismissed|all` from the disposition status (highest-wins), and filters by `?repo=`/`?run=`. This is *like* `JudgeRecommendations` but not "exactly": the judge dedups at read time and its disposition CASCADEs with one review; findings dedup in the coordinate and the disposition deliberately has **no run FK** (D12). Grouping/rendering by repo is a read concern; the store returns coordinate + repo + count + status + latest title.

**D8 — Findings are a new nav surface in the Work group with its own badge; the run-stream and notification surfaces reuse existing plumbing.** `Findings` `NavItem` in **Work** (a finding is work on *your code*, like Boards/Runs, not agent-grading). Its badge is a **new count source** (`CountOpenFindingsForUser`), separate from the shared bell `unread`; the open-findings count **rides on the `GET /api/findings` response meta** (the judge pattern) rather than a standalone route — no extra endpoint. The run-stream card is a new `finding` `run_messages` kind (no migration); the notification is a new `incidental_finding` renderer (`JudgeGroupRow` precedent). Accent is info/blue (D10).

**D9 — Auto-file is out of v1, but the schema leaves room.** The `finding_dispositions` status set and the server-assembled-label path are exactly what an auto-file mode would drive; adding it later is a create-time branch (insert the disposition straight to `filing`), not a schema change.

**D10 — Card accent is info/blue**, distinct from the amber gate (`question`/`plan`, which park the run) and orange (the user's own primary actions). A finding is a non-blocking side note. Cheap, reversible, flagged as a design choice.

**D11 — A per-run capture cap prevents a noisy run flooding the backlog.** `MaxFindingsPerRun` (default 10, mirroring `MaxPendingProposalsPerRun`): past the cap the tool returns a soft error ("finding cap reached for this run"), the agent keeps working. Combined with a tool description steering to genuinely off-task, actionable bugs (not style nits) and a `confidence` field.

**D12 — Retention: evidence CASCADEs with its run; dispositions intentionally orphan.** `findings.run_id → runs ON DELETE CASCADE` (evidence is per-run, mirrors `review_recommendations`). `finding_dispositions` has **no run FK** (it is a cross-run coordinate), so if every producing run is ever deleted the disposition orphans with zero evidence — desirable for `dismissed`/`filed` (they must stay resolved) but unbounded. There is no run-deletion path in the codebase today, so nothing cascades in practice; v1 states the retention story and accepts orphan accumulation. A `PruneFindingDispositions` analogue to `PruneNotificationsForUser` is a possible later addition, not v1. Because a `filed` coordinate must remain legible after its evidence is gone, `finding_dispositions` carries a `last_title` snapshot updated on each report.

## Milestones

Eight milestones. Success criteria are behavioural and validated by the repo's gate (`task gate:api`, `task gate:agent`, `task gate:web`) plus live-DB tests where the change is a store query. `-count=1` and `-race` are enforced at the Go gates; do not weaken them. **All forge interaction in tests uses a stubbed `Forge` driver** (the `ConfirmProposalForUser`/`FileIssue` test pattern) — an offline worker has no forge egress, so "an issue is filed" in every success criterion means *the fake `Forge` recorded a `CreateIssue` call with the asserted args and the disposition was stamped `filed`*, never a live forge call.

### M1 — Schema + store (foundation; owns the ENTIRE query set)
- Migration (drafts `00129`): `findings` (id, run_id FK→runs **ON DELETE CASCADE**, user_id FK→users, repo_id FK→repos, location text, title text, description_md text, labels jsonb, confidence text, created_at) and `finding_dispositions` (id, user_id, repo_id, location, `status` CHECK `('open','filing','filed','dismissed')`, filed_issue_iid bigint, filing_since timestamptz, dismiss_reason text, **content_hash text**, **last_title text**, created_at, resolved_at, **UNIQUE(user_id, repo_id, location)**, CHECK `((status='dismissed') = (dismiss_reason IS NOT NULL))`). `+goose Down` drops both.
- `sqlc generate`; the **full** query set lands here so no later milestone regenerates the foundation: `InsertFinding`, `UpsertOpenDisposition` (insert `open` via `ON CONFLICT DO NOTHING`; never resurrect `filed`/`dismissed` unless a caller-supplied content-hash mismatch re-opens — the re-open is a separate guarded `UPDATE`), `CountFindingsForRun`, `ListFindingsBacklog` (**`FROM finding_dispositions LEFT JOIN findings`**, deduped by coordinate, bucketed, `seen_in_runs`), `GetIncidentalFinding`, `ClaimFindingForFiling` (guarded `UPDATE … SET status='filing' WHERE (coord) AND status='open'` with a rows-affected check — not an INSERT-on-conflict), `SettleFindingFiled`, `DismissFinding`, `CountOpenFindingsForUser`, plus the two coalescing queries `FindUnreadNotificationForRunKind` and `UpdateNotificationPayload`. Declare each in `query_inventory_test.go`.
- **Success**: migration applies and rolls back on a live DB; the coordinate UNIQUE holds; `UpsertOpenDisposition` is idempotent and does not overwrite a `filed`/`dismissed` row; a content-hash mismatch re-opens a resolved coordinate while an identical hash does not; `ClaimFindingForFiling` moves exactly one `open`→`filing` and a second concurrent claim gets zero rows affected; the CHECK rejects a reasonless dismissal. A **normalisation/dedup** test asserts `"api/internal/Sweep.go "`, `"./api/internal/sweep.go"` and `"api/internal/sweep.go"` collapse to one coordinate, and that the same `location` under two `repo_id`s stays two coordinates. Live-DB tests throughout.

### M2 — Worker capture path (agent/src + api endpoint) — the load-bearing new seam
- **agent/src**: add `report_incidental_issue` as a plain MCP tool on the run lane (D2) — args `{title, description, location, labels?, confidence?}`, description steering to genuinely off-task actionable bugs and a symbol-anchored `location` (no line number). Thread `ctx.emit` into the tool's deps (new plumbing — `forge-tools.ts` shows the token-less run-scoped structure but emits nothing). Add `WorkerClient.reportFinding(runId, body)` → `POST /api/worker/runs/:id/findings`, **returning the created finding id**; on success `emit` a `finding` card carrying that id and return a terse ack. Register on all autonomous lanes; do **not** apply the `isIssueRun` gate.
- **api**: `WorkerCreateFinding` (mirror `WorkerCreateProposal`, `RequireWorker`, per-worker rate-limited) → `Service.CreateFinding`: derive `(user_id, repo_id)` from the claimed run (`GetRunByIDForUser`, never a client-sent id), enforce caps (`MaxFindingsPerRun`; `MaxIssueDescriptionBytes` from `service.go:58`, title/label caps), canonicalise+sanitise `location`, compute `content_hash`, insert the `findings` row, `UpsertOpenDisposition` (or re-open on hash mismatch), enqueue the coalesced notification (M3). Route registered in `mountWorkerRoutes` beside the proposals route.
- **Success**: an agent-lane test asserts `report_incidental_issue` is in the run-lane tool allowlist **and absent from the signal/park set** (so it can never be promoted to turn-ending) and is present regardless of `isIssueRun`; calling it posts a finding, emits a `finding` card carrying the returned id, and the turn continues; a `findings` row + an `open` disposition exist; the cap returns a soft error past `MaxFindingsPerRun`; user/repo come from the run row. Handler test covers `RequireWorker`, caps, derive-from-run, and `content_hash` computation.

### M3 — Notification (inbox + Slack), coalesced per run
- Add the `notifysvc` coalescing entry point using M1's two queries (D6): first finding for a run inserts the inbox row and fires **one** Slack DM (populated `SlackRender`); subsequent findings update the existing unread row's `payload.count` with **no** new Slack DM. Suppress entirely when the reported coordinate is already `filed`/`dismissed` with a matching `content_hash`.
- **Success**: reporting a finding creates exactly one inbox notification counting toward the bell `unread`; a second finding on the same run updates it to `count=2` (a table test asserts the row count stays 1 and the payload updates); the Slack seam `PublishNotification` is invoked once with a populated `SlackRender` (mocked) and is a no-op — never an error — when `s.slack == nil`; a finding on an already-dismissed matching coordinate creates no notification; a materially-different finding on that coordinate does notify (re-open). Table tests over coalescing, suppression, and re-open.

### M4 — Backlog read API + DTO (read-only; unblocks the web read surfaces)
- `GET /api/findings` (D7) — disposition-driven, deduped-by-coordinate, `?bucket=to_file|filed|dismissed|all` (default `to_file`), `?repo=`, `?run=`; response carries the rows (coordinate, repo, `seen_in_runs`, status, `last_title`, filed iid) **and** the open-findings count in meta (D8, judge pattern). `IncidentalFindingDTO` in `apitypes` with an `assertTags` wire test.
- `GET /api/findings/{id}/issue-draft` — the finding template (D4), sanitised.
- **Success**: the backlog dedupes a two-run finding into one row reading `seen in 2 runs`, buckets by disposition status, filters by repo, and returns the open count in meta; a `filed` coordinate whose evidence rows were deleted still appears (disposition-driven join, `last_title` shown); non-owner sees none of another user's rows; the wire test pins the DTO keys. ## Testing strategy

- **Stubbed forge everywhere.** No test performs a live forge call (offline worker); "filed" means the fake `Forge` recorded `CreateIssue(args)` and the disposition was stamped — the `ConfirmProposalForUser`/`FileIssue` pattern.
- **Store queries** (M1, M4) against a **live DB**: coordinate uniqueness + normalisation collapse, cross-repo separation, idempotent `UpsertOpenDisposition`, content-hash re-open, the `open→filing→filed`/`open→dismissed` state machine, the guarded claim preventing double-file, disposition-driven backlog dedup/bucket/repo-filter/meta-count.
- **`-count=1`** stays on at the Go gates.
- **Worker path** (M2): the tool is in the allowlist and **not** in the signal/park set, is present on all autonomous lanes, posts a finding, emits a card with the returned id, and the turn continues; the api derives user/repo from the run and enforces caps.
- **Notification** (M3): coalescing keeps one row and bumps `count`; Slack seam invoked once (mocked) and a no-op when unconnected; suppression + re-open.
- **Filing** (M5): server-assembled labels, claim-first double-file safety (concurrency test), owner scoping; the `apitypes` wire test.
- **CLI** (M6): `commands_test.go` enumeration + fake-backed verbs; exit-code contract.
- **Web** (M7): vitest for inert card render, bucket/repo grouping, gated actions, stale-card 409; a `VITE_UZI_MOCK=1` render pass.
- **End-to-end** (M8): the happy path and the anti-nag/re-open scenario, both offline.

## Risks and mitigations

- **R1 — Dedup coordinate drift / over-merge.** Mitigated by D3: `location` canonicalised to a fixed form (line numbers excluded), and a `content_hash` re-opens a materially-different finding at the same coordinate so distinct bugs are not permanently merged. Normalisation is tested (M1). Open reviewer question: missing-vs-present symbol matching (default: distinct).
- **R2 — Notification spam / re-nagging.** Mitigated by D6: coalesced per run, only the `open` bucket notifies, and a resolved matching coordinate never re-notifies — dismissing a bug makes it stay gone. The anti-nag guarantee is a dedicated M8 e2e criterion. The suppression race is a benign extra ping, acknowledged in D6.
- **R3 — Forge-write safety.** The worker never holds a forge token or calls `CreateIssue`; capture goes worker→api (`RequireWorker`) like proposals; filing is human-gated on the user's own connection via the claim-first write (D4). Filing text is resolved from the stored, sanitised row, never the request body.
- **R4 — Prompt injection via agent text.** `title`/`description`/`location` are untrusted. Mitigated by routing each through the matching field-level sanitiser (`SanitizeTitle`/`FenceBlock`+`SanitizeFiledBody`/`SafeInlineCode`, D4 — **not** `issuedraft.Render`), rendering inert in the web (escaped JSX), and server-assembling the marker label (D5). Branch only on the closed status/reason enums; treat all free text as data.
- **R5 — Forgejo label resolution.** `EnsureLabels` the marker before filing (D5).
- **R6 — Goose number collision.** Migration drafts `00129`, renamed above the live head at landing.
- **R7 — Scope creep into auto-file.** Deferred (D9); v1 is propose-then-file.
- **R8 — Overlap with the chat `propose_issue` path.** Avoided by D1/D2: separate table, endpoint, and lane; the chat path is untouched. And with `privcheck.Finding`: the store model/DTO is named `IncidentalFinding`.
- **R9 — Disposition orphan accumulation.** `finding_dispositions` has no run FK, so a fully-deleted run's coordinate orphans (D12). Acceptable in v1 (no run-deletion path exists today; `last_title` keeps a filed coordinate legible); a prune is a later addition.
- **R10 — Shared-file merge friction.** `handler.go`'s route table and the sqlc-generated files are the serialise points (not `findings.sql`, frozen in M1); the parallelization plan names them.
