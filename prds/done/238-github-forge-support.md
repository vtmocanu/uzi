## Problem

uzi has always claimed a forge-generic design — "GitLab first, others later" (`specs/human.md`). The `Forge` interface exists, the `forge_type` column exists and is already CHECK-widened once (`gitlab` → `gitlab, forgejo`, migration `00069`), and PRD #65 proved the abstraction by landing a second driver at full parity. Two drivers exist: `gitlab.go`, `forgejo.go`.

GitHub is the largest forge in the world and the one most prospective uzi users host their issues and repos on. Today they cannot use uzi at all. Unlike Forgejo (which was deferred on a *false* recorded blocker — see ADR-0065), GitHub was never blocked; it simply was not built. There is no wrong doc to correct here, only a driver to add.

The good news, and the reason this PRD is smaller than #65 despite GitHub being a bigger platform: **#65 already pulled every not-actually-abstracted layer behind the seam.** The three surprises that made Forgejo real work — the worker's un-abstracted GitLab client, the web's URL-by-string-surgery, and merge-permission modelling — are all solved. This PRD is a driver plus a handful of per-forge vocabulary entries, riding infrastructure that was built to take a third forge. ADR-0065's own Consequences section predicted this exact shape: *"Any future forge is a fourth thing: a driver file, its per-forge scope set, a `forgeNoun`/`pipelinestatus` vocabulary entry, and a `forge_types` advert."* This PRD is the test of that claim.

## Solution Overview

A `github` driver behind the existing `Forge` interface, at **full parity** with GitLab and Forgejo: board sync, runs, pull-request creation and watching, privilege guardrails, and the GitHub Actions CI-fix loop. The Go call sites do not change — `ForgeForConnection`/`ForgeForToken` already thread `forge.Type` through every one. Built on `github.com/google/go-github` (BSD-3), classic PAT auth, **github.com only** for v1.

The work is: the Go driver (`github.go` + `github_pipelines.go`), a GitHub arm on the four already-per-forge seams (privcheck scope rule, `pipelinestatus`/`pipelineBadge` status fold, `forgeNoun`/platform mapping, `agent/src/forge.ts` worker client), a one-line CHECK-widening migration, docs + ADR, and the go-live gate flip.

### Prior art (Inspiration-first convention)

Checked the two prior-art projects for a reusable GitHub client. **Neither is a drop-in** for uzi's PAT+REST `Forge` interface. **bottega** uses Octokit (TypeScript) — useful only as an endpoint-shape cross-check. **dot-agent-deck** has no GitHub API client. A hand-rolled GitHub **App** client pattern (JWT → installation token, GraphQL for mergeability, REST fallback) was also reviewed as an architectural reference for the *hard parts uzi does not need* (App JWT, GraphQL, installation tokens), though its secret hygiene (App key + tokens never logged or error-embedded) and a typed `RateLimitError{RetryAfter}` derived from `Retry-After`/`X-RateLimit-Reset` were worth citing as patterns — **not** the auth model itself (App, not PAT). uzi beats both prior-art projects on the axis that matters here: a forge-*neutral* interface with three drivers behind it, rather than a GitHub-specific one.

## Out of Scope

- **Fine-grained PATs and GitHub Apps.** v1 accepts classic PATs only (user decision, 2026-08-07). Fine-grained tokens do not expose their scopes for introspection the way classic tokens do (see D7), and GitHub Apps are a fundamentally different auth model (installation tokens, JWT signing, per-repo installs, webhooks) that does not fit uzi's per-user-PAT connection shape. Both are recorded as possible follow-ups, not this PRD.
- **GitHub Enterprise Server (GHES).** v1 is github.com only (user decision). The base-URL-driven design does not preclude GHES later; it is deliberately not validated or claimed here. A GHES base URL would be rejected by not being on the allowlist.
- **No fourth driver, and still no plugin/registry mechanism.** ADR-0065 said the third driver is the moment to reconsider a registry, "not now" being about the second. Three drivers behind a hand-written `switch` in `forge.New` is still not a framework; this PRD does not add one, but it does note (D12) whether the third driver's arrival changes that judgement.
- **No renaming of `MergeRequest`/`mr_iid`/`IID`** in Go, the DB, or the REST API — same as #65 D2. GitHub's PR `number` is a per-repo sequential id, structurally identical to GitLab's `iid` and Forgejo's PR `index`; one field carries all three.
- **uzi never creates branch protection.** Same as #65: that needs admin, which the least-privilege model forbids.
- **No GitHub Actions *workflow authoring*.** uzi reads Actions run/job status and job logs for the CI-fix loop; it never creates or edits workflow files — and on GitHub the required `{repo}`-only token *cannot* push a workflow-file change (the `workflow` scope is withheld, D7a), so an agent that tries fails at push. This is treated as an accepted constraint (arguably a CI-tamper-resistance feature), not a bug — see D7a for the open product question.
- **No webhooks.** uzi polls, on every forge; GitHub is no exception.

## Design Decisions

> **Research status (2026-08-07):** the GitHub-API facts in D5–D8 were verified against docs.github.com and the `google/go-github` source by an in-session research pass (sources cited in the Decision Log). The load-bearing facts are now confirmed; the handful still needing *live* confirmation against a real repo (rather than docs) are flagged **[verify-live]** and are M1/M4 acceptance items, not open design questions. The research also surfaced one hazard the initial draft missed — the `workflow` scope (D7a) — and one place uzi's semantics should be *narrower* than the raw GitHub enum (the CI-fix failure fold, D8).

### D1 — Full parity, or the forge is not supported

A GitHub user gets the same product as a GitLab or Forgejo user: same board, same guardrails, same CI-fix loop, no "GitHub-only" asterisks and no "not on GitHub yet" asterisks either. This is #65 D1 applied a third time. The CI-fix loop is explicitly in scope (user decision) — GitHub Actions job logs are always available on github.com, so there is no version-floor degradation branch of the kind Forgejo's D4 had to reason about.

### D2 — Terminology: GitHub says "Pull Request"

Same as #65 D2. Go types, DB columns, and the REST API keep `MergeRequest`/`IID`/`mr_iid`. Only user-visible copy switches, at the single mapping site `web/src/lib/forgeNoun.ts` (+ its Go twin `slacksvc/notifier.go`): a GitHub card says "Pull Request", abbrev "PR", reference sigil "#" (GitHub PRs and issues share one number namespace, so `#42` is correct), platform name "GitHub". This is the same vocabulary Forgejo already added; GitHub's entries sit beside Forgejo's. **No structural PLUMBING work** — `forge_type` already reaches the web per card and per run (#65 M8 did that, including the run-surface joins its own decision log corrected mid-flight). But **"only map entries" is false and was corrected in review (S3):** `MR_NOUN`/`PLATFORM` are additive `Record` maps, yet `mrAbbrev` and `mrRefSymbol` (`forgeNoun.ts`), the Go `slacksvc/notifier.go` twins, and the CLI `render.go` noun are binary `=== "forgejo"` **ternaries** whose default arm is GitLab's (`MR`, `!`) — a missing `github` arm renders `!42`/`MR` silently, the exact "default to one forge's word" trap D2 exists to prevent. And the connect form (`connectHints`/`botSetupDoc`) is per-forge copy that must gain a `github` arm or a GitHub user cannot connect at all (S2, M7). So M7 adds map entries **and** ternary arms **and** connect-form copy **and** unit assertions that GitHub renders PR/#/GitHub (SC3's grep only counts the GitLab literal; it does not verify the GitHub rendering — S7).

### D3 — Classic PAT auth; github.com only (v1)

The bot authenticates with a GitHub **classic** personal access token. The auth header is `Authorization: Bearer <token>` (GitHub also accepts the legacy `token <token>` form; Bearer is the current spelling). The connection base URL the user enters is `https://github.com`; the driver targets the API host `https://api.github.com`.

**"Classic only" must be ENFORCED, not merely intended (audit H4).** A fine-grained token (`github_pat_` prefix) cannot be introspected (no `X-OAuth-Scopes`, buggy expiry — D7), so if the driver just falls back to the introspection-unsupported *warning* path, the connect flow would **accept and save** a fine-grained token whose scopes were never checked (traced: `TokenInfo`→`ErrTokenIntrospectionUnsupported`→`evaluateToken` warns and returns before the scope check→`CheckToken` yields no Violation→`handler/forge.go:184` saves it). That silently defeats the over-privilege guard for exactly the token type whose breadth uzi cannot see. So the driver **refuses a `github_pat_`-prefixed token at `VerifyToken`** with a clear "fine-grained tokens are not supported yet; use a classic PAT (`ghp_…`)" error — fail-safe: refuse what you cannot introspect. This is a deliberately *different* disposition from GitLab's introspection-unsupported *warning* (which warns because that token's coarse shape is known); an un-introspectable fine-grained token's shape is unknown and potentially broader, so warn-not-reject is the wrong analogue. Pinned by a test (a `github_pat_` token is rejected at connect, not saved-with-warning).

**Driver client construction (audit S6, reconciled with the no-GHES scope):** production uses go-github's default base (`api.github.com`) — no override. Unit tests (`github_test.go`) and the M8 `/api/v3` fake must point the client at an `httptest` host, which uses go-github's base-URL override (`WithEnterpriseURLs`/`WithBaseURL`). **This is not "GHES support"** — it is the same base-URL-injection every driver's test harness uses (the GitLab/Forgejo tests do the identical thing). The Out-of-Scope "no GHES" line means uzi does not *validate, advertise, or claim* GHES as a product target and ships no GHES base URL on the allowlist; it does not mean the driver's client cannot be pointed at a non-default host, which it must be for tests. M1 specifies the one construction that serves both: default base for `github.com`, injected base for the test/fake host.

**The API host differs from the web host, and this is the one genuinely new base-URL wrinkle GitHub brings.** On GitLab and Forgejo the API lives under the same host as the web UI (`https://host/api/v4`, `https://host/api/v1`). On github.com the web host is `github.com` and the API host is `api.github.com` — a different subdomain, not a path. On the Go side go-github's default base URL is already `https://api.github.com/` (confirmed: `github.NewClient(...)` needs no base override for github.com), so the *driver* gets this for free. The **worker seam** still must map `github.com` → `api.github.com` when deriving the API base from a repo web URL, rather than appending a path (D9's `githubRepoParts`, mirroring #65's `forgejoRepoParts`). The allowlist stores the web host the user connects with (`https://github.com`); the SSRF guard is unaffected because `api.github.com` is a fixed, driver-internal derivation from an already-allowlisted host, not user input.

### D4 — No version gate

github.com is always current; every route this driver needs (issues, PRs, Actions runs/jobs/logs, repo permissions) is live and stable. There is no server-version floor, no `ErrForgeVersionUnsupported` path, and no `golang.org/x/mod/semver` comparison — the whole cluster of complexity Forgejo's D4/D4a carried does not exist here. (It would return if GHES were ever in scope, where the Actions-logs route history matters; it is not.) `VerifyToken` confirms the token works and returns identity; it never version-checks.

### D5 — SDK: `github.com/google/go-github/v90`

Use the maintained Go SDK (`github.com/google/go-github/v90/github`, v90.0.0, BSD-3). It has typed methods for every surface this driver needs: `Users.Get`, `Repositories.ListByAuthenticatedUser`/`Get`/`GetPermissions`/`GetBranch`/`ListRulesForBranch`, `Issues.*` (list/get/create/label add-remove-replace/`ListIssueEvents`/`CreateComment`), `PullRequests.Get`, `Actions.ListRepositoryWorkflowRuns`/`ListWorkflowJobs`/`GetWorkflowJobLogs`, `RateLimit.Get` (→ `*RateLimits`). (SDK names verified against v90 source: the rulesets method is `ListRulesForBranch`, not the pre-v87 `GetRulesForBranch` an earlier draft carried — see Decision Log.) Construction: `github.NewClient(github.WithHTTPClient(hc), github.WithAuthToken(tok))` — the injected `*http.Client` is exactly where the interface-mandated per-call timeout goes (`timeoutClient`, which go-github relies on since it has no separate timeout knob). This mirrors Forgejo's choice of an SDK over a hand-roll, justified the same way.

**One SDK ergonomic win over Forgejo:** go-github takes `ctx` per-method, so a **single long-lived `*github.Client` is safe to reuse** across calls — the driver does not need the gitea-SDK's rebuild-a-client-per-call dance (`forgejo.go:42-47`).

**Two warts to handle (both now confirmed):**
- **Job logs are a redirect the SDK does not follow to bytes — and the second hop is a NEW attack surface neither existing driver has (audit H5, elevated to R5).** `Actions.GetWorkflowJobLogs(ctx, owner, repo, jobID, maxRedirects) (*url.URL, *Response, error)` returns the parsed **redirect URL** to a short-lived **plain-text** job log (a 302 to a blob host, *different* from `api.github.com`; the *run*-logs endpoint returns a zip, the *job* endpoint returns text — the driver uses the job endpoint). `JobLogTail` must then GET that URL itself — and the naive "use the driver's `timeoutClient`" is unsafe: `timeoutClient` (`forge.go:447`) is a bare `http.Client{Timeout}` with the **default redirect policy (follows up to 10) and no host check**, while the `FORGE_ALLOWED_BASE_URLS` SSRF guard lives only at connection base-URL validation, not on this hop. A compromised/hostile forge (uzi already treats job logs as untrusted) could 302 to `http://169.254.169.254/…` or an internal service and have uzi fetch it, or replay the PAT cross-origin. So the second hop needs **Go-side transport guards that are the analogue of the worker's three D9 guards, treated as interface-level invariants**: (1) a **no-auth** client — never attach the PAT to the blob GET (the pre-signed URL does not need it, and must not receive it); (2) **refuse further redirects** (`CheckRedirect` → `http.ErrUseLastResponse`); (3) **require https and reject private/link-local/loopback hosts** (ideally allowlist GitHub's documented log domains). Then route the **body** through the PAT redactor and truncate to `maxBytes` from the end. **And never log the raw redirect URL** (audit M1): it is a pre-signed blob URL carrying its *own* short-lived token in the query string — a secret the PAT-only `newRedactor` does not know and cannot scrub — so any error mentioning it must strip the query string first. This is the GitHub analogue of GitLab's `/jobs/:id/trace` and Forgejo's `actions/jobs/{id}/logs`, but with a redirect hop those two do not have.
- **Token introspection is via response headers, not a JSON endpoint** — see D7.

### D6 — Guardrails: what a write-role bot can read on GitHub — the crux, and it is materially weaker than Forgejo

This is the one place GitHub is genuinely harder than Forgejo — the same area #65's security audit reshaped — so it gets the most scrutiny. The research confirmed the shape; the residual open question is a *live* one (does the rulesets endpoint reflect the calling bot's own rights), not a docs question.

uzi's bot holds **write** (push) access and never admin. On Forgejo `GET /repos/{o}/{r}/branches/{branch}` returns `user_can_push`/`user_can_merge` computed for the calling bot by the same code path the pre-receive hook enforces — a direct authoritative answer. **GitHub offers no such bot-scoped flag at write role**, and `GET /repos/{o}/{r}/branches/{branch}/protection` requires **`Administration: read`** (effectively repo admin — a write bot gets 403, the same wall #65 D6 hit on Forgejo's `branch_protections/` route). The confirmed reader-gated surface:

- **`GET /repos/{o}/{r}` → `permissions{admin, maintain, push, triage, pull}`** (booleans, computed for the authenticated user; go-github `Repository.GetPermissions()`). Authoritative for `ProjectRole` (`push:true,admin:false`→`RoleWrite`; `admin:true`→`RoleAdmin`) and for detecting an over-privileged (admin) bot. Backs `WriteRoleCanPush`'s "does the bot have push at all" half.
- **`GET /repos/{o}/{r}/branches/{branch}` → top-level `protected` bool**, readable at write role. Backs `BranchProtection.Protected` — always answerable. Its nested `protection` object detail is **not populated for a non-admin caller**, so it does *not* yield who-can-push/merge.
- **`GET /repos/{o}/{r}/rules/branches/{branch}` (rulesets) is `Metadata: read` → readable at write role** (go-github `Repositories.ListRulesForBranch`). It returns the **active enforced** rules on the branch (`pull_request`, `required_status_checks`, `non_fast_forward`, `update`, `creation`, `deletion`), excluding rules whose enforcement is `evaluate`/`disabled`. This is the reader-gated protection signal — but it has two documented limits below.

**Two limits that make this weaker than Forgejo, and drive the disposition:**
1. **Legacy branch protection is invisible here.** GitHub's classic *branch protection rules* and the newer *rulesets* are two independent systems. A repo protected the classic way exposes **nothing** through the rules endpoint at write role — the bot sees `protected:true` from Get-a-branch but cannot learn who may push. So the rulesets path only illuminates *ruleset*-based protection.
2. **The "rules that apply to me" semantics are under-documented.** [verify-live] whether `ListRulesForBranch` reflects the *calling bot's own* bypass ability (so an enforced `pull_request`/`non_fast_forward` rule genuinely means the bot cannot push), as opposed to just listing rules that exist. This is the one fact the research could not settle from docs and an M1 acceptance probe must (create a repo, add a ruleset, read as a write bot, observe).

**Disposition (fail-safe — reshaped by the security audit, which found the first draft's version internally unsatisfiable; see the note below):**
- `Protected`, `ProjectRole`, `member`: populated authoritatively from repo `permissions` + branch `protected` (all readable at write role).
- `WriteRoleCanPush` / `WriteRoleCanMerge`: authoritative **only when a ruleset covers the branch and is readable** (`Metadata:read`). On a **legacy-branch-protected** repo the branch-scoped push/merge answer lives only in the admin-gated `/protection` (403 for the bot), and `permissions.push` is **repo-scoped, not branch-scoped** — so it does **not** answer "may this role push to protected `main`". There, the driver sets both Can-push/merge fields **`false`** (never a fabricated `true`, which would make #66 refuse every properly-protected GitHub repo) **and sets a new `ProtectionUnverified` flag** so "undetermined" is never conflated with a verified `false`. `BotCanPush`/`BotCanMerge` stay false (GitLab-only, as the Forgejo driver already leaves them).
- **A new additive struct field, `forge.BranchProtection.ProtectionUnverified bool`.** This is the audit's H1 fix and it is load-bearing: the existing `evaluateRepo` (`privcheck/checker.go:154-211`) can only emit a Warning via its `roleErr`/`!haveBranch`/`bpErr` channels — the `Protected==true` path appends **only Violations**, and returning `bpErr` triggers an early return that *skips* the Protected check. So "report `Protected:true` truthfully AND emit a degradation warning, through the unchanged evaluator" is genuinely impossible without this field. `evaluateRepo` gains one branch: on `Protected && ProtectionUnverified`, append the warning "could not fully verify push/merge rights on protected `main`". Adding a struct field does **not** change the `Forge` interface method set and does **not** break the five fakes (they zero-value it → `false` → verified, the safe default) — but it *is* a change to a live privcheck path, so **M2 is not inert** (verify against existing privcheck tests, the #65-M3 caveat).
- **`#66` must treat `ProtectionUnverified` as fail-closed**, not read the absent Can-fields as safe. This is a consumer requirement recorded for #66, not built here — but without it, the audit's H3 stands: on a legacy-protected repo #66's `Protected:true, all-Can:false` predicate does **not** refuse, so the only thing protecting `main` there is layers 2–4, **not** #66.
- **`docs/github-bot-setup.md` leads with the operator obligation**: "protect `main` (or add a **ruleset** — legacy branch protection is not fully readable by the bot) and require pull-request reviews; on GitHub, uzi cannot always read, and never sets, this for you." Layers 2–4 hold regardless; layer-1 detection is honestly weaker on GitHub, stated not hidden.

**This is an ADR-worthy accepted limitation.** ADR-0238 records it explicitly: on a legacy-branch-protected GitHub repo, uzi's *detection* of a push/merge grant to protected `main` is undetermined and surfaces as a warning, not a Violation; #66 must fail-closed on `ProtectionUnverified`, and until it does, the primary directive rests on the other three guardrail layers there (which the audit verified hold end-to-end on GitHub: the worker only ever pushes the agent branch and never merges). This remains the single most important thing for review to pressure-test.

### D7 — Per-forge required scope set: `{repo}`, and why "least privilege" is coarser on GitHub

`privcheck.requiredScopesFor` gains a GitHub arm. A GitHub **classic** PAT's scopes are coarse by design: the minimum scope that grants private-repo contents write (git push), issues, pull requests, and read of that repo's Actions is the single **`repo`** scope (confirmed: Actions read rides on repo read; `repo` alone covers runs/jobs/logs on private repos).

So the required set is exactly `{repo}`. The "exactly, no more no less" semantics (`scopesEqualRequired`) carry over unchanged: fewer scopes fail `VerifyToken`/`ListProjects` already; more is over-privilege that PRD #5 blocks at save. A token with `repo, admin:org` or `repo, delete_repo` is a save-blocking violation — correct. **`workflow` is the one to think about — see D7a.**

**Honest caveat, stated because it is a real weakening vs GitLab/Forgejo:** GitHub's `repo` scope is broad — it grants full control of private repositories (contents, issues, PRs, statuses, webhooks, deployments) with no way to narrow to "issues + PR + push" the way Forgejo's three fine scopes do. uzi cannot make a classic PAT less privileged than `repo`; it can only refuse anything *broader*. This is inherent to classic PATs and is the strongest argument for a future fine-grained-PAT follow-up (which *can* express `Contents:write` + `Issues:write` + `Pull requests:write` + `Actions:read` + `Metadata:read`). It is documented, not solved.

**Token introspection via headers (confirmed mechanism):** GitHub has no `/personal_access_tokens/self` JSON endpoint. A classic PAT's granted scopes come back in the **`X-OAuth-Scopes`** response header on any authenticated request; the token's expiry in the **`GitHub-Authentication-Token-Expiration`** header (zero/absent = never expires); validity is simply whether the request 401s. So `TokenInfo` is **hand-rolled from response headers** — the driver must read `*github.Response.Response.Header`, not just typed fields (like Forgejo hand-rolled `TokenInfo`, for a different reason). A **fine-grained** token (`github_pat_` prefix) returns no `X-OAuth-Scopes` *and* a buggy expiry header (returns server-now, not real expiry — go-github #3708). Because it cannot be introspected, uzi **rejects it up front at `VerifyToken`** (D3, H4) rather than saving it on a warning — so on GitHub the `ErrTokenIntrospectionUnsupported` path is a defensive fallback, not the primary handling. Where the introspection-unsupported warning message *is* surfaced, it must be **made per-forge** (S4): keep GitLab's "requires 15.5+", do not flatten it to a generic string that degrades the GitLab hint. `site_admin` on `GET /user` maps to `BotIdentity.IsAdmin`, treated as a violation exactly as GitLab/Forgejo instance-admin is.

### D7a — The `workflow` scope: a new push-time hazard with no GitLab/Forgejo analogue

The research surfaced a GitHub-specific rule the initial draft missed and that touches the primary directive from an unexpected angle: **a `git push` that adds or edits any file under `.github/workflows/` is rejected by GitHub unless the token carries the `workflow` scope** (classic) / `Workflows: write` (fine-grained). uzi agents push arbitrary branches, so an agent whose change touches a workflow file will **fail at push time**, mid-run, with a GitHub error — unless the bot token has `workflow`.

This creates a genuine tension with D7's "exactly `{repo}`": requiring `{repo}` alone means workflow-touching pushes fail; permitting `{repo, workflow}` means a broader token uzi would otherwise flag as over-privileged.

**Recommended disposition (a safety feature, but the consequence is sharper than the draft said — review correction).** Keep the required set **exactly `{repo}`**, treating "uzi agents cannot modify `.github/workflows/` on GitHub" as an accepted, documented constraint — arguably desirable, since an agent then cannot tamper with the CI guarding the `main` uzi must never touch. When a run's push fails for this reason the worker surfaces the GitHub error verbatim (PAT-redacted). **The honest consequence, which the first draft understated (architect S5 / audit M2):** under strict `{repo}` equality, a token that carries `workflow` is a **save-BLOCKING** scope-set mismatch — uzi **refuses to connect it at all**, not merely "the agent loses workflow edits." So a user who legitimately needs workflow edits cannot use option (a) as-is. (The coarse `repo` scope's other powers — webhooks, deployments — are NOT agent-reachable, because the agent never holds the PAT, layer 2; the audit confirmed D7's coarseness is adequately mitigated there.) **RESOLVED 2026-08-07 (user): option (a) — forbid-and-document.** Required set is exactly `{repo}`; the driver **refuses a `workflow`-scoped token at connect** (over-privilege), and agent pushes touching `.github/workflows/*` fail at push with the GitHub error surfaced PAT-redacted. This is chosen as a deliberate CI-integrity boundary — an agent cannot tamper with the CI guarding `main`. Recorded in **ADR-0238** as a durable security decision, not just a decision-log line. The alternatives, kept for the record:
- **(a) forbid-and-document** — **CHOSEN.** Refuse a `workflow`-scoped token; CI-tamper-resistant; forecloses agent workflow edits entirely (a user needing those must wait for a fine-grained-PAT follow-up).
- **(b) allow-but-don't-require just `workflow`** — rejected: would break the clean "exactly" model (`scopesEqualRequired` growing a one-element allowed-extra set) for a use uzi deliberately does not want (agents editing CI).
- **(c) require `workflow`** — rejected: over-privileges every repo that never touches CI.

### D8 — GitHub Actions status: a two-field enum folded into one, added to the shared maps

GitHub Actions reports status in **two** fields (confirmed; go-github types both as `*string`, nil until concluded): a workflow-run/job `status` (`queued | in_progress | completed | waiting | requested | pending`) and, once `status == completed`, a `conclusion` (runs: `success | failure | cancelled | skipped | timed_out | action_required | neutral | stale | startup_failure`; jobs report the tighter subset without `stale`/`startup_failure`). `conclusion` is null until completion. (Note, fact-check N1: `startup_failure` is a real run conclusion but is **community/observed**, not in the official REST enum docs — the REST spec's Actions enums are themselves flagged incomplete upstream. So the `IsFailed` fixture must pin it, but treat the string as observed-behaviour, not doc-guaranteed: if GitHub ever spells it differently no doc pins it, and the e2e/fixtures are the only net.) uzi's `Pipeline`/`Job.Status` is a single verbatim string, so the driver **collapses the two fields into one**: while not completed, store `status`; once completed, store `conclusion`. This is the GitHub analogue of Forgejo's "two enums, not one" note, one layer trickier because the two fields are sequential rather than parallel. The driver stores the raw collapsed value; the two consumers below classify it.

**The CI-fix failure fold is deliberately NARROWER than "every terminal non-success", and this is a decision, not an oversight.** `pipelinestatus.IsFailed` is the CI-fix loop's *trigger* — it answers "should uzi spend a run trying to fix this build?", which is not the same question as the badge's "is this red?". So:
- **`api/internal/pipelinestatus/pipelinestatus.go` `IsFailed` (the fix trigger)**: add **`failure`, `timed_out`, `startup_failure`** (`failure` already present from Forgejo). **Deliberately excluded:** `cancelled` (a human cancelled — not uzi's to "fix"), `action_required` (a human must approve a gate/first-run — attention, not a code failure), `neutral`/`skipped`/`stale` (not failures). Folding `cancelled`/`action_required` into the fix trigger would make uzi launch a fix run at every cancelled or approval-pending build — wrong. (The research's raw "terminal failures" list is broader because it classifies *outcomes*; uzi's *fix trigger* is a narrower product judgement.) `IsSuccess` stays `success` only.
- **`web/src/lib/pipelineBadge.ts` `PIPELINE_TONES` (the badge)**: add `queued`→running, `in_progress`→running, `requested`→running, `timed_out`→failed, `action_required`→**attention**, `neutral`→neutral, `stale`→neutral, `startup_failure`→failed. Already-correct GitHub strings: `success`, `failure`, `cancelled` (two-L, GitHub matches Forgejo not GitLab), `skipped`, `waiting`. The **traps**: GitHub says `in_progress`, not `running`; `queued`, not `pending`; both must be added or an in-flight GitHub build renders neutral. `TestMirrorsWebPipelineBadge` pins the Go↔web correspondence — but note it pins the *failed/passed* tones, so the badge's `attention`/`neutral` entries for `action_required`/`stale` are web-only and not cross-checked against `IsFailed` (which is correct: they are neither failures nor passes). Update both maps together.

The collision claim (one merged, forge-blind map) must be re-audited for GitHub, and the audit must be *shown* in the map comment, not asserted (N10): every string GitHub *shares* with an existing key must *mean* the same thing. `success`/`failure`/`cancelled`/`skipped` do. `pending` — GitHub's commit-status API uses it for in-flight (already→running ✓). **`waiting` is the one genuine cross-forge collision** and must be called out: Forgejo's Actions `waiting` means in-flight (→running), while GitHub's run `waiting` means **blocked on a deployment-protection gate — a human must approve** (closer to `action_required`→attention). Because the map is forge-blind and the driver stores the raw string, the two cannot be told apart at the map. Resolution: keep `waiting`→running (the tone is a *nuance*, not a failure/pass, so no run is mis-triggered and no red build renders benign — the properties `TestMirrorsWebPipelineBadge` actually guards), and record in the map comment that GitHub's deployment-gate `waiting` is knowingly shown as "running" rather than "attention". If that proves confusing in practice, the GitHub driver can translate its own `waiting` before storing (the escape hatch, not the default).

### D9 — Worker seam: `GitHubClient` in `agent/src/forge.ts`, and the 422-vs-409 duplicate wrinkle

Add a `GitHubClient extends HttpForgeClient` beside `GitLabClient`/`ForgejoClient`. Per-forge bits only:
- `authHeaders`: `{ Authorization: 'Bearer ' + pat }`.
- `createUrl`: `POST {apiBase}/repos/{owner}/{repo}/pulls` where `apiBase` is `https://api.github.com` derived from the `github.com` web URL (D3 host mapping, via a new `githubRepoParts`).
- `createBody`: `{ head: sourceBranch, base: targetBranch, title, body: description }` (GitHub's `CreatePullRequest` shape; same-repo branch uses a bare `head` branch name — **[verify-live]** whether the bare form suffices or `owner:branch` is needed, an M6 acceptance item).
- `findOpenMr`: `GET {apiBase}/repos/{o}/{r}/pulls?state=open&head={owner}:{sourceBranch}&base={targetBranch}`, parse first result.
- `parseMr`: GitHub PR `number` → `iid`, `html_url` → `webUrl`.

**The one shared-base change: GitHub signals "PR already exists" with 422, not 409.** `HttpForgeClient.createMergeRequest` currently special-cases only 409 → find-existing (Forgejo's and GitLab's 409). GitHub returns **422 Unprocessable Entity** when a PR for the same head/base already exists. So the shared base must treat **both 409 and 422** as "maybe already exists → look it up", or `GitHubClient` overrides `createMergeRequest`. Preferred: widen the shared base's duplicate-detection to a driver-declared set of statuses (each driver already tolerates `findOpenMr` finding nothing), keeping the three transport guards (#65 D9: non-https refusal, `redirect:"error"`, dup→find-existing) as base-owned invariants a new driver inherits. Note 422 is GitHub's generic validation-error status, so `findOpenMr` finding no open PR must fall through to the real error (a 422 for some *other* reason must not be silently swallowed) — the same tolerance the Forgejo 409 path already has.

`forgeClientFor` gains a `github` arm. `ClaimRepo.forge_type` already exists (#65 D9) and already defaults absent→gitlab; the api emits `github` for GitHub connections. `runs.mr_web_url` already exists (#65 D8) and the worker already persists it at completion — **no schema or wire change on the worker path**, which is the seam #65 built and this PRD gets for free.

## Testing Strategy

`github_test.go` follows `gitlab_test.go`/`forgejo_test.go`: **hand-written `httptest` fixtures**, not recorded, so it needs no live GitHub in CI. A `mockGitHub` records `Authorization: Bearer <t>` and serves canned JSON.

1. **`ListIssues` filters out pull requests** (the #65 R4 trap, GitHub edition) — GitHub's `/issues` returns PRs too, each carrying a `pull_request` object; a mixed page in, issues only out. *Most likely to ship broken.*
2. **`ListProjects` filters on `permissions.push`** — a repo the bot only has `pull` on must not reach the picker.
3. **`UpdateIssueLabels` sends exactly one `PUT`** with the correct full set (an unrelated `keep-me` label survives the computed set), and **no-ops** (zero PUTs) when target==current.
4. **PR state mapping**: `{state:"open"}`→`opened`; `{state:"closed", merged:false}`→`closed`; `{state:"closed", merged:true}`→`merged`. GitHub uses `state` open/closed with a **separate `merged` bool** — not a distinct `merged` state — so the driver must read both.
5. **Issue-label-event mapping** (confirmed shape): `GET /issues/{n}/events` `event:"labeled"`→`add`, `event:"unlabeled"`→`remove`, each carrying an `actor` (login) + `created_at` + a `label{name}` — maps directly onto `forge.LabelEvent`. No raw-JSON workaround needed (unlike Forgejo, whose SDK mis-typed the label field); go-github `Issues.ListIssueEvents` is well-typed here.
6. **`ProjectRole`**: repo `permissions:{push:true, admin:false}`→`RoleWrite`; `{admin:true}`→`RoleAdmin` (a violation); `{pull:true, push:false}`→`RoleRead` (a violation). `member` derived from the `permissions` object (go-github `Repository.GetPermissions()`); **[verify-live]** what a non-collaborator on a *public* repo sees (a 403, or a `permissions` with only `pull:true`) — the analogue of Forgejo's "removed bot on public repo still 200s" derivation (#65 D7), an M1 acceptance probe.
7. **Branch protection (D6)**: `protected:false`→unprotected Violation (via the shared `evaluateRepo`); `protected:true` + `permissions.push:true` + a rulesets response with an enforced `non_fast_forward`/`pull_request` rule → push handling per D6; `protected:true` with `/protection` 403 and no readable ruleset → the degradation *warning*, never a silent "safe". **Assert the driver never calls the admin-gated `/branches/{b}/protection`** (it 403s a write bot — same discipline as #65's "never call `branch_protections/`"). The `ListRulesForBranch` bot-scoped-semantics fixture depends on the [verify-live] probe (R1).
8. **Per-forge scope rule (D7)**: exactly `{repo}` passes; `{repo, workflow}` and `{repo, delete_repo}` are save-blocking violations (superset); `{public_repo}` alone fails (subset — would have failed `ListProjects` anyway, but pin it). GitLab's `{api}` and Forgejo's three-scope rule unchanged. Header parsing: `X-OAuth-Scopes: repo` → `["repo"]`; a fine-grained token (no header) → `ErrTokenIntrospectionUnsupported` → warning, not violation.
9. **Actions status fold (D8)**: driver collapses `{status:"in_progress", conclusion:null}`→`"in_progress"` and `{status:"completed", conclusion:"failure"}`→`"failure"`. `pipelinestatus.IsFailed`: `failure`/`timed_out`/`startup_failure` true, `success`/`cancelled`/`skipped`/`neutral` false. `pipelineBadge` tone table: `in_progress`/`queued`→running, `timed_out`/`startup_failure`→failed, `action_required`→attention. `TestMirrorsWebPipelineBadge` stays green.
10. **CI logs**: `ListPipelineJobs` parses the job list; `JobLogTail` follows the log redirect (fixture the 302 → plain-text URL) and truncates to `maxBytes` from the **end** (D5).
11. **Redaction**: a GitHub error carrying the PAT is scrubbed. `redact.go` is value-based (`strings.ReplaceAll(s, token, "[REDACTED]")`), so `Authorization: Bearer <t>` is covered by construction — but the driver must route **every** error path through it, **including the hand-rolled header-based `TokenInfo`** and the second-hop log fetch (both outside the SDK). Note `newRedactor` ignores secrets under 8 chars — fine for GitHub's 40-char classic PATs (`ghp_...`).
12. **Pagination**: two-page `ListProjects` — go-github does **not** auto-paginate, so the driver loops on `Response.NextPage` until 0 (identical shape to Forgejo's `resp.NextPage==0` loop). Use `githubPerPage=100` (max).
13. **Rate-limit surfacing**: go-github returns `*github.RateLimitError` (primary) / `*github.AbuseRateLimitError` (secondary, `RetryAfter`); the driver surfaces a redacted, non-panicking error via `errors.As`, not a misread permission failure.
14. **`UpdateIssueDescription`** (S1): `PATCH` the issue `body` and read it back — pins the method that `forgesvc/prd_link_patch.go` calls, so PRD-link auto-patch works on GitHub. A stub would pass compile and silently no-op; the test must assert the body actually changed.
15. **Fine-grained token rejected at connect (H4)**: a `github_pat_`-prefixed token is refused by `VerifyToken` with the classic-only message and is **not** saved; a classic `ghp_` token proceeds. Guards the "classic only" invariant against the silent-save path.
16. **Job-log second-hop transport guards (H5)**: a `JobLogTail` whose redirect points at a private/loopback/non-https host is refused (no fetch); the fetch of a valid blob URL carries **no** `Authorization` header and does not follow a further redirect. Guards the SSRF/PAT-leak surface.

**e2e**: extend `e2e/forge-fake/forge-fake.mjs` with a `/api/v3/*` route table selected by path prefix, sharing state and the existing git smart-HTTP handler with the `/api/v4` and `/api/v1` tables — a third table on the same fake, never a third fake. `UZI_E2E_FORGE=github`, default `gitlab`. Per CLAUDE.md, e2e stays a local pre-merge gate, not CI. Any compose smoke uses the isolated-project incantation (`env -i … --env-file <dummy> -p <unique>`), never a bare `up` against the real `.env`.

## Risks

- **R1 (D6, high) — merge/push detection on protected `main` is UNDETERMINED (not just "degraded") on legacy-branch-protected GitHub repos, and #66 cannot cover it as currently specified.** Confirmed: `/protection` is admin-gated (403 for a write bot); the reader-gated rulesets endpoint only illuminates *ruleset*-based protection, so a classic-branch-protected repo gives the bot no reader-gated push/merge answer. uzi reports `protected:true` + the `ProtectionUnverified` warning, never a false "safe" in the badge. **Correcting the first draft (audit H3 / architect B1):** #66 must NOT be credited for this case — its `Protected`-first predicate reads `Protected:true, all-Can:false` as *allow*, so until #66 is taught to fail-closed on `ProtectionUnverified`, the only thing protecting `main` on a legacy-protected GitHub repo is **layers 2–4** (worker only ever pushes the agent branch, never merges — audit-verified), not #66. Documented in the setup doc and ADR-0238. **The rulesets bot-scope question is a design SPIKE, not an M1 checkbox (architect B1):** whether `ListRulesForBranch` reflects the *calling bot's own* bypass ability decides whether the "derive `WriteRoleCanMerge` from rulesets" path is real or itself a false-safe. It must be executed (create repo → add ruleset → read as a write bot) and **both outcomes written into `DefaultBranchProtection`'s design before M1 finalizes it** — the exact #65 shape of a riskiest assumption read from docs and never run.
- **R2 (D8, medium) — the Actions two-field collapse is the CI-fix loop's silent-failure surface**, exactly the class #65's e2e caught three times. A missed failure spelling (`timed_out`, `startup_failure`) means a red GitHub build never triggers a fix, invisibly; conversely, wrongly folding `cancelled`/`action_required` into the trigger makes uzi launch fix runs on human-cancelled or approval-pending builds. Pinned by fixtures (#9), the e2e (M8), and `TestMirrorsWebPipelineBadge`.
- **R3 (D7a, medium) — the `workflow` scope hazard.** A `{repo}`-only token cannot push a change touching `.github/workflows/*`; an agent that tries fails at push mid-run. Treated as an accepted constraint (D7a), but the product must confirm the disposition (forbid-and-document vs permit-as-extra vs require) and the worker must surface the push error clearly. This is the one decision in this PRD genuinely left to the user.
- **R4 (D7, medium) — `repo` scope is coarse; least-privilege is weaker on GitHub.** Accepted and documented; the mitigation is the future fine-grained-PAT follow-up, out of scope here. uzi still refuses anything broader than `repo`. Fine-grained tokens additionally cannot be introspected at all (no scopes header, buggy expiry header — go-github #3708), so a fine-grained token degrades scope-check to a warning.
- **R5 (D5, HIGH — raised from the draft's "low" by the audit) — the job-logs second hop is a new SSRF + PAT-leak surface.** `GetWorkflowJobLogs` returns a redirect `*url.URL` to a plain-text log on a *different* (blob) host; fetching it with the default-redirect, no-host-check `timeoutClient` lets a hostile forge redirect uzi to an internal address, and attaching the PAT to that GET (or following a further redirect) leaks it cross-origin. **Critical if implemented with the authenticated/default-redirect client.** Mitigation is the three Go-side transport guards in D5 (no-auth client, `CheckRedirect`→`ErrUseLastResponse`, https+host validation) plus never logging the raw pre-signed URL. Neither existing driver has this surface (their SDK trace fetch stays on the allowlisted API host). Fixture the redirect + a redirect-to-internal-host rejection in test #10.
- **R6 (D9, low) — 422-vs-409 duplicate PR.** The shared worker base hardcodes 409; GitHub uses 422 (its generic validation status). Widen the base's duplicate set and keep the fall-through-to-real-error tolerance. Caught by an M6 test that fires a duplicate create and asserts find-existing returns the open PR.
- **R7 (low) — rate limiting.** GitHub's 5000/hr primary limit and stricter secondary limits (concurrency, `Retry-After`) are tighter than GitLab's; go-github surfaces `*RateLimitError`/`*AbuseRateLimitError`. The driver must redact-and-surface these as errors (not misread a 403 rate-limit as a permission failure). The #74 cross-driver DoS hardening applies; decide whether to surface `Retry-After` distinctly or treat it like any other redacted error.
- **R8 (cross-PRD, medium — the #122 checkpoint push-broker) — the per-checkpoint pipeline-suppression is GitLab-specific and does nothing on GitHub.** PRD #122's **M8** (deferred, gated-on-evidence; `adr/0122-checkpoint-push-broker.md`) adds a server-side api push-broker that publishes each run checkpoint to `refs/heads/<branch>` via a pure-Go go-git smart-HTTP push, **suppressing the per-checkpoint pipeline with the GitLab `ci.skip` push-option** (its success criterion is literally "checkpoints fire **zero** extra pipelines"). #122 itself flags "one residual is **forge-specific smart-HTTP behaviour**, validated against `gitlab.example.com`." **Verified (docs.github.com):** GitHub Actions has **no `ci.skip` push-option** — a run is skipped only by a **commit-message marker** (`[skip ci]`, `[skip actions]`, …) on push/PR events. **GitHub is not special here — it shares this with the currently-shipping Forgejo driver:** Forgejo Actions (= Gitea Actions) also skips only via a commit-message marker (verified in Gitea source, `services/actions/notifier_helper.go`, `setting.Actions.SkipWorkflowStrings`), so `ci.skip` is **GitLab-only among all three forges** and M8's guarantee is already broken for Forgejo, independent of #238. So on a GitHub repo the broker's push-option is inert and **every brokered checkpoint would fire a fresh GitHub Actions run** — wasted Actions minutes, and worse, those in-flight/failed checkpoint pipelines feed **this PRD's** Actions-watching CI-fix loop + pipeline badge (D8), which could misread a mid-implementation checkpoint's red build as a fixable failure. **Disposition:** the broker is #122's build, not #238's, and M8 is deferred — so this is recorded as a **seam whichever PRD lands second must own**, not a #238 milestone. If M8 lands with GitHub live, its checkpoint-push path needs a GitHub-specific skip (rewrite/annotate the checkpoint commit with a `[skip ci]` marker before the brokered push, or don't publish checkpoints to GitHub branches carrying a `push`-triggered workflow) — a Forge-driver-level concern, since "how do I suppress CI on a push" is exactly the kind of per-forge knowledge the interface is meant to hold. Flag: the other clean git-facts also apply — the broker pushes to `origin` (the github.com clone URL, correct for git; distinct from `api.github.com`, D3) and authenticates via go-git BasicAuth (GitHub token as password), both forge-neutral enough to work, leaving `ci.skip` as the one real gap.

4. Privilege checks surface the GitHub scope rule (`{repo}` exact) and branch-protection findings; a GitHub `site_admin` bot or an over-broad token is flagged; a fine-grained (`github_pat_`) token is refused at connect (H4), not saved on a warning. For merge/push on protected `main`, the report is either an authoritative finding (rulesets readable) or a `ProtectionUnverified` **warning** (legacy protection) — never silently missing, and never a false "safe" in the badge.
5. The e2e `UZI_E2E_FORGE=github` lane passes locally.
7. `docs/github-bot-setup.md` leads with the operator's branch-protection obligation (D6, ruleset-not-legacy), passes `check-docs.mjs`, and renders in-app. ADR-0238 records the third-driver design, the D6 accepted-limitation (+ the `#66` fail-closed-on-`ProtectionUnverified` requirement), the D7a `workflow`-scope resolution, and the D12 "still no registry" judgement.
