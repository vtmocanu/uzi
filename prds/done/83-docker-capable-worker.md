## Problem

The worker has no Docker, by design. The `base` image ships `git + bash + node` plus nix/devbox for per-run CLI tools (PRD #18), and the runtime is deliberately locked down: `cap_drop: ALL`, `no-new-privileges:true`, non-root `worker` uid (10001) with a distinct cap-less `runner` uid (10002) for code execution (#51), **no `docker.sock`** (`specs/ai.md` §36: the worker *"never listens. No `docker.sock`"*). Tool provisioning is rootless/daemonless (nix/devbox) precisely to need neither Docker nor root.

That is fine until a user's PRD project **is** a Docker/Compose project — and the canonical instance is uzi dogfooding itself: `./e2e/run-e2e.sh` and `./scripts/smoke.sh` both require `docker compose up`. An agent working a uzi PRD in a uzi worker cannot run uzi's own pre-merge gates. More broadly, any repo whose tests shell out to `docker`/`docker compose`/`testcontainers` is unrunnable on a worker today, with no supported path — the agent just hits "command not found".

We want workers that **can** run Docker for those repos, **without** discarding the property that makes uzi safe. And the trust model is the crux of this PRD, so state it precisely (Decision 4): **we trust our users, but we do not trust the code the agent runs.** The agent is driven by a cloned repo and an issue body, either of which can carry prompt-injection; under `bypassPermissions` a hijacked agent will do what the injected instructions say. So "trusted users" relaxes the *operator/multi-tenant* threat model but does **not** relax the *hostile-repo-drives-the-agent* one. The defenses that protect the join token, the forge PAT, and `main` stay load-bearing.

## Trust framing (why "we trust our users" does not gut this PRD)

The owner's steer for this design was: *private AI factory, we trust our users, we can make security compromises to cut complexity.* The 3-agent review (research + architecture + security, 2026-07-18) converged on one correction that reorders everything: **the adversary here was never the user — it is the prompt-injectable agent.** Trusting the human buys real *scope* and *packaging* simplifications (below), but almost no *security* relaxation, because the agent runs semi-hostile repo code by design.

The security auditor verified in code that the three "secrets" are **not peers**, which is what tells us exactly which defenses matter:

- **Anthropic OAuth token** — already lives in the agent subprocess env as `CLAUDE_CODE_OAUTH_TOKEN` (`agent/src/sdk-env.ts`). The injectable agent **already holds it**; `docker run -e CLAUDE_CODE_OAUTH_TOKEN …` needs no filesystem read. Docker exposes nothing new here. The real leak vector is exfil over **unfiltered egress** — which is **PRD #50's job, not this PRD's**. This is the single biggest actual residual and it is out of #83's scope; flag it, don't pretend #83 closes it.
- **Join token** — `0400` worker-owned file at `/run/secrets/worker_token`; the agent runs as the cap-less `runner` uid and cannot read it (#51). The agent does **not** have it today.
- **Forge PAT** — never on agent-reachable disk or in the agent's env; worker-held, env-scoped only onto the worker's own git child (`specs/ai.md` §45). The agent does **not** have it today.

So the **only** new hole Docker opens is: a container can run as its own root inside the daemon and read any bind-mounted path, bypassing the #51 uid boundary — letting a hijacked agent `docker run -v /run/secrets/worker_token:/x` (or `-v /data:/x`) and steal the join token / PAT. The join token is the crown jewel: it lets the agent impersonate the worker, claim other runs for that user, and receive that user's decrypted PAT + Anthropic token in claim payloads. **That exact hole is what Decision 3 (separate-container mount ns) plugs, and it is the one property never to trade for simplicity.**

## Inspiration check

| Aspect | multica | bottega | coder (+ `myorg/k8s/coder`) | uzi today | uzi (this PRD) |
|---|---|---|---|---|---|
| Agent isolation | **None** — daemon on the user's machine runs the host `claude`/`codex` CLI in a host worktree (`SELF_HOSTING_AI.md`; `pkg/protocol/messages.go:74`) | Fixed worker deps; host tools assumed | Workspace = a container/pod; runs arbitrary user code by design | Containerized worker, `cap_drop: ALL`, worker/runner uid split (#51), no `docker.sock` | unchanged — this PRD does not relax the base worker's containment |
| How it gets Docker | **Free** — the agent is a host process with full host docker/PATH/creds | n/a | Sysbox RuntimeClass · Envbox · rootless Podman · privileged sidecar · host `docker.sock` | n/a | **Rootless DinD sidecar** (a separate daemon/container); the docker CLI now lives in `base` (Decision 1) |
| Cost of that choice | Zero isolation: docker access == full host access. The model uzi rejected | No sandbox story | Secure options need node-level infra (RuntimeClass/DaemonSet) or a privileged pod | — | Contained to the DinD userns; no host-root; keeps `no docker.sock`; secrets unreachable via Decision 3 |

**Reading of the field** (verified against submodule/vendor docs in the 2026-07-18 review):

- *Multica proves the cheap path and its price*: Docker "for free" by giving the agent the whole machine — full host docker, PATH, and credentials, no sandbox. Copying it deletes uzi's trust boundary; an anti-pattern here, not a template.
- *Coder is the only prior art with uzi's actual problem* (an isolated workspace that nonetheless needs Docker) and documents four solutions that bound our option space: **privileged DinD** / **host `docker.sock`** (coder's own docs call the privileged sidecar *"insecure … workspaces will be able to gain root access to the host machine"*; the socket is host-root by definition — **both disqualified**, and `no docker.sock` is a recorded invariant); **Sysbox RuntimeClass** (cleanest posture, but needs Ubuntu nodes + a `sysbox-deploy-k8s` DaemonSet that may install CRI-O and restart kubelet, and the project is slowing since Nestybox folded into Docker — a documented operator alternative, not the default); **Envbox** (bundles Sysbox but the outer pod is `privileged: true` with host `/lib/modules` — rejected); **rootless Podman / rootless DinD** (no host root, needs `/dev/fuse` + cgroup v2 + userns — **the option that preserves uzi's "no host root" invariant**, philosophically the same rootless stance as our nix/devbox engine).
- **Honesty correction from the review (must be in the PRD, was wrong before):** rootless does **not** mean "no `--privileged`." The official `docker:dind-rootless` image documents that `--privileged` is normally required even for the rootless variant (mount/userns/sysfs ops the default seccomp/AppArmor profile blocks); the **userns remap** is what delivers the security property (a breakout lands as an unprivileged host uid), *not* the absence of the flag. The truly flagless path needs a `/dev/fuse` device plugin + unconfined seccomp/AppArmor + ideally `hostUsers: false` (k8s ≥1.30 + containerd ≥2.0.5) and is fiddly. Industry does one of two things: privileged-but-userns'd DinD (GitLab CI's `docker:dind` service for ~10 years; GitHub Codespaces runs privileged DinD *inside* a per-user VM), or moves the boundary to a VM/microVM (Firecracker: Blacksmith, Namespace, Depot). VMs/microVMs/Kata/gVisor are the answer for *untrusted multi-tenant SaaS* — the lens uzi explicitly is not.

So this PRD takes **rootless DinD as a sidecar** as the primary mechanism on both compose and k8s, and makes an explicit, recorded decision (Decision 2) about the `--privileged` reality rather than implying rootless == unprivileged. Sysbox stays a documented escape hatch for operators who already run it.

## Solution Overview

Docker is delivered by two decoupled pieces, and the packaging changed after the review (Decision 1):

1. **The docker CLI moves into `base`** (`docker-cli` + `docker-cli-compose` + `docker-cli-buildx`, Alpine community — ~100 MB). It is **inert without a daemon**: `DOCKER_HOST` is unset unless a sidecar is wired, so `docker …` fails loudly with *"cannot connect to the Docker daemon"* rather than reaching for a host socket. There is **no separate `docker` template** — a docker CLI is ordinary tooling, not a "heavy/system-level" image variant (PRD #18's own bar for a template). The **capability** `docker` is therefore *"a daemon is reachable"*, self-reported by the worker probing `DOCKER_HOST` at register — reported reality, not a declared template→capability guess.
2. **A rootless DinD sidecar** provides the actual daemon, wired via `DOCKER_HOST`. It is a **separate container with its own mount namespace** (Decision 3), so containers it runs cannot see the worker's filesystem — in particular they cannot reach the join-token file, the decrypted forge PAT, or the Anthropic token. Rootless ⇒ a breakout lands as an unprivileged host uid. No host `docker.sock` is ever mounted. The sidecar is **opt-in per worker**: on compose via a profile, on k8s via choosing a docker-capable hosted worker type.

The default worker also gains **go + python** as first-class toolchain (the owner's "default worker should have docker/python/go available"): delivered through the existing nix/devbox tier (single source of truth, no second package path), with their nix closures **pre-warmed into the baked image `/nix`** at build time so they are effectively instant/available out of the box instead of paying the ~11-minute cold-start on first use.

Two delivery tracks, **both in scope for this PRD** (the k8s track is not deferred — per the CLAUDE.md k8s-first testing convention, k8s is where the team actually runs and validates, and running uzi's own `docker compose`-based e2e on a k8s worker is the real dogfooding win):

- **Compose track (the laptop dev loop).** An opt-in `dind-rootless` sidecar service in `docker-compose.yml`, profile-gated (`profiles: ["agent-docker"]`), isolated from the user's real Docker daemon. Self-contained; the reference implementation of the sidecar shape.
- **k8s track (the primary test/runtime environment).** A docker-capable hosted worker type provisioned by #58's shipped controller: the unified `base` image + a rootless-DinD pod sidecar, landed in a **separate, dedicated `baseline` namespace** (not a relaxation of #58's `restricted` default — Decision 7) with a `/dev/fuse` device DaemonSet. Opt-in, capacity-quota-bounded, never privileged-by-default beyond the recorded rootless `--privileged` reality, never sysbox-required. **#83 is not "done" until a k8s docker worker runs uzi's own e2e on dev-cluster.**

The default hosted-worker posture is otherwise **unchanged**: a worker only gets a *daemon* if its owner opts the sidecar in (the CLI being present costs nothing without one).

## Design Decisions

1. **The daemon is the non-provisionable unit; the CLI is ordinary tooling in `base`; the capability is the sidecar.** *(Revised — this replaces the original "docker is its own template.")* The original PRD made `docker` a template "because it needs a daemon," but the template shipped only the CLI — and a docker CLI is a static binary devbox/nix provisions trivially, which by PRD #18's own line ("templates exist only for what devbox/nix handles poorly") does **not** justify a template. The review flagged this as the PRD contradicting itself, plus a third 130-line lockstep copy of `base`, a CI kaniko job, and CLI/web template-surfacing for no gain. So: the CLI goes into `base` (inert without `DOCKER_HOST`); the **daemon** — a process + devices + namespaces, not a package — is the sidecar and can never be a nix package in the shared path; the **capability** `docker` means "a daemon is reachable," self-reported by probing `DOCKER_HOST`. This deletes the `docker` template, the separate CI build, and the template→capability map for docker (the worker reports reality). `go` + `python` are added to the default toolchain via the nix tier (with build-time closure pre-warm), *not* baked as apk packages — one provisioning path, no version drift against #18's pins.

2. **Rootless DinD sidecar, never the host socket — and the `--privileged` reality is recorded, not hidden.** The worker runs untrusted agent-driven code; any host-root-equivalent grant turns a prompt-injected agent into node/laptop compromise. That rules out the host `docker.sock` mount (host-root; `specs/ai.md` §36 invariant — kept) and privileged **non-rootless** dind. Rootless DinD confines the daemon and its containers to a userns-mapped unprivileged uid: strong isolation, no host root, same rootless stance as our nix/devbox engine. **But** (review correction) `docker:dind-rootless` normally still needs `--privileged` on the *outer* sidecar container; the userns remap — not the flag's absence — is the security property. Recorded decision for a private factory: **accept `privileged: true` on the *rootless* sidecar** (strictly safer than plain dind, far simpler than chasing flagless rootless) as the default, and document the flagless path (`/dev/fuse` plugin + unconfined seccomp + `hostUsers: false`) as the stronger posture on clusters that support it. Validate the exact minimal `security_opt`/device set day-1 of the compose milestone (Risks).

3. **The DinD daemon is a SEPARATE container (own mount namespace) — the load-bearing security property, now UNIVERSAL.** If Docker ran inside the worker container, a hijacked agent could `docker run -v /run/secrets/worker_token:/x` (or `-v /data:/x`) and read the join token, decrypted PAT, and Anthropic token straight out of the worker's filesystem — re-opening exactly what the #51 uid split closed (a container runs as its own root and reads any bind mount regardless of the `runner` uid). Because the daemon lives in its own container, `-v <path>` binds **the DinD container's** filesystem, which holds none of that. **Corollary:** the DinD sidecar must never mount the worker's secret, `/data`, or `/nix`; its storage is its own `dinddata` volume. A worker-level test pins that a container started through the sidecar **cannot** read the token path — this is the one security test that justifies the whole design. Because the CLI now lives in `base` (Decision 1), this invariant and its test are **promoted from a per-template concern to universal** — they hold on every worker that ever has a sidecar wired.

4. **Trusted users, untrusted repo: keep the agent-facing defenses; drop the operator-facing ceremony.** *(Calibrated to the owner's steer.)* "We trust our users" does not relax the hostile-repo-drives-the-agent threat, so these **stay**: Decision 3 (separate mount ns) + its test; rootless (host-root avoidance vs a hostile repo — matters even on the owner's own laptop, where a breakout would reach the owner's real docker daemon, ssh/browser creds, and other repos' on-disk secrets); no host `docker.sock`; the worker-holds-PAT boundary (§45); all existing guardrail denies (`git push`, force/history rewrites, credential/secret-path reads, `/proc`) unaffected; the #51 uid split. What "trusted users" **does** let us cut: per-capability admin *security* quota gating of docker (Decision 5); the `docker push` deny-by-default + per-repo allowlist deliberation (Decision 6, collapsed); over-worry about registry egress as a #83 concern (it's the pre-existing #50 egress gap). **The biggest actual residual — Anthropic-token/repo exfil via prompt injection over unfiltered egress — is outside #83 and belongs to #50; #83 must name it, not silently imply it's handled.**

5. **The daemon (sidecar) is opt-in per worker; the CLI is default. Quota is a capacity control, not a security gate.** A worker gets the docker CLI for free (default `base`); it gets a *daemon* only if the owner opts the sidecar in — on compose via `--profile agent-docker`, on k8s by choosing a docker-capable hosted worker type. For hosted workers, how many docker-capable pods a user may provision is bounded by **#58's existing per-user hosted-worker quota** (a resource/capacity control, reused as-is), **not** a new docker-specific security gate — the review confirmed capability gating is explicitly *not* a security boundary (#84 Decision 7), and under trusted users a per-capability security quota is moot. Recommended default profile for uzi-dogfooding workers: `agent-docker`, so *your* workers have docker by convention without imposing a daemon on every deployment shape.

6. **Registry egress / `docker push`: allow, document, do not gate.** The worker holds no registry credentials and the sidecar holds none, so an unauthenticated `docker push` simply fails at the registry; #18 Decision 6 already forbids pre-authenticated CLIs. The original PRD's milestone-level "deny-by-default + per-repo allowlist" deliberation is **collapsed to one documented sentence**: no registry creds exist, push fails, do not add creds; the real egress control is the orthogonal #50 proxy. (The agent can already exfil the data it legitimately holds — the one clone + its own Anthropic token — over plain `curl` today, so a docker-push guard buys nothing that #50 doesn't own.)

7. **Hosted docker workers live in their OWN namespace, not a relaxed `restricted` one.** PRD #58 Decision 6 pins default hosted pods to PodSecurity `restricted`, and its threat model leans on the worker namespace being *empty* (nothing but zero-privilege workers). Rootless DinD needs relaxations `restricted` forbids (a `/dev/fuse` device, userns, a looser seccomp/AppArmor profile, and the recorded outer `--privileged`). Rather than weaken the shared namespace for everyone, docker-capable workers are provisioned into a **second, dedicated `baseline` namespace** with `automountServiceAccountToken: false` preserved and the same "nothing else lives here" discipline. The default `restricted` namespace and its uniform posture are untouched; the weaker tier is bounded, opt-in, and separately blast-radiused. **This is precisely why the owner's "docker in the default worker" idea does NOT extend to a default-always-on daemon** (Decision 1): making the daemon default would force *every* hosted worker into `baseline`, a fleet-wide regression of #58's posture. CLI-in-base gives "docker available by default" without that cost; the daemon stays opt-in.

8. **Both tracks ship in this PRD; k8s is first-class, not deferred.** *(Revised — reprioritized 2026-07-18.)* #58 is shipped (v0.3.0, hosted workers live on dev-cluster), so the docker tier extends a real, in-production controller. The original PRD sequenced k8s "after" compose for scope; the CLAUDE.md k8s-first testing convention (the team now runs and validates on k8s, not compose) makes the k8s docker worker the track that delivers the real dogfooding value — running uzi's own `docker compose` e2e on a hosted worker. The compose track remains the self-contained laptop dev loop and the reference sidecar implementation, but k8s is **not** the "later" track: #83 is incomplete until a k8s docker worker runs uzi's e2e on dev-cluster. (A live hosted-provisioning bug, #82, is worth tracking but does not gate this.)

9. **How a docker run *reaches* a docker worker is PRD #84 — and the coupling is looser than first written.** #83 registers `docker` in #84's vocabulary as a **self-reported "daemon reachable"** capability (Decision 1), not a template-derived one. #84 owns Match/Gate: the static per-repo hint, the lead's plan-time inference, the capability-filtered claim query, and the plan-approval block when no eligible worker exists. Correction from the review: on a **homogeneous** fleet where the workers in play have the sidecar wired, a docker run just works with **no #84 needed** — routing only matters when the fleet is heterogeneous (some workers have a daemon, some don't) or for `jvm`/size fit. So #84 M1–M2 (vocabulary + claim predicate) remain wanted to stop a docker run being claimed by a daemon-less worker once fleets grow; #84's heavier inference/gate (M4) is genuinely useful but not a hard blocker for #83's dogfooding case. The original "user-facing completeness depends on #84 M2–M4" overstated it for the small-fleet reality.

## Technical Design

### 1. Docker CLI + go/python into `base` (agent + docs)

- `agent/templates/base/Dockerfile`: add `docker-cli`, `docker-cli-compose`, `docker-cli-buildx` (Alpine community) to the existing `apk add`. No `dockerd` in any image — the daemon is the sidecar. `jvm` inherits by mirroring `base` (the existing lockstep rule; the devbox/setpriv/nohooks layers are still the source of truth and stay test-pinned).
- `DOCKER_HOST` is **not** baked — it is set at run time by the worker only when a sidecar is wired (see §2/§4), so a worker with no sidecar fails loudly ("cannot connect to the Docker daemon") instead of silently reaching for a host socket.
- **Capability self-report:** at register the worker probes `DOCKER_HOST` (is a daemon reachable?) and reports `docker` in its capability set (feeds #84 M1). This replaces the deleted `docker` template's declared signal with reported reality. `UZI_WORKER_TEMPLATE=base` is unchanged (the drift badge still applies to `jvm`).
- **go + python default toolchain:** add them to the default nix/devbox tool set (on PATH for every run) and **pre-warm their nix closures into the baked image `/nix`** at build time so first use is instant. Single source of truth = #18's tier mechanism; the pre-warm is semantically invisible cache-warming. **Inherited caveat (#58):** the `/nix` named volume seeds from the image on *first* use only and never refreshes from a newer image — so the warm set updates only on volume delete + reprovision; document it.
- `docs/worker-setup.md`: docker is available on every worker (CLI); to actually run containers, bring up the sidecar (compose profile / k8s docker worker type); the trust note (rootless, isolated from your real Docker, no host socket).

### 2. Compose track: rootless DinD sidecar (laptop dev loop)

- New service `dind` in `docker-compose.yml`, image `docker:<pinned>-dind-rootless`, **profile-gated** (`profiles: ["agent-docker"]`); the plain `--profile agent` path is unchanged.
- Wiring — **prefer the shared-socket-volume**, not TCP: a named volume mounted into both `dind` (daemon writes its rootless socket there) and `agent` (reads it); `DOCKER_HOST=unix:///…/docker.sock`. No TCP surface at all. The `DOCKER_HOST=tcp://dind:2375` (compose-internal network, never published) variant is a documented fallback only — the review flagged an always-on unauthenticated daemon TCP port as a standing daemon-takeover surface, so socket-share is the default.
- **Day-1 validation (Decision 2 reality):** establish and record the exact minimal `security_opt`/device/`privileged` set the rootless sidecar needs on compose. If it needs outer `--privileged`, that is an accepted, recorded decision for a private factory (userns remap + separate mount ns + no worker secrets in reach), not an accident.
- The `dind` service mounts **none** of the worker's `agentdata`/`/data`/`/nix`/`worker_token` (Decision 3). Its storage is its own `dinddata` volume, where built images/layers land (disk-pressure → Risks).
- Sizing (PRD #42): the DinD daemon + build cache is a new consumer. `docs/worker-setup.md` gains: a docker worker budgets an extra ~1–2 GiB / ~1 CPU and a `dinddata` volume; uzi's own e2e inside dind pulls postgres 17 + builds api/web/agent, so expect 5–20 GiB steady-state `dinddata`. `AGENT_MEM_LIMIT`/`AGENT_CPUS` guidance updated.
- The worker CLI (`api/cmd/uzi`) and web worker-registration flow surface the docker sidecar choice (per the CLAUDE.md CLI-parity rule).

### 3. Guardrails (agent)

- `agent/src/guardrails.ts`: docker CLI is now in `base`, so the "deny docker unless it's the docker template" gate is **replaced** by: `docker` is allowed when a daemon is wired (`DOCKER_HOST` set / capability present) and denied otherwise, with the same evasion-resistant tokenizer that already defeats `sh -c`/`git -C` tricks. All existing denies stay intact on docker workers (`git push`, force/history rewrites, secret-mount prefix reads, `/proc`).
- `docker push`: allowed (Decision 6); one doc sentence records "no registry creds exist; push fails; don't add creds." ARCHITECTURE.md egress updated to note image pulls as a new outbound set (alongside #18's nix substituters), pointing at #50 for filtering.
- Tests: (a) the **universal Decision-3 invariant** — a container launched via the sidecar cannot read the worker's join-token path (the security test that justifies the design); (b) docker behavior is correct with/without a daemon wired (allowed when wired, clear failure when not), including through quoting/`sh -c` evasion (extends the existing tokenizer suite).

### 4. k8s track: hosted docker-capable worker tier (extends PRD #58's shipped controller — primary test env)

- A new hosted **worker type** ("docker") the #58 controller can provision. It uses the **unified `base` image** (docker CLI already present) and adds a **rootless-DinD sidecar container** to the pod; the worker container keeps all #58 posture (`runAsUser: 10001`, `automountServiceAccountToken: false`). `DOCKER_HOST` points at the sidecar (socket-share via a shared `emptyDir`, mirroring compose).
- Target namespace: a **second dedicated namespace** with PodSecurity `baseline` (not `restricted`), containing only docker-capable hosted workers. The controller's Role is extended to it with the same minimal verbs (#58 Decision 1); the empty-namespace discipline is preserved (no CNPG, no app secrets, no privileged SAs).
- `/dev/fuse` for rootless overlay: a `smarter-device-manager` (or equivalent generic fuse) DaemonSet exposes the fuse device as a schedulable resource (coder's documented approach); the pod requests it. The rootless sidecar carries the recorded relaxations (Decision 2); no host `docker.sock`, no RuntimeClass required.
- **Documented operator alternative:** if the cluster already runs Sysbox, provision docker workers as an unprivileged pod with `runtimeClassName: sysbox-runc` (strongest posture). This PRD does not require it and does not install sysbox; it is a config path in the docs.
- Capacity quota (reusing #58's per-user quota — Decision 5) bounds how many docker workers a user may provision. Not a security gate.
- **Prerequisite check (M-k8s):** confirm dev-cluster nodes support unprivileged userns + fuse (a #58-adjacent node capability check). **Definition of done for the k8s track:** a docker-capable hosted worker on dev-cluster runs uzi's own `./e2e/run-e2e.sh` (which does `docker compose up`) green.

### 5. Docs + specs

- New `docs/worker-docker.md` (audience: user): docker is available on every worker (CLI); to run containers, use a docker worker (compose profile / k8s docker type); it is rootless and isolated from your real Docker, has no host access, its resource cost, and the bring-up. Leading-fence frontmatter per `docs/README.md`.
- `docs/worker-setup.md`: the sidecar bring-up + sizing delta + `dinddata` GC/retention note.
- `specs/ai.md`: new section — docker-capable worker (CLI-in-base + rootless-DinD sidecar; the **universal** separate-mount-ns secret invariant; the `no docker.sock` invariant explicitly **preserved**; go/python default toolchain via warm-nix; the capability self-report). `ARCHITECTURE.md`: worker paragraph (docker CLI in base, optional DinD sidecar), worker egress (image pulls from registries → #50).
- `specs/human.md` is user-stated — **not edited without approval**; if any human-facing requirement needs to change, it is raised, not edited here.

## Risks & Open Questions

- **Rootless DinD limitations + the `--privileged` reality.** Needs cgroup v2 and userns; images that themselves require privileges (nested `--privileged`, certain mounts) will not run. Acceptable — the target is "run this repo's compose/testcontainers tests," not arbitrary privileged Docker. The outer sidecar likely needs `--privileged` even in the rootless variant (Decision 2); the userns remap is the security property. Overlay perf via fuse-overlayfs is slower than native; a known cost. Documented in `docs/worker-docker.md`.
- **Disk & memory pressure (`dinddata`).** A second large writable volume alongside `/nix` (#79/#82 territory): pulled base images and build cache grow unbounded without GC. M2/M4 must state a retention/GC story and the sizing delta (uzi-e2e-in-dind ≈ 5–20 GiB); on k8s (M3) it interacts with #58's PVC presets.
- **The one residual #83 does NOT close: Anthropic-token/repo exfil via prompt injection over unfiltered egress.** The token is already in the agent's env and egress is unfiltered; a hostile repo can `curl`/`docker push` it out. Default-CLI widens the channel slightly but does not create it. Real mitigation = **PRD #50 (egress proxy)**, deferred. This is the true crown residual — named here, owned there.
- **`docker compose` V2 in the sidecar.** Ship the `docker compose` plugin (compose v2 subcommand, not legacy `docker-compose`); pin and test in M1 to match what target repos expect.
- **Resolved (was open): k8s node prerequisites** → dev-cluster verified k8s 1.29.4 + containerd 1.6.31 (2026-07-19), BELOW the ≥1.30/≥2.0.5 pod-userns floor, so the flagless path is infeasible there; resolved by shipping a dedicated **privileged-tier** namespace instead (owner decision, Decision Log 2026-07-19). No `/dev/fuse` DaemonSet needed (privileged sidecar).
- **Resolved (was open): default for `docker push`** → allow + document (Decision 6); no registry creds exist, so push fails; the real control is #50.
- **Resolved (was open): docker as a template vs base** → CLI into `base`, daemon as opt-in sidecar, capability self-reported (Decision 1); the `docker` template and its CI build are dropped.

## Decision Log

- **2026-07-18 (created).** Prompted by "we need docker to test docker stuff" (uzi's own e2e/smoke need `docker compose up`, unrunnable on a worker). Investigated coder's four documented approaches (Sysbox RuntimeClass / Envbox / rootless Podman / privileged sidecar) against uzi's trust model, and multica's model (host daemon + host CLI, docker "free" via zero isolation — an anti-pattern here). Initial shape: rootless-DinD sidecar as an **opt-in `docker` template**, compose track first and k8s deferred.
- **2026-07-18 (3-agent design review + owner steer).** Reviewed by three fable-model agents (external research + architecture + security) under the owner's steer: *private factory, we trust our users, compromises OK to cut complexity*, plus the owner's idea that *the default worker should have docker/python/go available*. Outcomes folded in:
  - **Trust reframe (Decision 4):** the adversary is the prompt-injectable agent (hostile repo), not the user; trusting users cuts *operator* ceremony, not *agent-facing* defenses. Verified in code that the three secrets are not peers — the Anthropic token is already in the agent's env (real leak = egress → #50), while the join token + PAT are the crown jewels Docker could newly expose and Decision 3 plugs.
  - **Packaging (Decision 1):** docker CLI → `base` (inert without a daemon); the `docker` template + its CI build are **deleted**; the capability `docker` = "daemon reachable," self-reported. go + python added to the default toolchain via the nix tier with build-time closure pre-warm. Rejected default-always-on daemon (would force the whole hosted fleet into `baseline`, regressing #58 — Decision 7).
  - **Rootless honesty (Decision 2):** `dind-rootless` still normally needs outer `--privileged`; the userns remap is the security property. Accept `privileged: true` on the rootless sidecar for a private factory; document the flagless path as the stronger option.
  - **Decision 3 promoted to universal** (CLI now in base): separate-container mount ns + its secret-reachability test are the one non-negotiable property and now apply to every worker with a sidecar.
  - **Scope cuts (Decisions 5/6/9):** dropped per-capability *security* quota (kept #58's capacity quota); collapsed the `docker push`/registry-egress deliberation to allow+document; loosened the #84 coupling (homogeneous fleets need no routing).
  - **k8s elevated to first-class (Decision 8):** per the new CLAUDE.md k8s-first testing convention, the k8s docker worker is where the real dogfooding happens (running uzi's e2e on dev-cluster) — both tracks ship in this PRD; k8s is not the deferred track. Chosen mechanism unchanged: rootless-DinD sidecar on both compose and k8s, resolved as a **separate `baseline` namespace tier** (never a relaxation of #58's `restricted`); privileged/host-socket paths disqualified; sysbox/envbox documented as operator alternatives, not the default.
- **2026-07-19 (implemented — corrections discovered during the build; supersede the drafts above where noted).** Landed by a multi-agent team run across 12 commits on `feature/prd-83-docker-capable-worker`.
  - **Correction — the live Decision-3 efficacy test is NOT in M1.** Decisions 1/3 said the "universal Decision-3 secret-reachability test lands in M1." A *live* efficacy test (a container launched via the sidecar cannot read the token) structurally needs a running daemon, which M1 does not have (the sidecar is M2/M3). So M1 ships only the pure guardrail-composition + structural ("no baked `docker.sock`, `DOCKER_HOST` unset") tests; the live attack-matrix efficacy test lands in M2 (compose e2e) and M3 (k8s render + live DoD). The invariant is universal; its live test lives where a sidecar first exists.
  - **Correction — Decision 2 (accept `privileged`) and Decision 7 (`baseline` namespace) CONFLICT on k8s, and Q-B resolved it toward privileged.** PodSecurity `baseline` forbids `privileged` containers, so on k8s you cannot have both. The flagless-rootless alternative (no privileged; `/dev/fuse` device plugin; `hostUsers:false`) needs pod user namespaces = **k8s ≥1.30 + containerd ≥2.0.5**. **Q-B answer (verified live 2026-07-19): dev-cluster is k8s 1.29.4 + containerd 1.6.31 — both below that floor — so `baseline`+flagless is infeasible there.** Owner decision: ship the **same posture as the compose track** — a `privileged: true` rootless-DinD sidecar in a **dedicated `enforce: privileged` namespace** (`uzi-workers-docker`). Decision 7's real goal (a separate, blast-radius-isolated namespace so #58's `restricted` default is untouched) is PRESERVED; only the tier is `privileged`, not `baseline`. **Dropped from scope:** the `/dev/fuse` DaemonSet and `hostUsers:false` (privileged needs neither). Privilege-reduction was tested and confirmed: rootless dockerd genuinely requires `privileged` (reduced variants die in rootlesskit netns/sysfs setup, not fuse/overlay). Sysbox remains a documented stronger-posture operator alternative, not installed.
  - **Added — docker-namespace NetworkPolicy (the egress split the PRD under-specified).** The named residual (Decision 4 / Risks) is *external* egress (token/repo exfil) → PRD #50. But a default-allow-all docker namespace also leaves *in-cluster lateral* egress + cluster-wide ingress open, which #50 does not cover. M3 ships an adapted vanilla NetworkPolicy: `ingress:[]` (deny inbound, closes the dind daemon-port exposure) + egress = DNS + api + `ipBlock 0.0.0.0/0 except <cluster pod/service/link-local/node CIDRs>` — internet registry pulls work, in-cluster lateral is denied. Plus a Helm fail-guard so the tier can't render unfenced by accident. External egress filtering stays #50's residual.
  - **Clarified — no CLI surfacing (Decision 18).** Hosted provisioning is deliberately webui-only (`POST /api/workers/hosted` is cookie-only). The docker choice surfaces via a web toggle; a CLI `--docker` flag would require opening CLI provisioning, a separate out-of-scope security-posture decision. The CLAUDE.md CLI-parity rule does not apply to functionality intentionally excluded from the CLI.
  - **Unchanged residual, re-verified:** on the #58 single-uid k8s path the agent's direct read of the join token is guardrail-bounded (no uid fence — the split + 0400 hardening run only on the A1 root path); docker adds NO new reach to it (mount-ns closes the `-v` vector, verified). This is inherited from #58, not introduced by #83; PRD #51's k8s uid-split was not pulled forward (Q-D).
