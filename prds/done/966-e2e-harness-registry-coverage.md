## Problem

The nightly compose E2E (`e2e/run-e2e.sh`, `.github/workflows/e2e.yml`, cron `17 1 * * *`) is the **only** wire-level exerciser of the run lifecycle — worker join → plan gate → approve → stub implement → branch push → MR → restart/SIGKILL/cancel → MR-close watcher → bounded concurrency. Measured against the last 13 days:

1. **It is structurally fail-fast and unsummarised.** `run-e2e.sh` is 6012 lines, one linear script: ~750 lines of helpers, then ~55 phase groups (89 `say` banners) top to bottom. `fail()` is `printf … FAIL …; exit 1` (558 call sites); `pass()` prints and counts nothing (280 sites). One FAIL aborts the run and **discards every downstream phase's verdict**. The only summary is the hand-maintained `All E2E checks passed. (M6 runtime + PRD #24 MR-close + …)` roll-call string and the `wait_*` margin report. PRD #97 designed the fix — **M7, "harness structural refactor": extract `e2e/lib.sh`, split phases into `e2e/phases/NN-<name>.sh` sourced in order by a thin driver** (`prds/done/97-e2e-suite-hardening-speedup.md`, "M7 — (optional) harness structural refactor") — and marked it "optional, never started".
2. **It is red about a third of the time, and each red reports one failure with no artifacts.** Five `nightly-e2e` tracker issues in 13 days (#366, #372, #547, #730, #831; the workflow keeps one open at a time and comments on repeats). Root causes: two CI-uid parity chains the harness had never hit on a laptop (#366 dubious-ownership, #372 cross-uid push race on the shared bare), one **cross-phase state leak** (#730: "a claim returned run X, neither A nor B — the queue is dirty at end-of-file"; #762 patched the one leaking phase, the class remains), one real product race surfaced by the harness (#831 "concurrent cross-key PUT: expected one 200 + one 400, got 200 and 200"; the product-side fix for that family is the `pg_advisory_xact_lock` on settings writes, `store.SettingsMutationLockKey` at `api/internal/store/migrate.go:101`, shipped alongside migration 00178), and #547, whose cause was never recorded on the issue. The tracker issue body is a run URL and a SHA; the workflow uploads nothing; `cleanup()` runs `down -v` and `rm -rf "$RUNROOT"` on red exactly as on green (only `KEEP_RUNDIR`/`KEEP_STACK` change that, and the nightly sets neither).
3. **The implicit inter-phase contract is the leak surface.** Phases mutate the shared stack and later phases depend on it: the api is `--force-recreate`d with `E2E_FORGE_POLL_INTERVAL=2s` + `FORGE_RECONCILE_EVERY=2` in the MR-close phase and both focused forge lanes; `judge_enabled` is flipped on in the PRD #46 phase and off after the PRD #98 phases; the agent is recreated at `WORKER_MAX_CONCURRENT_RUNS=2` (PRD #42) then `3` (PRD #47); 12 `login` re-sessions in the default lane; `IID`/`RUN`/`MR_IID`/`UZI_BIN`/`WTOKEN` are produced in one phase and consumed hundreds of lines later. **Every stack mutation is disk or server state** (an `ENVFILE` append + `--force-recreate`, or an API write) — never a shell variable — which is what makes a subshell-per-phase model (M2) safe. None of it is declared anywhere; reordering or subsetting the script is unsafe, so a developer chasing phase 50 runs all 13–15 minutes.
4. **Coverage gaps, measured** (grep of the script for kind strings, route paths and `say` banners; negatives verified with `-F`):
   - **4 of 8 run kinds have zero wire coverage**: `prompt`, `task`, `mr_rework`, `self_improve` (the CHECK domain is `api/internal/store/migrations/00167_run_mr_rework_kind.sql:19`; constants in `workersvc/ci_fix.go`, `judge.go`, `chat.go`, `mr_rework.go`). `issue`, `ci_fix`, `chat`, `judge` are covered.
   - **The scheduling subsystem** — catalog defaults, sweeps with the `uzi` eligibility gate, `run-now`, `last_fire` — is what drives production every night and has **no** e2e phase (`/schedules` and `schedule-catalog` appear nowhere in the script; its only coverage is `*LiveDB` handler tests via `run-store-it.sh`, no worker or forge wire).
   - **Two of the three forge lanes never run in CI.** `UZI_E2E_FORGE=forgejo|github` select focused lifecycle blocks (`if [ "$FORGE" = … ]; then …; exit 0; fi`) that exit before the full suite; `e2e.yml` runs the bare default (gitlab). The github lane is additionally **driver-only** and its scope comment records why: the agent-side GitHub client derives its API base as `api.${host}` (`agent/src/forge.ts:366`, github.com-style, no `/api/v3` mount), the overlay aliases and the self-signed cert cover only `forge-fake.e2e`, so a worker cannot reach the fake as GitHub without an agent contract change. **Out of scope here (D12)**; the forgejo lane does drive a worker (its client hits `forge-fake.e2e/api/v1`, which is aliased).
   - Slack, OIDC, findings, memory, GitHub project sync, hosted/controller: not covered here and **not in scope** (each is either covered in-process with a mock upstream, needs an external system the isolated stack cannot fake, or is the k8s lane's job — recorded so nobody re-audits).
5. **Nothing in `web/` is exercised by a browser.** Out of scope for this PRD (D8) but recorded: the e2e `web` service is plain HTTP on `127.0.0.1:${E2E_WEB_PORT}` (`e2e/docker-compose.e2e.yml`, `web.ports: !override`), so a later Playwright smoke can target the same stack.

## Solution

Six milestones. M1 lands PRD #97's M7 as **pure motion**; M2 gives the driver its semantics (fail-soft, contract validation, quarantine, selection, listing) **with its hermetic regression test co-landed**; M3 keeps evidence on red and closes the two harness-side red classes; M4–M6 add the missing coverage as new registry phases. Every new assertion obeys the rules in `.claude/agent-team.md` and PRD #97: positive control before any absence check, no lowered ceilings, no retries, pass-through assertions.

**Kept invariants** (settled decisions, not re-opened): single stack, serial, same-process phase model (PRD #97 M7: "do **not** parallelize — one worker/DB/forge makes that impossible"); nightly + dispatch only, never per-PR (`e2e.yml` header); `wait_*` ceilings untouched (PRD #97 Decision 4); git Basic-auth on every run + `main`-push rejection by pre-receive hook (PRD #97 M1); the `env -i` self-re-exec with the `--e2e-sanitized` positional gate stays in the entry script; forge-fake stays "deliberately NOT a real forge".

  - **Subshell per phase, with the one shape that keeps errexit alive.** Bash ignores `set -e` inside any compound command that is the non-final operand of `||`/`&&` or the condition of `if`/`while`, and a subshell inherits that context — so `( source "$f" ) || rc=$?` and `if ( source "$f" )` run the phase with **errexit off**: a bare failing command with no `|| fail` (the `"${COMPOSE[@]}" up -d --no-deps --force-recreate … >/dev/null` lines, for instance) prints nothing and the phase reads PASS. The driver therefore runs `set +e; ( set -euo pipefail; source "$f" ); rc=$?; set -e` — never the `||`/`if` form. `fail()` keeps its `exit 1` (later assertions in a phase depend on earlier ones, so intra-phase fail-fast is correct); the driver reads `rc` and continues.
  - **`provides:` crosses the subshell trap-free.** The subshell runs `source lib.sh; source "$RUNROOT/phase.env"; source "$f"; declare -p $PROVIDES > "$RUNROOT/phase.env.next"` — a `fail`'s `exit 1` skips the dump, which is correct (a failed phase's outputs are not to be trusted) and makes the next consumer's `requires:` fail loudly naming both phases. The parent sources `phase.env.next` **at top level, not inside a function** (`declare -p` emits `declare --`, and sourcing that inside a function makes the variable function-local; measured). No phase installs a top-level `EXIT` trap today (the three backgrounded health legs use `trap - EXIT` in nested subshells), so nothing shadows this.
  - **`requires:` validation** before each phase: shell names must be non-empty; `env:KEY=VALUE` tokens must match a line in `$ENVFILE` (this is what catches "subset omitted the phase that sped the poller up", which a shell-variable check cannot); on failure the driver names the phase and the phase whose `provides:` carries the missing item. **`mutates:` lines also declare `env:` tokens they `provide`.**
  - **Fail-soft + critical.** `critical: yes` (boot seed, worker-online, happy-path) FAIL → stop; the rest recorded `SKIP (after critical failure)`. After any non-critical FAIL, a later FAIL in a phase whose `requires:` intersects a failed phase's `provides:` is tagged `suspect_cascade` (still a FAIL; exit code unaffected).
  - **End-of-phase quarantine.** Enumerate non-terminal runs **across all users** with `db_psql "select id, user_id from runs where status not in ('completed','failed','cancelled')"` — `GET /api/runs` is owner-scoped (`ListRunsForUser`, `api/internal/handler/runs.go`), and 12 re-logins mean an API diff can be blinded by a run another session created. ## Decision Log

- **D1 — single-stack, serial, same-process model kept.** PRD #97 M7's own constraint; one worker, one DB, one fake make parallel phases impossible. The registry buys selection and honesty, not concurrency.
- **D2 — a phase is a subshell run as `set +e; ( set -euo pipefail; source … ); rc=$?; set -e`; `provides:` crosses it by a trap-free `declare -p` after the source, re-sourced at top level.** Keeps `fail()`'s intra-phase fail-fast while the driver continues; the exact shape matters because the obvious `( … ) || rc=$?` silently disables errexit for the whole phase. A failed phase dumps nothing, by design.
- **D3 — no auto-retry of a failed phase.** Every prior flake in this repo (#242, #248, #524, #286, #312, #328, #162, and the e2e reds) was fixed by clocks, caps or a product fix, never by loosening; a retry is a loosened assertion with the loosening hidden. `race-sensitive:` tagging plus the margin report gives triage the hypothesis without hiding the failure.
- **D4 — quarantine is non-fatal by default, strict opt-in.** Cancelling a run is itself a stack mutation; a false-positive LEAK (a phase that legitimately hands a run forward and forgot `handoff:`) must not redden a nightly. Every LEAK is visible in the summary either way; `E2E_STRICT_LEAKS=1` is for the branch that fixes the last one. Enumeration is by DB, not by the owner-scoped API, so no session boundary can blind it.
- **D5 — a red run keeps its rundir.** The nightly runner is ephemeral, so on CI this costs nothing and (with #967's upload) gives the tracker issue its first artifacts; locally it replaces "re-run with `KEEP_RUNDIR=1`" with a printed path.
- **D6 — the quiet-period knob is a product change ridden by this PRD.** Same shape and justification as `SWEEP_INTERVAL` (issue #100: "small product change — normal MR flow"): a hardcoded 3-minute debounce is untestable in a 13-minute suite; the default is unchanged, the overlay opts in.
- **D7 — `run-e2e.sh` is anchored by phase slug, never by line.** PRD #97 M9b; the registry makes the slug the durable identifier and `--list` the index.
- **D8 — browser (Playwright) smoke is a separate PRD.** Different toolchain (`web/` devDependency + browser download on the runner), different failure modes, different reviewers; one theme per PRD. The e2e `web` service is plain HTTP on a random loopback port (`E2E_WEB_PORT`), so the follow-up can target this same stack.
- **D9 — workflow edits are split to #967.** `.claude/rules/prds.md`: the worker PAT lacks `workflow` scope; a workflow touch loses the whole branch. Everything the matrix/upload needs (`summary.md`, `junit.xml`, `artifacts/`, `UZI_E2E_FORGE` lanes as phases) is produced by this PRD so #967 is a few YAML lines.
- **D10 — forge-fake stays deliberately un-real.** One project, in-memory, auth not checked. The MR-discussions route + mutator is the minimal addition the watcher needs; no scope enforcement, no pagination, no second project.
- **D11 — Slack/OIDC/findings/memory/project-sync/hosted stay out.** Each is covered in-process with a mock upstream or belongs to the k8s lane; adding fakes for them is a different PRD each and is recorded here so the gap is not re-found.
- **D12 — the github lane stays driver-only.** A worker-driving github lane needs an `api.forge-fake.e2e` network alias, a cert SAN, the fake serving GitHub routes at that vhost's root, and most likely a change to how `agent/src/forge.ts` derives the API base for a non-`github.com` host — an agent contract change, which this PRD refuses to make. The lane's own scope comment already records this; #967's matrix still runs the lane nightly so the *driver* path stops rotting. A follow-up may take the contract change on its own terms.
- **D13 — M2 and its hermetic test land together.** The driver is new behaviour in a file no unit test covers; the root `CLAUDE.md` rule "every bug fix ships a regression test" (2026-09-01) is read here as "every new safety mechanism ships its disproof", and the errexit-in-subshell case is the one that only a hermetic test can see.

## Risks & mitigations

- **A helper or phase relies on a global set mid-phase for a *later* phase and the header misses it.** The subshell makes that a hard failure at the next phase's `requires:` check, naming both phases — loud, not silent. M1's first pass builds `provides:` mechanically (assignments of `[A-Z_]{3,}=` in the phase body that a later phase reads) and the M1 motion run validates the headers before M2 changes any semantics.
- **Subshell semantics**: `$BASHPID` differs (no phase uses it — verify with `-F`); `set -euo pipefail` is re-established inside the subshell explicitly; `cleanup` stays in the parent and a phase's `exit 1` never reaches it; `COMPOSE`, `WTOKEN`, `MARGINS_FILE`, `UZI_BIN` are parent-set and inherited; no `readonly`/`declare -A` exists in the script.
- **Subsetting can omit a stack mutation a later phase needs.** Closed mechanically by `env:` tokens in `requires:` validated against `$ENVFILE`; API-side mutations (`judge_enabled`, `mr_rework_enabled`) are re-applied by the phases that need them, which is cheap and idempotent.
- **Time budget creep**: SC9 is the ceiling with a stated gate-off order; no `wait_*` ceiling is lowered to make room.
- **`mr_rework` detection needs a green MR pipeline and a non-bot author**: both are explicit inputs of the `/_e2e` mutator; top-level notes carry no head SHA so GATE 2 is the debounce alone.
- **`uzi handoff` from inside the harness**: the host gitconfig + `uzi_cli` env change are named in M5; the `ls-remote` control runs before the handoff so a transport mistake fails in one line, not as a worker-clone timeout. `--repo $REPO_ID` is the disambiguator if `group/repo2` ever matches.
- **`self_improve` may need a product seam** — that is why it is a stretch with an explicit "record and leave uncovered" exit, and first in the gate-off order.
- **In-flight overlap**: none on `e2e/**`, `e2e/README.md`, `Taskfile.yml`, `api/internal/config`, `api/cmd/server/main.go`, `agent/src/executor.ts` from #954/#956/#960/#963 (each PRD's scope re-checked at plan time; #956 lists its nine packages and neither `config` nor `cmd/server` is among them). The `refactor` sweep's three slots tonight are #956/#960/#963; this PRD is hand-driven.
- **Validation needs a docker-capable worker**: the harness *is* `docker compose`, so the uzi run must land on the docker lane (PRD #83 capability scheduling; `uzi admin workers` shows `docker: true`). Confirm at approval time; a restricted-tier claim cannot run `./e2e/run-e2e.sh` and the run would validate nothing.
- **Offline worker**: every fact above is in-repo or in this document (the GitHub Actions run logs and tracker issues were read locally and are summarised in Problem §2; the #366/#372 fix commits are not in history, which is why M3 cites comment anchors); nothing in any milestone needs the open internet.
