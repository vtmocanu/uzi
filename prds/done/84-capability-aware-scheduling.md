## Problem

A run is claimed by whatever worker grabs it first (`ClaimRun`, `FOR UPDATE SKIP LOCKED`, with an affinity grace for resumes). A worker's template is **observability-only** — PRD #18 self-reports it (`template_reported`) and badges declared-vs-reported drift, but nothing routes on it. So if a run needs a toolchain or capability the claiming worker lacks, it fails **mid-run** with `command not found`, after burning a claim and part of a token budget, with a confusing failure the user cannot pre-empt.

This has been survivable for one reason: missing **CLI tools** are auto-provisioned per run (devbox tier-1/2, PRD #18), so "tool not found" is largely self-healing. That masks the absence of any real matching.

**Docker breaks the mask, and only half of it is closed.** Docker is the first capability that **cannot** be runtime-provisioned — it needs a daemon/sidecar, not a nix package (PRD #83 Decision 1). #83/#89 shipped the *authorization* half: an admin allowlist plus a claim gate that stops a docker *worker* from claiming a run for a repo it is not trusted with. But the *routing* half is still open in the direction that matters here: a docker-*needing* run has no marker on it, so a plain `base` worker will happily claim it and die on arrival — nothing can install a daemon into that worker at run time. (`jvm` has had the same latent gap since PRD #18; it is simply rarely hit. This PRD fixes the general case and retrofits `jvm`.)

So the system must know, *before committing the run to a worker*, that the run needs a docker-capable one — and must do something better than crash if none exists. **How does the user — or the planner — declare that a run needs a docker worker, and what happens when no available worker can satisfy it?**

## Inspiration check

| Aspect | Kubernetes scheduler | CI runners (GitHub/GitLab) | uzi today | uzi (this PRD) |
|---|---|---|---|---|
| Match work to capable executor | `nodeSelector` / taints+tolerations / `runtimeClass` | `runs-on:` labels / runner tags | Docker *worker*→allowlisted-repo only (`fn_worker_can_claim`); run→worker still first-come | Capability set per worker + `required ⊆ caps` predicate on the claim (both directions) |
| "No capable executor" | Pod stays `Pending`, surfaced with a reason | Job queues on a label with no runner; surfaced as pending | Run is claimed and fails mid-flight (for a docker-needing run on a base worker) | A "no eligible worker" **reason** on the still-`queued` run (a `health`/`health_reason` projection, no new status), + remediation, or blocked at the plan gate |
| Who declares the need | Author sets selectors/tolerations on the pod | Author sets `runs-on` | Admin allowlists repos (authorization); nobody declares the run's *need* | Static per-repo hint **and** plan-time inference by the lead (both) |

The pattern is settled prior art: **capability-as-selector scheduling with a pending/surfaced state when nothing matches.** uzi already has the hard parts — workers self-report (PRD #18/§299), runs already **stop for human approval** (`awaiting_approval`), and the claim gate is already an extensible SQL predicate (`fn_worker_can_claim`). This PRD wires those together rather than inventing a scheduler.

## Solution Overview

Three layers — **Declare → Match → Gate.**

1. **Declare (both sources — user decision 2026-07-18):**
   - **Static per-repo hint** (`repo.required_capabilities: [docker, …]`) in repo settings, next to PRD #18's tool profile / tier-2 toggle; optionally an issue label (`uzi:needs-docker`, deferred — see Open Questions). Known **before claim**, so the scheduler can route without waiting for a plan to run.
   - **Plan-time inference** by the lead: the planning step scans the clone and emits the run's **full requirement set** — non-provisionable `required_capabilities` (docker…), the provisionable **`required_tools`** toolchain (go, python, node…, inferred mainly from language manifests — `go.mod`, `package.json`, `pyproject.toml`, `Cargo.toml`, `pom.xml` — and build/test/CI scripts), plus an estimated **size class** (mem/CPU/disk) — alongside the agents it already proposes. This is a **pre-run readiness check** (Decision 11): make sure everything for a successful run is present or auto-provisionable *before* committing the run. The planner emits *requirements*, not a worker pick (Decision 8). **Authoritative and escalation-only** — it can add a requirement the hint missed, never remove a hinted one.
   - Effective requirement = hint ∪ plan-inferred.

2. **Match (capability-aware claim):** every worker advertises a **capability set** — the reported set already arrives on register (§299); M1 persists it and derives the rest from a server-side `template → capabilities` map plus provisioned-tool tags. `fn_worker_can_claim` gains the run's requirement set as an argument: a run's **non-provisionable** required capabilities must be a subset of the claiming worker's capabilities. A `base` worker will not claim a `docker` run. Affinity/resume grace and the existing docker-worker→allowlist clause are unchanged.

3. **Gate (stop only when genuinely unsatisfiable):** `unmet = required − (worker_caps ∪ provisionable)`; a missing CLI tool tier-1/2 can install is **not** unmet (provisioned, not gated). The gate also flags a **size** shortfall (the plan's estimate exceeds the worker's mem/CPU envelope), not only missing capabilities. When `unmet` or a size shortfall is non-empty, the gate offers a **remediation spectrum** (Decision 9): switch to an eligible worker you have · provision a *persistent* one (today, #58) · auto-provision an *ephemeral* one for this run (deferred). It surfaces at two moments:
   - **Pre-claim** (static hint already makes it unsatisfiable, no eligible worker online): the run **stays `queued`** and surfaces a **"no eligible worker"** reason (a `health`/`health_reason` projection over `queued`, **not** a new `runs.status` value — Decision 3) — not a silent hang or a mid-run crash — with the remediation CTA, consuming no claim. You provision (or start) a worker; the run then claims it. *Planning never runs on the wrong worker* (Path 1, Decision 9).
   - **At the plan-approval gate** (need discovered by inference on a worker that can plan but not execute): approval is **blocked** with the reason + remediation; on remediation the run is **requeued and re-claimed** by a capable worker, which **re-plans and executes** — existing claim + durable-plan mechanics, no cross-worker session transfer (Path 2, Decision 9, and see the ★ resolution in Risks).

## Design Decisions

1. **Capability matching is *scheduling*, and is distinct from *provisioning* and from *authorization*.** Three axes, kept separate:
   - **Provisioning** — nix CLI tools (PRD #18 tiers). Satisfied by installing per-run; **never gates**.
   - **Authorization** — the admin docker repo allowlist (shipped, `fn_worker_can_claim`). Owns *which repos* a docker worker may touch; admin-owned, not user-overridable.
   - **Scheduling/routing** — non-provisionable capability match (this PRD's remaining half). Owns *which worker* a docker-needing run may land on; matched at claim time and gated when unmet.

   The requirement's *type* picks the path. Getting this split right is what makes docker usable without regressing #18's provisioning UX and without re-litigating the admin authorization boundary.

2. **Two declaration sources: the hint pre-routes, the plan escalates** (user, 2026-07-18: "both"). The static repo hint is known before a plan exists, so the scheduler can route a statically-hinted run to the right worker with zero plan latency; plan-time inference is authoritative and catches needs the hint missed. They compose as a union, and inference is **escalation-only** so a heuristic can never silently *drop* a requirement the user explicitly declared.

3. **Reuse the existing plan-approval gate; surface one new pre-claim *condition* — do not invent a scheduler, and do not add a new run status.** uzi already halts at `awaiting_approval`; capability satisfaction is surfaced there for the inference path. The only genuinely new pre-claim surfacing is **"no eligible worker"** for the case where the hint makes a run unsatisfiable *before* any plan runs — otherwise such a run would either hang in `queued` forever (no worker will ever claim it) or, worse, be claimed and crash. **It is realized as a `health`/`health_reason` projection over the existing `queued` status, NOT a new `runs.status` value** — this preserves the nine-value status contract (adding a status touches the CLI enum + the WS unknown-rewrite) and matches #361, which adds its docker-specific reason the same way. Surfaced with remediation, not a silent queue.

4. **Capabilities are a bounded, server-owned vocabulary — not free-form strings.** A small server-owned enum (`docker`, `jvm`, `gpu`, …), each mapped to (a) the templates that provide it and (b) optionally a provisionable-tool tag. `docker` is the exception in *source*: it is worker-self-reported ("daemon reachable", §299), not template-derived, which is exactly the reported-reality-over-declared-intent stance Decision 7 assumes. The map is code-reviewed, so matching is deterministic and the UI/CLI can render a fixed set. No repo-supplied arbitrary capability names (they would be unmatchable and a spoofing surface). Implementation: a run's `required_capabilities` is validated against the vocabulary at enqueue/inference; an unknown name is dropped (hint) or never emitted (inference), never stored.

5. **Never over-gate.** A requirement that tier-1/2 provisioning can satisfy must not block approval or claiming — that would regress the PRD #18 experience where "install my repo's tools" just works. The gate subtracts the provisionable set first; only the residue stops a run. (Decision 1 restated as a hard rule for the gate implementation and its tests.)

6. **The hint is a contract; inference is a heuristic; and the ★ fork is RESOLVED — re-plan works today.** The static hint is the user's explicit, always-honored declaration. Plan-time inference (scan for compose/Dockerfile/testcontainers/`docker` in scripts) has false negatives by nature; it may only **add** requirements. A repo the scan misses still has the hint as the reliable path, and a missed inference degrades to today's clear mid-run failure — never to a wrong *removal* of a requirement.

   **The open fork the original draft flagged (★: "can execution resume from the approved plan alone?") is closed by the shipped resume mechanics.** SDK sessions are **worker-local**: `sessionTranscriptResolvable(runHome, sessionId)` reads *this worker's* on-disk transcript (`agent/src/sdk-session.ts:134`, globbing `$HOME/.claude/projects/<encoded-cwd>/<sid>.jsonl`, `:165`). On a claim by a *different* worker the transcript is not resolvable, so `runner.ts` drops `sessionId` (`agent/src/runner.ts:649-655`) and `planApproved` collapses to false for a non-seeded run (`planApproved: (claim.plan_approved) && (!!sessionId || seeded)`, `:827`; `approvedPlan: claim.plan_md`, `:831`; `seeded = claim.plan_source === "seeded"`, `:703`). The claim payload already carries `Branch`/`SessionID`/`PlanMd`/`PlanApproved`/`PlanSource` (`api/internal/workersvc/claim.go:38-43`, `:98-99`). So **a different worker resuming a plan-approved run today RE-PLANS** — safe, correct, costs one planning turn — and the seeded path proves implement-from-plan-text works when a session is genuinely absent. **Therefore Path 2 (requeue → re-plan on the capable worker) works now with no new machinery, and the static hint (Path 1) is a *convenience* that avoids the wasted planning turn, not a *requirement*.** No cross-worker session/worktree/PAT transfer is designed or needed.

7. **Matching is best-effort scheduling + a clear failure, not a security boundary.** A worker self-reports its capabilities; the join token stays the sole trust anchor (PRD #18 Decision 5). A worker that falsely claims `docker` and lacks it simply fails the run — identical to today's drift, not an escalation. The **security** boundary for docker is the admin allowlist + the guardrail (§300, `DOCKER_HOST`-keyed), both untouched here. So this PRD adds no trust surface; it improves routing and UX. (Guardrails and the uid split remain the security layers — do not weaken any of the four primary-directive guardrail layers on the theory this scheduling check covers them.)

8. **The planner emits *requirements*, not a worker choice — and requirements include size, not just boolean capabilities.** The lead outputs `required_capabilities` + `required_tools` + an estimated **size class** (mem/CPU/disk); it never picks, and never needs to know, your worker inventory. The server resolves those needs → *an eligible worker you have* or *a worker type + size to provision* (via the `template → capabilities` map + #58's S/M/L presets). This keeps the planner simple and inventory-agnostic, and lets the gate flag "too small for this plan," not only "missing docker." "Suggest a worker you don't have yet" is the normal unmet case — resolved by the remediation spectrum (Decision 9), not a special path.

9. **Remediation is a spectrum, and unmet dispatch reuses existing claim machinery — no cross-worker session handoff.** When nothing you have satisfies a run, the gate offers, in ascending cost: **(a)** route/switch to an eligible worker you already have; **(b)** one-click provision a *persistent* hosted worker (works today on #58's static provisioning); **(c)** auto-provision an *ephemeral* worker for just this run (deferred — depends on #58's spawn-on-demand + teardown, its explicit non-goals, and #79's ephemeral-cost/GC question). Two dispatch paths, both built on mechanics uzi already has (any worker claims a queued run; the approved plan is durable in `run_messages`), **not** live worktree/PAT/SDK-session transfer:
   - **Path 1 — hint-first (provision before planning).** The static hint makes the need known pre-claim, so an unsatisfiable run parks in "no eligible worker"; you provision; the capable worker then claims, plans, and executes. Cleanest — planning never lands on the wrong worker.
   - **Path 2 — plan-time discovery.** A worker that can plan claims and plans; the plan escalates to a capability/size it lacks; the gate blocks; on remediation the run is **requeued and re-claimed** by a capable worker that **re-plans and executes** (re-cloning as it would anyway). Per Decision 6 this is proven to work today: a cross-worker resume already re-plans. Path 1's only advantage is skipping that one planning turn.

10. **Considered and deferred: an always-on "control" worker + splitting one run across workers.** An always-on small worker for the light lane (plan/judge/chat) with heavy execution handed to a different worker mid-run was weighed and set aside: a *shared* control worker would hold many users' Anthropic tokens + forge PATs, breaking the per-user creds boundary the whole worker model protects; a *per-user* one just reintroduces the "keep a worker up" friction #58 reduces; and splitting a single run's plan and execute phases across workers needs live worktree/PAT/SDK-session transfer + claim reassignment — real new machinery for a laptop-first tool. #84's pre-claim state (Path 1) and requeue-then-re-plan (Path 2) deliver the same user outcome without it. Note: `judge` and `chat` are *already* separate light run kinds, so a small worker can naturally serve that lane today; only making *plan* its own claimable run would need the handoff above — a possible future PRD, not this one.

11. **The plan is a pre-run readiness check over the *whole toolchain*, not just non-provisionable capabilities.** The inference pass infers the run's full requirement set — the non-provisionable **capabilities** (docker…) *and* the **toolchain** (`required_tools`: go, python, node, rust, jvm… + specific CLIs), primarily from language manifests (`go.mod`, `package.json`, `pyproject.toml`/`requirements.txt`, `Cargo.toml`, `pom.xml`/`build.gradle`) and build/test/CI scripts — then **classifies each need before the run**:
    - **present** (base + template + already-provisioned) → ready;
    - **provisionable + allowlisted** (nix/devbox tier) → auto-provisioned, shown as "will install," never a nag (Decision 5);
    - **provisionable but not allowlisted** (admin policy forbids) → flagged/blocked: "repo needs `X`, not permitted — ask an admin";
    - **non-provisionable capability** (docker) → hard-gated (Decisions 1/3);
    - **unknown / unsatisfiable** → blocked.

    This is the user's north star — *"make sure we have everything for a successful run"* — surfaced at the plan gate: auto-resolve what we can, flag/gate only what we can't. It moves uzi's existing tool-gap scan from a post-hoc judge signal to a pre-run preflight. **Scope, honestly:** detect the *primary* toolchain from manifests (high-signal, low false-positive); do **not** try to enumerate every transitive CLI a test might shell out to — that long tail stays backstopped by the mid-run failure + the judge post-scan. The preflight raises the floor; it does not promise a guaranteed-green run (see Risks).

12. **The authorization-vs-routing override model (user, 2026-08-21).** Docker is a privileged tier; a user cannot self-approve it. The override rules follow from Decision 1's three axes:
    - **An approved (allowlisted) repo that needs docker is NEVER warned per-run.** It just routes to a docker worker (the existing claim gate permits it); if none is online → "no eligible worker" → provision. Zero per-run nagging (aligns with Decision 5, never over-gate).
    - **A non-allowlisted repo that genuinely needs docker is blocked as an admin-policy decision** ("ask an admin to allowlist this repo"), **not** a user self-override. Issue #361 already surfaces this reason for the "only docker workers online" case; #84 M3 reuses/coordinates that surface.
    - **The only user override is correcting a false-positive inference** ("it doesn't actually need docker") → run on base *without* the capability. This bypasses no security boundary — the user is choosing to run WITHOUT the capability, and the guardrail (§300) still denies docker use on a daemon-less worker. **Inference can only ADD a requirement; only the user can remove one** (Decision 6, the escalation-only rule, made concrete).
    - **Size is soft** (flag + proceed, never hard-block); **capability is hard**, and for docker the "hard" is the admin allowlist + routing, per above.

13. **One global admin kill-switch, default ON, gating only #84's *added* behavior — not the shipped allowlist.** A single global admin setting `KeyCapabilityAwareScheduling` (bool, **default TRUE**) turns #84's additions on/off. It follows the existing bool-default-true settings precedent (`KeyHealthEnabled` / `DefaultHealthEnabled = "true"` / `HealthEnabled(ctx)`, `api/internal/settings/settings.go:101`/`:194`/`:302`/`:720`, `Validate` bool case `:1051`), with the key + admin-card surfacing modeled on the docker allowlist (`DockerAllowlistCard`, `web/src/pages/AdminSettings.tsx:1232`).
    - **What it gates (ON = the whole PRD):** the plan-time inference preflight (M4), the readiness/plan-gate block (M4), the capability-match extension to the claim predicate (M2 — a docker-*needing* run is claimable only by a docker worker), and the "no eligible worker" queued-run reason (M3, which follows from M2's predicate).
    - **What it does NOT gate — load-bearing:** the already-shipped docker *authorization* half stays enforced regardless of the flag. `fn_worker_can_claim`'s existing docker-worker→allowlist clause (#83/#89) and #361's reasons are **never** bypassed by "off." Concretely, the flag gates only the *new* clause the M2 extension ANDs in: the function reads `capability_aware ∧ (required_capabilities ⊆ worker_caps)` as `NOT capability_aware OR <match>`, so when the flag is false the match clause is trivially true (no capability constraint) while the existing allowlist clause still enforces. "Off" reverts #84's additions, **not** the allowlist. (`required_capabilities` is non-provisionable by construction, so there is no `− provisionable` term at claim time — that subtraction belongs only to the M4 gate; see §3 and §4.)
    - **OFF is an explicit, DOCUMENTED degraded mode, not a silent correctness change.** With the flag off, runs claim best-effort exactly as they do today, and a capability mismatch **degrades to the existing mid-run failure**: a docker-*needing* run may be claimed by a non-docker worker and fail mid-run with `command not found`/no-daemon — the precise failure #84 exists to prevent. This is a kill switch, and the docs (M5) must state that consequence plainly so an admin turning it off knows what they are trading.
    - **Default-on is safe and cheap.** On a **homogeneous** fleet (all workers share caps) the capability match is a no-op — every worker satisfies every run — so default-on costs a simple single-worker/uniform deployment nothing and only helps heterogeneous fleets. The flag mainly earns its keep as an **escape hatch** if inference false-positives (Decision 6/11) start blocking runs an admin would rather let through.
    - **v1 is ONE global flag.** Do **not** build sub-toggles now. Note for the future: the inference preflight (M4) is the layer most likely to warrant its own sub-toggle later, since false-positives there are the most probable reason to want "block off, routing on." That is a follow-up, not this PRD.

## Technical Design

### 1. Capability vocabulary + worker advertisement (M1)
- A server-owned capability enum + a `template → capabilities` map. **The v1 vocabulary is exactly `{docker, jvm}`:** `docker` (worker-self-reported, "daemon reachable", §299 — NOT template-derived) and `jvm` (template-derived, retrofitted in M5). The map keys on the curated worker-template registry `workertmpl.Names = []string{"base", "jvm"}` (`api/internal/workertmpl/workertmpl.go:22`, `DefaultName = "base"` at `:18`, mirror of `agent/templates/<name>/`), giving `base → {}`, `jvm → {jvm}`; `docker` is added to a worker's set from the register payload, not the map. Code-reviewed, tested. Growing the vocabulary later (e.g. `gpu`) adds one enum member + one map row; no wire change (the register field is already an open `string[]`, §299).
- **Persist the already-arriving self-report.** The register wire field exists (§299, `worker_protocol.go:218-226`, accept-and-ignore today). M1 threads `Capabilities` into `wsvc.Register`, adds a worker column (e.g. `workers.capabilities text[]` or a small join table — coder's choice; `text[]` mirrors the `uuid[]` allowlist precedent and needs no join), and stores the reported set. Compat is already satisfied (the api tolerates the field), so no fleet-wedge risk.
- **Size/resource envelope.** Workers already report a live resource sample on heartbeat — `cpu_pct` / `mem_bytes` / `mem_limit_bytes` (`api/internal/handler/worker_protocol.go:368-370`). `mem_limit_bytes` is the per-worker ceiling. M1 surfaces the envelope (from that sample and/or the #58 preset the worker runs) next to the drift badge; it does **not** need a new heartbeat field for the mem ceiling.
- Surfaced on the workers/admin pages next to the drift badge.

### 2. Run requirement model + static hint (M2)
- `runs.required_capabilities` (non-provisionable) — `text[]`, **default empty** (`'{}'`) — SHIPPED in M2 (migration `00142`). **`runs.required_tools`** (provisionable toolchain) was **deferred to M4** and does not exist yet; M4 adds and populates it. The empty default means **no backfill** of existing rows. But note the contrast with PRD #320: #320's `priority` default is a *kind-derived computed function*, so it needs no writer; **a repo-hint value depends on the repo row, so it CANNOT be a column default** and must be written by the enqueue path.
- **The concrete writer is `Service.createRun`** (`api/internal/workersvc/service.go:3961`), the private shared seam every issue-run creator funnels through — `CreateRun` (`:3861`), `CreateScheduledRun`, `CreateAutopilotRun`, `CreateScheduledAutopilotRun` all delegate to it, and it already takes `repoID`. It reads the repo's `required_capabilities` hint and passes it into the `CreateRun` sqlc query's params (the INSERT at `runtime.sql:359`). **So this contradicts the "INSERT-site untouched" framing for the repo-bearing insert only:** the issue-run INSERT gains the column in its VALUES; the repo-less kinds (judge/chat/self_improve/prompt — `judge.sql`, `chat.sql`, `selfimprove.sql`) leave it at the `'{}'` default and are genuinely untouched. `ci_fix` and `task` runs are repo-bearing too (`ci_fix.sql`, `task.sql`) and should inherit the same hint via their own create paths; for M2's routing scope the issue-run seam is the load-bearing one. Plan inference (M4) later union-merges into the same column via a separate `UPDATE`, never an INSERT.
- **Repo settings: a new `repos.required_capabilities` static hint**, stored and surfaced on the precedent of PRD #18's tier-2 opt-in — column like `repo_devbox_opt_in` (migration `00047_repo_devbox_opt_in.sql:10`), DTO field like `RepoDevboxOptIn` (`api/internal/apitypes/repo.go:20-23`; the exact-key wire test at `apitypes/wire_test.go:471` must gain the new key), and a repo-settings web control beside the existing tier-2 toggle in `web/src/pages/Repos.tsx` (the `repo_devbox_opt_in` switch at `:861-867`, its `setRepoDevbox` mutation at `:272`, the tool-profile picker at `:47`/`:824`). Optional issue-label parsing (`uzi:needs-<cap>`) — deferred (Open Questions).

### 3. Capability-aware claim (M2)
- **Extend `fn_worker_can_claim`, do not fork it** (its own comment, `00113:13-14`, reserves this). The function gains the claiming worker's capability set and the run's `required_capabilities` as arguments; the predicate ANDs a new clause: `run_required_capabilities ⊆ worker_caps`. **No `− provisionable` term here:** `runs.required_capabilities` holds only non-provisionable capabilities by construction (Decision 4 — the provisionable toolchain lives in `runs.required_tools`, which the claim never reads), so subtracting the provisionable set at claim time would be a no-op. The subtraction lives only in the M4 gate formula (`unmet`, §4). For docker this reduces to "a run requiring `docker` is claimable only by a worker whose capability set includes `docker`" — i.e. `docker ∈ required ⟹ is_docker`. The existing docker-worker→allowlist clause is unchanged and still ANDs in.
  - **Both call sites in `ClaimRun` change together** (claiming worker `:571`, candidate peer `:608`) — the peer subquery must evaluate the same extended predicate so fleet-spread (#216) never defers a docker-needing run to a peer that also cannot run it. This is a single migration + a `sqlc generate`; the ORDER BY (`:626`) and `FOR UPDATE SKIP LOCKED` (`:629`) are untouched.
  - Affinity/resume grace and all other claim semantics unchanged. **Coordinate the one-line WHERE edit with PRD #320's one-line ORDER BY edit** (both touch `ClaimRun`; whoever lands second rebases — PRD #320 D10/R1).
  - **The kill-switch gates this clause (Decision 13).** `workersvc/service.go` reads `KeyCapabilityAwareScheduling` from the settings cache in the same place it already reads `DockerRepoAllowlist` (`service.go:1100-1116`) and threads it as a `ClaimRun` param (`@capability_aware`, beside `@is_docker_worker`/`@docker_repo_allowlist`, `:1118-1127`). The extended `fn_worker_can_claim` reads the new subset clause as `NOT @capability_aware OR (required_capabilities ⊆ worker_caps)`, so a false flag makes the match trivially true and the run claims best-effort — **while the existing docker-worker→allowlist clause is left ANDed in and always enforced**. This is the whole mechanism by which "off" reverts #84's addition without touching the shipped allowlist.
- **No sweeper change is needed for a parked run.** A run that no online worker can claim simply **stays `queued` and unclaimed**, and no sweep pass touches a `queued` run: `SweepRunningTimeout` is scoped `WHERE status = 'running'` (`runtime.sql:1547`), `SweepClaimedNeverStarted` to `'claimed'` (`:1492`/`:1512`), and `RequeueRunsOfStaleWorkers` / `RequeueWorkerRuns` / `FailWorkerRunsOverCap` to a stale-or-named worker's `claimed`/`running`/`awaiting_*` runs (`:1581`/`:1620`/`:1607`). So a parked run is immune to every timeout/requeue pass **by construction** — no PRD #42 change, no new "distinguish a parked run from a stale claim" logic. Its "stuck for Xm" signal is a display concern (M3), not a sweeper concern.

### 4. "No eligible worker" surfacing — a reason over `queued`, NOT a new status (M3)
- **No new `runs.status` value (Decision 3).** The "no eligible worker" condition is a `health`/`health_reason` projection over the existing `queued` status — exactly as #361 surfaces its docker-specific reason. This preserves the run-status contract (a new status would touch the CLI status enum + the WS unknown-status rewrite) and needs **no migration** (`runs.health_reason` is free text; only `runs.health` is CHECK-constrained).
- **Add `repo_id` and `kind` to `ListActiveRunsForHealth` if absent; build on them if present** (`runtime.sql:2156`; at this base SHA its SELECT list `:2169-2172` carries neither). #361 (a parallel MR) makes the same addition for the non-allowlisted-repo case. Because the offline worker runs at ONE base SHA and cannot coordinate with #361's branch, phrase the change idempotently: add each column only if the SELECT does not already project it, so whichever MR lands second is a rebase, not a conflict.
- The queued-reason resolver (`queuedReason`, `health.go:504`; consts `:57-107`) gains a capability-mismatch reason mapped to the existing `healthWaitingWorker` enum (free-text `health_reason`, no migration — same pattern as `reasonAllWorkersBusy` `:73`). Surfaced with the remediation spectrum (switch existing / provision persistent via #58).
- **No sweeper change (see §3):** a parked run stays `queued` and is untouched by every sweep pass. **Timeout policy: indefinite, with a surfaced age** — this is a *display* choice (the age the UI/CLI renders from `health_since`), **not** a sweeper timeout. See Open Questions.

### 5. Plan-time inference + the gate (M4)
- **What M4 builds on (shipped in M1–M3, verified on `main`):** the `capability` package (`Filter`, `TemplateCapabilities`, vocabulary `{docker, jvm}`) is the classifier's source of truth for legal capability names — M4 must `capability.Filter` any inferred capability before it is written, exactly as the M2 write paths do (`handler/forge.go:951`, `service.go:1045`). The `present` set the gate cross-checks against is a worker's stored `workers.capabilities` (migration `00141`). The kill-switch accessor `CapabilityAwareScheduling(ctx)` (`settings.go:758`) already exists — M4 reuses it, does not re-add it. **M4 ADDS `runs.required_tools text[]`** (deferred from M2; new migration numbered above the live head at landing — see Goose note) and the `unmet` gate surface below.
- **The requirement set comes from a DETERMINISTIC function, not the LLM's prose.** M4's inference is a pure `detect(clonePath) → { required_capabilities, required_tools, size_class }` function over the clone — reading language manifests (`go.mod`, `package.json`, `pyproject.toml`/`requirements.txt`, `Cargo.toml`, `pom.xml`/`build.gradle`) + build/test/CI scripts + docker markers (`Dockerfile`, `docker-compose.yml`, testcontainers) — and **it is the tested unit**. The lead may *narrate* the readiness summary, but the requirement set the gate acts on is `detect()`'s output, so M4's success criteria are offline-checkable against fixture clones with no LLM in the loop. **This is a NEW function** (there is no general manifest→toolchain detector today): the closest in-repo precedent is `agent/src/js-deps.ts`'s deterministic BFS over `package.json` (`isProject`/the walk at `:322-368`) — follow that clone-scan shape, but the go.mod/Cargo.toml/pom.xml/pyproject arms are new. It cross-checks against present + provisionable and **classifies each need** (Decision 11), emitting the set + classification in the plan payload/schema.
- **The kill-switch gates the BLOCK, not the inference (Decision 13).** The agent **always** runs `detect()` (it is cheap, deterministic, and its output feeds display + the select-time mismatch flag regardless). The **server** reads `KeyCapabilityAwareScheduling` at the plan-approval gate and, when the flag is off, **suppresses the block** — the gate never blocks on capability/size, approval proceeds exactly as today, and the populated `required_capabilities` is simply ignored by the (also flag-gated) claim clause (§3). So the flag is NOT plumbed into the plan request; it gates only the server-side gate decision. This keeps the executor inventory-agnostic (Decision 8) and keeps the requirement set available for observability even when gating is off.
- The plan-approval gate (PRD #41 surface) computes `unmet = required_capabilities − (worker_caps ∪ provisionable)` (**this is the one place `− provisionable` applies** — §3's claim clause does not) (+ any size shortfall) and, when non-empty AND the flag is on, **blocks approval** with the reason + the remediation spectrum. **The concrete surface:** the plan is emitted from the worker's `gatePlan` path (`agent/src/runner.ts:2270`, which emits `{ kind: "plan", payload: { plan_md } }` at `:2290`); M4 extends that plan payload + the run DTO that carries it (`apitypes/run.go` — `PlanMd` `:156`, `PlanSource` `:163`) with the readiness set (capability list, estimated size, per-worker satisfaction). Path 2's resume reads `claim.plan_md` (`runner.ts:831`), unchanged.
- On gate remediation (Path 2), the run is **requeued** so a capable worker re-claims it and **re-plans then executes** (durable plan in `run_messages`; the resume re-plans by construction per Decision 6). No live session transfer between workers.

### 6. Surfacing (web + CLI) (M4/M5)
- Plan approval shows a **pre-run readiness summary**: every inferred need (capabilities, toolchain, size) with its status — ready · will-install (provisioned) · needs-admin (not allowlisted) · provision-a-worker (non-provisionable) — plus per-worker satisfaction; the block state renders the remediation spectrum. Auto-resolvable needs never nag.
- **Worker suggestion + select-time flag:** wherever the user picks or is assigned a worker, the UI suggests the fitting one and flags a mismatch inline ("this worker has no `docker`" / "too small: plan estimates ~4 GiB, this worker is 2 GiB") *before* the run commits.
- Workers page shows each worker's capabilities **and size**. A run blocked on capability/size shows *why* + how to fix.
- `api/cmd/uzi` (PRD #64 CLI): the same requirement/satisfaction/block info exposed (list/inspect a run's required caps + size; the blocked state + remediation hint) — the CLI is a second consumer of the same API (CLAUDE.md CLI-parity rule).

### 7. Docs + specs (M5)
- `specs/ai.md` (append-only, AI-design): the capability model, the provisionable-vs-not-vs-authorization split, the extended claim predicate, the "no eligible worker" **queued-run health reason** (a projection, not a new status — Decision 3), plan `required_capabilities`. It already reserves this under §299 ("Storage + the claim-time match predicate are PRD #84's to own") and lists #84 under "Not yet in scope" in `ARCHITECTURE.md:1382-1383` — update both.
- **Docs naming caution:** `docs/scheduling.md` **already exists and is about *time* scheduling (cron-like schedules)** (`order: 82`, `audience: user`). Do **not** overload it with capability scheduling — add capability-scheduling docs as their own page (or a clearly separate section) to avoid conflating "schedule a run for later" with "route a run to a capable worker." `ARCHITECTURE.md` gets a capability-scheduling paragraph (workers advertise capabilities; runs carry requirements; the gate).
- **Document the kill-switch degraded mode plainly (Decision 13).** The capability-scheduling doc + the admin-settings help text must state that turning `KeyCapabilityAwareScheduling` off reverts #84's additions (best-effort claiming, capability mismatch degrades to the existing mid-run failure) and **does not** disable the docker repo allowlist — an admin needs to know exactly what they trade.
- `specs/human.md` is user-stated — not edited without approval.

## Risks & Open Questions

- **Readiness inference is a floor, not a guarantee.** Primary-toolchain detection from language manifests is high-signal; the long tail of tools a test shells out to is **not** exhaustively pre-flighted (that would be brittle and give false confidence). Those stay backstopped by the existing mid-run failure + the judge's post-scan. The preflight catches the common, high-signal gaps pre-run; it must not be sold as "guaranteed green."
- **Inference false negatives.** A repo that needs docker in a way the scan misses won't be gated. Mitigated by the static-hint contract (Decision 6) and the fact that a missed inference degrades to today's clear mid-run failure, not a wrong result. Tune the scan heuristics; document them.
- **Provisionable-vs-not classification drift.** The gate's correctness depends on an accurate "provisionable" set; it must track PRD #18's tiers/allowlist as they evolve. A capability wrongly marked provisionable would let a run be claimed by a worker that then fails; wrongly marked non-provisionable would over-gate. Single source of truth + tests.
- **`fn_worker_can_claim` signature change is a merge coordination point.** Both PRD #320 (ORDER BY term) and #216 (already merged, spread WHERE) touch `ClaimRun`. #84 edits the WHERE predicate (extends `fn_worker_can_claim`). Land order does not matter for correctness; whoever lands after #320 rebases the one-line ORDER BY vs the WHERE. **Do not fork `fn_worker_can_claim`** — extend it (its comment says so).
- **★ Can execution resume from the approved plan alone? — RESOLVED (see Decision 6).** A cross-worker resume re-plans today (`sessionTranscriptResolvable` is worker-local, `runner.ts:649-655`/`:827`), so Path 2 works with no new machinery and the static hint is a convenience, not a requirement. No longer an open fork.
- **Sweeper/timeouts — RESOLVED: no sweeper change, and the timeout is a DISPLAY choice.** A parked run stays `queued` and unclaimed, and no sweep pass touches a `queued` run (`SweepRunningTimeout` `WHERE status='running'` `runtime.sql:1547`; `SweepClaimedNeverStarted` `'claimed'`; the requeue/fail passes scoped to a stale-or-named worker's `claimed`/`running`/`awaiting_*` runs). So it is immune to timeout/requeue **by construction** — there is nothing for PRD #42 to distinguish and no new logic to write. The "park indefinitely, surface the age" recommendation is therefore purely a **display** decision (the UI/CLI render the age from `health_since`); it is not a sweeper timeout. A future soft-notification (Slack nudge) can ride PRD #47's existing nudge machinery if desired, but that is not gating.
- **Auto-ephemeral remediation is a separate feature (#529), not #58.** Remediation (c) is not buildable until a new `uzi-controller` spawn-on-demand + teardown feature exists (#529; PRD #58 shipped only *static* provisioning, left this as an explicit non-goal, and is closed; #79's cost/GC question). #84 designs the gate to *support* it as a mode; it lights up when #529 lands.
- **Size estimation quality — never hard-block on size.** The plan's size estimate is a heuristic; a low estimate under-provisions (OOM mid-run → #42's shared-cgroup requeue), a high one wastes capacity. Start coarse (S/M/L bands tied to #58 presets), refine from observed run stats later. **Size is a soft failure and capability is a hard one** — flag and let the user proceed on size; only capability gates. (Restated from the original draft; kept.)
- **Issue-label declaration — RESOLVED: defer past M2.** Ship the repo-settings hint in M2; defer `uzi:needs-<cap>` label parsing (it duplicates the hint's role and adds a forge-read path). Revisit only if a concrete need appears. The repo-settings hint is sufficient for M2's routing.
- **Docs naming collision.** `docs/scheduling.md` is time-scheduling; capability-scheduling docs must not conflate with it (M5). Flagged so the implementer does not append to the wrong page.
