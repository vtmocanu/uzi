## Problem

**`notifier.go` (1325 lines, 49 top-level declarations)** is the `slacksvc` engine plus four rendering concerns that arrived from four different PRDs and never got their own file, although the package's convention is one concern per file (`chat_open.go`, `chatpost.go`, `chatactions.go`, `gate.go`, `gatekeeper.go`, `health.go`, `linker.go`, `mrkdwn.go`, `replier.go`, `socket.go`, `steer_pending.go`, …, none over 732 lines) and the test file `notifier_notify_test.go` already uses the `notifier_<seam>` stem the source never adopted:

- **Engine** (`:28-279`, `logf` `:818-837`): `NotifierStore`, `Poster`, the two queue consts, `Notifier`, the three event types, `NewNotifier`, `PublishNotification`/`PublishState`/`PublishMessage`/`PublishInput`/`PublishHealth`, `Run` (the drain loop that dispatches to `handle`, `handleNotify`, `handleHealth` and `chatpost.go`'s `handleChatMsg`), `logf`.
- **Generic inbox notification DM** (PRD #46; `:280-399`): `handleNotify`, `notifyFactMarkupStripper`, `notificationBlocks`, `notificationFallback`. This is the seam `notifier_notify_test.go` (272 lines) already tests by name.
- **Chat status line** (PRD #191 M2b; `:501-580`): `handleChat`, `renderChatStatus` (called from `handle` at `:415`; distinct from the message-stream path in `chatpost.go`).
- **Run-health thread** (PRD #47; `:730-817`): `handleHealth`, `ensureRoot`.
- **Run-state DM** (PRDs #25/#122/#268; `:400-500`, `:581-729`, `:838-1325` minus the shared helpers): `handle`, `handleQuestion`, `handleGate`, `handleMilestone`, and the renderers `rootBlocks`, `mrContextElem`, `decodeMilestones`, `decodeMilestoneIDs`, `milestoneCounts`, `inProgressTitle`, `renderThreadBlocks`, `cancelledThreadBlocks`, `limitWaitDetail`, `statusGlyph`, `mrLink`, `isHTTPSURL`, `forgeMrAbbrev`, `forgeMrRef`, `iid`.

## Decision Log

- **D1: four seams, not one per handler.** The run-state path (`handle` → `rootBlocks`/`renderThreadBlocks` → `statusGlyph`/`mrContextElem`/`limitWaitDetail`/`milestoneCounts`) is one tightly interwoven concern from three PRDs; cutting it per handler would scatter renderers a reader needs together. The three small seams each map to exactly one originating PRD (#46, #191 M2b, #47) and one existing test grouping; the state seam maps to the rest of `notifier_test.go`. A dispatch/render cut of `notifier_state.go` was considered and dropped: it trades cohesion (a `handle*` and the blocks it builds in different files) for size the file does not need to lose, and an optional step is a judgment call an auto-approved worker cannot make.
- **D2: package-wide helpers stay in `notifier.go`.** `runURL`, `runLink`, `boundReason` (+ `maxFailureReason`), `threadSectionBlock` and `threadMrkdwnElem` are called from `chatactions.go`, `gate.go`, `question.go`, `health.go` and `chatpost.go`; the #963 rule is that a helper serving several seams stays in the base file. A `render_shared.go` would be a fifth file for ≈40 lines and a new name for readers to learn.
- **D3: both `go doc -all` and `go doc -u -all` are captured.** The exported surface (the two interfaces, `Notifier`, `NewNotifier`, the six exported methods) stays in the base file, so `-all` is a real check here; `-u -all` additionally pins every unexported declaration this PRD moves and is the one SC2 names, following #1025 D1 so the two PRDs landing the same night use the same instrument.
- **D4: `handleChat` stays a separate file although it is 80 lines.** It is the PRD #191 M2b status-line path, called from `handle` on a state transition, and distinct from `chatpost.go`'s `handleChatMsg` (the message stream). Putting it in `notifier_state.go` would be defensible; a file of its own is what a reader looking for "the chat status line" expects given `chat_open.go`/`chatpost.go`/`chatactions.go` already exist as per-concern files.
- **D5: the held PRD #1020 is repointed here, not left for #1020 to re-derive.** #1020 has no run and its M3 lands inside the notify seam; three identifier-level repoints now cost less than a base-staleness rebase later, and they keep `prds/1020` a truthful design record on the day it is sent.
