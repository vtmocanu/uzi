# PRD #1976: Site-list jobs: per-product site-list allowance and profile-bound jobs on the isolated lane

**Status**: Done (2026-10-01). Both milestones complete. Unblocked by PRD #1909 (PR #2002, `c4c94e2c`). Split out of PRD #1906 (its M8).

## Problem

PRD #1906 shipped site lists, the fetcher and the isolated no-internet worker lane, and PRD #1908 shipped repo-less jobs, but the two are not connected: job create refuses `egress_profile` with 422 `not_supported`, so no job can do official-sources research. The refusal stays until a product token can be limited to the site lists its product is allowed (PRD #1906 Decision 13); lifting it without that check would let any product token use any list.

## Outcome

A job can name a site list, and runs on the isolated lane with only that list's hosts reachable through the fetcher, when its caller may use that list.

Acceptance examples:
1. An admin allows product P to use list `vendor-docs`. A P product token creates a job with `egress_profile: vendor-docs`; the job is claimed only by a lane worker, fetches an allowed page, and its source log shows the fetch.
2. The same token names list `other-docs`, which P is not allowed: job create returns 403 and no run row is created.
3. A user token (not a product token) names any existing list: accepted, as before for user-owned runs.
4. The admin removes P's allowance for `vendor-docs`: the next P job naming it gets 403; jobs already created are not changed.

## Out of scope

- Live k8s verification. It is tracked as PRD #1906's M9 checklist (maintainer-owned, optional, not a milestone here).
- New site-list features (editing hosts, wildcards): PRD #1906 owns them and they are done.
- Job files and product skill sets: PRD #1909.
- Any change to lane placement rules (PRD #1906 Decision 9) or to the Claude-only rule for profile-bound runs (Decision 10).

## Modules and seams

- **Job create (`workersvc` `CreateJobRun`, `/api/v1/jobs` `V1JobCreateRequest`)**: gains the `egress_profile` decision. Interface: a caller identity (user token or product token with its product) plus a list name in; either a created profile-bound job or a typed refusal (403 not allowed, 404 unknown list, 422 for the existing non-list refusals). Invariant: the 422 `not_supported` on `egress_profile` is removed in the same change that adds the allowance check; no build accepts `egress_profile` without it. Tested through the `/api/v1/jobs` endpoint and the service call, live-DB.
- **Allowance store (new table, product x profile)**: admin writes are cookie-only (never a product or personal token), reads are admin-only. Tested through the admin API.
- **Lane claim**: unchanged clause (Decision 9); a profile-bound job must satisfy it and the job claim clause together, including PRD #1909's `job_files_v1` rollout gate in `ClaimRun` (`api/internal/store/queries/runtime.sql`, the `r.kind <> 'job'` arm). Tested by claim tests: a lane worker claims a profile-bound job; a non-lane worker never does.
- **Claim assembly (`api/internal/workersvc/claim_assembly.go`, `job_claim.go`, `claim_isolated.go`)**: today a job claim returns from `assembleJobClaim` before `isolateClaim` runs, so a job never gets a fetch grant or the isolation strip. A profile-bound job's claim must carry both the job block (inputs, model credential, product skills) and the `isolated_fetch` grant with the bound profile's snapshot, and must pass the same strip `isolateClaim` applies to other profile-bound runs, with one narrow exception: the job's own product skill set (PRD #1909, admin-approved, product-scoped) is kept, because official-sources research is the job type product skills exist for. `stripForIsolation` keeps clearing every other skill source. An unbound job's claim stays byte-identical to today.
- **Worker runtime (`agent/src`: `IsolatedRunner`, `IsolatedExecutor`, `JobRunner`)**: today the isolated executor does not offer `submit_job_result` (its `ISOLATED_TOOLS` comment defers it to this work), the isolated runner has no job input download, output upload or result post, and the job runner has no fetch tool. A profile-bound job runs one session with the isolated tool set (`ISOLATED_TOOLS`, including the fetch tool) plus `submit_job_result`, plus `Skill` and the single local product-skills plugin (MCP discovery off) only when the job carries product skills, and nothing else (no Bash, no SDK Web tools, no subagents, no other plugin), downloads its inputs, uploads its outputs and posts its result through the existing job routes, then completes. Which runner hosts it is the implementer's choice; the isolation guarantees of PRD #1906 (fixed tool set, path guard, fail closed without a valid grant or fetcher config) must hold unchanged.
- **Lane worker route allowlist (`api/internal/handler/worker_lane_routes.go` `laneWorkerAllowlist`)**: gains the job routes a profile-bound job needs: PRD #1909's file routes (`GET /api/worker/runs/{id}/files/{fileID}`, `POST /api/worker/runs/{id}/files`) and PRD #1908's result route (`POST /api/worker/runs/{id}/job-result`), each still fenced to job runs as today. Verified against main `12b6f6f2`: none of the three is on the list.

## Testing decisions

- Live-DB tests at the job-create seam for every row of the outcome examples, plus: unknown list 404, disabled product 403, a product token whose product has no allowance rows is refused (fail closed), and the allowance check runs for every product-token create (a mutation run removing it must redden a test).
- Claim tests for profile-bound jobs, following the existing lane-placement tests from PRD #1906 M5, plus claim-assembly tests: a profile-bound job's claim carries the job block and the fetch grant and passes the isolation strip; an unbound job's claim is unchanged.
- An end-to-end regression on a lane worker (stub executor, fake fetcher): claim, input download, an allowed fetch, a refused off-list fetch, output upload, result post, `completed`, with the source log recording the allowed fetch. A mutation dropping the fetch grant, the result route from the allowlist, or the job tool from the isolated tool set must redden it.
- Route-table test that the three job routes (the two file routes and `job-result`) are on the lane allowlist, and every worker route outside the existing lifecycle allowance plus those three still refuses a lane worker.
- Skills tests: a profile-bound job's claim keeps only its product's approved skills (no repo, user or builtin skills survive the strip); the lane session's effective tool set is exactly the isolated set plus `submit_job_result`, plus `Skill` and the single product-skills plugin only when that job carries skills; a job with no skills offers neither.
- Prior art: PRD #1906 M3/M5 live-DB tests, PRD #1908 M2/M3 job tests.
