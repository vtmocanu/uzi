## Problem

The activity pane (`web/src/components/ActivityFeed.tsx`, mounted at `RunView.tsx:394`) has three distinct UX failures, all reported by the user:

1. **Scroll spam.** `useRunStream` commits once per websocket frame (the `commit(state)` after `applyFrame`, `useRunStream.ts:100`), so `messages.length` increments one message at a time; the follow-scroll append effect (`useFollowScroll.ts:65`) re-fires on every increment and hard-jumps the viewport with `el.scrollTop = el.scrollHeight` (`useFollowScroll.ts:44`, deliberately instant, never smooth, no batching). A live agent burst (a `tool_use`, its `tool_result`, interleaved `text`/`thinking`, per-tool `status`) arrives as many frames in quick succession, so the pane visibly jerks to the bottom on every one. There is no way to watch the run without being dragged along.

2. **No real "who's alive."** "Active" is computed as `runningLive ? groups[groups.length - 1]?.agent` (`ActivityFeed.tsx:181`) — i.e. only the agent that authored the *newest* message, and only while `status === "running"`. A stalled agent still reads "active"; every other agent reads "idle" the instant a later one speaks; there is no `working` / `waiting` / `done` distinction and nothing reflects that the whole run is blocked on a human gate or a dead worker. You cannot glance at the pane and see the crew's state.

3. **Follow-ups vanish; no delivery signal.** A follow-up is a single insert into `run_user_inputs` (`CreateRunInput`, `runtime.sql:755`, reached through `SubmitInput`, `workersvc/service.go:1671`, at the plain-input insert `:1731`) — it is **never** written to `run_messages`, so nothing echoes it in the UI. The `FollowUpComposer` (`RunView.tsx:551`) clears the textarea on send (`setText("")`, `:565`) and shows the user nothing: no record that the message exists, and no indication of whether the worker has picked it up. The worker consumes inputs FIFO via `ConsumeInputs` (`workersvc/service.go:1250`), which stamps `consumed_at` — a perfect "the agent has it" signal that the UI never reads.

## Solution Overview

Rebuild the pane around the crew, not the scroll, and give the steering channel a visible queue.

- **Crew roster strip** at the pane top: one compact chip per agent role with a state dot — `working` / `waiting` / `idle` / `done` (plus a `stalled` sub-state) — so "who's alive" reads at a glance without opening a single log. Click a chip to jump to that agent.
- **Logs collapse by default.** Each agent is an accordion, closed by default, its header carrying a live one-liner ("running `go test ./...`") that updates *in place* (no scroll) and a `+N` unseen-message pill. Expand only what you care about — with an **Expand all** affordance and auto-expand for finished / single-agent runs so reading a done run is not death-by-clicks.
- **Follow is opt-in and contained.** A `Follow live` toggle, **off by default**, replaces the global auto-jump; when on, it tails only the *expanded* agent's own bounded-scroll region. The whole-pane yank is gone.
- **Steer queue with delivery status.** The steer panel grows a queue (in its own card, surviving the run going terminal): each follow-up shows immediately as **Queued**, flips to **Delivered** when the worker consumes it (`consumed_at`) — or **Delivered — applies after approval** if consumed while the run is at a plan gate — and to **Not delivered — run finished** if the run goes terminal with the input still unconsumed. Read from a small DTO over `run_user_inputs`; live via a data-less `input` WS frame that mirrors the existing `health` frame, and reconciled by REST refetch so a dropped frame self-heals.
- **No migration; thin backend.** The crew states are derived **client-side** from the existing message stream + `run.health` + `run.status`. The server work is one owner-scoped read endpoint (new `follow_up`-scoped query), one `Broadcaster.PublishInput` fan-out, and returning the created row from the existing follow-up write. There is **no schema change**.
- **CLI parity in the same MR** (CLAUDE.md "second consumer" rule): `uzi run inputs <run-id>` lists the steer queue with delivery status.

## Design Decisions

1. **The crew roster derives every state CLIENT-SIDE from data the pane already has — no new backend, no per-agent heartbeat.** The pane already receives the full `RunMessage[]` (each carries `agent`, `created_at`, `kind`, `seq`; `api.ts:986`), the `Run` (with `status` and `health`/`health_reason`, `api.ts:684`/`:671`), and `connected`. Everything the roster needs is a pure function of those. Grouping already exists (`groupByAgent`, `ActivityFeed.tsx:41`, keyed `m.agent ?? "lead"`); the roster adds a per-agent aggregate (last-activity time, message count, last kind) and a state function. Rejected alternative: surfacing the worker's raw `last_heartbeat_at` (`Worker.last_heartbeat_at`, `api.ts:611`) into the pane — **`run.health` already is that signal**, server-derived by PRD #47's sweeper (`waiting_worker` = no live worker, `stalled` = worker went quiet), and already pushed to this client over the `health` WS frame → `refreshRun` (`useRunStream.ts:106`). Re-plumbing the heartbeat would duplicate a derivation that already reaches the browser. The pane **maps `run.health`**, it does not re-derive liveness.

2. **The per-agent state ladder — the ACTIVE speaker trusts `run.health`; recency governs only the non-active split.** The original draft gated `working` on a 45s client recency and left a hole: with `STALE_MS=45s` but the server stall flag defaulting to **300s** (`health_stall_seconds`, `settings.go:127`), the active speaker during any quiet tool call between 45s and 300s (`go test`, `npm ci`, a build — the *common* busy case) fell through every branch to no state, so the pulsing dot vanished exactly when the agent was hardest at work. Corrected ladder, for a **live** run (`status ∈ {claimed, running}`):
   - **active speaker** = the agent of the newest message.
     - `working` — active speaker when `run.health == ok`. **Recency does not gate this** (the fix): if health says the worker is fine, a long tool call still reads `working`. Pulsing green.
     - `stalled` — active speaker when `run.health ∈ {stalled, slow, looping}`. `looping` maps here (amber), **not** to green `working` — it is a PRD #47 *warn* flag ("spinning without progress") and must not read as healthy, matching the `HealthFlag` warn chip already rendered for the same run (`RunView.tsx:102`).
   - **all agents** are `waiting` when `run.status === "awaiting_approval"` (blocked on the human gate) or `run.health == waiting_worker` (blocked on a worker); this dominates the per-agent view.
   - Otherwise, for a **non-active** agent, the 45s recency heuristic applies: last activity `< STALE_MS` ⇒ `waiting` ("recently handed off"), `≥ STALE_MS` ⇒ `idle`.
   - **done** — on a **terminal** run (`completed`/`failed`/`cancelled`), every agent is `done`.
   - **empty** — `groups.length === 0` (a `queued` run, or one that failed before any agent spoke): the strip renders a single muted "waiting for the first agent…" placeholder, not zero chips.

   **Honesty boundary:** the `working`/`stalled`/gate-`waiting`/`done` states are now exact (driven by `status`/`health`). The remaining approximation is the non-active `waiting`↔`idle` split — without an SDK handoff / subagent-boundary event (`agentOf` only reads `subagent_type`, `sdk-messages.ts:29`), "blocked on lead" vs "just quiet" is inferred from recency, and the `useNow(30_000)` tick (`ActivityFeed.tsx:149`) refreshes it coarsely (up to 30s lag). Both are acceptable for a non-active cosmetic split; a precise `handoff` control message is the named future refinement. Because the active speaker no longer depends on recency, the coarse tick never affects the `working` dot.

3. **Collapse-by-default + opt-in Follow REPLACES the global auto-scroll — a deliberate behavior change, scoped per-agent, with a finished-run escape hatch.** Today `useFollowScroll(messages.length)` owns one scroll container for the whole feed and auto-jumps it (`ActivityFeed.tsx:147`, `useFollowScroll.ts`), and `collapsed` starts empty so every agent is expanded (`ActivityFeed.tsx:146`). v2 inverts the default: the outer pane does **not** auto-scroll, each *expanded* agent body is its own bounded (`max-height`) scroll region, and the `Follow live` toggle (default **off**) tails only expanded agents. This is a genuine change to existing behavior (CLAUDE.md: confirm before changing functionality) — it is the explicit user request, recorded here as authorized. **Finished-run regression guard (S5):** collapse-by-default would otherwise turn reading a completed 8-agent run into 8 clicks; so on a **terminal** run (and on a **single-agent** run) the accordion **auto-expands**, and an **Expand all / Collapse all** control is always present. **Refactor accuracy (N4):** the cap-and-expand for very long runs is owned by `ActivityFeed`'s own `showAll` state + array slice (`ActivityFeed.tsx:177`), **not** by `useFollowScroll` — it is untouched. The `+N` "unseen while collapsed" pill is a genuine **rewrite** (a different semantic from the hook's current "unseen while scrolled up", `useFollowScroll.ts:65`), not a repurpose. **Kept as-is:** the cap-and-expand (`CAP_TRIGGER=1000`/`CAP_VISIBLE=500`, `ActivityFeed.tsx:115`), the per-tool-result expanders and Bash clamp (`RunEvent.tsx`), the `role="log"` a11y wiring, and the `prefers-reduced-motion` neutralization of pulse/spin (`index.css:195`) — the crew dot's pulse must honor it.

4. **The steer queue is a DTO over `run_user_inputs`, NOT a `run_message` — this sidesteps the gapless-`seq` allocation race.** The obvious "just echo the follow-up into the feed" is a trap: `run_messages` carries a **gapless per-run `seq`** (`InsertRunMessage`, `runtime.sql:580`, `ON CONFLICT (run_id, seq) DO NOTHING`) and the **worker is the sole seq allocator** — it seeds `this.seq = lastSeq` once at claim and increments locally without re-reading the DB (`agent/src/batcher.ts:39`), streaming each message. If the API injected a `user_message` at a server-chosen `last_seq+1`, it would collide with a seq the worker has already assigned locally but not yet flushed — and `ON CONFLICT DO NOTHING` would **silently drop the worker's message with no retry**, corrupting the one invariant the whole live stream rests on. A server-owned seq allocator is a cross-cutting rewrite of the batcher/resume/idempotency contract, correctly out of scope. So the follow-up is **not** a message:
   - The queue is read from the existing table via a **new `follow_up`-scoped, newest-first query** — NOT the judge's `ListRunInputsForRun` (`judge.sql:37`), which is `ORDER BY id ASC LIMIT @lim` (oldest-first, capped, all kinds) and would drop the *newest* follow-ups behind the `@lim` cap on a busy or chat run. The new query filters `kind='follow_up'`, orders newest-first, and is owner-scoped by the run resolve.
   - Delivery status is `consumed_at`: **NULL → Queued**, **set → Delivered**. No new column, **no migration**. (Note: the existing worker-facing `InputDTO`, `service.go:1239`, has no `consumed_at` and is a different struct — the read endpoint returns a new `SteerInputDTO {id, body, created_at, consumed_at}`.)
   - This is the same architectural move the health frame makes: a fact that lives authoritatively in a table, surfaced by re-read rather than pushed as stream payload.

5. **Delivery goes live via a NEW data-less `input` WS frame — but REST refetch is the source of truth, so a dropped frame self-heals.** `consumed_at` is stamped inside `ConsumeInputs` (`workersvc/service.go:1250`, worker-polled via `worker_protocol.go`'s inputs endpoint) in a single autocommit statement (`ConsumeRunInputs`, `runtime.sql:808`), so the value is committed before Go returns. After a consume that included ≥1 `follow_up`, the service calls a new `Broadcaster.PublishInput(runID)` that broadcasts `Event{Type: "input"}` carrying **no data**; the browser re-reads `GET /runs/{id}/inputs` — exactly how `health`/`state` frames work (`hub.go:118`, "carries NO authoritative data — the browser re-reads"). **Critical correction (S1 / hub back-pressure):** the hub silently drops frames for slow subscribers, and unlike `message` (self-heals via seq gaps) or `health` (continuously re-fired by the ongoing message stream), the `input` frame would be the *only* trigger for an inputs refetch — a single drop would strand the queue at "Queued" for an already-delivered input until reload. So the `input` frame is a **fast-path optimization, not the sole mechanism**: `useRunStream` refetches inputs on **mount, on `ws.onopen` / reconnect** (alongside the existing message `replay()`, `useRunStream.ts:89`), on any `state`/`health`-driven `refreshRun`, and on the `input` frame. That restores true parity with `health`.

   **Backend surface (corrected — not "one call site"):** the service holds a `Broadcaster` **interface** (`service.go:272`), not a `*Hub`. `PublishInput` must be added to: the interface; `MultiBroadcaster`'s fan-out (`service.go:292`); the hub impl (`hub.go`, alongside `PublishHealth`); a **no-op** on the Slack `Notifier` (`slacksvc/notifier.go:163`, exactly as it no-ops `PublishMessage` — the earlier "Slack shape untouched" claim was wrong); and the `fakeBroadcaster` test double (`service_test.go:1757`). The `ConsumeInputs` call site must guard `if s.bcast != nil` (mirroring `AppendMessages`, `service.go:915`) — it never broadcast before, so an unset broadcaster (some tests) would otherwise panic. The `Event` struct (`hub.go:31`) already marshals a bare `{"type":"input"}` (only `Type` lacks `omitempty`).

6. **"Delivered" means the worker HAS the input for its next turn — not that it acted on it. Two documented consumed-but-dropped cases.** `ConsumeInputs`'s own comment states delivery marks the input consumed with no separate ack, so a worker crash right after the GET drops that input, "an accepted MVP trade-off … the user can re-send" (`service.go:1248`). v2 does not change that contract; it makes it **visible**. Semantics shown: **Delivered = handed to the worker for its next turn**; whether it was *acted upon* is visible in the agent's subsequent messages, and if a consumed-but-dropped input is never acted on the run's `health` (`stalled`) surfaces it and the user re-sends. **Second drop case (S3):** a follow-up consumed while the run is at a plan gate is buffered worker-side; if the human then **rejects** the plan, the run fails and the buffered follow-up is never acted on — "Delivered" was shown but nothing happened. Both are documented in Risks, not fixed here.

7. **Delivery chip is derived client-side from `(consumed_at, run.status)`; the gate case gets its own copy; the queue must survive the terminal unmount.** The chip:
   - `consumed_at` NULL + non-terminal + not-at-gate → **Queued**
   - `consumed_at` NULL + `awaiting_approval` → **Queued** (the worker *will* consume it — see below — but until it does it is genuinely pending)
   - `consumed_at` set + `awaiting_approval` → **Delivered — applies after approval** (S3): a follow-up submitted during a gate **is** consumed immediately — the steering poll loop starts before the gate and runs throughout (`steering.start()`, `runner.ts:171`; consume-on-read routing `follow_up` to a buffer, `steering.ts:117`), so `consumed_at` is stamped and the `input` frame fires while the run is visibly blocked on the human's own approval. A bare "Delivered" there would mislead; the qualified copy is honest.
   - `consumed_at` set + running/terminal → **Delivered**
   - `consumed_at` NULL + terminal → **Not delivered — run finished**

   **Blocker fix (B1):** this last state is *unreachable* if the queue lives inside `FollowUpComposer`, because that component is mounted only when `!terminal` (`RunView.tsx:403`, `terminal = isTerminalRun(run.status)` `:170`) — the composer and its component-local queue state unmount the instant the run completes, so the user sees the queue vanish, never "Not delivered." So the **queue is hoisted into its own card, rendered for terminal runs too** (read-only when terminal — no textarea), and its inputs state is **lifted into `useRunStream`** (which persists across the terminal transition) rather than held in the composer. The composer keeps only the textarea + send.

8. **`GET /runs/{id}/inputs` is `RequireUser`, owner-only — matching the write; a non-owner admin degrades gracefully, not to an error.** The follow-up **write** (`CreateRunInput`) is `RequireUser` and owner-only (`SubmitInput(r.Context(), user.ID, …)`, `workers.go:541`; guarded by `TestCreateRunInputIsOwnerOnly`). The **read** matches: `RequireUser`, run resolved owner-scoped via `GetRunByIDForUser` (owner or 404), `kind='follow_up'` only. `RequireUser` (not cookie-only `RequireAuth`) is what lets `uzi run inputs` read it from a CLI token (Decision 10); owner-only preserves the read-only ceiling — a `uza_` `admin_ro` token keeps `IsAdmin`, so an owner-or-admin read would leak another user's steer text (follow-ups are never in `run_messages`, so this genuinely closes a leak). **N2 consequence:** the run *view* is owner-or-admin, so a non-owner admin can open another user's run and see its feed, but `GET /inputs` returns 404 for them and `SubmitInput` would 404 too. The queue card and composer must therefore render **empty/hidden and silent** for a non-owner viewer (a 404 on `/inputs` is treated as "no queue to show"), never an error banner.

9. **The pane redesign is FRONTEND-ONLY; the delivery feature is the only backend touch. M1 pre-lands the shared `RunView` seam so M2/M3 are genuinely parallel.** Problem 1 (scroll) and Problem 2 (crew) are pure `web/` refactors consuming data already on the wire (Decision 1). But M2 and M3 both touch `RunView.tsx` (`ActivityFeed` mount `:394` needs the `run` object for `health`/`status`; the composer/queue mount `:403` needs reworking), so they are not literally file-disjoint. **Fix:** M1 pre-lands the seam — pass the `run` object into `ActivityFeed`, and extract `FollowUpComposer` into its own file (`web/src/components/FollowUpComposer.tsx`) with the queue hoisted to its own card (Decision 7's B1 fix). After that seam, M2 (crew/scroll, `ActivityFeed.tsx` + the follow-scroll hook) and M3 (delivery, `hub`/`workersvc`/`ConsumeInputs` + the queue card + `useRunStream`) touch disjoint files and run in parallel.

10. **CLI parity: `uzi run inputs <run-id>`.** The CLI already sends follow-ups (`uzi run follow-up`, `run.go:263`; `kindFollowUp`, `run.go:23`) but cannot see them afterward. Add `uzi run inputs <run-id>` → `GET /runs/{id}/inputs`, printing each follow-up with its delivery state (`queued`/`delivered`) and relative time, `--json` for the raw DTO. Owner-scoped read works from a `uzc_` or read-only `uza_` token (Decision 8). **Chat caveat (N3):** a chat run seeds every turn as a `follow_up` row in `run_user_inputs` (`CreateChatRun`/`SubmitChatMessage`, `chat.go:284`), so `uzi run inputs <chat-run-id>` would list the seeded prompt + all chat turns as follow-ups; the command notes this (chat has its own web composer, unaffected). An **issue** run's queue starts genuinely empty — its prompt rides the claim payload's `issue_description`, not an input row.

**Interactions (for completeness):** **Chat runs** (`kind='chat'`) use a different *web* composer (`PostChatMessage`, `chat.go`), but — corrected — they **do** write `run_user_inputs` rows for each turn (`chat.go:284`); the web steer queue is scoped to issue/CI-fix runs where the composer is `follow_up`-based, and the CLI caveat above covers chat. **`approve_plan` / `cancel` / `reject_plan`** also flow through `run_user_inputs` but own their own UI (plan panel, Stop button); the queue renders **only `kind='follow_up'`**. **Slack** steering (`slacksvc/replier.go:177` submits `follow_up`) benefits for free — the same rows, now visible in the web queue — and the Slack `Notifier` gains a no-op `PublishInput` (Decision 5). **Hosted workers** need no change: the worker already stamps `consumed_at` via the endpoint it already calls; only the API's post-consume broadcast and the write's richer response are new. **The board cache / forge** are untouched (no forge write anywhere in this PRD).

## Success Criteria

- Watching a live run, the pane **no longer auto-scrolls** on incoming frames; a burst of tool activity updates the crew one-liner and `+N` pill **in place** without moving the viewport. Turning `Follow live` on tails only the expanded agent(s). Opening a **finished** run shows its agents expanded (or one Expand-all click), not 8 empty accordions.
- The crew strip shows, at a glance, which agents are `working` (pulsing — **including through a multi-minute tool call**, driven by `run.health` not a 45s timer), `stalled` (incl. `looping`), `waiting` (at a gate / on a worker / just handed off), `idle`, or `done` — a stalled or looping agent never reads healthy green (the Problem-2 bug).
- Sending a follow-up shows it **immediately** as **Queued**; it flips to **Delivered** on consume (or **Delivered — applies after approval** at a gate), and to **Not delivered — run finished** if the run reaches terminal still unconsumed — and the queue **remains visible after the run finishes**. A follow-up consumed while the browser was disconnected reconciles to Delivered on reconnect (not stuck at Queued).
- **No `run_message` is created for a follow-up** and the gapless `seq` stream is untouched (proven by the M5 e2e leg); **no token is spent and no forge write happens** anywhere.
- `uzi run inputs <run-id>` shows the same queue + delivery states as the web, from a CLI token; a read-only `uza_` token reads its own and is refused (404) on another owner's.

## Risks

- **`waiting` vs `idle` is a heuristic in v1** (Decision 2): without an SDK handoff event, "blocked on lead" vs "just quiet" is inferred from recency and refreshed on a coarse 30s tick. Mislabels are cosmetic (both non-active) and never touch the exact `working`/`stalled`/gate-`waiting`/`done` states. A `handoff` control message is the named refinement.
- **"Delivered" can show for a consumed-but-dropped input** — a worker crash right after the GET (Decision 6), *or* a follow-up consumed at a plan gate that is then **rejected** (S3): consumed, buffered, never acted on. Both are pre-existing consequences of the consume-on-read steering contract, now merely visible; the run's `health`/terminal state surfaces the stall and the user re-sends. Not introduced here; not fixed here.
- **Behavior change to the scroll model** (Decision 3): users habituated to the always-tailing feed must learn opt-in Follow. Mitigated by collapse-by-default reading as obviously intentional, the finished-run auto-expand, Expand-all, and the retained "jump to newest" affordance.
- **Refactoring the follow-scroll model to per-body** risks regressing the paused-follow "+N" logic it co-owns (the pill is a rewrite, N4); cap-and-expand is independent (`showAll`, `ActivityFeed.tsx:177`) and lower-risk. M2's vitest pins both.
- **`input`-frame back-pressure** (Decision 5): the hub drops frames for slow subscribers; delivery correctness therefore rests on the REST refetch (mount/reconnect/state/health), not the frame. The M5 dropped-frame test is the guard — if that refetch path regresses, the queue silently strands at Queued.

## Resolved Questions

- **Steer queue lives in its own card, not inside the composer and not inlined into the feed.** Inlining into the seq-ordered timeline would require the API to allocate `run_messages.seq`, racing the worker (Decision 4). Keeping it inside the `!terminal`-gated composer makes it vanish on completion (B1). So: own card, state in `useRunStream`, rendered (read-only) for terminal runs. Inlining into the feed is a future item gated on unifying seq allocation.
- **The active speaker's liveness comes from `run.health`, not client recency.** The 45s recency was a hole for long tool calls (B2); health is the authoritative, already-streamed signal (PRD #47). Recency survives only for the non-active `waiting`↔`idle` cosmetic split.
- **Crew liveness reuses `run.health`, not raw `last_heartbeat_at`** (Decision 1). (Corrects the mock's earlier "surface `last_heartbeat_at`" note, now aligned.)
- **The queue renders only `follow_up`.** `approve_plan`/`cancel`/`reject_plan` share the table but own dedicated UI; chat turns also live there but have their own composer (CLI caveat only).
- **No schema change.** Delivery is `consumed_at` on an existing table; crew state is client-derived. Zero migrations — unusually small backend surface for a user-visible feature (a new query, a `Broadcaster` method, a richer write response, one data-less frame).
