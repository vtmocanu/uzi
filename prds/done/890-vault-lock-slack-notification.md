# PRD #890 — Slack notify users when a deploy locks their vault

**Issue**: [#890](https://github.com/vtmocanu/uzi/issues/890)
**Status**: Complete (2026-08-31) — all milestones (M1-M5) shipped
**Priority**: Medium
**Author**: created via `/prd-create`

## Problem

The per-user vault (PRD #32) holds each user's unwrapped DEK **only in-memory**, in the singleton `Vault`'s `cache map[uuid.UUID][]byte` (`api/internal/vault/vault.go:85-93`). Presence in that map == unlocked. There is no DB flag and no external cache, so:

- **Every api restart drops the map, and every vault reverts to locked.** Because each release rolls new pods, a locked vault is the guaranteed state after every deploy (the code's own contract comments say so: `vault.go:59-61`, `handler/vault.go:15-17`, `docs/vault-threat-model.md:26-28,90-92`). The only exception is the seed admin, boot-unlocked at `api/cmd/server/main.go:393-402`.
- **A locked vault silently blocks work.** The worker claim gate `!s.vlt.Unlocked(...)` (`api/internal/workersvc/service.go:1252`; also `chat.go`, `health.go`) refuses to claim a run whose owner's vault is locked. Scheduled jobs (nightly sweeps, self-improve) and any queued run therefore stop claiming until the user next logs in and unlocks. This is the "one-time rollout stall" the threat model already names (`docs/vault-threat-model.md:157-165`).
- **Nothing tells the user.** No event, hook, or signal fires when the vault transitions to locked, and there is no notification when unlock state is lost on boot. The user finds out only when they notice a run never ran.

## Goal

After a restart, proactively notify each affected user over Slack that their vault is locked and needs unlocking, **before** their queued or scheduled work silently stalls. (Precisely: a locked owner's `queued` run is not claimed and just stays queued — it does not enter `failed`, so the existing run-failure notifier never fires for it; this is a silent stall, not a failure.) Scope the notification to users the lock actually affects, and never spam.

## Solution overview (trigger model: post-deploy, scoped)

A **boot reconciler** runs shortly after startup (and re-checks on the scheduler's existing tick). For each user who:

1. has a vault row (`user_vaults`), i.e. actually uses personal secrets;
2. has a confirmed, opted-in Slack delivery target (the existing `GetSlackDeliveryForUser` gate: `slack_notify = true AND slack_link_confirmed_at IS NOT NULL AND slack_resolved_id IS NOT NULL`, `api/internal/store/queries/slack.sql:79`);
3. has **work the lock actually blocks** — this must mirror what the claim gate withholds, not "any non-terminal run". `ClaimRun` claims exclusively `status = 'queued'` (`api/internal/store/queries/runtime.sql:596`), so a `running`/`claimed` run already holds its token and is unaffected by the lock. The correct predicate is: **≥1 run in `queued` (or `awaiting_approval`/`awaiting_input`, which return to `queued` on resume)** **OR** **≥1 schedule that will actually fire** — `enabled AND status = 'active' AND next_fire_at IS NOT NULL`, mirroring the due-gate `ClaimDueSchedules` (`api/internal/store/queries/schedules.sql:205`). A `fired`/`error`/parked schedule (`enabled=true` but not `active`) produces no blockable work and must not count;
4. has not already been notified for the current lock-episode (`user_vaults.lock_notified_at IS NULL`);
5. is not currently unlocked in this process (`vlt.Unlocked(userID)` == false — a fail-safe local skip that can only suppress a send, never cause one; it covers the boot-unlocked seed admin and anyone already unlocked on this pod),

the reconciler **atomically claims** the notify slot and sends **one** notification through the existing `notifysvc.Notify` seam (inbox row persisted first, best-effort Slack DM after).

The notification reuses the generic Family-B path (`notifysvc.Notify` → `SlackRender`), exactly like the judge-review and CI-autofix notifications. **No new slacksvc code, no new preference toggle, no per-type opt-out** — it inherits the one global `slack_notify` kill switch and the confirmed-link gate.

**Copy is cause-neutral, not "a restart locked it".** The reconciler runs on every scheduler tick, so it will also observe a vault a user locked deliberately via `POST /api/vault/lock` (`api/internal/handler/vault.go:131,141`), where no restart happened. The DM body therefore says "Your vault is locked — unlock it so your queued and scheduled runs can proceed", never asserting a restart as the cause. And a **deliberate lock is pre-acknowledged**: `Handler.VaultLock` sets `lock_notified_at = now()` at the same time it locks, so a user who locks on purpose is not then DM'd to unlock (Decision D6).

### Dedup / episode model (the load-bearing design decision)

A new nullable column `user_vaults.lock_notified_at timestamptz` is the dedup key.

- **Claim (send)**: `ClaimVaultLockNotice` — `UPDATE user_vaults SET lock_notified_at = now() WHERE user_id = $1 AND lock_notified_at IS NULL RETURNING user_id`. Only the row that comes back is sent — this makes the send **atomic across replicas**, so N api pods booting together produce **one** DM per user, not N.
- **Mark-before-send is at-most-once**: the mark is set *before* `Notify` runs, so a crash between the claim and the inbox write loses that episode's notification (marked-but-not-told) until the next unlock re-arms. This is the deliberate dedup tradeoff — never double, at the cost of a rare possibly-zero — and is acceptable (low probability, and the user still sees the locked banner in-app). (Decision D2.)
- **Re-arm (episode boundary)**: `ClearVaultLockNotice` — `UPDATE user_vaults SET lock_notified_at = NULL WHERE user_id = $1 AND lock_notified_at IS NOT NULL` (the `IS NOT NULL` guard makes it a no-op on the hot login path when already clear). Wired at the **end of `Vault.unlock` after the success switch** (not "after `put`" — `put` is reached inside `cacheFromRow:158` and `create:194`, both callees), covering every successful unlock path. It is **best-effort and logged, never fatal to the unlock**, mirroring `rewrapMasterSecrets` (`vault.go:141`): a DB hiccup on the clear must not fail an otherwise-valid unlock. An "episode" therefore ends at the next successful unlock: once a user unlocks, a **later** deploy that locks them again will notify afresh.
- **Anti-spam consequence (accepted)**: a user who is notified but **never unlocks** stays marked (the mark persists in the DB across every restart), so the reconciler excludes them on every later tick and every later deploy — the chronic-locked case is genuinely notified **once**, not per tick and not per deploy. This is deliberate: re-DMing someone who already ignored the first notice is worse than staying quiet. (Decision D2.)
- **Delivery-independent burn (accepted)**: the claim marks `lock_notified_at` whether or not the Slack DM can actually be delivered (e.g. slacksvc globally disabled while the user still has a confirmed per-user link). The inbox row still persists; the episode is consumed. Acceptable — the in-app inbox/banner remains, and Slack delivery is best-effort by contract.
- **First rollout**: the column defaults NULL for all existing rows, so the first deploy after this ships notifies every eligible user once. Intended.

### Where it lives

The scheduler (`schedsvc.New(q, wsvc, svc, settingsCache, notifier, vlt, ...)`, `api/cmd/server/main.go:721`) **already holds most of what the reconciler needs** — `q` (as the narrow `schedsvc.Store` interface), `vlt`, `notifier`, and a periodic tick. The reconciler is implemented as a step reached from `schedsvc`, plus a grace-delayed one-shot after boot. Two wiring costs the naive "just reuse it" framing hides, both budgeted into the milestones:

- **Interface widening.** `schedsvc` takes `q` as a narrow `Store` interface (`scheduler.go:79-98`), not raw `*store.Queries`, and reads settings through a `SettingsReader` that today exposes only `UziLabel(ctx)` (`scheduler.go:131`) — **no `PublicBaseURL`**. So M1/M2 must add the new queries to `schedsvc.Store` (and its test fake), and add `PublicBaseURL(ctx)` to `SettingsReader` plus a deep-link builder, following the existing notifiers (`judge_worker.go:224`, `workers.go:1407`). When the base URL is empty the DM **omits the link and still sends**, matching `TestBuildReviewNotificationNoBaseURL`.
- **The scheduler goroutine is itself gated.** `Boot`/`Run` start only when `cfg.SchedulerCheckInterval > 0` (`main.go:720-726`), and the boot tick it runs is *immediate* (`scheduler.go:191`). A reconciler folded naively into that path would (a) be silently dead whenever scheduled runs are disabled — a second off-switch the M3 kill switch could not override — and (b) fire with no grace delay. **Therefore the boot one-shot and the tick hook are wired independently of the scheduler goroutine** (e.g. a `time.AfterFunc` in `main.go`'s boot path plus the tick call), so the feature's only off-switches are its own M3 env flag and the per-user `slack_notify` gate. (Decision D1.)

## Non-goals

- **No per-notification-type preference system.** There is only the global `slack_notify` boolean today (`00044_slack.sql:14`); this feature reuses it. Adding the first per-type toggle is out of scope (Decision D3).
- **No idle-timeout auto-lock**, no change to when/why the vault locks — this only *notifies* about the existing lock behavior.
- **No email / webhook / other channel** — Slack DM + the existing in-app inbox row only (the inbox row comes for free from `notifysvc.Notify`).
- **No `.github/workflows/**` changes.** (Worker-scope constraint, see Risks.)
- **No CLI change.** The notification is a passive server-side DM; `api/cmd/uzi/` is unaffected. (Verified against the "new functionality ⇒ check the CLI" convention: nothing in the CLI surfaces or configures this.)

## Threat-model / safety review (resolved, offline)

Read `docs/vault-threat-model.md`. Findings, all settled from the code so an offline worker need not re-verify online:

- **Notifying the owner leaks nothing.** The owner already sees `vault.unlocked` in their `/api/me` session payload (`api/internal/handler/auth.go:409-413`), the `GET /api/vault/status` endpoint, and the `VaultBadge` / `VaultLockedBanner` UI (`web/src/components/VaultControls.tsx`). Lock/unlock state is not a protected secret. The threat model's indistinguishability requirement (identical 403 for wrong-password vs no-vault, `handler/vault.go:45-48`) is about **unauthenticated/other-user probing**, not about telling the authenticated owner their own state. The DM goes only to the owner's own confirmed Slack DM.
- **No secret material in the notification.** The DM carries a fixed title, a fixed body, and an in-app link — never the password, KEK, or DEK.
- **Multi-replica residual (documented limitation, ties to residual #7).** "Locked" is per-process: a user unlocked on pod A is still locked on pod B (`docs/vault-threat-model.md:90-92`). The local `vlt.Unlocked` skip (criterion 5) suppresses sends on the pod where they are unlocked, and the DB atomic claim dedups the send. But because an unlock on pod A re-arms the marker (`lock_notified_at = NULL`), pod B — still locked in its own process — can re-notify on its next tick: the bound is **at most one redundant DM per cross-pod unlock event**, not one total and not N. Cost is low (an extra "unlock your vault" DM shortly after they unlocked elsewhere) and single-api-replica deployments (the laptop dev loop and the current hosted api) never hit it. Documented, not solved, in this PRD (Decision D4).

## Offline-worker readiness

Every fact this PRD relies on was resolved from the codebase (file:line anchors above) or the shipped threat-model doc. There is **no open-web dependency**: no external API semantics, no upstream source to browse, no docs page to fetch. A restricted-egress sweep worker can implement this end to end. Load-bearing checks are offline-verifiable (live-DB tests + unit tests with fakes).

## Decision log

- **D1 — Reconciler logic reached from `schedsvc`, but invoked from `main.go` independently of the scheduler goroutine.** The scheduler already holds `q`, `vlt`, `notifier` and a tick, so the reconciler reuses those. But the goroutine is gated on `SchedulerCheckInterval > 0` and runs an immediate boot tick, so the invocation (boot one-shot + tick hook) is wired in `main.go` outside that gate — otherwise disabling scheduled runs would silently kill vault-lock notices and the M3 switch could not restore them. Rejected: a fully standalone poller (duplicates the deps schedsvc already wires) and a hook inside `Vault.Lock` (fires only on the explicit-lock endpoint, not the restart case that motivates this).
- **D2 — Re-arm on unlock, not on boot; mark-before-send.** `lock_notified_at` clears on the next successful unlock, so a user is notified at most once per lock-episode; the chronic-locked user (locked, pending work, never unlocks) is notified exactly once, not per tick and not per deploy. A boot-time reset was rejected because in multi-replica boots a later-booting pod would reset a marker an earlier pod already set, causing re-notification. Two accepted consequences: an ignored notice is not repeated on the next deploy (anti-spam); and because the mark is set before `Notify`, a crash between claim and send loses that episode's DM until the next unlock (at-most-once, never double).
- **D3 — Reuse the global `slack_notify` toggle; no per-type preference.** Research found exactly one preference column and no per-type system anywhere. Adding the first per-type toggle would be a larger, separate change (new column/table + `GetSlackDeliveryForUser` variant + web control). Out of scope; the global kill switch plus the M3 env switch are sufficient.
- **D4 — Multi-replica redundant-DM accepted as a documented limitation.** Fully solving cross-pod unlock visibility is out of scope and ties to threat-model residual #7. The local `vlt.Unlocked` skip + DB atomic claim keep the common (single-api-replica) case exactly correct and bound the multi-replica cost to at most one redundant DM.
- **D5 — Trigger = post-deploy scoped (chosen over "everyone" and "claim-gate reactive").** Scoped-to-pending-work is proactive (fires before the nightly sweep stalls), low-noise (skips idle users), and matches the stated goal. "Everyone" DMs idle users; "claim-gate" is reactive and can fire after a run already stalled, at an inconvenient hour.
- **D6 — Cause-neutral copy, and deliberate locks are pre-acknowledged.** Because the reconciler observes any locked vault (restart-locked or user-locked via `POST /api/vault/lock`), the DM never claims a restart caused the lock. And `Handler.VaultLock` sets `lock_notified_at = now()` when it locks, so a user who locks on purpose is treated as already-informed and is not DM'd to unlock. Rejected: restart-specific copy (wrong for the manual-lock path) and a separate restart-only detector (there is no lock event on restart to hook — the cache simply starts empty).

## Risks

- **Worker-scope constraint (`.claude/rules/prds.md`).** A PRD sent to a uzi sweep worker must keep `.github/workflows/**` out of both implementation and validation — the worker PAT lacks `workflow` scope, so any workflow-file touch in the branch diff is an atomic push rejection that loses the whole branch. This feature needs no workflow change; keep it that way. If CI needs a new job later, split it into a separate maintainer/local-only issue.
- **Live-DB tests are the real gate.** sqlc's type deduction is not Postgres's, so the new queries are not verified until a `*LiveDB` test executes them (`.claude/rules/go.md`). M1 and M4 must run under `./e2e/run-store-it.sh` with a positive control, not just `sqlc generate` + `go build`.
- **`-count=1` and the mutation discipline** apply to any query test added (`.claude/rules/go.md`); mutate the generated `*.sql.go` const, not just the `.sql` source.
- **Notification noise if scoping is wrong.** The lock blocks only `queued` claims — a query that also counts `running`/`claimed` runs, or `fired`/`error`/parked schedules (`enabled=true` but not `active`), DMs users the lock does not affect. The predicate must mirror `ClaimRun` (`runtime.sql:596`) and `ClaimDueSchedules` (`schedules.sql:205`); M2's and M4's scoping tests are the guard.
- **Silent off-switch via the scheduler.** The reconciler must be wired independently of the `SchedulerCheckInterval > 0` gate (D1); if folded into the scheduler goroutine, disabling scheduled runs would silently disable vault-lock notices, which the M3 kill switch could not override.
- **`schedsvc` settings interface is too narrow for the link.** `SettingsReader` exposes only `UziLabel`; M2 must add `PublicBaseURL(ctx)` and degrade gracefully (omit link, still send) when it is empty.

## Success criteria

1. After a restart, an eligible locked user (vault row + confirmed Slack + blockable work) receives exactly **one** Slack DM telling them to unlock, and an inbox row is persisted regardless of Slack delivery.
2. A user with no blockable work receives **no** DM — including a user whose only run is `running`/`claimed`, or whose only schedule is `fired`/`error`/parked.
3. The seed admin (boot-unlocked) and any currently-unlocked user receive **no** DM.
4. A user who locks deliberately via `POST /api/vault/lock` receives **no** unlock DM (pre-acknowledged), and the DM copy never asserts a restart as the cause.
5. On a subsequent deploy, a user who unlocked in between is notified again; a user who never unlocked is not re-notified.
6. Two concurrent claim attempts for the same user produce exactly one send (multi-replica dedup).
7. The global `slack_notify=false` kill switch and the M3 env switch each suppress the DM.
