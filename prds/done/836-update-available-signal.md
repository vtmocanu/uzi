## Problem

A deployed uzi instance already knows and displays its **own** version. `GET /api/version` returns `apitypes.BuildInfoDTO` (`api/internal/apitypes/buildinfo.go`), the SPA fetches it once and renders it in the sidebar footer via `BuildInfoPopover` (`web/src/components/BuildInfoPopover.tsx`, `displayVersion()` re-adds the `v` the server strips), and PRD #415 hangs a changelog drawer (`web/src/components/ChangelogDrawer.tsx`) off that popover.

What no surface answers is **"is there a newer release than the one I'm running?"** There is no upstream-release check anywhere in the product (confirmed across `api/`, `web/`, `controller/`, `agent/`, `docs/`). Two adjacent mechanisms exist and neither targets upstream uzi releases:

- **CLI-vs-server skew** (`api/internal/uzicli/versioncheck.go`) compares the CLI binary's stamp against the server's `/api/version`. Client-side, not upstream.
- **Agent-source update check** (`api/internal/agentsource/update.go`, PRD #702 M4) polls a configured agent-template git source and derives "update available" at read time. **This is the structural template for the poll→persist→derive core of this PRD** — same shape (poll upstream → persist facts → derive a boolean on read with zero egress), different target. (Its *scheduling* and *seeding* halves are NOT the right precedent — see D3.)

Consequence: an operator finds out uzi is behind only by manually checking GitHub, so instances drift, miss fixes, and there is no in-product nudge to update.

## Solution

Add a **server-side** periodic check against the GitHub Releases API for `vtmocanu/uzi`, persist the remote facts, derive "update available" at read time with zero egress, and surface it in the SPA on surfaces uzi already owns. The api is the only correct home: it is the sole outbound-egress holder, and `web` cannot call GitHub directly (no CORS; nginx only reverse-proxies `/api/*`).

**The whole feature is gated by admin runtime settings, default enabled**, with initial defaults seedable from config/env so helm sets the k8s default and compose uses env. Two independent toggles:

1. **`release_check_enabled`** (master) — when off, the api never calls github.com. This is the air-gap / privacy gate: without it an offline install logs poll errors hourly with no way to silence them.
2. **`release_check_banner_enabled`** — governs only the intrusive escalation banner (surface 4). Cosmetic; the pip and the admin card do not depend on it.

Both default `true` and are admin-editable at runtime (no redeploy). This mirrors uzi's judge-style admin gates rather than the deploy-time `workers.enabled` shape.

### Baked-in facts (resolved locally so the offline worker needs no internet)

The uzi worker has no open-web egress. Every internet-dependent fact this PRD relies on is stated here as resolved, with its source, so no milestone requires a live lookup:

- **Endpoint**: `GET https://api.github.com/repos/vtmocanu/uzi/releases/latest`. Returns "the most recent non-prerelease, non-draft release" — drafts and prereleases are excluded by the endpoint itself, so a prerelease-ahead is correctly treated as up to date. Fields used: `tag_name` (e.g. `v0.62.0`), `name`, `body` (markdown release notes — **persisted**, see storage + security below), `published_at` (RFC3339), `html_url`. Source: <https://docs.github.com/en/rest/releases/releases#get-the-latest-release>.
- **Rate limit**: unauthenticated **60 req/hr per IP**; authenticated (a token) **5,000 req/hr**. Source: <https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api>. A single server-side poll per instance at an hourly-or-slower cadence is trivially within 60/hr even unauthenticated. Do **not** let the SPA or CLI hit GitHub per browser/agent. Caveats baked in: a NAT'd fleet shares the per-IP budget, and `304 Not Modified` responses still count against the REST limit — so keep the interval modest and never poll per request. An optional token (`UZI_RELEASE_CHECK_TOKEN`) raises the ceiling but is not needed at this cadence.
- **🔴 Version-shape mismatch (the one real trap)**: the server serves the version **bare** — `0.14.0` — because the Dockerfile stamps `-X main.version=${UZI_VERSION#v}` (Model B: served value == image tag == chart appVersion). GitHub `tag_name` is **`v`-prefixed** (`v0.14.0`). `golang.org/x/mod/semver` **requires a leading `v` and treats every invalid version as equal** (`Compare` returns `0`, `IsValid` is false), so a naive `Compare(serverVersion, tag_name)` **fails silently OPEN** — it reports "up to date" for a pair that is actually behind. **Fix: re-prefix AND `IsValid`-guard BOTH operands before comparing.** The cleanest in-repo template is `agentsource.semverNewer` (`api/internal/agentsource/update.go`):

  ```go
  ca := "v" + strings.TrimPrefix(a, "v")
  cb := "v" + strings.TrimPrefix(b, "v")
  if !semver.IsValid(ca) || !semver.IsValid(cb) {
      return false // either side unparseable → "unknown", never "behind"
  }
  return semver.Compare(ca, cb) > 0
  ```

  This trap is documented at length in root `CLAUDE.md` and `.claude/rules/go.md` (the "COMPARING VERSIONS?" entry). The discriminating unit-test fixture MUST be a pair that is genuinely behind (`0.11.0` vs `0.11.7`) — an all-current fixture passes against the broken comparison, because `Compare("0.11.7","0.11.7")=0` is the right answer from a broken compare.
- **Security release IS auto-detectable v1 (no severity field needed, no extra API call).** The GitHub release JSON has no severity field, but uzi controls the release body: `.github/workflows/release.yml` generates each GitHub Release `body` from the matching `CHANGELOG.md` section **verbatim** (`scripts/changelog-section.sh body "$VERSION"`), and `CHANGELOG.md` follows Keep-a-Changelog with `### Security` subsections. So `security = true` is derivable by scanning the fetched `latest.body` for a `### Security` heading — a CHANGELOG-discipline heuristic, zero new API surface, no releases-list call. (See D5; this reverses the first-draft assumption that security was undetectable.)
- **HTTP client**: use a **dedicated** client, NOT the per-user forge driver `newGitHub` (`api/internal/forge/github.go`), which is built per-user with a PAT — the wrong trust context for an instance-global, unauthenticated check. Carry the guards `logClient` uses in that file: a hard `Timeout`, refuse redirects (`CheckRedirect` → `http.ErrUseLastResponse`), and a bounded response body. `timeoutClient()` (`api/internal/forge/forge.go`) is the minimal in-repo shape.
- **SSRF allowlist does not apply**: `FORGE_ALLOWED_BASE_URLS` (and the separate `AGENT_SOURCE_ALLOWED_BASE_URLS`) exist to guard **user-supplied** base URLs (`config.AgentSourceBaseURLAllowed`, `config.go`). This check hits a **compile-time-constant** URL (`api.github.com/repos/vtmocanu/uzi/...`), so the user-URL SSRF threat does not apply — and `api.github.com` would not match the default `https://github.com` allowlist entry anyway. No token is carried on the unauthenticated path, so the PAT-scrubbing redactor is not in play (still redact if a token is later used).

### Storage + serve pattern (poll→persist→derive, mirroring agent-source's core)

Poll on a schedule → persist remote facts to `app_settings` KV via `store.UpsertAppSetting` → derive "update available" + "far behind" at **read time** (`DeriveUpdate`-style, zero egress) → serve. New settings keys alongside the existing `settings.KeyAgentSource*` family (`api/internal/settings/`):

- Config/toggles: `KeyReleaseCheckEnabled` (bool, default `true`), `KeyReleaseCheckBannerEnabled` (bool, default `true`), `KeyReleaseCheckInterval` (duration, default `6h`). Optional secret `KeyReleaseCheckToken`.
- Persisted remote facts: `KeyReleaseLatestTag`, `KeyReleaseLatestName`, `KeyReleaseLatestBody` (the markdown, for the notes excerpt + the `### Security` scan), `KeyReleaseNotesURL`, `KeyReleasePublishedAt`, `KeyReleaseCheckedAt`.
- Each key gets a `settings.Validate` case (the agent-source keys are the pattern) and a `Defaults` entry where a default applies; `KeyReleaseCheckToken` is the only secret (`IsSecret`, sealed via `settings.ValueForStorage`).

## Milestones

Six meaningful milestones. M1-M3 (and M7's CLI sub-item) are api-only — no #833 overlap; M4-M6 are web and are **blocked until #833 is on main** (D6).

- [x] **M1 — Release-check service (api).** New package (`api/internal/releasecheck/`, mirroring `agentsource`'s file shape). A dedicated guarded HTTP client fetches `releases/latest`, parses the fields above, and — when the master toggle is on — persists the remote facts to `app_settings` (including `body`). A pure, read-time derivation computes, with the re-prefix + `IsValid` semver guard (mirror `agentsource.semverNewer`): `update_available` (latest strictly newer than the running bare version), `far_behind` (D4's heuristic — computed **server-side**, see D4), and `security` (a `### Security` heading in the persisted `body`). Never derives at write time; never mutates anything but the settings KV. Unit tests with an `httptest` server (no live egress): a newer release → available; equal → not available (and `update_available=false`, distinct from unchecked); a genuinely-behind pair through the semver guard (the discriminating fixture); a malformed/`dev` server version → "unknown", not "behind"; a `### Security` body → `security=true`; the master toggle off → status `disabled`, no egress, nothing persisted; an unreachable/HTTP-error upstream → status `error`, last-good facts preserved.
- [x] **M2 — Schedule + config + seeding (api).** Run M1 on a cadence via a **dedicated interval Runner**, mirroring `agentsource.NewRunner(...).Start(ctx)` (`api/internal/agentsource/reconcile.go`) — a panic-recovered goroutine that sleeps `KeyReleaseCheckInterval` per tick — wired next to `agentSourceRunner.Start(ctx)` in `api/cmd/server/main.go`. **Not** a `poller.Engine` detector and **not** a `schedsvc` job (those are the wrong mechanism; see D3). Env seeds via `config.go`'s existing helpers: `UZI_RELEASE_CHECK_ENABLED` (`parseBool`, default `true`), `UZI_RELEASE_CHECK_BANNER_ENABLED` (`parseBool`, default `true`), `UZI_RELEASE_CHECK_INTERVAL` (`parseDuration`, default `6h`), optional `UZI_RELEASE_CHECK_TOKEN`. A typo in a bool var must abort boot (the `parseBool` convention). Seed the env values into `app_settings` at boot via a **create-only** `seed.ReleaseCheckSettings(...)` mirroring `seed.SlackSettings` (`api/internal/seed/slack.go`, wired next to it in `main.go`): it writes only absent keys, so an admin's later "off" flip is never re-enabled on reboot, and the token is sealed via `settings.ValueForStorage` like `KeySlackBotToken`.
- [x] **M3 — API surface.** Extend `apitypes.BuildInfoDTO` with three **optional, omitted-when-unknown** top-level fields: `latest` (object `{version, name, published_at, notes_url, security}`), `update_available *bool`, and `far_behind *bool`. **`*bool`, not bare `bool`** — a bare `bool` with `omitempty` also omits `false`, collapsing "checked & up-to-date" into "never checked"; the pointer keeps nil/false/true as three distinct states, exactly the `*int`/`*int64` "unknown beats wrong" rule this DTO already uses. All three (and the `latest` object) are omitted when the check has not run or is disabled. `handler.Version` currently builds the DTO purely from boot-time build stamps and reads nothing from the DB; deriving these three makes it read `h.settings` (the read-through `*settings.Cache`, no per-request DB hit) — note this in Risks. Keep `TestVersionEndpointCarriesNothingPrivate` closed: add exactly **three** new allowlist entries (`latest`, `update_available`, `far_behind`) with reasons — the test walks only top-level struct tags and does NOT recurse into the named `latest` object, so its inner fields are public-by-construction and not separately audited (state this so the implementer neither over-reaches nor assumes coverage it lacks). Add an **admin-only** `POST /api/admin/release-check` ("Check now") mirroring `PostAgentSourceUpdateCheck` (`api/internal/handler/agent_source.go`): cookie-only `RequireAdmin`, triggers one check, returns the resulting status. Live-DB tests for persist/derive (`*LiveDB`, run via `./e2e/run-store-it.sh` / `-count=1`, per `.claude/rules/go.md`).
- [x] **M4 — Badge pip + popover row (web, all users).** A small brand-colored pip on the sidebar version badge when `update_available === true`, and a new row in `BuildInfoPopover` ("v0.66.0 available · 3 days ago"). Admin sees an "Update guide →" link (to the admin Updates card / docs); a non-admin sees "Ask your operator". **The pip renders ONLY from the server's `update_available` — never a client-side string compare** (the semver trap lives server-side, in one place). Extend the web `BuildInfo` TS type (`web/src/lib/api.ts`) with `latest?` (nested), `update_available?: boolean`, `far_behind?: boolean` — optional, mirroring the server omit, so the omitted-vs-false distinction survives typing (no `any` cast). Collapsed sidebar hides the pip (no room), consistent with the popover's collapsed variant. Design against the **post-#833 footer** (credit default-hidden). Vitest: pip on/off, admin vs member copy, and the omitted-`latest` (unknown) state showing nothing.
- [x] **M5 — Admin Settings → Updates card (web).** In `web/src/pages/AdminSettings.tsx` (the agent-source card is the pattern): current-vs-latest version delta, release name + date, a short release-notes excerpt from the persisted `body`, a **link out** to `notes_url` / `html_url` for the full notes, a **copyable upgrade runbook** (helm + docker-compose), a "Check now" button (`POST /api/admin/release-check`), and the two toggles (feature enable, banner enable). Zero ambient reach on its own — it is the destination the pip points to. Surfaces the `error`/`disabled` status in words (an air-gapped or rate-limited check says so here, and only here).
- [x] **M6 — Escalation banner (web, gated).** An admin-only top banner, shown ONLY when `release_check_banner_enabled` is on AND the server-derived `far_behind === true` (D4), with a **server-side snooze keyed to the release tag** (so a snooze clears when a newer release arrives). Reading the notes is a **link out** to `notes_url` / `html_url` — **no ChangelogDrawer upstream-feed** (that component sources a build-time bundle that cannot hold entries newer than the instance's own build; see D5-adjacent finding). Vitest: banner shows/hides on `far_behind` + toggle, snooze persists per tag, a near-current update never raises it.
- [x] **M7 — Docs, specs, ADR, chart, CLI, gates.** `docs/` user page for the update-check + an admin section on the toggles (leading-fence frontmatter `title`/`order`/`audience`). **Run `task docs:sync` and commit the mirror** — every top-level `docs/*.md` is mirrored into `api/internal/uzidocs/embed/`, and `TestEmbeddedDocsMatchSource` (`api/internal/uzidocs/uzidocs_test.go`) reddens `test:api` on byte drift; this is mandatory, not conditional (same guard-class as #833's). `ARCHITECTURE.md` note under the version/build-info area. `adr/0836-upstream-release-check.md` (ADR number == issue number) recording the new outbound-egress path and why it bypasses the SSRF allowlists (D7). Chart: `deploy/chart/values.yaml` + the api Deployment template wire `UZI_RELEASE_CHECK_*`. `specs/ai.md` note (do NOT touch `specs/human.md` without user approval — a new user-facing requirement routes through the user). **CLI (api-gated — depends only on M3, may ship on the api track ahead of the #833-blocked web milestones):** per the "new functionality ⇒ check `api/cmd/uzi/`" convention, `uzi version` surfaces "update available: vX.Y.Z" from the extended `/api/version` (it already consumes that endpoint via `uzicli`). Full gate green: `task gate:api`, `task gate:web`, `task gate:controller` if touched, and the live-DB sweep for M3.


## Decision Log

- **D1 — Gating is admin runtime settings (default on), not helm-only.** helm values gate only the k8s path; uzi also ships docker-compose (laptop dev loop + e2e/smoke), which has no helm. And the admin who sees the banner is exactly who wants to disable it, without a redeploy. So both toggles are `app_settings`, admin-editable, with env/helm seeding the initial default. `(user 2026-08-30)`
- **D2 — A separate master "check upstream at all" toggle.** Distinct from the banner toggle. Off → the api never calls github.com (air-gap / privacy). Without it, an offline install logs hourly poll errors it cannot silence. Default on. `(user 2026-08-30)`
- **D3 — Reuse the agent-source POLL→PERSIST→DERIVE core, but not its scheduling or seeding. (review)** The read-time derivation, the guarded client, the disabled/error status shape, and the semver guard all come straight from `api/internal/agentsource/update.go`. But agent-source *schedules* via a standalone `agentsource.NewRunner`/`Start` interval goroutine (`reconcile.go`, wired in `main.go`) — NOT a `poller.Engine` detector (those are post-forge-sync hooks) and NOT a `schedsvc` job — so M2 mirrors the Runner. And agent-source is admin-only (never env-seeded), so the *seeding* half follows `seed.SlackSettings` (create-only, `api/internal/seed/slack.go`) instead. Two precedents, deliberately.
- **D4 — "Far behind" is computed SERVER-side and exposed as `far_behind`. (review)** M4 mandates the pip render only from a server boolean "because the semver trap lives server-side, in one place"; the banner heuristic does the same version-gap math, so by that principle it must also be server-computed, not recomputed in the browser. v1 heuristic: `far_behind = update_available && (majorGap ≥ 1 OR minorGap ≥ 3 OR published_at ≥ 30 days ago)`. `majorGap`/`minorGap` come from `semver.Major` / `semver.MajorMinor` on the re-prefixed strings; the days check is on `published_at`. Thresholds are tunable and recorded here as defaults; a releases-LIST call to count an exact "N releases behind" is a future refinement, not v1.
- **D5 — Security detection IS in v1, from a `### Security` heading in the release body. (review)** The `releases/latest` payload has no severity field, but `.github/workflows/release.yml` emits each Release `body` from the matching `CHANGELOG.md` section verbatim (`scripts/changelog-section.sh body`), and the CHANGELOG uses Keep-a-Changelog `### Security` subsections. So v1 sets `security=true` when the persisted `latest.body` contains a `### Security` heading — a CHANGELOG-discipline heuristic, offline-derivable, no extra API call. (This reverses the first draft, which wrongly said security required inventing a marker the pipeline already emits.) Caveat: it depends on release-note discipline; a security fix shipped without a `### Security` heading reads as routine — acceptable for a nudge, and documented in the ADR.
- **D6 — Depends on #833, which is not on main yet. (review)** Both touch the `AppShell.tsx` footer row; the pip is designed against the post-#833 (credit-default-hidden) layout. #833 is on `origin/agent/issue-833` (PR #835 open), not `main`, so the web track (M4-M6) is blocked today. api work (M1-M3, M7 CLI) may start now. `(user 2026-08-30)`
- **D7 — The api's runtime egress must reach `api.github.com`.** A deployment concern, not code: a k8s NetworkPolicy or egress proxy that today allows `github.com` for forge traffic must also allow `api.github.com`. Note it in the ADR/chart docs; the `disabled`/`error` status degrades gracefully if egress is blocked (that is what the master toggle and the error status are for). This does NOT involve the worker egress tier (ADR 0285), which governs the agent worker container, not the api.
- **D8 — Env→settings seeding is create-only. (review)** `seed.ReleaseCheckSettings` writes only absent keys (the `seed.SlackSettings` contract), so redeploying with `UZI_RELEASE_CHECK_ENABLED` still `true` never re-enables a feature an admin turned off at runtime. The env var is the *initial* default; the admin setting is authoritative thereafter.

## Risks

- **Semver fail-open (highest):** an unguarded compare silently reports "up to date". Mitigated by mirroring `agentsource.semverNewer` and by a discriminating (genuinely-behind) unit fixture; the all-current fixture is a false control.
- **`/api/version` becomes settings-dependent:** the endpoint is unauthenticated and unrate-limited and today reads nothing from the DB; M3 makes it read `h.settings`. Mitigated by the existing read-through `settings.Cache` (no per-request DB hit); no secret is exposed (the token key is never serialized into the DTO).
- **DTO growth on an unauthenticated endpoint:** the new fields are public by construction; `TestVersionEndpointCarriesNothingPrivate` stays the gate that forces any future top-level field to be deliberate — with the caveat that it does not recurse into the `latest` object's inner fields, which are therefore public-by-construction and unaudited by that test.
- **Rate limit under NAT:** many instances behind one egress IP share 60/hr unauth. Mitigated by a modest default interval (6h) and an optional token.
- **Security heuristic depends on CHANGELOG discipline (D5):** a security fix without a `### Security` heading reads as routine. Acceptable for a nudge; documented in the ADR.
- **Footer race with #833:** removed by sequencing (D6), not by hope.

## Acceptance

1. With the feature enabled and a newer release published upstream, `GET /api/version` reports `update_available: true` with a `latest` object; the SPA shows the pip + popover row (admin and member copy differ); the admin Updates card shows the delta + notes excerpt + runbook.
2. `update_available` distinguishes three states: omitted (never checked / disabled), `false` (checked, up to date), `true` (behind) — proven by a test asserting all three.
3. With the master toggle off, the api makes no call to github.com, `/api/version` omits `latest`/`update_available`/`far_behind`, and no pip/banner shows.
4. The escalation banner shows only for `far_behind === true` (server-derived, D4) with the banner toggle on, snoozes per release tag, and never raises for a near-current update. A `### Security` release sets `security: true`.
5. The semver comparison is guarded (re-prefix + `IsValid` both operands), proven by a genuinely-behind unit fixture.
6. Toggles default on, are admin-editable at runtime, and are seedable from env/helm via a create-only seeder (an admin "off" survives reboot).
7. Docs (+ `task docs:sync` mirror, `TestEmbeddedDocsMatchSource` green), `ARCHITECTURE.md`, `adr/0836-*`, chart values, the CLI surface, and a `specs/ai.md` note are updated; `specs/human.md` is untouched. All gates green.
