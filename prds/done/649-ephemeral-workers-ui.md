# PRD #649: Web UI for ephemeral worker auto-provisioning

**Status**: Shipped
**Priority**: Medium
**Depends on / relates to**: PRD #529 (ephemeral worker auto-provisioning — shipped the mechanism off-by-default, opt-in, capped; left both gates UI-less). This PRD only wires the two existing backend gates into the SPA; it adds no new provisioning behaviour. Follows the `judge_enabled` surfacing precedent PRD #529 Decision 8 explicitly named but stopped short of.

## Problem

PRD #529 shipped ephemeral worker auto-provisioning: when a queued run needs a capability no online worker has, and the run's owner opted in, the api provisions a run-bound throwaway hosted worker and reaps it when the run finishes. It is gated twice — an **admin instance kill-switch** (`app_settings` key `ephemeral_workers_enabled`, default `false`) and a **per-user opt-in** (`users.ephemeral_workers_enabled` column, default `false`). PRD #529 Decision 8 says the per-user opt-in "follows the `judge_enabled` precedent (admin default + per-user override)", and judge surfaces in **both** the admin Settings and the per-user Run-defaults tab.

Ephemeral did not. Neither gate is exposed anywhere in `web/src`: the admin key is served only behind `GET /admin/settings` but no admin card renders it, and the per-user column has a store setter (`SetUserEphemeralWorkersEnabled`) but no handler, no route, and no web control. So the feature is **undiscoverable and effectively unusable**: an admin can only enable it by PUTing the settings API by hand, and a user cannot opt in at all through the product. This PRD closes that gap.

## What already exists (verified against the tree 2026-08-23)

This feature is **almost entirely web-side plumbing over gates that already exist**. Every backend primitive the toggles drive is already built and tested by PRD #529; the only new backend code is three thin read/write seams (one handler + two response-field additions).

**Admin instance kill-switch — fully built, just not rendered:**
- Key/const `KeyEphemeralWorkersEnabled = "ephemeral_workers_enabled"` (`api/internal/settings/settings.go:92`), default `DefaultEphemeralWorkersEnabled = "false"` (`settings.go:228`), registered in the `Defaults` map (`settings.go:359`) so `AdminView` already enumerates and serves it, validated as bool in `Validate` (`settings.go:1217`), typed getter `Cache.EphemeralWorkersEnabled(ctx)` (`settings.go:713`). The provisioner reads it in `ProvisionPass` (`api/internal/hostedsvc/ephemeral.go:86`) and returns early when off.
- Admin settings GET/PUT already round-trip any `Defaults` bool key with **no per-key backend work**: `GetSettings` (`api/internal/handler/settings.go:55`) → `AdminView`, `UpdateSettings` (`settings.go:107`) gates each key by `Known` → `IsEnvSourced` → `Validate`. Route `GET /admin/settings` (`handler.go:1017`) is under `RequireAdminRO`; `PUT /admin/settings` (`handler.go:1078`) is under `RequireAdmin` (the write group). So the admin toggle is **web-only**: the value already crosses the wire in the `settings` map; the SPA simply never reads or writes it.
- Cleanest web mirror is `JudgeSettingsCard` (`web/src/pages/AdminSettings.tsx:683`) — a single-bool card that reads `settings.judge_enabled === "true"` from the top-level `saved` state (seeded by `applyResponse(await api.getSettings())`, `AdminSettings.tsx:280`), has a `dirty` check, and saves with `api.updateSettings({ ... })`. (The `agent_source_enabled` checkbox lives inside the larger multi-field `AgentSourceSettingsCard` reading a *different* endpoint, so it is a worse mirror despite being the nearest by name.)

**Per-user opt-in — column + store setter built, no handler:**
- Column added by migration `00156_ephemeral_workers_optin.sql:9` (`ALTER TABLE users ADD COLUMN ephemeral_workers_enabled bool NOT NULL DEFAULT false`), on the sqlc model (`api/internal/store/models.go:615`, `EphemeralWorkersEnabled bool`). Store write query **already exists**: `SetUserEphemeralWorkersEnabled` (`api/internal/store/queries/users.sql:70`, generated `api/internal/store/users.sql.go:695`), whose own comment says it "Mirrors SetUserJudgeEnabled" and is for "the CLI/handler wiring later" — i.e. this PRD.
- The provisioner reads the per-user flag through `ListUnplaceableQueuedRunsForEphemeral` (`api/internal/store/queries/runtime.sql:2678`, per-user filter `JOIN users u ON u.id = r.user_id AND u.ephemeral_workers_enabled` at `runtime.sql:2723`), invoked at `ephemeral.go:99`. So flipping the column is the entire per-user effect; no other wiring is needed for provisioning to honour it.
- **No handler exposes the column today.** `apitypes.UserDTO` (`api/internal/apitypes/user.go:7-42`) carries `judge_enabled`, `autopilot_enabled`, `wait_on_limit`, `ci_autofix_enabled` but **not** ephemeral. The judge self-toggle is the pattern to copy exactly: route `PUT /me/judge` (`handler.go:836`, `RequireAuth` group) → handler `SetJudgeEnabled` (`api/internal/handler/judge.go:51`, takes the user from the session, never the body) → store `SetUserJudgeEnabled`. Web method `api.setJudgeEnabled` (`web/src/lib/api.ts:2812`).

**How the admin gate reaches a non-admin SPA — two live patterns to choose from:**
- Judge exposes a **derived** bool on the `/api/me` session payload: `sessionPayload` (`api/internal/handler/auth.go:351`) computes `judge_enforced_by_admin` (`auth.go:432`) from the instance setting and hands only that derived bool to non-admins (never the raw kill-switch). Web reads it in `AuthContext.tsx` (`judgeEnforcedByAdmin`, `AuthContext.tsx:68/130`) and `RunDefaults.tsx` uses it to disable/annotate — not to hide — the control.
- The hosted-worker surface already gates on a **session-authenticated config endpoint**: `GET /workers/hosted/config` (`api/internal/handler/hosted_workers.go:302`) returns `{ enabled, quota }` (`HostedConfig` type `web/src/lib/api.ts:1418`). `HostedWorkers.tsx` fetches it once on mount (`HostedWorkers.tsx:49`) and returns `null` when `!config.enabled` (`HostedWorkers.tsx:90`) — the whole hosted-worker card, where the new user toggle will live, is already hidden when hosting is off. The handler already holds `h.settings`, so it can read `EphemeralWorkersEnabled(ctx)` with no new dependency.

**The fleet-list marker — DTO exposes it, web ignores it:**
- `apitypes.WorkerDTO.Ephemeral bool json:"ephemeral"` (`api/internal/apitypes/worker.go:29`) already ships to the client on every worker. The web `Worker` type (`web/src/lib/api.ts`) does **not** declare `ephemeral`, and no component renders a badge for it, so an auto-provisioned worker is indistinguishable from a manually-provisioned hosted one in `web/src/pages/WorkersSettings.tsx`.

## Solution overview

Wire the two existing gates and the existing worker marker into the SPA, following the judge precedent for mechanism and the user's chosen placement for the per-user control:

1. **Admin** — a single-bool toggle card in `AdminSettings.tsx` (mirroring `JudgeSettingsCard`) for `ephemeral_workers_enabled`. Web-only; the value already round-trips through `/admin/settings`.
2. **Backend seams** — expose the per-user column and the admin gate to the SPA: add `ephemeral_workers_enabled` to `UserDTO` (mapped in `toDTO`; `sessionPayload` merely wraps that DTO, so no separate key is added there — see M2); add `ephemeral_enabled` (the admin gate) to the `HostedConfig` response; add a `PUT /me/ephemeral-workers` self-toggle handler over the existing store setter.
3. **User** — an "Auto-provision on demand" toggle inside the "Provision a hosted worker" card on the Workers page, rendered only when hosting is on **and** the admin gate is on, reflecting and writing the user's own opt-in. Placed there deliberately: `WorkersSettings.tsx` is framed in its own header comment as fleet **operations**, not a run preference, and the toggle is the automatic sibling of the manual **Provision** control it sits beside.
4. **Fleet list** — render an `ephemeral` badge in `WorkersSettings.tsx` beside the existing `hosted`/`docker` badges, so an auto-provisioned worker is legible while it exists.

**Placement note (deliberate divergence from judge's *location*, not its *mechanism*).** Judge's per-user opt-in lives on the Run-defaults tab because it is a per-run analysis preference. Ephemeral auto-provisioning is a fleet behaviour — it changes what workers exist — so its per-user control belongs on the Workers page next to manual provisioning, gated by the same `hostedConfig` signal that already governs that card. The read/write mechanism still mirrors judge exactly (per-user value on the User DTO, self-toggle at `PUT /me/...`, admin gate as a derived signal the SPA reads).

**Out of scope (stated so it is not silently folded in):** the duplicate `docker docker` badge on hosted rows (`WorkersSettings.tsx:567` renders `w.docker` as a badge and `:582` renders the `docker` capability chip, so a docker-capable worker double-renders) is a separate pre-existing dedup bug, filed apart from this PRD. No CLI change: `api/cmd/uzi` has no per-user-prefs write command to mirror today (confirmed — the judge CLI is read/triage only), so the Conventions "does the CLI need a matching change?" check resolves to a documented **no** here; a future `uzi profile` command would carry it.

## Risks & open questions

- **Failing closed on the admin-gate read.** `HostedConfig` must treat a settings read error as "ephemeral off" (hide the toggle), exactly as the card treats a failed `hostedConfig` fetch as "hosting off" (`HostedWorkers.tsx:40-45`). An error must never render an enabled-looking toggle for a feature the instance has off. M2 encodes this.
- **Self-toggle must not trust the body's user id.** The judge precedent takes the user from the session and ignores any body id (`judge.go:51`); `SetEphemeralWorkersEnabled` must do the same, or one user could flip another's opt-in. M2 success criteria assert this.
- **Two admin-gate delivery paths exist; this PRD picks `hostedConfig`, not the session payload.** Judge uses a derived `sessionPayload` bool. We put the ephemeral admin gate on `hostedConfig` instead because the control lives inside the hosted-worker card that already reads that endpoint for its visibility, keeping the ephemeral gate beside the hosting gate (both operator policy). The per-user *value* still rides the User DTO like judge. This is a deliberate, minor divergence; confirm at review.
- **Enabling the toggle does not change cost posture.** PRD #529 ships off-by-default because cold-start cost vs. a warm pool is unresolved (issue #79). Surfacing the toggles does not change that; the user copy must label the feature experimental and name the cold-start cost so turning it on is an informed choice, not a discovered surprise.
- **No new migration, no sqlc regen.** The column (`00156`) and its setter query already exist and are generated; M2 is hand-written Go over existing generated code. If a reviewer expects a migration, there isn't one and shouldn't be.
