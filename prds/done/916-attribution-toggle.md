## Problem

Every commit a uzi worker makes carries the Agent SDK's default attribution trailer (`Co-Authored-By: Claude … <noreply@anthropic.com>`), and MR/PR descriptions carry the generated-with attribution text. Some users must not have AI attribution in their git history (organizational policy); others want to keep it. Today there is no control: the SDK default is always on.

## Solution

A per-user boolean `attribution_enabled` (default `true`, preserving current behavior) following the **account-default** pattern (`ci_autofix_enabled`), NOT the `wait_on_limit` machinery. It is a single user-level value resolved once at claim time and consumed only in the agent's `SdkOptions`; it needs no per-schedule persistence, no per-run override UI, no park/gauge behavior.

**What this actually controls (read Verified facts first):** the observable deliverable is suppression of the SDK's `Co-Authored-By: Claude` **commit trailer** — precisely the git-history concern in the Problem. The MR/PR-description half of the Problem statement does not apply to uzi: the worker (not the SDK) opens the MR and hand-builds its body, which carries no Claude attribution to begin with. `attribution.pr` is therefore set for correctness/future-proofing but is inert today (D6).

- **Store**: `users.attribution_enabled bool NOT NULL DEFAULT true`.
- **API**: expose on the account-defaults DTO (`apitypes/user.go`), editable by the account owner through a toggle endpoint modeled on `ci_autofix_toggle.go`.
- **Claim**: resolve the owner's value at run creation and stamp it on the standard claim, which serves every commit-producing kind uniformly (issue, `ci_fix`, `self_improve`, `prompt`, task/handoff, `mr_rework`), exactly as `WaitOnLimit` rides the claim today. Chat is excluded (D5).
- **Agent**: when the flag is `false`, add `settings: { attribution: { commit: "", pr: "" } }` to the executor's `SdkOptions` (`sdk-executor.ts` `baseOptions`); when `true`, pass nothing and keep the SDK default.
- **Web**: a toggle in Settings alongside the existing account defaults.

### Verified facts (investigations resolved locally, so no worker/internet lookup is needed)

- **SDK seam confirmed against the pinned `@anthropic-ai/claude-agent-sdk@0.3.241` types** (`sdk.d.ts`). `Options.settings` is typed `string | Settings` (`sdk.d.ts:1979`). `Settings.attribution` (`sdk.d.ts:5414`) is `{ commit?: string; pr?: string; sessionUrl?: boolean; [k: string]: unknown }`, and the doc comments state for both `commit` and `pr`: **"Empty string hides attribution."** So `attribution: { commit: "", pr: "" }` is the correct, type-checked way to suppress SDK-authored attribution on both surfaces — but in uzi only the `commit` half is observable (the next bullet explains why `pr` is inert here).
- **Use `attribution`, not `includeCoAuthoredBy`.** `includeCoAuthoredBy?: boolean` still exists (`sdk.d.ts:5432`) but its own doc comment says *"Deprecated: Use attribution instead."* New code uses `attribution`.
- **Touch only `commit` and `pr`.** `Settings.attribution` also carries `sessionUrl` (the claude.ai session-link trailer, for web/Remote Control sessions); leave it unset so its default is preserved. Do not set the whole `Settings` object to anything beyond `attribution`.
- **`attribution.pr` is inert in uzi's architecture** (verified at HEAD). The `pr` field only suppresses PR text the SDK itself generates when the SDK opens a PR. In uzi the agent never holds a credential and never opens an MR/PR (`runner.ts` "the agent never had a credential"); the **worker** opens it via `forge.createMergeRequest(...)` with a body from `mrDescription()` (`runner.ts:2182`, `:3334`), and that body contains only uzi's own operational footer — no `Co-Authored-By`, no "Generated with Claude Code". A repo-wide grep finds no such attribution string anywhere in `agent/src` or `api/internal`. So the **commit** half is the real feature; `pr: ""` is harmless and future-proof but changes nothing observable today.
- **Chat has no commit/MR path and rides a different claim.** `chat-executor.ts` is read-only (`cwd=/opt/uzi-src`, no clone, no PAT, tools = Read/Grep/Glob only, no Bash/Write/Edit), so attribution has no effect on a chat run; and chat uses `ChatClaimPayload`/`assembleChatClaim` (`api/internal/workersvc/chat.go`), NOT `assembleClaim`, so the "ride the claim like WaitOnLimit" template does not even apply to it. Chat is out of scope (D5).
- **CLI**: `api/cmd/uzi` currently surfaces `wait_on_limit`/`ci_autofix` at the per-run and per-schedule level, not as an account-defaults command. M4 checks whether an account-defaults CLI surface exists to extend; if none does, no CLI change is owed (recorded, not skipped silently — per the repo's "new functionality ⇒ check the CLI" convention).

## Success criteria

1. With the toggle **off**, a worker-authored commit contains no `Co-Authored-By: Claude` trailer; with it **on** (default), the trailer is present as today. (The commit-trailer behavior is an SDK runtime property of `attribution.commit`; the unit tests in SC3 pin the option mapping, and the end-to-end trailer presence/absence is confirmed by a manual or integration check on a real run, not by a unit test.)
2. uzi's worker-authored MR/PR body is unchanged in both states and already contains no Claude attribution (it is built by `mrDescription()`); `attribution.pr` is set but inert (D6). SC1 makes no MR-suppression claim.
3. The value is read **per claim**, so flipping the toggle affects the user's next run without a worker restart (asserted in M2).
4. Executor unit tests assert the `settings.attribution` shape in the captured `SdkOptions` for both states (off ⇒ `{ commit: "", pr: "" }`; on ⇒ no `attribution` key).
5. `task gate` green across api/agent/web; **no `.github/workflows/**` entry appears in the branch diff** (`git diff --name-only <base>..HEAD` is empty there).

## Decision Log

- **D1 — opt-out, default `true`.** Preserves current behavior for everyone who never touches the setting; only users with a policy need act.
- **D2 — account-default pattern (`ci_autofix_enabled`), not `wait_on_limit`.** A single user-level bool resolved once and carried on the claim. Explicitly NOT per-schedule-persisted and NOT per-run-overridable — that machinery (park semantics, gauges, per-schedule snapshots) is what makes `wait_on_limit` a 600+-site feature and none of it is warranted here.
- **D3 — `Settings.attribution`, commit+pr only.** Uses the non-deprecated field (verified above); `includeCoAuthoredBy` is deprecated. `sessionUrl` is left unset so its default holds; the executor sets nothing else on `Settings`.
- **D4 — pass nothing when the flag is on.** Keep the SDK default rather than re-supplying the default text, so an upstream change to the default attribution text still flows through for opted-in users.
- **D5 — chat is out of scope.** The chat lane is read-only (no clone, no PAT, no commits, no MR) and rides a separate claim path (`ChatClaimPayload`/`assembleChatClaim`), so attribution has no observable effect there and the claim-mirroring template does not apply. Wiring it would add a second executor build site and a second claim-assembly path for zero behavior change. Excluded deliberately.
- **D6 — the deliverable is the commit trailer; `attribution.pr` is inert.** Verified at HEAD: uzi's worker (not the SDK) opens every MR/PR and hand-builds the body, which carries no Claude attribution. So there is no SDK-generated PR text to suppress, and the Problem statement's MR clause does not apply to uzi's architecture. `pr: ""` is still set (harmless, future-proofs the case where a future flow lets the SDK open a PR), but the observable feature is commit-trailer suppression. **Not folded in:** stripping uzi's own operational footer from MR bodies would be a worker-side behavior change (`mrDescription()`), a separate decision/issue, not this PRD.
- **D7 — owner-only toggle, no admin force-toggle.** The mirrored `ci_autofix` account default ships both a self endpoint and an admin per-user force-toggle (`ci_autofix_toggle.go:26`/`:55`). This is an org-policy/personal preference the account owner sets, so M1 ships only the owner endpoint; an admin force-toggle can be added later if a need appears.
