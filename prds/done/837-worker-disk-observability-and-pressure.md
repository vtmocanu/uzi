## The incident (why this exists)

A self-improve run on `vtmocanu/uzi` reported, in the worker status feed:

> tool provisioning failed with this repo's opt-in extra tool(s) (ruby@4.0.6); skipping them … devbox install … error: write of 20152 bytes: **No space left on device**

That message itself is **correct, by-design graceful degradation** (`agent/src/provision-run.ts`, tier-2 opt-in failure with no tier-1 packages → skip and continue). The real fault was infrastructure: worker `8e1fef71`'s `/nix` PVC was a **stale 4Gi volume created 2026-07-21**, while the other two workers had **20Gi** `/nix` PVCs (created Aug 09/11). The `/nix` size was bumped 4Gi→20Gi (PRD #87, for the prebaked Chromium closure) as a controller constant, but Kubernetes does not resize an existing PVC when a template default changes, so the pre-bump worker was stuck at 4Gi and could not fit the ruby closure + its glibc/gcc dependencies.

Three gaps this exposed, each a milestone:

1. **No disk visibility.** Workers report CPU and memory bars in the UI (PRD #49); disk is not collected or shown, so a 100%-full volume is invisible until a run fails on it.
2. **No pressure self-healing.** A worker whose volume is full stays full; nothing drains and recycles it to reclaim space.
3. **No reconcile of stale/undersized PVCs.** A worker provisioned before a size bump keeps its undersized PVC forever; new workers get the current size, old ones drift.

The controller's own code already anticipates this: `controller/internal/preset/preset.go`'s header comment on `nixSize` states the nix store has **no auto-GC** and that "v1's remedy is delete + reprovision." This PRD productizes that documented manual remedy.

## Solution

Four capabilities across three surfaces, plus docs:

1. **Collect per-volume disk usage on the worker heartbeat** (`/nix` and `/data`, the two separate PVCs) and persist it, mirroring the PRD #49 CPU/memory plumbing exactly (agent `WorkerStats` → `/api/worker/heartbeat` → `workers.stats_*` columns → `WorkerDTO`).
2. **Render disk bars in the web UI** next to the existing CPU/memory bars (`WorkerStats.tsx`), reusing the same `Bar`/`MeterTrack`/`formatBytes` primitives.
3. **Controller reconcile of undersized `/nix` PVCs** (part 3): when a worker's observed nix-PVC request is smaller than the current `preset.nixSize`, **teardown + reprovision the volume in place** (delete the Deployment + the undersized PVC, keep the worker row/uuid + join-token Secret, let the existing create-gate re-mint the PVC at the current size). **Not** in-place expansion.
4. **Controller disk-pressure recycle** (part 2): when a worker's volume is ≥ a threshold (default 90%), the api flags `disk_pressure` on the poll wire and the controller **drains-then-recycles** the worker (same teardown-in-place action as part 3), reusing the PRD #422 cordon/drain/deadline machinery so an in-flight run finishes first.

**The one load-bearing mechanism, verified in code:** a worker image roll is a JSON merge-patch over the Deployment's **pod template only** (`patchFor` in `controller/internal/kube/materializer.go`), so the **same PVCs re-attach** after the `Recreate` — the code says so directly ("never patched: PVC specs are near-immutable, so a size change is delete + reprovision, not a live edit"). Therefore **reclaiming disk requires deleting the PVC**, not rolling the pod. Both part 3 and part 4 delete-and-remint; neither is a pod roll.

**Why teardown-in-place, not drop-the-row (part 3/4 safety).** There is **no autoscaler / desired-replica / WorkerSet owner** in this system: the controller's desired set is literally the `workers` rows with `kind='hosted'`, and a **persistent** worker is created and deleted by a *user*. Nothing re-creates a dropped persistent worker. So a naive "delete the worker to force reprovision" would permanently remove a persistent worker. The safe realization (and the one that matches the user's "teardown + reprovision, not expand" intent) keeps the worker **row + uuid + join-token Secret** and only tears down the **kube volume objects**: the create-gate (`Materializer.reconcileWorker`, which gates each PVC create on the observed `HasNixPVC`/`HasDataPVC` boolean) re-mints the deleted PVC at the current `preset.nixSize` on the next tick. This is the exact property that already makes an image roll safe.

## Decision Log

- **D1 — Recycle means delete-and-remint the PVC, NOT roll the pod.** Verified in `materializer.go` (`patchFor` merge-patches the pod template only) and stated in-code: "a size change is delete + reprovision, not a live edit." An image roll re-attaches the same PVC, so a pod roll reclaims zero disk. Both M3 and M4 delete the PVC and rely on the create-gate to re-mint it. `(research 2026-08-30)`
- **D2 — Teardown-in-place (keep worker row + uuid + Secret), not drop-the-row.** There is no autoscaler/WorkerSet/desired-count owner; a persistent worker's row is user-owned and nothing re-creates it if dropped. So the recycle deletes only the Deployment + target PVC(s), preserving the row/uuid and the join-token Secret (the cluster Secret is the only copy of the delivered token). This honors the user's "teardown + reprovision, not expand" while being safe for persistent workers. `(user 2026-08-30; research-confirmed)`
- **D3 — In-place PVC expansion is rejected.** `tanzu-sc` supports `allowVolumeExpansion`, and expansion was used as the one-off manual unblock for the incident worker — but the durable fix is reprovision, per the user, and expansion cannot reclaim accumulated nix-store cruft (it only grows the ceiling). Recycle-to-fresh drops cruft and re-fetches only the current working set. `(user 2026-08-30)`
- **D4 — Both `/nix` and `/data` are metered.** They are separate PVCs/filesystems (`dataMountPath`/`nixMountPath`); the incident was `/nix`, but `/data` (clones/worktrees/HOMEs) accumulates too. M1 reports both; the UI shows what's reported; M4's `disk_pressure` fires on either.
- **D5 — API derives `disk_pressure`; controller actuates.** The controller has minimal RBAC (no pod metrics, no exec) and its only worker view is the poll, so the disk signal must ride the poll wire. Putting the threshold in the api (next to the stats columns) keeps it in one place and the wire a single boolean, mirroring how `busy`/`draining_since` already flow. The controller's job stays pure lifecycle. `(research 2026-08-30)`
- **D6 — Thrash guard = PVC-age cooldown, read statelessly.** The reconcile loop is stateless; rather than persist "last recycled", the guard reads the target PVC's `creationTimestamp` (the controller already lists PVCs). A worker back at pressure within `UZI_WORKER_DISK_RECYCLE_COOLDOWN` is a capacity problem (raise `nixSize`), surfaced as a warning, not recycled again.
- **D7 — Both recycle arms share one helper and the existing drain machinery.** M3 (size-drift) and M4 (pressure) are two drift arms calling one `recycleWorkerVolumes(worker, volumes)`; the drain-before-recycle reuses the PRD #422 busy-guard/cordon/`DrainDeadline`/`ForceRoll` verbatim. Design them together, not as separate loops. `(research 2026-08-30)`
- **D8 — Reclaim is recycle, not agent-side nix GC (v1).** `nix-collect-garbage` would be lighter (no cold cache) but the controller cannot exec into a worker, so a GC would need net-new agent self-GC logic; and the incident volume was undersized, where GC cannot help. v1 recycles; opportunistic agent-side nix GC is noted as future work.
- **D9 — Recycle defaults ON, guarded (over reviewer dissent).** `UZI_WORKER_DISK_RECYCLE_ENABLED` defaults `true`: the drain protection means no run is lost, the cooldown prevents loops, and self-healing the exact incident we hit is the point. Operators can disable. **Reviewer dissent, recorded deliberately:** the risk/correctness and testability reviews **unanimously recommended default-OFF plus splitting observe (M4 flag on the wire) from actuate (the recycle arm)**, so pressure could be observed in production before any automated teardown was trusted. The user chose default-ON with a single master toggle and a single `DiskPressure` bool (no observe/actuate split). The decision stands; the mitigation is that **every safety guard matters more with actuation on** — freshness + ≥2-heartbeat debounce + reset-on-action + PVC-age cooldown + drain-before-recycle + ephemeral exclusion are all retained precisely because the default is ON. `(user 2026-08-30, over reviewer recommendation)`

## Risks

- **Thrash on a genuinely-too-small volume (highest).** If the working set exceeds `nixSize`, a recycled worker refills and re-pressures. Mitigated by the D6 cooldown + capacity warning; the real fix there is raising `nixSize` (out of scope, a capacity decision).
- **Recycle interrupts availability.** A recycled worker is down between Deployment/PVC delete and the re-minted pod becoming Ready (a few reconcile ticks + schedule + PVC bind). Acceptable because it only happens to a **drained** (idle) worker; no in-flight run is lost.
- **Failed re-mint strands the worker (data loss, no rollback).** The multi-phase machine deletes the old PVC **before** re-minting; if the new PVC cannot bind (storageclass unavailable, quota exhausted, no schedulable node), the old data is already gone and there is **nothing to roll back to** — the worker is left with no volume, a permanent outage plus loss of whatever the recycled volume held. This is inherent to reclaim-by-delete and cannot be made atomic. Mitigation is **detection, not prevention**: phase 4 (re-mint) must detect a PVC stuck `Pending` past a bound-timeout and surface it loudly (a stable log token + the display-only report path) so an operator intervenes; the machine must not silently sit in a half-recycled state. Do **not** attempt an auto-rollback (there is no prior state to restore).
- **docker `dind-data` third PVC is a metering + recycle blind spot.** M1 meters only `/nix` and `/data`; on **docker-tier** workers the volume most likely to fill is `dind-data` (build/image cache), which is **unmetered and unrecycled** — so `disk_pressure` can never fire on it and M4 cannot recycle it. Documented as a **known gap + fast-follow** (meter `dind-data` in a later pass, then let M4's existing arm act on it); called out here so a docker worker filling its image cache is understood to be out of v1's reach, not a regression.
- **Wire golden churn.** Adding `DiskPressure` touches both protocol structs and the golden `controller_poll_wire.json`; a mismatch reddens the cross-module test. Expected and gated (`-count=1`); update the golden in the same commit.
- **Display-only invariant regression.** The `stats_disk_*` columns must never enter a scheduling query; the api's `disk_pressure` derivation reads them only for the poll, like `busy`. Assert this in a test mirroring the existing `stats_*` display-only guard.
- **Dev/compose has no `/nix` mount.** `statfs('/nix')` may fail or return the host root fs; M1 omits the field on failure and never fails the heartbeat, matching the cgroup collector's `process`-fallback discipline.
- **`nixSize` at the LimitRange ceiling.** `maxPVCStorage` is 20Gi and `nixSize` already equals it; a re-minted PVC must stay ≤ the ceiling (`ValidatePVCCeilings`). Fine at parity; a future `nixSize` raise must move the ceiling + quota together (documented in the chart values comments already).

## Acceptance

1. A worker with no disk stats shows no disk bar/segment (three-state clean).

3. A worker at ≥90% on either volume across **≥2 consecutive fresh heartbeats** is flagged `disk_pressure` on the poll wire and drained-then-recycled by the controller; a stale or single-spike sample does **not** flag it; a worker recycled within the cooldown is skipped and emits the fixed, test-asserted log token `disk-recycle-skipped-cooldown worker=<id>` (capacity-warned, not looped); an ephemeral (run-bound) worker is never recycled; `UZI_WORKER_DISK_RECYCLE_ENABLED=false` suppresses both arms.
