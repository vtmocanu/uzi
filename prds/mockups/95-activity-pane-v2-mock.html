Activity pane, rebuilt around the crew — not the scroll

Right now the pane is one live-tailing log that yanks to the bottom on every websocket frame, and your own follow-ups vanish into a worker queue you can't see. This reframes it: a crew roster you scan at a glance, logs collapsed by default, and a steer queue that shows delivery.

Rendered in uzi's real ember tokens. The mock is live — toggle Follow, expand agents, send a follow-up.

Problem 1

Every WS frame hard-jumps the pane to the bottom (el.scrollTop = scrollHeight, no batching). A tool burst = visible jerking.

Fix: logs collapse by default; auto-tail is opt-in and contained to one expanded agent.

Problem 2

"Active" = whichever role authored the newest message. A stalled agent still reads active; there's no real idle / waiting / done.

Fix: a crew strip with true per-agent state derived from last-activity + handoffs + worker heartbeat.

Problem 3

Follow-ups go to run_inputs, never run_messages. You never see your message, or whether the agent picked it up.

Fix: your message shows instantly as Queued, flips to Delivered when the worker consumes it.

Data honesty — what's real vs. what's a small new signal
  • have
    working / done are derivable today from message attribution + run status. done = an agent that emitted a result and hasn't spoken since a later agent started.
  • add
    idle vs waiting needs a per-agent last_activity_at (idle after ~Ns of silence) and an explicit handoff / subagent-start event to say "blocked on lead" vs "just quiet."
  • have
    true liveness — run.health (PRD #47) already derives worker liveness server-side (waiting_worker / stalled) from the heartbeat; the crew maps those states, so a dead or quiet worker greys the crew with no new plumbing.
  • add
    delivery status — the queued → delivered flip for follow-ups (Problem 3), read from run_user_inputs.consumed_at via a data-less WS input frame. The one genuinely new bit of plumbing (no migration).
