Mock — configurable board membership labels. Today a board renders only PRD-labelled issues, plus an all-or-nothing Show other issues checkbox. This proposes a per-user label filter with an admin-set default, so a repo can show bug alongside PRD out of the box. Sections 1–2 are today; 3–6 are visibility (which cards appear); §7 is eligibility (which cards can start a run). bug ships in both default lists, so out of the box a bug card appears on every board and offers Start run. Fixture repo below has 20 open issues: 5 PRD, 6 bug, 3 enhancement, 2 documentation, 1 security, 3 unlabelled.

5 · Proposed — the instance default

Admin › Settings › Labels

Labels

Which GitLab labels this factory reacts to. Changing a label never creates it on the forge — create the label in GitLab yourself. The labels must all differ.

PRD

Marks an issue as factory work. Only issues carrying this label can be run by an agent.

bug × add a label…

The default set of extra labels every board starts with. Issues carrying one appear alongside PRD issues, but still cannot start a run until promoted. Each user can override this for themselves per repo.

autopilot

Adding this label to a PRD issue lets an opted-in user run it end to end, with no plan-approval step.

Free text here, picker there. Admin is a text-entry tag input, because an operator legitimately pre-configures a label before any issue carries it. The per-user popover in §3 is a picker over labels actually present — different jobs, different affordances.
Validated like its siblings. settings.go:1017 already rejects a prdless_label colliding with prd_label or autopilot_label. The new list gets the same treatment: no duplicates, none equal to the three workflow labels, and a cap on list length.
Decided: bug ships in BOTH default lists. Visible and run-eligible (§7), not empty and not visibility-only. A board is more useful with bugs on it than without, and a bug you can see but cannot start is the friction this PRD set out to remove. An operator who disagrees clears one tag.
So every existing instance changes on upgrade, in two ways. Compiled defaults apply to any instance that never set the key (settings.go:176): boards gain their bug cards and those cards gain a Start run button, with no admin action. The visibility half is cosmetic and per-user reversible; the eligibility half is a run-gate change and needs to be called out in the changelog and the release notes, not discovered.
Autopilot is the line that does not move. Its candidate query keeps matching the primary label only (autopilot.sql:27), so no issue becomes startable unattended that was not already. Everything above requires a human to click. That asymmetry is what makes an opinionated default defensible at all, and it must be an explicit non-change in the diff, with a test that fails if someone "tidies" it into the set.

6 · Rules, and two sentences that are already wrong

precedence · product copy

Precedence, stated once

The membership set is always prd_label ∪ extras. Extras resolve as: the user's saved set for this repo if one exists, otherwise the admin default. A user's set is absolute, not a delta — simpler to reason about than a diff model, at the price that later admin changes do not reach a customised user, which Reset to default answers.

Storage is server-side per user, per repo, so it follows the account rather than the browser. There is no per-user settings table today, so this is new surface: a migration, a small read/write endpoint pair, and the board reading it at load.

Note the left operand is the primary label, not the run-eligible set. Eligibility does not imply visibility — otherwise bug, which ships eligible by default (§7), could never be unticked, and the "untick bug on a repo where they are noise" journey in §3 would be impossible. The two lists stay orthogonal.

Unchanged in every case: the uzi-self-improve tracker is never rendered. Closed issues are NOT excluded — the board has a Closed column (Board.tsx:57,502) and visibleCards has no state filter, so closed PRD cards keep appearing there exactly as today.

Phase 1 — decided

1. Answered: bug ships in both default lists — extras ["bug"] and run-eligible ["PRD","bug"]. See §5 and §7.

2. Per-repo per-user, taken as proposed: it matches today's uzi.board.<repoId>.showNonPRD key shape, and a monorepo and a docs repo do not want the same labels. More rows, more clicks; say so if you would rather have one set per user.

3. Does the CLI need it? uzi board renders the same cards; the CLI-parity convention says check, and the answer is likely "read the setting, no flag".

4. showNonPRD: true should migrate, not lapse: seed that user's set with Show all other issues checked. Letting it lapse silently narrows the board of the only users who had deliberately widened it.

7 · The machinery under §4's Start-run button

eligibility is a different list from visibility

Why loosening the run gate is defensible here

Today's gate (workersvc/service.go:2872, PRD #102 Decision 14) has a narrow stated purpose: it exists so "a non-PRD issue that happens to contain a prds/*.md link would [not] become runnable by accident" (prds/done/102-board-v2.md:501). A human clicking Start on a card carrying a label an admin deliberately configured as run-eligible is not that accident.

And the autonomous path is gated separately, not by this: autopilot's candidate query requires both the autopilot label and the primary label (store/queries/autopilot.sql:26-27). So this changes what a human may point uzi at, and nothing about what uzi picks up by itself.

The one structural rule: eligibility is a separate list with a different owner — never the §3 visibility list made runnable. A per-user view preference must not be able to widen what an agent can be told to work on a shared instance.

Labels

Admin › Settings › Labels

PRD primary bug × add a label…

Shipped default: PRD, bug. An issue carrying any of these can be started by a user. The primary is the one uzi writes — on Promote, and when the judge files an issue — and the only one autopilot matches. It cannot be removed.

documentation × add a label…

Visible on boards, but still not runnable until promoted. Run-eligible labels are shown automatically and need no entry here.

Defaults ON, and §4 depends on it. Off: a bug issue still needs a prds/*.md link or PRDLESS, so the one-click Start becomes two clicks with a differently-worded button.

Autopilot does not widen. At all. autopilot.sql:27 keeps matching the primary label only, so unattended pickup is exactly as narrow as today. Manual start widens; autonomous start does not. One line of deliberate non-change, and it is the half that makes the rest safe.
Writers use the primary; readers use the set. Getting this backwards is the bug this design invites. Ten server-side consumers of settings.PRDLabel today. Gates become set checks: workersvc/service.go:2872. Writers must not: Promote (board.go:981), the judge filing an issue (review_issue_draft.go:102, review_issue_file.go:131), issue creation (issues.go:62). A writer that picks "the first label in the set" starts labelling new issues bug.
The PRDLESS toggle's gate loosens with it. Board.tsx:1491 shows it only when isPRD. That becomes "is run-eligible", or the checkbox above makes it moot for eligible labels. Decision 16's reasoning survives untouched: the button must not appear where it grants nothing.
Open questions — eligibility 5. Is the PRD-link waiver per-instance (the checkbox above) or per-label? 6. Does a run started from a bug issue still get asked to update a prds/*.md file, or does the lead prompt branch? Today's instruction already opens on "if the issue description links a prds/*.md file" (docs/prdless.md:57), so this may already be answered. 7. uzi run start hits the same endpoint and is covered server-side — but does uzi board need to render the new button state? 8. Does PRDLESS still earn its keep once a whole label can waive the PRD link, or does it become the one-off version of the same idea?

What this half costs, stated plainly

The visibility half is a render filter plus a settings row: it cannot break a run. This half edits the run-eligibility gate, which is guardrail-adjacent, and touches ten call sites where the read/write distinction above is invisible to the type system — every one of them is a bare string today, so nothing fails to compile if a writer is handed the set.

Recommendation: one PRD, two milestones, the eligibility milestone reviewed on its own with the autopilot non-change asserted by a test. Splitting into two PRDs would ship the first half into exactly the three-click friction that prompted the second; merging them into one milestone hides a run-gate change inside a UI change.
