File a GitLab issue from a judge recommendation

Today the judge's recommendations (PRD #46) are a dead end: the run page lists them, and acting on one means copying the text into GitLab by hand. Only the improve_uzi subset ever reaches a forge, and only aggregated into the self-improvement engine's tracking issue.

Proposal: every recommendation gets a File issue button. It opens an editable draft the API templates from data it already has (no extra LLM call, no token spend), pre-targeted at the right repo, labelled PRD + PRDLESS so the issue lands on the board and is startable in one click. The filed issue's link is persisted on the recommendation, so the button becomes a link and the same row can't be filed twice.

Nothing auto-starts. No autopilot label is added: filing an issue and spending tokens on a run stay separate decisions.

Resolved after review (3× fable: architect, fact-checker, auditor)

  1. Re-judge no longer wipes filed links. The link moves to its own table keyed (review_id, category, target), which survives the recommendation delete-reinsert and makes a duplicate-file structurally impossible — (category, target) is not unique on the recommendation row, so the originally-drafted carry-forward LEFT JOIN would have fanned out.
  2. enable_tool / adjust_template keep the button. The ask was a button on each improvement; the human reads the draft before any write, and special-casing 2 of 6 categories buys a rule to learn against a mis-click that's already visible and cancellable. Revisit if these dominate the filed mix and get closed invalid.
  3. Who may file: owner + admin, with provenance shown. The bot authors the issue (uzi has no per-user forge identity), and the picker lists only repos you connected. An admin reading another user's review can file too — so the draft shows "from user X's worker, run <id>" prominently, because that text is attacker-influencable (worker-forged).
  4. Untrusted text is fenced, not blockquoted. A markdown blockquote does not neutralize inline links/images or GitLab quick-actions; the filed body puts every untrusted field in a code block and strips leading /-command lines, plus a broader secret-shape scan at draft time (the ingest scrub only covers 4 secret families, and this flow can write to a different project than the run's repo).
  5. Concurrent filing is claim-first. A read-then-write 409 only catches sequential re-clicks; the row is claimed atomically before the forge write, mirroring the chat-proposal flow uzi already audited into that shape.

What this does not change

  • Untrusted text stays untrusted. rationale_md / summary_md render as escaped plain text in the panel (RunView.tsx:688) and go into the issue body as data. The agent-side fence already covers the consequence: issue title/description are wrapped in UNTRUSTED_FRAME in the planning turn (prompt.ts:112), so a filed issue is exactly as untrusted as any other forge issue.
  • No new token spend. The API templates the body from rows it already has; the judge prompt and the worker are untouched.
  • No new forge capability. CreateIssue exists (forge/forge.go:225) and is already called from three places.
  • No new forge identity. The issue is authored by the connection's bot, exactly like every other write uzi makes. The filed issue says so in its footer, so a reader on GitLab isn't left wondering why the bot opened it.
