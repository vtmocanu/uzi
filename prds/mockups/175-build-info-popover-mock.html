CLI parity

not optional

Not a variant — this ships alongside whichever one you pick. CLAUDE.md's rule is that new functionality gets checked against api/cmd/uzi/.

uzi version today prints only the CLI's own ldflags stamp and never contacts the server (api/cmd/uzi/version.go). It also already supports --json, so the top-level version key stays exactly as it is — agents parse it today, and the Homebrew formula asserts on the human output. The server's coordinates nest underneath.

Widening the response is the actual change. Every variant above is just a different rendering of the same extra fields, which is why picking one is cheap and changing your mind later is cheaper.

What I would do

  1. Widen GET /api/version to a build-info object. Keep version as-is so nothing breaks.
  2. Hardcode founded as a Go const and compute age client-side. Neither needs a release to stay correct.
  3. Stamp commit and built_at through the ldflags block already in api/Dockerfile — two build args on a line that exists. commits is the odd one out: kaniko's build context is api/, so there is no .git to count. Ride the publish:assert-changelog job, which already runs at full depth on tags and is already a needs: of the publish jobs, and hand the number over as a dotenv artifact.
  4. Ship A first. It is the smallest honest surface, and it does not spend rail height or dashboard attention. Add C later if instance debugging ever needs a page.
