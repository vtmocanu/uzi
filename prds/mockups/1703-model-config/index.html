Model settings redesign: before / after mock

Design for issue #1703 (consistent model configuration across Claude and Codex). Every screen is a static artboard; notes carry the decisions (green), the issues marked with red pins (red) and the requirements for the issues (blue). Open this file in a browser from a checkout; the artboards load from this directory.

1 · User settings: before → after

RECOMMENDED: Option B, phased (agreed with buddy123) Rule: every model setting is a Claude/Codex pair, at admin (instance default) and user level. Models tab = one grid, rows x harness columns, each cell shows value + source, one Save. Judge + summaries get 'Runs on': Same as the run (default) / Claude / Codex, so a Claude run can get a Codex judge. An explicit choice is a hard choice (like a run's harness pin): no usable credential = skipped with a visible reason + retry, never charged to the other provider. Admin-enforced judge respects the user's choice. Phase 1 (Option A): honest Default labels (value + source), copy fixes, admin dropdowns for today's Claude fields. Later (epic): Codex effort, Codex judge + summary models, Codex summaries, 'Runs on' for helpers, one effective-settings API for web + CLI, then Models tab / admin grid / schedule group / run-start chip. Blue 'new setting' chips = needs backend work. NOT doing: per-run model override on Board, admin worker/effort defaults, Option C matrix for users. DECIDED (user, 2026-09-25): reasoning effort is per harness (Claude and Codex each have their own). Choosing between Codex credentials (pool / per-run / switch) is out of scope; the Codex credential cell stays read-only and can become a dropdown later without moving anything. LOCKED (user, 2026-09-25): sections 1, 2, 3, 4. Design complete.
Issues (red pins) 1 Every model dropdown says 'Inherit (account default)', but it means: admin instance default (judge, summary), lead template (Claude worker), gpt-6-astra (Codex worker). 2 The value in effect is never shown; copy hard-codes 'opus unless your admin changed it'. 3 The main setting (worker model) is card 8 of 9, under 7 unrelated toggles. 4 Four separate Save buttons for model settings, while the toggles on the same page save instantly. 5 Judge + summary models live inside feature cards; worker model and effort live elsewhere. 6 'Use my default' is an option on the control that IS your default. 7 Effort says 'your runs', but Codex worker runs ignore it today (codexEffort() returns undefined).
For the issue (acceptance criteria, not drawn) · from web-ux review, agreed with buddy123 A1 Every select has an accessible name built from its row + column ("Codex reasoning effort", "Judge runs on"), aria-describedby points at its In-effect line, real select semantics. A2 One atomic save for the Models tab: validate the whole payload, write all model/effort settings in one transaction, return per-field errors + the saved effective values. Unsaved-changes guard on in-app navigation. A3 Custom model ID input + blocking validation warning work inside a grid cell (Claude and the Codex worker lane allow custom IDs). A4 Below ~768px each setting stacks as a card with labelled Claude / Codex fields; bottom padding clears the sticky Save bar. A5 Visible focus ring distinct from the orange unsaved outline; theme tokens instead of raw colors, checked on the light themes. A6 Dim only the disabled control, never its reason text (contrast). A7 Blue new-setting chips are design notes only, never shipped.

2 · Admin instance defaults

Issues 8 Admin model fields are free text: no alias list, no validation (users get a dropdown for the same setting). 9 Help text shows the raw field name `judge_model`. 10 The section index has no link for Run summaries. 11 The two instance model defaults are split across two feature cards, below Forge labels.
For the issue (admin, not drawn) · from web-ux review B1 Each select has an accessible name ("Judge model, Codex"); real select semantics. B2 Per-cell save errors under each select; Save disabled until dirty; success announced via aria-live. B3 Column headers use the existing Claude / OpenAI provider logos and theme tokens, not hardcoded dots. B4 Remove or redirect the old #run-summaries jump anchor. B5 The green NEW tag does not ship. B6 Stored empty = Default (follows the built-in); a chosen value = pinned. Later, if wanted: an "N users override" line per row (needs an aggregate API). Not doing: an admin default for "Runs on" (an instance-wide Codex default would silently skip users without a Codex credential).

3 · Schedules and agent templates

Issues 1 Same misleading Inherit label (schedule: your default; subagent: the lead). 12 'your per-user Worker default' names a section that doesn't exist. 13 Nothing says what the schedule will actually run on. 14 Agents list prints bare 'inherit'. 15 Template Model field has no help text; Claude-only list with no harness context.
For the issue (schedules + agents, not drawn) · web-ux review + buddy123 C1 Preview is server-resolved and live; marks each value pinned (fixed at fire) or predicted (read at claim: user model, effort). C2 Per-harness agent template pins are their own epic child: storage, API, template rendering, Codex delegation (render.ts drops non-curated role models today). C3 Decide how a repo's own .claude/agents single model field maps (proposal: Claude pin; Codex follows lead). C4 Fix advice for an ignored pin depends on how many harnesses are usable (picker hidden with one). C5 One shared label helper for Default · value (source) across schedule, board, issue page and token picker. C6 Shared catalog cards never show a per-viewer value.

4 · Starting a run

Issue 16 You pick harness + token at start, but can't see which model or effort the run will use. After: read-only chip + breakdown. It adds visibility, not another override rung (buddy123 dropped its per-run override idea for this).
For the issue (starting a run, not drawn) · web-ux review + buddy123 D1 One shared preview component (compact line on the board card, open list on the issue page, static line on the chat card), one shared label helper. D2 Board: one server response per board with both harness predictions plus credential availability; cards pick by harness. Never reimplement the resolver in the browser; creating the run validates again. D3 Error state never claims defaults; Start stays available and shows the API's real validation error. D4 Own epic child: record the resolved lead model, effort and source per claim attempt (retries can differ), show it in the run header and the CLI. D5 Gate reason visible as text (not only a tooltip).
