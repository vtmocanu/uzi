Mode and pairing

system-follow with one theme per polarity

Every theme declares a polarity. Ember and Mission control are dark; Zori, Hală and Umbră are light. A user picks a mode and one theme for each polarity; the resolver decides which one paints.

Model

  • Registry: polarity: light | dark on each theme in api/internal/theme and web/src/lib/theme.ts. The Go side validates that the light slot only accepts a light theme, and vice versa, so a stale or tampered value cannot pair them wrong.
  • User settings: mode (system, lights_on, lights_off), lights_on_theme, lights_off_theme. The UI says Lights on / Lights off; polarity stays light/dark in the registry. Today's single theme override migrates into the dark slot with mode = dark, so nobody's screen changes on upgrade.
  • Instance defaults: the admin sets one theme per polarity; an empty user slot falls back to it, then to the shipped default (Ember / Hală).
  • Resolver: mode = system reads prefers-color-scheme and listens for changes, so the app flips live at sunset without a reload. Lights on and Lights off ignore the OS.
  • First paint: the pre-paint cache in index.html stores both slots plus the mode and evaluates the media query before the bundle loads, so there is no flash of the wrong polarity.
  • CLI: uzi settings appearance mirrors the three fields, per the rule that every web setting has a CLI twin.

UX rules

  • System is the default and the recommended choice; the hint line under it names which theme is on screen right now and which one is next, so the switch is never a surprise.
  • The picker for the polarity that cannot currently apply is dimmed, not hidden: the choice stays visible and editable.
  • Selecting a card applies it immediately (as today's picker does) and persists on success; a failed save reverts and says why.

Zori

dawn · the same factory at first light

Everything a person reads goes light. Everything the machines say (the activity feed, code, commands) stays in today's ember dark, so a run log looks exactly as it does now and sits in the page like an inspection window.

Where the dark goes

  • Console surfaces only: live activity, code blocks, tool output, CLI token boxes.
  • Sidebar, cards, board and run chrome are light.

Why it works

  • Zero new UX to learn; identical layout, identical pills, identical nav.
  • Logs keep syntax colours tuned for dark, which is where they read best.
  • Cards are the lightest thing on the page: elevation by lightness, the inverse of dark mode, no shadows needed.

Ship cost

  • One [data-theme="zori"] block in index.css, one entry in the Go and web theme registries.
  • A --console-* token family consumed by the six bg-ink log/code surfaces (ActivityFeed, AgentTemplateEditor, CliTokens, AgentDetail, ScheduleModal). That is the only component touch.

Risk

Lowest of the three. The visible change of identity: the ember orange must become rust on white (5.65:1), so the brand reads cooler at rest; the bright ember survives inside the dark panes and the brand tile.

Hală

the hall · the building stays dark, the floor is lit

The sidebar is the factory's steel frame and keeps today's ember look pixel for pixel: brand tile, active item, badges, rate-limit meters. The workspace goes light because that is where you read and decide. The product still reads as uzi from across the room.

Where the dark goes

  • Sidebar (and the mobile top bar), plus the console surfaces from Zori.
  • Content area is fully light, including run headers and board cards.

Why it works

  • Strongest figure/ground of the three: chrome recedes, content is the lightest surface on screen, so the eye lands on the work.
  • Nav badges (99+, 70, 8) keep the high-contrast dark ground they were tuned on; the rate-limit meters keep their ember colouring.
  • No white-wall fatigue on wide screens: the dark column anchors the layout.
  • Brand continuity: the first 264px of every screen are unchanged, so existing users keep their spatial memory.

Ship cost

  • Zori, plus a --nav-* token family (or a scoped remap) read by the sidebar in AppShell. One component touch, no per-theme branching.

Risk

Two adaptation zones side by side. Keep the seam a 1px edge with no shadow or gradient, and keep the sidebar's text ramp the ember one (AA-verified on dark), not a lightened copy.

Recommended default. Proven pattern for light modes of dark-branded tools, lowest relearning cost, and it composes with Umbră's live cards later as an opt-in.

Umbră

shadow · the factory is dark where it is working

Dark is not chrome here; it travels with live machine work. A running run's card, the live run header and the activity feed are dark. Everything at rest is light. Anything waiting on you gets the one warm mark: a rust rail and tint. Three states you can tell apart without reading a pill.

Where the dark goes

  • Dark: runs in claimed/running: board cards, in-flight rows, the run header, the console.
  • Rust rail: awaiting_approval and review requested: your turn.
  • Light: queued, done, failed, closed: at rest.

Why it works

  • Pre-attentive pop-out: on a thirty-card board the eye lands on the two or three dark cards without scanning status pills.
  • The approval item is the only warm thing on the page, so "what needs me" is answered before reading.
  • The dark ↔ light flip on a card is an event you notice from the corner of your eye when a run starts or finishes.

Ship cost

  • Zori, plus a data-live attribute on the issue card, in-flight rows and the run header (derived from run status), and a --live-* family. Two component touches plus tests.

Risk

Mixed polarity inside the content area. Mitigations: live cards keep the same radius, padding and 1px edge (no glow), the state is capped to the two machine-working statuses, and awaiting_approval is deliberately light so your decision surface never sits inside a dark card.

Shared rules

what all three proposals hold in common

  • No pure-white page. Ground is a cool steel grey, cards are white: elevation by lightness, the inverse of dark mode, with no shadows on cards. The tint leans blue like ember's near-black, not cream.
  • Text ramp verified. fg #151A22 / muted #4A5567 / faint #5F6A82 measure 15.9 / 6.8 / 4.9:1 on the ground; the faint tier clears AA on all three surfaces, the rule ember already keeps.
  • Status tones re-derived for light. ok #03705A, warn #9A4A05, danger #BE123C, info #0369A1, plan #4F46E5. Each is ≥4.5:1 as text on its own 10% pill tint, so the pill anatomy (10% fill, 40% border, coloured text) ships unchanged.
  • Brand orange splits. Rust #B93C0B for links, buttons and the ring on light ground (5.65:1); ember #FB923C only on dark surfaces where it has 8:1. Buttons carry white text.
  • Native controls follow. color-scheme: light on the theme block, dark inside the dark scopes, so scrollbars, selects and date inputs match their surface.
  • System option. The picker gains "System": prefers-color-scheme resolves to the light theme by day and ember by night, with the pre-paint cache in index.html reading the media query.
  • Type is a separate decision. IBM Plex Sans and Plex Mono are proposed (engineered forms, tabular figures, a mono sibling for logs); toggle to system-ui above to compare. Either ships through the existing --font-* tokens.
  • Motion. The milestone micro-bar keeps its blink; reduced-motion turns it off, as today.

Research applied

  • Elevated, tinted neutrals over bright white for all-day tools; surfaces lighter than the ground in light mode.
  • Dark-first tools shipping a light mode keep the dark identity in chrome or in the technical surfaces rather than inverting everything.
  • WCAG 2.2 AA holds at 4.5:1 for text regardless of polarity; APCA (WCAG 3 candidate) is stricter on thin light text, which is why the faint tier was pushed to 4.9:1 rather than stopping at 4.5.
