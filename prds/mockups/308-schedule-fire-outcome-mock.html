Why did my schedule start nothing?

A schedule can fire on time and still start zero runs — every candidate skipped for a benign reason the run-creation gate applies (no PRD link, not eligible, already running). Today that reason lives only in the api pod logs; the row just advances Last run and looks healthy. This mock surfaces the fire outcome: a per-fire breakdown of what matched, what started, and what was skipped and why — inline in the Schedules table and in uzi schedule get.

1 · Schedules list — the Last run column, enriched

The existing Last run cell shows only a timestamp. It gains an outcome summary — started in green, skipped in amber — and a disclosure to expand the last fire. A row that fired but started nothing now reads as a problem at a glance instead of looking fine.

3 · Skip reasons

Every benign skip the scheduler already computes becomes a named, typed reason — no free text. These are exactly the sentinels the run-creation gate returns today; the fire outcome just stops swallowing them.

no PRD link eligible but no prds/*.md link or PRDLESS not eligible carries no run-eligible label already running a run for this issue is active description too large issue body over the run cap

4 · CLI parity — uzi schedule get

The same last-fire summary is added to the CLI so an agent driving uzi headless can read why a sweep did nothing, without pod access. uzi schedule run-now returns the same per-candidate breakdown for the fire it triggers.

$ uzi schedule get 11129581 --json # jq of the new block
{
  "id": "11129581-a872-40ad-905b-993429168b39",
  "target": "sweep", "labels": ["bug"], "max_issues": 1,
  "last_fire": {
    "fired_at": "2026-08-12T00:00:07Z",
    "matched": 1, "started": 0, "skipped": 1,
    "run_ids": [],
    "skips": [
      { "issue_iid": 96, "reason": "no_prd_link" }
    ]
  }
}

$ uzi schedule run-now 11129581
Started 0 runs. Matched 1 candidate, skipped 1:
  #96  no PRD link  # add PRDLESS / a prds link, or raise --max-issues
