uzi · uzinele întunecate — design proposal

The update andon

uzi is a dark factory: it runs unattended and its operators walk the floor rarely. A real factory does not announce a pending parts change over the PA — it lights a lamp above the station. This proposal treats “a newer release exists” as andon signalling: one fact, three intensities, each surface exactly as loud as the situation deserves.

Updating a self-hosted uzi is an ops action — pull an image, bump a chart — so every surface informs and points at the runbook. None of them pretend to be a button that upgrades. Members see the lamp; operators get the work order.

Who sees it
Everyone. The pip is silent — it carries no text until the badge is hovered, so it never interrupts a member who can’t act on it.
When it fires
Whenever the server’s daily release check says a newer semver exists. Security releases turn the pip rose; that is the only escalation this tier ever does.
Dismissal
None, deliberately. A lamp that can be switched off is a lamp somebody switched off in March. It clears itself when the instance updates.
Tradeoff
Discoverability rides on the badge’s existing hover affordance — which the build-info popover has already trained users into.
STATION 02

The work order — Settings → Updates

Where the pip points. An admin-only card that owns the whole story: version delta, release notes excerpt, the copyable upgrade runbook, and the check itself. This is the “point to how” half of inform-and-point — flip the viewer toggle to see that members never get this surface at all.

This card doesn’t render for members. Members get the lamp and the changelog. The runbook, the check controls and the “N releases behind” framing are operator surfaces — showing a member a command they can’t run is noise dressed as transparency.
Who sees it
Admins only. It is the one surface that talks in ops verbs — image tags, chart versions, a check-now button.
What it owns
Release identity (name, date, delta), a 3-bullet notes excerpt with the changelog drawer’s category dots, the copyable runbook, and check health (“checked 12m ago”).
Failure state
If the GitHub check fails or rate-limits, only this card says so (“release check unavailable · retrying hourly”). A broken check never lights a pip.
Tradeoff
Zero ambient reach on its own — it’s a destination, not a signal. It needs Station 01 to exist.
STATION 03

The pull-cord — an escalation banner that almost never fires

A banner is the loudest thing an app can do to a returning user, so it is reserved for the two cases where silence would be negligent: a security release, or an instance ≥5 releases / 60 days behind. Routine updates never raise it — switch the signal to “Update available” and watch it stay away.

every rung considered

The signal ladder, ranked

Six approaches were on the table. The three stations above are the ones worth shipping; the other three are recorded with the reason they lost.

SurfaceAudienceFiresDismissalVerdict
1 · Badge pip + popover row everyone any newer release; rose for security none — clears on update SHIP
2 · Settings → Updates card admins always present; states: up-to-date / behind / security / check-failed n/a (destination) SHIP
3 · Changelog drawer markers everyone upstream releases render as “newer” entries above the current marker n/a (reading surface) SHIP — mostly exists
4 · Escalation banner admins security release, or ≥5 releases / 60 days behind snooze per release tag, server-side SHIP, GATED
5 · Login toast — would interrupt everyone for a fact only admins can act on; adds dismissal bookkeeping for zero reach beyond the pip — REJECTED
6 · Command-palette entry — uzi has no palette today; not worth a new surface for one verb — PARKED

Recommendation

Ship 1 + 2 together as one feature: the lamp and the work order. Neither is complete alone — the pip has no “how”, the card has no reach. Route the pip’s “Update guide” to the card, feed release notes through the changelog drawer that already renders running-vs-latest markers (3), and hold the banner (4) behind its security / far-behind gate.

This is the pattern self-hosted operators already trust from Grafana and Gitea — footer version, quiet update mark, admin page with the real story — expressed in surfaces uzi already owns. It respects the role asymmetry (members are informed, never nagged), degrades gracefully (a dead GitHub check silences the pip rather than crying wolf), and adds no new chrome: every tier lives inside an existing component.

for the coder — the seam

What the API owes the SPA

Wire shape

  • GET /api/version gains latest: { version, name, published_at, notes_url, security } + update_available.
  • Omitted entirely when the check hasn’t run or failed — absent, not null, matching the popover’s “unknown beats wrong” row rule.
  • Check cadence: daily, jittered, server-side; Check now is an admin-only POST.

Guards

  • Reuse parseSemver: a dev / demo build suppresses every tier — same neutrality rule the changelog drawer already enforces.
  • Banner snooze is per-user, keyed by release tag, stored server-side so it survives devices.
  • The pip renders only from update_available — never derived client-side by comparing strings.

Edge states designed, not patched

  • Check failed / rate-limited → admin card says “release check unavailable · retrying hourly”; no pip, no banner.
  • Latest == current → quiet “Up to date · checked 12m ago” in the popover; ok chip on the card.
  • Pre-release running (ahead of latest) → treated as up to date; never “behind”.
