Schedule runs: one-time or recurring, from web and CLI

Today a run can only start now — the board "Start run" button, uzi run create, or autopilot when a label appears. This adds a time-driven path so the dark factory can work off-hours: fire a run once at a future moment, or on a recurring cadence, against a pinned issue or a recurring sweep of every eligible PRD issue. All chrome below is painted from the app's real tokens; the shapes reuse existing components (table, badges, toggle, modal).

1 · The Schedules page

A new /schedules destination in the sidebar's Work group (beside Runs and Chat). Owner-scoped list: what each schedule targets, when it next fires, when it last fired, and a per-row enable toggle. Recurring rows persist; one-time rows disappear the moment they fire.

5 · CLI parity

Everything the web does, uzi schedule … does — built for agents (--json, documented exit codes) as much as humans. The --cron/--at split mirrors the modal's timing modes; --sweep vs --issue mirrors Target.

# recurring sweep — weekdays 02:00, auto-approve, park on limit $ uzi schedule create --repo uzi --sweep \ --cron "0 2 * * 1-5" --tz Europe/Bucharest --auto-approve --wait-on-limit ✓ created schedule sch_7Kd2 · next fire Mon 11 Aug 02:00 (in 6h 12m) # one-time — a single issue, tomorrow 09:00 $ uzi schedule create --repo uzi --issue 158 --at "2026-08-08T09:00+03:00" ✓ created schedule sch_9Qm4 · fires once at Aug 8 09:00 (in 13h 12m) $ uzi schedule list ID TARGET REPO WHEN NEXT ON sch_7Kd2 sweep vtmocanu/uzi 0 2 * * 1-5 in 6h 12m yes sch_9Qm4 #158 vtmocanu/uzi once in 13h 12m yes sch_3Bf1 #142 vtmocanu/uzi 0 3 * * * in 7h 12m yes sch_Zt88 sweep board-svc 0 */6 * * * — paused $ uzi schedule pause sch_7Kd2 # resume, run-now, get, delete all present ✓ paused sch_7Kd2 $ uzi schedule run-now sch_3Bf1 ✓ started run run_c81a from sch_3Bf1 (#142)
◆
One seam, honoured everywhere. Web, CLI, and the scheduler goroutine all create runs through the same shared path autopilot uses — so PRDLESS gating, forge issue fetch, active-run dedup and the usage-limit park behave identically no matter what triggered the run. A schedule can never do something a manual start can't.
