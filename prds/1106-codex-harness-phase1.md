## Problem

uzi runs only on a Claude credential. Every lane imports `@anthropic-ai/claude-agent-sdk` and the worker authenticates only with `CLAUDE_CODE_OAUTH_TOKEN` (`agent/src/sdk-env.ts:73-126`). A user who holds a Codex (ChatGPT) seat or an OpenAI API key cannot run agents on it.

#229 designs the full multi-provider system and orders its milestones judge-first because the judge's guardrail surface is vacuous. That defers what users want first: running whole issues on a flat Codex seat. It also assumed the Codex sandbox would replace the deny hook and that provider workers would be a separate fleet; both assumptions were checked on 2026-09-04 and neither holds (see *Verified facts*), which makes a simpler phase 1 possible.

## Solution

A run executes entirely on **one harness**, chosen per run: all agents on Claude (today's path, byte-for-byte unchanged) or all agents on Codex. No agent mixing.

- **One worker image carries both harnesses.** `agent/templates/base` gains the `@openai/codex` binary and `@openai/codex-sdk`. Harness is a property of the **run**, not of the worker; any worker runs either. No new `workertmpl` entry, no per-harness fleet, no claim routing by harness. This keeps the shared worktree, checkpoints and uid split identical for both harnesses, and it is what makes later in-worker mixing (a Claude lead delegating `coder` to a Codex thread on the same tree) cheap instead of a scheduler problem.
- **Credentials drive the UX; there is no admin toggle.** With one credential nothing new appears anywhere. With both, a default harness in Run Defaults, a split Start button for the per-run override, a harness select in the schedule modal, and a harness badge on runs (Claude unmarked). Facts about existing runs and workers are never hidden.
- **The guardrail ports as hooks, not as a sandbox.** The existing Bash screener, path guard and agent guard run as Codex `PreToolUse` command hooks; the uid split, sparse env and credential absence are OS-level and survive the swap; repo-borne Codex config is neutralized by marking the project untrusted. A conformance suite with one adversarial fixture per clause runs against both harnesses and is a first-class deliverable.
- **uzi's tools reach Codex over an out-of-process MCP transport** hosted by the worker on loopback; Claude keeps the in-process form (D0).
- **The tool-less advice lane** (judge, review, summary) runs on either harness so a Codex-only user keeps the judge. Chat stays on Claude.

### Out of scope (later phases of #229)

- Any mixing of agents across harnesses within a run; #727 profiles; sub-runs.
- OpenAI-compatible and local endpoints, the `wire_api` probe, the native chat-completions executor, the base-URL allowlist (D10). Phase 1 talks only to the fixed vendor endpoint.
- Device-code login (`codex login --device-auth`), capability-aware scheduling (#84), chat on Codex, Codex rate-limit meters (Claude's 5h/7d windows have no SDK-visible Codex equivalent in `runStreamed`).

### Later phases this PRD must not preclude (custom OpenAI URL, OpenAI-compatible, local LLM)

Tracked in #229 (D1, D10, R6, Success Criterion 4); listed here so phase 1 leaves the seams open.

- **Custom base URL / OpenAI-compatible endpoint** (OpenRouter, Azure OpenAI, an internal proxy, a self-hosted Responses-API server) is **not a new harness**: it is the Codex harness with a `[model_providers.<id>]` entry (`base_url`, `env_key`, `wire_api = "responses"`) in the provisioned `config.toml`, plus a third credential kind `openai_compatible {base_url, env_key, model}`. What it needs on top of phase 1: #229's admin base-URL allowlist (D10, mirrors `FORGE_ALLOWED_BASE_URLS`, https-only), a per-endpoint egress allowlist entry, and the vault-threat-model-style egress writeup. The project-layer denylist in fact 4 already stops a cloned repo from redirecting `base_url`.
- **Local LLM (Ollama, LM Studio)**: `codex exec` in 0.153.2 exposes `--oss` and `--local-provider lmstudio|ollama` (and an `oss_provider` config key), so a chat-completions-native local runtime may be reachable through the Codex harness directly. If that holds under the conformance suite, #229's third harness (the native chat-completions executor, finding 1) is unnecessary; if not, it stays as designed. Verify in that phase, not here.
- **Phase 1 keeps open**: `runs.harness` is `text` with a CHECK that a later additive migration widens; `user_secrets.kind` is CHECK-constrained (migration `00010`) and each new kind is one CHECK-widening migration plus a `store/enums.go` constant, the same step phase 1 takes for its two kinds; the per-run `CODEX_HOME/config.toml` is provisioned by the worker and is the only place a provider entry would go; the hook, the uid split and the conformance suite are endpoint-agnostic; the credential-card pattern extends to a third card without touching the first two; the credential-driven visibility rule extends unchanged (a user with only a compatible-endpoint credential sees only that).
- **Phase 1 explicitly does not ship**: any user-supplied `base_url`, any `model_providers` entry, the allowlist, or a local-provider flag. The Codex adapter talks only to the fixed vendor endpoint.

## Verified facts (2026-09-04)

Each fact names how it was established so an implementer can re-verify. Facts marked *offline* need no network beyond the package cache.

**Codex side** (openai/codex source at `main`, `@openai/codex@0.153.2`, the Codex config reference and MCP docs):

1. **Hooks.** `$CODEX_HOME/config.toml` accepts `[[hooks.PreToolUse]]` with a `matcher` regex and `type = "command"` handlers. Stdin is JSON with `session_id`, `turn_id`, `cwd`, `tool_name`, `tool_input`, `tool_use_id`, `permission_mode`, plus `agent_id` and `agent_type` when inside a subagent. Deny by exit code 2 with the reason on stderr, or exit 0 with `{"hookSpecificOutput":{"permissionDecision":"deny","permissionDecisionReason":…}}`. `spawn_agent` is a hookable `tool_name`. Async hooks cannot block. Hook `tool_name`s are Claude-style aliases mapped in `codex-rs/core/src/tools/hook_names.rs`: the shell tool is `Bash`, `apply_patch` is `Write`/`Edit`, `spawn_agent` is `Agent` (so the existing matchers port as is; M0(c) confirms the full table). Hooks carry a trust hash; `--dangerously-bypass-hook-trust` (or a persisted `trusted_hash` in `[hooks.state]`) runs provisioned hooks headless. Source: `codex-rs/hooks/src/events/pre_tool_use.rs`, `codex-rs/hooks/src/schema.rs`, `codex-rs/config/src/hooks_tests.rs`.
2. **OS sandbox is inert in a pod** (*offline, measured*). On `node:24-alpine` as uid 10002 with `--cap-drop ALL` and `no-new-privileges`, `codex sandbox linux -- id` fails with `bwrap: No permissions to create a new namespace`. OpenAI's documented answer for containers is host isolation plus `--sandbox danger-full-access`. So the Codex run uses `approval_policy = "never"` and `danger-full-access`, and the deny layer is the hook, exactly the Claude lane's `permissionMode: "bypassPermissions"` plus `PreToolUse` shape (`agent/src/sdk-executor.ts:975-991`).
3. **musl binary, no `ldd` sniff** (*offline, measured*). The npm launcher maps Linux to `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`; those are the only Linux builds. `codex --version` runs on `node:24-alpine` for both arches, also with a fake GNU `ldd` first on PATH (the #1082 trigger). `codex exec --sandbox danger-full-access` under pod conditions reaches `api.openai.com` and fails only with `401 Missing bearer`. `CODEX_HOME` under `/tmp` makes Codex refuse to create its helper-binary PATH aliases (`Refusing to create helper binaries under temporary dir`), so `CODEX_HOME` goes on the data volume.
4. **Repo-borne config is trust-gated.** Config layers load `${PWD}/config.toml`, `./.codex/config.toml` up the tree and `$(git rev-parse --show-toplevel)/.codex/config.toml`, each "loaded but disabled when the directory is untrusted" (`codex-rs/config/src/loader/mod.rs`). Agent roles (`.codex/agents/*.toml`) and exec-policy `.codex/rules/*.rules` are read per layer, so a disabled project layer contributes neither. `model_provider`, `model_providers`, `openai_base_url`, `chatgpt_base_url`, `notify`, `profile(s)` are on `PROJECT_LOCAL_CONFIG_DENYLIST` regardless of trust. `AGENTS.md` **is** trust-gated too: `load_project_instructions` (`codex-rs/core/src/agents_md.rs:60-63`) returns before the project read loop when `active_project.is_untrusted()`, so an untrusted project contributes no `AGENTS.md`; independently, `project_doc_max_bytes = 0` breaks out of the loop at `remaining == 0`, so the cap alone also yields an empty project doc. Both are set (belt and braces) and M4 keeps the fixture. Fact-checked 2026-09-04 against the raw source.
5. **SDK surface.** `@openai/codex-sdk` (`sdk/typescript/src/*.ts`): `CodexOptions {codexPathOverride, baseUrl, apiKey, config, configOverrides, env}`; `ThreadOptions {model, sandboxMode, workingDirectory, skipGitRepoCheck, modelReasoningEffort, networkAccessEnabled, webSearchMode, approvalPolicy, additionalDirectories}`; `startThread` / `resumeThread(id)`; `run` / `runStreamed` yielding `thread.started`, `turn.started`, `item.started|updated|completed`, `turn.completed {usage}`, `turn.failed`, `error`; items `agent_message`, `reasoning`, `command_execution {command, aggregated_output, exit_code, status}`, `file_change`, `mcp_tool_call {server, tool, arguments, result}`, `web_search`, `todo_list`, `error`; `Usage {input_tokens, cached_input_tokens, cache_write_input_tokens, output_tokens, reasoning_output_tokens}`; `outputSchema` on `run`. Sessions persist under `$CODEX_HOME/sessions`.
6. **Subagents.** `$CODEX_HOME/agents/<role>.toml` with `name`, `description`, `developer_instructions`, `model`, `model_reasoning_effort`, per-role `sandbox_mode`, per-role feature switches (`shell_tool = false`, `web_search = "disabled"`); `[agents] max_concurrent_threads_per_session`, `max_depth` (default 1, `DEFAULT_AGENT_MAX_DEPTH` in `codex-rs/core/src/config/mod.rs:242`, so a subagent cannot spawn), `features.multi_agent` (default on; `features.multi_agent_v2` takes precedence when set, `config_toml.rs:684`). Subagents inherit the parent's sandbox and permission mode.
7. **MCP.** `[mcp_servers.<name>]` stdio (`command`, `args`, `env`, `env_vars`, `cwd`, `startup_timeout_sec`, `tool_timeout_sec`) or streamable HTTP (`url`, `bearer_token_env_var`, `http_headers`), with `enabled_tools` / `disabled_tools`.

## Decision log

- **D0 (from #229): the Claude path is unchanged.** A run with no harness selected, or a user with only an Anthropic credential, gets today's code: same options, same in-process tools, same hooks, same tests. The port is an extraction behind an interface, not a modification. No existing-behavior test changes (SC0).
- **D1: one image, harness is a run property.** `runs.harness text NOT NULL DEFAULT 'claude' CHECK (harness IN ('claude','codex'))`, frozen at creation from the request or the user's default. Workers do not declare a harness; the claim query gains nothing for routing, only the D5 seat-lock predicate for `codex_auth` runs. Rationale: the trust boundary is the worker, not the harness; a second fleet buys nothing in phase 1 and would make in-worker mixing later impossible.
- **D2: naming.** `harness` in code, API, schema and CLI flags (`--harness claude|codex`); UI labels "Claude" and "Codex"; credential cards "Anthropic" and "OpenAI / Codex". Not "provider", which #229 uses for the wider matrix.
- **D3: credential kinds.** Two new `user_secrets.kind` values, `openai_api_key` and `codex_auth` (the verbatim `auth.json` from `codex login`), added by one migration that widens `00010`'s CHECK, with matching constants and a declared seal path in `store/enums.go` (both `SealedWithDEK` through the per-user vault, like the Anthropic token, so the `user_id||kind` AAD binding holds). Same slot in `CODEX_HOME/auth.json` either way (#229 D9). No device-code flow in phase 1.
- **D4: refresh write-back on every checkpoint.** A Codex seat rotates its refresh token and writes the new `auth.json` on refresh, and a seat idle for about eight days is dead. The worker reads back `CODEX_HOME/auth.json` at every checkpoint publish, at park and graceful shutdown, and at run end, and posts it to a new join-token-authenticated endpoint that re-seals the secret; the api rejects a write-back whose secret version changed underneath (optimistic version). A run requeued onto a fresh pod therefore seeds from the latest written-back state, not from the original upload. The seed is copied in only when the run's `CODEX_HOME/auth.json` is absent.
- **D5: one in-flight run per Codex seat credential.** Refresh-token rotation semantics are unverified (whether an old refresh token stays valid after rotation). Until M0 settles it, the claim path holds at most one running run per `codex_auth` secret, as a `NOT EXISTS` predicate keyed on a new `runs.codex_secret_id` (mirror of `runs.anthropic_secret_id`, `00086`); API-key credentials are unconstrained. A crashed run holds its seat until the sweeper's stale-heartbeat timeout releases it, which is accepted. If M0 finds rotation is non-invalidating, this becomes a per-seat concurrency cap (#229 Q3) instead of 1.
- **D6: the layer map for Codex.** Clause → layer: `git push` / remote mutation / force ops / `git config --get` / bare `env` / `ps` / `/proc` / secret paths / wrapper depth → the **Bash screener as a `PreToolUse` command hook** matching the shell tool; outside-worktree and `.git` access → the **path guard as a hook** matching the file tools, plus the uid split; subagent allowlist and nested spawn → the **agent guard as a hook** on `spawn_agent` plus `agents.max_depth = 1`; repo-borne config → the project marked **untrusted** in the user layer plus `project_doc_max_bytes = 0` for `AGENTS.md`, verified by fixture; credential absence → the sparse env (`OPENAI_API_KEY`, `CODEX_API_KEY`, global `CODEX_HOME` stripped) and `CODEX_HOME/auth.json` added to the secret-path deny list; process tree → the wrapper at `codexPathOverride` does `setpriv` to `runner` and `setsid` so the existing group kill applies; **synchronous delegation (#34, B1)** → a delegated subagent must complete within the lead's turn, never backgrounded or deferred: Claude enforces it with `run_in_background:false` in the agent guard and `disallowedTools: [...ASYNC_DEFERRAL_TOOLS]`; on Codex M0(b) establishes whether a `spawn_agent` child thread can outlive the parent turn, and if it can, the adapter closes every child thread at each turn boundary before the pre-push reap and the hook denies `spawn_agent` from inside a subagent, with a fixture for both. Codex's own sandbox is configured `danger-full-access` and is not a layer.
- **D7: uzi tools over MCP; signals stay stream-observed.** Tool handlers are defined once as plain async functions; two adapters expose them: the existing `createSdkMcpServer` for Claude, and a worker-hosted streamable-HTTP MCP endpoint bound to `127.0.0.1` with a per-run bearer token (`bearer_token_env_var`) for Codex. Handlers run in the worker's event loop, so the model still blocks on the tool result. The run-control signals (`submit_plan`, `signal_done`, `ask_user`, `checkpoint`) are **not** latched at the HTTP handler: as on Claude (`scanSignals` and the `isSubagentFrame` rejection in `signals.ts`), the worker latches them only from a main-thread `mcp_tool_call` item observed in the `runStreamed` stream, so a subagent can never mark a run done or submit a plan. This requires subagent attribution on stream items (M0(b)); if an item's origin is ambiguous it is treated as subagent-originated and rejected (fail closed), which makes M0(b) a blocking gate on M3, not a degradation. Per-role reach uses `enabled_tools` in the role's config layer, an allowlist, mirroring `agents.ts:181-198`; the main-thread scan is the harness-independent backstop and is reasserted for Codex, not inherited.
- **D8: per-harness prompt rendering, Claude byte-identical.** The builtin bodies in `api/internal/agenttmpl/builtins/*.md` are **not edited** in phase 1, so the Claude rendering, the pristine-refresh path and every Anthropic run stay exactly as today (D0). The Codex render step, applied at provisioning, maps `tools:` to the role TOML (`shell_tool`, `web_search`, MCP `enabled_tools`, the hook enforcing read-only by `agent_type`) and rewrites the Claude-only tool vocabulary in the body (`SendMessage`, `TaskUpdate`, `TaskList`, `TaskGet`, `Agent`, `Read`/`Edit`/`Grep`/`Glob`) to Codex wording through a fixed substitution table committed next to the renderer, with a test that the Claude render of every builtin is unchanged. Making the bodies harness-neutral at the source is a later, separate change with its own prompt review. The `.claude/agents/` roster is untouched (dev roster, decoupled).
- **D9: per-harness model and effort vocabulary.** A server-owned list per harness (Claude: today's aliases; Codex: an explicit initial list settled in M0 from the models the SDK accepts, with reasoning effort mapped from uzi's effort values to `modelReasoningEffort`). The templates editor's per-role `model` is a per-harness alias; a Claude alias is never sent to Codex and vice versa, the render step falls back to the harness default and records it in the run's status frame.
- **D10: advice lane on either harness.** `model-pass.ts` gains a Codex implementation: one `thread.run` with `outputSchema`, a deny-all `PreToolUse` hook, `sandboxMode: "read-only"`, no MCP. The judge, review and summary settings gain no new knobs; they run on the run's harness when the user has no Anthropic credential, else on the configured Claude model as today.
- **D11: no fallback across credentials.** A run or schedule pinned to a harness whose credential was removed fails with `no_credential_for_harness` on the run header and schedule row. Silent fallback would move cost onto a seat the user did not choose.
- **D12: egress widens fleet-wide, recorded against ADR-0285.** Codex runs need `api.openai.com`, `chatgpt.com` and `auth.openai.com`. The restricted tier's allowlist is a namespace-level FQDN policy (`worker-fqdn-egress.yaml`), so the entries apply to every worker in the tier, including workers running only Claude runs; per-run egress is not expressible at that layer and D1 deliberately has no per-harness fleet. This is accepted as symmetric with the existing `*.anthropic.com` entry (an unauthenticated POST to either vendor is the same exfiltration class) and the ADR-0285 tier table gains the three hosts. Chart-level, shipped in phase 1, not a runtime toggle. **Confirmed by the user 2026-09-04**; the alternative, a per-harness worker pool, would reopen #229 D4 and was rejected.
- **D13: Codex isolation is gated, not just tested.** `settingSources: []` is ratcheted by `semgrep/settings-sources-isolation.yml`, which is blind to a new query surface. The Codex adapter gets its own equivalent: a single `codexThreadOptions()` builder is the only call site allowed to construct `CodexOptions`/`ThreadOptions`, and a semgrep rule fails `sast:semgrep` on any other `startThread`/`resumeThread` call or on a builder missing the untrusted-project marking, `project_doc_max_bytes = 0`, `approval_policy = "never"` and the sparse env.

## Success criteria

0. **No regression (D0)**: with no Codex credential, uzi behaves exactly as today; `agent/test/` unchanged through M2; every existing gate green.
1. A user with a Codex seat runs a labeled issue end to end on Codex on dev-cluster: plan, approval, implementation with subagents, MR opened, `main` untouched. The same worker runs a Claude run before and after.
2. The conformance suite is green for both harnesses and every clause in D6 is asserted as exercised on each.
3. UI is credential-driven: an Anthropic-only user sees no Codex control; a Codex-only user sees no Anthropic-only control (rate-limit meters, token pool toggle, credential badge); a user with both sees the harness picker in Run Defaults, the split Start button and the schedule select.
4. A Codex seat used across at least two runs more than eight days apart still authenticates, because the write-back stored the rotated token.
5. `run_usage` rows carry `harness`; a Codex-seat run reports tokens with no dollar cost and an API-key run reports metered cost.
6. The judge, review and summary lanes produce output on a Codex-only account.
7. Nothing under `.github/workflows/` changes in any commit of this PRD.
8. Two runs created on the same Codex seat: exactly one claims, the other waits, and the seat is released on the first run's terminal state or its stale-heartbeat sweep (live-DB test, D5).
9. A `submit_plan` or `signal_done` call emitted by a Codex subagent is rejected and the run does not transition (conformance fixture, D7).
10. Every `startThread`/`resumeThread` in `agent/src` goes through `codexThreadOptions()`, enforced by `sast:semgrep` (D13).

## Risks

- **R1 (from #229): seat terms of service.** Decided 2026-08-04: proceed under the one-human-one-seat model with API keys as the documented fallback; a per-vendor re-check is a GA precondition, not a prototyping one.
- **R2: refresh rotation and concurrency.** If rotation invalidates the old token, two concurrent runs on one seat kill each other. Mitigation: D5 (one run per seat) until M0 answers; the write-back version check catches a lost race loudly.
- **R3: SDK unknowns.** Abort semantics and child-thread visibility could force a different cancel path (kill the process group, then `resumeThread`) or lose subagent attribution in the feed. Mitigation: M0 answers before M2 starts; attribution degrades to lead-only frames, never to dropped frames.
- **R4: `AGENTS.md` neutralization regresses upstream.** Both switches are verified in source today (fact 4), but either could change in a Codex release. Mitigation: the M4 fixture (a repo `AGENTS.md` with a canary instruction, asserted absent from the model's behaviour and from the session transcript) runs in `gate:agent`, so a Codex version bump that reopens the vector reddens the gate.
- **R5: worker egress.** A uzi worker cannot reach `api.openai.com` today, so M0, M3's live path and M6 cannot run inside a uzi run; they are maintainer-local or dev-cluster steps. Everything else (extraction, hooks, suite, schema, UI) is offline and uzi-runnable.
- **R6: image weight.** The Codex binary adds roughly the size of one more Rust CLI to `base`; acceptable, but the build guard must keep the fake-`ldd` case from #1082 in its checklist even though the launcher does not sniff, so a future launcher change is caught.
- **R7: prompt vocabulary under Codex.** Builtin bodies are not edited (D8), so the pristine-refresh path is untouched; but a customized template (`customized = true`) or a repo-provided agent may name Claude-only tools that the substitution table does not know. Mitigation: the Codex render step strips unknown tool names, records them in the run's status frame, and the conformance suite has a fixture for an unknown tool name. Anthropic runs cannot be affected: the Claude render is asserted byte-identical.
