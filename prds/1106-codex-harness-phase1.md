**Issue**: [#1106](https://github.com/vtmocanu/uzi/issues/1106) · **Label**: PRD · **Priority**: Medium (strategic; phase 1 of #229)
**Status**: Draft. Whole-PRD review on 2026-09-05 found blocking design gaps and reopened M0 (see *Progress log*).
**Parent**: [#229](https://github.com/vtmocanu/uzi/issues/229) (multi-provider agents + judge, `prds/229-multi-provider-agents-judge.md`). ## Problem

uzi runs only on a Claude credential. Every lane imports `@anthropic-ai/claude-agent-sdk` and the worker authenticates only with `CLAUDE_CODE_OAUTH_TOKEN` (`agent/src/sdk-env.ts:73-126`). A user who holds a Codex (ChatGPT) seat or an OpenAI API key cannot run agents on it.

#229 designs the full multi-provider system and orders its milestones judge-first because the judge's guardrail surface is vacuous. That defers what users want first: running whole issues on a flat Codex seat. It also assumed the Codex sandbox would replace the deny hook and that provider workers would be a separate fleet; both assumptions were checked on 2026-09-04 and neither holds (see *Verified facts*), which makes a simpler phase 1 possible.

## Solution

A run executes entirely on **one harness**, chosen per run: all agents on Claude (today's path, byte-for-byte unchanged) or all agents on Codex. No agent mixing.

- **Each worker image carries both harnesses.** The independently built `agent/templates/base` and `agent/templates/jvm` images both gain the pinned `@openai/codex` binary and `@openai/codex-sdk`, with a guard in each build. Harness is a property of the **run**, not of the worker; any worker runs either. No new `workertmpl` entry, no per-harness fleet, no claim routing by harness. This keeps the shared worktree, checkpoints and uid split identical for both harnesses, and it is what makes later in-worker mixing (a Claude lead delegating `coder` to a Codex thread on the same tree) cheap instead of a scheduler problem.
- **Credentials drive the UX; there is no admin toggle.** With one credential nothing new appears anywhere. With both, a default harness in Run Defaults, a split Start button for the per-run override, a harness select in the schedule modal, and a harness badge on runs (Claude unmarked). Facts about existing runs and workers are never hidden.
- **Guardrail parity is a release gate, not an assumed port.** Codex's pod sandbox is inert, but whole-PRD review found that upstream `PreToolUse` failure paths and `write_stdin` are fail-open and that the current Claude hook adapters do not accept Codex's names or payloads. M0 remains open for a fail-closed execution design; the uid split, sparse env and credential absence remain OS-level layers, and repo-borne Codex config remains trust-gated. A conformance suite with one adversarial fixture per clause runs against both harnesses and is a first-class deliverable.
- **uzi's tools reach Codex over an out-of-process MCP transport** hosted by the worker on loopback; Claude keeps the in-process form (D0).
- **The tool-less advice lane** (judge, review, summary) runs on either harness so a Codex-only user keeps the judge. Chat stays on Claude.

### Out of scope (later phases of #229)

- Any mixing of agents across harnesses within a run; #727 profiles; sub-runs.
- OpenAI-compatible and local endpoints, the `wire_api` probe, the native chat-completions executor, the base-URL allowlist (D10). Phase 1 talks only to the fixed vendor endpoint.
- Device-code login (`codex login --device-auth`), capability-aware scheduling (#84), chat on Codex, Codex rate-limit meters (Claude's 5h/7d windows have no SDK-visible Codex equivalent in `runStreamed`).

### Later phases this PRD must not preclude (custom OpenAI URL, OpenAI-compatible, local LLM)

Tracked in #229 (D1, D10, R6, Success Criterion 4); listed here so phase 1 leaves the seams open.

- **Custom base URL / OpenAI-compatible endpoint** (OpenRouter, Azure OpenAI, an internal proxy, a self-hosted Responses-API server) is **not a new harness**: it is the Codex harness with a `[model_providers.<id>]` entry (`base_url`, `env_key`, `wire_api = "responses"`) in the provisioned `config.toml`, plus a third credential kind `openai_compatible {base_url, env_key, model}`. What it needs on top of phase 1: #229's admin base-URL allowlist (D10, mirrors `FORGE_ALLOWED_BASE_URLS`, https-only), a per-endpoint egress allowlist entry, and the vault-threat-model-style egress writeup. The project-layer denylist in fact 4 already stops a cloned repo from redirecting `base_url`.
- **Local LLM (Ollama, LM Studio)**: `codex exec` in 0.153.2 exposes `--oss` and `--local-provider lmstudio|ollama` (and an `oss_provider` config key), so a chat-completions-native local runtime may be reachable through the Codex harness directly. If that holds under the conformance suite, #229's third harness (the native chat-completions executor, finding 1) is unnecessary; if not, it stays as designed. Verify in that phase, not here.
- **Phase 1 keeps open**: `runs.harness` is `text` with a CHECK that a later additive migration widens; `user_secrets.kind` is CHECK-constrained (migration `00010`) and each new kind is one CHECK-widening migration plus a `store/enums.go` constant, the same step phase 1 takes for its two kinds; the per-run `CODEX_HOME/config.toml` is provisioned by the worker and is the only place a provider entry would go; the hook, the uid split and the conformance suite are endpoint-agnostic; the credential-card pattern extends to a third card without touching the first two; the credential-driven visibility rule extends unchanged (a user with only a compatible-endpoint credential sees only that).
- **Phase 1 explicitly does not ship**: any user-supplied `base_url`, any `model_providers` entry, the allowlist, or a local-provider flag. The Codex adapter talks only to the fixed vendor endpoint.

## Verified facts (2026-09-04; M0 additions 2026-09-05)

Each fact names how it was established so an implementer can re-verify. Facts marked *offline* need no network beyond the package cache.

**Codex side** (openai/codex source at `main`, `@openai/codex@0.153.2`, the Codex config reference and MCP docs):

1. **Hooks.** `$CODEX_HOME/config.toml` accepts synchronous `[[hooks.PreToolUse]]` command handlers; deny is exit 2 with the reason on stderr or an exit-0 JSON deny. A credential-free real CLI+SDK probe, driven through a local fake Responses server with positive controls, observed the exact stdin `tool_name` sequence `Bash`, `apply_patch`, `Bash`, `spawn_agent`, `mcp__m0__mark`: both the shell operation and the ordinary file read through `exec_command` were `Bash`, with no separate `Read` hook on this measured Codex path. The source-level `Write`/`Edit` names are matcher aliases for `apply_patch`, and `Agent` is a matcher alias for `spawn_agent`; `Bash` and the MCP name had no alias. The live code-mode path instead emitted `collaborationspawn_agent` and `collaborationwait_agent` even with `multi_agent_v2 = false`; its `SubagentStart`/`SubagentStop` hooks carried `agent_id` and `agent_type`. Matchers must cover both surfaces. A denied harmless shell/patch attempt reached the model's follow-up request and produced no side effect, proving enforcement rather than observation. Hooks carry a trust hash; `--dangerously-bypass-hook-trust` is required headless, the SDK has no corresponding option, and the `codexPathOverride` wrapper must inject it. Source and measurement details: [ADR-1106](../adr/1106-codex-harness.md).
2. **OS sandbox is inert in a pod** (*offline, measured*). On `node:24-alpine` as uid 10002 with `--cap-drop ALL` and `no-new-privileges`, `codex sandbox linux -- id` fails with `bwrap: No permissions to create a new namespace`. OpenAI's documented answer for containers is host isolation plus `--sandbox danger-full-access`. So the Codex run uses `approval_policy = "never"` and `danger-full-access`, and the deny layer is the hook, exactly the Claude lane's `permissionMode: "bypassPermissions"` plus `PreToolUse` shape (`agent/src/sdk-executor.ts:975-991`).
3. **musl binary, no `ldd` sniff** (*offline, measured*). The npm launcher maps Linux to `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`; those are the only Linux builds. `codex --version` runs on `node:24-alpine` for both arches, also with a fake GNU `ldd` first on PATH (the #1082 trigger). `codex exec --sandbox danger-full-access` under pod conditions reaches `api.openai.com` and fails only with `401 Missing bearer`. `CODEX_HOME` under `/tmp` makes Codex refuse to create its helper-binary PATH aliases (`Refusing to create helper binaries under temporary dir`), so `CODEX_HOME` goes on the data volume.
4. **Repo-borne config is trust-gated.** Config layers load `${PWD}/config.toml`, `./.codex/config.toml` up the tree and `$(git rev-parse --show-toplevel)/.codex/config.toml`, each "loaded but disabled when the directory is untrusted" (`codex-rs/config/src/loader/mod.rs`). Agent roles (`.codex/agents/*.toml`) and exec-policy `.codex/rules/*.rules` are read per layer, so a disabled project layer contributes neither. `model_provider`, `model_providers`, `openai_base_url`, `chatgpt_base_url`, `notify`, `profile(s)` are on `PROJECT_LOCAL_CONFIG_DENYLIST` regardless of trust. `AGENTS.md` **is** trust-gated too: `load_project_instructions` (`codex-rs/core/src/agents_md.rs:60-63`) returns before the project read loop when `active_project.is_untrusted()`, so an untrusted project contributes no `AGENTS.md`; independently, `project_doc_max_bytes = 0` breaks out of the loop at `remaining == 0`, so the cap alone also yields an empty project doc. Both are set (belt and braces) and M4 keeps the fixture. Fact-checked 2026-09-04 against the raw source.
5. **SDK and runtime surface.** `@openai/codex-sdk` (`sdk/typescript/src/*.ts`): `CodexOptions {codexPathOverride, baseUrl, apiKey, config, configOverrides, env}`; `ThreadOptions {model, sandboxMode, workingDirectory, skipGitRepoCheck, modelReasoningEffort, networkAccessEnabled, webSearchMode, webSearchEnabled, approvalPolicy, additionalDirectories, threadSource}` (`webSearchEnabled` is the legacy form); `startThread` / `resumeThread(id)`; `run` / `runStreamed` yielding `thread.started`, `turn.started`, `item.started|updated|completed`, `turn.completed {usage}`, `turn.failed`, `error`; declared items `agent_message`, `reasoning`, `command_execution`, `file_change`, `mcp_tool_call`, `web_search`, `todo_list`, `error`; `Usage {input_tokens, cached_input_tokens, cache_write_input_tokens, output_tokens, reasoning_output_tokens}`; `outputSchema` on `run`. Sessions persist under `$CODEX_HOME/sessions`. The 0.153.2 declarations omit the `collab_tool_call` that both real runtime probes emitted, so the adapter needs a narrow runtime decoder. The exact 0.153.2 exec source filters notifications to the primary thread and turn; independently observed child requests/completions produced no child message or tool frames in the parent stream, and one child completed after parent `turn.completed`.
6. **Subagents.** `$CODEX_HOME/agents/<role>.toml` admits bounded role metadata, instructions, model/effort and supported feature overrides; nested role loading filters sandbox, approval, web and MCP configuration so the parent sandbox, approval policy and MCP configuration are preserved. Therefore per-role `sandbox_mode`, `web_search`, or MCP `enabled_tools` is not an available policy mechanism. `[agents] max_concurrent_threads_per_session` and `max_depth` remain parent configuration (default depth 1, `DEFAULT_AGENT_MAX_DEPTH` in `codex-rs/core/src/config/mod.rs:242`); `features.multi_agent` defaults on and `features.multi_agent_v2` takes precedence when set (`config_toml.rs:684`).
7. **MCP.** `[mcp_servers.<name>]` stdio (`command`, `args`, `env`, `env_vars`, `cwd`, `startup_timeout_sec`, `tool_timeout_sec`) or streamable HTTP (`url`, `bearer_token_env_var`, `http_headers`), with `enabled_tools` / `disabled_tools`.

## Decision log

- **D0 (from #229): the Claude path is unchanged.** A run with no harness selected, or a user with only an Anthropic credential, gets today's code: same options, same in-process tools, same hooks, same tests. The port is an extraction behind an interface, not a modification. No existing-behavior test changes (SC0).
- **D1: one image, harness is a run property.** `runs.harness text NOT NULL DEFAULT 'claude' CHECK (harness IN ('claude','codex'))`, frozen at creation with the value the D11 resolver produced (the column default exists for pre-feature rows; the service always writes the resolved value). Workers do not declare a harness; the claim query gains nothing for routing, only the D5 seat-lock predicate for `codex_auth` runs. Rationale: the trust boundary is the worker, not the harness; a second fleet buys nothing in phase 1 and would make in-worker mixing later impossible.
- **D2: naming.** `harness` in code, API, schema and CLI flags (`--harness claude|codex`); UI labels "Claude" and "Codex"; credential cards "Anthropic" and "OpenAI / Codex". Not "provider", which #229 uses for the wider matrix.
- **D3: credential kinds.** Two new `user_secrets.kind` values, `openai_api_key` and `codex_auth` (the verbatim `auth.json` from `codex login`), added by one migration that widens `00010`'s CHECK, with matching constants and a declared seal path in `store/enums.go` (both `SealedWithDEK` through the per-user vault, like the Anthropic token, so the `user_id||kind` AAD binding holds). Same slot in `CODEX_HOME/auth.json` either way (#229 D9). No device-code flow in phase 1.
- **D4 (reopened): refresh write-back on every checkpoint, run-scoped, ordered before the terminal transition.** Credential-kind/row selection, secret version and CAS validation, reconciliation and failure recovery are open; the following is a desired invariant, not an accepted route contract. A Codex seat rotates its refresh token and writes the new `auth.json` on refresh, and a seat idle for about eight days is dead. The worker reads back `CODEX_HOME/auth.json` at every checkpoint publish, at park and graceful shutdown, and at run end, and posts it to `POST /api/worker/runs/{id}/codex-auth` with `{expected_version, auth_json}`. The desired authority is the run's credential binding: the api resolves the run through `GetRunOwnedByWorker`, derives the target rather than trusting request identity, checks kind, owner and a seat-held status, and re-seals through the vault with the same `user_id||kind` AAD. A stale version must reject without overwrite, but the negative matrix is not accepted: an "another run" case is not executable without a per-run capability. The run-end write-back must precede the terminal transition because `GetRunOwnedByWorker` does not filter on status and the status check would otherwise drop it; rejected write-back must be visible, never silently skipped. A fresh pod must seed from the latest reconciled state only when its run home lacks `auth.json`.
- **D5 (provisional): one in-flight run per Codex seat credential, enforced by the database.** Per-seat identity and the exact credential binding point remain open; the database invariant below is the desired conservative outcome. M0 proved that a forced refresh rotates persisted auth state, but deliberately did not replay the prior refresh token because the exact client treats reuse/revocation failures as permanent re-login failures and the experiment could revoke the token family. Phase 1 therefore does not rely on prior-token usability: at most one run per `codex_auth` secret may be in the **seat-held set** `('claimed','running','awaiting_approval','awaiting_input','awaiting_followup')` (the busy set `ListAllWorkers` already uses; `limit_wait` and `pool_wait` are Anthropic parks a Codex run never enters in phase 1); API-key credentials are unconstrained. The proposal freezes `runs.codex_secret_id` at run creation and uses a partial unique index over the seat-held statuses, because a `NOT EXISTS` in `ClaimRun` is racy under READ COMMITTED. `ClaimRun` retains the predicate for steady-state selection; the index catches the race as `23505`, handled as no claim. Terminal transition or stale-heartbeat requeue releases the proposed lock. SC8 must race separate transactions. Any future relaxation needs separate safe token-reuse evidence and an advisory lock, since a cap above 1 is not expressible as a unique index.
- **D6 (reopened): Codex guardrail parity needs a fail-closed design.** The measured canonical names remain `Bash`, `apply_patch`, normal/v1 `spawn_agent`, code-mode `collaborationspawn_agent`/`collaborationwait_agent`, and `mcp__…`, but alias-only reuse is rejected. The current Claude `buildPathGuardHook` and `buildAgentGuardHook` do not accept those canonical names or payloads; Codex needs explicit adapters, including Codex `apply_patch` path parsing. Upstream hook serialization/spawn/timeout/malformed-output failures and the unhooked `write_stdin` path are fail-open, so hook matching alone cannot enforce the Bash, secret-path, outside-worktree, `.git`, nested-agent or synchronous-delegation clauses. The uid split, sparse env, untrusted project and `project_doc_max_bytes = 0` remain independent layers; Codex's own sandbox remains configured `danger-full-access` and is not one. M0 must settle the missing fail-closed layer and child drain.
- **D7 (reopened): uzi tools over MCP; Codex parent streams are root-only.** The measured root MCP call and root-only stream remain valid, including the runtime-only `collab_tool_call` decoder and fail-closed treatment of unknown origin. The proposed loopback per-run MCP transport is not accepted until disposal and bearer/shell isolation are defined and tested. Role files cannot supply per-role MCP `enabled_tools`; subagent tool and signal policy must instead use a proven global hook or another fail-closed mechanism. A root stream cannot classify hidden child calls, so the happy-path attributed hook is not by itself a child-signal guarantee.
- **D8 (provisional): per-harness prompt rendering, Claude byte-identical.** The builtin bodies remain unedited and Claude rendering must stay byte-identical (D0). A Codex vocabulary substitution may still be needed, but role TOML cannot enforce the previously proposed per-role sandbox, web or MCP policy because those overrides are filtered. The final renderer and role-policy mechanism wait on D6/D7; the `.claude/agents/` dev roster remains untouched.
- **D9: per-harness model and effort vocabulary.** The product owns an explicit list per harness (Claude: today's aliases; initial Codex list: `gpt-6-astra` and `gpt-5.6-sol`, both proven by real no-tool turns at `max`). Uzi keeps its existing `low|medium|high|xhigh|max` effort contract and maps those values one-to-one to Codex `modelReasoningEffort`. The refreshed 0.153.2 server catalog also listed `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.5`, `gpt-5.4-mini`, and `gpt-5.3-codex-spark`, with model-specific effort sets recorded in ADR-1106; catalog visibility is discovery evidence, not an automatic picker expansion. `persistent` failed without a safely classifiable reason, so the SDK's wider effort union is not picker authority. The templates editor's per-role `model` is a per-harness alias; a Claude alias is never sent to Codex and vice versa, the render step falls back to the harness default and records it in the run's status frame.
- **D10 (reopened): advice lane on either harness.** Exhaustive advice-consumer routing, typed rate-limit/error behavior and the fail-closed tool-less policy are unresolved. The desired shape is one Codex `thread.run` with `outputSchema`, read-only isolation and no MCP; judge, review and summary must preserve their current Claude behavior and route explicitly rather than by an incomplete credential heuristic.
- **D11 (provisional): explicit selection never falls back; an implicit default resolves.** Exhaustive run-kind routing, old-worker claim compatibility, and model/default/schedule/TUI semantics remain open; the following is the desired resolver behavior. One resolver, shared by `POST /repos/{id}/runs`, the chat `start_run` and schedule fire, decides the run's harness in this order: (1) a harness named on the request, or a schedule's non-null `harness`, is **explicit**: used as is, and if the user holds no credential of that kind the run fails `no_credential_for_harness` on the run header and schedule row (silent fallback would move cost onto a seat the user did not choose); (2) otherwise `users.default_harness`, when set and its credential exists; (3) otherwise the sole harness the user holds a credential for, when exactly one; (4) otherwise, both credentials and no usable default, `claude` (D0); (5) no credential at all is the existing gate (`hasToken.ts` in the UI, the create-run rejection in the api). `users.default_harness` and `run_schedules.harness` are both nullable, null meaning "resolve at creation or fire time"; `runs.harness` and `runs.codex_secret_id` record what was resolved, frozen (D1, D5). Without step 3 a Codex-only user, who by SC3 sees no picker, would start `claude` runs that fail step 1 with no control to change it.

  | credentials held | picker (SC3) | `default_harness` null | `default_harness` names a harness with no credential |
  |---|---|---|---|
  | none | none, gate | gate (5) | gate (5) |
  | Anthropic only | none | `claude` (3) | `claude` (3) |
  | Codex only | none | `codex` (3) | `codex` (3) |
  | both | Run Defaults, Start, schedule | `claude` (4) | cannot occur (both exist) |

  Transitions: adding a second credential reveals the picker and leaves `default_harness` null, so runs stay on `claude` until the user picks (D0); removing a credential does **not** rewrite `default_harness` (it is a preference, not a pin), the dangling value is skipped at step 2 and step 3 resolves to the remaining credential; a schedule pinned to the removed harness fails at step 1 on every fire until the user edits it or re-adds a credential of that kind, and the schedule row says so. Re-adding a credential makes the same default and the same pinned schedules work again with no edit.
- **D12: egress widens fleet-wide, recorded against ADR-0285.** Codex runs need `api.openai.com`, `chatgpt.com` and `auth.openai.com`. The restricted tier's allowlist is a namespace-level FQDN policy (`worker-fqdn-egress.yaml`), so the entries apply to every worker in the tier, including workers running only Claude runs; per-run egress is not expressible at that layer and D1 deliberately has no per-harness fleet. This is accepted as symmetric with the existing `*.anthropic.com` entry (an unauthenticated POST to either vendor is the same exfiltration class) and the ADR-0285 tier table gains the three hosts. Chart-level, shipped in phase 1, not a runtime toggle. **Confirmed by the user 2026-09-04**; the alternative, a per-harness worker pool, would reopen #229 D4 and was rejected.

## Open design blockers from whole-PRD review

These findings are unresolved contracts, not implementation prescriptions:

- Codex still needs an exact credential-kind and row-selection rule, including
  per-seat identity when multiple seat/API-key rows exist.
- Secret versioning, CAS/write-back validation, reconciliation, failure recovery
  and per-seat identity are unspecified. The proposed "another run" negative
  test is impossible without a per-run capability, and M1 currently needs M5's
  run binding while M5 depends on M1, forming a DAG cycle.
- Routing is not exhaustive across every run kind and advice consumer, and an
  old worker may claim a new Codex run without understanding its harness.
- API-key metered-cost calculation is undefined, so SC5 remains blocked; model,
  default, schedule and TUI semantics also need one consistent contract.
- Both `base` and `jvm` images need Codex build guards. Release acceptance still
  lacks a real compose e2e gate and a pre-merge image publish/rollback path.

M0, M1, M3, M4, M5 and M6 remain blocked on the relevant items above; their
current text is a work list, not an accepted design.

## Risks

- **R1 (from #229): seat terms of service.** Decided 2026-08-04: proceed under the one-human-one-seat model with API keys as the documented fallback; a per-vendor re-check is a GA precondition, not a prototyping one.
- **R2: refresh rotation and concurrency.** M0 proved that refresh rotates persisted auth state but deliberately did not replay the prior token because doing so could revoke the token family. Mitigation: D5 remains a one-run-per-seat database invariant; refresh write-back preserves the newest state, and its version check catches a lost race loudly. Any future concurrency relaxation needs separate safe token-reuse evidence.
- **R3: SDK drift and root-only visibility.** M0 proved server-backed abort/resume and found that 0.153.2 filters child messages/tools from the parent stream while emitting undeclared `collab_tool_call` lifecycle frames; a child can outlive parent `turn.completed`. Mitigation: a narrow runtime decoder and honest lifecycle-only feed degradation. M0 remains open for a measured child drain; the runner's process-tree reap at checkpoint, terminal and pre-credentialed-git boundaries is not evidence that provider child threads stopped, and ordinary iteration boundaries deliberately use `reap: false`.
- **R4: `AGENTS.md` neutralization regresses upstream.** Both switches are verified in source today (fact 4), but either could change in a Codex release. Mitigation: the M4 fixture (a repo `AGENTS.md` with a canary instruction, asserted absent from the model's behaviour and from the session transcript) runs in `gate:agent`, so a Codex version bump that reopens the vector reddens the gate.
- **R5: worker egress.** Restricted and standard hosted workers cannot reach the OpenAI endpoints today; the docker tier has broad egress and is a different security posture. M0 stays maintainer-local because it uses a maintainer credential, while M3's live path and M6 are dev-cluster steps. Credential-free fake-server conformance, extraction, schema and UI work remain uzi-runnable in the appropriate tier.
- **R6: image weight.** The Codex binary adds roughly the size of one more Rust CLI to `base`; acceptable, but the build guard must keep the fake-`ldd` case from #1082 in its checklist even though the launcher does not sniff, so a future launcher change is caught.
- **R7: prompt vocabulary under Codex.** Builtin bodies are not edited (D8), so the pristine-refresh path is untouched; but a customized template (`customized = true`) or a repo-provided agent may name Claude-only tools that the substitution table does not know. Mitigation: the Codex render step strips unknown tool names, records them in the run's status frame, and the conformance suite has a fixture for an unknown tool name. Anthropic runs cannot be affected: the Claude render is asserted byte-identical.

## Open questions

- **Q1**: resolved into D9: initial Codex list `gpt-6-astra` and `gpt-5.6-sol`; uzi `low|medium|high|xhigh|max` maps one-to-one, while the wider server catalog and SDK union do not automatically expand the picker.
- **Q2**: resolved into D4 (write-back on every checkpoint, park, shutdown and run end), because a mid-run rotation followed by a requeue onto a fresh pod would otherwise resurrect a stale token.
- **Q3**: unresolved: Codex needs a fail-closed plan-vs-implement write-policy mechanism. Neither hook `permission_mode: plan` nor the existing phase-marker approach is accepted for Codex yet.
