## Problem

uzi runs only on a Claude credential. Every lane imports `@anthropic-ai/claude-agent-sdk` and the worker authenticates only with `CLAUDE_CODE_OAUTH_TOKEN` (`agent/src/sdk-env.ts:73-126`). A user who holds a Codex (ChatGPT) seat or an OpenAI API key cannot run agents on it.

#229 designs the full multi-provider system and orders its milestones judge-first because the judge's guardrail surface is vacuous. That defers what users want first: running whole issues on a flat Codex seat. It also assumed the Codex sandbox would replace the deny hook and that provider workers would be a separate fleet; both assumptions were checked on 2026-09-04 and neither holds (see *Verified facts*), which makes a simpler phase 1 possible.

## Solution

A run executes entirely on **one harness**, chosen per run: all agents on Claude (today's path, byte-for-byte unchanged) or all agents on Codex. No agent mixing.

- **Each worker image carries both harnesses.** The independently built `agent/templates/base` and `agent/templates/jvm` images both gain the pinned `@openai/codex` binary, with a guard in each build; the adapter uses app-server; no unused SDK dependency is prescribed. Harness is a property of the **run**, not of the worker; no per-harness fleet or new `workertmpl` entry. Old-worker compatibility must be resolved before enabling Codex claims. This keeps the shared worktree, checkpoints and uid split identical for both harnesses and avoids a separate scheduler for later in-worker mixing.
- **Credentials drive the UX; there is no admin toggle.** Credential management supports named Codex logins and API keys with one user default across those Codex credentials (D3). After M5 enables routing, one available harness needs no harness picker; both harnesses expose Run Defaults, a per-run override, a schedule select and a harness badge (Claude unmarked). Credential counts do not stand in for harness availability. M1 only adds management and a dark binding/API foundation: saving a Codex credential must not unlock Codex execution. Facts about existing runs and workers are never hidden.
- **Guardrail parity is a release gate, not an assumed port.** Codex's pod sandbox is inert, but whole-PRD review found that upstream `PreToolUse` failure paths and `write_stdin` are fail-open and that the current Claude hook adapters do not accept Codex's names or payloads. M0 accepted the fail-closed execution architecture; production parity remains M3/M4 work; the uid split, sparse env and credential absence remain OS-level layers, and repo-borne Codex config remains trust-gated. A conformance suite with one adversarial fixture per clause runs against both harnesses and is a first-class deliverable.
- **The accepted Codex transport uses app-server.** Its design uses worker-owned app-server callbacks and synchronous worker-created child threads (D6/D7); the earlier loopback-MCP/native-role design is not accepted. Claude keeps its in-process form (D0).
- **The isolated advice lane** (judge, review, summary) is intended to run on either harness so a Codex-only user keeps the judge. The shared advice ceiling permits isolated pure in-memory calculation on both harnesses (D10); Claude's current tool-less path remains unchanged. Chat stays on Claude.

### Out of scope (later phases of #229)

- Any mixing of agents across harnesses within a run; #727 profiles; sub-runs.
- OpenAI-compatible and local endpoints, the `wire_api` probe, the native chat-completions executor, the base-URL allowlist (D10). Phase 1 talks only to the fixed vendor endpoint.
- Device-code login (`codex login --device-auth`), capability-aware scheduling (#84), chat on Codex, Codex rate-limit meters (Claude's 5h/7d windows have no SDK-visible Codex equivalent in `runStreamed`).

### Later phases this PRD must not preclude (custom OpenAI URL, OpenAI-compatible, local LLM)

Tracked in #229 (D1, D10, R6, Success Criterion 4); listed here so phase 1 leaves the seams open.

- **Custom base URL / OpenAI-compatible endpoint** (OpenRouter, Azure OpenAI, an internal proxy, a self-hosted Responses-API server) is **not a new harness**: it is the Codex harness with a `[model_providers.<id>]` entry (`base_url`, `env_key`, `wire_api = "responses"`) in the provisioned `config.toml`, plus a third credential kind `openai_compatible {base_url, env_key, model}`. What it needs on top of phase 1: #229's admin base-URL allowlist (D10, mirrors `FORGE_ALLOWED_BASE_URLS`, https-only), a per-endpoint egress allowlist entry, and the vault-threat-model-style egress writeup. The project-layer denylist in fact 4 already stops a cloned repo from redirecting `base_url`.
- **Local LLM (Ollama, LM Studio)**: `codex exec` in 0.153.2 exposes `--oss` and `--local-provider lmstudio|ollama` (and an `oss_provider` config key), so a chat-completions-native local runtime may be reachable through the Codex harness directly. If that holds under the conformance suite, #229's third harness (the native chat-completions executor, finding 1) is unnecessary; if not, it stays as designed. Verify in that phase, not here.
- **Phase 1 keeps open**: `runs.harness` is `text` with a CHECK that a later additive migration widens; `user_secrets.kind` is CHECK-constrained (migration `00010`) and each new kind is one CHECK-widening migration plus a `store/enums.go` constant, the same step phase 1 takes for its two kinds; the per-run `CODEX_HOME/config.toml` is provisioned by the worker and is the only place a provider entry would go; the hook, the uid split and the conformance suite are endpoint-agnostic; the credential-card pattern extends to a third card without touching the first two; the credential-driven visibility rule extends unchanged (a user with only a compatible-endpoint credential sees only that).
- **Phase 1 explicitly does not ship**: any user-supplied `base_url`, any `model_providers` entry, the allowlist, or a local-provider flag. The Codex adapter talks only to the fixed vendor endpoint.

## Verified facts (2026-09-04; M0 additions 2026-09-05)

Each fact names how it was established so an implementer can re-verify. Facts marked *offline* need no network beyond the package cache.

**Codex side** (openai/codex source at `main`, `@openai/codex@0.153.2`, the Codex config reference and MCP docs):

1. **Hooks.** `$CODEX_HOME/config.toml` accepts synchronous `[[hooks.PreToolUse]]` command handlers; deny is exit 2 with the reason on stderr or an exit-0 JSON deny. A credential-free real CLI+SDK probe, driven through a local fake Responses server with positive controls, observed the exact stdin `tool_name` sequence `Bash`, `apply_patch`, `Bash`, `spawn_agent`, `mcp__m0__mark`: both the shell operation and the ordinary file read through `exec_command` were `Bash`, with no separate `Read` hook on this measured Codex path. The source-level `Write`/`Edit` names are matcher aliases for `apply_patch`, and `Agent` is a matcher alias for `spawn_agent`; `Bash` and the MCP name had no alias. The live code-mode path instead emitted `collaborationspawn_agent` and `collaborationwait_agent` even with `multi_agent_v2 = false`; its `SubagentStart`/`SubagentStop` hooks carried `agent_id` and `agent_type`. Matchers must cover both surfaces. A denied harmless shell/patch attempt reached the model's follow-up request and produced no side effect, proving enforcement rather than observation. The exec/SDK probe used a wrapper injecting `--dangerously-bypass-hook-trust`; the SDK has no corresponding option. The committed app-server continuation additionally needed `thread/start`'s `config: { bypass_hook_trust: true }` to arm its hooks; the global flag alone did not. Neither fixture bypass is an accepted production trust decision. Source and measurement details: [ADR-1106](../adr/1106-codex-harness.md).
2. **OS sandbox is inert in a pod** (*offline, measured*). On `node:24-alpine` as uid 10002 with `--cap-drop ALL` and `no-new-privileges`, `codex sandbox linux -- id` fails with `bwrap: No permissions to create a new namespace`. OpenAI's documented answer for containers is host isolation plus `--sandbox danger-full-access`. This does not require `approval_policy = "never"`: the app-server continuation measures `untrusted` approvals with `danger-full-access`, and managed native one-shot execution removes the retained-stdin path. The integrated fail-closed design is accepted, with production conformance in M3/M4; hook-only enforcement is insufficient.
3. **musl binary, no `ldd` sniff** (*offline, measured*). The npm launcher maps Linux to `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`; those are the only Linux builds. `codex --version` runs on `node:24-alpine` for both arches, also with a fake GNU `ldd` first on PATH (the #1082 trigger). `codex exec --sandbox danger-full-access` under pod conditions reaches `api.openai.com` and fails only with `401 Missing bearer`. `CODEX_HOME` under `/tmp` makes Codex refuse to create its helper-binary PATH aliases (`Refusing to create helper binaries under temporary dir`), so `CODEX_HOME` goes on the data volume.
4. **Repo-borne config is trust-gated.** Config layers load `${PWD}/config.toml`, `./.codex/config.toml` up the tree and `$(git rev-parse --show-toplevel)/.codex/config.toml`, each "loaded but disabled when the directory is untrusted" (`codex-rs/config/src/loader/mod.rs`). Agent roles (`.codex/agents/*.toml`) and exec-policy `.codex/rules/*.rules` are read per layer, so a disabled project layer contributes neither. `model_provider`, `model_providers`, `openai_base_url`, `chatgpt_base_url`, `notify`, `profile(s)` are on `PROJECT_LOCAL_CONFIG_DENYLIST` regardless of trust. `AGENTS.md` **is** trust-gated too: `load_project_instructions` (`codex-rs/core/src/agents_md.rs:60-63`) returns before the project read loop when `active_project.is_untrusted()`, so an untrusted project contributes no `AGENTS.md`; independently, `project_doc_max_bytes = 0` breaks out of the loop at `remaining == 0`, so the cap alone also yields an empty project doc. Both are set (belt and braces) and M4 keeps the fixture. Fact-checked 2026-09-04 against the raw source.
5. **SDK and runtime surface.** `@openai/codex-sdk` (`sdk/typescript/src/*.ts`): `CodexOptions {codexPathOverride, baseUrl, apiKey, config, configOverrides, env}`; `ThreadOptions {model, sandboxMode, workingDirectory, skipGitRepoCheck, modelReasoningEffort, networkAccessEnabled, webSearchMode, webSearchEnabled, approvalPolicy, additionalDirectories, threadSource}` (`webSearchEnabled` is the legacy form); `startThread` / `resumeThread(id)`; `run` / `runStreamed` yielding `thread.started`, `turn.started`, `item.started|updated|completed`, `turn.completed {usage}`, `turn.failed`, `error`; declared items `agent_message`, `reasoning`, `command_execution`, `file_change`, `mcp_tool_call`, `web_search`, `todo_list`, `error`; `Usage {input_tokens, cached_input_tokens, cache_write_input_tokens, output_tokens, reasoning_output_tokens}`; `outputSchema` on `run`. Sessions persist under `$CODEX_HOME/sessions`. The 0.153.2 declarations omit the `collab_tool_call` that both real runtime probes emitted, so an exec/SDK adapter would need a narrow runtime decoder; the accepted design uses app-server callbacks instead. The exact 0.153.2 exec source filters notifications to the primary thread and turn; the SDK probe exposed no child message or tool frames. Its delayed server response alone did not prove child consumption or action after parent completion. The committed app-server probe now proves actual post-parent child activity with a marker and a subsequent request carrying tool output; its known-child interruption and terminal cleanup results are bounded in ADR-1106.
6. **Subagents.** `$CODEX_HOME/agents/<role>.toml` admits bounded role metadata, instructions, model/effort and supported feature overrides; nested role loading filters sandbox, approval, web and MCP configuration so the parent sandbox, approval policy and MCP configuration are preserved. Therefore per-role `sandbox_mode`, `web_search`, or MCP `enabled_tools` is not an available policy mechanism. `[agents] max_concurrent_threads_per_session` and `max_depth` remain parent configuration (default depth 1, `DEFAULT_AGENT_MAX_DEPTH` in `codex-rs/core/src/config/mod.rs:242`); `features.multi_agent` defaults on and `features.multi_agent_v2` takes precedence when set (`config_toml.rs:684`).
7. **MCP.** `[mcp_servers.<name>]` stdio (`command`, `args`, `env`, `env_vars`, `cwd`, `startup_timeout_sec`, `tool_timeout_sec`) or streamable HTTP (`url`, `bearer_token_env_var`, `http_headers`), with `enabled_tools` / `disabled_tools`.

## Decision log

- **D0 (from #229): the Claude path is unchanged.** A run with no harness selected, or a user with only an Anthropic credential, gets today's code: same options, same in-process tools, same hooks, same tests. The port is an extraction behind an interface, not a modification. No existing-behavior test changes (SC0).
- **D1: one image, harness is a run property.** `runs.harness text NOT NULL DEFAULT 'claude' CHECK (harness IN ('claude','codex'))`, frozen at creation with the value the D11 resolver produced (the column default exists for pre-feature rows; the enabled service writes the resolved value). M1 owns the minimal immutable credential binding; M5 owns broad harness selection and routing. Workers do not form a per-harness fleet; old-worker claim compatibility remains an enablement prerequisite. D5 permits concurrent runs on the same subscription. Rationale: the trust boundary is the worker, and a second fleet would obstruct later in-worker mixing.
- **D2: naming.** `harness` in code, API, schema and CLI flags (`--harness claude|codex`); UI labels "Claude" and "Codex"; credential cards "Anthropic" and "OpenAI / Codex". Not "provider", which #229 uses for the wider matrix.
- **D3 (user-approved 2026-09-06): named Codex logins and API keys, one Codex credential default.** Add `openai_api_key` and `codex_auth` kinds to `user_secrets`, with matching `store/enums.go` constants and declared `SealedWithDEK` seal paths through the per-user vault (`user_id||kind` AAD). Support named imports/keys and one user-selected default across the two Codex kinds, separate from the Anthropic default. At run creation, resolve and freeze the selected credential and auth mode; a later default change must not retarget that run, and a subscription failure must never silently spend an API key. Exact selection/deletion/rotation transitions belong in the M1 plan. Rationale: users can manage several logins and control which billing mode a run spends. Impact: storage/default CRUD, metadata DTOs, credential card, read-only CLI listing and the immutable binding are M1; broad run pickers remain M5. No device-code flow in phase 1.
- **D4 (user-approved 2026-09-06): persist refreshed login before durability boundaries, with run-scoped authority and recoverable failure.** Refresh can rotate auth state; there is no accepted fixed idle-expiry claim. Before checkpoint publication, pause/park, graceful shutdown or completion, the latest refreshed login must be durably persisted and acknowledged. Stale writes reject without replacing newer state; retries need idempotent reconciliation for lost acknowledgments. A persistence failure pauses progress and retains recoverable state for retry; request re-login only when recovery is impossible. Recovery is not promised after loss of every durable copy. The api authorizes with a run-specific capability **and** the currently owning worker, derives the target secret from the immutable run binding, checks kind/owner/lifecycle, and re-seals through the vault; requests cannot select a secret or user id. `GetRunOwnedByWorker` alone is insufficient because its worker id survives terminal transition. The M1 plan must specify capability lifetime/revocation, version/CAS/idempotence and protected recovery storage; M3 wires provider refresh and all runner boundaries to it. Rationale: prevent stale-token resurrection and cross-run writes without turning recoverable storage failure into forced re-login.
- **D5 (user-approved correction 2026-09-06): concurrent runs on one Codex subscription are allowed, as with Anthropic.** This supersedes the earlier recommendation to queue on a busy seat and the conservative run-long seat-lock policy discussed in M0/ADR-1106. Do not add a seat-held run-state set, active-seat unique index, claim predicate or seat-busy queue that serializes whole runs. API keys likewise acquire no subscription-specific run lock. Canonicalize the actual provider account/workspace identity, established from verified provider evidence rather than an invented claim field, label or saved-row id; duplicate imports must share refresh coordination/state, not create a concurrency limit. Coordinate only credential operations, using a short operation-scoped mechanism plus version/CAS/idempotence. **CAS after refresh does not prevent two provider-side refreshes from racing or invalidating tokens.** Before implementation, the M1 plan must establish an enforceable refresh mechanism, authority scope, duplicate-import reconciliation, crash/lease-loss behavior and the M3 runtime seam that prevents uncoordinated refresh. Do not assume the provider permits old-token reuse or concurrent rotation. A run keeps its chosen credential/auth mode while that credential's version advances. Rationale: preserve parallel run throughput while preventing stale or conflicting login updates. Impact: SC8 tests concurrent runs plus coordinated refresh, not mutual exclusion of runs.
- **D6 (accepted architecture): worker-owned fail-closed policy; production parity remains M3/M4.** Healthy hook denies do not cover upstream failure paths or retained `write_stdin`; alias-only reuse of Claude hooks is rejected. Native and intended-model code-mode fixtures now measure managed shell approvals and one-shot execution. The accepted design disables native environments/agents and gives authority only to worker-owned dynamic callbacks, checked against immutable runtime thread/turn, role and phase state. The uid split, sparse env, untrusted project and `project_doc_max_bytes = 0` remain independent layers. Native-authority controls, representative synchronous delegation and actual-host disposal now have bounded fixture evidence; the capability owners, explicit untrusted construction and per-run supervisor-root registry define how production handlers and the joint outer gate compose, with implementation/conformance in M3/M4; see [ADR-1106](../adr/1106-codex-harness.md#execution-policy).
- **D7 (accepted architecture): worker-owned app-server callbacks.** Separate uzi handlers from Claude in-process MCP registration without changing Claude behavior. For Codex, app-server `item/tool/call` carries measured runtime thread/turn/call identity through native and code-mode fixtures. The specified worker registry authorizes callbacks before invocation, rejects unknown/stale origins, preserves per-role tool/skill and phase policy, and admits workflow signals only for the root. Worker-created child threads provide the synchronous-delegation design; native role files cannot enforce these restrictions. This supersedes the unaccepted loopback-MCP candidate and avoids its model-side bearer. Representative callback admission, role policy and disposal now have fixture evidence; the production registry and outer safety gate are specified for M3/M4 implementation. Exec/SDK root-only visibility remains protocol evidence, not the chosen feed contract; [ADR-1106](../adr/1106-codex-harness.md) bounds both.
- **D8 (provisional): per-harness prompt rendering, Claude byte-identical.** The builtin bodies remain unedited and Claude rendering must stay byte-identical (D0). A Codex vocabulary substitution may still be needed, but role TOML cannot enforce the previously proposed per-role sandbox, web or MCP policy because those overrides are filtered. The M3 renderer follows the accepted role/tool mapping from D6/D7; worker callbacks enforce that policy; the `.claude/agents/` dev roster remains untouched.
- **D9: per-harness model and effort vocabulary.** The product owns an explicit list per harness (Claude: today's aliases; initial Codex list: `gpt-6-astra` and `gpt-5.6-sol`, both proven by real no-tool turns at `max`). Uzi keeps its existing `low|medium|high|xhigh|max` effort contract and maps those values one-to-one to Codex `modelReasoningEffort`. The refreshed 0.153.2 server catalog also listed `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.5`, `gpt-5.4-mini`, and `gpt-5.3-codex-spark`, with model-specific effort sets recorded in ADR-1106; catalog visibility is discovery evidence, not an automatic picker expansion. `persistent` failed without a safely classifiable reason, so the SDK's wider effort union is not picker authority. The templates editor's per-role `model` is a per-harness alias; a Claude alias is never sent to Codex and vice versa, the render step falls back to the harness default and records it in the run's status frame.
- **D10 (user-approved 2026-09-05): shared advice capability ceiling on both harnesses.** Claude and Codex may use isolated pure in-memory calculation; shell/commands, filesystem access, network tools, delegation, run/worker callbacks and credential access are denied. The accepted [contract companion](../e2e/codex-m0/harness-contract.md) separates run/advice construction and preserves neutral result/error handling. This permission adds no Claude calculator: current `model-pass.ts` denies every tool through `buildDenyAllHook`, unchanged in M0/M2 under D0. A future Claude calculation tool needs its own isolated implementation and conformance; a shell-based calculator is not permitted. Codex pure-cell fixtures provide bounded evidence; no Claude calculator or live API-key path was tested. Exhaustive advice routing remains downstream work; native output-schema enforcement remains lane-specific and unaccepted. Preserve Claude parsing, synchronous callback authority and existing outer fallbacks.
- **D11 (credential policy approved 2026-09-06; broad routing contract still provisional): explicit selection never falls back; harness and credential defaults are distinct.** When provider execution is enabled, one M5 resolver shared by run creation, chat `start_run` and schedule fire chooses the harness: (1) an explicit request/schedule harness is used as named, or returns `no_credential_for_harness`; (2) otherwise a usable `users.default_harness`; (3) otherwise the sole available harness; (4) otherwise Claude when both are available and no usable default is set (D0); (5) no credentials retains the existing gate. `users.default_harness` and `run_schedules.harness` remain nullable. After Codex is selected, resolve its named credential under D3 and freeze the credential/auth-mode binding at run creation; do not silently switch a missing/failed subscription to an API key. Missing/default/deletion cases must be explicit in the M1 plan and later M5 resolver tests. Changing a preference affects future runs only; refreshing a credential may advance its version without changing the run's selected credential. Exhaustive run-kind/advice routing, old-worker compatibility and model/default/schedule/TUI behavior remain M5/M3 contracts. M1 must keep today's Claude execution eligibility unchanged even when Codex credentials have been saved.

## Risks

- **R1 (from #229): seat terms of service.** Decided 2026-08-04: proceed under the one-human-one-seat model with API keys as the documented fallback; a per-vendor re-check is a GA precondition, not a prototyping one.
- **R2: refresh rotation under concurrent runs.** M0 proved rotation but deliberately did not replay the prior token; this supplies no guarantee that provider-side concurrent refresh is safe. D5 now permits concurrent subscription runs. Mitigate refresh races through verified short credential-operation coordination, shared latest-state reconciliation and protected recovery; version CAS alone cannot prevent provider token invalidation. The plan must stop if it cannot establish an enforceable mechanism, and the M3 adapter must use that mechanism before concurrent Codex execution is enabled.
- **R3: protocol drift and incomplete ownership.** The exec/SDK stream is root-only; app-server fixtures expose actual child events. Intended-model code-mode coverage now measures managed approvals and dynamic identity, and the native-isolation/broker/supervisor fixtures add bounded authority and actual-host disposal evidence; the integrated production barrier is specified but not implemented. Use runtime identity and observed content without fabricated attribution. Process reaping and child quiescence are separate barriers; ordinary iteration fetch-back still uses `reap: false`. See ADR-1106 for the specified supervisor and explicit legacy Claude behavior.
- **R4: `AGENTS.md` neutralization regresses upstream.** Both switches are verified in source today (fact 4), but either could change in a Codex release. Mitigation: the M4 fixture (a repo `AGENTS.md` with a canary instruction, asserted absent from the model's behaviour and from the session transcript) runs in `gate:agent`, so a Codex version bump that reopens the vector reddens the gate.
- **R5: worker egress.** Restricted and standard hosted workers cannot reach the OpenAI endpoints today; the docker tier has broad egress and is a different security posture. M0 stays maintainer-local because it uses a maintainer credential, while M3's live path and M6 are dev-cluster steps. Credential-free fake-server conformance, extraction, schema and UI work remain uzi-runnable in the appropriate tier.
- **R6: image weight.** The Codex binary adds roughly the size of one more Rust CLI to `base`; acceptable, but the build guard must keep the fake-`ldd` case from #1082 in its checklist even though the launcher does not sniff, so a future launcher change is caught.
- **R7: prompt vocabulary under Codex.** Builtin bodies are not edited (D8), so the pristine-refresh path is untouched; but a customized template (`customized = true`) or a repo-provided agent may name Claude-only tools that the substitution table does not know. Mitigation: the Codex render step strips unknown tool names, records them in the run's status frame, and the conformance suite has a fixture for an unknown tool name. Anthropic runs cannot be affected: the Claude render is asserted byte-identical.
