# PRD #1378: Opt-in RC channel for the uzi-cli Homebrew formula

- **Issue**: #1378
- **Priority**: Medium
- **Surfaces**: the Homebrew tap layer only. New `Formula/uzi-cli-rc.rb` (a render template), a one-line addition to `Formula/uzi-cli.rb`, a second `brew-rc:` include + `lint:formula` line in `Taskfile.yml`, a channel-aware `scripts/brew-local-test.sh`, and a terse note in the `uzi-release` skill (M1-M2). A `.github/workflows/brew.yml` change (widen trigger, extend the Validate regex, add a channel-detect step, rewire Render/Publish, and serialize the tap push) plus the coupled `release-watch.sh` / `release-verify.sh` RC-brew handling are **maintainer-local** (M3, split into its own issue). No route, DTO, migration, Go source, web, worker or chart-template change. No README or `docs/*.md` change.
- **Guardrail**: M3 touches `.github/workflows/**`, which a uzi worker cannot push (its PAT lacks `workflow` scope, atomic push rejection — `.claude/rules/prds.md`). So M1-M2 are the uzi-bound, workflow-free part, and M3 is done in a local session with a `workflow`-scoped token, cross-linked as a separate maintainer issue. Before finalize, `git diff --name-only <base>..HEAD` on the uzi branch shows zero entries under `.github/workflows/`.

## Problem

PRD #1265 made releases RC-first: `release-cut X.Y.Z` cuts `vX.Y.Z-rc.1`, whose tag publishes the images and chart exactly as a stable tag does, but **deliberately publishes no Homebrew formula** (`brew.yml` trigger `["v*", "!v*-*"]` excludes any prerelease). That is correct for the *stable* `uzi-cli` formula: Homebrew users must never be silently moved onto a candidate. The gap is that there is then **no brew path to install an RC of the CLI at all**. A dogfooder who wants to exercise a candidate CLI on macOS/Linux has to `go install github.com/vtmocanu/uzi/api/cmd/uzi@vX.Y.Z-rc.N` or download from the pre-release GitHub Release. We want a first-class, opt-in brew lane that keeps stable users on stable while letting a tester upgrade to the newest RC.

## Solution

Add a **separate, opt-in** `uzi-cli-rc` formula to `vtmocanu/homebrew-tap`, alongside the existing `uzi-cli`:

- Source-built exactly like `uzi-cli` (`depends_on "go" => :build`, `cd api && go build ./cmd/uzi`, version stamped via `-X main.version=v#{version}`); the only content differences are the class name and a `conflicts_with` line.
- Tracks the **newest RC**: each `vX.Y.Z-rc.N` tag re-renders `Formula/uzi-cli-rc.rb` to that tag's source tarball. The stable `uzi-cli` formula continues to move only on stable tags.
- **Reciprocal `conflicts_with`** so exactly one `uzi` binary is active at a time: `uzi-cli-rc` declares `conflicts_with "uzi-cli"` and `uzi-cli` declares `conflicts_with "uzi-cli-rc"`. Both build a binary named `uzi`, so Homebrew keeps them mutually exclusive: `brew install vtmocanu/tap/uzi-cli-rc` while stable is present tells the user to uninstall stable first; `brew uninstall uzi-cli && brew install uzi-cli-rc` switches the active `uzi`, and the reverse switches back. The source build makes the switch cost one `go build`.
- **Dev/dogfood lane only**: no README, no `docs/*.md`, no in-app docs. The opt-in incantation lives in the `uzi-release` skill's mechanics reference so it is recoverable without being advertised to end users. `brew upgrade uzi-cli` never surfaces an RC.

### User journey

- Stable user: unchanged. `brew install vtmocanu/tap/uzi-cli`; `brew upgrade uzi-cli` only ever sees stable tags.
- RC tester: `brew install vtmocanu/tap/uzi-cli-rc` (uninstalling stable if present); `brew upgrade uzi-cli-rc` follows the newest RC; `brew uninstall uzi-cli-rc && brew install uzi-cli` returns to stable.

## Resolved facts (baked in for an offline worker)

The worker has no open-web egress; every internet-dependent fact below was resolved locally during PRD authoring and is stated as settled, not as a task.

1. **Homebrew has no same-name channel primitive.** There is no `brew install --pre`; the `devel do` block was removed in Homebrew 2.0 (2019); `--HEAD` builds from git `main`, not RC tags (and our formula ships no `head` URL). A formula is one name -> one current version. A parallel opt-in formula is therefore the mechanism, and it is what comparable tools do (a `-beta`/`-rc` sibling formula in the same tap, one active binary via a conflict). Take the idea, write our own expression.
2. **The positional `conflicts_with "name", because: "..."` form used here is current.** The deprecated one (Homebrew/brew#20575) is the *cask* `conflicts_with formula:` keyword form. Formula-to-formula positional `conflicts_with` is not deprecated.
3. **Homebrew auto-detects the version from a `-rc.N` archive URL.** Measured locally with `brew ruby -e 'Version.parse(...)'`: `.../archive/refs/tags/v0.83.0.tar.gz` => `0.83.0` and `.../v0.83.0-rc.2.tar.gz` => `0.83.0-rc.2`. So `uzi-cli-rc.rb` needs **no explicit `version` stanza** (it mirrors `uzi-cli.rb`, which relies on the same auto-detection), and `test do assert_match "v#{version}" ... end` holds: `version` = `0.83.0-rc.2`, the build stamps `v0.83.0-rc.2`, and `uzi version` prints it. This one behaviour is the single point the RC formula's version handling and `test` block depend on; it is re-confirmed by the maintainer's local SC5 install.
4. **The render mechanic is unchanged.** `homebrew-tap.yml`'s `formula`/`publish` tasks compute the tarball sha256 and substitute `@@URL@@` / `@@SHA256@@` / `@@VERSION@@` for any tag, RC or stable (`homebrew-tap.yml:93-96`); `TARBALL_URL` defaults to `https://github.com/<GH_REPO>/archive/refs/tags/<VERSION>.tar.gz` (`:73`), `FORMULA_OUT` to `dist/<NAME>.rb` (`:72`), `TAP_FORMULA_PATH` to `Formula/<NAME>.rb` (`:110`). A second include with `NAME: uzi-cli-rc` and `FORMULA_TEMPLATE: Formula/uzi-cli-rc.rb` reuses it verbatim and publishes `Formula/uzi-cli-rc.rb`; **do not edit the vendored `homebrew-tap.yml`** (it carries an upstream SHA). Note `uzi-cli.rb` uses no `@@VERSION@@` token (auto-detect), consistent with fact 3.
5. **The stable formula has no `conflicts_with` today** (`grep -rn conflicts_with Formula/` => none), so M1's reciprocal line is the first, and adding one against a formula stable-only users will not have installed is inert for them (Homebrew checks conflicts only against *installed* formulae, so naming a not-yet-published `uzi-cli-rc` is harmless).
6. **The worker toolchain covers the new offline checks.** `ruby@4.0.6` is a tier-2 package for this repo (`devbox.json:36`, added so a formula-editing run can lint), so `./scripts/lint-formula.sh` parses (>= 3.1) rather than taking its loud skip. `task brew-rc:formula` with a `file://` `TARBALL_URL` needs only `curl` (Alpine base image) and `shasum -a 256` (from provisioned perl) — the same tools `scripts/brew-local-test.sh` already exercises offline.

It stays a separate workflow from `release.yml` (a tap-push failure must not redden the image+chart release).
  - **Serialize the tap push (blocking correctness fix).** Today only stable tags trigger `brew.yml`, so exactly one run ever pushes to the tap. After this change an RC tag also triggers it, and a **promote ceremony pushes the stable tag AND an RC tag within minutes** (CLAUDE.md: push order stable tag, then main, then RC tag). The current concurrency group is per-ref (`brew-${{ github.ref }}`, `:52-54`), so those two runs are in different groups and are **not serialized**; both do a bare `git push --quiet origin main` into `vtmocanu/homebrew-tap` from a fresh clone with no pull/rebase/retry (`homebrew-tap.yml:120-131`), and can collide on a non-fast-forward push, reddening one run (which `release-watch.sh` then reports as a failed publish). Fix: give `brew.yml` a **ref-independent** concurrency group (e.g. `group: brew-tap-publish`, `cancel-in-progress: false`) so the two publishes queue. (They render/publish different formula files, so serializing is sufficient; no pull-retry needed once ordered.)
  - `.agents/skills/uzi-release/scripts/release-watch.sh` and `release-verify.sh`: an RC tag now also produces a `brew.yml` run (rendering `uzi-cli-rc`), so RC mode must wait on / verify that run instead of skipping brew, and the PRD #1265-era comments that assert "brew.yml does not run for a prerelease" (release-watch.sh `:4-5,58-60`, release-verify.sh `:44-47`) must be corrected. Bundled with the trigger change so the watcher never waits for a run that does not exist (and vice versa).

## Decision Log

- **D1 — separate formula, not a channel flag.** Homebrew has no same-name channel primitive (fact 1), so an opt-in parallel formula is the only mechanism that keeps stable users on stable. Chosen over `--HEAD` (builds `main`, not RC tags) and over publishing RCs onto `uzi-cli` (PRD #1265's explicit non-goal).
- **D2 — this does not reverse PRD #1265 M4.** #1265 froze the *stable* `uzi-cli` formula so it can never point at a candidate; that holds unchanged. #1378 adds a *distinct* `uzi-cli-rc` formula. Stable users never see an RC either way. M3 widens the `brew.yml` trigger and routes by channel rather than reintroducing the failing-on-RC behaviour #1265 removed.
- **D3 — `conflicts_with` for one active binary.** The user chose mutual exclusion (one active `uzi`) over the non-conflicting "both installed, switch with `brew link/unlink`" approach: clearer state, and the source build makes switching cheap. Uses the current positional `conflicts_with` form (fact 2).
- **D4 — dev/dogfood only; no user-facing docs.** RC is a development lane, so no README/`docs/*.md`. The incantation is recorded in the `uzi-release` skill so it is not lost, without advertising it.
- **D5 — no explicit `version` stanza.** Auto-detection handles `-rc.N` (fact 3), so `uzi-cli-rc.rb` stays a near-exact mirror of `uzi-cli.rb`.
- **D6 — M3 is maintainer-local.** The workflow-scope guardrail (`.claude/rules/prds.md`) forbids a uzi worker from touching `.github/workflows/**`; `release-watch.sh`/`release-verify.sh` are coupled to that trigger change (they must only wait on an RC brew run once one exists) and land with it, even though as plain shell a worker could otherwise push them.

## Risks

- **R1 — RC formula drifts from stable.** Two near-identical templates can diverge (e.g. a `caveats` fix applied to one only). Mitigation: M2's shared `lint:formula` over both, and a review note to apply body changes to both; the files are intentionally identical except class name + `conflicts_with`.
- **R2 — sequencing between M1-M2 and M3.** If `release-watch.sh` were taught to wait on an RC brew run before the `brew.yml` trigger widening merged, RC releases would hang. Mitigation: both live in M3 and land together; M1-M2 add no release-time behaviour (the formula + plumbing sit inert until M3 widens the trigger).
- **R3 — a user with both channels linked.** `conflicts_with` prevents installing both, but a manually `brew link`-forced state could confuse. Mitigation: the reciprocal declaration plus the M2 note; this is standard Homebrew behaviour, not uzi-specific.
- **R4 — `brew audit` cosmetics.** A prerelease `version` and a `-rc` formula name may draw `brew audit` style notes. Accepted: this is a private tap, not homebrew-core, and the sibling formulae already live there.
- **R5 — tap-push collision on a promote (blocking, addressed in M3).** The stable and RC tag pushes of a promote ceremony trigger two `brew.yml` runs in different per-ref concurrency groups; both push to the tap's `main` with no rebase/retry and can non-fast-forward one to red. Mitigation: M3 serializes `brew.yml` with a ref-independent concurrency group. Until M3 lands this cannot occur (M1-M2 do not change the trigger).
