# PRD #1416: Rewriting a published run branch is doomed and only discovered at finalize

- **Issue**: #1416
- **Priority**: High
- **Surfaces**: worker (`agent/src/runner.ts`, `agent/src/git.ts`, `agent/src/prompt.ts`, `agent/src/steering.ts`, both executors `agent/src/sdk-executor.ts` and the Codex executor), api (`api/internal/workersvc/failorigin.go`, one goose migration widening `runs_fail_origin_check`), docs (`docs/github-bot-setup.md`, `docs/cli.md`, the CLI skill source), one ADR. - **Guardrail**: nothing here touches `.github/workflows/**` (`.claude/rules/prds.md`). **No protocol field is added or changed** (D8): every mechanism is worker-local over data the worker already holds; the only new value on the wire is one `fail_origin` string in a field the terminal report already carries and the api already coerces.
- **Landing order**: **after PRD #1247 M5 merges** (it reworks `git.ts`, `runner.ts` and `steering.ts` around the credential-switch capture/release, which M3 must run ahead of), **before #1390 and #1393 are dispatched**. - **Origin**: task run `52fe0e79` (2026-09-16), the review rework of PR #1397. All ten milestones committed and gated green, `signal_done` recorded, run ended `failed`. Root cause and recovery facts below; the design was brainstormed with a peer session and every load-bearing claim re-read from `main` at `0da47d5b`.

## Problem

A run's branch is often **already published** on the forge before the agent starts: `uzi handoff` pushes the user's HEAD to `uzi/task/<run-id>` and only then dispatches; an mr_rework run works on an existing MR branch; a resumed run continues a branch its first finalize pushed; a self_improve run has a fixed branch. The worker lands the agent's work with a **plain fast-forward push** (`git.ts pushBranch`) and never force-pushes: force is denied by the guardrails, by the bot's role, and by design. Three things follow from that, and none of them is visible to the agent today:

1. **Nothing tells the agent.** The prompt says "commit your work locally on the branch (never push)". The guardrails deny force flags and `push`, not `rebase`, `commit --amend`, `reset` or `filter-*`. The plan gate does not react to a plan that literally says `git rebase --onto`.
2. **Nothing detects a rewrite until finalize.** Run `52fe0e79` was seeded from `agent/issue-1247` at `59dee00e`, published as `uzi/task/52fe0e79…`. Its own plan, milestone m1, rebased the 23 published commits, recording the assumption "the rebase is a local history operation; the worker performs the push at finalize". From about 06:00 UTC the run was unlandable; finalize found out at 11:03. Because a Renovate bump to `ci.yml` had landed on `main` mid-run, the push took the workflow-align path: the overlay aligned, its push was rejected non-fast-forward, merge and rebase both conflicted with `c1d867a1` (the same protocol files), and the run failed **`finalize_base_align_conflict`**, which names the wrong cause. Without the `ci.yml` drift the plain push would have hit the same rejection and, for a task run, rethrown into the **generic catch**: `failed`, a raw git error, **no `preserved_patch`**.
3. **A park after a rewrite sets the work aside.** The same-run reseed (`git.ts runnerCloneForBranch`, fact 11) prefers the recovered tracking tip only when it strictly descends from `refs/remotes/origin/<branch>`; on divergence origin wins. So a pause, a limit park, a shutdown roll, or a #1247 credential switch after a rewrite resumes the agent on the **published** tip: the rewritten commits stay in the tracking ref and the capture, but the run continues without them. A rewrite followed by `signal_done` in the same turn also skips every checkpoint between the rewrite and finalize (fact 13), so prevention alone cannot be the mechanism.

The work was recoverable (the #1296 capture and the preserved patch both held `707464cf`), but the run counted as failed for the wrong reason, recovery took a human session, and landing became a hand merge. Three earlier runs in the same PRD chain failed for three different reasons; this is the one uzi could have turned into a completed run.

## Solution

Prevention, detection, and a non-destructive repair, all inside the worker:

1. **Tell the agent the fact** (M1). When the branch exists on the forge at claim, the worker records the published floor **P** and both prompts (plan and implement) name it with the rule: fast-forward only, never rewrite at or below P, integrate the default branch with `git merge`.
2. **Detect early and steer** (M2). Every time the runner tip enters the worker bare (`fetchAgentBranch`, on the checkpoint cadence and before every park, release, capture and finalize) the worker tests ancestry of P and of the latest confirmed checkpoint floor **C** against the fetched tip **H**, tri-state (ancestor, divergent, unknown). On *divergent* it posts a `status` run message and hands the agent a **worker-authoritative safety steer** consumed by both executors at their next loop top. It never blocks a git command (D2).
3. **Bridge instead of fail** (M3). At every publication boundary a divergent H is wrapped: a worker-synthesised commit **B** whose tree is exactly H's tree and whose parents are H plus every missing floor (P, and C when it is not reachable), the two-parent form being `git merge -s ours P` built with `commit-tree` on a temp index (the checkpoint overlay's technique, fact 12). B preserves H byte-for-byte, keeps both histories, and **fast-forwards from P without force**. Bridging runs before any capture or release (so a park never sets H aside), at finalize before the align chain, and after the align rebase fallback (which itself rewrites P, fact 14). Steer stays prevention; the bridge is correctness.
4. **Fail honestly when bridging is impossible** (M4). If B cannot be built or validated (tree equal to H's, P and H both ancestors), the run fails typed **`history_rewritten`** with `preserved_patch`, on both push paths, never `finalize_base_align_conflict` and never the generic catch. A non-fast-forward rejection of a valid B is concurrent branch movement, not a rewrite, and keeps its own classification. `push_secret_blocked` keeps precedence (fact 15).
5. **Nudge at the plan gate** (M5). A plan proposing `rebase`, `--amend`, `filter-repo`/`filter-branch`, `reset --hard` or a forced push on a branch with a published floor gets a visible `status` line next to the plan; on an auto-approved run the steer is queued for the first implement turn.

### User journey

- A maintainer runs `uzi handoff` on a reviewed branch: "rebase onto main, then fix the eight findings". Today the run does everything and fails at push. After this PRD the plan prompt names P; the plan proposes `git merge` and lands. If the agent rebases anyway, within one checkpoint interval the run log reads "history rewritten below published tip 59dee00e; steering the agent", the agent pins its tip and restores P as an ancestor (`git merge -s ours <P>`), finalize fast-forwards. If the agent ignores the steer, finalize bridges and pushes anyway; the MR carries a one-line note that the branch was bridged and `git log --first-parent` still reads as the agent's rewritten history.
- A rewrite followed by a pause: the worker bridges before the capture, the reseed adopts B (it descends from P), the agent resumes on its own work.
- Only when the forge rejects B too (the branch moved under the run, or the object cannot be built) does the run end `failed` / `history_rewritten`, reason naming P and the recipe, diff preserved, capture available.

## Resolved facts (baked in for an offline worker)

Read from `main` at `0da47d5b` or measured on run `52fe0e79`; every code fact re-verifies offline.

1. **The finalize push is a plain fast-forward push.** `agent/src/git.ts pushBranch` runs `git push origin refs/uzi-runner/<branch>:refs/heads/<branch>`, no force flag. Force-push is denied unconditionally by the guardrail `push` rule; `FORCE_DENY_SUBCOMMANDS` in `agent/src/guardrails.ts` lists only `checkout`, `switch`, `restore`. `rebase`, `commit --amend`, `reset`, `filter-*` are not denied.
2. **The claim-time forge tip is in the worker bare.** `git.ts originBranchTip(barePath, branch)` reads `refs/remotes/origin/<branch>` without fetching (issue #1117 uses it at the mr_rework finalize); `null` when the branch did not exist at clone. This is **P**. It must be recorded once at claim, as runner-level state that survives an executor restart (the agent session restarted several times inside `52fe0e79`), and never taken from `RunnerClone.baseCommit`, which can point at unpublished recovered work.
3. **The runner tip enters the bare through one seam.** `fetchAgentBranch(barePath, clonePath, branch, runId)` writes `refs/uzi-runner/<branch>`; callers: finalize (`runner.ts` ~1970), the checkpoint fetch-back `fetchBackBestEffort` (~4704, driven by `CHECKPOINT_INTERVAL`, `agent/src/config.ts:339`, default `20m`, `0` disables), the park path (~877, ~1022), `captureRecoveryRestorePoint` (~5575) and `captureHoldContext` (~5793). Every ancestry check and every bridge hangs off this seam, in the bare only: a worker-uid git against the runner clone crosses the ownership seam the code already avoids (`branchTip` reads the clone as the runner uid for exactly that reason).
4. **Today's typed finalize failures and where the rewrite falls through.** The #377 guard (~2295) fails `workflow_scope_missing` when the branch touched workflows. The align chain (~2560 to ~2820) handles "behind on workflows": overlay (#627) then merge then rebase; each rejected push, including the non-fast-forward arm (~2774), routes to `failBaseAlignConflict` (typed, `preserved_patch = workflowScopeDiff(bare, originalAgentTip)`). The plain push (~2848) types only GH013 and, for `kind === "mr_rework"`, a non-fast-forward as `branch_moved` (#1117), then `throw e`. `agent/test/runner-base-align.test.ts` case (g) pins the align-path non-ff; nothing pins the plain-path non-ff.
5. **The fail-origin vocabulary is closed and pinned.** `api/internal/workersvc/failorigin.go` lists thirteen values; `workerReportableFailOrigins` decides what a worker may report (`CoerceFailOrigin` drops the rest); `runs_fail_origin_check` was last widened in `00232` (DROP + ADD, the `00186` template); `TestFailOriginVocabularyMatchesCheck` parses the newest migration's CHECK and is number-agnostic since #1410. `failure_reason` is free text, intentionally never parsed.
6. **The prompt carries no publication fact.** `ImplementPromptInput` (`agent/src/prompt.ts:1083`) has `branch`, `baseCommit`, `defaultBranchCommit`, `priorWork`; `PlanPromptInput` (`:949`) likewise; the only push guidance is `:1271`. The resume notice (`:589-611`) is the pattern for a branch fact rendered from a worker-verified number. The default branch **name** is repo-controlled text and must not be rendered (`:725`); refer to "the default branch" and its SHA (`defaultBranchCommit`).
7. **Follow-ups are server inputs.** `SteeringChannel` (`agent/src/steering.ts`) routes server `follow_up` inputs, each with a real input id that advances the `open_followup_id` wake-guard watermark (~394-417), into a queue drained by `pullFollowUp()` at the executor loop top; the executor renders a follow-up as **untrusted** user input inside `<follow_up>` (`prompt.ts` ~1122, ~1260). A worker-originated message must not travel that channel (D3).
8. **The #1247 credential-switch trip aborts the turn and releases the claim.** Not a steer channel either (D3).
9. **Codex has no hooks.** `agent/src/codex/config.ts` sets `hooks = false` in the production Codex config, so a PostToolUse hook is Claude-only and cannot be the detection mechanism (D1).
10. **The plan gate is worker-side.** `runner.ts gatePlan(planMd, milestones, onAwaitingApproval)` (~5958); auto-approve short-circuits (~4095). A `status` run message is the existing worker-to-human channel (`batcher.emit({kind:"status", agent:"worker", …})`).
11. **The same-run reseed sets a diverged tip aside.** `git.ts runnerCloneForBranch` (~786-793): when this run owns the tracking ref and `refs/remotes/origin/<branch>` exists, the tracking ref is adopted only if `merge-base --is-ancestor origin tracking` holds; on divergence the clone is seeded from origin, `seededFrom = "origin"`. A rewrite followed by any park therefore resumes without the rewritten commits unless they are bridged first.
12. **Multi-parent wrapper commits already exist.** `git.ts buildWorkflowOverlay` (~1594-1714) builds a transport wrapper with `read-tree` into a temp index, `write-tree`, then `commit-tree` with several `-p` parents, deterministic identity and dates, worker-uid, no PAT, no working tree. The bridge B reuses that technique with H's tree unchanged.
13. **A same-turn rewrite plus `signal_done` skips the checkpoint.** The SDK executor handles `signal_done` inside the frame that carried it (`agent/src/sdk-executor.ts` ~2463-2530); the next checkpoint fetch-back never runs before finalize. Detection at finalize and the bridge are therefore mandatory, the mid-run steer is not sufficient.
14. **The align rebase fallback rewrites P too.** A rebase-aligned branch replays the agent's commits onto the default (`git.ts alignBranchWithDefault`, rebase arm), so on a published branch its push is rejected non-fast-forward today (test case (g), `git.ts` ~3572-3580 doc). With the bridge applied to the rebased result, that fallback becomes landable.
15. **The pre-push secret scan floor fails open on divergence.** `git.ts` (~2213-2272): the floor is the fresh remote tip only when it is an ancestor of the tracking tip; a diverged remote returns `null` and the worker relies on the GH013 remote backstop. After bridging, P is an ancestor of B and `P..B` is the real, scannable push delta. `push_secret_blocked` must keep precedence over `history_rewritten`, and a `preserved_patch` is written only from a range the scan trusted.
16. **Measured on `52fe0e79`.** Seeded 05:05 UTC (plan auto-approved), m1 rebase about 06:00, `signal_done` 11:03:22, finalize status lines 11:03:24 and 11:03:27, `finished_at` 11:03:27.30, `preserved_patch` 523 342 bytes, capture `134bedd6` created 11:03:27.97 with `source_sha = 707464cf`. `git log 4f4fb383..707464cf -- .github/workflows/` is empty, so the overlay was eligible and its push could only have been rejected non-fast-forward. `59dee00e` is not an ancestor of `707464cf`.
17. **Which runs have a published floor.** Any run whose branch exists on the forge at claim: task (seeded by `uzi handoff`, `api/internal/handler/runs_lifecycle.go` ~197), mr_rework, self_improve, ci_fix on an existing run branch, and every resume of a run whose branch was pushed. Keyed on **P being non-null**, never on run kind. `refs/uzi-checkpoints/<branch>` is uzi-owned transport and is **not** a published floor for this rule.

## Decision Log

- **D1 — Detection is worker-local, bare-only, at the fetch-back seam.** Both floors and the tip are refs in the worker bare (facts 2, 3); one `merge-base --is-ancestor` per fetch-back costs nothing and bounds detection at `CHECKPOINT_INTERVAL`. A PostToolUse hook would be same-turn but Claude-only (fact 9) and would need a runner callback from inside the SDK process; progress reports are fire-and-forget metadata, not graph boundaries. Rejected.
- **D2 — Steer, never deny.** A rewrite wholly above P is valid and routine; command parsing cannot prove the affected range without replicating the ancestry check. No `rebase`/`amend`/`reset` denial. But "steer only" is insufficient (facts 11, 13): unresolved divergence must not reach a release or a push, which is what the bridge guarantees.
- **D3 — A distinct worker-authoritative steer channel.** Follow-ups carry server input ids, advance the wake-guard watermark and render as untrusted user text (fact 7); the credential-switch trip aborts and releases the claim (fact 8). Synthesising either would corrupt their semantics. The `safetySteer` slot is consumed by both executors ahead of any follow-up and rendered as worker guidance.
- **D4 — Bridge, do not fail, when history diverged.** B has H's tree exactly and both H and P as parents, so it fast-forwards from P without force, loses nothing, and keeps `--first-parent` history readable as the agent's. Applied before capture/release (fact 11), at finalize before the align chain, and after the align rebase fallback (fact 14). A bridged branch's MR says so in one sentence; a squash-merge collapses the doubled lineage anyway. `history_rewritten` is reserved for a bridge that cannot be built or validated; a valid B rejected non-fast-forward is concurrent branch movement and keeps that classification.
- **D5 — The plan-gate nudge is a regex over `plan_md`, warn-only, false positives accepted.** A plan is prose; one spurious status line costs nothing; a false negative is caught by M2/M3.
- **D6 — A new fail origin, not a reworded existing one.** `finalize_base_align_conflict` is factually different, `agent_failure` is the catch-all the dashboard and the judge triage on, and `failure_reason` is never parsed (fact 5). Cost: two list entries and one migration in the established template.
- **D7 — The fact is a worker-verified SHA, never text the agent infers.** Same rule as `priorCommits` (fact 6); the default-branch name stays out of the prompt.
- **D8 — No protocol change.** Everything runs inside the worker over data it already holds. This keeps the PRD clear of #1247 M5, #1390 and #1393, which all edit `protocol.ts`.
- **D9 — `--force-with-lease` restricted to `uzi/task/<id>` rejected.** Not because a correctly scoped force would touch `main` (it would not), but because it adds a destructive publication path to the worker, the single-writer namespace assumption does not hold for mr_rework, resumed issue or self_improve branches, and the bridge makes force unnecessary. Revisit only if M7 shows bridged histories are unacceptable to reviewers.
- **D10 — Outcome class is out of scope.** A run that could not publish its output failed, whatever its gates said; PRD #1293 counts it as such on purpose. A "needs landing" presentation bucket derived from `fail_origin` plus capture availability is a separate, smaller issue (#1418).

## Risks

- **Bridged history reads oddly in the forge's commit list** (both lineages visible until squash). Mitigation: the status line and the MR sentence explain it; `--first-parent` stays clean; D9 revisit criterion.
- **The steer lands at a loop top, not mid-turn.** A long subagent wave delays it; the bridge covers the gap, so the cost is a bridged history rather than a lost run.

This makes the note survive a claim release/reclaim, where flight state is gone but pushed history is not. See [ADR-1416](../adr/1416-published-branch-rewrite.md) for the full decision record.
