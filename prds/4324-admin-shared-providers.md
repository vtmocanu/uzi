## Problem and outcome

An operator should define a Claude gateway URL, supported auth style and model map once, while each user supplies and controls their own credential. This PRD delivers that one outcome: admin-owned shared definitions with `per_user_key` custody, usable by all users. User-owned providers continue unchanged.

Organization-funded `operator_key` mode is a separate child PRD and issue (#4540) blocked by #4324. It is not a hidden milestone or an entry dependency here. The #4323 M1 dependency is for sequencing and the common schema. This PRD enables shared definitions only for Claude. #4633 is the Codex shared-definition follow-up.

Acceptance examples:

1. An admin creates a shared definition. B attaches an enabled personal key, tests and selects it; B's new Claude run uses that key with the shared definition's frozen revision, never a vendor credential. C without a key gets the existing HTTP 409 response with reason `provider_source_unusable` and a human message explaining the missing key (internal cause `key_missing`); no new HTTP field or error vocabulary is introduced.
2. B's successful Test and C's failed Test remain separate; B never sees C's key or Test evidence. Rotating B's key makes old-key results unknown, and a delayed old result cannot overwrite current-key evidence.
3. A user can edit only their own attached key, Test it and select/clear the source. User provider PATCH/endpoint/retire/delete routes cannot mutate a shared definition, including for an admin using those owner routes. Shared-definition mutation is through cookie/CSRF admin routes only.
4. Removing a shared definition selected by any user is refused with `provider_in_use_as_source`. Retirement stops fresh selections/runs, preserves the selected source as unusable and never silently selects vendor spend. Existing frozen claims/retries retain #4320's retire versus revoke semantics.

## Design

### Catalogue and immutable definitions

Use `model_providers.owner_user_id IS NULL` for a shared definition. The database scope column described below encodes owner identity for a composite FK. Add `credential_mode`, with both `CHECK ((owner_user_id IS NULL) = (credential_mode IS NOT NULL))` and `CHECK (credential_mode IN ('per_user_key'))`. Constrain shared definitions to the Claude engine in this delivery with a named CHECK `(owner_user_id IS NOT NULL OR engine = 'claude')`; an admin create with engine `codex` is refused with a 4xx and writes no row, and #4633 relaxes the CHECK. (The 00517 `users_codex_provider_fkey` composite owner FK can never match a NULL-owner row, so a shared definition also cannot become a Codex source.) Existing user-owned rows retain non-null owner and null mode. Ownership and credential mode are immutable after creation. Shared per-user definitions also fix base URL and auth style at creation: later admin edits may change name and model map only. A new endpoint/auth style requires a new definition and explicit user selection/key attachment, avoiding silent personal-key repointing. Existing user-owned endpoint editing remains unchanged.

Shared names are case-insensitively unique in their own namespace. Build the partial `lower(name)` index for NULL-owner rows with the repository's separate `NO TRANSACTION` concurrent drop-and-rebuild pattern. Serialize shared create/count decisions under one bounded catalogue transaction lock, enforcing the 50 shared-definition cap across admins, including retired definitions. User-owned quotas and names remain separate. List/get show credential mode. Only admin reads show selected-user and attached-key counts.

### Referential integrity and authorization

The current source FK (00479) and provider-key FK (00477) both bind provider references to the same owner. Retain database enforcement when admitting a shared reference:

- Keep `model_providers.owner_user_id` as the ownership authority. Add `scope_owner_id uuid NOT NULL`, with `UNIQUE (scope_owner_id, id)`, `CHECK (scope_owner_id = COALESCE(owner_user_id, nil_uuid))` and `CHECK (owner_user_id IS NULL OR owner_user_id <> nil_uuid)`. Here `nil_uuid` denotes the all-zero UUID literal cast to `uuid`. Verify no personal owner uses it before backfill. Set the scope at provider insertion and keep it immutable.
- Add nullable `user_secrets.provider_scope_id` and `users.claude_provider_scope_id`. The constraint must require either both ID and scope NULL, or both non-NULL with scope equal to the referencing user ID or the shared sentinel. Include explicit NULL checks so SQL's UNKNOWN cannot pass a partial reference. For `openai_compatible_key`, require the user's own scope. Only eligible Claude recipients can select or attach a Claude shared key. Replace the named key and Claude-source FKs with composite `(provider_scope_id, provider_id)` and `(claude_provider_scope_id, claude_provider_id)` FKs, respectively, to the new parent key. Preserve CASCADE for keys and RESTRICT for source selection. Keep `users.codex_provider_id` and its composite owner FK intact.
- Personal reference backfills use their existing owner IDs and leave keys, revisions, selections and ciphertext intact. Provider-key INSERT and Claude-source set/clear write the scope and ID together. Keep the landed engine/kind validation and provider-key uniqueness for both kinds: at `814b485c`, `InsertProviderKeySecret` (`model_providers.sql` around L135-148) derives the key kind from the provider's engine, and the vault AAD must keep matching that kind; 00515's `provider_key_check` admits both kinds, and 00514/00519 stay as they are. Keep `model_providers_owner_id_key` (00476): it is the parent key of 00517 `users_codex_provider_fkey`, so never `DROP ... CASCADE` it. The key-FK Down restores 00477's definition under the same name and leaves 00515's checks unchanged. Stage additive columns, bounded backfills and concurrent uniqueness where needed. Use short lock bounds, drop and re-add each FK under the same name in one ALTER, use NOT VALID, then validate separately. The API is a hard singleton with Recreate and Goose runs at boot before serving requests (`deploy/README.md` L77, “hard singleton”, and `api/cmd/server/main.go` L223, `store.Migrate(ctx, migrationDSN)`). This deployment already prevents old API writers from racing the migration. Prove the old-schema upgrade and provider, source and key writes after boot.
- Guarded Downs lock affected tables before checking. Refuse if shared selections, attached shared keys or NULL-owner definitions remain, before restoring owner-only FKs or setting owner NOT NULL. Never clear sources for fallback, reassign ownership or delete key custody automatically. The Downs are LiveDB-tested schema guards. Production has no operator Down path, and `store.MigrateDownTo` is used by tests.

- **Image-only rollback:** the owner chose to document the rollback behavior. This delivery adds no compatibility trigger. Older API writes omit the new scope fields, so provider creation, key attachment and Claude source set/clear fail closed. This includes personal-provider users clearing their source back to vendor. Key disable/delete and provider retirement remain available stop levers for rows the older API can address. Shared selections can return `provider_missing` and shared bindings can become stale. Pause or cancel affected runs before rolling back. Recover write access by re-upgrading. Per engine, on the older post-#4323 image, Codex source set/clear still works: the Claude scope pair is untouched and the 00517 FK is unchanged. Provider creation and key attachment fail closed for both engines. Pin this in the rollback test.
- **Migration seams:** M1 replaces no placement or claim SQL function. At `814b485c` the `fn_placement_admitting_workers` head is 00521; its provider clause, ClaimRun's clause (`runtime.sql`, around L1533) and the wake/reap predicates check capability only. If one of them must change, that is a plan change: its Up extends the live definition at landing (preserving the merged Codex clauses) and its Down restores that exact immediate predecessor byte for byte (00521 at `814b485c`).

### Per-user Test evidence and probe snapshot

Use a new Test evidence table and keep the legacy `model_provider_probe_results` table, including its `(provider_id, revision)` conflict target, for older APIs. Store at most one row per `(provider_id, user_id)`, carrying the captured provider revision, key secret ID and key revision. Use cascade FKs for provider, user and exact revision/key references. The key FK is `(user_id, key_secret_id) REFERENCES user_secrets(user_id, id) ON DELETE CASCADE`, backed by `user_secrets_user_id_id_key` (00077). Capture the tuple before the probe. On completion, conditionally upsert only if the caller, visibility, current provider revision and current key identity/revision still match, with the provider-before-key order. Readers expose only that exact current tuple. Rotation or an edit makes old evidence unknown, and a late response cannot overwrite current evidence. Discard legacy provider-wide cache rows at migration while preserving the old table shape, so existing personal definitions initially show “not tested.” Down drops the new cache table. Preserve existing probe time, rate and concurrency limits.

Retain #4320's consistent endpoint/key snapshot protection before dialing. A key rotation between provider-row read and secret-open refuses before sending new material to an old endpoint. An old-key/old-endpoint request already authorized at its final pre-dial check may finish; this is not instantaneous revocation.
