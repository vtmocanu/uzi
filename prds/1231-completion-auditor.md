## Problem and outcome

Structural coverage cannot determine whether arbitrary acceptance criteria are truly satisfied. A lead can declare every milestone while part of one remains missing, as PR #1220 did for M3. Plan-time source coverage improves the contract but does not judge the final implementation.

Run a separate read-only completion auditor against the entire frozen semantic contract and exact final evidence head. Gate evidence must be independently reproduced or captured with provenance. A semantic permit requires every in-scope worker criterion satisfied or exactly owner-accepted. Evidence/head drift, auditor outages and pass/cost caps hold the authoring run rather than losing it; an outage exits through an owner-triggered retry under the remaining budget or cancel-and-rerun.

## Included

- A production bounded advice transport for both harnesses, shared by coverage review and the audit (M0).
- Read-only, tool-less completion auditor isolated from the lead session, built on the advice-lane primitive through that transport.
- Trusted server contract/source payload and untrusted repository-data treatment.
- Plan-declared gate commands frozen at approval, executed by the worker at the exact head, with re-execution only as the fallback.
- A deterministic, worker-built evidence packet with a fixed input budget.
- `satisfied|unsatisfied|unverified` per-criterion results.
- At most two verdict-bearing full-contract audits per run; no incremental audits.
- Concrete audit wall/token/pass ceilings and recovery behavior.

- Default-on instance semantic enrollment for new eligible issue runs; explicit admin kill-switch and instance-admin model/cost ceilings frozen per run. No per-repo override at launch.
- Creation-time frozen profiles, hard capability routing and named queued health during version skew; no live-fleet default selection or automatic downgrade.
- Web/CLI audit, evidence, head and cost visibility.

## Decisions

### D1: Audit in one tool-less read-only turn

The auditor runs in the trusted worker process using the owner's provider credential but no lead transcript, tools, edit capability or write-capable agents. It is one tool-less, repo-isolated, wall-capped `runReadOnlyModelPass` (`agent/src/model-pass.ts`) turn, not a new harness/loop, invoked only through M0's production bounded transport. `AdviceRequest` labels are `judge | review | summary | now | coverage` (#1230 added `coverage`); add `audit`. Validate output with a strict bounded schema validator in the style of #1230's `validateCoverageReport` (`agent/src/plan-contract-report.ts`). Schema failure consumes the single D4 retry; a second failure holds `audit_unavailable`. Server-frozen contract identity is authoritative; source/evidence text is untrusted requirements/evidence data, not executable instructions. A repository `satisfied` assertion is not proof.

The evidence packet is built deterministically by the worker, never by the model: a complete diff manifest (every changed path with stats), bounded criterion-linked patches and context, gate evidence summaries and artifact digests. Raw multi-megabyte gate logs are never sent. The prompt is ordered contract and source snapshots first, packet last, which maximizes provider-cache eligibility for a second pass; the primitive does not guarantee a cache read and no budget assumes one. The builder targets a fixed input budget; a criterion whose linked context does not fit returns `unverified` with reason `context_truncated`, visible in the UI, never a silent trim to `satisfied`. Audit cost therefore scales with the diff and the criteria count, not with implementation wall time.

The worker remains the trust boundary because it holds the PAT. Independence protects against lead assumptions and prompt history, not worker compromise.

### D2: Plan-declared gates, executed by the worker and bound to the head (AI-synced 2026-10-22)

Lead prose about gate output is unverified. Gate commands are declared in the semantic plan proposal and frozen at approval with the contract. Each declaration carries structured argv (no shell string), a repo-relative cwd, a timeout, a gate type (`test|lint|build|other`) and the criteria it evidences. Proposed criteria carry no ID (`ProposedSemanticCriterion` in `api/internal/apitypes/semantic_plan.go`; the server mints IDs after validation), so a declaration names its criteria by bounded proposal-local references into the same proposal. The server resolves every reference to the canonical server-minted criterion ID before candidate hashing, Plan cross-check review and approval, and rejects the proposal on a foreign, ambiguous or unresolved reference. The lead never mints an authoritative ID. The resolved declarations extend #1230's semantic proposal and candidate identity under a new candidate identity version, so the candidate digest, the Plan cross-check payload and exact owner approval all bind them. Structural candidates and stored contracts are unchanged.

Coverage review assesses whether the declared gates meet the source requirements. A lead's declaration alone cannot certify completeness: missing or insufficient gates for a requirement are coverage uncertainty under #1230 D3 and take the human gate. Repository configuration (a Taskfile, a package script) may inform the lead's proposal but is not a second authority.

The worker executes each frozen declaration itself through the existing isolated runner boundary (the runner uid, as `launchRunnerCommandRoot` in `agent/src/codex/launcher.ts` and `spawnDetached` in `agent/src/sdk-spawn.ts` already use), without worker credentials (no PAT, provider token or join token in the environment). It captures output outside the repository and binds the artifact to the frozen declaration identity, argv, scrubbed-environment policy, committed head, clean-tree fingerprint, exit status, timing, completeness/truncation markers and digest. Generic shell output and lead-run commands are not evidence. A positive test count is required for `test` gates only. Current `gatesUnverified`/`gatesDiscoveryTruncated` fields describe dependency discovery, not gate results.

Re-execution is the fallback, not the default: the worker reruns a gate only when its captured artifact is missing, corrupt, incomplete, does not match the frozen declaration or is head/tree-mismatched. Re-execution runs under the declared timeout and is excluded from the audit wall cap in D4, which covers model invocations only.

There are no incremental audits. A full-contract audit runs when a structurally complete candidate is claimed at a given head. If it rejects, the same lead reworks once; rework or an evidence refresh changes the reuse key, and then the second full audit runs. A completion attempt reuses the standing verdict, and issues no new audit, only when its reuse key is identical: contract revision, exact head, clean-tree fingerprint, evidence-packet digest (gate artifacts included), audit protocol version and the frozen model/config. New evidence at the same head is a new key and permits a new audit, within the pass cap. Every permit requires a full-contract audit at the exact evidence head; file overlap alone never carries a verdict. The single exception to the identical-revision rule is D4's exact acceptance transition, which changes no criterion, gate, head, packet or configuration.

### D3: Handle late ADR-456 head drift through recovery

Keep alignment in `phasePublish` (`agent/src/runner.ts`, after the permit is obtained): when the branch's workflow subtree differs from the freshly fetched default tip, it overlays the default's workflow subtree, with merge and rebase as fallbacks. If the semantic evidence head differs after the GitHub-only ADR-456 workflow-tree alignment, do not reuse the audit. Publish a new checkpoint for the aligned tip, preserve the tree/session, and enter `recovery_wait` with `recovery_wait_cause='base_aligned'` and zero/minimal delay. The cause widens `runs_recovery_wait_cause_check` and `recoveryWaitCauses` (`api/internal/workersvc/forgepark.go`), is sent only behind a negotiated API feature (older APIs reject an unknown cause with 400), and does not bump `recovery_wait_count` or provider-outage backoff. Resume the same run/session, rerun gates on the aligned tree and require a new signal/audit. The second alignment should be a no-op.

This is an automatic recovery, not an owner acceptance question. Secret-scan/finalization failures retain existing typed behavior.

### D4: Bound cost without accepting uncertainty

Missing results, skipped gates, truncated discovery, truncated packet context and non-worker evidence are unverified. Auditor transport or schema errors get the initial call, one retry, then the `audit_unavailable` hold: no `recovery_wait` loop and no further automatic recovery, and they never ask the owner to waive an outage.

The ceilings are concrete instance defaults, configurable by the instance admin and frozen at run creation. Per-repo/user ceiling overrides are deferred, not silently introduced as required opt-in:

| Bound | Default |
|---|---|
| Model | `sonnet` (or the provider's balanced equivalent), medium effort where supported |
| Wall | 5 minutes per model invocation; 10 minutes aggregate model-invocation wall per run (fallback gate re-execution is not included) |
| Passes | two verdict-bearing full audits maximum per run |
| Retry | one automatic transport/schema retry per audit attempt; it does not reset wall or token budgets, and owner-triggered attempts share the same immutable aggregate wall/token budgets |
| Tokens | 100,000 normalized provider tokens total across completion-audit calls, counting uncached input, cache read/write and output; 4,000 output tokens maximum per verdict |

Every bound is enforced server-side through an audit reserve/settle ledger mirroring #1230's coverage `reserve`/`settle` routes (`/api/worker/runs/{id}/semantic/coverage/reserve|settle`), never a worker-local counter. The ceilings are stored in a versioned extension of `apitypes.SemanticPolicy` inside `semantic_planning.enrollment`.

Both consumed and remaining bounds are visible on the feed. Holds use the existing completion hold (`SetRunCompletionHold`) with `hold_reason='completion_blocked'` unchanged, plus a new typed `completion_hold_cause` (`audit_cap|audit_unavailable`) the worker sends behind a negotiated API feature. Keeping `hold_reason` unchanged preserves the owner-resume refusal, sweeper exclusions and `DecideCompletion` routing that key on `completion_blocked`.

Pass/wall/token exhaustion holds with cause `audit_cap`; no automatic loop. The owner may `accept` exact named unverified criteria under M4's semantic accept extension, or cancel/re-run; `continue` cannot repair an exhausted frozen cap and is refused there. Admin ceiling changes affect future runs only; no run top-up is added. Transport/schema retry exhaustion without a verdict holds with cause `audit_unavailable`, not a semantic finding. Its exits are a new owner decision `retry_audit` on `POST /api/runs/{id}/completion/decision` (one initial-call-plus-one-retry attempt under the remaining immutable budget), or cancel/re-run. `retry_audit` is valid only for `audit_unavailable`; exhausted remaining budget becomes `audit_cap`. `accept` and `continue` are refused on `audit_unavailable`: no verdict names criteria and acceptance is never an outage waiver. No cap turns unmet/unverified into satisfied.

**Exact acceptance transition.** An owner `accept` bumps the contract revision, which would otherwise break D2 verdict reuse and, at an exhausted pass cap, strand the run. The server therefore validates a narrow transition instead of rerunning the model. The accepted revision records the original audited revision and full D2 reuse key and binds them to the resulting decision revision. Between the two revisions only the accepted-criteria set may differ, adding exactly the named worker-kind criteria that the bound verdict reported `unverified`. The criteria, gate declarations, head, tree fingerprint, packet digest, audit protocol version and frozen model/config must all be unchanged. The permit then treats the bound verdict as current for the decision revision: accepted criteria count as owner-accepted, every other criterion still needs `satisfied`. Any other change between the revisions (including a second unrelated owner decision) breaks the binding and needs a new audit within the pass cap. `unsatisfied` criteria are never acceptable; they require rework or cancel.

The expected cost of the happy path is one sonnet turn over a bounded packet, on the order of minutes and low single-digit dollars; a run that consumed five hours of implementation does not earn a proportionally long audit.

A provider safety-policy refusal on a tool-less audit advice pass is `audit_unavailable` under D4, not a #3068 lead refusal, automatic harness switch or semantic waiver. Coverage advice refusal separately follows #1230 D3. Preserve the advice lane's authority boundary.

### D6: Default-on instance policy, explicit rollback and bounded spend

#1230's compiler/reviewer stays production-unreachable until this child activates coverage and audit together. Add instance `semantic_completion_rollout`, code default `true`, no preseeded false rows, editable through the existing admin settings surface. An explicit admin `false` is the emergency kill-switch for new runs, not removal of stored contracts. Admin model/effort and coverage/audit ceilings freeze per run. No repo setting, column, override write seam or owner ceiling controls ship at launch; those are deferred. If a later override is justified, nullable/absent must mean inherit, and it cannot defeat an admin disable; do not create false default rows.

Eligibility remains the shipped structural enrollment domain: new unseeded, non-interactive issue runs on both harnesses with the structural rollout enabled. Preserve seeded/legacy exclusions and explicit structural disable. In that domain semantic is default-on, not a hidden per-repo opt-in. A known explicit semantic disable selects structural without semantic model calls for new runs only. Both rollout keys resolve from one settings snapshot; a key set by ENV overlay counts as known. When that snapshot cannot be read and no valid cache exists, creation of an unseeded issue run is refused with a typed retriable error. This deliberately supersedes #1626's cold-read-as-legacy fallback for that domain once #1231 ships; seeded and non-issue creation paths are unchanged. A failed refresh over a valid cache uses the cached values for both keys.

The refusal contract is `semantic_policy_unavailable`, HTTP 503 with a positive `Retry-After`, and no run/row created. Manual CLI/web creation shows the retriable error without an automatic client retry loop. Scheduler handling reuses existing patterns, with no new retry engine. A single-issue fire (once or recurring) is held un-advanced like the credential-disabled once hold. The `semantic_policy_unavailable` skip is recorded through the held-fire last_fire write, deduplicated, and the fire retries on the next tick. A sweep stops its fan-out at the first refusal. With nothing started it is held un-advanced the same way. With runs already started it records the typed skip and advances: a recurring sweep re-picks the candidate at its next fire. A once sweep accepts that boundary, recorded visibly rather than lost silently, because a held refire would start more than max_issues. `semantic_policy_unavailable` joins the closed SkipReason set with its web/CLI mirrors and the parity test. Preserve idempotency and avoid burst loops. Tests cover both keys from one snapshot, cached refresh failure, explicit structural false yielding legacy, explicit semantic false yielding structural, seeded/non-issue unchanged, uncached unseeded refusal with zero writes, and each single-issue/sweep retry boundary without loss of visibility or duplicate starts.

Enrollment never follows momentary fleet readiness: persist it once under D5. New API/old worker queues semantic rows; old API/new worker before semantic rows exist retains old structural behavior; matched releases prove both harnesses. Every new worker-to-API field or value (hold cause, `base_aligned`, audit reserve/settle and evidence routes) is sent only behind a negotiated API feature; a new worker facing an old API holds rather than sending it. Activating chart/compose releases must pair the API with a worker image whose semantic capability behavior is proven on that image, not inferred from tag existence. Use existing release-pin machinery and explicit release evidence without workflow-file edits or a new readiness latch.

Supported rollback disables semantic enrollment for future runs and uses only API/worker releases that retain semantic profile/claim/permit enforcement. Existing semantic runs remain semantic and may queue. Downgrading to a pre-semantic API while semantic runs or authority exist is unsupported and prohibited in the runbook: an old binary cannot enforce unknown semantics. A forced unsupported deployment can violate guarantees; do not call it safe rollback or count later cancellation/roll-forward as preservation proof. Retain schema/data and require forward repair or a separately reviewed drained migration, never contract stripping.

Default-on uses bounded model usage on the owner's credential: coverage at most 120k normalized tokens and audit at most 100k per run by their separate defaults. These are maxima, not expected bills. Coverage runs only at #1230's exact approval decision point; intermediate Plan cross-check revisions consume no coverage calls. Budgets remain independent, frozen and non-resetting. #1232 proves integrated default-on compatibility/rollback; it does not flip defaults again. The independent-audit guarantee applies to semantic enrollment, not explicit disables or excluded lanes.

### D7: Enforceable whole-call bounds before launch (AI-synced 2026-10-22)

#1230's coverage reviewer runs only through the dormant `BoundedCoverageTestTransport` (`agent/src/plan-contract-review.ts`); no shipped harness has a whole-call token cap, and the Codex advice harness has no output cap at all. M0 replaces that seam with one production bounded transport per harness, used by coverage and audit. It must enforce, in the transport and not in the prompt, a whole-call ceiling covering input, framing, cache, thinking, output and hidden retries, plus the deadline. A conservative preflight input bound refuses before invocation. Only the transport certifies terminal usage as complete. An output cap, estimate or post-hoc usage observation alone is insufficient.

If a harness cannot meet this enforceable whole-call bound, the limitation returns to the user before launch scope or guarantees change. There is no silent Claude-only launch and no weaker bound.

**Spike result, Codex (2026-10-22): infeasible on the inspected path.** The spike inspected the pinned stock Codex app-server (0.162.1, `agent/codex/codex-package.lock`) offline: source, schemas and both credential compositions, with no inference calls. Neither subscription nor API-key credentials yield an enforceable whole-call bound:
- No app-server RPC (`turn/start`, `thread/start`) or serialized HTTP/WebSocket Responses request exposes an output-token ceiling.
- uzi's Codex advice renderer drops `maxOutputTokens` and `thinking`.
- Internal HTTP/stream retries, stream recovery and follow-up inference run beneath one advice turn. The built-in `openai` provider's retry defaults cannot be overridden through a partial provider table.
- Effort, verbosity, output schema, native token/rollout budgets, text caps and cancellation are not a pre-enforced token bound.

A direct API-key Responses call supports a generated-token cap, but it is a different transport. Enforcement on the subscription backend is unproven. This is not a claim that every possible Codex change is impossible. It means the M0 Codex transport is not a generalization of the existing seam: it needs a separately reviewed, approved transport/runtime design. That design must enforce a generated-token ceiling, bound every attempt and continuation under one durable reservation, and account for the complete input and framing before each request. This PRD keeps activate-together and both-harness scope and chooses no fallback.

**Spike result, Codex subscription direct path (2026-10-23): no supported bound.** OpenAI supports subscription-backed direct Responses calls only through a separately authorized OAuth flow: the app's own client registration, PKCE and a direct-use scope ([overview](https://developers.openai.com/siwc/token-sharing-open-source), [sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference)). Its [preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) list `max_output_tokens` as unsupported on that route. uzi's existing Codex subscription credentials come from a `codex login` import and the fixed Codex CLI client, and are not proven interchangeable with that grant. Only API-key calls document `max_output_tokens` ([reasoning](https://developers.openai.com/api/docs/guides/reasoning#controlling-costs)).

**Spike result, Claude (2026-10-23): not certifiable on the SDK path; the direct path needs an API key.**
- The Agent SDK advice path sends every built-in tool schema (tool-less only through a deny hook) and has unbounded turns. Its retries, max-tokens continuations, refusal fallback and helper calls sit inside a closed CLI binary and cannot be certified. Usage is observed only after the fact.
- A direct single-request `/v1/messages` transport with `max_tokens`, no tools, zero retries and an abort deadline would be enforceable per request. Byte-based input admission (tokens are at most UTF-8 bytes plus a framing allowance) is a proposed method, not certified evidence: it needs proof for the exact provider request and tokenizer, including injected content.
- uzi's Claude credential is subscription OAuth only. Anthropic's [legal and compliance](https://code.claude.com/docs/en/legal-and-compliance) and [Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview) pages direct products to API-key authentication and forbid third-party products routing requests through Free/Pro/Max plan credentials or intermediating them. The OAuth beta header on `/v1/messages` is undocumented ([beta headers](https://platform.claude.com/docs/en/api/beta-headers)); [token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting) is documented with API keys only. A direct Claude transport therefore needs an Anthropic Console API key, a credential lane uzi does not have.

**Open product decision (not chosen here).** Any redesign must choose one option. Weakening the guarantee or narrowing eligibility needs explicit user approval.
- (a) API-key-only semantic enrollment with direct capped transports. This adds an Anthropic API-key credential lane and narrows the default-on eligibility promise: subscription-credential runs never get semantic enrollment. When the completion audit is unavailable, the run must hold; that never becomes human approval of unaudited work.
- (b) Wait for providers to expose enforced caps on subscription paths.
- (c) A revised bound definition, only if enforced per-request input and output bounds, a bounded request count and shared reservations can be proven on the actual paths. The inspected SDK and app-server paths lack those primitives.

## Acceptance criteria

- A lead declaring every milestone cannot obtain a semantic permit while one criterion is unsatisfied, or unverified without the owner's exact acceptance under D4's acceptance transition.
- Every semantic permit uses a full-contract audit of the exact final head; no incremental audit exists, at most two verdict-bearing audits run per run, and a verdict is reused only under the identical D2 reuse key.
- The auditor is tool-less and consumes a worker-built packet; an overflowed criterion is `unverified` with `context_truncated`, never `satisfied`.
- Gate commands are plan-declared and frozen at approval; their criterion references resolve server-side to canonical IDs or the proposal is rejected; coverage review judges their sufficiency. Gate evidence is a worker-executed, credential-free runner-uid artifact bound to the frozen declaration, argv, environment policy, head, tree fingerprint, exit, timing, completeness and digest; re-execution is the fallback only, runs under the declared timeout and consumes no audit wall.
- Coverage and audit calls on both harnesses are enforceably bounded per D7, or launch waits for a user decision.
- D4 ceilings (model, per-call/aggregate wall, passes, retry, tokens) are enforced server-side, visible, instance-admin configured and frozen per run; exhaustion holds with cause `audit_cap` or `audit_unavailable` under `hold_reason='completion_blocked'`.
- With a known admin semantic disable, new eligible issue runs remain structural with zero coverage/audit calls; unknown policy fails creation retriably rather than silently disabling enforcement. Existing enrollment and frozen model/budgets do not change.
- Repository prompt injection cannot redefine server contract or auditor authority.
- ADR-456 head drift republishes the aligned checkpoint and automatically resumes for new evidence without stale-audit reuse.
- Auditor outage holds with `audit_unavailable` after one retry and exits only through `retry_audit` under the remaining budget or cancel-and-rerun; cap exhaustion holds with `audit_cap` and refuses `continue`; neither silently accepts or loses work.
- Semantic `accept` binds exact worker-kind criterion IDs reported `unverified` by the standing verdict, the contract revision and the evidence head; the decision revision reuses the bound verdict only when nothing but the accepted set changed; stale, replayed, `unsatisfied` or outage-time accepts are refused, and maintainer criteria remain reachable only through `authorize_maintainer`.
- Workers lacking `completion_audit_v1` cannot claim semantic runs through any override or kill-switch.
- Default-on works on both harnesses without stored settings rows or repo opt-in. Missing capable capacity queues semantic runs with a named reason, including planning claims; seeded/legacy and explicit structural-off lanes remain excluded.
- Coverage runs only at the exact approval decision point. Intermediate checker revisions spend no coverage budget; a changed candidate/source/criteria/gate declaration cannot reuse stale coverage or required checker approval. Both ledgers stay independently capped.
- Only exact frozen human-authorized maintainer criteria can remain outstanding on a truthful non-closing delivery, with no second equivalent owner decision. Auto-approval, ordinary prose and checked display boxes cannot invent an exemption or waive failed worker gates.
- Maximum-size owner semantic reads and decisions complete within production 15-second listener deadlines with a reported margin.
- API/worker skew and semantic-aware rollback preserve profiles and head/revision fences. No supported rollback strips authority or downgrades a semantic run; a pre-semantic API downgrade with semantic authority present is explicitly unsupported.
- Audit cost/pass bounds and results are visible without exposing raw content.
- #1233 can add blockers through reserved permit fields without changing this wire contract.
