## Problem

`uzi skill install` writes the agent skill to exactly one place, and `uzi skill install-hook` wires its auto-refresh into exactly one harness:

- `api/internal/uzicli/skill.go:30` fixes the install dir as `skillDirParts = {".claude", "skills", "uzi-cli"}` under `$HOME`; the comment at `:26-29` calls it "the FIXED install location" with no user-supplied component, an invariant `TestSkillInstallDoesNotTouchCommands` (`skill_test.go:189`) pins. `Status()` (`:133`) and `Install()` (`:178` does the `MkdirAll`) report one path; the state file beside the skill is `.uzi-cli-state.json` (`:35`).
- `api/internal/uzicli/skillhook.go:16-25` manages a Claude Code `SessionStart` hook in `home/.claude/settings.json` only (the same fixed-location comment at `:28-31`), with `hookEvent = "SessionStart"`, `hookMatcher = "startup"`, `hookCommand = "uzi skill install"`, `hookTimeout = 15` (`:37-44`).
- `api/cmd/uzi/skill.go:90-151`: the two cobra `Short` strings (`:95`, `:129`) and the comments name Claude Code (runtime messages say "SessionStart hook"); `uzi skill status` prints one `PATH` row plus one `HOOK_INSTALLED` / `HOOK_CURRENT` pair, and `status --json` emits one object `{skill: SkillStatusResult, hook: HookStatusResult}` (`skillStatusJSON`, `:164-167`, pinned by `TestSkillStatusJSONIncludesHook` in `skill_cmd_test.go:101`). `install --json`, `install-hook --json` and `uninstall-hook --json` each emit one result object (`SkillInstallResult`, `HookInstallResult`, `HookUninstallResult`); `TestSkillInstallForceJSON` (`:208`) only substring-checks `"wrote": true`.
- The embedded body names the Claude harness or path at four places: the "Generated artifact" note (`api/internal/uzicli/skill/SKILL.md:21`), the `install-hook` bullet and the source-of-truth paragraph under `### The skill itself` (`:1223`, lines `:1231-1235` and `:1240`), and one Claude-specific *measurement* about background `run wait` being reaped (`:358`).
- `docs/cli.md:34-39` and `:1331-1372` (§"Bundled skill and session-start hook") document the same single path and single hook, and `specs/ai.md:7960-7973` (the PRD #64 realization) states the installer as a single path.

An operator who drives uzi from OpenAI Codex CLI therefore gets no skill: Codex never sees `SKILL.md`, "send to uzi" triggers nothing, and there is no refresh on CLI upgrade. Yet Codex reads the same `SKILL.md` format from a user-level skills directory and has a `SessionStart` hook with the same JSON shape as Claude's, so the whole feature is a second target for code that already exists.

## Verified facts about Codex CLI (source: openai/codex, 2026-09-05)

1. **Skill roots.** `codex-rs/ext/skills/src/host_roots.rs` resolves skill directories per config layer: Project `./.codex/skills` (repo scope, plus any `.agents/skills` directory between the repo root and cwd), User `$CODEX_HOME/skills` **and** `~/.agents/skills`, System `$CODEX_HOME/skills/.system`, Admin `<system_config_dir>/skills`. `$CODEX_HOME` defaults to `~/.codex`.
2. **SKILL.md frontmatter** (`codex-rs/skills/src/assets/samples/skill-creator/SKILL.md`, `codex-rs/memories/write/templates/memories/consolidation.md`): `name` (lowercase, digits, hyphens, ≤ 64 chars), `description`, optional `argument-hint`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `context` / `agent` / `model`. Our frontmatter (`name`, `description`, `allowed-tools: Bash(uzi *)`, `user-invocable: false`) parses as-is. `allowed-tools` is a Claude permission glob; Codex's exec policy governs its own tool access, so the field is inert there, not harmful.
3. **Trigger** (`codex-rs/ext/skills/src/catalog_prompt.rs`): a skill fires when the user names it (`$uzi-cli`) or the task matches its description; the agent must read `SKILL.md` completely before acting. Our description's "send to uzi" / "ship to uzi" cue therefore works unchanged.
4. **Hook events** (`codex-rs/hooks/src/lib.rs`, `HOOK_EVENT_NAMES`): `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `SubagentStart`, `SubagentStop`, `Stop`.
5. **Hook sources** (`codex-rs/hooks/src/engine/discovery.rs`): per layer, `hooks.json` in the layer's hooks folder (`$CODEX_HOME/hooks.json` for the user layer) and/or an inline `[hooks]` table in `config.toml`; loading both in one layer emits a warning ("prefer a single representation"). The JSON shape (`codex-rs/config/src/hooks_tests.rs`) is `{"description"?: string, "hooks": {"SessionStart": [{"matcher"?: string, "hooks": [{"type": "command", "command": string, "timeout"?: int, "statusMessage"?: string, "async"?: bool}]}]}}` — the same `hooks.<Event>[].hooks[]` nesting Claude uses in `settings.json`.
6. **Trust.** Every hook gets a sha256 over its normalized identity (event + matcher + handler config); the user's decision is persisted in `config.toml` as `[hooks.state."<source-path>:<event_key>:<group-index>:<hook-index>"]` with `enabled` and `trusted_hash`. An untrusted hook does not run headless (only `--dangerously-bypass-hook-trust` overrides). Observed locally: keys such as `/Users/…/.codex/hooks.json:session_start:0:0`. **The key embeds array indices**, so inserting an entry *before* an existing one, or removing one that has successors, renumbers those successors' keys and drops their trust.
7. **Feature flag.** The local install carries `[features] hooks = true` in `config.toml`. Whether current Codex needs it, or hooks are on by default, is M0's question (c); the installer never writes it either way.
8. **Claude Code, for contrast** (`code.claude.com/docs/en/skills`, `…/agent-sdk/skills`): personal skills load from `~/.claude/skills/` and project skills from `.claude/skills/` up to the repo root. The docs list no `~/.agents/skills` root, so a single shared file cannot serve both harnesses today (D1). This repo's own `.claude/skills/frontend-design` is a symlink to `../../.agents/skills/frontend-design`: a mirror maintained by a third-party installer, not native reading.

## Solution

Teach the installer a **second target** rather than a second mechanism. One embedded `SKILL.md`, two install sites, two hook files, one `status` table:

| | Claude Code (today, unchanged) | Codex CLI (new) |
|---|---|---|
| skill path | `~/.claude/skills/uzi-cli/SKILL.md` | `$CODEX_HOME/skills/uzi-cli/SKILL.md` (default `~/.codex/skills/uzi-cli/SKILL.md`) |
| state / backup | `.uzi-cli-state.json`, `SKILL.md.bak` beside it | same files, beside the Codex copy |
| detected when | always | the Codex home **exists as a directory**: `$CODEX_HOME` when set (absolute), else `~/.codex` (D2, D8) |
| hook file | `~/.claude/settings.json` → `hooks.SessionStart[]` | `$CODEX_HOME/hooks.json` → `hooks.SessionStart[]` |
| hook entry | `{matcher:"startup", hooks:[{type:command, command:"uzi skill install", timeout:15}]}` | `{hooks:[{type:command, command:"uzi skill install", timeout:15}]}` (matcher per M0 (d)) |
| trust | none needed | user trusts once in Codex; installer never writes `[hooks.state]` |

- `uzi skill install [--force] [--target claude|codex|all]` — default `all`, meaning *every detected target*. The best-effort auto-install every `uzi` command already performs (`UZI_SKILL_AUTO_UPGRADE`) uses the same default, so a Codex user gets the copy on their first `uzi` command without asking for it, and a machine without `~/.codex` sees no new directory.
- `uzi skill install-hook [--target …]` / `uninstall-hook [--target …]` — same targets. For Codex the entry is **appended at the end** of `hooks.SessionStart` (fact 6) and the command prints, once, that Codex will ask to trust the new hook on its next start.
- `uzi skill status` — one row group per detected target (`TARGET`, `PATH`, `INSTALLED`, `UP_TO_DATE`, `USER_EDITED`, `HOOK_INSTALLED`, `HOOK_CURRENT`). `--json` on every `skill` verb follows one rule (D6): today's top-level object keeps describing the Claude target, and a new `targets[]` array carries one element per target acted on.
- The embedded body's two Claude-specific sentences become harness-neutral (D3); `docs/cli.md` gains the Codex column.

## Decision Log

- **D1 — A second target under `$CODEX_HOME/skills`, not a shared `~/.agents/skills` file.** Codex reads `~/.agents/skills` (fact 1) but Claude Code does not (fact 8), so a single shared write cannot replace the Claude path. `~/.agents/skills` is also the tree third-party skill installers populate (65 skills there on the reference machine, mirrored into `~/.claude/skills` by that installer), so a generated file there competes with another tool's inventory. `$CODEX_HOME/skills/uzi-cli` is Codex-owned, `CODEX_HOME`-relocatable, and mirrors the Claude path's shape exactly. Revisit if Claude Code adopts `~/.agents/skills`; the target list makes that a one-line addition.
- **D2 — Detection by presence, never creation.** The auto-install runs on every `uzi` command, so it must not litter: Codex is a target only when its home **directory already exists** (`$CODEX_HOME` when set, else `~/.codex`). `Install`'s `MkdirAll` (`skill.go:178`) then creates only `skills/uzi-cli/` beneath that existing home, never the home itself. A `CODEX_HOME` that points at a nonexistent directory is not a Codex install; the auto path skips it silently and `--target codex` is `uzicli.ExitUsage` naming the value.
- **D3 — One embedded body, harness-neutral wording.** Two bodies would double the drift test's surface and let the two copies disagree about the same CLI. Only the two sentences that name Claude Code change; the command reference is identical for both harnesses because the CLI is.
- **D4 — uzi never writes Codex trust state.** Writing `trusted_hash` ourselves is indistinguishable from `--dangerously-bypass-hook-trust`; the whole point of the hash is that a *user* approved *this* command. The one-time prompt is the cost of correctness. The installer also never edits `config.toml`: TOML round-tripping loses comments and formatting, and `hooks.json` is the JSON twin Codex reads for the same layer (fact 5).
- **D5 — Append at the end; warn on a non-terminal uninstall.** Trust keys embed array indices (fact 6). Appending keeps every existing key stable; removing our entry when others follow renumbers theirs. The alternative, refusing to uninstall unless last, leaves the user with a hook they cannot remove through uzi; printing the consequence and proceeding is the smaller harm. M0 (e) confirms the behaviour before M2 commits to it.
- **D6 — Every `skill` verb's `--json` stays backward compatible, by one rule.** Today `status --json` is `{skill, hook}` (`skillStatusJSON`) and `install` / `install-hook` / `uninstall-hook --json` each emit one result object. The rule: the top-level object keeps describing the **Claude** target exactly as today (Claude is always a target, so it is always present), and a new `targets` array carries one element per target acted on: `status` → `[{target, skill: SkillStatusResult, hook: HookStatusResult}]`, `install` → `[{target, ...SkillInstallResult}]`, `install-hook` → `[{target, ...HookInstallResult}]`, `uninstall-hook` → `[{target, ...HookUninstallResult}]`. With `--target claude` the array has one element that duplicates the top level. A consumer written against the old shape keeps working (`TestSkillStatusJSONIncludesHook` must pass unchanged); a new consumer reads the array. Exit status for a multi-target verb: 0 only if every requested target succeeded, else the first failure's code.
- **D7 — The auto-install stays best-effort; its stderr policy is per target.** Today the per-command auto-install warns on stderr when the Claude write fails (`api/cmd/uzi/skill.go:213-215`, asserted by `TestAutoUpgradeNeverFatalOnError`); the CLI has no debug level. That warning stays for Claude. A failed **Codex** write on the auto path is silent: the Claude copy is the one the auto path has always guaranteed, and a read-only `~/.codex/skills` must not add a line to every `uzi run list`. An explicit `uzi skill install` reports every target's failure and exits per D6. Neither path ever fails the command the user actually ran.
- **D8 — `$CODEX_HOME` is the one user-influenced path component, and it is bounded.** `skill.go:26-29`, `skillhook.go:28-31` and `TestSkillInstallDoesNotTouchCommands` rest on "a fixed location under `$HOME`, no user-supplied component". `CODEX_HOME` is the user's own environment, not remote input, but the invariant still needs restating rather than quietly dropping: the value must be an absolute path (a relative one is rejected, never joined to cwd), it is `filepath.Clean`ed, it is used only when it names an existing directory (D2), and the installer appends the fixed `skills/uzi-cli/` tail beneath it. The lookup is injected (M1), so tests control it; the two comments and the test are updated to say exactly this.

## Risks & mitigations

- **R1 — Codex changes its skill root or hook schema.** Both are read from source at a named version (0.153.4); M0/M4 re-verify against whatever is installed. The `skillTarget` list and the hook wrapper shape are data, so a path or wrapper change is a constant edit, not a redesign.
- **R2 — Hooks feature-gated off on a user's Codex.** The trust notice printed by `install-hook --target codex` is **unconditional** and also says that hooks must be enabled in Codex (`[features] hooks = true`) if M0 (c) finds that still matters; uzi does not read or edit `config.toml` for this (D4). If a later need to read it arises, `github.com/BurntSushi/toml` is already in `api/go.mod`, so a read-only parse costs no new dependency; that is not in this PRD.
- **R3 — Duplicate skill via `~/.agents/skills`.** A user whose third-party installer also mirrors skills into `~/.agents/skills` could end up with two `uzi-cli` entries in Codex if they also install ours there by hand. We write only `$CODEX_HOME/skills`; the docs say so.
- **R4 — Trust prompt read as an error.** A user who has never trusted a Codex hook may not expect the prompt. `install-hook` prints exactly what Codex will ask and why; `docs/cli.md` repeats it.
- **R5 — `uninstall-hook` renumbers a successor's trust key.** Mitigated by append-at-end (our entry is last unless another tool appended later) and by the explicit warning (D5).
