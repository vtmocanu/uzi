## Problem

A run that reaches its wall-clock budget is failed. `SweepRunningTimeout` (`api/internal/store/queries/runtime.sql:3337`) flips every `running` row past its deadline to `failed` with `failure_reason = 'run exceeded RUN_TIMEOUT'` (`api/internal/workersvc/sweep.go:94-113`), whether or not its worker is alive and the work is sound. The motivating case: a seven-milestone issue run (PRD #1484, run `da8af56e`) with a live worker was failed at exactly its 8h budget, mid-implementation, and its work had to be recovered by hand.

Three shipped features surround this and none prevents it:

- PRD #1170 warns at 85% of the budget (`api/internal/workersvc/health.go:454-461`), with a Slack DM carrying the deadline and the extend command (`api/internal/slacksvc/health.go:204-228`).
- PRD #1189 lets the owner extend (`uzi run extend <id> --by 2h`, the web `ExtendTimePopover`), but only an owner who reacts before the deadline.
- PRD #1190 lets the owner pause on demand. The park it built (non-terminal `paused`, clock stopped, checkpoint, same-worker or cross-worker resume) is exactly what a run out of time needs, but nothing enters it involuntarily.

PRD #1226 routes a wall trip to a hold only **after** a first completion attempt, and its rollout is off (`prds/done/1226-structural-completion-interlock.md:86`: "Before any completion attempt exists, existing stall, wall and budget outcomes remain unchanged"). The common case, a run still implementing when the clock runs out, still dies.

An unattended run (a nightly sweep, an owner asleep) therefore loses its session and its uncommitted work to a clock, and the owner's first chance to decide comes after the decision has been made for them.

## Solution

- **At the deadline the run parks, it does not fail.** The timeout sweep stops failing runs. For a run whose worker is alive and speaks the wall-park protocol it files a system-authored pause request with a new mode `wall`; the worker drops the turn in flight, captures the tree, and parks in the existing `paused` status with `hold_reason = 'budget_exhausted'`. For a run whose worker is dead, does not speak the protocol, or has not parked within a fixed grace, the sweep parks the row itself and fences the old flight.
- **The owner is asked.** Web (a "Time limit reached" panel), CLI (`uzi run get`, `uzi run wait`), TUI (the run moves to NEEDS YOU) and Slack (a reply in the run's thread with the exact commands) present the same three choices: **Extend** (adds time and resumes in one action), **Stop** (finalize the completed milestones into a merge request; milestone issue runs only), **Cancel**.
- **The park has no expiry and the behaviour has no switch** (owner decisions D1 and D2). A parked run waits until its owner acts. No admin setting, per-user setting or rollout flag restores fail-at-the-wall.
- **Both harnesses park.** Claude and Codex runs take the same wall park; neither may fail at the wall.
- **Every kind the sweep can time out is covered**: `issue`, non-interactive `task`, `prompt`, `self_improve`, `mr_rework`, `ci_fix`. Owner-initiated pause keeps its four kinds.

## Resolved facts (no internet needed; every anchor read on 2026-09-20 at `main` 0ba6a0f2, re-based to 10bdc1e8, whose only change is the PRD #1493 file)

**The server sweep is the clock that fires.** `SweepRunningTimeout`'s predicate (`runtime.sql:3393-3436`) is `status = 'running' AND started_at < now - (COALESCE(budget_wall_seconds, global) + budget_paused_seconds + budget_extension_seconds) AND kind NOT IN ('chat','judge') AND interactive = false`, minus the PRD #1226 carve-out (`NOT (completion_attempts > 0 AND worker heartbeat live)`) and two pending-write guards (a journaled terminal outcome in `worker_active_runs`, `:3430-3436`). The SQL itself stamps `fail_origin = 'run_timeout'` and `move_pending_since` (`:3382-3383`). Go then calls `publishSwept` and `maybeEnqueueJudgeByID` per row. The sweep ticks every 15s by default (`api/internal/config/config.go:395`, `SWEEP_INTERVAL`).

**The worker's own wall is deliberately looser than the server's.** Claim assembly serves `RunTimeoutSeconds = COALESCE(budget_wall_seconds, RUN_TIMEOUT) + budget_extension_seconds` (`api/internal/workersvc/claim_assembly.go:566`), the full total on every claim, never the remainder. The worker seeds `wallRemainingMs` from it on each fresh process (`agent/src/sdk-executor.ts:1173-1185`), lifts it upward on a served extension (`:2033-2039`), and `armWall` (`:3660-3672`) trips `REASON_WALL` (`:129`). The comment at `:2032` states the invariant: the worker never trips before the (always >=) server deadline. So the server sweep is what kills a run in practice (the motivating run carries the sweep's string), and the worker's trip is the rarer second path.

**Where a wall trip goes today.** In the implement loop's turn catch (`sdk-executor.ts:2290-2304`) a `REASON_WALL` or `REASON_IDLE` error routes to `routeCompletionHold` only when `completionAttempted` is true and the seam is wired (`:3584`); otherwise `throw err`, the legacy terminal failure. `PauseNowSignal` is handled in the same catch (`:2264`) and parks through `requestPause`. A declined `now` park restarts the turn (`:1222-1232`, `:1608`).

**The Codex harness does neither.** `agent/src/codex/codex-executor.ts:1894-1900` converts any `ctx.signal` abort into `REASON_CANCEL` without reading `signal.reason`, so a `PauseNowSignal` reads as a cancel; its own wall timer throws a plain `REASON_WALL` (`:1907`, `:1940-1954`); its loop never calls `parkForPause`. A Codex run today has no pause seam at all.

**The runner's generic fallback is terminal.** An executor error that no arm claims reaches `reportGenericFailure` (`agent/src/runner.ts:1730-1732`). The non-terminal end precedents are the e2e drop seam (`:1722-1728`: no terminal report, run left `running`) and the retained held-state park (`:2338`).

**A fenced-out flight sees `stale_claim`, and today that is a plain stop.** A `/state` report refused by the fence comes back with `disposition: "stale_claim"` (`protocol.ts:2222-2227`); the report choke point throws `StaleClaimError` (`runner.ts:4402-4417`); `reportIteration` swallows every error with a warning (`:5375-5443`); and the outer `StaleClaimError` arm closes the batcher with **no preserve flag** and ordinary cleanup (`:1658-1666`), because the only case it knows is a credential-switch release where the new claim has its own clone.

**The pause machinery (PRD #1190).**

- Columns `pause_requested_at`, `pause_mode`, `pause_after_count` come from `00204_run_paused.sql`; the mode CHECK is `runs_pause_mode_check CHECK (pause_mode IS NULL OR pause_mode IN ('milestone','now'))` (`:33-34`). `run_user_inputs_kind_check` already admits `pause`, `pause_cancel`, `resume`, `extend`.
- `CreatePauseInput` (`runtime.sql:4790`) is one CTE: stamp the three columns where `status = 'running' AND kind IN ('issue','task','prompt','self_improve') AND interactive = false`, then insert the `kind='pause'` input row whose body is the mode. `CancelPauseInput` (`:4825`) clears them. `ClearPauseRequest` (`:2476-2498`, the `pause_failed` path) clears them under the generation fence with no mode guard. `ConsumeRunInputs` (`:4879-4910`) drains every unconsumed `pause` row to the worker, so a `pause` input outlives any settlement that clears only the `runs.pause_*` columns. The worker's steering channel polls `/inputs` every 3s by default (`agent/src/runner.ts:780`) and consumes the input; `SteeringChannel.route` maps any non-`now` pause body to `milestone` (`agent/src/steering.ts:792-813`) and `seedPauseRequested` accepts only `milestone` and `now` (`:308-325`). An old worker image receiving `wall` therefore parks at the next milestone boundary, if ever, and never drops the turn.
- The pending-pause columns survive the involuntary parks and a worker death; the claim re-seeds them (`PausePending`, `api/internal/workersvc/claim.go:103`; `pause_pending`, `agent/src/protocol.ts:1063`), and the running-report ACK carries the server-decided `pauseRequested` (`protocol.ts:2192`), honoured at the loop top (`sdk-executor.ts:2089-2100`).
- `handlePausePark` (`agent/src/runner.ts:6770`) is **publish-or-stay**: it WIP-commits dirty edits into a `wip(park):` marker, fetches the clone tip back to the bare tracking ref, publishes through `publishCheckpointBestEffort` (`:6176`), and parks only if the publish lands; otherwise it reports `pause_failed`, the server clears the request, and the run continues.
- `SetRunPaused` (`runtime.sql:2237`, statement `:2266-2279`) is guarded `status = 'running' AND worker_id = @worker_id AND pause_requested_at IS NOT NULL`: a park needs a durable pending request. `SetRunRunning` (`:1204`) refuses a `paused` row (`:1485`) but **admits `queued`** for the same worker. The worker-driven transitions (`running`, `awaiting_*`, `paused`, `failed`, legacy `completed`) are fenced in Go by `SetState`'s `FOR UPDATE` wrapper rather than in their SQL (`api/internal/workersvc/credential_switch.go:19-38`), and that fence is **nil-guarded**: a report that stamps no `claim_generation` is honoured, the compatibility contract for a worker without `credential_switch_v1` (`runtime.sql:2791-2798`). Every image since PRD #1247 M5 stamps it.
- `ResumePausedRun` (`:2344`, statement `:2368-2378`) moves `paused` to `queued`, banks the parked time into `budget_paused_seconds`, keeps `started_at`, `session_id`, `last_seq`, `worker_id`, bumps `codex_claim_epoch`, and neither sets `claim_released_at` nor reads `hold_reason`. `ResumeRunNow` (`api/internal/handler/resume.go:26-93`) dispatches on status; its `case "paused"` (`:58`) does not read `hold_reason`.
- `paused` is absent from `RequeueRunsOfStaleWorkers` (`:3544`), `FailWorkerRunsOverCap` (`:3594`), `RequeueWorkerRuns` (`:3629`), `ListActiveRunsForHealth` (`:5057`) and the timeout sweep, so a paused run survives its worker's death and is never flagged or failed.

**The claim fence and the snapshot.** `ReleaseCredentialSwitch` (`:2380-2425`) is the precedent for a server-side release of a live flight: `status='queued', claim_released_at = now()`, which arms the fence `(claim_generation = @g AND claim_released_at IS NULL)` that `SetRunFailed`, `SetRunCompletionHold`, `ClearPauseRequest` and the other fenced writers check; `ClaimRun` (`:981-997`) bumps `claim_generation` and clears `claim_released_at` in one UPDATE; its candidate predicate (`:754-780`) admits a `queued` row to any eligible worker when `worker_id IS NULL`, to the pinned worker always, and to a peer only when the pinned worker is stale, draining, or past the affinity cutoff (ADR-628). A credential-switch release keeps `worker_id` precisely so the same worker reclaims with the new credential, so `claim_released_at` alone cannot mean "never this worker again". `UpsertWorkerActiveRun` (`:3689-3715`) accepts a snapshot row on ownership alone (`r.worker_id = @worker_id`), and `ClaimRun`'s exclusion (1) (`:922-927`) refuses to claim a run whose snapshot row at the current generation is fresh. So a run moved `paused → queued` under an old, unfenced flight can be kept unclaimable by that flight's heartbeat, and un-parked by its `running` report.

**Stale-worker classification is lock-serialised.** `RequeueRunsOfStaleWorkers` (`:3548-3557`) takes the stale worker rows `FOR UPDATE ORDER BY id` in a `locked` CTE so the decision serialises with `HeartbeatWorker`. Any new statement that classifies live-versus-stale must take the same lock.

**Protocol capabilities exist.** `protocol_capabilities` (`agent/src/protocol.ts:333-341`) is the worker-advertised, server-filtered set stored in `workers.protocol_capabilities` (`runtime.sql:195-203`); `ClaimRun` reads it directly for `completion_interlock_v1` and `codex_harness_v1` (`:806-830`, `:888-899`), and `health.go:133-146` names the no-capable-worker reasons. ## Design

### Store

Migration `00241_run_wall_park.sql` (draft): (a) widen `runs_pause_mode_check` to `('milestone','now','wall')`, `DROP` + `ADD ... NOT VALID`; (b) `ALTER TABLE runs ADD COLUMN budget_finalize_seconds int NOT NULL DEFAULT 0` with `runs_budget_finalize_seconds_check CHECK (budget_finalize_seconds >= 0)` added separately, `NOT VALID`; (c) `ALTER TABLE runs ADD COLUMN released_worker_id uuid, ADD COLUMN released_worker_nonce text` (both nullable, no FK: together they name one worker **process incarnation** to exclude from the next claim; `workers.snapshot_register_nonce`, `00236`, rotates on every registration, so a restarted worker is a different incarnation). `00242_validate_run_wall_park.sql` runs `VALIDATE CONSTRAINT` on both (the #1189 two-step shape, `00219`/`00220`). Down restores the two-value CHECK validated and drops the three columns, so a down fails while a `wall` row exists rather than stranding it. `hold_reason` stays unconstrained text; `pause_requested_at` dates the request, `status_since` dates the park, and "checkpoint published" is `checkpoint_tip = hold_captured_head`.

**The wall-clock total gains a third term.** Everywhere the deadline is computed, the expression becomes `COALESCE(budget_wall_seconds, global) + budget_extension_seconds + budget_finalize_seconds` (plus `budget_paused_seconds` where the site adds it): the two new sweep statements, `StampCompletionBudgetExhausted` (which also gains the **missing** `budget_extension_seconds` term, its comment block rewritten to say it mirrors the sweep's deadline and carve-out rather than being its byte-for-byte complement), `RunDeadline` (`health.go:924`), claim assembly's `RunTimeoutSeconds` (`claim_assembly.go:566`) and `budget_total_seconds` (`runs_dto.go`). In Go, one helper computes the total; in SQL each site is written out and a live-DB test pins that the sweep, the stamp and `RunDeadline` agree on one row with all three terms non-zero.

`SweepRunningTimeout` is **replaced** by two statements over the deadline expression (keep its comment's reasoning about the per-run interval, the ceiling and the #1189 paragraph):

- `RequestWallParks :many`. Rows past the deadline (the existing predicate, the #1226 carve-out kept so post-attempt live rows still go to `StampCompletionBudgetExhausted`, the two terminal-pending guards kept) whose worker row (joined) has a live heartbeat **and** `'wall_park_v1' = ANY(workers.protocol_capabilities)`, and whose `pause_mode IS DISTINCT FROM 'wall'`: set `pause_requested_at = now(), pause_mode = 'wall', pause_after_count = NULL` and insert a `run_user_inputs` row `kind = 'pause', body = 'wall'` in the same CTE (the `CreatePauseInput` shape). It overwrites a pending owner `milestone` or `now` request (both park; the wall wins the wording). No kind allowlist beyond the sweep's own: `mr_rework` and `ci_fix` are requested too.
- `ParkRunsAtWall :many`. Takes the affected worker rows `FOR UPDATE ORDER BY id` in a `locked` CTE (the `RequeueRunsOfStaleWorkers` shape, so live-versus-stale serialises with `HeartbeatWorker`), then parks rows past the deadline (same predicate, carve-out and guards) where **any** of: the worker heartbeat is stale; the worker lacks `wall_park_v1`; `pause_mode = 'wall' AND pause_requested_at < now - @grace`. The write: `status = 'paused', status_since = now(), hold_reason = 'budget_exhausted', hold_captured_head = NULL, claim_released_at = now()`, clear the three pause columns and consume the wall input (see *Settling a wall request settles its input*), `codex_cap_hash = NULL, codex_claim_epoch + 1`, reset health, **capture `released_worker_id = worker_id, released_worker_nonce = <the locked worker row's snapshot_register_nonce>`** (the incarnation that failed to park, read under the same lock, D19), keep `worker_id` (informational: the panel names it), `session_id`, `last_seq`, `started_at`, `claim_generation`; and in the same CTE delete the run's `worker_active_runs` rows. `claim_released_at = now()` **arms the fence**: every later report from the old flight is rejected (`SetRunFailed` already checks it; `SetRunRunning` and `SetRunCompleted` gain the same conjunct, see below). `@grace` is a fixed Go constant, 10 minutes, not a setting. Order in the sweep: `ParkRunsAtWall` runs **before** `RequeueRunsOfStaleWorkers`, so a dead worker's out-of-time run parks once instead of being requeued, re-claimed and re-cloned only to park.

The worker's own park:

- `SetRunWallPark :one`, a new worker-authored, **fenced** transition (`worker_id = @worker_id AND claim_generation = @g AND claim_released_at IS NULL`) for the new `wall_park` report: `WHERE status = 'running' AND completion_attempts = 0 AND <past the deadline expression>`, sets `status = 'paused', hold_reason = 'budget_exhausted', hold_captured_head = sqlc.narg(...)`, clears the pause columns, consumes the wall input, resets health, returns the row. **The deadline is the sole authority; a pending `wall` request is not sufficient**, because an owner extension moves the deadline but leaves `pause_mode = 'wall'` on the row. It admits both the request-driven park and the worker's own pre-attempt `REASON_WALL` trip (which arrives before any request exists), and refuses (0 rows) a row that is no longer past its deadline, the extended-in-the-window case: the handler answers the row's current status, and the worker clears its sticky wall mode, lifts its wall from the ACK's served total, and restarts the turn (the existing declined-`now` path), because the owner just bought it time.
- `SetRunPaused` (the owner-pause park) gains `AND pause_mode IN ('milestone','now')`: an owner-pause report can never consume a wall request. `SetRunCompletionHold` additionally clears `pause_requested_at`, `pause_mode`, `pause_after_count` when `pause_mode = 'wall'` (settling a wall request that a first completion attempt overtook, D14).
- **Settling a wall request settles its input.** Every statement that clears `pause_mode = 'wall'` (`SetRunWallPark`, `ParkRunsAtWall`, `SetRunCompletionHold`, `CreateExtendInput`) also stamps `consumed_at = now()` on the run's unconsumed `run_user_inputs` rows with `kind = 'pause' AND body = 'wall'` in the same statement (D18). Otherwise `ConsumeRunInputs` hands the stale `wall` to the next flight, which aborts its first turn.

### Agent (both harnesses)

- `protocol.ts`: `"wall"` joins the pause mode union; the `wall_park` report joins the report union (fields: `captured_head` nullable, `published` boolean); `protocol_capabilities` gains `wall_park_v1`. `SteeringChannel.route("pause", "wall")` aborts the turn in flight exactly like `now` (the `PauseNowSignal` path, carrying the mode) and records `wall`; `seedPauseRequested` accepts `wall`; `pause_cancel` cannot clear it.
- **The wall park is capture-first, not publish-or-stay** (D4). A `wall` park does not use `handlePausePark`'s contract. If the capture cannot be verified after the bounded retry, the park still happens, **degraded**: flags stay set, the clone and HOME stay on the worker, the head is reported null, and a feed message says the latest local work is unverified and lives only on this worker. - **An unknown park acknowledgement never becomes a failure** (D17). If the `wall_park` report cannot be delivered (server unreachable through the batcher's retries), the flight retains clone and HOME, emits **no terminal report**, and ends non-terminal like the retained held-state park (`runner.ts:2338`); the sweep's stale-worker path parks the row server-side. ## Decision log

- **D1 (owner, 2026-09-20): the park never expires.** No TTL, no auto-fail, no auto-finalize. A parked run waits until its owner extends, stops or cancels. Consequence accepted: it holds its lane (issue, schedule, merge request) and, on a hosted fleet, its run-bound worker and volume, for as long as it waits.
- **D2 (owner, 2026-09-20): not configurable.** No admin setting, per-user setting or rollout flag. Park-at-the-wall replaces fail-at-the-wall outright, on both harnesses.
- **D3: the sweep is the trigger, through the pause channel.** The server deadline is the clock that fires first by construction, and the 3s steering poll already aborts a turn in flight for a `now` pause. A served ACK flag alone (the #1226 shape) waits for the next report, which a long turn delays; the input reaches the worker in seconds. The columns also survive a worker death and re-arm on re-claim, which a one-shot flag does not.
- **D4: capture-first, never publish-or-stay.** PRD #1190's Decision 8 refuses to park when the checkpoint cannot be published because the honest fallback is to keep running. A run out of time has no such fallback, so the wall park takes the completion hold's rule: a verified local capture makes the park, the publish is best-effort, and even an unverifiable capture parks (degraded, same-worker-only, said so on every surface) rather than fails.
- **D5: the server parks what the worker cannot.** A dead worker's row, an incapable worker's row, and a live worker's row that has not parked within 10 minutes of the request, are parked by the sweep. The last bound on a wedged worker (PRD #108) thereby moves from "failed at `RUN_TIMEOUT`" to "parked at `RUN_TIMEOUT` plus the grace": the run still leaves `running`, its reports are still refused, and the owner is still told, but nothing is thrown away.
- **D6: the two holds partition on `completion_attempts`.** Post-attempt live rows keep PRD #1226's route and `completion_blocked`; everything else takes this one. Neither hold's resume path accepts the other's rows: `ResumePausedRun` refuses `completion_blocked` explicitly, the decision endpoint refuses `budget_exhausted` as it already does.
- **D7: Extend resumes.** On this hold an extension has one purpose, so it is one action: add the time, bank the overrun, requeue. A bare `resume` without budget is refused with the command that works.
- **D8: the admin's extension allowance still binds.** It is a spend control that predates this PRD, not a switch on the park. With the allowance used up or set to `0`, Extend is disabled and says why; Stop and Cancel remain, and the run still waits.
- **D9: Stop is the existing stop plus a fixed finalize allowance.** 1800s, system-granted, once, in its own column `budget_finalize_seconds` so it is outside the owner cap by construction and the column doubles as the once-only marker. Only a milestone issue run with a finished milestone has something to deliver; other kinds get Extend and Cancel.
- **D10: all six timed kinds.** Carving out `mr_rework` and `ci_fix` would keep a fail-at-the-wall path alive, which D2 rules out. A parked rework holds its merge request's single rework slot until the owner acts; that is visible and intended.
- **D11: the grace is a constant.** It exists to let a live worker finish its capture. A setting would be a knob nobody can reason about and a way to reintroduce a de facto timeout.
- **D12: two runs on one issue.** M1 alone rewrites the sweep, adds a fenced transition, touches fourteen statements and two owner actions, and carries some thirty live-DB scenarios; the motivating run showed what happens to a seven-milestone run in one budget. Run 1 ships the safety property with the CLI as its owner surface; run 2 ships the rest against a landed contract (the PRD #1255 shape).
- **D13: `wall_park_v1` is negotiation, not a toggle.** Worker images do not roll with the app, so an old worker will meet a new sweep. An old worker cannot be asked to park (it reads `wall` as a milestone pause); its out-of-time run is parked server-side at once and, because the resume drops its affinity (D19), is reclaimed by another safe incarnation, a peer or the re-registered same worker, and restored from its last checkpoint. That is a degraded park, never a failure, so D2 holds on a mixed fleet.
- **D14: the completion hold wins the race.** A wall request stamped at `completion_attempts = 0` can be overtaken by the worker's first completion attempt before the worker acts on it. The worker knows it attempted and routes to the completion hold, whose write rechecks `completion_attempts > 0` and now also settles the wall request; `SetRunWallPark` rechecks `completion_attempts = 0` as the server-side backstop. No row can carry both holds' state.
- **D15: the wall park is its own fenced transition, and the deadline is its only authority.** `SetRunPaused` requires a durable pending request and derives nothing about the wall; the worker's own pre-attempt trip has no request to consume. `SetRunWallPark` admits a past-deadline row only, fenced on the flight; a pending `wall` request is not enough, because an extension moves the deadline without clearing the request. Its refusal therefore has one meaning (the owner just extended) and one response (clear the sticky mode, restart).
- **D16: a server-side park arms the claim fence, and its resume drops the affinity.** The parked flight may still be alive. `claim_released_at = now()` plus the snapshot delete is the `ReleaseCredentialSwitch` precedent, and the two snapshot statements are closed in the same milestone, so the fence rejects every later report from a generation-stamping flight (every image since PRD #1247 M5). The fence is nil-guarded by contract for older workers, so it is not the whole mechanism: a server-parked row resumes with `worker_id = NULL` (D19), and the ownership guard on every report writer then rejects the old flight whether or not it stamps a generation, and the fence itself no longer honours a generation-less report on a released claim, at every fenced site including `completeRunWithPermit`, which runs its own permit transaction outside the `SetState` wrapper (`credential_switch.go:42-45`).
- **D18: settling a wall request settles its input.** The request lives in two places, the `runs.pause_*` columns and a `run_user_inputs` row the worker drains. Every statement that clears the columns for a `wall` request consumes the row in the same statement; a settlement that did only half would hand a resumed flight a stale abort on its first turn.
- **D19: a server-parked row resumes without its worker and bars it from reclaiming.** The worker did not park itself, so it is dead, incapable, or unresponsive; keeping `worker_id` would pin the resume to it under ADR-628's affinity grace and let its unfenced reports through, and merely nulling it would still let that worker win the next claim once its slot frees. `released_worker_id` plus `released_worker_nonce`, captured by the server park from the locked worker row, name that **incarnation** until a claim clears them: a peer claims at once, and the same worker claims again only after it re-registers, so an owner with one worker restarts it rather than losing the run. The pair is captured at park time, not at resume, because the park has no expiry and the worker may already be a new, safe incarnation by the time the owner acts. It is a separate marker, not a reading of `claim_released_at`, because a credential-switch release keeps the same worker on purpose; and it is an incarnation, not a UUID, because a UUID exclusion cleared only by a successful claim would strand a single-worker deployment forever. A worker-side park keeps the affinity, as PRD #1190.
- **D17: an unknown park acknowledgement ends non-terminal.** A worker that cannot deliver its park report retains everything and reports nothing terminal; the sweep parks the row from the stale-worker side. Converting to the legacy failure would let a journaled failure replay past the terminal-pending guard and win over the park.

## Success criteria

- A `running` run of any timed kind, on either harness, that passes its deadline with a live capable worker is `paused` with `hold_reason = 'budget_exhausted'` within seconds, its dirty tree WIP-committed and fetched back, its checkpoint published when the forge allows. It is never `failed` with `fail_origin = 'run_timeout'`.
- The same run with a dead, incapable or unresponsive worker is parked by the server with its old flight fenced, and resumes on another safe incarnation, a peer or the re-registered same worker, from its last checkpoint; the old flight's later reports change nothing, whether or not it stamps a generation.
- Extend from the web or the CLI resumes the run with exactly the granted time; the session continues on the same worker when it is alive.
- Stop on a parked milestone issue run produces a merge request with the finished milestones and the rest reported as not done, without consuming the owner's extension cap.
- An extended post-attempt run is not steered into the completion hold before its extended deadline.
- Every surface says why the run is parked and what the owner can do, and none says `paused by you`.
- A post-attempt interlock run still takes the completion hold; an owner pause still behaves as PRD #1190 specifies.
- `task gate` is green in both runs; the live-DB suite ran and passed; no file under `.github/workflows/` is touched.

## Risks

- **Parked runs accumulate unnoticed.** With no expiry, an owner who ignores Slack leaves lanes and hosted workers held. Mitigation in scope: NEEDS YOU in the TUI, the board badge, the lane note, the Slack reply. Out of scope here and worth a follow-up: listing long-parked runs on the admin Health tab (PRD #1484).
- **A late terminal from a fenced flight.** After a server-side park the old flight's `completed` is rejected like its `failed`. The sweep's terminal-pending guard already keeps a flight that journaled its outcome out of the park; the residual is a flight that finalizes after the grace without journaling, whose merge request then exists on the forge while the run reads parked. Cancel closes that run; accepted and documented.
- **A wedged worker keeps spending after a server-side park.** The park stops the run's state from advancing, not the worker's process. Unchanged from today's failure path; M2's unrequested-`paused` handling covers a worker that is slow rather than wedged.
- **The request-then-park window.** An owner's extension that lands after the request voids it in the same statement (columns cleared, input consumed); if the input already aborted the turn, the worker's park is refused and the turn restarts (D15). If the server parked first, the row is parked with budget and `resume` restarts it without a second extension. One extra click in a seconds-wide window, accepted.
- **Two capture paths.** The wall park reuses `captureHoldContext` beside `handlePausePark`. Share the helper; a third copy of WIP-commit-and-fetch-back is how the #1190 stale-tip bug happened.
- **Schedules behind a parked run stop firing** (`HasActiveRunForSchedule`). The skip reason is already recorded per fire; the docs and the panel's lane note say so.
- **Run size.** Run 1 is still large. M1 first, checkpoint after each milestone, and the watcher extends rather than letting it reach its own wall.

## Out of scope

- An expiry, an auto-extend, or any setting for this behaviour (D1, D2).
- Releasing a hosted run-bound worker while its run is parked on a durable checkpoint (the resume would become cross-worker). A real capacity lever; separate issue.
- `REASON_IDLE` before a completion attempt, `MAX_ITERATIONS`, and the no-progress stall: they stay failures. `chat`, `judge` and interactive tasks never time out and are untouched.
- Stop for non-milestone kinds (delivering a partial `prompt` or `self_improve` run).
- Changing PRD #1226's hold route or its rollout, or PRD #1232's integration work (the `StampCompletionBudgetExhausted` deadline fix is a bug fix inside the existing route, not a route change).
- Any `.github/workflows/**` change.
