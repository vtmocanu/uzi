# PRD #1202: On-demand MR rework, past the automatic cycle cap, with optional guidance

**Issue:** [#1202](https://github.com/vtmocanu/uzi/issues/1202)
**Status:** Ready for planning; no implementation yet.
**Execution:** Sent to uzi in Auto mode (plan reviewed at the gate, MR rework on). api (store queries, workersvc, handler, poller halt text) + web + CLI + docs. **No migration.** Do not touch `.github/workflows/**`.

Use current `main` and a new working branch, never write to `main`.

## Problem

The MR review watcher (PRD #700) reworks a completed run's merge request from new review comments on its own, up to a per-MR cap of automatic cycles (default 5, admin-configurable). At the cap it posts one halt comment and one inbox notification and stops for good: the ledger row that counts cycles is dropped only when the MR leaves the `opened` state, so nothing an owner does short of merging or closing the MR makes the watcher look at it again. The documented escape hatch ("address the remaining comments yourself, or push more changes to the branch") resets nothing; a push just produces another review round the watcher will refuse.

The cap exists to bound *unattended* spend (PRD #700 Decision 5's cost envelope: default-ON, every opted-in user's every MR, five full runs each, on the owner's token). An owner who has read the halt and wants one more cycle is not the loop the cap guards against. The sibling feature already has this shape: ci-autofix stops at its own cap and the manual **Fix CI** button is its documented escape hatch (`docs/ci-autofix.md`). MR rework is the only automatic loop in uzi with no manual sibling, and `docs/mr-review-watcher.md` says so in its Known limitations.

Two smaller gaps ride along. A halted owner has no way to say *what* to fix ("only CodeRabbit's thread on the migration; ignore the naming nits"), so even a working retry would re-litigate every open finding. And the per-run rework toggle in the web is shown only on `issue` runs, although PRD #908 widened the watcher to `prompt` and `self_improve` runs and the server honours the per-run override on all three.

## Solution

An owner-scoped, on-demand rework trigger on a completed run whose MR is open, with optional guidance text, on all three surfaces:

- `POST /api/runs/{id}/rework` with body `{"guidance": "<text, optional>"}`; answers `201 {"run": …}` with the new `mr_rework` run.
- A **Rework now** control inside the existing per-run MR-rework panel on the run page, with a collapsed guidance field and an inline "N of M automatic cycles used" line so the owner can see why the watcher stopped.
- `uzi run rework <run-id> [-m|--message <guidance>]`.

The manual cycle skips the four *policy* gates (the cap, the quiet-period debounce, the head-SHA staleness check, the green-pipeline requirement) and keeps every *correctness* guard (the cross-kind branch guard, the one-active-rework-per-MR index, the admin kill-switch, the owner's Anthropic token, the MR being open). It advances the consumed high-water so the automatic watcher never fires on the same comments again, and it does **not** increment the automatic cycle count. The cap halt comment and notification are reworded to point at it.

## Design

### Store

No migration. Two query changes in `api/internal/store/queries/mr_rework.sql`, then `sqlc generate`:

- **`CreateAutoMRReworkRun` keeps its name and gains a `@trigger_source` argument** (`'mr_rework'` from the detector, `'manual'` from the endpoint); its doc comment says the name is historical and the argument is the only thing that differs between the two callers. Everything else in the statement, the `WHERE NOT EXISTS` cross-kind guard, `auto_approve = true`, the nullable snapshot, stays byte-identical. **Do not rename the query**: `mr_rework_branch_guard_livedb_test.go` (~`:245`) probes `pg_stat_activity` with `query LIKE '%CreateAutoMRReworkRun%'` keyed on the generated `-- name:` header, and a rename would silently turn that lock-detection helper into a constant false. The added `Params` field is compile-forced at every call site: the `workersvc` `Store` interface (`service.go:326`) is unchanged in name, `fakeStore` and its `mrReworkRunParams` field (`service_test.go:378`, `:1166`) gain the field, and the store live-DB tests that call the query (`mr_rework_livedb_test.go`, `scheduled_mr_state_livedb_test.go`, `trigger_source_livedb_test.go`) pass `'mr_rework'`. The Go service keeps `CreateAutoMRReworkRun` (unchanged signature, passes `'mr_rework'`) and gains `CreateManualMRReworkRun` (passes `'manual'`); both call one shared body with the source the only difference (the `createCIFixRun` shape). Rejected: a second query with a duplicated statement body (the guard predicate would then exist twice and drift).
- **New `CreateManualMRReworkRunAndAdvance :one`** (a !1207 review hardening — folds the run INSERT and the ledger write into ONE atomic statement so the create and the high-water advance commit together or roll back together): the `led` CTE upserts `high_water = GREATEST(existing, @high_water)`, `halt_notified = false`, `updated_at = now()`, with **`attempt_count` untouched** (an INSERT starts it at 0). The invariant holds: a manual cycle consumes comments and opens a new halt episode but never spends an automatic cycle. It runs on **every** successful manual create, including a guidance-only one: `GREATEST` preserves the mark when nothing is new, and the latch reset is what D9 promises.

The existing `GetMRReworkLedger` serves the endpoint's "what is new" read and the DTO's cycle count. The owner-has-a-token check reuses the `EXISTS user_secrets … kind = 'anthropic_token'` predicate already used at `anthropic_rate_limits.sql:277` (a small `:one` query if none is exported).

### Server

The handler (`StartRunRework` in `api/internal/handler/mrrework_run.go`, beside the toggle) does the reads only it can do (the settings cache, the forge) and `workersvc.StartMRReworkForRun(ctx, userID, runID, guidance, snapshot)` in `api/internal/workersvc/mr_rework.go` owns the run-state checks and the create, so the web and CLI (which both call this one endpoint) cannot drift. In order:

1. **Handler:** auth user, path id, decode `{guidance}`; `len(guidance) <= MaxGuidanceBytes` else 400. The constant is already `handler.MaxGuidanceBytes` (`schedules.go:34`) and the new handler is in the same package, so nothing moves.
2. **Handler:** admin kill-switch. `h.settings.MrReworkEnabled` read fail-closed as the detector does (off **or** read error → 409 "MR rework is disabled on this instance"). The handler holds the concrete `*settings.Cache`; `workersvc`'s settings interfaces do not expose this read (Resolved facts), and widening one for a single call is not worth the wiring. The **per-user and per-run opt-outs are deliberately ignored** (D2).
3. **Handler:** `GetRunByIDForUser` (404, never 403), then `GetRepoForUser` on the run's `repo_id` keyed on the **caller** (the `createCIFixRun` shape; a run the caller owns on a repo they no longer own is a 404, the correct answer), build the forge client as `CreateCIFixRun` does, `ListMergeRequestComments`, `BuildReviewCommentsSnapshot(comments, repo.BotForgeUserID)`. A forge read failure is 502 with the redacted error, as Fix CI does. A nil snapshot is fine: guidance-only still proceeds, a bare trigger then 409s at step 7.
4. **Service:** `GetRunByIDForUser` again (the service must not trust a handler-supplied row); `kind ∈ {issue, prompt, self_improve}` (the watcher's candidate kinds), `status = completed`, `mr_iid` set, `mr_state = 'opened'`, `branch` present (non-null, non-empty); each failure is a typed error the handler maps to a 409 naming the reason ("this run has no merge request", "the merge request is not open", "only a completed issue, prompt or self-improvement run can be reworked").
5. **Service:** the owner holds an Anthropic token, else 409 "add an Anthropic token first" (the candidate query's gate, applied at the door instead of letting a doomed run burn a worker).
6. **Service:** read the ledger (no row = zero values, as the detector does); `maxActionableID` over the snapshot exactly as the detector computes it; `isNew := maxActionableID > high_water`.
7. **Service:** if `!isNew` **and** the guidance is empty → 409 "nothing to rework: no new review comments since the last cycle, and no guidance given". Guidance alone is a valid trigger (D3).
8. **Service:** compose the description: the auto path's sentence plus the guidance section via the shared composer (`composeRunDescription` moves to `workersvc`, exported; `schedsvc/scheduler.go` keeps a one-line delegate so its byte-asserted tests in `scheduler_test.go` stay green; `schedsvc` already imports `workersvc`, so no cycle). Title `Rework MR review (on demand): <ref> (!<mr>)`.
9. **Service:** `CreateManualMRReworkRun` with the **full** snapshot (D3); `ErrBranchInUse` → 409 "a CI fix is working this branch", `ErrActiveMRReworkExists` → 409 "a rework is already running for this merge request".
10. **Service:** on success the ledger high-water advance to `maxActionableID` (0 when the snapshot is nil) is folded into the atomic create (`CreateManualMRReworkRunAndAdvance`), so the run and the advance commit together or roll back together. `GREATEST` keeps the mark where it is on a guidance-only trigger with nothing new, and the advance is what clears `halt_notified` for the new episode (D9), so it is unconditional, not gated on `isNew`. This replaced a create-then-record two-step whose separate advance failure was only logged while the create returned success — a !1207 review finding, since an unadvanced ledger let the automatic watcher re-fire on the same comments once the manual run went terminal.
11. **Handler:** answer `201 {"run": runToDTO(...)}`.

Route: `r.With(forgeLimiter.PerUserMiddleware).Post("/{id}/rework", h.StartRunRework)` in the **`RequireUser`** group next to `/{id}/mr-rework` (D5). Two tests are forced by the mount: `route_limiter_mounts_test.go` enumerates every route (`wantRouteMounts`, `:190`; "a new one fails", `:134`) and must gain `{"POST", "/api/runs/{id}/rework", limForge}`; and the router-level Bearer test is a clone of `TestCLIReachesMrReworkOverBearerLiveDB` (`cli_auth_livedb_test.go:484`: a `uzc_` Bearer reaches it, a cross-user run is 404, no credential is 401). The `forgeLimiter` is needed because the endpoint reads the forge on every call.

**Run DTO** (`api/internal/apitypes/run.go`, enriched in `GetRun`'s caller in `runs_lifecycle.go`, **not** inside `runToDTO`, which stays pure): two nullable fields, `mr_rework_auto_cycles` (the ledger's `attempt_count`, 0 when no row) and `mr_rework_auto_cap` (the live `h.settings.MrReworkCap`, default on error as the detector does), populated only when `run.UserID == user.ID` (explicit, because `GetRun` reads through `GetRunForViewer` and an admin sees any run) **and** the run is one of the three kinds **and** its MR is `opened`; null otherwise. One PK lookup plus one cached settings read; null for a non-owner so the fields leak nothing. Re-record `fixtures/api-contract/run.{zero,full}.json` from the failing contract-test output (recorded, never hand-authored) and mirror the fields in `web/src/lib/apiTypes.ts`.

**The halt.** `mrReworkHaltCommentBody` gains one sentence naming the manual path ("To run one more cycle yourself, open the run in uzi and press Rework now, or run `uzi run rework <run-id>`; on-demand cycles do not count against this limit."). `notifyHalt` passes `RunID: &cand.SourceRunID` so the inbox row links to the run page. The `CIAutofixPayload.Reason` text is unchanged.

`CreateAutoMRReworkRun`'s doc comment loses "there is no manual mr_rework trigger (Decision 13)" and points here.

### Agent

Nothing. The guidance rides `issue_description`, which the worker already renders as data inside the `<issue_description>` fence, and `MR_REWORK_LIFECYCLE_APPEND` already governs re-replies. `trigger_source` is not read by the worker.

## Decision log

- **D1: a manual cycle never counts against the automatic cap.** The cap bounds unattended spend; a human pressing the button is attended and spends their own token. Counting it would make the button fail exactly when it is needed (at the cap). The ledger's own comments already say `attempt_count` is automatic-only. Rejected: a second cap on manual cycles (the owner's token is the bound, as for `run create`).
- **D2: policy gates skipped, correctness guards kept.** Skipped: the cap, the debounce, the head-SHA staleness check, the green pipeline (the owner knows the state of their MR; a rework on a red pipeline is a legitimate choice, and its push runs CI anyway). Kept: the cross-kind branch guard and the one-active-rework index (two runs in one worktree is a correctness failure), the admin kill-switch (the instance decides whether the feature exists), the token check (a doomed run helps nobody), the open-MR check (the write-back has nowhere to land), the source run's branch being present (a nullable/empty branch would create a manual run that fails at worker claim assembly; refused with a typed 409 before create — a !1207 review hardening). The per-user and per-run opt-outs mean "do not do this unasked"; a manual trigger is asked, so they do not apply.
- **D3: the snapshot is the full kept set, the trigger is "new actionable comment or guidance".** The forge type carries no resolved flag, so "every unresolved finding" cannot be built without touching three drivers. The automatic path already ships the full snapshot and relies on the worker's lifecycle prompt to skip findings addressed in a prior cycle; the manual path does the same, so the two runs are shaped identically and the worker sees the whole thread when guidance refers to an older finding. To re-do a finding an earlier cycle skipped, the owner posts a comment on the MR (a human top-level note is actionable) or names it in the guidance. Rejected: a per-comment "consumed" marker in the snapshot (a struct change with an agent mirror, for a case guidance covers); an `--all` flag (a second semantics to document for the same outcome).
- **D4: auto-approved, no plan gate.** The manual Fix CI parks at the gate because a CI fix may touch CI configuration, which the guard exists for. A rework has no such dimension, the owner has just read the findings, and the automatic path is already gate-less (PRD #700 Decision 1). A gate would add a round trip to a run whose plan is the findings list.
- **D5: `RequireUser`, so the CLI verb works.** `uzi run create` and `uzi schedule run-now` already mint token-spending runs from a `uzc_` Bearer; the cookie-only `rejudge` was an audit decision about the judge lane, not a rule that spend mints are cookie-only. Owner-scoped in SQL, 404 for a foreign run, router-level auth test as the sibling verbs have.
- **D6: guidance rides the description through the existing composer.** One header format on every surface that carries owner steering; the worker needs no new field and no new fence. The composer moves to (or is re-exported from) `workersvc` so `schedsvc` and the handler read one function; its byte-asserted tests stay valid because the join is unchanged. Rejected: a `guidance` column on `runs` (a migration for text the description already carries).
- **D7: `trigger_source = 'manual'`.** The column exists for exactly this, the CHECK admits the value, and `run get` already prints it, so the two kinds of rework are distinguishable in every listing and in usage folds without a new column.
- **D8: a new verb, `uzi run rework`, not a flag on `uzi run mr-rework`.** The existing verb is a tri-state setter; `--now` on a setter reads as "apply the setting now". The action verbs (`expedite`, `resume-now`, `revise`) are their own commands, and `-m` is what a steer message is called on every run verb.
- **D9: a manual cycle resets the halt latch.** `halt_notified` is one comment per halt episode; a manual cycle is a new episode, so a genuinely-new comment that hits the cap afterwards is announced once more rather than silently refused. Mirrors what the automatic proceed does.
- **D10: the halt text names the button and the verb, and the notification links to the run.** #813's item 3 asks that the cutoff not be a dead end; pointing at the manual path is the half that needs no new UI. Listing the remaining findings in the comment stays with #813.
- **D11: the cycle count is on the run DTO, owner-only.** Without it the owner cannot tell why the watcher stopped from the run page. Two nullable fields, one PK read, null for a non-owner; a `GET /runs/{id}/mr-rework` endpoint for two integers would be dead surface.
- **D12: the web toggle widens to the three watched kinds.** A found stale doc (`mrRework.ts:17` still says issue-only) and a real gap: the server honours the per-run override on `prompt` and `self_improve` runs since PRD #908, and the web hid the control. Fixed in the same milestone because `canReworkNow` is built on the same predicate.
- **D13: TUI and Slack are read-only for this feature.** The board is triage; a rework is a run-page action. The halt already reaches the inbox, and a Slack nudge is a follow-up if the inbox proves too quiet.

## Success criteria

- On an MR at the cap, **Rework now** with guidance starts an `mr_rework` run within one request: `trigger_source = manual`, the guidance in its description, the automatic cycle count unchanged before and after, and the next poll tick starts nothing on the same comments.
- The same trigger from `uzi run rework <id> -m '…'` with a `uzc_` token produces the same run; `--json` returns the `{"run": …}` envelope; a second call while the first is running exits 5 with the server's message.
- A trigger on a run that is not completed, has no MR, whose MR is merged, whose owner has no token, or on an instance with the kill-switch off, is refused with a message naming why; a bare trigger with nothing new and no guidance is refused the same way.
- A `prompt` run's page now shows the rework toggle; a completed `prompt` run with an open MR shows **Rework now**.
- The cap halt comment names the button and the verb, and the inbox row for the halt opens the run page.
- `task gate` green; no migration; no workflow file in the diff.

## Risks

- **Merge adjacency with PR #1200 (pause/resume) and PR #1203 (themes).** #1200 touches the generated `store/mr_rework.sql.go` (its four new `runs` columns regenerate every `… FROM runs` statement), `run_limits.go`, `run.go`, `apitypes/run.go`, `api.ts` and `RunView.tsx`; #1203 touches `RunView.tsx`. Whichever of #1200 and this PRD lands second must run `sqlc generate` against the merged schema on its landing rebase rather than resolve the generated file by hand, and its `run.go` verb registration and `run_limits.go` verb will conflict textually with the pause verb; `apitypes/run.go` and the api-contract fixtures must be re-recorded after the rebase, not merged. The web collisions are adjacent-line textual and resolve in the rebase.
- **`GetRepoForUser` is keyed on the caller, not the run.** The run's `repo_id` is loaded for its owner; a run the caller owns on a repo they no longer own reads as 404, which is the correct answer. The test suite should pin it rather than let the handler take the run's `user_id` as the repo lookup key.
- **Guidance is owner-authored but still rendered as data.** It enters the same `<issue_description>` fence as an issue body; nothing in the worker treats it as an instruction channel with more authority than the issue text. The 8 KiB cap keeps the description under `MaxIssueDescriptionBytes`.
- **The high-water is still one scalar (#1199).** A manual advance can skip a new inline comment whose id is below a consumed issue-comment id, exactly as the automatic path can. Fail-safe (the finding falls back to human review), unchanged by this PRD, and guidance is the owner's way around it.
- **Moving the composer.** `composeRunDescription` has byte-asserted tests in `schedsvc`; re-exporting from `workersvc` and keeping a one-line delegate in `schedsvc` keeps them green. Do not change the join.
- **The skill-drift test.** `TestSkillMatchesCommandTree` (`api/cmd/uzi/skill_drift_test.go`) pins `SKILL.md`'s command block to the cobra tree in both directions; the M3 verb line must match the block's exact formatting, and any `--flag` the bullet names must exist on the command.
- **`sqlc generate` needs the module proxy** (see PRD #1170's Risks for the offline hand-edit shape). The change is one added argument and one new `:exec`; the hand-edit is small if the proxy is unreachable.
