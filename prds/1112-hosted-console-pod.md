# PRD #1112: Hosted console pod (a human-driven elevated agent seat in the cluster)

**Issue**: [#1112](https://github.com/vtmocanu/uzi/issues/1112) · **Labels**: brainstorm, PRD · **Priority**: Low (design spike; not a committed PRD)
**Status**: Brainstorm draft, 2026-09-05. M0 is a go/no-go gate for everything after it.
**Depends on**: [#1106](https://github.com/vtmocanu/uzi/issues/1106) (Codex harness phase 1) for the Codex half only; the Claude half has no dependency.
**Related**: [ADR-285](../adr/0285-worker-egress-tier-trust-model.md) (the two worker tiers this adds a third to), `docs/hosted-workers.md`, `docs/worker-docker.md`, `docs/vault-threat-model.md`.
**Area**: `deploy/chart` (a new `console` tier) · `controller/` (reconcile a console per user) · `api/internal/store`, `api/internal/handler` (gate, join token, heartbeat, credential hand-over) · a new console image under `deploy/` or `agent/templates/` · `web/src/pages/WorkersSettings.tsx` (Console tab) · `web/nginx.conf` (Orca pairing proxy) · `api/cmd/uzi/` (CLI parity) · `docs/`.
**Line references** are against `92a6e60` (main, 2026-09-05).
**Scope guard**: no `.github/workflows/**` change in implementation or validation (`.claude/rules/prds.md`). The console image build is a maintainer-local CI issue if one is needed.

## Problem

uzi's run lane is deliberately unprivileged, in four independent layers: the forge role plus protected branch, the worker holds the PAT and the agent never does, the `PreToolUse` deny hook in `agent/src/guardrails.ts` (`REASON_PUSH`, line 140: "the worker opens MRs; the agent never pushes"), and `settingSources: []`. Egress is fenced per tier (ADR-285). That is the primary directive, `main` is never touched, and none of it changes here.

The work that closes the loop is privileged and still happens on one laptop: admin-merging a reviewed MR past branch protection, cutting a release (a `v*` tag publishes images, chart, Release and formula unattended), recovering a run's branch off a worker volume, running a gate against a branch, steering a stuck run from a real shell. That session is a human driving Claude Code with the human's own credentials. Today it exists only where the laptop is, so it cannot be picked up from a phone, survives no laptop sleep, and its tool set (kube contexts, forge CLIs, `task`, the pinned toolchains) is reassembled by hand on every machine.

Two client surfaces already exist for driving such a session remotely, and neither needs uzi to be an IDE:

- **Claude Code Remote Control** connects the Claude iOS/Android app or claude.ai/code to a Claude Code process running anywhere, outbound-only.
- **Orca** (MIT) is a desktop and mobile client for a headless runtime that owns worktrees, terminals and agent accounts (Claude and Codex), reachable over a paired WebSocket endpoint.

What is missing is the seat: a per-user pod in the cluster with the tools, the user's own credentials, an interactive agent process kept alive, and a way to reach it that adds no public port.

## Solution

An optional **console** pod per user, provisioned by the controller on clusters an operator marks as trusted, gated three times exactly like ephemeral workers (`deploy/chart/values.yaml:184-189`): chart flag, then admin setting, then per-user opt-in. The pod runs an interactive Claude Code session (Codex after #1106) on the user's own forge credential, inside tmux, with a human driving every step. Two client transports ship, as alternatives the user picks per console, not one or the other:

- **A. Claude Code Remote Control** (default). The pod runs `claude remote-control` in server mode. Traffic is outbound HTTPS to Anthropic; nothing is exposed. The Claude app sends messages, approves tool calls, and shows the diff. Requires a claude.ai subscription login (API keys are not supported), so M0 establishes whether the OAuth token uzi already stores satisfies it.
- **B. Orca** (opt-in). The pod runs `orca serve` with a pairing address that points at a uzi-proxied `wss://` path; `web`'s nginx forwards `/console/<id>/` to the pod's Service only for the owning uzi session, and Orca's own per-client pairing token is the second lock. The Orca desktop and mobile apps pair to that endpoint with no desktop kept open. Orca's mobile app is a remote control (reply to prompts, quick commands, source control), not a free-typing terminal; that is the documented product shape, not a gap this PRD closes.
- **Shell fallback, both transports**: mosh or SSH inside the pod, reached only through a tunnel the operator chooses (a tailnet sidecar or a port-forward), never a Service of type LoadBalancer or NodePort. This is where the human types what the agent must not: the release tag push, and anything against a kube context.

It is a **third tier** next to restricted and docker: a human seat, not an agent seat. Its egress is broad but named, its credential is in the human's hands, and it never reuses the run lane, the worker image, the run state machine or the claim path. In ADR-285's discipline, every egress measurement must now name one of three tiers.

### What this is not

- Not a change to any guardrail layer of the run lane. The console is a different pod, image, namespace and codepath; a reader who finds run-lane code branching on "console" has found a defect.
- Not uzi as an IDE. The editor and the terminal UI are Claude's app and Orca's client; uzi provisions, gates, hands over credentials, shows the connection coordinates, and audits start/stop.
- Not an elevation grant. uzi mounts the user's own forge PAT; what that PAT can do is decided by the human's role on the forge, exactly as on the laptop.
- Not unattended. Permission mode stays `default` (approve each tool call); `bypassPermissions` is refused by the supervisor. An autonomous run is what the run lane is for.

### Out of scope

- Multi-user consoles, shared consoles, console-to-console messaging.
- Any kube credential inside the console (Q3). Recovering a run off a worker volume stays a maintainer-local recipe until that question is settled.
- Orca Relay (Orca's cloud relay). It routes terminal data through a third party; the proxied pairing endpoint makes it unnecessary.
- Compose. A laptop already is the console; this is a hosted-only feature, and the chart is the only install path.
- Codex in the console before #1106 lands the Codex credential kind and image.

## Verified facts (2026-09-05)

Each fact names its source so an implementer can re-verify. Facts marked *offline* need no network.

**Orca** (installed 1.4.196 on the maintainer's machine, its bundled `LICENSE`, the public docs at onorca.dev, and the public repo):

1. **License is MIT** (*offline*). `app.asar` bundles `LICENSE`: "MIT License, Copyright (c) 2026 Lovecast Inc." The public repository is MIT. Bring-your-own-subscription; no fee, no proxy layer.
2. **Headless runtime exists** (*offline*, `orca serve --help`). Flags: `--port`, `--pairing-address <host|wss://url>`, `--mobile-pairing`, `--no-pairing`, `--project-root`. The help text says the pairing address may be "a reachable LAN, Tailscale, SSH-forward, or reverse-proxy endpoint" and gives `--pairing-address wss://sandbox.example.com` as an example, so a reverse-proxied `wss://` path is a documented deployment shape. Clients authenticate with a pairing link that Orca says to treat like a password; each paired client gets its own revocable token. The docs say not to forward the Orca port to the public internet.
3. **Server owns, client renders.** Per the remote-servers docs the server owns repositories, worktrees, terminals, agent sessions, provider accounts, browser state and the filesystem; a client owns UI and input delivery. A headless server therefore replaces tmux for Orca-managed terminals; tmux is still needed for transport A.
4. **Mobile app is read-mostly.** The mobile docs call it "intentionally not a full editor, it's a remote control": agent status, scrollback, replying to prompts (text, dictation, photos), file browsing, source control, account switching, saved quick commands. No continuous terminal typing. iOS on the App Store, Android as an APK, both marked beta.
5. **Desktop-free mobile pairing is contradicted between two docs pages.** The remote-servers page says the mobile app pairs directly to `orca serve --mobile-pairing`; the mobile page says the desktop must stay open; issue #10426 (opened 2026-07-24, open at writing) asks for exactly the desktop-free path. The 1.4.196 binary carries the flag. **M0 settles this by measurement**; the PRD does not assume it.
6. **Accounts are per host.** `orca account add [--agent claude|codex]` runs `claude login` / `codex login` on the host and registers the account with the runtime; Codex uses device authorization, so it completes from another machine. Claude's login expects a browser, so the console seeds Claude from the stored OAuth token instead (D3).

**Claude Code Remote Control** (official docs page, read 2026-09-05):

7. **Plans and auth.** Available on all plans; subscription login only, "API keys are not supported". On Team and Enterprise it is off until an Owner enables the toggle in admin settings; an incompatible data-retention configuration greys the toggle out. `claude remote-control --help` checks eligibility before printing help, so on an unauthenticated host it errors (or, measured here, hangs long enough to be killed) instead of listing flags.
8. **Transport.** "Your local Claude Code session makes outbound HTTPS requests only and never opens inbound ports"; it registers with the Anthropic API and polls. The transcript, including tool activity, is stored on Anthropic servers while connected, to keep devices in sync and to reconnect. Requires port 443 to the Anthropic API from the pod.
9. **Server mode.** `claude remote-control` stays in the foreground, prints a session URL and a QR code, and serves several sessions; `--spawn worktree` gives each on-demand session its own git worktree; `--permission-mode` sets the starting mode; `--name` titles the session. Sessions of a stopped server can be brought back for about four hours with `--continue` or `--session-id`. Global `claude` flags before `remote-control` are mostly refused (only ones like `--verbose` and `--model` pass through), so per-session settings must come from the settings files, not the command line.
10. **Process must live.** "To keep a session running on a remote machine after you disconnect from SSH, start it inside tmux or screen." A crashed session in server mode is re-served on the next message. Permission prompts and `AskUserQuestion` stay open until answered; other forwarded dialogs expire after five minutes to their no-action default. The Fable usage-credits consent prompt is **not** forwarded and appears only in the terminal.

**uzi, in-repo** (*offline*):

11. **The triple gate already exists** for ephemeral workers: `deploy/chart/values.yaml:184-189` states "requires hosted-worker hosting enabled AND the admin DB setting `ephemeral_workers_enabled` AND the per-user opt-in"; `users.ephemeral_workers_enabled` and `users.judge_enabled` are the per-user columns (`api/internal/store/models.go:637` and the `users` column list). The judge is the precedent for "off by default, gated twice (admin globally, then per user)".
12. **The controller is the only kube-credentialed component**, scoped to namespaces that contain nothing but hosted workers (`controller/cmd/controller/main.go:51-54`), and it already takes a second, optional namespace for the docker tier (`main.go:71-72`, `WorkerDockerNamespace`, empty = off). A third optional namespace follows that shape.
13. **Egress templates to copy**: the default-deny floor `worker-networkpolicy.yaml`, the FQDN allowlist `worker-fqdn-egress.yaml` (renders `allowFQDNs` plus the forge hosts single-sourced from `forge.allowedBaseURLs`, and fails the render when that list is empty), and the docker tier's CIDR policy. `worker-invariants.yaml` is the pattern for refusing an unsafe combination at render time.
14. **`web` is the only published port** and its nginx has exact-match `location = /api/ws` for the run WebSocket and `location /api/` for the REST proxy (`web/nginx.conf:30-47`). A `/console/<id>/` WebSocket location with `auth_request` against the api is the same mechanism.
15. **Workers authenticate outbound with a join token** (sha256 stored, shown once; `api/internal/hostedsvc/service.go:62`), and the hosting status endpoint already reports an `enabled` flag to the UI (`api/internal/handler/hosted_workers.go:318`). The console heartbeat channel reuses the shape.
16. **The Bash screener is reusable as a plain hook.** `agent/src/guardrails.ts` documents the wrapper and `-C`/`-c` evasions it closes (lines 17-38, 250-251, 521). Claude Code's `PreToolUse` command hooks receive the same tool input JSON as the SDK hook, so a "console profile" of the screener can run from `~/.claude/settings.json` in the console without the SDK.

## Decision log

- **D1: a third tier, fully separate.** Own namespace (`console.namespace`), own image (`console.image`), own NetworkPolicy, own quota and PVC, own reconcile loop in the controller, off by default (`console.enabled: false`). Rationale: a sidecar in the worker pod would share the network namespace and volume with an unprivileged agent process, defeating the tier-qualified egress model and putting an elevated credential one mount away from the agent; and the worker roll loop (cordon, drain, roll) must never touch a human's live session. The console image is not the worker image; it starts from the same base pins but adds tmux, mosh-server, the forge CLIs, `task`, and Orca.
- **D2: the ephemeral-workers gate, verbatim.** Chart `console.enabled` and hosting enabled (the controller must run), then admin setting `console_enabled` (PUT /settings), then `users.console_enabled`. The Workers page shows a Console tab only when all three hold, and the api's hosting status reports `console.enabled` so the UI never guesses. "Trusted cluster" is the chart flag: an operator decision the UI can display but not make.
- **D3: credentials are the user's own, handed over as files, never as env.** The connected forge PAT (already sealed in `secretbox`) is written to a 0600 file consumed by a git credential helper and the forge CLI's token-from-file login; it is on the deny list of the console's Bash screener (D7). The Anthropic side seeds from the stored OAuth token; if M0 finds Remote Control rejects it, the user completes a one-time `claude login` from the mosh shell and the resulting credentials file persists on the console PVC as user data. Codex (after #1106) seeds `CODEX_HOME/auth.json` the same way the worker does, and the console's refresh write-back reuses #1106 D4. uzi never mints a broader token than the user connected; a separate elevated-PAT secret kind is Q1.
- **D4: transport A is Remote Control, in server mode, in tmux, and it is the default.** The pod's supervisor starts `tmux` and inside it `claude remote-control --spawn worktree --permission-mode default --name <repo>`; the session URL and QR are read from the server's output and posted to the api over the console join token (D9), stored sealed on the console row, shown only to the owner, and rotated whenever the server restarts. The URL is a credential and is treated like one: never logged, never in an event row. Rationale: zero ingress, approvals from the phone, and the reconnect story is Anthropic's.
- **D5: transport B is Orca behind uzi's own front door.** `orca serve --port <p> --pairing-address wss://<uzi-host>/console/<id> --mobile-pairing` in the pod; nginx location `/console/<id>/` proxies WebSocket upgrades to the console Service after an `auth_request` to `GET /api/console/<id>/authz` that passes only for the owning session. Orca's pairing token is the second lock. Orca Relay is disabled and its hosts are not in the egress list. The pairing link is surfaced in the UI exactly like D4's URL. If M0 fact 5 measures that mobile still needs a desktop, transport B ships desktop-only and the PRD says so.
- **D6: egress is broad but named, and never `0.0.0.0/0`.** The console FQDN allowlist is: the forge hosts (single-sourced from `forge.allowedBaseURLs`, as the worker template does), `*.anthropic.com`, the package caches the worker tier already lists, the container registry the chart publishes to (release verification), and the OpenAI API hosts once #1106 lands. Operators add to `console.fqdnEgress.allowFQDNs` per cluster. Rationale: the human is the residual, but a prompt-injected elevated Claude is the threat, and the allowlist bounds where it can send what it read.
- **D7: the console keeps one deny hook, for what a phone should never approve.** A `PreToolUse` command hook, the Bash screener in a console profile, denies: any `git push` whose refspec touches `refs/tags/` or carries `--tags`; force and history-rewriting pushes; reads of the credential files from D3; `git config --get` on the credential helper. Ordinary pushes, merges through the forge CLI, and gate runs are allowed. The human types a tag push in the mosh shell. Rationale: a tag push publishes unattended and the harness classifier already blocks it on the laptop; approving it from a phone with the diff pane closed is the failure this hook prevents.
- **D8: one console per user, sleep instead of delete.** The console is a stable-identity pod with a retained PVC. After `console.idleSleepAfter` (default 4h with no connected client and no running tmux command) the controller scales it to zero; the UI and CLI wake it. Delete is explicit and removes the PVC. The console is not part of the worker fleet roll: `console.image.tag` is its own pin and a roll waits for an idle console.
- **D9: the api provisions nothing.** The api writes desired state (`consoles` rows: owner, transport, state, image tag) and the controller reconciles them, exactly the hosted-worker split. The console pod talks back over a join token (sha256 stored, shown once) on `/api/console/*`: heartbeat, connection coordinates, connected-client kind, session start/stop. No cookies, no CSRF on that prefix, as for `/api/worker/*`.
- **D10: audit is coordinates, not content.** `console_events` records start, sleep, wake, delete, transport chosen, client connected/disconnected (kind only), and hook denials with the denied command's first token. It never records transcripts, commands, or URLs. Transcript custody is stated in the docs: Anthropic servers for transport A while connected, the pod's own storage for Orca.
- **D11: CLI parity.** `uzi console start|stop|sleep|wake|status|url [--transport claude|orca]`, and `uzi console delete` with confirmation. `docs/cli.md` gains the group.
- **D12: the primary directive's wording gets an ADR, not an edit.** "`main` is never touched" is a property of the run lane. The console is a human seat where the human touches `main` on purpose, with their own credential. ADR `adr/1112-console-tier.md` <!-- check-docs:ignore-path: created by M0 --> records the tier, its trust direction, and that no run-lane guardrail may be reused as a reason to weaken the console's, or the reverse.

## Success criteria

1. **Run lane untouched**: no file under `agent/src/` used by the run lane changes behaviour; `agent/test/` is unchanged except for the new screener-profile fixtures; every existing gate green.
2. With `console.enabled: false` (the default) nothing renders, no endpoint exists, and the Workers page shows no Console tab. Each of the three gate legs off, independently, hides the feature.
3. A user with the full gate creates a console, scans the QR from the Workers page with the Claude app, and approves a tool call from the phone; the pod has no Service of a type other than ClusterIP and no ingress except the nginx path.
4. The same console, on transport B, pairs the Orca desktop app through `/console/<id>/`; a non-owner session gets 403 from the authz endpoint and the WebSocket never upgrades.
5. Claude attempting `git push origin v1.2.3` (and `--tags`, and a force push) inside the console is denied by the hook with the denial recorded in `console_events`; the same command typed in the mosh shell succeeds, because the human is the authorization.
6. The console's egress is bounded by its allowlist: an off-list host times out from the pod, measured on the console tier and labelled as such.
7. Sleep after idle, wake from UI and CLI, and the PVC survives both; a worker fleet roll leaves a busy console alone.
8. No transcript, command line, or URL appears in `console_events` or the api logs; `scan:secrets` is green with the join-token and PAT fixtures assembled at runtime.
9. Nothing under `.github/workflows/` changes in any commit of this PRD.

## Risks

- **R1: credential blast radius.** The console holds a PAT that can merge to `main` and, if it has the bypass role, create a release tag. Mitigations: the credential is the user's own and no broader than what they connected (D3); the tag-push hook (D7); permission mode `default` and no bypass (Solution); egress allowlist (D6). Residual: a human approving a bad merge from a phone, which is the same residual as on the laptop.
- **R2: prompt injection into an elevated seat.** The console's Claude reads MR diffs, review comments and issue text written by others. Mitigations: every tool call is approved by the human; the repo's own `.claude/` loads only because the user owns it (`settingSources` limited to the user scope for any other repo); D6 bounds exfiltration targets; D7 bounds the irreversible action.
- **R3: Orca is a moving target.** The mobile app is beta and the desktop-free pairing story is contradicted between its own docs pages (fact 5). Mitigations: M0 measures before any code; transport A carries the feature alone if B slips; the console pins `console.orca.version` and Orca's self-update hosts stay off the allowlist.
- **R4: Remote Control depends on Anthropic's relay and account policy.** Team and Enterprise need an Owner toggle; an incompatible retention setting disables it entirely; transcripts are stored server-side while connected. Mitigations: the docs state all three plainly; the shell fallback and transport B need neither.
- **R5: cost and cluster load.** A console is a long-lived pod with a PVC per user. Mitigations: sleep after idle (D8), a per-namespace quota (M1), the admin gate to cap who may have one.
- **R6: the seat drifts into an IDE.** Requests will follow for editors, port-forwards, previews. Mitigation: the "What this is not" section and D12's ADR; anything beyond provisioning, gating, hand-over, coordinates and audit is a new PRD.
- **R7: the deny hook is bypassable by design.** The human owns the shell, so the hook only stops the agent, not the person. That is the intent; the risk is a future "let Claude push the tag, I am watching" flag. Mitigation: SC5 pins the behaviour and D7 states why.

## Open questions

- **Q1**: a separate `console_forge_pat` secret kind (an elevated token distinct from the connected one) versus reusing the connected PAT. Proposed: reuse, plus a scope warning from M0(b); a distinct kind only if the connected PAT routinely lacks `workflow`.
- **Q2**: sleep policy details: does an open Remote Control session with no activity count as idle? Proposed: idle means no connected client for the period, so a phone left connected keeps the console awake.
- **Q3**: whether a console may ever hold a kube credential (for run recovery off a worker volume). Proposed: no in this PRD; if yes later, a read-only Role scoped to the worker namespaces and its own ADR.
- **Q4**: whether Orca's update channel and telemetry can be disabled by configuration in a headless server; if not, the egress denial is the control and the docs say so.
- **Q5**: where the console image is built and published. It touches CI, so it is a maintainer-local issue cross-linked here, not a milestone of this PRD.
