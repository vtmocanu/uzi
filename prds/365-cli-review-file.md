# PRD #365 — `uzi review file`: file a judge recommendation as a forge issue from the CLI (and fix `uzi findings file`/`dismiss`)

- **Issue**: [#365](https://github.com/vtmocanu/uzi/issues/365)
- **Priority**: Medium
- **Status**: Draft — not started
- **Forge scope**: All forges (GitLab, Forgejo, GitHub). The change is in auth-tier mounting and the CLI; filing itself reuses the existing driver-neutral `CreateIssue` path, so nothing here is forge-specific.
- **Handoff**: queued for the `Night-Shift` uzi sweep (offline worker). This PRD is entirely codebase-local — no milestone needs open-web access. Live-DB tests use the repo's throwaway-Postgres harness (`./e2e/run-store-it.sh`), which is local, not internet.

---

## Problem

Filing a judge recommendation, or an incidental finding, as a forge issue is **web-only** today, and the CLI surface for it is inconsistent and partly broken:

- **`uzi review` has no `file` verb.** Its verbs are `show / backlog / resolve / dismiss / undo / stats` (`api/cmd/uzi/review.go`, `newReviewCmd` → `cmd.AddCommand(...)` ~:200). Filing a rec is only reachable from the web board.
- **The server route for review-rec filing exists but is cookie-only.** `POST /api/runs/{id}/review/recommendations/{recID}/issue` → `Handler.FileIssue` (`api/internal/handler/review_issue_file.go`) is mounted on the **cookie+CSRF `RequireAuth`** group (`handler.go` ~:1151–1162). The uzicli client authenticates with a **Bearer CLI token only** (`api/internal/uzicli/client.go` `newRequest` ~:393–408 sets `Authorization: Bearer …` and nothing else — no cookie jar, no CSRF), and `RequireAuth` accepts **only the JWT cookie** (`api/internal/middleware/auth.go` `RequireAuth` ~:39–63). So a CLI token cannot reach the review filing route at all.
- **`uzi findings file` and `uzi findings dismiss` are shipped but broken from the CLI.** Both commands exist (`api/cmd/uzi/findings.go` `newFindingsCmd`) with client methods (`FileFinding`, `DismissFinding` in `client.go`), but their routes — `POST /api/findings/{id}/issue` (`FileFinding`) and `POST /api/findings/{id}/dismiss` (`DismissFinding`) — are both in the findings **writes** group on `RequireAuth` (`handler.go` ~:691–695). A CLI Bearer request to either returns **401**. This is a latent bug: a shipped CLI command cannot reach its own route.
- **Inconsistency with review's own triage.** Review's `resolve / dismiss / undo` (`SetDisposition` / `DeleteDisposition`) are already on `RequireUser` (`handler.go` ~:1142–1143) and work from a CLI token. So review can triage from the CLI but not file; findings can neither file nor dismiss from the CLI. There is no principled reason for the split — it is an artifact of how the two features were mounted.
- **Manual `gh issue create` loses linkage.** Filing a rec by hand produces a standalone issue that is **not** recorded under the review's `filed_issues` and does **not** move the rec to the `filed` bucket, so it shows unlinked in-app and the rec stays `todo`. (Real instance: judge rec "lint ratchet stale origin main mirror false red backlog" had to be filed manually as issue #363, which is unlinked.)

## Solution overview

Two changes, both small:

1. **Move the filing routes to the CLI-reachable auth tier.** Move `FileIssue` (review), `FileFinding` (findings), and `DismissFinding` (findings) from the cookie-only `RequireAuth` group to the `RequireUser` group, keeping the forge limiter on the two forge writes and no limiter on the local dismiss. `RequireUser` **accepts both** a browser session cookie **and** a Bearer CLI token via **presence dispatch** (`api/internal/middleware/cli_auth.go` `RequireUser` ~:13–49): a request with an `Authorization: Bearer` header takes the CLI-token path (owner-scoped, admin→owner masked), and any other request takes the unchanged cookie path **with CSRF still enforced**. So the browser filing UX is byte-identical and gains no CSRF hole, while the CLI gains access. This is the exact tier the findings *reads*, review's *dispositions*, and `CreateRun` already use.

2. **Add `uzi review file <run-id> <rec-id>`.** A new verb that mirrors `uzi findings file`: it files with **server-templated defaults**, assembled from the existing issue-draft endpoint (`GET …/issue-draft` → `IssueDraftDTO{ DefaultRepoID, Title, Description }`, already `RequireUser`/CLI-reachable, `api/internal/handler/review_issue_draft.go` ~:137–140), then POSTs them to the filing route. Filing through the real handler gives the in-app linkage for free (the handler claims the coordinate, files, and records it under `filed_issues`, moving the rec to the `filed` bucket).

The token-mint, worker-mint, forge-connection PAT write, and unattended-spend consent routes (autopilot / judge / wait-on-limit / rejudge) **stay cookie-only** — this change is scoped to issue filing and a local dismiss only.

## Security decision: why moving these routes off cookie-only is safe

The stated invariant is "a CLI token cannot drive a forge write" (`handler.go` findings-writes comment; `cli_auth_livedb_test.go`). Loosening it **for issue filing specifically** is justified and bounded:

- **Filing reveals no secret.** The routes that must stay cookie-only do so because they mint or reveal credentials (`POST /workers` returns a claimable token yielding the decrypted PAT + Anthropic token — Decision 18; `POST /forge/connections` writes a bot PAT; `DELETE /me/secrets/anthropic_token` is a factory kill). Filing an issue on the user's **own already-connected forge** exposes none of that.
- **A CLI token can already do the costlier thing.** `POST /repos/{id}/runs` (`CreateRun`) is `RequireUser`/CLI-reachable (`handler.go` ~:1013) and **spends the user's Anthropic budget** by queuing agent runs. A stolen token that can spend money is a strictly larger exposure than one that can also file a labeled issue.
- **Be precise about what this changes, though.** `FileIssue`/`FileFinding` perform a **synchronous, in-request** forge write (`CreateIssue`, plus `EnsureLabels` for findings). `CreateRun`'s forge writes happen **later, via the worker's PAT**, not in the request. So this is the **first direct in-request forge write reachable on a Bearer path**, which makes the blanket phrasing "a CLI token cannot drive a forge write" literally false rather than merely narrowed. That is acceptable given the bounds above, but the doc updates (M4) should state the new rule as "a CLI token can drive issue *filing* (rate-limited, owner-scoped, reversible) but still cannot mint/reveal credentials or trigger unattended spend", not silently drop the old absolute.
- **Bounded and reversible.** The two forge writes keep `forgeLimiter.PerUserMiddleware` (per-user rate cap), are owner-scoped (a foreign run/finding/repo is a 404), and produce a labeled issue that is trivially reversible (close it). The findings dismiss is a local DB write with no forge blast radius.
- **No CSRF regression.** `RequireUser` preserves CSRF on the browser path via presence dispatch; the CSRF-bypass-shape test already pins this behavior.

## Risks and mitigations

- **Perceived security loosening** → scoped to issue filing + a local dismiss, justified in the Security Decision above (no secret revealed; costlier `CreateRun` already CLI-reachable; rate-limited, owner-scoped, reversible). The mints/reveals/consent switches stay cookie-only.
- **CSRF regression on the browser path** → `RequireUser` preserves CSRF via presence dispatch; a milestone-3 test asserts a cookie POST without the CSRF header is still 403.
- **Empty default repo for a rec** (ambiguous default, e.g. a global `improve_uzi` rec with multiple connected repos) → the CLI surfaces the draft's note and requires `--repo`, never guessing which repo to file against.
- **Draft/file two-step race** (the rec changes between the draft GET and the file POST) → the file handler re-reads and re-sanitizes server-side and is claim-first (409 on a concurrent file), so the CLI's composed body cannot bypass any server check; the two-step is exactly what the web already does.
- **Stale doc/comment drift** → the deliberately-placed auth comments at the mount sites and in `cli_auth_livedb_test.go` are updated in the same change (repo rule: correct a doc the moment the work disproves it).

## Dependencies

- Existing seams only: the `RequireUser` middleware, `FileIssue` / `FileFinding` / `DismissFinding` handlers, the review and findings issue-draft reads, and the uzicli client/command scaffolding. No new migration, no new dependency, no cross-repo change.

## Out of scope

- A group/bulk form of `uzi review file` (filing N issues from a backlog coordinate) — filing is one issue per rec, matching the web; the group form stays for `resolve`/`dismiss` only.
- Editing the draft before filing from the CLI (title/description/labels) — that remains the web's rich-editor job; the CLI files server-templated defaults (with an optional `--repo`), exactly as `uzi findings file` does.
- Moving any credential-minting, credential-revealing, or unattended-spend consent route off cookie-only.
- Any change to the web filing UX.
