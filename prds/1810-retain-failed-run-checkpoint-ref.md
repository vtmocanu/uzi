# PRD #1810: Keep a failed run's checkpoint ref while its recovery is open

**Issue**: #1810
**Status**: In progress (M1-M4 implemented; M5 live acceptance pending)
**Priority**: High
**Created**: 2026-09-27

Split out of PRD #1809 (worker disk safety), which covers why the run failed. This PRD covers why its work was nearly lost.

## Problem

An issue or self-improve run publishes checkpoints to origin at `refs/uzi-checkpoints/<branch>` through the api push broker (`api/internal/pushbroker/pushbroker.go`). On a terminal transition the api deletes that ref, best-effort (`deleteCheckpointBestEffort`, PRD #1030 M4), from three call sites: `api/internal/workersvc/service.go` ~4080, `api/internal/workersvc/submit.go` ~425 and ~630. The reason is sound for a completed run: a stale ref would later block a new run on the same branch with a `not_descendant` skip.

**Amendment (M4 implementation):** the ref delete was only ever called from those three sites, but a run can go terminal through at least seven other writers that never touched it: `FailRunsOfStaleWorkersOverCap`, `FailWorkerRunsOverCap`, `FailRunsMissingFromSnapshot`, `MarkRunFailedByID`, `FailRunAutoStop`, `FailClaimAssemblyExact` and `FailCodexAccountWaitRun`. Under the old best-effort-delete design that was merely an inconsistency (a leaked ref, harmless). Under the retention design it would have been a coverage gap (a terminal run at one of those sites gets no `checkpoint_retentions` row at all, and its custody hold's ref location is never tracked). The sweeper's backfill arm (M4) closes this: it scans terminal runs with a published checkpoint and no record, on a persisted watermark, and records them exactly as the original three call sites would have.

For `failed` and `cancelled` it removes the wrong thing. A few lines above the `service.go` call, the same code deliberately keeps custody holds open for failed and cancelled runs ("those retain custody for capture or explicit discard"). So uzi keeps custody of the run's work while deleting the one copy of it that lives off the worker. The helper's comment names the worker's `refs/uzi-runner/*` as the primary recovery path, but that path is gone whenever the worker is ephemeral, its volume is lost, or it is unreachable.

Observed on 2026-09-27 on the issue #1798 run:

- 11:06 UTC: `checkpoint published to origin (time-based)`.
- 11:18 UTC: `park checkpoint published to origin`.
- 13:02 UTC: the run failed (a full data volume, PRD #1809).
- Afterwards `git ls-remote origin 'refs/uzi-checkpoints/*'` listed no ref for that branch while other issues' refs remained.
- `uzi run recovery` showed two `source_only` holds with no captures.
- The committed work survived only in the worker's working clone.

This is distinct from #1790, where a park never obtains an off-worker copy. Here the copy existed and was deleted afterwards.

## Goal

The last published checkpoint of a failed or cancelled run stays reachable on origin until its recovery is settled, without ever blocking a new run on the same branch and without a forced ref update.

## Decision log

**D1. Retention follows custody.** The api does not delete a run's checkpoint ref while any custody hold for that run is open. For a completed run with no open hold, today's delete-on-completion stays. A completed generation can coexist with an older open hold of the same run; the ref is then retained while that older hold is open, or its tip is preserved under the run's recovery ref (D2) before the branch ref is freed. A failed or cancelled run with **no** hold (a worker without the recovery capability does not create one) keeps today's delete; the PRD states this rather than widening retention to runs uzi cannot settle.

**D2. Supersession moves the old tip to a run-specific recovery ref, never deletes it.** When a new run on the same branch needs the checkpoint slot, the api:

1. **persists first**: records on the old run (or its hold) the intent `superseding`, the recovery ref name `refs/uzi-recovery/<old-run-id>` and the expected tip, in one transaction, before touching the forge;
2. creates that recovery ref on origin pointing at the tip, compare-and-swap with old = zero, pack-less (the object is already on the remote). An existing recovery ref **at the expected tip** counts as success (a retry after a crash); one at a **different** tip stops supersession and leaves the branch ref alone;
3. deletes `refs/uzi-checkpoints/<branch>` compare-and-swap on that tip (the existing `DeleteOptions.ExpectedOldTip` path). A ref already absent, or advanced by another run, counts as done for this step;
4. marks the record `superseded` and lets the new run's publish proceed.

Every step is idempotent and CAS; nothing is forced, preserving the push broker's "NEVER FORCED" rule (`pushbroker.go` ~11). Because the record is written before the first forge write, a crash at any point leaves the tip discoverable: the sweeper reconciles a `superseding` record by re-running steps 2-4. The push broker gains a ref-create primitive for step 1. The namespace is outside `refs/uzi-checkpoints/` on purpose: every worker bare mirrors `+refs/uzi-checkpoints/*` (`agent/src/git.ts` ~4104) and new runs seed from `refs/uzi-checkpoints/<branch>` (~1178), so a recovery ref there would leak into unrelated runs. It is also outside `refs/heads`.

**Amendment (M3/M4 implementation).** Two details of D2 as originally written did not survive implementation intact:

- **"Serialise on the old run's row lock" → a per-run PostgreSQL session advisory lock held across the whole operation, including the forge calls, with a liveness fence checked immediately before every forge write and a scheduled post-settlement audit.** A row lock is released at transaction commit and so cannot span "commit the intent, then make the forge calls" — exactly the ordering the invariant needs. The advisory lock is taken with try semantics (a busy lock is a no-op, left for a later trigger or the sweeper) and pinned to one dedicated connection for the operation's duration; the fence re-reads `pg_locks` on that same session so a lock lost mid-operation (a terminated backend, a dropped connection) is caught before the next forge write rather than after. See the ADR (`adr/1810-checkpoint-retention-follows-custody.md`) for why the fence alone still leaves one narrow window, and what the post-settlement audit closes.
- **"Pack-less" → an empty (zero-object) pack.** `git receive-pack` requires a pack for any non-delete command; the smallest legal payload for "the object is already on the remote" is an empty pack, not no pack at all.

**Amendment (2026-09-28, M-rework implementation): the trigger widened from a refused publish to any publish that does not own the slot, and a terminal run's own publish is now serialized.** D2 as originally written (and its first amendment above) triggered supersession only on a `not_descendant` refusal: another run's checkpoint publish tries to push and the broker's CAS refuses it because a different run's retained/superseding record sits on the branch ref. That misses the case where the new run's publish would *fast-forward* over the old tip (its work descends from it) — the broker's CAS then ACCEPTS the push, so no refusal ever fires, and the old run's record is left `retained` at a tip that is no longer the branch tip. The trigger is now: **any publish by a run that does not own the active retained/superseding record on the branch, whether the push would be refused `not_descendant` or would descend and succeed.** A live issue run's publish claims the slot BEFORE pushing (`claimCheckpointSlot`, `api/internal/workersvc/checkpoint_supersession.go`, backed by the new query `ListActiveCheckpointRetentionsForBranch`): it supersedes every other run's active record on the branch first, and pushes only once all of them freed the ref; a record still in its retry backoff, or a busy lock/slot, is a benign `not_descendant` skip that the worker retries next tick (the old `not_descendant` → `freeCheckpointSlot` retry stays wired as the fallback for a record the claim check does not drive: a settling record, a record that appeared after the check, a race with another writer). A **terminal** run's publish over another run's active record is refused `superseded` outright, with no forge call — a terminal run must never evict or fast-forward over another run's retention. And because the trigger no longer waits for a broker refusal, a terminal run's own publish (its superseded check, the branch-slot check, the push, the tip persist, the record track) now runs under the run's retention advisory lock (`publishTerminalLocked`), so a supersession of that same run cannot interleave with it; any settle the publish itself owes is dispatched only after the lock releases.

**Amendment (2026-09-28, rework round 2): the terminal `checkpoint_retentions` row is now written in the SAME transaction as the status commit, and a live-routed publish's unknown-outcome push is now closed by a durable record, not by elapsed time alone.** Two gaps remained after the round-1 amendment above:

- **The race the round-1 amendment did not touch:** the terminal writers that never called the Go post-commit path (the sweeper's stale-worker and over-cap fails, `FailRunsMissingFromSnapshot`, `MarkRunFailedByID`, `FailRunAutoStop`, `FailClaimAssemblyExact`, `FailCodexAccountWaitRun`) left a window, between the status commit and the sweeper's backfill arm picking it up, where `claimCheckpointSlot` could list the branch's active records, see none, and push a descendant tip straight over the old run's retained checkpoint. Migration 00266 (a draft number, renumbered above the live head at merge, per the PRD's own constraint below) adds an `AFTER UPDATE OF status` trigger on `runs` that inserts the `checkpoint_retentions` row in the SAME transaction as EVERY terminal transition (`retained` while a custody hold is open, else `settling`; the branch derived exactly as `checkpointBranch` does, kind first), so any reader that observes the terminal status also observes the row. No new issue run exists until the old one is terminal (`uq_runs_one_active_per_issue`, migration 00170), so no branch lock is needed for this fix; the Go post-commit path still runs, re-reads the row the trigger already wrote, and dispatches the settle it owes. The sweeper's backfill arm stays wired as the backstop for the coverage gaps the trigger does not close (see the Implementation notes below).
- **Residual 2, per reviewer steering: a five-minute cooling period reduces the race but does not prove it closed.** A client-side timeout proves nothing about a receive-pack request the forge already accepted — it can still land on origin after the client gave up, after the run went terminal, and after a newer run superseded its record. Elapsed time alone was never sufficient evidence, so it is documented here as a delay, not a correctness proof. Migration 00267 (also a draft number) adds `checkpoint_publish_attempts`, a durable row written BEFORE every push (branch, ref, tip, the run) and cleared only on a known outcome (a definitive refusal, or a successful push whose tip is persisted and tracked). A live-routed push additionally carries a `livePublishPrePushBudget` (2 minutes, measured from `routedAt`, which is stamped BEFORE the status read so a slow read can only shorten the budget, never start it after the run's terminal commit) after which it is refused rather than sent. The sweeper's attempts arm (part of `ReconcileCheckpointRetentions`) compares the branch ref on origin against outstanding attempt rows for terminal runs and, under the run's retention lock, either re-records the landed tip on the run's record (compare-and-set against the tip the arm read before listing origin) or, once no custody hold of the run is open, CAS-deletes the branch ref at exactly that tip. The publish path's own tip persist and record track are themselves compare-and-set against the pre-push base, so a late write can never move a tip backwards over a newer publish or the sweeper's own re-record. The cooling period (`checkpointSupersessionCooling`, 5 minutes, sized comfortably larger than the pre-push budget plus the broker's own push timeout) is kept as a DELAY that narrows how often the race is even reachable, but the durable attempt record, not elapsed time, is what proves it safe. A live-DB test (`TestLatePublishLandsAfterCoolingLiveDB`, `api/internal/workersvc/checkpoint_publish_attempt_livedb_test.go`) drives a remote update landing after the cooling window has elapsed and confirms it cannot leave a permanently untracked branch ref.
- **The sweeper's `ReconcileCheckpointRetentions` pass is now bounded**, unrelated to residual 2 but landed in this round: it previously ran each arm to completion with no time budget, so a slow or hung forge could stall Sweep's later passes indefinitely. The pass now starts no further record once a pass-wide budget (`retentionPassBudget`, 30s) has elapsed, checked before starting each record in every arm rather than mid-record, and each record's locked operation runs under an op timeout (`retentionSweepOpTimeout`, 60s) rather than the publish path's own 2-minute `retentionOpTimeout`. 60s fits the longest locked operation (a superseding record's re-drive, five forge calls) on a slow but healthy forge answering each call in about 10s; it is deliberately not sized to five calls at the broker's 30s per-call ceiling, which would let one record hold the sweeper's single goroutine for minutes every tick. A forge slower than about 12s per call makes a sweeper re-drive time out and back off: every re-drive step is idempotent against origin, so what an attempt completed stays done (a re-drive still repeats each call); with no custody hold open the next pass takes the three-call stuck exit instead; and the publish path's own re-drive runs under the 2-minute bound. An operation cut off by its deadline still runs its failure bookkeeping and lock release on un-cancelled contexts, so a hung forge call still records the failure and releases the lock rather than leaving the record stuck; all of an operation's bookkeeping after its deadline (the step's own failure write, then the expiry path's lock re-check, read and write) shares one 10s window past that deadline, and the expiry path writes nothing unless a fresh fence re-check shows the lock is still held. Worst case per retention pass (the rest of the Sweep tick adds to it), per the code's own accounting: `retentionPassBudget + retentionSweepOpTimeout + 10s bookkeeping + 10s unlock + 10s connection teardown = 30s + 60s + 30s = 120s`, below the sweeper health beat's danger line (ten 15s default intervals, 150s); leftover work carries to the next tick, logged once per pass. The four forge-calling arms (work, unheld, audit, attempts) also rotate which arm runs first each pass, so a burst of slow records in one arm cannot starve the arms after it across many passes.

**D3. The recovery ref is recorded and settled like the hold it protects.** The api records the recovery ref (name and tip) on the run or hold, so `uzi run recovery` and the web recovery view read it instead of the branch ref once superseded. The ref is deleted (CAS on its recorded tip) after the run's last hold is released or discarded. Every release and discard writer triggers that check after its transaction commits: `ReleaseCustodyHold`, `ReleaseCustodyHoldExact`, `ReleasePredecessorCustodyHoldByAncestry`, `ReleasePredecessorCustodyHoldByLiveAncestry`, `DiscardCustodyHoldForOwner` (`api/internal/store/queries/recovery.sql`). A failed forge delete is retried by a reconciliation pass (the sweeper) rather than dropped, so refs do not accumulate.

**Amendment (dropped, dormant): the live-settle ancestry proof does not read the recovery ref.** D3 as originally written also named the live-settle ancestry proof (`ReleasePredecessorCustodyHoldByLiveAncestry`, `api/internal/apitypes/recovery.go` ~222) as a reader of the recovery ref. That reader was not built: it only ever runs against a *live* run's own checkpoint or branch head, and a `checkpoint_retentions` record — the only place a recovery ref is recorded — is only ever created at a *terminal* transition. The two can never meet, so wiring the recovery ref into that reader would be dead code. See M3's amendment below.

**D4 (2026-09-28, rework round 2). Residual 2 is closed by a durable pre-push record, not by the cooling period; a per-publish lease was considered and rejected.** The maintainer's lander and reviewer steering on the round-1 plan held that a five-minute cooling period before a supersession's recovery-ref create narrows the race but does not prove it closed: a client-side push timeout says nothing about whether the forge's receive-pack request, already sent, will or will not land later. Three fixes were on the table:

- **A per-publish lease** (a time-boxed claim a live publish takes before pushing, checked by supersession before it proceeds) was considered and rejected. It lapses while a detached supersession is still running (the lease's clock and the supersession's forge round-trips are not the same clock), it is unsafe to clear after a push whose outcome is unknown (clearing it early re-opens the exact race it exists to close; leaving it stale blocks the next publish for no reason once the push really did fail), and it is overwritten by two overlapping publishes of the SAME run (a retry racing the original attempt), which a single lease slot cannot distinguish.
- **Elapsed time alone** (a longer cooling period, or waiting out the broker's own push timeout before superseding) was rejected for the reason above: it is evidence of likelihood, not of an outcome the forge already committed to.
- **A durable pre-push record plus sweeper reconciliation** (adopted): `checkpoint_publish_attempts` records intent before the push, independent of any client-side clock, and the sweeper closes the loop by comparing what the record says against what origin actually carries — the direct question, rather than an inference from elapsed time. This is what round 2 implements (see the amendment to D2 above and the residuals below). The cooling period is kept as a companion delay (it still reduces how often a late push and a supersession's create overlap at all) but is documented as exactly that, not as proof.

Also landed in this round, closing the OTHER open gap from the amended Problem statement (the seven terminal writers that never called the Go retention path): a database trigger that writes the `checkpoint_retentions` row in the same transaction as every terminal status commit, so no terminal writer can leave a window where the row does not yet exist. See the amendment to D2 above.

**D5 (2026-09-28, landing review). A no-op publish counts only for the run's own persisted tip.** Publish of a tip origin's checkpoint ref already holds writes nothing (the broker's already-current short-circuit), so its success proves only that origin has the tip. Counted as published, it let a new run record another run's ref at the same SHA (a `settling` record's ref, or a late push the attempts arm deletes) as its own durable checkpoint, and that run's CAS delete then removed it. The api now treats an already-current result as published only when the tip equals the run's persisted `runs.checkpoint_tip` read immediately before the push; otherwise it answers the benign `not_descendant` skip and persists nothing. An outstanding attempt row is not proof of ownership: it is written before its push, which may never have landed. A lock or delete marker between adoption and deletion was considered and rejected as more machinery on the hot publish path for the same invariant. Reach was already narrow: a fresh run adopts a mirrored checkpoint only when it is its own (the owner anchor, #1042/#1059), so its clone tip can equal another run's tip only when that tip is also the pushed branch head.

## Implementation notes / residuals

- **Migrations 00264 (`checkpoint_retentions` + `checkpoint_retention_meta`) and 00265 (the backfill scan's expression index) are numbered as drafts** in this branch's tree; both are renumbered above the live head at landing (`task migration:renumber`), per the PRD's own constraint above. **Migrations 00266 (the terminal-transition trigger) and 00267 (`checkpoint_publish_attempts`), added in rework round 2, are draft numbers too** and are renumbered the same way at merge time.
- **Residual 1 of the original three is closed** by the 2026-09-28 (rework round 1) amendment to D2: a publish `Publish` routes as **terminal** at its status read can no longer land *inside* a supersession of that same run, because that publish now holds the run's own retention lock across its superseded check, push and track (`publishTerminalLocked`), and a supersession takes that same lock.
- **Residual 2 is closed by rework round 2's durable publish-attempt record, not by the cooling period alone.** Round 1 narrowed it to a specific window (a run that reads as **live** at the moment `Publish` starts, then turns terminal while that unlocked push is still in flight) and left it open, relying only on a five-minute cooling period before a supersession's recovery-ref create — which reduces how often the window is hit but never proves a late-landing push safe, since a client-side timeout says nothing about whether the forge's receive-pack request still lands. Round 2 closes it with a row written BEFORE every push (`checkpoint_publish_attempts`, migration 00267) plus a live-routed push's own 2-minute pre-push budget (measured from `routedAt`, stamped before the status read), and the sweeper's attempts arm reconciles any push whose outcome landed late: it compares the branch ref on origin against the outstanding attempt row and, under the run's retention lock, either re-records the tip on the run's record (compare-and-set) or, once no custody hold of the run is open, CAS-deletes the branch ref at that tip. The cooling period stays, now documented as a delay that narrows exposure, not the correctness proof.
- **New residual (rework round 2): a custody-gated delete costs the new run `not_descendant` skips until custody releases.** When the attempts arm finds a late-landing push and the old run still has an open custody hold, it re-records the tip rather than deleting the ref (the held work may be the only copy), so a newer run's checkpoints keep being refused `not_descendant` until that hold is released or discarded — the same trade-off the stuck-supersession exit already accepts elsewhere in this PRD.
- **New residual (rework round 2): an attempt row is retired after a 7-day horizon, or dropped with its run.** `publishAttemptHorizon` (7 days) is a documented, not enforced-safe, outer bound: past it the sweeper stops reconciling an unresolved attempt, and an attempt whose run no longer exists is dropped because the sweeper then has no forge coordinates to act on. A push the forge applies after either point still leaves a branch ref no record tracks, for a human to clear.
- **Residual 3 (tip lag) is unchanged**: in the tip-lag case — the record's recorded tip lags what the run itself later published, and that later tip is not the run's own persisted `checkpoint_tip` either — a stuck supersession's exit leaves the branch ref for a human to clear.
- **A stuck `superseding` record blocks the new run for as long as it stays in backoff** (unchanged from rework round 1). If a run's supersession gets stuck (its recorded tip is not what origin actually carries, e.g. the branch is not at the tip it names) it is left `superseding` with `last_error` and a backoff — `claimCheckpointSlot` treats a record still in that backoff as `not_descendant` and refuses the new live run's checkpoints outright, not just the one publish that hit it (its list is also bounded, `LIMIT 10`). This is not purely sweeper-driven: once the record's backoff expires, the very next publish on the branch re-drives it inline through `claimCheckpointSlot`, with no sweeper tick required. That frees the new run only when the cause was transient (a forge error); a persistent cause (the branch is not at the recorded tip, a recovery ref at another tip) fails the re-drive the same way and restarts the backoff, so the new run stays blocked until the old run's holds all release and the sweeper's stuck-exit path (`exitStuckSupersessionLocked`) clears the record.
- **New residual (rework round 2): the sweeper's retention pass is bounded, so a busy tick leaves work for the next one.** `ReconcileCheckpointRetentions` now stops starting new records once its pass-wide 30s budget is spent, and each record it does start is capped at a 60s op timeout; worst case per retention pass is ~120s, before the rest of the Sweep tick (a forge slower than about 12s per call makes a sweeper re-drive of a superseding record time out and retry on a later pass). Leftover records (and any arm the pass never reached) are picked up on the next tick rather than the same one, so reconciliation of a late-landing push, a stuck supersession, or a settle can take more than one sweeper interval under load. This bounds the sweeper against a hung forge; it also means the residuals above are not instantly reconciled even when the mechanism that closes them is otherwise working.
  Full mechanism and reasoning: `adr/1810-checkpoint-retention-follows-custody.md`.

## Success criteria

- A failed or cancelled run's published checkpoint stays on origin while its custody is open.
- A new run on the same branch is never blocked by a retained ref, except in the documented residuals: a stuck supersession blocks its checkpoints until the old run's holds release and the stuck exit clears the record, a late-landed old tip blocks them while the old run's hold is open, and a new run may be skipped for up to the 5-minute cooling period after the old run ends.
- No checkpoint or recovery ref is ever force-updated.
- Once a run's last hold settles, its retained or recovery ref is owed a CAS delete, retried by the sweeper until it succeeds (when the run, its repository or its forge connection no longer exists, the record is kept as an abandoned audit row instead).

## Risks

- **Refs accumulating on origin.** Mitigation: deletion is tied to hold settlement across all five writers, with sweeper reconciliation.
- **A retained ref confusing a new run's seed.** Mitigation: supersession moves it out of `refs/uzi-checkpoints/` before the new run publishes, and the recovery namespace is never mirrored into worker bares.
- **Partial or interrupted supersession.** Mitigation: the intent is persisted before any forge write, every step is idempotent CAS, and the sweeper reconciles a `superseding` record; the tip exists in at least one recorded ref at every point.

## Out of scope

- A park that never obtains an off-worker copy (#1790).
- The disk-full failure itself (PRD #1809).
