## Problem

CI wall-clock is long and, worse, **highly variable on an unchanged job set**. Measured across six recent pipelines (live GitLab API, 2026-08-04):

| Pipeline | Trigger | Wall-clock | Note |
|---|---|---|---|
| 20337 | main push | 9m04s | fast/clean |
| 20364 | main push | 11m30s | clean, representative |
| 20327 | main push | 11m53s | clean |
| 20330 | main push | 14m34s | moderate queue waits |
| 20360 | main push | **29m44s** | runner contention + a 1135s e2e |
| 20374 | MR !181 | 9m35s | **no e2e on MRs** |

The pipeline is **already a maximally-parallel flat DAG**: every gate job sets `needs: []`, so all ~13 gates start at pipeline T+0 on separate runners. The four `stages:` names are organizational, not barriers. So there is **no stage-barrier win to chase** — summed compute is ~62 min into ~11.5 min wall on a clean run (~5.4x parallelism). The cost is concentrated in four structural spots on the **critical path**, which is:

```
critical path = max(Wave-A gate durations) + max(Wave-B job durations)
  Wave A (parallel, T+0): validate:*, lint:*, test:*, helm_chart          (~13 jobs)
  Wave B (starts after ALL of Wave A): build:*  AND  e2e:kind-smoke
```

The four spots, ranked by measured wall-clock impact:

1. **`e2e:kind-smoke`** (main only) — the Wave-B tail on every main pipeline, and the most *unstable* job in the whole pipeline: **238s → 338s → 520s → 1135s** across the sample. It **rebuilds the api and web images from scratch in its own DinD** (`docker build`, `.gitlab-ci.yml:1909-1910`) — the exact same two Dockerfiles/contexts that `build:api`/`build:web` already build in the same pipeline. Duplicate build work, on the tail, with a cold docker cache every run.
2. **`build:*` block on the entire gate set.** `.kaniko_build` carries `needs: *gate_needs` (`.gitlab-ci.yml:1291`), so all four build jobs — including `build:agent [base]`+`[jvm]`, the ~2.6 GiB nix+Chromium image, cache-less on MRs by design — cannot start until the *slowest of all 13 gates* finishes. `build:agent` is the Wave-B long pole (300-390s) whenever e2e is fast or absent (it is the MR tail).
3. **`test:api-store-it` sits in `.gate_needs`** (`.gitlab-ci.yml:291`), spinning a `postgres:17` service + serial LiveDB sweep. When it is the slowest Wave-A gate (measured **540s** in pipeline 20360, that run's max), it delays the start of *every* build and e2e. The file itself flags this membership as an unmeasured cost and pre-authorizes revisiting it (`.gitlab-ci.yml:257-277`).
4. **Cold-cache linter builds.** `lint:api`/`lint:controller` acquire golangci-lint via `go run …golangci-lint@v2.12.2`, which **compiles the linter from source** on a cold `lint-` cache — measured `lint:controller` cold at **564.8s** (MR !157), easily the pipeline's long pole on the first push of any branch.

Separately, a **9m→30m swing** is dominated by **runner queue contention** (e2e queued 102s, build:agent[jvm] 93s, test:agent 32-61s on bad runs vs 1-2s clean) and inherent registry-pull variance in e2e (kindest/node ~1 GB + the CNPG operator/postgres images, pulled cold into ephemeral DinD every run). Both are runner-side infra, not job design — M7 / separate issue.

## Constraints (what "without losing functionality" means here)

- **Local==CI invariant (PRD #103 SC-1).** Every gate job invokes `task <target>`; the recipe is defined once in `Taskfile.yml`. A change that alters *what a job runs* only in CI would make `task gate` and CI disagree. **M1-M4 and M6 are CI-orchestration-only** (the `needs:`/`rules:`/artifact plumbing *around* the same `task` calls) and preserve this by construction. **M5 is the sole exception** and MUST land inside the `Taskfile.yml` recipe so local and CI acquire the identical pinned binary.
- **No gate weakened.** No test, assertion, `changes:`-skip of a *correctness* check, or coverage drop. `-race` and `-count=1` stay (see Rejected). The KinD smoke keeps a real cluster, the real chart, CNPG postgres, and the actual built api+web images reachable through the web→api proxy against a fresh DB — the win is in *how the images arrive*, never in what `scripts/smoke.sh` checks.
- **Release atomicity preserved.** `publish:*` keep `needs: *publish_needs` (`.gitlab-ci.yml:1530/1738/1794`) untouched; a red gate still blocks every tag publish. All build-decoupling changes touch MR/main **validation** builds (`--no-push`, `.gitlab-ci.yml:1326`) only.
- **MR trust boundary preserved.** MR builds stay credential-less + cache-less + `--no-push` (`.gitlab-ci.yml:28-38`, `1280-1285`). No change gives an agent-authored MR registry-write or shared-cache access. The e2e image-reuse in M3 is safe precisely because e2e is **protected-ref only** (`.gitlab-ci.yml:1875-1878`).

## Solution overview

Six milestones, none of which removes a check. In critical-path terms:

- **M1** moves `build:*` off the Wave-A tail so they overlap the gates (`max(gate)+build` → `max(gate, build)`). Biggest MR win.
- **M2** removes the `postgres:17` gate from the build critical path (one line, pre-authorized, measurement in hand).
- **M3** stops `e2e:kind-smoke` rebuilding api+web — it loads the images `build:api`/`build:web` already produced. Biggest main-branch win.
- **M4** skips heavy builds on MRs that do not touch that component (runner-minutes; wall on unrelated MRs).
- **M5** prebuilt-pins golangci-lint so a cold `lint-` cache stops compiling the linter from source. Cold-start win.
- **M6** low-risk cleanups (throwaway-Postgres durability off; cache the `task`/shellcheck tarballs).

M0 establishes the measurement so each milestone proves its own delta. M7 (runner capacity + registry mirror) is out of scope, filed separately.

## Decision log

- **D0 — Orchestration-only wherever possible; `Taskfile.yml` stays the source of truth.** M1-M4 and M6 change only the DAG/plumbing around unchanged `task <target>` calls, so `task gate` locally and CI execute byte-identical recipes. This is non-negotiable (PRD #103 SC-1). Any milestone that cannot be done this way is called out (only M5).
- **D1 — `build:*` decouple via component-scoped `needs:`, not `needs: []`.** `build:api` → `["validate:api","test:api","lint:api"]`; `build:controller`/`build:web`/`build:agent` likewise over their own component's gates. Preferred over the more aggressive `needs: []` (which would start a build before its own tests) because it keeps the sensible "don't build an image whose own component failed" property while still removing the cross-component wait that dominates today. Publish jobs keep `*publish_needs` (atomicity untouched). Accepted cost: a build may run when an *unrelated* component's gate later fails — wasted validation minutes on MRs (nothing ships); on main it can warm the Harbor layer cache from a commit whose unrelated tests failed, which is harmless because layers are content-addressed and tests do not affect image content. **Settled (M0, 2026-08-04): component-scoped `needs:`, NOT `needs: []`.** The `needs: []` variant is rejected for the reason stated — it would start a build before its own component's tests, discarding the "don't build an image whose own component failed" property for no additional critical-path win (the cross-component wait is what dominates, and component-scoping already removes that).
- **D2 — `needs:` cannot be varied by `rules:` in GitLab, so D1 is a static edge.** That is fine: `build:*` never run on tags (`if $CI_COMMIT_TAG when never`), so there is no ref where the static edge is wrong.
- **D3 — Drop `test:api-store-it` from `.gate_needs`, keep it in `.publish_needs`.** The file pre-authorizes this (`.gitlab-ci.yml:257-277`): the `.gate_needs` membership is "an unmeasured latency cost … a made decision," the release-integrity reason is "entirely about `.publish_needs`," and the revisit criterion is "read store-it's duration against the MAX of all other gate jobs on a **WARM** pipeline; if it is not the max it added EXACTLY ZERO." **Read honestly against that criterion the benefit is small, not the 540s an earlier draft claimed** (review finding M-3): on the representative *clean* pipeline 20364, store-it is 189.9s while `lint:controller` is 346.7s and `test:api` 312.9s — store-it is **mid-pack, not the critical-path gate**, so removal saves ~0 on clean runs. It is the slowest gate only on *contended* pipelines (20360, 540.1s), the exact cold/contention confound the block says to exclude. And after M1 decouples the builds, `.gate_needs` is consumed only by `e2e:kind-smoke` (main-only), shrinking the effect further to "e2e may start slightly earlier on already-degraded main pipelines." So M2 is reframed as a **worst-case-tail trim + a correctness cleanup** (removing an admitted list asymmetry the file itself flags as inviting a future wrong "fix"), not a headline win. It is safe regardless: store-it still runs on every ref and still gates every publish (the "red job nothing needs" hazard is a `.publish_needs` concern, untouched here).
- **D4 — `e2e:kind-smoke` consumes prebuilt images on main, falls back to self-build on tags.** `build:api`/`build:web` add `--tarPath <img>.tar --destination uzi-api:kind`/`uzi-web:kind` alongside the existing `--no-push` (**on protected non-tag refs only**, gated in-script on `$CI_COMMIT_REF_PROTECTED` true and `$CI_COMMIT_TAG` empty, so MR builds don't upload an artifact nobody consumes — review finding m-5), publishing the tar as a job artifact. `e2e:kind-smoke` gains `needs: [{job: "build:api", optional: true, artifacts: true}, {job: "build:web", optional: true, artifacts: true}, <gate list per D4a>]`, and its script becomes **conditional**: `if [ -f <img>.tar ]; then kind load image-archive …; else docker build … && kind load docker-image …; fi`. **`optional: true` is load-bearing** (review finding B1 — the blocker): `e2e` runs on tags (`$CI_COMMIT_REF_PROTECTED`), but `build:api`/`build:web` are **skipped on tags** (`$CI_COMMIT_TAG when never`, `.gitlab-ci.yml:1295-1296`) because publish builds+pushes instead. A non-optional `needs:` on a skipped job **fails pipeline creation** and kills every release; with `optional: true` the tag pipeline creates fine, the tar is absent, and e2e falls back to today's exact `docker build` path — **tag smoke coverage preserved unchanged** (SC-0). On main the tar is present → fast `kind load image-archive`. Format verified (review finding m-1): kaniko `--tarPath` emits a `docker save`-compatible (docker-archive) tarball via go-containerregistry `tarball.WriteToFile`, exactly what `kind load image-archive` accepts; layers are compressed so tar size ≈ image size. **Credential-less on the artifact path** (no registry, no Harbor creds), so the MR trust boundary is untouched. Chosen over pushing a pipeline-scoped registry image (adds a registry round-trip + creds) and over `docker build --cache-from` against the kaniko cache repo (rejected: kaniko's cache layout is not consumable by buildkit `--cache-from`).
- **D4a — `e2e`'s gate `needs:` is the full current `.gate_needs` set minus `test:api-store-it`** (which M2 removes globally), pinned explicitly, not an ellipsis (review finding m-4). e2e installs `deploy/chart` itself so it already supersets `helm_chart`, but the other gates stay in its `needs:` so e2e cannot start reporting before them — dropping any gate from e2e's `needs:` would be a behavior change (e2e could pass while a gate it used to wait behind is still red). The only intended change to e2e's gate dependencies is the store-it removal M2 makes everywhere.
- **D5 — `changes:` path-gates `build:api`/`build:web`/`build:controller` on MR refs only; NEVER `build:agent`, and NEVER on protected refs.** `build:agent` bakes uzi's whole source at `/opt/uzi-src` with `UZI_SRC_SHA=$CI_COMMIT_SHA`, so almost any change is a real input — a `changes: agent/**` gate would wrongly skip it. Main builds stay unconditional because M3 consumes `build:api`/`build:web`'s artifacts on main; a `changes:`-skipped build on main would leave e2e without its tar, and D4's `optional:` fallback would then silently self-build on main — quietly losing M3's win rather than erroring. So the `changes:` filter attaches to the **MR rule branch only**. (The tag path is already handled by the pre-existing `$CI_COMMIT_TAG when never` rule plus D4's fallback; D5 is only the MR-vs-main split.) **Settled (M0, 2026-08-04): `build:agent` is NEVER `changes:`-gated, and NO build is `changes:`-gated on a protected ref.** `build:agent` bakes uzi's whole source at `/opt/uzi-src` with `UZI_SRC_SHA=$CI_COMMIT_SHA`, so almost any change is a real input; a `changes: agent/**` gate would wrongly skip it. The other three (`build:api`/`build:web`/`build:controller`) get a `changes:` filter on the MR rule branch only.
- **D6 — M5 (prebuilt-pin golangci-lint) is downgraded to an investigate-first spike; it may not be viable, and "byte-identical findings" is NOT yet proven** (review finding M-2). Today `go run …golangci-lint@v2.12.2` builds the linter with CI's own pinned Go toolchain (golang:1.26, `GOTOOLCHAIN=local`), so the linter's build-Go always matches the code's `go` directive. A downloaded **release binary** carries a frozen build-Go, and golangci-lint can only lint code whose Go *language* version is ≤ the Go it was built with (golangci-lint #5641/#6272, FAQ). If v2.12.2's release binary was built with Go language < 1.26 it emits typecheck errors on this repo's `go 1.26.4` code — **different findings or a red job, not byte-identical**. The Taskfile comment M5 would edit already rejects a frozen-toolchain linter for exactly this (`Taskfile.yml:916-920`). So M5's DoD *starts* with a verification gate: confirm the v2.12.2 release binary's build-Go language ≥ both modules' `go` directive AND add a guard that fails loudly if a future linter release regresses below it. If that can't be guaranteed cheaply, **M5 is dropped** and the cold linter-build cost is accepted (or attacked by warming the `lint-` GOCACHE, which has no toolchain-coupling risk). If it lands it MUST be in the Taskfile (local==CI). This is the toolchain-version axis `task`/shellcheck never had — those are self-contained tools with no dependency on the target code's language version; golangci-lint is not, which is why the "same trust model" argument only covers the checksum axis, not this one.
- **D7 — Every structural change fixes its own docs in the same commit** (repo fix-the-doc rule). M1 rewrites the atomicity comment near `.kaniko_build`; M2 updates the pre-authorization block (`.gitlab-ci.yml:257-287`) to record the measurement and that the criterion was actioned; M3 rewrites the e2e job header (`~:1834`) and the `stack.md` CI paragraph; the root `CLAUDE.md` Commands section is updated where it describes the gate DAG. Doc update is in each milestone's Definition of Done, not a separate milestone.

## The pipeline shape (for implementers)

`e2e:kind-smoke` (`.gitlab-ci.yml:1842-1931`) is main/tags only (`rules:` at `:1875-1878`, `if $CI_COMMIT_REF_PROTECTED == "true"`; the DinD-on-shared-runner host-escape reason is documented at `:1868-1874`). It: builds a KinD config and `kind create cluster` (pulls ~1 GB `kindest/node`), `docker build`s uzi-api + uzi-web in its own DinD (`:1909-1910`), `kind load`s them (`:1911`), applies the CNPG operator, `helm install`s `deploy/chart` with `deploy/values/kind-smoke.yaml` (`:1922`), waits for postgres/api/web Ready, then port-forwards and runs `bash scripts/smoke.sh`. `smoke.sh` asserts the full auth/authz/CSRF/session-revocation journey through the web→api proxy against a fresh DB (concurrent first-registration race electing exactly one admin, admin/non-admin split, 403/401 boundaries, CSRF enforcement, session revocation). That contract is what any speedup must preserve; the win is in how the api/web images arrive, not in the assertions. It does NOT invoke `e2e/run-e2e.sh` (the compose harness, not in CI) and the smoke script is `scripts/smoke.sh`.

## Explicitly rejected / non-goals (do not "fix" these)

- **Removing `-race`** — measured ~1s wall on these *compilation-dominated* suites (test:api 41s raced vs 40s unraced), not the 2-10x of exec-dominated ones; it catches a real `workersvc` data race (3/3 vs 2/3 with the lock deleted). Keep.
- **Removing `-count=1`** — ~0s cost in CI (MRs change source, tests re-run regardless) and it guards the documented cross-module-fixture silent-green bug (a gutted `fixtures/…` printed `ok (cached)` without it). Keep.
- **Caching MR `build:agent`** — cache-less *by trust design* (an agent-authored MR controls its own `.gitlab-ci.yml`; Harbor cache-write access is a poisoning vector). The expensive nix+Chromium layer is exactly the one that would benefit, which is what makes this tempting — but it is the guardrail, not an oversight. The fix is M1 (parallelize), not caching.
- **Baking pinned Go tools into a custom CI image** — violates the repo's "upstream digest-pinned images only" convention and risks local/CI tool-version drift. M5's Taskfile-curl approach is the convention-safe alternative.
- **Merging `validate:web`+`test:web` / `validate:agent`+`test:agent`** to save an `npm ci` — with free runners this *raises* wall-clock (sum vs max of two parallel jobs); it only helps under runner-queue constraint, and it trades away the "test reported as test, not conflated" separation the repo values. Deferred to the M7 runner-capacity decision, not adopted here.
- **Bounded `GIT_DEPTH` on the lint jobs** (currently `0`) — real but risky (a long-lived branch whose merge-base is deeper than the bound trips the pre-flight and needs a manual unshallow); `publish:assert-changelog` genuinely needs full history + tags. Low value, deferred.
- **M7 (out of scope, separate issue): runner capacity + registry pull-through mirror.** The 9m→30m swing is queue contention (e2e queued 102s, build:agent 93s, test:agent 32-61s), and e2e's inherent variance is cold registry pulls of kindest/node + CNPG images into ephemeral DinD. Both are runner-side infra outside `.gitlab-ci.yml`. File as an infra issue; note it here as the known ceiling this PRD cannot reach in-repo.

## Risks & mitigations

- **M1: a build runs when an unrelated gate fails.** Mitigation: MR builds `--no-push` (ship nothing); main builds only warm a content-addressed cache. Accepted (D1).
- **M3: artifact size.** The api tar is small; the web tar larger. Mitigation: measure the artifact transfer vs the removed cold-build time; the DinD `docker build` it replaces is strictly larger and on the critical path. If transfer dominates unexpectedly, fall back to D4's pipeline-scoped-registry variant (protected-ref only).
- **M3/M4 interaction:** a `changes:`-skipped main build would leave e2e's tar absent and the `optional:` fallback would silently self-build on main, quietly losing M3's win. Mitigation: D5 forbids `changes:` on protected refs (main included); reviewer-checklist item that e2e's `needs:` builds are unconditional on main.
- **M3 tag path (B1):** the blocker was a non-optional `needs:` on `build:api`/`build:web` failing tag-pipeline creation. Mitigation: `optional: true` needs + script fallback (D4). Verify by dry-running/inspecting a tag pipeline's DAG that creation succeeds and e2e self-builds.
- **M5: per-arch checksum drift.** Mitigation: pin darwin/arm64 + linux/amd64 checksums exactly as `.task_setup` does; a bad pin fails the `sha256sum -c`, loud, on first run.
- **General: measuring the delta is confounded by runner contention.** Mitigation: read deltas on warm pipelines and prefer the per-job `duration` (excludes `queued_duration`) over wall-clock for attribution; M7 contention is tracked separately so it does not get mistaken for a milestone regression.

## Review findings

Adversarial architect review, 2026-08-04, verified against `fc9996f0`. All the PRD's line anchors checked out; the substantive findings below are folded into the body above.

- **B1 (BLOCKER, resolved in D4/M3):** M3's static `needs: [build:api, build:web]` would break every release. `e2e:kind-smoke` runs on tags (`$CI_COMMIT_REF_PROTECTED`), but `build:api`/`build:web` are skipped on tags (`$CI_COMMIT_TAG when never`, `:1295-1296`); a non-optional `needs:` on a skipped job fails pipeline creation. M5 now starts with a verification gate and is droppable.
