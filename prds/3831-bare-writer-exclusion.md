## 1. Status, scope and non-goals

- **Status.** Draft, Gate A revision under the 2026-11-04 owner amendment, PROPOSED, awaiting maintainer review. No implementation is authorized. (2026-11-08: #3644 Gate B implemented the compose path; see the Gate B delivery note at the top.)
- **Saved-pin restore, defined (amendment Q3).** In this record, "saved-pin restore" means the #3644 M2 to M4 feature as the owner amendment scopes it: the successor worker process restores into a **fresh attempt** seeded from a **verified** saved pin, and installs its own attribution in the shared bare for that fresh attempt. [M]
  - No same-source takeover: same-source takeover stays parked (amendment Q3).
  - The predecessor's mutable source clone is not trusted without the existing capture proof (the verified restore-point check below, or a new capture).
  - The predecessor's slot stays foreign-active and its source stays retained; the successor takes no authority over it.
- **Existing restore-point consumers are not that feature.** Two shipped paths already reuse a saved restore point [S]:
  - `agent/src/runner.ts:26300-26302`, in `recoverRetainedClaim`, reads `source.recovery.restoreTip` (`? source.recovery.restoreTip : undefined;`) and calls `verifiedRecoveryRestorePoint` (`agent/src/git.ts:9004`). **Object writes.** The `runSynthesisGit` rows write only loose objects into `<bare>/objects`. Crash residue: unreferenced objects, kept because the worker never runs `gc` (Detached maintenance, below), and possibly git's own temporary object files (inferred). **Comparison within one slot (same runtime slot, below).**
- **Inode reuse is expected.** A namespace inode number is unique only among live namespaces; the number is reused after the namespace is freed (inferred). So the namespace identity alone cannot tell "same namespace" from "a new one with a reused number". The init start time is required with it.
- **Same boot.** Equal (device, inode, init start) means the same or an indistinguishable namespace: refuse. S.initStart less than or equal to P.initStart: refuse (inverted or equal). Only S.initStart strictly greater than P.initStart, with S's namespace identity read in the same boot, separates the two instances. P's record is written by P's worker after P's init started, so P's init lived at least until that write; an equal start tick needs P's whole life, record write included, inside one tick, and refuses fail-safe at no practical cost (inferred).
- **Different boot.** Within one slot pinned to one node, a different boot ID means the node rebooted, so every process of P's boot is dead (inferred). A pod is pinned to one node for its life (inferred from Kubernetes scheduling semantics); a Docker container belongs to one daemon on one host (inferred). Across slots a different boot ID proves nothing: the other boot may be another node, still running.
- **Distinct is necessary, not sufficient.** A distinct identity shows S is not P's namespace. That P's namespace is gone comes from the supported runtime's lifecycle guarantee for the **same** runtime slot: the runtime tears a container's PID namespace down (the kernel kills every member when init dies, `prds/1860-pod-epoch-writer-exclusion.md:234`, quoted in 3.1 [I]) before it starts the next instance of that container (inferred runtime behaviour; O). Q4 accepts the dead-shim and termination-history gaps of that guarantee for hosted in-pod restarts [M]; the other lanes' gaps are derived per posture in 3.2.

### 4.2 Consumption ledger

- Volume-global ledger: `agent/templates/pod-epoch-init.cjs:84`, `ledger: path.join(root, '.uzi-epoch-consumed'),`. [S]
- Durability and order (research note 3, from `pod-epoch-init.cjs` `consume`; not re-read line by line): open, `flock` EX on the ledger inode, verify, append one 37-byte UUID record, `fsync`, verify, release. It runs before evaluation and before admission. An unsynced append is settled by the next process as `existing` (consumed for good). A torn ledger stops startup without admission. The ledger is never truncated or reset, and a consumed pod UID is never reusable. The evidence itself is not stored locally; only the consumption is. [I, research note 3 summary]
- Consequence for restore: one evaluation per pod UID, at startup. Any restore later in the pod's life, or after a container restart, has no fresh proof. So (c) needs the attested result persisted for restore's own consumption (3.2 (c); the pod record, 6(c)), and the in-pod candidates (b) and (d) do not use the epoch proof at all: they rest on the 3.0 identity and the same-slot teardown guarantee.

## 5. Smallest-design comparison

**Bar.** Each option is judged against the amended contract (6(a)), the postures of 3.2, legacy writers (2.4: every stable release up to v0.85.2 writes the bare with no W and no record) and rollback to an older build.

### 5.1 Options rejected without new state

- **(ii) Reuse #3031's bounded writer exclusion.** A worker-local, deny-only process scan (`adr/1197-transient-recovery-park.md:145-146`, "runs a deny-only process scan (worker-local, never signalling)") [I]. It cannot see another PID namespace (inferred, 4.4), offers PID absence, which the issue body names as non-evidence, and its producer is disabled (`agent/src/recovery.ts:127`, `export const TERMINAL_ORIGIN_ADMISSION_ENABLED: boolean = false;`) [S]. **Reject.**
- **(iii) Isolate restore mutations from old writers.** Stale writes still land on the predecessor's journal keys that restore reads (`agent/src/git.ts:8691`, `await this.runGit(barePath, ["config", "--local", recoveryCaptureKey(branch), value]);`) [S], and a copy-out at admission is one observation of state a live writer may be changing. Under the amended contract the covered writers are gone by teardown, so isolation adds a second store and closes nothing. **Reject.**
- **(iv) Durable pre-launch enrollment of every relevant bare writer.** 23 restore-relevant UNCOVERED rows and 3 GATED rows (2.3). A dead parent's `running` record cannot be released without proof that its orphan is dead (`adr/1783-run-quiescence-and-attempt-clone-paths.md:1318-1320`, "No process scan, PID absence or empty lock holder clears it.") [I], which is exactly what teardown evidence supplies; legacy writers stay unrecorded. **Reject**, standalone and as a component.

(B) is one write-once record per process, one write-once record per evidenced new pod (6(c)), and one evaluator at the existing restore entry. It is smaller than (iv) and has none of (A)'s rollback cost.

## 6. Chosen contract (PROPOSED, not approved)

A proposed contract for owner approval. No implementation is authorized. Terms: S is the successor worker process, P the owner of the foreign-active source slot being restored, X P's pod when S runs in a different pod.

### 6(a) Invariant, trust scope and older-writer set

**Invariant (amended) [M].** Restore relies on evidenced container-instance teardown: S verifies that P's container instance, and every earlier instance it could inherit writers from, is gone. Missing, unknown or ambiguous evidence refuses: retain and stop.

**Checked versus relied on.**
- *Checked at admission:* P's own record exists and names P's slot and execution identity; S's identity is distinct and later in the same slot, or a different boot in the same slot; for a new pod, a persisted attested pod record names P's pod as the predecessor (6(c), 6(d)).
- *Relied on, not checked (Q4) [M]:* the runtime tears down P's container instance, and every earlier container instance in the pod, before it starts the next. Q4 accepts the dead-shim and termination-history gaps. Distinct identity is necessary, not sufficient (amendment Q5): death comes from this reliance, not from the comparison.
- *Outside the proof (trust assumptions) [M]:* survivors of older pods, including writers a worker started there (Q2); node-root infrastructure, including a rootful DinD daemon's reach (Q7); trusted operator actions (Q8). These are a recorded scope change, not evidence that such writers cannot write.
- *Single-uid trust limits (Q6) [M].* The record MAC protects against corruption and against non-worker uids under uid-split only. Under single-uid a runner-uid process shares the worker uid; string screening is then the primary protection of the worker token (`agent/src/guardrails.ts:231-232`, "(and remains the primary bar-raise on a #58 single-uid start, where there is no" / "split; see docs/proc-hardening.md)"), so such a process could read the token and forge a boundary or pod record, and could swap the `runner-shared` entry (`adr/3153-runner-shared-pvc-subpath.md`; `render_dind.go:63-66`, 3.2 (b)). Both are within Q6's documented trust limits; the MAC is not protection against them.

**Older-writer set per candidate.**
- *In-pod restart, (b) and (d):* P's container instance and every earlier `worker` instance in the pod, with their git children and runner-uid processes, all of which live in those PID namespaces (Q4).
- *New pod, (c):* X's last container instances (attested evidence, 6(c)); X's earlier instances (Q16, open); earlier `worker` instances of S's own pod (Q4, in-pod).
- *Nested DinD containers* reach `/data/runner`, not the bare (3.2 (b)); their reach into S's fresh attempt is Q13.

**Child lifetime.** No launch path sets pdeathsig (2.1 sweep: 0). An orphan git child of a dead worker runs on until its PID namespace's init dies, when the kernel kills it (3.1, inferred from `prds/1860-pod-epoch-writer-exclusion.md:234`) [I]. The contract relies on that teardown; 8.1 tests it on a real namespace.

**Non-evidence (issue body) [M].** "Repeated empty snapshots, PID absence, a released worker lock, a timer, or `config.lock` alone are not replacement authority." Also an epoch EX hold that ends before admission (4.1). W stays held for the process lifetime and is used only to make this design's own writes uncontended.

### 6(d) Admission predicate

Per claim of a run whose source slot is foreign-active and carries a saved pin (the #3644 entry), inside one authority transaction A, every condition must hold:

- **R1. S's own record.** Present, MAC valid, version known, and equal to S's live identity re-read now (incarnation, slot, execution identity), with the 3.0 visibility rule and zero time-namespace offsets.
- **R2. P keyed by the slot owner.** P = the slot's `owner.worker`; P = S takes the existing path. Read exactly `boundaries/<sha256(P)>`. A slot owner with no record of its own refuses (Q10); never fall back to any other record, including an earlier instance's record for the same slot.
- **R3. P's record.** Decodable, version known, MAC valid, every field present.
- **R4. Slot.** P.slot = S.slot: in-pod path (R5). P.slot is a different pod on the hosted DinD lane: new-pod path (R7). Any other difference refuses (compose: Q12).
- **R5. Same slot, same boot.** (P.dev, P.ino, P.startTicks) differs from S's and P.startTicks < S.startTicks; equal, inverted or ambiguous refuses (3.0). **Same slot, different boot:** a kernel or host reboot (restarting Docker does not change the kernel boot ID); accept (a pod stays on one node; a Docker container on one daemon; inferred, 3.0).
- **R6. Runtime posture.** S's declared runtime is in {containerd-runc, crio-crun} and equals P's recorded runtime: the set the epoch proof accepts (`controller/internal/kube/pod_epoch_evidence.go:77`, `func podEpochRuntime(s string) bool { return s == "containerd-runc" \|\| s == "crio-crun" }`), whose resolver also refuses any RuntimeClass (`controller/internal/kube/pod_epoch_identity.go:43`, `if !podEpochRuntime(w.Runtime) \|\| p.Spec.RuntimeClassName != nil \|\| p.Labels[LabelWorkerID] != w.ID {`). [S] Worker pods render no RuntimeClass (`grep -n 'RuntimeClassName' controller/internal/kube/render*.go`, 0 hits). Undeclared, unknown or sandboxed runtimes refuse. Compose's runtime declaration belongs to Q11 and Q12.
- **R7. New pod.** S's pod record (6(c)) is valid; its predecessor equals P.slot's pod UID and P.slot's container is `worker`. If S is not the pod record's writer, S and the writer are compared as in R5 (in-pod, Q4).
- **R8. Bare clear.** `assertBareClear` on the run's bound bare passes (`agent/src/authority-runtime.ts:1045`, `async #assertBareClear(bare: string, op: string): Promise<void> {`; refusal `:1056-1057`) [S], and no other foreign-active slot or pending footprint covers the bound bare or source, P's own retained slot excepted.
- **R9. Scope (formerly E10).** Only the run's bound bare and its slots are read; an unrelated or unknown bare never refuses an ordinary pin or capture (tripwire, 6(g)).

**Then, still inside A,** S's first successor mutation: its own successor attribution for a **fresh attempt** (Q3, section 7), with P and the digests of P's record (and of the pod record, on R7) as basis. Close A; write S's attribution into the bare (#3644), syncing the bare's `config` and directory (`agent/src/git.ts:7776-7779`). **Refusal** at any condition: retain and stop, nothing written, today's refusal (section 1).

**Race ordering.** W excludes a concurrent compatible worker. R1 to R8 and the first mutation share A. The writers in 6(a)'s set are dead by the relied-on teardown before S's container instance started, so no TOCTOU window remains against them; trust-assumption classes (Q2, Q7, Q8) are not ordered by anything here.

### 6(e) Durability and recovery

**Write order** (boundary record; the pod record is the same with `pods/` and "before `worker.run`"):
1. After `ensureAuthorityDir`, under W, fsync the data root **unconditionally**. The existing sync is conditional (`agent/src/authority-lock.ts:229`, `const created = await mkdirPrivate(ctx.authorityDir, ctx.uid);`; `:234`, `if (created) await syncDirectory(ctx.dataDir);`), so after a crash between the `mkdir` and that sync no later process (which sees `created` false) fsyncs the data root; the entry's durability then depends on writeback timing, and a power loss before writeback can drop it. [S]
2. Ensure `boundaries/` (or `pods/`) exists; fsync `.uzi-authority` unconditionally.
3. Create the tmp file `O_EXCL|O_NOFOLLOW`, write, fsync.
4. Install without replacing: `link` the tmp to the record name; `EEXIST` refuses; unlink the tmp. `writeDurable` (`completion-authority.ts:378-401`) cannot be used unchanged: it installs with a replacing rename (`:390`, `await ops.rename(tmp, path.join(dir, name));`). [S]
5. fsync the containing directory.
6. Read the record back and compare.
7. Only then the first bare or slot write (boundary record) or admission (pod record).

**Failure model.**
- *Process crash at any point:* either no record or a complete one; absence refuses (Q10).
- *Storage or power loss:* covered only on supported storage (ext4 or xfs, `authority-lock.ts:170`, `export async function requireSupportedStorage(`) with honoured fsync, which is owed operator evidence (8.2), and only because every directory from the data root down is synced (steps 1, 2, 5).
- *Out of scope:* the data root's own entry in its mount root (a volume mount, not created by the worker), and restoring an old copy of the store (`completion-authority.ts:68`, "or a full reset), is NOT detected and is out of scope.").

| Crash point | Recovered state | Outcome |
|---|---|---|
| between `mkdir` of `.uzi-authority` and step 1 (the root-entry window) | process crash: entry present; power loss: entry may vanish | step 1 of the next process syncs it; if it vanished, no record exists and successors refuse |
| before or during step 2 | no record | refuse; nothing written to the bare |
| after step 3, before the link | stale tmp, no record | refuse; tmp never read |
| after the link, before the tmp unlink | record plus a second name for it | harmless; tmp never read |
| after the unlink, before step 5 | record visible; may be lost on power loss | the process had written nothing; absence refuses |
| after step 6 | durable | first bare or slot write may follow |
| restore: after A commits, before S's bare attribution write (6(d)) | S's slot attributed with P's digests as basis; bare journal unchanged; P's slot untouched | #3644 contract obligation (not yet implemented [M]): read the slot-versus-bare mismatch fail-closed and retain; a later successor meets two foreign-active slots and refuses at R8; Gate B tests this window |

**Recovery.** Records are rediscovered by key at admission (P from the slot owner, the pod record from S's pod UID). No replay, repair or rewrite. Tmp names are never read; a startup sweep may delete them.

**Verification seams.** `AuthorityFsOps` has only `syncFile`, `syncDir` and `rename` (`completion-authority.ts:99-103`) [S]; Gate B adds link, unlink and read-back hooks and a test of the interrupted root-creation window (8.1).

### 6(f) Versions and rollback

- **Older writers** write no record. As P they refuse (Q10): the first restart after rollout is not restorable, a cost disclosed in the recovery docs and release notes (8.1).
- **Older readers** ignore `boundaries/` and `pods/` (5.2).
- **Mixed versions.** W excludes a concurrent compatible worker on one data directory; overlapping pods run one image (`prds/3430-pod-epoch-lock-shadow.md:187`, "Pods that overlap on one volume come from the same ReplicaSet, so they run the same image.") [I]; an out-of-band build is Q8.
- **Record-only rollback** (no restore has run on the data volume) to a pre-gate build is safe: no restore, records ignored and left in place. After a roll-forward, rollback-era incarnations have no record and refuse as P.
- **Rollback after a restore** is not established by the records alone: ignoring `boundaries/` and `pods/` says nothing about how an older build attaches to, recovers or discards S's successor slot and bare attribution, whose representation is #3644's and off-tree. #3644 obligation, verified by Gate B (8.1): restored attribution carries a fence that every build below the restore-enabling release refuses (including builds that already write `boundaries/` and `pods/` but predate the fence), as for the completion fence (`specs/human.md:1421`, "Older workers refuse to attach, recover or discard a journal carrying the fence (accepted rollback fence)."). Such a reader must refuse the successor slot and attribution rather than ignore them; for slots `exact()` already refuses an unknown shape (5.2), but nothing shown here makes older readers refuse unknown attribution keys, so Gate B must demonstrate it. Nothing is silently downgraded or force-cleared, and P's retained state stays untouched. Until that fence exists and is tested, rollback below the restore-enabling release after any restore is unsupported and documented as such.
- **Undecodable, new-version or bad-MAC records** (for example after a worker-token change) are preserved, never rewritten or deleted, and refuse. No silent downgrade: a missing or failed record never widens eligibility.
- **Growth (Q9).** No pruning in this contract; Gate B measures record growth per process start.

### 6(g) Unchanged and preserved

- **No force-clear.** Slots, footprints, custody, fences and provenance are never cleared or reclassified to make the predicate pass; a refused source stays retained until a guarded operator discard (`specs/human.md:1421`, "There is no TTL, size cap, disk-pressure reclaim or generic force-clear; retained bytes are unbounded."). [S]
- **Eligibility is not authority.** Passing R1 to R9 permits only S's own successor attribution for a fresh attempt. It grants no release, deletion, capture, takeover or discard authority over P's slot, source epoch, fence, pins, journals or custody.
- **Q3 interface for #3644.** Restore seeds a fresh attempt from a verified pin; this record invents no #3644 key layout. S's successor attribution must not overwrite P's per-branch journal entry (`uzi-recovery.<branch>.clone`, 2.3); Gate B shows the key layout, otherwise restore refuses.
- **Ordinary paths unaffected.** Capture and pin paths never run the predicate. The tripwire `agent/test/recovery-coordinator.test.ts:507`, `` it(`an unrelated unknown bare does not suppress an ordinary ${boundary} (#3831 tripwire)`, async t => { ``, stays green. [S]
- **Observed refusal unchanged.** `admitSourceUse` and `preservation_failed` are unchanged by Gate A (section 1).

The worker logs `independent restore refused; predecessor retained`, emits one bounded feed line and writes nothing to P's journal, ledger, slot, clone or HOME. Except for the parked unsupported classes (amendment 15), a refused run keeps item-7 accounting: on the running path it is charged requeues up to `RUN_MAX_REQUEUES`, then parks at `recovery_wait` / `worker_requeue_exhausted` when custody is uncertain (`TestClaimedNeverStartedChargeRetainedCustodyRunningPathLiveDB`); the claimed path can consume uncharged generations up to the run's own hold-admission bound or park at server-only `retained_continuation_unwitnessed`; a custody-blocked queued run on a live worker may stay queued even at the cap. Each accepted generation opens a custody hold counting toward `custody_hold_limit`. An owner Cancel already persisted server-side is observed at the pre-write stops (9.2).
- **6(d) unsupported predecessors (amendment 15).** Three positively evidenced classes are refused before any source effect and, when the api advertises `recovery_cause_retained_recovery_adoption_failed`, parked for the owner at `recovery_wait` / `retained_recovery_adoption_failed` (`holdUnsupportedRestore`, `agent/src/runner.ts`): **canonical** (an attempt-less journal `{runId, clonePath}` at the canonical clone path, slot foreign-owned and active with no pending footprint or publication, and complete, non-conflicting attribution; a journal carrying an attemptId at the canonical path still refuses `predecessor_path`; a fresh unwired no-DinD key keeps canonical paths), **hosted** (this worker is a hosted pod with a valid own boundary record matching live, and P's slot has no publication) and a **missing boundary record** for P's incarnation (decided inside `evaluateComposeRestore`, so only after the own-record, single-pin and census checks pass; with no pin or several pins it refuses `no_eligible_pin` or `pin_ambiguous` and is not parked). Without the capability the item-7 nonterminal stop applies. The cause has a third meaning here: continuation was refused because this release does not support the predecessor, with no attempted adoption, no persisted `adoption_failed` blocker and no proven quiescence. The park changes none of P's bytes and reaps nothing. The parked run holds P's hold and the current generation's, and an owner Resume adds a claim and a hold; an owner-held hosted run blocks its worker's ordinary image roll until the owner cancels or discards it. Not delivered: the restore uses the single ordinary pin record of P's authenticated generation (several refuse `pin_ambiguous`, none `no_eligible_pin`); ordering among multiple records and a finalization-pin preference are not implemented.
- **P after a restore.** P stays retained, and its generation-G hold stays open and fails closed (`restorePredecessorHolds`: FINAL, settlement, ancestry and report retirement refuse for G). The hold counts toward `custody_hold_limit`. The only exit is the owner's guarded discard, S first and then P, through `agent/src/ops/retained-source-server.ts`, which removes the retained-home marker last. The server's verified-merge discard closes only server custody holds. Edits made in P after the pin are not carried into S; the loss is unmeasured.
- **6(e) failure model.** The boundary record follows steps 1 to 6: an unconditional data-root sync, a private `boundaries/` directory, a `.uzi-authority` sync, an `O_EXCL` tmp file, a non-replacing `link` (`EEXIST` refuses), unlink, a directory sync and a read-back. The restore's config writes are renames followed by a sync: the entry writes and the tombstone are also read back, and the seed's ledger append is checked only indirectly when the following `seeding` write re-reads the config. Later live successor `writeRestoreJournal` replacements have no following sync. The restore exit's `rewriteConfigAtomically` syncs its temporary file but not the directory, and the exit then calls `syncRestoreWrite`. The delivered guarantee is therefore the **process-crash model only**: a process or container crash, or an injected fault, leaves a refusal and never a reuse of P. **No storage or power-loss guarantee is claimed.** The 6(e) table row "after A commits, before S's bare attribution write" is met as a refusal: the next claim meets the restore entry or a foreign slot and stops.
- **6(f).** Q10 holds: a missing P record refuses (`predecessor_record_missing`). Rollback after a restore to any build before the restore-enabling release is **unsupported** (the compatibility proof below ran v0.87.0-rc.2's sources). The fence that every older build would refuse is not built (#3981). `agent/test/independent-restore-rc2-compat.proof.ts` records what rc.2 does to a restored fixture (#3644 amendment 9), and rolling forward from an rc.2-released predecessor reaches the guarded discards of S then P (#3644 amendment 14, `holdingEvidence` for the holding-root mode). Where rc.2's ledger compaction dropped the evidence, the roll-forward refuses and P's bytes stay. Record-only rollback is not separately evidenced by this delivery. Q9: no pruning, and production growth is unmeasured.
- **6(g).** Unchanged. The #3831 tripwire stays green, and eligibility grants no authority over P.
