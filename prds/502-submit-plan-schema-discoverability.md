## Problem

The `submit_plan` MCP tool (`mcp__uzi__submit_plan`) takes a single **required** argument, `plan_md` (a Markdown string), plus an optional `milestones` on issue runs. But nothing the model reads before calling **names that key or marks it the sole required argument**: neither the tool description nor the `plan_md` property `.describe()` mentions `plan_md`, and the planning prompt only says "call the `submit_plan` tool with the plan as Markdown". So a first call that supplies the plan body under a plausible-but-wrong key (`plan`, `summary`, `body`, `markdown`) fails zod validation, `plan_md` comes through undefined, and the model burns a self-corrected turn.

The validation error the model gets back is generated by the MCP SDK + zod, not by uzi, and it buries the key: `MCP error -32602: Input validation error: Invalid arguments for tool submit_plan: [ { "expected": "string", "code": "invalid_type", "path": [ "plan_md" ], "message": "Invalid input: expected string, received undefined" } ]` — the key `plan_md` appears only inside the structured `"path"`, and the human-readable per-issue `message` does not name it. uzi cannot cleanly rewrite that error text (the SDK produces it and the `submit_plan` handler deliberately ignores its input), but uzi **does** own the schema/description strings the model reads **before** it calls, which is the right lever.

## Solution

Strengthen the two uzi-owned strings in `agent/src/signals.ts` so the expected key is named up front:
1. the `plan_md` property `.describe()` — mark it REQUIRED, name the key, and say it is the only required argument (and that it is not `plan`/`summary`/`body`/`markdown`);
2. the tool description — name the `plan_md` argument in prose.

Keep `plan_md` **required** (`z.string()`, not `.optional()`): the required constraint does useful work — making it optional would let the SDK accept an empty call and `scanSignals` would silently record an empty plan, which is strictly worse than a self-corrected turn. Pin the change with a `signals.test.ts` assertion on the property description.

### Where the body is actually read, and where the error comes from

- uzi does **not** validate the call itself. The authoritative extraction is `scanSignals()` (`signals.ts:557-561`): it reads `input["plan_md"]` off the observed `tool_use` stream and treats a missing/blank body as an empty-but-submitted plan (`out.plan = out.plan ?? ""`).
- The rejection the model sees is produced one layer down by the **MCP SDK's zod validation** (`@modelcontextprotocol/sdk@1.30.0`, `McpServer.validateToolInput`), before the handler runs, and rendered from `zod@4.4.3`'s `ZodError.message` (`JSON.stringify(issues, …)`). There is **no api-side (`api/internal/`) validation** of the `submit_plan` call; the api only ever sees the resulting `runs.plan_md` column.
- **Not to be confused** with `agent/src/client.ts` `postPlanSummary()` (`~:358-364`), which is the worker→api HTTP body `{summary, deltas[], plan_md}` for plan-summary persistence (with `plan_md` a stale-write guard) — a different feature whose adjacent `{summary, deltas, plan_md}` shape is, if anything, a plausible source of the key confusion.

## Design decisions

1. **Fix the schema/description strings uzi owns, not the SDK/zod error.** The model reads the tool description and the property `.describe()` (which becomes the JSON `inputSchema` property description) **before** calling; naming the key there is the correct, in-repo, offline lever. The validation error text is SDK/zod-generated and the handler ignores input, so it is not uzi's to rewrite.
2. **Keep `plan_md` required.** Making it `.optional()` would let an empty call succeed and `scanSignals` would record an empty plan — worse than a named error and a retry.
3. **Concrete wording** (em-dash-free per repo style; note the existing `:209` strings carry pre-existing em dashes, which are left as-is):
   - `signals.ts:191` describe →
     `"REQUIRED. The full implementation plan, as Markdown. Pass it as the top-level string argument named 'plan_md' (not 'plan', 'summary', 'body', or 'markdown'). This is the only required argument."`
   - `signals.ts:209` description → append: `"Pass the plan as the 'plan_md' argument (Markdown)."`
4. **Do not touch `prompt.ts`.** The optional prompt tweak (`prompt.ts:752-754`) is deliberately left out so this PRD stays disjoint from PRD #501; the `signals.ts` change is sufficient.

## Risks & mitigations

- **Assuming uzi can rewrite the validation error.** It cannot (SDK/zod-generated; handler ignores input). Mitigation: Decision 1 fixes the pre-call schema/description strings the model actually reads.
- **Making `plan_md` optional to "avoid the error".** That records an empty plan silently. Mitigation: Decision 2 keeps it required.
- **Vacuous test.** Mitigation: M1 reverts the describe string to confirm the assertion reddens.
- **Introducing an em dash** in the new strings. Mitigation: Decision 3 wording is em-dash-free; the pre-existing `:209` em dashes are left untouched.

## Dependencies

- **No external / internet dependency.** The test inspects the built tool with scripted input; no live session, no network, no Anthropic token. Deps are already pinned in `agent/package-lock.json`; nothing new is added.
- **No shared-file collision** with the other batch PRDs: this touches only `agent/src/signals.ts` and its test; PRD #501 owns `agent/src/prompt.ts` and the runner/executor files (different files in the same module).
