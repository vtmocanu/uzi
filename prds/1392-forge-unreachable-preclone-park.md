# PRD #1392: Park a run on a transient forge failure at clone or fetch, instead of failing it

- **Issue**: #1392
- **Priority**: Medium
- **Surfaces**: agent (`agent/src/runner.ts` `phaseClone`, `agent/src/git.ts` `ensureClone`, `agent/src/forge-retry.ts`, `agent/src/recovery.ts`, `agent/src/protocol.ts`), api (`api/internal/workersvc/recoverywait.go`, `api/internal/workersvc/service.go` `SetState`, `api/internal/workersvc/failorigin.go`, `api/internal/workersvc/judge_enqueue.go`, `api/internal/recovery/service.go`, the `SetRunRecoveryWait` / release queries, one goose migration, `RunDTO` in `api/internal/apitypes/run.go` and `handler/runs_dto.go`), the three run surfaces (web run page, TUI, `uzi run get`), docs and two ADR amendments.
- **Guardrail**: nothing touches `.github/workflows/**`. The e2e phase runs locally under `./e2e/run-e2e.sh`.
- **Siblings**: #1390 (api-side outage recovery, its own PRD) and #1391 (worker-side batcher and terminal-report replay). #1324 (brainstorm) is the *finalize-time* forge outage, push and MR-open after the work is done; this PRD is the *clone-time* hop only and hands #1324 the typed cause and the cap counter to reuse (its clone-specific failure reason is not reusable). #1088 / PR #1385 is the Anthropic provider park, post-clone, a different trigger on the same `recovery_wait` state; the cause vocabulary below leaves it room (D9).

## Problem

On 2026-09-15 a run attempt started at 15:41 UTC and was `failed` at 15:42:

```
git fetch --prune origin failed: fatal: unable to access 'https://github.com/<owner>/<repo>.git/': Could not resolve host: github.com
```

Cluster DNS blipped on that node for well under a minute; the same worker fetched the same host successfully twenty seconds later. The retry loop in `withForgeRetry` had spent its schedule (six attempts, 31 s of sleeps) and `phaseClone` let the exhaustion escape into the generic terminal path: `fail_origin = agent_failure`, the issue released, the owner left to notice and re-dispatch. That attempt happened to be an illegitimate double claim (#1390), but a legitimate resume in the same window fails identically, and a run resumed from a park (`limit_wait`, `recovery_wait`, `pool_wait`, an owner pause) re-clones on every resume, so every resume is exposed.

The runtime already knows how to park on a transient condition it cannot fix by retrying: an empty model turn parks in `recovery_wait` and the sweeper promotes it back on a capped backoff (#1197). The forge being unreachable at clone is the same class of condition, but the existing park cannot be reused as-is (facts 5 to 9): it assumes a clone exists, its custody rules recognise no "never had a source" case, it has no cause and no lifetime cap, and its release call is best-effort.

## Solution

A **pre-clone transient park** built on the existing `recovery_wait` state and promotion cadence, with four additions: a typed cause, a forge-only lifetime cap, a fifth custody evidence class, and one atomic server transaction that settles custody and parks (or fails) together.

- **Worker (`phaseClone`)**: when `ensureClone` exhausts `withForgeRetry` with a transient verdict (only `ensureClone` is wrapped; `runnerCloneForClaim` is local, fact 4), the worker attempts **no** recovery capture (there is nothing to capture) and **reports first**: `{status: "recovery_wait", recovery_cause: "forge_unreachable", claim_generation}`. It acts on the acknowledged disposition (D10): `recovery_wait` → emit and flush one feed event carrying the acknowledged retry stamp, close the batcher, preserve the SDK session and HOME only if a transcript is resolvable for `claim.session_id`, return the slot; `cancelled`, or `failed` when the cap branch fired (the server has already committed the terminal state and answers 200 with `run.status = failed`), or any other authoritative terminal status → close the still-open batcher, terminal cleanup, no park event, no second report; `stale_claim` → stop silently, no further report (#1247); `custody_unsettled` → the batcher stays open and today's failed path runs; a transport failure after the send is an unknown outcome reconciled by the ownership probe until it is known (D10), never a failure. It calls no release endpoint itself on a current api; the release is the server's, inside the park transaction.
- **Api (`SetState`)**: the park for this cause is one locked transaction: validate the cause against the server enum; lock the run row and require `worker_id = me`, `status = running`, `claim_generation = request generation` and, once #1247 has landed, `claim_released_at IS NULL`; read the stamped stop verdict under the lock and, if a cancel is stamped, transition to `cancelled` instead of parking (D4); require **exactly one** open hold for (run, worker, generation) and release it with the new hold evidence `no_adopted_source` (D3); then park (`recovery_wait`, `recovery_wait_cause`, `forge_park_count + 1`, backoff from `recovery_wait_count` as today, `recovery_retry_not_before` returned on the ack) or, when the count would exceed `RUN_FORGE_UNREACHABLE_MAX_PARKS` (default 6, `0` = unlimited), fail the run with the server-derived `fail_origin = forge_unreachable` and a fixed reason. Precedence: a run-generation or `claim_released_at` mismatch answers 409 `stale_claim` with no custody or state change (#1247's rule, checked before anything mutates); only for a current, unreleased generation whose exact-hold cardinality or evidence step cannot settle does the transaction roll back with 409 `custody_unsettled`; a duplicate of an already-applied park answers 409 with status `recovery_wait` (idempotent, lost-ack safe). Promotion is `PromoteRecoveryWaitRuns`, unchanged. The judge is not enqueued for a `forge_unreachable` failure.
- **Resume**: a promoted run is `queued` with `worker_id` kept, so the affinity rules decide **placement** (fact 10) and the bare cache decides **warmth** independently (fact 11): the owner is usually warm on a fetch failure and cold after a failed first clone (the partial bare is removed); a sibling may be warm from another run of the same repo. Both are ordinary claims that open their own generation hold; the PRD tests placement and warmth separately.
- **Surfaces**: `RunDTO` gains `recovery_wait_cause`, `recovery_retry_not_before`, `forge_park_count` and `forge_park_max` (effective, `0` = unlimited); the run page pill, the TUI status line and `uzi run get` say "waiting for the forge, retry at HH:MM (N of MAX)" for this cause, and keep today's wording otherwise.

### User journey

- **Owner, DNS or forge blip under a minute**: the run's feed shows one line ("forge unreachable at clone, retrying at HH:MM"), the card reads a park, the run resumes on its own a minute later and continues. No re-dispatch, no held work, no failed run.
- **Owner, forge down for an hour**: six parks, then the run fails with `forge_unreachable` and a reason naming the count; nothing to recover from this claim, which adopted no new source (an earlier generation's artifacts, if any, stay under their own holds).
- **Owner cancels during the retries**: the run ends cancelled, as it does today.
- **Operator**: `RUN_FORGE_UNREACHABLE_MAX_PARKS` plus the existing `RUN_RECOVERY_PARK_BASE` / `RUN_RECOVERY_MAX_PARK` tune it; `docs/configuration.md` gains the knob.

## Resolved facts (baked in for an offline worker)

Read from the tree at `6603f793` and adversarially re-verified by a second session over two rounds; every line is re-checkable without egress.

1. **Retry shape.** `FORGE_RETRY_SCHEDULE = [1s, 2s, 4s, 8s, 16s]` (`agent/src/forge-retry.ts:25`): six attempts, five sleeps, 31 s sleeping; five `transient forge error; retrying push/MR-create` warnings precede the sleeps, the sixth failure rethrows (`forge-retry.ts:285-343`). Each git attempt has its own 10-minute timeout (`GIT_TIMEOUT_MS`, `agent/src/git.ts:132`), so the worst case is about an hour; a fast DNS failure is why the incident took 33 s. The log line names `push/MR-create` regardless of phase.
2. **Classification.** For generic git text: DNS resolution failure, connection refused/timeout, TLS phrases and HTTP 500/502/503 are transient; 401/403/404 win permanent; other codes only when another phrase matches (`forge-retry.ts:54-121`). A `ForgeError` with status ≥ 500 or 429 is transient on the API path, but a **git-text** 429 is not classified (`forge-retry.test.ts:67-95`). A closed port yields connection refused, which is transient (`agent/test/git.test.ts:147-178`). Warm fetch and cold clone both run through `withForgeRetry` (`git.ts:515-542`).
3. **Exhaustion today.** The error escapes `phaseClone` into the generic terminal failed path, `fail_origin = agent_failure` (`runner.ts:733-779, 911-1044, 1061-1112`; `workersvc/service.go:2689-2713`); the shutdown branch is separate.
4. **`phaseClone` ordering.** It reports `running`, starts the `SteeringChannel`, then awaits `ensureClone`, then `runnerCloneForClaim`; `flight.barePath`, `worktreePath` and `branch` are assigned after those succeed (`runner.ts:2946-3008`). Steering can consume and latch an owner cancel during the retries (`steering.ts:268-286, 591-594`), and the server turns a `failed` report with `stop_kind` into `cancelled` (`workersvc/service.go:2650-2678`). Only `ensureClone` is wrapped in `withForgeRetry`; `runnerCloneForClaim` is a local operation (`runner.ts:5326-5369`). A resume claim carries `claim.session_id`, but that does not prove a local transcript exists on this worker (`main.ts:123-132`); `sessionTranscriptResolvable` is deliberately fail-open, "present or unreadable" (`sdk-session.ts:124-178`), so "a transcript is resolvable" is the worker's existing notion, not a literal file check; `observedSessionId` is unset pre-clone (`runner.ts:2822-2829`) and `SetRunRecoveryWait` `COALESCE`s the session id (`runtime.sql:1794-1804`). A stop verdict is stamped by `CreateStopVerdictInput` concurrently and without a status guard (`runtime.sql:3451-3491`), so a cancel can land between any worker-side check and the park; today's failed path cannot settle pre-clone custody because `reapThenSettleRecoveryGeneration` returns when there is no bare path (`runner.ts:4569-4595`). Exact pre-clone inventory: `executeClaim` has already built the executor and HOME, registered secrets, the batcher, the abort controller and steering (`runner.ts:686-731, 2760-2870`); on an `ensureClone` throw there is no bare path, runner clone, worktree, branch, recovery journal, `ActiveRun` entry (set only at `runner.ts:2998-3003`), milestone, checkpoint or model session. The outer `finally` disposes Codex safety, stops steering, clears the gate and question maps and evicts secrets (`runner.ts:1114-1161`) but does **not** close the batcher; HOME is the only conditional artifact (`runner.ts:1203-1254`).
5. **The recovery park assumes a clone.** `handleRecoveryExhausted` captures a restore point that needs the clone paths; with none the attempt reads `verified: false` and retries capture while owned (`runner.ts:4597-4753, 4968-5018`); cleanup preserves HOME whenever `preserveSession` is true (`runner.ts:1230-1254`) and removes the runner clone in `finally` (`runner.ts:1203-1222`).
6. **Custody.** `ClaimRun`'s `hold` CTE opens a generation hold for a recovery-capable claimant on the six code-publishing kinds (`runtime.sql:843-862`); the custody-admission gate blocks the owner at `custodyHoldLimit` 8 open holds (`runtime.sql:711-723`). Open holds from failed releases therefore accumulate toward that gate.
7. **`recovery_wait` has no cause and no cap.** `setRecoveryWait` ignores the `StateRequest` and persists only the retry stamp and session id (`recoverywait.go:38-114`); `recovery_wait_count` shapes the backoff only; `PromoteRecoveryWaitRuns` promotes forever (`runtime.sql:1753-1839`); the park acceptance is guarded on id + worker + running and a duplicate is a 0-row no-op (`runtime.sql:1768-1804`). Defaults: `RUN_RECOVERY_PARK_BASE` 1 min, `RUN_RECOVERY_MAX_PARK` 30 min, jitter 5 to 30 s (`config.go:958-959`, `recoverywait.go:14-31`). `StateRequest` free-text fields are untrusted worker input validated in the service (`service.go:2100-2128`).
8. **`fail_origin`** is a server-side vocabulary of 12 values (`workersvc/failorigin.go:29-59`) with a worker-reportable subset (`failorigin.go:81-108`) and a matching CHECK; adding a value is a DROP+ADD (`migrations/00186…:30-45`). Every applied `failed` reaches `maybeEnqueueJudge` unless its origin is in the pre-start exclusion list (`service.go:2738-2762`, `judge_enqueue.go:20-31, 106-134`).
9. **Custody release and its evidence.** `POST /worker/runs/{id}/archives/release` with `{generation}` releases this worker's open hold of that generation (`recovery/service.go:476-539`, `recovery.sql:270-286`); `ReleaseCustodyHoldExact` trusts the supplied generation and can release an older same-worker hold; a v1 worker without a generation is refused as ambiguous when several are open. The worker wrapper swallows transport and server errors and returns nothing (`recovery.ts:509-555`). The holds table carries state, provenance and timestamps only, no evidence column (`migrations/00223:21-51`). A service-level transaction seam exists (`service.go:1358-1364`). ADR-1296 permits a release only on publication, archive, fresh-forge no-output proof, or owner discard, and requires a park to retain unverifiable work (`adr/1296-durable-run-recovery.md:235-261`); ADR-1197 allows only a verified capture before `recovery_wait` (`adr/1197-transient-recovery-park.md:40-58`); `ARCHITECTURE.md:662-688` restates both. None of them names the case where a generation never adopted a source; a warm bare or an older retained clone belongs to an earlier generation and is inventoried separately after clone.
10. **Resume placement.** Promotion keeps `worker_id` (`runtime.sql:1824-1838`); `ClaimRun` prefers the owner while it is live or draining and lets a sibling claim after `WORKER_AFFINITY_CEILING` (2 h) or once the owner is stale and not draining (`runtime.sql:675-700`).
11. **Cache warmth is independent of placement.** `ensureClone` warm-fetches or cold-clones by whether the bare exists (`git.ts:515-544`); a failed cold clone removes its partial bare (`git.ts:2697-2723`), so the owner is cold after a failed first clone, and a sibling may be warm from another run of the same repo.
12. **Review runner.** `ensureClone` also serves `review-runner.ts`; a clone failure there becomes a failed review inside a completed review run (`review-runner.ts:88-158`). Out of scope here (D6).
13. **State reports decode strictly** (`httpx.DecodeJSON` sets `DisallowUnknownFields`, `worker_protocol.go:597-624`, `httpx/respond.go:91-103`): an api that predates the new fields 400s a report carrying them (D7). Today's 409 body is `{run}` with no disposition and an unmapped service error is a 500 (`worker_protocol.go:614-649`); `readRunAck` parses status and budget fields only (`client.ts:363-418, 1057-1085`). An api that predates #1349 v2 has no generation-exact release, and its `SetRunRecoveryWait` touches `runs` only (`runtime.sql:1794-1804`) while an eligible claim still opened a hold.
14. **DTO.** `RunDTO.RetryNotBefore` is the limit-wait stamp only (`apitypes/run.go:554-580`); `runToDTO` maps `runs.retry_not_before`, not `recovery_retry_not_before` (`handler/runs_dto.go:209-220`); no effective cap is exposed.
15. **Live-DB tests.** `task gate:api` skips `*LiveDB` tests without `UZI_TEST_DATABASE_URL`; the required sweep is `./e2e/run-store-it.sh` or a serial `-p 1` run with positive RUN/PASS controls (`.claude/rules/go.md:75-100`).
16. **e2e harness and the forge.** In the default harness the forge URL is rewritten to a bind-mounted local git directory (`e2e/lib.sh:710-733`, `docker-compose.e2e.yml:237-245`), so stopping `forge-fake` does **not** affect clone or fetch; only the smart-HTTP mode removes the rewrite (`lib.sh:696-708`). A stopped container is expected to answer connection refused or a connect timeout rather than a DNS failure; all three classify transient, and the phase asserts the park, not the phrase.
17. **Migration head** is `00229` on `main`; #1247 drafts `00230`/`00231`, #1390 drafts `00232`; this PRD drafts `00233`, renumbered at the landing rebase (CLAUDE.md, migration numbering).

## Success criteria

- **SC1**: a transient forge failure at clone or fetch parks the run with `recovery_wait_cause = forge_unreachable` whenever custody and protocol settlement are confirmed, and it resumes on promotion (M1+M2, proven by M3 and M4); when settlement cannot be confirmed the run fails safely without releasing an unproven hold, exactly as today.
- **SC2**: parking opens no capture and leaves no open custody hold for the parked generation, because release and park are one locked transaction and anything but exactly one eligible hold refuses the park; on an older api the worker parks only after a positively confirmed exact release; the owner's open-hold count is unchanged across any number of forge parks (M1+M2+M3).
- **SC3**: past the cap the run fails with `fail_origin = forge_unreachable`, a reason naming the count, and no judge run; a permanent forge error still fails at once; an owner cancel during the retries ends cancelled (M1+M2).
- **SC4**: owner and sibling placement are proven on the api, warm and cold clone paths are proven on the agent; an older api receiving the typed report degrades to today's untyped, uncapped park when its exact release is positively confirmed, and to today's safe failure otherwise, never to a leaked hold (M2 D7, M3).
- **SC5**: the empty-turn and provider parks keep their scheduling, session and cap behaviour unchanged: their cause stays NULL and they neither increment nor reset `forge_park_count` (a run that forge-parked earlier keeps its lifetime count through a later empty-turn or provider park); `recovery_retry_not_before` and the effective `forge_park_max` are simply reported for them too.
- **SC6**: `task gate:api` plus the live-DB sweep, `task gate:agent`, `task gate:web`, `task gate:repo` (the staged e2e script), `task check:migration-additive`, `task check-docs:web` green; the e2e phase green locally.

## Decision Log

- **D1 — Reuse `recovery_wait`, add a cause; do not add a fourth park state.** The state already has the promotion cadence, the owner cancel path and the surfaces. A new status would touch the thirteen-value status list on every surface for no semantic gain. The cause column is what makes a forge-only cap and forge-specific wording possible without changing the empty-turn park. ADR-1197 and ADR-1296 are amended to admit the pre-clone case (M5), because a new ADR beside contradicting ones would leave the contradiction.
- **D2 — Forge-only cap, counted separately from the backoff, decided at report time.** `recovery_wait_count` keeps shaping the backoff for every cause; `forge_park_count` is the cap's counter so the empty-turn park keeps its "no lifetime cap" contract (fact 7). The park-or-fail decision is made inside `SetState` and fanned out as an authoritative status; a sweeper-side cap would fail the sixth *sleeping* park later and race promotion and cancel. Six fresh parks are about an hour of waiting at the defaults, more when earlier parks already raised the backoff; `0` disables the cap.
- **D3 — Custody is settled in the same transaction as the park, under a fifth evidence class.** The worker-side release is best-effort and blind (fact 9), so "park after releasing" cannot promise zero holds (finding folded from review). A generation that never adopted a source has nothing to prove against the forge: its hold releases on that evidence, recorded in a new constrained `release_evidence` column on the hold (fact 9 shows today's table cannot represent it); anything already on disk belongs to an earlier generation and is inventoried after the next successful clone as today. The transaction requires exactly one eligible hold for the exact (run, worker, generation) because the existing exact release trusts the supplied generation and could release an older same-worker hold; zero, several, or any failed step is a refused park, never a silent one.
- **D4 — The park is reported from `phaseClone` after the running report and steering start, so it unwinds exactly those.** Nothing downstream of the clone has run (no checkpoint, no progress, no scope state), but a cancel can be stamped at any moment (fact 4) and the feed should only promise what the server acknowledged: the park transaction reads the stamped stop verdict under its lock and cancels instead of parking, still releasing the generation's hold (today's failed path cannot settle pre-clone custody), and the worker emits the feed event only on a `recovery_wait` ack, closing the batcher after it so a later error is never dropped. HOME is preserved only after that ack and only when a transcript is resolvable, so no terminal or stale HOME leaks (fact 5).
- **D5 — Placement and warmth are separate facts, both tested.** Affinity decides which worker claims the promoted run (fact 10); the bare cache decides whether that worker fetches or clones (fact 11). The PRD promises neither "same worker" nor "warm"; it promises both paths work and that the owner is preferred while live.
- **D6 — Review runner excluded.** A review run's clone failure is reported inside a completed review run today (fact 12); changing that is a different product decision and its runner has no park protocol. Named here so the boundary is explicit.
- **D7 — The cause is additive and degrades capability-aware; the generation never degrades.** A 400 from an api that predates `recovery_cause` (fact 13) is retried once without it; whether `claim_generation` stays on the state report depends on what the api advertised: the #1247 state fence accepts it, the `6603f793` baseline does not (its generation lives on the release request only), so the fallback is split by capability rather than guessed. Because an older api's park touches no custody (fact 13), the untyped fallback is allowed only after a positively confirmed exact release; otherwise the worker fails as today. The accepted degradation on a mixed fleet is therefore: an untyped park with no cause, no forge count and no cap, or today's failure, never a leaked hold and never a lost heartbeat. This differs from #1390 D7 because a heartbeat cannot be retried without cost, a park report can.
- **D8 — #1324 reuses, this PRD does not absorb.** Finalize-time outages have committed work, a pushed-or-not branch and an MR-or-not; their custody question is the opposite of this one. They get the same cause value and cap counter, which is why both live on `runs` rather than in a clone-phase-specific place.
- **D10 — The park report's ack carries a disposition the worker dispatches on.** `recovery_wait` (parked, with the retry stamp the feed event quotes), `cancelled` (a stamped cancel won the lock), `failed` (the cap branch committed the terminal state; treated like any authoritative terminal ack: cleanup, no park event, no second report), `stale_claim` (#1247: stop silently, no further report), `custody_unsettled` (fail-safe: today's failed path), and a duplicate park answering `recovery_wait` so a lost ack is idempotent. Everything the worker shows or cleans up follows the ack, never precedes it; a transport failure after the send is reconciled by probe until the outcome is known, never treated as a failure.
- **D9 — Cause vocabulary leaves NULL for legacy and reserves `provider_outage` for #1088.** Mapping an absent cause to `empty_turn` would mislabel the provider park PR #1385 emits untyped today; NULL means "untyped", the enum names the three typed causes, and #1088 adopts `provider_outage` when it lands.

## Risks

- **Flapping forge**: a forge that fails at clone on every other attempt keeps a run parked for up to the cap; bounded by design, and the owner cancel path still works throughout.
- **Cap too low for a real outage**: 6 parks is about an hour; an operator can raise it or set `0`. Named in `docs/configuration.md`.
- **Landing order**: #1390 (draft `00232`) and #1247 (`00230`/`00231`) touch `runtime.sql`, `worker_protocol.go`, `protocol.ts` and `runner.ts`; numbering is settled at the rebase (CLAUDE.md, migration numbering) and the touched regions do not overlap in intent (claim/heartbeat vs the park writer). #1247's generation fence, once merged, applies to this park report through the `claim_generation` it already carries.
- **A git-text 429 at clone is not classified transient today** (fact 2); it stays a failed run unless a later change adds the case. Out of scope.
