A Codex root turn classified cyberPolicy or misalignmentPolicyViolation currently ends its run as provider_policy_refusal. The owner can lose the opportunity to continue with narrower guidance even though files and a conversation may remain usable. Conversely, ordinary Codex recovery can fall back from a rejected/missing conversation to a fresh one. That fallback must not silently reset a conversation after a policy refusal.

The earlier #3068 design coupled this outcome to accepted-plan Stop authority, revision receipts and a broad implementation/proof program. Its preserved checkpoint is work in progress, not an implementation baseline or permission to ship those unfinished pieces.

A policy classification is an observed provider result, not an explanation of why the provider refused.

**Guarantee boundary:** the durable server state protects applied refusals under the lane-specific consent rule. Surviving local pending evidence protects the affected run from competing execution on its worker before application. Unrelated work follows the bounded scoped-claim and unchanged bodyless compatibility contracts in [ADR-3607](../adr/3607-compact-policy-hold-m1-isolation.md). If that worker/journal is absent past TerminalPendingLease (default one hour) and another worker reclaims first, or the declared server-wall release race precedes delivery, the server may not yet know the refusal: an unconstrained claim can start a fresh conversation. This is a named residual, not a global guarantee for an unapplied observation. State it in owner docs and A1 and test it explicitly; do not infer historical authority to conceal it.

**Attempt-path decision and disclosure:** main at 95bc98be sets attemptPaths from Docker wiring and drops session_id before transcript checks on every new effective-attempt-path claim (runner.ts:3034, 11661, 11929-11952). Retained recovery can enable that mode on an unwired worker too. The compact feature does not make that path session-compatible. Its Resume action must say **fresh conversation from the saved work**, show preservation provenance, and require explicit owner consent bound to this exact held episode. Once that owner transaction queues the run, the episode is resolved and later claims behave as today, including normal attempt-path session resets. They do not repeatedly re-hold merely because this earlier refusal occurred. A new actual refusal creates a new held episode requiring new consent. This deliberately relaxes until-terminal consent only for the attempt-path rule; do not promise same-conversation resume or blame the provider for a path-based refusal. In-process approval is not itself proof of a new claim. Same-conversation resume on Docker-wired lanes is a separately tracked follow-up, not a blocker here.

**Compatible-to-attempt transition:** a run may first refuse on a compatible path, successfully Preserve, and later be claimed on an attempt path. It must first re-hold with the fresh-from-saved-work warning. If the owner confirms that episode, the transaction clears preserve_required and **ends the earlier compatible-lane until-terminal guarantee for the rest of this run**, including later compatible-path claims, until a new refusal starts a new episode. Show this consequence in the confirmation and owner docs, not only in the implementation comments. It is the approved lane-transition consequence, not a reusable one-claim Fresh grant.

**Operational cost:** an indefinite hold retains affinity and custody. Its retained open custody holds count toward the owner's admission limit of 8 under existing accounting and can block new runs; do not confuse a policy hold with an exemption from that limit. A paused assigned run also keeps the hosted worker busy in ListHostedWorkersForController, so #3103's drain-until-idle/template roll may wait indefinitely. This feature adds no admission relief, force roll or hold timeout; it must not advertise an operationally idle held worker or release custody just to escape the limit. Exercise these consequences in tests and document them.

Owner actions:

- **Resume on an effective-attempt-path lane:** explicitly confirm fresh conversation from the saved work for this refusal episode, with optional guidance. Atomically resolve that episode and queue the run. Later claims follow today's behavior, until another refusal; an old request cannot consent to that later episode. There is no separate per-claim Fresh grant on this lane.
- **Resume on a session-compatible lane, optionally with guidance:** continue the preserved conversation. Missing/unknown transcript or provider rejection re-holds as resume_rejected without thread/start; preserving remains required on later claims. If recovery actually changes to an incompatible attempt path, first re-hold with the newly verified fresh-from-saved-work mode; never silently reinterpret an earlier Preserve action as that consent.
- **Explicit Fresh on a session-compatible lane, subject to its safe-cut checkpoint:** consent permits one fresh conversation under one claim, retaining the until-terminal constraint for later claims. Files, plan approval/framing and ordinary execution constraints remain. A lost response, worker crash, later claim or credential change cannot reuse that permission. If this narrow checkpoint cannot pass, leave this option unavailable and use the scope-cut/partial-delivery decision; do not build a broader grant subsystem. This optional path is distinct from the attempt-path episode Resume.
- **Cancel:** existing terminal cancellation; source/custody disposition remains independently guarded.
- **Existing Stop, conditional:** finalize the existing completed scope only. It is unavailable during a pending revision or when current evidence is uncertain. It must have service-side enforcement and an ordinary-executor zero-new-root-turn proof. If that cannot be achieved narrowly, ship this hold with Stop unavailable, record why, and leave the extension to a follow-up. Do not rebuild the old accepted-Stop subsystem.

Acceptance examples:

1. On a session-compatible lane, an implementation root refuses. The worker captures through its genuine safety boundary and holds, without completion, a second root turn or an MR claiming success. The owner adds guidance and resumes. If the provider supports continuing that session, its next turn includes the guidance. If it refuses again, the run holds again. Simulated provider tests prove both branches; real-provider behavior is A1.
2. On an attempt-path lane, the first refusal holds. A legacy/empty Resume or a token change cannot silently start a fresh conversation. The owner explicitly confirms fresh from saved work; the queued run and a later ordinary pickup need no repeated consent for that resolved episode. A new refusal holds again, and replaying the old episode's confirmation is refused. On a session-compatible lane with a missing conversation, Resume re-holds; only a new explicit one-claim Fresh choice permits a fresh start, and a later reclaim cannot reuse it.
3. A hold POST applies but its response is lost. The owner resumes before local replay. Reconciliation recognizes the already-applied outcome and cannot undo the owner action, reopen a resolved attempt-path episode or consume a compatible-lane Fresh permission. An unapplied surviving refusal can be re-held by the independently authorized current claim without a model turn or consent consumption; absent that authority it stays visibly pending. Cancel remains effective. Stop is offered only under its narrow service-side eligibility.

### 2. Lane-specific consent: episode Resume versus preserving continuation
