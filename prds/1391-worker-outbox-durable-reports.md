## Problem

On 2026-09-15 the api was unreachable for about 50 minutes while three runs kept executing on their hosted worker. Ten minutes in, each run's message batcher tripped its breaker and never recovered: nothing those runs produced afterwards ever reached the api, the board stayed empty for hours, and the health detector read the silence as `stalled` on a run that was mid-implementation. The trip also fired a `failed` state report that happened to die in the same outage; on a shorter outage it lands and marks a healthy run failed. A prompt run finished during the outage with its PR open, its `completed` report exhausted its retries, the executor's fallback `failed` report exhausted too, and the run was later requeued and redone from scratch.

Every one of these is the worker treating the api as the only place a message or an outcome can live. It has no durable local queue, no ordered replay, and no fence between "the trace is complete" and "the run is complete".

## Solution

A **worker-owned, authenticated outbox** under `/data`, an **ordered replay** driven by heartbeat success and worker startup, and a **write-ahead terminal-report contract** the api can trust.

- **Messages (Run A)**: the transient class never trips the batcher. After `TRANSIENT_TRIP_MS` of failures a run's batcher switches its flush target from the network to the outbox (same batching, same cadence, each flush one fsync'd segment) and stays "spilled" until a heartbeat succeeds; a per-worker drainer then replays every run's segments in `seq` order over the normal messages route and retires each on 2xx, and the batcher resumes flushing to the network. The permanent class (401/403/404, rejected tombstone, exhausted bisect) keeps today's trip and `failed`. Every segment records the claim generation it was produced under. A dropped range (quota, `ENOSPC`) is recorded locally as one compact range record and expanded at replay into **one tombstone per seq**, so the stream stays contiguous for the browser and honest for the fence.
- **Terminal reports (Run B)**: `completed` / `failed` of run-lane attempts (issue-family kinds, judge and review; chat excluded, D6) are journaled **write-ahead**, installed exclusively (first writer wins), keyed by run and claim generation, carrying the phase at journal time and a `messages_through_seq` fence, **before** the first network attempt; the send then proceeds and the journal is retired only when the transition applied (200) or the returned status is terminal. Replay sends the run's messages first, then the terminal report with the fence; the api refuses a terminal transition whose fence is ahead of `runs.last_seq` (typed 409, `messages_pending`). A journaled outcome is the outcome: no executor falls through to a second `failed`.
- **Claim protection (Run B)**: a run with a pending terminal journal is listed in the worker's snapshot with `terminal_pending: true` (#1390's contract), which keeps the api from re-claiming it or advancing its generation; the pending set is sent **with the register request** (`RegisterRequest.active_snapshot`, defined in #1390 M2a: persisted before the orphan pass, nonce exempt because no nonce exists yet) so those leases exist before any sibling can claim; the heartbeat loop starts before the boot replay so leases keep refreshing; on boot the worker resolves every pending terminal journal **before** starting its claim loops, and keeps them closed while the pending set exceeds what the api will lease; a queued second attempt in the common run-lane router drains that run's pending terminal and probes ownership with the generation before executing.
- **Visibility (Run A)**: the heartbeat reports per-run outbox depth in its own isolated field; the api's health detector turns a non-zero depth into a server-written reason ("updates are queued on the worker and will replay") instead of the misleading `stalled`; `uzi admin workers` shows the depth.

### User journey

- **Owner, api outage of any length**: the feed pauses, then catches up in order when the api returns, with a contiguous run of gap markers only where a quota forced a drop. Replay starts within one heartbeat of the api returning and a run that finished during the outage is `completed` with its MR once its own backlog has replayed; nothing is redone.
- **Owner, worker restarts mid-outage**: on boot the worker replays its pending outcomes before claiming anything; a finished run's outcome lands even though the process that produced it is gone.
- **Owner, short outage**: no `failed` report is ever produced by a transport failure; once the worker's heartbeat reaches the api, the run's health can read "queued on the worker" while the backlog drains and clears itself.

13. **Interlocked carve-out.** Live post-attempt interlocked runs are excluded from the ordinary timeout sweep (`sweep.go:45-80`); without replay a lost terminal report on one of those leaves it non-terminal indefinitely.

It is **atomic and server-enforced**: the cancel is one owner-scoped row-locked `UPDATE` whose predicate joins the run to its `worker_active_runs` row on the owning worker, the run's exact current generation, `terminal_pending = true` and an unexpired lease, **or** to an owning worker under an unexpired `pending_overflow` when the run is not listed (M4's rotation makes that window short, the alternative predicate makes it never a dead end); a Go-side check followed by `CancelRunServerSide` would race a clear or a re-claim and cancel G+1 on stale G evidence. If the replayed `SetState` wins the lock the cancel answers with the terminal state; if the cancel wins, the replay's no-op 409 returns `cancelled`, the journal retires, MR coordinates still reconcile through the no-op terminal path (`service.go:2721-2732`, fact 3), completion side effects never fire, the pending set shrinks and claims reopen on the next snapshot. The api treats such a run as having **no live poller** (today's `hasLivePoller` would call a fresh, non-parked run live and enqueue a cancel to an executor that no longer exists, `service.go:4558-4594`, `submit.go:285-370`). The confirmation is **server-enforced, not UI-only**: without `discard_pending_outcome: true` on the cancel request the api answers a typed 409 `outcome_pending_confirmation_required` (today's CLI cancel is an unconditional POST with no force flag, `run_lifecycle.go:126-144`, and would otherwise silently discard a completed outcome); the CLI gains `uzi run cancel --discard-pending-outcome` (non-TTY safe, no prompt), the web modal names what is lost and retries with the bit; owner-only, admin read-only tokens get 404. Surfaces this adds: `api/cmd/uzi/run_lifecycle.go`, the cancel request/client/handler, `web/src/RunView.tsx` and `web/src/lib/api.ts`. Nothing is ever discarded on a timer (D13). First-writer arbitration: the first durably installed outcome for a generation wins; a later different outcome is logged and dropped; the permanent-failure hook awaits its `failed` journal's durable installation and then **aborts** the attempt, so a completion that raced it can never reverse the winner (D5). Every executor's catch treats a journaled outcome as final and never attempts a fallback `failed` (fact 2). Judge and review journal their terminal **state** only, never the verdict or review POST (D6). Api: `SetState` for a terminal transition carrying `messages_through_seq` (validated `>= 0`) refuses with 409 `messages_pending` when `runs.last_seq < messages_through_seq` (checked first, cheap) **or** `count(run_messages where seq BETWEEN 1 AND messages_through_seq) < messages_through_seq` (contiguity over the existing `(run_id, seq)` index; `last_seq` alone is a maximum, seq has no positivity check, fact 4), so judge, task-review and notifications never fire ahead of a complete trace. A new read `GET /worker/runs/{id}/message-gaps?through=N&limit=&cursor=` returns the missing seqs as bounded ranges with a cursor (index-backed; the read never materialises N rows), so a worker whose outbox is fully drained and still refused (a hole from before this feature, or a dropped range) fills them page by page with per-seq tombstones ("unrecoverable gap"), re-checks, and retries; total fill is bounded by `WORKER_GAP_FILL_MAX` (default 10,000 seqs) and the api answers a **typed 409 `gap_unrecoverable`** (never a 400, which D9 would read as an unknown field and strip the fence) when `messages_through_seq` is more than that far above its stored count, since the schema has no positivity or contiguity CHECK (fact 4) and one absurd seq could otherwise imply billions of holes; past the bound the journal is marked `blocked` with reason `gap_unrecoverable` (D13) instead of spinning. The fence itself is **negotiated**: the api advertises `terminal_fence` in `protocol_features` once this milestone lands, the worker sends `messages_through_seq` only then, and D9's fallback applies only to an api that does not advertise it. The 409 body is `{run, reason: "messages_pending"}`; `readRunAck` / `StateAck` gain `reason`, and an unreadable body is treated as "keep the journal", never as retired. ## Success criteria

- **SC1** (Run A): no transient api failure of any length produces a `failed` report; every message the batcher has flushed to the network or spilled to disk lands once, in order, contiguous, with per-seq gap markers only where a quota or the spill buffer cap forced a drop (M1+M2, proven by M5); a run re-claimed before its replay completed loses the old attempt's unreplayed frames semantically, with no server marker, until #1390 protects pending runs (D11). A worker process crash loses the spill buffer contents not yet flushed (at most the cap) while spilled, and the unbounded in-memory buffer as today when not; a range record for cap-pressure drops is written at the next flush; a crash before that flush loses the accounting too, and the loss is semantic (the next attempt reuses the seq numbers), admitted through the `spilled_unclean` marker's restart log line, never sized, inferred or fabricated.
- **SC2** (Run B): a terminal outcome produced during an outage is journaled before it is first sent while the reserve holds (four hard-max journals by default), lands after the api returns, after its messages, and its api side effects fire only then (M3); past the reserve it is sent unjournaled as today, logged and counted, never silently dropped.
- **SC3** (Run B): a worker restart during an outage still lands the outcome, before the worker claims anything (M4).
- **SC4** (Run B): no second execution of a run-lane run ever starts over a pending outcome or a stale claim generation, because a pending outcome is leased from the register request onward and, while the pending set exceeds the lease quota, the `pending_overflow` flag closes every run this worker owns to every claimant (M4 with #1390). Chat is excluded (D6).
- **SC5**: an older api never loses a heartbeat to the new fields and never sees a fence (D8, D9); an older worker image keeps exactly today's behaviour, its 10-minute breaker and false `failed` included, until the fleet rolls.
- **SC6**: the outbox is bounded (quota, derived physical reserve, retention, spill buffer cap, canonicalised terminal size), authenticated against accidental corruption and against the runner on the split-UID runtime, and its hosted single-UID residual (integrity and durability against a hostile model) is documented (M1, D1).
- **SC7**: `task gate:agent`, `task gate:api`, `task gate:web`, `task gate:repo` (the staged phase script), `task check-docs:web` green; the e2e phase green locally.

## Decision Log

- **D1 — Authenticated outbox in worker-owned `/data`; the hosted single-UID residual is named, not hidden.** The run HOME is deleted at terminal cleanup and shared with the runner; `/data` is the recovery journal's precedent. On the split-UID runtime file modes keep the runner out and the MAC catches accidental corruption. On the hosted runtime there is no UID split (fact 7): the model process shares the uid, can read any key the worker can, and can therefore forge, truncate or delete any run's outbox; against a hostile model the outbox guarantees neither integrity nor durability there, and the docs say so. The key is a worker-local secret rather than the join token only so that token rotation does not strand records. A two-container split on hosted k8s is the follow-up that closes the residual (`docs/proc-hardening.md` rules out the `setpriv` flag there); it is not in this PRD.
- **D2 — Bounded, contiguous, never silent.** "Deliver every message" cannot be unconditional (fact 10). Quota and `ENOSPC` replace the oldest segment with one compact range record that replay expands into one api tombstone per seq, so the browser stream (contiguous only, fact 4) and the terminal fence both stay honest without the replacement ever being larger than what it replaces; a physical reserve file, released on `ENOSPC`, is what makes the range record and the next few terminal journals writable on a full volume; beyond its stated size the outcome is sent unjournaled as today, which is a bounded, logged degradation rather than a promise.
- **D3 — Terminal reports are write-ahead and fenced on `runs.last_seq`.** Journaling only after exhaustion (fact 2) loses the outcome to a crash during the retries and to a typed 409 on the first attempt; journaling before the first send makes the journal the outcome from the start. The fence keys on the existing high-water mark plus a contiguity count, because `last_seq` is a maximum and inserts admit holes (fact 4); D2's per-seq tombstones are what make an honest worker able to satisfy it.
- **D4 — Terminal journals are keyed by generation, carry the phase, and are installed exclusively.** With #1247 a completion under an old generation is refused; a journal that names its generation is exactly what replays correctly under the right one and retires as `stale_claim` under the wrong one; the phase it records is what #1390's snapshot reports for a pending outcome after a restart. Temp-and-rename replaces and a bare exclusive create is not crash-atomic (a partial file would block the legitimate writer), so first-writer-wins needs temp + `fsync` + a no-replace link under single-flight (fact 10): two outcomes for one generation (the permanent-failure hook's `failed` racing a completion, fact 1) resolve to the first durably installed.
- **D5 — A permanent message failure aborts the attempt.** Today it reports `failed` while the executor keeps running (fact 1), which is the split-brain in miniature. Journaling `failed` and aborting makes the run's state and the worker's behaviour agree.
- **D6 — Judge and review journal terminal state, never the verdict; chat is out of terminal journaling and the claim fence.** The timeout sweep excludes judge runs (fact 12), so a lost judge terminal would sit `running` forever under a live heartbeat; journaling its terminal state closes that, a `failed` judge stays manually re-judgeable from the run page, and the verdict POST is never replayed (it would duplicate notifications). Review follows the same shape. Chat has no claim generation (#1390 D10), so neither the generation-keyed terminal journal nor the queued-attempt fence can apply to it; chat keeps the message outbox (Run A) and today's terminal behaviour.
- **D7 — Boot gates claims on pending outcomes, not on a timer.** A 60 s bound is not a correctness boundary (fact 11: two timeouts already exceed it); the claim loops start only once every pending terminal is retired or listed `terminal_pending` in the snapshot, stay closed while the pending set exceeds what #1390 leases, and message drain stays in the background; the pending set travels with the register request so the leases exist before the api's register-time orphan pass runs.
- **D8 — Heartbeat extensions use the shared negotiation and the isolated-field pattern.** `RegisterResponse.protocol_features: string[]` is the one wire shape for #1390 and #1391 (whichever lands first adds the field, the other its value); the outbox report is its own `json.RawMessage`, parsed drop-not-fail like `stats`, so a malformed or oversized report never costs a heartbeat. The register advertisement is a **deduped UNION of per-feature slices, never a single literal a sibling PRD would overwrite**: this run (Run A) adds `heartbeat_outbox`; #1392 adds `recovery_park_cause` and `recovery_release_exact_echo`; whichever lands second merges the slices at its landing rebase (union, never replace). `claim_generation_fence` and `terminal_fence` are advertised by #1247/#1390 and Run B respectively, on their own slice, not here, so a current api never tells the worker to send a fence it still rejects.
- **D9 — The fence is negotiated; a 400 is only ever an unknown field.** The worker sends `messages_through_seq` only to an api that advertises `terminal_fence`; a 400 from an older api is retried once without it, and the worst case there is today's unfenced completion, never a lost outcome. A recognised invalid fence is a typed 409 (`gap_unrecoverable`), so it can never be confused with the unknown-field case and never strips the fence.
- **D13 — A blocked outcome is surfaced and owner-resolved, never timed out.** A journal the api permanently refuses would otherwise hold the worker's pending set, and through `pending_overflow` its claims, forever. The manifest records the reason, the heartbeat and DTO show it, the run's health names it, and the owner's cancel, through an atomic owner-scoped no-live-poller branch that the server refuses without an explicit discard bit, produces the terminal ack that retires it; a silent discard would trade a visible stall for a lost outcome.
- **D12 — Segments are immutable and one generation-numbered manifest is the only metadata authority.** In-place mutation would break both the MAC and the crash contract, so every rewrite is a new versioned file plus the next manifest generation; the cursor lives inside the manifest so two metadata files can never disagree after a crash; only a valid manifest can prove that a seq range is missing, which is why a bad record is "rejected and logged" and a gap marker needs manifest evidence.
- **D11 — Run A records generations and retires stale segments locally; it does not pretend to protect them.** Under #1247 every append is fenced by generation, so a segment must know the generation it was produced under; until Run B and #1390 lease a pending run, a re-claim can still bump the generation before replay. The old segments cannot be written under the old generation, tombstones for them cannot either, and rebinding them to the new generation would fabricate frames the new attempt never produced; the next attempt reuses the seq numbers, so there is not even a numeric hole to mark. The honest outcome is a local retire with a warning and a `stale_retired` counter the operator can see on the worker (manifest, heartbeat, DTO): an admitted semantic loss, not a silent one and not a forged replay.
- **D10 — Two runs, one PRD, two issues.** Run A (#1391) is self-contained and shippable now; Run B (#1393) needs #1390's lease, register snapshot and overflow closure to make "no generation bump under a pending outcome" true (fact 6), so it is dispatched after #1390 and #1391 merge. Two issues rather than one scoped run because the scope ceiling is positional and cannot be attached to an approval atomically.

## Risks

- **Replay burst after a long outage**: bounded by the quota and by the api's per-batch limits; the drainer sends one batch at a time per run and yields between runs.
- **Hosted single-UID residual** (D1): a hostile model command on a hosted worker can read the key and forge, truncate or delete any run's outbox; neither integrity nor durability against it holds there until the follow-up lands. That follow-up is a **two-container split** (the model process in its own container behind an IPC boundary): `docs/proc-hardening.md:129-150` explicitly warns against mapping the `setpriv` UID flag onto restricted k8s, so `UZI_UID_SPLIT` is not the hosted answer.
- **Landing order**: Run A overlaps #1247 and #1390 on `runner.ts`, `client.ts`, `protocol.ts` and `worker_protocol.go` only at the message path; Run B overlaps #1390 on the snapshot and claim router and must follow it.
- **Stub executor pacing in e2e** may need a small sentinel to keep emitting during the outage; add it beside the existing ones in `executor.ts`.
