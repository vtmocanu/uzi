## Problem

A user who wants the runtime's own judgment ("let Claude Code or Codex pick") cannot express it. Both effort controls on **Settings → Run defaults → Reasoning effort** offer only "Inherit (uzi default: medium)" or an explicit level, and the server turns an unset preference into `medium` on every claim, so some effort is always sent.

Separately, a Codex model may not accept every level uzi offers. uzi passes the level through unchanged (correct), but nothing tells the user why the turn then fails: the transport never surfaces the provider's message text, so an unsupported level reads as an opaque `badRequest` failure, and no test pins that uzi does not rewrite or retry the level.

## Outcome

Each harness's effort preference gains a third state beside "Inherit (uzi default: medium)" and an explicit level: **Runtime default**. It stores the sentinel `runtime` in the existing column, and every claim built from that preference carries no `default_effort`, so no effort reaches the SDK/CLI, `thread/start`, root, child, advice or cross-check `turn/start`, in every lane that reads the setting today. For Codex, uzi never rewrites a chosen level: a level the runtime's own catalog does not list for the run's model is sent unchanged after a visible warning, and a provider rejection fails the turn through the normal path with no retry at another level. Showing the Codex catalog default is child B2; Claude shows "value not reported".

### Acceptance examples

1. **Codex Runtime default.** A user picks Codex effort **Runtime default** and saves. A new Codex issue run's claim JSON has no `default_effort` key; the root `thread/start` and every root and child `turn/start` carry no `effort` key. An unpinned Codex cross-check child of that user's Claude run also has no `default_effort` and sends no `effort`; its result view reads "Effort: runtime default (worker default)".
2. **Claude Runtime default.** A user picks Claude effort **Runtime default**. Issue, judge, chat and job claims for that user have no `default_effort`; `buildSdkOptions` has no `effort` key and the CLI gets no `--effort`. `uzi settings get` prints the row `effort  claude  runtime default  medium  runtime default (value not reported)  your choice`.
3. **Unsupported Codex level.** A user with Codex effort `max` and a custom Codex model `gpt-5.5` (catalog lists `low…xhigh`) starts a run. Before the first `turn/start` the activity feed shows "Codex 0.162.1 does not list reasoning effort max for gpt-5.5. uzi sends it unchanged; the provider may reject it. Choose a listed level or Runtime default." The `turn/start` carries `effort: "max"`. If the provider rejects the turn, the run fails through its normal failure path and no second `turn/start` with another level is sent.

## Modules and seams

### 1. Effort resolution (`api/internal/agenttmpl/effort.go`), the single stored-to-wire mapping

- `EffortRuntime = "runtime"`: the stored and API token for Runtime default. Not a member of `EffortLevels`.
- `ValidateDefaultEffort(raw string) (string, error)`: for the two user preference fields only. Blank → `""` (store NULL); `runtime` or one of `EffortLevels` (exact, after trim) → that value; else the existing error text extended with "or runtime". `ValidateEffort` (cross-check pins) is unchanged and still rejects `runtime`.
- `ResolveHarnessEffort(harness string, stored *string) EffortResolution` where `EffortResolution{Mode, Level, Source}`: `Mode` is `explicit` or `runtime_default` (child H's tokens); `Level` is set only for `explicit`; `Source` is `user_default` or `builtin`. Mapping: NULL/blank → `explicit`, the harness's uzi default (`medium`), `builtin`; a level → `explicit`, that level, `user_default`; `runtime` → `runtime_default`, no level, `user_default`; any other stored string (corrupt or future) → `explicit`, `medium`, `builtin`, never verbatim. `ResolveDefaultEffort` / `ResolveDefaultCodexEffort` become thin wrappers or are removed (coder's choice; no caller may keep the verbatim pass-through).
- `resolveEffortPtr` and `resolveHarnessEffortPtr` return nil exactly for `runtime_default`.
- **H/B handover (same text in H §3):** whichever of B and H lands second wires `EffortResolution.Source` into H's `resolveLeadSettings` `EffortSource` (H's claim `default_effort_source`) instead of "column non-blank". If H is on the base when B lands, B does it in M1 and adds the cases to H's `request_cases` in `fixtures/lead-config/contract.json`; otherwise H does it (cross-review items 10 and 21).
- `ResolveCrossCheck`: with no effort pin, the cell's `Effort` is the family preference's stored token after this mapping: a level, the harness default, or the literal `runtime`; `EffortSource` stays `worker default`. `assembleClaim`'s checker branch then passes `runtime` through `resolveHarnessEffortPtr`, which returns nil, so the child claim has no `default_effort`. The settings DTO's `ResolvedEffort: resolved.Effort` already yields `runtime`. A pinned effort is unchanged.
- Invariant: no claim ever carries the string `runtime`. Tested through the interface in `effort_test.go` (both harnesses × NULL, blank, five levels, `runtime`, corrupt) and the cross-check resolution tests.

### 4. Codex catalog probe (M2; `agent/src/codex/codex-harness.ts`, wired from `codex-executor.ts`)

Caller-facing interface: an opt-in `CodexHarness` option `catalogProbe?: { model: string; timeoutMs: number; onEntry: (entry: CodexCatalogEntry | undefined) => void }`, invoked once per harness instance after the root thread is started or resumed (after the quarantine assertion `startThread` already makes) and before the first `startTurnRpc`. It issues one `model/list` `{limit: 200, includeHidden: true}` on the root transport and awaits it up to `timeoutMs` (production default 2000 ms from an executor dep, `catalogProbeTimeoutMs`, modelled on `contextUsageTimeoutMs`). `CodexCatalogEntry = { defaultEffort?: string; supportedEfforts: readonly string[] }`.

- Bounds (the response is untrusted): at most 200 `data` entries scanned; match `model === requested || id === requested` with strings ≤ `MaxModelLen` (100) bytes; `supportedReasoningEfforts` at most 16 entries of ≤ 16-byte strings; `defaultReasoningEffort` ≤ 16 bytes. Anything malformed, absent, timed out or erroring → `onEntry(undefined)`. Never throws into the turn, never paginates, never logs the response.
- B supplies the probe only on the claim's first root epoch and only when the claim carries an explicit level. Because an unset preference resolves to explicit `medium`, that is almost every Codex claim; only Runtime default skips it. B consumes `supportedEfforts`; `defaultEffort` is parsed for child B2, which reuses this probe (adding a non-blocking call for Runtime default claims) rather than adding one.
- Latency: one local RPC before the first turn of nearly every Codex claim, bounded by the timeout. The cost is unmeasured; the PR's live check on a hosted worker records the measured `model/list` round trip (p50 and max over at least five claims) beside the 2000 ms bound.
- Test fakes: there is no shared Codex fake. Each test file has its own `FakeTransport` or responder: `agent/test/codex-harness.test.ts`, `agent/test/codex-executor.test.ts`, `agent/test/runner-harness.ts`, `agent/test/plan-revision-provider-fixture.ts`, `agent/test/draft-plan-script.ts`. Their default responders return `{}` for an unknown method, which the probe treats as malformed and resolves to `onEntry(undefined)` at once, so no test waits and none sees a note. Tests that record sent methods (for example `codex-executor.test.ts` `sent.push(request.method)`) will see the extra `model/list` and must be updated. Timeout tests inject `catalogProbeTimeoutMs: 10`.

### 5. Codex unsupported-level policy (M2; `codex-executor.ts`)

When the claim carries an explicit level L and `onEntry` delivered an entry whose `supportedEfforts` does not contain L, emit one worker status before the first root `turn/start`: `event: "effort_not_in_catalog"`, `text` as in acceptance example 3. The model is rendered through `sanitizeName` (`render.ts`, module-private today: export it or move it beside the note; no second sanitizer). Then send L unchanged. No note when the probe timed out, found no entry, or the run uses Runtime default. A provider rejection follows today's failure path; the executor never issues a second `turn/start` at a different level and never uses the catalog to pick one. A rejection of a level the catalog does list stays opaque (D6).

## Risks

- **Exhaustive reader/writer search** (re-run in one command): `git grep -n -E 'GetUserDefaultEffort|GetUserDefaultCodexEffort|ResolveDefaultEffort\(|ResolveDefaultCodexEffort\(|resolveEffortPtr\(|resolveHarnessEffortPtr\(' -- api ':!*_test.go'`, `git grep -n -P '\.Default(Codex)?Effort\b' -- 'api/**/*.go' ':!**/*_test.go' ':!api/internal/store/*.sql.go'`, `git grep -n -E 'default_(codex_)?effort' -- api/internal/store/queries web/src api/cmd/uzi`. At `587b66d74`: readers are claim assembly (incl. the cross-check checker branch), judge, chat, job, cross-check pins (workersvc and handler), settings GET; writer is settings PUT only; external surfaces are Run defaults, CrossCheckDefaults, the cross-check result views, the mock, CLI `settings get` and demo. The isolated lane inherits the assembled claim.
- **Rollout orders.** API first, workers old: a `runtime` preference produces claims without `default_effort`; every shipped worker path omits effort when the key is absent (baseline rows), and Codex claims still require `codex_runtime_v2`. Workers first, api old: old apis never send an out-of-set effort; the M2 warning is worker-local. No capability needed in either order.
- **Rollback (accepted, with an operator step).** The chart runs one api replica with `strategy: Recreate`, so there is no mixed-replica window. The real path is an app rollback below this PRD, which reads `runtime` verbatim and puts it on claims, and which also rolls `workers.image.tag` back, so old api and old workers co-occur after the drain. Then: Claude lanes pass `--effort runtime` to CLI 2.1.293 (outcome unverified; likely a launch-time argument error that fails the run); the Codex cross-check lane sends `effort: "runtime"` to `turn/start`, which 0.162.1 forwards verbatim to the provider (likely a provider rejection); other Codex lanes drop it in `render.ts`. Workers at or above M1 drop it in the claim guard. Mitigation, documented in `docs/worker-effort.md` "Rolling back": before rolling the api back below this PRD run `UPDATE users SET default_effort = NULL WHERE default_effort = 'runtime'; UPDATE users SET default_codex_effort = NULL WHERE default_codex_effort = 'runtime';` (those users then get `medium`).
- **Resumed sessions keep their level.** Codex 0.162.1 reapplies a thread's persisted `model_reasoning_effort` on `thread/resume`, and `turn/start.effort` persists for later turns. A run resumed onto a thread driven earlier at an explicit level keeps that level after the owner switches to Runtime default. Documented; child H shows the effective value. Children Q-claude and Q-codex own the related case "Runtime default implementation effort after an explicit planning effort" (cross-review item 11). - **Catalog drift.** The Codex catalog can refresh per account, so the warning can be wrong in either direction; it is advisory and never blocks.
- **Second implementations.** The mock projection is pinned to Go by `fixtures/effort-defaults/cases.json`. `CrossCheckDefaults`' client-side label is covered by its own test cases for NULL, a level and `runtime`.

## Decision Log

- **D1. Store Runtime default as the sentinel `runtime` in the existing columns.** Reason: the epic constraint (no storage reshape) and no migration; the columns have no CHECK. Rejected: boolean columns (a reshape, two fields that can disagree); NULL meaning runtime (NULL already means `medium`).
- **D2. Represent "send nothing" by omitting `default_effort`, with no new capability.** Reason: every shipped worker path omits effort when the key is absent, so both rollout orders work. Rejected: an explicit wire token (capability gate for no gain).
- **D3. Interpret the sentinel in one resolver that also returns mode and source, and treat an unknown stored value as the uzi default.** Reason: every lane funnels through `resolveEffortPtr` / `resolveHarnessEffortPtr` / `ResolveCrossCheck`; returning mode and source lets H report what was sent without re-deriving it; closing the verbatim pass-through removes the rollback bug class. `ResolveCrossCheck` carries the token through instead of blanking it, because the checker branch re-resolves its value (r1 blocker). Rejected: per-lane checks.
- **D4. One agent-side closed set and a claim-decode guard.** Reason: one place covers the Codex cross-check lane that bypasses `resolveEffort` and every Claude lane. Rejected: guards per runner (five sites).
- **D5. Codex catalog source is `model/list`, bounded, with an injected timeout, owned by B.** Reason: `supportedReasoningEfforts` exists only there; B2 reuses the same probe for `defaultReasoningEffort`, so there is one Codex probe. Traced at 092d3acd: the `thread/start` / `thread/resume` response `reasoningEffort` is the thread's configured or persisted effort (`config_snapshot.reasoning_effort` from `config.model_reasoning_effort`; resume reapplies the persisted value), not the catalog default and not a supported-level list. Rejected: using H's thread response (wrong semantics for both uses); a build-time catalog copy (ignores per-account refresh).
- **D6. User decision 2026-10-21: warn, do not block, when the Codex catalog lacks the chosen level.** Send the level unchanged, warn before the turn from the runtime's catalog, never retry or rewrite. Reason: 0.162.1 sends explicit levels verbatim and the provider decides; uzi cannot show the provider's message, so the catalog note is how the user learns the likely cause. Rejected: refuse before the turn (a lagging or account-filtered catalog would block runs the provider accepts); clamp or downgrade (forbidden by the epic); save-time validation (model and catalog unknown at save time). Deferred: a closed `unsupported_effort` tag beside `modelRejectionTag`'s `model_not_found`, because no captured provider envelope exists and ADR-1106 records that a `persistent` failure could not be told apart from an entitlement failure; a rejection of a listed level therefore stays opaque.
- **D7. Probe only explicit-level claims (almost every Codex claim, since unset is explicit `medium`), awaited before the first turn.** Reason: the note is useful mainly on the failure path, so it must precede the turn; Runtime default has nothing to warn about. The measured latency goes in the PR. Rejected: concurrent fire-and-forget (the note can arrive after an early terminal failure).
- **D8. Runtime default applies wherever the per-harness preference applies today** (issue runs and subagents, judge, chat, job, isolated, cross-check worker default). Reason: one meaning for one setting. Rejected: issue runs only (the judge and checker would silently keep `medium` while the setting says otherwise).
- **D9. Runtime default is not a cross-check pin value.** Reason: pins are hard explicit choices by spec; an unpinned cell already follows the family preference.
- **D10. Cross-check result views label NULL effort with source `worker default` as "runtime default"; the code DTO gains the existing source column.** Reason: the epic's "value in effect and its source are visible"; that combination cannot occur before this PRD, so no legacy row is mislabelled. Rejected: storing `runtime` in `checker_effort` (it records what was delivered, and nothing was).
- **D11. CLI is read-only and uses C's six-column table; B owns `EffortSettingCellDTO`.** Reason: `PUT /api/me/settings` is cookie-only (child O); coordinator ruling (round 3): one effort cell shape, C-style, owned by B and reused by B2 (optional `catalog_default`) and F; every CLI row uses C's table. Coordinator ruling (round 3, final): B is blocked by C and consumes C's fixture, label functions and renderer by name.
