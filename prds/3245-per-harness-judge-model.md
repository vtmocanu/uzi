## Problem

A user whose runs execute on Codex cannot choose the model their judge runs on, and nobody sees which model it uses:

- The judge inherits the harness of the run it judges. There is one per-user `judge_model` and one instance `judge_model`, both Claude-vocabulary in the UI. At claim, the resolved value (by default the instance `opus`) is dropped for a Codex judge with a visible `harness_model_fallback` note, so **every default-configured Codex judge emits a "stored model is not valid for the codex harness" note** on a setting the user never touched, and then runs on whatever the worker's provider default is.
- The review row records an empty judge model for those Codex judges (the agent copies the claim's empty `judge_model` into the review).
- The only way to steer a Codex judge today is to type a Codex id into the Claude-labelled field, which then breaks every Claude judge of that user (dropped with a note). `gpt-6-luna` typed there is not even dropped: it is sent to the Claude SDK and fails.
- An admin who once pinned an instance judge model cannot return to the built-in default: the admin API rejects a blank value, so "follow uzi's default, including future changes" is unreachable.
- `docs/judge.md` says a Codex judge falls back to `gpt-6-astra`; it falls back to `gpt-6.1-sol`.

## Outcome

Every judge model setting is a Claude/Codex pair at the user and the instance level. For a judge run on harness *h*, the model is resolved per lane, independently for Claude and Codex: **user value for *h* > instance value for *h* > built-in for *h***. The claim always carries a concrete model valid for *h*. Stored values invalid for their lane (legacy data) are skipped with the existing visible note and resolution continues to the next tier. An admin can reset either instance value to the built-in; instance values are stored trimmed, so a whitespace-only value is that reset. The value in effect and its source are visible in the web UI and in `uzi settings get`.

### Acceptance examples

1. **Default Codex judge.** A user with no judge settings, instance defaults untouched, finishes a Codex run with the judge on. The judge claim carries `judge_model = "gpt-6.1-sol"`; no `harness_model_fallback` message is written; the stored review's model is `gpt-6.1-sol`. (Today: `judge_model` absent, one fallback note, review model `""`.)
2. **Pinned per harness.** The user sets Claude judge model `haiku` and Codex judge model `gpt-6-astra` in Settings → Run defaults. A Claude run's judge claim carries `haiku`; a Codex run's carries `gpt-6-astra`; neither writes a fallback note. `uzi settings get` shows `judge  claude  Pin · haiku  opus  haiku  your choice` and `judge  codex  Pin · gpt-6-astra  gpt-6.1-sol  gpt-6-astra  your choice`. The same claims result with the admin's enforce-all switch on and the user's opt-in off.
3. **Instance reset.** The admin had pinned the instance Codex judge model to `gpt-6-sol`. In Admin → Instance → Run judge they choose "Default · gpt-6.1-sol (built-in)" and save. The admin GET reports `codex_judge_model = gpt-6.1-sol`, source `default`; the next Codex judge of a user without an own value carries `gpt-6.1-sol`. Submitting `"   "` through the API has the same effect. The same works for the Claude lane (`opus`).
4. **Legacy user value.** A user stored `gpt-6-astra` in `judge_model` before this change. After migration, their Codex lane holds `gpt-6-astra` (copied) and Codex judges use it with no note. Their Claude judges skip the stored Codex id with one fallback note and run on the instance Claude value (`opus`); the Claude row shows the stored value with "In effect: opus · instance default" beneath it until they change it (the PUT now refuses to re-save a Codex id there).
5. **Legacy instance value.** The instance `judge_model` held `"\tgpt-6-sol "` before this change. After migration the instance Codex key holds `gpt-6-sol` and the instance Claude key is unchanged. Every Codex judge without a user value runs on `gpt-6-sol` with no note (as today). Every Claude judge without a user value skips the stored Codex id with one note and runs on the built-in `opus` (today: the same note and an unnamed SDK default). The admin's Claude judge model select shows the stored value with the warning "Not a Claude model: Claude judges use the built-in opus. Choose Default to clear it." Choosing Default and saving stops the notes.
6. **Valid alias, no note.** A Claude judge whose effective value is the instance alias `sonnet` writes no fallback note.

### 2. Tiered resolver (`api/internal/agenttmpl`, pure, deep module)

- **Generic:** `ResolveTieredModel(accept func(string) bool, user, instance, builtin string) ModelResolution`. Walks `[user, instance, builtin]`, trimming each; the first non-blank value with `accept(value)` wins. `ModelResolution{Model, Source, DefaultModel, DefaultSource string; Dropped []string}`: `Source` ∈ {`user_default`, `instance_default`, `builtin`}; `DefaultModel` / `DefaultSource` are the same walk without the user tier (what "Default" means to this user), `DefaultSource` ∈ {`instance_default`, `builtin`}; `Dropped` lists each non-blank rejected candidate in tier order. These are the shared #1703 provenance tokens, `fixed_at = claim`.
- **Judge:** `ResolveJudgeModel(harness, user, instance string) ModelResolution`, with `accept` = Claude: not in `CodexRoleModels`; Codex: in `CuratedCodexModels`; builtin = `DefaultClaudeJudgeModel = "opus"` / `DefaultCodexJudgeModel = "gpt-6.1-sol"` (new constants here; `settings.Defaults` references them, avoiding the settings→agenttmpl import cycle). Unknown harness: Claude rules (the judge only ever has `claude` or `codex`).
- **Invariants:** `Model` is never empty when `builtin` is accepted (test-pinned for both harnesses); for Codex it is always curated, which keeps the judge exemption in ClaimRun's custom-Codex clause sound with no claim-SQL change.
- **Hides:** tier order, blank and whitespace handling, the per-harness vocabulary, built-ins, legacy fall-through. D's `ResolveSummaryModel` wraps the same generic with its own `accept` and builtin, so judge and summary share one signature, one package and one result type.
- **Callers:** `assembleJudgeClaim` (claim), `userSettingsResponse` (settings cells), `auth.go` `effective_judge_model` (session consent field, Claude lane). The web mock is a deliberate second implementation, pinned by `fixtures/model-settings/judge.json`.
- **Built-ins are not in `fixtures/codex-models/models.json`** (it holds sets only). The judge built-ins live in the sibling file `fixtures/model-settings/judge.json` (`{"builtins": {"claude": "opus", "codex": "gpt-6.1-sol"}, "cases": [...]}`, D's `fixtures/model-settings/summary.json` precedent). A Go test pins `DefaultClaudeJudgeModel`, `DefaultCodexJudgeModel` and `settings.Defaults` for both keys to `builtins`; the web test pins the mock's `defaults` to it.

### 3. Instance accessor and trim-at-storage (`api/internal/settings`)

- **One accessor, two forms:** `Cache.InstanceModels(ctx, keys []string) (map[string]string, error)` reads one cache snapshot and returns, for each requested key, the env-over-DB value; `Cache.InstanceModel(ctx, key string) (stored string, err error)` is its one-key form (same rules, same snapshot semantics). Values are for **non-secret** keys only, trimmed, `""` when unset; a secret key in the request returns an error and never a value. `InstanceModel` replaces `Cache.JudgeModel` (removed; the deadcode gate holds Go at zero). The built-in is `settings.Defaults[key]`. **Error posture (shared with D):** on an error the caller logs and treats the instance tier as unset (`""`), so resolution falls to the built-in; a claim never fails on it. `workersvc.SettingsReader` replaces `JudgeModel` with `InstanceModel`; D later removes `SummaryModel` the same way.
- **Keys:** new `KeyCodexJudgeModel = "codex_judge_model"`, `Defaults` → `agenttmpl.DefaultCodexJudgeModel` (no seeded row, `Known`, non-secret). `KeyJudgeModel` default → `agenttmpl.DefaultClaudeJudgeModel` (same value, `opus`).
- **Validate:** `KeyJudgeModel` gets its own case → `ValidateClaudeLaneModel` (so `""` and whitespace-only are accepted as the reset); `KeyCodexJudgeModel` → `""`/whitespace-only, or a `CuratedCodexModels` member after trim (distinct messages for a Claude alias and for "not a Codex judge model"). `KeySummaryModel` stays on `validateModelAlias` in its own case until D changes it; C neither changes nor asserts it.
- **Trim-at-storage (v4.1 §5):** `settings.NormalizeForStorage(key, value string) string` trims the instance model keys (judge here; D adds its keys to the same set) and is applied in `UpdateSettings` before validation, the merged precheck and `ValueForStorage`. A whitespace-only submission therefore stores exactly `""`, which `Cache.effective`/`Cache.source` read as the default with source `default`. Other keys keep verbatim storage (no repo-wide change). Bounds: `MaxModelLen` (100 bytes) after trim.
- **Reset semantics:** the empty row is written by the existing admin PUT (audited `updated_by`); no new route, no delete query.

## Decision Log

- **User decision 2026-10-21: the Codex built-in judge model is `gpt-6.1-sol`** (D1). Kept as a separate constant (`DefaultCodexJudgeModel`), not an alias of the worker default. Reason: it is what every default Codex judge runs on today, so the upgrade changes no one's model or spend, including under enforced mode; a future worker-default change does not move judges implicitly. Rejected: `gpt-6-astra` (the mock's value; about five times the per-token price in `agent/src/codex/codex-pricing.json`), `gpt-6-sol` (task review's model; a different job).
- **User decision 2026-10-21: a Codex id is rejected in the Claude judge lane, and an empty instance value resets to the built-in.** Implemented by `ValidateClaudeLaneModel` (the five `role` ids, so `gpt-6-luna` too, buddy C1) at user and instance level, and by trim-at-storage plus an accepted `""` (D6).
- **D2. Codex judge lanes accept curated ids only,** at user and instance level. Reason: a custom Codex judge model would need the advice renderer to pass non-curated ids and ClaimRun's custom-Codex clause, its SQL mirrors and the hosted lease arms to stop exempting judges and to read the instance key from `app_settings` in SQL; large claim-path change, no stated need. `gpt-6-luna` is excluded for the reason in module 1. Rejected: custom ids with that gate; the `role` set. The Claude lane keeps today's custom-id acceptance.
- **D3. One generic tiered resolver in `agenttmpl`, shared by judge and summary; the mock is a fixture-pinned mirror.** Reason: today the judge resolution exists three times and already disagrees on harness handling, and D needs the same walk. `agenttmpl` because the vocabulary sets live there and `settings` already imports it (the reverse import would cycle); built-ins are `agenttmpl` constants referenced by `settings.Defaults`. Rejected: a judge-only resolver in `workersvc` (r1; two packages and shapes with D), a web-side resolver.
- **D4. The migration copies, never moves, at both levels.** Curated Codex ids in `users.judge_model` and in the instance `judge_model` are copied (trimmed) into the Codex lane; the Claude lanes keep them, where they keep producing the existing visible note until the user or admin chooses Default. Reason: an image-only rollback then reads exactly the pre-upgrade instance value, so old-binary Codex judges keep their model (a move would make them drop `opus` with a note on every claim); no data is rewritten.
