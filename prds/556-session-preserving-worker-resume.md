# PRD #556 — Session-preserving worker-shutdown resume

- **Issue**: [#556](https://github.com/vtmocanu/uzi/issues/556)
- **Priority**: Medium (run-continuity / cost; no data loss, no guardrail impact)
- **Status**: M1–M5 landed on `agent/issue-556`; M6 (live dev-cluster validation) deferred — needs a hosted k8s worker not available to the implementing run

## Problem

When a worker container is restarted **outside uzi's controlled release path**, an in-flight run is interrupted and re-planned rather than resumed. Committed git work survives; the agent's SDK conversation does not.

### What was observed (2026-08-22, run #534)

A hosted docker-lane worker running a mid-implementation **gated** PRD run received a `SIGTERM` and its container restarted **in place** (same pod, same ReplicaSet, Deployment revision unchanged, exit 0, no kubelet `Killing` event, node healthy, co-located worker unaffected). This was during a control-plane release but was **not** a controlled worker roll — the trigger was a direct signal to the one container, external to uzi (most consistent with a kubelet in-place restart / node-level action). The worker handled it correctly: it fetched the agent's commits back to the tracking ref and left the run for requeue. Within its affinity grace the **same** worker re-claimed the run, but it could not find the SDK session, emitted `resume_lineage_break`, and **re-planned from scratch — re-hitting the human approval gate**. Milestones M1–M3 were already committed, so no code was lost; the cost was a re-plan, a second approval gate, and repeated planning spend.

### Why it happens (mechanism, verified against the tree)

- **Git durability already works.** Both the park path and the shutdown-interrupt path fetch the agent's committed branch back into the worker's bare repo at `refs/uzi-runner/<branch>` (`agent/src/runner.ts` ~:1800), and an owned resume reseeds off that tracking ref (PRD #218 M1/M2). This is why the commits survived.
- **The SDK session transcript does NOT survive a shutdown.** The runner's `finally` block has a "park carve-out" (PRD #35 Decision 6a, PRD #218 M6, comment `runner.ts` ~:1874-1900): **exactly two** filesystem removals are skipped **only for a parked run** — the skills plugin dir (`runner.ts` ~:1925, `if (worktreePath && !parked)`) and the per-run SDK HOME (`runner.ts` ~:1945, `if (runHome && !parked)`, which holds the resumable transcript). The shutdown-interrupt branch (`active?.shuttingDown`, `runner.ts` ~:1790-1806) does the git fetch-back but **does not set `parked`** (`parked` is declared at ~:531 and assigned only at ~:1767 on the limit-park path), so the `finally` deletes both dirs.
- **So the same-worker resume cannot resume.** The transcript lives on the durable `/data` PVC and is meant to survive a container restart (`agent/src/sdk-env.ts` ~:19-20; `agent/src/main.ts` ~:89 `sdkHomeRoot = <dataDir>/agent-home`, ~:115 `runHome = <sdkHomeRoot>/<runId>`). The session id is checkpointed server-side during the run and re-delivered as `claim.session_id` on the next claim (`runner.ts` ~:650, ~:868), so the transcript file is the ONLY missing piece. But because the shutdown path already deleted `agent-home/<runId>`, the re-claim's `sessionTranscriptResolvable(runHome, sessionId, …)` (`agent/src/sdk-session.ts` ~:123-134) returns false, the run drops the resume and starts a fresh SDK session (`RESUME_LINEAGE_BREAK_EVENT`, `runner.ts` ~:661/:675).
- **Surge protection does not and cannot cover this.** PRD #422 / ADR-0422 only guards the **controller's own Deployment rolls** (cordon-then-defer a busy worker). ADR-0422 explicitly scopes out "a node drain, OOM, or eviction outside a controlled release" (`adr/0422-decouple-worker-version.md` ~:54) — exactly this class. This PRD does not touch surge protection; it makes the **resume** survive the interruption regardless of what caused it.

### Scope of the fix

The affinity grace re-lands a requeued run on its **original** worker during a grace window (claims are `FOR UPDATE SKIP LOCKED` with an affinity grace for resumes). That worker's PVC still holds `agent-home/<runId>` — *if the shutdown path had not deleted it*. So preserving the HOME across a shutdown interrupt makes the **same-worker resume** (the common case) continue the agent session instead of re-planning. Making **any** worker able to resume (cross-worker session durability) needs the transcript to be durable across PVCs (shared storage or api-side persistence) and is a larger, separate effort — **explicitly out of scope here** (see Out of scope). On k8s each worker's data volume is a per-worker `ReadWriteOnce` PVC (`controller/internal/kube/render.go` ~:658), so a cross-worker resume lands on a different PVC that never held the HOME — the fetch-back keeps its committed work safe and the existing lineage-break re-plan path (unchanged) handles it.

## Solution

Preserve the per-run SDK session HOME and the skills plugin dir across a **worker-shutdown interrupt** — the same two filesystem carve-outs a park already makes — so a same-worker re-claim within the affinity grace resumes the SDK session. Scope the carve-out to **exactly those two filesystem removals** (`runner.ts` ~:1925 and ~:1945), never to the secret eviction (`runner.ts` ~:1873, unconditional, structurally upstream of the carve-out), the steering-poller stop (~:1844), or the gate-map deletes — the `finally`'s own warning block (`runner.ts` ~:1902-1914) records that widening `!parked` over those regresses silently (the secret eviction fails with no red test; `steering.stop()` fails as a process hang that `node --test` reports as `fail 0`).

Reclaiming a preserved HOME whose run does not resume on this worker is **already handled by the existing garbage collector** (`agent/src/home-reclaim.ts`, `reclaimStrandedRunHomes`, PRD #108 M6, wired at `main.ts` ~:244, on by default) — this PRD verifies and tests that coverage rather than adding a new sweep (see M3).

### Design decisions

- **D1 — A distinct `preserveSession` discriminator, declared at function scope, scoped to the two fs removals only.** Introduce a flag (declared at function scope like `parked` at `runner.ts` ~:531, so it is visible in the `finally`) set true on the `active?.shuttingDown` branch that, in the `finally`, skips the HOME + plugin-dir removals exactly as `parked` does. It must NOT gate the secret eviction, `steering.stop()`, or the gate-map deletes — those are structurally upstream of the carve-out and must still run on shutdown. Prefer a new named flag over overloading `parked`, because `parked` also drives park-only behavior (report semantics, resume seeding, the park log at ~:1950); the two concepts share only the fs-carve-out.
- **D2 — Security parity with a park.** A preserved HOME keeps the SDK transcript on the PVC (tool outputs can contain secrets). A **park** already accepts exactly this for its whole park window (verified: `runner.ts` ~:1945 skips the HOME removal on a park), so a shutdown-preserved HOME is at-rest-identical, not a new class of exposure. The run-scoped secrets are still evicted from the logger on shutdown (`runner.ts` ~:1873, unconditional — verified). State this parity explicitly so a reviewer does not read the change as introducing at-rest secret exposure.
- **D3 — Preservation is same-worker-conditional in effect, unconditional on disk.** The worker cannot know at shutdown whether the resume will land on itself or another worker, so it preserves unconditionally and relies on the existing GC (D4) to reclaim the HOME when the run turns out not to resume here. The resume-side already degrades correctly: if the HOME is absent (cross-worker, or already reaped), `sessionTranscriptResolvable` is false and the existing `resume_lineage_break` re-plan path runs — unchanged.
- **D4 — Reclamation reuses the existing terminal-status GC; no new reap criteria.** `reclaimStrandedRunHomes` (`home-reclaim.ts`) already sweeps every `agent-home/<runId>` and reaps those whose run the api reports **terminal** (`completed`/`failed`/`cancelled`, ~:84-88). It is **provenance-agnostic**, so once M1 lands it covers shutdown-preserved HOMEs by construction, exactly as it already covers park-preserved ones. It **deliberately never reaps a non-terminal run** — including a run `running` on another worker, and any run whose status it cannot read (404 / api-down are skipped, ~:293-302) — because on a shared-volume topology a sibling worker could otherwise delete a HOME an SDK is actively using (PRD #108 Risk 5, `home-reclaim.ts` ~:14-54). **This PRD keeps that invariant and adds no eager or time-based reaping.** In particular it does **not** add a "reap because owned by another worker" criterion (that reaps a non-terminal run — safe only under k8s per-worker PVCs, catastrophic under the shared-volume compose lane the GC models as live) and does **not** add a TTL-delete (the GC has no delete-on-unknown-status by design; a limit park can legitimately live up to 8 days). The residual cross-worker orphan (worker A's HOME after the run resumed on worker B) is reaped when worker A next boots and the run has gone terminal — a **bounded, pre-existing leak identical to what a park already has today**, not something this PRD introduces or must fix.
- **D5 — Emit a positive resume signal.** A successful same-worker session resume after a restart should be observable in the run feed (a new event alongside `RESUME_LINEAGE_BREAK_EVENT` at `runner.ts` ~:661/:675), so operators can tell "resumed cleanly" from "re-planned" and measure how often each happens. Purely additive.

## Success criteria

1. A mid-implementation run interrupted by a worker-container SIGTERM and re-claimed by the **same** worker within the affinity grace **resumes its SDK session** (the D5 event fires; no `resume_lineage_break`, no re-plan, no second approval gate for a gated run). Falsifiable: on `main` today this run re-plans (the shutdown path deletes the HOME → transcript unresolvable → fresh session).
2. On a shutdown interrupt, the run-scoped secrets are still evicted from the logger, the steering poller is stopped, and the gate maps are cleared — proven by tests that go red if the new carve-out swallows any of them.
3. A shutdown-preserved HOME is reaped by the existing GC once its run is terminal and never while non-terminal — proven by a test against `reclaimStrandedRunHomes`. No new sweep, no eager/TTL reaping. (A same-worker resume that runs to completion cleans up its HOME normally on the terminal path; the only residual is the bounded, pre-existing cross-worker orphan identical to a park.)
4. The committed-work durability (fetch-back to `refs/uzi-runner/<branch>`) is unchanged and still covers the cross-worker case where the session cannot be resumed.
5. `task gate:agent` (and `gate:api`/`gate:controller` if touched) green.
6. The live dev-cluster validation (M6) shows a real interrupted run resuming its session, with the run id and markers recorded.

## Risks & mitigations

- **R1 — Silently disabling a required cleanup by widening the carve-out too far.** The `finally`'s own warning (`runner.ts` ~:1902-1914): the secret eviction regresses with no red test, `steering.stop()` regresses as a process hang that the `node --test` tally reports as `fail 0`. **Mitigation:** the two carved removals (~:1925, ~:1945) are the ONLY statements guarded by `!parked`; the secret eviction (~:1873) and `steering.stop()` (~:1844) are structurally upstream, so a flag appearing only at those two lines cannot reach them. M4 adds explicit red-on-regression tests on top; read the exit code, not the tally.
- **R2 — At-rest secret exposure via a preserved transcript.** **Mitigation:** D2 — identical to what a park already does; the logger secret eviction is unchanged. No new exposure class.
- **R3 — HOME accumulation / ephemeral-storage pressure** (issue #225 is a worker-eviction cause). **Mitigation:** the existing terminal-status GC (D4) already reaps preserved HOMEs of any provenance; a same-worker resume-to-completion cleans up normally. The only residual is the bounded cross-worker orphan reaped at the original worker's next boot — identical to today's park behavior, not new. **Self-correlation note:** the same container restart that interrupts the run also triggers `reclaimStrandedRunHomes` at the next boot, so the accumulation window is naturally checkpointed at each restart (the requeued run reads non-terminal and is correctly skipped, so the resume is not broken).
- **R4 — GC deleting a HOME a live resume still needs.** **Mitigation:** by NOT changing the GC's invariant — it reaps only runs the api positively reports terminal, and skips every non-terminal or unknown status (`home-reclaim.ts` ~:84-88, ~:293-302). The rejected "owned-by-another-worker" and "TTL-delete" ideas would have violated exactly this and are explicitly out (D4).
- **R5 — Cross-worker interruptions still re-plan.** Accepted and out of scope (see below); the fetch-back keeps committed work safe, and the lineage-break path is unchanged for that case. On k8s the resuming worker has a different PVC that never held the transcript, so cross-worker resume is genuinely a different-storage problem.

## Dependencies

- Builds directly on PRD #218 (tracking-ref durability), the PRD #35 D6a park carve-out, and PRD #108 M6 (`home-reclaim.ts`) — this PRD extends the same `finally` block, reuses the `agent-home/<runId>` HOME and `sessionTranscriptResolvable` preflight, and reuses the existing GC rather than adding one.
- No new migration, no forge/GraphQL change, no web change. The terminal-status GC needs no api change (`getChatRun().status` already exists and is already used by `home-reclaim.ts`). *(Note: the rejected "owned-elsewhere" reap would have required a new api field — `WorkerRunDetail` carries `status` but no `worker_id` — which is one more reason it is out of scope.)*
- Primarily `agent/` (runner carve-out + the D5 event + a `home-reclaim` test).

## Out of scope

- **Cross-worker session durability** (uploading/sharing the SDK transcript so ANY worker resumes an interrupted run): larger, needs shared storage or api-side transcript persistence; a separate PRD. This one targets the same-worker resume within the affinity grace.
- **A new or periodic HOME garbage collector, eager owned-elsewhere reaping, or TTL-delete**: the existing startup terminal-status GC is sufficient and safe; changing it is explicitly rejected (D4). Making the sweep periodic is a possible separate enhancement, not part of this PRD.
- **Changing surge protection or the release path** (PRD #422 / ADR-0422): the interruption source is external; this PRD hardens the resume, not the trigger.
- **Preventing the in-place container restart itself** (identifying/eliminating the SIGTERM source): an infra/ops question for the cluster, not a uzi code change.
