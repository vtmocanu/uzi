## Problem

uzi's board is a label-driven kanban: **columns ARE forge labels** (GitLab issue-board model), built entirely by uzi from labels — no forge's native board API is used. Moving a card swaps the issue's column label via `UpdateIssueLabels` (forge-first), and the run-lifecycle automation moves those same labels as a run progresses (`In Progress`, `Human Review`).

A user who has connected a GitHub repo can already use uzi's own board. But they cannot see or drive an equivalent board **inside GitHub's native UI** that stays in step with uzi, because:

- **GitHub Projects v2 cannot make columns out of labels.** A Projects v2 board's **column** field must be a single-select or iteration field — in practice the built-in **"Status"** field — never labels. (Group-by/swimlanes have expanded over time and are not load-bearing here; the column-axis constraint is the point.) So a native GitHub board is a *different* field (`Status`) than uzi's source of truth (labels).
- **GitHub fires no repo-level Action when a card is dragged.** Projects v2 item events (`projects_v2_item`) are delivered only as *organization* webhooks and are absent from the GitHub Actions trigger list, so there is no repo workflow that reacts to a board drag. (See Resolved External Facts, F5.)

The result: uzi's label board and a hand-made GitHub Project board drift independently. The user wants them kept in sync both ways — drag in uzi and it shows in GitHub, drag in GitHub and it shows in uzi.

## Solution overview

A **GitHub-only, in-uzi** bidirectional projection between a repo's board **column labels** and a linked GitHub **Projects v2 "Status"** single-select field. The label stays canonical; Status is a projection.

- **Forward (label → Status), "F1"**: project a Status write from the **two uzi-originated column-move call sites** — the manual drag (`handler.MoveIssue`) and the run-lifecycle automation (`runlifecycle.apply`) — **not** from inside `forgesvc.Service.AutoMove` itself. Both call sites already hold the full `store.Queries` and the repo row, and hooking them (rather than the shared `AutoMove`) is what **structurally breaks the forward↔reverse recursion** (D6): the reverse poller also calls `AutoMove`, so a hook *inside* `AutoMove` would re-fire on every reverse writeback. After the label write succeeds, if the forge is GitHub and sync is enabled, set the linked item's Status to the target column's option **and update `last_status_option_id`** so the next poll does not see a self-inflicted change. Best-effort and non-fatal (like CI-badge enrichment): a Status-sync failure must never fail the drag or the run-lifecycle move.
- **Reverse (Status → label), "R2"**: extend the poller (`api/internal/poller/poller.go`) with a **per-tick sibling step** (alongside `SyncMRStates` / `SyncPipelines`, run every tick regardless of the FullSync-vs-IncrementalSync choice) that, for GitHub synced repos, reads the linked project's item Statuses via GraphQL, diffs each against `last_status_option_id`, and for any changed item writes the matching column label through the ordinary `AutoMove` path. uzi's normal issue reconciliation then moves its own board. This is the only viable reverse mechanism because uzi is outbound-only (no inbound webhook server, confirmed: no inbound webhook handler exists in `api/internal/handler/`) and GitHub exposes no repo-Action trigger for board drags.
- **Only column labels sync.** The board's column labels (`Planned`, `In Progress`, `Human Review`, `Later`, plus the implicit `Open`/Backlog and `Closed`) map 1:1 to Status options. Non-column labels (`PRD`, `autopilot`, `bug`, `PRDLESS`, …) stay plain labels and are ignored by the sync. A single-select Status holds exactly one value, which matches a card sitting in exactly one column.
- **No ping-pong.** Every write on both sides is guarded by an idempotent no-op check that compares against the **live** value (only write if it differs). Note `AutoMove` does **not** itself short-circuit a no-op label change — it always re-upserts the cache — so the idempotency must live entirely in the new Status setter and the reverse label-writeback, not be assumed from the host function. Convergence is proven by SC-2's test, not by inspection: because both directions pass through `AutoMove`, the recursion is structural and the live-value no-op guard is load-bearing.
- **No GitHub Actions and no new Go dependency.** All Projects v2 calls are raw GraphQL `POST`s to `/graphql` using the existing connection token; go-github (`github.com/google/go-github/v90`) is REST-only and stays the driver's transport for everything else.

## Resolved external facts (GitHub Projects v2)

These are settled here so the offline worker needs no internet. Sources are GitHub docs/changelog, verified 2026-08-18.

- **F1 — Projects v2 is GraphQL-only.** There is no REST API for Projects v2 (REST `/projects` was classic-only and classic was sunset 2024-08-23). Key objects: `ProjectV2`, `ProjectV2Item`, `ProjectV2SingleSelectField` (has `options { id name }`). Key mutations: `addProjectV2ItemById`, `updateProjectV2ItemFieldValue`, `createProjectV2`, `linkProjectV2ToRepository`. Docs: https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects
- **F2 — Set an item's Status.** `updateProjectV2ItemFieldValue(input: { projectId, itemId, fieldId, value: { singleSelectOptionId: "<OPTION_ID>" } })`. You must first resolve, as node IDs: the **project** id (`user(login:).projectV2(number:){id}`), the **Status field** id and its **option** ids (`ProjectV2SingleSelectField.options{ id name }`), and the **item** id.
- **F3 — Item id for an issue.** `addProjectV2ItemById(input: { projectId, contentId })` idempotently adds the issue (contentId = the issue's node id) and returns `item { id }`; an already-present issue returns its existing item id. Existing items can also be paginated via `ProjectV2.items` and matched by `content` → issue number.
- **F4 — Token.** The Actions default `GITHUB_TOKEN` is repo-scoped and **cannot** touch Projects v2. A **classic PAT with `project` scope** (read+write; `read:project` is read-only) is required. uzi already requires a classic PAT (fine-grained PATs are rejected at `api/internal/forge/github.go:170`), so the only change is that the stored PAT must carry the `project` scope. A classic PAT's scopes can be edited in place on github.com without changing the token value, so uzi's sealed copy keeps working.
- **F5 — No reverse trigger.** No `projects_v2*` event exists as a GitHub Actions trigger; the events are delivered only as *organization* webhooks or to *GitHub Apps* (not repo webhooks). There is therefore no repo-native way to react to a board drag. F5 is the *secondary* justification for polling; the *primary* one is that uzi is outbound-only with no inbound webhook server, so even an org webhook/App has nowhere to deliver. Docs: https://docs.github.com/en/actions/reference/events-that-trigger-workflows and https://docs.github.com/en/webhooks/webhook-events-and-payloads
- **F6 — Forward-trigger alternative rejected.** A repo Action on `on: issues [labeled, unlabeled]` could set Status, but it (a) needs a project-scoped PAT stored as a repo secret, (b) is GitHub-Actions-only, and (c) duplicates a move uzi already performs. The user explicitly does not want Actions; F1 in `AutoMove` covers the same ground centrally.
- **F7 — Rate limits.** GraphQL budget for a PAT is 5,000 points/hour and 2,000 points/minute; a paginated project+items+field-value query costs on the order of tens of points, so a per-poll-cycle read of one project is comfortably within budget. Paginate items in pages of ≤100. Docs: https://docs.github.com/en/graphql/overview/rate-limits-and-node-limits-for-the-graphql-api
- **F8 — Create + link a project via API.** `createProjectV2(input: { ownerId: ID!, title: String!, repositoryId: ID })` creates a project; `ownerId` is the User or Organization node id (`query { user(login:"…"){ id } }`, or `viewer { id }` for the authenticated user). `linkProjectV2ToRepository(input: { projectId, repositoryId })` (and `unlinkProjectV2FromRepository`) associate it with a repo for discoverability under the repo's Projects tab; linking is not required for the board's fields/items to work. Creating a user project needs only the classic PAT `project` scope; linking a repo additionally needs repo access. Docs: https://docs.github.com/en/graphql/reference/mutations and .../input-objects
- **F9 — Single-select field + options ARE fully API-manageable (decisive for autonomy).** `createProjectV2Field(input: { projectId, dataType: SINGLE_SELECT, name, singleSelectOptions: [{ name, color, description }] })` creates a field with its full option list in one call. `updateProjectV2Field(input: { fieldId, singleSelectOptions: [...] })` adds/renames/recolors/removes options on an **existing** field (incl. the built-in "Status"). This shipped GA on 2024-12-12; the identity-preserving option `id` input shipped 2026-04-23 (no preview header). **Load-bearing rules baked in:**
  - `singleSelectOptions` is a **full-list REPLACE**, not a patch. To keep options (and every item's value on them), first **query the field's current options and echo each kept option back WITH its existing `id`**; add an option by including it without an `id`; remove one by omitting it — **omitting/recreating an option CLEARS that value on every item using it.**
  - An **empty** `singleSelectOptions` list appears to be a **silent no-op** (ignored) — *PLAUSIBLE but not confirmed against a primary source*; the design never intentionally sends an empty list, so a wrong reading is low-consequence. Named live-check before relying on it: send `updateProjectV2Field(singleSelectOptions: [])` against a throwaway field and confirm options are retained.
  - `color` is a required enum, one of `BLUE, GRAY, GREEN, ORANGE, PINK, PURPLE, RED, YELLOW` (GitHub's documented 8-color single-select palette — *exact enum spelling PLAUSIBLE, not pinned to the schema page*; a wrong value is a runtime mutation error, non-fatal, not data loss); `description` is required (`String!`, pass `""` if none).
  - A freshly created project ships with a built-in "Status" field (Todo/In Progress/Done) that **cannot be deleted**. Recommendation: **create uzi's own single-select field** via `createProjectV2Field` for full control over names/ids, rather than blind-overwriting the built-in Status (which would need read-then-echo of its ids to avoid clearing values). Docs: https://docs.github.com/en/graphql/reference/input-objects ; changelog https://github.blog/changelog/2024-12-12-github-issues-projects-close-issue-as-a-duplicate-rest-api-for-sub-issues-and-more/

## Architecture and integration seams

Exact pointers so the implementer does not have to rediscover them (SHAs omitted deliberately — re-derive line numbers at implementation time; the symbols are stable anchors):

- **Neutral forge interface** (`api/internal/forge/forge.go`): label/issue methods only, no board concept. **Do not add Projects v2 methods here** — GitLab and Forgejo have no equivalent. Instead define a small **optional capability interface** (e.g. `ProjectBoardSyncer`) implemented **only** by the github driver, and type-assert `forge.Forge` to it at the call sites. GitLab/Forgejo forges fail the assertion and the sync is skipped for them.
- **GitHub driver** (`api/internal/forge/github.go`): built on `go-github/v90`, REST, single long-lived client, resolves project id → owner/repo slug. Add the Projects v2 GraphQL calls here as raw `POST …/graphql`. **Transport preconditions (load-bearing for offline tests):** use the driver's *authenticated* client (`g.client.Client()` or a hand-set `Authorization` header / `g.token`) — the struct's `logClient` (~:47) is deliberately no-auth and redirect-refusing and must NOT be reused; and **derive the GraphQL endpoint from `g.client.BaseURL()`** (the struct stores no base URL; the httptest harness reaches the driver via `WithEnterpriseURLs`, which appends `/api/v3`), never a hardcoded `api.github.com/graphql`, or the httptest mux cannot intercept the calls. New unit tests follow the existing `github_test.go` httptest pattern and must mount the GraphQL route on the mock mux (no live network).
- **Forward seam — hook the two uzi-move CALL SITES, not `AutoMove` itself** (D6):
  - manual drag: `api/internal/handler/board.go` `MoveIssue` (~:755) → after `h.svc.AutoMove`
  - run automation: `api/internal/runlifecycle/lifecycle.go` `apply` (~:270, `AutoMove` call ~:333) → after the move
  These two sites hold the full `store.Queries` + repo row (so no need to thread new dependencies into `forgesvc.Service`, whose `q IssueStore`/`labels LabelConfig` are narrow), and — critically — they are the *uzi-originated* moves. The poller's reverse writeback also calls `AutoMove` but is not one of these sites, so hooking the sites (not the shared function) is what stops a reverse write from re-projecting to Status. (Alternative considered and rejected: hook `AutoMove` with a `suppressProjection` flag on the reverse call — more plumbing, same effect.)
- **Reverse seam** (`api/internal/poller/poller.go`): the ticker loop is `Run` (~:204) → `tick` (~:242) → `syncRepo` (~:293), which already chains optional post-sync siblings (`SyncMRStates` ~:327, `SyncPipelines` ~:361, `autopilot.detect`, `ciAutoFix.detect`). Add the reverse-sync step there as a **genuine per-tick sibling that runs every tick** (not a rider on `FullSync`, which only runs when `reconcileDue`). Note the real concurrency concern is **not** tick overlap (ticks never overlap; `tick` does `wg.Wait()`), but that the **forward path runs in the HTTP handler and can execute concurrently with a poller tick's reverse read of the same project** — the live-value no-op guard must tolerate that interleaving.
- **Column model** (`api/internal/board/board.go`): `ColumnInProgress`, `ColumnHumanReview`; default seeded columns in `api/internal/forgesvc/service.go` `DefaultColumns` (`Planned`, `In Progress`, `Human Review`, `Later`). `ResolveColumn` / `PlanLabelMove` are the pure helpers.
- **Settings** (`api/internal/settings/settings.go`): feature-flag pattern to mirror is `KeyJudgeEnabled` / `DefaultJudgeEnabled` (off by default). Add a `github_project_sync_enabled` key, default `"false"`, so the feature is a strict no-op until an admin turns it on.
- **Persistence** (`api/internal/store/migrations/`, current head `00130`): new migration(s), drafted high and **renumbered to the next free number above the live head at merge** (goose is strict, no allow-missing). See Data model below.

## Data model (new)

Draft migration `00131_github_project_sync.sql` (renumber at merge). Two concerns: the per-repo project linkage, and the per-issue item id + last-synced Status for the poller diff.

- **`github_project_links`** (one row per synced repo): `repo_id` (FK, unique), `project_node_id` (text, `PVT_…`), `project_number` (int), `status_field_id` (text, `PVTSSF_…`), `status_options` (jsonb: map of column-name → option-id), `owned_by_uzi` (bool — did uzi create this project, vs. adopt a user's — governs teardown, D8), `last_synced_at`, `last_error` (text null — observability; a best-effort sync that fails must be *visible*, not silent), `created_at`, `updated_at`. The **presence of this row is the per-repo "enabled" state** — the `github_project_sync_enabled` setting is only the instance-wide kill-switch; per-repo enable/link/adopt is this row plus its node ids.
- **Per-issue projection state**: side table `github_project_items` (`repo_id`, `forge_issue_iid`, `item_node_id` (`PVTI_…`), `last_status_option_id` text null, `last_synced_at`). A side table (not an `issues` column) keeps GitHub-only state off the shared `issues` row and out of the neutral cache. `last_status_option_id` is the poller's diff basis; **it is written by BOTH the forward hook (when it sets Status) and the reverse step (after it writes a label)** — if the forward path skipped it, every uzi-driven Status change would register as a false GitHub-side change on the next poll (converges via the no-op, but churns). See D7.

## GitHub Project setup (how a project must be created)

**Design intent: fully autonomous provisioning, confirmed achievable end to end via the API (F8, F9).** uzi creates and configures the GitHub Project with zero manual clicks — the user enables sync and a working, seeded board appears. Manual UI steps are a *fallback only* for the case where the user wants to reuse a project they already built by hand.

**Autonomous provisioning flow (primary path), on enabling sync for a repo:**

1. Resolve the connection owner's node id (`viewer { id }`, or `user(login:){ id }` / `organization(login:){ id }` per D3).
2. `createProjectV2(ownerId, title)` a project (or discover the repo's already-linked one), and `linkProjectV2ToRepository` so it appears under the repo's Projects tab.
3. **`createProjectV2Field(dataType: SINGLE_SELECT, name: "uzi Status", singleSelectOptions: […])`** — create uzi's OWN Status single-select whose options are the repo's board column names, each with a color and a (possibly empty) description. Creating our own field (rather than overwriting the undeletable built-in "Status") avoids read-then-echo of the built-in's option ids and keeps full control of names/ids. Persist the field id and the column-name → option-id map.
4. `addProjectV2ItemById` each current issue (idempotent; returns the item id, persisted), then `updateProjectV2ItemFieldValue` to seed each item's Status from its current column label.

**Ongoing option maintenance (D5):** if a board column is added/renamed/removed later, updating options uses `updateProjectV2Field`, which is a **full-list replace** — uzi must read the field's current options and echo kept options back **with their existing `id`s** (adding new ones without an id, dropping removed ones), or item Status values on changed options are cleared; an empty list is a silent no-op (F9).

**Manual setup (fallback / pre-existing project):** the github.com UI steps — New project → Board layout → set the Status field options to the uzi columns (`Planned`/`In Progress`/`Human Review`/`Later`, plus how Open/Closed map per D1/D2) → link to the repo → optionally an "auto-add by `label:PRD`" workflow — plus how the user tells uzi which existing project number to adopt (uzi then reads its field/option ids instead of creating its own field).

The status-option set mirrors the repo's board columns. The implicit `Closed` column maps from issue state (a closed issue), not a drag; whether a dedicated "Done/Closed" Status option is included is a Decision-log item below.

## Success criteria

**Offline-verifiable (the sweep worker closes these with unit/httptest, no live network):**

1. **SC-2 — Convergence.** A round trip converges: a uzi move → Status write → next poll produces **no forge label call** (a no-op writeback), never oscillation. Proven by the M8 test.
2. **SC-3 — Scope of sync.** Only column labels participate; non-column labels are never touched, and Status is never set to a value outside the repo's board columns. Proven by mapping + guard tests.
3. **SC-4 — Forge isolation.** GitLab and Forgejo repos are unaffected: the `ProjectBoardSyncer` assertion fails → sync skipped; the neutral `Forge` interface gains no Projects method. Proven by a grep-guard + skip test.
4. **SC-5 — No-op-until-enabled + scope failure.** The feature is a strict no-op until an admin enables it; a stored PAT lacking `project` scope produces a clear, non-fatal error (via the `X-OAuth-Scopes` introspection already in `parseGitHubScopes`), not a silent or fatal failure. Proven by a httptest returning a scope header without `project`.
5. **SC-6 — Hygiene.** No new Go dependency (`go.mod` diff clean); `task gate:api` (incl. `-race`, deadcode, lint ratchet) green.

**Live-acceptance (require a real GitHub Project + a `project`-scoped PAT; a human/e2e step, NOT offline-closable):**

- **SC-A1 — Round trip.** With sync enabled on a real GitHub repo, moving a card in uzi sets the corresponding Status on the linked Project (**one `updateProjectV2ItemFieldValue` call for an already-added item; two if the item must be added first** — see M7 backfill), and dragging a card in the GitHub board sets the corresponding column label within one poll cycle, uzi's board reflecting it on the next reconcile.
- **SC-A2 — Provisioning (only if M4 shipped).** Enabling sync autonomously produces a working, seeded board with the correct Status options and every current issue placed, no manual GitHub-UI step. (For the core adopt-existing path, the user supplies the project; SC-A2 does not apply.)

### Acceptance vs. offline verification

The sweep worker can prove every SC-* above (code shaping + logic) but **cannot self-close SC-A1/SC-A2** — httptest proves request *shaping*, not that GitHub's live API accepts the mutation sequence. Those are explicitly a post-merge human/e2e gate against a real project with a `project`-scoped PAT. This is why the Handoff line scopes "internet-independent" to *implementation*, not *acceptance*.

## Risks and mitigations

- **Ping-pong / oscillation — the load-bearing risk.** Forward and reverse **both pass through `AutoMove`**, so the recursion is *structural*, not incidental. Mitigation is layered: (a) hook the forward projection at the two uzi-move call sites, not inside `AutoMove` (D6), so the reverse writeback does not re-project; (b) both directions write `last_status_option_id` (D7); (c) the no-op guard compares against the **live** value, tolerating a forward-handler/reverse-poller interleave. Convergence is a gate (SC-2, M8), proven by test — not asserted by inspection.
- **Forward/reverse concurrency** → the forward path runs in the HTTP handler and can run concurrently with a poller tick's reverse read of the same project (tick overlap is *not* the concern — ticks never overlap). The live-value no-op guard must tolerate that interleaving; worst case is a redundant same-value Status write, never a wrong label.
- **Data loss via option reconcile (F9)** → `updateProjectV2Field` is a full-list replace; a mis-echoed option id clears every item's Status (corroborated: community #198803). Mitigations: uzi creates its OWN field (M4) rather than overwriting the built-in Status; v1 is **bootstrap-once, no ongoing reconcile** (D5); any reconcile echoes existing option ids.
- **Projects v2 API is a moving target** (some field/webhook features are recent GA / one sub-fact unconfirmed — F9 empty-list and color enum) → the feature is off by default; all calls are isolated in the github driver behind the capability interface; failures are non-fatal and now *visible* via `last_error` (M7).
- **PAT missing `project` scope** → detect and surface a clear admin-facing error; never fail a drag or a run because of it.
- **Poll latency for the reverse direction** → acceptable by design (uzi is poll-based already); the poll cost is within the GraphQL budget (F7). Documented as eventually-consistent on the poll cadence, not instant (M9).
- **Silent best-effort failure** → a non-fatal sync that fails for weeks is exactly this codebase's most-guarded failure mode → `github_project_links.last_error`/`last_synced_at` + a health surface (M7), not just a log line.
- **Migration numbering collision** with other in-flight PRDs → draft high, renumber above the live head at merge (repo convention).

## Dependencies

- A GitHub connection whose stored **classic PAT carries the `project` scope** (read+write). Editable in place; no re-entry (F4).
- Existing seams: the two uzi-move call sites (`handler.MoveIssue`, `runlifecycle.apply`), `forgesvc.AutoMove` (reverse writeback), the poller ticker (`Run`→`tick`→`syncRepo`), the settings store, and the github driver's authenticated transport. No cross-repo dependency.
- **Internal ordering only** (no external deps): M1+M2 first (they own the capability interface and the marker contract), then M3, then M5/M6, then M7/M8, then M9; M4 optional after the core.

## Out of scope

- GitLab / Forgejo native boards (they already have GitLab's own issue board; uzi's label board covers Forgejo).
- Syncing non-column labels, custom Projects fields other than Status, iteration fields, or roadmap layout.
- Real-time reverse sync via GitHub App / org webhook (would remove poll latency but requires an org/App and an inbound endpoint uzi does not have; explicitly rejected — see F5).
- A GitHub Actions-based implementation (user rejected; see F6).

## Open questions / Decision log

- **D1 — Closed/Done option**: does the Status option set include a terminal "Done"/"Closed" that maps to issue state, or is Closed left purely to issue state with no Status option? (Leaning: no dedicated option; Closed is issue-state, consistent with uzi's implicit Closed column.)
- **D2 — Backlog/Open option**: represent uzi's implicit `Open` (no column label) as a Status option (e.g. "Backlog"/"No Status") or leave it as GitHub's built-in "No Status". (Leaning: map Open → GitHub's native "No Status" to avoid an extra option.)
- **D3 — Project ownership**: user-owned project (this repo is `github.com/vtmocanu/uzi`, a user repo) vs. org project. Bootstrap must resolve the connection owner's node id accordingly.
- **D4 — Auto-provision vs. manual options**: **RESOLVED — full autonomous provisioning is achievable via the API** (F8, F9), delivered as the optional M4 autonomy phase on top of the core adopt-existing path (M3). Splitting it out (rather than making it the required core) is deliberate: it is a second, higher-risk feature (the F9 replace can wipe Status), and the core bidirectional sync ships and is provable over an adopted project without it. "Autonomous would be cool" is honored by M4, sequenced after the core is proven.
- **D5 — Column change propagation**: **RESOLVED for v1 — bootstrap-once, no ongoing reconcile.** Options are set at provisioning/adoption; a later board-column add/rename/remove is a documented manual step. Ongoing propagation (with the F9 read-then-echo-ids discipline) is a follow-up, kept out of v1 to avoid the highest-risk destructive path. Unknown Status options seen on the reverse path are ignored and logged.
- **D6 — Forward hook location (RESOLVED)**: hook the **two uzi-move call sites** (`handler.MoveIssue`, `runlifecycle.apply`), not `forgesvc.Service.AutoMove`. Rationale: (a) the reverse poller also calls `AutoMove`, so a hook inside it would re-project reverse writes to Status (structural loop); (b) the call sites already hold `store.Queries` + repo row, avoiding dependency-threading into `Service`'s narrow `q`/`labels`. Alternative (AutoMove + `suppressProjection` flag) rejected as more plumbing for the same effect.
- **D7 — `last_status_option_id` write-ownership (RESOLVED)**: written by **both** the forward hook (when it sets Status) and the reverse step (after it writes a label). If forward skipped it, every uzi-driven Status change would look like a GitHub-side change next poll (converges but churns). The no-op guards compare against the **live** value, not the stored marker.
- **D8 — Teardown on disable (RESOLVED in M7)**: disable is **local-only and non-destructive for BOTH `owned_by_uzi` values in v1**. `Disable` deletes uzi's own link + item rows and never issues a destructive GitHub mutation (no project delete, no card archive) — an adopted project is the user's and is kept; a uzi-owned project (M4) is likewise frozen/kept, with API-side deletion left as a deliberate future step. Re-enable = re-Adopt (idempotent). The `switch owned_by_uzi` is in place so a future divergence has a home.
- **D9 — PAT `project`-scope allowance (RESOLVED in M3)**: this feature requires the connection's classic PAT to carry the `project` scope (F4), but `privcheck` enforced GitHub scopes == exactly `{repo}` (set-equality, PRD #238 D7), which would reject such a PAT at connect time. Resolved by adding a minimal **allowed-optional** set `{project, read:project}` for GitHub only and changing acceptance to *superset-of-required ∧ subset-of-(required ∪ optional)*. `workflow`/`delete_repo` stay over-privilege; GitLab/Forgejo are unchanged. This preserves the user's least-privilege principle (the scope is *needed* for the approved feature and cannot touch `main`). Audited sound.
- **D10 — No CLI verb, no dedicated web UI in v1 (RESOLVED in M9)**: the admin surface is the four admin-only HTTP routes (`/admin/repos/{id}/github-project-sync` POST adopt / POST `…/provision` / DELETE / GET, plus the `github_project_sync_enabled` instance setting). No `api/cmd/uzi/` verb: the CLI's admin surface is read-only by construction (admin write endpoints are cookie-only). A dedicated **web admin UI** (a settings-page toggle + an adopt/provision/disable control) was **not** in the approved plan's scope and is **not** built — an admin drives the feature via the admin API, which is also what the SC-A1/SC-A2 live-acceptance step exercises. Building the web UI is a recommended follow-up issue.
