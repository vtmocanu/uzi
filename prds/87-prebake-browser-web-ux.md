## What changed in this revision (and why the old plan was heavier than needed)

The first draft recommended a **dedicated `browser` image variant** (like `jvm`), leaving "variant vs `base`" as an open gate-zero decision. The owner's decision is to put the browser in the **shared `devbox global` toolchain** (`agent/devbox-global/devbox.json`), which every worker Dockerfile installs — `base` **and** `jvm`, in the lockstep the manifest already documents. That is strictly simpler and it is the right call at uzi's scale (a single amd64 dev fleet on dev-cluster, dogfooding). Concretely, riding the shared toolchain **deletes** all of this that the variant approach required:

- **No new template.** No `agent/templates/browser/Dockerfile`, no `.gitlab-ci.yml` `.agent_templates` matrix entry, no `controller/internal/preset/preset.go` `templateImages` entry, no `api/internal/hostedsvc/testdata/hosted_templates.json` golden bump, no `preset_contract_test.go` churn, no api provisioning path for a new template name. (The variant would have been a ~6-file cross-cutting registration pinned by a shared api↔controller golden — all avoided.) **One caveat, not zero controller touch:** the closure's size may force a `nixSize` bump in `preset.go` (a single field + fleet PVC math — see §2(c)), which is distinct from and far smaller than the registration machinery above.
- **No image-name collision.** A `browser` template would publish `.../agent-browser:<tag>` — colliding namewise with the `agent-browser` CLI baked inside it. Gone.
- **No fleet-routing dependency (the old M4b / PRD #84).** With every worker image carrying the browser, there is nothing to route: any worker can run `web-ux`. The capability is simply present, not scheduled onto a subset. This is also what makes shipping a **builtin** `web-ux` coherent (§6): a builtin the lead can always pick only makes sense if every worker can actually run it.

What riding the shared toolchain does **not** simplify away, and this PRD still owns: the runtime env contract that makes Chromium *start* under the hardening (§4 — the actual M0 fix; `devbox.json` delivers the binary, it cannot express launch flags), the security review (§5 — now fleet-wide, so *more* important, not less), the worker-local crash-close (§1 — kept as defense-in-depth for any runtime where a browser is absent by design, e.g. compose or a future slimmed image), and the `web-ux` builtin (§6).

## Problem

The agent-team role library defines a **`web-ux`** role whose defining duty is to drive a running app in a **real browser** via the `agent-browser` CLI (navigate, click, snapshot the a11y tree, screenshot) and report UX / accessibility / flow-integrity findings. It is the one role that catches client-side dead-ends that unit tests and API-level e2e both pass through.

`web-ux` is not yet a builtin product role (`api/internal/agenttmpl/builtins/` ships ten files — `lead` + `architect`, `auditor`, `coder`, `documenter`, `fact-checker`, `researcher`, `reviewer`, `spec-keeper`, `tester` — no `web-ux`). But it does not need to be a builtin to run in a worker: **PRD #37** (`agent/src/repoagents.ts`) parses the cloned repo's own `.claude/agents/*.md`, and `agent/src/agents.ts` `selectSubagents` (source `"repo"`) hands that whole roster — `web-ux` included — to the lead via the SDK `agents` option, independent of `settingSources: []`. This repo has `.claude/agents/web-ux.md`, so a dogfooding run on `vtmocanu/uzi` that selects the repo agent-source at the plan gate gives the lead a `web-ux` subagent. (A builtin-source run never sees it — a condition worth stating, and one §6 removes.)

The moment the lead engages it in a worker, it fails — because the worker runtime provides nothing to run it with:

- The worker base image (`agent/templates/base/Dockerfile`) is a minimal Node 22 + git + bash + nix/devbox image. Its baked toolchain (`agent/devbox-global/devbox.json`) lists only `go`, `gcc`, `python3`, `python3Packages.pip` — **no browser, no `agent-browser` CLI**. `agent-browser` is not in `agent/package.json`, not baked in either template Dockerfile, and referenced nowhere in `agent/src`.
- With nothing provided, the engaged agent **improvises**: it installs `agent-browser` ad hoc and, needing a browser, pulls a Chromium through the worker's baked nix/devbox — and that Chromium then cannot start (see M0).

Net: `web-ux` works today only in the **local agent-team dev loop** (a developer's own machine, real Chrome). In the worker runtime — the team's primary runtime per CLAUDE.md ("we mostly test in k8s now") — it is dead weight that ends in a crash. That is exactly the "works in one runtime, silently broken in the primary one" trap CLAUDE.md warns about.

## M0 — Root cause, confirmed from a live worker crash (2026-07-20)

A dogfooding worker run engaged the repo-detected `web-ux` subagent. It installed `agent-browser` and provisioned a nix Chromium (`/nix/store/…-chromium-150.0.7871.46-sandbox`), which aborted before it could serve a page:

```
✗ Chrome exited early without writing DevToolsActivePort
FATAL:sandbox/linux/suid/client/setuid_sandbox_host.cc:166] The SUID sandbox helper binary was
found, but is not configured correctly. Rather than run without sandboxing I'm aborting now.
You need to make sure that …/__chromium-suid-sandbox is owned by root and has mode 4755.
…cpufreq/scaling_cur_freq: No such file or directory
Hint: try --args "--no-sandbox" (required in containers, VMs, and some Linux setups)
```

This is **not fixable by choice of browser package**. The worker is deliberately hardened (PRD #51): it runs as the unprivileged `worker` uid under `no-new-privileges:true` + `cap_drop: ALL` (docker-compose.yml:240-254; the entrypoint drops all but ambient `SETUID`/`SETGID` post-window), and its nix store is owned `worker:runner`, not root (base/Dockerfile:96). Chromium's SUID sandbox helper requires a `root:root` mode-`4755` (setuid-root) binary; under `no-new-privileges` that binary can neither exist nor gain privilege, so Chromium's zygote refuses to run and aborts. **Any** nix/Chromium build that ships the SUID sandbox will abort identically here. (Verified independently in the review.)

Crucially, M0 also proves the package-availability question is already answered: **Chromium is genuinely in nixpkgs and realizes onto the worker's own store** — the crash is a *start-up posture* failure (`--no-sandbox` needed), not a "browser not available in nix" failure. The one open question the prebake must still settle is not existence but **binary-cache coverage** (prebuilt vs from-source at the pinned rev — see §2).

Two secondary observations from the same crash, folded into the solution:

1. **The sandbox must be disabled explicitly.** `--no-sandbox` is safe under this exact posture: the container is already the isolation boundary (unprivileged uid, `cap_drop: ALL`, `no-new-privileges`, seccomp), so Chromium's own sandbox is redundant and non-functional. This is a property of uzi's hardening, independent of which browser we bake.
2. **`agent-browser` persists launch options in a daemon.** The crash log also shows `--executable-path ignored: daemon already running` — once a broken daemon is up, later invocations with corrected path/args silently no-op until `agent-browser close`. A first-launch failure therefore wedges the whole run's browser surface, not just one call.

## Solution

Deliver a browser + fonts + `agent-browser` to **every** worker image through the **one** shared toolchain path (PRD #18/#83 — no second package path, no runtime download, everything pinned and pre-warmed into the baked `/nix`), configure the runtime so Chromium can actually start under uzi's hardening, secure the new egress surface, and ship the `web-ux` builtin. The crash-close (§1) is independent of the prebake and lands first.

### 1. Close the crash worker-locally, FIRST — independent of the prebake

Whether or not the browser is prebaked yet, a run must never hand `web-ux` a browser-less worker and let it abort. This is worker-local and needs no scheduler change:

- At roster assembly (`agent/src/agents.ts` `selectSubagents`, repo source), **detect browser presence** (probe `agent-browser` + a resolvable Chromium on PATH / at `AGENT_BROWSER_EXECUTABLE_PATH`) and mark/skip a browser-driving role when absent.
- **Graceful degradation keyed on the failure, not the name.** The durable protection is that an engaged agent which finds no runnable browser reports a clear "no browser in this runtime — skipping browser validation" message instead of a raw Chromium SUID abort. Prefer implementing this so it protects **any** browser-driving agent (a user repo may name theirs something other than `web-ux`), e.g. via the `agent-browser` invocation exiting cleanly when no executable resolves, rather than a filter that only recognizes the literal name `web-ux`.

Once the prebake (§3) lands, the hosted fleet **never** hits this path — every worker has the browser — so §1 becomes pure defense-in-depth for compose and any future browser-less image. It still ships first, so the M0 crash stops immediately regardless of prebake timing.

### 2. Gate-zero: verify cache coverage + measure the closure cost (do this before touching `devbox.json` for real)

Three checks, any of which changes the plan, so they gate the prebake:

- **(a) Binary-cache availability — the one real feasibility risk.** Verify `chromium` + the font package + `fontconfig` resolve as **prebuilt** artifacts from `cache.nixos.org` at the pinned nixpkgs revision. This matters per build arch, and the arches are NOT symmetric:
  - **amd64 is the hard gate.** CI builds the agent image **amd64-only** — `.gitlab-ci.yml` hardcodes `--build-arg TARGETARCH=amd64` in both `build:agent` and `publish:agent`, both shared runners are amd64, and kaniko implements none of buildkit's platform args (no multi-arch, no buildx). A cache miss on amd64 means kaniko builds Chromium **from source** under a no-buildkit executor — hours, near-certain CI failure. This is a release blocker.
  - **arm64 is an EXPLICIT exit criterion, not a footnote — it gates the mandated e2e loop.** Nothing in CI builds arm64, but the local pre-merge gate does: `./e2e/run-e2e.sh` runs `docker compose --profile agent build` (which builds the agent image), and M7's DoD requires that gate green. So a single aarch64 cache **miss** = from-source Chromium on every Apple-Silicon dev machine = the e2e gate effectively bricked there until a fallback is adopted. nixpkgs `chromium` is frequently *not* cached for aarch64. Therefore M2 must **decide the fallback now** (e.g. `playwright-driver.browsers`' chromium) as the escape hatch, not "if it bites" — arm64 cache coverage (or a chosen cache-friendly package) is a hard M2 exit criterion, gated by the layer-cached reality that it's once-per-`devbox.json`-bump per machine.
- **(b) `agent-browser` interface pinned here too.** The entire §4 runtime contract rests on `agent-browser`'s flag/env interface (`--executable-path`/`--args` are proven by M0; the env vars `AGENT_BROWSER_EXECUTABLE_PATH` / `AGENT_BROWSER_ARGS` / idle-timeout are NOT). Pin the exact `agent-browser` package + version and confirm its interface **now**, alongside the cache check — both can independently invalidate the design, and both must land before the Dockerfile/env are frozen (the old draft deferred this to M4, after the bake — too late).
- **(c) Cost deltas, measured not guessed — four numbers, not two.** Measure and record in the Decision Log: (i) image-size delta; (ii) **protected-ref** build-time delta; (iii) **MR-pipeline build-time delta MEASURED SEPARATELY** — MR pipelines build kaniko **cache-less** (`.gitlab-ci.yml`: `--cache=true` only when `KANIKO_AUTH=true`, i.e. protected refs), so every MR re-realizes the full Chromium closure and re-snapshots the enlarged `/nix`, **twice** (base+jvm matrix); this recurs on every MR, not once, and is the delta developers actually feel; (iv) #92 `/nix`-reseed-time delta. **Also re-validate `nixSize`** (`controller/internal/preset/preset.go` — a flat 4Gi sized against a *measured 209 MB* baked store, and nix has no auto-GC so a long-lived worker's store only grows into it): a ~600 MB–1 GB Chromium closure multiplies the baked store 4–6× and eats per-run provisioning headroom, so confirm 4Gi still holds or bump it. A `nixSize` bump is the **one** controller-side change the shared-toolchain path may need (distinct from — and far smaller than — the variant's registration; it is a single field + fleet PVC math, not the `templateImages`/golden/contract machinery). Since the closure rides `base` **and** `jvm` and every worker's #92 reseed, these are the costs the owner is accepting; recorded so the choice is evidence-backed and a future large multi-tenant fleet can revisit "variant vs shared" against real figures.

### 3. Prebake browser + fonts + `agent-browser` on the shared toolchain path

Extend the go/python prebake — the SAME manifest and stanza (`agent/devbox-global/devbox.json` + `agent/templates/base/Dockerfile` lines 125-172, mirrored by `jvm` at lines ~83-122 — the COPY+install is at jvm:91-95 but the `/opt/uzi-toolchain` expose + PATH + fail-closed guard you must extend live at jvm:97-122), which already carries #92's `/opt/uzi-toolchain` expose + PATH wiring + fail-closed guard:

- **`agent/devbox-global/devbox.json`**: add pinned **`chromium`**, a **font package** (e.g. `dejavu_fonts`/`liberation_ttf`), and **`fontconfig`** to `packages`; regenerate the sibling **`devbox.lock`** (pins the nixpkgs rev to exact store paths — bump manifest + lock together, per the manifest's own note). A nix Chromium closure ships **no fonts**, so without the font package + fontconfig every screenshot (the role's entire evidence artifact) renders tofu/blank; add fontconfig cache setup / `FONTCONFIG_FILE` if the built image needs it.
- **`agent-browser` is NOT a nix package** — it is a small Node CLI, so it does **not** go in `devbox.json`. Pin it in **`agent/package.json`** next to `tsx` (`base/Dockerfile:174` — "Only runtime deps (tsx) are needed"), baked, **never installed per-run** (the ad-hoc install is what produced M0).
- **Extend the fail-closed BUILD guard** (`base/Dockerfile:171-172`, mirrored in `jvm`) to also assert `agent-browser` resolves AND an **exit-bounded** headless launch succeeds — wrap it in `timeout N …` and use a real launch (e.g. `--headless --no-sandbox --disable-dev-shm-usage --dump-dom about:blank`), **not** a bare `--version` (which never actually launches Chromium), so a hung browser **fails the build** instead of hanging the CI job to its own timeout. (No structural reason it can't run under kaniko: `RUN` executes as root, `--no-sandbox` permits a root launch, `--disable-dev-shm-usage` covers the small builder `/dev/shm`.) **Honest caveat:** this runs in the BUILDER (root, no `cap_drop`, builder `/dev`), so it validates the binary + shared libs + fonts, NOT the runtime hardening posture — only M7 exercises the posture.

Because both `base` and `jvm` install the shared manifest, this delivers the browser to **every** worker image with one manifest edit — the whole point of the owner's choice.

### 4. Runtime env contract so Chromium starts under the PRD #51 hardening (the M0 fix)

`devbox.json` puts Chromium on PATH; it cannot express launch flags. These ENV must be set in **BOTH** `agent/templates/base/Dockerfile` **and** `agent/templates/jvm/Dockerfile` — **jvm is `FROM node:22-alpine`, NOT `FROM base`, so ENV does NOT inherit**; every shared ENV in jvm today is an explicit mirrored copy, and these are no different. Setting them only in `base` would leave jvm workers with the browser binary (M3 gives it to both) but no launch flags → **jvm workers re-crash with exactly the M0 SUID abort this PRD exists to fix**, on the template the re-scope was supposed to cover for free. Set, in lockstep, both files:

- `AGENT_BROWSER_EXECUTABLE_PATH` → the prebaked Chromium, pointed at the **stable `/opt/uzi-toolchain/bin` handle (#92), never a raw `/nix/store/…` path**. ENV is static text baked at build time; a store path rolls per rebuild — this is precisely #92's lesson. Never let `agent-browser` auto-discover / auto-download.
- `AGENT_BROWSER_ARGS="--no-sandbox,--disable-dev-shm-usage"` — `--no-sandbox` mandatory per M0; **`--disable-dev-shm-usage` because compose sets no `shm_size`** (grep: zero hits → 64 MB default `/dev/shm`), and `/dev/shm` exhaustion is headless Chromium's next classic abort after the sandbox one. On k8s, alternatively size an `emptyDir` `medium: Memory` at `/dev/shm` (decide in §2/M7). Add `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` if any playwright dep is pulled in.
- If §2(b) finds the `AGENT_BROWSER_*` env vars unsupported at the pinned `agent-browser` version, ship a tiny wrapper that passes the flags instead.
- Stale-daemon fix (pick ONE, not both — they target the same M0-secondary issue): a sane `AGENT_BROWSER_IDLE_TIMEOUT_MS`, or an entrypoint `agent-browser close` at run start.

Without these ENV, Chromium is on PATH and **still aborts exactly like M0** — the manifest delivers the browser, this milestone makes it *start* — and because jvm does not inherit base's ENV, forgetting the jvm copy silently re-creates M0 on every jvm worker.

### 5. Security — name the surface, don't just "review" it (now fleet-wide)

Because the browser rides the shared toolchain, **every** worker now carries the egress/SSRF surface, not an opt-in subset — so this matters more than under the variant plan, not less. The good news, verified against the chart: **the containment is ~90% already shipped.** The worker egress set — the vanilla floor (`deploy/chart/templates/worker-networkpolicy.yaml`) + the Antrea FQDN ANNP (`worker-fqdn-egress.yaml`), configured in `deploy/values/dev-cluster.yaml` — is already default-deny in both directions, allows only DNS + the api + named external FQDNs (`gitlab.example.com`, `*.anthropic.com`, `cache.nixos.org`), and its `denyCIDRs` drop-belt **already** blocks `169.254.169.254/32` (cloud metadata), `10.96.0.1/32` (kube-apiserver) and `192.0.2.0/24` (node CIDR/kubelet). So a browser SSRF from a worker is already bounded to those few destinations by default-deny. The remaining work is one rule + sign-off:

- **Verify the blocks, do NOT rebuild them.** The metadata / apiserver / node-CIDR drops already exist in `workers.fqdnEgress.denyCIDRs` on dev-cluster (present as of 2026-07-20). §5 confirms them; it does not re-add them.
- **Add exactly ONE allow — the M7 target — as a selector-based rule (Decision: Option A, owner-chosen 2026-07-20).** M7 drives uzi's own **in-cluster `web` Service**, which nothing currently permits (the floor allows only DNS + api). Add a single egress rule to the vanilla floor via the existing, currently-empty `workers.networkPolicy.extraEgress` hook: `namespaceSelector` = the release namespace + `podSelector` = `app.kubernetes.io/component: web`, on the web port — modeled exactly on the api allow already in `worker-networkpolicy.yaml`. It **must** be selector-based, not FQDN: Antrea's FQDN ANNP cannot match an in-cluster Service, because AntreaProxy rewrites the Service IP to a pod IP before policy enforcement (`worker-networkpolicy.yaml:62-67`). No new template — just the values entry, values-gated like the rest. **(Option B — allowing the public ingress `uzi.example.com` via `allowFQDNs` — was rejected: hairpinning to our own ingress from in-cluster is fragile NAT-loopback, and it would drive the browser against the public TLS + real-auth surface; the in-cluster Service is cleaner and stays off the public path.)**
- **No other egress for browser-capable workers.** Validating uzi's own UI needs only the target app; the existing forge/anthropic/nix allows are unrelated, and everything else stays denied — that default-deny **is** the SSRF containment. Targeting arbitrary user apps is per-run egress, tracked as §7's deferred target-app follow-up.
- The read-only bound of the `web-ux` role (it forbids real mutations without explicit user permission) recorded as a likelihood control, not a substitute for the egress rule.
- Name the kindnet no-enforcement caveat (already documented in `deploy/README.md`): a green KinD run proves nothing about egress enforcement — only the dev-cluster rollout (M7) does.
- Auditor sign-off required.

### Decision Log / alternatives considered

- **Delivery: shared `devbox global` toolchain (CHOSEN, owner directive) vs a dedicated `browser` image variant.** Chosen: extend `agent/devbox-global/devbox.json`, which both `base` and `jvm` install. Rationale: it is the ONE nix path the whole worker toolchain already uses (go/gcc/python), so the browser is one manifest edit + the §4 env, and it deletes the variant's ~6-file cross-cutting registration (new Dockerfile, CI matrix, `preset.go` `templateImages`, the api↔controller `hosted_templates.json` golden + `preset_contract_test.go`, the api provisioning path), the `agent-browser` image-name collision, AND the fleet-routing dependency (old M4b / PRD #84 — with every worker browser-capable there is nothing to route). The accepted cost is closure weight on every worker image + every #92 reseed, quantified in §2(c). Correct at uzi's scale (single amd64 dev fleet); a future large multi-tenant fleet can revisit against the §2(c) numbers.
- **Fix by picking a "sandbox-friendly" browser package instead of `--no-sandbox`** — rejected: the blocker is the PRD #51 hardening (no setuid, non-root store), not the package. No nix Chromium build can satisfy a setuid-root sandbox helper here.
- **Unprivileged user-namespace sandbox (no SUID, so no `--no-sandbox`)** — considered, rejected. Chromium's userns sandbox would work without `--no-sandbox`; it is blocked here only by Docker's default seccomp / k8s `RuntimeDefault` denying `CLONE_NEWUSER`, which a custom seccomp profile could allow. Rejected knowingly: it adds profile-distribution cost (incl. k8s `Localhost` seccomp profiles) and trades userns kernel attack surface for renderer sandboxing that the container boundary already substitutes for. `--no-sandbox` under the existing hardening is simpler and no less safe here.
- **Weaken worker hardening (grant setuid / drop `no-new-privileges`)** — rejected outright: trades a redundant in-process sandbox for a real reduction in worker containment.
- **Let the agent install `agent-browser`/Chromium per-run (status quo)** — rejected: it caused M0 (unpinned; the improvised nix Chromium aborts) and violates the PRD #18 no-runtime-download rule.
- **Gate `web-ux` via PRD #84 capability-aware scheduling** — moot under the chosen delivery: every worker is browser-capable, so there is nothing to schedule. #84 was only relevant to the rejected variant approach.

### Correction to §4 (baked ENV is INERT for the agent — the actual delivery is the shim)

§4 as written specifies baking `AGENT_BROWSER_*` ENV into the Dockerfiles. That is **necessary but not sufficient**: `agent/src/sdk-env.ts` `buildSdkEnv` hands the SDK/agent subprocess a **sparse, from-scratch allowlisted env** (only `CLAUDE_CODE_OAUTH_TOKEN`, `HOME`, `PATH=runnerPath()`, the provision-allowlisted keys, and `DOCKER_HOST`) — it does NOT inherit the image ENV, so the baked `AGENT_BROWSER_EXECUTABLE_PATH`/`AGENT_BROWSER_ARGS`/`FONTCONFIG_FILE` never reach the agent's Bash tool. Left at the baked ENV alone, agent-browser (invoked by the agent) would auto-discover Chromium on PATH and launch it **without `--no-sandbox`** → the exact M0 SUID abort recurs, and fonts would be tofu. **Resolution (verified against `buildSdkEnv`):** the shim — which DOES run on the agent PATH — re-establishes all four vars as **defaults** (`: "${VAR:=…}"`, so an explicit caller value still wins) right before exec. This scopes the vars to the agent-browser process + its Chromium child rather than widening the deliberately-minimal agent env, and needs no `sdk-env.ts` change. The baked Dockerfile ENV is kept (worker/build context + the build guard + documented contract). This is the crux of M4 and was the coder's finding, lead-verified.
