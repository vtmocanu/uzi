**Status:** Ready for planning; implementation requires the plan gate below.

## Approved policies

These are user-approved 2026-09-06; the parent's D3/D4/D5/D11 carry rationale.

- Support named `codex_auth` logins and `openai_api_key` rows, one default across those Codex kinds, separately from Anthropic defaults. Resolve and freeze the selected credential/auth mode at run creation; default changes affect future runs. Never silently switch a subscription run to a paid key. Credential version may advance while the selected credential stays fixed; replacing a saved row must not silently move a bound run to another provider account/workspace.
- Use verified actual provider account/workspace identity for duplicate-import reconciliation and shared refresh state. A label, row id, callback hint or merely decoded JWT is not proof of that identity. Do not invent a provider claim field.
- **Multiple runs on the same Codex subscription may execute concurrently, as with Anthropic.** This explicitly supersedes the earlier seat-busy queue recommendation. No run-long seat lock, seat-held status set, active-seat unique index or subscription claim predicate. Existing general user/worker capacity controls stay intact; API keys acquire no subscription-specific lock.
- Coordinate credential operations only. Persist the latest refreshed login before checkpoint publication, pause/park, graceful shutdown or completion; reject stale writes and reconcile lost acknowledgments idempotently. Persistence failure pauses progress and retains protected recoverable state. Re-login is the last resort when recovery is impossible; recovery after loss of every durable copy is not promised. CAS alone cannot prevent two provider-side refreshes from rotating the same token.
- Require a run-specific capability **and** its currently owning worker for credential operations. The server derives the target credential from the immutable run binding; requests cannot select a user or secret id. Lifecycle/reclaim/revocation checks must supplement worker ownership.
- M1 owns storage and the minimal immutable run binding, removing the M1/M5 dependency cycle. M5 consumes it; broad harness defaults/pickers, start/schedule routing and run-kind enablement remain outside this child.

## Plan gate: settle mechanisms before implementation

The Auto plan must specify the exact schema, default/delete/replace behavior, verified identity source and validation, duplicate-import handling, capability scope/lifetime/revocation, secret version/CAS/idempotence, protected recovery storage and short refresh-operation coordination. Separate approved policy from proposed implementation. Do not infer provider token-reuse safety from M0.

A source-evidenced candidate is API-owned refresh authority with access-token-only app-server sessions: pinned Codex 0.153.2 supports `account/login/start` with `chatgptAuthTokens` and `account/chatgptAuthTokens/refresh` callbacks. The callback has a 10-second deadline and carries a reason plus `previousAccountId` hint, not trusted run/generation authority. Bind a future M3 control connection to the API-owned credential and generation. Codex's token parser only decodes JWT data and the host can supply an account id; neither validates the saved identity for uzi. This is source evidence, **not runtime proof** or an approved provider identity field. Source-only anchors at upstream `657a993c` (0.153.2): [login and refresh protocol](https://github.com/openai/codex/blob/657a993c/codex-rs/app-server-protocol/src/protocol/v2/account.rs) (`ChatgptAuthTokens`, refresh request/response; lines 90, 279, 295, 524), [external auth bridge](https://github.com/openai/codex/blob/657a993c/codex-rs/app-server/src/external_auth.rs) (10-second deadline, lines 18/33), [auth manager](https://github.com/openai/codex/blob/657a993c/codex-rs/login/src/auth/manager.rs) (empty refresh token/host account override, line 1723) and `token_data.rs` (payload decoding, line 117). These findings are provided for offline planning; no upstream test was run to establish this candidate.

The plan must demonstrate how its server contract supports two clients concurrently without whole-run serialization: one coordinated provider refresh for a stale generation, durable commit before distributing the newer access token, and retrying clients reconciled to the committed generation. Address cancellation, lost reply, credential replacement/revocation and ambiguous provider outcomes. If the provider accepted a rotation before its response was lost, do not blindly retry the old token or expire a coordination lease into a second refresh. Retain/quarantine the unresolved credential operation for safe reconciliation; require re-login only if recovery is impossible. Show bounded behavior compatible with the 10-second callback, including the failure response; M3 later proves the real protocol bridge.

Resolve these choices at the normal plan gate. If trusted identity or safe refresh cannot be established from supplied evidence and available source, report the exact missing prerequisite and block dependent implementation; do not manufacture a provider guarantee. No broad design review or live provider experiment is required just to write the plan.
