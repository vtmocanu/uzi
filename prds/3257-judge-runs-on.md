# PRD #3257: Judge runs on (Claude, Codex or the run's own harness)

**Status**: Ready. Child of epic #1703 (letter E). Blockers #3245 (per-harness judge model) and #3248 (per-harness summary model) have landed. Split on 2026-11-10 with the maintainer's agreement: this PRD covers the judge only; "Summaries run on" is the sibling #4156 with its own credential design.

The mock is the presentation reference: layout, order, wording and colour roles. Small deviations for consistency with the app (its tokens, components, spacing) are expected. A larger deviation (a dropped element, a different layout or information) only when necessary, listed in the PR body under `Mock deviations` with its reason; an absent list claims parity. The PR carries side-by-side screenshots. This PRD's text wins where it specifies; the mock governs what the text leaves out. The mock's Settings -> Models tab does not exist yet (#3263): render the rows on the current Run defaults judge card, as `AfterRunDefaults.dc.html` shows, and leave the Models tab to #3263.

## Problem

The judge always runs on the harness of the run it reviews (`judgeHarness := Harness(run.Harness)` in `maybeEnqueueJudge`, `api/internal/workersvc/judge_enqueue.go`, and in `RerunJudge`, `api/internal/workersvc/judge_read.go`; documented in `docs/judge.md`). A user who wants every run judged by one provider (for example Codex judging Claude runs, to get a second family's view or to spend one quota) cannot choose it. When the inherited harness has no usable credential, the automatic judge is skipped silently (`slog.Debug` only), so the user sees no judge and no reason.

## Outcome

- A per-user setting **Judge runs on**: `Same as the run` (default, stored as NULL), `Claude` or `Codex`.
- Automatic enqueue and the manual **Run judge / Re-run judge** button create the judge run on the resolved harness: the setting when explicit, else the target run's harness. The judge run binds its own credential for that harness through the existing paths (Claude: the user's judge token binding at claim; Codex: the usable Codex credential frozen at judge-run creation). Nothing is borrowed from the target run's credential.
- **An explicit choice is hard.** If the chosen harness has no usable credential, the judge is skipped, never created on the other harness and never charged to the other provider. The run page shows the skip reason, and the existing Run judge button retries with the setting and credentials current at the click.
- **Admin-enforced judge** (`judge_enforce_all`) follows each user's choice.
- The judge model comes from the per-harness judge model setting (#3245) of the **judge run's** harness, as today.
- Web: a "Judge runs on" select on the Run defaults judge card, the unused judge-model lane dimmed with "Not used: the judge runs on <harness>", and copy that no longer says the judge always follows the run's harness. CLI: `uzi settings get` (table and `--json`) shows the setting and its source. Effective settings (#3254) report the resolved judge harness and its source.

Acceptance examples:

- User sets Judge runs on = Codex and holds a usable Codex credential. A Claude issue run completes; a judge run with `harness=codex` is created, reviews it with the Codex judge model, and its usage is attributed to Codex. No Anthropic token is read for that judge.
- Same user deletes their Codex credential. The next Claude run completes; no judge run is created, the run page judge panel says the judge was skipped because no usable Codex credential exists, with the Run judge button. Clicking it returns the existing 422 refusal; no Claude judge is ever created.
- Setting unset: behaviour is identical to today on both harnesses (existing tests stay green), except that a credential skip is now shown on the run page instead of being silent.

## Out of scope

- "Summaries run on" (sibling issue): summaries run inside the target run's claim, which carries one provider's credential; choosing another harness there is a separate trust-boundary design.
- An admin instance default for Runs on (the mock records why: an instance-wide Codex default would silently skip users without a Codex credential).
- CLI writes of the setting: `PUT /me/settings` is cookie-only (`api/internal/handler/routes_me.go`); authenticated CLI writes are designed in #3264, which extends to this field when it lands. No CLI `rejudge` verb (none exists today).
- Task-review settings (#1570), primary-run cross-harness switching, choosing among several Codex credentials.
- The Settings -> Models tab (#3263).

## Modules and seams

- **Setting storage**: an additive migration adds `users.judge_runs_on text NULL CONSTRAINT users_judge_runs_on_check CHECK (judge_runs_on IN ('claude','codex'))` (nullable, no default: metadata-only add). NULL means same as the run. Queries (`api/internal/store/queries/users.sql`): add the column to `GetUserSettings`' explicit column list and a `SetUserJudgeRunsOn :one` (`UPDATE users SET judge_runs_on = @judge_runs_on WHERE id = @id RETURNING judge_runs_on`), called PATCH-style beside `SetUserCodexJudgeModel` in `PutMySettings`; null maps to SQL NULL and validation happens before any write. Run `sqlc generate` and commit `api/internal/store/*.sql.go`. Migration number is a draft; it is renumbered at merge (`task migration:renumber`). Read and written through `GetMySettings` / `PutMySettings` (`api/internal/handler/user_settings.go`) and the `UserSettingsDTO` (`api/internal/apitypes/user_settings.go`) as `judge_runs_on: string|null`, the `default_harness` convention: absent leaves it unchanged, null clears it to same-as-run, `"claude"`/`"codex"` sets it, anything else is 400 `invalid judge_runs_on`. Contract fixtures under `fixtures/api-contract/` and the web mirrors (`web/src/lib/apiTypes.ts`, `web/src/mocks/mockApi/settings.ts`) update in the same change.
- **Judge harness resolver** (one pure function in `api/internal/workersvc`, used by both `maybeEnqueueJudge` and `RerunJudge`): input the owner's `judge_runs_on` and the target run's harness; output the judge harness. A failure to read the owner's setting is a judge-enqueue error (logged, nothing created, nothing recorded), never a silent fallback to the target's harness. Both callers pass the result to `createRunResolved` as an explicit selection, exactly as they pass the inherited harness today, so the existing no-fallback contract (`ErrNoCredentialForHarness`) is what makes the choice hard. The existing Claude token presence pre-checks (the `KindAnthropicToken` checks in both functions) must key on the **resolved judge harness**, not the target run's harness; otherwise a Claude target configured for Codex is skipped before `createRunResolved`, or a Codex target configured for Claude skips the check.
- **Gate order**: credential refusals are recorded only after every other judge gate has passed (status, `runkind.JudgeEligible`, admin global switch, opt-in or enforced, the 4b fail-origin skip sets and the spend guards), so a run the judge would never review records nothing. Move Gate 4 (the credential pre-check, today before Gates 4b and 5 in `maybeEnqueueJudge`) below Gate 5; do not change what any other gate decides. Refusal sources map to fixed codes, in `startRefusal`'s order (`api/internal/handler/effective_settings.go`): `ErrHarnessCredentialDisabled` maps to `credential_disabled`; `ErrCodexPoolUnavailable` (today it falls through to `slog.Warn` in `maybeEnqueueJudge`) maps to `codex_pool_unavailable`; the Anthropic-token pre-check and `ErrNoCredentialForHarness` map to `no_usable_credential`. Any other error records nothing.
- **Skip record** (M2): a new table `judge_skips (target_run_id uuid PRIMARY KEY REFERENCES runs ON DELETE CASCADE, harness text NOT NULL CHECK (harness IN ('claude','codex')), reason text NOT NULL CHECK (reason IN ('no_usable_credential','credential_disabled','codex_pool_unavailable')), created_at timestamptz NOT NULL DEFAULT now())`. Owner is the target run's owner (no `user_id` column; deletion cascades through `runs`; the PK covers lookup and cascade). Fenced against a concurrent judge creation by a row lock on the target run: the automatic enqueue writes the skip only after its create transaction rolled back (`createRunAtomic`, `api/internal/workersvc/harness_resolver.go`), in its own transaction that first takes `SELECT ... FROM runs WHERE id = <target> FOR UPDATE`, then `INSERT ... SELECT ... WHERE NOT EXISTS (SELECT 1 FROM runs WHERE kind = 'judge' AND target_run_id = <target>) ON CONFLICT (target_run_id) DO UPDATE SET harness, reason, created_at = now()`. Every judge creation (automatic and rerun) takes the same target-row lock and issues `DELETE FROM judge_skips WHERE target_run_id = <target>` inside the `createRunResolved` insert closure, on its `q` (the `qtx` that runs `CreateJudgeRun` and the Codex freeze), never on `s.q`; the DELETE joins the `Store` interface and the unit `fakeStore`. A judge created first leaves the late skip write a no-op; a skip written first is deleted by the creation. Read precedence is review, then pending judge, then skip. Server-authored fixed codes only: no provider error text, no credential identifiers. Not in `run_reviews` (that row needs a real verdict, is unique per target, and its presence means a completed review to `JudgePanel` and the review listings). Not a `run_message` on the terminal target run (it would need terminal-run sequence and idempotency design for no gain).
- **Review read**: `GetRunReviewPanel` (`api/internal/workersvc/judge_read.go`) returns the skip after its `GetRunForViewer` gate, only when `review` and `pending_judge` are both nil; a new sqlc query `GetJudgeSkipForTarget` in `queries/judge.sql` is a plain by-target lookup documented as caller-scoped like `GetRunReviewForTarget`. The handler (`GetRunReview`, `api/internal/handler/judge.go`, route `GET /api/runs/{id}/review`) emits `skip {harness, reason, at}` on every success path, always present, `null` when there is none (the same convention as `pending_judge`). `uzi review show` (`api/cmd/uzi/review.go`, which rebuilds its own envelope) shows the skip in the table and keeps `skip` in `--json`; update `uzicli.RunReview`. The run page judge panel (`web/src/pages/runView/JudgePanel.tsx`) derives its copy from the stored row only, never from the current setting: for example "The judge was skipped on <at>: Codex had no usable credential." with a link to Run defaults and the existing Run judge button; the copy is viewer-neutral (an admin viewing another user's run reads no "your"). A rerun refusal keeps the existing 422 codes (`no_credential_for_harness`, the Codex pool body) and the panel shows them inline; the `no_credential_for_harness` message (`api/internal/handler/judge.go`) changes from "the target run's harness has no usable credential" to "the judge's harness (<harness>) has no usable credential".
- **Claim time is unchanged**: `assembleJudgeClaim` already keys the judge model and credential on the judge run's own harness. A credential that becomes unusable between creation and claim keeps today's park or fail behaviour on the judge run.
- **Usage**: the judge run's usage is already attributed to the judge run's harness. Verify with a test that a Codex judge on a Claude target records Codex usage and cost; no attribution code change is expected.
- **Effective settings** (`api/internal/handler/effective_settings.go`, `EffectiveSettingsDTO`): add a new top-level `judge_harness: HarnessValueDTO` field on `EffectiveSettingsDTO` (additive; `EffectiveSettingsVersion` stays 1): explicit setting -> `value` `"claude"`/`"codex"`, `source` `user_default`; unset -> `value` null, `source` `same_as_run` (a new source token, documented beside `chosen_at_create` on `HarnessValueDTO` in `api/internal/apitypes/effective_settings.go` and added to the TS source union in `web/src/lib/apiTypes.ts`); `fixed_at` `create` (the existing token: the judge harness is fixed when the judge run is created) in both cases; `notes` empty. The judge-model cell for the lane that will not be used carries a new note `not_used`, with labels for `not_used` and the new `same_as_run` source added to `fixtures/model-settings/contract.json`; contract tests pin the full inherited and explicit `judge_harness` wire cells; update `fixtures/api-contract/effective_settings*.json`, the web mirror and the CLI renderer (`api/cmd/uzi/settings_effective.go`, `settings_models.go`).
- **Web settings**: `web/src/pages/RunDefaults.tsx` judge card: the select (options in the mock's order), the dimmed lane, and the copy at the "The judge runs on the harness of the run it reviews" sentence. The Judge runs on select is always visible and keeps an explicit Claude or Codex value even when that harness has no usable credential (including under enforcement): it must not reuse the usable-harness gate the model lanes use (`showCodexLane = codexUsable` / `showClaudeLane` in `RunDefaults.tsx`) and never silently changes the stored value; the card shows that the chosen harness has no usable credential. When the judge harness is Codex, the "Token the judge spends" picker is dimmed "Not used: the judge runs on Codex" per the mock. The same sentence in `web/src/pages/adminSettings/JudgeSettingsCard.tsx` changes to say the judge runs on each user's choice, defaulting to the run's harness. `SummarySettingsCard.tsx` is untouched (summaries still follow the run).
- **Text safety**: no new untrusted text is rendered; the skip reason is a fixed server code mapped to fixed copy.

Resource bounds: the setting is one enum column; the skip record is at most one row per target run, deleted with the run; no new background work, polling or provider calls.

## Decision Log

- **2026-11-10 Split from Summaries run on** (maintainer agreed): the judge is its own run, so choosing its harness reuses the per-harness credential selection, freezing and release paths that already exist; summaries run inside the target run's claim, which carries one provider's credential (`ClaimSecrets` in `api/internal/workersvc/claim.go`), so a cross-harness summary is a different trust-boundary design. Rejected: one PRD for both (one large PR whose hard part does not help the judge).
- **Amends PRD #1429 D4 for the judge only** (`prds/done/1429-codex-public-activation.md`): derived runs inherit the source run's harness; the judge now runs on an explicit user choice when set, still with no fallback and a visible reason. MR-rework, task review and then-fix keep inheriting. Authority: the epic #1703 decision locked with the maintainer ("Judge and summaries get Runs on").
- **Enforced mode honours an unusable explicit choice by skipping** (maintainer decision 2026-11-10): under `judge_enforce_all`, an explicit Judge runs on whose credential is unusable skips the judge with the visible reason; it does not fall back to the reviewed run's harness. Rejected: a fallback under enforcement only (it would spend a provider the user explicitly excluded; guaranteeing a judge despite missing credentials would need a separate admin-owned credential policy). `docs/judge.md`'s "Enforced mode has no separate user opt-out switch" paragraph is rewritten to say an explicit choice without a usable credential is skipped with a reason.
- **Resolve the harness at judge-run creation, from the setting current at that time**, for both automatic enqueue and rerun. Rejected: freezing the choice on the target run (a retry after the user fixes their settings would keep failing).
- **Explicit choice is hard, via the existing explicit selection to `createRunResolved`**. Rejected: a fallback to the target's harness (it would charge a provider the user excluded).
- **Skip record in a small `judge_skips` table, fenced by a target-row lock, read after review and pending judge, copy from the stored row**. Rejected: `run_reviews.status = 'skipped'` (needs a fake verdict; a review row means a completed review to every consumer) and a `run_message` on the terminal target run (terminal-run sequencing and idempotency for no gain). Recorded only after all other gates so it never reports on runs the judge would not review; only automatic enqueue writes it, since a rerun refusal is already shown synchronously.
- **Settings surface on Run defaults now, Models tab later** (#3263 owns the tab). **CLI read now, writes with #3264** (the write route is cookie-only by design today).
- **No admin Runs-on default** (epic #1703 decision).
