# PRD #1906: Official-sources web research: egress site lists, a fetch service, and a no-internet worker lane

**Issue**: #1906
**Status**: Draft (revised after review, 2026-09-29)
**Priority**: High
**Related**: ADR-0285 (worker egress is a two-tier trust boundary), #1651 (the allowlist is IP-level, not host-level), PRD #529 (run-bound ephemeral workers), PRD #83 (docker tier, the precedent for a second worker namespace), PRD #50 (LLM egress proxy, draft), PRD #1332 (the protocol-capability claim clause this PRD mirrors), `docs/capability-scheduling.md`, PRD #1908 (repo-less jobs, which carry the site-list setting), PRD #1909 (files and source log in job results), PRD #1907 (products and product tokens)

## Problem

External products that build on uzi need **vetted web research**: a worker reads a vendor's official documentation and datasheets and writes an analysis. The requirement is hard, not best effort: **the research may use official sources only**, from the first release.

uzi cannot enforce that today:

1. **Worker egress is IP-level.** The restricted tier names its destinations in a CNI FQDN policy (`deploy/chart/templates/worker-fqdn-egress.yaml` on Antrea, `worker-ovn-egress.yaml` on OVN-Kubernetes). Both resolve the name and allow the resulting addresses; neither checks TLS SNI or the HTTP Host header (ADR-0285, "IP-level, not host-level"; #1651).
2. **Official documentation sits on shared hosting.** A DNS check (2026-09-29) of a few large vendors' documentation and support hosts found them on AWS CloudFront, a Salesforce edge network, and vendor-operated edge networks that also serve other customers. Allowing those addresses opens TCP 443 to every other site on them.
3. **The docker tier is open by design** (`worker-docker-networkpolicy.yaml`, ADR-0285), and the restricted tier's list is namespace-wide, so no per-run list is expressible.
4. **Claude's built-in `WebSearch` runs server-side at Anthropic.** No worker-side network rule can restrict or log what it reads.
5. **Bash is a general network client.** Any run with Bash can reach whatever the pod's network admits, so restricting only the named web tools is not a boundary (the `agent/src/repoagents.ts` header makes the same point for subagents).

The same check on OKD 4.22 (OVN-Kubernetes) found no built-in name-level egress control: `EgressFirewall` `dnsName` is IP-level, and the installed `AdminNetworkPolicy` (v1alpha1) has no domain-name peer at all. Cilium matches SNI but would replace the CNI. A service-mesh egress gateway could check SNI but brings a whole mesh and handles per-run lists poorly.

## Current state (verified on `main`, 2026-09-29)

- **Worker namespaces.** The controller renders a worker into one of two namespaces: `namespaceFor` returns `cfg.DockerNamespace` for a docker worker and `cfg.Namespace` otherwise (`controller/internal/kube/render.go:306`). `protocol.DesiredWorker.Docker` is the pod-shape dimension that selects it (`controller/internal/protocol/protocol.go:47-54`), mirrored from the api's `hostedsvc.DesiredWorker`.
- **Run-bound workers.** `DesiredWorker.Ephemeral` marks a worker whose lifetime is one run (`controller/internal/protocol/protocol.go:75-80`); the api provisions them in `api/internal/hostedsvc/ephemeral.go`. `workers.kind` (`external` / `hosted`) is set by the server, not reported by the worker (`api/internal/store/migrations/00066_hosted_workers.sql:24`).
- **Worker network floor.** `deploy/chart/templates/worker-networkpolicy.yaml` is a default-deny in both directions with selector-based egress allows for DNS and the api's worker port, plus two optional knobs: `workers.networkPolicy.allowWebService` (`:85`) and `workers.networkPolicy.extraEgress` (`:112`). Named external egress is added by `worker-fqdn-egress.yaml` (Antrea) or the NetworkPolicy plus `EgressFirewall` pair in `worker-ovn-egress.yaml` (OVN). OVN wildcards are refused at render unless `workers.fqdnEgress.ovn.allowWildcards` is set (`deploy/chart/values.yaml`, `fqdnEgress` block).
- **The api has no egress policy** (`deploy/chart/templates/api-networkpolicy.yaml` polices ingress only).
- **Model endpoint.** The worker reaches Anthropic directly: the SDK child gets `CLAUDE_CODE_OAUTH_TOKEN` in its env (`agent/src/sdk-env.ts`). PRD #50 would move that behind the api and is still a draft. Nothing in `agent/src` sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` today.
- **Restricting the tool set.** The SDK `tools` option limits which built-in tools exist at all; chat runs use it to allow only `Read`, `Grep`, `Glob` plus in-process MCP tools (`agent/src/chat-executor.ts:59`, `:250`), and root file tools at the run directory with `buildPathGuardHook` (`agent/src/chat-executor.ts:268`, `agent/src/guardrails.ts`). Issue runs use `disallowedTools` for a narrow deny list (`agent/src/sdk-executor.ts`).
- **In-process MCP tools** run inside the worker's node process, not in the SDK child: `createSdkMcpServer` in `agent/src/findings-tools.ts:146`, `agent/src/forge-tools.ts:288`, `agent/src/memory-tools.ts`.
- **Worker routes that return third-party content.** Worker-authenticated, run-scoped reads of agent memory and of forge issues, merge requests and pipeline jobs (`api/internal/handler/handler.go:1160-1173`). None of it passes a fetcher or a source log.
- **Capability matching and its escape hatches.** A run's `required_capabilities` must be a subset of a worker's effective capabilities inside `fn_worker_can_claim` (migration `00151`), which is bypassed wholesale when `capability_aware` is off (`NOT capability_aware OR ...`). `ClearRunRequiredCapabilities` (the "run without it" action) wipes a run's requirement, and worker scheduler capabilities are self-reported at registration (`api/internal/handler/worker_protocol.go:225`).
- **The hard-clause precedent.** Protocol capabilities (`workers.protocol_capabilities`, `api/internal/handler/worker_protocol.go:230`) back dedicated claim clauses that sit **outside** `fn_worker_can_claim`, `ClearRunRequiredCapabilities` and the kill-switch: the completion-interlock and Codex clauses in `api/internal/store/queries/runtime.sql:881-893`, documented at `api/internal/capability/capability.go:60-75` (`CodexHarnessV1`).
- **Images.** The api image builds one binary, `/server` (`api/Dockerfile:53-62`). A new image would need a `.github/workflows/release.yml` change.
- **Chart render checks** are shell scripts run by CI and Task: `scripts/assert-chart-render.sh`, and `scripts/assert-openshift-render.sh` via `task render:openshift-check`.

## Decisions

1. **A run with a site list runs in its own worker lane with no internet.** A third worker namespace (working name `uzi-workers-isolated`, a chart value). Its NetworkPolicy is default-deny, and its only egress is DNS, the api, the fetch service, and the model endpoint (Decision 6). It does **not** inherit `allowWebService` or `extraEgress`. This is a backstop for the network path. It is not the whole boundary: DNS recursion (a query-name and TXT channel) and the model API remain reachable, and both need code execution in the pod to abuse. The real boundary is the tool set (Decision 5); the network lane guarantees that the tool set is the only thing standing between the agent and a general client, and removes the general client.
2. **Web content comes only through `uzi-fetcher`, a separate service.** It is part of uzi (same repo, chart and release), but runs as its own Deployment, never inside the api: the api holds every secret (`UZI_SECRET_KEY`, forge PATs, model tokens), and the fetcher parses untrusted internet content. To avoid a new image (and the release-workflow change a new image needs), it ships as a second binary in the existing api image (`api/cmd/fetcher`, run with a different `command`). Worker to fetcher and fetcher to api use TLS, as worker claims to the api already do.
3. **What the fetcher accepts and checks, on every request:**
   - **Request shape is fixed:** `GET` only; the agent supplies a URL and nothing else (no headers, no body, no method). The fetcher sets `Host` and SNI from the same parsed URL it checked, so there is no Host-header domain fronting. URLs with userinfo are refused; URL length is capped.
   - HTTPS only; the normalized host is on the run's site list (Decision 4 normalization; exact names, or a `*.` entry covering subdomains);
   - every redirect hop is re-checked against the list (bounded hop count, redirect bodies discarded under a small cap);
   - every resolved address is public: IPv4-mapped IPv6 is unmapped first; private, loopback, link-local, CGNAT, multicast, `fc00::/7`, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`, Teredo `2001::/32`, and the cluster's pod, service and node ranges are refused; **all** resolved addresses must pass; the connection is pinned to the checked address, so DNS rebinding between check and connect cannot swap it;
   - the HTTP client ignores proxy environment (`Proxy: nil`), so an injected `HTTPS_PROXY` (for example a cluster-wide proxy) cannot resolve names behind the pinning;
   - the TLS certificate verifies against system roots for that host;
   - **size caps count decoded bytes:** the fetcher requests `Accept-Encoding: identity` and reads through a limit of cap+1 bytes, so transparent decompression cannot exceed the cap; response header bytes are capped too. Caps per file, per run total, per run file count, and concurrent fetches per run. **Per-run totals and counts are enforced in the api** (the fetcher asks before and reports after each fetch), because per-replica counters do not add up across fetcher replicas. Admission is an **atomic reservation**: before a fetch, one transaction reserves the per-file maximum bytes, one file slot and one concurrency slot against the run's totals; on completion or failure the fetcher reports the actual bytes and the api reconciles (releases the unused part, frees the slot). Parallel fetches therefore cannot jointly pass a check and overshoot a run total. A sweep releases reservations left by a crashed fetcher.
   Control is per URL, not per IP, so a shared IP address does not leak other sites. A single host with many publishers (a code-hosting site, an object-storage host, a documentation-hosting platform, a vendor community forum) is not made safe by this: see Decision 4.
4. **Site lists are admin-managed and named.** An `egress_profiles` table (name, description, host entries). A run can only reference a list by name; no request can send domains. Only admins create or edit lists. Host entries are **normalized at write time and at match time** (lowercase, IDNA A-label, trailing dot stripped). A wildcard `*.base` is refused when `base` is a public suffix (the Public Suffix List, ICANN and private sections, vendored and pinned), so `*.com`, `*.co.uk`, `*.github.io`, `*.cloudfront.net` and `*.amazonaws.com` are rejected. A small built-in list of known multi-publisher hosts (code hosting, object storage, docs hosting, forums) needs an explicit per-entry override to be added, with a warning in the admin API. Profile names and descriptions pass the same terminal-safety check as other admin display strings (`termsafe.Validate`) and are length-capped.
5. **The agent gets a fetch tool, and no general network tool.** A profile-bound run gets a fixed, **named** tool set: `Read`, `Write`, `Edit`, `Grep`, `Glob`, the in-process fetch MCP tool, and `submit_job_result` (PRD #1908). Nothing else: no `Bash`, `WebFetch`, `WebSearch`, `Agent` or `Task`, no forge tools, no memory tools. The agent side **refuses to start** a profile-bound run whose effective tool set differs from that list (fail closed). The api also refuses, server-side, the worker routes that return third-party content (agent memory, forge reads and writes, trace fetches of other runs) for a profile-bound run, so an old or modified agent cannot use them either. File tools are rooted at the run workspace by the existing path guard, which also denies `/run/uzi-secrets`. The fetch tool saves each download into the run workspace under `sources/<sha256>` (never a name from the URL or `Content-Disposition`) and returns its path, final URL, content type, size and sha256; the agent reads it with `Read`, which handles PDFs. The lane sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` in the SDK child's env.
6. **Model endpoint: exact host only.** The lane allows `api.anthropic.com` by exact name through the existing FQDN mechanism (Antrea or OVN), never a wildcard. On 2026-09-29 its addresses were registered to Anthropic, PBC, not a shared CDN. That is a point-in-time observation, not a lasting guarantee: if the hosting changes, the IP-level rule could admit other sites on those addresses. It does not open a content path by itself, because without Bash or another general client the agent cannot originate traffic to them (Decision 5); M8 re-checks the hosting, and the ADR records it as a residual. When PRD #50 lands, the lane drops direct model egress and reaches the model through the api.
7. **Per-run fetch credential.** The api mints an opaque credential when a profile-bound run is claimed (stored as sha256, like join tokens), delivers it in the claim response, and revokes it when the run goes terminal. It lives in the worker's node process (the in-process MCP tool), never in the SDK child's env. The fetcher validates it by calling an api introspection endpoint with the fetcher's own service credential. The **site list is snapshotted onto the run at claim**, and introspection returns that snapshot, so an admin edit does not change a running run and a short introspection cache only delays revocation, never widens a list.
8. **Source log, fail closed.** The fetcher reports every attempt (allowed or refused) to the api: requested URL, final URL, verdict and reason, status, content type, bytes, sha256, time. **The api takes the run from the per-run credential the fetcher forwards**, never from a run id the fetcher supplies, so the fetcher's service credential cannot write rows into another run. If introspection or the log write fails, the fetch is refused, so "every attempt is logged" holds. The api stores it in a `run_fetches` table, readable by the run owner (API and `uzi run fetches <run>`). URL, final URL, content type and reason are site- or agent-controlled: control and bidi characters are rejected or escaped at write time, and the CLI renders them through the same plain-text path as other untrusted fields. PRD #1909 folds the log into job results.
9. **Placement is exclusive, and server-owned.** A profile-bound run can be claimed **only** by a worker the api itself provisioned as a lane worker, and a lane worker claims **only** profile-bound runs. This is a dedicated claim clause in `ClaimRun`, **outside** `fn_worker_can_claim`, `required_capabilities`, `ClearRunRequiredCapabilities` and the `capability_aware` kill-switch, following the Codex and completion-interlock clauses. It keys on two facts: a server-set worker column (hosted, and provisioned into the lane by the api; never a worker self-report), and a protocol capability (working name `isolated_fetch_v1`) proving the worker runs this PRD's agent code. An older agent, a compose worker, a standard or docker worker, or a run with its requirements cleared can never claim a profile-bound run. Lane workers are run-bound (PRD #529), so no file from one run is visible to the next.
10. **Claude only at first.** A profile-bound run is refused for the Codex harness at creation and at claim: Codex's own web search is server-side.
11. **Search is a fetch.** There is no general web search. A vendor's own site-search page on an allowed host is fetched like any other URL.
12. **No forge credential in the lane.** A profile-bound run's claim carries no forge PAT.
13. **Product allowance (job integration, M8).** When PRD #1908's jobs exist, a job may name a site list only if the caller may use it: a user token may use any list, a product token (PRD #1907) only the lists its product is allowed. The allowance is a table here (product, profile). This milestone is also what lifts PRD #1908's 422 on `egress_profile`, so there is never a window where a product token can use a site list without the allowance check.

## Out of scope

- The job kind, the jobs API, and which job types set a site list: PRD #1908.
- Durable storage of downloaded files beyond the run workspace, and results as product artifacts: PRD #1909.
- Product tokens and consent: PRD #1907 and PRD #1910.
- TLS interception (MITM) and URL-path rules. Control is per host, per request.
- Closing #1651 for the existing restricted tier. The fetcher is reusable for that later, but this PRD does not reroute issue runs.
- The docker tier. A profile-bound run never uses docker.
- Compose support for the lane. Compose has no NetworkPolicy, so there is no lane there.
- A web admin page for site lists. The admin API and CLI are enough to start; the page can follow.

## Success criteria

- A profile-bound run can read content only from hosts on its site list, whatever the agent attempts, proven by M9.
- No placement path (kill-switch, cleared requirements, self-reported capability, old agent) puts a profile-bound run outside the lane, proven by M5's tests.
- Every fetch attempt is in the source log with its verdict, or the fetch did not happen.
- A product token can use only the site lists its product is allowed.
- No new image and no workflow change; the lane is off by default and existing tiers are unchanged.

## Risks

- **An Anthropic-side tool that reads the web.** The model could call a server-side tool only if the SDK offers it; the fixed tool set excludes `WebSearch` and `WebFetch`. If a future SDK version adds a server-side web tool that `tools` does not govern, the fail-closed check in M4 must catch it: it asserts the effective tool list, not only the requested one.
- **DNS and the model API as channels.** Both stay reachable from the lane. Abusing either needs code execution in the pod, which the named tool set does not provide. Recorded as residuals in the ADR, not claimed closed.
- **Model host drift.** If the SDK needs another Anthropic host, the run fails loudly in M9; if the model host's addresses move to shared hosting, the IP-level rule admits more addresses without adding a client. Add exact names only, from a real failure, as the existing `allowFQDNs` comment already requires.
- **Vendor file hosts.** Official files often live on a different host than the main site. Lists will need tuning; the source log shows every refusal.
- **Multi-publisher hosts.** An admin who overrides the multi-publisher warning admits every publisher on that host. The override is explicit and documented.
- **Fetcher as an SSRF target.** Mitigated twice: the fetcher's own address checks and pinning, and its NetworkPolicy excluding cluster and private ranges.
- **Credential theft inside the pod.** Without Bash the agent cannot read process memory; the credential is scoped to one run and dies with it.

## Open questions (resolved)

1. Resolved 2026-09-29: default caps are 25 MiB per file, 200 MiB and 100 files per run, 4 concurrent fetches per run (admin-configurable).
2. Resolved 2026-09-29: the lane namespace is `uzi-workers-isolated`, at the same restricted Pod Security level as the standard tier.

## Decision Log

- 2026-09-29: Enforcement point is a fetch service, not a CONNECT proxy, a service mesh, or CNI rules. CNI rules are IP-level; a proxy or mesh still leaves a general network path and handles per-run lists poorly; a fetch service is the only reachable content path, with per-URL checks and an exact source log.
- 2026-09-29: The fetcher is a separate Deployment built into the api image. Keeps untrusted parsing away from the api's secrets without a new image.
- 2026-09-29: No Bash in profile-bound runs. Bash is a general network client, and the lane's model host is reachable, so without this the model API itself would be a path to other content.
- 2026-09-29: Review round (buddy review plus a security review). Changes: placement moved from `required_capabilities` to a dedicated server-owned claim clause outside `fn_worker_can_claim`, `ClearRunRequiredCapabilities` and the kill-switch, keyed on an api-set lane marker plus a protocol capability, because the kill-switch, the "run without it" action and self-reported capabilities each defeated the original design; public-suffix wildcard rejection and host normalization; an explicit named tool set plus server-side refusal of third-party-content worker routes; request shape pinned (GET, URL only, no userinfo, `Proxy: nil`, all addresses checked including IPv4-mapped, NAT64, 6to4 and Teredo); decoded-byte caps with identity encoding and api-side per-run totals; source log keyed from the forwarded credential and fail closed; write-time character checks; workspace-rooted file tools and sha256 file names; run-bound lane workers; site-list snapshot at claim; TLS on both fetcher legs; lane policy without `allowWebService`/`extraEgress`; no forge PAT in the lane; the fetcher's own NetworkPolicy excludes cluster and private ranges in both families and is tested live; the model-host ownership check is recorded as point-in-time, and DNS and the model API are named residuals rather than "nowhere else to go". Cross-PRD: this PRD gains the job-integration milestone (M8) that lifts PRD #1908's `egress_profile` 422 and owns the product-to-site-list allowance, so no product token ever uses a list unchecked; live acceptance is part of completion. The web admin page for site lists was dropped from M1 (API and CLI suffice to start).
