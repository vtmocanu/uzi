## Problem

Cutting a release is one irreversible step. A `vX.Y.Z` tag publishes the five images and the chart to GHCR, creates a GitHub Release marked latest, publishes the Homebrew formula (`brew.yml`) and, because the deployment's ArgoCD Application tracks the chart with a semver range, rolls the running instance within minutes. There is no way to run a build for a day before it becomes *the* release: the first real exercise of a version is also its publication to every stable-only surface (Homebrew users, the in-app update check, the Release page).

Today's ceremony (`release-cut.sh` then tag) is fine as mechanics; what is missing is a channel between "green on main" and "stable", and a way to promote what was actually run rather than whatever main has moved on to.

## Solution

A **release train with a prerelease channel**:

- **RC by default.** `release-cut X.Y.Z` cuts `vX.Y.Z-rc.1`. The tag publishes images and chart at `X.Y.Z-rc.1` exactly as a stable tag does, creates a GitHub Release flagged *pre-release* (never latest), and does **not** publish the Homebrew formula.
- **The deployment dogfoods the candidate.** Its ArgoCD Application tracks `0.*-0`, a range that admits `0.x` prereleases and still excludes `1.0.0` and `1.0.0-rc.1` (verified below), so the instance rolls each RC as it publishes. Stable-only consumers (Homebrew, `releases/latest`, the in-app update check) keep tracking stable and never see an RC.
- **Lockstep promotion, from the tested commit.** The next `release-cut Y.Z.W` promotes the in-flight RC to stable *and* cuts the next RC in one command. Stable `vX.Y.Z` is built from the RC's own commit on a throwaway release branch (Chart.yaml version and the worker pin are the only edits), so what was run is what ships; main, which has moved on, becomes `vY.Z.W-rc.1`. The script refuses to promote silently: with an RC in flight it prints the facts (which RC, live since when, how many shipping merges since) and requires an explicit verb, and the `uzi-release` skill puts that question to the user.
- **One changelog section per stable version, opened at the first RC.** The first RC of `X.Y.Z` folds `[Unreleased]` into `## [X.Y.Z] - <date>`; later RCs of the same version append to that section; promotion refreshes the date. Every gate finds its section by stripping the prerelease suffix, so an RC's Release notes are the real section and promotion needs no changelog surgery.

### Already prerelease-aware, unchanged by this PRD

- **The in-app update check cannot surface an RC.** Only `api` talks to GitHub, at the compile-time constant `/repos/vtmocanu/uzi/releases/latest` (`api/internal/releasecheck/client.go:23`), which GitHub serves as the newest non-prerelease, non-draft Release. Web and the CLI render the server booleans only (`api/cmd/uzi/version.go:165`; ADR-836). `derive.go` compares with `golang.org/x/mod/semver` (`semverNewer`, `:97-104`; `UpdateAvailable` `:32-33`; `FarBehind` `:44-56`), which orders prereleases per spec: a deployment on `0.84.0-rc.1` against latest `0.83.0` derives no update; one still on `0.83.0-rc.2` when `0.83.0` is promoted derives an update, correct and transient (the same train cut rolls it to `0.84.0-rc.1`). **No test pins a prerelease running version** (`derive_test.go`: `TestUpdateAvailable :13`, `TestFarBehind :42`, `TestSecurity :76`, none with a `-` version); M5 adds them, since an RC running version becomes the routine state.
- **`brew.yml` already refuses a prerelease, by failing.** Trigger `tags: ["v*"]` plus `workflow_dispatch` (`:34-40`); the Validate step's regex is strict `^v(0|[1-9][0-9]*)\.(...)\.(...)$` (`:66-72`) and exits 1 on `v0.83.0-rc.1` with `refusing to publish`. So the formula can never point at an RC, but the run goes red, and `release-watch.sh` (which watches `release.yml` **and** `brew.yml` to green, `:1-30`) would report a failed publish on every RC. The fix is "do not run", not "fail" (M4).
- **`changelog-links.sh` only links stable sections.** The footer regenerator matches `^## \[[0-9]+\.[0-9]+\.[0-9]+\]` (`:96`) and writes `[Unreleased]: .../compare/v<newest>...HEAD` (`:109`) and `[X.Y.Z]: .../compare/v<prev>...v<X.Y.Z>` (`:119`). Under D3 a section is always a stable number, so this script needs no change; the `[X.Y.Z]` compare link exists from the first RC and resolves once `vX.Y.Z` is pushed (D3 accepts the dangling window).
- **Worker upgrade health is a semver ordering that keeps `-rc.N` significant.** `UZI_WORKER_IMAGE_TAG` is "the release tag of the agent image to run" (`controller/internal/config/config.go:321`; `controller/internal/protocol/protocol.go:126`); the api classifies a worker `up_to_date | outdated | unknown` (`api/internal/apitypes/worker.go:63`) in `classifyByVersion` (`api/internal/workersvc/upgrade.go:117-145`): `semver.Compare(normSemver(reported), normSemver(target))`, ahead or equal is `up_to_date`, behind is `outdated`. SemVer precedence ignores `+build` and orders `X.Y.Z-rc.N < X.Y.Z`, so a worker running the RC image the chart pins compares equal (`up_to_date`), while a worker running an RC image against a *stable* pin of the same base compares behind (`outdated`); that asymmetry is what D11 rests on. (The `split_part(..., '+', 1)` in `api/internal/store/worker_roll_health.sql.go:213-214` is the roll-health `upgrading_since` guard, not this classification.)
- **Rebuilds are reproducible enough that promotion may rebuild.** Every base image is digest-pinned (`api/Dockerfile:4,56`, `web/Dockerfile:11,55`, `controller/Dockerfile:8,24`), Go builds carry `-buildvcs=false -s -w`, and the promote commit changes no source. The only intended differences between the RC image and the stable image are the ldflags stamps (`api/Dockerfile:53`: `main.version`, `main.builtAt`, counts). This is why D6 rebuilds instead of retagging.
- **No prerelease or scratch tag exists today.** `git tag -l` minus `v[0-9]+.[0-9]+.[0-9]+` is empty; the highest tag is `v0.82.0`. The tag-listing logic in M1/M2 starts from a clean slate.
- **`release.yml` reuses the previous agent image by digest when the runtime surface is unchanged, and this tolerates prereleases as is.** The `decide` step (`:374-405`) takes `PREV` as the newest `v*` tag by git version sort excluding the tag being built, diffs the autobump's `AGENT_PATHS` since it, and on no change re-tags `PREV`'s image **by manifest digest** as `:VERSION` (skipping the build; falls back to a build when the previous image is absent). Any previous tag, RC or stable, is a valid diff base, so an RC above or below its stable in git's sort changes nothing here. It matters for D11: a promote tag's `:X.Y.Z` agent image is normally the RC's bytes, whose baked `UZI_AGENT_VERSION` (`agent/templates/base/Dockerfile:443-444`, reported by the worker from `agent/src/config.ts:256`) still says `X.Y.Z-rc.N`.
- **`scripts/worker-tag-autobump.sh` needs no change.** It reads the pin (`read_pin`), resolves `refs/tags/v<pin>` (an RC pin resolves like any other), diffs the runtime surface since it and bumps the pin to the version being cut only when that surface changed; otherwise the pin, and the fleet, stay put (ADR-0422). Under the train the pin can legitimately read `0.83.0-rc.2` inside the stable `0.83.0` chart: that names the exact worker image that was tested, and D11 explains why it must not be rewritten.

### Semver range for the GitOps side (measured, not assumed)

Masterminds/semver v3 is the constraint engine ArgoCD uses for a Helm `targetRevision` range. Measured with a scratch Go program against **v3.3.0, v3.4.0 and v3.5.0** (identical results):

| constraint | `0.83.0-rc.1` | `0.83.0` | `1.0.0-rc.1` | `1.0.0` |
|---|---|---|---|---|
| `0.*` (today) | false | true | false | false |
| **`0.*-0`** | **true** | true | **false** | **false** |
| `0.x.x-0` | true | true | false | false |
| `>= 0.0.0-0, < 1.0.0` | true | true | **true** (leaks) | false |
| `>= 0.0.0-0` | true | true | true | true |

`0.*-0` is the constraint: it admits `0.x` prereleases and keeps a future major, and its RCs, a deliberate human change. The explicit-range spelling leaks `1.0.0-rc.1` and is rejected (D8). Ordering: `0.84.0-rc.1 > 0.83.0 > 0.83.0-rc.N`, so after a train cut that publishes both `0.83.0` and `0.84.0-rc.1` the range resolves to the new RC.

## Design

### D1: RC by default; stable is a promotion, or an explicit escape

`release-cut <X.Y.Z>` names the version a **candidate** is being cut for. Given the tags (`git fetch --tags` first), with `S` = the highest stable tag and `B-rc.N` = the *in-flight* RC: the highest-versioned RC whose base has no stable tag. An abandoned base (`--skip-promote`) leaves lower RC tags with no stable forever; they are ignored, never an error.

**Tag selection never uses a mixed version sort.** Git's `version:refname` orders `-rc.N` against its base by string length unless `versionsort.suffix` is configured, so the scripts (a) filter to stable tags (no `-`) before sorting for `S` and `PREV`, and (b) find the in-flight RC by grouping `v*-rc.*` tags per base and comparing `N` numerically (`rc.10 > rc.9`). The fixture asserts both.

| state | invocation | result |
|---|---|---|
| no RC in flight | `release-cut X.Y.Z` (`X.Y.Z > S`) | `vX.Y.Z-rc.1` on main: fold `[Unreleased]` into `## [X.Y.Z]` (D3), `Chart.yaml` version and appVersion to `X.Y.Z-rc.1` |
| `B-rc.N` in flight | `release-cut B` | `vB-rc.(N+1)` on main: the previous candidate was not good enough, keep testing `B`. Requires `[Unreleased]` to be **empty** (D3: re-spin entries are written into the open `## [B]` section); a non-empty `[Unreleased]` is refused with the entries printed |
| `B-rc.N` in flight | `release-cut X.Y.Z` (`X.Y.Z > B`), no verb | **refuse**, exit 3, print the facts: `B-rc.N`, its tag date, shipping first-parent merges since it (the oracle's `is_shipping` classification), whether `[Unreleased]` is empty |
| `B-rc.N` in flight | `... --promote` | promote `B` from `vB-rc.N` (D5), then `vX.Y.Z-rc.1` on main. If nothing shipped since `vB-rc.N` and `[Unreleased]` is empty, promote only and say so; main's `Chart.yaml` then stays at `B-rc.N` until the next cut, which is harmless (nothing is tagged on main) |
| `B-rc.N` in flight | `... --skip-promote` | abandon `B`: rename `## [B]` to `## [X.Y.Z]` **and fold the current `[Unreleased]` into it** (the merges since `vB-rc.N` ship in `X.Y.Z` and the oracle's window is `S..HEAD`), cut `vX.Y.Z-rc.1`. `B`'s RC tags and pre-release Releases stay as history |
| no RC in flight | `release-cut X.Y.Z --stable` | today's behaviour: a plain `vX.Y.Z` on main, from main's tip. Escape for a docs-only release. Refused while an RC is in flight |
| any | `--promote --no-commit` | rejected: the promote half tags unconditionally and has no half-state. `--no-commit` applies to the main half only |

**Hotfixing a promoted stable is not a `release-cut` verb in this PRD.** `--stable` cuts from main's tip and would ship the next version's features under a patch number. A patch release is built like a promotion, by hand: worktree at `vB`, cherry-pick the fix commits (already merged to main), `## [B.1]` citing them, `Chart.yaml` to `B.1`, tag `vB.1`, push. M6 documents the procedure; a `--hotfix` verb is a follow-up issue once the train has run a few cycles. D4 already handles the resulting tag (its branch shares main's merge base, the RC commit), and the fixture asserts it.

The script never asks a question (D7). It is the `uzi-release` skill that, on the refusal, tells the user the printed facts and asks: promote (the default), next RC, or skip.

### D2: The prerelease form is `X.Y.Z-rc.N`, `N` from 1, and nothing else

One shape, so every gate can strip it with `${v%%-*}` and every listing can classify with "contains `-`". `assert-version` already accepts the general SemVer prerelease grammar; the scripts here are stricter on purpose and reject any other suffix.

### D3: One changelog section per stable version, opened by the first RC, appended to by later RCs, dated at promotion

- `release-cut X.Y.Z` for `rc.1` folds a non-empty `[Unreleased]` into `## [X.Y.Z] - <today>` exactly as today's fold does, and leaves an empty `[Unreleased]` on top. `--changelog-file` keeps its meaning (a drafted section replaces the fold).
- `rc.(N+1)` requires `## [X.Y.Z]` to exist and `[Unreleased]` to be empty. The section is *open* until promotion: the entries for a re-spin are written directly into it (under the right `###` subsection) before running `release-cut B`, exactly as entries are written in the release cut today (`assert-changelog-covers-release.sh` header). The oracle then demands every shipping merge since `S` be cited there. Rejected: an automatic subsection-aware append from `[Unreleased]`; it is the one transform nothing else in the toolchain does, and a malformed merge (a duplicated `### Added`) is invisible to both the oracle and `changelog-links --check`.
- Promotion (D5) rewrites the heading date to the promote date on both the release branch and main, so the two copies of the section stay byte-identical.
- The oracle and `changelog-section.sh` locate the section by `${VERSION%%-*}`. An RC's Release notes are therefore the real section, titled `vX.Y.Z-rc.N`; the stable Release reuses it, titled `vX.Y.Z` plus the optional marker.
- Rejected: pointing RC gates and notes at `[Unreleased]` and folding only at promotion. It works for `rc.1` but promotion then has to split `[Unreleased]` into "what was in the RC" and "what landed after", a line-set subtraction that breaks the moment an entry is reworded, and it leaves the ledger without a section for a version whose images and Release already exist.

### D4: The coverage window is "since the highest lower stable tag by version", never `git describe`

`PREV` = the highest tag matching `v[0-9]+.[0-9]+.[0-9]+` (no `-`) whose version is lower than `${VERSION%%-*}`: the stable tags are filtered **first** (so git's prerelease ordering never enters), then sorted; empty means "first release", as today. This is right in all five cases: `rc.1` of `X.Y.Z` (since `S`), `rc.2` (still since `S`, the section must cover the whole cycle), the stable `X.Y.Z` on its release branch (since `S`; `X.Y.Z` itself is excluded by "lower than"), the next RC on main (since `X.Y.Z`, even though that tag is not an ancestor of main: `git log --first-parent vX.Y.Z..HEAD` walks main and stops at the merge base, the RC commit, which is exactly "what landed after the RC"), and the next RC after a patch `vX.Y.Z-patch` cut off `vX.Y.Z` (same merge base, same window; the cherry-picked fixes' originals on main are in it and ship in that RC, correctly). `release-cut` computes `PREV` the same way and drops its `<prev-tag>` positional (an optional `--prev-tag` override remains for a repair). The oracle keeps its file-not-pipe discipline; none of this adds a pipe into `grep -q`.

### D5: Promotion builds stable from the RC commit on a throwaway release branch

Given `vB-rc.N` at commit `X'`:

1. Refuse if a `release/B` branch or worktree already exists (a previous aborted promotion; the lead removes it deliberately). `git worktree add <tmp> -b release/B vB-rc.N`. On it: `Chart.yaml` version and appVersion to `B`; `## [B]` heading date to today; `worker-tag-autobump.sh B` unchanged (the pin stays at the RC's tag when the surface is unchanged, D11); `changelog-links.sh`; commit `chore(release): vB (promotes vB-rc.N)`. Assert `git diff --name-only vB-rc.N..HEAD` is a subset of `{CHANGELOG.md, deploy/chart/Chart.yaml, deploy/chart/values.yaml, scripts/assert-worker-tag-decoupled.sh}`; anything else removes the worktree and branch and aborts **before** any tag exists. Only then the annotated tag `vB`, created locally by the script.
2. The worktree and the `release/B` branch are removed after tagging (and on any abort). The tag carries the commit; `git push origin vB` pushes it. The branch is never pushed and stable tags are **not** ancestors of main (D4 handles it). This is the Kubernetes shape (release branches derive from main, main never merges them back), not git-flow's merge-back; a `-s ours` merge-back was considered and dropped as an extra commit that buys nothing once D4 stops using ancestry. Repair: a pushed `v*` tag is immutable under the ruleset, so a botched pushed RC is followed by `rc.(N+1)` and a botched pushed stable by a patch release (the hotfix procedure in D1); a local-only mistake is `git tag -d` plus a rerun.
3. The promote commit gets no `ci.yml` run (`ci.yml` runs on PRs and `main`). Accepted because `X'` was green on main, the diff allowlist proves no source changed, `release.yml` re-runs `assert-version` and `assert-changelog` on the tag, and `kind-smoke.yml` runs on every `v*` tag.
4. Then on main: fold `[Unreleased]` into `## [X.Y.Z]` (D3), refresh the `## [B]` date, `Chart.yaml` to `X.Y.Z-rc.1`, autobump, links, commit `chore(release): vX.Y.Z-rc.1`, verify with the oracle (`PREV` is the local `vB`, so it must be created first) and `changelog-links --check`. As today the RC tag on main is applied by the lead only after `ci.yml` is green on the release commit.
5. **Push order is stable tag, then main, then the RC tag.** The RC tag's `assert-changelog` job computes `PREV` from the tags it can see; `vB` must already be on the remote. The script prints the three push lines in that order; the skill repeats it. The wrong order fails loudly in CI (an uncited-merges FAIL), not silently.

### D6: Promotion rebuilds; artifact retagging is deferred

Retagging the RC images as stable (`crane tag`, same digest, cosign referrers ride along) would still need the chart re-packaged (`version`/`appVersion` are inside the tarball and pods follow `appVersion`), a commit for the tag under Model B, and the ldflags-stamped binaries would report `-rc.N` in `/api/version`, the TUI and the footer. It removes the rebuild, not the branch, and does not avoid the deployment re-roll either (the pod image tag string changes). With digest-pinned bases and metadata-only promote commits, the rebuild is equivalent in everything but the intended stamps. Revisit only for digest-level provenance or if builds stop being cheap.

### D7: Non-interactive scripts, verbs over prompts

`release-cut.sh` is driven by the lead in-session; a blocking `read` is the wrong shape for an agent and a trap for a human on a slow terminal. State is derived from tags at every run (no state file). Refusals exit 3 with the facts; the skill owns the conversation.

### D8: The deployment opts in with `0.*-0`, described generically

`deploy/README.md` gains: a deployment that should run candidates tracks `0.*-0`; one that should only ever see stable keeps `0.*`. The maintainer flips the real Application out of tree. With no stable environment beside it, the single instance is permanently on the candidate train; rollback is `rc.(N+1)`, or a temporary exact pin to the last stable. Publishing both tags of a train cut within minutes can roll the instance to `B` and then to `X.Y.Z-rc.1` (identical code as `vB-rc.N` plus stamps); accepted as a harmless transient.

### D9: Stable-only surfaces are protected by construction, and pinned by tests

`releases/latest`, the `--prerelease` flag, the `x/mod/semver` compare and the brew trigger negation together mean no user-facing surface (Homebrew, the Release page's Latest badge, the sidebar pip, the admin Updates card, `uzi version`) can name an RC. M5 pins the compare with prerelease cases; M7 observes the rest live.

### D10: `specs/human.md` gains the requirement

"Releases are cut as release candidates by default; a stable release is promoted from the candidate's own commit; surfaces meant for stable users (the Homebrew formula, the GitHub Release marked latest, the in-app update check) never surface a candidate." Approved by the user in the session that produced this PRD.

### D11: The worker pin is never rewritten on a stable cut

An earlier draft normalized a `B-rc.N` pin to `B` when promoting, so a stable chart would not name an RC worker image. That is a latent cry-wolf bug. A worker reports the version baked into its image at build time (`UZI_AGENT_VERSION`, `agent/templates/base/Dockerfile:443-444`, read at `agent/src/config.ts:256`), and `release.yml` builds the promote tag's `agent-*:B` images by re-tagging the RC's digest when the runtime surface is unchanged (`:374-405`), so `:B` would still report `B-rc.N`. The api classifies upgrade health by semver ordering (`classifyByVersion`, `api/internal/workersvc/upgrade.go:117-145`), and `B-rc.N < B`, so a fleet pinned to `B` would sit `outdated` forever, the cry-wolf failure the roll-health code exists to avoid. Forcing a rebuild instead would roll the fleet on every promotion, reintroducing the churn ADR-0422 removed. So: the pin is a concrete image tag that moves only when the runtime surface changes, RC or stable alike; `0.83.0-rc.2` inside the `0.83.0` chart is correct and names the tested image. `uzi worker list` shows it as such.

## Risks and mitigations

- **A strict `X.Y.Z` check somewhere reddens `main` on the first RC commit.** M1's sweep enumerates every version regex before M2 lands; the known ones are listed under *Needs changing*. `helm lint` accepts a SemVer 2 prerelease chart version; OCI and Docker tags accept `-` and `.`.
- **The stable tag is not on `main`.** Tooling that assumes `git describe` finds the last release breaks; the sweep also covers `describe` uses (today: only the oracle). GitHub's Release page shows the tag's own commit; the compare footer `v0.82.0...v0.83.0` is correct since the RC commit is on main.
- **The promote commit has no `ci.yml` run.** Bounded by the diff allowlist, `release.yml`'s two asserts and `kind-smoke.yml` on the tag (D5.3).
- **Pushing the RC tag before the stable tag.** The RC's oracle then computes `PREV` from the previous stable and fails on uncited merges: loud. The script and skill both state the order.
- **A stable chart pinning an RC worker image.** By design (D11); rewriting the pin is the bug. SC8 checks the fleet stays `up_to_date` through a promotion.
- **Git's version sort puts `-rc.N` above its base.** Never sorted mixed (D1); the fixture pins `rc.10 > rc.9` and stable-vs-RC selection.
- **Lockstep means one bug blocks both the promotion and the next RC at release time.** The fixture drives every verb offline before the first live cycle; the promote half aborts before any tag exists; `--no-commit` leaves the main half reviewable.
- **The single instance runs candidates only.** Accepted by the user (no second namespace). Rollback is `rc.(N+1)` or a temporary exact pin.
- **`--skip-promote` leaves RC tags and a Release for a version that never went stable.** Documented; the section is renamed and folded, the pre-release Releases stay as history.
