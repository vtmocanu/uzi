## Problem

The activity pane (`web/src/components/ActivityFeed.tsx`, mounted at `RunView.tsx:394`) has three distinct UX failures, all reported by the user:

1. **Scroll spam.** `useRunStream` commits once per websocket frame (`useRunStream.ts:25`), so `messages.length` increments one message at a time; the follow-scroll append effect (`useFollowScroll.ts:65`) re-fires on every increment and hard-jumps the viewport with `el.scrollTop = el.scrollHeight` (`useFollowScroll.ts:41`, deliberately instant, never smooth, no batching). A live agent burst (a `tool_use`, its `tool_result`, interleaved `text`/`thinking`, per-tool `status`) arrives as many frames in quick succession, so the pane visibly jerks to the bottom on every one. There is no way to watch the run without being dragged along.

2. **No real "who's alive."** "Active" is computed as `runningLive ? groups[groups.length - 1]?.agent` (`ActivityFeed.tsx:181`) — i.e. only the agent that authored the *newest* message, and only while `status === "running"`. A stalled agent still reads "active"; every other agent reads "idle" the instant a later one speaks; there is no `working` / `waiting` / `done` distinction and nothing reflects that the whole run is blocked on a human gate or a dead worker. You cannot glance at the pane and see the crew's state.

3. **Follow-ups vanish; no delivery signal.** A follow-up is a single insert into `run_user_inputs` (`CreateRunInput`, `runtime.sql:755`, via `SubmitInput`, `workersvc/service.go:1731`) — it is **never** written to `run_messages`, so nothing echoes it in the UI. The `FollowUpComposer` (`RunView.tsx:551`) clears the textarea on send and shows the user nothing: no record that the message exists, and no indication of whether the worker has picked it up. The worker consumes inputs FIFO via `ConsumeInputs` (`workersvc/service.go:1250`), which stamps `consumed_at` — a perfect "the agent has it" signal that the UI never reads.

## Solution Overview

Rebuild the pane around the crew, not the scroll, and give the steering channel a visible queue.

- **Crew roster strip** at the pane top: one compact chip per agent role with a state dot — `working` / `waiting` / `idle` / `done` (plus a `stalled` sub-state) — so "who's alive" reads at a glance without opening a single log. Click a chip to jump to that agent.
- **Logs collapse by default.** Each agent is an accordion, closed by default, its header carrying a live one-liner ("running `go test ./...`") that updates *in place* (no scroll) and a `+N` unseen-message pill. Expand only what you care about.
- **Follow is opt-in and contained.** A `Follow live` toggle, **off by default**, replaces the global auto-jump; when on, it tails only the *expanded* agent's own bounded-scroll region. The whole-pane yank is gone.
- **Steer queue with delivery status.** The `FollowUpComposer` grows a queue: each follow-up shows immediately as **Queued**, then flips to **Delivered** when the worker consumes it (`consumed_at`), and to **Not delivered — run finished** if the run goes terminal first. Read from a small DTO over `run_user_inputs`; live via a data-less `input` WS frame that mirrors the existing `health` frame.
- **No migration; almost no backend.** The crew states are derived **client-side** from the existing message stream + `run.health` + `run.status`. The only server work is one owner-scoped read endpoint (reusing an existing query) and one data-less WS frame. There is **no schema change**.
- **CLI parity in the same MR** (CLAUDE.md "second consumer" rule): `uzi run inputs <run-id>` lists the steer queue with delivery status.

## Design Decisions

1. **The crew roster derives every state CLIENT-SIDE from data the pane already has — no new backend, no per-agent heartbeat.** The pane already receives the full `RunMessage[]` (each carries `agent`, `created_at`, `kind`, `seq`; `api.ts:986`), the `Run` (with `status` and `health`/`health_reason`, `api.ts:684`/`:671`), and `connected`. Everything the roster needs is a pure function of those. Grouping already exists (`groupByAgent`, `ActivityFeed.tsx:41`, keyed `m.agent ?? "lead"`); the roster adds a per-agent aggregate (last-activity time, message count, last kind) and a state function. Rejected alternative: surfacing the worker's raw `last_heartbeat_at` (`Worker.last_heartbeat_at`, `api.ts:611`) into the pane — **`run.health` already is that signal**, server-derived by PRD #47's sweeper (`waiting_worker` = no live worker, `stalled` = worker went quiet), and already pushed to this client over the `health` WS frame (`hub.go:112`). Re-plumbing the heartbeat would duplicate a derivation that already reaches the browser. The pane **maps `run.health`**, it does not re-derive liveness.

2. **The per-agent state ladder — and an honest boundary on what is derivable in v1.** For a **live** run (`status ∈ {claimed, running}`):
   - **active speaker** = the agent of the newest message.
   - `working` — the active speaker, when `run.health ∈ {ok, looping, approval_idle→n/a}` and its last activity is recent (< `STALE_MS`, default 45s). The pulsing green dot; the only thing that animates when logs are closed.
   - `stalled` — the active speaker when `run.health ∈ {stalled, slow}`. A working sub-variant (amber), so a frozen agent no longer masquerades as "active" (the exact bug in Problem 2).
   - `waiting` — **all** agents when `run.status === "awaiting_approval"` (the whole run is blocked on the human gate), **or** `run.health === "waiting_worker"` (blocked on a worker); otherwise a non-active agent whose last message is recent (< `STALE_MS`), read as "recently handed off."
   - `idle` — a non-active agent silent for ≥ `STALE_MS`.
   - **done** — on a **terminal** run (`completed`/`failed`/`cancelled`), every agent is `done`; there is no "idle" once the run is over.

   **Honesty boundary (fable, note this):** the split between `waiting` (handed off, blocked-on-lead) and `idle` (just quiet) is a **recency heuristic** in v1, because the Agent SDK emits no explicit handoff / subagent-boundary event — `agentOf` only reads `subagent_type` off each message (`sdk-messages.ts:28`). `working`/`stalled`/`done` and the gate/worker `waiting` cases are exact (driven by `status`/`health`); the recency-based `waiting`↔`idle` split is the one approximation. A precise handoff marker (a `handoff` control message when a subagent returns to lead) is a **named future refinement**, out of scope here. The mock's "data honesty" footer states this; the PRD is the source of truth for it.

3. **Collapse-by-default + opt-in Follow REPLACES the global auto-scroll — a deliberate behavior change, scoped per-agent.** Today `useFollowScroll(messages.length)` owns one scroll container for the whole feed and auto-jumps it (`ActivityFeed.tsx:147`, `useFollowScroll.ts`). v2 inverts the default: the outer pane does **not** auto-scroll at all; each *expanded* agent body is its own bounded (`max-height`) scroll region, and the `Follow live` toggle (default **off**) tails only expanded agents. This is a genuine change to existing behavior (CLAUDE.md: confirm before changing functionality) — it is the explicit user request, recorded here as authorized. `useFollowScroll` is refactored to operate per-agent-body (or replaced by a small per-body tail hook); the "N new ↓" paused-follow affordance (`ActivityFeed.tsx:242`) is repurposed to the crew's `+N` unseen pill. **Kept as-is:** the cap-and-expand for very long runs (`CAP_TRIGGER = 1000` / `CAP_VISIBLE = 500`, `ActivityFeed.tsx:115`), the per-tool-result expanders and Bash clamp (`RunEvent.tsx`), the `role="log"` a11y wiring, and the `prefers-reduced-motion` neutralization of the pulse/spin (`index.css:195`) — the crew dot's pulse must honor it.

4. **The steer queue is a DTO over `run_user_inputs`, NOT a `run_message` — this sidesteps the gapless-`seq` allocation race.** The obvious "just echo the follow-up into the feed" is a trap: `run_messages` carries a **gapless per-run `seq`** (`InsertRunMessage`, `runtime.sql:577`) and the **worker is the sole seq allocator** — it computes the next seq and streams messages; the client dedups/orders/keys on it (`runStream.ts`). If the API injected a `user_message` with a server-chosen seq while the worker concurrently emitted its own next seq, they would collide or gap, corrupting the one invariant the whole live stream rests on. So the follow-up is **not** a message. Instead:
   - The queue is read from the existing table via a DTO. `ListRunInputsForRun` **already exists** (`judge.sql:37`, `SELECT id, run_id, kind, body, consumed_at, created_at FROM run_user_inputs`); the endpoint filters it to `kind='follow_up'`, owner-scoped.
   - Delivery status is `consumed_at`: **NULL → Queued**, **set → Delivered**. No new column, **no migration**.
   - This is the same architectural move the health frame makes: a fact that lives authoritatively in a table, surfaced by re-read rather than pushed as stream payload.

5. **Delivery goes live via a NEW data-less `input` WS frame, mirroring `PublishHealth` exactly.** `consumed_at` is stamped inside `ConsumeInputs` (`workersvc/service.go:1250`, worker-polled). After a successful consume that included ≥1 `follow_up`, the service calls a new `Hub.PublishInput(runID)` that broadcasts `Event{Type: "input"}` carrying **no data** — the browser re-reads `GET /runs/{id}/inputs`, precisely how `health`/`state` frames work ("carries NO authoritative data — the browser re-reads", `hub.go:112`). `useRunStream`'s frame switch (`runStream.ts:87`) gains an `input` case → refetch inputs. No new socket, no change to the message seq stream, and Slack's no-op `PublishMessage` shape is untouched. The `Event` struct (`hub.go:32`) already tolerates a bare `type`.

6. **"Delivered" means the worker HAS the input for its next turn — not that it has acted on it. The crash-drop is a documented, pre-existing limitation.** `ConsumeInputs`'s own comment states delivery marks the input consumed with no separate ack, so a worker crash right after the GET drops that input, "an accepted MVP trade-off … the user can re-send" (`service.go:1247`). v2 does not change that contract; it makes it **visible**. Semantics shown to the user: **Delivered = handed to the worker for its next turn.** Whether it was *acted upon* is already visible in the agent's subsequent messages. If a consumed-but-dropped input is never acted on, the run's own `health` (`stalled`) surfaces it and the user re-sends — the same recovery the code already assumes, now with a queue to see it in. Stated as a Risk.

7. **Terminal-before-consume → "Not delivered — run finished," derived client-side.** A follow-up submitted moments before the run reaches a terminal status is never consumed (`consumed_at` stays NULL) and never will be. The composer derives the chip from `(consumed_at, run.status)`: NULL + non-terminal → **Queued**; NULL + terminal → **Not delivered — run finished** (distinct copy, not a stuck "Queued"); set → **Delivered**. No server state needed; `terminal` is already known to the view (`RunView.tsx`).

8. **`GET /runs/{id}/inputs` is `RequireUser`, owner-only — matching the write it pairs with.** The follow-up **write** (`CreateRunInput`) is mounted on `RequireUser` and is owner-only (`SubmitInput(r.Context(), user.ID, …)`, `workers.go:541`; the same posture PRD #94 Decision 5 documents and `TestCreateRunInputIsOwnerOnly` guards). The **read** matches: `RequireUser`, run resolved owner-scoped (owner or 404), `kind='follow_up'` only. `RequireUser` (not cookie-only `RequireAuth`) is what lets `uzi run inputs` read it from a CLI token (Decision 10), and owner-only preserves the read-only ceiling — a `uza_` `admin_ro` token keeps `IsAdmin`, so an owner-or-admin read would leak another user's steer text; owner-only closes it. No token spend, no forge write.

9. **The pane redesign is FRONTEND-ONLY; the delivery feature is the only backend touch. Clean split for parallel work.** Problem 1 (scroll) and Problem 2 (crew) are pure `web/` refactors of `ActivityFeed.tsx` + the follow-scroll hook, consuming data already on the wire (Decision 1). Problem 3 (delivery) is: one read endpoint (reusing `ListRunInputsForRun`), one `Hub.PublishInput` call site in `ConsumeInputs`, one `useRunStream` frame case, and the composer's queue UI. The two tracks touch disjoint files, so M2 (crew/scroll web) and M3 (delivery, thin server + composer) can run in parallel after the shared types land.

10. **CLI parity: `uzi run inputs <run-id>`.** The CLI already sends follow-ups (`uzi run follow-up`, `run.go:263`; `kindFollowUp`, `run.go:23`) but cannot see them afterward. Add `uzi run inputs <run-id>` → `GET /runs/{id}/inputs`, printing each follow-up with its delivery state (`queued`/`delivered`) and relative time, `--json` for the raw DTO. Owner-scoped read works from a `uzc_` or read-only `uza_` token (Decision 8). This is the CLAUDE.md "new functionality ⇒ check the CLI" obligation discharged in the same MR.

**Interactions (for completeness):** **Chat runs** (`kind='chat'`) use a different message path (`PostChatMessage`, `chat.go`) and their own composer, not `run_user_inputs` — the steer queue is scoped to issue/CI-fix runs and is simply absent for chat, unchanged. **`approve_plan` / `cancel` / `reject_plan`** also flow through `run_user_inputs` but own their own UI (plan panel, Stop button); the queue renders **only `kind='follow_up'`**, so those are untouched. **Slack** steering (`slacksvc/replier.go:177` submits `follow_up`) benefits for free — the same rows, now visible in the web queue. **Hosted workers** need no change: the worker already stamps `consumed_at` via the endpoint it already calls; only the API's post-consume broadcast is new. **The board cache / forge** are untouched (no forge write anywhere in this PRD).

## Success Criteria

- Watching a live run, the pane **no longer auto-scrolls** on incoming frames; a burst of tool activity updates the crew one-liner and `+N` pill **in place** without moving the viewport. Turning `Follow live` on tails only the agent(s) the user has expanded.
- The crew strip shows, at a glance and without opening any log, which agents are `working` (pulsing), `stalled`, `waiting` (at a gate / on a worker / just handed off), `idle`, or `done` — and a stalled agent reads `stalled`, never a frozen "active" (the Problem-2 bug).
- Sending a follow-up shows it **immediately** in the steer queue as **Queued**; it flips to **Delivered** the moment the worker consumes it (driven by `consumed_at` via the `input` frame), and to **Not delivered — run finished** if the run reaches a terminal state first.
- **No `run_message` is created for a follow-up** and the gapless `seq` stream is untouched (proven by the M5 e2e leg); **no token is spent and no forge write happens** anywhere in the flow.
- `uzi run inputs <run-id>` shows the same queue + delivery states as the web, from a CLI token; a read-only `uza_` token reads its own and is refused (404) on another owner's.

## Risks

- **`waiting` vs `idle` is a heuristic in v1** (Decision 2): without an SDK handoff event, "blocked on lead" vs "just quiet" is inferred from recency. Mislabels are cosmetic (both are non-active states) and the exact states (`working`/`stalled`/`done`/gate-`waiting`) dominate the cases users act on. A precise `handoff` control message is the named refinement.
- **"Delivered" can show for a consumed-but-dropped input** if the worker crashes right after the GET (Decision 6) — a pre-existing MVP trade-off the code already documents (`service.go:1247`), now merely visible. The run's `health` (`stalled`) surfaces the stall and the user re-sends. Not introduced here; not fixed here.
- **Behavior change to the scroll model** (Decision 3): users habituated to the always-tailing feed must learn the opt-in Follow. Mitigated by collapse-by-default making the change obviously intentional and by keeping the "jump to newest" affordance. Called out because it changes existing functionality.
- **Refactoring `useFollowScroll` to per-body** risks regressing the cap-and-expand and paused-follow logic it currently co-owns; M2's vitest pins both.

## Resolved Questions

- **Steer queue lives in the composer panel, not inlined into the activity feed.** Inlining user turns into the seq-ordered timeline would require the API to allocate `run_messages.seq`, racing the worker (Decision 4). The user asked to see messages "in the queue"; the composer queue answers that directly and safely. Inlining is a future item gated on unifying seq allocation.
- **Crew liveness reuses `run.health`, not raw `last_heartbeat_at`.** PRD #47 already derives and streams worker liveness; the pane maps it (Decision 1). (Corrects the mock's earlier "surface `last_heartbeat_at`" note, now aligned.)
- **The queue renders only `follow_up`.** `approve_plan`/`cancel`/`reject_plan` share the table but own dedicated UI; mixing them into the queue would double-render the gate/stop controls.
- **No schema change.** Delivery is `consumed_at` on an existing table; crew state is client-derived. This PRD adds zero migrations — unusually small backend surface for a user-visible feature.
