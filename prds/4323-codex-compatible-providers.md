# PRD #4323: User-owned Responses-compatible providers on the Codex engine

**Issue**: [#4323](https://github.com/vtmocanu/uzi/issues/4323)
**Priority**: High
**Umbrella**: [#4319](https://github.com/vtmocanu/uzi/issues/4319)
**Dependencies**: PRD #4320 and PRD #4321 must be completed before implementation begins. PRD #4321 must identify at least one auth/transport path preserving the production safety contract.
**Disposition**: Commit and push for later; no dispatch or sweep enrollment.

**Terms of use**: Follow the umbrella's maintainer terms-of-use note before shipping. Providers accept API/cloud/gateway keys only; `codex_auth` subscription credentials are never forwarded. The OpenAI terms re-check is a maintainer obligation, not an offline worker investigation.

## Problem

Users who have an approved Responses-compatible endpoint and its own credential cannot use it with the Codex engine. The current production adapter fixes the provider to OpenAI and accepts only vendor API-key/subscription authentication. Treating a gateway key as an OpenAI vendor key, or changing a base URL independently of the bound credential, could disclose a secret or charge the wrong account.

PRD #4320 supplies engine-neutral provider management and selection, plus the Claude implementation. PRD #4321 supplies the offline runtime evidence needed to extend the Codex adapter without weakening ADR-1106's execution policy. This PRD delivers one additional user-visible outcome: approved user-owned Responses providers work across the currently supported Codex surfaces.

Current-main anchors (baseline 3c4a5ed7b363535bb91fbeb2a69b7c115eb69436; re-read at implementation, including later main a233883de):

- `agent/src/codex/config.ts:158` restricts production config to built-in OpenAI; `:134` is a separate custom-provider config path, not production compatibility proof.
- `agent/src/codex/launcher.ts:779` replaces the child environment; `agent/src/codex/appserver-auth.ts:342` supplies vendor credentials through login RPCs.
- `api/internal/store/enums.go:21` defines the existing vendor credential kinds. `api/internal/handler/secrets.go:28` seals user secrets via vault policy.
- `api/internal/workersvc/harness_resolver.go:465` resolves Codex credential usability and `:617` freezes creation-time bindings transactionally. `api/internal/workersvc/claim.go:547` documents the current subscription/API-key claim union and scoped credential-operation capability.
- `prds/done/1106-codex-harness-phase1.md:36` anticipates a distinct compatible-endpoint auth profile, allowlist and egress analysis. PRD #4323 implements that direction through PRD #4320's shared provider object, not a third harness.

## Outcome

A user can create, test and select a user-owned provider with engine `codex` and protocol `openai_responses` through the web and CLI surfaces established by PRD #4320. It uses only that provider's credential and supported model mapping, with the same execution boundary as existing Codex runs.

Acceptance examples:

1. The operator approves an exact base URL. A user saves a Responses provider and its own credential, sees separate authentication/protocol and tool-use probe results, selects it as default, and starts a Codex run. The run reaches only its approved binding and completes through worker-owned callbacks. Vendor credentials are absent from that claim and provider launch.
2. With `users.codex_provider_id` set, explicit `--harness codex` uses that provider source. Explicit `--harness claude` uses `claude_provider_id` when set, otherwise today's Claude vendor credential ladder. `default_harness` continues to select the engine for implicit requests. A broken or revoked selected Responses source returns the typed provider refusal, even when a vendor credential or another engine is usable; it never silently spends an OpenAI subscription, OpenAI vendor key or another provider key.
3. A provider changes while a run is queued or parked. The existing run preserves its bound provider and secret-material revisions, or receives the core's explicit revoked/unavailable/stale outcome on its next actual claim. An already-held claim retains its authority until it ends; cancellation is the immediate stop, as in PRD #4320 D9. The run never silently adopts a new destination or credential during resume. Existing native-vendor runs retain their behavior.

## Out of scope

Chat-Completions-only endpoints, arbitrary provider plugins/config snippets, subscription OAuth forwarded to third parties, new harnesses, per-run/schedule provider selectors, per-role provider mixing, admin-shared providers, provider budgets/reserve, runtime upgrades and PRD #50 proxy composition. Codex provider runs on the isolated lane remain out of scope: PRD #4322 M3 enables that lane for Claude providers only. This does not add Codex support to surfaces that currently do not support Codex. Codex-engine shared providers remain a follow-up after C and D, rather than being delivered by D. No implementation or validation edits under `.github/workflows/`.

## Modules and seams

- **Provider management/probe, inherited from PRD #4320.** Reuse the `model_providers` and `model_provider_revisions` tables and `{id, owner scope user|shared, name, engine claude|codex, protocol anthropic_messages|openai_responses, base_url, auth_style, model_map, revision}` contract. This slice accepts user-owned `codex`/`openai_responses` profiles only, with the auth styles PRD #4321 established. Add `user_secrets.kind = openai_compatible_key`, sealed through the existing vault path with unchanged `(user, kind)` AAD and immutable, owner-checked `provider_id` association. Match PRD #4320's explicit database-write residual in the threat model; no provider reassignment update exists. Do not overload `openai_api_key` or `codex_auth`. Web and CLI share validation and safe probe-result codes. Unsupported auth styles fail at save; probe failures echo neither response content nor secrets.
- **Destination authority.** `UZI_PROVIDER_ALLOWED_BASE_URLS` remains deployment-only, exact-base-URL including path, HTTPS-only with loopback permitted only by the core's explicit development flag. The API checks at save/probe/create/claim. The worker validates the trusted claim's binding shape, HTTPS/development-loopback rules and credential mutual exclusion; it does not carry a second deployment allowlist copy. This relies on the API as the existing trusted credential custodian and authority over destinations. Keep the protected runtime config/env boundary, so repository content cannot replace the bound URL. Worker FQDN egress still requires operator configuration; a successful save/probe does not grant network reach. That egress list is namespace-wide, not per-run destination isolation. Redirects must not forward credentials or repository content. PRD #4321's observed redirect/discovery behavior determines the required adapter enforcement; unresolved behavior blocks activation, rather than relying on a disabled probe redirect alone.
- **Selection and binding.** `users.codex_provider_id` is a nullable per-engine source choice: null preserves today's complete vendor resolver and pool ladder; a provider id selects only that source and its own credential. `claude_provider_id` is PRD #4320's counterpart. `default_harness` still chooses the engine; `--harness X` uses X's source. Existing vendor `user_secrets.is_default`, its two-kind Codex index, count/clear/insert/default/disable semantics and worker/judge vendor ladders remain unchanged. Provider keys never join those vendor groups; `auto_eligible` and `is_default` remain false, with explicit provider-key insertion rather than the first-of-kind auto-default query. Check the selected source before Codex auto-pool resolution; a broken selected provider refuses explicitly rather than falling through within or across engines. Transactional creation freezes provider identity/revision and credential authority together. Claim carries exactly one `provider` object `{provider_id, revision, engine, protocol, base_url, auth_style, credential, model_map}` and no vendor credential alongside. Re-check owner access, revision liveness, credential enablement and destination policy at each actual claim. Follow PRD #4320's revision/revocation contract on retries, parked promotion and resume. Never relabel a provider credential as a vendor credential to satisfy an old token-presence guard.
- **Static key state and schema boundary.** Each `openai_compatible_key` has an owner-scoped `codex_credential_state` row with status `static`, null provider account and its existing `material_revision` counter (`00200_codex_credential_state.sql:19`, `codex_credentials.sql:44-50`). Rotation bumps that counter atomically with ciphertext replacement; also freeze/check `user_secrets.enablement_rev` so disable/re-enable cannot revive an old claim binding. Freeze `(provider_id, provider revision, secret id, material_revision, enablement_rev)` at creation and compare before opening material at claim, including vault-read retry paths. The provider binding is distinct from the vendor `runs.codex_auth_mode` and `ClaimCodexSecrets` union: do not label it `subscription` or vendor `api_key` to fit `runs_codex_auth_mode_check` (`00202_run_codex_binding.sql:27`). Keep vendor auth fields absent on provider runs, extending only shape constraints that need to admit the exclusive provider-binding arm; existing vendor rows and enum meanings do not change. Audit the hard-coded vendor index (`00198_codex_secret_kinds.sql:26`), default clear (`codex_credentials.sql:132`) and all kind-based readers to ensure the new kind is excluded from vendor selection, refresh, meter, vault-default and switch paths. The reused static-state row supplies a revision fence, not authority to enter vendor account flows.
- **Codex launch/auth adapter.** Add the smallest explicit adapter needed for PRD #4321's accepted configuration, using a distinct internal provider identity rather than overriding built-in `openai`. Keep environment replacement, system-config refusal, explicit untrusted project state, native tool/extension suppression, code-host callback admission, disposal and credential isolation. Config keys are worker-generated from validated fields, never arbitrary TOML/env/header objects supplied by the user or repo. Reuse the scoped credential-release boundary where appropriate; static provider keys must not enter vendor subscription refresh, account linking, pool selection or vendor account-meter APIs. If PRD #4321 cannot preserve the intended credential surface, settle that decision before implementation starts.
- **Models and supported lanes.** Reuse `model_map` to resolve current Codex model choices without rewriting source templates. Validate against PRD #4321's accepted capability envelope and reject unmapped/unsupported explicit pins clearly. Same-run continuation, recovery and associated model passes retain their originating frozen authority. Cross-checks keep the opposite-engine requirement, resolve that engine's authorized source transactionally at child creation, freeze their own binding and retain it on retries/resume. Judges honor the existing independent harness and pinned/default credential policy, resolving the applicable provider source only where that policy calls for default/source selection; a pinned vendor judge is not replaced by the lead's provider. Conflicting explicit policies refuse rather than silently selecting another credential. Apply these rules to every currently Codex-capable issue, job, judge, cross-check, advice and summary path. A provider-unaware helper cannot fall back to native-vendor credentials. Do not certify an endpoint from one small tool-use probe: report that limited result separately from production compatibility requirements.
- **Untrusted-input bounds.** PRD #4320's numerical URL/name/map/key limits, per-owner provider quota, probe body/response limits, probe concurrency/rate limits and deadlines are inherited unchanged and must be revalidated at Codex entry points. No new unbounded field, metadata fetch or background discovery is added. Runtime transport uses existing frame/output bounds, run wall-time/cancellation and worker concurrency; configure model discovery/retries from PRD #4321's bounded accepted path rather than accepting gateway-suggested destinations or unbounded discovery payloads. Focused tests exercise each inherited bound through the Responses profile, including oversized errors and stalled streams. If a proposed runtime path cannot enforce the shared bounds, reject that path and record the blocker.
- **Usage and errors.** Provider headroom/limits read unknown; subscription reserves and vendor meter polling do not gate or probe this credential. Preserve observed token counters, existing wall-time/concurrency controls and reliable gateway-reported accounting, while never assigning vendor prices to an arbitrary mapped model without a valid basis. Authentication failure affects only the provider credential. Reuse core failure codes and scrub both exact credential values and credential-shaped payloads from errors/logs. A gateway outage never enables fallback spend.
- **Refusal and live switching.** Keep #3068's safety hold only for the validated refusal classifications already emitted by the pinned Codex runtime (`agent/src/provider-policy-refusal.ts`, `agent/src/codex/codex-harness.ts`, `delegation.ts`). The same recognized structured tag from a custom Responses provider follows the same hold; a gateway's free-text refusal, 401/403/429 or arbitrary message cannot masquerade as that tag and follows the existing bounded generic/auth/rate error path. No text-matching classifier or provider fallback is added. Preserve each lane's lifecycle, including terminal failure for jobs. Provider runs refuse live Codex account switching with a typed reason at the switch admission/apply resolver, including the eventual #4202 path, before vendor credential release or binding writes. Existing vendor switching remains unchanged. Document this boundary and cover provider-to-vendor and vendor-to-provider attempts, including source-setting changes between selection and apply.

Run storage reuses A1's concrete fields: `provider_id`, `provider_revision`, `provider_key_mode='user_key'`, `provider_key_secret_id` and `provider_key_rev` (the user key's `enablement_rev`). C additionally stores the static Codex key's `material_revision` as `provider_key_material_rev`, nullable outside this provider arm; both fences must match before opening. Existing vendor `runs.codex_*` auth fields remain absent on provider runs. The additional material fence uses the existing Codex static-state revision semantics without changing the shared key-mode discriminator or weakening A1's disable/re-enable fence.

Existing Codex isolation was characterized for fixed trusted vendor endpoints and synthetic local fakes. That safety story does not automatically cover user-controlled endpoint URLs, response metadata, redirects or model catalogs. The core's operator-approved destination policy plus PRD #4321's bounded runtime evidence must cover the new callers. Preserve vendor behavior separately; user/provider response data cannot select a callback's run, role, phase or credential authority.

## Testing decisions

Source-setting lifecycle mirrors A1: `users.codex_provider_id` has a single-column FK to `model_providers` with `ON DELETE RESTRICT`. Deleting a provider still selected by any user returns `provider_in_use_as_source`; retirement keeps the source set and new requests return `provider_source_unusable`. Never auto-null the source on delete, retirement or grant changes. Clearing a source is an explicit owner action, not an error fallback. The resolver checks ownership/access and engine as well as the FK.

Automatic selection mirrors A1 in both directions: a set Codex provider source makes the corresponding path ineligible for `automaticHarnessEligible` and `evaluateCreationOverflow`, including overflow from a vendor engine into the provider and from the provider into a vendor engine. Unknown provider usage never enters weekly-reading comparisons. Add tests for both directions, with a usable alternate-engine vendor credential and with a usable Codex pool.

Audit every reader of `codex_credential_state`, not only queries with credential-kind predicates. In particular, `api/internal/store/queries/codex_rate_limits.sql:458` treats `status='static'` as unmetered: the new compatible key must report unknown provider headroom/cost instead of inheriting unlimited vendor capacity or entering a reserve, fallback, meter or automatic selector. Scope the correction to the new kind so existing `openai_api_key` behavior remains unchanged. Cover status-based projections, settings/CLI/web DTOs, account readers, pool/reserve selectors and secret conversion/reset.

Gateway limit handling reuses A1's `limit_wait` state and `provider_gateway_limit` reason, with resume delays 1, 5 and 15 minutes, then owner Resume only; no vendor reset estimate or pool promotion. Persist the retry count across claims so requeue cannot reset the cap. Keep existing sweeper, Resume handler and web/CLI/Slack readers, naming the provider; jobs fail terminally. Typed authentication/refusal errors remain distinct. Test the full timer/owner-resume sequence using controlled timers, the unchanged binding after reclaim, and the E2E reason literal.

Judge selection is independently resolved and frozen, not inherited from the target. Mirror A2's Claude judge table whenever the selected judge engine is Claude: pinned vendor credential remains pinned; default and auto use the Claude provider source when set, otherwise their existing vendor default/pool paths. For a Codex judge, the current code has no separate Anthropic-style three-valued judge bind mode: `judgeHarnessFor` selects Codex, then creation uses the Codex resolver. Null `users.codex_provider_id` preserves that entire vendor default/account-mode resolver; set selects the provider source before vendor pool selection. Do not invent a Codex judge pin/auto setting or apply `judge_anthropic_bind_mode` to it. Preserve any independently authorized explicit credential pin at an applicable existing seam, refusing a conflict instead of silently replacing it. Test owner-selected judge engine in both directions, the Claude pinned/default/auto rows, and a Codex judge with both vendor account modes and a set/unset provider source.

Rollout uses a distinct worker capability `codex_provider_v1`: the API issues Codex provider claims only to workers advertising it, and health reports no capable worker otherwise. A1's `claude_provider_v1` alone does not qualify a worker for C. All provider-capable agent wiring ships before the corresponding server lanes are admitted. Document API-first (claims wait) and worker-first (unused capability) rollout and the separately pinned hosted-worker roll. Test both a legacy worker and an A1-only worker; neither may claim a C provider run.

Binding details: fence the frozen provider revision, Codex static-key `material_revision` and `enablement_rev` before opening it, returning `provider_binding_stale` rather than sending replacement material to the frozen URL. A selected provider source takes precedence over `codex_account_mode=auto` and pool selection. Follow PRD #4320's next-actual-claim revocation semantics; no mid-claim provider revalidation or credential re-release is introduced by this slice. Existing vendor boundary reconciliation remains unchanged. Test both cross-check directions, an opposite-engine judge and a same-engine judge with a distinct pinned vendor credential. Test an unusable selected provider with a usable vendor credential on each engine; no implicit fallback spend is permitted. Exercise recognized structured refusal versus unknown/free-text gateway errors, and #4202 switch rejection.

Use PRD #4321's offline pinned-runtime/local-fake experiments as executable regression evidence. Extend existing config, launcher, auth, executor, resolver/claim, handler, web and CLI tests only at the seams changed. Positive proofs include real request delivery to the intended fake, worker callback execution, supported advice and successful bounded resume. Negative proofs include wrong owner/revision, disabled/revoked key, allowlist removal, redirect, unsupported auth/model, auxiliary endpoint substitution, malformed/oversized response and stream cancellation. Assert zero vendor credential release/calls by instrumenting release and dispatch seams, not by searching logs alone. Keep native-vendor fixtures as non-regression controls.

Assemble secret-shaped fixtures at runtime. Every bug fix gets a watched red/green regression. When a product detail/event/receipt/forge contract changes, sweep old identifiers across `e2e/phases/`, `e2e/lib.sh`, `e2e/lib.test.sh` and `e2e/forge-fake/`, update affected harness expectations, run `task test:e2e-lib` and `task test:forge-fake`, and name affected unrun phases in the PR.

In-run: `UZI_DEADCODE_AGENT_REQUIRED=1 task check:agent` plus touched/directly affected tests and `task test:codex-m4`; `task check:api` plus affected Go package tests with `-race -count=1`; `task check:web` plus touched Vitest/browser cases for changed UI; relevant migration, contract, docs and changelog checks; `task scan:secrets` with canary evidence. All runtime compatibility tests use the installed matching pinned Linux runtime and local fakes, without open-web access or live credentials. Use event-driven readiness; measure affected test-step time before/after when runtime grows.

Landing obligations, outside milestones: **full agent suite: exact-head PR CI**, existing worker-UID/runtime conformance and the applicable API/web/repo CI checks. Cluster-only behavior gets a linked acceptance issue covering hosted restricted-worker egress, actual provider binding and native-vendor regression; primary runtime is hosted Kubernetes, with compose maintained. Live external-gateway certification is not implied by the offline fake. The acceptance issue has no sweep label or deadline and does not block merge unless the user explicitly requires that proof.

## Decision Log

- **Build on PRD #4320 and PRD #4321.** Reason: reuse one provider security/ownership contract and ship only a measured Codex auth/transport path. Rejected: a second endpoint subsystem or implementing before the spike is resolved.
- **Responses only, no new harness.** Reason: the existing Codex adapter is the intended extension point. Rejected: treating Chat-Completions compatibility as sufficient or adding a native executor here.
- **One bound provider, no fallback spend.** Reason: destination and credential jointly define authority; errors cannot authorize another account. Rejected: storing gateway credentials under vendor kinds or inheriting ambient config/env.
- **Per-engine source choice preserves vendor defaults.** Reason: nullable `claude_provider_id` / `codex_provider_id` selects a provider explicitly while null leaves existing vendor defaults and bind ladders untouched. `default_harness` still selects the engine; `--harness X` uses X's source. Rejected: widening vendor `is_default` groups, which changes existing readers, writer conflict targets and previously created vendor runs; also rejected treating an explicit engine pin as authority to spend another source.
- **Static Codex state supplies material fencing only.** Reason: the existing `material_revision` is a concrete reusable fence; `(user, kind)` vault AAD stays unchanged and the new kind's immutable provider association is validated. Rejected: citing `OpenByIDOfKindAtRevision` for a key with no state row, or calling a provider key a vendor API key to enter existing auth branches.
- **Reuse existing run limits; headroom stays unknown.** Reason: provider subscription quota is not known to uzi. Rejected: vendor reserve probes on gateway credentials, invented zero usage or removal of unrelated runtime bounds.
- **No arbitrary auth/config injection.** Reason: a bounded supported auth style preserves reviewable secret handling. Rejected: user-provided TOML, env maps or arbitrary header dictionaries as an escape hatch.
- **Activation contract comes from PRD #4321.** Reason: current production managed auth and code-host behavior must be preserved. At implementation entry, cite PRD #4321's final matrix and list exactly which styles, metadata and transport features this slice accepts; unsupported behavior remains disabled.
