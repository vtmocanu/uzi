## Problem

`/workers` is one long column of three cards: **Register a worker** (a form used once per machine), **Hosted workers** (a form used once per worker plus one persisted toggle), then **Your workers** (the fleet: upgrade banner, per-worker status, CPU/memory gauges, token binding, Delete). Three costs:

1. **The daily view is at the bottom.** The fleet list is what a user opens the page for; on a two-worker fleet its first card starts roughly a screen down, under two forms they touched once.
2. **The wrong path is first.** Self-hosted registration precedes hosted provisioning, but on a k8s deployment hosted is the primary worker path (root `CLAUDE.md`, *Conventions*: "we mostly test in k8s now"; hosted is "the *primary* worker path"). The zero-effort option should lead.
3. **The empty state points at the wrong form.** A new user with hosting available reads "Generate a join token above", which sends them to the manual path.

The page also carries a flow that assumes one scroll: at quota, the hosted card says "delete one to provision another" and the delete controls are in the list below; after a provision, the announcement says the worker "appears in your workers below". Any split has to carry those two loops across the seam.

## Solution

Two tabs under the page header, plus a header action and a deep link, with the forms reordered hosted-first. Same components, same API calls, same DTOs; this is composition and copy, not behaviour. No route, handler, or CLI change (`api/cmd/uzi/` is unaffected: the page's API surface does not move).

### Design (complete spec, so a worker needs no mock)

**Header.** `PageHeader` keeps title and description; it gains `actions={<Button><PlusIcon /> Add a worker</Button>}` (the Schedules `New schedule` shape; the label matches the tab name exactly, on purpose). Clicking it selects the **Add a worker** tab and moves focus to the add panel's first control (the hosted Template select when the hosted card renders, else the Name input). It stays visible on both tabs (D9).

**Tab bar**, directly under the header, the Schedules recipe verbatim (`role="tablist"` with `aria-label="Workers"`, two `role="tab"` buttons with ids, `aria-selected`, `aria-controls`, roving `tabIndex`, `onTabKeyDown` with Left/Right wrap and Home/End, automatic activation, `TAB_BASE`/`TAB_ACTIVE`/`TAB_INACTIVE` classes copied, not imported; see D6):

- `Your workers · N` where N is `workers.length`; the suffix is omitted at 0 (the Schedules `· count` convention).
- `Add a worker`.

**Landing tab depends on the fleet (D11).** The default is decided **once, after the first workers load resolves**: `workers.length === 0` → `Add a worker` (a new user should meet the forms, not an empty list); one or more → `Your workers`. **Count every worker the list returns, whatever its state**: offline, upgrading, cordoned, draining, stale-heartbeat or otherwise unhealthy workers are exactly the ones their owner opened the page to look at, so a fleet of one broken worker still lands on Your workers. Never derive the landing tab from online/healthy counts. Until that load resolves, the tab bar renders with no tab selected and both panels hidden behind the existing skeleton, so the page never flashes the wrong tab. After that, the count never moves the selection on its own: deleting the last worker leaves the user where they are (the empty state then shows on Your workers), and a first worker appearing via the 10s poll does not yank them off the add tab mid-copy of a join token. Both tabs are always rendered (a one-tab tablist is an a11y smell).

**Deep link.** `?tab=add` or `?tab=workers` selects that tab on load, read once via `useSearchParams` (the Findings precedent) and taking precedence over the count-based default; any other or absent value means the default. Switching tabs writes the param with `{ replace: true }` so the URL stays shareable without polluting history. No other state goes in the URL.

**Panels.** Both `role="tabpanel"` panels are always mounted; the inactive one carries the `hidden` attribute (D4). Each is `aria-labelledby` its tab.

*Your workers panel* (top to bottom): the `notice` slot (moved here from between the forms and the list; every announcement describes the list, and focus behaviour is unchanged), then the **Your workers** card exactly as today: `FleetUpgradePanel`, the worker rows with all their badges, gauges, token picker, Delete and hosted-delete confirmation. The **empty state** changes: title "No workers yet", description "Provision a hosted worker and it comes online on its own, or register your own machine with a join token." and an `action` with **Provision a hosted worker** (primary; rendered only when hosted manual provisioning is available, see *Availability* below) and **Register your own** (secondary). When hosting is unavailable the single primary reads **Register a worker** and the description drops the hosted clause. Each CTA selects the add tab and moves focus to its form's first control (Template select / Name input).

*Add a worker panel* (top to bottom): the one-time **join-token card** when `newToken` is set (unchanged; it stays mounted across a tab switch and clears only on Done); the **Hosted workers** card (`<HostedWorkers>`, unchanged gates: renders nothing when hosting is off); the register card retitled **Register your own worker**, form unchanged, help text amended so "flagged below" reads "flagged under Your workers".

**Cross-tab flows.**

- *At quota.* `HostedWorkers` renders `"{n} of {quota} used — "` followed by a link-styled `<button type="button">delete one to provision another</button>` instead of plain text. It calls a new required prop `onShowWorkers: () => void`; the page selects the Your workers tab and moves focus to the first **hosted** worker row's container (the `<li>` at `WorkersSettings.tsx:425`, given `tabIndex={-1}`; rows have no heading element, the name is a `<span>`), never to a Delete button (the `:237-254` rule stands; a hosted delete is armed, not one-click, but the rule is about not parking a keyboard user on a destructor at all).
- *After a provision.* In the page's `onProvisioned` handler, select the Your workers tab **and** announce in the same synchronous batch (both state setters before any `await`), so the panel is un-`hidden` in the same render the `[notice]` focus effect (`WorkersSettings.tsx:244-246`) runs in; `.focus()` on an element inside a hidden panel silently no-ops. The notice sits at the top of that panel so it is visible and takes focus (existing behaviour). Copy: "Provisioned {name} — it is listed below and comes online on its own."
- *After Generate join token.* Stay on the add tab; the token card appears at the top of the panel (today it is at the top of the page, above the forms). Rebinding a token, deleting a worker: unchanged, they happen on the Your workers tab and announce there.
- *Prose.* `HostedWorkers.tsx:211-217` "It appears below and comes online on its own, and you delete it there like any other worker." becomes "It shows up under **Your workers** and comes online on its own, and you delete it there like any other worker."

**Availability (for the empty-state CTA).** The page does not know whether hosting is on: `HostedWorkers` fetches `hostedConfig` itself and renders nothing when it is off. Add an optional prop `onAvailability?: (a: { manual: boolean }) => void`, invoked **from the fetch effect itself, exactly once per mount**, with `manual = enabled && quota > 0`, and with `{ manual: false }` when the config is disabled, at quota 0, or on a rejected read. It must fire **before** the component's early `return null` paths (`HostedWorkers.tsx:121` and `:130`), or the page never learns that hosting is off. This works only because D4 keeps the add panel mounted: `HostedWorkers` mounts, fetches and reports even while its panel is hidden. It keeps the one-shot fetch where its 24 tests already pin it (`HostedWorkers.test.tsx:117` "reads the policy once and never polls it"); lifting the fetch into the page was rejected for that reason (D8).

**Unchanged on purpose.** The Auto-provision on demand toggle stays inside the hosted card (D5). The page-level error alert stays above the tabs. Polling, delete confirmation, focus-return-to-Delete after a dismissed confirm, token rebind, upgrade badges: untouched.

## Success criteria

1. `/workers` opens on **Your workers** with the fleet card as the first content under the tab bar when the user has at least one worker, and on **Add a worker** when they have none; `?tab=add` / `?tab=workers` override that. The selection never changes on its own after load. The tab label carries the live worker count.
2. On the add tab the Hosted workers card precedes the Register your own worker card whenever hosting is on; with hosting off only the register card renders and nothing hosted appears anywhere.
3. The tablist meets the APG tabs pattern (roles, `aria-selected`, `aria-controls`, roving tabindex, arrow/Home/End keys, automatic activation) and the hidden panel is out of the accessibility tree, verified by unit tests (M1) and a browser pass (M4).
4. The three cross-tab loops work: at quota the "delete one" control lands on the list without focusing a Delete button; a provision returns to the list with the announcement focused; the join-token card survives a tab round-trip and clears on Done.
5. The empty state offers **Provision a hosted worker** first when hosting is available, and only **Register a worker** when it is not; each CTA lands focus in the right form.
6. All 56 + 24 existing tests pass, updated where they assumed a single column; `task gate:web` and `task gate` green; `check-docs` green; `git diff --name-only origin/main..HEAD -- .github/workflows/` is empty.

## Decision log

- **D1 — Tabs, not a modal or drawer for the add flow.** A drawer that closes on outside click can lose the one-time join token; `web/` has no modal primitive (specs/ai.md:7457, PRD #58) and the hosted prose plus the persisted toggle are too much for one; tabs keep every existing card and test intact.
- **D2 — Names: `Your workers · N` and `Add a worker`, not "Status" and "Add new worker".** "Status" is vague on a page already titled Workers; `Your workers` is the existing section title; the `· N` suffix is the Schedules convention.
- **D3 — Hosted first on the add tab; register retitled "Register your own worker".** Hosted is the primary worker path on k8s deployments and the zero-effort option; the retitle makes the contrast between the two cards read.
- **D4 — Both panels stay mounted, the inactive one `hidden`.** Departs from Schedules, which unmounts. Reasons: the join-token card must not vanish on a tab switch; `HostedWorkers` fetches its config once on mount and its tests pin that; the notice slot's focus effect keys on state, not on mount; and D8's `onAvailability` only reaches the page on the Your workers tab because the hidden add panel still mounts `HostedWorkers`. `hidden` removes the panel from the accessibility tree and from `getByRole` queries, which is what tests should assert.
- **D5 — Auto-provision on demand stays in the hosted card.** Someone hunting for a docker-capable worker looks under Add a worker, and the toggle reads as "let uzi add workers for you". Alternative recorded: a fleet-policy row beside the upgrade banner on Your workers. Revisit only if users report not finding it.
- **D6 — Copy the Schedules tab recipe; do not extract a shared primitive here.** `Schedules.tsx` is in PRD #929 M1's diff (file collision), and Findings/Judge carry their own inline tab classes, so a shared `Tabs` primitive is a three-page migration. File it as a follow-up issue referencing the three copies; keep this PRD page-local.
- **D7 — `?tab=add` via `useSearchParams`, written with `replace: true`.** The Findings precedent; a deep link lets `docs/worker-setup.md` point straight at the form. History is not polluted by tab clicks.
- **D8 — Availability reaches the page through an `onAvailability` callback, not by lifting the fetch.** Lifting `hostedConfig` into the page would move 24 tests' subject; a callback adds one prop and one assertion.
- **D9 — The header Add worker button is always visible.** Hiding it on the add tab shifts the header on every switch; leaving it is harmless and keeps the affordance discoverable from either tab.
- **D10 — Focus targets are explicit.** Header button and empty-state CTAs focus the first control of the relevant form; the at-quota link focuses the first hosted row's heading. Never a Delete button (existing rule at `WorkersSettings.tsx:237-254`).
- **D11 — A new user lands on Add a worker; both tabs stay visible.** The user's first instinct was to hide Your workers at zero workers. Rejected in favour of a count-dependent landing tab: hiding one tab of two leaves a one-tab tablist, and the tab would vanish under a user who deletes their last worker. Hiding the whole tab bar at zero (an onboarding layout mode) was the other option, declined for the extra layout mode and its delete-the-last-one flicker. The landing decision is made once per page load, after the first fetch, and a URL param beats it (user decision, 2026-09-03).

## Risks and mitigations

- **Test churn in a 56-test file.** Many tests query add-panel content without a tab switch. With D4 they still find it via `getByText`, but `getByRole` excludes hidden content, so role queries need `openAddTab()`. Mitigation: one helper, applied per test; no blanket `{ hidden: true }`.
- **A hidden panel that is only visually hidden.** If `hidden` is replaced by a CSS class, screen readers and role queries see both panels. Mitigation: M1 asserts `toHaveAttribute("hidden")` on the inactive panel and that `getByRole("tabpanel")` returns exactly one.
- **Focus landing on nothing.** Focus targets exist only after the tab switch renders. Mitigation: use `requestAnimationFrame`/effect-after-state (the pattern the notice focus effect already uses at `:250-254`), and test with `document.activeElement` (already the file's idiom at `:564`, `:671`, `:710`). Keyboard tests use `fireEvent.keyDown`, as the file does today; Schedules' handler is an `onKeyDown`.
- **The 10s fleet poll can disturb a parked focus.** `usePollWhileVisible` (`WorkersSettings.tsx:193`) re-renders the rows every 10s, so focus parked on a `tabIndex={-1}` row after the at-quota jump could be lost if rows reorder. Rows are keyed by id, so this is low risk; M3 asserts focus survives one poll tick with an unchanged fleet.
- **Stale docs and screenshot.** The docs edits are in M5; the screenshot is called out as a maintainer follow-up so nobody reads its absence as a missed step.
- **Collision with in-flight work.** #908 (`schedsvc`) and #1061 (`api/cmd/uzi` TUI) share no files with this PRD; epic #915's remaining web extractions (`ScheduleModal.tsx`, `RunEvent.tsx`, `ActivityFeed.tsx`, `AppShell.tsx`) do not touch `WorkersSettings.tsx` or `HostedWorkers.tsx`. `specs/ai.md` is append-only by section number; resolve a number clash at merge.
- **Workflow-scope guardrail.** Nothing here needs `.github/workflows/`; validation is vitest plus a mock-mode browser pass.
