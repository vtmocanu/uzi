# PRD #357: Explicit per-repo remove action

**GitHub Issue**: [#357](https://github.com/vtmocanu/uzi/issues/357)
**Status**: Draft (created 2026-08-18)
**Priority**: Medium
**Related**:
- `ListProjects` (`api/internal/handler/forge.go:486-553`) — the add/update-only projects refresh whose lack of a prune is the root cause. This PRD does **not** add pruning to it (see D1); it adds a separate, explicit remove.
- `SetRepoEnabled` (`api/internal/handler/forge.go:621-697`) and `SetRepoEnabledForUser` (`api/internal/store/queries/forge.sql:148-152`) — the owner-scoped, disable-is-never-gated pattern this PRD mirrors for the delete path.
- `DeleteConnection` (`api/internal/handler/forge.go:459-481`) / `DeleteForgeConnectionForUser` (`api/internal/store/queries/forge.sql:36-37`) — the existing all-or-nothing removal (whole connection, cascade). This PRD is the surgical, single-repo counterpart.
- `poller.Engine` (`api/internal/poller/poller.go:28-31`) — disabling a repo only drops it from the *enabled poll set*; it does **not** cancel an in-flight run. This is why "disabled" does not imply "quiescent" and motivates the active-run guard (D7).

## Problem

uzi has no way to remove a single connected repo. Two facts combine into a permanent stale duplicate:

1. **The projects refresh is add/update-only and never prunes.** `ListProjects` (`forge.go:486-553`) fetches the bot's live membership and upserts each project via `UpsertRepo` (`api/internal/store/queries/forge.sql:55-64`), then returns **all** rows for the connection (`ListReposByConnectionForUser`). Nothing deletes a row that is no longer in the fetched list. So once a `repos` row exists, it persists until the whole connection is deleted.

2. **Repos are keyed by the forge's numeric project id, not the path.** `repos` is `UNIQUE (connection_id, forge_project_id)` (`api/internal/store/migrations/00002_forge.sql:31`, schema comment `:19-22`: *"Keyed by the forge's numeric project id (paths get renamed; ids do not)."*). GitHub (and GitLab) never reuse ids, so deleting a forge project and recreating it at the same path yields a **new** id → a **second** `repos` row. Both render the same `path_with_namespace` but are distinct rows to uzi.

Observed live 2026-08-18: a user who recreated `vtmocanu/uzi` sees **two** `vtmocanu/uzi` entries. Disabling one (`SetRepoEnabled`, `forge.go:621`) only flips `enabled` — the row stays and still shows in the projects list. Refreshing the list cannot help (it only adds). The only removals that exist today are:
- **Disable** — keeps the row (the bug above), or
- **Delete the whole connection** — `DELETE /forge/connections/{id}` (`forge.go:459-481`), which cascades away **every** repo, board column, and cached issue under that bot PAT. A sledgehammer for a single stale row.

There is no `DELETE /repos/{id}` route (confirmed: `api/internal/handler/handler.go:1005-1053` registers `GET / POST /{id}/runs /{id}/schedules PUT /{id} PATCH /{id}` and board/tool routes, but no per-repo delete), no `DeleteRepo*` query, and no CLI remove (`api/cmd/uzi/repo.go` has only `list`).

## Solution

Add an explicit, owner-scoped **remove** action across all three consumers of the repos surface, deleting the `repos` row and letting existing foreign keys cascade its derived data. Do **not** auto-prune on refresh (D1).

1. **DB + API.** New query `DeleteRepoForUser` (owner-scoped, `:execrows`, mirroring `DeleteForgeConnectionForUser`); `sqlc generate`. New handler `DeleteRepo` for `DELETE /api/repos/{id}`, registered beside `POST /{id}/runs` in the `RequireUser` group (`handler.go:1005-1024`, cookie OR `uzc_` Bearer) — **not** the cookie-only `RequireAuth` group, so the CLI's Bearer token is accepted (issue #428 regression class). The handler fetches the repo (404 on missing/foreign via `GetRepoForUser`), **rejects an enabled repo** with 409 (D2) and **a repo with a non-terminal run** with 409 (D7), then deletes and returns 204 (mirroring `DeleteConnection`, `forge.go:480`).
2. **Web.** `api.deleteRepo(id)` client method (`request<null>("DELETE", ...)`, mirroring `deleteConnection` at `web/src/lib/api.ts:2665-2666`). A **Remove** button on **disabled** repo rows in `Repos.tsx`, behind the existing inline-confirm idiom (`confirmTrustId`, `Repos.tsx:34`, confirm block `:590-615`); on success, drop the row from local state. Mock-mode parity so the flow is demo/browser-verifiable.
3. **CLI.** `uzi repo remove <id>` subcommand (`api/cmd/uzi/repo.go`), calling a new `Client.DeleteRepo` (interface `api/internal/uzicli/client.go:103`, `HTTPClient` `:902`, `FakeClient` `api/internal/uzicli/fake.go:433`). Destructive, so it requires a `--force`/confirm. Documented in `docs/cli.md`.

**Cascade blast radius (documented, intentional).** Deleting a `repos` row cascades via `ON DELETE CASCADE` to the **direct** referencers: runs (`00020_workers_runs.sql`), cached issues + board_columns (`00002_forge.sql`), autopilot triggers (`00038`), pipeline_statuses (`00042`), tool_profiles (`00046`), chat_runs (`00053`), agent_memory (`00072`), run_schedules (`00103`), board_prefs (`00107`), ci_autofix_attempts (`00117`), and `findings` + `finding_dispositions` (`00129`); plus `ON DELETE SET NULL` to `recommendation_filed_issues.filed_repo_id` (`00071`). The true radius is larger **transitively via `runs`**: deleting the run rows in turn cascades `run_messages`/`run_events`, `run_reviews` and children, `run_usage`, notifications, and slack thread mappings, and NULLs run back-references (chat `resume_of_run_id`, `agent_memory.run_id`, review `*_run_id`). For a disabled stale row this is typically empty, and D7 refuses removal while a live run exists so the cascade never yanks a `runs` subtree out from under an executing worker; where history does exist on a quiescent repo, removing it is correct by design — that is what "remove" means, versus "disable".

**No migration.** Pure query + handler + route + client + CLI + tests. Avoids the goose merge-time renumbering hazard entirely.

## Success criteria

1. A user can remove a single **disabled** repo from the board/projects list without deleting the whole forge connection, from the web UI **and** the CLI.
2. Removing a repo deletes its `repos` row and cascades its derived rows (runs, issues, board columns, ...); a sibling repo on the same connection is untouched (asserted in M1).
3. An **enabled** repo cannot be removed via the API (409), so an actively-tracked repo's board/history cannot be nuked by a stray call (asserted in M1).
4. The projects refresh (`ListProjects`) stays non-pruning (D1) — no routine read deletes data. This is a diff-verified invariant (the PRD touches no `ListProjects` code), not a runtime assertion, so it is checked by review of the diff rather than by a test.
5. All quality gates pass: `task gate` (api + controller + web + agent + repo).

## Decision Log

- **D1 — Add an explicit remove; do NOT prune on refresh.** Auto-deleting rows absent from a `ListProjects` fetch is rejected: the fetch reflects the bot's *current* membership, which is transient (a permissions blip, a token scope loss, a suspended/reconfigured GitHub App install, or a partial/paginated response all make a repo momentarily "absent"). Because `repos.id` is an `ON DELETE CASCADE` anchor for a dozen tables, a prune would let a routine, frequent read cascade-delete runs/board/issues on a hiccup — exactly the "irreversible thing as a side effect of a read" the repo's destructive-ops philosophy forbids. An explicit, bounded, owner-initiated remove has none of that blast radius.
- **D2 — The server rejects DELETE unless the repo is `enabled = false`.** Disabling is the "I've stopped tracking this" state and is never gated (`forge.go:640-641`); remove is reachable only from there. This makes accidental destruction of an active repo's board/history structurally impossible, which matters because two callers here are **non-interactive** — the CLI and (for the sweep that implements this PRD) an auto-approving worker — so a UI confirm is not the real safety; the server guard is. Cost is one extra click (disable, then remove). *Alternative considered:* allow delete on any owned repo with a UI-only confirm — rejected as unsafe for the CLI/automation paths.
- **D3 — Removal is not permanent for a repo the bot still has access to.** If the bot can still see the repo, the next `ListProjects` refresh re-adds it as a disabled row. This is correct: the projects list reflects live membership. Remove is meant for **stale** repos the bot no longer sees (deleted/recreated project, or bot removed from the old one). Documented in M4 and in the CLI/UI copy so it is not read as a bug; to keep a still-visible repo out permanently, remove the bot's access on the forge first.
- **D4 — CLI parity is in scope.** Per the "New uzi functionality ⇒ check whether `api/cmd/uzi/` needs a matching CLI change" convention: `repo` already exposes `list`, and remove is a natural sibling. It is destructive, so it requires `--force`/confirm.
- **D5 — No migration.** The feature is a new query + handler + route + client + CLI + tests; no schema change. This sidesteps the goose merge-time renumbering rule and keeps the change reviewable in one MR.
- **D6 — Return codes mirror existing handlers.** 400 (bad id), 404 (missing/foreign, via `GetRepoForUser` + `pgx.ErrNoRows`), 409 (enabled, or has a non-terminal run — see D7), 204 (removed, like `DeleteConnection`). No new DTO — the DELETE has an empty body.
- **D7 — Also reject removal while the repo has a non-terminal run.** "Disabled" is not "quiescent": disabling only drops the repo from the enabled poll set (`poller.go:28-31`); it does not cancel a `queued/claimed/running/awaiting_approval/awaiting_input` run. Removing such a repo would cascade-delete that run's `runs` row and its whole transitive subtree out from under an executing worker (compose *or* a hosted `controller/` pod). So the handler counts active runs (`CountActiveRunsForRepo`) and returns 409 if any exist. *Alternative considered:* accept the removal and rely on the worker/sweeper tolerating a vanished `runs` row — rejected: the orphan-reconcile behavior of the hosted controller under a mid-run row deletion is not something this PRD should assume, and 409-then-retry is the safe, cheap contract. The window closes on its own when the run reaches a terminal state.

## Risks & mitigations

- **Cascade deletes more than the user expects.** Mitigated by D2 (only a disabled repo, i.e. one you have already stopped tracking) and by explicit confirm copy naming the consequence (board + run history). M1 asserts a sibling repo is untouched.
- **Vacuous negative test.** "Remove button not shown for enabled repo" could pass vacuously. Mitigated by pairing it with the positive (shown + works for a disabled repo) in M2, and by M1's paired 204/409 assertions, per `.claude/rules/web.md`.
- **Removed repo reappears and reads as a bug.** Expected per D3 (bot still has access → refresh re-adds). Mitigated by documenting it in copy and M4; not a defect.
- **Mock/demo mode can't exercise the flow.** Mitigated by adding `mockApi.deleteRepo` in M2 so a browser/demo pass sees the real UX (and no stray `/api/` call escapes the mock nginx tripwire).
- **Fetch-then-delete race.** The handler fetches (for the 404/409 checks) then deletes; a concurrent enable between the two could otherwise delete a just-enabled repo. It is single-*owner* but not single-*action* (a web tab and the CLI can race), so M1 folds `AND enabled = false` into the DELETE itself as the default (not a fallback) — the fetch drives the precise status code, the predicate is the atomic guard. The active-run guard (D7) has the same shape and the same closing window.
- **Removing a repo with active runs (D7).** Disabling does not cancel in-flight runs, so a naive delete could cascade a live `runs` subtree out from under an executing worker — including a hosted `controller/` pod, whose orphan-reconcile behavior this PRD deliberately does not assume. Mitigated by D7's 409 (count non-terminal runs, refuse while any exist) and asserted in M1 case (d).

## Out of scope

- Pruning `ListProjects` (D1) — the projects refresh stays non-pruning.
- Removing the bot from the forge project (uzi has no membership-write call in any driver; the user does that on the forge, out of band).
- Any schema/migration change, and any change to `UpsertRepo` or the repos uniqueness key.
- The optional stale-flag surface (M5) unless the owner opts in.

## Resolved decisions

1. **Disabled-only guard (D2): KEEP.** Removal is reachable only from the disabled state — a disabled repo shows a **Remove** button in its row and is deleted in one click (confirm → gone from the list and the DB). An *enabled* repo is not directly removable (409); disable it first. Chosen over allow-delete-enabled-with-confirm because two of the three callers are non-interactive (CLI, auto-approving sweep worker), so a server-side state precondition is the real safety, not a dialog — and the motivating case (a stale duplicate) is already disabled, so the guard adds zero friction there.
2. **Stale-flag milestone (M5): DEFERRED.** The explicit Remove action solves the reported pain. M5 would need a schema change (record "seen in last fetch") and would touch `ListProjects` — the path D1 deliberately keeps non-pruning — so it is a separate follow-up only if stale rows keep accumulating, not part of this PRD.
