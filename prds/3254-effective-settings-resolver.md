## Problem

A user starting a run cannot see which model, effort or harness it will use. The board card and the issue page show a harness and an Anthropic token picker and nothing else; the chat start card shows only Start and Dismiss (it sends the repo and issue, the server picks the harness). Settings labels inherit from four different places with one "Inherit" wording. A schedule's model pin is silently ignored at claim when the run resolves to the other harness. A selected token can be refused only by pressing Start.

The answers live on the server (claim assembly, the D11 harness resolver, the credential-override validator, the schedule save and fire rules) and partly in the worker (lead template fallback, Codex built-ins, the subagent override). After children B, B2, C, D, G and H land, each rule has one home, and several already surface as settings cells on `GET /me/settings` (judge, summary, cross-check, effort with its catalog default). What is still missing is one place that composes them per start surface and per schedule: the lead worker model and effort with their source, the harness each start choice resolves to, token validity, task-review built-ins, and the schedule preview including subagents. Children I, J2, K, L and O consume it.

## Outcome

One resolver, composed in the handler from the claim's own code and the sibling homes above, answers what a run would use. Every model value is C's `ModelSettingCellDTO` and every effort value B's `EffortSettingCellDTO`, wrapped with `setting`, `fixed_at` (`create`: frozen when the run is created or fired; `claim`: read when a worker picks the run up), `ignored` and `notes`, labelled through C's settings-cell table. It covers the user's defaults (both harness columns), every start surface in one request, a server-side check for any token choice that request does not cover, and a schedule (draft or saved) including its subagent behavior. `uzi settings get` shows the same rows. No credential material is returned.

### Acceptance examples

1. **Claude-only user, nothing configured.** One enabled Anthropic token, no Codex credential, no lanes, no efforts, builtin `lead` template (`opus`). `GET /api/me/effective-settings`: start choice `default` resolves harness `claude`, `harness_source: automatic`, `fixed_at: create`; choice `codex` refuses `no_credential_for_harness`. Claude `worker_model` cell: `model: null`, `default_model` and `resolved_model` `opus`, `default_source` and `source` `template`, `fixed_at: claim`; `worker_effort` cell: `resolved_effort: medium`, `source: builtin`, `mode: explicit`. A board start plus a real claim ships `default_model: null`, `default_effort: medium`, and H's `resolveLeadRequest` on the worker yields `opus` with source `template`.
2. **Runtime default effort.** Codex effort set to Runtime default (B). Codex `worker_effort` cell: `effort: "runtime"`, `resolved_effort: ""`, `source: user_default`, `mode: runtime_default`, `catalog_default` from B2 for the predicted Codex model, for example `{state: "known", effort: "low", model: "gpt-6.1-sol", runtime_version: "0.162.1", observed_at: ...}`, or `state: "unknown"` / `"varies"`. The Claude cell in the same mode has no `catalog_default`. The real Codex claim carries no `default_effort`.
3. **Schedule pin on the other harness, subagents toggle on.** User default harness `codex` (usable), Codex lane `gpt-6-sol`; draft `{target: "sweep", harness: null, model: "sonnet", override_subagent_model: true, credential_override: null}`. `POST /api/me/effective-settings/schedule-preview`: harness `codex` (`user_default`, `create`); `worker_model` `resolved_model: gpt-6-sol` (`user_default`, `claim`) with `ignored: {value: "sonnet", source: "schedule_pin"}` and note `schedule_pin_ignored`; subagents `{mode: "follow_lead", lead_value: "gpt-6-sol"}`; note `issue_labels_may_select_harness`. Firing that schedule now creates a Codex run whose claim ships `gpt-6-sol`, records the fallback note and carries `override_subagent_model: true`. With the harness pinned to Claude and a Claude lead resolving to `""` (lead template model cleared, no lane), the same toggle reports `{mode: "own_pins", ...}`, as the Claude executor applies no override without a lead model.
4. **Disabled pinned token.** Both harnesses usable; the user picks a disabled Anthropic token on a card. `POST /api/me/effective-settings/start-preview` `{harness: null, credential_override: {mode: "pinned", secret_id: <id>}}` returns `refusal: credential_disabled`; the same create returns 409 with the disabled message. With an enabled token it returns harness `claude` and credential source `token_override`, `fixed_at: create`. For a saved schedule whose stored pin was disabled since, `schedule-preview` `{schedule_id: <id>}` returns `refusal: credential_disabled` (the fire-time rule), and for a stored pin whose token was deleted it returns credential source `claim_selection` (the FK nulled the pin, so it inherits).
5. **Codex task review.** Codex lane `task_review_model`: `resolved_model: gpt-6-sol`, `source: builtin`, note `not_configurable`, whatever the Codex lane holds; `task_review_effort`: `resolved_effort: ""`, `mode: runtime_default`, `source: builtin`, note `not_sent`. Claude lane: `resolved_model: ""`, `source: builtin`, note `sdk_default` (although the Claude review claim ships the lane, the reviewer ignores it); effort `resolved_effort: ""`, `runtime_default`, note `not_sent`.

## Modules and seams

### 1. Lead prediction (`workersvc`, `agenttmpl`)

- **Review branch first.** A task-review run never reaches the lead path, so the review prediction is decided before any claim rule: Codex `gpt-6-sol` (`builtin`, `not_configurable`), Claude `""` (`builtin`, `sdk_default`), effort `""` with mode `runtime_default` and note `not_sent` on both. The Claude lane that the review claim still ships is ignored by the reviewer and is never reported. The Codex review built-in lives in a sibling fixture `fixtures/model-settings/task-review.json` (`{"builtins": {"claude": "", "codex": "gpt-6-sol"}}`, D's `summary.json` precedent; built-ins never go into `models.json`), read by a Go test against the `agenttmpl` constant and an agent test against `CODEX_TASK_REVIEW_MODEL`. `review-runner.test.ts` pins that both review passes send no effort and that the Claude pass sends no model. This is F's own seam, not part of H's matrix.
- **Claim part (lead lane).** H's `resolveLeadSettings`, called directly with the inputs `assembleClaim` reads: `Model` / `ModelSource`, `Effort` / `EffortSource` (nil `Effort` is "send nothing", mode `runtime_default`), `DroppedRunModel` (the ignored incompatible pin). `assembleClaim` keeps today's conditional lane read; a test pins that a Codex review claim and a cross-check claim still assemble when the lane read errors.
- **Worker part.** When the claim model is empty, the value is the worker default. Its one Go home is the step `ResolveCrossCheck` already performs with no pins. M1 splits it into one exported `agenttmpl` function, `ResolveWorkerDefaultModel(harness, lane, templateClaude, templateCodex) (model, source)`, sources `user_default` \| `template` \| `builtin`, that `ResolveCrossCheck`, B2's read key and F all call. It **replaces** B2's `codexWorkerDefaultModel` (B2 lands first): M1 deletes that function and repoints B2's read key at `ResolveWorkerDefaultModel`, so only one worker-default function remains. `PinForHarness` is applied **inside** the function, so every caller sees exactly the pin the claim delivers (`agentsFromTemplates` uses the same filter). Template inputs are the cross-check lateral's raw `template_model` / `template_codex_model`. An empty Claude result is `""` in C's cell (`resolved_model` is a string): the SDK or account decides, note `sdk_default`.
- **Not strictly behavior-neutral (accepted).** Today the cross-check Claude path filters a Claude template pin with the curated four; `PinForHarness` filters with the `role` five. A legacy Claude template pin of `gpt-6-luna` (G's write rules reject new ones; "delivery does not rely on" the write-side invariant) is shipped to a Claude checker today and becomes `""` (SDK default) after M1, matching what the lead itself receives. M1 adds a regression test for that row and names the change in the changelog fragment.
- **Cross-language pin.** F appends its lead-lane cases to H's `request_cases` and adds the Go reader, which runs `resolveLeadSettings` plus `ResolveWorkerDefaultModel` on each case; `LEAD_REQUEST_CASES` runs the same list through `resolveLeadRequest` with `selectLeadTemplate`. F's cases, one per behavior not already in the list: no lead template delivered (user overlay disables the lead: SDK default); Claude template `gpt-6-luna` (filtered: SDK default); schedule pin compatible; schedule pin incompatible (lane). "Two lead-shaped names" stays a defensive case only: the reserved-name rule (`LeadNameRe` comment, `assembleClaim` "at most one lead-matching template") makes it unreachable through the API.

### 2. Prediction primitives (`api/internal/workersvc/effective_settings.go`, new)

`workersvc` cannot import `schedsvc` or `handler` (both import it). It therefore exposes primitives only, and the handler composes (§3):

- `(*Service).PredictHarness(ctx, userID, explicit *Harness) (HarnessPrediction, error)`: `resolveRunHarnessQ` (unchanged), plus the rule that fired (from `resolveHarness`, which additionally returns it; callers that do not need it ignore it), a flag when a stored default harness was skipped as unusable, and the credential source and Codex auth mode. Refusals return the create sentinels.
- `(*Service).PredictLead(ctx, userID, harness, frozenModel *string, overrideSubagent bool, review bool) (LeadPrediction, error)`: §1, plus the subagent result. Reads `ListUserCrossCheckPins` (lanes, efforts, both template pins in one statement) and, for subagents, `ListClaimAgentTemplates` through G's projection.
- **Subagents.** Codex with the override on, or Claude with the override on and a non-empty lead: `{mode: "follow_lead", lead_value}`. Otherwise (override off, or Claude with lead `""`): `{mode: "own_pins", lead_value, pinned: [{name, model}], pinned_truncated}`: every allocated own subagent whose `PinForHarness` pin for the harness is set, sorted by name, at most 32; the rest follow the lead (or the SDK default when the lead is `""`). Always note `repo_agents_not_predicted`. Names are `agenttmpl.IsValidName` values (at most 64 bytes, `[a-z0-9-]`).
- Existing exported validators are reused as they are: `ResolveCredentialOverride` (start and schedule override validation), `CheckStoredCredentialOverrideEnabled` (a stored schedule pin).

### 3. Composition (`api/internal/handler/effective_settings.go`, new): the deep module

- **Instance snapshot.** M1 adds `Cache.InstanceModels(ctx, keys []string) (map[string]string, error)` beside C's `InstanceModel`, reading one `snapshot` map with the same trimming, `""` for unset and refusal of secret keys; `InstanceModel` becomes its one-key form. The handler reads every instance model key once per request and passes the values into C's cell-builder helper (judge, summary) and into `ResolveJudgeModel` / `ResolveSummaryModel`. Cache semantics, documented: the snapshot is the cache's current immutable map (TTL). A refresh error serves the last map only while the cache is valid; a cold cache, and any refresh error right after an admin settings write (`Invalidate`), return the error. On that error F follows C's shared posture (instance tier unset, so the built-in), exactly as a claim would, and marks each affected cell with note `instance_settings_unavailable`. A later claim may read a newer snapshot, which `fixed_at: claim` states.
- **No cross-query DB snapshot.** User-scoped values come from the sibling row reads; claim assembly has no snapshot either (D9).
- **GET:** `PredictHarness` for each start choice; `PredictLead` per harness (lead lane and review); judge and summary cells from C's helper, identical to the `GET /me/settings` cells for one snapshot; cross-check cells from `crossCheckPinSettings` mapped onto C's and B's cell fields; `catalog_default` from B2's read for Codex effort cells in `runtime_default` mode.
- **Start-preview:** `PredictHarness(explicit)`, then `ResolveCredentialOverride(kind = issue, resolved harness)`: create's validation without the insert.
- **Schedule-preview.** Request: either a draft, or `schedule_id` (owner-scoped `GetRunScheduleForUser`, 404 otherwise) with optional draft fields that replace the stored ones (absent means "as stored"). Order, as save then fire would apply them:
  1. Save rules, only for fields the request supplies: model syntax (`agenttmpl.ValidateModel`); a supplied override through `ResolveCredentialOverride(scheduleLaneKind(target), scheduleEffectiveHarness(...))`.
  2. Fire rules: harness through `PredictHarness` with the pin as explicit; a stored (not re-supplied) pinned override through `CheckStoredCredentialOverrideEnabled` (deleted inherits, disabled refuses); the codex-override conflict for an unpinned schedule whose override meets a Codex resolution; `PredictLead` with the pin as frozen model and the subagent toggle.
  Fire-rule errors map through `schedsvc.SkipReasonForErr` (exported from `skipReasonForErr`, no behavior change).
- **Errors:** any store error returns 500 with no partial body (D16); an instance-cache error does not (posture above). A nil settings reader (unit fakes only) omits judge and summary cells.
- **Hides:** D11 routing and refusal classification, override validation at save and fire, the review exception, lane, pin, template and built-in precedence, subagent override semantics per harness, judge, summary and catalog-default composition, instance provenance.

### 4. Vocabulary and labels

Three separate named enums on the wire, narrowed per field in the TS types:

- **`source`** (model and effort cells; the shared §1 subset F emits): `schedule_pin`, `user_default`, `template`, `builtin`, `instance_default`, `cross_check_pin`, `cross_check_worker_default`. Cross-check mapping: `pin` to `cross_check_pin`, `worker default` to `cross_check_worker_default`; `CrossCheckPinDTO` is unchanged.
- **`harness_source`:** `run_override` (an explicit start choice), `schedule_pin`, `user_default`, `automatic`.
- **`credential_source`:** `claim_selection` (no override: worker binding, pool or owner default at claim), `auto_selection` (mode `auto`), `owner_default` (mode `default`, or the self-improve lane), `token_override` (mode `pinned`, `fixed_at: create`), `codex_default_credential` (`fixed_at: create`). Codex adds `auth_mode` (`subscription` \| `api_key`). Never an id, label or value.
- **Note codes:** `schedule_pin_ignored`, `sdk_default`, `not_configurable`, `not_sent`, `user_default_harness_unusable`, `issue_labels_may_select_harness`, `repo_agents_not_predicted`, `token_fixed` (self-improve), `instance_settings_unavailable`. Codes only on the wire.
- **Labels:** tokens only on the wire. - **Start-preview request:** `{harness: "claude"|"codex"|null, credential_override: {mode: "inherit"|"auto"|"default"|"pinned", secret_id?: uuid} | null}`. Response `{version, harness (HarnessValueDTO or null), refusal, refusal_detail, credential}`. A `pinned` mode without `secret_id` decodes and returns refusal `credential_override_invalid`, as create's validator answers; a malformed uuid or unknown field is 400.
- **Schedule-preview request:** `{schedule_id?: uuid, target?: issue|sweep|prompt|self_improve|ci_watch, harness?: "claude"|"codex"|null, model?: string|null, override_subagent_model?: bool, credential_override?: same shape|null}`; without `schedule_id`, `target` is required and absent fields mean "not set". Response `{version, harness (HarnessValueDTO or null), refusal, worker_model (model cell), worker_effort (effort cell), credential, subagents, notes[]}`.
- **Refusal enums (closed):**
  - Start (GET and start-preview): `no_credential_for_harness` (create's 422 code; `refusal_detail: credential_disabled` when every credential is disabled), `no_usable_credential`; start-preview adds the override refusals `credential_override_harness_unsupported`, `credential_not_found`, `credential_disabled`, `credential_override_invalid`, each mapped by `errors.Is` from the sentinel create returns. `credential_disabled` therefore appears in two fields with two meanings (a disabled harness slot as `refusal_detail`, a disabled pinned token as `refusal`); clients read the field, never the token alone.
  - Schedule, save step: `credential_not_found`, `credential_override_lane_not_switchable`, `credential_override_harness_unsupported`, `credential_override_invalid`, `invalid_model`. Fire step: `SkipReasonForErr`'s `credential_disabled`, `no_usable_credential`, `codex_override_conflict`, and the hard `no_credential_for_harness`. The save step runs first, so `credential_override_harness_unsupported` is reachable only for a supplied override validated against a pinned Codex harness; a fire-time Codex conflict is `codex_override_conflict`, as the scheduler records. They differ from the start set because the scheduler classifies a disabled pin separately (advance or hold), while create answers one 422.
- **Bounds:** strict decode (`httpx.DecodeJSONStrictBounded`, 1 KiB start-preview, 2 KiB schedule-preview; unknown fields and trailing values rejected); invalid enums and malformed uuids are 400. The board sends no issue list (D2). Response sizes fixed by construction: GET 3 harness values + 12 lane cells + 8 cross-check cells + 2 credential objects, asserted below 16 KiB with every model at `MaxModelLen`; start-preview 1 harness value + 1 credential, below 2 KiB; schedule-preview 1 harness value + 2 cells + 1 credential + at most 32 subagent entries, below 12 KiB with 64-byte names and 100-byte models.
- **Errors:** 401 without auth; 400 on a bad body; 404 for a foreign or missing `schedule_id`; 500 on a store error (no partial body).
