## Problem

uzi is single-provider (Anthropic/Claude) end to end. Every lane — the agent loop (`agent/src/runner.ts`), chat (`chat-executor.ts`), and the judge (`judge-runner.ts:15`) — imports `@anthropic-ai/claude-agent-sdk`, and the worker authenticates only with a Claude credential (`agent/src/sdk-env.ts` sets `CLAUDE_CODE_OAUTH_TOKEN`, pins `ANTHROPIC_*` to undefined). Consequences:

1. A user who holds an OpenAI/Codex subscription, or runs a self-hosted model, cannot use it for agents or the judge.
2. Agents in a run cannot be mixed across providers (e.g. a Claude coder with a GPT auditor, or a local model for cheap read-only roles).
3. The judge cannot run on an independent provider, which is where cross-model review has the most value (a same-model judge shares its subject's blind spots).
4. The only non-Claude path today would be metered OpenAI API keys — the exact cost the team is trying to avoid. Subscription seats (the model that makes uzi economically viable for Claude) have no equivalent for other providers today.

## Solution

A provider abstraction where a **provider is "a model harness + an auth profile"**, driven by **dedicated provider-pinned workers**. The **existing Claude/Anthropic subscription path is preserved exactly as today** (D0) and becomes the reference adapter; everything else is additive. There are **three harnesses**:

- **Claude harness** (`@anthropic-ai/claude-agent-sdk` / Claude Code) — Anthropic, via a subscription OAuth seat or an API key. **Unchanged from today.**
- **Codex CLI harness** — Codex/OpenAI and any **Responses-API** endpoint, via the CLI's `model_providers` config (`base_url` + `env_key` + `wire_api="responses"`): a Codex/ChatGPT subscription seat, an OpenAI API key, or a Responses-API-speaking compatible/self-hosted endpoint.
- **Native chat-completions executor** — for **Chat-Completions-only** endpoints the Codex harness cannot reach (Ollama, LM Studio, and many OpenAI-compatible/local runtimes). Added per finding 1 (the `wire_api="responses"` constraint), because those endpoints are exactly the local/privacy path Success Criterion 4 promises.

Provider mixing becomes a **scheduling** property, not a session one: a **cross-provider** subagent is a provider-routable **sub-run** claimed by a worker whose capability matches its provider; **same-provider** subagents keep today's in-SDK orchestration (D12, hybrid). The "main is never touched" guardrail is lifted into a **provider-neutral contract with a shared conformance suite** that the Claude hook, the Codex sandbox, and the native executor must each pass.

### Provider matrix

| Class | Harness | Auth mode(s) | Cost model |
|---|---|---|---|
| Anthropic (Claude) | Claude Agent SDK | subscription OAuth seat (`CLAUDE_CODE_OAUTH_TOKEN`); or Anthropic API key | subscription (flat) or metered |
| OpenAI / Codex | Codex CLI | Sign in with ChatGPT (seat, via portable `~/.codex/auth.json`); or OpenAI API key | subscription (flat) or metered |
| OpenAI-compatible | Codex CLI if the endpoint speaks the **Responses API**; otherwise the **native chat-completions executor** | provider API key (OpenRouter, Azure OpenAI, DeepSeek, Together, Groq, internal proxy) | metered (varies) |
| Self-hosted / local | **Native chat-completions executor** (Ollama/LM Studio are Chat-Completions-native; Codex CLI only if the runtime exposes Responses) | none, or a local key | zero marginal cost, no external egress |

Which harness a compatible/local endpoint uses is decided by an **M0 endpoint-capability probe** (finding 1), not assumed — the matrix promises coverage the probe must first confirm.

The subscription seat is headless-injectable for both vendors (`CLAUDE_CODE_OAUTH_TOKEN` for Claude; a copied `~/.codex/auth.json` or `codex login --device-auth` for Codex), which is what makes the "seat in a worker" pattern viable on both sides.

## Prior art

Per the repo's inspiration-first rule, the three prior-art projects and comparable tools were read (code, not READMEs; 2026-08-04) before locking the design. They confirm this PRD's central premise and supplied three patterns adopted below.

- **bottega** (`inspiration/bottega`, the closest analog — web orchestrator, plan→impl⇄review→PR, multi-user): a provider **registry behind one `LlmProvider` interface** (`reference/server/services/providers/registry.ts:23-25`, `types.ts:29-55`), Claude via the Agent SDK + per-user OAuth token (`claudeCredentials.ts`), Codex via **`@openai/codex-sdk`** (`providers/openai/index.ts:10,83,92`) with a **per-user `CODEX_HOME`/`auth.json`** and global auth env stripped (`codexCredentials.ts:1-34,148-188,314-323`), all normalized to one `UnifiedMessage` stream, per-conversation provider tag, and an explicit capability matrix (Codex path lacks canUseTool/MCP/images/thinking, `startCodexConversation.ts:22-30`). This is the template; D7/D9/D15/D17 copy from it.
- **multica** (`inspiration/multica`): pure CLI-subprocess orchestrator across ~18 coding CLIs; **manages no tokens** — auth lives entirely in each CLI (*"Multica never receives login tokens from Claude, Codex, or any other CLI"*). Confirms the seat is only reachable through the CLI.
- **dot-agent-deck** (`inspiration/dot-agent-deck`): Rust TUI running CLIs in PTY panes; per-role `command` string; installs hooks into each CLI, no auth management.
- **The premise is confirmed**: Codex/ChatGPT-subscription auth **requires the `codex` binary** — `@openai/codex-sdk` is itself a JSONL-over-stdio shim that spawns it; OpenAI ships no HTTP/SDK path for subscription tokens. The only counter-example is opencode's *unofficial* community plugin reverse-implementing OpenAI's OAuth against an undocumented endpoint — noted and rejected as a dependency. So uzi's Claude=SDK / Codex=subprocess asymmetry is not a quirk of uzi; it is inherent and matches every project that supports both.

Sources: [@openai/codex-sdk](https://www.npmjs.com/package/@openai/codex-sdk), [Codex SDK README](https://github.com/openai/codex/blob/main/sdk/typescript/README.md), [Codex auth docs](https://developers.openai.com/codex/auth), [opencode-openai-codex-auth (rejected)](https://numman-ali.github.io/opencode-openai-codex-auth/).

## Decision log

- **D0 — The Claude/Anthropic path is preserved unchanged; this is a behavior-preserving refactor, not a rewrite.** uzi keeps working exactly as today on a Claude subscription: a run with no provider selected resolves to Claude-as-today, with the same seat auth (`CLAUDE_CODE_OAUTH_TOKEN`), the same in-SDK orchestration, the same guardrails. The existing worker path becomes the reference `RunExecutor`/`JudgeModel` adapter by **extraction behind a port**, not modification. Every other provider is additive. Per the repo rule "ALWAYS confirm before changing existing functionality," the invariant is that no existing-behavior test changes — see Success Criterion 0.
- **D1 — Three harnesses (revised from "two only" per finding 1).** Codex CLI via `model_providers` covers Codex/OpenAI seats/keys and any **Responses-API** endpoint; a **native chat-completions executor** covers Chat-Completions-only endpoints (Ollama, LM Studio, many compatible/local runtimes) that Codex — which since Feb 2026 requires `wire_api="responses"` — cannot reach. The original "two harnesses / one non-Anthropic mechanism" goal was buying adapter-count savings with coverage the matrix already promises; the honest cost is two non-Anthropic guardrail surfaces (Codex sandbox + native executor's own confinement) instead of one. An **M0 endpoint-capability probe** decides, per target endpoint, which harness applies and shrinks the advertised matrix to what actually passes. Verified 2026-08-04: Codex reads `~/.codex/config.toml` `[model_providers.<id>]` with `base_url`/`env_key`/`wire_api` on every invocation. **The Codex adapter drives the binary via `@openai/codex-sdk`** (a typed JSONL-over-stdio shim that spawns the native `codex` binary), not hand-parsed `codex exec` — bottega's approach; it gives typed streaming while keeping the subprocess the subscription seat requires (see Prior art).
- **D2 — A provider is explicit `{harness, auth_profile, base_url?, model}`, never inferred from the model-id prefix.** Prefix-sniffing (`claude-*` vs `gpt-*`) is brittle across gateways and Azure deployment names. Routing is an explicit field.
- **D3 — Subscription is the default cost mode where a vendor offers one** (Claude, Codex); API key, OpenAI-compatible, and local are additional modes, not the primary. This keeps the cost goal central: the reference deployment runs on seats, not meters.
- **D4 — Provider = a worker capability.** Dedicated provider-pinned worker pools, scheduled on PRD #84's capability-aware claim. Each worker is single-harness, single-credential.
- **D5 — A subagent is a provider-routable sub-run.** The lead stays an agent on its own provider; its "spawn subagent" tool is intercepted by uzi and turned into a sub-run dispatched to the matching pool, with the structured result returned as the tool result. uzi owns routing; the model owns reasoning.
- **D6 — Split by the resolved TOOLS ALLOWLIST, not the role name (corrected per finding 5).** The earlier draft keyed this off role names and mislabeled `tester` read-only; the code (`agents.ts:16-45`) is emphatic that read-only is a property of the *resolved tools allowlist*, the roster is user-customizable, and a malformed null-tools template **inherits all tools**. So the split is computed at dispatch from the resolved allowlist: a subagent whose allowlist contains no write/mutation tools fans out freely cross-provider; anything else — including inherit-all/malformed — is treated as **mutating** and serialized against the canonical tree (co-located shared volume or patch-return). The measured read-only set as of 2026-08-03 was `{reviewer, auditor, fact-checker, researcher, web-ux}`, but that is an observation, not the rule. Read-only fan-out is the low-risk beachhead and delivers most of the mixing value — subject to the M3 shared-tree decision in D14.
- **D7 — Ports-and-adapters, no translation gateway.** `RunExecutor` and `JudgeModel` ports; core (protocol, `run_messages`, approval gate, sweeper, triage) talks only to the ports. Reject the `ANTHROPIC_BASE_URL`→LiteLLM masquerade: it makes OpenAI pretend to be Anthropic and loses native fidelity. The abstraction lives at uzi's boundary, not the wire protocol.
- **D8 — The guardrail is a provider-neutral contract with a shared conformance suite.** "main is never touched" (deny `git push`, history rewrites, credential reads, incl. shell-wrapper evasion) is defined once; each adapter maps it onto its mechanism (Claude `PreToolUse` hook; Codex sandbox + approval mode) and must pass the same adversarial deny suite, in the style of the repo's cross-module wire-contract goldens. No adapter ships un-certified.
- **D9 — Credentials are typed secret kinds / profiles** in the existing vault/secretbox: a Claude seat, an Anthropic key, a Codex seat, an OpenAI key, and an OpenAI-compatible profile (`{base_url, env_key, model, wire_api}`). The `sdk-env` protected-keys sandbox and PRD #111's pool/auto-select generalize to be provider-aware; Codex credentials are injected via `env_key` and a **per-user/per-worker private `CODEX_HOME`** holding its own `auth.json`, with global `OPENAI_API_KEY`/`CODEX_HOME`/`CODEX_API_KEY` stripped so per-user auth wins (bottega's `codexCredentials` pattern). `auth.json` holds *either* an OAuth seat *or* an API key in the same slot, so subscription and metered key are one code path.
- **D10 — Admin base-URL allowlist for OpenAI-compatible and local endpoints** (mirrors `FORGE_ALLOWED_BASE_URLS`). Repo contents are sent to the model endpoint, so an arbitrary `base_url` is an exfiltration channel. Only allowlisted (and ideally in-cluster/local) endpoints are permitted. Local/self-hosted is the safest posture and is called out as the recommended privacy path.
- **D11 — Usage/cost accounting is provider-aware** (extends ADR-0195's per-model fold to carry provider). Local/self-hosted is a zero-marginal-cost lane; the pool's rate-limit-headroom logic must not assume Anthropic semantics.
- **D12 — Hybrid orchestration (decided per finding 3, was "lean uniform").** Same-provider subagents keep today's in-SDK `AgentDefinition` orchestration; only **cross-provider** subagents become sub-runs. The in-process machinery carries real security properties (the `run_in_background:false` force for #34, the turn-boundary reap for B1, the plan-turn write-strip #203, the signal/memory denies) that a uniform sub-run model would have to re-derive at a new boundary for no benefit on same-provider runs. Sub-runs are used only where a provider boundary genuinely prevents in-SDK delegation (a GPT subagent cannot run inside a Claude `query`). This also means D0's "Claude path unchanged" holds for pure-Claude runs by construction — they never touch the sub-run path.
- **D13 — The judge gains an independent-provider option.** It is a single structured-output call (all harnesses do JSON-schema output natively) with **no tools** (deny-all hook), so its guardrail-conformance surface is vacuous — which is exactly why it is the cleanest place to prove the port and why M1 precedes M3. Cross-model review is intrinsically valuable.
- **D14 — Read-only cross-provider review works against forge-fetched COMMITTED state, not the live worktree (resolves a missing decision from finding 3).** A reviewer running as a separate sub-run on a separate provider-pinned worker cannot see the coder's uncommitted worktree without the shared-tree primitive M4 defers. So M3's cross-provider read-only roles review the **MR diff / fetched committed state**; the in-loop reviewer↔coder cycle over the live worktree stays same-provider (in-SDK) until M4. This keeps M3 genuinely free of M4's hard problem.
- **D15 — The Codex/native `model_providers` config and credentials are provisioned worker-side and read-only to the agent uid (resolves a missing decision from finding 6).** The Bash guard has no filesystem-write rule and `~/.codex` lives outside the worktree jail, so allowlist enforcement cannot rely on agent good behaviour. Containment is the existing uid split: config is worker-owned `0444`, the agent runs as `runner`, and cannot rewrite `base_url`. Allowlist enforcement happens at provisioning; the uid boundary prevents runtime rewrite. This must be a named layer, not implied. The private `CODEX_HOME` (D9) is the same containment surface — worker-owned, agent-unwritable — and the reason uzi never reads the global `~/.codex` (bottega does likewise).
- **D17 — A provider capability matrix drives graceful degradation (adopted from bottega).** Harnesses are not feature-equal: bottega's Codex path has no `canUseTool` (interactive tool-permission callback), MCP, image input, or thinking-token deltas that the Claude SDK provides. So each adapter declares its capabilities, and (a) a subagent whose role needs a capability its target provider lacks is not routable there — the dispatcher rejects the assignment rather than silently degrading, and (b) the guardrail contract (D16) accounts for the fact that a missing `canUseTool` means the deny decision must be enforced by the sandbox/uid layers, not an in-loop callback. The matrix is part of the M0 ADR and is consulted at dispatch alongside the tools-allowlist split (D6).
- **D16 — The guardrail contract adds a repo-isolation clause covering `settingSources: []`'s intent (resolves finding 3, security-critical).** "The cloned repo cannot alter the harness's model/tools/approval/egress config or inject instructions." Codex walks up to `.git` and loads `AGENTS.md` prose (a live injection vector) even though it ignores project-local `sandbox_mode`/`approval_policy`/`model_providers`; the Codex adapter must neutralize `AGENTS.md`/`.codex` discovery. The conformance suite asserts *outcomes* per clause across all three harnesses (a pure predicate on the Claude side, live-execute-under-confinement on the others), with one adversarial fixture per clause and a per-adapter "this clause was exercised" assertion, plus a written clause-to-layer map (which of the four independent layers satisfies each clause differs per harness). Per the repo rule, no layer is dropped on the theory another covers it.

## Success criteria

0. **No regression (D0)**: with no provider configured, uzi behaves exactly as today on a Claude subscription — same auth, orchestration, and guardrails; no existing-behavior test changes. This is the gating criterion; the feature ships dark until it holds.
1. A single run's agents can span Anthropic + Codex + a local model, chosen per agent, with the mixing happening at the scheduler.
2. The judge runs on a provider independent of the agents under review.
3. Where a vendor offers a subscription, runs consume a **seat** (flat cost), not a metered key — verified for both Claude and Codex.
4. A self-hosted/local endpoint runs a full role with **no external egress** of repo contents.
5. The guardrail conformance suite passes for every adapter; "main is never touched" is demonstrated per provider, not assumed from the Claude path.
6. No arbitrary `base_url` is reachable — only admin-allowlisted endpoints (D10).

## Risks

- **R1 — Subscription-for-factory-use is a gray area for BOTH vendors, and the risk is symmetric, not Codex-specific** (verified 2026-08-04). The axis is not the vendor but "one human, one subscription, one beneficiary." **Anthropic** has the *explicit* rule: subscription OAuth tokens are for its own products, with a narrow carve-out for single-beneficiary automation (CI on your own repo); production/shared/multi-tenant use must use **API keys** (Commercial Terms). **OpenAI** is vaguer — API keys are the "recommended default for automation," no explicit prohibition found, governed by the general ChatGPT Terms. So uzi's *existing* Claude-seat usage is itself defensible only under the one-beneficiary carve-out, and Codex is no worse. *Mitigation (load-bearing, and it covers both providers)*: uzi is strictly **per-user-own-token, per-user-own-work** — each user brings their own seat and it only ever acts on that user's own runs; uzi must never pool one subscription across users. The metered **API-key mode is the always-legal fallback** if either vendor's seat terms tighten. Seats remain per-human with capped rolling windows, so per-seat parallelism accounting is Q3. **Decision recorded (user, 2026-08-04): proceed assuming seats are permitted under the one-beneficiary model, with API keys as the documented fallback and a per-provider ToS re-check a precondition of GA — not of prototyping.** R7 tracks that re-check.
- **R2 — Data egress.** Repo code is sent to whatever endpoint a provider names; an arbitrary `base_url` is an exfiltration channel. *Mitigation*: D10's admin allowlist; prefer in-cluster/local; a threat-model writeup (M6) in the style of `docs/vault-threat-model.md`.
- **R3 — Guardrail parity.** The Codex sandbox must be proven equivalent to the Claude deny-hook. *Mitigation*: the shared conformance suite (D8) gates each adapter; no adapter ships without it green.
- **R4 — Harness fidelity divergence.** Codex tooling/output differs from the Claude SDK; the sub-run handoff must normalize into uzi's `run_messages` stream and honor pause/resume. *Mitigation*: drive Codex via `@openai/codex-sdk`'s typed JSONL streaming rather than parsing `codex exec` stdout (D1), and normalize every harness to one message shape the way bottega's `UnifiedMessage` does; plus an explicit, versioned handoff contract (part of M3). D17's capability matrix bounds what divergence a given role can tolerate.
- **R5 — Shared working tree** for mutating cross-provider subagents is the genuinely hard sub-design (M4), deferred behind the read-only beachhead on purpose.
- **R6 — `wire_api` coverage (resolved into D1).** Codex requires `wire_api="responses"`, which Ollama/LM Studio and many compatible endpoints do not speak. *Resolution*: the native chat-completions executor (D1, third harness) covers them, and an M0 endpoint probe decides per endpoint. No longer an open risk — it is a scoped deliverable.
- **R7 — ToS/licensing** for automated code generation varies by provider and by subscription tier; must be checked per provider before it is offered as supported.

## Review findings

Architectural review by the architect role, 2026-08-04, against HEAD `660c26c0`. Claims below were verified against the tree and against the Codex CLI's current behaviour, not judged in the abstract. Verdict scale: **sound** / **needs-work** / **wrong**.

### Per-section verdicts

**1. Harness/provider claims — SOUND (verified).** Every claim in the Problem section checks out. `agent/package.json:18` carries exactly one model dependency (`@anthropic-ai/claude-agent-sdk@0.3.219`); a `grep -rli "openai\|codex"` across `agent/src` returns nothing. `sdk-env.ts:29-34` pins `PROTECTED_ENV_KEYS = {CLAUDE_CODE_OAUTH_TOKEN, HOME, ANTHROPIC_API_KEY, ANTHROPIC_AUTH_TOKEN}` and `:87-88` sets the two `ANTHROPIC_*` keys to `undefined` — the "OAuth seat, `ANTHROPIC_*` pinned undefined" claim is exact. The judge is confirmed a single structured-output call: `judge-runner.ts:249-307` (`consumeModel`) runs one `queryFn`, breaks on the first `isResult`, with a deny-all `PreToolUse` hook and `settingSources: []` — no tools, no worktree, JSON out. This is genuinely the cleanest lane to prove a port (see M1 verdict).

**2. Two-harness synthesis (D1) — NEEDS-WORK; R6 is under-ranked and threatens two of four provider classes.** The "one harness, `model_providers` config" mechanism is real: Codex reads `[model_providers.<id>]` with `base_url`/`env_key`/`wire_api`. But the `wire_api="responses"`-only constraint is not a per-endpoint footnote — as of Feb 2026 Codex **removed** `wire_api="chat"`; custom providers must speak the OpenAI **Responses** API, which most OpenAI-compatible and local runtimes do **not** implement (Ollama and LM Studio are Chat-Completions-native; DeepSeek/Together/Groq/Azure vary). So the matrix rows "OpenAI-compatible" and "Self-hosted/local" — and Success Criteria 4 (local, "the recommended privacy path") — rest on a capability many target endpoints lack. R6 files this as "verify per endpoint in M2" and Q2 as a scope question; it is really a **structural** hole in D1's "two harnesses cover everything non-Anthropic." Recommendation: do not treat "two harnesses only" as settled. Either (a) gate the OpenAI-compatible/local matrix rows on a pre-M2 Responses-API probe of the *specific* endpoints you intend to support (and shrink the matrix to what passes), or (b) accept a third, native chat-completions executor for the local/compatible lane. A native OpenAI-Agents-SDK executor is the honest best-practice option for chat-completions endpoints; the PRD's argument for avoiding it (minimize adapter count / collapse guardrail surface) is sound *for seats*, but it is buying harness-count savings with coverage the matrix already promises. Make the coverage claim follow the probe, not the other way round.

**3. Sub-run / subagent routing (D5/D6) — NEEDS-WORK; D6's read-only/mutating split is factually off against the roster, and D5's "uniform" lean (D12) is the wrong default.** Today subagents are in-SDK `AgentDefinition`s inside one `query` (`agents.ts:103-181`); the lead's spawn is the SDK `Agent` tool, intercepted by `buildAgentGuardHook` (`guardrails.ts:616-647`) which forces `run_in_background:false` for synchronous in-turn delegation (#34) and the executor reaps the tree at the turn boundary (B1). That in-process machinery is what makes B1, #34, the plan-turn write-strip (#203, `agents.ts:311-332`), and the signal/memory server denies work. Moving orchestration into uzi as claimable sub-runs re-derives every one of those security properties at a new boundary — it is over-reach **for same-provider runs**, and defensible **only** where a provider boundary genuinely prevents in-SDK delegation (a GPT subagent cannot run inside a Claude `query`). So Q1/D12 should **flip to hybrid**: keep in-SDK subagents for same-provider fan-out, use sub-runs only across providers. "Give up the SDK's free orchestration" undersells what is given up — it is the guardrail-carrying orchestration, not just scheduling.
   - D6's partition is **wrong as written**. It lists `tester` as read-only ("already report-only"); `agents.ts:27` states tester *declares write tools* (with architect, documenter, spec-keeper), and the measured read-only set (`agents.ts:20-22`, 2026-08-03) was `{reviewer, auditor, fact-checker, researcher, web-ux}` — tester is not in it, and `web-ux` (omitted by D6) is. More structurally: `agents.ts:16-45` is emphatic that read-only is a property of the resolved **tools allowlist**, never the role name, that the roster is user-customisable, and that a *malformed* custom template with null tools **inherits all tools** (accepted residual, :39-45). A cross-provider fan-out that keys "may I run this read-only, unserialized, on any worker?" off the role *name* re-opens exactly that residual as a routing decision. Derive the split from the resolved allowlist at dispatch, and treat inherit-all as mutating.
   - Hidden dependency: even **read-only** cross-provider roles need the tree they review. The in-loop reviewer↔coder cycle reviews the coder's *uncommitted worktree*; a reviewer running as a separate sub-run on a separate provider-pinned worker (D4: single-harness, single-credential) cannot see it without the same shared-tree primitive M4 defers (R5). D6's "read-only fan-out is the low-risk beachhead" holds only if M3's reviewer reviews *forge-fetched* committed state (the MR diff), not the live worktree. State which, because it changes whether M3 is actually free of M4's hard problem.

**4. Scheduling reuse — NEEDS-WORK; the primitives are the right ones but two of three are not as ready as cited.** #84 (Decision 4, bounded server-owned capability enum) is the correct home for "provider as capability" (D4) — but #84 is **Draft, not landed**, so M2's "provider-pinned pools on #84" depends on unshipped work; say so. Note also #84 Decision 7 is explicit that capability matching is "best-effort scheduling, **not** a security boundary" — since D8 makes the guardrail *mechanism* provider-dependent, provider-routing is security-adjacent, and the reconciliation is that the **credential** (M2/D9), not the capability tag, is the real bind (a worker holds exactly one provider credential and cannot execute against a provider it has none for). Make that explicit so a spoofed capability tag can't be read as a guardrail bypass. #111 is cited as "generalizes to seats," but #111 is Anthropic-shaped to the bone (the `anthropic_rate_limits` gauge, `runs.anthropic_secret_id`, the 5h/7d window ranking) **and** explicitly scoped the judge lane *out* (D4: "Extending auto to the judge lane is a clean follow-up, explicitly out of scope"). What genuinely reuses is the **seam** (one resolution site, `claimSecretID`→`workerSecretID`) and the per-run-credential-record pattern — not the ranker. So M1 (judge, auto-select across providers) must do two generalizations #111 deferred at once; budget it as new work, not reuse. #58 is DONE and its worker-type=image + S/M/L presets fit, but #58 provisions **static, persistent** workers (autoscaling/scale-to-zero/spawn-on-demand are explicit non-goals) — the word "pool" in D4/M2 overstates it, and a Codex-harness worker is a **new worker image** (Codex CLI + sandbox baked in), a real new artifact #58 does not give you for free.

**5. Guardrail contract (D8) — NEEDS-WORK; direction is right, the enumerated contract is INCOMPLETE, and the two mechanisms are not homomorphic.** Lifting "main is never touched" into a provider-neutral contract + conformance suite is the correct architecture, and demonstrating per-provider rather than assuming from the Claude path is exactly right (Success Criterion 5). Three concrete problems:
   - **The contract D8 enumerates drops a whole layer.** The project's primary directive is four independent layers; D8 lists the Bash-deny layer's clauses (push, history rewrite, credential read, shell-wrapper evasion) but is **silent on `settingSources: []`** — the repo-borne-injection defense. Verified: Codex *does* load repo-borne instructions — it walks up to the `.git` root and reads `AGENTS.md` and `.codex/config.toml` before working. The saving grace is partial: Codex **ignores** `model_provider(s)`, `approval_policy`, `sandbox_mode`, `profile(s)` when set in *project-local* config (so a cloned repo cannot downgrade the sandbox), but `AGENTS.md` **prose instructions are still loaded**. So the Codex adapter must explicitly neutralise repo `AGENTS.md`/`.codex` discovery, and D8's contract must add a clause "the cloned repo cannot alter the harness's model/tools/approval/egress config or inject instructions." Per this repo's own rule ("never weaken one layer on the theory another covers it; escalate"), this is not optional.
   - **The two mechanisms cannot share one literal suite.** The Claude side asserts a **pure, synchronous** function (`screenBashCommand`, `guardrails.ts:525-531`) with no live session — that is why the existing suite is cheap. The Codex sandbox is an **OS-level** seatbelt/landlock filesystem+network confinement enforced at runtime; you cannot assert it as a pure predicate. The "shared conformance suite" must therefore be two harnesses asserting the same *outcomes* (static assertion vs live-execute-under-sandbox-and-observe-denial), not the same assertions. Name that, and author the fixture to **discriminate** per contract clause (one adversarial case per clause: `git push`, `git -C x push`, `sh -c 'git push'`, `git config --get`, `Read /proc/<pid>/environ`, base64|sh) with an assertion that each clause is actually exercised on each adapter — otherwise a green suite is a snapshot of the Claude screener's blind spots re-run against a sandbox that answers "denied" for an unrelated reason (network-off).
   - **Clause-to-layer mapping differs per provider and must be written down.** The Codex sandbox denies *by workspace-write + network-off*, not by git subcommand. It does **not** deny `git config --get` or `Read /proc/.../environ` (reads are broadly allowed); those are covered on uzi's real topology by the **uid split + mount-ns** layers (`sdk-env.ts:110-134`, `guardrails.ts` path-guard header), which are provider-independent and survive. That is fine — but D8 must map each contract clause to the layer that satisfies it *for each harness*, rather than implying one mechanism covers all. There is a real risk the Codex sandbox "can't express an equivalent deny policy" for the semantic clauses; the answer is that it doesn't have to, provided the uid/mount-ns layers and the credential-absence are proven present on the Codex worker too.

**6. Egress (D10/R2) and ToS (R1) — D10 SOUND but with a missing enforcement-point analysis; R1 UNDER-STATED and it threatens the PRD's economic premise.** D10 mirroring `FORGE_ALLOWED_BASE_URLS` (https-only, SSRF guard) is the right pattern. But the enforcement point differs from the forge case: the forge base_url is dialed by the **API** (sole secret-holder); the model base_url is dialed by the **worker/Codex-CLI** from `~/.codex/config.toml`. A prompt-injected agent under the Codex harness can rewrite that config — `guardrails.ts:98-105` documents that the Bash guard has **no filesystem-write rule** (`echo >`, `sed -i`, `tee` all pass) and the path-guard only jails the *worktree*, while `~/.codex` is in HOME outside it. Containment exists (the uid split: config is worker-owned, agent runs as `runner`, so a worker-owned `0444` config is unwritable to the agent) but the PRD never names it. Add a decision: "the Codex `model_providers` config is provisioned worker-side and read-only to the agent uid; allowlist enforcement is at provisioning, and the uid boundary — not agent good behaviour — prevents runtime rewrite." Without it, D10's allowlist is enforced only where the agent can edit around it. **R1**: honest about OpenAI's API-keys-for-automation guidance, but the mitigation ("it is one human's seat") does not address the real hazard — automation-detection account bans do not care whose seat drove them, and headless injection of `~/.codex/auth.json` into a server worker is a grayer ToS area than Anthropic's officially-documented `CLAUDE_CODE_OAUTH_TOKEN`. If a per-provider ToS check (R7) finds Codex seats may not drive server automation, **D3's "subscription is the default cost mode" collapses for the non-Anthropic side**, and with it the Problem's premise #4 (seats are what make non-Anthropic economically viable). This is strategic, not a footnote: verify Codex-seat ToS **before** M1 commits to a Codex seat, and record what the cost model degrades to (metered keys) if it fails.

**7. Milestone sequencing — NEEDS-WORK; M1 has hidden dependencies on M2, though judge-first is otherwise the right beachhead.** Judge-first is a genuinely good call for one under-stated reason worth making explicit: the judge runs **no tools** (deny-all hook), so the entire guardrail-conformance surface (M3's first-class deliverable) is **vacuous** for it — M1 proves the `JudgeModel` port and a Codex adapter without owing the security suite. That should be stated as the reason M1 precedes M3, not left implicit. But M1 as written ("the judge runs on a Codex seat, OpenAI key, OpenAI-compatible endpoint, **or a local model**") depends on machinery the PRD schedules *after* it in M2: the typed Codex secret kind + `env_key`/`auth.json` injection (D9) and — critically — the **base-URL allowlist (D10)**. The judge ships repo-derived trace content to the endpoint (`judge-runner.ts` warns the trace "may contain third-party secrets"), so offering an OpenAI-compatible/local judge endpoint *before* D10 exists is an egress hole. Fix: pull a minimal credential-injection + allowlist slice out of M2 to land with or before M1, or narrow M1's first cut to the **seat/API-key** modes (fixed vendor endpoint, no arbitrary base_url) and defer the compatible/local judge to after D10. M3-before-M4 (read-only before mutating) is correctly ordered; the only caveat is the shared-tree dependency noted in section 3.
