# PRD #1247: Per-run Anthropic token selection: choose at start, switch while parked, at the gate, or mid-run

**Issue**: #1247
**Priority**: Medium
**Status**: Planned
**Builds on**: PRD #104 (named tokens, worker binding), PRD #111 (auto-select by headroom, `runs.anthropic_secret_id`), PRD #217 (do not re-pick the just-exhausted token, `limit_dead_secret_id`), PRD #754 (auto lane is pooled-only, `pool_wait`, one-owner-per-tick pool resume), PRD #1190 (owner pause), PRD #759 / #1062 (checkpoint + resume-in-place across a limit park), PRD #1079 (per-leg usage fold), PRD #1140 (auto bind mode default), PRD #1349 (recovery custody: `runs.claim_generation`, verified restore points).

## Problem

Which Anthropic credential a run spends is a **worker** property (`workers.anthropic_bind_mode` + `workers.anthropic_secret_id`, migrations `00078`/`00088`), resolved once per claim by `claimSecretID` (`api/internal/workersvc/secretchoice.go:300`) and shipped once in the claim payload (`claim_assembly.go`, wire field `anthropic_oauth_token`; `agent/src/protocol.ts:550` "the claim payload is the only delivery path"). The agent sets it as `CLAUDE_CODE_OAUTH_TOKEN` for the whole run (`agent/src/runner.ts`, `agent/src/sdk-env.ts`). There is no per-run choice and no way to change it once claimed.

Observed 2026-09-15 on the dev instance: four runs (two issue runs, one `mr_rework`, one `prompt`) parked in `limit_wait` on **token A** (`rate_limit_type: seven_day`, `retry_not_before` ~7 h out) while **token B** sat pooled and `eligible`. Every available verb refused: `uzi run pause` ("the clock is already stopped"), `uzi run resume` and `uzi run resume-now` ("run is limit_wait"; server-side 409, not a CLI gap). Pinning the worker to token B (`uzi worker set-token`) is accepted but "takes effect on the worker's next claim", and nothing forces that claim before `retry_not_before`. The only lever was destructive: cancel and recreate.

Three distinct gaps:

1. **No manual control.** A user cannot start a run on a chosen token, cannot switch a parked run onto a token with headroom, cannot switch at the plan gate, and cannot switch a running run.
2. **Auto-failover is a one-shot decision.** `decideLimitPark` Decision 6e (`api/internal/workersvc/limitwait.go:370`) already lowers the park to "now" when `autoselect.NextAvailable` finds a pooled alternative, but only **at park time**. A token pooled, or a gauge that turns eligible, *after* the park is never re-asked; the run sleeps until `retry_not_before` regardless. That is what happened above: token B became spendable after the park and nobody re-evaluated.
3. **6e ignores how the next claim will resolve.** `limitwait.go:373` lowers the park from any pooled alternative even when the claiming worker is pinned or default-bound, so the promoted run re-parks on the same token and burns `RUN_LIMIT_MAX_WAITS`. Pre-existing for worker pins; newly relevant once a run can carry its own pin.

## Goal

1. **Auto-failover while parked** (no human): a `limit_wait` run whose next claim resolves through the `auto` selector is promoted as soon as a pooled alternative becomes eligible, not only at park time; a run whose next claim is pinned is never promoted early, at park time or later.
2. **Per-run credential override**: choose the token at `run create` (CLI + web + schedule), switch it on a parked or queued run (promotes immediately), switch at the plan gate, and switch a running run. One override, one precedence ladder, one verb whose behaviour depends on run state.

### Non-goals

- **Cross-harness switching (Claude ⇄ Codex).** A token switch keeps the harness and the SDK session. Codex is a different runtime (app-server, own transcript format, own guardrail conformance per PRD #1287, own credential lifecycle with `POST /api/worker/runs/{id}/codex/{release,refresh}`); no session resume exists across harnesses. A cross-provider move is a **harness handoff at a restart boundary** (plan gate or milestone boundary, cold-started from the approved plan + milestone state, the shape the seeded-plan path and durable recovery already have). That is a separate PRD under #229 / #1106 after #1106 M5B. This PRD keeps the override column provider-neutral (D9) and makes the unsupported case an explicit error, which is the only cheap slice.
- **Zero-interruption hot swap.** The SDK subprocess owns its env; a live token cannot be replaced without an interrupt. True seamless switching is PRD #50 (LLM egress proxy: the worker never holds the token). This PRD works without #50 and becomes seamless with it.
- **Chat lane** (deliberately unbindable, `secretchoice.go:124`), **judge lane** (own binding, PRD #1140) and the **`self_improve` lane** (follows the judge binding, `secretchoice.go:301`) are unchanged; the verb refuses them rather than writing an override their ladder would ignore (D10).
- Token CRUD stays web-only (PRD #104 D8); this PRD only re-points spend among tokens the caller already owns, the same class as `uzi token pool`.

## User impact

- A run parked on an exhausted account resumes by itself when another pooled account has headroom (auto workers), or in one command / one click otherwise: `uzi run set-token <run-id> <label>`.
- `uzi run create --token <label>` (or `--token auto`) and the same picker in the web start dialog and the schedule modal: the run spends that token from its first turn, whatever the worker is bound to.
- At the plan gate: pick the token for the implementation phase before approving.
- On a running run: switch, losing at most the in-flight step (the UI says so).
- Every surface that shows the run's token (run page, `uzi run get`, TUI crew rail per #623) shows the current token, a pending switch (requested / released, awaiting reclaim), and the history of applied switches.

### Data (draft migration `00230`; renumbered above the live head at merge; additive only)

- `runs.credential_override_mode TEXT NULL CHECK (IN ('pinned','auto','default'))`, `runs.credential_override_secret_id UUID NULL REFERENCES user_secrets(id) ON DELETE SET NULL`. NULL mode = inherit the worker binding (today's behaviour, back-compat by construction). A `pinned` mode whose id was nulled by a token delete resolves as inherit (D1).
- **The claim generation is the existing `runs.claim_generation BIGINT`** (migration `00223`, PRD #1349): `ClaimRun` increments it atomically with the recovery custody hold it opens (`runtime.sql` "ClaimRun"). This PRD adds no generation column and never increments it outside `ClaimRun`; every new column, param and DTO field that carries it is `BIGINT` / `int64`.
- `runs.claim_released_at TIMESTAMPTZ NULL`: the released-claim fence (D3). Set by the release transition, cleared by `ClaimRun`.
- `runs.credential_switch_requested_at TIMESTAMPTZ NULL`, `runs.credential_switch_generation BIGINT NULL`: a pending held-state switch and the claim it targets (D4). Independent of the pause columns (D11).
- `run_credential_epochs (run_id, claim_generation BIGINT, secret_id UUID NULL, label TEXT, select_reason TEXT, applied_at)`: one row per claim, written by `recordRunCredential` after a successful open. The attribution journal and the "applied" fact (D7, D14).
- `run_messages.claim_generation BIGINT NULL`: the originating generation on every canonical frame, stamped server-side by the fenced append (D7). A hot-path, nullable, additive column, accepted knowingly (see D7 for the rejected alternative).
- `run_usage.claim_generation BIGINT NULL`: derived output of the fold, never its evidence (D7).
- `run_schedules.credential_override_mode/secret_id`: the same two columns so a fired run inherits the schedule's choice (D5).
- `runs.anthropic_select_reason` gains `run_pinned` and `run_default`; `auto` via override reuses the selector's own reasons.

### Resolution ladder (the one seam)

`claimSecretID` (`secretchoice.go:300`) becomes: `self_improve` → judge binding (unchanged, first) → **run override** (`pinned` → `staticChoice(id, run_pinned)`; `auto` → `autoChoice`; `default` → an explicitly constructed `secretChoice{reason: run_default}`, since `staticChoice(nil, …)` always reports `default`) → worker bind mode (unchanged). `openAnthropic` and `assembleClaim` never learn the override exists (R4 of #104). The override id is opened with the same owner-scoped lookup as a worker pin (D11 of #104) **plus a kind predicate** (`anthropic_token`), because the by-id opener is owner-scoped but not kind-scoped.

**Effective next-claim mode** is one shared pure policy, `effectiveNextClaimMode(run, ownerJudgeMode, worker)`: `self_improve` → the owner's judge bind mode; else the run override (a nulled pin → inherit); else the recorded `worker_id`'s bind mode; a missing or deleted worker → `unknown`. Used by Decision 6e at park time (fixing gap 3), by the duration-time pass (D8), and by the verb's D6 warnings. Never derived from `anthropic_select_reason`, which describes the previous claim and goes stale the moment a binding changes while parked.

### One validator for every override write

`validateCredentialOverride(ctx, userID, kind, harness, mode, secretID)` runs at `run create`, `run approve --token`, `run set-token`, `schedule create/edit`: the secret must be the caller's own `user_secrets` row of kind `anthropic_token` (404 otherwise); a run or schedule whose effective harness is `codex` (`runs.harness`, `run_schedules.harness`, else `users.default_harness`) → 422; kinds `chat`, `judge`, `self_improve` → 409 "lane not switchable" (D10); mode `inherit` clears both columns (D5).

### The verb and its state table

`POST /api/runs/{id}/credential` (owner-only, mounted in `RequireUser` so the `uzc_` CLI Bearer works; not the cookie-only group) with `{mode: pinned|auto|default|inherit, secret_id?}`; CLI `uzi run set-token <run-id> <label>|--auto|--default|--inherit`. The override columns are written first in every row below (idempotent; harmless if the transition that follows finds 0 rows), then:

| status | transition |
|---|---|
| `queued` | nothing more; the next claim honours the override |
| `limit_wait` | a single-row **early promote** whose mutation set is exactly `PromoteLimitWaitRuns`' (`runtime.sql`): `status='queued'`, `status_since`, `started_at = NULL` (fresh wall), `budget_paused_seconds = 0`, `codex_cap_hash = NULL`, `codex_claim_epoch + 1`, `health='ok'`, `health_reason = NULL`, `health_since = NULL`, `updated_at`; and which **preserves** `worker_id`, `session_id`, `last_seq`, every limit field, `limit_dead_secret_id`, `retry_not_before` and both retry counters, so `claimExclude` (`secretchoice.go:336`) keeps excluding the dead token while its window is closed. A column-parity test pins the two queries together, naming every column above (the `limitWindowFor` lockstep pattern) |
| `pool_wait` | the existing `PromotePoolWaitRun` |
| `recovery_wait` | the existing recovery promote |
| `paused` | the existing `ResumePausedRun` (banks `budget_paused_seconds`, does not reset the wall) |
| `awaiting_approval`, `awaiting_input`, `awaiting_followup`, `running` (a worker holds the session; any kind the validator admits, `mr_rework`/`ci_fix`/`prompt`/`task` included) | the **switch protocol** below. 409 with a named reason when the holding worker does not advertise the `credential_switch` capability |
| `claimed` | 409: the claim payload is being assembled; retry in a moment |
| `completed`, `failed`, `cancelled` | 409 |

Post-resume deadline assertions cover every parked row: a run promoted after hours in `limit_wait` gets a fresh wall, a resumed pause keeps its banked budget, and none can time out on its first report.

### The held-state switch protocol (D3, D4, D13, D14)

Modelled on the **limit park**, not on the owner pause, whose primitive cannot serve here: `CreatePauseInput` admits only a running, non-interactive `issue`/`task`/`prompt`/`self_improve` run (`runtime.sql` "CreatePauseInput"); the gate, question and follow-up waiters in `agent/src/steering.ts` do not resolve on a pause; `handlePausePark` parks only on `ack.status === "paused"` (`runner.ts:4929`); and a `now` pause with no durable checkpoint is `pause_failed` and keeps running (`runner.ts:4862`, PRD #1190 Decision 8). Three facts about the current worker shape the steps: a 409 on a state report is folded into a normal ack with `applied:false` and the loop **continues** (`client.ts:371`), so nothing stops a flight today; parking retires the runner clone even when HOME is preserved (`runner.ts:1203`), so a local capture must be verified, not best-effort; and the worker's concurrency is a bare `Set<Promise>` with no same-run exclusion (`worker.ts:200`), so a reclaim can start while the old `execute()` is still in its `finally`.

1. **Request.** The verb writes the override and stamps `credential_switch_requested_at` + `credential_switch_generation = runs.claim_generation`. Nothing else changes; the run stays in its status. The stamp is visible as *requested*.
2. **Signal transport.** A `credential_switch {generation}` field on **every** `GET /api/worker/runs/{id}/inputs` response, including one with `inputs: []` (the idle gate/question/follow-up waiters poll that route continuously, `steering.ts:666`; `getInputs` at `client.ts:580` and the steering loop are extended to surface the metadata), and on the state-report ack. **While a switch is pending for the current claim, the inputs handler returns the signal and consumes nothing**: `ConsumeRunInputs` marks rows consumed on read (`runtime.sql` "ConsumeRunInputs"), so any answer or follow-up that would otherwise race the release stays unconsumed for the next claim. No user action is required.
3. **Local release, two-phase, before the server learns anything.** Quiesce: abort the in-flight turn (the abort a `now` pause uses), stop steering. Capture a **verified** local restore point through `captureRecoveryRestorePoint` (`runner.ts:4982`: dirty → WIP marker commit required; clean → an explicit clean proof; an unreadable status is *not* verified), then publish it best-effort (remote publication is the only best-effort half). On an unverified capture: keep the clone (`preserveRecoveryClone`), do **not** release, retry on the next poll; after a bounded number of failures write a `switch_failed` audit row and a feed note, clear the stamp, and continue on the old token. On a verified capture: drain pending message batches, release every run-keyed map and retire the clone (the same teardown the run's `finally` performs, `runner.ts:1131`), and only then report. Because teardown completes before the server can requeue, a reclaim on a spare slot can never overlap the old flight's cleanup.
4. **Release transition.** The worker reports `{status: "credential_switch", claim_generation}`. In **one statement** the server requires `claim_generation = @gen AND claim_released_at IS NULL AND worker_id = @worker AND status IN (<held set>)`, sets `status = 'queued'`, `claim_released_at = now()`, banks the gap like a pause (`budget_paused_seconds`; the wall is not reset), and keeps the stamp, now visible as *released, awaiting reclaim*. Ack `status: "queued"` is confirmation only; the flight is already gone. A lost report is retried; if it never lands, that run's heartbeats stop and the existing stale-worker requeue converges it to `queued` with the override already written.
5. **Fence.** Every worker-driven mutating transition (`SetRunRunning`, every state report, `AppendMessages`, any heartbeat write that touches the run row) carries `claim_generation` and is predicated **atomically in SQL** on `claim_generation = @gen AND claim_released_at IS NULL`; a Go-side check before an unfenced update is not accepted. A rejected report returns a **typed `stale_claim` disposition** in the ack, on which the new worker stops that flight without further reports; existing 409 acknowledgements keep their meaning. A generation-less report is honoured only on a claim negotiated as legacy (a worker without the capability), never on a fenced claim. `ClaimRun` clears `claim_released_at` and increments the generation, closing the window. Tests: a delayed report at `G` before reclaim (rejected), after reclaim (rejected), and a concurrent check/update interleave.
6. **Resume phase.** The claim carries `resume_phase`: `awaiting_approval` with the submitted plan's seq, `awaiting_input` with the open question, `awaiting_followup`, or `implementing` with the approved plan. The executor restores that phase instead of re-entering the planning turn, which today it skips only for a seeded or already-approved plan (`sdk-executor.ts:1385`). Tests: `set-token` alone keeps the **same** unapproved plan at the gate; switch + answer and switch + follow-up delivered in one batch are neither lost nor double-applied; approve + token implements the approved plan once.
7. **Applied.** The stamp is cleared by the next `run_credential_epochs` write, i.e. when a credential is actually opened at reclaim; that write also emits the run message and the Slack note. Release is not application: a reclaim that holds (`pool_wait`), fails, or resolves `auto` / a nulled pin onto a different token than expected keeps the stamp visible until the outcome is known.
8. **Composition.** `uzi run approve --token <label>` = validator + override + switch stamp + approval, in that order; the next inputs poll carries the signal, the worker releases before its first implement turn, and the reclaim resumes in phase `implementing`. A pending owner pause survives a switch unchanged: the worker re-arms it from `pause_pending` on resume (`protocol.ts:925`). `pause_cancel` and `pause_failed` never touch the switch stamp.
9. **Old workers.** The capability is advertised in the heartbeat and claim (`caps: ["credential_switch"]`). Without it the verb returns 409 naming the worker and the minimum version; the override is not written. Old workers keep working unchanged on legacy claims.

### Auto-failover re-evaluation (D8)

A second limit-wait promoter beside `PromoteLimitWaitRuns` (`sweep.go:169`): for each `limit_wait` run with `retry_not_before > now` and `limit_dead_secret_id` set whose `effectiveNextClaimMode` is `auto`, recompute `autoselect.NextAvailable(candidates, dead, policy, now)` over the owner's current pool and promote when the floor is `<= now`. **At most one run per owner per tick, oldest first**, sharing the guard `resumePoolWaitRuns` already applies (`sweep.go:278`), because this pass bypasses the park-time jitter that is the only thing staggering a wave (`runtime.sql` "PromoteLimitWaitRuns"). `pinned`, `default` and `unknown` modes are skipped: promoting them would only re-park.

**Pool promoter fix.** `resumePoolWaitRuns` (`sweep.go:314`) counts pool membership with no exclusion and relies on "a `pool_wait` run can never carry a future `retry_not_before`". Early promotion (the verb and D8) breaks that invariant: an `auto` run switched early whose only pooled token is its dead one is held in `pool_wait` with a future stamp, and the promoter would resume it every tick while `SetRunPoolWait` deliberately never counts against `RUN_LIMIT_MAX_WAITS`. The promoter therefore evaluates `autoselect.Floor(cands, claimExclude(run)).ok`, the same question the re-claim asks. Regression: sole-dead-token early switch to `auto` holds once and is not promoted until the window reopens or another token pools.

## Decision Log

- **D1 (override shape): two nullable columns on `runs`, mode + secret id, FK `ON DELETE SET NULL`.** NULL mode is inherit, so every pre-feature run and every run created without a choice behaves exactly as today. A `pinned` mode with a nulled id resolves as inherit, mirroring PRD #104's "deleting a bound token unbinds" for workers. Rejected: a single free-text column (cannot express `auto`/`default` vs a pin without sentinel ids); a join table as the resolution seam (history belongs in the epoch journal, D7).
- **D2 (precedence): judge lane for `self_improve` → run override → worker bind mode.** The override outranks the worker because the user chose it for *this* run; it never outranks the judge binding because `self_improve` is uzi reviewing itself and is billed separately by design (`secretchoice.go:288`). The ladder stays inside `claimSecretID` (R4: resolution lives in one place).
- **D3 (claim boundary only, one delivery path, fenced by the existing generation): a switch always takes effect at a claim.** No endpoint returns a token to a live run; `protocol.ts:550` stays true. The fence reuses `runs.claim_generation` (owned by `ClaimRun` together with the custody hold, PRD #1349) plus `claim_released_at`, so the run never disconnects from its custody generation and a released claim is rejected until reclaim. "Mid-run" is quiesce → verified capture → local teardown → release → reclaim → session resume. Cost: the in-flight generation and any tool call in progress are discarded; prompt cache is cold on the new org. The UI states it.
- **D4 (one verb, state-dependent; held states use a switch-specific protocol):** the table and protocol above. Rejected: reusing the owner-pause columns and ack (allowlist too narrow, waiters do not resolve, `paused` ack contract, Decision 8 refuses a no-checkpoint park, shared columns erase independent intents); separate `resume-now --token` / `approve --token` / `switch` mechanisms (three shapes for the skill to teach); a milestone-boundary fallback for the gate (does not satisfy "implementation starts on the chosen token"); reporting the release before local teardown (a spare-slot reclaim would race the old flight's `finally`).
- **D5 (three-way flags, plus inherit):** `--token` on `run create`, `run approve`, `schedule create/edit` is three-way like `--mr-rework`: omit = inherit, `<label>` = pin, `auto` = force the pool selector, `default` = the owner default; `run set-token --inherit` / schedule `--token inherit` clears an override (`default` is not inherit on an auto or pinned worker). On `schedule edit` an omitted `--token` leaves the stored value unchanged at the CLI/web layer by round-tripping it; the PATCH's own replace semantics are not changed.
- **D6 (warn, never refuse on headroom):** pinning the run's `limit_dead_secret_id`, a token whose gauge reads exhausted or stale, or `auto` when the pool minus the dead token is empty ("will hold in `pool_wait`"), returns 200 with a `warning` the CLI prints and the web shows. Refusals are reserved for facts: foreign or unknown id → 404, terminal run → 409, unsupported lane → 409, Codex harness or wrong kind → 422 (D9/D10), worker without the capability → 409.
- **D7 (attribution is a journal with provenance on the frames): `run_credential_epochs` + `run_messages.claim_generation` → `run_usage.claim_generation`.** `runs.anthropic_secret_id/label/select_reason` keep meaning "the credential of the current claim". Frames carry the generation they were produced under, stamped by the fenced append, so both the incremental fold and a refold attribute a leg to its epoch; `run_usage.claim_generation` is output, never evidence. Rejected: inferring the generation from timestamps or the latest run row (a refold would relabel old spend); a journal `seq`-boundary cutoff (`AppendMessages` is worker-scoped and a late batch from the same worker can cross the reclaim, so the boundary would need atomic cutoffs plus fenced drains for no gain over stamping). Accepted cost: one nullable column on the hot-path `run_messages` table, numbered at merge like every migration.
- **D8 (auto-failover re-evaluation, bounded): parked runs are re-asked every sweep tick, only when their effective next-claim mode is auto, one per owner per tick.** Extends Decision 6e from park-time to park-duration and fixes 6e itself to consult the same policy. Rejected: reactive promotion from the `token pool` write (misses a gauge that merely turns eligible); promoting pinned runs (guaranteed re-park); promoting every eligible run in one tick (herd on the one credential).
- **D9 (provider-neutral column, Anthropic-only behaviour):** the FK targets `user_secrets.id` of any `kind`; the validator rejects a non-`anthropic_token` kind and a Codex-harness run or schedule with 422, and the by-id open is kind-scoped as defense in depth. A later harness-handoff PRD lifts the check instead of adding a column.
- **D10 (unchanged lanes are refused, not ignored):** chat, judge and `self_improve` runs return 409 from the verb; their ladders would ignore the override and a silently accepted write would misreport intent.
- **D11 (independent intents): the switch stamp is not a pause column.** A pending pause survives a switch; `pause_cancel` and `pause_failed` never settle a switch; only an applied switch, a bounded capture failure, or a terminal state does. Concurrency tests cover pause-then-switch, switch-then-`pause_cancel`, and switch-then-terminal.
- **D12 (naming): `uzi run set-token`**, parity with `uzi worker set-token`; `retoken` rejected for vocabulary drift.
- **D13 (gate switch is not an approval, and never a re-plan):** `run set-token` at `awaiting_approval` stamps the switch, the idle waiter's next inputs poll releases, and the reclaim resumes at the same gate with the same submitted plan (`resume_phase`). Approval stays a separate act; `run approve --token` composes the two.
- **D14 (released is not applied):** the release transition keeps the stamp; only the next epoch write clears it and emits attribution and notifications. A blocked or differently-resolved reclaim stays visible as pending.

## Success criteria

- The 2026-09-15 scenario resolves two ways: (a) with no human action, an `auto` run parked on token A resumes on token B within a few sweep ticks of B becoming eligible (one run per owner per tick); (b) for any run, `uzi run set-token <run-id> <label>` returns it to `queued` at once and the next claim spends that token, visible on the run page, `uzi run get` and the TUI.
- A pinned or default-bound run is never promoted early, at park time or later.
- `uzi run create --token <label>` spends that token from turn one on a worker bound to a different one.
- Switching at the gate keeps the same plan and applies to the implementation phase without a second approval; switching a running run loses at most the interrupted step and continues the same session; no committed work is lost; a stale report from the old flight cannot undo it before or after reclaim.
- Spend before a switch stays attributed to the old token after any replay or refold.
- No pre-feature run changes behaviour (NULL override = today's ladder; old workers unaffected on legacy claims); `gate:api`, `gate:web`, `gate:agent`, `gate:repo` green; contract fixtures re-recorded, not hand-edited.

## Risks and mitigations

- **Cross-org session resume does not continue the transcript.** Already assumed by the auto lane since PRD #217; M0(a) produces the evidence. Fallback if it fails: cold restart from the last verified restore point (the PRD #1296 recovery path) with a run-feed note, still no lost commits.
- **Thrash** (switch onto a token that re-parks): bounded by `RUN_LIMIT_MAX_WAITS` for limit parks; the `pool_wait` loop is closed by the promoter fix (M3); D6 warns before either.
- **A stale flight races the switch**: the atomic generation + `claim_released_at` fence (M5) rejects it before and after reclaim; the typed `stale_claim` disposition stops the old flight.
- **The old flight's teardown clobbers the new one**: prevented by ordering, not by the fence: the server cannot requeue until the worker reports, and the worker reports only after teardown.
- **An unverified local capture**: the run is not released; the clone is kept and the capture retried; a bounded failure surfaces as `switch_failed` and the run continues on the old token.
- **Old worker fleet**: the verb refuses held-state switches with a named reason; parked-state switches and create-time choice need no worker change.
- **Token deleted between set and claim**: FK `ON DELETE SET NULL` → inherit; the claim never fails on a dangling id.
- **Older CLI against a newer server** drops the new `--json` fields (the documented version-skew behaviour); the version warning covers it.
- **Cookie-only route trap**: the router-level auth test in M4 is mandatory.
- **`sqlc` type inference on the early-promote and fenced queries**: exercised by live-DB tests, never trusted from a clean `sqlc generate` alone (`.claude/rules/go.md`).
- **`run_messages` migration on a large table**: nullable, default-less, additive, so no rewrite; numbered at merge above the live head.
