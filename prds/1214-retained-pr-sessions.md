# PRD #1214: Retain PR sessions for faster MR rework

**Issue:** [#1214](https://github.com/vtmocanu/uzi/issues/1214)
**Status:** Ready for implementation after two review rounds and final confirmation. No implementation started; M9 remains an optional separate delivery.
**Priority:** Medium.
**Origin:** User discussion on 2026-09-08, following [#813](https://github.com/vtmocanu/uzi/issues/813).
**Execution:** Commit and push for later. Review with the existing reviewer session; do not launch additional review agents. No immediate uzi run or sweep labels.

Implement on a new branch from current `main`. The core spans api, agent, web and CLI; optional worker-lease work may additionally affect the controller's display protocol. No implementation or validation may create or modify `.github/workflows/**`. Assign migration numbers above the live migration head at merge time.

## Problem and intended outcome

An implementation run learns the repository, evaluates alternatives, records decisions, runs tests and opens a PR. Completion then deletes its local session state. The review watcher creates a separate `mr_rework` run that works on the same branch without that conversation. Each review cycle can repeat discovery and reconstruct why the existing code was written that way.

The user proposed parking runs until their PR merges so rework could continue with the original context, initially including keeping their workers alive in drain mode. After discussing the fleet cost of indefinitely open PRs, the user selected durable session retention with bounded worker retention. The desired improvement is faster rework, especially time to the first useful edit. No numerical speedup has been measured or promised.

Preserve a continuing PR session across separate implementation and rework attempts. Make it recoverable after the original worker is gone, release execution capacity between attempts, and prefer a ready local copy when available. Keep worker upgrades, emergency replacement, and quota recovery independent of a human merging the PR.

## User journey

1. An owner enables **Retain context for PR rework** in Settings. This controls retaining new context and using existing retained context; it does not enable automatic rework by itself.
2. An eligible run opens a PR. Its run still completes and its board card stays in Human Review. The run page shows **Context retained for rework**, the last saved time and the expiry.
3. Automatic rework, or the manual rework path when #1202 is available, creates an ordinary new `mr_rework` attempt. It restores the most recent compatible PR session, reconciles the current branch with the saved head, and receives the new findings in that conversation.
4. The rework feed says whether context was reused locally, restored from storage, or unavailable, with a bounded reason. The new attempt retains its own cost, duration, outcome, findings snapshot and review history.
5. After a successful rework, the retained session advances to that attempt. A later round includes the previous rounds' decisions, not just the original implementation.
6. Merge, closure, expiry or **Forget retained context** releases retained artifacts. Existing run messages and accounting remain governed by their existing lifecycle. A PR can still be reworked with a fresh session when retention is unavailable.

## Scope

### Included

- A durable, owner-scoped PR session linked to existing completed runs and subsequent rework attempts.
- The existing watched source kinds: `issue`, `prompt` and `self_improve`; their `mr_rework` descendants extend the same session.
- Claude session recovery for the currently deployed rework path, behind the existing provider-neutral harness boundary. The generation format carries an explicit provider discriminator. Codex recovery is a blocked follow-on, as described below; this PRD must not claim it works merely because a local Codex artifact can be copied.
- Recovery on a different eligible worker for every worker kind, and same-worker reuse on persistent hosted/external workers. Same-worker reuse of a completed ephemeral worker belongs to optional M9.
- Bounded local artifact retention and worker preference, without occupying a run execution slot or blocking a rollout until PR merge. Optional ephemeral-worker leases are isolated in M9 and do not block the durable-session core.
- Explicit cold-start fallback, independent attempt accounting, retention controls, CLI/web visibility and performance evidence.

### Excluded

- Reopening a terminal implementation run or adding a new `runs.status`. A parked PR session is a separate lifecycle object.
- Widening the review watcher's eligible source kinds to task PRs. That is a separate part of #813.
- Changing review-trigger debounce, cycle caps, comment high-water tracking, review finding disposition or automatic merge policy.
- Implementing #813's independent self-review proposal. Existing review requirements remain in force, including when the authoring session is reused.
- Preserving live SDK processes, arbitrary background processes, full container memory or every dependency/build cache.
- General transcript search/export, cross-repository memory, provider-to-provider conversation conversion, or a new object-storage service.
- Persisting SDK credentials or copying an entire HOME directory into the API database.
- Making Codex publicly routable or changing rework provider selection. Codex continuation requires #1171's public routing, a verified packaged-app-server artifact allowlist, and explicit rework-provider inheritance. Until those prerequisites land, Codex-sourced context is `unavailable(provider_unroutable)` and no attempt switches provider to reuse it. Its recovery and measurement rows are deferred, not passed.

## Design decisions

### D1: Separate PR session lifetime from execution lifetime

Introduce a PR session identity keyed by server-derived owner, repository, forge PR identity and branch incarnation. Associate the initial producing run and each consuming attempt with it. Keep implementation and rework runs terminal when their work finishes; never reopen completed rows, restart their budget clocks or keep them in the active-run count.

Logical PR session states are `retained`, `in_use`, `unavailable` and `released`, with a separate incomplete upload state that is never resumable. A session can be retained while its PR waits for review, then be consumed by one branch-writing attempt at a time. The existing branch exclusivity guards still arbitrate all writers, including CI fixes. A session does not reserve the branch while idle.

### D2: Store private, verified generations through the API

Use the existing PostgreSQL service and API-held `secretbox` encryption for bounded session artifacts. Compress before encryption, while enforcing decoded-byte limits during streaming decompression. Workers communicate only through authenticated `/api/worker/*` routes; they gain no database credential, object-store credential or additional network destination. Transcript content can contain source and sensitive tool output even when credential files are excluded, so it must be encrypted, owner-scoped and omitted from logs, notifications, public Git refs and ordinary DTOs. This increases `pgdata`, WAL, vacuum and backup load; instance dumps contain the encrypted artifacts. M8 must measure stored bytes and database/backup growth, with no assumed compression ratio.

Each immutable generation records the producing attempt, provider, provider/codec version, session identifier, workspace identity, published branch head, previous generation, artifact manifest and integrity information. M1 adds the pushed head SHA to the upload/finalize and completed-report contract; it is a worker-reported value under the current claim fence, not a server-verified forge fact. For a rework, publication means an accepted push to the existing PR branch, not creating another PR. The fresh fetch and ancestry check at restore verify compatibility with the actual branch. Finalizing the upload creates a complete but staged generation. It becomes eligible only when the API atomically records the producing run's successful completion and activates that staged generation for the same reported PR identity/head. Never expose a partial upload or a staged generation from an unfinished/failed attempt as retained. An upload failure must not turn a successfully published PR into a failed implementation run; report context unavailability and permit future fresh rework.

Use bounded chunk upload with an idempotency identity, expected part counts and a final commit acknowledgement. Authenticate every operation against the current worker claim, including a claim-generation fence so a delayed request from a superseded claim cannot publish a newer snapshot. Content hashes detect accidental corruption; authenticated storage and server-side binding establish provenance. Retrying completion returns the same committed generation. Advancing the current-generation pointer is compare-and-swap, so an older attempt cannot overwrite a later round.

M1 freezes the concrete route/request/response/claim-fence contract, versioned manifest schema, metadata DTOs, rejection enums and limits in the PRD before M2 implements its transfer client. M1 and M2 are sequential; an assumed contract is not a basis for parallel execution. Do not place provider-specific SDK types in Go transport or the neutral harness interface.

### D3: Export a resumable context, then stop execution

The provider codec exports only the session artifacts required for continuation. Recreate tool definitions, skills, agent configuration and credentials from the new claim; preserve a manifest identifying the prior configuration for compatibility checks. Session storage does not authorize restoring old credentials or a more permissive tool policy.

For Claude, the export allowlist is the producing session's `projects/<project>/<session-id>.jsonl` plus that session's `projects/<project>/<session-id>/` transcript/sidecar subtree, discovered and validated with the pinned SDK. No sibling sessions or other `.claude/` trees are included: exclude credential files, `settings*.json`, `todos/`, `shell-snapshots/`, `debug/` and `statsig/`. Validate compaction and subagent sidecars with real provider artifacts. If using `sessionStore`, handle `mirror_error` and establish a complete snapshot with an explicit verified export/finalization path before temporary SDK state disappears. Do not use a successful mirror callback as proof that every preceding batch arrived. Reject path traversal, absolute artifact paths, symlinks, special files, decompression bombs and unsupported versions before materialization.

Required finalization order: finish the last provider turn; successfully publish the branch/PR; export and upload the final context; receive the server's complete-generation acknowledgement; then report `completed` carrying that generation ID and pushed head. The terminal status change and generation activation commit in one database transaction, before any terminal cleanup hook can delete the ephemeral worker. An admitted retry of that completed report returns the generation committed for that producing attempt, not the PR's possibly newer current generation. Only after the acknowledgement/terminal response may the runner remove the source HOME. If export fails or is revoked, report `completed` with an explicit context-unavailable reason instead. No provider turn may run after capture; a later turn invalidates that candidate and requires a fresh export. The staged-and-reclaimed crash outcome applies only before the completion report was accepted; after acceptance both completion and activation are durable together.

Optional export is bounded by a short timeout and the run's remaining reporting allowance. If that allowance is exhausted, skip/abort export and report successful publication with `context_unavailable(export_timeout)`; do not turn the optional save into an agent failure or a new recovery park. Existing authoritative cancellation, claim-fence rejection and terminal-state handling still apply; retention grants no right to override them.

The run's provider process and subprocesses are reaped, run-scoped secrets are evicted and execution capacity is released exactly as on normal completion. Retain only an approved local artifact cache and, if explicitly enabled, a separately bounded worker lease. No API request or model keepalive is sent merely because a PR is waiting for review.

### D4: Restore into a new attempt with current authority and current code

At rework creation, resolve the latest compatible generation for the exact PR lineage. Keep `target_run_id`'s existing meaning; expose context provenance through new additive fields. Use both the original implementation and the latest completed rework lineage, avoiding a reset to the initial conversation every round. If #1202 lands first, its manual path uses this same resolver without modifying its distinct trigger policy.

Carry that handoff in a new additive claim field containing generation ID, provider/codec version, source session ID and canonical workspace key. Never prefill `claim.session_id` or `runs.session_id` from the source run: those fields mean this attempt has already executed and drive Git recovery, approval and budget semantics. The first turn resumes/forks the imported context through the codec while remaining a fresh rework attempt; its own session ID is then recorded through the normal report path. Test that inherited context does not mark the attempt as an ordinary resumed run, adopt another attempt's checkpoint authority or bypass its plan/review policy.

Use the source lineage's canonical clone key for retained-context rework. Today an issue run uses `issue-<iid>`, whereas its rework uses `agent-issue-<iid>` (`agent/src/run-kind.ts`); simply copying a transcript into the new HOME is insufficient. Derive/validate the canonical key from server-known source kind and identifiers, then join it under the claiming worker's trusted runner root. Never accept an arbitrary path from an artifact. With the standard worker layout this preserves the same real cwd on another worker, so remembered tool paths remain valid. A custom worker with an incompatible root requires a tested provider-supported relocation path or an explicit `workspace_incompatible` fresh fallback. Restore/import must occur before the current local-only `inspectSession`/resume preflight can discard the session ID. Test the issue-to-rework path specifically, as well as the already-matching scheduled-run slugs.

Canonical cwd reuse also requires worker-local serialization across different attempts sharing that workspace, through final cleanup. The source run can already be terminal in the API while its runner is still deleting files; a new rework must not construct a clone that the previous attempt's delayed cleanup then deletes. Hold a workspace ownership/serialization guard until cleanup completes and verify ownership on deletion. Preserve ADR-1197's recovery journal: neither a new attempt nor retained-context GC may authorize deleting an unverified clone owned by another attempt. Cover delayed source cleanup racing a new rework and an abandoned recovery journal as concrete regression cases.

At claim, the server rechecks owner/repository access, retention consent, PR identity, provider compatibility and branch exclusivity before granting access to that one source generation. An unrelated run belonging to the same user is not authorized to retrieve arbitrary stored conversations. Old or unsupported workers may take the normal fresh path and report that capability explicitly.

Fetch the current PR branch before beginning a resumed turn. If the saved head remains an ancestor, present the intervening changes as fresh evidence and require re-reading affected code. If history is incompatible, the PR is closed/merged, identity was reused, or the generation cannot be validated, do not resume it blindly. Closed/merged PRs stop rework; incompatible or missing context produces an explicit fresh rework where normal policy permits it. Keep the existing non-fast-forward push protection: never force-push to make a retained snapshot fit.

The first resumed turn identifies the new attempt, current branch/head, current goals and the current review snapshot. Rebuild MCP tools and guards for the current run. All reply/resolve calls remain bound to that attempt's snapshot, even if the old conversation includes different thread IDs, a previous run ID or obsolete instructions. Resumed history is context, never an authority to bypass current approval, credential, scope or tool restrictions.

When practical, fork or copy the retained generation into the new attempt's provider session so failure cannot mutate the last complete source generation. Provider-native session identity transformations belong in the codec; never rewrite transcript IDs with a string replacement. Retry the same attempt with its own newest valid checkpoint. Promote a new PR generation only after that round publishes successfully.

### D5: Keep worker retention bounded and subordinate to capacity

Prefer a ready local copy on an eligible worker. Use a distinct rework preference with a maximum 30-second queue delay; do not inherit the existing 2h paused-run affinity ceiling into a new rework attempt. Once the delay expires, any eligible worker can restore the durable context. Existing paused-run affinity is unchanged.

The local cache lives at `<worker-data-root>/pr-session-cache/<generation-id>`, outside every per-run HOME, with worker-only directory permissions and validated server-assigned identifiers. A cached artifact is usable only when its generation ID and verified manifest/content hashes match the generation selected by the current authorized claim; otherwise fetch that generation from the API. Reclaim entries after 24h or the server expiry, whichever is earlier, and enforce a 512 MiB per-worker cache limit with oldest-unused eviction. Server release/revocation learned on a claim invalidates the local copy immediately; local TTL still works when the API is unavailable. A bounded periodic cache sweep is separate from terminal-HOME reclamation and cannot delete a generation during materialization or an in-flight recovery clone.

A healthy persistent worker remains available for other runs. Do not drain the whole worker merely because one of its PR sessions is parked. A draining worker is ineligible for a newly created rework attempt, including one for a PR it produced. Its existing right to resume an already-owned promoted run is unchanged. Worker preference excludes draining workers and never resets or extends rollout deadlines.

The optional ephemeral-worker lease is M9, which may ship after the M1-M8 core or be declined if measurements do not justify it. Its default is zero. An operator may test a nonzero lease, capped at two hours, only with durable recovery enabled; 30 minutes is an evaluation setting, not the shipped default. During the lease it can claim only server-verified rework descendants of its bound PR session while non-draining. This widens its binding from one attempt to one PR lineage; it must not become a general pooled worker. Retained workers consume real fleet/quota capacity and must be displayed/countable as such, but consume no active-run slot or execution budget.

Retaining a worker does not retain its deleted runner clone or per-run HOME cache. It can save pod scheduling, registration, fresh PVC/Nix seeding and shared `/nix` or DinD initialization, in addition to transcript transfer (`controller/internal/kube/render.go`, `RenderPVCs` and `seed-nix`). Whether those savings justify idle reservations is unmeasured. M8 must report provisioning/seed/registration time, retained pod-minutes and resource requests before recommending a nonzero lease.

With no lease, including the shipped zero default if M9 is implemented, current ephemeral behavior is unchanged: the same terminal transition tears down the worker and the reaper selects the same rows. No new claim may reach an already-deleted worker. The controller retains its existing row-present/row-absent behavior; changing controller lifecycle semantics is unnecessary for the core.

M9 only: evict retained idle workers before refusing fresh work solely because those workers occupy the owner's worker quota. Expired leases, disk pressure, image updates and forced replacement may also evict them. Ordinary eviction follows a verified durable acknowledgement; an emergency worker loss is allowed at any time and yields the documented context fallback if no valid snapshot exists. Failed persistence never extends a worker lease indefinitely. Controller and API deletion/reaping agree on this new idle lease; repeated reconciliation is idempotent.

### D6: Bound storage and give the owner control

Initial rollout is opt-in: an admin kill-switch defaults off, and the owner setting defaults off. This does not change `mr_rework_enabled` or imply consent to extra automatic runs. After correctness and performance validation, changing defaults is a separate explicit product decision.

Retention and rework consent are independent. `runs.mr_rework_enabled` continues to override the owner's automatic-rework preference and does not delete retained context when switched off. Retention off means a permitted rework starts fresh. Effective capture/restore permission requires the admin setting, owner setting and PR-session row's sticky forget flag all to allow it. The forget flag lives on the PR session, not on each attempt's `runs` row.

Initial configurable bounds: 30 days since the last successfully saved rework context, 256 MiB per complete generation, 1 GiB of retained artifacts per owner including all generations and in-progress uploads, and 8 MiB per upload request. Limits apply to decoded bytes as well as transport bytes. Reject oversized candidates with a content-free reason and retain a compatible previous complete generation when possible. Never silently truncate a transcript and call it resumable. Reclaim abandoned uploads after one hour; remove superseded generations once no active attempt references them.

When the existing MR-state sync observes merge or closure, stop offering context for new claims and reclaim inactive artifacts on the next GC pass. Where that sync is not running, the 30-day TTL remains the cleanup backstop; never claim instantaneous remote closure detection. Claim/restore still checks that the PR is open under D4. A failed forge read is unknown, not closure. Expiry releases context, not the original run, PR or run-message history. A reopened PR starts fresh after release. User/repo deletion follows existing ownership deletion rules and deletes associated retained artifacts.

**Forget retained context** and disabling retention prevent new restoration immediately and schedule deletion; an active attempt may finish with the context already in memory, but may not publish another retained generation for that revoked lineage. Explain this in the UI. Forget is sticky for that PR so the next automatic round cannot silently save it again; re-enabling requires an explicit owner action. Administrative disabling is also honored at upload finalization, not just at the initial claim. GC and revocation must race safely with upload, restore, rework completion and worker teardown.

### D7: Preserve attempt accounting and independent judgment

Each rework receives its ordinary new-run budget and existing review policy. Idle PR-session time counts in neither attempt duration nor active/busy run totals. Preserve charged usage from the new model calls, including processing the restored context, but never count historical conversation usage as new spend. Cover providers that expose cumulative session counters as well as per-call records; accounting recovery must remain idempotent on retry. Pin the concrete Claude test: attempt B resumes A's generation; B's `run_usage_totals` equals B's own charged result frames, A's usage remains unchanged, and B's resumed-context input/cache processing is included. `claude-harness.ts` reports result usage with `basis: session`; do not infer accounting correctness merely from the new run ID.

Retaining the implementation conversation can preserve incorrect assumptions. Existing reviewer waves and the requirement to validate each finding against current code remain. Session reuse is not evidence that a finding is correct, that the original decision must be preserved, or that the rework diff has been reviewed.

### D8: Make benefit and degradation visible

The API exposes additive context metadata on run detail/list: availability, source attempt, provider, retained timestamp, expiry and the selected restore mode/reason for a consuming attempt. Never expose raw transcripts or arbitrary storage keys. CLI JSON and web use the same semantics. A missing field from an old worker/version is unknown, not a verified fresh or restored result.

Record context export/restore time, claim-to-first-edit time (nullable for no-op rounds), active rework duration, relevant discovery tool calls, token/cache usage and charged cost. Use content-free structured events; do not label global metrics with run IDs, session IDs, repository paths or arbitrary reasons. Separate queue delay, worker preparation, model execution, CI and external-review waiting.

## Risks, dependencies and delivery boundaries

- **SDK alpha and best-effort mirrors.** `sessionStore` availability is verified, but end-to-end durable recovery through uzi is new work. A missing final batch can be more misleading than no context. Complete-manifest commit and real provider-resume tests are mandatory; unsupported versions produce explicit fresh fallback.
- **Sensitive retained content.** Excluding credential files does not remove secrets a model or tool included in the transcript. Encrypt and restrict the entire payload. Treat artifacts as untrusted data, bound parsing/materialization, and never copy raw provider-auth state across attempts. API secret-key rotation can invalidate retained artifacts; report that as unavailable and reclaim them.
- **Old authority inside a resumed conversation.** Previous run IDs, thread IDs, tool instructions and decisions do not grant current permission. Validate against the new claim and snapshot on every write. Independent review is still necessary.
- **Provider and usage compatibility.** Restore only supported provider/codec combinations. #1171 is open as of 2026-09-08; public Codex routing, packaged artifact characterization and rework-provider inheritance are prerequisites to the explicitly deferred Codex continuation. Keep the format provider-neutral without adding untested codecs or declaring Codex covered by a Claude-only test.
- **Manual rework and high-water work.** #1202 is open as of 2026-09-08; it is an integration neighbor, not a prerequisite to automatic context reuse. #1199 changes trigger tracking and #1117 concerns branch movement. Keep those policies separate and test concurrency/branch drift at the shared boundary.
- **Ephemeral isolation (M9 only).** A retained worker is restricted to one PR lineage; broadening that to unrelated runs would undo its isolation contract. Storage durability is what permits prompt eviction when there is no safe reuse.
- **Storage growth and stalled PRs.** TTL and per-owner/per-generation/cache limits bound core retention; M9 additionally needs oldest-idle worker eviction. Artifact expiry never cancels a completed run or silently clears an active attempt's loaded state.
- **Operational validation.** A gate-green code change is not enough. Real hosted-worker replacement and paired rework measurements are part of acceptance, with remaining operator work recorded explicitly.

No `docs/ROADMAP.md` exists in the inspected checkout, so no roadmap update is required. #813 remains open for its independent hardening proposals.
