## Problem

An owner who wants a running run to stop spending for a while has three tools, none of which is a pause. `cancel` is terminal. `stop` and `scope` finish what is committed and finalize into a merge request (`api/internal/workersvc/submit.go:164-215`). The involuntary parks (`limit_wait`, `pool_wait`, the three `awaiting_*` gates) happen to the run; the owner cannot ask for one. So a run that is fine but ill-timed (a rate window the owner wants to save for something else, a review the owner wants to do before the next milestone, a night the owner would rather not be woken for) is either left running or thrown away.

Everything a pause needs already exists for the usage-limit park: a non-terminal status that keeps the issue, the session, the worker affinity and the message history (`SetRunLimitWait`, `api/internal/store/queries/runtime.sql:1338-1398`); a checkpoint published to the forge on park (issue #1030 M2); a promotion back to `queued` that keeps `worker_id` (`PromoteLimitWaitRuns`, `:1416-1470`); a claim whose affinity leg follows worker liveness ([ADR-628](../adr/0628-cross-worker-resume-durability.md)); a resume that continues the SDK session on the same worker or recovers the tree from the checkpoint on another (`agent/src/sdk-session.ts`, `agent/src/git.ts:473-640`). What is missing is the voluntary entry and the on-demand exit.

## Solution

- **A new non-terminal status `paused`**, in the wait family beside `limit_wait` and `pool_wait`: In Progress on the board, exempt from the timeout sweep (which only looks at `running`), never flagged by the health detector, untouched by the stale-worker requeues, and never a `TERMINAL_RUN_STATUSES` member on the worker.
- **`pause` is an owner-only steering input** with a mode: `milestone` (default; park once the milestone in flight is reported complete, or at the next turn boundary on a run without milestones) or `now` (drop the turn in flight and park on the last checkpoint). A pending pause is a **flag on the running run, not a status**: the run stays `running`, the page shows `Pause requested · after M4` with **Cancel pause** and **Pause now**, and `pause_cancel` withdraws it.
- **The worker parks like a limit park**: it publishes a checkpoint, reports `paused`, and exits the run, freeing its slot and preserving the run's HOME. If the checkpoint cannot be published the run does **not** park: it stays running, the request is cleared, and the owner is told.
- **`resume` moves `paused` to `queued`** with the worker pin kept and the parked time banked into `budget_paused_seconds`, so the clock stops while paused and the remaining budget is what it was. The claim then does what it does for a promoted limit park.
- **Surfaces**: web (pill, panel, Resume as the conditional header action, Pause ▾ beside Stop run), CLI (`uzi run pause [--now|--cancel]`, `uzi run resume`), TUI (the word `‖ paused`, a row-2 line for the request and for the park, the rate-limit line reworded `waiting:`), Slack thread replies when a pause lands, fails or resumes.

## Design

### Store

Migration `00204_run_paused.sql` (draft):

- widen `runs_status_check` to add `'paused'`: `DROP CONSTRAINT IF EXISTS runs_status_check; ADD CONSTRAINT runs_status_check CHECK (status IN (<the eleven values of the Up at 00170:18-22>, 'paused'))`, with a Down that restores exactly those eleven; verify the list against the live constraint (`\d+ runs` on the dev database, or the Up block, never the Down block);
- `ALTER TABLE runs ADD COLUMN pause_requested_at timestamptz; ADD COLUMN pause_mode text CHECK (pause_mode IN ('milestone','now')); ADD COLUMN pause_after_count int;` (`pause_after_count` is `len(milestones_completed)` at request time, the count the milestone mode waits to exceed);
- `ADD COLUMN IF NOT EXISTS checkpoint_tip_at timestamptz` (shared with #1189; whichever lands second removes this line at its landing rebase, see Risks). `SetRunCheckpointTip` stamps it. Heads-up: no existing migration uses `IF NOT EXISTS`; it is plain Postgres and goose runs raw SQL, so it works, but apply the migration twice on a scratch database in M1 to be sure.

Queries (each mirrors the named precedent and inherits its comments' reasons):

- `CreatePauseInput :one` (CTE like `CreateScopeCeilingInput`): `UPDATE runs SET pause_requested_at = now(), pause_mode = @mode, pause_after_count = COALESCE(jsonb_array_length(milestones_completed), 0) WHERE id = @id AND status = 'running' AND kind IN ('issue','task','prompt','self_improve') AND interactive = false RETURNING …` plus the `kind='pause'` audit row. 0 rows → Go maps to `ErrPauseNotRunning` (409, message names the current status: `run is awaiting_approval; the clock is already stopped`) or `ErrPauseNotSupported` (409, `chat runs already park between turns` / `interactive tasks park after each turn` / `judge, mr_rework and ci_fix runs are short and finish on their own`). A second `pause` while one is pending replaces the mode (so `now` escalates a pending `milestone`), audited.
- `CancelPauseInput :one`: clears the three columns where `pause_requested_at IS NOT NULL AND status = 'running'`, audit row `kind='pause_cancel'`; 0 rows → 409 `no pause is pending`.
- `SetRunPaused :execrows` (mirror `SetRunLimitWait`): `status = 'paused', status_since = now(), session_id = COALESCE(sqlc.narg('session_id'), session_id), pause_requested_at = NULL, pause_mode = NULL, pause_after_count = NULL, health = 'ok', health_reason = NULL, health_since = NULL, updated_at = now() WHERE id = @id AND worker_id = @worker_id AND status = 'running'`. Positive source guard, for `SetRunLimitWait`'s reasons. No counter (a pause spends no budget).
- `ResumePausedRun :one` (mirror `PromoteLimitWaitRuns`, **but** with the gate-park accounting): `status = 'queued', status_since = now(), budget_paused_seconds = budget_paused_seconds + GREATEST(0, EXTRACT(EPOCH FROM (now() - status_since))::int), codex_cap_hash = NULL, codex_claim_epoch = codex_claim_epoch + 1, health = 'ok', …, updated_at = now() WHERE id = @id AND user_id = @user_id AND status = 'paused' RETURNING id, user_id, status`. `started_at`, `session_id`, `last_seq`, `worker_id` untouched; `requeue_count` not bumped. Ownership is the predicate (0 rows → 404 foreign, 409 not paused), the `ResumeRunNow` shape.
- `ClearPauseRequest :execrows` for the worker's `pause_failed` report (see *Agent*), keyed on `id AND worker_id`.
- **`SetRunRunning` gains `AND status <> 'paused'`** beside its existing `<> 'limit_wait'` (`runtime.sql:1049`) and `<> 'pool_wait'` (`:1055`) guards, for the reason its 🔴 comment gives at `:1040-1055`: two pre-gate fire-and-forget `running` reports already exist, so a late or reordered one arriving after the park would flip `paused` back to `running` under a worker that has exited, and the run would then sit ownerless until `RUN_TIMEOUT` killed it. `paused` sits inside `NOT IN (terminal)` and is caught by neither existing guard. Live-DB test: a `running` report against a `paused` row is a 0-row no-op (mutation check: remove the guard and watch it flip).
- **The involuntary parks do not clear a pending pause.** `SetRunLimitWait`, `SetRunPoolWait` and the question park (`awaiting_input`) leave `pause_requested_at`, `pause_mode` and `pause_after_count` untouched, so an owner's request made before a usage-limit park re-arms on the first `running` report after the promotion: the ACK rule sees the columns and answers `pause_requested: true`, and the worker parks at the next boundary (for `now`, before spending a turn). This is the intended reading of "pause it and keep it paused" and is pinned by a live-DB test (request, park to `limit_wait`, promote, claim, `running` report → ACK true). Only `SetRunPaused` (consumed), `CancelPauseInput` (withdrawn), `ClearPauseRequest` (failed) and the terminal transitions clear the columns.
- `RequeueRunsOfStaleWorkers`, `FailWorkerRunsOverCap`, `RequeueWorkerRuns`, `SweepRunningTimeout`, `ListActiveRunsForHealth`: **no change**; `paused` is absent from every list, which is the behaviour wanted (a paused run survives its worker's death and stays paused; on `resume` the ADR-628 affinity leg falls open because the pinned worker is stale or gone). A live-DB test pins each.

### Server

- `runInputKinds` gains `pause` and `pause_cancel` only; the CHECK gains `pause`, `pause_cancel` **and** `resume` (the last for the audit row the resume endpoint writes; `resume` is not a `POST /inputs` kind, so there is exactly one resume mechanism). `ConsumeRunInputs` (`runtime.sql:2780`, today `p.kind <> 'scope'`) must exclude `resume` too (and `extend`, if #1189 has landed): a server-only kind drained by the worker hits `SteeringChannel.route`'s default arm and logs `steering: ignoring unknown input kind` (`agent/src/steering.ts:544-545`). `pause` and `pause_cancel` **are** consumed: the worker's steering route needs them (the `now` abort and the flag clear).
- The `pause` branch in `SubmitInput` distinguishes its 409 classes from a 0-row `CreatePauseInput` by re-reading the run row it already fetched (`GetRun` at the top of `SubmitInput`), the way `ResumeRunNow` branches after `GetRunByIDForUser`: status not `running` → `ErrPauseNotRunning` naming the status; kind or `interactive` outside the allowlist → `ErrPauseNotSupported` with the per-kind sentence. Same TOCTOU as `scope`, accepted.
- **Resume is the existing endpoint, widened.** `ResumeRunNow` (`handler/resume.go`) today writes first (`PromotePoolWaitRun` at `:32`) and reads the run only to word the 409 (`GetRunByIDForUser` at `:43`, message `run is not waiting for a pooled token` at `:49`). Reorder it: read first, then dispatch on `status`: `pool_wait` → `PromotePoolWaitRun`, `paused` → `ResumePausedRun`, anything else → 409 naming the status (`run is running`, `run is awaiting_approval`, …). Both branches write the `kind='resume'` audit row. `POST /api/runs/{id}/resume-now` keeps its path; the web already calls it for pool holds.
- The running-report ACK (built beside `ScopeCeiling` in `runs_dto.go`) gains `pause_requested bool`, **decided by the server**: true when `pause_mode = 'now'`, or when `pause_mode = 'milestone'` and (`milestones_frozen` is empty, or `len(milestones_completed) > pause_after_count`). The worker honours a boolean; the boundary rule lives in one place. `pause_requested` is a worker-facing ACK field and is **not** owner-gated (the ACK goes to the worker holding the run, exactly like `scopeCeiling`); the three `pause_*` columns on the owner-facing DTO are. The claim payload gains `pause_pending bool` and `pause_mode`, like `StopPending`, so a worker that dies with a request pending re-arms it on resume: the columns survive the requeue (no requeue writer touches them), the re-claim seeds the flag, and `pause_after_count` still compares against the monotone `milestones_completed`.
- `SetState` (`worker_protocol.go`) admits `paused` with the same ack contract as `limit_wait` (the worker keys off the returned status), and a new worker report `pause_failed` (body: reason) that calls `ClearPauseRequest`, emits a `pause_failed` feed message and triggers the Slack DM below.
- `runlifecycle`: `paused` joins the In Progress case with a comment in the `limit_wait` style (`:182-188`).
- DTO: `pause_requested_at`, `pause_mode`, `pause_after_count` (owner-only, like `health_reason`: they describe an owner's intent), `checkpoint_tip_at`; `latestRunDTO` needs only the status.
- Slack (`notifier_state.go`): on the `paused` status report, a thread reply `‖ Paused after milestone 3 · checkpoint <short sha> · resume from the run page or \`uzi run resume <id>\``; on `pause_failed`, `⚠ Could not pause: <reason>. The run is still running.`; on the first `running` after a pause, the existing `▶️ Resumed` reply, by generalising the limit-pause marker (`SetSlackRunLimitPause`) to record any park kind, or adding a sibling marker; `handleLimitResume`'s `case` lists gain `paused` where they name the parks.

### Agent

- `protocol.ts`: `"paused"` in the status union; `"pause"`, `"pause_cancel"` in the input union (`resume` never reaches the worker); `pause_requested` on `StateAck`; `pause_pending` / `pause_mode` on the claim.
- `SteeringChannel`: a sticky `pauseMode: "milestone" | "now" | null`, seeded from the claim; `route("pause", body)` sets it (a `now` body also aborts the in-flight turn through a new `PauseNowSignal`, distinct from `cancel` so the catch parks instead of failing); `route("pause_cancel")` clears it.
- Honor gate: a **separate** loop-top branch in the `for (;;)` loop (`sdk-executor.ts:1690-1745`), placed after `served` is read and **outside** the scope block, because that block is gated `isIssueRun && …` (`:1724`, `isIssueRun` from `:862`) and three of the four pausable kinds are not issue runs: `if (served?.pause_requested) { pausedAt = { completedCount: served.completedCount, total: frozenMilestones?.length }; ctx.emit steer_ack {directive:"pause", …}; break; }` for **any** kind. On `PauseNowSignal` in the turn's catch, the same latch. The executor returns a result the runner recognises as "park for pause". An M2 test drives a `prompt`-kind fixture through the gate.
- Runner: the park path mirrors `handleLimitReached` (`:3341-3395`): emit a `paused` feed event, `flush`, publish the checkpoint through `publishCheckpointBestEffort` **first**; if the publish fails, report `pause_failed` (server clears the request), emit the failure, and continue the run as if no pause were pending (a `now` pause whose publish fails also continues: the aborted turn is **restarted** at the next iteration, the same way a cancelled turn is on `revise`, and the `pause_failed` message says so: `Could not pause: <reason>. The run is still running and has restarted the interrupted step.`); if it succeeds, `reportState({status:"paused"})` and clean up as unparked unless `ack.status === "paused"`. HOME is preserved exactly as for a limit park (`:828-860`); the worker frees its slot.
- `TERMINAL_RUN_STATUSES` is **not** touched; a test asserts `paused` is absent and that the reclaim sweep keeps a paused run's HOME.

## Decision log

- **D1: a new status, not a reuse of `limit_wait`.** `limit_wait` is promoted by a clock the server owns (`retry_not_before`) and counts against `RUN_LIMIT_MAX_WAITS`; a user pause resumes only on demand and spends no budget. Overloading the status would make the promotion pass, the Slack wording, the health exemption and the CLI's "auto-resumes" copy all lie. Precedent: `pool_wait` (PRD #754) got its own status for the same reason.
- **D2: the clock stops; the remaining budget is preserved.** Gate-park accounting (`budget_paused_seconds`, issue #783), not the limit park's fresh wall (Decision 6d). A voluntary pause that reset the wall would be an uncapped extension and would make #1189's cap pointless; a pause that consumed budget would punish the owner for waiting. Rejected: fresh wall on resume.
- **D3: a pending pause is a flag, not a status.** From the 2026-09-07 UX review of the mock: a second new status (`pausing`) would have been a DB CHECK value, a board state and a TUI word for a transient the worker may never reach (checkpoint publish can fail). The run stays `running`, which is true, and the request is data the page and the TUI can show.
- **D4: the server decides the boundary; the worker honours a boolean.** The milestone rule needs `milestones_completed` at request time versus now, and whether the run has frozen milestones at all. That is server data, and putting the comparison on the ACK means one implementation, one test table, and a worker that cannot drift from it.
- **D5: `now` drops the in-flight turn.** The same thing the limit park does to a turn (a turn cannot be checkpointed mid-flight), bounded by the 20-minute time-based checkpoints (PRD #267) and the milestone checkpoints. The UI names the age of the last checkpoint so the owner knows what `now` costs before choosing it.
- **D6: only `running` accepts a pause, and a pending pause survives an involuntary park.** Every other non-terminal status is already a park with its own clock stopped and its own exit; pausing a gated run would need a second exit condition on each of them, so the request is refused with a 409 naming the current wait. But a request made while `running` that is overtaken by a usage-limit park or a clarification question is kept: the columns survive the park and the promotion, and the ACK re-fires on the first `running` report after, so the run parks at its next boundary. An owner who said "pause" and then watched the run hit a limit should not have to say it again. Rejected: clearing the columns on every park (loses the intent) and admitting `pause` on parked statuses (a second exit per park).
- **D7: kind allowlist `issue`, non-interactive `task`, `prompt`, `self_improve`.** The other kinds either already park between turns or finish within minutes; a 409 with a reason beats a no-op that looks like it worked.
- **D8: checkpoint first, then park; a failed publish means no park.** A paused run whose work exists only on one worker's disk is a promise the resume cannot keep if that worker rolls. Staying running is the honest fallback; the owner is told and can retry or use `now` later.
- **D9: paused survives worker death and is excluded from every requeue.** A dead worker's paused run must stay paused; on `resume` the ADR-628 affinity leg lets any live worker claim it. Rejected: adding `paused` to `RequeueRunsOfStaleWorkers`, which would silently un-pause on a roll.
- **D10: no maximum pause duration in v1.** The run holds no worker slot and spends nothing; what it holds is its HOME transcript on the worker's volume (~170 MB, the reclaim sweep keeps it) and its forge branch. A `RUN_PAUSE_MAX` that fails or cancels a long-forgotten pause is a follow-up once someone measures the disk cost.
- **D11: `info` tone for the pill.** The involuntary holds are warning-toned because they are something to notice; a pause is something the owner did. The TUI uses the wait colour for both because it has no second hold colour, and the word carries the difference.
- **D12: the TUI gains one word and a row-2 line, no controls.** Owner decision 2026-09-07; the board is triage, and a paused run needs no triage.
- **D13: `waiting:` replaces `paused:` on the rate-limit line.** The old text would read as a user pause once one exists.
- **D14: one resume mechanism, the existing `/resume-now` endpoint widened.** The web already calls it for pool holds and the CLI already has `run resume-now`; widening costs a read-first dispatch on status, and a plain `run resume` verb is added because "resume-now" reads wrong for a run nobody else was going to resume. `resume` is a CHECK value for the audit row the endpoint writes, not a `POST /inputs` kind: two entry points doing the same write would leave one of them dead surface.
- **D15: the pause invariants get an ADR.** They are negative-space rules (a status that must stay out of five lists, a guard that must stay in one query) of exactly the kind the `TERMINAL_RUN_STATUSES` 🔴 note and ADR-628's predicate exist for; a Decision Log entry in a PRD that moves to `prds/done/` is not where the next editor of `RequeueRunsOfStaleWorkers` will look.

## Success criteria

- A running issue run paused with the default mode keeps running until its current milestone is reported complete, then shows `paused` within one worker report, its checkpoint is on the forge, its worker is free, and `uzi run get`, the page, the TUI and Slack all say so.
- `Cancel pause` before the boundary leaves the run running with no trace but the audit rows; `Pause now` parks within one turn abort and names what was discarded.
- `resume` on the same live worker continues the SDK session with no re-plan; `resume` while that worker is draining waits for its new pod and then continues the session; `resume` after the worker is gone lands on another worker, recovers the tree from the checkpoint and re-plans only the remaining milestones; in every case the remaining budget equals what it was at the pause.
- A pause requested before a usage-limit park lands at the first boundary after the run resumes from that park; a late `running` report never un-pauses a paused run.
- A paused run is never failed by the timeout sweep, never requeued by a worker's death, never health-flagged, and its HOME is never reclaimed.
- A pause on a chat run, an interactive task, a judge run, or a run at a gate is refused with a message that names why.
- `task gate` green; one migration; no workflow file in the diff.

## Risks

- **Landing order with #1189.** Both PRDs touch `runtime.sql` (`SetRunCheckpointTip`, `ConsumeRunInputs`), `runs_dto.go`, `apitypes/run.go`, `RunView.tsx` and the `SteerQueueCard` row, and both draft a migration (`00203` / `00204`). Rule: **whichever merges first owns `checkpoint_tip_at`** (the column and the `SetRunCheckpointTip` stamp); the second, on its landing rebase, drops its own `ADD … IF NOT EXISTS` and `DROP`, keeps the stamp as it finds it, adds its kind to the `ConsumeRunInputs` exclusion list rather than replacing it, and renumbers its migration to the live head. The other collisions are textual (adjacent DTO fields, adjacent buttons) and resolve in the rebase. `check:migration-numbering` catches a duplicate prefix.
- **The 74-file checklist.** A status added in one place and missed in another shows up as a raw `paused` word or a wrong column: the `ui.test.tsx` label loop, the TUI render test and the lifecycle test cover the three surfaces that would misrender; run `git grep -n -F pool_wait` at the end of M1 and M3 and check each hit that branches on a status list.
- **Old worker against a new server.** An old worker never reports `paused` and ignores `pause_requested`; a pause requested on its run waits until the fleet rolls. An old TUI draws the default `· paused`, legible. Neither errors. An old server against a new worker never sends `pause_requested`; the worker's flag stays false.
- **`pause_failed` leaves the owner mid-intent.** The Slack DM and the feed line say the run is still running; the page's chip disappears because the server cleared the request. The M3 test pins that the chip goes away.
- **The `now` abort path shares code with `cancel`.** `PauseNowSignal` must be caught before the generic cancel catch; a test that a `now` pause does not produce `REASON_CANCELLED` or a `failed` report guards it.
- **`sqlc generate` needs the module proxy** (see PRD #1170's Risks for the offline hand-edit shape).

## Out of scope

- Extending the budget (PRD #1189); this PRD reads its `budget_total_seconds` when present and renders without it otherwise.
- A maximum pause duration or auto-cancel of stale pauses (D10).
- Pausing a run that is at a gate or a limit park (D6).
- A pause from Slack or the TUI; both read-only for this feature.
- Renaming `budget_paused_seconds`, which now also counts user pauses; its comment gains a sentence, the column keeps its name.
