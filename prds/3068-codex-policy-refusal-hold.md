## Binding outcome and kind fence

Admit a hold only when **harness is Codex, origin is root, kind is one of `issue`, `task`, `prompt`, `self_improve`, and `interactive=false`**, with both sides negotiated. A server predicate and worker predicate enforce the same positive fence. Chat, interactive runs, Claude, judge, job, cross_check and any other kind retain their current behavior. Child refusals continue returning `child_policy_refused` to their lead.

Eligible refusal: `status='paused'`, `hold_reason='provider_policy_refusal'`; retain work, conversation identity, custody and worker affinity. No intentional automatic refusal retry, fresh lead conversation, harness switch, terminal refusal cap or hold expiry. The bounded existing terminal-pending lease has an explicit residual worker-loss race below; this is not a global exactly-once execution guarantee. A further owner-authorized attempt that is refused holds again. A refusal classification is displayed neutrally, without claiming why the provider refused.

### User decisions 2026-10-16

- **Q1 / B1: admit plan-REVISE refusals, user decision 2026-10-16 (q-rp-1(a)).** Hold a root planning refusal while `awaiting_approval` only when the current claim is verifiably revising; preserve the original plan and gate. Initial planning and implementation refusal behavior is unchanged by this choice.
- **Q2 / S1: until terminal, user decision 2026-10-16 (q-rp-2(a)).** After the first actual refusal, every later fresh lead conversation requires exact-claim owner consent, even after a successful resume.
- **Q3 / S7: three milestones, same run/PR, user decision 2026-10-16 (q-rp-3(a)).** M1 hold/preserve-resume/guidance/Cancel via CLI; M2 fresh retry/Stop/set-token/wall race; M3 web/TUI/Slack.

Owner actions, in scope:

1. **Resume with guidance:** preserve the original conversation. Persist guidance before making the run claimable. If that conversation cannot continue for any reason, re-park `resume_rejected` and tell the owner; do not issue `thread/start` as a fallback.
2. **Retry in fresh session:** a separate, explicit owner choice with confirmation that conversation context is discarded while recovered files and the execution contract remain. It grants one fresh-session claim, not permission for future automatic fresh sessions.
3. **Stop:** finalize what is already complete, mirroring the existing `CanStopAtProviderHold` availability gate (noninteractive milestone issue, at least one completed milestone). No further milestone starts. Other admitted kinds show why Stop is unavailable rather than claiming they can finalize milestones. Stop does not authorize a fresh lead conversation. A Stop claim whose authoritative completed scope is already at its ceiling skips only the early session re-park check and follows normal executor execution. The existing scope boundary prevents a root turn. The harness fresh-thread guard remains authoritative if execution unexpectedly reaches a thread start; no separate Stop dispatcher/result builder is added.
4. **Cancel:** existing terminal cancellation and separate custody disposition rules.

Harness changes and manually transferring work to another run remain separate existing operations, not a new continuation action here. Do not promise that a new run automatically adopts another run's checkpoint: checkpoint adoption is run-owned and claim-bound.

## Acceptance examples

- Root planning or implementation refusal holds with tag, phase, opaque correlation, count, checkpoint provenance and the owner actions. Draft planning output remains unapproved evidence; no plan gate or another model turn is manufactured.
- Owner supplies guidance and resumes on the same usable conversation. The next root turn includes the guidance. Another actual refusal increments the count once and holds again.
- A different worker, missing/unknown transcript, changed Docker attempt path, absent session id or provider rejection of `thread/resume` causes `resume_rejected`, preserves the count and original refusal metadata, and starts no fresh thread/model turn.
- Owner explicitly chooses fresh retry. Exactly the authorized claim may start a new conversation; the new thread id is persisted. A crash before that identity is durably recorded must not grant a second automatic fresh start to a later claim.
- Failed checkpoint publication still holds; display local-only/unverified preservation truthfully. Pending hold delivery cannot disappear from a healthy worker's snapshot and cause an automatic replay. API-confirmed hold is distinct from a locally journaled, delivery-pending outcome.
- Stop finalizes only the completed scope; Cancel terminates. A budget-exhausted owner hold says **extend first**. None of these actions silently switches harness or disables provider controls.
