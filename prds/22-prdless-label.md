# PRD #22: PRDLESS Label — Run Issues Without a PRD Link

**GitLab Issue**: [#22](https://gitlab.example.com/vtmocanu/uzi/-/issues/22)
**Status**: In progress — M2/M4/M5 done (3/6); M1/M3/M6 blocked on prd-21 landing to main
**Priority**: Medium
**Created**: 2026-07-05

**Depends on**: PRD #19 (`app_settings` infra, admin GET/PUT, Settings UI, bootstrap label delivery, autopilot) — **landed**, all references below are against the shipped code. **Hard coordination dependency on the in-flight `prd-21-mission-control-theme` branch**: it rewires settings validation from the uniform `ValidateLabel` call to a per-key `settings.Validate(key, value)` switch and touches the exact files M1 edits (`api/internal/settings/settings.go`, `api/internal/handler/settings.go`, `web/src/pages/AdminSettings.tsx`). Land #22 M1 **after** prd-21 and reuse its `Validate()` switch; if prd-21 stalls, M1 owns introducing the switch instead. No migration needed (see Technical Design).

## Problem

Every run requires a `prds/*.md` link in the issue description. The gate is enforced server-side in the shared `createRun` (`api/internal/workersvc/service.go:657-658` → `ErrNoPRDLink`), which both the manual `CreateRun` and the autopilot `CreateAutopilotRun` paths call; the handler maps it to a 422 (`api/internal/handler/workers.go:307-314`). The web app surfaces it as "no PRD link" warning badges (`web/src/pages/Board.tsx`, `web/src/pages/IssueView.tsx`). (Line refs approximate; the tree moves.)

That gate is the right default — the PRD is the agent's spec, and issues without one produce aimless runs. But for genuinely small work (a typo fix, a one-file tweak, a smoke test like issue #20's `vlad-test.txt` file) the gate forces authoring a throwaway `prds/*.md` file whose entire content restates the issue description. The workaround people actually use — a fake link to a nonexistent PRD file — is worse than an explicit escape hatch: it satisfies the regex (`forgesvc.prdLinkRe` matches the path shape, not file existence) while lying on the board.

## Solution Overview

An admin-controlled escape-hatch label, default name **`PRDLESS`**:

1. **Two new `app_settings` keys**: `prdless_enabled` (bool, default `true`) and `prdless_label` (default `"PRDLESS"`). Both editable on the admin Settings page: a toggle plus a name field (name field disabled while the toggle is off).
2. **Gate bypass**: when the feature is enabled and the issue carries the prdless label, run creation skips the `HasPrdLink` check — on both the manual and the autopilot path. Everything else about the run is unchanged — same state machine, same planning turn, same approval gate, same guardrails.
3. **Web surfaces**: the "no PRD link" warning badge is replaced by a distinct `PRDLESS` badge on cards/issue view when the bypass applies; the session bootstrap payload (`sessionPayload`, which already carries `prd_label`/`autopilot_label`) additionally carries `prdless_label` + `prdless_enabled`.
4. **UI label toggle**: the label can be applied/removed directly from the uzi web UI (issue view, and the card on the board) — forge-first write, same pattern and trust model as board column moves. No round-trip to GitLab's UI needed for the common case.

## Design Decisions

1. **On by default** (user, 2026-07-05). The escape hatch is available out of the box; an issue still only bypasses the gate if someone deliberately applies the `PRDLESS` label, so default-on does not weaken anything for unlabeled issues. Admins who want the strict PRD-only regime flip the toggle off.
2. **The label is checked on the forge-fresh snapshot, not only the cache.** Both run-creation paths already fetch the issue from the forge right before creating the run — the manual handler (`api/internal/handler/workers.go:275-280`) and the autopilot poller (`api/internal/poller/autopilot.go:176`) — and `forge.Issue.Labels` is on the snapshot. The bypass decision uses those fresh labels, so a just-added PRDLESS label works immediately without waiting for a poller cycle. Matching is **exact** (case- and whitespace-sensitive), the same way board column labels match. The cached `issues.labels` column keeps board badges honest between polls.
3. **Policy in the callers, enforcement in the service** (review round 1 finding 1, revised in round 2). `workersvc` today has no settings dependency and should not gain one. Each caller that holds a fresh snapshot computes `allowWithoutPRD := prdlessEnabled && slices.Contains(issue.Labels, prdlessLabel)` and passes that single bool down: the manual handler into `CreateRun`, the autopilot poller into `CreateAutopilotRun`. The shared `createRun` gate becomes `if !issue.HasPrdLink && !allowWithoutPRD { return ErrNoPRDLink }` — one enforcement point, two policy call sites. (Round 2 correction: the autopilot path does a fresh `GetIssue` too, so it uses the fresh snapshot exactly like the manual path — no cached-labels special case, and autopilot parity is part of M2, not a follow-up.)
4. **The gate is evaluated once, at run creation** (review round 1 finding 5). Disabling prdless (or removing the label) neither stops nor re-gates an already queued/claimed/running/awaiting-approval run — the sweeper requeue paths and `Claim`/resume never re-check `HasPrdLink` today, and prdless inherits that: toggling off only blocks *new* runs. Documented, deliberate.
5. **Bypass is a gate exception, not a mode.** No new run flag, no claim-payload change, no prompt-template variant. The run proceeds exactly as a PRD-linked run does; the agent works from the issue description alone (which is already the run's `issue_description` snapshot). If the description is thin, the planning turn + human approval gate — both retained — are the safety net, which is precisely why prdless does NOT touch the approval flow.
6. **Quality gate, not a security boundary — and it stays that way.** Who can apply the label is bounded by GitLab (project members with at least Reporter can label) plus, via the UI label endpoint, anyone with a uzi session on a connected repo — the same population that can already move cards between columns (which is also a forge label write). The bypass never weakens any of the four `main`-protection layers, and the human still clicks Start and approves the plan. Autopilot composition: an issue carrying PRD + autopilot + PRDLESS labels runs unattended with no PRD — allowed by design (all three are explicit opt-ins) but must be called out in docs, and M2 covers it with a composition test.
7. **Label-name validation via per-key dispatch.** Reality check against main (review round 2 finding 1): there is **no per-key validation switch in main** — `UpdateSettings` runs a uniform `settings.ValidateLabel(value)` over every known key (`api/internal/handler/settings.go:57-67`), which would silently accept `prdless_enabled="banana"`. The **prd-21 branch introduces** `settings.Validate(key, value)` (per-key dispatch, `default:` → `ValidateLabel`). M1 registers into that switch (or introduces it, per the Depends-on line): `prdless_enabled` → strict bool parse (`"true"`/`"false"`); `prdless_label` → label rules (non-empty, ≤ 64 chars, no comma) **plus** pairwise-distinct from both `prd_label` and `autopilot_label` (equal to `prd_label` would exempt every issue; equal to `autopilot_label` would conflate "hands-off" with "spec-less"). Distinctness edge cases (review round 1 finding 6): enforced **regardless of the toggle state** — a disabled-but-colliding prdless label must be renamed before the conflicting `prd_label`/`autopilot_label` value can be saved (keeps re-enabling always safe; the error message says which key to rename); and a single PUT changing multiple keys validates the **post-merge set atomically**, never each key against stale stored values. Disabling the toggle does not clear the name — re-enabling restores the previous label.
8. **Label creation happens on first UI apply, not at settings-save time.** Saving the setting never touches the forge. But the UI label endpoint (Decision 10) calls `forge.EnsureLabels` before an apply, so the label is auto-created on the project the first time someone applies it from uzi — the same mechanism board column labels use. `EnsureLabels` requires a color (GitLab label creation needs one; column labels pin theirs in `handler/board.go`), so M4 defines a color constant for the prdless label. Admins applying the label from GitLab's own UI instead still create it themselves there; docs cover both paths.
9. **`has_prd_link` semantics are untouched, and prdless settings edits don't trigger repo resyncs.** The cached flag and the `HasPRDLink` regex keep meaning "description links a PRD file". The bypass is computed at decision points (run creation, badge rendering) as `hasPrdLink || (prdlessEnabled && labels.contains(prdlessLabel))` — no schema change, and the board converges instantly on toggle because badges derive from data already present client-side. Corollary (review round 2 finding 9): the settings PUT calls `ForceReconcile()` for changed keys (`handler/settings.go:164`); the prdless keys don't affect the poller's PRD-label filter, so M1 excludes them from the `changed` set — the precedent prd-21 sets for its presentation-only `default_theme` key.
10. **UI apply/remove is a new single-label helper, not `AutoMove`** (review round 2 finding 5). `AutoMove` is column-semantics: `board.PlanLabelMove` strips all *other column labels* to enforce single-column membership — reusing it for prdless would clobber columns. M4 adds a dedicated forgesvc helper that only adds or removes the one prdless label and preserves everything else, keeping `AutoMove`'s forge-first discipline: diff the prdless label against the issue's current cached labels first (already present on apply / already absent on remove → local no-op success, **no forge call**); otherwise `EnsureLabels` (apply only) then one `UpdateIssueLabels` call with a single-element add or remove set; only on forge success update the cache **incrementally** (add/remove the one label on the current cached set — never a wholesale overwrite computed from stale data). The endpoint is scoped to the prdless label only (resolved server-side from settings — the client never names the label), returns 422 when the feature is disabled, and rides the normal cookie+CSRF session **plus the per-user forge limiter** like every other forge-writing route. Generic arbitrary-label editing from uzi is explicitly out of scope: labels are board semantics (columns, PRD, autopilot, prdless), and free-form label management stays in GitLab.

## Technical Design

### 1. Settings (api)

- Keys `prdless_enabled` (`"true"`/`"false"` in the TEXT KV store, typed bool accessor in `api/internal/settings` alongside `PRDLabel`/`AutopilotLabel`) and `prdless_label`. Compiled-in defaults (`true`, `"PRDLESS"`) go in the `Defaults` map — `Cache.All`/`Effective` range over `Defaults` and return every known key with its default, so **absent rows are synthesized server-side** and `GET /api/admin/settings` always includes both keys; no client-side default synthesis, no seed rows, **no migration**.
- Validation per Decision 7: register both keys in the per-key `Validate(key, value)` switch (prd-21's, or introduce it), bool parse + label rules + pairwise-distinctness on the post-merge set.
- Exclude both keys from the `changed` set that triggers `ForceReconcile` (Decision 9).

### 2. Gate bypass (api)

- Per Decision 3: both callers compute `allowWithoutPRD` from their fresh snapshot and pass the bool in — `CreateRun` (manual, handler) and `CreateAutopilotRun` (poller, `api/internal/poller/autopilot.go:176-197`); the shared `createRun` gate (`api/internal/workersvc/service.go:657-658`) becomes `if !issue.HasPrdLink && !allowWithoutPRD { return ErrNoPRDLink }`. `workersvc` gains no settings dependency.
- The signature changes touch the existing no-PRD-link tests — now two of them, manual (`api/internal/workersvc/service_test.go:~879`) and autopilot (`:~909-912`) — update them in M2, don't bolt on parallel ones. Add the composition test (PRD + autopilot + PRDLESS labels, no PRD link → unattended run) in M2 as well.
- The 422 message (`workers.go:307-314`) is extended when prdless is enabled instance-wide: `"issue has no PRD link; add a prds/*.md link (or the PRDLESS label) before starting a run"` — the label name interpolated from settings.

### 3. UI label toggle (api + web)

- Endpoint: `POST /api/repos/{id}/issues/{iid}/prdless` (`{id}` matches the existing route convention, cf. `POST /api/repos/{id}/issues/{iid}/move` in `api/internal/handler/handler.go:~247` and `repoForRequest`), body `{"apply": true|false}`. Registered under `RequireAuth` **with `forgeLimiter.PerUserMiddleware`** like move/sync/create-run.
- Handler flow: load settings → 422 if `prdless_enabled` is off → resolve label name server-side → call the new forgesvc single-label helper (Decision 10: cached-labels diff for idempotent no-op, `EnsureLabels` on apply, one `UpdateIssueLabels`, incremental cache update on success).
- Response: the refreshed card DTO built the same way `MoveIssue`'s is — including the column-position map and the `latest_run` re-hydration `MoveIssue` does so a single-card replace doesn't blank the run badge (`api/internal/handler/board.go:~515-528`).
- Web: a toggle affordance on `IssueView.tsx` (primary) and the board card (secondary, e.g. next to the existing card actions) — visible only when `prdless_enabled`; reflects current label state from cached labels; no optimistic update (wait for the 200, per forge-first discipline).

### 4. Web badges + bootstrap

- Bootstrap: add `prdless_label` (string) and `prdless_enabled` (bool — `sessionPayload` in `api/internal/handler/auth.go:~279-287` currently emits only strings, so this adds its first bool field, backed by the typed accessor) alongside the existing labels.
- `Board.tsx` card badge and `IssueView.tsx` badge: when `!has_prd_link`, show the warning badge unless prdless is enabled and the card's labels include the prdless label — then show a distinct badge (e.g. tone `warning`→`accent`, text `PRDLESS`, title "PRD-link gate bypassed by label").
- Board label-suggestion filter also excludes `prdless_label` from column suggestions.
- Admin Settings page: toggle + name field per Solution Overview (coordinate with prd-21's `AdminSettings.tsx` changes).

### 5. Docs + specs

- `docs/`: admin-settings page section (what prdless does, that it's a quality-gate bypass not a security change, the autopilot composition caveat, label auto-created on first UI apply / create-it-yourself when labeling from GitLab).
- `specs/ai.md`: decisions above. `specs/human.md` (user approval required): the prdless user story.

## Risks

- **Erosion of the PRD discipline**: the label must be deliberately applied per issue, the settings toggle is admin-only, and the plan-approval gate is retained; instances wanting the strict regime disable the feature. (Note the two "toggles" are different populations: the *settings* toggle is admin-only; the *label* apply/remove endpoint is any uzi session on a connected repo, Decision 6.)
- **Label added by a low-trust GitLab member or any uzi session user**: same trust model as board columns (labels already drive board moves, from both GitLab and the uzi UI); the human Start click (or the deliberate autopilot label) remains the actual trigger.
- **Skew between fresh labels and cache**: badges may lag a poller cycle behind GitLab; the gate itself never lags because it reads the fresh snapshot (Decision 2). The UI toggle updates the cache synchronously on success; a concurrent poll can transiently clobber that write with a pre-write snapshot (same last-write-wins skew board moves already live with) and it self-heals on the next forge-authoritative poll.
- **prd-21 merge conflicts**: M1's three files are all touched by the in-flight prd-21 branch — sequencing per the Depends-on line avoids rework.
