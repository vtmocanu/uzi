**Priority**: Medium

**Mockup**: `prds/mockups/41-plan-revision-mock.html` (4 states: gate open → Request-changes composer → revising → re-gated v2)
**Depends on**: PRD #4 (plan gate + steering wire, done), PRD #33 (stop_kind semantics, done). **Independent of PRD #39** (chat agent): revision reuses the gate's existing verdict-await mechanism; #39's blocking await-follow-up primitive is not needed here.
**Related**: PRD #19 (autopilot auto-approve — untouched by design), PRD #25 (Slack surface: gate buttons M4, replier M5 — extended by Decision 10, incl. a scoped reversal of its plan content-minimization), specs/ai.md §51 (SDK session resume — the mechanism revision rides).

## Problem

The plan gate is binary. A user reviewing a plan at `awaiting_approval` can approve or reject-with-reason — and reject **fails the run** (`PlanRejectedError` thrown at `sdk-executor.ts:309`, converted to `status=failed` at `runner.ts:195-200`). There is no way to steer: "drop step 3, reuse the existing endpoint" requires killing the run, editing the issue, and re-running the whole planning turn from scratch on a fresh run. Follow-ups sent while parked don't help — `steering.ts` deliberately queues them past approval (they inject into the *implementation* turn, `steering.ts:11-14`), so they cannot influence the plan they were aimed at.

## Solution Overview

A third gate action, **Request changes**: the user's feedback is delivered to the *planning* session as a new steering verdict kind (`revise_plan`); the worker resumes the same SDK session with the feedback, the lead produces an updated plan, and the gate re-opens with plan v2. Bounded revision rounds; approve/reject semantics unchanged; autopilot's auto-approve short-circuit never sees any of it. The gate loop is **round-aware** via a monotonic epoch: a verdict can only ever apply to the plan version the user was actually shown, on every surface — worker-side epoch discard for the web wire, generation-guarded anchors + server-enforced supersede for Slack (Decisions 3/10, where both review rounds concentrated their blocking/high findings).

## Design Decisions

1. **`revise_plan` is a fourth steering-input kind, not a repurposed `follow_up`.** `run_user_inputs.kind` CHECK (`00020_workers_runs.sql:86`) gains `'revise_plan'`. Repurposing `follow_up`-at-gate was rejected: follow-up's "queue for the next implementation turn" semantics are load-bearing (a user may legitimately park an implementation note while deciding on the plan; the Slack replier even documents the split, `replier.go:164-170`), and overloading it would make the gate's behavior depend on run status at delivery time — a race. A distinct kind keeps both wires unambiguous.
2. **One gate-event mechanism, epoch-tagged — not a second delivery primitive bolted beside the verdict buffer (↳review-r2 BLOCKING 1/3, reworked to the reviewer's simpler shape).** The first draft of this decision mixed two primitives (latest-wins verdict buffer + a follow-up-style FIFO for revises) and was unbuildable as specified: the FIFO never wakes `awaitVerdict` (a lone revise would park until the 24h deadline), and the buffer can't hold two revises. Rework: `steering.ts` keeps today's latest-wins buffer for approve/reject (cancel additionally trips the AbortController, unchanged), adds a FIFO revise queue, and the gate waits on a single **epoch-tagged gate-event select** that (a) is woken by a revise enqueue as well as by verdict delivery, (b) enforces per-round precedence in one place — **a current-epoch revise beats a buffered approve** (so the batch [revise, approve] yields one revision round then a fresh gate, never an approve of the pre-feedback plan), and (c) discards prior-epoch verdicts (Decision 3). `PlanVerdict` gains `{kind: "revise", feedback}`. The gate loop lives where the gate lives today: `sdk-executor.ts` phase 1 becomes `plan → gate → (revise → resume session with feedback → require new plan → re-gate)*` until approve/reject/cancel, fail-closed (any loop exit that is not an explicit approve/reject/cancel is an error). The planning session is resumed via the same `resumeId` the executor already threads between turns (§51) — full planning context, no transcript replay.
3. **Round-awareness via a monotonic epoch, with the barrier AT the re-report (↳review-r2 BLOCKING 2 — the round-1 fix put the barrier at the wrong instant).** Round 1 placed the stale-verdict discard at revision-turn start, leaving the entire revision turn (minutes) unguarded: an approve clicked mid-revision would buffer and instantly resolve the v2 gate — implementing a plan no human saw. Rework: the steering channel carries a **gate epoch**, incremented at each `awaiting_approval` (re-)report — the last step before the gate awaits the new round. Every verdict is stamped with its arrival epoch; the gate-event select accepts approve/reject only from the **current** epoch and discards older ones with a feed notice ("approval ignored — the plan changed"); `cancel` is epoch-exempt (always applies). Queued revises are epoch-stamped and discarded the same way (↳review-r2 MAJOR 4, decided): feedback authored against v1 does not silently spend a round revising a v2 the user hasn't reacted to — the feed notice invites a re-send. Honest cap consequence: the discarded revise's persisted row still counts toward the server-side budget (Decision 6 counts rows as a spend upper bound; strictness favored, stated as a residual). The server keeps accepting approve on any non-terminal run — staleness is resolved at the single consumer, the gate. Tests pin: approve-during-revision (any instant between feedback send and re-report) is discarded; approve-after-re-report lands; [revise, approve] in one poll batch → one revision round then a fresh gate; lone revise wakes the gate immediately; stale queued revise discarded with notice.
4. **The run stays in `awaiting_approval` while revising — no new run status.** A new `revising_plan` status would touch the status CHECK, the sweeper, the board lifecycle maps (`runlifecycle/lifecycle.go:143-172`), badges, and every status switch in web — for a state that is worker-internal and short. Instead the worker emits a `plan_revising` run-message (and later the new `plan` message) so the UI derives the state from the feed (Decision 9 specifies the derivation rule). Honest consequence: `RUN_TIMEOUT` continues not to apply while parked-or-revising (`SweepRunningTimeout` matches `status='running'` only, `runtime.sql:306-312`); the bounds are Decision 5's clocks. This also avoids the trap where flipping back to `running` mid-revision insta-fails the run (`started_at` is not reset by revision, and a run that parked >2h would already be past the cutoff).
5. **Clocks, honestly (↳review D2/D6 — the original "timer NOT reset" claim was not achievable as structured).** (a) **Total gate deadline**: `gatePlan` creates a fresh 24h `setTimeout` per call (`runner.ts:269-273`), so a naive per-round `gatePlan` call would reset the clock each round (~4×24h worst case). The gate deadline is therefore hoisted to an **absolute deadline computed at first gate entry** and threaded through every round (the `wallRemainingMs` threading pattern, `sdk-executor.ts:485-493`); timeout still resolves as reject with "plan approval timed out". (b) **Revision turns spend the run's single cumulative wall budget** — there is no per-revision wall-clock; `wallRemainingMs` is one pool debited across ALL turns including revisions, so N slow revisions genuinely starve the implement/review loop's budget. Stated as the real cost instead of inventing a new mechanism; the round cap (Decision 6) is what keeps it small. (c) Idle detection inside a revision turn: the existing `driveTurn` idle machinery applies unchanged.
6. **Bounded rounds: `PLAN_MAX_REVISIONS` (default 3), enforced twice, counting the same thing (↳review D3/S2).** Server: `SubmitInput` rejects the N+1th `revise_plan` with a clear 4xx, counting **all persisted `revise_plan` rows for the run with NO `consumed_at` filter** — `ConsumeRunInputs` marks-consumed but never deletes (`runtime.sql:407-421`), so consumption must not reset the count (counting only pending rows would silently defeat the cap). Worker: independent round counter refusing further rounds with "revision budget exhausted" prose in the feed; resets on requeue by design, which is why the server count is the authoritative bound. Off-by-one pinned: N revisions allowed, N+1th refused. Wiring: the cap rides claim config like the iteration caps (`claim.go:141-143` pattern), env `PLAN_MAX_REVISIONS` on the API side. A test asserts a consumed revise still counts.
7. **Server-side handling of `revise_plan` mirrors `approve_plan`, not `reject_plan`.** In `SubmitInput` (`workersvc/service.go:1009`), revise is a plain enqueue: no stop-verdict CTE, no `stop_kind` stamp, no server-side transition when the poller is stale (a revise aimed at a dead worker waits for the requeue+affinity resume, same as an approve would). Known edges, accepted and documented: (a) a worker that consumed the revise and then died loses it — the consume path has no ack (`ConsumeInputs`, `service.go:727-730`, backed by the `ConsumeRunInputs` query); the user re-sends, same as existing steering; (b) a `reject_plan` submitted mid-revision buffers rather than aborting the in-flight turn (only `cancel` trips the AbortController, `steering.ts:107-109`) — the reject lands at the next gate entry; the turn's spend is wasted but bounded (↳review D10).
8. **Autopilot is structurally unaffected.** The auto-approve short-circuit (`runner.ts:257-263`) resolves the gate before any `/inputs` wait, so an autopilot run can never receive a revise verdict. No code change, one test pinning it.
9. **Plan history rides `run_messages`; `runs.plan_md` stays "latest plan"; feed ordering is specified (↳review D7/D8).** Every revised plan is re-emitted as the existing `plan` message kind and re-reported via `reportState({status: "awaiting_approval", plan_md})` (`SetRunAwaitingApproval`, `runtime.sql:203-210`) — the run row always holds the plan being gated; the feed holds every version plus the feedback that produced it (user feedback emitted as `plan_feedback`; `run_messages.kind` carries no CHECK, per PRD #39 D12). Ordering contract: the revision loop mirrors today's flush-before-re-report (`runner.ts:252-265`) — `plan` message flushed, then `awaiting_approval` re-reported — so the feed never lags the state. UI derivation rule: the panel state is the **latest of {`plan`, `plan_revising`} by `seq`** (not "a plan_revising exists"), else the chip sticks after re-gate. Both new kinds get explicit render cases in `RunEvent.tsx` (beside the `plan` case at `RunEvent.tsx:721`) and ActivityFeed; feedback renders through the untrusted `<Markdown>` component or the escaped default — never a raw sink (react-markdown, no rehype-raw; a vitest pins the new kinds render escaped, ↳review S5).
10. **Slack gets full gate parity: see the plan, steer the plan (user decision 2026-07-10; supersedes the review's minimal-fix scoping and, for `plan_md` only, PRD #25's content-minimization).** Two prior facts change deliberately: (a) the gate message today contains **no plan excerpt** by design (`gate.go:33-41` — "the plan stays behind the deep link"); the user chose parity, so on every gate and re-gate the notifier posts the plan into the run thread, with the exact pipeline pinned (↳review-r2 F3/F7): `ScrubSecrets` → **`EscapeMrkdwn` applied to the entire plan blob** → truncate on a rune boundary to Slack's 3000-char section-block limit (an external API limit not enforced by slack-go or poster.go today — net-new work) → append the "full plan in uzi" deep link as separate trusted markup outside the truncated region. Whole-blob escaping is deliberate and load-bearing: plan_md quotes attacker-influenceable forge content, and unescaped mrkdwn (`<https://evil|Open in uzi>`, `<!here>`, `<@U…>`) would render as clickable spoofed links/mentions in the owner's DM — note this is the *opposite* of the per-field rule `EscapeMrkdwn`'s own doc mandates for interleaved-markup strings (`redact.go:18-20`), correct here precisely because the blob contains no trusted markup. A test asserts a plan containing `<`, `>`, `<@U…>`, `<https://…|…>` renders inert. Truncation is safe against secret-splitting (scrub patterns are prefix-anchored greedy, `redact.go:28-30`; a split escape entity renders as literal text) and the deep link exposes only a run UUID behind auth. The thread copy is **lossy by design** (↳review-r2 design 10): a multi-KB plan truncates mid-structure and escaping mangles mrkdwn niceties — acceptable because the deep link is the canonical rendering. Privacy honesty (↳review-r2 F4): this reversal materially widens what leaves the box — plan bodies quote source and issue content, and neither the worker redactor (the run's own four secrets) nor `ScrubSecrets` (three credential patterns) catches an unrelated secret the model quoted into a plan (an `AKIA…` key, a plain password). Gate posts go to the owner's 1:1 DM (`notifier.go:146`), so exposure is Slack's cloud + workspace admin/export boundary, not other members. `docs/slack.md` (which today promises "run status metadata") and ARCHITECTURE.md's trust model MUST be updated to say plan content now goes to Slack's cloud and non-pattern secrets in plans are not scrubbed. The reversal is scoped to `plan_md`; all other content minimization stands. (b) The gate gains a third button, **Request changes**, working exactly like today's reasoned reject: pressing it flips the gate anchor to a new `revise-pending` state (mirroring `gateStateRejectPending`, `gatekeeper.go:115-126`), and the next thread reply is the feedback — the replier's state machine (`replier.go:148-183`) gains a `revise-pending` branch submitting `revise_plan` (with the same stale-status guard as the reasoned-reject branch, so a reply after the gate resolved elsewhere never triggers a round). A bare reply during an open gate keeps nudging (updated string naming all three actions) — no accidental revisions from casual comments. Also required regardless of parity (↳review D4 — MAJOR; ↳review-r2 F1/F2 — the two HIGHs that make it concrete): the re-gate hazard is real and confirmed end to end — a v2 re-report *does* re-fire `PublishState` (SetRunAwaitingApproval's WHERE only excludes terminal states, `runtime.sql:209-210`) but the notifier's `gateOpen` short-circuit (`notifier.go:203-206`) swallows it, so no v2 gate posts and v1's Approve stays live; and the gatekeeper's stale-click guard checks run status only (`gatekeeper.go:98-104`), which a stale click passes because the run is still `awaiting_approval` for v2. Five named fixes (↳review-r2 F1/F2 + design MAJOR 5/6/7/8): (a) **a gate generation reaches the anchor** — `slack_run_messages` gains a `gate_generation` column (the Slack carrier of Decision 3's epoch; `GetSlackRunContext` exposes no revision signal today, and without one the notifier either never re-posts — this bug — or re-posts on every redundant state broadcast, DM spam). `handleGate` keys re-posting on generation change, not on "gate already open"; each re-gate posts a fresh gate message (plan vN), edits the previous one button-free to "superseded by plan vN", and updates `gate_ts` + `gate_generation`. (b) **Superseding is server-enforced, not best-effort**: the gatekeeper refuses a click whose `a.MessageTS != anchor.GateTs` ("this gate was superseded — see the latest message"), so the no-unseen-plan guarantee never depends on a best-effort Slack message edit; this also stops a stale Reject/Request-changes click from overwriting the live anchor's `gate_ts` with the old message ts (`gatekeeper.go:119-121`). (c) **The revise-pending reply accept is a compare-and-swap, because the reject-pending guard does not transfer** (↳review-r2 design 5): reject's `run.Status=="awaiting_approval"` guard (`replier.go:149`) is safe only because reject makes the run terminal; revision keeps the run `awaiting_approval` throughout (Decision 4), so two replies would both pass. Accepting the first reply atomically clears `revise_pending` (conditional `SetSlackRunGate`, single winner); the loser gets the nudge. (d) **One ordering rule for the anchor row** (↳review-r2 design 7): all gate-anchor writes are generation-guarded — the notifier writes `gate_ts`/`gate_generation` when posting generation N; gatekeeper/replier clears are conditional on the anchor still pointing at the message they acted on; stale writers lose, so a replier clear can never clobber the freshly-posted v2 anchor. (e) **The plan-in-thread post is bound to the fresh-gate-post branch, keyed by the same generation** (↳review-r2 design 8) — never to `handle()` itself, which runs on every `awaiting_approval` re-broadcast (the notifier's `renderThread` returns "" for `awaiting_approval` today precisely to avoid thread spam, `notifier.go:181,271-273`). (f) Decision 3's worker-side epoch discard covers verdicts sent *before* the re-report; (a)+(b) cover clicks *after* it.
11. **Revision feedback is the user's own text — no untrusted-evidence wrapping, and honest limits on redaction (↳review S4).** The prompt injected into the planning session frames feedback as the plan reviewer's instruction (it IS the human owner speaking, unlike forge-derived text). Redaction honesty: the run redactor knows only the run's own four secrets (`runner.ts:78-80`) — feedback containing an unrelated pasted secret is stored verbatim in `run_messages` and is admin-visible like all run content (`GetRunForViewer`, parity with reject reasons and follow-ups today, not a new hole). `docs/` states that feedback is stored in the run feed and visible to admins.
12. **Kind whitelist changes in every place it lives (↳review S3/D12).** Three server/client sites move together: the handler's `runInputKinds` map (`handler/workers.go:44-47`) + its error string (`workers.go:487`), the DB CHECK (migration), and web's `RunInputKind` (`api.ts:550`). A partial update fails oddly (400 vs 500 on CHECK violation) — named here so it's one commit.

## Technical Design

### API (api/)

- **Migration (draft `00070` — renumber at landing per CLAUDE.md; live head `00051`, PRD #37 holds `00061`, PRD #39 holds `00065`)**: (a) the `run_user_inputs` kind CHECK is an unnamed inline constraint — Up: `ALTER TABLE run_user_inputs DROP CONSTRAINT IF EXISTS run_user_inputs_kind_check` then `ADD CONSTRAINT run_user_inputs_kind_check CHECK (kind IN ('follow_up','approve_plan','reject_plan','cancel','revise_plan'))`. Down restores the 4-kind CHECK and **fails once any `revise_plan` row exists** — accepted, stated (↳review S7). (b) `slack_run_messages.gate_generation int` (Decision 10a — the epoch carrier for the Slack anchor). No runs columns, no new tables.
- **`SubmitInput`**: accept `revise_plan` (plain-enqueue branch); revision-count guard per Decision 6 (new `CountRunReviseInputs` query, **no `consumed_at` filter**) returning a 4xx with a clear message when exhausted; existing `ErrRunTerminal` guard covers terminal runs. A revise on a run that is not at the gate is enqueued and consumed at the next gate entry — accepted, documented.
- **Handler**: `runInputKinds` map + error string extended (Decision 12). Note (↳review S6, defense-in-depth): `/api/runs/:id/inputs` rides only `RequireAuth` with no per-user rate limiter (`handler/handler.go:416-421`) — pre-existing for follow_up; the round cap is the real compute bound; a general inputs limiter is a recorded revisit, not this PRD.
- **Claim config**: `plan_max_revisions` added to the claim payload (`claim.go:141-143` pattern).
- **Slack** (`slacksvc/`): plan-in-thread posting bound to the fresh-gate-post branch, generation-keyed (scrub → whole-blob escape → rune-safe truncate → trusted deep link); third gate button + `revise-pending` anchor state (`gate_state` is text, no migration for it); replier `revise-pending` branch → CAS-accept then `SubmitInput("revise_plan")`; notifier re-post keyed on `gate_generation`; server-enforced supersede (gatekeeper refuses `MessageTS != anchor.GateTs`); generation-guarded anchor writes (ordering rule, Decision 10d); nudge string (Decision 10).
- No sweeper change (Decision 4), no lifecycle change, no claim-lane change.

### Worker (agent/)

- **`steering.ts`**: `PlanVerdict` gains `{kind: "revise", feedback: string}`; the epoch-tagged gate-event select (Decision 2/3): approve/reject keep latest-wins buffering but are epoch-stamped on arrival; `revise_plan` enters an epoch-stamped FIFO that **wakes the gate waiter**; `awaitGateEvent(epoch)` applies the precedence rule (current-epoch revise > buffered current-epoch approve/reject; prior-epoch anything discarded with feed notice; cancel epoch-exempt); epoch incremented by the gate at each `awaiting_approval` (re-)report.
- **`runner.ts` `gatePlan`**: absolute gate deadline hoisted across rounds (Decision 5a); returns revise verdicts to the executor; timeout-reject reason unchanged.
- **`sdk-executor.ts` phase 1**: fail-closed gate loop (Decision 3c) — on revise: emit `plan_feedback` + `plan_revising`, `driveTurn` with `buildRevisePlanPrompt` resuming `resumeId`, require a plan (`REASON_NO_PLAN` guard), flush `plan` message, re-report `awaiting_approval`, re-gate. Worker-side round counter (Decision 6). Resume-at-gate test (↳review D5): the existing resume path re-runs the planning turn on requeue (`sdk-executor.ts:300-304`) — a run lost mid-revision re-plans on resume, then consumes the pending revise; pinned by a test, and the pre-existing fragility (resume session must re-emit a plan signal or `REASON_NO_PLAN`) is named since revision makes long-parked runs more common.

## Out of Scope

- Free-form multi-turn chat with the planner at the gate (this is bounded request-changes rounds; a chat surface is PRD #39's territory).
- Slack content-minimization reversal beyond `plan_md` (run logs, diffs, feed content stay behind the deep link; Decision 10 reverses it for the plan only).
- A Slack bare-reply-as-feedback mode (feedback requires the Request-changes button first; casual thread replies keep the nudge).
- Plan diffing/rendering beyond the feed-derived history accordion (no structured plan format, no server-side diff).
- Revision on autopilot runs (Decision 8).
- Editing the plan text directly in the UI (the agent revises; the human steers).
- Resetting the total gate deadline per revision round (Decision 5a — one absolute deadline).
- A per-user rate limiter on `/api/runs/:id/inputs` (pre-existing gap, recorded revisit; the round cap bounds revision compute).

## Accepted residuals (named, per review)

- **Revise input lost if the worker dies after consuming it** — `ConsumeRunInputs` has no ack; the user re-sends. Parity with existing steering (↳review, security assurance 5).
- **A reject submitted mid-revision wastes the in-flight turn's spend** — it buffers until the next gate entry; bounded by the wall budget (↳review D10).
- **Feedback is stored verbatim (minus the run's own four secrets) and admin-visible** — parity with reject reasons and follow-ups (Decision 11).
- **Revision turns drain the run's single wall budget** — many slow revisions can starve implementation; the round cap is the practical bound (Decision 5b).
- **Resume-at-gate re-plans before applying a pending revise** — pre-existing resume behavior, amplified by longer parked times; pinned by test, not redesigned here (↳review D5). Corollary (↳review-r2): already-consumed revise rows still count against the cap after a requeue re-plan, so the resumed run may have fewer rounds left than its fresh plan suggests.
- **A discarded stale revise still burns a server-side cap slot** — the epoch discard (Decision 3) drops feedback authored against a superseded plan, but its persisted row counts toward `PLAN_MAX_REVISIONS` (spend-protection strictness favored; the feed notice invites a re-send).
- **The Slack layer adds no submission idempotency of its own beyond the revise-pending CAS** — the server-side cap counting persisted rows is load-bearing; it must never be "optimized" to count pending rows (↳review-r2 F5).
- **A revise-pending reply arriving after the gate resolved elsewhere becomes a follow_up** — identical to the existing reject-pending residual (`replier.go:148-183`); ownership-checked and bounded, documented so it isn't mistaken for a hole (↳review-r2 F6).
- **Plan content now leaves the box** — Slack's cloud (retention, admin export, e-discovery) holds plan bodies quoting source/issue content; non-pattern secrets a model quotes into a plan are not scrubbed by any layer. ## Success Criteria

- A user at the gate clicks Request changes, sends feedback, and gets an updated plan at the same gate — same run, same branch, planning context retained (the v2 plan visibly incorporates the feedback without re-deriving from scratch).
- **No plan version is ever implemented without a human having seen it**: an approve sent at ANY instant between feedback and the re-report is provably discarded (feed notice), and a click on a superseded Slack gate message is refused server-side — the guarantee never rests on a best-effort message edit.
- A full revision round works from Slack alone, without opening the web UI: the plan (and each revision) is readable in the run thread, and Request changes → threaded feedback drives the round.
- Reject still fails the run with the reason; approve still starts implementation; autopilot runs behave byte-for-byte as before.
- The 4th revision attempt is refused with a clear message in both the API response and the feed — including after a requeue (consumed rows still count).
- The total time a run may sit at the gate across all rounds is one 24h budget, not 24h per round.
- A worker lost mid-revision requeues under the existing affinity rules and the resumed run re-parks at the gate.
- Feed shows the full trail: plan v1 → feedback → revising → plan v2; `runs.plan_md` always equals the currently-gated plan.
