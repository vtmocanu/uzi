## Problem

A run's wall-clock budget is frozen when its plan is approved: for a milestone-structured issue run it is `RUN_TIMEOUT × min(milestones, 12)` capped at 8h (`milestoneBudgetCap`, `budgetWallCeilingSeconds`, `api/internal/workersvc/budget.go:9-17`), which on the maintainer's 6h cluster means every run with two or more milestones sits at the 8h cap; otherwise it is the global `RUN_TIMEOUT` (2h default). `SweepRunningTimeout` (`api/internal/store/queries/runtime.sql:2082-2136`) fails a `running` run the moment `started_at + COALESCE(budget_wall_seconds, RUN_TIMEOUT) + budget_paused_seconds` passes, with `fail_origin = 'run_timeout'`. Nothing lets the owner grant that run more time: the only levers are `RUN_TIMEOUT` (global, operator-only, a restart) and `run scope` / `run stop` (finalize what is committed). PRD #1170 adds a near-timeout warning at 85% of the budget and shows the time left, so the owner now learns the run will be killed and still cannot act on it from the page or the CLI.

Measured on the maintainer's cluster over 45 days (PRD #1170's window): one run was killed at 480/480 minutes, another reached 95% and then failed on an unrelated push. Rare, but each one loses the tail of an 8h run to a limit the owner would have lifted had they been asked. The run page also never shows the budget at all: `budget_wall_seconds` and `started_at` are on the run DTO (`api/internal/apitypes/run.go:153`, `:294`) and the web uses them only in mock fixtures.

## Solution

- **An additive extension, never a mutated budget.** New `runs.budget_extension_seconds int NOT NULL DEFAULT 0 CHECK (>= 0)`, added to the sweep's interval, to `RunDeadline`, to the health arm's effective timeout **and to the worker's own armed wall** (both at claim and on the running-report ACK, so a running run does not self-trip its worker wall before the extended server deadline; see D6). `budget_wall_seconds` stays immutable and capped at 8h exactly as the sweep's comment demands (`runtime.sql:2110-2115`): the ceiling bounds what the lead can buy itself; a human grants the extension.
- **An owner-only `extend` steering input**, audited in `run_user_inputs` like `scope`, with a body of whole seconds. Total extension per run is capped by a new admin setting `run_extension_cap_seconds` (default 16h; `0` disables extending). Allowed on any non-terminal run of a kind the sweep can time out, including a parked one; refused with 409 on `chat`, `judge` and interactive tasks, which never time out.
- **Web**: on every run that can time out, the header's live elapsed text gains the budget, `3h 48m / 8h` (focusable, tooltip names the deadline). While PRD #1170's near-timeout flag is up, an **Extend time…** button appears in the header (the way Expedite appears only on a queued run) and a near-timeout panel modelled on the limit-wait panel explains what will happen. Extend always opens a chooser (+1h / +2h / +4h / +8h / custom, +2h preselected) that shows used, allowance left and the resulting deadline; it never adds time on the first click.
- **CLI**: `uzi run extend <id> --by 2h`; `uzi run get` shows the extension in its `DEADLINE` row.
- **Slack**: #1170's near-timeout DM gains the viewer-local deadline, time left, the age of the last checkpoint and the exact CLI command; the command is omitted when the cap is exhausted.
- **TUI**: unchanged beyond #1170 (read-only; no extend from the TUI, owner decision 2026-09-07).

### Store

Additive only. Heads-up: none of the 115 existing `ADD COLUMN` migrations uses `IF NOT EXISTS`; it is plain Postgres and goose runs raw SQL, so it works, but check the migration applies twice cleanly on a scratch database (`goose up`, `goose down`, `goose up`) as part of M1.
- `ConsumeRunInputs` (`runtime.sql:2780`, `… AND p.kind <> 'scope'`) becomes `p.kind NOT IN ('scope', 'extend')`. The exclusion exists because a server-only directive drained by the worker hits `SteeringChannel.route`'s default arm and logs `steering: ignoring unknown input kind` (`agent/src/steering.ts:544-545`); `extend` is server-only exactly like `scope` (D6). Update the comment at `:2777-2779` to name both.
- `SweepRunningTimeout`: the interval becomes `COALESCE(budget_wall_seconds, @global_timeout_seconds) + budget_paused_seconds + budget_extension_seconds`. Nothing else in the statement moves; the comment gains one paragraph naming this PRD and restating that the ceiling still lives at the freeze writers.
- `SetRunCheckpointTip` (`:2924-2928`) also sets `checkpoint_tip_at = now()`; still no `updated_at` bump, for the reason its comment gives.
- New `CreateExtendInput :one` CTE, modelled on `CreateScopeCeilingInput`: `UPDATE runs SET budget_extension_seconds = budget_extension_seconds + @secs, updated_at = now() WHERE id = @id AND status NOT IN ('completed','failed','cancelled') AND kind NOT IN ('chat','judge') AND interactive = false AND budget_extension_seconds + @secs <= @cap RETURNING budget_extension_seconds`, then `INSERT INTO run_user_inputs (run_id, kind, body, disposition) SELECT @id, 'extend', @body, 'applied' …` from the CTE. `disposition = 'applied'` at insert (the CHECK from `00162_run_scope_steering.sql:16-22` admits it) because an extension takes effect in the same statement; a NULL would leave the row "pending" in `uzi run inputs` forever, since nothing settles it the way `SettleScopeInputDisposition` settles a scope row. Zero rows means one of the guards failed; Go distinguishes cap (`ErrExtensionCapExceeded`, 409 with the remaining allowance in the message) from untimed kind (`ErrExtendNotTimed`, 409) from terminal (`ErrRunTerminal`, already 409) by reading the run row it already fetched. That read is the same TOCTOU `scope` accepts: a run that goes terminal between `GetRun` and the CTE is reported as the guard the stale row suggests; harmless (the run is dead either way) and noted here so nobody adds a second query to close it.
- `ListActiveRunsForHealth` gains `budget_extension_seconds`. `GetSlackRunContext` gains whatever `RunDeadline` needs plus `checkpoint_tip_at` and `budget_extension_seconds`.

### The clock

`RunDeadline` adds `budget_extension_seconds` to its sum; `runningTarget`'s `effTimeout` becomes `COALESCE(budget_wall_seconds, RunTimeout) + budget_extension_seconds` so the 85% test moves with the extension and the flag clears on the next sweep tick (the detector re-evaluates every pass and writes `ok` when the arm no longer fires). No other health change; a run that later crosses 85% of the extended budget is flagged and nudged again, which is the D8 behaviour #1170 accepted.

### The input

- `runInputKinds` gains `"extend"`; the CHECK gains `'extend'`.
- `SubmitInput` branch, after the existing guards and before the `stop` branch: body is a base-10 integer of seconds, `>= 60`, else `ErrInvalidExtension` (400). Cap from `settings.RunExtensionCapSeconds(ctx)`; `0` means extending is disabled (`ErrExtendDisabled`, 409, message says the admin has turned extensions off). Audit body: `extend +2h → total extension 2h of 16h; times out 17:20 UTC`, computed **before** the CTE from the fetched row (projected total = the row's `budget_extension_seconds` + `@secs`; projected deadline = `RunDeadline` over the fetched row with the projected total), so the write stays one statement and needs no read-back. UTC in the audit row; the UI localizes. `SubmitInputResult` gains `ExtensionSeconds *int` (the new total) and `DeadlineAt *time.Time` so the CLI can print the outcome without a read-back.
- **The worker is served the extension** (see D6, and *The worker's wall* below): the sweep and the health arm read the column, and so does the worker's armed wall. Leaving the worker uninformed makes the extend a silent no-op for any run whose armed wall equals its frozen budget (`mr_rework`, and every run once extended past its frozen budget), because the worker trips `REASON_WALL` (`agent/src/sdk-executor.ts:128`) at the old time before the server sweep fires. So the served wall must carry `budget_extension_seconds`.

### The worker's wall

The worker arms a hard wall at claim from `RunTimeoutSeconds = COALESCE(budget_wall_seconds, RUN_TIMEOUT)` (`api/internal/workersvc/claim_assembly.go:436`) and trips `REASON_WALL` (`agent/src/sdk-executor.ts:128`) as a hard failure, independent of the server sweep. So a server-columns-only extend never reaches the run that is actually about to die. The worker-serve, folded in from the accepted field finding:

- **Claim assembly** adds `budget_extension_seconds` to the served `RunTimeoutSeconds`, so a run extended while `queued`/parked arms the already-larger wall when it starts.
- **Running-report ACK** carries the current extension the way `wallSeconds` is served today, so a mid-run extend lifts the wall of a run already executing. The worker treats a larger served wall as authoritative.
- **Re-lift past the first scale.** The one-shot `wallScaled` latch (`sdk-executor.ts:1848`, `&& !wallScaled`) and per-turn arming today allow exactly one upward move; a served bump must re-arm the in-turn wall each time it grows, so a second extension is not swallowed by the latch. Only upward moves are honored (an extension only ever adds); the worker never shortens its own wall from a served value.
- **Provider-neutral.** The served value is a scalar wall in seconds through the existing harness boundary; no provider SDK type crosses into Go transport (mirrors #1214's constraint).

This is the D6 reversal: the worker *is* told, because not telling it ships a no-op that is worse than shipping nothing. M1's acceptance test proves a running run survives past its original wall on a served extension, on both an `mr_rework` run (armed wall == frozen budget, the reproduced case) and a milestone-scaled issue run (which has `wallScaled` headroom and must still honor a second bump).

### The setting

`KeyRunExtensionCapSeconds = "run_extension_cap_seconds"`, `DefaultRunExtensionCapSeconds = "57600"`, in `Defaults`; accessor `RunExtensionCapSeconds(ctx) (int, error)`; validator `validateExtensionCapSeconds`: `0` (disabled) or `[3600, 604800]` (1h to 7d), error text `must be 0 (disabled) or between 3600 and 604800 seconds`. Admin card: a field in the Run health card under the near-timeout percent, label `Extension allowance per run (seconds)`, hint `Total extra wall-clock time an owner may grant a run through Extend; 57600 = 16h. 0 turns extending off.`, with its own client-side validator (the seconds fields keep theirs, the percent field keeps #1170's).

### DTO

`RunDTO` (and so `RunListItemDTO`) gains `budget_extension_seconds int`, `budget_extension_cap_seconds int` (the effective admin cap, so the chooser and the CLI need no second request), `budget_total_seconds *int` (`COALESCE(budget_wall_seconds, RUN_TIMEOUT) + budget_extension_seconds`, nil for kinds that never time out), `budget_used_seconds *int` (**active** time so far: `now - started_at - budget_paused_seconds`, clamped at 0, nil when `started_at` is null; valid in every status, so a paused run reports a frozen figure) and `checkpoint_tip_at *time.Time`. One clock: the header's "used", the chooser's facts and #1170's `deadline_at` are all paused-aware and agree; the raw wall elapsed at `RunView.tsx:106` is **not** what `/ 8h` is measured against, because on a run that sat 32m at its plan gate raw elapsed would disagree with the deadline in the same header. `latestRunDTO` gains none of these: the board card shows the badge only, and the badge's countdown comes from #1170's `deadline_at`.

### Web

## Decision log

- **D1: an additive column, the frozen budget stays immutable.** The sweep trusts `budget_wall_seconds` as an already-capped server-only value and says the cap must stay at every writer; the 8h ceiling exists so a lead cannot buy itself budget through milestone count. A human-granted extension is a different trust and gets its own column, so neither invariant moves. Rejected: `UPDATE runs SET budget_wall_seconds = …` from the handler.
- **D2: a steering input, not a PATCH endpoint.** `scope` shows the shape: one CTE writes the control and the audit row, the owner and terminal guards are `SubmitInput`'s, and the CLI reuses `submitInput`. The audit row is the point: an extension changes when a run dies, and `uzi run inputs` should show who granted it and when. Rejected: `PATCH /runs/{id}/budget` like priority (no audit trail).
- **D3: the cap is a per-run total from an admin setting, `0` disables.** A per-extension cap is bypassed by repeating; a hard-coded cap would need a release to change. 16h default: two full ceilings, generous for a human decision and still finite. Bounds `[1h, 7d]` because a cap under an hour is noise and over a week is no cap.
- **D4: extend is allowed on any non-terminal, timed run, including a parked one.** The column is additive and inert until the run is `running`; refusing it on a gated run would make an owner wait for the run to resume before granting time it may need immediately. Kinds the sweep never times out (`chat`, `judge`, interactive tasks) are refused with 409 rather than silently accepted, so a script cannot believe it did something.
- **D5: Extend always opens the chooser; there is no one-click add.** From the 2026-09-07 UX review of the mock: a state-changing action with a hidden magnitude is the wrong default; the chooser preselects +2h so the common case is still two clicks.
- **D6 (revised 2026-09-10): the worker is served the extension.** The original decision ("the worker is not told; its wall is an advisory soft self-check looser than the sweep") was **falsified by the field finding below**: the worker arms a *hard* wall at claim from `COALESCE(budget_wall_seconds, RUN_TIMEOUT)` (`claim_assembly.go:436`) and trips `REASON_WALL` at that time regardless of the server sweep, so for any run whose armed wall equals its frozen budget the server-columns-only extend is a silent no-op (deadline moves, flag clears, run still dies) — worse than shipping nothing. The worker-serve therefore moves from follow-up into M1: `budget_extension_seconds` is added to the served wall at claim assembly and on the running-report ACK, and `sdk-executor.ts` honors an upward-only served bump and re-arms past the one-shot `wallScaled` latch. The "second clock" objection is answered by keeping the server authoritative (the sweep still owns the kill) and the worker's wall strictly `>=` the server deadline: an upward-only served value can never make the worker trip *before* the server, only avoid tripping earlier. Provider-neutral: a scalar wall in seconds, no SDK type in Go transport. See *The worker's wall*.
- **D7: healthy runs show text, not controls.** Mirrors the #1170 TUI decision and the Expedite precedent: the header carries state, and grows an action only when the state calls for one. The 85% flag fired on 2 runs in 45 days; a permanent button is clutter.
- **D8: server-computed `budget_total_seconds` and `budget_extension_cap_seconds` on the DTO.** Clients never add `RUN_TIMEOUT` (which they do not know) to anything, and the chooser needs the cap without an admin-only settings call.
- **D9: Slack uses `<!date^…>`.** Viewer-local time with no stored time zone; the fallback is UTC. The command is omitted at cap so the DM never tells someone to run a command that will 409.
- **D10: `checkpoint_tip_at` lands here with `IF NOT EXISTS`.** #1190 needs it too; whichever merges second is a no-op. The panel and the DM both need "how old is the last checkpoint", which the tip SHA alone cannot answer.
- **D11: no TUI change.** Read-only surface; #1170 already shows the countdown there. Owner decision 2026-09-07.

## Field finding (2026-09-09; ACCEPTED 2026-09-10 — folded into D6, *The worker's wall* and M1)

This began as a provisional observation and is now an accepted design input: the mechanism is confirmed from the code (the worker's armed wall reads only `budget_wall_seconds`), so the worker-serve is in M1. The one thing M1 still re-derives is the exact numeric reproduction, since the original observation used a proxy (a `budget_wall_seconds` DB edit, not the shipped `budget_extension_seconds` column).

- **Observation.** A running `mr_rework` run had its server budget extended by editing `budget_wall_seconds` in the DB (6h to 9h). `deadline_at` and the near-timeout flag both moved (API-confirmed), yet the run still failed at the original 6h mark with `fail_origin=agent_failure`, `failure_reason="run exceeded its wall-clock timeout"`: the worker's own `REASON_WALL` (`agent/src/sdk-executor.ts:128`), not the server sweep (which stamps `fail_origin=run_timeout`).
- **Why it contradicts the original D6 and the "A worker's soft wall" risk.** The worker arms its wall at claim from `RunTimeoutSeconds = COALESCE(budget_wall_seconds, RUN_TIMEOUT)` (`api/internal/workersvc/claim_assembly.go:436`) and trips it as a hard failure. For any run whose armed wall equals the frozen budget (`mr_rework`, and every run once extended past its frozen budget), the worker trips before the extended server deadline. A server-columns-only extend is then a silent no-op: the deadline moves and the flag clears while the run still dies at the old time, which is worse than shipping nothing. The one-shot `wallScaled` latch (`sdk-executor.ts:1848`, `&& !wallScaled`) and per-turn arming also block a naive "serve it on the ACK" from lifting the wall a second time.
- **Accepted scope.** The worker-serve is in M1 (see *The worker's wall* and D6): feed `budget_extension_seconds` into the served wall (claim assembly plus the running-report ACK), re-lift the wall past the first scale, re-arm the in-turn wall on a served bump, and prove a running run survives past its original wall.
- **What M1 still re-derives.** The original observation edited `budget_wall_seconds`, not the shipped `budget_extension_seconds`; the run was `mr_rework` (never milestone-scaled, so no `wallScaled` headroom); `RUN_TIMEOUT` on that cluster was 6h, not the 2h this PRD's prose assumes. M1's acceptance test reproduces against the real column on both an `mr_rework` run and a milestone-scaled issue run.

## Success criteria

- A running issue run with an 8h budget extended by 2h is failed by the sweep only after 10h active; `deadline_at`, the header, `uzi run get` and the Slack DM all name the same new deadline.
- The extended run **does not self-trip its worker wall** at the original budget: the worker is served the extension and survives past its original wall, proven on both an `mr_rework` run (armed wall == frozen budget) and a milestone-scaled issue run; a second extension re-lifts the wall past the `wallScaled` latch.
- Extending clears the near-timeout flag on the next sweep tick and the run page loses the chip and the panel; a later crossing of 85% of the extended budget re-flags it.
- The cap is enforced server-side (409 with the remaining allowance), reflected in the chooser (confirm disabled) and the CLI (message printed verbatim); `0` turns the feature off everywhere at once.
- A healthy run's header differs from today only by the ` / 8h` text; a chat run's header is unchanged.
- `task gate` green; one additive migration; no workflow file in the diff.

## Risks

- **Rollout skew.** A new SPA against an api pod without the four DTO fields sees `undefined`: the header falls back to plain elapsed and the button does not render (`budget_extension_cap_seconds` undefined is treated as "unknown", not `0`). Keep every new web field optional; the M2 tests pin the fallback.
- **Two drafts numbered 00203.** #1190 drafts `00204`; at landing renumber to the live head. `check:migration-numbering` in `gate:repo` catches a duplicate prefix.
- **`sqlc generate` needs the module proxy** (see #1170's Risks for the hand-edit fallback shape).
- **The worker's hard wall (now served, not a residual risk).** The worker arms a *hard* wall at claim and trips `REASON_WALL` independent of the sweep, so an unserved extension is a no-op for the very run about to die (the 2026-09-09 field finding). M1 serves `budget_extension_seconds` into the claim wall and the running-report ACK and re-arms past the `wallScaled` latch; the residual risk is only that the re-arm misses a second bump, which the agent survival test pins. The server stays authoritative (the sweep owns the kill; the served wall is upward-only and always `>=` the server deadline).
- **Health nudge repeat.** After an extension the run may re-cross 85% and DM again; accepted per #1170 D8.

## Out of scope

- Pausing and resuming a run (PRD #1190), the `paused` status, and the TUI vocabulary for it.
- Any TUI change; any change to `RUN_TIMEOUT`, the freeze or the 8h ceiling.
- Auto-extension policies (an autopilot run extends itself). The point of the ceiling is that only a human grants time.
- A per-user or per-repo cap; the cap is instance-wide.
