## Problem

Three UX rough edges flagged from the live UI (`uzi.example.com`):

1. **Sidebar collapse chevron eats a full row.** The desktop collapse toggle (`web/src/components/AppShell.tsx`) rendered as its own full-width footer row above the vault/user block, spending a whole row on a `<` chevron.
2. **"Last fire" disclosure caret renders broken.** On the Schedules page (`web/src/pages/Schedules.tsx`, PRD #308 M4), the caret next to the underlined "Last fire" link looked broken — thin, stray lines, worse in the open/ascending state.
3. **The `/runs` past-runs list is thin.** No search, no date grouping, no progressive loading — a flat list gated behind a "Show past runs" click, which does not scale as history grows.

## Solution

1. Fold the collapse toggle into the footer user cluster (last element of the expanded row and the collapsed rail column, past a hairline divider), keeping persistence, `aria-expanded`, keyboard access, and both expanded + collapsed-rail states.
2. Replace the `▾` **font glyph** (baseline-drift artifact; the rotated-open state renders as stray lines) with the viewBox-centred SVG `ChevronDownIcon` (`rotate-180` for open, `motion-reduce:transition-none`). Correct the affordance: an in-place disclosure must not wear the app's blue-underlined-link costume, which promises navigation — restyled to muted text + chevron.
3. Give past runs the board's experience: search (title/repo/#iid/worker/status), date grouping (days this week → "Week of Aug 3" → "July 2026"), and board-style progressive reveal (`lanePaging` reused verbatim: cap 10, page 50, "Show 50 more · N left"). Reorder the page live-to-archival: **Active (yours) → Factory status (admin) → Past runs (archive)**. Seed the mock with ~150 deterministic terminal history runs so grouping/paging are demonstrable.

**Seam for the coder (backend, deferred, not needed at current volumes):** all filtering/grouping/paging is client-side over what `listRuns` returns. If the API grows server paging, the seam is `GET /api/runs?query=&after=<cursor>` returning page + total; `lanePaging`/`groupRuns` are pure over whatever list arrives, so only `RunsList.load()` changes.

- **2026-08-14 — Built by an agent-team `ux-designer` (fable), interactively.** The three items were the user's suggestions; the designer was mandated to push back where it disagreed. - **2026-08-14 — M5 accepted (Factory hides own runs), with a premise correction.** The designer agreed and, verifying in code, corrected the amendment's premise: `RunListItem` has no `is_mine` (that field is on `LatestRun`); the filter keys on `owner_email` with a keep-visible fallback for rows lacking it. It also found and fixed a mock defect (every admin-list row stamped with the session admin's email) that had inflated the on-screen duplication.
- **2026-08-14 — M6 accepted (routed tabs, not a new sidebar destination).** The designer pushed back on a separate sidebar entry and recommended in-page tabs under one "Runs" route; the user approved. On the count-flicker nit, the designer corrected the lead's proposed fix: hoisting the fetch into `RunsShell` would not have helped because `RunsShell` rendered inside each tab page and remounted with it — the persistent thing had to be a React Router layout route (`RunsLayout`).
