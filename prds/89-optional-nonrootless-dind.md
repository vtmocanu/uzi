## Problem

PRD #83 shipped the docker-capable worker tier as a **rootless** Docker-in-Docker sidecar (`docker:*-dind-rootless`, runs the daemon as an unprivileged uid inside a privileged, NetworkPolicy-fenced namespace). Rootless dockerd requires **unprivileged user namespaces** enabled on the node kernel (`kernel.unprivileged_userns_clone=1`).

On the live dev-cluster enablement (2026-07-19) that prerequisite was not met: the nodes are **vendor Linux OS, kernel 6.1.83**, which ships with unprivileged userns **disabled** (a hardening default). The rootless dind sidecar crash-loops at startup:

```
error: attempting to run rootless dockerd but need
'kernel.unprivileged_userns_clone' (/proc/sys/kernel/unprivileged_userns_clone) set to 1
```

Everything else was correct — the Deployment, both PVCs bound, scheduling, and the pod **passed privileged admission** — but the daemon cannot run rootless on these nodes. `kernel.unprivileged_userns_clone` is a **node-scoped** sysctl (not settable per-pod), so there is no in-chart way to satisfy rootless here without a node-level change to the shared cluster (which re-opens the userns attack surface Linux deliberately hardens off).

PRD #83's k8s definition of done — "a docker-capable hosted worker on dev-cluster runs `./e2e/run-e2e.sh` green" — is therefore unreachable on this cluster with the rootless-only design. #83 flagged the node prerequisite as unverified; it turned out to be a hard blocker.

## Solution

Make the DinD posture a **per-cluster toggle**, defaulting to the safer rootless design, with a non-rootless privileged fallback for clusters whose nodes cannot do rootless:

- **`workers.docker.rootless: true`** (chart default) — unchanged PRD #83 behavior. Clusters whose nodes support unprivileged userns keep the stronger posture.
- **`workers.docker.rootless: false`** — the controller renders a **non-rootless** privileged DinD sidecar: `dockerd` as root (uid 0) inside the already-privileged, already-fenced `uzi-workers-docker` namespace, listening on a **pod-local loopback TCP** endpoint the non-root worker reaches (`DOCKER_HOST=tcp://127.0.0.1:2375`). dev-cluster sets this `false`.

The toggle lives in values but selects **controller-rendered** behavior (the dind sidecar is emitted by `controller/internal/kube/render.go`, not Helm), so the chart plumbs it to a controller env var and the render branches on it. The matching dind image (`docker:*-dind-rootless` vs `docker:*-dind`) is selected alongside.

Nothing about the default changes: on every other cluster uzi keeps rootless. This is a scoped, opt-in relaxation for a node constraint, recorded as an owner override of #83's rootless-only stance (Decision Log).

| Node prerequisite | host has docker | none (works on Linux) | unprivileged userns (**absent on dev-cluster**) | none (works on Linux) |

Readings:
- **multica** proves the cheap path and its price: docker "for free" by deleting the sandbox. Copying it would gut uzi's trust boundary. Strictly worse; not a k8s pattern at all.
- **coder** is the only prior art with uzi's actual shape (an isolated workspace that needs docker on this cluster), and it runs **exactly the non-rootless privileged dind** we're proposing — it never attempts rootless in k8s. That establishes **posture parity**: the container posture is the accepted, working standard on dev-cluster's infra, not a uzi invention. It also hands us the clean client transport: **pod-local loopback TCP `127.0.0.1:2375`**. **But posture parity is not threat-model parity** — coder's docker is driven by a trusted human, uzi's by a prompt-injectable agent on hostile-capable repo content; see Security framing for why that matters and how the provisioning allowlist narrows the gap.
- **Ours stays stricter than coder** even in non-rootless mode: coder has no NetworkPolicy fence and no dedicated blast-radius namespace; we keep #83's dedicated `uzi-workers-docker` namespace, its NetworkPolicy fence (in-cluster lateral egress + all ingress denied), and the worker/runner uid split — and we default to rootless where the node allows it, which coder never does.

## Security framing

Reviewed by an architect (design fit) and an auditor (security), 2026-07-19. Both agreed the mandatory hygiene below; the auditor raised a Critical the first draft understated. This section is the corrected, owner-accepted framing.

Non-rootless dind runs the daemon as **real root with no user namespace**. On dev-cluster the rootless tier is ALSO `privileged: true` (PRD #83 Decision 2 — the userns remap, not the flag, was its security property), so the delta between the two postures is narrow but sharp: rootlesskit interposes a userns *inside* the privileged sidecar, so a nested-container escape lands as a **mapped, unprivileged uid**; non-rootless has no userns, so the same escape lands as **real node root**.

**The residual non-rootless introduces is NODE ROOT, and it is the owner's accepted risk — stated plainly, not glossed:**

- **Mechanism.** The agent runs semi-hostile repo/issue code (prompt-injectable, under bypassPermissions) and, by design, reaches the root daemon at `tcp://127.0.0.1:2375` (it needs docker for the repo's tests). A hijacked agent can `docker run --privileged`, and because the sidecar is privileged with host `/dev` and no userns, obtain node root.
- **What does NOT bound it** (correcting the first draft, which claimed "bounded by the same fence + dedicated-namespace blast radius"): the NetworkPolicy fences the *pod* netns — node root is in the *node* netns, so the fence is bypassed. The dedicated namespace bounds the *k8s RBAC* radius — node root reads the node filesystem directly, below the k8s API. The #51 uid split is *filesystem* containment — daemon access is *network* (shared pod netns), so it gives zero protection here. **None of #83's load-bearing defenses bound node root.** (The mount-ns of #83 Decision 3 IS structurally preserved — the sidecar mounts only socket/data, not the worker's secret volume — but it is no longer the binding constraint: node root reaches the same secrets via the node filesystem, a path Decision 3 never covered.)
- **Blast radius.** dev-cluster has a single worker nodepool and no node pinning (verified in `render.go` + the chart, and `kubectl get nodes`), so docker-worker pods co-schedule with the api pod and CNPG. Node root reads every co-scheduled pod's secrets from `/var/lib/kubelet`, including the api pod's **`UZI_SECRET_KEY`** — the master key that decrypts EVERY user's forge PAT + Anthropic token — plus CNPG creds and the node identity. This is a strictly larger compromise than the join-token theft #83 Decision 3 was built to stop.
- **NOT covered by PRD #50.** #50 (egress proxy) addresses external exfil; it does nothing about a node-filesystem read of co-scheduled secrets or node-identity lateral movement. Node root is THIS PRD's own residual, distinct from #50's egress residual.

**Why accepting it is defensible here — and exactly where the coder analogy holds and breaks.** Coder (`myorg/k8s/coder`) runs the identical non-rootless privileged `docker:*-dind` on these same nodes, so the *container posture* is the cluster norm, not a uzi invention. But coder's docker is driven by a **trusted human at a keyboard**; uzi's is driven by an **autonomous, prompt-injectable agent** on third-party repo content — so the same posture is triggerable by hostile *repo content*, not just a trusted person. The mitigations below narrow that gap **materially, but not to zero** (fable review, 2026-07-19): an autonomous agent never becomes a trusted human, and injection also rides issue/MR bodies, dependency postinstall scripts, and pulled images even on a *trusted, allowlisted* repo. And the DoD itself pulls upstream images (postgres/golang/node/nginx) from Docker Hub and runs them under a root privileged daemon, so a compromised upstream image is node root with **no prompt injection at all**. "Same as coder" is an honest *posture* claim; it is not an honest *threat-model* claim, even with the allowlist. The acceptance stands on the private-factory bet + the mitigations, not on coder-equivalence.

**Mitigations (this PRD's scope), none requiring a node change:**
1. **Loopback-bind, mandatory (M1).** dockerd binds `tcp://127.0.0.1:2375` explicitly, suppressing `docker:dind`'s automatic `0.0.0.0:2375` listener, so the unauthenticated root daemon is never on the pod IP. The render-invariant test asserts the **POSITIVE** — the dind Command is present and its only `--host` value is `tcp://127.0.0.1:2375` (0.8.1 correction: TCP loopback ONLY, no unix socket — see M0 addendum) — NOT "no `0.0.0.0` string", which is defeatable: dropping the command override entirely passes a negative test while the image entrypoint restores the `0.0.0.0:2375` listener (fable review). (The NetworkPolicy `ingress:[]` is only the backstop; this is the primary control.)
2. **Repo allowlist at CLAIM/DISPATCH (M-allow).** The trigger is repo content, so the gate must bind where a docker worker picks up work, not only where it is provisioned. A provision-time *user* allowlist is insufficient: the `ClaimRun` query (`api/internal/store/queries/runtime.sql:221`) claims ANY of the worker's user's queued non-chat runs with **no repo predicate**, so one docker worker sets `DOCKER_HOST` for every repo that user has. The load-bearing control is a claim/dispatch predicate — a docker worker only claims runs whose repo is on the allowlist (fable review; verified in the query). Repo-less runs (judge; the ungated chat lane) are exempt from this predicate — **not** because "no repo checkout" means no content can reach the daemon (a judge still reasons over an untrusted, prompt-injectable trace), but because those runs' EXECUTORS carry no daemon-reaching tool: `agent/src/judge-runner.ts` wires a deny-ALL `PreToolUse` hook, and `agent/src/chat-executor.ts` grants only `Read`/`Grep`/`Glob` + the read-only uzi MCP, so `DOCKER_HOST` is inert for either even if set (auditor Medium, pinned by an agent/ regression test).
3. **Soft anti-affinity (cheap, no node change).** Preferred pod anti-affinity keeps the api pod (holding `UZI_SECRET_KEY`) and CNPG off docker-worker nodes. With kubelet NodeRestriction, node root reads only the secrets of pods bound to THAT node, so keeping the crown-jewel pods off docker-worker nodes directly shrinks the worst outcome. Best-effort (soft), and dev-cluster's 4 worker nodes give it real room. Not a full fix, but a few lines that attack the headline consequence.
4. **Explicit acknowledgement (M2).** `workers.docker.rootless: false` refuses to render without `workers.docker.acknowledgeNonRootlessNodeRoot: true`, mirroring the `networkPolicy.acknowledgeUnfenced` idiom, so the node-root acceptance is a loud, visible operator choice (the auditor's recommendation; overrides #83's "drop operator ceremony" default because this residual is reachable by untrusted repo content).
5. **Reduced-cap was tested live and does NOT work on these nodes (see Decision Log 2026-07-19).** Dropping `--privileged` for a curated cap set runs dockerd but cannot create containers on cgroup v2 (`mkdir /sys/fs/cgroup/docker: read-only file system`); a writable cgroup needs privileged or host cgroup access (a node change, excluded). So full `--privileged` is required on dev-cluster, and the node-root residual cannot be closed at the pod level here — hence the explicit owner acceptance above.

## Bind-mount blocker + the shared workdir (Decision-3 amendment)

The fable review (2026-07-19) surfaced a structural blocker neither opus review caught, and it is **bigger than the DoD**: under #83 Decision 3 the dind daemon mounts none of the worker's filesystem, so **any** `docker run -v <path>` / compose bind-mount resolves the source in the *daemon's* fs and gets an **empty dir**. That breaks uzi's own e2e (`e2e/docker-compose.e2e.yml` bind-mounts `${E2E_RUN_DIR}/{certs,fakeremote,forge-fake-state,agent-gitconfig,…}` — verified) AND a large fraction of real repos whose docker setups bind-mount their source. It bites rootless and non-rootless equally; it was simply never hit because #83's k8s DoD never ran (rootless crash-looped). So docker workers are not actually usable for bind-mounting repos today, on any posture.

**Fix (owner-approved 2026-07-19): a bounded shared scratch workdir — a narrow Decision-3 amendment.** An `emptyDir` mounted into BOTH the worker and the dind sidecar at the **same path**, carrying the run's workdir / repo checkout, and **NO secrets** (the join token, PAT, and per-run secret volume stay in their own mounts, unshared — so Decision 3's crown-jewel property is preserved). This is coder's "mount home into dind" pattern minus "home == everything": we share only the no-secrets workdir. Compose/`docker run -v` bind sources under that workdir then resolve correctly in the daemon. This unblocks docker workers on rootless clusters too, so it is recorded as a general Decision-3 amendment, not a non-rootless-only hack. Kept IN this PRD (M-workdir) because #89 is the PRD driving docker-workers-to-done and its DoD depends on it; spec-keeper records the amendment in `specs/ai.md`.

## Validate-first (before any implementation)

Per the owner's direction, the non-rootless posture is proven live on the target cluster BEFORE controller code is written:

- **M0 (this PRD's gate):** apply a hand-written pod to `uzi-workers-docker` on dev-cluster mirroring the non-rootless design — a privileged `docker:28-dind` sidecar (root) + a **non-root (uid 10001, like the worker)** client that reaches the daemon over `tcp://127.0.0.1:2375` and runs a container. Success = dockerd starts on the Linux node (where rootless could not) AND the non-root client drives it. Only then do M1+ proceed.

## Decision Log

- **2026-07-19 — Non-rootless is opt-in per cluster, default rootless.** The rootless posture (PRD #83) stays the default and the recommended stance; non-rootless is a documented escape hatch for nodes without unprivileged userns (dev-cluster / Linux). This preserves #83's security intent everywhere it can be met and confines the relaxation to clusters that provably cannot do rootless.
- **2026-07-19 — Client transport is pod-local loopback TCP (`127.0.0.1:2375`), matching coder.** Avoids the root-owned-unix-socket-vs-non-root-worker permission problem; the endpoint is on loopback only (not the pod IP), so the trust boundary is identical to a shared unix socket (same-pod containers only).
- **2026-07-19 — Validate before implementing.** Prove the non-rootless daemon runs on the real Linux nodes and a non-root client drives it, in `uzi-workers-docker`, before writing render code (M0 gate — PASSED). Rationale: #83's rootless design was written against an unverified node assumption that turned out false in production; do not repeat that with the fallback.
- **2026-07-19 — Reduced-cap non-rootless was tested live and REJECTED for dev-cluster.** To try to close the node-root vector without touching nodes, a prototype ran non-rootless dind with `privileged:false` + a curated cap set (SYS_ADMIN, NET_ADMIN, MKNOD, … seccomp Unconfined) and no host devices. Result: dockerd started (overlay2 + networking fine) but **could not create containers** — `mkdir /sys/fs/cgroup/docker: read-only file system`. On cgroup v2, k8s mounts `/sys/fs/cgroup` read-only for non-privileged containers; a writable cgroup needs `privileged:true` (which re-grants all host devices) or a host cgroup bind-mount (a node change). No capability fixes it. **Conclusion: full `--privileged` is required on these nodes; the node-root residual cannot be closed at the pod level here.**
- **2026-07-19 — Owner accepts the node-root residual, on stated terms.** Given (a) no node changes and (b) docker is wanted, non-rootless full-privileged is the only working path, and node root is inherent to it on shared nodes. The owner accepts it as a private-factory risk, conditioned on the mitigations: loopback-bind (M1), provisioning allowlist to trusted repos (M-allow), the `acknowledgeNonRootlessNodeRoot` flag (M2), and honest docs.
