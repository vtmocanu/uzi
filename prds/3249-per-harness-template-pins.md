## Problem

An admin or user who works with both harnesses cannot say "this subagent runs on `sonnet` for Claude runs and on `gpt-6-sol` for Codex runs". An agent template has one `model` field, and the editor only offers Claude models:

- A Claude alias pin (every builtin ships one) does nothing on a Codex run. It is dropped with an `unknown_model` diagnostic, and the subagent falls back to the run's model.
- A Codex model pin (possible through the API, or a repo `.claude/agents/*.md` file) is passed unchanged to the Claude SDK on a Claude run, where it can fail at provider execution.
- The lead template's model is the Claude root fallback. On Codex runs it is ignored entirely, so there is no template-level Codex default for the root.

Repo-authored agents have the same single-field problem. The Agents page, the editor and the agent-source approval card cannot show or set a Codex choice.

## Outcome

Every agent template has a **Claude pin** (the existing `model` field) and a **Codex pin** (new `codex_model`). A run uses only the pin for its own harness. An empty pin follows the lead (the root model the run resolved); on the lead template an empty pin means the built-in. Each pin rejects the other family's vocabulary at save, and the claim filters the family again, so a pin never reaches the wrong provider even for rows written outside the API. The schedule toggle "Apply model also to agents" still overrides both. Builtins keep their upstream `model:` as the Claude pin and keep tracking upstream prompt changes while pristine. Single-`model:` sources (repo `.claude/agents/*.md`, agent-source sync) map by vocabulary; `.codex/agents/*.toml` agents have no pin. One lead-template rule governs every executor and reader.

Acceptance examples:

1. **Both pins.** `researcher` has Claude pin `sonnet` and Codex pin `gpt-6-sol`. A Codex run that delegates to `researcher` sends `gpt-6-sol` in that child turn's model. A Claude run's `researcher` `AgentDefinition.model` is `sonnet`. Neither run records an `unknown_model` diagnostic for `researcher`.
2. **Migrated leak.** Before upgrade a template stores `model = 'gpt-6-sol'`. After the migration `model` is NULL and `codex_model = 'gpt-6-sol'`. On a Claude run that subagent's definition has no `model` key (it follows the lead). On a Codex run it still runs on `gpt-6-sol`.
3. **Save-time rejection and keep.** `PUT /api/agent-templates/{id}` with `"model": "gpt-6-sol"` answers 400 naming `model`. `"codex_model": "opus"` and `"codex_model": "gpt-7-preview"` answer 400 naming `codex_model` (Codex pins are closed to the `role` set). A PUT that omits `codex_model` leaves the stored Codex pin unchanged and does not change the customized state.
4. **Lead Codex pin.** The lead template's Codex pin is `gpt-6-astra`. A Codex issue run for a user with no Codex worker model runs its root on `gpt-6-astra`, and H records source `template`. A user whose Codex worker model is `gpt-6-sol` runs on `gpt-6-sol` (source `user_default`). A schedule pin `gpt-5.6-sol` wins over both (source `schedule_pin`).
5. **Repo agent.** A repo's `.claude/agents/coder.md` declares `model: gpt-6-sol`. On a Claude run that `coder` has no model; on a Codex run it runs on `gpt-6-sol`. The same file with `model: opus` runs `coder` on `opus` for Claude and follows the lead on Codex, with no diagnostic.

## Modules and seams

### S1. Pin rules (`api/internal/agenttmpl`)

Deep module: callers ask "is this a valid pin for harness H" and "which pin does this single model value belong to". The vocabulary lives in child C's `fixtures/codex-models/models.json` `role` set and its Go set `agenttmpl.CodexRoleModels`; G adds no fixture and no Go list of its own.

- Agent and web use C's exports, already pinned to the fixture by C's tests: `isCodexRoleModel(model)` in `agent/src/codex/render.ts` (C M2) for S4 and S5, and `CODEX_ROLE_MODELS` in `web/src/lib/codexModels.ts` (C M3) for S6. G adds no vocabulary export and no fixture reader.
- `ValidateTemplatePin(harness, raw string) (string, error)`. Blank after trim returns `""`, nil (NULL = Default). Otherwise `ValidateModel` first (so a shared-surface value is at most 100 bytes and carries no control or format character). `claude`: delegates to `agenttmpl.ValidateClaudeLaneModel` (rejects every `CodexRoleModels` id, incl. `gpt-6-luna`); custom Claude ids pass (closed-list guard, no prefix guessing, PRD #1551 D3). `codex`: must be a `CodexRoleModels` member; a Claude alias or any custom id fails. Unknown harness is an error. Used for every template, lead included.
- `SplitModelPin(raw string) (claude, codex string)` for sources that carry one `model` value: a trimmed `role` member is the Codex pin, any other non-empty value the Claude pin. Pure; callers have already applied their own syntax rule.
- `PinForHarness(harness string, claudePin, codexPin string) string`: the delivery filter. Claude returns `claudePin` unless it is a `role` id; Codex returns `codexPin` only if it is a `role` id; anything else returns `""`. This is the second line of defense after the write-side rules, for rows written by a rolled-back binary, a direct SQL write or any future writer.
- `Definition.CodexModel string`. `Render` does not emit it (the rendered file is a Claude Code subagent file, which has no Codex field; `/rendered` stays Claude-only). `SameContent` compares it exactly, like `Model`.
- Write-side invariant after M1a: `model` is NULL or not a `role` id; `codex_model` is NULL or a `role` id. The API validates, sync classifies, the migration moves existing values, builtins are test-enforced Claude-only. Delivery does not rely on it (`PinForHarness`).
- Tested through table tests on the three functions, including `gpt-6-luna` in each (the one id that separates `role` from `curated`).

### S2. Template HTTP API (`api/internal/handler/agent_templates.go`)

- `agentTemplateDTO`, `builtinDefinitionDTO` and `templateWriteRequest` gain `codex_model` (string or null). `model` keeps its name and meaning: the Claude pin.
- A template-only wrapper (`validateTemplatePin`) over `agenttmpl.ValidateTemplatePin` replaces `validateModel` in `validateTemplateFields` only. The per-user settings callers of `validateModel` keep their rules.
- Request semantics. `model`: as today (null or blank clears), through the Claude rule. `codex_model` is tri-state: absent on create = NULL; absent on update = **the stored value is merged into the validated fields before both the customized decision (`updateMarksCustomized`) and the write**; JSON null or blank = clear; a string goes through the Codex rule. Follow the `Present` + value pattern of `apitypes.OptionalHarness`. Reason: a tab opened before the upgrade PUTs without `codex_model`; it must neither wipe the pin nor flip a customized builtin back to pristine (which would let the next boot's `RefreshPristineBuiltin` clear the pin).
- Errors: 400 naming the field (`model: …` / `codex_model: …`). Authorization order unchanged (the row is loaded and authorized before any validation error is revealed).
- `updateMarksCustomized`, `differsFromBuiltin`, `templateToDefinition`, `fieldsToDefinition` carry `CodexModel`, so the customized flag and the drift badge include the Codex pin (user decision G1). Reset re-applies the shipped definition, whose Codex pin is empty, so Reset clears it.
- Tested in `agent_templates_test.go` (`TestValidateTemplateFields` style), `agent_templates_customized_test.go` (new case: an update that omits `codex_model` on a builtin with a stored pin and otherwise shipped content stays customized), `agent_templates_drift_test.go`, plus separate LiveDB round trips: an update without `codex_model` preserves the pin through reconcile; an update with null clears it.
