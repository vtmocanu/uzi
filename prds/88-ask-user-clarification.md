## Problem

After the plan-approval gate, a run is autonomous. The lead has exactly two out-of-band signals — `submit_plan` and `signal_done` (`agent/src/signals.ts:21-22`) — and **no way to ask the human a free-form question**. The SDK runs `permissionMode: "bypassPermissions"` (`agent/src/sdk-executor.ts:288`), so no permission prompt ever surfaces, and `AskUserQuestion`/`ExitPlanMode` are not wired at all. Local Claude Code has `AskUserQuestion` for exactly the moment an agent hits a fork it should not resolve alone; uzi has nothing equivalent.

The consequences on a longer run:

- **Mid-run**: when the lead meets an ambiguous requirement, a missing product decision, or a plausible-but-destructive action, it can only **guess**, prematurely `signal_done`, or **stall**. Stalling is the worst: the idle timeout (10 min default, `sdk-executor.ts:50`, `REASON_IDLE`) fails the run as *"run stalled: no agent activity within the idle timeout"*. There is no third option — "pause and ask."
- **Pre-run**: there is no check for whether the task is even answerable. An underspecified issue goes straight into a planning turn that burns tokens (and, with autopilot, straight into implementation) before the user ever learns the spec was ambiguous. The plan gate can only reject *after* the plan is produced; it cannot say "before I plan, I need to know X."

Human-in-the-loop today is two fixed channels and neither is agent-pull: the **plan-approval gate** (structural, once, before implementation) and **user-initiated steering** (`follow_up`, the user must proactively push; the agent cannot solicit it). The agent can never say "I'm blocked, I need you."

## Inspiration check

| Aspect | Local Claude Code | uzi today | uzi (this PRD) |
|---|---|---|---|
| Agent asks the human a question | `AskUserQuestion` tool — blocks, renders options, resumes on answer | None — `bypassPermissions`, no `AskUserQuestion`; agent guesses/stalls | `ask_user` signal → run parks `awaiting_input` → answer resumes the session |

| Not blocking forever | Human is there | Idle timeout fails a stalled run | Bounded answer deadline; autopilot auto-resolves (Decision 8) |

The park-surface-resume shape is settled prior art in this very codebase: the **plan gate** already stops a run for human approval (`awaiting_approval` + `gatePlan` verdict-await), and **#41** already delivers a typed steering input back into a live SDK session with Slack parity. This PRD adds a *third* reason to stop — a free-form question — reusing both rather than inventing a new interaction model. **inspiration/** check (bottega/multica/dot-agent-deck): none expose an agent-initiated question channel; this is net-new for the peer set, so there is no "beat X" bar, only the local-Claude-Code parity bar above.

## Solution Overview

A general **clarification mechanism**, triggerable at two moments:

1. **Mid-run (M1–M3, the core):** the lead calls a new in-process signal tool **`ask_user(questions)`** when it needs a human decision. The worker parks the run in a new **`awaiting_input`** status, emits a `question` run-message, and awaits an `answer` steering input — mirroring exactly how the plan gate emits a plan, posts `awaiting_approval`, and awaits a verdict. The question surfaces in the **UI feed** (with an answer composer) and, opt-in, in the owner's **Slack DM** thread. The user answers on either surface; the `answer` is delivered to the **same SDK session** (resumed via the `resumeId` the executor already threads, §51); the run returns to `running` and continues.

2. **Pre-run (M4):** the same `ask_user` can fire in the **planning turn**, *before* `submit_plan`, so the user clarifies an underspecified issue up front rather than after a wasted plan. **PRD #84's pre-run readiness check emits spec-clarification questions through this path** — #84 decides "the task is ambiguous," #88 owns surfacing and answering. "When possible" is a judgment call the prompt guides (Decision 7): ask only when a wrong guess is costly and the answer is not inferable from the repo or the issue.

The whole thing is bounded (answer deadline + per-run question cap), autopilot-safe (auto-resolve), and reaches the CLI (`uzi run answer`). It is scoped to **runs** (`sdk-executor.ts`); chat is already interactive by construction (a park-between-turns loop) and is out of scope.

## Design Decisions

1. **`ask_user` is a third in-process signal tool, not an overload of `submit_plan`.** `signals.ts` today registers exactly `submit_plan` + `signal_done`; add `ask_user`. Like the other two, its handler only returns a stub and the worker acts on observing the `tool_use` via `scanSignals` (the dual "handler + scan" shape that keeps it testable with a scripted `queryFn`). Payload is **structured**, mirroring `AskUserQuestion`'s shape so the UI can render it richly and the model has a familiar contract: a list of questions, each `{ question, header, options?: [{label, description}], multiSelect? }`. Free-text answers are always allowed even when options are offered. Only the lead (full toolset) reaches it, same as the other signals; subagents cannot ask the user (the guard hook denies signal tools to the roster).

2. **`answer` is a new steering-input kind, delivered like `revise_plan`.** `run_user_inputs.kind` CHECK (`00020_workers_runs.sql:86`, currently `follow_up|approve_plan|reject_plan|cancel`; #41 adds `revise_plan`) gains `'answer'`. It resolves the pending **question verdict** the executor awaits — the direct analog of `gatePlan`'s approve/reject verdict. It is deliberately **not** a `follow_up`: follow-up's "queue for the *next* implementation turn" semantics are load-bearing and would make delivery depend on run status at arrival time (the exact race #41 Decision 1 rejects). A distinct kind keeps the wire unambiguous — an `answer` resolves *this* question; a `follow_up` is an unsolicited note for later.
   - **The kind whitelist lives in five places, changed in one commit (#41 Decision 12 — carried in full, since #88 review found #88 named only two).** Adding `'answer'` touches: (1) the DB CHECK (`00020_workers_runs.sql:86`); (2) the handler accept-set `runInputKinds` (`api/internal/handler/workers.go:78-79`); (3) the 400 error string that enumerates the kinds (`workers.go:536-537`); (4) the web `RunInputKind` type; (5) the CLI (Decision 10). A partial update yields a confusing 400-vs-500 mismatch. Server-side, `answer` has **no no-poller stop branch** (like `approve_plan`, `service.go` `SubmitInput`): an answer aimed at a dead worker waits for the requeue+affinity resume — which is exactly why Decision 3's worker-death sweeps must include `awaiting_input` (a parked run with a dead worker must be *recoverable*, or the answer waits forever).

3. **A new run status `awaiting_input` — this IS worth a status, where #41's `revising_plan` was not.** #41 Decision 4 refused a new status for plan revision because it was short and worker-internal.
   - **The load-bearing reason for a distinct status (the one the first draft missed).** "Lasts hours / no `RUN_TIMEOUT` / needs a badge" is all true but *weak* — `awaiting_approval` already gives those. The reason you genuinely **cannot reuse `awaiting_approval`** is the resume transition: `SetRunRunning` gates `awaiting_approval → running` on a **consumed `approve_plan`** (`runtime.sql:320-324`). An `answer` never satisfies that predicate, so a run parked as `awaiting_approval` for a *question* could never return to `running`. #41's revise sidesteps this only by staying `awaiting_approval` **and** inventing `gate_state='revise_pending'` (`00044:34`) to carry the sub-state. A distinct status is the clean alternative: the Slack replier and web/CLI route on `run.Status` alone, and the resume path gets its own guard (below). So the *decision* is right; the *cost* is bigger than "the sweeper."
   - **Full cost enumeration (the #88 review's finding A–D — a new status does NOT inherit what `awaiting_approval` earns; each `status IN (…)` site is explicit).** A migration adds `'awaiting_input'` to the CHECK (`00020_workers_runs.sql:37`; draft `00072`, above live head `00071`). Then **every** enumerated site that lists `awaiting_approval` must also list `awaiting_input`:
     - **(A) Worker-death recovery — four sweeps, MANDATORY.** `RequeueRunsOfStaleWorkers` (`runtime.sql:506`), `FailRunsOfStaleWorkersOverCap` (`:491`), `RequeueWorkerRuns` (`:540`), `FailWorkerRunsOverCap` (`:527`) all use `status IN ('claimed','running','awaiting_approval')`. Omit `awaiting_input` and a worker that dies while parked **strands the run forever** (dead `worker_id`, an `answer` that waits for a resume that never comes). `RUN_TIMEOUT`-exemption and worker-death recovery are **different axes**; the run's affinity-grace resume then re-enters `awaiting_input` on the new worker (the question is durable in `run_messages`, like the plan).
     - **(B) Resume guard — `SetRunRunning`, MANDATORY (the #44 F2 race recurs).** `awaiting_input → running` needs the same guard `awaiting_approval → running` has (`runtime.sql:320-324`): require a **consumed `answer`**, else a retry-delayed fire-and-forget `reportState({status:"running"})` (`runner.ts:219-236`) lands after the `awaiting_input` report and silently flips the run back to `running`, hiding the question until it dies on the deadline. (Decision 4 restates this.)
     - **(C) Concurrency accounting — `busy`/`active_runs`.** `ListWorkersByUser` (`runtime.sql:36,41`) and `ListAllWorkers` (`:204,209`) count `status IN (…'awaiting_approval')`. Omit `awaiting_input` and a worker parked on a question reads not-busy and can claim **another** run past its `max_concurrent_runs`. (`CountWorkerNonTerminalRuns:98` / `ListActiveRunsAll:186` use `NOT IN (terminal)` and get it free — the sites are genuinely mixed, which is why they must be enumerated, not assumed.)
     - **(D) Board lifecycle — `reconcilerDecision`, corrected.** `awaiting_approval` is **not** a board no-op: it maps to a move in `reconcilerDecision` (`lifecycle.go:163`). A new status left out falls to default → `move_pending_since` is never cleared → spurious "column move gave up" warnings after 30 min for every parked run. Add `awaiting_input` to the non-terminal case at `lifecycle.go:163` (it stays a no-op in `notifierDecision`).
     - Plus the non-enumerated followers: status badges, every web status switch, the CLI list rendering (Decision 10). Reusing `awaiting_approval` would additionally conflate "approve my plan" with "answer my question" across all of these surfaces.

4. **The gate loop mirrors the plan gate — but right-sized, NOT #41's full precedence engine (review finding E).** In `sdk-executor.ts`, a turn that emits `ask_user` calls a new `ctx.askUser(questions)` that flushes the `question` run-message, reports `awaiting_input`, and awaits an `answer`. The session is resumed via the existing `resumeId` — full context, no transcript replay. `PlanVerdict`'s sibling here is `AnswerVerdict { answers | cancelled }`; on resume `SetRunRunning` requires the consumed `answer` (Decision 3B). **What #88 does *not* need:** #41's epoch-tagged select exists to resolve a hard race unique to revision — v1's `approve` can be **in flight while v2 auto-re-opens** the gate, and a poll batch `[revise, approve]` needs per-round precedence. A mid-run question has **no auto-re-open**: the lead is *stopped* after `ask_user` and only resumes *after* an answer, so two live question-versions never overlap. So #88 needs only **first/latest-wins** on the answer buffer plus a **single generation tag** for the one genuine async race: a late `answer` to an already-resolved Q1 (a Slack reply that arrives after Q1 resolved and the lead asked Q2) must be discarded, not applied to the live Q2. `cancel` is generation-exempt and always aborts.
   - **Dependency honesty:** PRD #41 is **Draft/unbuilt**, so "reuse #41's steering/Slack machinery" means *either wait for #41 to land, or build that machinery here* — it is not free-riding on shipped code. Right-sizing to first/latest-wins + one generation tag keeps #88 M1 from being blocked on #41's precedence engine, which #88 does not use. The `revise_plan`-style delivery shape and the Slack pipeline (Decision 9) are the parts genuinely shared.

5. **Bounds: an answer deadline + a per-run question cap.** (a) **Answer deadline** — an absolute deadline computed at first park (a worker-in-memory `setTimeout`, like the plan gate's `runner.ts:495-499`). Config `QUESTION_TIMEOUT` (default proposed **24h**, matching the plan gate). On timeout the run **fails** with "clarification timed out" — failing closed is safest; a configurable default-action is out of scope. *Honest limitation, same as the plan gate:* the timer is not durable — a worker death + requeue+resume (Decision 3A) resets it; state that rather than implying the absolute deadline survives a requeue. (b) **Question cap — WORKER-SIDE, not `SubmitInput` (review error 2).** A question is an **in-process `ask_user` signal** (agent→worker, observed via `scanSignals`), so unlike `PLAN_MAX_REVISIONS` (which counts `revise_plan` *input rows* the server sees) there is **no `run_user_inputs` row to count** and `SubmitInput` only ever sees *answers*. The cap therefore lives in the **executor**: it counts `ask_user` parks per run and refuses beyond `QUESTION_MAX` (default proposed **5**), optionally backstopped by counting persisted `question` run-messages. Exhaustion emits a refusal into the feed; the lead proceeds on best judgment. **This makes the cap M1 (worker mechanism), not M5** — M1–M4 must not ship unprotected against a looping lead. (c) **Idle timeout does not fire while parked**: the await lives *outside* `driveTurn` (like `gatePlan`), so the idle machinery does not run during the park.

6. **UI: derive the state from the feed, add an answer composer (reuse #41's surfaces).** New run-message kinds `question` and `answer`, rendered in `RunEvent.tsx` (beside the `plan` case) and `ActivityFeed`, through the escaped `<Markdown>` sink — never raw (the #41 D9 rule; a vitest pins escaped render, since question text can quote attacker-influenceable issue/repo content). The run panel shows an **"Answer required"** affordance with a composer (the #41 Request-changes composer is the precedent, incl. its mockup); submitting POSTs steering `kind=answer`. Options, when present, render as selectable chips with a free-text fallback. The board/run row shows the `awaiting_input` status chip.

7. **Prompt guidance — when to ask (this is the quality bar).** The lead's plan and implementation prompts (`agent/src/prompt.ts`) gain an explicit heuristic: **ask only when a wrong guess is costly AND the answer is not inferable** from the repo, the issue, or the existing plan; never ask for trivia, never ask what a `grep` would answer, batch related questions into one `ask_user`. This is what keeps the feature from becoming a nag. The pre-run (planning-turn) variant is framed as "surface blocking ambiguities *before* proposing a plan," so the user resolves them once rather than round-tripping through plan rejections.
   - **The pre-run path trips an existing hard-fail — M4 must fix it (review finding F).** `sdk-executor.ts:371` throws `REASON_NO_PLAN` ("the agent ended the planning turn without submitting a plan") whenever a planning turn returns `plan.plan === undefined`. A pre-run `ask_user` ends the planning turn **with questions and no plan** → without a fix the run *fails* instead of parking. M4 special-cases it: a planning turn that ended by asking (questions present, no plan) parks at `awaiting_input`; on answer the run **resumes the planning session and re-plans** (→ eventually `submit_plan` → normal plan gate). Only "no plan AND no questions" stays the `REASON_NO_PLAN` error. This is the concrete landmine in the pre-run trigger and is the first thing M4 wires.
   - **Turn-boundary contract (load-bearing, minor to state).** Like `submit_plan`'s "STOP and end your turn" (`signals.ts:47`), the lead MUST end its turn after `ask_user`; the park happens *between* turns (the executor calls `ctx.askUser` after `driveTurn` returns, having read `result.questions` from `scanSignals`), and the answer is delivered as a **resumed user turn**, not the tool's return value. "Mirrors `AskUserQuestion`" is true only for the payload *shape*. The answer-resume turn does **not** count against `RUN_MAX_ITERATIONS` (a clarification is not an implement/review iteration).

8. **Autopilot auto-resolves — it must never hang.** Autopilot (PRD #19) is "no human in the loop"; its auto-approve short-circuit lives *inside* `gatePlan` at `runner.ts:465-489` (`if (autoApprove) …`), fed by `claim.auto_approve` threaded in at `runner.ts:229-230` (the earlier `runner.ts:257-263` in the draft was the wrong ref — that's the ci_fix `not_code` path). The auto-resolve here is **net-new, not a reuse**: `askUser` must receive `claim.auto_approve` the same way `gatePlan` does, and when set, resolve immediately with a sentinel **"no human available — proceed on your best judgment, and note the assumption you made"** answer, so the run continues instead of parking forever. One test pins that an autopilot run never enters `awaiting_input`.

9. **Slack: full parity — see the question, answer the question (reuses #41 D10's *design*, and is simpler).** With Slack linked + notify on, a park posts the question into the owner's 1:1 DM run thread via the existing notifier/poster, through the **#41 D10 pipeline**: `ScrubSecrets → EscapeMrkdwn` (whole-blob, since question text quotes attacker-influenceable content) `→ truncate on a rune boundary to the 3000-char section limit → deep-link appended as separate trusted markup`. **Two honest caveats vs. "reuse wholesale":** (1) **#41 M4 is unbuilt**, so this pipeline is **net-new code**, not a call into shipped Slack machinery. (2) The answer round-trip is **simpler than revise** — no button, no `gate_state` anchor: the distinct `awaiting_input` status *is* the routing signal. The **replier** `HandleMessage` (`replier.go:98-186`) switches on `run.Status`; add an `awaiting_input` case that submits `SubmitInput("answer", text)` **before the default branch (`replier.go:177`)** — otherwise a reply to a parked run falls through and becomes a `follow_up`. The **double-submit race** (two replies before the worker flips status, both seeing `awaiting_input`, both enqueuing an `answer`) is resolved **worker-side** as first-wins on the `askUser` await (there is no `gate_state` anchor to compare-and-swap on, unlike #41's revise). Generation tag (Decision 4) discards an answer to an already-resolved question. Offered options MAY render as Slack buttons (a follow-on); free-text reply is the M3 baseline. Privacy honesty carries over from #41 D10: question bodies can quote source/issue content the run redactor and `ScrubSecrets` do not fully cover; `docs/slack.md` + ARCHITECTURE.md's trust model must say so. Opt-in and DM-scoped (`notifier.go`), so exposure is Slack's cloud + workspace-admin boundary, not other members.

10. **CLI parity (PRD #64).** `api/cmd/uzi/run.go` gains an **`answer`** verb (`uzi run answer <id> [--option ...] [message]`), sibling to the existing `approve|reject|cancel|follow-up` (`commands_test.go:59`), and `run list`/`run get` render the `awaiting_input` status + the open question. This keeps the CLI a first-class consumer per CLAUDE.md's "new functionality ⇒ check `api/cmd/uzi`" rule; the DTO fields M2 adds (open-question payload, status) are what the CLI reads.

11. **We mostly test in k8s now (CLAUDE.md, 2026-07-18).** The Slack round-trip and the park/resume across a real worker are validated on the hosted k8s deployment (dev-cluster) as a first-class target, not only under docker-compose; the compose path stays green for the e2e/smoke harness.

## Risks & mitigations

- **Nagging / over-asking** → Decision 7 prompt heuristic + Decision 5 per-run cap; the bar is "costly wrong guess AND not inferable."
- **A run parked forever** → Decision 5 absolute deadline (fail-closed) + Decision 8 autopilot auto-resolve; sweeper treats `awaiting_input` as a legit park (never a stale claim, per #42).
- **Stale answers** (answer a superseded question) → Decision 4 epoch discard (web) + Decision 9 generation guard (Slack), both inherited from #41.
