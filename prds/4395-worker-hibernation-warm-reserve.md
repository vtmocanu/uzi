# PRD #4395: Worker hibernation: keep one warm worker per pool, hibernate the surplus

**Epic**: #4204 (step 5, "capability-aware warm coverage"). **Status**: Draft, 2026-11-16. **Blocked by**: none open; builds on PRD #4205 (sleep/wake), PRD #4206 (cache cleanup) and PRD #4207 (automatic hibernation), all merged.

## Problem

Automatic hibernation (PRD #4207) puts a persistent hosted worker to sleep only after it has had no run activity for `worker_hibernation_idle_after` (default 14 days). A user with two or more interchangeable workers keeps all of them awake while they use any one of them now and then. On the affected deployment (2026-11-16 snapshot) 5 of the owners of the 15 persistent hosted workers have two or more workers; all 15 have a declared template and size. Each awake worker holds a pod's CPU and memory reservation.

## Outcome

With a new default-off admin setting on, uzi keeps **one idle, ready worker per owner per equivalence pool** awake and hibernates the other idle workers of that pool after a short idle threshold (default 2 hours). When the warm worker takes a run and the pool has no other idle ready worker, uzi starts waking one automatically hibernated worker of that pool, so a following run does not pay a cold start once that wake has settled. Once the owner has had no run of any kind for the long threshold (`worker_hibernation_idle_after`), uzi stops replenishing and every pooled worker of that owner may sleep. Warm-reserve wakes never count as owner activity.

Acceptance examples:

1. Owner A has two workers with the same pool key (below), both awake, idle and ready. With the setting on and a 2h surplus threshold, after 2h the one used less recently is hibernated and the other stays awake. A single run then starts on the awake one with no cold start.
2. Owner A's warm worker claims a run. The pool now has no idle ready awake worker, no healthy waking member, and A is active. Within one pass uzi moves one of A's automatically hibernated (or still preparing) pool members to `waking` (system wake, reason names the warm reserve), without writing a demand-wake receipt. Once its wake settles, a second concurrent run can land on it without a cold start. It is not surplus again before the surplus threshold has elapsed since that settle.
3. Owner B has one Docker worker and one non-Docker worker (different pools). Neither is surplus; each sleeps only under the long-threshold rule.
4. Owner A runs nothing for 14 days. Replenishment stops, and the long pass hibernates every idle pooled worker of A, including one warm-woken during those 14 days (warm wakes do not extend the owner clock). Admin health judges on the same clock.
5. Setting off: decisions are exactly today's PRD #4207 behaviour: the existing queries (`GetWorkerIdleness`, `ListAutoHibernationCandidates`, `ListAutoHibernationBlockers`) run unchanged, no surplus admissions, no warm wakes. Switching the setting off right after a warm wake does not hibernate that worker early (every settle still writes `last_wake_settled_at`).
6. An admin manually hibernates pool member B while A is busy. The next pass does not wake B (warm wakes only target automatically admitted sleepers).

## Out of scope

- Ordering sizes or templates ("a large worker covers a medium one"). v1 pools only workers with identical keys. Concrete sizing lives in `controller/internal/preset/preset.go`; a supported cross-size relation is a later refinement.
- Counting spare claim slots on a busy worker as the reserve. The reserve is an **idle** worker (no non-terminal run assigned).
- Demand prediction, schedule-aware pre-warming, per-user opt-out, per-pool settings, per-pool activity clocks (see D9).
- Ephemeral/run-bound workers, compose and local workers.
- Controller changes. Admission, cache cleanup and controller refusal are reused unchanged.
- Dropping the now-redundant `idx_runs_user` index (a later human decision from `pg_stat_user_indexes`).
- `.github/workflows/**`.

## Modules and seams

**Settings** (pattern: `worker_hibernation_auto` / `worker_hibernation_idle_after`, `api/internal/settings/keys.go`, the single-key validators in `settings_hosted.go`; web: the hibernation settings card, `web/src/lib/apiTypes.ts`, and the mock validator `web/src/mocks/mockApi/settings.ts` pinned by `mockApi.mockFidelity.test.ts`).

- `worker_hibernation_surplus`: bool, default false. Effective only while `worker_hibernation_enabled` and `worker_hibernation_auto` are both on.
- `worker_hibernation_surplus_idle_after`: Go duration, default `2h`, validated to [`15m`, `336h`] (single-key validator, like the existing ones). The pass uses `min(surplus_idle_after, idle_after)` at read time; the card shows a hint when the surplus value exceeds `idle_after`. No cross-key write refusal.
- The CLI has no settings write path for these keys (settings writes are web-only); check `api/cmd/uzi/` for any settings display and update it if one lists hibernation keys.

**Equivalence pool.** A pure function over worker rows, unit-tested in isolation.

- Key: `(user_id, template_declared, hosted_size, isolated_lane, docker_enabled, effective capabilities via fn_effective_worker_caps (as a sorted, deduplicated set), protocol_capabilities (sorted, deduplicated set), max_concurrent_runs, max_cross_check_slots)`. Exact equality; NULL matches only NULL for `max_cross_check_slots`.
- A worker that is ephemeral, non-hosted, or has NULL `template_declared`, `hosted_size` or `docker_enabled` (never registered) is in no pool: never surplus, never re-warmed (PRD #4207 rule only).
- Computed from worker rows only, never from display-only controller evidence (`roll_pacing`, the #4385 roll-marker report) or Kubernetes readiness.
- Invariant established (replaces any "never wrongly equivalent" claim): pool members share every worker-level claim-relevant field the api stores. Per-run facts (affinity, pins, the Docker repo allowlist, harness and model) can still differ between runs; a mismatch costs at most one demand wake (the existing PRD #4205 path), never a stranded run.

**Ready (serving) predicate.** Whether an awake pool member can take the next run now. It must not be equated with `store.WorkerAcceptsNewIntake` alone (that covers cordon, drain, maintenance and hibernation). Ready = `status = online`, heartbeat fresher than `WorkerHeartbeatStale`, `hibernation_state = 'none'`, `WorkerAcceptsNewIntake` true, usable slot capacity (no non-terminal run assigned, since the reserve is an idle worker), and no other worker-wide condition the api knows prevents new claims: the implementer audits and lists in the PR the memory-authority, cleanup-pending, outbox and pending-outcome gates (the agent pauses claims on pending-outcome overflow, `agent/src/worker.ts` ~1499/1554; the api sees `pending_overflow` / `pending_outcome_count`), and any condition whose state cannot be established makes the member **not ready** (fail closed: worst case an extra worker stays awake or a sleeper is re-warmed). Custody on a member does not by itself make it non-serving; serving eligibility and permission to hibernate are separate questions.

**Wake target eligibility ("as if awake").** A sleeper may be warm-woken only if: its current hibernation op was admitted by the automatic pass (`auto_long` or `auto_surplus`, below), it is not manually cordoned and not under maintenance, and it has no `wake_error`. Preference order: `preparing` members first (withdrawn through `moveToWaking`, which supports it), then `hibernated`; within each, most recently used first, then oldest, then lowest id.

**Op-bound origin marker (one additive migration plus one validate migration).** The hibernation op lives in columns on `workers` (`hibernation_op_id` and friends, all rewritten by `writeHibernation`). Add nullable columns, no defaults, no backfill (existing rows read as legacy):

- `hibernation_origin_op_id uuid` (the op the markers below belong to),
- `hibernation_admit_origin text` (`manual`, `auto_long`, `auto_surplus`), set where the op is admitted,
- `hibernation_wake_origin text` (`manual`, `demand`, `system`, `warm`), set where the op moves to `waking`,
- `last_manual_wake_settled_at timestamptz` (owner-wide long anchor input, below).

Constraints added `NOT VALID` with `SET LOCAL lock_timeout = '5s'` (00457 pattern), validated in a separate migration (00458 pattern): domain CHECKs on both origin columns, and coherence (origins set only when `hibernation_origin_op_id` is set). All columns go into `WriteWorkerHibernation`, or `writeHibernation` silently never persists them. A marker is valid only when `hibernation_origin_op_id = hibernation_op_id`; anything else (including a new op minted by an older api replica during a rolling deploy) reads as legacy: admit origin unknown (never warm-woken), wake origin non-warm.

- **Every `moveToWaking` caller gets an origin:** `WakeWorker` with an actor (handler) = `manual`; `DemandWake` = `demand`; the warm path = `warm`; nil-actor `WakeWorker` other than the warm path, `ApplyTransition` refused-after-scale-down, settle-pass preparation deadline, settle-pass hibernation disabled, and `hibernation_cleanup.go` withdrawal = `system`.
- **Join precedence:** `moveToWaking` is a no-op on an already waking row and keeps its op; a `manual` or `demand` request on a waking `warm` op upgrades the wake origin to the stronger one; nothing ever downgrades to `warm`. An origin-only upgrade counts as a persisted change: today `DemandWake` writes the row only when `moveToWaking` reports a change, so the upgrade is written in the same transaction, preserving the op id, first wake time and existing readiness evidence.
- **Settlement (`trySettle`):** writes `last_wake_settled_at` on **every** settle exactly as today (warm included), so `GetWorkerIdleness`, the surplus anchor and off-mode behaviour are unchanged; additionally writes `last_manual_wake_settled_at` when the valid wake origin is `manual`. Settlement leaves the op's markers in place until the next op, so the origin of the wake that set `last_wake_settled_at` stays readable.
- **Conservative legacy policy (long anchor input):** the long anchor's wake term is `GREATEST(last_manual_wake_settled_at, CASE WHEN the current op's markers are valid AND its wake origin IN ('warm','system') THEN NULL ELSE last_wake_settled_at END)`. So a recent wake with no valid marker (an existing row from before the migration, or a manual op settled by an older replica) keeps its full grace, and only a positively known warm or system wake is excluded from the owner clock.
- **Grace carry-forward across op replacement:** `last_manual_wake_settled_at` is the durable manual-grade grace anchor: it holds manual settles and the conservative legacy baseline. Before any write that replaces the op's markers or sets its wake origin to `warm`/`system` (a new admission, a new `moveToWaking` op), the same transaction first raises `last_manual_wake_settled_at` to `last_wake_settled_at` when the current op's settle counts as manual-grade under the term above. An earlier settlement is never classified by a later op's origin, and known warm/system transitions neither advance nor erase grace already earned.

**Owner activity anchor (user decision 3).** One statement, served by indexes:

`GREATEST( (SELECT max(created_at) FROM runs WHERE user_id = @owner), (SELECT max(COALESCE(finished_at, status_since)) FROM runs WHERE user_id = @owner AND status IN ('completed','failed','cancelled')) )`, plus `EXISTS` any non-terminal run with `user_id = @owner` (any kind: scheduled, judge, job, chat, repo-less, unassigned, ownership-released), which makes the owner **active now**. Attribution is by `runs.user_id` only, never by `worker_id`, so a run that ran on no worker, a released worker or a since-deleted worker counts by its finish as well as its creation.

- Every run kind counts, so a daily scheduled job keeps an owner active (intended).
- Two new indexes, each in its own `-- +goose NO TRANSACTION` migration with 00459's drop-then-create pattern: `runs_user_created_idx ON runs (user_id, created_at)`, and the partial expression index `runs_user_terminal_end_idx ON runs (user_id, (COALESCE(finished_at, status_since))) WHERE status IN ('completed','failed','cancelled')`, the per-user twin of 00459's `runs_worker_terminal_end_idx`. `created_at` is immutable (no new HOT loss); a row enters the partial index at its terminal transition, which already changes `status` and is non-HOT today. The implementer confirms the plan uses both (LiveDB plan test below) and, if the final query shape differs, keeps an indexed path with no per-run scan.

**Two idle clocks.**

- **Surplus anchor** (surplus admission only): today's `GetWorkerIdleness` anchor, unchanged (`GREATEST(last terminal finish on this worker, last_wake_settled_at, created_at)`). Because every settle, warm included, writes `last_wake_settled_at`, a warm-woken worker gets at least the surplus threshold of residence.
- **Long anchor while surplus mode is on** (long pass for pooled workers, its locked recheck, and `fleet.hibernation` for them): `GREATEST(owner activity anchor, worker.created_at, the conservative wake term above)`, and never long-idle while the owner is active now. Demand wakes need no term (the run's own `created_at` counts); `system` and `warm` wakes never extend it. New queries, one statement each, used in lockstep by `ListAutoHibernationCandidates`'s surplus-mode sibling, the `autoAdmit` recheck and `ListAutoHibernationBlockers`'s surplus-mode sibling; the existing three queries stay byte-identical for off mode and for unpooled workers. `TestAutoAdmitReadsIdlenessOnce` is updated to pin exactly one idleness read per mode.

**Policy pass (extends `HibernationAutoPass`, `api/internal/workersvc/hibernation_auto.go`).** At most once per minute, before the demand waker in the same sweeper tick (`cmd/server/main.go` order).

- **One transaction per decision, owner-locked first.** A new helper runs: `pg_advisory_xact_lock(HibernationOwnerLockClass, objid(owner uuid first four bytes))` as the first statement (new constant beside `HostedProvisionLockClass` in `api/internal/store/migrate.go`; never reuse an existing class), then `GetWorkerForUpdate(candidate)`, then ONE fresh statement reading the owner's whole pool decision input (each member's key fields, state, intake and readiness columns, heartbeat, non-terminal count, surplus anchor, pending `hibernation_wakes`, wake error, origins, plus the owner anchor), with `now` and cutoffs passed from Go, then the write, then commit. The decision read is never folded into the lock statement and never taken from the list query. Mutations reuse the locked-row helpers (`hibernateRefusal` + `admitHibernation` + `writeHibernation`; `moveToWaking` + `writeHibernation`, as `DemandWake` does). It never calls `WakeWorker` or `HibernateWorker` (each opens its own transaction; calling one under the candidate lock would hang on a second connection).
- **Lock-order invariant:** no path takes `HibernationOwnerLockClass` while holding a worker or run row lock; the pass takes it before any row lock and inserts no hibernation event (an FK insert would take KEY SHARE on `users`). Paths that do not take it and why that is safe: manual `HibernateWorker` (admin intent; warm wake never targets a manual sleeper), the claim path and `DemandWake` (they only add awake or busy capacity).
- **Surplus admission.** Candidate is pooled, awake, idle by the surplus anchor at or before `now - min(surplus, idle_after)`, and another member of its pool is awake, ready and idle and is the deterministic keeper (most recent surplus anchor first, then oldest `created_at`, then lowest id; slot counts are equal within a pool because `max_concurrent_runs` is in the key). The candidate is never the keeper. Admission uses the unchanged refusal path with admit origin `auto_surplus` and reason `automatic: surplus in pool, idle <threshold>`; refusals are recorded with `SetWorkerHibernationBlocked` as today.
- **Long admission while surplus mode is on.** For pooled workers the long pass uses the long anchor above, runs under the same owner lock, and records admit origin `auto_long`. Unpooled workers keep today's path exactly.
- **Warm wake.** For a pool with no awake ready idle member, no `waking` member without `wake_error` (a healthy waking member counts toward the reserve), the owner active within `idle_after` (or active now), and no member holding a pending demand wake: move exactly one eligible sleeper (target rules above) to `waking` with wake origin `warm` and reason `automatic: warm reserve`. Never write a `hibernation_wakes` row (PRD #4205 D9/D20 receipts stay per queued run). Existing demand-wake and ephemeral-provisioning behaviour is unchanged: a queued run attaches to a warm-waking worker only when it independently qualifies for a demand wake (`ListHibernationWakeDemand` treats an online capable worker as coverage even when it is full), and a proactive wake alone does not suppress saturation-driven ephemeral provisioning (`wakeSuppressesProvision` needs that run's own receipt).
- **Budgets and fairness.** While surplus mode is on, one shared budget of 10 state changes per pass covers long admissions, surplus admissions and warm wakes, and each owner gets at most one change per pass across all three. Owners are served oldest-pending-first (by the candidate's anchor), so one owner with many pools cannot take the whole budget in one pass. Candidate listing stays bounded by fleet size (≤512).
- **Accepted races (Risks).** The keeper is read, not locked: a claim committing on it right after a surplus admission leaves the pool with no idle reserve; the next pass repairs it (withdrawing the still-`preparing` member first). Both members hibernated cannot happen through the pass: under the owner lock the second admission sees the first as `preparing` and finds no keeper. The keeper can also become non-ready through a manual hibernate, cordon, roll drain, maintenance or a stale heartbeat; the pass repairs that only while the owner is active (intended). Readiness may change right after observation; replenishment repairs rather than guarantees uninterrupted ready capacity.

**Admin health.** `fleet.hibernation` keeps its one-snapshot count, age and row-limit guarantees, and while surplus mode is on judges pooled workers by the long anchor (so an old unused worker of an owner active elsewhere does not warn while it is merely surplus-refused). Surplus refusals are recorded on the row (visible in the admin worker JSON from #4385) but do not raise the check. A warm wake that fails (`wake_error`) surfaces through the existing `fleet.hibernation_wake` check; the pool is then re-warmed from another eligible sleeper.

**Resource bounds.** No untrusted input: inputs are admin settings (validated, bounded) and worker/run rows. Per pass: at most 10 state changes, one advisory lock per touched owner held only for that owner's transaction, candidate scans bounded by fleet size, the owner anchor served by indexes. No new tables, no event rows; growth is the new index only.

## Risks

- **Docker cache churn:** every surplus sleep of a Docker worker runs the PRD #4206 cache prune, so a re-warmed Docker worker starts with a pruned build cache.
- **Roll interaction:** every image roll drains keepers, so pools re-warm after a roll; #4384's documented `roll_cohort_cleanup_pending` limit (one owner, several pools, one namespace) can refuse surplus admissions until that owner's next roll.
- **After a long sleep** the first run may wake two workers (a demand wake for the run, then a warm wake for the reserve). Intended.
- **Rolling deploy:** what decides is marker validity (op-id binding), not which replica settles. An old replica minting an op leaves markers bound to another op id, so that op reads as legacy and its settle counts as manual-grade (conservative; it may extend the owner clock once, during the rollout window only). An old replica settling an op whose valid warm marker remains present writes only `last_wake_settled_at`, and the term still excludes it as warm. An old replica settling a valid manual op writes no `last_manual_wake_settled_at`, but the term counts it through `last_wake_settled_at`, and the carry-forward preserves it before the next op.

## Decision Log

- **D1. Exact equivalence pools in v1** (lead/buddy/architect). Worker-level claim-relevant fields must match; per-run facts can still differ, costing at most a demand wake. Size ordering has no supported relation in the api. Rejected: capability superset plus size ordering.
- **D2. The reserve is one idle worker, not one free slot** (roadmap wording). Rejected: counting spare slots on a busy worker.
- **D3. Proactive re-warm is in v1** (user decision 2026-11-16). Rejected: v1 without re-warm. Hence M1 and M2 ship together.
- **D4. Surplus threshold default 2h, bounds 15m..336h** (user decision 2026-11-16), applied as `min(surplus, idle_after)` at read time. Rejected: a cross-key write refusal (today's validators are single-key, and it would be asymmetric when `idle_after` is lowered later).
- **D5. Owner-wide long clock while surplus mode is on** (user decision 2026-11-16): owner run activity of any kind, any non-terminal owner run = active now, plus the worker's creation and its last **manual** wake settle. Warm and system wakes never extend it; demand wakes are covered by their run. Revises PRD #4207 D2/D7 for pooled workers only while the new setting is on. Rejected: keeping the per-worker clock, which lets replenishment keep a reserve awake indefinitely.
- **D6. Owner-scoped advisory lock, then candidate row lock, then one fresh decision read, all in one transaction** (lead/buddy/dba/architect). The keeper row is read, not locked: a concurrent claim on the keeper can cost one warm-wake cycle, never both members hibernated. Rejected: `FOR UPDATE` on all pool rows (blocks claims and heartbeats on every member and needs id-ordered locking), and calling the transaction-opening `WakeWorker`/`HibernateWorker` under the lock (hangs on a second connection).
- **D7. Warm wakes never write a demand-wake receipt, and demand-wake and ephemeral-provisioning behaviour is unchanged** (lead/buddy/architect). A pool with a pending demand wake gets no warm wake; a queued run attaches to a warm-waking worker only when it qualifies for a demand wake on its own. Rejected: claiming warm wakes suppress duplicate ephemeral provisioning (existing code ties suppression to the run's own receipt; changing that would be a separate design decision).
- **D8. Churn bounds without extra timers** (lead/buddy): a healthy waking member counts toward the reserve, one change per owner per pass, residence equals the surplus threshold through the unchanged `last_wake_settled_at`. Rejected: a busy-delay timer plus an hourly quota.
- **D9. A reserve stays warm per pool while the owner is active anywhere** (lead). Accepted for v1; per-pool activity is a later refinement if measurements show cost.
- **D10. Warm wakes target only automatically admitted sleepers** (architect). An admin's manual hibernation is never undone by the policy. Rejected: waking any hibernated member.
- **D11. Op-bound origin markers on `workers`** (dba/buddy). There is no op table; binding to `hibernation_op_id` makes a rolling deploy and op replacement safe. Every settle keeps writing `last_wake_settled_at`, so off-mode and the toggle-off case stay unchanged.
- **D12. Two new per-user indexes on `runs`** (dba/buddy): `(user_id, created_at)` and a partial terminal-end index by user. Owner activity is attributed by `runs.user_id`, so worker-less and released runs count fully. Without the indexes the owner anchor costs O(owner lifetime runs) per pooled owner per minute (PG17/PG16 have no btree skip scan). Rejected: an unindexed aggregate on `idx_runs_user`, and attributing finishes through the owner's workers (misses worker-less, released and deleted-worker runs).
- **D15. Conservative legacy wake grace** (buddy): only a positively known warm or system wake is excluded from the owner clock; an unmarked wake counts as manual-grade. Grace is carried forward into `last_manual_wake_settled_at` before any op replacement, so a later op's origin never reclassifies an earlier settle.
