## Problem and outcome

A user with a Codex subscription wants to see account usage and reset times in the same places they see Claude limits. Today uzi can store named Codex logins, but its meters, polling, DTOs and terminal views cover Anthropic only. A user cannot tell whether their Codex account has room for more work without leaving uzi.

Show Codex account meters in Settings, the sidebar, Admin rate limits and the CLI/TUI. Mirror Claude's Settings checkmarks for choosing which additional accounts appear in both the sidebar and TUI, with the subscription default shown automatically. Collect readings in the API even when no worker or run is active, including usage incurred outside uzi as reported by the provider. Use the saved subscription identity and existing credential coordination. This feature provides visibility; it does not change run admission, automatic credential selection, parking, schedules or paid fallback policy.

## Proposed design

### 1. API-owned polling and shared credentials

Use a dedicated Codex account poller in the existing API process. Production calls target only the fixed usage host; response bodies, redirects, timeouts, request concurrency and retry delays are bounded. Disable redirects on credentialed requests. Use a separate `UZI_CODEX_USAGE_POLL_INTERVAL` (default 5 minutes; zero disables collection); the Claude interval and paid-probe option keep their existing meanings. No model invocation, inference charge, browser scraping or on-disk CLI session scan is needed.

Wake collection after a successful login save/replacement and vault unlock, with coalescing and bounded work. Reuse M1's nonrotating identity reconciliation to turn a valid staged login into a linked account. Do not establish identity from a label, decoded JWT or client-supplied account hint. If verification is incomplete or the imported access token has already expired, show an actionable state; do not rotate an unverified login just to discover its identity.

For linked accounts, open only the canonical durably committed credential under the vault rules. Poll once per `(uzi user, canonical provider account)`, even if several saved aliases refer to it. Send the verified workspace id as the upstream header. Treat a returned identity mismatch as an unusable reading, not a new account mapping. Respect revocation, material revision, credential revision, in-flight refresh and quarantined recovery state.

Add an internal, non-HTTP account-reader authorization path to the same refresh coordinator after #1171 lands. The worker-facing wrapper must still require its existing run capability and current-worker checks. Do not fabricate a run, weaken those checks, or create a public token-release endpoint. A poll refresh and a worker refresh for the same generation must converge on one durable operation. Preserve operation-id retry/reconciliation, durable commit before release, recovery fencing and quarantine on ambiguous provider outcomes. A polling timeout never permits a blind second exchange of a possibly spent refresh token. No run-long account lock and no second OAuth refresher.

On rejected access, first re-read canonical generation; a concurrently committed newer token can support one bounded retry. A genuinely expired linked login uses the common coordinator only when its state permits rotation. Repeated auth rejection, missing renewal material or unrecoverable state is actionable in Settings. A bare 403 does not prove expiry and must not trigger a refresh loop. Honor bounded `Retry-After`/backoff for 429 and transient errors. Last successful readings survive failed requests with their original observation timestamp.

**Re-authentication must restore collection.** At this baseline, `advanceCodexRefresh` returns `ErrCodexRefreshNoToken` without quarantining an account whose login lacks renewal material; `CodexReconciler.reconcileTuple` restores a replacement login only for a quarantined account. A fresh same-account import can therefore link back to the expired canonical blob. M1 must freeze and persist an account-level `reauth_required` discriminator separate from refresh coordination/quarantine; M2 consumes it to restore a verified replacement. The exact additive column/query layout is settled at the plan gate below. This is a required implementation change, not behavior claimed to exist today.

`reauth_required` records proven inability to use/renew the current canonical generation, including rejected expired access with no renewal material. Its unset state is not proof that a login is usable. Bind writes to the observed account generation and credential revision: an old HTTP failure must not mark newly refreshed/replaced material unusable. A timeout, 429, vault lock, missing client injection or bare 403 alone must not set it. It survives API restarts and duplicate imports, applies to generation-zero accounts with no run history, and is cleared atomically when a verified usable generation is installed. Preserve in-flight intents, quarantine and recoverable newer material as independent coordination states.

The canonical replacement predicate must handle `quarantined OR reauth_required`, subject to the existing recovery precedence, owner/identity checks, generation/credential-revision fencing and alias material-revision CAS. Being marked for re-authentication must not bypass an active refresh or overwrite recoverable newer state. Install the verified replacement, advance generation, clear the applicable re-authentication state and link the alias in one transaction; a failed link/restore CAS rolls back the replacement. Healthy duplicate imports retain canonical material. Plan-time coordination with #1171 decides which existing repair to reuse; #1209 remains responsible for the complete idle-account path if #1171 does not supply it.

### 2. Account identity, windows and freshness

Store a current snapshot keyed by owner plus canonical account, with a normalized collection of buckets/windows and the last successful observation time. Keep poll-health/last-attempt state separate from the last success. Discard results whose captured account/credential revision is obsolete; a replacement/relink during an HTTP request must not publish another account's reading. Account removal cascades its snapshot; deleting an alias leaves sibling aliases attached to the same reading. Serve only accounts with a currently visible owned alias. Never deduplicate across uzi users or expose raw provider account/user ids.

Present one budget per canonical account with its saved aliases, rather than counting duplicate imports as extra capacity. Each bucket carries its stable id and optional bounded display name. Preserve unknown extra buckets and partial windows without merging unrelated quotas. Main `rate_limit` becomes bucket `codex`; additional buckets keep their supplied identifiers. Reject ambiguous duplicate bucket ids and malformed known fields. A valid numeric zero is a reading; missing/null is unknown.

Use actual durations, not assumptions that primary means 5 hours and secondary means 7 days. Normalize durations as seconds and resets as nullable Unix seconds; use `reset_at` when valid, without fabricating an epoch from malformed/missing data. Show descriptive labels such as `5-hour`, `7-day`, or the reported duration. Keep primary/secondary role distinct when labels coincide. Validate percentages and numeric bounds; invalid windows never become a fresh zero. Clamp only the visual fill if a legitimate percentage exceeds 100, while retaining the displayed value. Whole-response failure must not overwrite a prior valid snapshot.

Statuses distinguish no saved subscription, pending verification, no reading, fresh, stale, vault locked, credential action required and polling disabled. No subscription returns an empty collection, not a fictitious zero row. API keys get a concise explanation in their credential surface that subscription windows do not apply; do not send API keys to this endpoint. Age beyond three effective polling intervals marks a reading stale; disabling polling makes any retained reading stale immediately. Vault lock stops credential access and collection and is visible even with a recent cached reading. Reset countdown reaching zero waits for a new reading; it must not clear the meter locally.

### 3. Owner/admin API and UI parity

Add separate owner/admin reads, proposed as `GET /api/me/codex-rate-limits` and `GET /api/admin/codex-rate-limits`. Keep the existing Claude `{tokens: [...]}` / `{users: [...]}` payloads intact. Define shared Go/web/CLI contracts with an opaque uzi account id, safe alias metadata, collection status, last-success time, staleness/poll health and normalized buckets. No login blob, access/refresh token, raw provider body, provider account id or internal coordination state reaches these DTOs. Reads are cached and do not synchronously refresh credentials; apply the existing owner/default-CLI and admin/admin-CLI authorization domains. Responses use private/no-store caching.

**Shared sidebar/TUI checkmarks (user clarification, 2026-09-08):** Settings exposes `Show in sidebar and TUI` for each linked Codex account, matching the existing Claude checkmark flow. The account containing the current default `codex_auth` alias is always included and its checkmark indicates that default rule; other accounts are opt-in. If the Codex default is an API key or an unlinked login, no subscription account is implicitly selected. A proposed separate `sidebar_codex_account_ids` user preference stores only the additional opaque account ids; an empty set means default-only. Preserve the existing Claude `sidebar_token_ids` and pool flags. Duplicate aliases share one checkmark/budget, and renaming an alias does not change the selected account. A default-account change recomputes only the implicit selection while retaining valid explicitly selected extras.

Persist the preference through the existing cookie-authenticated user-settings write and expose it through the existing owner/CLI-readable settings DTO. Validate and bound the whole submitted set: ids must belong to the current user's linked subscription accounts, never an API key or another user's account; deduplicate entries. Settings updates that omit the new field must preserve it. Deleted/unlinked accounts disappear from the effective selection and their stale ids are pruned without selecting another account. Both sidebar and TUI use the same persisted preference, refresh it through their existing settings-fetch paths, and retain the last known choice on a transient settings-read failure. A Settings toggle updates the web sidebar immediately after save; a running TUI applies it on its next settings refresh without restart. An unselected account becoming busy must not add itself. Settings and admin retain the full account inventory regardless of compact-view selection. The display choice never changes polling, credential defaults, run routing or quota eligibility.

### 4. Scope boundaries

Included: account visibility, automatic idle collection, safe renewal through the existing coordination core, duplicate-login attribution, all meter surfaces above, contract tests and operational documentation.

Excluded: Codex run enablement, harness conformance, worker app-server notification ingestion, run admission/parking/autoselect changes, cross-provider fallback, API-key RPM/TPM or billing dashboards, spend-control/credit balances, consuming reset credits, sending provider emails, new login/device-auth flows, custom endpoints, new services and worker image changes. Provider credit/limit-reached indications must not be described as guaranteed runnable capacity; this is a utilization view.

## Risks and decisions

- **Provider endpoint drift:** the backing HTTP endpoint is version-evidenced, not a stable public REST promise. Bound and isolate its decoder, ignore additive unknown fields, preserve last-good data on invalid known fields and provide truthful unavailable states.
- **Credential coordination conflict:** #1171 and this feature touch the same authority/refresh code. Land #1171 first; the implementation plan must name the internal principal and prove worker authorization remains intact. Never make run id optional on a worker refresh route.
- **Credential linking is not already wired:** saving a login currently leaves it `staging`. M2 owns the meter-side production trigger using M1's reconciler. Skipping this would produce a correct-looking dashboard that can never populate.
- **Alias is not quota:** account identity and budget deduplication are scoped to one uzi user; neither a different saved name nor a second login import creates capacity. Preserve workspace distinctions.
- **Visibility is not admission:** utilization, estimates and provider limit flags do not grant run eligibility and do not alter Claude selection/parking behavior.
