## Problem

Runs spend the user's own Anthropic tokens, but uzi is almost blind to consumption:

1. The SDK's terminal `result` frame carries full token accounting (`usage`: input/output/cache-read/cache-creation tokens; `modelUsage`: the same per model incl. `costUSD`), and the worker **drops all of it** — only `duration_ms`/`num_turns`/`total_cost_usd` are forwarded (`agent/src/sdk-messages.ts:113-115`).
2. What does survive (a per-phase `$x.yz`) is buried in the activity log finish line (`web/src/components/RunEvent.tsx:142-147`); there is no per-run total anywhere.
3. Failed runs report nothing at all: the error branch of `mapResult` forwards only `subtype` + `errors`, though the SDK error result carries the same `usage`/`total_cost_usd` fields — the runs most worth auditing are the least visible.
4. Nothing is aggregated: a user cannot see what they have consumed in uzi in total, and an admin cannot see what the whole factory (all users, all runs) has consumed.

## Solution Overview

Per the approved mock:

1. **Worker forwards token data**: `mapResult` passes `usage` + `modelUsage` through on both success and error result frames.
2. **API folds per-run usage**: on every result frame delivered to `AppendMessages`, the API upserts a `run_usage` snapshot table (latest-wins, idempotent) — server-side, no worker-protocol change beyond payload content; run/user/factory totals are sums over it.
3. **Run view**: usage strip in the header (tokens in with cache-hit bar, tokens out, duration, cost), collapsible per-phase table (one row per result frame), collapsible per-agent table ("coder: 800k out" — Decision 11), token counts on the activity-log finish lines.
4. **Runs list**: tokens + cost join each row's meta line; running runs show "so far" figures that update as phases complete.
5. **Dashboard, every user**: "Your usage" card — lifetime + last-7-days totals across their runs.
6. **Dashboard, admin only**: "Factory total" card (all users/all runs) + per-user breakdown table with share bars.

## Design Decisions

1. **Storage is a `run_usage` snapshot table upserted latest-wins — not SUM-columns on `runs`** (↳review: the original additive-fold-into-`runs`-columns design had an unfixable crash window, finding below; this shape follows multica's `task_usage` prior art — `inspiration/multica/server/migrations/032_task_usage.up.sql`, `server/pkg/db/queries/task_usage.sql` — per the inspiration-first convention). Schema: `run_usage(run_id FK→runs ON DELETE CASCADE, session_id text, model text, input_tokens, cache_read_tokens, cache_creation_tokens, output_tokens bigint, cost_usd numeric(12,6), updated_at, PRIMARY KEY (run_id, session_id, model))` — one row per SDK `query()` invocation per model, fed from the frame's `modelUsage` (per-model breakdown persisted for free; UI breakdown stays out of scope).
2. **The fold runs on EVERY delivered result frame, so it is idempotent by construction and has no crash window** (↳review, was the blocking finding). `workersvc.AppendMessages` (`api/internal/workersvc/service.go:593`) defensively parses each *delivered* (not just newly-inserted) `status`/`error` message for `payload.event == "result"` and upserts `run_usage` with `ON CONFLICT (run_id, session_id, model) DO UPDATE SET … = EXCLUDED.…` (latest snapshot wins). Why not fold only newly-inserted frames: the message insert and the usage write are separate statements (the `Store` interface exposes no transaction seam — the same constraint that shaped `CreateStopVerdictInput`, `api/internal/store/queries/runtime.sql:426`), so a crash between them would skip the fold forever on retry (the seq dedup that makes the append idempotent is exactly what would suppress the retry's fold). With upsert-on-every-delivery, an un-acked batch is retried by the worker and the re-delivered frame simply rewrites the same row — at-least-once delivery + idempotent write = correct totals. Malformed/absent usage → skip, never fail the append. No new worker→API endpoint. **↳M2: the `DO UPDATE SET = EXCLUDED` above (written for the expected verdict a) shipped as `GREATEST(run_usage.col, EXCLUDED.col)` instead — under M1's verdict (b, cumulative) a stable session_id can see two different cumulative snapshots land on the same key, so plain overwrite would let a crash-retry of an EARLIER frame regress the row; GREATEST is monotonic, keeping "re-delivery changes nothing" true. Consequence for M3: rollups take `MAX`/GREATEST per `(run_id, model)` (greatest-wins, NOT latest-by-`updated_at` — robust to out-of-order/replayed frames), then SUM across models; never a `SUM` over rows. Chat runs (`kind='chat'`) are skipped by the fold entirely (PRD #39 spend is out of scope).**
3. **Frame semantics (per-invocation vs cumulative-across-resume) are pinned by M1 before M2 builds anything** (↳review: the risk is real — multica found ACP usage frames are *cumulative* snapshots, `inspiration/multica/server/pkg/agent/hermes.go:1191`). Each phase is its own `query()` invocation resuming the prior session id (`driveTurn`, `agent/src/sdk-executor.ts:374-376`), and session ids evolve across turns. M1's experiment must cover BOTH same-process multi-turn resume AND cross-process resume from a persisted session id (the requeue path, `service.go:264-286`). The two possible outcomes map onto the same table with different rollup rules, so the storage shape survives either verdict: (a) *per-invocation deltas* (expected): run total = `SUM` over all rows; (b) *cumulative-across-resume*: rollup key collapses to `(run_id, model)` latest-wins, multica-style. No worker-side delta normalization in either case — the worker forwards raw SDK numbers, and server rollup + client per-phase table consume the same raw frames, so the two surfaces cannot diverge (↳review).

   **↳M1 verdict (2026-07-12): (b) CUMULATIVE-across-resume. PROVISIONAL — no live run (this environment has no Anthropic OAuth credential; the testing-credentials policy forbids live sessions), but the evidence is decompiled from the EXACT shipping CLI the SDK spawns (`@anthropic-ai/claude-agent-sdk-darwin-arm64/claude`, `manifest.json` version 2.1.201 / commit 5bb45156, spawned by SDK 0.3.201), so confidence is high.** Evidence chain (bundled CLI source): the terminal result frame is built reading a single process-global accumulator `qt` — `total_cost_usd: dy()` where `dy()=return qt.totalCostUSD`; `modelUsage: Fx()` where `Fx()=return qt.modelUsage`; and `usage: pts()` where `pts()` **sums over `Fx()`** (`Object.values(qt.modelUsage).reduce(...)`), so the top-level `usage` and `modelUsage` are the same accumulator. On resume the CLI **seeds** `qt` with the prior session's persisted totals before this invocation runs: `NWn(sessionId){ let t=NCo(sessionId); if(!t) return false; return XIt(t), true }`, where `NCo` reads persisted `{lastCost, lastModelUsage, lastSessionId}` and restores only when `lastSessionId===sessionId` (so the requeue path — cross-process resume from the persisted id, home dir preserved per PRD #42 — restores too), and `XIt({totalCostUSD, modelUsage, …})` writes `qt.totalCostUSD=…, qt.modelUsage=…`; a second in-conversation-setup restore `if(ll) XIt(ll)` sits in the session-init block alongside a `"fork"`-mode branch. This invocation's API responses then ADD on top (`fVp` does `r.inputTokens += t.input_tokens`, etc., into `qt.modelUsage`). Net: each phase's result frame reports the cumulative session totals up to that phase — consistent with `duration_ms`/`num_turns` also being per-invocation is NOT the case here; those are per-invocation while `usage`/`cost` are cumulative, because they read different state. **Consequence for M2: do NOT `SUM` result-frame rows — roll up latest-wins per `(run_id, model)` (Decision 1's `session_id` is in the PK, but since ids evolve per turn each carries a cumulative snapshot, so the rollup must take the latest/greatest per model, never a sum across sessions).** Recommended live confirmation when credentials exist: a two-phase run — phase-2's result `total_cost_usd` should be ≥ phase-1's (cumulative), not reset toward 0 (delta).

   **Decision 11 corollary (confirmed same-version):** the per-agent path is a DIFFERENT and correct data path precisely because the assistant frame's `message.usage` (`BetaUsage`) is **per-API-call**, not the cumulative `qt` accumulator — each API response carries its own usage (`fVp`'s argument `t`), and the accumulation into `qt` is a separate step. So summing assistant-frame usage per agent is correct, while summing result frames would over-count. Subagent assistant frames carry both `message.usage` and `subagent_type` on this SDK version (types: `SDKAssistantMessage.subagent_type?: string` + `message: BetaMessage` whose `usage` is non-optional, sdk.d.ts:2762; every assistant frame's `message` is an API-response `BetaMessage`, which always includes `usage`).
4. **Failed AND cancelled runs are counted** (↳review: cancelled added). The error branch of `mapResult` forwards `usage`/`modelUsage`/`total_cost_usd` too (the SDK's `SDKResultError` carries them), and the API folds `error`-kind result frames the same as `status`-kind ones. `AppendMessages` deliberately keeps no terminal-status guard: a result frame landing after a mid-flight cancel still folds — pre-cancel spend is real spend. A run that burned $3 before dying must show $3.
5. **Per-phase detail comes from the message stream, not new storage.** The run view already replays all messages (REST `?after=<seq>`, no LIMIT — full replay; + ws); the per-phase table and finish lines derive client-side from the result frames in that stream. `run_usage` exists so lists and rollups stay cheap queries, not to feed the phase table.
6. **Rollups are aggregate queries over `run_usage`**: per-run totals join a `SUM … GROUP BY run_id` into the run list/detail queries; `GET /api/usage` (self: lifetime + last-7-days totals, run count) and `GET /api/admin/usage` (factory totals + per-user rows) `SUM` over `run_usage` joined through `runs` to `users`. Pre-feature runs simply have no rows → the UI shows nothing (never a fake 0). At laptop scale this needs no denormalization.
7. **Visibility: self-only for users, everything for admins.** "Your usage" shows only the requesting user's runs. The factory total and per-user breakdown are admin-only (`/api/admin/usage`, admin-gated like the existing admin endpoints). Non-admins never see other users' consumption. **Trust caveat (↳M2 audit):** every figure in `run_usage` is self-reported by the run's worker (the fold trusts the frame's `modelUsage` numbers), so the factory/per-user rollups — and M3's admin endpoint that surfaces them — inherit that trust: a compromised worker can misreport its own runs' spend. This is an accounting/reporting surface, not an authorization one; it is not a basis for billing or enforcement (Decision 8 already frames cost as an estimate).
8. **Tokens are the headline, cost is secondary.** The SDK's `total_cost_usd` is an estimate (API-key pricing; subscription-auth users may see $0). The UI leads with token counts (always true) and shows cost alongside when present; a $0.00 cost with nonzero tokens renders as "—".
9. **Live updates ride the existing ws stream.** Usage changes exactly when a result frame is broadcast; the run view folds incoming frames into its local totals, and the runs list refreshes on its existing cadence. No new ws message kinds, no polling.
10. **One shared token formatter.** A `formatTokens` helper (`web/src/lib/`) renders 999→"999", 48_200→"48.2k", 1_280_000→"1.28M" with `tabular-nums`; every surface uses it so figures read identically across the app.
11. **Per-agent attribution is client-derived from assistant-frame usage — no storage change** (user request 2026-07-12: "coder used 800k"). The result frame carries only a query-level usage total + a per-model breakdown — no per-agent field exists on its type (subagent-inclusion semantics are confirmed alongside the M1 experiment); but every SDK assistant frame carries the API call's `message.usage` (SDK `SDKAssistantMessage.message: BetaMessage`) plus the existing attribution key `subagent_type` (already consumed by `agentOf`, `agent/src/sdk-messages.ts:28`). The worker attaches that frame's `usage` to **exactly one** emitted run message per SDK frame — and the attach happens **executor-side, on the first message that survives the signal filter**, not inside `mapAssistant` (↳review: the executor drops signal `tool_use` messages *after* mapping — `submit_plan`/`signal_done`, `sdk-executor.ts:473-476` — and every phase terminates on such a frame; attaching to `mapAssistant`'s first output would systematically lose the lead's highest-context frames whenever the terminating frame has no preceding text/thinking block). `mapAssistant` explodes one frame into N messages, so attaching to all would multiply the sums. Assistant usage is **client-only**: `AppendMessages` folds only `payload.event == "result"` frames into `run_usage` and must never fold assistant usage — the server rollup and the per-agent table are deliberately different data paths (↳review). The run view groups persisted messages by `agent`, sums per-call usage, and renders a per-agent table next to the per-phase one (Decision 5 pattern: full unbounded replay makes it complete, incl. failed/cancelled runs whose frames landed before death). The per-agent rows are a **pure reduction over the seq-deduped message list**, recomputed from state — never an incremental ws-fed accumulator, which would double-count on the ws→reconnect→REST-replay overlap (↳review; same rule as the per-phase table). `BetaUsage` fields other than `output_tokens` are nullable — the client sum coalesces null→0, and the shape differs from `ModelUsage` (snake_case/nullable vs camelCase/non-null), so the web types handle both (↳review). Caveats, by design: (a) per-agent figures are *attribution*, and the table must not be forced to reconcile with the usage strip — divergence sources: frames whose every mapped message is filtered (signal-only frames), frames with only unmapped blocks, compaction/summarization API calls, and refusal-fallback `supersedes` replacements (both the superseded and replacement frames persist with usage, so the table can double-count what the strip doesn't; rare, accepted — ↳review); (b) tokens only, no per-agent cost — per-call usage has no cost field and `modelUsage` splits by model, not agent; (c) per-agent stays per-run detail — no cross-run per-agent rollups (out of scope).

## Technical Design

### agent (worker)

- `agent/src/sdk-messages.ts` `mapResult`: success payload gains `usage` + `modelUsage` (unguarded passthrough, same style as `num_turns` — absent fields vanish in JSON serialization); error payload gains `usage`, `modelUsage`, `total_cost_usd`, `num_turns`, `duration_ms`.
- `agent/src/sdk-executor.ts` `driveTurn` emit loop: the frame's `message.usage` is attached to the first emitted message that **survives the signal filter** (Decision 11 — ↳review, not inside `mapAssistant`, which cannot see the executor-side drop of `submit_plan`/`signal_done` tool_use messages) — one usage record per SDK frame regardless of how many blocks it explodes into; a frame whose every message is filtered loses its usage (Decision 11 caveat a).
- Tests (`agent/test/`): success and error frames carry usage through; malformed/absent usage yields payloads without the keys; assistant-frame usage lands exactly once per frame (multi-block frame → one `usage`); signal-first and signal-only terminating frames (usage lands on the surviving message / is dropped without error — ↳review); subagent frames keep their `subagent_type` attribution alongside usage; the Decision-2 semantics experiment.

### api

- Migration (draft `00052_run_usage.sql` — **renumber to the live head at merge time** per the repo convention): the `run_usage` table (Decision 1).
- `api/internal/store/queries/`: `UpsertRunUsage` (latest-wins, Decision 2), run list/detail selects extended with `SUM … GROUP BY run_id` totals, `SelfUsage` + `AdminUsage` aggregates; `sqlc generate`.
- `api/internal/workersvc/service.go` `AppendMessages`: for every *delivered* message (including seq-deduped replays), defensively parse result-frame usage and upsert `run_usage` (Decision 2). Unit tests: totals across multi-frame runs, replayed-batch convergence (re-delivery rewrites identical rows — the crash-retry path), error-frame folding, malformed-payload no-op.
- `api/internal/handler/`: run list/detail responses gain the usage fields; new `GET /api/usage` (session-authed) and `GET /api/admin/usage` (admin-gated). Handler tests.

### web

- `web/src/lib/api.ts`: usage fields on `RunListItem`/run detail; `UsageSummary` + admin types; the two new calls.
- `web/src/lib/formatTokens.ts` (+ tests): Decision 10.
- `web/src/pages/RunView.tsx`: header usage strip + collapsible per-phase table (client-derived, Decision 5) + collapsible per-agent table (client-derived group-by-`agent` sum over assistant-frame usage, Decision 11 — pure reduction over the deduped message list, null-coalescing `BetaUsage` fields), live fold-in of ws result frames (Decision 9); per-agent rows update as messages stream because the reduction re-runs, not via an accumulator (↳review).
- `web/src/components/RunEvent.tsx` `describeStatus`/finish line: token bits join duration/turns/cost; error result lines show tokens too (Decision 4).
- `web/src/pages/RunsList.tsx`: tokens + cost in the row meta line (hidden when the run has no usage rows, Decision 6).
- `web/src/pages/Dashboard.tsx`: "Your usage" card for everyone; admin-only "Factory total" card + per-user table per the mock.
- Vitest for each surface; existing RunEvent/RunsList/Dashboard tests updated, not deleted.

### e2e

- ↳review: the stub executor (`agent/src/executor.ts`) emits NO result frame today — only `status` text frames; the real result frame exists only on the SDK path. M6 *adds* a synthetic result-frame emission (`event: "result"` with fixed usage numbers) to the stub, then `e2e` asserts the numbers land on the run and in `/api/usage`.
- ↳review (Decision 11): the stub also gains a synthetic usage-bearing assistant-style message with `agent: "coder"` + `payload.usage`, so e2e exercises the persist→replay→group-by-agent path; without it no integration test would touch the per-agent table despite it being a headline success criterion.

## Review notes (verified non-issues)

- No result-frame path bypasses the fold point: frames reach the DB only via `ctx.emit` → `WorkerRunMessages` → `AppendMessages`; run completion, the sweeper, requeue, and register carry no usage.
- Full-run message replay is unbounded (`ListRunMessagesAfter` has no LIMIT), so the client-derived per-phase table can never be truncated; the LIMIT 200/500 elsewhere are run-*list* caps.
- Resume after requeue does NOT re-persist old frames (new turns get new gapless seqs), so there is no replay-of-old-frames double count; the only semantics risk is Decision 3's cumulative-vs-delta question.
- `/api/usage` and `/api/admin/usage` fit the existing session-authed and `RequireAdmin` route groups respectively; neither path exists today.

## Out of Scope

- Per-model breakdown **UI** (the data is persisted in `run_usage` rows for free; no surface renders it yet).
- Per-agent **cost** and cross-run per-agent rollups (Decision 11 caveats b/c — per-agent is tokens-only, per-run detail).
- Budgets, quotas, alerts, or any enforcement based on usage.
- Backfilling pre-feature runs (their columns stay NULL; the stream data to backfill from mostly doesn't include usage anyway).
- Per-repo rollups and time-series charts (the aggregates make them easy follow-ups).
- Counting tokens spent outside runs (e.g. the PRD #39 chat agent) — that feature should reuse these columns' pattern when it lands.

## Success Criteria

- Every run started after this lands shows tokens in/cached/out + cost on its run view, list row, and finish lines — including failed and cancelled runs.
- A run that used subagents shows a per-agent token breakdown on its run view (e.g. "coder — 800k out"), attributed via `subagent_type`, with the lead as its own row; rows exist only for agents with usage-bearing assistant frames.
- A user's dashboard total equals the sum of their runs' totals; the admin factory total equals the sum over all users.
- Worker retries / message replays never double-count (pinned by tests).
- Pre-feature runs render without usage UI — never a fabricated 0.
- Implemented UI passes the M6 side-by-side against the approved mock; `go test ./...`, `npm test`, `npm run typecheck`, agent tests, and e2e all green.
