## Problem

PRD #95 gave the activity pane (`web/src/components/ActivityFeed.tsx`, mounted at `RunView.tsx:394`) a crew roster strip and collapse-by-default logs. It left the **feed itself** with two structural UX failures the user reported directly (screenshot: a run of `lead / researcher / lead / researcher / …` bars, most of them empty):

1. **The feed shows the same agents over and over.** `groupByAgent` (`ActivityFeed.tsx:40`) starts a new block on every switch of the **consecutive** message author (`if (last && last.agent === agent) last.messages.push … else groups.push(…)`). A normal orchestration ping-pong — lead delegates, a subagent runs, lead delegates again — therefore renders as a tall stack of blocks that are really 2–3 agents. Worse, the live one-liner is attached only to an agent's **first** block (`oneLiner={firstBlock ? agentOneLiner(...) : ""}`, `ActivityFeed.tsx:447`), so every repeat block is a near-empty bar carrying just a coloured name + a timestamp. The pane looks busy and duplicative while saying almost nothing.

2. **Two parallel subagents of the same role are indistinguishable, and would silently merge.** The lead can emit multiple `Agent` tool_use blocks in one turn, so two `coder` subagents run at once. But attribution stops at the role name: `agentOf(msg)` returns `msg["subagent_type"] ?? "lead"` (`agent/src/sdk-messages.ts:28`), and the whole wire carries only `agent: string | null` (`OutgoingMessage`, `agent/src/protocol.ts:511` → `IncomingMessage`, `api/internal/workersvc/service.go:872` → `run_messages.agent`, `00020_workers_runs.sql:75` → `MessageDTO.Agent`, `api/internal/apitypes/run.go:118` → `RunMessage.agent`, `web/src/lib/api.ts:1022`). Both coders emit `agent:"coder"`. Any "aggregate the feed by agent name" refactor — the obvious fix for Problem 1 — would collapse their interleaved messages into one garbled `coder` lane. **The data needed to tell them apart is thrown away**, even though the SDK provides it (`parent_tool_use_id` + `task_description`, both dropped at `sdk-messages.ts:28`).

The roster strip from PRD #95 partially de-dupes the *header* (it lists unique agent roles with dots), but the **feed below it does not**, so the same information appears twice — once clean, once noisy — which is itself the duplication the user is objecting to.

## Solution Overview

Rebuild the feed around **one lane per real actor (invocation)**, key identity to the subagent's SDK **`parent_tool_use_id`** and its label to the SDK's **`task_description`** (two nullable columns, both stateless per-frame fields), and make the roster **conditional** so it stops duplicating the lanes.

- **Instance lanes.** A lane is one actor's whole contribution, keyed by `agent_instance` (`= parent_tool_use_id`; the parentless lead is its own lane). Non-adjacent turns coalesce into their lane instead of spawning a fresh bar, so the ping-pong stops multiplying. Each lane keeps the #95 accordion body, the live one-liner (now on the lane, not just its first block), the `+N` unseen pill, and expand/collapse.
- **Task labels from the SDK, per frame — no client-side join, no window dependency.** A subagent lane is titled `coder · <task>` where `<task>` is `agent_label` (`= task_description`, "Description of the subagent task that produced this message", `sdk.d.ts:2777`), carried on every subagent frame exactly as `agent`/`subagent_type` is. Two coders become `coder · web gate UX` and `coder · API wiring`: distinct, named by *what* they do, and correct even when the spawning turn scrolled out of the window.
- **A status dot on every lane.** Each lane header carries the #95 `crewStateFor` dot (`working / stalled / waiting / idle / done`, `ActivityFeed.tsx:77`/`:102`), so a **collapsed** lane still shows whether that actor is live. The word beside the dot is the label; there is **no standing legend** (a `title` tooltip reinforces the colour).
- **The roster becomes conditional, and re-roled as a summary.** With every lane carrying a dot, the always-on crew strip now duplicates the lane list. So: in **By-agent** view there is no separate strip when the crew is small — the collapsed lanes *are* the roster; a slim **role rollup** (`coder ×2 ● working · tester ×2 ● stalled · …`, worst-state wins the dot, click filters) appears **only** when a role has ≥2 instances or lanes overflow the glance. In **Timeline** view (the raw chronological stream, one toggle away) the roster stays as the navigation/jump aid it is today.
- **Two columns, threaded; everything else client-side.** The only backend change is two nullable `run_messages` columns (`agent_instance text`, `agent_label text`) plus threading them through the message wire and the live `message` WS frame. The worker emits both as **pure per-message fields** (`parent_tool_use_id` + `task_description` are on every complete SDK assistant/user frame) — no worker-side correlation state. Lane grouping, the dot, the toggle, and the rollup are all `web/`.
- **Graceful for old runs and the lead.** Both columns are NULL for the lead and for every pre-migration message; the web falls back to the role name as the lane key and drops the `· task` suffix. No backfill.
- **CLI parity in the same MR** (CLAUDE.md "second consumer" rule): `--json` parity is free the moment M1 lands (the CLI marshals `MessageDTO` verbatim); the human line format gains the instance/label.

## Design Decisions

1. **Identity AND label are both stateless per-frame SDK fields, persisted as two nullable columns — no worker state, no client-side join, no dependency on the spawn frame [C1].** SDK 0.3.201 (pinned) puts on every complete assistant/user frame, top-level and alongside `subagent_type`: `parent_tool_use_id: string | null` (the invocation id, `sdk.d.ts:2765`/`:4295`) and `task_description?: string` ("Description of the subagent task that produced this message", `sdk.d.ts:2777`). Both are read exactly as `agentOf` already reads its sibling `msg["subagent_type"]` (`sdk-messages.ts:28`): pure, per-message, no correlation map, correct across resume. uzi already persists only complete frames — partial `stream_event` frames are intentionally dropped (`sdk-messages.ts` header comment). So identity = `parent_tool_use_id` (→ `agent_instance`), label = `task_description` (→ `agent_label`); the lead and every pre-migration frame carry NULL for both, and two parallel `coder` invocations get distinct ids + their own labels. **Rejected alternative — persist only `agent_instance` and derive the label client-side** from the lead's spawn tool_use `description` (via `toolSummary`/`buildToolIndex`, `RunEvent.tsx:86`/`:388`): it saves one column but (a) shows no label when the spawn frame is older than the cap-and-expand window (`CAP_VISIBLE=500`); (b) depends on the pane's spawn-tool parsing, which currently switches only on the legacy `"Task"` name while the live tool is `"Agent"` (`guardrails.ts:71`/`:583`, canonicalized `repoagents.ts:71`) → a dead path for live runs; and (c) leans on the unverified `parent_tool_use_id == spawn tool_use id` equality (that forwarding lives in the native CLI binary, not `sdk.mjs` — PLAUSIBLE, not locally confirmed). The `task_description` column sidesteps all three — the label is on the frame itself — for the cost of one nullable column denormalized exactly as `agent` already is. That trade tips to two columns.

2. **A lane aggregates all of an instance's frames — a deliberate, scoped change to the feed's ordering, with the raw stream one toggle away.** Today the feed is a strict chronological transcript (`groupByAgent` over `visible` in seq order). Grouping by instance means a lane's body is chronological *within the instance*, but two lanes are no longer globally interleaved by seq — the "aggregate by name" the user asked for. This is a genuine behaviour change to existing functionality (CLAUDE.md: confirm before changing) — it is the explicit user request, recorded here as authorized. The escape hatch: a **`By agent` / `Timeline`** segmented toggle in the pane header. `By agent` (default) is the new instance-lane view; `Timeline` renders today's chronological, per-consecutive-run grouping verbatim (the existing `groupByAgent` path, kept, not deleted) for anyone debugging cross-agent interleavings. The lane key is `m.agent_instance ?? m.agent ?? "lead"`, so the lead and any NULL-instance (pre-migration) message fall back to a per-role lane.

3. **The per-lane dot reuses `crewStateFor` verbatim; the state model does not change, only its rendering site multiplies.** PRD #95's ladder (`ActivityFeed.tsx:77`) already computes `working / stalled / waiting / idle / done` from `run.status` + `run.health` + recency, and the active-speaker `working` trusts `run.health` (#95 Decision 2/B2, unchanged). v3 computes it **per lane** and renders the dot on each lane header (not only on the roster chips). The active speaker is still "the agent of the newest message while live"; extended to instances, it is the *instance* of the newest message, so exactly one lane pulses. `CREW_TONE` (`:102`), the `animate-pulse` + `prefers-reduced-motion` neutralization (`index.css`), and the empty-state placeholder all carry over. **No new state, no new backend for state.**

4. **No standing legend; the state word beside the dot IS the label, with a `title` tooltip.** A persistent five-swatch legend is redundant when every dot is labelled in situ ("● working", "● idle"). The pane renders the state word next to each dot (as the roster chips already do, `ActivityFeed.tsx:399`) and adds the mapping as a `title` on the dot for reinforcement. This is a deliberate *removal* of chrome, not an omission. (The mockup keeps a compact state key only as reviewer documentation, folded into a single card — not a product element.)

5. **The roster stops being an always-on fixture and becomes a conditional, higher-altitude role rollup — because per-lane dots make the old strip a duplicate.** With Decision 3, a collapsed lane already shows name + dot + state, which is exactly what the #95 crew chip showed. Rendering both (the `crew.order.map` strip at `ActivityFeed.tsx:369` **and** the lane headers) reintroduces the very duplication this PRD removes. Resolution, by view:
   - **By-agent view, small crew** (no role has ≥2 instances **and** lane count ≤ a glance threshold, ~6): **no strip.** The collapsed lanes are the roster. `crew.order.length`-gated affordances (Expand/Collapse all) stay in the header.
   - **By-agent view, busy crew** (any role has ≥2 live instances, or lanes exceed the threshold): a **role rollup** bar — one chip per *role* (not per instance) with a count (`coder ×2`) and a single dot whose state is the **worst** among that role's instances (attention-priority: `stalled > waiting > working > idle > done`), so a stalled tester surfaces first. Clicking a role filters/scrolls to its lanes. This is a real summary tier the per-instance lanes cannot provide, so it is not a duplicate.
   - **Timeline view**: the roster stays as-is (the PRD #95 jump strip) — in a scattered chronological stream a fixed status+jump strip is still the best navigation, and the rollup's "collapse repeats" value does not apply.
   This "earn its place, never a gate" conditionality mirrors the repo's own posture on the agent roster (CLAUDE.md: a nudge, not a fixture).

6. **The live `message` WS frame must carry both columns, mirroring how it already carries `agent`.** The browser renders a `message` frame's payload directly — `useRunStream` builds the `RunMessage` straight from the frame (`agent: frame.agent ?? null`, `useRunStream.ts:91`), no REST re-read — so a live subagent frame can only land in the correct lane if the frame itself carries the id + label. The hub `Event` (`hub/hub.go:32`, `Agent *string`) and `hub.PublishMessage` (positional `agent`, `hub.go:100`) grow `agentInstance`/`agentLabel`; the web `WsEvent` (`api.ts:1071`) grows them too — a straight parallel to the existing `agent` field, no new mechanism. REST replay (`ListRunMessagesAfter`, `runtime.sql:584`) also returns the columns, so reconnect/replay places lanes identically. A dropped `message` frame self-heals via the existing seq-gap replay (PRD #95), so a live lane frame is at worst delayed, never lost.

7. **Label is untrusted-ish text and is truncated + rendered plain, never as markdown.** `task_description` is authored by uzi's own builtin `lead` (not the repo), so it is model-generated, not attacker-supplied. Still, it is rendered as a plain, single-line, `truncate`d string in the lane header (as `toolSummary` already does via `firstLine`, `RunEvent.tsx`), never through `<Markdown>` — consistent with how repo-supplied agent descriptions are handled at the plan gate (PRD #37). No new escaping surface.

8. **Degradation is explicit, not silent.** Three cases, all falling back visibly rather than merging wrongly:
   - **Lead / pre-migration messages** (both columns NULL): lane key falls back to `agent` role name — **one lane per role**. For a legacy `lead/researcher/lead/researcher` run this **coalesces into one lane per role**, i.e. the intended Problem-1 fix, NOT today's per-consecutive-run rendering (`ActivityFeed.tsx:40`). This is a deliberate re-render of history under the By-agent default; the `Timeline` toggle reproduces today's exact rendering [C3]. No backfill migration.
   - **Label absent** (`task_description` unset on a frame): lane shows the role name **without** a `· task` suffix (still distinct by instance id). No window dependency (the column, not a client join, supplies the label).
   - **Resume**: both fields are per-frame with no worker state, so a resumed worker labels correctly going forward; already-persisted messages keep their stored values.

9. **Frontend-heavy: one migration (two columns) + a wire thread, then agent and web work in parallel.** The schema/wire change (M1) is small and shared; after it lands, the worker capture (M2, `agent/` only) and the pane rebuild (M3, `web/` only) touch disjoint files. Migration numbering follows the house rule (draft `00074`, above the live head `00073`; renamed to the next free number at landing — `api/internal/store/migrate.go` is strict goose).

10. **CLI parity (CLAUDE.md "second consumer"), correctly scoped.** The CLI does not group — `renderMessage` (`api/cmd/uzi/run.go:489`) prints one line per message with an `agent` column, and `--json` marshals `MessageDTO` verbatim, so **JSON parity is free the moment M1 lands** and there is no "silent merge" to prevent. M4's real scope is adding the instance short-id + label to the human line format so two same-role coders read distinctly in `uzi run watch`/`show`.

11. **Subagent lanes carry tool activity only, unless `forwardSubagentText` is flipped — a documented current limit and the obvious companion knob [C4].** The SDK forwards only `tool_use`/`tool_result` from subagents by default; text/thinking are dropped unless `forwardSubagentText: true` (`sdk.d.ts:1588`). uzi does not set it (`sdk-executor.ts:329` sets only `includePartialMessages: false`), so a subagent lane's body today holds its tool rail but none of its prose — and part of *why* Problem 1's bars look empty is that subagent prose never reaches the stream. This PRD does **not** flip it (that changes message volume + token cost, so it is not bundled blindly), but flags it as the natural follow-up: with instance lanes in place, `forwardSubagentText: true` is what fills them.

**Interactions (for completeness):** **Chat / judge / self-improve runs** put `NESTED_AGENT_TOOL` (`"Agent"`) in `disallowedTools` (`chat-executor.ts:249`, `repoagents.ts:65`), so they never produce a non-null `parent_tool_use_id` → they render as a single lead-keyed lane, unaffected. **The steer queue, plan gate, health chips** (PRD #95/#47) are untouched — this PRD changes only how the message feed is grouped/labelled and how the roster is gated. **The forge / board cache** are not touched (no forge read or write anywhere in this PRD). **Usage accounting** (PRD #40, per-seq `phaseUsageBySeq`) is keyed by seq and is orthogonal to grouping.

## Success Criteria

- A run that today shows a stack of `lead / researcher / lead / researcher / …` bars (most empty) renders as **one lane per actor**, each with a live one-liner and a status dot — the empty repeat bars are gone.
- **Two `coder` subagents running in parallel appear as two distinct lanes**, titled by their task (`coder · web gate UX`, `coder · API wiring`) from `agent_label`, never merged into one `coder` block; their interleaved messages land in the right lane live (via the WS frame's `agent_instance`) and on reconnect (via replay).
- Every **collapsed** lane shows whether that actor is `working` (exactly one pulsing) / `stalled` / `waiting` / `idle` / `done`, with no standing legend.
- The roster **is not shown** for a small By-agent crew (the lanes are the roster); a **role rollup** appears only when a role is doubled or lanes overflow, surfacing the worst state first; `Timeline` view keeps the jump strip.
- A **legacy run** (messages with no `agent_instance`) renders as **coalesced role lanes** under By-agent (the intended fix) and reproduces **today's exact per-consecutive-run rendering** under `Timeline` [C3]; **chat / judge** runs render as a single lead lane. No backfill.
- No new forge call, no token spend, and no change to the steer queue / plan gate / health surfaces.

## Risks

- **Behaviour change to the feed's ordering (Decision 2, [C3]).** By-agent grouping trades the global cross-agent timeline for de-duplication, and re-renders legacy runs; mitigated by the `Timeline` toggle (raw stream retained) and by it being the explicit user request. Revisit if users relied on the chronological default.
- **Subagent lanes are prose-empty until `forwardSubagentText` (Decision 11).** A lane may show only a tool rail; the companion knob is flagged as follow-up, not bundled (cost/volume change). No regression versus today.
- **`parent_tool_use_id == spawn tool_use id` is unverified** (native CLI binary). No longer load-bearing — the label comes from `task_description`, not a join — so this is informational, not a risk to the label.
- **SDK drift on `parent_tool_use_id` / `task_description`.** A reshape degrades `asString(...)` to `undefined` → NULL columns → role-fallback lane (today's behaviour), never a crash — the defensive-probe posture `sdk-messages.ts` already uses.
- **Provisional issue number.** This file is `#99` by guess (forge unreachable at authoring); reconcile with the real GitLab issue iid and rename the file + mockup before the issue is created.
